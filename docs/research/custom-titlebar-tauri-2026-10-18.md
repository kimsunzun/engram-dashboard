# 크롬식 제목 표시줄 — Tauri v2 · WebView2 구현 선택지 조사 (2026-10-18)

> **상태:** 조사 끝 · 결정 대기(T-66 — `docs/tracking.md`). 설계-결정 모드 · medium.
> **방법:** 수집 4 갈래(피어 OSS · 플러그인 / Windows 11 · WebView2 · Tauri 수단 / 창 끌기 영역과 HTML5 끌어 놓기 / 적대 리뷰가 짚은 누락 — 스냅 플러그인 셋 · Windows App SDK · `shadow`) → 메인 합성 · grounding(로컬 의존성 소스 · GitHub API) → cross-family 적대 리뷰 1 차 BLOCK → 누락 수집 · 고침(아래 「적대 리뷰」).
> **확신도 범례:** 확실 = 1차 출처(소스 · 공식 문서)로 확인 · 가능성 높음 = 1차 출처 하나 또는 읽었으나 돌려 보지 않음 · 불확실 = 간접 · 미검.
> **우리 버전:** `tauri` 2.11.3 · `tauri-runtime-wry` 2.11.3 · `wry` 0.55.1(`Cargo.lock`).

## 결론

1. **창 끌기 · 빈 곳 더블클릭 최대화 · 크기 조절 테두리는 Tauri 코어가 준다 — 단 권한을 더해야 한다.** 탭바의 빈 자리 요소에 `data-tauri-drag-region` 을 달면 그 요소 자신을 누를 때만 끌기가 시작되고(자식인 탭 머리 · 단추는 건드리지 않는다) 두 번 누르면 최대화를 뒤집는다. 그 스크립트가 부르는 `start_dragging` 권한(`core:window:allow-start-dragging`)이 지금 capability 에 없다(`src-tauri/capabilities/default.json` · `popup.json` — `core:default` 만 · `internal_toggle_maximize` 는 `core:default` → `core:window:default` 에 이미 들어 있다 — `tauri-2.11.3/permissions/window/autogenerated/reference.md`). — 확실
2. **Windows 11 스냅 레이아웃(최대화 단추 위에 올리면 뜨는 배치 고르기)은 Tauri 에 없다**(tauri#4531 · 2022 년부터 열림). 조사한 오버레이 플러그인(아래 3 절)은 전부 **HTML 최대화 단추 위에 투명 Win32 자식 창을 덮고 그 창이 `WM_NCHITTEST` 에 `HTMAXBUTTON` 을 돌려주는** 꼴이다(소스 확인 — 합성 호스팅으로 가는 Wails v3 같은 다른 길은 wry 변경이 필요하다). 단추 위 올림 · 누름은 그 자식 창이 받으므로 웹으로 중계해야 한다. 큰 Tauri 앱들(Yaak · Cap · GitButler · Clash Verge Rev · Hoppscotch)은 메뉴를 포기하고 HTML 단추만 쓴다. — 확실(메커니즘) · 가능성 높음(큰 앱들)
3. **그 오버레이는 의존으로 들이기보다 `platform` 에 옮겨 짓는(MIT 귀속 유지) 편이 맞다.** 가른 기준은 셋이다 — ① 우리 HTML 단추 · 우리 사각형을 받는가(`decoration` 은 단추를 플러그인이 만들어 탈락 — 시험 · e2e 가 갖춰진 것은 그쪽뿐이다) ② 사용 이력(남은 둘은 각 6★ · 0★, 생성 2026-05 · 2026-10, 실사용 보고 없음) ③ 우리 규칙(OS 코드는 `platform` 한 곳 · 새 전역 핸들 금지 · 창 생성은 `WebviewEnv::finish` 한 곳)과 맞추는 비용. 옮길 Win32 코어는 160–360 줄 규모다. — 가능성 높음
4. **탭 끌기와의 관계:** Tauri 방식의 끌기 영역은 **누름 판정에서** 탭 머리를 건드리지 않는다(확실). 다른 창에서 끌어온 탭을 그 빈 자리에 놓는 것 · 끌기 세션 유지는 돌려 보지 않았다(불확실 — 끌기 영역은 사건을 막지 않는 평범한 요소라 막을 이유는 보이지 않는다). CSS `app-region: drag` 방식은 그 영역이 비클라이언트가 되어 놓기가 닿는지 아무도 확인하지 않았다.
5. **피할 것:** `tauri-plugin-decorum` 의 스냅 = Win+Z 가짜 키 입력 · WebView2 Window Controls Overlay = 실험 판 · Windows App SDK 제목 표시줄 = Rust 투영 · 런타임 의존이 무겁고 선례 없음.

## 1. 우리 제약 (CLAUDE.md · 코드)

- 창을 만드는 코드는 전부 `src-tauri/src/webview_env.rs` 의 `WebviewEnv::finish` 를 지난다(ADR-0283) — 테두리 없음 · 그림자는 그 한 곳에서. 팝아웃은 런타임에 만든다.
- OS 마다 다른 운영 코드는 `platform` crate 안에만(ADR-0266) — 스냅 오버레이는 그 crate 의 목적 모듈 하나.
- 「LLM-우선 제어」 — 최소화 · 최대화 · 닫기는 사람 단추와 LLM 이 같은 핸들(버스 명령)을 흔든다. 웹이 Tauri 창 API 를 직접 부르면 두 번째 표면이 된다. 새 전역 핸들을 늘리지 않는다.
- 탭 머리는 HTML5 `draggable`(순서 이동 · 슬롯 도킹). 웹뷰 드롭 처리기는 꺼 두었다(`dragDropEnabled: false` · `disable_drag_drop_handler()`).
- capability = `core:default` 등뿐(`src-tauri/capabilities/default.json:6` · `popup.json:6`) — 창 끌기(`core:window:allow-start-dragging`) 권한 없음 · 최대화 뒤집기는 기본에 있다.

## 4. 선택지

**추천 = ① 로 시작하고 스냅 메뉴가 필요하면 ② 를 같은 단계의 둘째 조각으로.** ① 은 탭바 · 단추 · 창 옵션 · 권한 하나이고, 최소화 · 최대화 · 닫기는 웹이 Tauri 창 API 를 직접 부르지 않고 버스 명령을 지난다(LLM 이 같은 핸들). ② 의 웹 쪽(단추 사각형 넘기기 · 올림/누름 받기)도 같은 버스 · 사건 길을 쓰고 전역 핸들을 늘리지 않는다. **스냅 메뉴가 꼭 있어야 하나는 사용자가 정한다**(체감 기능).

## 5. 미확인 · 다음에 잴 것

- 끌기 영역(빈 탭바 자리) 위로 다른 창의 탭을 놓을 때 `dragover`/`drop` 이 닿는가 · tauri#10767 이 슬롯 도킹 끌기 상태와 얽히는가 — ① 구현 뒤 실측.
- 오버레이 플러그인 셋은 빌드 · 실행해 보지 않았다 — 스냅 메뉴가 실제로 뜨는지는 README · 데모 · 소스 읽기 기준.
- 스냅 오버레이의 최소 창 폭 조건(330–500 px 보고 — Zbrooklyn) · Windows 10 동작.
- 팝아웃 창도 같은 크롬을 쓰는가(지금 팝아웃은 OS 제목 표시줄) — 범위 결정.
- VS Code · Windows Terminal 의 Windows 쪽 구현은 읽지 않았다.

- **1 차(codex · cross-family) = BLOCK** — 반영함: ① 끌기 영역에 필요한 권한이 capability 에 없다(치명 — 결론 1 · 1 절 · 2 절) ② 스냅 플러그인 셋 누락(추가 수집 → 3 절) ③ WCO 행의 x86 실패 오귀속(그것은 별도 네이티브 시도 — 고침) ④ 「탭 끌기와 충돌 없음 = 확실」 과장(누름 판정까지만 확실로 낮춤 — 결론 4) ⑤ 「구현은 전부 같은 꼴」 과장(진짜 메뉴를 띄우는 것으로 좁힘) ⑥ `app-region` 조건(런타임 `Settings9`) ⑦ `shadow` · Windows App SDK 누락(2 절) ⑧ 출처 링크 없음(자료 절).
