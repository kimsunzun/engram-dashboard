# Chrome-style title bar — survey of implementation options for Tauri v2 · WebView2 (2026-10-18)

> **Status:** survey done · awaiting decision (T-66 — `docs/tracking.md`). Design-decision mode · medium.
> **Method:** 4 collection tracks (peer OSS · plugins / Windows 11 · WebView2 · Tauri means / window-drag regions and HTML5 drag and drop / omissions pointed out by the adversarial review — three snap plugins · Windows App SDK · `shadow`) → main synthesis · grounding (local dependency source · GitHub API) → cross-family adversarial review round 1 BLOCK → collect omissions · fix (see 「적대 리뷰」 below).
> **Confidence legend:** certain = confirmed from a primary source (source · official docs) · likely = one primary source, or read but not run · uncertain = indirect · unchecked.
> **Our versions:** `tauri` 2.11.3 · `tauri-runtime-wry` 2.11.3 · `wry` 0.55.1 (`Cargo.lock`).

## Conclusion

1. **Window dragging · double-click on an empty spot to maximize · resize borders are provided by Tauri core — but a permission must be added.** Put `data-tauri-drag-region` on the empty-space element of the tab bar, and dragging starts only when that element itself is pressed (its children, tab headers and buttons, are not touched), and a double press toggles maximize. The `start_dragging` permission that script calls (`core:window:allow-start-dragging`) is currently missing from the capability (`src-tauri/capabilities/default.json` · `popup.json` — only `core:default` · `internal_toggle_maximize` is already in `core:default` → `core:window:default` — `tauri-2.11.3/permissions/window/autogenerated/reference.md`). — certain
2. **Windows 11 snap layouts (the layout picker that appears when hovering over the maximize button) do not exist in Tauri** (tauri#4531 · open since 2022). All the overlay plugins surveyed (section 3 below) take the form of **covering the HTML maximize button with a transparent Win32 child window that returns `HTMAXBUTTON` for `WM_NCHITTEST`** (confirmed in source — other routes, such as Wails v3 going through composition hosting, need changes to wry). Hover and press on the button are received by that child window, so they must be relayed to the web. The big Tauri apps (Yaak · Cap · GitButler · Clash Verge Rev · Hoppscotch) give up the menu and use only the HTML buttons. — certain (mechanism) · likely (the big apps)
3. **It is better to port that overlay into `platform` (keeping the MIT attribution) than to take it in as a dependency.** There are three criteria for deciding — ① does it accept our HTML button · our rectangle (`decoration` is out because the plugin creates the button — it is the only one with tests · e2e in place) ② usage history (the remaining two have 6★ · 0★, created 2026-05 · 2026-10, no real-use reports) ③ the cost of fitting our rules (OS code in `platform` only · no new global handles · window creation in `WebviewEnv::finish` only). The Win32 core to port is on the scale of 160–360 lines. — likely
4. **Relation to tab dragging:** a Tauri-style drag region does not touch tab headers **at press-decision time** (certain). Dropping a tab dragged from another window onto that empty spot, and keeping the drag session alive, were not run (uncertain — the drag region is an ordinary element that does not block events, so no reason to block is visible). With the CSS `app-region: drag` approach, that region becomes non-client, and nobody has confirmed whether a drop reaches it.
5. **Avoid:** `tauri-plugin-decorum`'s snap = fake Win+Z key input · WebView2 Window Controls Overlay = experimental version · Windows App SDK title bar = the Rust projection · runtime dependency are heavy and there is no precedent.

## 1. Our constraints (CLAUDE.md · code)

- All code that creates a window passes through `WebviewEnv::finish` in `src-tauri/src/webview_env.rs` (ADR-0283) — no border · shadow are set in that one place. Pop-outs are created at runtime.
- OS-specific operational code goes only inside the `platform` crate (ADR-0266) — the snap overlay is one purpose-specific module of that crate.
- 「LLM-우선 제어」 — minimize · maximize · close are shaken by the human buttons and the LLM through the same handle (bus command). If the web calls the Tauri window API directly, that becomes a second surface. Do not add new global handles.
- Tab headers are HTML5 `draggable` (reordering · slot docking). The webview drop handler is turned off (`dragDropEnabled: false` · `disable_drag_drop_handler()`).
- capability = only `core:default` etc. (`src-tauri/capabilities/default.json:6` · `popup.json:6`) — no window-drag permission (`core:window:allow-start-dragging`) · toggling maximize is in the default.

| `data-tauri-drag-region` | Left press → `start_dragging` (Windows = `WM_NCLBUTTONDOWN`/`HTCAPTION` → OS move loop — dragging to the top edge of the screen gives Aero snap) · double press → `internal_toggle_maximize` · no value/`true` = that element itself only · `deep` = down to descendants · it blocks pressable descendants (buttons · `role="tab"` etc.) | **Permission required** (`core:window:allow-start-dragging` — toggling maximize is in the default) · tauri#10767 (open): after the press `mouseup` does not arrive and focus flickers | certain · `tauri-2.11.3/src/window/scripts/drag.js:42-124` · https://github.com/tauri-apps/tauri/issues/10767 |
| CSS `app-region: drag` | WebView2 non-client area — drag · double press · system menu · touch/pen | Pointer events do not reach the web inside it (revived with `no-drag`) · **whether an HTML5 drag dropped onto it reaches it is unchecked** · it is turned on only when the runtime provides `ICoreWebView2Settings9` | certain (the code that turns it on — `wry-0.55.1/src/webview2/mod.rs:600-602`) · uncertain (drop) |
| Snap overlay (Win32 child window → `HTMAXBUTTON`) | **A real snap menu** | Hover · press on the button do not reach the web (relay needed) · the web has to measure the position and pass it (DPI · zoom · window size change · full screen) · one per window | certain · source in section 3 below |

| macOS `titleBarStyle: Overlay` + `hiddenTitle` | The OS draws the traffic lights and only the title is hidden, putting the tab row at the very top | Leave the left side empty for the traffic lights | likely · Yaak `crates-tauri/yaak-window/src/window.rs:113-118` · Spacedrive |

## 4. Options

| | Dragging · double-click · resizing | Snap menu | Cost · risk |
|---|---|---|---|
| **① HTML buttons + `data-tauri-drag-region`** (big-app practice) | Works (core · add one permission) | None (Win+Z · dragging to the top edge of the screen work) | Small · tauri#10767 |
| **② ① + the snap overlay written directly in `platform`** (keep attribution and refer to `window-integration` · `snap-layout` · `decoration`) | Works | **Real** | Medium — Win32 child window · a path for the web to pass the button rectangle · relaying hover/press · DPI · full screen · per pop-out · HTML buttons on Windows 10 |
| ③ ① + plugin dependency (`window-integration`) | Works | Real | 0★ · 2-week-old code · bundles unrelated features |
| ④ Native buttons (`window-controls`) | Works | Real | Cannot be styled |
| ⑤ `decorum` | Works | Imitation | **Rejected** |
| ⑥ WebView2 WCO · ⑦ Windows App SDK | — | — | **Rejected (for now)** — experimental version · heavy dependency · no precedent |
| Drag region via CSS `app-region` | Works + system menu · touch | — | Dropping onto an empty tab bar unchecked → if chosen, spike first |

**Recommendation = start with ①, and if the snap menu is needed, add ② as the second piece of the same stage.** ① is the tab bar · buttons · window options · one permission, and minimize · maximize · close pass through bus commands rather than the web calling the Tauri window API directly (the LLM uses the same handle). The web side of ② (passing the button rectangle · receiving hover/press) also uses the same bus · event path and adds no global handle. **Whether the snap menu is a must-have is for the user to decide** (a felt feature).

## 5. Unconfirmed · what to measure next
