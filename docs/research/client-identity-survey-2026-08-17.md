# 슬라이스 B 조사 — 클라이언트 자작 식별자의 입구 검증·보관

- 상태: **medium tier · 적대 리뷰 완료 = MATERIALLY-FLAWED → 정정 반영본(2판)**
- 수집 3갈래(주도 경량 3명) · grounding = 메인 외부 검증 7건 · 적대 리뷰 = 타계열 1회(effort high, web_search ON) → findings 11건 중 **반증 출처 동반 8건 채택**
- 날짜: 2026-08-17
- 확신도 범례: **확실**(grounding 지지 + 독립 교차확증) · **가능성 높음**(지지, 단일 출처) · **불확실/보류**(미지지 또는 출처 침묵)

> ★**1판이 틀린 자리를 지우지 않고 남긴다**★ — 다음 세션이 같은 결론을 다시 도출하지 않도록. 정정은 각 자리에 인라인으로 박았다.

## 우리 제약 (설계 문서에서 추출)

- **C1** 이 값은 **인증 통과 전**에 들어온다(첫 인사 프레임) → 검증은 싸야 하고 거절이 정보를 흘리면 안 된다. (TRD §3-7 조항 6)
- **C2** 소비처는 **명부 하나뿐** — 인증 판단·조회·이벤트·화면에 안 쓴다. (ADR-0150)
- **C3** 식별자 없는 연결은 **연결 id 파생으로 fail-open**. (메인 판단, 사용자 승인 아님)
- **C4** 클라가 두 종류 — 네이티브 셸(Rust)과 브라우저/직결(TS). 설계 문서: "갈리면 두 클라의 행동이 달라지는 것이 문제". (TRD §9)
- **C5** ★앱에 **디스크 영속 표면이 아직 없다**★ — 레이아웃도 인메모리뿐.
- **C6** ★half-open을 데몬이 **최대 50초** 모른다★ — 그 창에서 옛 주인이 살아 있는 것으로 보인다.
- **C7** 신규 서드파티 crate는 신중히. **C8** 저장소 선례: 이름 ≤128 B · 모양 ≤4096 B · 주인당 512 · 전체 4096.

### ★리뷰가 지적한 제약 서술의 공백 (인정, 미해소)★

**C1~C8 어디에도 "돌아온 클라와 사칭자를 구분해야 한다"는 요구가 적혀 있지 않다.** 1판은 그 요구를 미룬 결함 2건을 가리키는 것으로 대신했는데, **위협 모형 없이는 인수·거부·인증 결속·공존 중 무엇이 필요한지가 도출되지 않는다**(리뷰 finding 4, 반증 없는 우려이나 타당). **다음 세션이 먼저 할 일 = 그 요구를 명문화하는 것.** 이 조사만으로 방식을 고르면 근거 없는 선택이 된다.

## 발견 1 — 판정 방식은 **셋이 아니라 최소 다섯**이다 (1판의 3분류는 불완전)

| 방식 | 하는 일 | 실물 | 상태 |
|---|---|---|---|
| **A. 무조건 인수** | 같은 문자열이면 묻지 않고 기존 소유자를 쫓아낸다. 문자열 소유 = 자격 | MQTT ClientID · Kafka `transactional.id` | 확실 |
| **B. 판별 후 펜싱** | 산 소유자가 붙어 있는 동안 재소유를 거부하고, 떨어진 뒤에만 연다 | **SMB2 Durable Handle v2** | 확실(단 실물 1건) |
| **C. 서버 발급 토큰** | 서버가 준 재개 토큰을 클라가 돌려준다 | WAMP · Socket.IO · ZooKeeper | 확실 |
| **★D. 자기증명 신원(신설)★** | 클라가 **키쌍을 만들고 신원을 공개키에서 파생**한다 → 채널 수립 때 **소유 증명**으로 검증. 문자열을 아는 것만으로는 사칭 불가 | libp2p Peer ID | 가능성 높음(리뷰어 제시) |
| **★E. 인증 후 늦은 결속(신설)★** | pre-auth에서 값은 싸게 파싱만 하고, **소유권 부여는 인증 완료 후**로 미룬다 | XMPP 리소스 바인딩(SASL 후) | 가능성 높음(리뷰어 제시) |

**D·E는 1판이 통째로 빠뜨렸고, 둘 다 우리 제약에 잘 맞는다** — D는 아래 발견 2의 치명적 지적에 답하고, E는 C1(pre-auth)에 직접 답한다. 출처: https://docs.libp2p.io/concepts/fundamentals/peers/ · https://www.rfc-editor.org/info/rfc6120/

### ★★발견 2 — 1판의 중심 주장이 무너졌다: "옛 소유자가 떨어질 때까지 기다리기"는 **배타성**이지 **신원**이 아니다★★

리뷰 finding 2(반증 출처 동반, 채택). 옛 연결이 죽었다고 판정된 **뒤에는, 그 문자열을 아는 아무 프로세스나 가져갈 수 있다.** 1판은 B가 "C5 비용 0으로 요구를 충족한다"고 적었는데 **거짓이다** — 인용한 두 실물 다 **추가 인수(second factor)** 를 쓴다:

- **SMB2**: `CreateGuid`(오픈 시점 생성) + 조건부 `ClientGuid` + `FileId` + ★**인증된 `DurableOwner`(OS 사용자)**★. 즉 신원의 무게는 **인증 계층**이 진다.
- **Kafka 정적 멤버십**: 브로커가 발급한 `member.id`.

**1판의 "B = 비용 0" 칸은 삭제한다.** 두 번째 인수가 필요하고, 그것이 재시작을 넘어야 하면 C5 비용이 되살아난다.

### SMB2 — 이 조사에서 **유일하게 살아남은** 모델 B 실물 (grounding 지지 · 적대 리뷰도 확인)

재소유는 **세 가지가 동시에** 맞아야 통과한다: ① `Open.CreateGuid` == 요청의 `CreateGuid` ② 리스가 있으면 `Open.ClientGuid` == 그 연결의 `ClientGuid` ③ ★`Open.Session`이 **NULL**이어야 한다 = **옛 소유자가 아직 붙어 있으면 거부**★. 추가로 OS 사용자가 `Open.DurableOwner`와 다르면 거부.
리뷰어의 WHAT SURVIVED가 이것을 재확인하며 **연결 유실 처리가 그 칸을 NULL로 만든다**는 것까지 확인했다.

- ★**정정 1**★ 1판: "실패는 전부 `STATUS_OBJECT_NAME_NOT_FOUND`라 사유를 구분해 주지 않는다". **거짓** — `DurableOwner` 불일치는 `STATUS_ACCESS_DENIED`, 일부 플래그 실패는 `STATUS_INVALID_PARAMETER`다(리뷰 finding 6, 내가 가져온 원문에 그대로 있었는데 합성에서 뭉갰다).
- ★**정정 2**★ v1→v2 개정 *사유*는 여전히 미검(내가 본 페이지에 없다).
- 출처: https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-smb2/62ba68d0-8806-4aef-a229-eefb5827160f

### ★Kafka 정적 멤버십의 분류 = 불확실/보류 (1판은 B라고 단정했다)★

리뷰어는 "신규가 새 `member.id`를 받고 매핑이 갱신되며 **옛 멤버가** 펜싱된다 → B가 아니라 인수+세대펜싱"이라고 반박했다. **내가 KIP 원문을 다시 직접 확인한 결과 그 페이지는 이 시나리오를 아예 다루지 않는다** — 내 읽기도 리뷰어 읽기도 확정되지 않는다.
- 원문이 지지하는 것만: 클라가 `group.instance.id`를 선언한다 · 알려진 멤버의 재가입은 리밸런스 없이 캐시된 할당을 돌려받는다 · 회수는 세션 타임아웃 또는 관리자 강제 제거 · `FENCED_INSTANCE_ID(78)`이 존재하고 `member.id` 불일치와 관련된다.
- ★원문이 침묵하는 것: **누가 펜싱되는가**(신규 vs 옛), 그리고 매핑 갱신이 즉시인가.★ 리뷰어가 인용한 *"we shall generate a member.id to reply to the member rejoin request immediately"* 는 리뷰어 읽기 쪽으로 기울지만 확정은 아니다.
- ★**정정 3**★ 1판이 함께 보고한 `UNRELEASED_INSTANCE_ID`는 원문에 없다 → 삭제.
- **귀결: 모델 B의 실물은 SMB2 하나로 줄었다.** 결론을 Kafka에 얹지 말 것.

## 발견 3 — 입구 검증

**MQTT ClientID (grounding 지지 · OASIS v5.0 원문):** *"The Server MUST allow ClientID's which are between 1 and 23 UTF-8 encoded bytes in length"* `[MQTT-3.1.3-5]` + *"MAY allow … more than 23"*. 보장 문자셋은 **영숫자뿐**. 빈 문자열은 특례(서버가 만들어 주고 `CONNACK`으로 알림).

- ★**정정 4**★ 1판: "최대치를 사양이 정하지 않는다". **부정확** — ClientID는 MQTT UTF-8 Encoded String 타입이고 그 타입의 **최대는 65,535바이트**(§1.5.4, 2바이트 길이 접두). 참인 것은 "**ClientID 전용의 더 작은 상한을 정하지 않고, 서버가 자기 상한을 알릴 수단이 없다**"뿐이다.
- ★**정정 5**★ 1판: "거절 사유 코드를 뭉뚱그려 정보를 안 흘린다". **거짓** — MQTT 5.0에는 `0x85` **"Client Identifier not valid"** 전용 코드가 있어 실패 범주를 알려 준다. 즉 **성숙 사양의 실제 관행은 "사유를 숨긴다"가 아니다.** C1의 "거절이 정보를 흘리면 안 된다"를 이 선례로 정당화할 수 없다.
- ★웹 요약의 "MQTT 5.0 = 256바이트"는 원문 직접 확인으로 반박됨 — 쓰지 말 것.
- 출처: https://docs.oasis-open.org/mqtt/mqtt/v5.0/mqtt-v5.0.html

**다른 수치**(가능성 높음, 재확인 미실시): SSH 최초 식별 문자열 255자(RFC 4253 §4.2) · IRC 닉 문법 9자(RFC 2812) · QUIC 연결 ID 20바이트(RFC 9000 — **역할이 다르다**, 받는 쪽이 고르는 라우팅용).

**문자셋의 실제 사유는 표시·프레이밍 안전**(가능성 높음): Redis `CLIENT SETNAME`이 공백·개행을 거부하는 이유는 이름이 줄 단위 응답에 박히기 때문. 로그 인젝션 사유는 사양이 아니라 OWASP 계열 일반 지침.

- ★**정정 6**★ 1판: "어느 사양도 정규화를 규정하지 않는다". **거짓** — **XMPP는 규범적으로 PRECIS를 적용**하며 resourcepart는 OpaqueString 프로파일, 그 규칙이 **NFC를 요구**한다(RFC 7622 §3.4 · RFC 8265). 1판이 XMPP를 자기 피어 목록에 올려놓고 이걸 놓쳤다. 출처: https://www.rfc-editor.org/info/rfc7622/ · https://www.rfc-editor.org/rfc/rfc8265.html
- 정규화를 **키로** 쓰는 함정은 여전히 유효(혼동문자 매핑과 유니코드 정규화가 31문자에서 불일치, 조사된 12개 시스템 중 맞춘 곳 없음 — 가능성 높음, 2차 출처).

**pre-auth 특정 지침은 사양에 없다**(확실 — 없다는 것이 발견). CWE-770 + OWASP가 그 자리를 메운다.

## 발견 4 — 보관

**브라우저 저장소는 best-effort (grounding 지지 · MDN 원문):** origin 단위 **전부-또는-무** 축출 · `navigator.storage.persist()`는 **요청이지 보장이 아니다**(Firefox는 사용자에게 묻고, Chrome/Safari/Edge는 상호작용 이력으로 자동 판정·프롬프트 없음) · 시크릿 모드는 세션 종료 시 소멸.
- ★**정정 7**★ 1판: "Safari는 7일 후 지운다"를 무조건으로 적었다. **조건부다** — *"Safari proactively evicts data **when cross-site tracking prevention is turned on**"*. 내가 가져온 원문에 그 조건이 있었는데 보고서에서 떨어뜨렸다(리뷰 finding 9).
- 출처: https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria

**복제 위험이 지배적 실패 유형이고 자동 탐지를 만든 곳이 거의 없다**(가능성 높음): 신원 자료가 복사되는 디렉터리 안에 살기 때문에 VM 클론·프로필 로밍·백업 복원이 같은 뿌리다. `systemd machine-id`·Syncthing·Headscale·Fing 전부 런타임 탐지 없음. Headscale은 클론 탐지 요청을 **"not planned"로 닫았다**(확실). 엔터프라이즈 VDI만 전용 재개인화 도구를 갖는다(거기선 클론이 정상 경로).
- ★**정정 8**★ 1판이 Syncthing 문서를 근거로 "인스턴스당 1회 · OS 사용자·머신과 무관"이라 했는데 **그 페이지는 셋 다 서술하지 않는다** → 미지지. 지지되는 것은 파생 방식(인증서 DER의 SHA-256)과 형식(base32 52자, 4자 그룹 + 검사숫자)뿐.

- ★**정정 9**★ 1판: "네이티브와 브라우저가 문자 그대로 같은 자작 식별자를 내미는 제품은 없다". **반증됨** — Eclipse Paho는 브라우저 JS 클라이언트와 Java 클라이언트가 **둘 다 애플리케이션이 준 `clientId`를 받는다**. 같은 값을 양쪽에서 내밀 수 있다(리뷰어 지적: 이것이 바람직함을 증명하진 않지만 **부재 주장과 거기서 끌어낸 추론은 무너진다**). 출처: https://eclipse.dev/paho/clients/js/
- 남는 사실: WhatsApp·Signal은 **클라 종류마다 독립 신원 + 계정 층 교차서명**, GA4는 **익명 층은 갈리게 두고 인증 층에서만 통일**(둘 다 가능성 높음, 2차 출처).

## 거부 후보 (ADR 거부 대안으로 넘길 것)

- **서버 발급 재개 토큰(WAMP·Socket.IO·ZooKeeper)** — 방향이 반대(서버가 신원을 준다). ADR-0150 문면과 배치.
- **Kubernetes 리더 선출 `holderIdentity`** — 신원이 프로세스마다 랜덤이고 만료 후 누구나 가져간다. "같은 이 vs 남" 판별이 없다.
- **tmux 세션 소유권** — OS 소켓 파일 권한(uid)에 위임. 프로토콜 층 선언이 아니다.
- **SIP `+sip.instance`** — 이미 강한 인증을 통과한 뒤의 흐름 관리용. (★XMPP는 거부 후보에서 빼야 한다 — E 모델의 실물이고 PRECIS 정규화 근거원이다.)
- **혼동문자 기반 동일성 판정** — 알고리즘이 갈려 31문자 불일치. C2에선 얻는 게 없다.

## 쟁점·한계 (contested 유지 — 메인이 판결하지 않는다)

1. ★**요구가 미문서**★ — "돌아온 클라 vs 사칭자 구분"이 제약에 없다. **이걸 먼저 쓰지 않으면 방식 선택이 근거 없다.**
2. ★**Kafka 정적 멤버십 분류 = 보류**★ — 원문 침묵. 결론을 여기 얹지 말 것.
3. ★**D·E 미조사**★ — 리뷰어가 제시했고 우리 제약에 잘 맞아 보이는데, **이번 조사 예산에 안 들어 있었다.** 비용·crate 영향·브라우저 실현성이 미확인. **다음 라운드 1순위.**
4. **P3 vs C4 모순** 미해소 — 갈림을 문제로 볼지 설계로 볼지가 사용자 결정.
5. **미조사:** SMB2 v1→v2 개정 사유(Samba 제안 문서) · STOMP·etcd lease · `transactional.id`/AMQP `container-id` 길이 상한 · 한 앱 동시 2개·안정판/개발판 나란히 쓸 때의 신원 처리.
6. **부재 증명 아님:** "프로세스 수명 신원을 쓰는 곳이 없다"·"두 클라가 같은 값을 내미는 제품이 없다" — 후자는 Paho로 실제 반증됐다. 전자도 같은 취급할 것.

## 다음 세션이 할 일 (순서)

1. **위협 모형·요구를 명문화**한다(쟁점 1). 그 전에 방식을 고르지 않는다.
2. **D(자기증명 신원)·E(늦은 결속)를 조사**한다(쟁점 3) — 지금 후보 공간이 불완전한 상태다.
3. 그 뒤에 선택지를 사용자에게 올린다. **이 2판만으로 결정하지 말 것.**
