## 0. 결론 (먼저)

1. **녹(PASS) — 도구 끝 반응 지연 합 = 2275 µs < 6000 µs.** `max(①) 783 + max(리더 밀림) 1405 + max(②) 87`. 여유는 3.7 ms 다(한도의 38 %). 네 로그를 합친 값이고, 로그별로 보아도 판정이 서는 둘은 PASS 다(F2 = 1486 µs · F = 131 µs). 파서 경고(표본 20 미만)는 합산에서 전부 풀린다. **확실**(로그 값 그대로 · 파서 공식 그대로).
2. **지배 항 = 리더 밀림 1405 µs — 병렬 도구 3개가 동시에 출력을 쏟은 턴의 도구 끝 한 건이다**(T 실행 `seq=74`). 순차 도구의 도구 끝 밀림은 p95 631 µs 이고, 그 최댓값들은 6000 줄 폭주 뒤 끝 줄이다. P2g 정의(리더가 `read()` 밖에서 바빴던 시간의 상한)로는 **실제로 바빴던 시간**이지 계측 결함이 아니다. 다만 상한이라 실제 대기는 이 이하다(§6). **가능성 높음.**
3. **① 의 최댓값 783 µs 는 대부분 줄 해독이다** — `handle_us` 769 µs(리더가 줄을 집은 순간 → 신호를 세운 순간). 6000 줄짜리 `aggregatedOutput` 을 실은 `item/completed` 한 줄(약 340 KB)을 푸는 시간이고, 라이터가 깨기까지 남은 몫은 수십 µs 다. 출력이 작은 도구 끝은 ① p50 100 µs. **확실**(두 칸이 같은 줄에 찍힌다).
4. **② 는 작고 고르다** — 턴 id 홉 23 건 49–87 µs · 출력 폭주 중 곧바로 넘긴 steer 28 건 29–72 µs(합산 79 건 p95 70 µs). **확실.**
5. **답 끝 반응 합 = 221 µs**(① 59 + 밀림 75 + ② 87). M16 의 가장 좁은 답 끝 창 9.4 ms 에 비해 40 배 넘게 작다 — 답 구간을 붙드는 데 데몬 쪽 지연은 걸림이 안 된다. 판정이 아니라 비교값이다. **확실**(값) · 답 구간 창에 늘 들어간다는 결론은 **가능성 높음**(M16 은 벤더 단독 하네스였다).
6. **넘긴 입력은 전부 같은 턴에서 받아들여졌다** — 턴 id 홉 23/23 이 `OK<n> TWO` 로 답을 받았고, 폭주 중 steer 28/28 이 그 턴 끝 답에 번호째 나열됐다(`1.1, 1.2, 1.3, 1.4` 등 7/7 턴). 버려진 입력 0(`Dropped` 0 · 오류 0). **확실.**

## 1. 방법

**데몬:** 격리 워크트리(`4ba00b5`, detached)에서 release 데몬을 짓고, 실행마다 **새 격리 데이터 폴더**로 직접 띄웠다(`scripts/launch-detached.ps1 -EnvVars 'RUST_LOG=warn,engram::codex_handover=debug','ENGRAM_DATA_DIR=<격리 폴더>'`). 실행 = 데몬 하나 = codex 에이전트 하나라 로그마다 `seq` 공간이 하나다(파서의 중복 `seq` 경고 0). ★앱(클라이언트 셸)은 띄우지 않았다★ — 아래 드라이버가 데몬에 직접 붙는다.

**드라이버(`m15b.mjs`):** 앞단 `WsTransport`/`ProtocolClient` 와 같은 WS 프레임을 데몬에 직접 보낸다 — `daemon.json` 의 토큰으로 `Auth` → `Hello` → `CreateProfile{backend:'codex', output_format:'StreamJson'}` → `SpawnProfile` → `Subscribe` → 입력은 `WriteStdin`(챗 칸 `RichSlot` 과 같은 raw 텍스트). Origin 헤더가 없어 net `ws.rs` 의 「네이티브/하네스 허용」 갈래로 들어간다. 턴이 끝났다고 보는 조건 = `TurnEnd` 수신 + 미결 입력(`Queued` 뒤 `Delivered`/`Dropped` 가 안 온 것) 0 + 6 초 조용.

**실행 넷(모두 같은 PC·같은 codex 설정):**

| 실행 | 목적 | 턴 | 턴당 조작 |
|---|---|---|---|
| T | 도구 끝 · 병렬 도구 | 7 | 턴 1–6: `node flood.js 1000/3000/5000/2000` 넷을 따로따로 순서대로 돌리라고 시킨다 · 턴 7: `node flood.js 3000 20 100` 셋을 **병렬로** 돌리라고 시킨다 |
| H | 턴 id 홉(`turn/start` 응답 → 쥔 항목 steer) | 23 | 글 A(`Reply with just the word OK<n>.`)와 글 B(`Also append the word TWO …`)를 **연달아** 보낸다 — B 는 턴 id 가 오기 전에 닿아 쥐어졌다가 턴 id 신호에서 넘어간다 |
| F2 | 출력 폭주 중 steer | 7 | `node flood.js 6000 40 100`(6000 줄 · 약 2.4 초에 걸쳐 쏟는다)을 **그대로** 돌리라고 시키고, 그 `ToolCall` 뒤 +700/+1100/+1500/+1900 ms 에 글을 하나씩 친다 |

**판정 공식:** 파서(`parse-handover-trace.mjs`, 커밋 `4ba00b5` 판)의 것 그대로다. 합산은 네 로그의 원값을 합친 뒤 같은 `stats()`·`LIMIT_US` 로 다시 셌다. 로그별 파서 출력과 짝짓기 검사(짝 없는 줄 0 · 형식 오류 0)는 실행마다 따로 돌렸다.

## 3. 판정 (TRD M15 행)

- **도구 끝: 녹.** `783 + 1405 + 87 = 2275 µs < 6000 µs`. 세 항의 최댓값은 **서로 다른 사건**에서 왔으므로(① = F2 `seq=32` · 밀림 = T `seq=74` · ② = H `seq=65`) 한 사건의 실제 지연보다 크게 잡은 보수적 합이다. **확실.**
- **지배 항의 성격:** 병렬 도구 셋이 동시에 쏟은 출력을 리더가 멈춤 없이 처리하던 중에 닿은 도구 끝 줄이다. P2g 정의대로 바빴던 시간만 셌으니 실제 부하다. 계측 결함의 흔적(한가한 틈을 세는 것)은 없다 — 턴 사이를 지난 `turn_id` 밀림이 최대 118 µs 다(A단계 옛 정의에서는 101 초였다). **가능성 높음**(상한이라 실제 파이프 대기는 이 이하. 한가한 뒤 첫 줄에 앞 청크 꼬리 처리 시간이 드는 알려진 큰 쪽 오차가 있다 — `DrainMark` doc).
- **답 끝(비교값): 221 µs** — M16 가장 좁은 창 9.4 ms 안에 넉넉히 든다.

## 4. 재현

1. 격리 워크트리: `git worktree add --detach <폴더> 4ba00b5` → 그 안에서 `scripts/run-detached.ps1 -Command "cargo build --release -p engram-dashboard-daemon"`(`__EXIT=0`, 2 분 8 초).
2. 실행마다: 새 데이터 폴더 → `launch-detached.ps1 -Exe '<워크트리>/target/release/engram-dashboard-daemon.exe' -WorkDir '<codex 작업 폴더>' -EnvVars 'RUST_LOG=warn,engram::codex_handover=debug','ENGRAM_DATA_DIR=<데이터 폴더>'`(Git Bash 에서 `-Command` 로 부른다 · 경로는 슬래시).
3. `node m15b.mjs <데이터 폴더> <codex 작업 폴더> <tools|hops|flood> <턴 수> <사건.jsonl>` — 작업 폴더에 `flood.js` 를 둔다. 이 초안의 순서: `tools 7` → `hops 23` → `flood 7`. 실행 사이마다 데몬을 끄고(자기 PID · `ExecutablePath` 확인 뒤 `taskkill /T /F`) 새로 띄운다.
4. 로그별 `node parse-handover-trace.mjs <로그> [--json] [--extract …]` → `node m15combine.mjs <parser.mjs> T=<로그> H=<로그> F=<로그> F2=<로그>`.
5. 폭주 창: `node m15floodcheck.mjs <F2 사건.jsonl> <F2 로그>`.

## 6. 한계 · 미검

- **도구 끝 신호가 직접 깨운 steer 는 한 건도 없다**(`hop="signal" signal="tool_end"` 0). 도는 턴에 친 글은 전부 곧바로 넘어갔고(announce), 도구 끝까지 쥐어졌다 넘어간 것이 없었다. 그래서 판정의 ② 는 턴 id 홉과 곧바로 넘김으로 채웠다. 세 항을 따로 재 더하는 설계(README 「한 번에 도는 경로가 없어서」) 그대로이지만, **도구 끝 → steer 한 경로를 끝에서 끝까지 잰 값은 없다.** 확실.
- **폭주가 steer 시각에 실제로 흐르고 있었다는 것**은 턴 1 에서만 직접 봤다(첫 델타 +568 ms). 턴 2–7 은 같은 명령·같은 도구 시간(3043–3119 ms)에서 미룬 추론이다. 가능성 높음.
- **`lag_us` 는 상한이다.** 실제 파이프 대기를 따로 재서 대조하지 않았다. 「Windows 파이프 읽기는 그 순간 있는 만큼 돌려준다」는 전제(`DrainMark` doc)도 이 통로에서 따로 확인하지 않았다. 불확실.
- **모델이 M16 과 다르다**(`gpt-6-sol`/`high` 대 `gpt-6-luna`/`low`). 잰 세 다리는 데몬 안의 시간이라 모델에 안 묶이지만(가능성 높음), 병렬 도구를 쓸지·명령을 감쌀지는 모델 행동이다.
- **입력 경로가 앱과 다르다** — 셸(Tauri) 대신 드라이버가 같은 wire 로 데몬에 붙었다. 잰 다리는 전부 데몬 codex 통로 안이라 영향이 없다고 본다(가능성 높음). **직접 띄운 데몬에 앱이 붙는지는 이번에도 확인하지 않았다.**
- **PC 부하를 통제하지 않았다** — 다른 세션의 codex 프로세스가 같은 PC 에서 돌고 있었다. 한 번의 측정 세션이다.
- 계측 줄 중 `wake`·`steer` 는 steer 를 다 쓴 뒤 몰아서 찍힌다(`Traced`). 로그의 줄 순서·시각은 쓰기 순서가 아니고, 짝은 `seq` 로만 지었다.

## 7. 선행 문서와 어긋난 것 · 절차에 대한 관측

- **M15 README 의 절차 초안(앱을 띄워 직접 띄운 데몬에 붙인다 · debug 빌드)은 쓰지 않았다.** WS 로 데몬에 직접 붙는 드라이버면 셸 빌드·npm·vite 포트·identifier 충돌이 전부 필요 없다. 판정도 release 로 했다 — debug 빌드는 ① 이 크게 잡힌다(A단계 debug: 대량 출력 도구 끝 `handle_us` 2134 µs · 이번 release: 같은 부류 최대 769 µs).
- **「출력을 보이지 말라」고 시키면 모델이 출력을 변수에 삼킨다**(F 7/7) — 폭주 표본이 되지 않는다. 폭주를 원하면 「그대로 · 리다이렉트·파이프·변수 없이」라고 적는다(F2 7/7 이 원문 그대로 돌았다).
- README 가 권한 「보낸 직후 턴 id 가 오기 전에 글을 친다」는 연달아 보낸 `WriteStdin` 두 프레임으로 23/23 재현됐다.
- M15 A단계 로그(커밋 `df1ab8d`, debug)는 `lag_us` 옛 정의라 판정에 쓰지 않았다(README 머리 경고와 같다).
