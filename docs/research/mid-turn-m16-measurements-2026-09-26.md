## 0. 결론 (먼저)

1. **녹 — 세 사례 모두 창이 있다.** 답 끝 신호를 받는 그 핸들러에서 넘긴 steer 는 **40/40** 이 같은 턴의 후속 샘플링에 들었고 모델이 그 글에 답했다(도구 없는 긴 답 A 14/14 · 도구 뒤 마지막 답 B 12/12 · `plan` 턴 C 14/14 · +0 ms 20/20 · +1 ms 20/20). 빗나간 것은 **신호에서 일부러 늦춘 steer 뿐**이고, 그것도 전부 `thread/tokenUsage/updated` 를 받은 뒤 1.5 ms 이상 늦게 쓴 것이었다(10/10 `-32600`). → **P8 은 답 구간도 붙든다**(TRD M16 행 「녹 = 답 구간도 붙든다」).
2. **창 = 답 끝 신호 → 그 샘플링의 `tokenUsage` 알림 + 약 0.2–0.4 ms.** 창의 길이는 신호 뒤 `tokenUsage` 가 오기까지로 정해지고, 그 값은 **A 9.4–66.3 ms(중앙 30) · B 28.2–96 ms(중앙 40.6) · C 27.1–66.7 ms(중앙 36.4)** 였다(74 회 전부). ★**가장 좁은 창 = 9.4 ms(A)**★ — M15 의 **답 끝 반응 지연**을 견줄 값이 이것이다(M15 는 아직 안 쟀다 — P2e2 뒤). 도구 끝 창(M7 최소 6 ms)보다 넓다.
3. **`plan` 끝을 재현했다 — 단 우리 앱이 스스로는 닿지 않는 모드에서다.** `plan` 항목은 Plan 협업 모드에서만 나오고, 그 모드는 실험 API(`initialize` 의 `capabilities.experimentalApi` + `turn/start.collaborationMode`)로만 켜진다. 우리 codex backend 는 둘 다 보내지 않는다(`crates/engram-dashboard-agent/src/backend/codex/` 에서 `experimentalApi`·`collaborationMode` 0 건). 재현됐고 녹이므로 **`plan` 은 `agentMessage` 와 같은 답 끝 신호로 둔다** — 「그 밖」으로 내릴 근거가 없다.
4. ★**설계에 걸리는 새 사실 셋**★
   - **벤더의 마지막 대기분 확인은 둘이다 — `run_turn` 안(`core/src/session/turn.rs:555-567`)과, `run_turn` 이 돌아온 뒤 태스크 고리(`core/src/tasks/regular.rs:120`).** 둘째 확인이 대기 입력을 보면 **같은 턴 안에서 `run_turn` 을 빈 입력으로 다시 돈다.** 그래서 `tokenUsage` 뒤 0.1–0.2 ms 에 쓴 steer 도 같은 턴에 답을 받았다(10/10 · 에코가 `tokenUsage` 뒤 27–28.6 ms — 먼저 든 steer 의 1.8–3.6 ms 와 갈린다). Phase 0b §3 이 「마지막 대기 입력 확인」으로 적은 자리는 첫째다(§9).
   - **`plan` 항목 id 가 한 턴 안에서 되쓰인다** — `<턴 id>-plan` 하나가 샘플링마다 `item/started` → `item/completed` 를 다시 받는다(C 에서 후속 샘플링이 돈 22 턴 모두 같은 id 로 두 쌍). 항목 id 로 상태를 쥐는 곳은 「끝난 id 가 다시 시작된다」를 견뎌야 한다.
   - **늦은 steer 의 `-32600` 이 `turn/completed` 보다 먼저 온 것이 또 나왔다** — 10 번 중 2 번(−0.2 ms · −1.2 ms). Phase 0b M10 의 −0.1 ms 와 같은 현상이다(`-32600` 순서를 가정하지 않는다는 TRD 처분이 맞다).
5. **답 끝 신호 앞에는 리더 밀림이 거의 없다(M15 에 넘길 재료).** 74 번 모두 신호 앞 20 ms 동안 도착한 줄이 **0** 이었고, 마지막 델타는 신호보다 40 ms 이상 앞섰다. 신호 줄은 조용한 파이프에 홀로 온다 — 답 끝 반응 지연에서 리더 밀림 항은 작을 것이다(추론 · 불확실 — 데몬 경로는 안 쟀다).

**판정(시도마다):**

- 답 항목의 `item/completed` 는 스트림의 `OutputItemDone` 에서 나간다(`core/src/session/turn.rs` `try_run_sampling_request` `:2583-2692` — `plan` 도 같은 자리의 `maybe_complete_plan_item_from_message` `:2247-2273`). 스트림은 그 뒤 `ResponseEvent::Completed`(`:2828-2877`)까지 흐르고, 돌던 도구를 비운 뒤 `send_token_count_event`(→ `thread/tokenUsage/updated`, `:3042-3050`)를 내고 돌아온다.
- 첫째 확인 = `run_turn` 의 `has_pending_input`(`:555-567` · `needs_follow_up = model_needs_follow_up || has_pending_input`).
- 둘째 확인 = `RegularTask` 고리(`core/src/tasks/regular.rs:104-124`): `run_turn` 이 돌아온 뒤 `has_pending_input` 이면 `next_input = Vec::new()` 로 `run_turn` 을 다시 부른다 — 같은 태스크 · 같은 턴 id.

- 그러니 **창 = 신호 → 둘째 확인**이고, 그 끝은 `tokenUsage` 알림 바로 뒤다. 이 판독대로 `sweep` 을 gap 양쪽에 퍼뜨렸다.

## 3. 창

**창 = 신호 → 둘째 확인.** 시도마다 잰 gap 위에 약 0.2–0.4 ms 가 더해진 값이다.

| | A | B | C |
|---|---|---|---|
| gap 최소 · 중앙 · 최대(ms, 시도 수) | **9.4** · 30.0 · 66.3 (26) | 28.2 · 40.6 · 96.0 (23) | 27.1 · 36.4 · 66.7 (25) |
| 신호에서 늦춰 쓰고도 맞힌 가장 늦은 steer | +47.8 | +51.5 | +49.7 |
| `tokenUsage` 뒤에 쓰고 맞힌 가장 늦은 steer | +0.2 | +0.2 | +0.2 |
| `tokenUsage` 뒤에 쓰고 빗나간 가장 이른 steer | +2.3 | +1.5 | +3.2 |

- **창의 끝은 신호가 아니라 `tokenUsage` 에 붙어 있다.** `sweep` 24 번이 한 줄로 갈렸다 — `tokenUsage` 보다 먼저 쓴 14 번은 전부 맞힘, 1.5 ms 이상 뒤에 쓴 10 번은 전부 `-32600`. 신호에서 같은 d 만큼 늦춰도 그 턴의 gap 에 따라 맞기도 빗나가기도 했다(A d≈19: gap 15 → 빗나감 · A d≈30: gap 61 → 맞힘). 확실.
- **끝의 폭 = `tokenUsage` 뒤 (0.2, 1.5) ms — 실측 · 약 0.2–0.4 ms — M10 과 합친 추론.** 여기서 `tokenUsage` +0.1–0.2 는 10/10 맞았고, M10 은 +0.4–0.6 에서 기록만(둘째 확인을 지남) · +1.4 에서 `-32600` 이었다. 가능성 높음.
- **둘째 확인이 창을 넓힌다(§0.4).** 에코가 `tokenUsage` 뒤 몇 ms 에 오는지가 두 갈래로 뚜렷이 갈린다 — `tokenUsage` 보다 먼저 든 steer 는 **1.8–3.6 ms**(첫째 확인 → 같은 `run_turn` 이 곧바로 샘플링) · `tokenUsage` 뒤 0.1–0.2 ms 에 쓴 steer 는 **27.0–28.6 ms**(한 번 362 ms — 둘째 확인 → `run_turn` 을 새로 부르며 샘플링 준비를 다시 한다). 첫째 확인을 지나서 든 steer 가 둘째 확인에 잡혔다는 판독과 맞는다. 가능성 높음(벤더 내부 시각은 못 본다). 예외 하나 — B `sweep` #122 는 먼저 들었는데 20.3 ms 였다(원인 모름).
- **기록만 창은 이번에도 좁았다** — 한 번도 안 맞혔다. 도구 없이 끝나는 턴의 `tokenUsage` → `turn/completed` 는 3.0–4.5 ms 였다(M10 의 3.3–3.6 ms 와 같다).
- **M15 와 견줄 값:** 답 끝 반응 지연(M15 행 — 답 끝 ① 최댓값 + 그때의 리더 밀림 최댓값 + ② 최댓값)을 **최소 창 9.4 ms**(A) 와 견준다. B·C 만 놓고 보면 최소 27.1 ms 다. 리더 밀림의 재료: 74 번 모두 신호 앞 20 ms 안에 도착한 줄 **0** · 마지막 델타 → 신호 **40.1 ms 이상**(A 42.2–314.2 · B 40.1–1455 · C 131.1–251.6) · 신호 앞 답 델타 수 A 203–227 · B 102–113 · C 62–72(대개 한 줄이 한 stdout 조각으로 왔다). 신호는 조용한 파이프에 홀로 온다 — 리더가 그 앞 줄을 처리하느라 밀려 있을 까닭이 작다(추론 · 불확실 — 우리 데몬 리더에서 잰 것이 아니다).

## 4. 판정 (TRD M16 행)

| 사례 | 맞힘(신호에서 곧바로) | 창(최소 · 중앙) | 녹/적 |
|---|---|---|---|
| A 도구 없는 긴 답 | 14/14 | 9.4 · 30.0 ms | **녹** |
| B 도구 뒤 마지막 답 | 12/12 | 28.2 · 40.6 ms | **녹** |

- **§5-5 구간 표 「답 구간」 칸 = 「M16 녹 = 쥔다 → 답 끝 신호에 곧바로」.** P8 은 답 구간도 붙든다. `plan` 은 「그 밖」으로 내리지 않는다 — 끝 신호가 확인됐다.
- ★**단서 하나 — M15 가 이 녹을 조건으로 바꿀 수 있다**★: 답 끝 반응 지연이 최소 창 9.4 ms 를 넘으면 창이 가장 좁은 턴에서 붙든 글이 둘째 확인을 놓친다. 그때 그 글은 기록만(M10 — 턴 끝 정산이 받는다)이나 `-32600`(다음 턴으로)으로 떨어진다 — **한 경계 늦을 뿐 잃지는 않는다**(TRD §5-5 의 두 처분). M15 행이 이것을 「판정이 아니라 견줄 값」으로 두었으므로 멈춤 조건은 아니다.
- **TRD §5-5 신호 ③(샘플링 끝 = `tokenUsage`)을 「너무 좁아 기대지 않는다」로 둔 것이 맞다** — 그 신호에서 쓴 steer 가 드는 폭은 약 0.2–0.4 ms 다(§3).

## 5. 재현

- **시나리오:** `codex_harness.js` 시나리오 `M16`. 환경변수 — `M16_CASE`(`A`·`B`·`C`) · `M16_N`(`sig` 수, 기본 10 · +0/+1 번갈아) · `M16_TOK`(`tok` 수, 기본 3) · `M16_SWEEP`(`sweep` 수, 기본 6) · `M16_K0`(첫 시도 번호 = 낱말 KIWI*k* 의 *k*). 로그 이름 = `codex-M16-<사례>-<stamp>.jsonl`. 본 실행은 `M16_N=12 M16_TOK=3 M16_SWEEP=8` · `M16_K0` = A 1 · B 101 · C 301(파일럿 = A `2/1/0` · C `2/0/0`, `M16_K0` 1 · 201).
- **실행:** `node codex_harness.cjs M16 <로그 폴더> <작업 폴더>` — 모델·effort 는 5·6 번째 인자(기본 `gpt-6-luna` · `low`). 작업 폴더는 저장소 밖 스크래치를 썼다.
- **요약:** `node m16codex.cjs <로그>... [verbose]` — 시도마다 한 줄 + 사례별 모드 맞힘 수 · gap 분포 · 맞힘/빗나감 steer 시점 · 에코−`tokenUsage` 두 갈래 · 신호 앞 조용함 · `-32600` 대 `turn/completed` 순서.
- ★**ESM 함정**★(Phase 0b §4 와 같다) — 저장소 `package.json` 이 `"type":"module"` 이라 저장소 안에서 `node *.js` 는 `require is not defined` 로 죽는다. **저장소 밖으로 `.cjs` 로 복사해** 거기서 돌린다.

## 7. 한계

- **한 모델 · 한 버전 · 한 PC 다.** `gpt-6-luna`(low) · 0.156.1. 모델이 느리거나 응답 끝을 늦게 보내는 서버 상태에서는 gap 이 달라진다 — 이번 최소 9.4 ms 가 하한이라는 보장은 없다(표본 안의 최소다).
- **B 의 신호는 도구 뒤 첫 `final_answer` 뿐이다.** 도구 앞 설명 메시지(`commentary` — 도는 도구가 없을 때 끝나고 같은 샘플링이 도구를 이어 부른다)는 한 번도 안 나와 못 쟀다. 그 신호에서 넘긴 글은 소스상 도구 뒤 샘플링으로 들어가야 한다(첫째 확인 전에 대기함에 있다 — 가능성 높음 · 미실측).
- **병렬 도구 · 긴 출력 도구 뒤의 답은 안 쟀다** — 그쪽은 M15 가 도구 끝에서 잰다.
- **C 는 실험 API 조건이다.** 우리 앱은 그 모드를 열지 않는다. ★TUI 에서 Plan 모드로 쓰던 스레드를 우리 앱이 `thread/resume` 하면 그 모드가 이어지는지는 안 봤다★(불확실) — 이어진다면 우리 앱에서도 `plan` 이 나온다.
- **창의 끝 폭(0.2–0.4 ms)은 M10 과 합친 추론이다.** 이번 실측만으로는 (0.2, 1.5) ms 다.
- **하네스 반응이지 데몬 반응이 아니다.** steer 는 신호 뒤 0.0–1.3 ms 에 **쓰기를 불렀다**(node 파이프 쓰기가 실제로 나간 시각은 아니다). 데몬의 반응 지연은 M15 가 잰다.
- **사용자 codex hooks 설정을 들여다보지 않았다**(Phase 0b 와 같다). 둘째 확인 경로의 27 ms 에 훅이 들었는지는 모른다.
