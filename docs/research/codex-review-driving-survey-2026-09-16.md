# codex 를 자동 코드리뷰어로 모는 법 (리서치 + 자체 실측)

- 상태: ★**열화(degraded)**★ (2026-09-16) · 강도: research 스킬 **medium — 적대 리뷰 생략(cross-family 검증 없음)**
- 방법: Claude 경량 3갈래 병렬 수집(공식 1차 / 실사용 선례 / 도구 무관 패턴) → 메인 grounding.
  **규약상 붙어야 할 cross-family 적대 리뷰를 돌리지 않았다** — 그 슬롯이 codex 자신이고, 같은 날
  실측 4회를 이미 태워 한도를 아꼈다. 이 라벨을 떼려면 적대 리뷰를 거쳐야 한다.
- 함께 실린 것: ★**자체 A/B/C 실측**★(§8) — 같은 리뷰 과업 하나를 네 갈래로 돌려 잰 것.
  아는 한 「같은 도구를 핀 vs 탐색으로 갈라 잰」 공개 자료가 없어, 이 절이 우리 조건의 정본이다.
- 목적: `/review` 의 blind(codex) 슬롯 호출 방식을 고칠 근거 확보. 계기 = 호출당 비용 폭증과
  2026-09-15 세션의 한도 사망 2회.

이 문서는 확신도 대신 **어떻게 확인했나**를 단다 — 이번 조사에서 그 축이 결론을 더 잘 갈랐다.

## 핵심 결론

1. ✅ **codex 에는 리뷰 전용 경로가 이미 있다** — `codex exec review`. 리뷰 프롬프트를 발명할 필요가 없다(§1).
2. ✅ **자체 실측: 탐색을 막으면 입력 9배·미캐시 3배·시간 1.8배가 준다. 대신 결함 하나를 놓쳤다**(§8).
3. ✅ **자체 실측: 따뜻한 스레드를 이어 쓰면 2회차가 입력 6.8배·미캐시 13배·시간 31배 싸다**(§8).
4. ◆ **「diff 만 주는 쪽이 낫다」는 비에이전트 방식에서만 성립한다 — 에이전트 루프를 붙이면 뒤집힌다**(§7).
   우리 codex 는 에이전트 쪽이라 그 결론을 그대로 옮길 수 없다. 그래서 §8 이 정본이다.
5. △ **캐시된 토큰도 플랜 한도를 태우는 것으로 보인다**(§5). resume 을 한도 대책으로 기대하면 안 된다.
6. ✅◆ **함정 셋** — 범위 플래그와 커스텀 지시 동시 사용 불가 · 범위를 빼면 조용히 딴 것을 리뷰 ·
   resume 은 플래그 표면이 다르다(§4).
7. ○ **판정을 종료코드로 하면 안 된다** — 결함이 있어도 0 이고 한도 사망도 안 나온다(§6).

## 1. codex 에는 리뷰 전용 경로가 이미 있다

- ✅ **`codex exec review`** 가 실재한다. 범위 = `--base <BRANCH>` · `--uncommitted` · `--commit <SHA>` 셋 중 하나.
  회수 = `--json` · `--output-schema <FILE>` · `-o <FILE>` · `-m <MODEL>`.
  ★**`-s/--sandbox` · `-C/--cd` · `--add-dir` 는 없다**★ — `codex exec` 에만 있다. 이 경로에서 샌드박스는
  `-c 'sandbox_mode="read-only"'` 로만 지정된다(안 하면 `config.toml` 기본을 따르고, 신뢰된 프로젝트에선
  쓰기일 수 있다).
- ◆ **리뷰 시스템 프롬프트가 바이너리에 컴파일돼 있다.** 우리에게 직결되는 조항 둘:
  - "The bug was introduced in the commit (pre-existing bugs should not be flagged)."
  - "It is not enough to speculate that a change may disrupt another part of the codebase, to be
    considered a bug, one must identify the other parts of the code that are provably affected."
  - 분량 정책: "If there is no finding that a person would definitely love to see and fix, prefer
    outputting no findings."
  - ★**우리 `/review` 가 겪던 오탐 부류(선재 결함 지적·추측성 파급 주장)를 벤더가 이미 프롬프트로 막고 있다**★.
- ◆ **출력이 정형이다** — `findings[]` = title · body · confidence_score · priority(0~3) ·
  code_location(absolute_file_path, line_range), 그리고 overall_correctness("patch is correct" 또는
  "patch is incorrect") · overall_explanation · overall_confidence_score.
- ◆ **리뷰는 자식 세션으로 돈다** — 부모 컨텍스트를 물려받지 않는다(바이너리의 타입 설명이
  "Structured review result produced by a child review session.").
- ◆ 내장 프롬프트가 **「다른 곳(파일 포함)에 더 구체적인 지침이 있으면 그것이 이 일반 지침을 덮는다」**고
  명시한다 → **AGENTS.md 로 리뷰 기준을 주입하는 것이 설계상 지원된다.** 단 「범위 제한 용도로 쓰라」는
  명시 권고는 찾지 못했다.

## 2. ★공식 안에서도 「diff 를 주나 훑게 두나」가 갈린다★

- ○ **공식 GitHub Action** = diff 를 안 넘긴다. 체크아웃을 탐색시키고 커밋 범위만 알려준다.
  **기본 리뷰 프롬프트를 동봉하지 않는다** — 사용자가 직접 준다.
- ○ **OpenAI 쿡북** = 반대다. `git --no-pager diff --unified=5 <BASE> <HEAD>` 를 **프롬프트 텍스트에
  직접 이어붙이고** `codex exec --output-schema ... --sandbox read-only -` 로 stdin 에 먹인다.
- ○ 쿡북 프롬프트 첫 문장이 §1 내장본과 **글자 단위로 같다** — 쿡북은 내장본의 파생이다.

**→ 1차 출처끼리 갈렸다. 문서로는 안 풀리고, §8 자체 실측이 답한다.**

## 3. 현장은 「diff 인라인 + 탐색 금지」로 수렴했다

- ○ **한 팀의 전후 측정**(가장 구체적인 외부 수치): 탐색시켰더니 330초 예산을 다 태우고
  **grep 출력 403KB · 빈 stdout · exit 124** 로 죽었고, 하류 에이전트가 그것을 "codex 미가용"으로 오보했다.
  「탐색 금지」 한 줄 + diff 인라인 후 **exit 0 · 324초 · 54,231 토큰 · 도구 호출 0회**.
  그들 결론: 103KB diff 위로는 상한을 올리기보다 **diff 를 쪼개거나 effort 를 낮추는 쪽**이 맞다.
- ○ **반대 실천도 의도적으로 존재한다** — diff 가 크면 오히려 자기가 수집하게 둔다.
  한 곳의 명시 임계 = **변경 파일 2개·약 150줄 이하면 전문 인라인, 넘으면 파일 목록 + shortstat 만 주고
  「read-only git 명령으로 직접 확인하라」**.
- ○ **diff 밖 지적을 담을 자리를 출력 형식에 따로 만드는 패턴**(한 곳의 이름은 `out_of_scope_notes`).
  ★안 만들면 모델이 그것을 결함 목록에 밀어 넣는다★. 실제 CI 예제의 프롬프트(발췌):
  - "REVIEW ONLY lines changed in the DIFF; ignore any other code."
  - "You may read some other files outside the DIFF ONLY for CONTEXT."
  - "If you notice issues outside the DIFF, put them in out_of_scope_notes, not in findings."
- ○ **반패딩은 「아부하지 마라」가 아니라 교정 규칙으로 한다**:
  "Prefer one strong finding over several weak ones. Do not dilute serious issues with filler.
  If the change looks safe, say so directly and return no findings."
- ○ **완료 마커 관습은 없다.** 대신 `-o <파일>` + **종료코드 + 비어있지 않음 + JSON 파싱 성공**의 3중 판정.

## 4. ★함정 — 둘은 메인이 직접 확인했다★

- ✅ **범위 플래그와 커스텀 지시를 같이 못 쓴다.** `codex exec review --base master "focus on security"` →
  `error: the argument '--base <BRANCH>' cannot be used with '[PROMPT]'`
- ○ ★**지시를 남기려고 범위 플래그를 빼면 에러 없이 「커밋 안 된 작업트리」로 떨어진다**★.
  프롬프트에 어떤 범위를 쓰든 CLI 가 리뷰어에게 먹이는 것은 바뀌지 않는다 —
  **엉뚱한 변경을 확신에 차서 리뷰한다.** (0.144.1 관측 · 0.154.0 재확인 안 함)
- ✅ **`codex exec resume` 은 `-s` 도 `-C` 도 안 받는다**(종료코드 2, API 호출 전 거절).
  샌드박스·작업 디렉터리는 **첫 호출에서 못 박히고 이후 못 바꾼다.**
  → fresh 와 resume 에 같은 플래그 문자열을 쓰는 껍데기는 resume 마다 죽는다.
- ○ **`--ephemeral` 과 resume 은 같이 못 쓴다** — 조용히 새 스레드가 생긴다(열린 버그).
- ○ **널리 복사되는 2차 문서 하나가 이 조합들을 되는 것처럼 적어 놨다.** 측정된 모든 버전에서 거짓이다.
- ○ 그 밖의 열린 이슈: SSE 스트림 전 무한 대기(타임아웃·재시도 없음) · 비-TTY 에서 stdin 대기 행 ·
  **stdio 가 TTY 에서 분리되면 출력 없이 조용히 죽음**(분리 실행 런처에 직결) · 부모 종료 후 자식 프로세스 잔존.

## 5. ★캐시 토큰은 플랜 한도를 태우는 것으로 보인다★

- △ 어떤 세션이 **5시간 창을 0% → 98% 로 소진**했는데 입력 2,340만 중 **96.8% 가 캐시**였다.
  다른 제보도 같은 방향(101초에 0→16%, 입력 167만 중 152만 캐시).
- ◆ **OpenAI 는 이에 답한 적이 없다** — 해당 이슈는 열린 채다. 초과분 credit 과금에서는 캐시 입력이
  약 1/10 요율로 **할인되어 계산**되지만, ChatGPT 플랜의 포함 한도는 토큰이 아니라 **"5시간당 메시지 수"**
  로 서술돼 있어 축이 다르다.
- ◆ **CLI 사용량은 cloud/IDE 와 같은 통을 쓴다**("Local messages and cloud chats share your plan's
  usage allowance"). 리셋 = 5시간 창 + 주간 한도 별도 가능.

**→ 「가능성 높음」이지 확정이 아니다. 다만 resume 을 한도 대책으로 기대하면 안 된다.**
★**그런데 §8 의 결론은 이 미확정과 무관하게 선다**★ — 캐시가 full 로 잡히든 할인되든 핀·재사용 양쪽 다
이기기 때문이다(§8 말미).

## 6. 판정은 종료코드로 하면 안 된다

- ○ **결함이 있어도 종료코드는 0 이다.** 출력을 파싱해야 한다.
- ◆ 한도 소진의 문서화된 판정 수단은 **`--json` 의 실패 이벤트**뿐이다.
  바이너리의 오류 분류: usage_limit_exceeded · usage_limit_reached · context_window_exceeded ·
  server_overloaded · quota_exceeded. ★**종료코드 매핑은 공식 문서에 없다.**★
- ◆ 사용자 대면 문구(바이너리 실측, 발췌): "You've hit your usage limit." ·
  "Usage limit reached. You've reached your usage limit." · "Your workspace is out of credits."
- ○ 현장은 stderr 를 정규식으로 긁는다 — 그게 최선의 상태이고, 경험으로 키운 목록이지 계약이 아니다.
  ★한 곳은 서드파티 MCP 서버의 인증 잡음을 **먼저 걸러낸다**★ — 매 실행 나타나면서 codex 자신의
  한도 상태와는 무관하기 때문이다.
- ○ ★**`--json` 없이 돌리면 전체 에이전트 대화(1만 줄+)가 터미널로 쏟아진다**★ — 그것이 도구 결과로
  들어가면 호출자 컨텍스트가 넘친다. 항상 로그 파일로 돌린다.

## 7. 도구 무관 — 「핀이 이긴다」에는 조건이 붙는다

- ◆ **AACR-Bench**: 비에이전트 전 방식이 **diff > 파일 > 저장소** 위계를 일관되게 따른다
  (예: 33.82% → 22.59% → 17.60%). ★**에이전트 방식만 역전**★(4.28% → 8.00%), 그마저 모델 의존적이다.
- ◆ 같은 벤치의 코멘트 분포(검증된 1,505건): **diff 수준 754(50.1%) · 파일 수준 518(34.4%) ·
  저장소 수준 233(15.5%)**. ★**「얼마나 열어줘야 하나」의 숫자가 여기서 나온다**★ —
  변경 파일 전문까지 주면 약 85% 가 사정권, hunk 만 주면 최대 절반이 원리적으로 밖이다.
- ◆ 에이전트 탐색은 **precision 을 크게 올린다**(한 모델 39.90% vs 컨텍스트 없음 8.70%) 대신
  recall 은 낮다(10.10%) — 고확신·저커버리지.
- ◆ **Cloudflare 프로덕션 30일 131,246 건** — 중앙값 **$0.98** · P99 $4.45 · 중앙 지연 3분 39초 ·
  캐시 적중 **85.7%**. 구조 = **diff 를 프롬프트에 안 넣고 파일별 patch 를 디스크에 써서 경로만 전달**,
  공유 컨텍스트도 파일로 빼 7개 sub-reviewer 에 중복 주입을 피한다(그들 표현 "7배 토큰 비용 곱셈" 회피).
  sub-reviewer 는 grep·read 로 **필요할 때만** 넓힌다. 위험도 3단 분기(2 / 4 / 7+ 에이전트).
- ◆ **Anthropic 의 Code Review 도 diff-only 가 아니다** — **diff + 주변 코드**를 병렬 에이전트가 보고,
  **별도 검증 단계**가 후보를 실제 코드 동작에 대조해 오탐을 거른다.
- ◆ **긴 입력은 낭비가 아니라 성능 저하다**(18개 프런티어 모델 대상) — 같은 정보를 담은 짧은 프롬프트가
  전 모델에서 긴 쪽을 이겼다. ★단 이것은 retrieval 벤치이지 코드리뷰 벤치가 아니다★(전이는 추정).
- ◆ **값싼 맥락 패턴의 선례** = 파일 내용 대신 **파일 목록 + 핵심 심볼 시그니처**를 의존 그래프 랭킹으로
  골라 작은 토큰 예산 안에 넣는 방식(기본 1k 토큰). ★절감 수치는 그 문서에 없다★.

### ★반론 — 핀이 실제로 잃는 것★

- 위 15.5% 가 **손실의 하한**이다(변경 파일 전문까지 줬을 때). hunk 만이면 최대 50%.
- §8 에서 **실제로 한 건 잃었다** — 그것이 이 반론의 우리 쪽 실물이다.
- 벤더 자체 벤치 하나가 전수 인덱싱의 우위를 주장하나 ★**방법론이 오탐을 점수에서 명시적으로 제외한다**★ —
  recall 만 재는 벤치라 recall-first 설계에 구조적으로 유리하다. 근거로 쓰기 어렵다.
- 컨텍스트 추가의 이득은 **모델 등급에 따라 부호가 갈린다** — 폐쇄형은 이득(+14.99% / F1 +72.17%),
  오픈형은 손해(-1.05% ~ -7.98%). ★가장 큰 이득을 준 것은 코드가 아니라 **이슈·PR 설명 같은 텍스트 맥락**★.

## 8. ★자체 실측 — 같은 리뷰 과업, 네 갈래★

같은 대상 하나를 네 갈래로 돌렸다. 대상 = `git diff 4e8a090~3 4e8a090 -- '*.rs'` (**988줄 · 58,740바이트 · 5파일**).
모델 = `gpt-5.6-sol`, effort `high`, 네 갈래 동일. 역할 오염 방지 2줄을 네 갈래 모두에 넣었다.

| 갈래 | 요청 | 입력 | 캐시 | 미캐시 | 출력 | 벽시계 | 진짜 리뷰? |
|---|---|---|---|---|---|---|---|
| **A** 탐색 허용·저장소 cwd | 26 | 2,207,103 | 2,074,752 | 132,351 | 9,528 | 309s | **예 — 결함 3건** |
| **B** 핀·중립 cwd·탐색 금지 | 7 | 246,053 | 201,856 | 44,197 | 6,922 | 172s | **예 — 결함 2건** |
| **C** resume 2회차(한계 증분) | 1 | 54,443 | 49,664 | **4,779** | **55** | **8s** | **예 — 0 도구 호출** |
| **C-대조** fresh 2회차 | 9 | 368,417 | 305,792 | 62,625 | 7,606 | 251s | 예 |

- **네 갈래 모두 진짜 리뷰를 냈다. 역할 오염 0/4** — 방어 2줄이 실효했다.
- **핀의 이득 = 입력 9배 · 미캐시 3배 · 시간 1.8배 · 왕복 26→7회.**
- **핀의 대가 = 결함 1건.** B 가 놓친 것은 **diff 밖 호출부를 읽어야 보이는 잠금 해제 경합**이었다.
  최상위 결함은 둘이 합의했다. ★n=1 — 대상 하나·회차 하나라 누락률이 아니다★.
- **지시가 통제로 먹혔다** — B 가 실행한 명령 6개가 전부 건네준 diff 파일 읽기였다. git 도 저장소도 안 건드렸다.
- **resume 2회차 = 입력 6.8배 · 미캐시 13배 · 출력 138배 · 시간 31배 싸다.** 도구 호출 0.

### ★측정 자체가 틀릴 뻔했다 — 이 함정이 제일 중요하다★

**`--json` 의 `turn.completed.usage` 는 그 턴의 값이 아니라 세션 누적값이다.**
C 는 모델 왕복 **1회·도구 0회**인데 `input_tokens: 300,496` 으로 보고했다 — 전체 컨텍스트가 약 55k 인데
불가능한 값이다. 세션 로그가 정확히 설명한다: 그 요청의 실제 입력은 54,443 이고,
300,496 = B 의 246,053 + 54,443 이다.

- **요청별 값을 읽는 자리** = `~/.codex/sessions/YYYY/MM/DD/rollout-*-<uuid>.jsonl` 의
  `payload.type == "token_count"` → `info.last_token_usage`(이 요청) / `info.total_token_usage`(누적).
- ★**이 오독이 직전 기록의 「resume 은 raw 입력이 더 크다」를 만들었다**★ — 세션 총계와 단일 요청을
  견준 것이었다. 정정 = resume 2회차의 실제 입력은 54,443 이고 **91% 가 캐시**다.
- **「호출당 17만」이라는 옛 전제도 스케일이 틀렸다** — 실제 탐색 리뷰는 26회 왕복 누적 220만이다.
  빈 디렉터리 16.5k 는 단일 요청 값이라 둘을 빼는 연산이 애초에 성립하지 않았다.

### 결론이 미확정 전제와 무관하게 선다

§5 의 미확정(캐시가 한도에 full 로 잡히나)이 어느 쪽으로 판명되든:

- full 로 잡히면 **A 의 220만**이 문제의 숫자 → 핀이 **9배** 이긴다.
- 할인되면 **미캐시 13만**이 문제의 숫자 → 핀이 **3배** 이긴다.

resume 도 같다(6.8배 또는 13배). **그러니 §5 의 답을 기다리지 않고 둘 다 채택할 수 있다.**

### 재현 레시피

```sh
# A — 탐색 허용
codex exec --json -o out_A.md --skip-git-repo-check \
  -s read-only -c model_reasoning_effort="high" -C "<repo>" \
  "$(cat prompt_A.txt)" < /dev/null > jsonl_A.jsonl 2> err_A.txt

# B — 핀(중립 cwd · diff 를 ./target.diff 로 건넴 · 프롬프트에서 탐색 금지)
codex exec --json -o out_B.md --skip-git-repo-check \
  -s read-only -c model_reasoning_effort="high" -C "<중립 디렉터리>" \
  "$(cat prompt_B.txt)" < /dev/null > jsonl_B.jsonl 2> err_B.txt

# UUID 회수 = JSONL 첫 줄의 thread.started
UUID=$(head -1 jsonl_B.jsonl | grep -o '[0-9a-f-]\{36\}')

# C — resume. ★-s 도 -C 도 붙이면 안 된다★ (§4). 세션의 디렉터리로 먼저 이동한다.
cd "<중립 디렉터리>" && codex exec resume "$UUID" --json -o out_C.md --skip-git-repo-check \
  -c model_reasoning_effort="high" \
  "$(cat prompt_C.txt)" < /dev/null > jsonl_C.jsonl 2> err_C.txt
```

- 원시 산출물(프롬프트·diff·JSONL·리뷰 본문)은 세션 스크래치패드에 있고 **세션과 함께 사라진다.**
- 사소하지만 혼동거리: `< /dev/null` 을 붙여도 `Reading additional input from stdin...` 이 stderr 에 찍힌다 —
  오류 신호로 읽지 말 것.

## 쟁점·한계

1. ★**적대 리뷰 미실시**★ — 위 전부가 확증-편향 점검을 안 거쳤다. 이 문서의 상태 라벨이 그것이다.
2. **캐시 토큰과 플랜 한도**(§5) — 사용자 제보뿐, 벤더 미확인. 단 §8 결론은 여기 안 걸린다.
3. **우리 조건이 벤치와 다르다**(핵심 결론 4) — 에이전트 루프라 「diff 가 이긴다」를 그대로 못 옮긴다.
4. **§8 의 품질 축은 n=1** — 대상 하나·회차 하나·한 패스. 「핀이 결함을 놓친다」는 실물이지 비율이 아니다.
   **A 의 탐색량 자체도 비결정적이다** — 26회 왕복은 한 번의 뽑기지 평균이 아니다.
5. **`fork` 미측정** — 4회 예산 밖. 맥락 1회 적재 후 렌즈별 분기가 되는지는 여전히 모른다.
6. **한도 사망의 겉모습 미측정** — 어느 갈래도 안 죽었다. 종료코드·문구를 아직 모른다
   (다만 **인자 파싱 거절 = 종료코드 2 · API 호출 0** 은 확인했다).
7. **resume 이 3회차 이후에도 싼지 미측정** — 이력이 매 턴 자라므로 fresh 와의 손익분기가 있을 텐데
   재지 않았다. **캐시 유지 시간도 모른다** — 실측은 몇 분 간격이었다(사용자 판단: 지금은 우선순위 아님).
8. **웹 출처는 전부 수집자의 요약 경유**다(◆ 바이너리 추출과 ✅ 로컬 확인분 제외). 인용 문구를 원문에서
   직접 본 것이 아니다.
9. 수집자 하나가 **결과 없는 제안 논문 하나를 증거로 쓰지 말라고 명시**했다 — 반영했다(인용하지 않음).
