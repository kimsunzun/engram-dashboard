The user: 「모든 컨텐츠가 하나하나 다 그런게 걸린다 — 공용으로 시스템하냐 그냥 가냐」 (every piece of content gets caught by this one by one — do we build a shared system or just move on?).
- **Method:** three collectors — ① an internal exhaustive pass (Opus) ② direct peer source (Opus) ③ general pattern documents (Sonnet). The main session re-checked the key claims against the source (「메인 재확인」 (main-session re-check) in each section).
- **Confidence:** certain = source · primary document checked · likely = partly checked + inference · uncertain = not checked
- **Constraints:** ADR-0035 (layout is owned by the backend · the frontend does not do optimistic updates) · CLAUDE.md 「LLM-우선 제어」 (LLM-first control) (a human and an LLM shake the same handle — where the guard is placed also applies to the LLM path)

## Conclusions

- **Our app's human writes have no 「전체 교체 쓰기」 (full-replace write)** (one in-window command that the LLM·cdp calls is the exception — below). All of the roughly 30 human writes are intent · absolute-value writes with a target id, and the shell does every layout write as a read-modify-write inside the lock and notifies after releasing the lock. A late-arriving older snapshot is dropped by version comparison (`src/store/viewStore.ts:287` — main-session re-check). So **human writes have no write that overwrites the webview copy wholesale.** ★One exception (certain — found in the 2026-09-30 review)★: the in-window command `layout.setSlotContent` (the LLM·cdp path called through window JS — the human UI does not call it) **fills the missing `show_*` cells of a usage slot from the webview copy** and sends them to `set_slot_content` as a full payload (`mergeUsageShows` in `src/commands/tabCommands.ts`) — if the shell-side cells changed in between, it overwrites them. It is already written down as a postponed follow-up (TRD S21 usage-limit-slot §3 #102 ⑤ — switching to per-cell `set_usage_slot` makes it atomic). However, **a write accepted later can overwrite an earlier write (last writer wins)** — version comparison filters only older snapshots, not competing writes (`src/store/viewStore.ts:281-287`), `set_slot_content` replaces even a filled slot unconditionally (`src-tauri/src/layout/manager.rs:565`), human calls are not serialized, and there is no guarantee that the lock order matches the click order (supplied by the adversarial review — not re-checked by the main session). (certain — no full replace in human writes · the exception above / likely — the overwrite path)
- **What actually gets caught falls into three groups.** (likely — the consequences are mostly inferred, the paths are checked)
  - **Duplicate effects (no guard):** tab `+` twice → two tabs (`src/components/layout/TabBar.tsx:193`) · splitting the same slot twice · the slot menu's agent exit · agent creation. **The LLM path is caught too** — `spawn_into` does the daemon spawn (asynchronous) first, before taking the layout lock (`src-tauri/src/layout/apply.rs:574`), so concurrent calls can each create an agent + tab, and if placement fails the spawned agent survives. The frontend registry does not serialize either (`src/commands/registry.ts:120`). (supplied by the adversarial review — not re-checked by the main session)
  - **A relative operation computed from an old value (intent lost):** the usage display toggle (`!current` — the second one resends the same value) · Ctrl+Tab (computes the next tab from the old `active` — pressing twice moves only one step, `src/commands/tabCommands.ts:84-92` main-session re-check).
  - **The target is already gone:** closing a tab · slot, pop-out, closing a window twice → the second time the shell returns `Err` as a value and the frontend only logs it (harmless).
- **Guards differ from component to component.** The agent list `busyRef` (until the response — `src/components/agent/AgentList.tsx:65,137` main-session re-check) · the preset palette ref guard · the usage ⟳ 「조회 중 무시」 (ignore while querying) · the queued-input ✕ `disabled` · the folder dialog modal. **The layout family has no frontend guard at all.**
- **Peers are in two camps.** ① change the screen first and re-lay the pending intent on top of the server state (t3code · orca — only remote sessions · GitHub edits, the core tabs · layout are not comparison targets (table below) · paseo · vibe-kanban) ② the client sends only the intent, and the server applies it in order and redraws (zellij · herdr). In one case of ① (orca) there is a **shared hook that drops the second input while the same key is being processed** (orca `useImmediateMutation` — main-session re-check · used for GitHub PR·issue edits). But this hook checks `pendingRef.current` while it puts the key in with `setPendingKeys` and the ref is synchronized at render, so two calls before a render can both pass (`src/renderer/src/hooks/useImmediateMutation.ts:8-30` · supplied by the adversarial review). **The pattern is supported, but it is not a synchronous guard.**
- **General literature:** nobody recommends 「낙관적 갱신 + 무방어」 (optimistic update + no defense) — concurrent optimistic updates being reverted by a late reflection is a documented failure. Established escape hatches: per-target serialization (TanStack Query `scope.id` — changes in the same scope are **queued and resumed in turn**, not dropped) · disabling the action button while pending (the React `useOptimistic` docs example) · sync-engine-style numbering and reapplication (Replicache · Linear). There is advice to avoid optimistic updates when server logic would have to be duplicated on the client (TkDodo).

## Options

| | What | Solves | Does not solve | Cost | ADR-0035 |
|---|---|---|---|---|---|
| **O1 status quo** | add per-component guards when needed | — | duplicate effects · lost intent | 0 | kept |
| **O2 shared 「처리 중 무시」 (ignore while in progress)** | an in-progress marker per key (command + target) — re-input of the same key is dropped until it is released (orca style). **The location is the crux** — if it is attached only to `dispatch` (`src/commands/dispatch.ts:15`), UI paths that call store functions directly are missed (for example the tab bar calls `createTab` directly — `src/components/layout/WindowLayout.tsx:179`). It must sit where all human writes pass (the store/invoke layer) or on both sides. **The release point** is also the crux — releasing at the command response is not completion of the reflection: the shell emits the event before the response (`src-tauri/src/layout/apply.rs:190`) but the frontend applies the event through a separate listener (`WindowLayout.tsx:69`), so the guard can be released before the view is updated. It must be released at the time the reflection is applied (version advance) or at response + a timeout fallback, and the former is exact but risks locking if an event is lost, while the latter is simple but leaves a gap — a trade-off. (supplied by the adversarial review) | duplicate effects (tab `+` · split · exit · create) · toggling the same cell twice becomes one | lost intent (Ctrl+Tab twice = one step) — without a per-command policy, even a legitimate second input is dropped | small — once the location · release point are decided, one place | kept |
| **O2b per-target serial queue** | instead of dropping the second input of the same key, apply it on top of the latest state after the first processing finishes (TanStack `scope.id` style) | orders duplicate effects without losing intent · preserves an intended second create·move | unnecessary delay when the second is meaningless anyway (re-clicking a checkbox) · needs queue length · cancellation policy | larger than O2 — queue · release point · failure propagation | kept |
| **O3 the shell computes relative operations** | send relative operations such as flip · next tab as an 「의도」 (intent) and have the shell compute inside the lock (zellij style) | lost intent (twice = twice) | duplicate effects | one shell command per operation | kept |
| **O4 optimistic update + reapplying pending intent** | change the screen first and re-lay the pending intent on top of the server snapshot (t3code style) | everything + perceived latency | — | large — pending list · numbering · rollback, duplicating server logic on the client | **overturns it** |

- **O2 and O3 overlap on relative operations such as `tab.next` (`src/commands/tabCommands.ts:85`).** If O2 covers that command, O2 drops again the 「두 번 = 두 번」 (twice = twice) that O3 tries to preserve. To use them together, a **per-command policy table** (drop / serial queue / pass through) or an exemption list is needed. If applied across the board without a policy, legitimate re-input is lost, such as the second Ctrl+Tab · an intended second tab creation. For the checkbox that triggered this document, 「버림」 (drop) is the same as the current behavior.
- **LLM path:** if O2 is attached only to `dispatch` (the human path — `fireAndForget`), the LLM bus path stays as it is. 「LLM 은 응답을 기다린 뒤 다음 호출을 한다」 (the LLM waits for the response and then makes the next call) is an assumption on the caller side, not a guard — if parallel calls · retries come, the `spawn_into` duplicate creation · orphan agent in 「중복 효과」 above happens as is (the registry does not serialize — `src/commands/registry.ts:120`, supplied by the adversarial review). To cover the LLM path, a guard on the shell side (a lock before the spawn, or an idempotency key) is needed.
- **Response vs reflection:** the existing guard (`busyRef`) is released at the **response**. The order between the response and the reflection event is not guaranteed (the shell releases the lock, notifies, and then responds — normally the reflection comes first, but the channels differ so it is not guaranteed, inference). Releasing at the response is simple but can release before the reflection, and releasing at the reflection (version advance) is exact but locks if the event is lost — see the release-point item of O2.

## Rejected candidates (ADR rejected-alternative candidates)

- **O4 optimistic update** — it overturns ADR-0035 and the layout computation (focus after split · close, etc.) would have to be duplicated in the frontend. Our app uses local IPC, so latency is a few milliseconds and the perceived gain is small (estimate — not measured).
- **Version-based CAS writes (each request carries the expected version and the shell compares)** — the view snapshot version already exists (`src/store/viewStore.ts:287`) but there is no comparison on the write side. After receiving a rejection a retry UX is newly needed, and there is no peer precedent (collector: none found).

## Adversarial review (codex · 2026-09-30)

Verdict needs-fixes. The evidence (file:line · URL) is supplied by the reviewer and the main session did not re-check it against the source (marked on each item).

## What to decide when handing over to the follow-up topic

- A per-command policy table — which commands are drop / serial queue / pass through (checkbox = drop, `tab.next` · tab creation = candidates under review)
- Guard location — does the store/invoke layer cover even direct calls (`createTab`, etc.), or is it doubled with `dispatch`
- Release point — reflection applied (version advance) vs command response vs response + timeout fallback
- LLM path scope — does it include shell-side guards such as a lock before the spawn in `spawn_into`, or an idempotency key
- Display — whether to make the disabled state visible or drop quietly
- ★**Premise — it is not only local**★ (user 2026-09-30): 「로컬이 메인이지만 저 너머의 데몬끼리 오케스트레이션하고 그 모든 데몬이 한 클라이언트에 붙는 형태가 될 것」 (local is the main case, but it will become a form where daemons far away orchestrate each other and all those daemons attach to one client). So **the round-trip time differs by state owner** — layout (shell · same PC) is short, and state held by a remote daemon (agents · usage, etc.) is a network round trip. 「로컬 IPC 라 짧다」 (it is short because it is local IPC) (the O4 rejection basis) does not hold on the remote-daemon side. Also decide whether to split policy · display per owner, and how to assign order · numbers when there are several daemons.

- **I did not find a primary document that states the textbook answer that fits our structure exactly — 「데몬이 상태를 쥐고 이벤트로 밀어 준다」 (the daemon holds the state and pushes it as events).** The closest is to use the request-cache approach with confirmation-wait as the default, and wire daemon events so that they update the cache (collector's inference).

## Discussion summary — the starting point of the follow-up topic (user and main session · 2026-09-30)

- **In a word = split operations into groups and decide one handling per group.** A new operation only chooses which group it belongs to (no per-operation discussion).

  | Group | Examples | Handling (starting proposal) |
  |---|---|---|
  | The screen itself | opening a popup · scrolling · text being typed | immediate |
  | Twice is an accident | create · delete · exit | the shell already blocks delete · close · exit (no target → `Err`) · **create cannot be blocked** (tab `+` twice = two tabs) → if the shell processes an idempotency key per request exactly once (Stripe style), it is unified on the server side and no screen guard is needed |
  | Twice means twice | flip · move · next tab | send the intent and have the server (shell · daemon) compute in order (zellij · herdr style) |
  | Far away and slow | remote daemon operations | one of the two above + measure, and if it is sluggish, optimistic update only for that operation · make 「처리 중」 (in progress) visible |

- **Structural recognition:** we are **daemon → shell → screen**, three tiers, and the shell is a server to the screen too. Three tiers themselves are common (orca = terminal daemon → Electron core → screen). ★**The unusual point = the middle layer (shell) also holds the layout**★ — in orca the screen store holds the layout and it changes immediately. We put it in the shell so that the LLM and a human use the same handle (「LLM-우선 제어」) · so that several windows see one state (ADR-0035·0057), and the price is that even tab creation is a round trip. 「셸이 레이아웃을 쥐는 곳이 우리뿐」 (we are the only ones whose shell holds the layout) means we did not see it within the surveyed range, not that it was verified.
- **Optimistic update (screen first → reconcile when the server answers) is not a bad approach but a tool to apply selectively only to slow places** — price = duplicating server computation on the screen · reverting on a late reflection · rollback. For layout (same PC) there is almost no gain (ADR-0035 also forbids it).
