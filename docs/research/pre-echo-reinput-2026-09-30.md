# 반영 전 재입력 — 앱 전체 실태와 선례 (설계 서베이)

- **상태:** medium 조사 · 2026-09-30 · 적대 리뷰 반영(needs-fixes → 수정) · 결정 = 이번 브랜치(사용량 슬롯)는 현행 유지, 공용 처리는 후속 주제(사용자 결정 2026-09-30)
- **계기:** 사용량 슬롯 팝업 체크박스를 반영(echo) 전에 같은 칸을 다시 누르면 두 번째 클릭이 사실상 무시된다는 리뷰 지적(ADR-0257 · TRD S21 usage-limit-slot §3 #102 ⑤). 사용자: 「모든 컨텐츠가 하나하나 다 그런게 걸린다 — 공용으로 시스템하냐 그냥 가냐」.
- **방법:** 수집자 셋 — ① 내부 전수(Opus) ② 직접 피어 소스(Opus) ③ 일반 패턴 문서(Sonnet). 메인이 핵심 클레임을 소스에서 재확인했다(각 절 「메인 재확인」).
- **확신도:** 확실 = 소스·1차 문서 확인 · 가능성 높음 = 일부 확인 + 추론 · 불확실 = 미확인
- **제약:** ADR-0035(레이아웃은 백엔드 소유 · 프론트는 낙관적 갱신을 하지 않는다) · CLAUDE.md 「LLM-우선 제어」(사람과 LLM 이 같은 핸들을 흔든다 — 가드를 어디 두느냐가 LLM 경로에도 걸린다)

## 결론

- **우리 앱의 사람 쓰기엔 「전체 교체 쓰기」가 없다**(LLM·cdp 가 부르는 창 안 명령 하나는 예외 — 아래). 사람 쓰기 약 30개 전부가 대상 id 를 가진 의도·절대값 쓰기이고, 셸은 모든 레이아웃 쓰기를 락 안의 읽기-수정-쓰기로 하고 락을 놓은 뒤 알린다. 늦게 온 옛 스냅숏은 버전 비교로 버린다(`src/store/viewStore.ts:287` — 메인 재확인). 그래서 **사람 쓰기에는 웹뷰 사본을 통째로 덮어쓰는 쓰기가 없다.** ★예외 하나(확실 — 2026-09-30 리뷰 적출)★: 창 안 명령 `layout.setSlotContent`(창 JS 로 부르는 LLM·cdp 경로 — 사람 UI 는 부르지 않는다)는 사용량 슬롯의 빠진 `show_*` 칸을 **웹뷰 사본에서 채워** `set_slot_content` 전량으로 보낸다(`src/commands/tabCommands.ts` 의 `mergeUsageShows`) — 그 사이 셸 쪽 칸이 바뀌었으면 덮는다. 이미 미룬 후속으로 적혀 있다(TRD S21 usage-limit-slot §3 #102 ⑤ — 칸별 `set_usage_slot` 으로 돌리면 원자적이 된다). 다만 **나중에 받아들여진 쓰기가 먼저 쓴 것을 덮어쓸 수는 있다(마지막 쓴 쪽 승리)** — 버전 비교는 옛 스냅숏만 거르지 경쟁하는 쓰기는 못 거른다(`src/store/viewStore.ts:281-287`), `set_slot_content` 는 찬 슬롯도 무조건 교체한다(`src-tauri/src/layout/manager.rs:565`), 사람 호출은 직렬화되지 않고 락 순서가 클릭 순서와 같다는 보장도 없다(적대 리뷰 제공 — 메인 미재확인). (확실 — 사람 쓰기의 전체 교체 없음 · 위 예외 / 가능성 높음 — 덮어쓰기 경로)
- **실제로 걸리는 것은 세 부류다.** (가능성 높음 — 결과는 대부분 추론, 경로는 확인)
  - **중복 효과(가드 없음):** 탭 `+` 두 번 → 탭 둘(`src/components/layout/TabBar.tsx:193`) · 같은 슬롯 분할 두 번 · 슬롯 메뉴의 에이전트 종료 · 에이전트 생성. **LLM 경로도 걸린다** — `spawn_into` 는 레이아웃 락을 잡기 전에 데몬 스폰(비동기)을 먼저 해서(`src-tauri/src/layout/apply.rs:574`) 동시 호출이 각자 에이전트+탭을 만들 수 있고, 배치가 실패하면 스폰된 에이전트가 살아남는다. 프론트 레지스트리도 직렬화하지 않는다(`src/commands/registry.ts:120`). (적대 리뷰 제공 — 메인 미재확인)
  - **상대 조작이 옛 값에서 계산됨(의도 유실):** 사용량 표시 토글(`!current` — 두 번째가 같은 값 재전송) · Ctrl+Tab(옛 `active` 에서 다음 탭 계산 — 두 번 눌러도 한 칸, `src/commands/tabCommands.ts:84-92` 메인 재확인).
  - **대상이 이미 없음:** 탭·슬롯 닫기, 팝아웃, 창 닫기 두 번 → 둘째는 셸이 `Err` 를 값으로 돌려주고 프론트는 로그만 남긴다(무해).
- **가드는 컴포넌트마다 제각각이다.** 에이전트 목록 `busyRef`(응답까지 — `src/components/agent/AgentList.tsx:65,137` 메인 재확인) · 프리셋 팔레트 ref 가드 · 사용량 ⟳ 「조회 중 무시」 · 대기 입력 ✕ `disabled` · 폴더 대화상자 모달. **레이아웃 계열엔 프론트 가드가 하나도 없다.**
- **피어는 두 진영이다.** ① 화면을 먼저 바꾸고 대기 중인 의도를 서버 상태 위에 다시 얹는다(t3code · orca — 원격 세션·GitHub 편집만, 본체 탭·레이아웃은 비교 대상이 아니다(아래 표) · paseo · vibe-kanban) ② 클라이언트는 의도만 보내고 서버가 순서대로 적용해 다시 그린다(zellij · herdr). ①의 한 사례(orca)로 **같은 키가 처리 중이면 두 번째 입력을 버리는 공용 훅**이 있다(orca `useImmediateMutation` — 메인 재확인 · 쓰는 곳은 GitHub PR·이슈 편집). 단 이 훅은 `pendingRef.current` 를 검사하면서 키는 `setPendingKeys` 로 넣고 ref 는 렌더 때 맞춰지므로, 렌더 전에 두 번 부르면 둘 다 통과할 수 있다(`src/renderer/src/hooks/useImmediateMutation.ts:8-30` · 적대 리뷰 제공). **패턴은 지지하지만 동기 가드는 아니다.**
- **일반 문헌:** 「낙관적 갱신 + 무방어」를 권하는 곳은 없다 — 동시 낙관적 갱신이 늦은 반영에 되돌려지는 것이 문서화된 실패다. 확립된 탈출구: 대상별 직렬화(TanStack Query `scope.id` — 같은 scope 의 변경을 **큐에 세워 차례로 재개**하며 버리지 않는다) · 대기 중 액션 버튼 비활성(React `useOptimistic` 문서 예시) · 동기화 엔진식 번호 매기기와 재적용(Replicache · Linear). 서버 로직을 클라이언트에 복제해야 하면 낙관적 갱신을 피하라는 권고가 있다(TkDodo).

| **O2 공용 「처리 중 무시」** | 키(명령 + 대상)별 처리 중 표식 — 풀릴 때까지 같은 키 재입력을 버린다(orca 형). **위치가 관건** — `dispatch`(`src/commands/dispatch.ts:15`)에만 걸면 store 함수를 직접 부르는 UI 경로(예: 탭 바가 `createTab` 을 직접 호출 — `src/components/layout/WindowLayout.tsx:179`)를 놓친다. 사람 쓰기가 모두 지나는 곳(store/invoke 층) 또는 양쪽에 둬야 한다. **해제 시점**도 관건 — 명령 응답에서 풀면 반영 완료가 아니다: 셸은 응답 전에 이벤트를 내지만(`src-tauri/src/layout/apply.rs:190`) 프론트는 별도 리스너로 이벤트를 적용하므로(`WindowLayout.tsx:69`) 뷰가 갱신되기 전에 가드가 풀릴 수 있다. 반영 적용(버전 전진) 시점 또는 응답 + 타임아웃 폴백에서 풀어야 하고, 앞쪽은 정확하지만 이벤트 유실 시 잠기는 위험이, 뒤쪽은 단순하지만 틈이 남는 절충이 있다. - **O2 와 O3 는 `tab.next`(`src/commands/tabCommands.ts:85`) 같은 상대 조작에서 겹친다.** O2 가 그 명령까지 덮으면 O3 가 살리려는 「두 번 = 두 번」을 O2 가 다시 버린다. 함께 쓰려면 **명령별 정책 표**(버림 / 직렬 큐 / 통과)나 면제 목록이 필요하다. 정책 없이 일괄 적용하면 두 번째 Ctrl+Tab · 의도한 두 번째 탭 생성처럼 정당한 재입력이 유실된다. 이 글이 계기로 삼은 체크박스는 「버림」이 현행 동작과 같다.
- **LLM 경로:** O2 를 `dispatch`(사람 경로 — `fireAndForget`)에만 걸면 LLM 버스 경로는 그대로다. 「LLM 은 응답을 기다린 뒤 다음 호출을 한다」는 호출자 쪽 가정이지 가드가 아니다 — 병렬 호출·재시도가 오면 위 「중복 효과」의 `spawn_into` 중복 생성·고아 에이전트가 그대로 난다(레지스트리는 직렬화하지 않는다 — `src/commands/registry.ts:120`, 적대 리뷰 제공). LLM 경로를 덮으려면 셸 쪽(스폰 전 락 또는 멱등 키)에 가드가 필요하다.
- **응답 vs 반영:** 기존 가드(`busyRef`)는 **응답**에서 풀린다. 응답과 반영 이벤트는 순서가 보장되지 않는다(셸은 락을 놓고 알린 뒤 응답한다 — 보통 반영이 먼저지만 채널이 달라 보장은 아니다, 추론). 응답 해제는 단순하나 반영 전에 풀릴 수 있고, 반영(버전 전진) 해제는 정확하나 이벤트가 유실되면 잠긴다 — O2 의 해제 시점 항 참조.

## 거부 후보 (ADR 거부 대안 후보)

- **O4 낙관적 갱신** — ADR-0035 를 뒤집고, 레이아웃 계산(분할·닫기 후 포커스 등)을 프론트에 복제해야 한다. 우리 앱은 로컬 IPC 라 지연이 수 밀리초여서 체감 이득이 작다(추정 — 미측정).
- **버전 기반 CAS 쓰기(요청마다 기대 버전을 싣고 셸이 비교)** — 뷰 스냅숏 버전은 이미 있으나(`src/store/viewStore.ts:287`) 쓰기 쪽 비교는 없다. 거절을 받은 뒤 재시도 UX 가 새로 필요하고 피어 선례가 없다(수집자: 찾은 곳 없음).

## 공백

- 내부: 에이전트 모니터링 선택기의 가드 · `agent.spawn`·`window.create` 를 쏘는 UI 위치 · LLM 경로 `spawn_into` 중복 동작은 조사자가 추적하지 않았고 적대 리뷰가 경로를 지적했다(메인 미재확인). 「중복 효과」 결과는 대부분 경로 확인 + 결과 추론이다.
- 피어: tmux 제어 모드 · VS Code · Zed 는 보지 않았다. t3code 가 `reorderPin` 을 서버에서 어떻게 적용하는지 · paseo 레이아웃 소유권은 미확인.
- 문헌: RTK Query · Apollo · Zero · CAS 문서는 읽지 않았다. 「처리 중 비활성」을 권고로 명시한 1차 문서는 못 찾았으나, React `useOptimistic` 문서 예시가 대기 중 버튼 비활성을 보여 준다(적대 리뷰 지적 — 「문헌 공백」 서술은 정정).

## 적대 리뷰 (codex · 2026-09-30)

판정 needs-fixes. 근거(파일:줄·URL)는 리뷰어 제공이며 메인이 소스에서 재확인하지 않았다(각 항목에 표시).

1. **(high) O2 가 `dispatch` 에만 있으면 직접 호출 UI 를 놓친다** — 탭 바가 `WindowLayout.tsx:179` 에서 `createTab` 을 직접 부른다(`dispatch.ts:15` 우회). → O2 행에 위치 요건(store/invoke 층 또는 양쪽) 반영.
2. **(high) 응답에서 풀면 반영 완료가 아니다** — 셸은 응답 전에 이벤트를 내지만(`apply.rs:190`) 프론트는 별도 리스너로 적용한다(`WindowLayout.tsx:69`). → O2 행·「응답 vs 반영」에 해제 시점 대안(버전 전진 / 응답 + 타임아웃)과 절충 반영.
3. **(high) 어떤 반복을 두 번으로 셀지 명시 필요** — 두 번째 Ctrl+Tab · 의도한 두 번째 탭 생성을 버리면 의도 유실. → 명령별 정책(버림 / 직렬 큐 / 통과) 도입, 체크박스 사례는 「버림」으로 명기(O2 · 겹침 항 · 후속 목록).
4. **(medium) O2 와 O3 가 `tab.next`(`tabCommands.ts:85`)에서 겹친다** — 「겹치지 않아 함께 쓸 수 있다」 문장 정정: 명령별 정책·면제가 있어야 병용.
5. **(high) 「값이 조용히 날아가는 부류는 사실상 없다」는 과장** — 버전 검사는 옛 스냅숏만 거르고(`viewStore.ts:281-287`) 경쟁 쓰기는 못 거른다, `set_slot_content` 는 무조건 교체(`manager.rs:565`). → 결론 문구를 「웹뷰 사본 통째 교체 쓰기는 없으나 나중에 받아들여진 쓰기가 앞선 쓰기를 덮는다(마지막 쓴 쪽 승리)」로 수정.
6. **(medium) orca 훅은 동기 가드가 아니다** — `pendingRef.current` 검사 + `setPendingKeys` 등록, ref 는 렌더 시 동기화(`useImmediateMutation.ts:8-30`). → 「패턴은 지지, 동기 가드는 아님」으로 하향(결론 · 제품별 근거).
7. **(medium) TanStack `scope.id` 는 버리지 않고 큐잉·재개한다** — 귀속 정정, O2b 「대상별 직렬 큐」(두 번째 입력이 대기 후 최신 상태에서 적용)를 O2 「처리 중 무시」와 구분해 추가.
8. **(medium) 문헌 공백 주장이 틀렸다** — React `useOptimistic` 문서가 대기 중 버튼 비활성을 보인다. → 「일반 문헌」 항 · 제품별 근거 · 공백 줄 정정.
9. **(medium) LLM 중복 생성 누락** — `spawn_into` 가 락 전에 비동기 데몬 스폰을 하고(`apply.rs:574`) 동시 호출이 각자 에이전트+탭을 만들거나 배치 실패 시 고아 에이전트가 남는다, 레지스트리도 직렬화 안 함(`registry.ts:120`). 「LLM 은 응답을 기다린다」는 호출자 가정이지 가드가 아니다. → 결론 위험 항 · LLM 경로 항 · 공백에 반영.
10. **(low) O4 거부 사유 「지연 수 ms」 미측정** — 「추정(미측정)」 표기.

## 후속 주제로 넘길 때 정할 것

- 명령별 정책 표 — 어떤 명령이 버림 / 직렬 큐 / 통과인가(체크박스 = 버림, `tab.next` · 탭 생성 = 후보 검토)
- 가드 위치 — store/invoke 층으로 직접 호출(`createTab` 등)까지 덮는가, `dispatch` 와 이중으로 두는가
- 해제 시점 — 반영 적용(버전 전진) vs 명령 응답 vs 응답 + 타임아웃 폴백
- LLM 경로 범위 — `spawn_into` 의 스폰 전 락·멱등 키 등 셸 쪽 가드를 포함하는가
- 표시 방식 — 비활성 상태를 보이게 할지, 조용히 버릴지
- ★**전제 — 로컬만이 아니다**★(사용자 2026-09-30): 「로컬이 메인이지만 저 너머의 데몬끼리 오케스트레이션하고 그 모든 데몬이 한 클라이언트에 붙는 형태가 될 것」. 그래서 **상태 주인마다 왕복 시간이 다르다** — 레이아웃(셸 · 같은 PC)은 짧고, 원격 데몬이 쥔 상태(에이전트 · 사용량 등)는 네트워크 왕복이다. 「로컬 IPC 라 짧다」(O4 거부 근거)는 원격 데몬 쪽엔 성립하지 않는다. 주인별로 정책·표시를 가를지, 데몬이 여럿일 때 순서·번호를 어떻게 매길지도 정할 것.

## 덧붙임 — 클라이언트 상태 / 서버 상태 분리 방식과 라이브러리 (light · 2026-09-30)

사용자 질문: 「결국 클라 자체적인 것과 서버 오가는 것의 처리를 나눠야 하는 것 아니냐 — 라이브러리도 있지 않냐」. 수집자 1명(Sonnet · 4회 조회) · 적대 리뷰 없음(light).

| 방식 | 메커니즘 | 처리 중 · 재입력 | 라이브러리 | 출처 · 확신도 |
|---|---|---|---|---|
| 요청-캐시(서버 상태 캐시 + 변경) | 서버 데이터는 캐시, 쓰기는 mutation → 무효화·재조회. 전역 스토어엔 화면 상태만 | mutation 마다 `isPending` · 중복 입력은 앱 몫(비활성) · 낙관적 갱신은 선택(기본은 확인 대기) · 같은 범위 직렬화 `scope`(본문 조사에서 확인 — tanstack.com/…/guides/mutations) | TanStack Query · RTK Query | tanstack.com/query/latest/docs/framework/react/guides/does-this-replace-client-state · …/optimistic-updates · redux.js.org/tutorials/essentials/part-7-rtk-query-basics — 확실. 「푸시 이벤트로 캐시를 채우기」는 읽은 문서에 없음(수동 연결) |
| 동기화 엔진 | 모든 서버 상태가 한 층을 지남 · 로컬 적용 + 순번 붙은 대기 변경 · 서버가 순서대로 실행 · 당겨오면 서버 상태로 되감고 대기 변경 재적용 | 설계상 직렬 · 기본 낙관적 | Replicache (Zero · ElectricSQL 은 같은 계열 — 미확인. vibe-kanban 이 ElectricSQL/TanStack DB 를 씀 — 본문 피어 표) | doc.replicache.dev/concepts/how-it-works — 확실 |
| 의도만 보내고 서버가 권위 | 클라이언트는 의도를 보내고 서버가 돌려준 것만 그린다(요청-캐시에서 낙관적 갱신을 뺀 것과 같다) | 1차 출처 없음 — 의도별 처리 중 표식이나 비활성 | (라이브러리 아님 — zellij · herdr 가 이 모양) | 불확실(수집자 추론) |

- **「데몬이 상태를 쥐고 이벤트로 밀어 준다」는 우리 구조에 딱 맞는 정석을 적은 1차 문서는 못 찾았다.** 가장 가까운 것은 요청-캐시 방식을 확인 대기 기본으로 쓰고, 데몬 이벤트가 캐시를 갱신하게 잇는 것이다(수집자 추론).
- **우리 지금 모양:** 서버 상태가 Zustand 스토어에 있고 Tauri 이벤트가 채운다(`src/store/viewStore.ts` 등). 요청-캐시 라이브러리를 들이면 쓰기 쪽(처리 중 · 직렬화)을 공용으로 얻지만, 새 의존성과 스토어 이주가 따른다 — 후속 주제에서 선택지로 올린다.

## 논의 정리 — 후속 주제의 출발점 (사용자와 메인 · 2026-09-30)

- **한마디로 = 조작을 그룹으로 나누고 그룹마다 처리 하나를 정한다.** 새 조작은 어느 그룹인지만 고른다(조작별 개별 논의를 하지 않는다).

  | 그룹 | 예 | 처리(출발안) |
  |---|---|---|
  | 화면 자체 | 팝업 열기 · 스크롤 · 입력 중 글자 | 즉시 |
  | 두 번이면 사고 | 생성 · 삭제 · 종료 | 삭제·닫기·종료는 셸이 이미 막는다(대상 없음 → `Err`) · **생성은 못 막는다**(탭 `+` 두 번 = 탭 둘) → 요청별 멱등 키를 셸이 한 번만 처리(Stripe 형)하면 서버 쪽으로 통일, 화면 가드 불필요 |
  | 두 번이면 두 번 | 뒤집기 · 이동 · 다음 탭 | 의도를 보내고 서버(셸·데몬)가 순서대로 계산(zellij·herdr 형) |
  | 멀리 있고 느림 | 원격 데몬 조작 | 위 둘 중 하나 + 실측해서 굼뜨면 그 조작만 낙관적 갱신 · 「처리 중」을 보이게 |

- **구조 인식:** 우리는 **데몬 → 셸 → 화면** 3단이고 셸도 화면에겐 서버다. 3단 자체는 흔하다(orca = 터미널 데몬 → Electron 본체 → 화면). ★**드문 점 = 가운데 층(셸)이 레이아웃까지 쥔다**★ — orca 는 레이아웃을 화면 스토어가 쥐어 즉시 바뀐다. 우리는 LLM 과 사람이 같은 핸들을 쓰게(「LLM-우선 제어」) · 창 여럿이 한 상태를 보게(ADR-0035·0057) 셸에 뒀고, 그 대가로 탭 생성도 왕복이다. 「셸이 레이아웃을 쥐는 곳이 우리뿐」은 조사 범위에서 못 봤다는 뜻이지 확인이 아니다.
- **낙관적 갱신(화면 먼저 → 서버 오면 맞춤)은 나쁜 방식이 아니라 느린 곳에만 골라 쓰는 도구다** — 대가 = 서버 계산의 화면 복제 · 늦은 반영의 되돌림 · 롤백. 레이아웃(같은 PC)엔 이득이 거의 없다(ADR-0035 도 막는다).
