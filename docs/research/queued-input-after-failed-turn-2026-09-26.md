# 턴이 진짜 오류로 실패한 뒤 대기 입력을 어떻게 다루나 — 관행 light 조사 (2026-09-26)

- **상태:** light (적대 리뷰 없음 — tier 규정) · 수집 = 경량 워커 1명(웹 검색 + 로컬 클론 grep) · grounding = 메인이 핵심 클레임을 원문으로 스팟체크
- **질문:** 요청 한도 · 과부하 · 맥락 초과로 턴이 실패했을 때 ① 기다리던 사용자 글 ② 다른 에이전트가 보낸 메시지(우편)를 도구가 자동으로 다시 넣나, 사용자를 기다리며 멈추나 · 둘이 함께 기다리면 어느 쪽이 먼저인가
- **소비처:** 턴 도중 입력 TRD §10-4 N11(빚진 후속 턴의 실패) · 오류 턴 뒤 우편 처리(PRD §3-9 · §3-10)
- **확신도 범례:** 확실 = 독립 교차확증 · 가능성 높음 = 출처 하나가 지지 · 불확실 · 모름

## 결론

1. **층이 둘로 갈린다 — 전송 층의 자동 재시도 → 그래도 실패하면 턴 실패로 드러난다.** 턴 실패로 드러난 뒤 그 턴을 저절로 다시 돌리는 도구는 찾지 못했다. Claude Code 는 그것을 요청한 이슈 둘을 `not_planned` 로 닫았다. — 가능성 높음
2. **턴 실패 뒤 대기 입력을 자동으로 흘려보내는 것은 사용자가 결함으로 신고한 동작이다.** codex 는 사용 한도 실패를 평범한 끝난 턴처럼 다뤄 줄 선 후속 글을 하나씩 자동 제출하고, 전부 같은 이유로 실패한다. 신고자는 「크레딧이 돌아올 때까지 멈춤」을 요구한다 — 줄은 지키고, 멈춤을 보여 주고, 사용자가 재개 · 편집 · 순서 변경 · 삭제한다. — 가능성 높음(이슈 한 건 · 신고자의 소스 판독 · 공식 문서 아님)
3. **에이전트 간 메시지는 턴 경계에서만 들어간다**(Claude Code Agent Teams). 턴 실패 뒤 그것을 어떻게 하는지는 못 찾았다. — 경계 전달 = 가능성 높음 · 실패 뒤 = 모름
4. **사용자 글과 에이전트 간 메시지 사이의 순서 규칙을 문서로 정한 도구는 못 찾았다.** — 모름

## 공백

- 턴 실패 뒤 대기 사용자 글의 처분을 **공식 문서로** 적은 도구는 없다 — codex 근거는 이슈뿐이다.
- 사용자 글 ↔ 에이전트 간 메시지 순서 규칙: 모든 도구에서 못 찾음.
- 턴 실패 뒤 에이전트 간 메시지 처분: 못 찾음.
- 안 본 것: Aider · Cline · AutoGen · LangGraph · OpenHands · CrewAI · t3code · orca 의 오류 경로(예산).

## 이 조사가 받치는 것 (해석 — 사실과 구분)

- 사용자가 세운 원칙 「진짜 오류면 사용자 글이든 우편이든 자동으로 넣지 않고 사용자 입력이 깨운다」는 결론 2 가 보여 주는 사용자 요구와 같은 방향이다. 반대로 오늘 PRD §3-9 의 「오류 턴 뒤 목록이 비면 우편은 곧바로 든다」는 codex #24443 이 결함으로 부른 모양(실패 뒤 대기 입력을 자동으로 흘려보냄)을 우편에 대해 하는 셈이다.
- 결론 1 에 따라, 우리 층이 `turn/completed(failed)` 를 볼 때는 벤더의 전송 층 재시도가 이미 끝난 뒤일 가능성이 높다 — 우리 쪽 재시도는 같은 오류를 한 번 더 부르는 것이 된다(codex 쪽 재시도 횟수는 메인 미확인).
