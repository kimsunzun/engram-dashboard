# Investigation — tab dragging across a process boundary: who owns the drag state, geometry, and decision + frontend base candidates

- **Status:** 4 collection tracks · main grounding · cross-family adversarial review pending · awaiting decision (user).
- **Date:** 2026-10-19
- **Trigger:** In measuring the slot docking Chrome-style drag implementation (up to TRD 6.3 U8), defects kept recurring at the shell ↔ webview boundary — ① on re-attach, the model write was drawn before the web notification, giving one frame at position 0 ② the web reported a stale, zero-width tab bar geometry and the shell misjudged (B1) ③ it attached and detached after only 11 ms. User: 「자꾸 버그가 튀어나오는 원인이 뭐야」 (what is the cause of bugs popping up all the time) · 「우리랑 비슷한 다른 곳은 어떻게 했는지」 (how did other places similar to ours do it) · 「베이스 삼아야 될 것도 하나 선정 — 프론트 단 · 성숙한 것 · rust 와 리엑트 분리되는 구조」 (also pick one thing to use as a base — frontend layer · mature · a structure where rust and react are separate).
- **Method:** 4 collectors (direct peers · techniques that prevent out-of-order · ways to test boundary defects · frontend base candidates) → main grounding (checked lines against saved copies of the originals and clones — 「grounding」 below) → cross-family adversarial review (codex).
- **Confidence legend:** certain = primary source + independent cross-confirmation · likely = one primary source (supported by grounding) · uncertain = unchecked · inference.
- **Companion documents:** [slot-docking-chrome-desktop-drag-2026-10-18.md](slot-docking-chrome-desktop-drag-2026-10-18.md) (Chrome Views mechanism — not repeated here) · [../refactoring/slot-docking-drag-code-audit-2026-10-18.md](../refactoring/slot-docking-drag-code-audit-2026-10-18.md).

## Conclusion

### A. Peers — none modifies the model across a process boundary during a drag

| # | Finding | Source | Confidence |
|---|---|---|---|
| A1 | **A peer whose renderer and model owner are split freezes the model for the whole drag and writes it only once on drop.** The Chromium WebUI tab bar (a web page in a renderer process ↔ the browser process `TabStripModel`) moves only its own DOM during the drag and calls `tabsProxy_.moveTab(id, dstIndex)` once in `finish()` · cancel puts the DOM back in its original place. The model-side echo (`onTabMoved_`) only puts the element back in that position, so if it is already there nothing happens | `chrome/browser/resources/tab_strip/drag_manager.ts` (tag 120.0.6099.1) #224-240 · `tab_list.ts` #575-578 | likely |
| A2 | Even in the same process, mature implementations follow the same rule — Firefox moves only the visual with `translateX` during the drag, and the model move (`moveTabTo` · `moveTabsBefore/After` · `adoptTab` between windows) is only inside `handle_drop` · Windows Terminal has the target compute the position at drop and makes one `RequestReceiveContent(src, dst, index)` call | Firefox `browser/components/tabbrowser/content/drag-and-drop.js` #105-273 (model calls 0) · #274-555 · Windows Terminal `TerminalPage.cpp` #6050-6062 | likely |
| A3 | **Only the drawing side holds the tab bar geometry — no peer sends the geometry to the owner.** The renderer decides the position on a live DOM or XAML (`getBoundingClientRect` · `e.GetPosition(item)` + `ActualWidth`), and the owner receives only 「탭 X → 자리 N」 (tab X → position N) or 「창 밖 화면 점 P 에 놓음」 (dropped outside at screen point P). The shape like ours, where the web measures, debounces, and reports, and the owner decides with that, was not in the 7 peers | the sources above | likely (evidence of absence — a sample of 7) |
| A4 | **For attaching between windows, every peer leaves it to an OS drag and drop session** — the target window's renderer receives dragover and drop itself and computes the position (WebUI makes a placeholder tab `PLACEHOLDER_TAB_ID = -1` in the target tab bar and drags it). Cursor following is the OS drag image (`setDragImage` · Vivaldi cuts the tab area as a bitmap and passes it to `tabsPrivate.startDrag`). The price = no 「커서를 따라오는 진짜 창」 (a real window that follows the cursor) · no preview before the drop · no snapping during the drag — Windows Terminal lists exactly this as unresolved (#16129 · #14900) | `drag_manager.ts` #15 · #120 · #302 · Vivaldi `tabs_private_api.cc` #902-949 · `tabs_private.json` #1101-1121 (`targetWindowId` of `onDragEnd`) · microsoft/terminal#16129 | likely |
| A5 | **「커서를 따라오는 진짜 창 + 놓기 전 붙기」 (A real window that follows the cursor + attaching before the drop) (Chrome Views shape) exists only in one-process native implementations** — Chrome Views · the WinUI 3 TabView tear-off API (same process). Zero places were found that do this in an app with a native owner + a web renderer (VS Code is a `window.open` auxiliary window inside one renderer · Wave reorders only inside the window · Warp is request #9030). dockview's Tauri experiment measures our boundary exactly and writes that 「메인 창과 스크립트 못 하는 창(별 JS 맥락) 사이 끌기는 없고 앞으로도 없다」 (there is no dragging between the main window and a window that cannot be scripted (a separate JS context), and there will not be) (back-translated) — **but that is a statement about the path where the library hands the drag over inside the JS heap.** The path where the shell (native) holds the drag, like ours, is outside that document's scope | dockview `packages/dockview-tauri-demo/docs/unscriptable-windows.md` #155-170 (@`1eb9c69` 2026-10-17) · base-track collection | likely (0 places = not found ≠ does not exist · the WinUI 3 API is from memory = uncertain) |
| A6 | Vivaldi has a structure closest to ours: the **whole window UI is a React app and the window and tab model is Chromium C++**. The browser side knows the drag only as a single 「탭 끌기 중」 (tab drag in progress) flag and returns the end to JS as `onDragEnd(canceled, x, y, targetWindowId)` · it appears that JS decides new window / move and requests it once (the JS bundle is closed, minified code, so it could not be read directly) | `tabs_private_api.cc` #946-949 · `tabs_private.json` #1101-1125 | C++ side = likely · JS side = uncertain |
| A7 | It separately guards against the case where the drag end event does not arrive — Firefox, even if the drag session insists it still exists, takes a primary-button press as evidence that 「끌기는 끝났다」 (the drag has ended) and recovers, and **at that time it deliberately skips the path of tearing off with stale coordinates** | `drag-and-drop.js` #905-930 | likely |

### B. Techniques used when keeping the boundary and putting the owner on one side

| # | Technique | What it prevents | Source | Relation to our defects | Confidence |
|---|---|---|---|---|---|
| B1 | **Wayland `configure(serial)` → `ack_configure(serial)` → commit** — the owner sends state with a number, and the drawing side returns the number after drawing that numbered state completely · if several are queued, replying only to the last is enough, and a reply with a stale number is an error | The owner judging from the drawing or geometry of a different state | `wayland-protocols` `stable/xdg-shell/xdg-shell.xml` #572-615 | all of ① · ② · ③ — the shell decision uses only geometry measured after drawing at 「지금 모델 번호」 (the current model number) | likely (grounding = checked against the source wording) |
| B2 | Chromium surface synchronization (`LocalSurfaceId`) — keeps showing the old frame until a frame with the matching number arrives | resize flicker · mismatched frames | implementer notes hackmd.io/@elkurin/HJ1yK-6jh · chromium.org surfaces design document | ① — do not draw until the model + drag state of the same number have all arrived | uncertain (original design document not found · implementer notes) |
| B3 | Chromium Viz — sends the hit-test geometry **together with the frame that made that geometry** · if it cannot be trusted, falls back to 「물어보기」 (ask) (`kHitTestAsk`) | deciding with geometry that differs from the screen | `components/viz/common/hit_test/hit_test_query.cc` · `hit_test_data_provider.h` | ② — zero-width · stale geometry as 「모름」 (unknown) | uncertain (header · search summary) |
| B4 | Counterexample — Electron drag regions: the main process decides from rectangles the renderer sent → if messages queue up, stale rectangles (macOS live resize) · Electron responds with a diagnostic flag, not a protocol | — | releases.electronjs.org/pr/53598 | a known defect of the same kind as ② | uncertain (release notes) |
| B5 | Figma — discards server updates for a property that has its own change not yet acknowledged · Replicache — after an optimistic apply, rolls back to the server state and reapplies, revealing it **all at once** · game client prediction — numbers the input and records which input number a decision rested on | bounce-back during interaction · stale replies | figma.com/blog/how-figmas-multiplayer-technology-works · doc.replicache.dev/concepts/how-it-works · gabrielgambetta.com/client-side-prediction-server-reconciliation.html | ③ diagnosis (which input number is the decision for) · ignoring model echoes during the drag | likely (implementer writing) |

- **Main's judgment (not a source):** A and B are two faces of the same conclusion. Peers erased the ordering problem by removing 「끌기 도중 경계 너머 모델 쓰기」 (writing the model across the boundary during a drag) entirely (A1 · A2), and systems that cannot remove it (window managers) bound it with numbers and acknowledgments (B1 · B2).

### C. How to catch boundary defects with tests

| # | Method | What it catches | Source | Cost | Confidence |
|---|---|---|---|---|---|

| C3 | Record the IPC messages of an actual session (both sides · numbers · times) → replay them into a fake transport as a regression test · assert a per-frame invariant in debug builds (「그린 자리 == 모델 자리」 (drawn position == model position)) | recurrence of a defect a person saw first | no precedent (design idea) | low–medium (estimate) | uncertain |

- **Base track conclusion:** taking one as is, there is no React library that keeps the Rust-owns-the-model principle (ADR-0035) and the separate-webview-per-window structure (ADR-0057) and also does dragging between windows. For a library to do dragging between windows, the live model has to be in one JS context (the VS Code shape — directly against our principle). So the 「베이스」 (base) splits in two — **the renderer inside one window** (FlexLayout fits best · the value of swapping it for our current direct implementation has to be measured separately) and **a model for the boundary design** (the Chromium WebUI tab bar — a mature real example of the same split structure).

### E. The Windows look of an OS drag — what the dotted square next to the cursor is (additional collection 2026-10-20 · main grounding = E1 · E2)

| # | Finding | Source | Confidence |
|---|---|---|---|
| E1 | **The dotted square next to the cursor = the OLE default 「이동」 (move) cursor** (arrow + dotted box). OLE draws it when the drag source's `IDropSource::GiveFeedback` returns `DRAGDROP_S_USEDEFAULTCURSORS` · copy = box + 「+」 · none = a prohibition circle. Attaching a drag image does not remove it because the cursor is separate | MS Learn `IDropSource::GiveFeedback` · the collector drew cursor resources 1–7 of this PC's `ole32.dll` to confirm | likely |
| E2 | **Chromium (= WebView2 · Electron/VS Code) always uses the default cursor** — `GiveFeedback` unconditionally returns `DRAGDROP_S_USEDEFAULTCURSORS`. | E3 | The drag image is drawn by the Windows shell helper (`IDragSourceHelper::InitializeFromBitmap`) — translucency and feathered edges are the shell look, and Firefox uses the same helper. `setDragImage(요소)` (element) is opaque 1.0 · up to 8192 px per side · **the 10-16 investigation's 「알파 0.75 · `<img>` 200×200」 (alpha 0.75 · img 200×200) is for the default image and selection drags, so it is wrong for `setDragImage`** | `os_exchange_data_provider_win.cc` #968-997 · Blink `data_transfer.cc` #123-128 · #160-161 · `drag_controller.cc` #110-117 | likely |
| E4 | Peer looks — Firefox = a 160×90 page thumbnail (opaque) · arrow cursor · the image is kept even inside the tab bar · VS Code = the tab element as it is (`setDragImage(tab, 0, 0)`) · default OLE cursor (dotted box — not measured on screen) · Windows Terminal = XAML default (not observed) | `drag-and-drop.js` #1254-1332 · vscode `multiEditorTabsControl.ts` #1309-1324 · terminal `TerminalPage.cpp` #5942-6000 | likely |

| E6 | Esc and 「창 밖 놓기」 (drop outside the window) are the same signal in HTML (`dragend` · `dropEffect "none"`) — Firefox separates them with the private `mozUserCancelled` · on a drop outside the window the Windows shell draws a failure (bounce-back) animation — Firefox has the private `mozShowFailAnimation`, and for VS Code there is a statement that a Chromium patch blocked it (unchecked) | `drag-and-drop.js` #672-690 · `drag_source_win.cc` #17-20 · github.com/zcbenz/dnd-drag-hint | likely (VS Code patch = uncertain) |

## Design implications (material for options — not a decision)

| | Approach | Our defects ①②③ | Cost and risk |
|---|---|---|---|
| **F (peer consensus)** | **Freeze the model during the drag.** The shell holds one 「끌기 덧층」 (drag overlay layer) (the dragged tab · the window it is in now · the position) with a number, and every window draws one snapshot of 「모델 + 덧층」 (model + overlay layer) · the model write is once at drop · cancel = discard the overlay layer. The position decision inside the tab bar is by that window's webview from its own DOM (A3 — geometry is not sent to the shell). Only the decision between windows (which window's tab bar is it over) needs geometry in the shell → that trusts only a report carrying the B1 number | ① disappears (no model write during the drag) · ② the scope narrows to the one between-window decision and is blocked by the number · ③ diagnosed and blocked by the overlay layer number | Showing the tab content in the detached window is also done through the overlay layer (in the model it is still in the original window) — the terminal output subscription has to follow the overlay layer (unchecked) · the LLM bus and saving during the drag see the pre-drag state (atomicity improves) · Chrome Views modifies the model during the drag — this differs from that (relation to the user decision 「크롬 소스 그대로」 (exactly Chrome's source) = needs a judgment) |
| **G (one-side owner + numbers)** | Keep the model write during the drag as it is now, put a number on every shell → web push · the web replies with the geometry after drawing that number completely (B1) · the shell decides only from the geometry of the current number · the web keeps the old frame until the model + drag state of the same number have all arrived (B2) | ① · ② · ③ blocked | No peer precedent (only window manager precedent) · numbering plumbing in every path · the web needs a deadline policy for 「그리지 않고 기다리는」 (waiting without drawing) |
| H (patch per defect) | Current structure + only the three confirmed defects | ① · ③ in part | Small · the same class comes back |
| ~~Go back to OS drag and drop~~ | The method most peers use | removes at the root | Loses real window following · attaching before the drop — the user decided on the Chrome Views way on 2026-10-18 · reversal |
| ~~One webview + `window.open`~~ | VS Code shape · dockview/FlexLayout do the dragging between windows | removes at the root | The model owner moves to JS → violates ADR-0035 · the LLM-first control principle · tears up the separate-webview-per-window structure |

- **Together with either:** C1 (shuffling the order of shell ↔ web events with the fast-check scheduler) + C3 (recording the messages of a measured session → replay regression) — a net that catches before a person does.
