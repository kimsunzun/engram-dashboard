# ADR-0015: Daemon lifetime = persist-until-kill, console = detachable viewer

- 상태: 확정 (2026-06-15, basis: prior-art survey of tmux/Zellij/Emacs/mosh/dtach + the previous session's churn incident)
- 관련: CLAUDE.md §5(LLM-first control)·"데몬/전송 앵커" · ADR-0013(the three daemon references) · ADR-0008(restore, supplemented) · `src-tauri/src/discovery.rs` · `crates/engram-dashboard-daemon/`

## 맥락
In the previous session the daemon console (an empty window) was tied to the daemon's lifeline, so closing the console window caused a **churn loop**: the daemon dies → the app re-discovers → re-spawns → restores sessions, over and over. We must state clearly "when does the daemon live and when does it die" and "what is the relationship between the console window and the daemon".

Conclusion of the prior-art survey: tmux, Zellij, the Emacs daemon, mosh and dtach **all separate "the process that holds the PTY" from "the viewer/console that looks at it"**, and daemonize from the launching terminal so they are not tied to the window's lifetime. The structure we hit, "the console window owns the daemon's lifetime", exists in none of these tools — that is the identity of the bug.

## 결정
1. **Daemon lifetime = persist-until-kill.** Staying alive in the background even with zero agents is our premise. The daemon **dies only on an explicit `shutdown` command (by a human or an LLM call).** We **do not provide** a tmux-style "auto-exit when zero agents and zero clients" option (unneeded complexity — simplified to a single policy).
2. **The daemon is spawned windowless.** When creating it through Windows WMI `Win32_Process.Create`, use `CREATE_NO_WINDOW`/`DETACHED_PROCESS` so no console window is allocated at all → a "window that kills the daemon when closed" does not exist.
3. **The console = a detachable viewer client.** The console is not the daemon's lifeline; it is a **view that optionally attaches to and detaches from a live daemon** (tmux attach/detach, Emacs `emacsclient -c`). Closing the console leaves the daemon alive, and reopening it re-attaches. While open, its use is a **UI-less debug/command console window** — showing debug messages + sending commands directly to the daemon (REPL-like). The console (and every viewer) **cannot spawn or kill the daemon** (read and command only; lifetime control goes only through the separate `shutdown` handle).
4. **ensure-on-open.** The app secures the daemon when it opens — attach if it is alive, start then attach if not (the Emacs `emacsclient --alternate-editor=""` pattern). Closing the app only drops the WS connection and the daemon survives.

## 거부한 대안
- **tmux `exit-empty`-style auto-exit (zero agents + zero clients → auto exit, grace window)** — it has the benefit of reclaiming resources, but it conflicts with our premise of "always alive in the background", and only adds test surface such as a grace timer and the agents×clients quadrants. Not even offered as an option, by explicit user decision.
- **mosh-style timeout alone (exit N seconds after the connection drops)** — with local IPC there is no benefit of recovering from an unstable network, and it reintroduces the churn of "daemon disappears after idle → re-spawn → re-restore". Only the grace-debounce idea may be borrowed (if needed in the future).
- **The console as the daemon's parent/owner window (current)** — the cause of the previous churn. Discarded.
- **Granting the console/viewer permission to spawn and kill the daemon** — violates the hands/brain separation (§5). Lifetime control is gathered in one explicit handle.

## 근거
- Prior art: ensure-daemon-on-open ⇐ Emacs `emacsclient --alternate-editor=""`; persist-on-detach ⇐ Zellij `ActiveDetached`/the Emacs daemon; "the viewer is just a socket client, separate from the process that holds the PTY" ⇐ dtach/abduco.
- §5 LLM-first control: daemon lifetime must be an **explicit `shutdown` command handle**, not an implicit behavior of the console window, so that a human click and an LLM call go through the same entry point.
- The previous session's churn is evidence that the "console = lifeline" design failed.

## 영향 / 불변식
- **The console/viewer cannot spawn or kill the daemon** — daemon lifetime control only through the explicit `shutdown` handle (human/LLM). Violating this brings the churn back.
- **Daemon spawn is windowless** — do not create a path that ties it to a console window.
- **No auto-exit policy** — if the proposal "shut the daemon down when idle" comes up again, record it under a new number by discarding this ADR (Superseded); do not overwrite it.
- For the restore policy see ADR-0008 (daemon cold boot, once).
