# ADR-0081: LLM UI control relay: the app = a WS peer that receives daemon commands + an opaque relay envelope + application through the Tauri invoke-shim (reusing the human path)

- 상태: 확정 (2026-07-14, basis: measured terrain + two user fork decisions + `/review prd` passed) · 부분 폐기 by ADR-0155 (decisions 1 and 2 replaced) · 부분 폐기 by ADR-0154 (the premise that target addressing is not needed) · 부분 폐기 by ADR-0308 (the no-argument-parsing part of the daemon-stays-opaque clause (allowing conversion of agent-reference arguments))
- 관련: PRD and TRD `docs/process/S17-llm-control-surface/spec/` · ADR-0080 (control surface architecture, parent) · ADR-0014 (CLI-via-Bash) · ADR-0035 (ViewManager = UI authority) · CLAUDE.md §5(LLM-우선 제어) · implementation anchors (planned): `crates/engram-dashboard-protocol/src/messages.rs`, `crates/engram-dashboard-daemon/src/connection_core.rs`, `src-tauri/src/daemon_client/connection.rs` · step-log S17 · Amended by ADR-0155 (decisions 1 and 2 replaced) · Amended by ADR-0154 (the premise that target addressing is not needed) · Amended by ADR-0308 (the no-argument-parsing part of the daemon-stays-opaque clause (allowing conversion of agent-reference arguments))

## 맥락
In release, the LLM (child claude) must control the UI (layout, tabs, slots) (§5, PRD S17, R3). ADR-0080 set the direction as "engram-ctl → daemon WS, with the UI delivered to the app by the **daemon opaque-relay**". But measurement (2026-07-14, a sub-agent terrain survey) shows the daemon has **no cross-client routing** — every WS connection is a symmetric peer and there is only broadcast (status/list), and there is no path for "daemon → deliver to a specific connection" or "the app receives an inbound command → applies it to the ViewManager". The request_id correlation already exists (for every side-effect `AgentCommand`), but the UI relay itself is net-new. This ADR fixes the concrete protocol of that relay + the app application path.

## 결정
1. **App role registration** — right after auth, the app (the client src-tauri) sends `RegisterRole{UiApp}` to register itself as the "UI authority connection". The daemon marks that ConnId as the UI-app connection (premise of a single app instance = PRD scope → target addressing is not needed).
2. **Opaque relay envelope (single request_id)** — `CLI→데몬 RelayUi{request_id, payload(opaque JSON value)}` (CLI to daemon) → `데몬→앱 UiCommand{request_id, payload}` (daemon to app) → `앱→데몬 UiResult{request_id, result}` (app to daemon) → `데몬→CLI` (daemon to CLI) the result with the same request_id. ★The CLI's `request_id` is passed through **end-to-end as is**★ (no separate `relay_id` namespace). The daemon **does not parse the payload** and keeps only a `request_id→원 ConnId` routing table (request_id → origin ConnId) (opaque bridging — ADR-0080 preserved). (Variant field names are examples — to be fixed in the TRD/implementation.)
3. **App application = a shared `ViewCommand` application service + async correlation** — the app applies the UI command received through the relay to the ViewManager through a **transport-neutral `ViewCommand` application service shared by the human Tauri path and the relay** (a single path, §5 maintained). ★The relay applies **outside** the `daemon_client` actor and correlates by `request_id`★ (the actor keeps serving the socket). (User fork decision 2026-07-14.) ★**Amended 2026-07-14 (/review trd)**: a pure invoke-shim re-entry **self-deadlocks** on a compound command (`spawn_into` — inside itself it does `client.send_command().await`, and the reply is resolved only in the same actor's stream loop) → refined to a shared application service + async correlation.★
4. **Reuse the request_id correlation** — built on top of the existing correlation (`PendingMap`→oneshot). The relay bridges **the same request_id** across the round trip (CLI→daemon→app→daemon→CLI) (no relay_id).

## 거부한 대안
- **broadcast + an app filter** — the daemon broadcasts the UI command to all connections and the app filters only its own. It is noisy (every other connection and window sees it) and, being a filter rather than addressing a target, the command leaks to multiple windows and non-app connections.
- **An app-owned separate endpoint** — the app opens its own WS/IPC endpoint and the CLI connects directly. A second endpoint, with discovery and auth duplicated + the app cannot be connected to directly on mobile (remote daemon) → already rejected in ADR-0080, reconfirmed here.
- **Calling the ViewManager directly** (the daemon_client task skips the shared application path and calls the ViewManager directly) — fast, but the human path and the LLM path diverge, so **two code paths must be kept in sync** and there is a lock-ordering risk. It violates §5 "a human click uses the same handle too" (single control surface). Rejected in the fork by adopting (A), the shared application path. (The opposite extreme, "re-invoking the Tauri command entry as is on top of the actor", was also rejected for the compound command self-deadlock — see the amendment of decision #3. The adopted option is in between: a **shared `ViewCommand` application service** + the relay's async correlation outside the actor.)
- **A CDP/webview handle** (the current temporary path `cdp.mjs eval`, `window.__*`) — in the release exe the remote debugging port and the webview handle are dead (the collapse point in the PRD background). It was this project's original motivation, so it cannot be reintroduced.

## 근거
- **Measured (2026-07-14):** the request_id correlation, backend commands, and portfile+WS already exist (reused) / the cross-client routing, the app inbound handler, and the relay envelope are net-new (`messages.rs`, `connection_core.rs`, `ws.rs`, `daemon_client/connection.rs`).
- **§5 consistency:** the shared `ViewCommand` application service takes exactly the same ViewManager application path as a human UI click, making "a human click = the same handle as LLM control" a structure (a single control surface, one place to maintain). The relay merely calls that service from outside the actor, so it shares the same path without re-entry.
- **ADR-0080 preserved:** since the daemon does not read the payload, the opaque-relay invariant holds. With R7 (child scope) deferred there is no fine-grained authorization → the opaque is clean.
- **PRD passed:** `/review prd` full passed three rounds (2026-07-14) — this relay is built on top of the fixed requirements, scope, and contract.

## 영향 / 불변식
- **The app = a WS peer that receives daemon commands (a new capability).** Until now the app only consumed events + sent outbound commands — now the `daemon_client` connection gets an **inbound UI-command handler**. This inbound path must go to the ViewManager through the **`ViewCommand` application service shared with the human path** — calling the ViewManager directly is forbidden (§5, preventing two paths).
- **★Relay application is outside the actor (non-blocking).★** The relay inbound handler runs the application **outside the `daemon_client` actor task (in a spawned task)** and correlates by `request_id→oneshot` — if a compound Tauri command is awaited inline in the actor, the `client.send_command().await` that the command itself calls is resolved only in the same actor, causing a **self-deadlock** (the amendment of decision #3). The daemon `RelayUi` dispatch also returns immediately without awaiting the app round trip (preventing head-of-line blocking of per-connection sequential dispatch — TRD §3).
- **The daemon stays opaque (ADR-0080):** the daemon does not parse the UI payload (an opaque JSON value). The relay table is only `request_id→원 ConnId` (request_id → origin ConnId). Putting UI semantics into the daemon violates ADR-0080 and 0035. The UI command enum + the payload→`ViewCommand` dispatch map are only in `src-tauri` — `engram-ctl`, the daemon relay, and `core` must not import the UI enum (core is tauri-free, ADR-0003).
- **★The relay routing table lifetime bound + a connection cleanup sweep.★** A table entry = `{request_id→원 ConnId, deadline}` (request_id → origin ConnId, deadline). Eviction = (1) receiving `UiResult` (2) connection cleanup of either endpoint (sweep the entries keyed by that ConnId — both the origin CLI and the app) (3) timeout. The dedup store is also **bounded** (TTL/LRU — not unbounded over the daemon lifetime). A `UiResult` with an unknown/duplicate request_id → drop.
- **★Dedup is committed only on UiResult (after application).★** The dedup entry of a relay UI command is committed **only after a successful `UiResult`** (no pre-caching — a false-success cache on timeout = violates the PRD "UI success is confirmed after the ViewManager applies it"). In-flight duplicates coalesce into the same pending.
- **★RegisterRole resent on reconnect + last-wins.★** The app resends `RegisterRole{UiApp}` not only on the first auth but on **every reconnect** (carried in the reconnect handshake) — otherwise after a reconnect the daemon has no UI-app target and the UI relay wrongly fails with `APP_OFFLINE`. A duplicate UiApp registration = **last-registration-wins** (the new ConnId replaces the stale one).
- **request_id preserved across the round trip:** the **same request_id** is kept across the whole CLI→daemon→app→daemon→CLI span. If the app role is not registered, `RelayUi` fails with an honest error (no target = `APP_OFFLINE`, not-applied confirmed).
- **Single app instance premise:** with multiple apps the target is ambiguous (outside PRD scope, follow-up). The policy when there is more than one role registration is undecided in the TRD.
- When implementing, the code anchor `// ADR-0081` = the relay envelope dispatch (`connection_core`), the app inbound handler (`daemon_client`), the shared `ViewCommand` application service (`src-tauri`), and `RegisterRole`.
