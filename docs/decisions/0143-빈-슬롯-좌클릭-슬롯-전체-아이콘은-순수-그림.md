# ADR-0143: Left-click on an empty slot = the whole slot (the icon is a pure picture)

- 상태: 확정 (2026-08-17, grounds: user decision) · 부분 폐기 by ADR-0144 (empty slot left-click menu opening)
- 관련: Amends ADR-0141 (click target and icon interactivity) · ADR-0065(empty slot menu composition) · `src/components/layout/ViewLayoutRenderer.tsx` · Amended by ADR-0144 (empty slot left-click menu opening)

## 맥락

ADR-0141 put a `+` icon in the empty slot and attached a click handler to **the icon only**. After seeing the implementation the user said that is not it (2026-08-17): for an empty slot, **a left-click anywhere on the slot** should bring up the menu, as a right-click does.

The problem with making only the icon pressable is the target size. An empty slot takes a large area of the screen, yet the only place that actually responded was the 32px square in the middle — pressing anywhere else only moved focus.

Incidentally, making the icon a native button brought along three problems. A path into the tab order that reaches a menu that cannot be operated by keyboard (ADR-0141 decision 6 covered it by excluding it from the order) · handling of clicks without coordinates · an accessible name dedicated to the button. All three **arose because it was a button**.

## 결정

1. **Left-click on an empty slot = the whole slot is the target.** A left-click on the slot container opens the same menu as right-click at the same coordinates. The result is the same whether the click lands on the icon or on blank margin.
2. **`+` is a pure picture.** It is not a button, and it has no click handler, accessible name or tab index of its own. It is removed from the pointer event targets, so the click reaches the slot as is.
3. **Make the icon larger** — bigger than 32px (user instruction 2026-08-17). It is an indicator, not a target, so the size follows readability alone.
4. **The menu is floated off the anchor, not attached to it — farther than the double-click recognition radius.** ADR-0141 only made sure the anchor does not fall *inside* the menu rectangle, but that meant the anchor **sits flush** against the menu corner. This became dangerous once the target widened to the whole slot: when an empty slot is double-clicked, the first click opens the menu and the second click runs an item even if it is off by only 1px — near the bottom of the screen the menu is flipped upward so the bottom-most `닫기` lands under the cursor, and since the layout is not on disk, there is no means to undo it. Whether the direction is flipped or not, **a gap is put between the anchor and the menu**. The gap is derived from the OS double-click movement tolerance (Windows `SM_CXDOUBLECLK`, default 4px) — it is not an arbitrary value.
5. **Three icon-only clauses of ADR-0141 are discarded** — the own click handler ("icon click" in decision 3), the own accessible name (the `slot.openMenu` key), and the tab order exclusion (decision 6). Their grounds are gone: without a button there is nothing to enter the order and nothing to name. **The `slot.openMenu` i18n key is deleted.** ★But the click without coordinates did not disappear★ — that path **moved** from the button to the slot, and the current code trusts the coordinates as they are. That is, if code calls `.click()` on the slot element, the menu opens at the top-left of the viewport. No such call site exists in the repo, so it is left latent, and **it was not judged gone and deleted** (the first draft wrote it wrongly that way — pulled out by review).
6. **Right-click and focus move stay as they are.** A left-click causes focus and the menu together.

## 거부한 대안

- **Keep the handler on the icon too and add one to the container** — the user explicitly asked to remove icon-only handling with "그냥 + 누름처리하지 말고" (gloss: just do not treat the + as a press) (2026-08-17). Moreover, if two handlers overlap, an icon click goes through both and the menu opens twice, or, if propagation is cut to prevent that, focus move breaks — that is the reason it was decided at the time of ADR-0141 not to cut propagation.
- **Keep the icon as a button but sized to cover the whole slot** — the target grows, but the button remains, so the three incidental problems above (tab order · click without coordinates · accessible name) stay. It keeps the complexity with nothing gained.
- **Left-click only focuses, the menu is right-click only (the state before ADR-0141)** — it goes back to the original report (2026-08-17) that the path to fill an empty slot is not visible on screen.

## 근거

- **User decision (2026-08-17)** — the user specified all three: enlarging the click target, making the icon non-interactive, and increasing the size.
- **Grounds that removing the button is pure subtraction** — the code that goes away with this decision is the icon's click handler · `tabIndex` · `aria-label` · the coordinate-less click detection and their tests. What is newly added is only one branch for the container left-click.

## 영향 / 불변식

- **There is still one menu opening path** — `setContextMenu`. Left-click and right-click shake the same state (this invariant of ADR-0141 remains valid).
- **Do not re-attach interaction to `+`.** If a handler · `tabIndex` · `role` is put on the icon again, it overlaps the container handler and causes a double opening, and the keyboard trap path that ADR-0141 covered by excluding it from the order comes back. **The target is the slot, and the icon is an indicator.**
- **The gap between the anchor and the menu is larger than the double-click recognition radius** (decision 4). If this gap shrinks, a double-click on an empty slot runs a menu item — in a slot at the bottom `닫기` gets hit, the slot disappears and there is no means to undo. ADR-0141's "the anchor does not fall inside the menu" is **strengthened** by this clause (merely sitting on the boundary is not enough). The flipping itself remains valid.
- **While the menu is open, clicking inside the menu does not reposition it.** The menu is mounted inside the slot, not in a portal, so a click on a part with no handler of its own (the submenu container row · the divider · the padding) rises up to the container. If not blocked, that click reopens the menu under the cursor and creates the state where the anchor overlaps the menu.
- **By contrast, a click on the slot margin moves the menu to the new position — this is intended.** The menu's own close-on-outside-click runs first on `mousedown` and clears the state, and the following `click` reopens it at the new coordinates. That is, the clause above is not "ignore any left-click while the menu is open" — **what separates the two is whether the click point is inside or outside the menu**. Because this depends on that order (mousedown first), if the outside-click close is moved to `click` or removed, a margin click is silently swallowed and the menu can be neither moved nor closed.
- **The left-click branch applies only to empty slots** — a left-click on a slot with content only moves focus (the terminal and the tree have click meanings of their own).
- **What stays alive from ADR-0141** — removal of the two lines of text and deletion of `common.viewEmpty` (decision 1), the frameless icon (decision 2), keeping right-click (decision 4), and the invariant that the menu flips at the edge instead of pushing.
