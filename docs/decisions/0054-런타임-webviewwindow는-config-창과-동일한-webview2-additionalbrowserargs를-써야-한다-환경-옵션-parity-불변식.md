# ADR-0054: A runtime WebviewWindow must use the same WebView2 additionalBrowserArgs as the config windows (environment-option parity invariant)

## 맥락
Slot popup detach (`pop_out_slot`) creates a new OS window at runtime with `WebviewWindowBuilder::build()`. But on Windows (WebView2), **the runtime-created window was a "ghost"**: `build()` returned `Ok` and the window was registered in the Tauri registry (`getAllWindows()`), but **no actual OS window (HWND) came into existence** (confirmed with Win32 `EnumWindows` — which enumerates hidden windows too: the window count did not grow). The config windows declared in `tauri.conf.json` (`main`, `agent-tree`) were displayed normally, and **only runtime-created windows** were ghosts. A bare `about:blank` window (a spike that ruled out popup, view and routing entirely) was a ghost in the same way, so the cause narrowed down to **runtime window creation itself**, not the popup logic, the URL or the dev server.

## 결정
**Every piece of code that creates a WebView window at runtime must give it an `additionalBrowserArgs` that is character-for-character identical to the config windows'.** Put that value in the SSOT constant `WEBVIEW2_BROWSER_ARGS` (`popout.rs`), and the runtime builder references it with `.additional_browser_args(WEBVIEW2_BROWSER_ARGS)`. Value = `--disable-features=msWebOOUI,msPdfOOUI --autoplay-policy=no-user-gesture-required` (identical to the two items of `additionalBrowserArgs` in the current `tauri.conf.json`). The config JSON is parsed strictly (`deny_unknown_fields`), so a sync comment cannot be placed in it, and we put "must be in sync with tauri.conf.json" in the comment on the constant side.

★(2026-10-08 revision mark — ADR-0283) The location of the constant and the config copy have changed — the constant is a single one in `webview_env.rs` and the config does not carry this value. The present shape is the first item of 「영향 / 불변식」.★

## 거부한 대안
- **Wrap the build in `run_on_main_thread` from an async command (the thread/STA hypothesis)** — the hypothesis "an async command runs on a tokio worker thread, so it cannot meet the WebView2 STA UI-thread requirement and becomes a ghost". **Disproved by measurement**: even when build was executed on the main event-loop thread with `run_on_main_thread` (completion confirmed by waiting on mpsc), the ghost remained. It is not a thread problem.
- **Adopt wry's broader default args (additionally disabling `msSmartScreenProtection`)** — at a glance it looks like a "standard value", but then a **new mismatch** with the config windows arises and the same bug recurs. The invariant is not "the standard value" but "identical to each other within the same user-data folder" → match the config value exactly.
- **Single-source generation (automatic config↔constant sync via build.rs, or a build-time assert)** — the ideal option that blocks drift at the root, but out of the scope of this fix. The risk of silent drift in the JSON→Rust direction is left as a **follow-up hardening** (a build-time assert comparing the constant against the parsed config) (reflects the review finding).

## 근거
- WebView2 (COM/STA) requires that WebViews sharing the same user-data folder create their environment with **identical `CoreWebView2EnvironmentOptions`** (= `additionalBrowserArgs`). If the options diverge because the config windows are given args and the runtime windows are not, creating the runtime WebView2 environment in the same folder **fails silently** (build returns Ok and the window is registered in the tao registry, but no HWND is created = a ghost).
- **Measured (single variable)**: in the original ghost state, adding **only** `.additional_browser_args(config 문자열)` (other conditions restored) took the `EnumWindows` window count from 7 to 10, and the `HELLO`/`slot-popup-1` windows were actually displayed. With the real `pop_out_slot` too, the `Engram — slot-popup-1` OS window (visible, valid HWND) was confirmed.
- Reaching the root cause = ADR-0038 (no solo guessing for a non-trivial defect; OSS/cross-investigation first). After the thread hypothesis was disproved, a cross-family (Codex) cross-check pointed to the config↔runtime args mismatch → grounded against the repo config → proved by spike.

## 영향 / 불변식
- ★**(2026-10-08 revision mark — ADR-0283) The invariant stands as it is and the range it covers has widened**★ — every window of the same data folder (windows declared in config · runtime windows) receives the same four things: data folder · `additionalBrowserArgs` · browser extensions · scrollbar look. Every piece of code that creates a window passes through the finishing function `WebviewEnv::finish` (`src-tauri/src/webview_env.rs`), and the config-declared windows are also not created by Tauri (`"create": false`) but created by the shell going through that function. 「동기 지점(3중 중복)」, 「후속: build-time assert」 and 「묶이는 코드: `popout.rs`」 below are the old shape — the constant is a single one in `webview_env.rs`, and writing it again in the config trips a test (`config_windows_leave_every_environment_option_at_the_default` in `webview_env.rs`).
- **Invariant (parity):** **every** WebView window of the same user-data folder (config or runtime alike) uses an **identical** `additionalBrowserArgs`. Violating it makes a runtime window a ghost (no HWND created). Any new runtime window creation site must pass `WEBVIEW2_BROWSER_ARGS`.
- **Sync point (triple duplication):** `tauri.conf.json` (2 places: main and agent-tree) + `WEBVIEW2_BROWSER_ARGS` (1 place in Rust). If you change one side, change the others too. Currently enforced only by the comment on the constant (one-way) — **follow-up: enforce both directions with a build-time assert** (rejected alternative 3 above).
- **Code tied to it:** `popout.rs` (the constant + the application in `pop_out_slot`). Other runtime windows in the future (e.g. codex or API-backend windows) will also reference this constant.
