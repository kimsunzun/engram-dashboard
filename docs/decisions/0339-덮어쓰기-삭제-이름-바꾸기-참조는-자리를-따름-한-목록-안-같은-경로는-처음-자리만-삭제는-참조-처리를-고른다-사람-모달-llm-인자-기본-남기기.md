# ADR-0339: Overwrite = delete + rename (references follow the place · the same path within one list keeps only the first place) · delete chooses how to handle references (human = modal · LLM = argument, default keep)

## 맥락
The S25 stage 4 P3 code review pointed out same-path duplicates within one agent list (`[b, b]`) after a path rewrite — they are made by the in-engram [덮어쓰기] (overwrite) move (old file → `.trash` · ADR-0335 decision 4) and by relink (ADR-0330). The problem that an agent attached only to the overwritten old file silently receives the new content was discussed together. User question 「우리 데이터를 파일에 못 넣으면서 링크되는 성숙한 시스템 없음?」 → research `docs/research/external-file-reference-tracking-2026-11-01.md`. On the delete side the user also wanted a way to throw away references, so ADR-0335 decision 5 is replaced (rejected alternative F), and the list of operations that fix references (ADR-0335 decision 1) and what the profile edit port accepts (decision 6) are widened.

## 결정
1. **Moving with overwrite = delete the old file (`.trash`) + rename.** References are not chosen but follow the place and point to the new file that came into that place — it is a replacement (user 「대체하는거라서 링크는 무조건 달아야되는거잖아」 — G58). An agent attached only to the overwritten old file also receives the new content. No reference choice is offered for overwrite. Even if it is overwritten with a file of a different kind, references follow the place, and if the kind does not fit, that line shows as 「틀린 종류」 (TRD M78) (main 2026-11-01 — M107 · accepted).
   - **Duplicate cleanup** — after a path rewrite, the same path within one list (`same_path` — ADR-0325) keeps only the first place. It is not a separate concept but the cleanup after delete + rename (user 「중복접기라는 단어의 개념은 아니라는거지. 그냥 삭제잖아」 — G58).
   - Scope (main 2026-11-01 — M102 · M103) = every list touched by **any path rewrite** (overwrite move · move · rename · relink — ADR-0330) — agent attachments · the lists of preset files · the unsaved edit-draft lines of the window that issued the command (after applying the mapping of ADR-0338 decision 8). The reason = if a duplicate remains in a preset list, it breaks 「목록 안 같은 항목 중복 = 어긋남」 (TRD M78 · M85) — the next save is refused.
2. **Delete chooses how to handle references** (replaces ADR-0335 decision 5 「삭제는 참조를 고치지 않는다」 — G59).
   - Human — if there are references, always a confirmation modal [취소] (cancel) [참조도 빼고 이동] (remove references too and move) [휴지통으로 이동](G60) (move to trash).
   - LLM — if there are references and no `--yes`, it is refused with `CONFLICT` as now and the references are returned (PRD R48 as is). Removing references is chosen with one optional argument (`--detach-refs` — the name is a placeholder · the final name is decided in the TRD following `docs/reference/llm-command-conventions.md`) · if not removed, the default = keep (user 「기본값을 남기기 … 그 기본값이란게 LLM한테의 기본값이지? 사람은 무조건 물어봐야되니」 — G60). That `CONFLICT` answer carries, together with the references, the following two forms (`--yes` = keep · `--yes --detach-refs` = remove references too) — so that the LLM does not guess the form (main 2026-11-01 — M99 · the criterion the user delegated 「llm이 명령을 쏠때 햇깔리지 않고 잘 유지하는것 기준」).
   - Argument screening (main 2026-11-01 — M108 · same criterion) — giving only `--detach-refs` without `--yes` is the same as having no `--yes` (`CONFLICT` + the two forms). Giving `--detach-refs` to an operation outside the three below (delete · `SKILL.md` rename · moving out of `SKILL.md`) is refused with `INVALID_ARGUMENT` (it is not silently ignored · whether it is one of those three is decided by the shape of the operation, not by whether there are references).
   - **The operation shape of `detachRefs`** (main 2026-11-01 — M110 · same criterion) — that argument applies, for each item within one operation, only to an item of one of three shapes: deleting an item · renaming the skill folder's `SKILL.md` · a move in which `SKILL.md` leaves its place directly under that skill folder (it also applies when moving into a subfolder of the same skill folder — since `SKILL.md` is no longer directly under that folder · PRD R12). For an item of a matching shape, the references only decide whether there is actually a line to remove (if there are no references no line is removed and it is not a refusal either). Other items of the same multi-path operation are not affected, and `INVALID_ARGUMENT` is only when the operation has no item of such a shape at all.
   - Keep = the current rule as is — the reference stays at its original path as 「찾을 수 없음」 and is released by itself when restored to its original place.
   - Remove references too = remove the lines that point to that item from the preset · agent lists · a delete that removed the references does not re-attach them even when restored.
   - **Paths to remove** (main 2026-11-01 — M105) = all the paths that operation deleted — the item itself, for a folder all descendants in it, and in the `SKILL.md` case (below) that skill folder. It is counted at execution, not a list of only the referenced ones captured at planning (the same reason as ADR-0335 decision 6 — so as not to miss a line attached in between). A preset that went to `.trash` in the same operation is not a target of line removal. Agents attach only presets (`AgentProfile.presets` · `default_preset`), so only the preset file paths among them are passed to the agent removal (`remove_preset_paths`).
   - **Same-window draft** (main 2026-11-01 — M103) — the answer of an operation that removed references carries the removed paths, and the lines of those paths are also removed from the unsaved edit draft of the window that issued the command (other edits in the draft stay as they are · the same share as applying the mapping of ADR-0338 decision 8 — so that a later [저장] does not revive the removed lines).
   - **If interrupted midway** (main 2026-11-01 — M104) — if it is interrupted after the move to `.trash` (or the rename · move below) has finished, the lines not yet removed are the same as keep — they remain as 「찾을 수 없음」, re-attach when put back to the original place, and it can be redone by removing with × or by putting back to the original place and then removing references again (ADR-0335 decision 2's no progress record, as is).
   - Deleting even one `SKILL.md` makes that skill gone — references pointing to that skill folder also follow the same choice (remove references too = remove the lines that point to that folder · user 「skill.md가 없으면 스킬 자체가없어지는거잖아. 그럼 참조를 빼야되는거 아님? 그 참조는 에이전트가 스킬을 인식한다는 기준으로 해야지」 — G62). What a reference holds is the folder path, and whether a skill exists is decided by `SKILL.md` (the skill recognition rule as is — PRD R12).
   - Renaming `SKILL.md` of a referenced skill also makes that skill gone, so it is the same choice (user 「이것도 링크옵션으로 되야하지 않음? 사실 이런경우 자체가 이상하긴한데」 — G63) — human = confirmation modal [취소] [참조도 빼고 바꾸기] (remove references too and rename) [이름 바꾸기] (rename) (if the references are kept, 「찾을 수 없음」) · LLM · CLI = the same `--yes` + optional `--detach-refs` (placeholder) · default keep · two forms in the `CONFLICT` answer. Order = rename first → remove that skill's lines from the preset files. Agents do not attach skills, so they change only through that preset, and `remove_preset_paths` is not called with a skill folder path (there is no matching attachment). Deleting `SKILL.md` above and moving below are the same.
   - Moving `SKILL.md` of a referenced skill out of that skill folder (drag move · cut and paste) also makes that skill gone, so it is the same choice (main 2026-11-01 — M106 · from the principle of G62 · G63 above) — human = confirmation modal [취소] [참조도 빼고 옮기기] (remove references too and move) [옮기기] (move) · LLM · CLI = the `--yes` of `library.move` + optional `--detach-refs` · default keep · two forms in the `CONFLICT` answer. Order = move first → preset files (no agent step — same as above). Renaming · moving the skill folder itself is an ordinary move — the references are fixed (it is not a fourth case).
3. **The way of pointing (the mechanism) stays the path** (ADR-0315) — the overwrite policy is not decided by the mechanism.

## 거부한 대안
- **(C) Rewrite the attachment of the overwritten old file to a path inside `.trash` so that it follows on the in-app restore** — it needs five more rules (simultaneous mapping · name collision on restore · rolling back a partial failure · emptying · launch handling) and no precedent like engram was found (the research wrote that DEVONthink keeps trash item references until emptied, but that is a database structure and the main session has not cross-checked it — research). The user settled overwrite = replacement.
- **(B) Unconditionally detach the attachments of the overwritten one** — it conflicts with the meaning of replacement (user).
- **(D) Point by OS file identity (file ID · object ID) — as a means of fixing the overwrite policy** — a mechanism does not decide the overwrite policy. In a save that writes a temporary file and swaps it in, the file ID can change (the resulting file ID of `ReplaceFile` = the replacement's — Microsoft Learn · checked against the original text) · the same function keeps the object ID of the original file (checked against the original text) · object ID is NTFS only. It stays in tracking T-74 as a candidate for recovery after an outside move.
- **(E) Sidecar file ID (Unity `.meta` · Godot `.uid`) — as a means of fixing the overwrite policy** — no engram-only file is added to the library folder (user 「메타파일은 하지말고」 — G61). Side ground — when moving from outside, the sidecar must be moved together (Godot checked against the original text — move only · research). By this rejection the sidecar also drops out of the candidates of T-74 (recovery after an outside move). The in-file id (a fixed id engram writes inside the file) is also taken out at the same place — no engram data is put into files (main 2026-11-01 — M109 · from the premise of the user's 2026-11-01 question 「우리만의 데이터를 삽입 못하면서」).
- **(F) Always keep, with no choice on delete** (the old ADR-0335 decision 5) — the user also wanted to throw them away (「삭제는 옵션이 있어야되지 않음? 기존 링크를 남기단지 날리던지」 — G59).

## 영향 / 불변식
- 「한 목록 안 같은 경로는 처음 자리만」 is added to P3's path rewrite (profile registry `try_rewrite_preset_paths`) · the path rewrite of preset files (file-operation stage) · relink · the line rewrite of the same-window draft follow the same rule (main 2026-11-01 — M102 · M103).
- The reference-removal argument (placeholder `--detach-refs`) and the modal buttons are added to the delete command · rename command · move command (when it makes `SKILL.md` of a referenced skill no longer a skill — file-operation stage) · the two forms are carried in the `CONFLICT` answer without `--yes` · the answer of an operation that removed references carries the removed paths.
- The places changed in ADR-0335 (the ADR-0335 body is not edited — this ADR carries the amendment scope): decision 5 is replaced · decision 1 (operations with reference fixes = move · rename · relink) gains delete with references removed · `SKILL.md` rename with references removed · moving out (lines are removed through the same reference-fixing path) · decision 6 (only the old → new mapping to the port) gains the removal verb `remove_preset_paths(paths)` · the same three are added to impact 「공통 뼈대(계획 → 실행 → 참조 고침)는 이동 · 이름 바꾸기 · 다시 연결만 쓴다」 · rejected alternative 「파일마다 고정 정체(사이드카 `.meta` · 파일 안 id · NTFS 파일 id)를 다시 연결 후보로」 narrows — sidecar and in-file id are not candidates (G61 · M109) and the NTFS file id becomes object ID · hash (tracking T-74).
- The order of reference removal = the move to `.trash` (or the rename · move) first → preset files → agents (the skeleton of ADR-0335 decision 1 as is · main 2026-11-01 — M100).
- Reference removal on the agent side = the whole-registry removal verb of the profile edit port (`remove_preset_paths(paths)` — the name is a placeholder · main 2026-11-01 — M101). It removes the same attachment, equal by `same_path` to one of the given paths, from all agents under one registry lock, and returns the changed agents in id order. It does not accept an agent list — the same reason as `rewrite_preset_paths` (race with a copy — ADR-0335 decision 6). It is added together with the port at stage 4. It is called only for the preset files that a delete with references removed deleted — agents attach only presets, so it is not called in the `SKILL.md` cases (delete · rename · move).
- No sidecar (`.meta` · `.uid` form) is placed in the library folder (G61) and no engram id is written inside files (M109) — candidates for recovery after an outside move (OS file identity (object ID) · hash etc.) stay in tracking T-74 — that is its share, not the overwrite policy.
- Whether to show the reference notice in the overwrite confirmation dialog too is checked at the file-operation stage (undecided).
