# ADR-0142: 우편 배달 병렬화 축과 같은 세션 배제 축

- 상태: 확정 (2026-08-18, 근거: 실측 2회 + review deep 3라운드)
- 관련: ADR-0104(flush 트리거·idle 게이트) · ADR-0107(이름 축 in-flight 회계 + `deferred_flush` 표식 — 대상 축이 그 형태를 복제한다) · ADR-0125(주입 코드 한 벌) · ADR-0110(메시징 커널 격리) · ADR-0129(flush 파이프라인 거주지) · ADR-0088(배달 관측 레코드) · ADR-0103/0104(무손실 복원) · ADR-0101/0111(이름 키 파킹) · `crates/engram-dashboard-daemon/src/messaging_host.rs`(디스패처) · `crates/engram-dashboard-messaging/src/service.rs`(`drain_queue` 두 축) · step-log S22 · Amends ADR-0125 (겹침 가드 단일 축 서술을 두 축으로)

## 맥락

터미널(Raw) 수신자 배달은 **본문 write → `SUBMIT_PACING`(0.5초) → 제출 write** 다. 제출을 만드는 건 바이트가 아니라 **수신자의 read 경계**라, 두 write를 벌리는 대기가 제출의 일부다(실측 2026-08-17 — `backend::SUBMIT_PACING` doc이 정본).

데몬의 flush 레인이 **전역 직렬**이었다: 각 배달을 `spawn_blocking` 으로 던지고 **완료를 await 한 뒤** 다음 트리거를 꺼냈다. 그래서 터미널 수신자 하나의 0.5초가 다른 수신자 전부를 세웠고, 페이싱이 **아예 필요 없는** StreamJson 수신자(`submit_sequence()` = None)까지 그 뒤에 섰다. 옛 코드는 이 성질을 "사람 대화 수준 메시지율이니 감수한다"로 주석에 수용해 뒀다. 사용자 판정: **"엔터 하나 치자고 배달 줄 전체를 세우는 건 시스템이 아니다."**

## 결정

### 결정 1 — 배달 병렬화 축 = 도어벨 AgentId (호스트)

flush 레인을 **수신자별 디스패처**로 교체한다. 도어벨(`FlushMsg`)에 실린 AgentId로 분할해 서로 다른 키는 동시 진행하고, 같은 키는 대기열로 직렬을 유지한다. `spawn_blocking` 핸들을 인라인 await 하지 않고, 완료를 클로저 안의 Drop 가드가 채널로 알린다(그 자리에서 await 하는 것이 곧 head-of-line blocking 이므로).

**이 축의 목적은 처리량이고 정합성 보장은 하지 않는다** — 같은 세션 배제는 결정 2가 진다. 호스트는 도어벨 id만 알고 그 편지가 어느 세션으로 갈지 모르기 때문이다.

### 결정 2 — 같은 세션 배제 = 커널의 해석된 대상 id 축, 이름 축과 병존

**분할 키(도어벨 id)는 실제 주입 대상이 아니다.** 대상은 항목별로 `drain_queue` 안에서 해석된다(`hinted_id` 우선 → 이름 유일 도달). 그래서 **서로 다른 두 이름 큐가 한 세션으로 수렴**할 수 있고, 트리거는 **산 에이전트 개명 + 그 빈 이름을 다른 에이전트가 인계**다. 기존 0단계 in-flight 가드는 **park 큐 이름 키**라 이 축을 구조적으로 못 본다.

그래서 `in_flight_targets`(해석된 대상 세션 id 집합)를 추가한다. 판정과 등록은 **같은 락 구간** 안에 두고, 물러난 쪽은 항목을 **원래 순서로 되돌린 뒤** 대기자를 등록해 이긴 쪽이 정산하며 같은 도어벨을 다시 누른다(`deferred_flush` 와 **누르는 동사는 하나**).

**이름 축은 그대로 둔다** — cap 분모 회계가 그 축에 얹혀 있어, 좁히거나 id로 갈아끼우면 순서 보장과 유입 통제가 함께 깨진다.

### 결정 3 — `DrainReport` 의 caller-facing 판정은 호출자 자기 몫으로 좁힌다

`retreated` · `caller_inject_error` 는 **호출자 자신의 그룹**에서 일어난 일만 담는다. 드레인 하나가 여러 대상으로 갈라지므로, 넓은 채로 두면 **남의 사정이 발신자 응답 문구가 된다**(상대가 턴 중인데 "다른 발송이 겹쳤다", 시도조차 안 된 메시지에 "배달 실패"). 발신자는 LLM이고 그 문구로 다음 행동을 정하므로 오보는 실해다.

**`gated` 는 의도적으로 드레인 전체 범위로 남긴다** — 사유 우선순위의 **맨 끝** 갈래라 그 자리에서는 참이다(앞의 두 사유가 이미 걸러졌다면 남은 설명은 "상대가 턴 중"뿐이다). 미구현이 아니라 결정이다 — 좁히려는 다음 세션은 먼저 그 우선순위를 확인할 것.

## 거부한 대안

- **전역 직렬 유지** — 옛 주석의 수용("사람 대화 수준 메시지율")은 우편이 실제 경로가 된 지금 틀렸다. 실측으로 JSON 수신자가 남의 0.5초를 그대로 기다린 것이 확인됐다(사용자 판정).
- **제출 write 를 예약(defer)해 비블로킹화** — `/research` 가 찾은 동종 선례(Herdr · AWS Labs CAO)가 이 형태(300ms 예약)다. 거부 이유 둘: ① `submit_input_observed` 의 **Err 계약이 깨진다** — 제출 실패를 배달 시점에 알 수 없어 무손실 재파킹(코드 앵커는 ADR-0103/0104 — ADR-0088 은 실패 관측 레코드 쪽이다. Err 계약 자체의 정본은 `core/src/agent/session.rs` 의 `submit_input_observed` doc)이 성립하지 않고, 봉투가 입력창에 미제출로 남은 채 "배달됨"으로 정산된다. ② **같은 수신자 본문 병합을 막지 못한다** — 예약은 본문 둘이 연달아 나가는 것을 막는 장치가 아니라 만드는 쪽이라, 같은 세션 배제가 여전히 필요해진다. 그 배제가 곧 **결정 2의 대상 축**이므로 예약은 잉여다. ★결정 1(도어벨 id 분할)로 오독하지 말 것★ — 그 축은 병합을 막지 않는다(결정 1 문단이 명시적으로 부인한다). 이 혼동이 1라운드 리뷰가 세 리뷰어 독립으로 적출한 그 오류다.
- **에이전트별 상주 태스크·스레드**(Herdr 의 pane별 채널 형태) — 들고 있을 상태가 "대기열 + 진행중 여부" 두 칸뿐인데 에이전트 사망 시 정리·수명 관리 표면이 새로 생긴다. 지도 항목은 대기열이 비면 지우면 끝난다. 리뷰(동시성 렌즈)도 semaphore 단순화안을 "부품은 줄지만 순서 보장을 라이브러리 성질로 넘기는 교환"으로 판정해 지금 바꿀 근거가 약하다고 봤다.
- **`SUBMIT_PACING` 을 300ms 로 낮추기** — 우리 실측값은 500ms 이고 상수 doc 이 "줄이면 재발"을 경고한다. 병렬화로 head-of-line 이 사라지면 값을 줄일 동기 자체가 없다. ★선례군이 둘이라 수치가 갈린다 — 헷갈리지 말 것★: 300ms 는 **상주 데몬형**(Herdr · AWS Labs CAO)의 정착값이고 둘 다 그 근거를 코드에 남기지 않았다. 반면 상수 doc 이 인용하는 0.5초는 **tmux 기반 오케스트레이터**군의 정착값이다(`backend/mod.rs` 의 그 문단이 정본). ADR-0038 절차로 값의 출처를 추적하는 세션은 두 군을 갈라 볼 것.
- **호스트에서 (canonical 이름 ∪ 힌트 큐) 합집합 단위 직렬화** — 대상 해석이 드레인 **안에서** 일어나므로 호스트는 그 편지가 어느 세션으로 갈지 알 수 없고, execution 시점 재해석과 경합한다.
- **우편함 키를 이름 → id 로 재키** — **폐기가 아니라 별건 과제로 미룸**(사용자 결정). 지금 이름 키가 공짜로 해주는 두 구제를 명시 장치로 대체해야 한다: ① 아직 없는 상대에게 보낼 때 그 시점에 id 가 없어 키를 만들 재료가 없다(파킹 자체가 성립하지 않는다) ② 재시작로 id 가 바뀔 때 옛 id 큐의 편지를 새 id 로 이관해야 한다(현재는 이름이 그 역할 — ADR-0101 · ADR-0111 결정 6).
- **결정 2 를 안 하고 잔여로 수용** — 메인이 한 번 이 방향을 택했으나 **사용자가 기각**했다. 조건(개명 + 이름 인계)이 전부 사용자 조작으로 도달 가능하고, 결과가 두 사람의 편지가 한 턴으로 합쳐지는 정합성 손상이다.
- **결정 3 에서 `target_deferred` 같은 플래그를 하나 더 두기** — 거부. `gated` 와 새 플래그 사이 어떤 고정 우선순위를 두어도 두 혼재 경우 중 하나가 틀린다(내 몫이 대기 + 남이 물러남 / 내 몫이 물러남 + 남이 대기). 호출자 자기 그룹으로 좁히면 두 소비처가 같은 사실을 읽는다.

## 근거

- **실측 2회**(2026-08-18) — 편지를 파킹시킨 뒤 Raw · StreamJson 수신자를 연달아 스폰해 도어벨을 겹치게 만들고 데몬 debug 로그 시각을 대조했다. 도어벨→delivered 가 Raw 는 두 번 다 **501ms**(= 페이싱 창), JSON 은 자기 도어벨 후 **1ms 미만**이고 Raw 완료보다 **265ms · 383ms 먼저** 끝났다. 옛 직렬 레인이면 JSON 의 delivered 줄이 Raw 뒤에 찍힌다. 발송 시점 응답이 `pending` 두 행이라 **동기 배달이 아니라 flush 레인 배달**임도 확정됐다.

## 영향 / 불변식

- **같은 세션에 동시 주입 금지** — 어기면 두 번째 본문이 첫 CR 앞에 닿아 봉투 둘이 한 턴으로 합쳐 제출된다(두 사람의 편지가 뒤엉킨다). 이 배제는 **커널 소유**다 — 호스트로 올릴 수 없다.
- **`in_flight_targets` 는 fail-open 이 없다**(수용한 잔여) — 이름 축은 `saturating_sub` 로 분모를 0 으로 수렴시키고 busy 축은 `BUSY_MAX_TURN` 상한이 있으나 이 축은 없다. 막는 불변식은 하나뿐이다: **`insert` 가 실행된 경로에서는, 그 해제를 소유하는 `FlightSettle` 이 생성되기 전까지 실패할 수 있는 것(early return · `?` · 패닉하는 호출)이 하나도 없어야 한다**(생성 뒤로는 어느 경로로 빠져나가도 Drop 이 갚는다). 여기서 "실패" 는 **언와인딩하는** 실패다 — 할당 실패처럼 abort 로 끝나는 것은 갚을 프로세스가 남지 않으므로 논외다. ★구간이 아니라 **경로** 기준이다★ — 줄 범위로 읽으면 `insert` 가 실행되지 않은 경로의 early return 이 반례처럼 보여, 나중에 정말 도달 가능한 early return 을 넣는 변경이 그걸 선례로 든다. 그 경로에 실패 지점을 넣는 변경이 생기면 이 잔여를 재론한다. 갇히면 그 세션이 편지를 영영 못 받는다(이 서브시스템 최악 실패 모드).
- **물러남에는 반드시 되울림이 짝** — 가드만 남기고 `deferred_flush`/`deferred_by_target` 되울림을 걷어내면 물러난 편지가 다음 등장·턴 종료 통지나 TTL 까지 발이 묶인다.
- **수용한 잔여** — 이긴 쪽이 주입 중 언와인딩하면 대상은 해제되지만 재기동 신호는 누락된다(물러난 편지가 다음 도어벨·TTL 까지 대기). 워크스페이스 release 는 `panic = "abort"` 라 이 경로는 debug·test 빌드에만 존재한다.
- **호스트는 같은 세션 배제를 주장하지 않는다**(ADR-0110) — 그 진술이 사는 곳은 모듈 헤더가 아니라 **`run_flush_lane` 의 함수 doc** 이다(찾을 때 파일 헤더를 뒤지지 말 것). 자기가 도어벨 id 단위로만 직렬화한다고 적고 정합성은 커널 축을 가리킨다. 커널 헤더도 호스트 성질을 전제하지 않는다.
- **미확인** — 실측은 데몬 직결 경로로 수행했다(앱 UI 미검증 — 타 워크트리 앱이 단일 인스턴스 자리 점유). 대상 축 테스트는 같은 스레드 재진입으로 인터리빙을 만들어 **두 OS 스레드가 한 대상을 경합하는 경우는 어느 테스트도 덮지 않는다**(구조적 논증뿐). 통과 2회는 smoke 증거이고 race-freedom 증명이 아니다.
- **이 결정이 닫지 않은 것 = T-28**(추적 목록) — 같은 실측이 **갓 스폰된 터미널 수신자는 배달된 편지를 제출하지 않는다**를 잡았다(CR 이 스폰+약 0.5초에 닿는데 그 세션의 claude 는 그보다 약 0.5초 더 뒤에 부팅을 마친다). 위 "값을 줄일 동기가 없다"는 **head-of-line 관점의 진술이고, 부팅 직후 수신자에게 0.5초가 충분한지와는 별개 문제다.** 페이싱 값을 다시 꺼내는 세션은 T-28 을 먼저 읽을 것 — 같은 실측을 다시 걷지 않도록.
