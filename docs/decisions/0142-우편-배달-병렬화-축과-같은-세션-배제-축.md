# ADR-0142: The mail delivery parallelization axis and the same-session exclusion axis

- 상태: 확정 (2026-08-18, grounds: 2 measurements + 3 rounds of review deep) · 부분 폐기 by ADR-0292 (the abort premise of the accepted residual) · 부분 폐기 by ADR-0309 (decision 2 keeps the name axis)
- 관련: ADR-0104(flush trigger · idle gate) · ADR-0107(name-axis in-flight accounting + the `deferred_flush` marker — the target axis duplicates that shape) · ADR-0125(one set of injection code) · ADR-0110(messaging kernel isolation) · ADR-0129(home of the flush pipeline) · ADR-0088(delivery observation record) · ADR-0103/0104(lossless restore) · ADR-0101/0111(name-keyed parking) · `crates/engram-dashboard-daemon/src/messaging_host.rs`(dispatcher) · `crates/engram-dashboard-messaging/src/service.rs`(the two axes of `drain_queue`) · step-log S22 · Amends ADR-0125 (the single-axis description of the overlap guard becomes two axes) · Amended by ADR-0292 (the abort premise of the accepted residual) · Amended by ADR-0309 (decision 2 keeps the name axis)

## 맥락

Delivery to a terminal (Raw) recipient is **body write → `SUBMIT_PACING` (0.5 seconds) → submit write**. What makes the submit is not the bytes but **the recipient's read boundary**, so the wait that separates the two writes is part of the submit (measured 2026-08-17 — the `backend::SUBMIT_PACING` doc is the source of truth).

The daemon's flush lane was **globally serial**: it threw each delivery into `spawn_blocking`, **awaited its completion**, and only then took out the next trigger. So the 0.5 seconds of a single terminal recipient stalled every other recipient, and even StreamJson recipients that **need no pacing at all** (`submit_sequence()` = None) queued behind it. The old code accepted this property in a comment as "the message rate is at the level of human conversation, so we put up with it." The user's decision: **"엔터 하나 치자고 배달 줄 전체를 세우는 건 시스템이 아니다."** (gloss: stalling the whole delivery line just to press one Enter is not a system.)

## 결정

### 결정 1 — The delivery parallelization axis = the doorbell AgentId (host)

Replace the flush lane with a **per-recipient dispatcher**. It partitions by the AgentId carried on the doorbell (`FlushMsg`); different keys proceed concurrently, and the same key stays serial through a queue. The `spawn_blocking` handle is not awaited inline; a Drop guard inside the closure reports completion over a channel (awaiting on the spot is itself head-of-line blocking).

**The purpose of this axis is throughput, and it gives no correctness guarantee** — same-session exclusion is carried by decision 2. This is because the host knows only the doorbell id and does not know which session that letter will go to.

### 결정 2 — Same-session exclusion = the kernel's resolved-target-id axis, coexisting with the name axis

**The partition key (the doorbell id) is not the actual injection target.** The target is resolved per item inside `drain_queue` (`hinted_id` first → unique reach by name). So **two different name queues can converge on one session**, and the trigger is **a live agent is renamed + another agent takes over that now-empty name**. The existing step-0 in-flight guard is keyed by the **park queue name**, so it structurally cannot see this axis.

So `in_flight_targets` (the set of resolved target session ids) is added. The decision and the registration sit **inside the same lock section**; the side that backs off **returns its items to their original order**, then registers a waiter, and the winner settles and presses the same doorbell again (**one verb for pressing**, shared with `deferred_flush`).

**The name axis stays as it is** — the cap denominator accounting rides on that axis, and narrowing it or swapping it for id would break the ordering guarantee and the inflow control together.

### 결정 3 — The caller-facing decisions of `DrainReport` are narrowed to the caller's own share

`retreated` · `caller_inject_error` hold only what happened in **the caller's own group**. One drain splits across several targets, so if left broad, **someone else's circumstances become the sender's response wording** (the counterpart is mid-turn yet it says "another send overlapped," or "delivery failed" for a message that was never even attempted). The sender is an LLM and decides its next action from that wording, so a misreport does real harm.

**`gated` is intentionally left at whole-drain scope** — it is the branch at the **very end** of the reason priority, so it is true at that spot (if the two earlier reasons were already filtered out, the only explanation left is "the counterpart is mid-turn"). It is a decision, not an unimplemented item — a later session that wants to narrow it must first check that priority.

## 거부한 대안

- **Keep the global serial lane** — the old comment's acceptance ("the message rate is at the level of human conversation") is wrong now that mail has become a real path. Measurement confirmed that a JSON recipient waited out someone else's 0.5 seconds as is (user decision).
- **Schedule (defer) the submit write to make it non-blocking** — the same-kind precedent that `/research` found (Herdr · AWS Labs CAO) has this shape (a 300ms reservation). Two reasons for rejection: ① **the Err contract of `submit_input_observed` breaks** — a submit failure cannot be known at delivery time, so lossless re-parking does not hold (the code anchor is ADR-0103/0104 — ADR-0088 is on the failure observation record side. The source of truth for the Err contract itself is the `submit_input_observed` doc in `core/src/agent/session.rs`), and the envelope is settled as "delivered" while it remains unsubmitted in the input box. ② **It cannot prevent merging bodies for the same recipient** — a reservation is not a device that prevents two bodies going out back to back but one that creates it, so same-session exclusion is still needed. That exclusion is exactly **the target axis of decision 2**, so the reservation is redundant. ★Do not misread this as decision 1 (doorbell id partition)★ — that axis does not prevent merging (the decision 1 paragraph explicitly denies it). This confusion is the very error that round 1 of the review pulled out independently from three reviewers.
- **A resident task/thread per agent** (the per-pane channel shape of Herdr) — the state to hold is only two cells, "queue + in-progress flag," but a new surface for cleanup and lifetime management on agent death appears. A map entry is done once it is deleted when the queue empties. The review (concurrency lens) also judged the semaphore simplification proposal as "an exchange that reduces parts but hands the ordering guarantee over to a library property," and saw weak grounds to change now.
- **Lower `SUBMIT_PACING` to 300ms** — our measured value is 500ms and the constant doc warns "reducing it brings regression back." Once parallelization removes head-of-line, there is no motive to reduce the value at all. ★There are two groups of precedent, so the numbers differ — do not confuse them★: 300ms is the settled value of the **resident daemon type** (Herdr · AWS Labs CAO), and neither left its grounds in code. By contrast the 0.5 seconds that the constant doc cites is the settled value of the **tmux-based orchestrator** group (that paragraph in `backend/mod.rs` is the source of truth). A session tracing the origin of the value by the ADR-0038 procedure should look at the two groups separately.
- **Serialize at the host by the union of (canonical name ∪ hint queue)** — target resolution happens **inside** the drain, so the host cannot know which session that letter will go to, and it races with re-resolution at execution time.
- **Re-key the mailbox from name to id** — **deferred as a separate task, not discarded** (user decision). The two rescues that the name key now gives for free would have to be replaced with explicit devices: ① when sending to a counterpart that does not exist yet, there is no id at that moment and so no material to make a key from (parking itself does not hold) ② when the id changes on restart, the letters in the old id's queue must be migrated to the new id (currently the name plays that role — ADR-0101 · ADR-0111 decision 6).
- **Skip decision 2 and accept it as a residual** — main chose this direction once, but **the user rejected it**. The conditions (rename + name takeover) are all reachable by user actions, and the result is a correctness loss where two people's letters merge into one turn.
- **Add one more flag such as `target_deferred` in decision 3** — rejected. Whatever fixed priority is set between `gated` and the new flag, one of the two mixed cases comes out wrong (my share is waiting + someone else's backed off / my share backed off + someone else's is waiting). Narrowing to the caller's own group makes the two consumers read the same fact.

## 근거

- **2 measurements** (2026-08-18) — after parking a letter, Raw and StreamJson recipients were spawned back to back so the doorbells overlapped, and the daemon debug log times were compared. Doorbell→delivered was **501ms** for Raw both times (= the pacing window), and for JSON it was **under 1ms** after its own doorbell and finished **265ms · 383ms earlier** than the Raw completion. With the old serial lane, JSON's delivered line would be printed after Raw. The send-time response being two `pending` rows also confirmed that it is **flush lane delivery, not synchronous delivery**.
- **review code deep** — doc-aware invariant breaker · cross-family blind breaker · concurrency and shutdown lens. Round 1 caught the defect in decision 2 (partition key ≠ injection target) through independent extraction by three reviewers. In round 3 the doc-aware reviewer gave PASS and confirmed at code points that the decision and the registration are in one lock section, and that the register→release→collect order has no missed-wakeup window.
  ★**Do not read this as "passed round 3"**★ — in the same round 3 the blind reviewer gave FIX on 2 items, and those 2 (one is the **`caller_inject_error` scope of decision 3**) were fixed in the 4th coder round. What covers the changes of the 4th and 5th rounds (anchors · wording) is a separate follow-up review, and **its decision is in step-log S22** — a session that wants to check per-round coverage should look there.

## 영향 / 불변식

- **No simultaneous injection into the same session** — if violated, the second body reaches the input before the first CR, and two envelopes are submitted merged into one turn (two people's letters get entangled). This exclusion is **kernel-owned** — it cannot be lifted to the host.
- **`in_flight_targets` has no fail-open** (accepted residual) — the name axis converges its denominator to 0 with `saturating_sub` and the busy axis has the `BUSY_MAX_TURN` cap, but this axis has none. There is only one invariant that blocks it: **on a path where `insert` ran, nothing that can fail (an early return · `?` · a call that panics) may exist before the `FlightSettle` that owns its release is created** (after creation, whatever path it leaves by, Drop pays it back). Here "fail" means a **unwinding** failure — something that ends in abort, like an allocation failure, is out of scope because no process is left to pay back. ★The criterion is the **path**, not the section★ — if read as a line range, an early return on a path where `insert` did not run looks like a counterexample, and a later change that inserts a truly reachable early return would cite that as precedent. If a change appears that puts a failure point on that path, reopen this residual. If it gets stuck, that session never receives letters again (the worst failure mode of this subsystem).
- **A back-off must always be paired with an echo** — if only the guard is left and the `deferred_flush`/`deferred_by_target` echo is removed, the backed-off letter is stuck until the next appearance, the turn-end notification, or the TTL.
- **Accepted residual** — if the winner unwinds during injection, the target is released but the restart signal is missed (the backed-off letter waits until the next doorbell or the TTL). The workspace release is `panic = "abort"`, so this path exists only in debug and test builds.
- **The host does not claim same-session exclusion** (ADR-0110) — the place where that statement lives is not the module header but **the function doc of `run_flush_lane`** (do not search the file header when looking for it). It states that it serializes only per doorbell id and points to the kernel axis for correctness. The kernel header also does not presuppose host properties.
- **Unconfirmed** — the measurement was done through the direct-to-daemon path (the app UI was not verified — an app from another worktree occupied the single-instance slot). The target-axis test builds the interleaving through same-thread re-entry, so **no test covers the case where two OS threads race for one target** (structural argument only). The 2 passes are smoke evidence and not a proof of race-freedom.
- **What this decision did not close = T-28** (tracked list) — the same measurement caught that **a freshly spawned terminal recipient does not submit the delivered letter** (the CR arrives at spawn + about 0.5 seconds, but the claude in that session finishes booting about 0.5 seconds later than that). The "no motive to reduce the value" above is **a statement from the head-of-line viewpoint, and it is a separate matter from whether 0.5 seconds is enough for a recipient right after boot.** A session that revisits the pacing value should read T-28 first — so as not to take the same measurement again.
