# ADR-0324: Library locking convention — one `RwLock` + scan-generation ticket (FIFO) + conditional late merge · the trash lock is a separate leaf with hand-over

- 상태: 제안 (2026-10-31, basis: TRD `/review trd` re-review R1~R6 applied — main M34 · M35 · M37 · M39 · M40 · M41 · M43 · M44 · M45 · M46 · M47 · M48 · M50 · M51 · M52 · M53 · M54 (report) · flow check G17 · research `docs/research/markdown-frontmatter-hash-sync-crates-2026-10-31.md` (lock components))
- 관련: ADR-0311 · ADR-0314 (request form · first scan) · ADR-0335 · ADR-0320 · ADR-0332 (new-schema re-check) · ADR-0322 · ADR-0006 (lock order) · the lock order in CLAUDE.md 「핵심 불변식」 · TRD `docs/process/S25-preset-library/trd.md` §1-4 flow ① 「잠금」 ①~⑤ · 「Engram 안의 변경」 · §3 locking · §1-11a scenarios 1 · 5 · 6 · 8 · 10 · findings 9 · 17 · §4 「메모리 목록 · 훑기」 · 「파일 조작 · 휴지통」 row

## 맥락
asset-library holds an in-memory `Catalog` (items · a reverse index of references from the preset side), and since the port is synchronous, several threads call it together — the launch check (deadline 7 seconds · 「실행은 전체 훑기를 기다리지 않는다」), list · detail reads, scans (first scan · `library.refresh` · `setRoot`), Engram changes (file operations · preset edits · relink), new-schema re-check, and emptying the trash. Six re-review rounds caught the race defects in turn (ghost items · blocking itself · endless overtaking · false 「찾을 수 없음」 · stalls over 7 seconds), and the fixes gathered into one rule.

## 결정
1. **The `Catalog` lock = one `std::sync::RwLock`** (the port is synchronous, so it is not a tokio lock). Walking · parsing is outside the lock, and the write lock is taken only at the moment `Catalog` is swapped in. The edges going outward while holding that lock are only the profile edit port and `ProfileRegistry` reads, and the manager holds neither the registry nor the reservation lock when calling `LaunchKitSource` — asset-library → manager, one direction.
2. **Do not take the write lock while holding a read lock** (M35). The launch check reads the attached files outside the lock, runs `resolve` · `validate` under the read lock and then releases it, and merges the newly read bytes under a separate short write lock (decision 5). The same goes for 「목록에 없는 경로 하나 확인해 넣기」 of `library.list`.
3. **Scan ↔ Engram change = scan generation `Mutex` + `Condvar`** (not the library lock — M35). That `Mutex` holds the scan in progress · the number of changes in progress · the change generation · the root generation · the swap-in count · the ticket queue (the root generation's place is only here — M43). It is a leaf — it takes no other lock while held, and while waiting on that `Condvar` the library lock is not held.
4. **Order = one line of tickets (FIFO — M41)**: a scan enters when all the preceding numbers have finished, and a change enters when all the preceding numbers have entered and no scan is in progress (changes drawn in sequence enter together). Raising generations — a change raises the change generation **before** it releases the write lock (M39), `setRoot` raises the root generation, and the scan's swap-in raises the swap-in count (M43). A swap-in discards its result and scans again if the change generation moved after the scan started (M35), and leaves items outside the scan range as published (M34).
5. **Late merge = conditional** (M39 · M43): the launch check's new bytes · the list safeguard's insert write down the change generation · root generation · swap-in count together **before** the disk read outside the lock, and compare again inside the write lock that merges — if a generation moved, discard the whole thing, and if only a swap-in intervened, discard only the insertion of paths that are not in `Catalog` (the list safeguard's insert is always for a path that did not exist, so it is discarded then). If all three are unchanged it goes in immediately even during a scan (M34), and if the same item was read together within the scan range, the one read later remains (the order = a monotonic number drawn before opening the file · an item the scan could not find within the range is counted as having read 「없음」 at the number from before it listed that folder — M43).
6. **First-scan entrance** (M37 · M40 · M48 · M51): every `LibraryCommandHost` method that reads `Catalog` (`library.*` read · `preset.get` · `agent.presets` · tree ⛔ · edits that carry the problem list or reference counts in the answer, or whose plan · validation reads `Catalog`) starts or waits for the first scan — for edits **at the method entrance**, ahead of the ticket · the in-progress count · the library lock. 「첫 훑기가 끝났다」 = **one full** scan has been published (a folder-scoped publish does not change it). `library.refresh {folder}` before the first scan also passes through the full first scan (the answer is that folder's share), and if the first scan waited for was not published, it passes through the entrance again instead of drawing a ticket (if it fails there too, that failure is the answer). The launch check (`LaunchKitSource::check`) is outside this entrance.
7. **Request coalescing** (M9 · M44): a `Catalog` read waiting for the first scan (including the edit entrance) also attaches to a scan that is already walking — it does not need to be new, only `Catalog` must exist. `library.refresh` attaches only to a covering generation that has not started walking yet, and if the covering scan is already walking it draws its own ticket (the 「밖에서 바꾼 뒤 refresh 를 부른다」 contract — PRD R41). Refreshes that arrive in a crowd fold into one generation before walking.
8. **The settings re-check for a new schema is also a change** (M45): **after** plugging the new schema into the checker, it draws a ticket, counts as in progress, raises the change generation inside the write lock, and also fixes the check results attached to the parse cache (M49). It does not pass the first-scan entrance and does not trigger a first scan — if no scan has ever happened, `Catalog` is empty and there is nothing to do.
9. **The trash lock = a separate leaf** (M46 · M47 · M50 · M52 · M53 · M54): it lines up only the operations that touch `.trash`. Moving (files pushed out by delete · overwrite) · restoring take this while holding the library write lock (order = library lock → trash lock). `library.emptyTrash` takes neither the library lock nor a ticket — it reads the root once briefly with a read lock and releases it, then takes the trash lock briefly to capture the bundle list, and takes · sends · releases **per bundle**. **Hand-over**: the moving side raises the waiting count before it waits, and lowers it after finishing **all** moves of `.trash` of that operation (one operation = one trash step = one bundle — M53). Emptying waits, holding no lock at all, until that count is 0 before taking the list and before taking each bundle. The waiting count must be raisable even while a bundle is being sent (if it is placed behind a lock held during sending, emptying reads 0 the moment it is released), all are woken when the state changes, and it is lowered on failure · early-return paths too (guard — M54). Shape example = `Mutex<휴지통 상태>` + `Condvar` (state = held · waiting count) — the exact form is an implementation judgment.
10. Components = std `Mutex` + `Condvar` + a hand-built ticket — no third-party lock is brought in (research).

## 거부한 대안
- **A scan that holds the write lock while walking** — the launch check waits for the full scan (violates update rule 「실행은 기다리지 않는다」 — TRD flow ① 「잠금」 ① · finding 9).
- **Upgrading from a read lock to a write lock** — `std` `RwLock` has no upgrade, so it blocks itself (M35 · re-review B2).
- **During a scan, skip the launch check's merge and let the swap-in put it in** (the old rule) — the swap-in of a folder A scan reverts a folder B item that a launch fixed in the meantime, so the problem list · ⛔ went stale (M34 · re-review B1).
- **An unconditional late merge** — it revived the old path · old bytes of a rename · delete · preset edit that finished between that read and the merge (ghost items · M11 broken — M39 · R2 C1). Comparing only the generation re-inserted a path that a covering scan after an outside delete had removed (M43 · R3 E1).
- **An edit joins the first scan after drawing a ticket or counting as in progress** — either a change in progress blocks the start of that scan, or the swap-in of a scan that already ran waits on that change's write lock and blocks itself (M40 · R2 C2).
- **A turn without fairness** (whoever grabs first enters) — newly arriving scans overtake a waiting change endlessly, or overlapping changes put off the first scan endlessly (M41 · R2 C3).
- **`library.refresh` attaches to a scan that is already walking** — it returns a result that missed the bytes the caller changed outside before that (PRD R41 broken — M44 · R3 E2).
- **A folder refresh before the first scan scans only that folder** — a partial `Catalog` is published, so references outside the folder become a false 「찾을 수 없음」, and the LLM can see that and 「고칠」 user data (M48 · R4 H2). Scanning only the folder with a ticket after the first scan waited for failed is the same defect (M51 · R5 J2).
- **A schema re-check that fixes `Catalog` outside tickets · generations** — the first scan that was walking published an old-schema result, and a wrong ⛔ · problem stayed until restart (M45 · R3 E3).
- **Emptying holds the library write lock throughout** — `.trash` is outside `Catalog` yet it passed the 7-second deadline and stalled the launch's read lock (M46 · R3 E4).
- **Emptying holds the trash lock throughout** — a delete · restore that arrived during emptying waited for the whole emptying while holding the write lock, so every read lock stalled beyond 7 seconds, and `setRoot` also got in the middle of emptying (M47 · R4 H1).
- **Only release per bundle and immediately take again** (no hand-over) — `std` `Mutex` is not fair, so emptying takes it again right away, and a delete that waits holding the write lock can lose throughout the emptying (M50 · R5 J1 · std `Mutex` on Windows has no hand-over — research).
- **Listing the bundles outside the lock** — it catches a half-full bundle in the middle of a move (M52 · R5 J3).
- **Raising and lowering the waiting count per item** — between several-item restores · two overwrites, emptying takes the next bundle (or the list) (M53 · R6 K1).
- **`parking_lot`** — it newly enters the daemon graph (only 0.12.5 is in the lock through tauri), 0.13.0 removed automatic eventual fairness and raised MSRV to 1.95 · mixed conditions like 「훑기는 배타 · 편집은 동시」 cannot be expressed as lock fairness (research). **`spin::TicketMutex`** — it spins. **The `ticket_lock` crate** — it is not on crates.io (same research).

## 영향 / 불변식
- **Lock order**: library `RwLock` → trash lock. The scan generation `Mutex` · trash lock are leaves. The profile edit port · registry reads can be called under the library lock and never the reverse. A candidate to add to the lock-order line of CLAUDE.md 「핵심 불변식」 (user confirmation at implementation).
- **Adding a new path that changes `Catalog`** (a new kind of change) also takes on the ticket · the in-progress count · raising the generation inside the write lock — if one is missing, the late merge revives the old state. A new read method passes the first-scan entrance.
- **What remains (accepted)**: a read answered between the first scan's swap-in and the schema re-check can show an old-schema result — the next query is right (M45 · scenario 8). A delete · restore that arrives during emptying waits holding the write lock while one bundle is sent, and during that the launch's read lock also stalls (M47) — if even one bundle is long, the next step = move the captured bundle into a hidden folder inside `.trash` and then send it without a lock (only when measurement calls for it — finding 17).
- FIFO · hand-over · conditional merge are fixed deterministically by the §4 tests (asserted at the gate, not by racing — M50 · M53 · failure injection = M51).
