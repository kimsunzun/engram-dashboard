# ADR-0233: The codex JSON session id is persisted when the other side echoes the first user message — if it dies after sending and before the echo, the next activation is a new conversation

- 상태: 확정 (2026-09-26, basis: user decision 2026-09-26 (TRD §10-1 24) + P2 local QA full measurement (isolated release — persistence confirmed at the first echo)) · 부분 폐기 by ADR-0292 (the pump Failed description of a reader-port panic)
- 관련: Amends ADR-0226 (decision 2 trigger and the decision 11 exception and the invariant in Impact, based on the first user message echo in codex JSON) · Amends ADR-0231 (closes the entrance at the end of decision 9 that persists the id of the first input taken back while codex is connecting) · Amends ADR-0185 (withdraws, for codex JSON, the Phase 2 requirement in Impact to persist before the first turn) · TRD `docs/process/S21-codex-backend/trd-mid-turn-input-queue.md`(§5-8 · §10-1 24 · §10-6 first row) · `docs/reference/backend-capabilities.md` §1 「codex 에만 있는 위험」 · Related ADR-0218(lock reclaim for the codex terminal — that slot of decision 11 is unchanged) · ADR-0071(profile save lock discipline — the thread that runs the commit changes) · ADR-0004(the backend decides whether to plug in the first-turn port) · step-log S21 · Amended by ADR-0292 (the pump Failed description of a reader-port panic)

## 맥락
ADR-0226 made the session id persist only when the incarnation's 「첫 제출 래치」 commits — the first moment when both inputs (`offer` = the id is known · `note_submission` = just before the first user turn goes out) have stood, and the session's input verbs count a submission **before** `send_input` (decision 2 of that ADR). Its premise was 「세션이 통로에 넘긴 글은 곧 상대에게 간다」.

Turning on codex JSON as `TransportOwned` through mid-turn input (ADR-0231) (P2c) broke that premise. The path **holds** text while connecting · waiting for a turn id · in a tool span and so on, and held text is taken back with ✕ (no vendor call). So the first text typed before the connection of a new codex agent is up stands on the list → the session counts it as a submission → it meets the `offer` of the handshake response and the id is persisted → if the user takes that text back with ✕, **the id of a thread with not a single turn is left in the profile.** `thread/start` does not create a rollout (`docs/reference/backend-capabilities.md` §1), so the next activation's `thread/resume` returns to the very failure ADR-0226 meant to remove (`-32600 no rollout found` → 「이어받을 대화가 없습니다」 — context P2 of that ADR). ADR-0231 decision 9 recorded this as one new entrance to the ADR-0226 class 「이 결정이 새로 만드는 쓰레기」 (a pre-implementation description).

During implementation (after P2c) this entrance came up as a concern before review, and the user decided the persistence moment.

## 결정
1. ★**The thread id of codex JSON (app-server · `TransportOwned`) is persisted when the other side first echoes a user message on the live stream — not when the session counts our submission**★ [User]. The user: 「세션 id가 저장되는건 우리가 보내는 시점이 아니고 오는 시점이잖아」 → 「제출하는게 아니고 코덱스가 뱉는거 기준으로 저장하라고 최초 뱉을때가 완전한 타이밍인거잖아. 미세하게 중간에 종료되서 저장안되는건 그냥 초기화 하라고하고」 → (asked about the first echo versus the `thread/start` response) → 「일단 실제 아이디가 생성된 기준이어야지 당연히. 그게 사용자 글을 에코할때잖아.」
   - **The latch is unchanged** — the state machine · compare-and-swap · 「포트는 화신당 많아야 한 번」 (ADR-0226 decisions 2–4) do not change. `offer` is also at today's place (`record_session_id`, which the path writer receives from the handshake response). All that changes is **who calls** `note_submission` in this slot, and **when**.
   - **The calling place = the path reader** — the latch hands out the first-turn port (`FirstTurnSink` = `SessionIdLatch::first_turn_sink` → the existing `note_submission`), the assembly point passes it to `open_spawn`, and the codex app-server branch plugs it into the path paired with `TransportOwned`. The reader calls it once per incarnation (`Reader::witness_first_turn`). The backend decides whether to plug it in — the other backends and modes discard it (ADR-0004).
   - **What counts** [Picked]: any `userMessage` in a live `item/started`·`item/completed` — with or without `clientId` · a mail turn · a turn below the version floor · a late echo after the turn end too (the fact that the text is in the vendor history is the same). Only a line that **states** another thread is excluded. History restoration does not pass through this gate.
   - **Which thread and which lock** [Picked]: it is called holding no lock at all, **after** that line's screen emit — so that what lies beyond the port, a profile disk write, does not hold the bubble. So one profile save per incarnation runs on the codex reader thread (the save discipline of ADR-0071 bounds that time).
   - **Session side** — `count_turn_submission` still follows the submission rejection during user exit (ADR-0226 decision 4), and for `TransportOwned` it returns without counting.
2. ★**So this slot has no 「첫 턴 전에 영속」 — it persists at the echo after the first turn is sent**★ [User]. If the agent or the daemon dies after sending and before the echo, nothing is persisted and the next activation opens a new conversation (no id → Fresh — the entrance of ADR-0226 decision 1 as is). In between, a conversation containing the first message may have formed on the other side, and that conversation cannot be taken over — the outcome the user accepted (「그냥 초기화」). This applies only to the **first** turn of this incarnation: a taking-over incarnation already has a stored value, and later turns have nothing to do with persistence.
3. **Scope = codex JSON only** [User]. Claude (both modes) is unchanged — whether or not it goes on the list, it writes to stdin at once, so submission is the hand-over, and the first input of an incarnation is Direct because no turn is running (if mail opened a turn first, that mail is the first submission — TRD §5-8). So a list item that could be taken back with ✕ in claude stands only after an earlier turn already counted. The codex terminal is also unchanged (ADR-0226 decision 11 — the later of submission and lock reclaim).
4. **Clauses amended** (a stamp on each ADR's status line and related line):
   - **ADR-0226 decision 2** — 「방아쇠는 입력 경계 하나다(백엔드 중립) · 세션의 입력 두 동사가 `send_input` 앞에서 센다」 → there are two counting places: the session's input boundary (claude both modes · codex terminal) and the first echo at the codex JSON path reader. The latch is still one per incarnation. ★The 「codex `writer_loop` 의 `turn/start` 직전」 that that ADR rejected is still rejected (see 「거부한 대안」 below)★ — the reason for that rejection, 「방아쇠가 둘이 된다」, was accepted as a cost in this slot.
   - **ADR-0226 decision 11** — the slots where 「첫 턴 전 영속」 does not hold go from one, the codex terminal, to **two**: the codex terminal (the later one) · codex JSON (the first echo — decision 2).
   - **ADR-0226 「영향 / 불변식」** — ① in the exception description of the new line of CLAUDE.md 「핵심 불변식」 (「세션 id 영속 = 첫 제출 래치 한 지점」), codex JSON is included. ② one paired discipline is added to 「운영 조립점에서 래치는 필수다」 — if a backend that reports `TransportOwned` does not plug the first-turn port into the path, no incarnation can persist an id (every takeover becomes a new conversation without an error — canonical wording = the `FirstTurnSink` type doc). ③ 「ADR-0185 의 크래시 창은 codex 터미널을 뺀 세 칸에서 녹아 없어진다」 in the 「근거」 of that ADR drops to two slots — in codex JSON that window (send → echo) is open again.
   - **End of ADR-0231 decision 9** — 「codex 연결 중 ✕ 는 ADR-0226 쓰레기 부류(대화 없는 id 영속)에 새 입구 하나를 더한다」 → that entrance is closed: text taken back is never echoed, so it leaves no id. Among the stamps that ADR put on ADR-0226, 「연결 중 거둔 첫 입력의 id 영속을 쓰레기 부류에 더함」 is also outdated in the same sense.
   - **ADR-0185 「영향」 Phase 2 requirement** — 「응답으로 받은 sid 는 첫 턴을 허용하기 전에 persist 한다」 → withdrawn for codex JSON (the user's acceptance in decision 2). That requirement speaks of an id issued by the other side (codex), and the codex terminal was already excluded by ADR-0226 decision 11, so it no longer stands in any codex mode (for claude we pick the id ourselves and persist it before the first submission — ADR-0226 decision 1).

## 거부한 대안
The notation follows the ADR-0231 legend — **[User]** = a decision the user answered · **[Delegated]** = a decision or review decision the user entrusted · **[Picked]** = an internal implementation the implementation picked itself.

- **The session counts when it receives** (ADR-0226 decision 2 as is · TRD 8th edition §5-8) [User] — if the first text typed while connecting is taken back with ✕, a zero-turn id is persisted, and the next activation fails trying to take over a conversation that does not exist (context above). It is an entrance first opened when P2c turned codex on as `TransportOwned` — before that there was no text that could be taken back.
- **Persist from the `thread/start` response** (question's B) [User] — every agent that exits without saying a word or takes back its first text leaves a zero-turn id — this reverses ADR-0226 D1 (「저장된 id 가 있다 ⟺ 이어받을 대화가 있다」). The user: 「일단 실제 아이디가 생성된 기준이어야지 당연히. 그게 사용자 글을 에코할때잖아.」
- **Count at hand-over (just before the writer writes `turn/start`·`turn/steer`)** [User] — this is still 「우리가 보내는 시점」 (「세션 id가 저장되는건 우리가 보내는 시점이 아니고 오는 시점이잖아」). One more hand-over-side trigger stands inside the path — exactly the shape ADR-0226 rejected (「거부한 대안」 of that ADR · TRD §5-8).

## 근거
- **User decision** — 2026-09-26 during implementation (TRD §10-1 24 · §10-6 first row · decider = the user). The verbatim utterance is in decision 1 above. There were two questions (A = the first echo · B = the `thread/start` response).
- **Why the first echo is 「대화가 생긴 때」** — a new codex thread has no rollout until the first user message (codex 0.154.0 self-test · that `thread/start` does not create a rollout was reconfirmed by our measurement too — `docs/reference/backend-capabilities.md` §1). So an id before the echo has nothing to take over, and the echo is the signal that the text has entered the vendor history. ★Whether the rollout is already written to disk at the moment of the echo was not measured — likely★.
- **Measured** — P2 local QA full (isolated portable release · `3014247`): confirmed that the session id is saved at the first echo. ★Not measured★: the path of taking over again a thread whose daemon died after persisting at the echo and before that turn ended.
- **Review** — this decision landed within the P2 piece and went through the P2 review together (`/review code deep` · FIX → fix → PASS).

## 영향 / 불변식
- **Landing** — P2 `3014247` (push · CI green). Code anchors: `first_turn_sink` · `witness_first_turn` · `count_turn_submission` also carry `ADR-0233` · the `FirstTurnSink` type · codex `open_spawn` · the manager wiring remain `// ADR-0226 · ADR-0231` — how to find them = `rg "first_turn_sink|witness_first_turn|FirstTurnSink" crates/`.
- ★**Paired discipline — `TransportOwned` ⟺ the first-turn port in the path**★. With only one side, it silently breaks: with `TransportOwned` and no port, neither the session nor the path counts, so no incarnation can persist an id (every next activation is a new conversation — no error), and if the port is plugged in and the session also counts, the ✕-while-connecting entrance comes back to life. What guards it = the `FirstTurnSink` type doc · the ★ comment of codex `open_spawn` · the manager's wiring structure test (whether the spawn path passes `Some(latch.first_turn_sink())` — `rg "first_turn_sink" crates/engram-dashboard-agent/src/manager.rs`).
- **CLAUDE.md 「핵심 불변식」**: the codex JSON exception (persist at the first echo · no persistence if it dies before the echo) was put into the line 「세션 id 영속 = 첫 제출 래치 한 지점」 together with this decision.
- **Accepted remainder** (TRD §5-9): if the vendor changes to stop echoing `userMessage`, persistence stops **silently** (only the latch's 「보류」 info log remains) · the commit runs on the codex reader thread, and in the meantime it does not read the other side's stdout (bounded by one save) · if the port panics on the reader thread, the pump goes `Failed` (release is `panic = "abort"`) · the window between kill and a late commit (the same as the window of `record_session_id`).
- **What breaks if violated**: reviving session-side counting for codex JSON reopens the zero-turn id entrance · moving it to the `thread/start` response or the hand-over time instead of the echo overturns the user decision.
