# ADR-0201: Resume success is decided by a "ready" signal — not a time window

- 상태: 확정 (2026-09-15, basis: user decision + measured against a real codex app-server and a real claude CLI)
- 관련: Amends ADR-0082 (the means of finding out resume failure) · ADR-0200 · ADR-0202 · ADR-0001(kill causality) · ADR-0019(reaper) · ADR-0199(the transport does not kill) · `manager.rs::early_activation_verdict` · `transport/mod.rs::AgentTransport::link_state`

## 맥락

ADR-0082 found out resume failure by an **early-exit window**: if the process exits abnormally within a short time after the resume spawn, it is decided a failure. The reason that means suited claude is that claude's resume is a **process launch** — `claude --resume <sid>` has no response it returns, so there is no way to find out other than watching for a moment.

codex is different in nature. Resume is a **request-response**, so the answer comes at once (measured: a normal round trip about 130ms, a rejection immediately). But because codex inherited that window rule as it was, it became a 「성공」 (“success”) **because the process is still alive even after being rejected**. 「N초 동안 안 죽었다」 (“It did not die for N seconds”) is not evidence of success.

Three rounds of patching this mismatch locally ran, and each time a new defect arose next to it:
1. When we blocked only the fast rejection, the **slow failure** (request deadline 30 seconds vs decision window 3 seconds) stayed as a 「성공」 (“success”) as it was.
2. When we stretched the window to 15 seconds to block that, **even a successful resume took 15 seconds every time** (one re-activation held a tokio worker for 15 seconds, and boot restore took number of profiles × 15 seconds).
3. When we tried to bring the decision forward inside the window, a race branch remained that **produces `Alive` without looking at the connection**.

All three have the same cause — **the means of decision was wrong, and we were adjusting the window length.**

## 결정

**Success = did the agent emit a signal that it is 「입력 받을 준비가 됐다」 (“ready to receive input”).** We decide by a signal, not by time (user decision 2026-09-15).

- The transport **declares the connection state** (`link_state()` — `Establishing`/`Up`/`Down{reason}`). For a backend that declares it, **the decision ends the moment the connection is concluded**: `Up` is success, `Down` is failure with its reason. Neither waits for a window.
- **For a backend that does not declare, nothing changes** (default = does not declare). claude·shell·stdio·codex terminal mode fall here. claude's window is claude's own means, so we keep it — that path is unchanged byte for byte.
- A failure after that is a **separate event**. A turn failing or the process dying after it is ready is seen by the existing path (pump → terminal point → reaper).
- **The reaping is done by the side that judged it a failure.** The transport only closes stdin and reports `Down`, and the manager reaps through the existing 2-verb path. At this time **we do not stamp the user-kill-intent mark** — that would be a false record.

## 거부한 대안

- **Tune the window length (make the request deadline shorter than the decision window)** — we actually did this in round 2, and it produced a regression where the success path takes 15 seconds (independently found by two reviewers, traced through the `manager.rs` call path). A contract that keeps two deadlines tuned to each other is kept only by tests because the files are split, and above all it **does not make success fast.**
- **The transport waits in a bounded way and then reaps directly** — we did this in round 2 and it crossed the line ADR-0199 drew (the transport calling `kill`·`TerminateJobObject`). We removed it.
- **Apply the same rule to claude too** — measured, a ready signal really exists for claude as well (if you put one readiness-check request line into stdin, only a healthy session answers, and a wrong sid never answers and dies. Turn consumption 0, response 0.73~1.67 seconds). **Even so we do not include it in this scope** — the claude path is not broken now, and if we shake what is not broken in the middle of a defect, we cannot tell the source of a regression. We raise it as a separate matter.
- **Use the `system/init` line as claude's ready signal** — **rejected** by measurement. On claude 2.1.269 that line does not appear at startup at all (0 cases for both resume and fresh start, observed for 25 seconds/10 seconds). The version the ground in our code comment names is 2.1.170, and it changed in between.

## 근거

- **Measured (2026-09-15, real codex app-server 0.154.0)**: a rejection comes at once as an error response. A normal round trip about 130ms. There is no reason to wait.
- **Measured (2026-09-15, real claude 2.1.269)**: a failure comes in about 1 second as `No conversation found with session ID: <uuid>` on both stdout and stderr. Success is **completely silent** on the stream, and answering the readiness-check request is the only positive signal.
- **Everything is local** — a claude session is a local file, codex is a local app-server process. The network is used only in a real turn. So there is no structural reason for the response to be slow, and having a large window was itself groundless slack.
- **3 mutation verifications** (revert so `Up` does not end the decision / revert so success clears the failure record / remove the call that reaps on failure) — the corresponding test actually breaks in each case.

## 영향 / 불변식

- The `Alive` decision now reaches **only backends that do not declare a connection**. If codex (app-server) falls to `Alive`, it is a regression.
- One window constant remains as a **give-up backstop** — it is not a policy window. The success path does not wait for it, and the only trigger is 「통로가 아무 판정도 못 냈다」 (“the transport could not produce any decision”). The reason it was kept: if the peer does not read our stdin, `write_all` blocks indefinitely so the transport cannot reach the failure branch, and then the activation call hangs **forever**.
- **A Fresh spawn also goes through this decision** (only for backends that declare a connection). ★When this line was first written it said 「Fresh 는 이 판정을 돌지 않는다 — 미해결」 (“Fresh does not go through this decision — unresolved”), and it was closed the same day★ — the decision did not change, but **the implementation at the time of writing had not caught up.** Both entrances (manual activation · the non-resume branch of boot restore) pass through it.
  - ★**The line below is not something the user gave but an argument that came out of the implementation round**★ (presented by the coder · verified by the reviewer · adopted by the main agent, 2026-09-15): **the axis that splits is not the mode but the link axis** — `thread/start` and `thread/resume` are the same round trip and produce the same failure type, so putting an owner on only one side makes that asymmetry itself the defect. Since the subject of the 「결정」 section above was **the transport** from the start, this is not an extension of the decision but a consequence that follows from it.
  - ★**The title says 「이어받기」 (“resume”), so a session looking for Fresh behavior misses this ADR**★ — the title·filename are history so we leave them, and instead this line is that spot.
- The two new constants (handshake budget 10 seconds · backstop) are **not measured values.** They are judgment values set at about 70 times the measured round trip, and what is kept is not the size but the **order** (budget < backstop), and only that order is kept by a test.
