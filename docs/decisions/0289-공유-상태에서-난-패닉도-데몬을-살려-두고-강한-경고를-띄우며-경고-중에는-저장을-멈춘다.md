# ADR-0289: Keep the daemon alive even on a panic from shared state, show a strong warning, and stop saving during the warning

- 상태: **폐기 (Superseded by ADR-0290)** — the user heard the default policy of mature projects (exit · restart when shared state may be broken) and went back to exit, as is the practice (2026-10-10). ~~확정 (2026-10-10, basis: decisions 1 · 2 · 4 = user decision 2026-10-10 (re-decided after main corrected the peer report) · decision 3 = main's judgment (user delegation 「성숙한 프로그램 관행대로 처리하면 될듯」 2026-10-10))~~
- 관련: Amends ADR-0288 (decision 3, normal exit on a shared-state panic) · ADR-0180 (the strip · popup split — the surface of this warning is decided by the TRD on that eligibility) · research `docs/research/panic-policy-peers-2026-10-08.md` · `docs/research/stop-writes-after-internal-error-2026-10-10.md`

## 맥락

ADR-0288 decision 3 set a panic that occurs while changing shared state to a normal exit. The user decided that after hearing main's report that 「다른 곳은 다 종료한다」, and that report was wrong — the research worker had written herdr separately as 「격리 경계는 없지만 비주 스레드 패닉은 그 스레드만 죽인다」, and main dropped it when merging. The document review brought it back. The corrected picture: the peers that were designed on purpose (zellij · Zed · Alacritty · wezterm) exit, while herdr · atuin · helix, with no design, rely on std default behavior, so on a non-main thread panic only that thread dies and they keep running without a notice (herdr = the daemon peer closest to ours · likely · atuin · helix uncertain). Neither side is clustered enough to call it the practice.

The user's direction (ADR-0288 — 「패닉에 의한 종료는 최대한 하지 않는다」) is unchanged.

## 결정

This changes ADR-0288 decision 3. The rest (decisions 1 · 2 · 4 · the unwind premise · the items passed to the TRD) stays as it is.

1. **The daemon stays alive even on a panic that occurs while changing shared state** — if the panic is in a spawned thread · task, only that thread · task ends and the process and the other agents keep running (the default behavior of an unwind build). The places where the process ends anyway are written in 「영향」.
2. **Show a strong warning** — the daemon panic hook detects the panic, and the shell shows 「내부 오류가 났다 · 작업을 정리하고 재시작하라」 as a warning the user cannot close. The daemon holds the warning state and the shell receives it every time it attaches — so that the warning does not disappear even if only the shell restarts (if it were a one-shot event, after a shell restart only saving would be stopped while the screen shows nothing — it would become the 「조용히 살리기」 that the user rejected).
3. **During the warning, stop the daemon's disk saves** (main's judgment) — so that a half-changed memory state is not carried by a save to overwrite healthy files (`agents.json` · `presets.json` etc.), leave the last known-good saved state. On restart it starts again from that state, and what was changed during the warning is lost (visible to the user — the warning text tells them). The practice is partial (see 「근거」 below).
4. **Implementation order** — first do the unwind switch + strong warning + stopping saves. The pump panic already has code that cleans up only that agent, so it is used as it is. The rest of ADR-0288 decisions 1 · 2 (cleanly cleaning up one request · one agent and ending with a small notice instead of the warning) is done later — if the warning is frequent, then (user 2026-10-10 「그렇게 하던지」).

The following are decided in the TRD — the warning surface (decided by the strip · popup eligibility of ADR-0180) · the warning text · the list of saves to stop · the path that carries the daemon-held warning state to the shell · whether a panic confined by the pump also raises the strong warning. The detailed forks are decided by main following the practice of mature projects and reported (user 2026-10-10).

## 거부한 대안

- **Normal exit (ADR-0288 decision 3)** — the user heard the corrected picture and decided again toward 「일단 살리는 게」. This is the side that fits the user's direction (minimize panic exits).
- **Silently keep alive (herdr · atuin · helix style)** — user: 「조용히 살리는 건 좀 그렇고」. (Main's explanation: the function the dead thread was in charge of is left stopped with no indication.)

## 근거

- The grouping of conclusion 2 of the research report and the placement of herdr · atuin · helix (added by round 2 of the document review — herdr's `Cargo.toml` has no `panic` setting, so its release build is unwind · confirmed in the local clone).
- The practice for stopping saves (decision 3) — `docs/research/stop-writes-after-internal-error-2026-10-10.md` (light · no adversarial review): storage layers block writes after an error and keep running (ext4 `errors=remount-ro` · ZFS `failmode=continue` · RocksDB switching to read-only — the triggers are storage-layer errors such as an I/O failure · a corruption-check mismatch · running out of space). No direct precedent was found that does the same after an app memory bug, and the closest, PostgreSQL, does the opposite and restarts. Stopping saves is a main judgment that moves the shape of the storage layer up to the app layer.
- The means of detecting a panic already exists — the daemon panic hook (`crates/engram-dashboard-daemon/src/lib.rs:133`) is called before unwinding for a panic on any thread (std docs — the hook runs even under abort).

## 영향 / 불변식

- **The places where this decision overturned or made stale parts of ADR-0288** — ADR-0288 is committed and so is not rewritten, so all are written here.
  - Decision 3 (normal exit) — decision 1 of this ADR replaces it.
  - The second rejected alternative (「공유 상태에서 난 패닉도 살려 두고 강한 경고로 재시작을 유도」) — the premise of that rejection (「다들 종료한다」) was main's wrong report, and this ADR adopted that alternative.
  - The deferral of 「셸 사유 고지」 in the third basis — for the warning only, decision 2 of this ADR replaces it (the deferral of the exit time limit · the next-boot restore marking stays as it is).
  - Three lines of 「영향」 tied to decision 3 — 「3 의 경로는 오염된 공유 락에서도 끝까지 가야 한다」 · 「3 은 다음 부팅 복원을 지금처럼 탄다」 · 「3 은 정상 종료 경로를 그대로 쓰므로 T-52 를 함께 본다」.
- **Places where the process ends remain even under unwind** (the TRD confirms the list) — a panic in the main future and the connection accept loop inside it (`crates/engram-dashboard-daemon/src/main.rs:11-15` `#[tokio::main]` → `run()` · `lib.rs:385-387`) · a panic propagated through `std::thread::scope` or `join().expect` (example: `crates/engram-dashboard-agent/src/manager.rs:2946`) · a panic in `Drop` during unwinding · a panic crossing an `extern "system"` callback (these three abort — ADR-0288 decision 4).
- **A signal newly added to the hook does not take locks** — the hook runs on the panicking thread before unwinding. Taking again a lock that thread holds is a deadlock. The signal is left as a lock-free marker, and carrying it to the shell is done by another thread · task. ★The existing hook's `tracing::error!` already takes the log file Mutex★ — there is a documented window where, if it panics while holding that lock, the hook waits on itself (`crates/engram-dashboard-base/src/logging/mod.rs:101,110-115`). The TRD closes this hole before the hook gets heavier.
- **A poisoned shared lock stays and the daemon keeps running** — other threads that open that lock with `.expect` can panic in a chain. Each chained panic also takes the same warning path. Where to cut the chain is decided by the lock poisoning policy (TRD — the item ADR-0288 passed on).
- **Stopping saves during the warning does not bind the shell-side saves** — the shell (settings · screen state) is a separate process, so a daemon panic does not corrupt its memory.
