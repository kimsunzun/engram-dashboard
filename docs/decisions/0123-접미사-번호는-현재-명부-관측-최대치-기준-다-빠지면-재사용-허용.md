# ADR-0123: Suffix numbers are based on the maximum observed in the current registry — reuse is allowed once all are gone

- 상태: 확정 (2026-07-31, basis: user decision — "현재 남아있는 것 기준으로 카운트 세니깐 다 빠지면 0부터 시작하는 게 맞지")
- 관련: Amends ADR-0115 (withdraws the ban on number reuse) · Amends ADR-0120 (also withdraws the "no number reuse" clause that 0120 reconfirmed) · ADR-0116 decision 3 (delete cleanup hook — the safety basis of this decision) · ADR-0119 (single registry entry point — the object of observation) · `crates/engram-dashboard-core/src/agent/manager.rs` (`// ADR-0123` anchor at implementation) · step-log S18.9

## 맥락

ADR-0115 set the automatic suffix number as "monotonically increasing as the **maximum number observed for that name + 1**", and nailed down the **ban on number reuse** as its basis — even if `bob(1)` dies, the next is `bob(2)`. The reason was to prevent the number of a dead entity from coming back to life and being misread as "same number = same entity". ADR-0120 explicitly reconfirmed this clause as **still valid**.

But the two clauses cannot hold together. The "observed maximum" is observed only in the **current registry**, so if `bob(1)` is deleted, the observed maximum drops back to 0 and the next issue becomes `bob(1)`. To really block reuse, one has to hold separately a state the registry cannot give — a per-name high-water record.

The A1 implementation actually went down that road: it added an in-memory high-water map wrapped in a mutex. The review pulled out three costs — ① it is limited to the process lifetime, so a daemon restart resets it anyway and the clause is only half kept ② a decision that breaks a living ADR clause was left only in a code comment, without an ADR ③ the mutex guarding that map holds disk writes and N `canonicalize` syscalls, so it serializes create, rename and spawn globally.

That is, the device meant to keep the clause did not keep it fully and still paid the cost.

## 결정

**1. The number is the maximum observed in the current registry + 1 — that is all.** No separate high-water state is held. When that name series is entirely gone from the registry, the numbers start again from the beginning.

**2. Withdraw the "no number reuse" clause of ADR-0115.** The part where ADR-0120 reconfirmed that clause is withdrawn together with it.

**3. The remaining clauses of ADR-0115 stay valid** — automatic suffix for the same name, notation `이름(1)`, observed maximum + 1 (within the same registry it is still monotonically increasing, so live ones never share a number), epoch replacement is not a rename target. The uniqueness scope of ADR-0120 (globally unique including sleeping profiles) stays too.

**4. The lock that serializes assignment stays.** The high-water map goes away, but the lock's other role — binding observation through commit atomically to prevent **two from taking the same name at the same time** — is a necessary condition of uniqueness, so it stays. It becomes a stateless assignment gate.

## 거부한 대안

- **Persist a counter in `agents.json`** (the main agent's recommendation) — the original clause is kept fully across restarts. A field missing from an existing file is read as a default, so no migration device was needed either. **Rejected by the user**: the judgment that it is not a problem in the first place — "다 빠지면 0부터 시작하는 게 맞지 뭐 문제될 거 있음?" We do not carry one more persistent state to block something that is not a problem.
- **Keep the in-memory high-water (the current A1 implementation)** — it is reset anyway on restart, so it keeps the clause only by half. A "half-kept invariant" is easily misread by the next session as a full guarantee, so it is rather worse. The lock cost comes on top.
- **Leave the number as a tombstone on deletion** — it blocks reuse, but creates a tombstone list that grows forever, and when to clean it becomes a new open item. It is expensive compared with what it gains (preventing number misreading).

## 근거

- User decision (2026-07-31): "현재 남아있는 것 기준으로 카운트 세니깐 다 빠지면 0부터 시작하는 게 맞지 뭐 문제될 거 있음?"
- **The harm path the original clause meant to block is already closed by another device** (confirmed in code): when a profile is deleted, the delete cleanup hook (ADR-0116 decision 3) **terminates the parked letters and open contracts addressed to that name**. So even if the same number is issued again later, **there is no path to inherit the old letters.** What ADR-0115 worried about was not an actual misdelivery but a person's or LLM's misreading of the entity, and when no same-name entry remains there is nothing to misread.
- **The remaining cost is log readability only** — the `bob(1)` in a past log and today's `bob(1)` may be different entities. The user's judgment is that it is not worth carrying one more state.
- **Live ones still do not overlap** — since it is "observed maximum + 1", if `bob` and `bob(2)` are in the registry, the next is `bob(3)`. Reuse happens only when that name series is empty.

## 영향 / 불변식

- **The number is a derived value of the registry, not a separate state** — no counter is stored anywhere. The question "why do numbers go back after a restart?" is answered by this ADR (not a bug).
- **Assignment atomicity is invariant** — observation (registry scan) and commit (registry write) must be inside one critical section. If this is loosened, two concurrent creations receive the same name (violation of ADR-0120 uniqueness).
- **Do not needlessly bring disk I/O or filesystem syscalls into the lock's critical section** — a review finding. Move computation not needed for atomicity outside the lock. **The delivery path does not take this lock** (ADR-0119: a disk write does not block session lookup) — this property must be kept.
- **Note when reading ADR-0115 and 0120** — both documents state "no number reuse", but it was withdrawn by this ADR. The partial-discard stamp on the status line of each body is canonical.
- Unverified (to confirm at implementation): whether the suffix parser distinguishes "no suffix" from "suffix 0" (`bob` vs `bob(0)`) — a defect the review pulled out; if confused, an unused name is misjudged as occupied.
