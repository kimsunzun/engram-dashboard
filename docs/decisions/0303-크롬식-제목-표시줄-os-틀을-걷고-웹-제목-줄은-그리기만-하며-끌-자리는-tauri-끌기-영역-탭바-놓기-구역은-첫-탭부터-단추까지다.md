# ADR-0303: Chrome-style title bar — strip the OS frame, the web title row only draws, the drag spot is the Tauri drag region, and the tab-bar drop zone runs from the first tab to the + button

## 맥락

The OS title bar took a separate row above the tab bar — we decided to have the tab bar stand in the title-bar spot, like Chrome and the Windows 11 Explorer (user decision 2026-10-17 · PRD §1). Going to a borderless window means we have to rebuild what the OS title bar provided: window drag · double click · window buttons · resizing · the inactive look · the minimum window width · the window menu (Alt+Space · right click) · the snap layout menu (ADR-0304).

Tab drag is an OS (HTML5) drag (ADR-0296 · ADR-0297) — whether HTML5 `dragover` · `drop` reach over a drag region was the biggest unverified item after slot docking 4.9 (PRD W2), and which drag-region technique we use decides it (Q5 — the user left it to the main agent · 2026-10-23).

## 결정

1. **The OS frame is stripped in one place, `WebviewEnv::finish`** (TRD §8-1 · ADR-0283) — `decorations(false)` · `shadow(true)` are attached only when platform `window::caption_style()` (main-agent decision M17 — 「단추를 우리가 그리나 · 왼쪽 비울 폭」) answers that the buttons are drawn. main · popouts · warm windows · restored popouts all pass through it — **popouts get the same title bar** (user decision 2026-10-23 — Q2). `decorations` · `shadow` are not written in the main declaration in `tauri.conf.json`. Resizing = the Tauri core's borderless-window resizing.
2. **The title row (web) only draws** — `TitleRow` = the tab bar (tabs · `+`) · the empty draggable spot `GrabGap` (minimum 42 — **separate** from the number marker · main-agent decision M10) · the number marker (ADR-0300 — a drag spot · `pointer-events: none` · `aria-hidden`) · the three window buttons (they call registry commands — ADR-0302). Only the tab bar shrinks, so **tabs shrink first** (R13 — overflow is exactly as in slot docking R24 · the tab width constants stay as they are because the shape does not change · main-agent decision M18). The standby mode (warm window) · loading · boot-failure screens also draw the title row — only the standby mode omits the buttons (TRD §7-1). Size values (main-agent decision M10 · source of truth = `titleRow/metrics.ts`): tab bar 28 · top margin in the normal state `TOP_GAP` 6 (row 34) · top margin when maximized 0 (row 28 — Chromium `TabStrip::CanExtendDragHandle`) · window button width 46 · number marker minimum 28. `TOP_GAP` doubles as the response to folded drag (W13) — its value is set by measurement (S13) and the user confirms the look (main-agent decision M32 · user confirmation needed (QA)).
3. **Window buttons** (R10 · R21) — all three are real buttons (Tab order · Enter · Space · focus outline). The third button: main = 「모든 창 숨기기」 (hide all windows) lucide `EyeOff` · hover = the same pale background as the other buttons (not red) (user decision 2026-10-24 — T3) · popout = 「창 닫기」 (close window) `X` · hover = red. What the buttons do is ADR-0302.
4. **Drag spot = Tauri `data-tauri-drag-region`** (Q5 = ① — main-agent decision M27 · user delegation 2026-10-23 · spike S1) — a valueless attribute on `TitleRow` · the tab-row line · `GrabGap` (the element itself only — child tabs · `+` · buttons do not start a drag). Double click = maximize ↔ restore size (`internal_toggle_maximize` in `drag.js`). The permission `core:window:allow-start-dragging` is added to main · popouts (if missed, it silently fails — W4). **The area around the tabs (empty space in the tab row · the top margin in the normal state) is also a drag spot** (user decision 2026-10-23 — R25). Drag and double click are at the OS gesture layer, so they do not go through the bus (D7).
5. **The window menu (Alt+Space · right click on a drag spot) = accept the native one as is and build nothing** (Q10 = ① — main-agent decision M28 · user delegation 2026-10-23 · 2026-10-24 instruction) — QA records the result (AC23 ①: if it does not appear, write that regression in PRD §2 non-goals and report it to the user). What this technique loses (accepted · reported to the user): the window menu on right click on a drag spot (`drag.js` only looks at the left button — W6) · touch · pen drag (unverified).
6. **The tab-bar zone for a tab drop = horizontally from the left of the first tab to the right end of `+` × vertically the title row (including the top margin)** (user decision 2026-10-26 · T-66 — 「탭이 있는 곳(첫 탭 ~ `+`)만 탭바 구역」 (only where the tabs are, first tab to the plus button, is the tab-bar zone) · it reverses the horizontal extent of main-agent decision M26 and the vertical extent stays) — a drop on the empty space right of `+` · the empty draggable spot · the number marker · the window buttons = a new window (the button is not pressed — an HTML5 drop does not emit `click` · likely · AC12 measures it). If there are no tabs, the zone = `+` only. `stripZone` in `dock/bands.ts` still widens that rectangle up and down by `STRIP_ZONE_PX` — the shell's `strip_zone` · the golden does not change.
   - **D-a** (user decision 2026-10-26) — for a tab dragged in its own tab bar too, once the cursor passes the right end of `+` it is outside the zone: order movement stops and it returns to its place, the remaining tabs are visible (slot docking R15), and releasing there tears it off into a new window.
   - **D-b** (user acceptance 2026-10-26) — the top edge 0..15 px of the canvas below the right of `+`, which became outside the zone, is the outer top band (dropping there splits above the whole layout · preview before the drop) — since what is above it is no longer the tab bar, the lower band is treated as the top edge of the content.
   - The remaining rules of tab drag (order movement · docking to another window · tearing off into a new window · cancelling entirely if the target closes just before the drop) do not change (R14 · ADR-0296 · ADR-0297).
7. **Window facts are received by adding fields to the existing `window:frame` path** (main-agent decision M21) — `focused` (the window's own field pushed with `Focused(b)` = the event value · pull and any other push = platform `is_foreground`) · `caption { buttons, leading_inset, snap_overlay }`. The window's facts are also pushed on a `Focused` event. There is no new event and no new pull invoke.
8. **An inactive window dims its title row** (R11 — default, main agent's proposal) — if `data-window-active="false"` on `TitleRow`, the theme token `--chrome-inactive-fg` applies to tab text · number · button glyphs. **The dimming contrast (dark 3.6:1 · light 3.1:1 · e-ink barely visible) is accepted as is — the token is not fixed** (user decision 2026-10-26).
9. **Minimum window width** (R20 · main-agent decision M11) — the web computes and reports it per window (`report_window_min_width { width, height, seq, epoch }` — the source of truth for the policy constant = the screen · ADR-0227 precedent). The shell's `chrome::ChromeBook` (pure decision) decides and the adapter applies it as the OS minimum size.
   - **The OS minimum size is applied only to a window in the normal (restored-size) state, and while maximized · minimized it is neither applied nor lifted — when it becomes normal (`Resized`), the recorded value is applied** (main-agent decision · U8b 2026-10-26 — replaces TRD version 0.3's 「최대화면 걷는다」 (lift it when maximized)).
   - Applied value = the reported inner size + the invisible border (outer − inner · resolved to logical by scale — U8b review fix).
   - The widening pull (D14) is done **only at open** (a new window · a warm window handed over · boot restore · copy acceptance — open mark `mark_opening` · for main in copy acceptance, lifting before placement `lift_min`), and pulls inside the work area by the visible edge (`fit_min_width` · if the work area is narrower than the window, the visible left end = the left end of the work area). While a human moves the window, only the OS minimum size applies (PRD R20 · AC34 — default, main agent's proposal · review codex ⑩).
   - Report order = `(epoch = 페이지를 읽은 벽시계 ms, seq)` lexicographic (main-agent decision · U8a review 2026-10-25) · report only after receiving the window number (main-agent decision · U8b review 2026-10-26) · send it before the first-paint notice, but with a wait cap of 300 ms so that the first paint is not blocked.
   - The inner size in an old state file is used as is — the first boot window becomes shorter by the frame height (once only · PRD D14 · W5 — accepted).
10. **macOS is not built this time, but not blocked** (R16 · D10 — default, main agent's proposal) — the OS split for the chrome look is in one place, platform `caption_style()`, and the web draws according to the window fact's `caption`. The current code is `{ drawn_buttons: true, leading_inset: 0 }` on every OS.
11. **Of the five carried over from the slot-docking measurements, only ② (dragging around the tab = window move) is done** (user decision 2026-10-23 — 「어차피 탭 남는부분 끌면되니 … 구지 따로 구현할 필요 없음」) — ① the window following when dragging the tab of a popout that has only one tab · ③ dragging main's only tab = window move · ④ a forbidden cursor outside the window · ⑤ the drag image for reordering are not done (R26–R28).

## 거부한 대안

- **Drag region = CSS `app-region: drag`** (Q5 ②) — a tab dropped on it ends up with no receiver: hit testing of an `app-region` area goes to the top-level window (HWND), and tao has attached a file-only `RegisterDragDrop` there (the `no_drop_handler` in our `webview_env` turns off only the webview's own · debug session measurement 2026-10-24 — certain). The advantage this branch gave (the OS provides the window menu · touch · pen) is lost with this. Rejection strength = measured (main-agent decision M27 · user delegation).
- **A window menu we draw** (Q10 ② — a web menu on Alt+Space · right click on a drag spot · items call bus commands) — key interception · menu drawing · accessibility work grows. Rejection strength = descriptive (cost) (main-agent decision M28 · user delegation).
- **Tab-bar zone horizontally = the whole title row** (main-agent decision M26 — the implementation U8a built · a drop on empty space · `+` · the empty draggable spot · number · buttons · top margin = the end of that tab bar · the main agent's recommendation reason = once the OS frame is stripped, it is more predictable for anywhere in the top strip of the window to go into that window — TRD §12-2 「구역」 (zone)) — the user checked Chrome's drop on top of a tab (「크롬은 탭이 있는곳에 있어야 탭으로 가는데」) and decided 「탭이 있는 곳(첫 탭 ~ `+`)만 탭바 구역」 (2026-10-26). ★This does not mean it is the same as Chrome up to the boundary for tearing off one's own tab★ — research `docs/research/slot-docking-chrome-desktop-drag-2026-10-18.md` A5 reads Chrome's tear-off boundary as outside the horizontal extent of the tab-bar drag region (TRD §7-9). Rejected = user decision 2026-10-26.
- **Slot docking's zone horizontal extent (first tab ~ the end of the measured `available` = row end − `+` width — up to the empty space right of `+`)** — narrowed to the first tab ~ the right end of `+` by the same user decision (PRD R14). Rejected = user decision 2026-10-26.
- **Keep one's own tab attached up to the end of `dragAreaWidth` (the measured `available`) — up to the empty space right of `+`** (D-a's rejected alternative) — if it has to go that far to be torn off, it is hard to handle (the user). Rejected = user decision 2026-10-26.
- **Carry the window facts on a new event channel `window:chrome` · new pull invokes (`window_chrome_state` · `window_chrome`)** (TRD version 0.1) — review codex ⑧ pointed out that fields should be added to the existing `WindowFrame` path (subscribe first · pull once · if an event comes after the pull, discard the pull's reply), so it was withdrawn. The TRD gives no other rejection reasons. Rejection strength = weak (review finding only).
- **Substitute the number marker for the minimum empty draggable spot** (PRD R13 left it to the TRD) — Chromium `FrameGrabHandle::CalculatePreferredSize` always leaves 42 (「탭줄이 차도 잡을 자리를 남긴다」 — source copy `horizontal_tab_strip_region_view.cc`) (main-agent decision M10). Rejection strength = code (Chromium source).
- **Shrink the buttons in a narrow window · guarantee only the empty draggable spot and hide even the active tab** (the other branches of PRD D15) — the former is out of line with Windows · Chrome, and the latter hides what you are looking at. Rejection strength = descriptive (default, main agent's proposal). ★2026-10-26 — the latter branch partly came back: which tab stands in the tab spot at the minimum width is decided by the tab-bar overflow rule (user decision Q22 「Chrome 과 같은 한계를 받아들인다」), so an active tab that is not the first tab can be hidden (measured · main-agent decision M35 · PRD AC22) — the empty draggable spot · number · buttons are still guaranteed★
- **Add the title row height at first boot to keep the outer size** (the other branch of PRD D14) — that height differs by scale and OS version, so it was not chosen. Rejection strength = descriptive.
- **Lift the OS minimum size while maximized** (TRD version 0.3 §7-7 「최대화면 걷는다」) — tao 0.35.3's minimum-size setter (`set_min_inner_size`) re-applies the current size (`set_inner_size`), which clears the maximized flag and returns to the restored size with `SW_RESTORE`, and for a hidden window it shows and activates it (source reading — `platform_impl/windows/window.rs` · `window_state.rs` `apply_diff`). The maximized rectangle = the work area is guarded by tao's borderless-window `WM_NCCALCSIZE` (it clips to rcWork — source reading). Rejection strength = code (source reading) (main-agent decision · U8b 2026-10-26).
- **Pass the reported inner size as is as the OS minimum size** (U8b first implementation) — tao's `WM_GETMINMAXINFO` does not add the border to the minimum tracking size of a frameless window, and `WM_NCCALCSIZE` shrinks the inside, so the inner size was dragged smaller than the reported value, by about 16 px in width and about 9 px in height at 100 % (source reading · U8b review). Rejection strength = code.
- **Make the page marker `epoch` of the minimum-width report a random number** (U8a review 2026-10-25) — a late report from the page before reload overwrites the new page's value. Rejection strength = descriptive (code inference).
- **Report the minimum width even before receiving the number (warm standby · loading · boot failure)** (U8b review · 2026-10-26) — for a warm window, the standby report and the report after it is taken in are the same page and cannot be separated by order, so if the in-flight standby report (width 120) first withdraws the open mark recorded when the window is taken in, the window taken in is not widened by the pull. The other branches = let only a page newer than the `epoch` at the time the shell records the mark withdraw it (it cannot block this, because it is the same page) · add a 「대기」 flag to the report (it grows the wire). Rejection strength = code.
- **Fix the token so the dimming contrast is raised** — the user accepted the current contrast as is (2026-10-26). The reason for not fixing it is not recorded. Rejected = user decision (no reason recorded).
- **Only popouts with an OS title bar + a tab bar below it (the current look)** (the other branch of Q2) — the user decided 「같다」 (it fits slot docking R24 「모든 창의 탭바가 같다」, and the premise 「팝아웃과 main 의 창 틀이 같다」 that the new-window spot computation `inset_dip` relies on holds — W5). Rejected = user decision 2026-10-23.
- **Slot-docking measurements ① · ③ · ④ · ⑤** — ① the window following when dragging a popout with only one tab: peers whose window UI is web and whose window · tab model is in a different process (Vivaldi · the Chrome WebUI tab bar) behave the same — a real window that follows the cursor exists only in single-process native implementations (research `docs/research/slot-docking-drag-ownership-peers-2026-10-19.md` A4–A6) · ③ dragging main's only tab = window move: slot docking Q35 as is · ④ forbidden cursor · ⑤ drag image: both arise because WebView2 owns the HTML5 drag, and the three ways to change that (A `DragStarting` · B Chrome-style direct window move · C shell-direct `DoDragDrop`) are all large (research `docs/research/tab-drag-outside-cursor-2026-10-22.md` conclusion). To move the window right away, drag the space left over around the tabs (R25). Rejected = user decision 2026-10-23.

## 영향 / 불변식

- **The title row is the only mouse spot that moves and closes a window in a window whose OS frame is stripped** — the rules for what covers it (notification band · restore modal) = ADR-0306.
- **The web only renders** — the buttons call registry commands and do not call the Tauri window API (ADR-0302 invariant 3). The drag-spot attribute is kept in one place (`titleRow/dragRegion.ts`).
- No OS `cfg` goes in the shell's new code (`chrome/` · `commands/window_ctl.rs`) — the OS split is platform only (`caption_style` · `is_foreground`) (TRD §8-3 — 4f · 4g · 4h unchanged).
- The minimum-size ledger `ChromeBook` is a leaf lock — while held, there is no OS call · emit · other lock. Reading size state · recording in the ledger · the OS setter run as one main-thread job (`lift_min` — U8b review 2).
- ★**Open · unverified (not decisions)**★: S8 — whether maximizing on a screen whose work area is narrower than the minimum size exceeds the work area (if it overflows: ① accept ② shrink the applied minimum size to that monitor's work area ③ a platform `WM_GETMINMAXINFO` subclass — raised to the user) · S13 — folded drag and `TOP_GAP` (whether the cause is Win32 or Blink is unknown · deadlines · thresholds are not changed before the cause is pinned down) · S14 — a drop on top of the top-edge resize child window is lost (main-agent decision M33: after measuring, ① remove that spot from the zone and accept ② a receiver for drops at the platform top-level window level) · S12 — whether the `Focused` event comes on every OS activation change (if it is missed, the dimming is late) · AC13 (tauri#10767 — tab press right after a window drag) · results of Alt+Space · right click · Win+Z · S9 · S10 · S11 · the 6 px jump of a window revived by maximize.
- Anchors — put `// ADR-0303` on `webview_env.rs` (where the frame is stripped) · `chrome/book.rs` · `chrome/mod.rs` (applying the minimum size · the open mark) · platform `window::caption_style` · `titleRow/dragRegion.ts` · the zone computation in `tabStrip/measure.ts` · `state::placement::fit_min_width`.
