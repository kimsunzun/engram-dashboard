# ADR-0297: Slot docking tab drag — block nothing during the drag · at the drop, look up the target again, attach if it exists and do nothing if not

- 상태: 확정 (2026-10-20, 근거: user decision (「상관없어 그냥 예외 최대한 적게 넣으면 됨. 관행에 최대한 맞춰서」 · 「크리티컬한게 아니고 어차피 유저가 다시 하면 되는거라서」) + survey `docs/research/drag-external-events-practice-2026-10-20.md`)
- 관련: Amends ADR-0296 (the scope of the invariant "zero shell calls during the drag") · TRD `docs/process/S21-slot-docking/trd.md` (edition 7 §2-2 · §2-4 · §3-3 · §4-3 · §4-7 · §8-4) · U3 code review (2026-10-20 · FIX)

## 맥락
ADR-0296 set 「끌기 도중 셸 호출 0」 as an invariant, and TRD edition 7 widened it to all the calls the drag *causes*, so that the terminal `resizePty` is deferred during the drag (§4-7 · U3 piece A). The U3 code review (2026-10-20) caught two more calls that leak outside that frame — the window frame lookup right after a window opens (`window_frame`) · the wait timer of the canvas size report. It is a structure where one more exception must be added every time a call unrelated to the drag appears. The user's question — 「끌기 때문에 메인에 있는걸 멈추면 모든 예외사항들을 추가해야되서」. The same review also decided the handling at the drop — the drop is based on the preview (it is not judged again with the coordinates of the moment of the drop — 「유저는 미리보기로 판단하는거잖아」) · a drop on the same window and the same position sends nothing to the shell (「드래그 스타트 안보내는거면 엔드도 보내지마」).

## 결정
1. **Block nothing and defer nothing during the drag.** Shell calls unrelated to the drag (terminal size fitting · window frame lookup · canvas size report · the LLM's tab and window operations and so on) flow as usual during the drag too. The invariant of ADR-0296 is narrowed to **「끌기가 끄는 동안 자기 판정 · 상태를 셸과 맞추지 않는다 — 끌기 명령은 놓을 때(받은 창의 drop · 출처의 dragend) 보낸다」** (its share in preventing the boundary sync defect of the old engine stays).
2. **At the drop, the shell looks up the target the drop pointed at again by id** — the dragged tab · the target tab · the target cell. If it exists, it is applied **to match the current state**, and if not, nothing happens. Example: if the tab-bar position exceeds the list length that shrank in the meantime, it is clamped to the end position · if the target cell was split in the meantime, the tab attaches to that cell as long as that cell remains · if the dragged tab or the target cell is gone, nothing happens.
3. **The rest at the drop**
   - **Decided together (2026-10-20)** — a drop on the same window and the same position does not send even the source dragend (zero shell calls — 「드래그 스타트 안보내는거면 엔드도 보내지마」).
   - **Unchanged** — the drop goes to the target the preview (the last decision) pointed at (user reconfirmation 「유저는 미리보기로 판단하는거잖아」) · a drag that the engine folded makes zero shell calls · during the drag the decision is made by the web alone · restoring the source's original selection after cancel · ignore is the conditional `switch_tab_if` (the shell changes it only when that window's active tab is still the dragged tab — it is not a drop cross-check, it is a device so that it does not overwrite a tab the user or the LLM picked in the meantime).

## 거부한 대안
- **Deferral (TRD edition 7 §4-7 · U3 piece A)** — an exception must be added every time a call unrelated to the drag appears. That the U3 review caught two new gaps outside that frame (the window frame lookup · the canvas report) is the proof. It is not practice either — we found no peer that blocks IPC or saving during the drag, and the deferral precedents are only local risks such as destroying the window that holds the drag (survey conclusion 3). The user: 「모든 예외사항들을 추가해야되서」.
- **Cancel the drag when an event arrives during the drag** — web code has no way to cancel an HTML5 drag in progress (Chromium source — survey B), and the shell (wry window hosting) has no supported way either (Esc injection is unchecked). Peers that end a drag midway end it only when the dragged item or its tab bar (container) changes — Chromium = removal of the dragged tab · adding a tab during a window drag (forced completion) / Lumino = adding · removing a tab in that tab bar · a direction change (abort). No peer ends it on unrelated events such as IPC or a window resize (survey conclusion 2). The user: 「관행에 최대한 맞춰서」.
- **Strict rejection (what was the U1 shell code — the TabBar tab list cross-check · `SeamAt` revision number · active · `expect_window`)** — reject if the state differs from what the drop saw even slightly. It has more exceptions than the mainstream practice (VS Code · dockview · FlexLayout · Zed · Lumino dock — look up again by id and do nothing if absent (dockview throws)), and a slightly off result is not fatal — the user: 「크리티컬한게 아니고 어차피 유저가 다시 하면 되는거라서」.

## 근거
- Survey `docs/research/drag-external-events-practice-2026-10-20.md` (medium · codex adversarial review reflected) — the mainstream practice = leave it alone + look up again by id at the drop and do nothing if absent (dockview throws).
- Our 「끌기 도중 셸 호출 0」 is a design choice inherited from the sync defects of the old Chrome-style engine (the context of ADR-0296). The HTML5 spike measured that invoke · emit are normal during the drag (`docs/research/slot-docking-drag-mechanism-2026-10-16.md` — RDP · 22 times · a small sample). Chromium deliberately runs work inside the DoDragDrop loop.

## 영향 / 불변식
- Web: U3 piece A (`dock/dragActive.ts` · the deferral during the drag in `TerminalSlot`) was removed. Deferral of the window frame and the canvas report is not built. If the canvas size changes during the drag, the receiving window measures again and decides again with the last point (so the preview follows the new size). A drop that arrives when there is no open preview round is decided at that point (the only fallback). `CachedView.layoutRev` in `viewStore` was removed (as in HEAD).
- wire: in `DropTo`, the state fields used in the decision — `TabBar.expect` · `Seam.rev` · `Seam.active` — were dropped; the payload = `TabBar{index}` · `Seam{target, anchor, side, share}` · `NewWindow{…}`. `from` stays (the window that receives the result notification · the window that uses the next active · the source window frame that counts the new window position).
- Shell: the drop is `DockGuard::NONE` — `DockGuard.expect_window` · `TargetExpect::SeamAt` were removed. There is no rejection that compares the state the drop saw — the target check is existence only (`TabNotFound` · `WindowNotFound` · `SlotNotFound` · `SlotNotInTab`) and the geometry checks (`InvalidShare` · `ZeroArea`) are unchanged. The tab-bar position is clamped to the end of the current list. If the dragged tab went to another window in the meantime, a drop onto our webview pulls that tab out of its current window (a drop outside a webview = the accepted gap below · `initial` is the next active only when that tab is in `from` — `DockMove.successor_window` · otherwise shell succession). If the seam target tab was moved, it attaches to that window and gives that window focus.
- Accepted gap: if during the drag the LLM moves the dragged tab to another window or closes it, the source head is detached and the source dragend of that drag does not come — a drop outside our webview does nothing (no new window). The main agent decided this by applying the principle of this decision (minimal exceptions) (user delegation 2026-10-21 · TRD edition 7 §9-2 · §9-5).
- Remaining fat: the revision number `layout_rev` (the shell · the `ViewSnapshot` field) stays with no consumer, and TRD U6 (model fat) removes it together with the old-engine cross-check (`expect_source` · `TargetExpect::{Seam, Tabs}` · `DockError::{SourceChanged, TargetChanged}`).
- TRD edition 7 §2-2 · §2-4 · §3-3 · §4-3 · §4-7 · §8-4 C7 (「끄는 동안 셸 호출 전부 0」 → 「끄는 동안 끌기 명령 0」) were aligned to this decision.
- **Do not revive** — deferral that blocks unrelated calls during the drag · a cross-check that rejects when the state differs from what the drop saw. Both increase exceptions.
