# ADR-0283: Webview data folder = `<root>\webview` · static windows in setup · all windows in the same environment (ADR-0054 extension) · fall back to the default folder if it cannot be written · main creation failure exits

- 상태: 확정 (2026-10-08, basis: TRD `docs/process/S21-storage/trd.md` §4 · §6-5 ⑧ · §10 M4 · §11-2 + user decision 2026-10-07 (M4 (c) — if it cannot be written, fall back to the default place and proceed · no dialog / if main cannot be created, end the app) + P4 implementation `11f8787` · `/review code full` PASS · `/qa full` PASS (GUI measurement — TRD §14-21))
- 관련: ADR-0264(data layout — that decision left `<root>\webview\` as a place only and handed the move to this decision) · ADR-0134 decision 4 (if the data root cannot be written, fail clearly — the fallback of the webview folder lets that path show the reason in a window, see 「근거」 below) · ADR-0135 · ADR-0102(builder manage — ★the 「웹뷰가 setup 전에 invoke 한다」 in its 맥락 no longer holds for static windows · the decision is still correct as is (that ADR's 관련 line)★) · ADR-0225(removing the tree-only window — the tree-side code this decision added is removed at the same time, see 「영향」 below) · ADR-0271(splits `DataLayout` into the daemon's part and the shell's part — `webview_dir()` went to the shell's part `src-tauri/src/discovery/layout.rs` · ADR-0282) · TRD `docs/process/S21-storage/trd.md` §4 · §6-5 · §14-21 · `src-tauri/src/webview_env.rs` · `src-tauri/src/state/placement.rs`(`restore_windows` · `build_static` · `confirm_created`) · `src-tauri/src/lib.rs`(setup ⑧ · the exit code at `RunEvent::Exit`) · `src-tauri/tauri.conf.json` · step-log S21 · Amends ADR-0054 (the place of the constant, the config copy and the triple sync point; the range of environment options the invariant covers) · Amends ADR-0137 (the description of the WebView2 data folder cost in the impact)

## 맥락

- **The webview data folder was outside the data root.** The window's WebView2 user data folder was the Tauri default place (`%LOCALAPPDATA%\<identifier>`). ADR-0264 left `<root>\webview\` as a place and handed the move to a following decision.
- **Settings alone cannot point at that folder (checked against the Tauri 2.11.3 source — TRD §4).** The builder's `data_directory(PathBuf)` uses an absolute path as is, but the config key `dataDirectory` accepts only a relative path and attaches it under `LocalData/<label>/` (`webview/mod.rs:392-418`). So the windows declared by the config (main · agent-tree) also have to go through the Rust builder.
- **Windows in the same folder must have the same environment options (ADR-0054).** A window that breaks this has `build()` return `Ok` but has no OS window (a ghost window). The browser arguments were written separately in three places, the config (two windows) and the Rust constant (`popout.rs`), and were being matched by hand. Once the folder is moved, the folder itself also becomes an environment option that has to match.
- **Tauri created the config windows ahead of the user setup** (`app.rs:2521-2531`). So the saved main placement was applied after the window had come up at the config placement, and in a `--hidden` boot the main was shown and then hidden (TRD §6-5 ⑧ · §4).
- Two questions remain — when the webview folder cannot be written (TRD §10 M4) · when a window could not be created.

## 결정

1. **Webview data folder = `<root>\webview`** (the shell's `DataLayout::webview_dir()` — `src-tauri/src/discovery/layout.rs`). Convert it to an absolute path, check it, and pass the same value — the data root may be a relative path through `ENGRAM_DATA_DIR`.
2. **The shell creates the static windows in setup.** The two windows of `tauri.conf.json` keep only their declaration and have `"create": false`, so Tauri does not create them (marked 2026-10-08 — the tree window no longer exists after the ADR-0225 implementation `ab332a1`). Boot setup ⑧ (after the run marker ⑤ of the state boot — TRD §6-5 I6) creates them with `WebviewWindowBuilder::from_config` and applies the saved placement · size · maximized state at creation. In a `--hidden` boot, main is created hidden from the start. A window created hidden does not take focus (`focused(false)`).
3. **All windows in the same environment — an extension of ADR-0054.** All code that creates windows (static windows · runtime pop-outs) goes through one finishing function, `WebviewEnv::finish` (`src-tauri/src/webview_env.rs`), and its values come from one instance per shell. What the finish attaches = the data folder (when one is set) · the browser arguments · browser extensions off · the default scrollbar look — the four that wry puts into the WebView2 environment. The canonical source of the browser arguments is the one Rust constant `WEBVIEW2_BROWSER_ARGS`, and the config does not carry that value (`additionalBrowserArgs` was removed).
4. **If it cannot be written, fall back to the default folder (user decision 2026-10-07 — M4 (c)).** The write check is done **once per process** before creating windows, and every window receives that answer. If it cannot be written, the data folder is not passed, so it proceeds with the Tauri default place (`%LOCALAPPDATA%\<identifier>`) and leaves a warn log (the reason only — the path goes in the log field). There is no dialog.
5. **If main cannot be created, end the app · the tree window continues (user decision 2026-10-07).** main failure = error log → marker → app exit request → `RunEvent::Exit` writes the screen state `Final`, releases the shell run lock, and then calls `std::process::exit(1)`. A tree window failure is logged and it continues without that window (marked 2026-10-08 — the tree window no longer exists after the ADR-0225 implementation `ab332a1`). A silent failure where `build()` returns `Ok` but the runtime could not create the window (no WebView2 runtime, etc.) is checked with one getter call right after creation and counted as a failure (`confirm_created`).

## 거부한 대안

- **The config key `dataDirectory`** — it accepts only a relative path and is attached under `LocalData/<label>/` (Tauri source — 「맥락」 above). It cannot point at `<root>\webview`. Rejection ground = code.
- **Tauri 2.12 `appDirectoriesOverride`** — the upgrade comes first (it is not in 2.11.3 — TRD §11-1). Rejection ground = code (not in the current version).
- **Keep `%LOCALAPPDATA%`** — it is outside the data root, so it breaks the portable layout (ADR-0134), and worktrees with the same identifier share localStorage (TRD §11-2).
- **Automatically delete the old folder (`%LOCALAPPDATA%\com.engram.dashboard[.dev]`)** — user decision U1 (the user is the only user, so old values are not handled — TRD §10 F4) · another worktree with the same identifier · an old build may be using it, and if it is in use it is only half deleted (TRD §4).
- **A native dialog and then exit if it cannot be written** (the first half of M4 (a) — answered that way once on the same day and then changed) — user decision 2026-10-07: the storage policy 「멈추지 않고 진행」 (TRD §6 D8). If the whole data root cannot be written, the existing path of ADR-0134 decision 4 · ADR-0135 shows the reason in the window after it comes up — if the app exits, that window is gone too.
- **Document network-share data folders as unsupported for the time being (amending ADR-0134 decision 3)** — user decision 2026-10-07: the shared folder in ADR-0134 decision 3 is a problem of exclusion between daemons, and the webview folder is on the client side, so it is unrelated. ADR-0134 decision 3 is not amended.
- **Continue with the tray alone even if main cannot be created** — user decision 2026-10-07 (chose exit). The user's reason: 「이상한 것들 에러 나면 강제 종료가 맞지」. If it keeps running, a process holding only the single-instance lock and `state.lock` remains without a window, and launching again only hands off to that process and nothing happens (to the user it is a frozen app — raised in review) · before P4, the only case that ended with a Tauri setup panic was when window creation returned `Err`, and a silent runtime failure (`build()` is `Ok`) kept running without a window — the process holding only the lock just mentioned is exactly that.

## 근거

- **Source cross-check (Tauri 2.11.3 · tao 0.35.3 · tauri-runtime-wry 2.11.3 · wry 0.55.1):** `data_directory` uses an absolute path as is and uses `LocalData/<identifier>` only when none is specified (`webview/webview_window.rs:1024` · `manager/webview.rs:534-545`) · the `create` flag (`tauri-utils-2.9.3/src/config.rs:1936`) · `from_config` (`webview_window.rs:150`) · the four options that wry `create_environment` puts in the environment (the head of `webview_env.rs`) · an exit request ends with `ControlFlow::Exit` (tao = code 0), so exit code 1 is issued directly in `RunEvent::Exit` (`lib.rs`).
- **Silent-failure measurement (QA 2026-10-07):** if the runtime is hidden with `WEBVIEW2_BROWSER_EXECUTABLE_FOLDER`, tauri-runtime-wry only logs the window creation failure (`WebviewRuntimeNotInstalled`) and `build()` returns `Ok`. After the check was added = exit code 1 · `clean_exit:true` · launching again right away is normal. In a release build, Tauri's own error dialog 「Could not find the WebView2 Runtime.」 appears before that (not ours — tauri-runtime-wry 2.11.3 `src/lib.rs:4757-4765` · `cfg(all(not(debug_assertions), windows))`) [source reading — QA was only the debug build].
- **Focus measurement (QA 2026-10-07):** in 3/3 visible boots before the fix, the hidden tree window took the foreground · after `focused(false)` main is the foreground. That the cause is wry's `MoveFocus` at the end of creation is source reading (the `build_static` comment in `placement.rs` — [미검]).
- **Gates:** `/review code full` (2 reviewers · 3 re-fixes) PASS · `/qa full` PASS — workspace · shell target · vitest · 11 GUI items + mixed DPI · re-measurement A–F (numbers = TRD §14-21 · step-log).
- **The cost of M4 (c) (attached to the user decision — TRD §10 M4):** a fallback run shares the webview folder across worktrees with the same identifier — there is no value read from that folder now (TRD §4 「잃는 것」).

## 영향 / 불변식

- **All code that creates windows goes through `WebviewEnv::finish`** — a window that skips it has an environment that differs from the other windows and becomes a ghost window (ADR-0054). The pop-out builder creates no window and raises an error if that instance is not managed (`build_window` in `commands/popout.rs`). The `// ADR-0054` anchors = the head of `webview_env.rs` · `build_static` in `placement.rs`.
- **Do not write environment options in the config again · do not remove `"create": false`** — tests guard it: `config_windows_leave_every_environment_option_at_the_default` in `webview_env.rs` · `every_config_window_is_left_to_the_boot_and_the_boot_knows_them_all` in `placement.rs`. The config ↔ constant sync problem that ADR-0054 left as a 「후속 하드닝」 disappeared as the config stopped carrying that value.
- **The folder decision is once per process** — if it is asked again per window, the windows of one process would receive different folders (`OnceLock` · do not attach `Clone` to `WebviewEnv` — the comment in that file).
- **Static window creation is setup ⑧, after the run marker (⑤)** — even if the app dies while creating windows, the next boot reads it as abnormal (TRD §6-5 I6). Thanks to this order, the restore state the window first pulls is the value decided by boot stage ⑥.
- **Known limits (not fixed — TRD §14-21):** ① if only the tree window fails silently, that dead registration stays in Tauri's window table and the visibility decision answers 「보인다」 (the reviewers' judgments differed · in practice it is hard to reach, and ADR-0225 removes the tree window — accepted) ★(marked 2026-10-08) the ADR-0225 implementation (`ab332a1`) removed the tree window so there is no target — the 「트리 창은 계속」 branch of decision 5 disappeared with it★ ② in a visible boot with a saved maximized main, it is shown at normal size for about 0.5–0.8 seconds and then maximized (the same as L3) ③ the focus order of a runtime-restored pop-out is unchanged · the pop-out of a `--hidden` boot still shows briefly and then hides (F13 · ★2026-10-08 new observation (ADR-0225 GUI QA · winq probe): between that show and hide, the restored pop-out takes the foreground for about 0.3 seconds — P4 measured only the show-and-hide and did not measure the foreground, so that it was already so before this change is likely★) ④ whether WebView2 accepts a user data folder on a network share has not been checked.
- **Overlap with ADR-0225:** this decision added the tree-window code (and its guard test) and it is removed together when ADR-0225 is implemented. The canonical source of the list = the single 「함께 바꿀 곳」 in ADR-0225 — it is not copied here. ★(marked 2026-10-08) Removed — ADR-0225 「구현 기록」 (`ab332a1`). The `focused(false)` for a window created hidden is now only for the main of a `--hidden` boot (decision 2)★.
