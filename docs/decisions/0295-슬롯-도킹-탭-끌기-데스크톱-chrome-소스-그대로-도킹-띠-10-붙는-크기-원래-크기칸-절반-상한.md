# ADR-0295: Slot docking tab drag = the desktop Chrome source as is · docking strip 10% · attached size = original size (capped at half the cell)

- 상태: 확정 (2026-10-18, 근거: user decision (after the 9c mouse measurement failed — 「크롬 보고 좀 참고하라니깐 드럽게 다르게 구현하네」 · 「내가 크롬 소스보고 똑같이 하라고 했잖아」 · attached size 「최대크기를 반으로 하고 기존 크기를 최대한 따르는게」 · 「붙이는 쪽 기준으로 사이즈를 맞추면됨」) + survey `docs/research/slot-docking-chrome-desktop-drag-2026-10-18.md` (checked against the Chromium main originals · one codex adversarial review)) · 부분 폐기 by ADR-0296 (decisions 1 and 2, the drag method) · 부분 폐기 by ADR-0298 (the tab separator size and the close button size in decision 1)
- 관련: PRD `docs/process/S21-slot-docking/prd.md` (edition 4.8 reflects this decision — R2 · R3 · R3a · R7 · R12 · AC2–AC4 · AC25 and so on) · TRD `docs/process/S21-slot-docking/trd.md` · code audit `docs/refactoring/slot-docking-drag-code-audit-2026-10-18.md` · earlier survey `docs/research/slot-docking-chrome-tab-drag-2026-10-17.md` (this decision discards its recommendation A) · `docs/research/slot-docking-drag-mechanism-2026-10-16.md` · ADR-0266 (OS branches only inside `platform`) · ADR-0227 (split renderer · strip geometry `src-tauri/src/dock/hit.rs`) · T-65 (slot docking LLM commands) · T-66 (title bar) · Amended by ADR-0296 (decisions 1 and 2, the drag method) · Amends ADR-0168 (only the top corner radius, the separator rule and the inactive tab token of decision 5) · Amended by ADR-0298 (the tab separator size and the close button size in decision 1)

## 맥락

When the user measured slot docking 9c (Chrome WebUI tab-bar style reordering on top of HTML5 drag and drop · uncommitted) with the mouse, the defects came from one root — the OS drag image followed even drags inside the tab bar · a dotted box next to the cursor (the OLE drag cursor) · a gauge over other windows (waiting before attaching) · dragging a one-tab window · Esc did not return to the original place · a transition at drop time · the X moved on consecutive closes · the active tab was hard to tell apart · the docking area was wide, so pulling a tab out to a new window meant going to the middle of the cell.

The cause is that the earlier survey took 「Chrome」 to be Chrome's **touch-mode WebUI tab bar** (`chrome/browser/resources/tab_strip/` · removed from main — HTML5 drag and drop). The **desktop Chrome (Views tab bar)** the user meant does not use OS drag and drop — it moves the real tab with mouse capture, and on release makes the real new window follow the cursor through the Windows window-move loop, and attaches with no timer when it touches another window's tab bar (the survey's A table). The user said that, because the tab bar will keep doubling as the title bar (T-66), that interlock must be designed too.

## 결정

1. **The tab drag is carried over from the desktop Chrome source as is** — both the mechanism and the constants (the survey's A table · Chromium main 2026-10-18): mouse capture · drag start 10 px (Euclidean) · inside the tab bar = the real tab follows the cursor and neighboring tabs step aside in 200 ms · the order changes when it moves beyond `16 × 탭 폭 ÷ 표준 폭` · active at the moment of the press · outside 15 px above or below the tab bar = detach → at once a real new window is created under the cursor and made to follow through the Windows window-move loop (`WM_SYSCOMMAND SC_MOVE|0x0002` · end = `WM_CANCELMODE`) · no drag image · touching another window's tab bar (±15 px) attaches with no timer, and the order moves in that window before the drop · Esc = back to the original window · original place · selection · maximized state · if there is only one tab, the window itself goes into the move loop without detaching · consecutive closes = the width is fixed until the mouse leaves the tab bar (40 below · 60 px slack on the new-tab side · the mouse has no timer) · active tab shape (top corner 10 · bottom curve 12 · separator rule) · empty tab bar = window drag area (including 6 px above inactive tabs when not maximized).
2. **If the Chrome method turns out to be technically impossible somewhere in this stack, do not invent an alternative** — stop and take the evidence (spike measurement) to the user. That is why the spike (the survey's 「P 의 스파이크」 S1–S6) runs before implementation.
3. **Docking (splitting cells) is our own feature that Chrome does not have, so it stays** — when the detached window is dragged over a cell of our window, it is in attach mode only while the cursor is in the **10% strip** at the cell edge (the same form as the 0.1 of VS Code's editor `editorDropTarget.ts`), and on drop it splits that cell and attaches, and the dragged window disappears. Dropped outside the strip (the middle of a cell · the desktop and so on), the dragged window stays as a new window as it is — the 「칸 가운데 = 새 창」 target is gone.
4. **Attached size = the original size of the dragged tab, capped at half the attached cell** — only the length in the split direction counts (left/right = width · up/down = height) · the other direction is fitted to the attached cell · the preview paints this resulting size (the 10% strip and the preview are different things). It replaces PRD R7's 「새것 1/3 고정」 (`DOCK_NEW_SHARE`).

## 거부한 대안

- **Keep HTML5 drag and drop + Chrome WebUI tab bar style (the earlier survey's recommendation A · the 9c implementation)** — failed in the user's mouse measurement (2026-10-18): the OS drag image · dotted cursor · waiting before attaching · dragging a one-tab window all come from that method (HTML5 can set the drag image only at the start and cannot change the OS drag cursor — the survey's conclusion · the 9c measurement).
- **Keep the current method + fix only what can be fixed (survey option R)** — the user did not choose it (2026-10-18): of the defects above, the image · dotted box · gauge · one-tab window would remain.
- **Move the detached window by the shell with `SetWindowPos` without the OS move loop (survey P2 · proposed by the codex review)** — rejected by the user (「크롬 소스보고 똑같이」): it differs from Chrome and cannot receive Windows snap during the drag.
- **Pointer only inside the tab bar · OS drag on detach (survey Q)** — the web side alone has no API to start an OS drag in the middle of a gesture (conclusion 2 of `slot-docking-chrome-tab-drag-2026-10-17.md`).
- **Fixed attached size 1/3 (PRD R7)** — the user: if you attach something that was kept small (for example usage), it should stay small.
- **「칸 가운데 = 새 창」 · strip = preview size (the current `hit.rs` `landing_rect`)** — the attaching area was wide, so pulling a tab out to a new window meant going to the middle (the user's measurement) · every peer (VS Code · dockview · FlexLayout · Lumino) uses middle = merge, and there is no precedent for 「가운데 = 새 창」 (survey C).

## 영향 / 불변식

- **The 9c drag code is not committed** — backup `.claude/handoff/attachments/slot-docking-9c-before-chrome-redesign-2026-10-18.patch`. What to keep (geometry · layout application · Chrome reporting · tab width) and what to remove (most of the shell ledger `book.rs` · the `dockDrag.ts` event handling · `dragImage.ts` · the OLE reporting wire) is canonical in the code audit document.
- **Window move loop start · end · hooks go in purpose-specific functions in `platform`** (ADR-0266 — OS branches only there). macOS is surveyed separately (`performWindowDragWithEvent` not surveyed).
- **LLM path** — the results of the new gestures (move between windows · order · split · detach) go through the same application path as the T-65 commands (`layout::apply`) (CLAUDE.md 「LLM-우선 제어」).
- **Occlusion (old open item 1) — closed:** the dragged window can cover the area under the cursor and hide the strip and preview of the window below, so the guide and preview are drawn in a **separate always-on-top · transparent · click-through · non-activating window** (peer practice — AvalonDock · Qt ADS · KDDockWidgets · survey D · user confirmation 2026-10-18 「ㅇㅇ 쭉쭉 진행해」). Whether Tauri can make such a window is spike S7.
- PRD edition 4.8 changed R3 · R7 · AC2–AC4 · AC25 (Esc = the place it was shown) and so on by this decision. Any key other than Esc = ends as a drop (Chrome A8) is also part of decision 1.
