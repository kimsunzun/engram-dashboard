# ADR-0295: 슬롯 도킹 탭 끌기 = 데스크톱 Chrome 소스 그대로 · 도킹 띠 10% · 붙는 크기 = 원래 크기(칸 절반 상한)

## 맥락

슬롯 도킹 9c(HTML5 끌어 놓기 위에 Chrome WebUI 탭바 꼴 순서 이동 · 미커밋)를 사용자가 마우스로 실측하자 결함이 한 뿌리에서 나왔다 — 탭바 안 끌기에도 OS 끌기 그림이 따라옴 · 커서 옆 점선 네모(OLE 끌기 커서) · 다른 창 위 게이지(붙기 전 기다림) · 탭 하나 창의 끌기 · Esc 가 원래 자리로 안 돌아감 · 놓을 때 전환 · 연달아 닫기에서 X 가 움직임 · 활성 탭 구별 약함 · 도킹 영역이 넓어 새 창으로 빼려면 칸 가운데까지 가야 함.

원인은 앞선 조사가 「Chrome」을 Chrome 의 **터치 모드 WebUI 탭바**(`chrome/browser/resources/tab_strip/` · main 에서 지워짐 — HTML5 끌어 놓기)로 잡은 것이다. 사용자가 뜻한 **데스크톱 Chrome(Views 탭바)은 OS 끌어 놓기를 쓰지 않는다** — 마우스 캡처로 진짜 탭을 움직이고, 떼면 진짜 새 창을 Windows 창 이동 루프로 커서에 따라오게 하며, 다른 창 탭바에 닿으면 타이머 없이 붙는다(조사 A 표). 사용자는 앞으로도 탭바가 제목 표시줄을 겸하게 할 것이라(T-66) 그 맞물림도 함께 설계해야 한다고 했다.

## 결정

1. **탭 끌기는 데스크톱 Chrome 소스 그대로 옮긴다** — 메커니즘과 상수 모두(조사 A 표 · Chromium main 2026-10-18): 마우스 캡처 · 끌기 시작 10 px(유클리드) · 탭바 안 = 진짜 탭이 커서를 따라가고 옆 탭이 200 ms 로 비켜남 · 순서는 `16 × 탭 폭 ÷ 표준 폭` 넘게 움직일 때 바뀜 · 누르는 순간 활성 · 탭바 위아래 15 px 밖 = 떼기 → 그 즉시 진짜 새 창을 커서 밑에 만들어 Windows 창 이동 루프(`WM_SYSCOMMAND SC_MOVE|0x0002` · 끝 = `WM_CANCELMODE`)로 따라오게 함 · 끌기 그림 없음 · 다른 창 탭바(±15 px)에 닿으면 타이머 없이 붙고 놓기 전에 그 창에서 순서 이동 · Esc = 원래 창 · 원래 자리 · 선택 · 최대화로 되돌림 · 탭 하나뿐이면 떼지 않고 창 자체를 이동 루프로 · 연달아 닫기 = 마우스가 탭바를 떠날 때까지 폭 고정(아래 40 · 새 탭 쪽 60 px 여유 · 마우스는 타이머 없음) · 활성 탭 모양(위 모서리 10 · 아래 휘어짐 12 · 구분선 규칙) · 빈 탭바 = 창 끌기 영역(최대화가 아닐 때 비활성 탭 위 6 px 포함).
2. **이 스택에서 Chrome 방식이 기술적으로 안 되는 곳이 나오면 대안을 지어내지 않는다** — 멈추고 근거(스파이크 실측)를 들고 사용자에게 올린다. 그래서 구현 전에 스파이크(조사 「P 의 스파이크」 S1–S6)를 먼저 돈다.
3. **도킹(칸 나누기)은 Chrome 에 없는 우리 기능이라 남긴다** — 떼어진 창을 끌고 우리 창의 칸 위로 가면, 칸 가장자리 **10% 띠**(VS Code 편집기 `editorDropTarget.ts` 의 0.1 과 같은 꼴)에 커서가 있을 때만 붙기 모드이고, 놓으면 그 칸을 나눠 붙고 끌던 창은 사라진다. 띠 밖(칸 가운데 · 바탕화면 등)에서 놓으면 끌던 창이 그대로 새 창으로 남는다 — 「칸 가운데 = 새 창」 표적은 없어진다.
4. **붙는 크기 = 끌어온 탭의 원래 크기, 붙는 칸의 절반 상한** — 나누는 방향의 길이만 따진다(좌우 = 폭 · 위아래 = 높이) · 다른 방향은 붙는 칸에 맞춘다 · 미리보기는 이 결과 크기를 칠한다(띠 10% 와 미리보기는 다른 것). PRD R7 의 「새것 1/3 고정」(`DOCK_NEW_SHARE`)을 대신한다.

## 거부한 대안

- **HTML5 끌어 놓기 유지 + Chrome WebUI 탭바 꼴(앞선 조사 추천 A · 9c 구현)** — 사용자 마우스 실측(2026-10-18)에서 불합격: OS 끌기 그림 · 점선 커서 · 붙기 전 기다림 · 탭 하나 창 끌기가 그 수단에서 나온다(HTML5 는 끌기 그림을 시작 때만 정할 수 있고 OS 끌기 커서를 바꿀 수 없다 — 조사 결론 · 9c 실측).
- **지금 방식 유지 + 고칠 수 있는 것만(조사 선택지 R)** — 사용자가 고르지 않았다(2026-10-18): 위 결함 중 그림 · 점선 · 게이지 · 탭 하나 창이 남는다.
- **떼어진 창을 OS 이동 루프 없이 셸이 `SetWindowPos` 로 옮기기(조사 P2 · codex 리뷰가 제안)** — 사용자 기각(「크롬 소스보고 똑같이」): Chrome 과 다르고 끌기 도중 Windows 스냅을 못 받는다.
- **탭바 안만 포인터 · 떼면 OS 끌기(조사 Q)** — 웹 쪽만으로 제스처 도중 OS 끌기를 시작할 API 가 없다(`slot-docking-chrome-tab-drag-2026-10-17.md` 결론 2).
- **붙는 크기 1/3 고정(PRD R7)** — 사용자: 작게 둔 것(예: 사용량)을 붙이면 그대로 작아야 한다.
- **「칸 가운데 = 새 창」 · 띠 = 미리보기 크기(지금 `hit.rs` `landing_rect`)** — 붙는 영역이 넓어 새 창으로 빼려면 가운데까지 가야 했다(사용자 실측) · 피어(VS Code · dockview · FlexLayout · Lumino) 모두 가운데 = 합치기이고 「가운데 = 새 창」 선례 없음(조사 C).

## 영향 / 불변식

- **9c 끌기 코드는 커밋하지 않는다** — 백업 `.claude/handoff/attachments/slot-docking-9c-before-chrome-redesign-2026-10-18.patch`. 살릴 것(기하 · 레이아웃 적용 · 크롬 보고 · 탭 폭)과 걷을 것(셸 장부 `book.rs` 대부분 · `dockDrag.ts` 사건 처리 · `dragImage.ts` · OLE 보고 wire)은 코드 점검 문서가 정본.
- **창 이동 루프 시작 · 끝 · 훅은 `platform` 의 목적 함수로** 둔다(ADR-0266 — OS 분기는 거기만). macOS 는 따로 조사(`performWindowDragWithEvent` 미조사).
- **LLM 경로** — 새 제스처의 결과(창 사이 이동 · 순서 · 분할 · 떼기)는 T-65 명령과 같은 적용 경로(`layout::apply`)를 지나게 한다(CLAUDE.md 「LLM-우선 제어」).
- **가림(옛 미결 1) — 닫음:** 끌던 창이 커서 밑을 덮어 밑 창의 띠 · 미리보기를 가릴 수 있어, 안내 · 미리보기는 **따로 된 항상 위 · 투명 · 클릭 통과 · 비활성 창**에 그린다(피어 관행 — AvalonDock · Qt ADS · KDDockWidgets · 조사 D · 사용자 확인 2026-10-18 「ㅇㅇ 쭉쭉 진행해」). Tauri 로 그 창이 되는지는 스파이크 S7.
- PRD 4.8판이 R3 · R7 · AC2–AC4 · AC25(Esc = 보이던 자리) 등을 이 결정으로 바꿨다. Esc 밖의 다른 키 = 놓은 것으로 끝(Chrome A8)도 결정 1 에 든다.
