# ADR-0125: A send drains the queue to the end in its own turn (synchronous drain · delivered restored)

- 상태: 확정 (2026-08-01, basis: user decision — "그냥 하나 발송될때 그 루틴에서 리턴되기전에 큐에 있으면 다 보내고 리턴 ok 하면 안됨? 그 턴에 다, 처리 가능하잖아", "이게 맞지 않음?") · 부분 폐기 by ADR-0142 (the overlap guard's single-axis description becomes two axes)
- 관련: **Supersedes ADR-0124** (all-queue + asynchronous flush lane — giving up `delivered` was overpayment) · ADR-0121 (the adoption of strict FIFO as the rejected alternative was done by 0124 and this ADR keeps it) · ADR-0116 (decision 7, idle gate skipping, stays · **the modal-widget risk at the injection moment is already "known and accepted"** — it is not a risk this decision newly creates) · ADR-0104 (`delivered` = the actual injection moment — this ADR revives that meaning in the response too) · ADR-0113 (turn state promoted to shared — a follow-up slice where the owner of injection timing moves to the agent layer. It layers on without conflict) · ADR-0111 (per-recipient failure rows · partial progress — stays) · `crates/engram-dashboard-messaging/src/service.rs` (`// ADR-0125` anchor at implementation) · implementation contract = `docs/process/S18-messaging-v1/spec/messaging-v1-spec.md` §3·§5·§6 · Amended by ADR-0142 (the overlap guard's single-axis description becomes two axes)

## 맥락

ADR-0124 was confirmed a few hours earlier the same day and **not one line of code was started.** 0124 abolished the direct-send shortcut and structurally removed the ordering problem, but at the cost of **giving up `delivered` in the send response** — every normal send converges to `pending`, and the actual injection is done later by the asynchronous flush lane.

0124 paid that cost for one reason only. It did not want to touch the **existing design that detached the flush from the sending thread** (`with_flush_trigger` — so the batch write does not run on the MCP/HTTP request thread), and then loading and injection are at different moments, so when the send returns it does not yet know whether it was delivered. 0124 put this plan ("the sending thread finishes the flush synchronously and answers `delivered`") under **rejected alternatives** and wrote "the sender pays for someone else's backlog" as the reason for rejection.

**The user's remark (2026-08-01):** "그냥 하나 발송될 때 그 루틴에서 리턴되기 전에 큐에 있으면 다 보내고 리턴 ok 하면 안 됨? 그 턴에 다 처리 가능하잖아."

Looking at the reason for rejection again, **the exchange rate was bad.** The mailbox cap is 100 per recipient and the message rate is at human-conversation level, so the drain the sender takes on is bounded and short. For that cost **the order and `delivered` can be had together**, yet 0124 got only the order and gave up `delivered`.

## 결정

**1. A send loads behind the queue, then in the same call drains that recipient's queue from the front as far as it can be put in, and returns.**

Loading is inside the lock; the drain (injection) is outside the lock. Since it takes from the front, **older items go out first and this letter goes after them** — the order holds by loading order. Devices like seat reservation and direct-send joining decisions are not needed (a gain 0124 obtained and this ADR keeps).

**2. The response vocabulary keeps the 3 kinds `delivered` · `pending` · `failed`.**

- **`delivered`** — in this call's drain, that letter was actually injected (= written to stdin and fully accepted).
- **`pending`** — it could not be put in now and stayed in the queue. Three reasons: **the recipient is mid-turn** (backend with a turn signal) · **the recipient is asleep** · **injection failed**. It goes out at the next occasion (appearance · idle transition · the drain of a later send · doorbell).
- **`failed`** — decided *before* queue loading. **4 kinds kept**: no such name (`RECIPIENT_NOT_FOUND`) · ambiguous same name (`RECIPIENT_AMBIGUOUS`) · mailbox exceeded (`MAILBOX_FULL`) · reply contract exceeded (`REQUEST_CAPACITY`).

**"Everything handled in that turn" does not always hold** — the three `pending` reasons above are the exceptions. So the answer is not "all ok" but **a mixture of what went in and what could not**. In real use the recipient is usually idle, so most fall to `delivered`.

**3. The asynchronous flush lane stays.** The occasions on which it runs — appearance (spawn · restore · epoch replacement) · turn end (idle transition) · doorbell — are unchanged. The synchronous drain is **running that lane once on the sending thread**, not a second path — the injection code is one set.

**4. The ledger does not change.** `delivered` keeps being recorded at the **actual injection moment** (ADR-0104). With a synchronous drain, loading and injection are in the same call so a ledger row can start as `delivered`, and if it could not be put in it stays `pending` — the "initial state uniformly `pending`" that 0124 would have created and its consequences (the `delivered`-starting row of the transition table becoming unreachable · every send temporarily exposed in the argument-less `messages`) are **discarded together.**

## 거부한 대안

- **ADR-0124 (all-queue loading + asynchronous flush lane)** — the object this ADR discards. It gets the order but **loses `delivered`.** The means for the sending agent to know "did it actually arrive" disappears, and to fill that loss one would end up building an asynchronous delivery receipt anew (next item). The only motive was not to touch the existing design (`with_flush_trigger`), and the value that design wanted to protect (the sender not paying for someone else's backlog) is small at this scale.
- **Keep the seat reservation (2026-07-31 wip `76ea887`)** — the order is guaranteed but the burst is serialized so 100 concurrent sends become 1 `delivered` + 99 `pending`. **The self-contradiction of a device built to protect `delivered` removing 99% of `delivered` in a burst.** Moreover direct send, seat and joining decisions referenced each other and the code kept swelling (the user's remark: "간단하게 구현하면 되는데 왜 이렇게 복잡하게 끌고 갔냐").
- **Asynchronous delivery receipt (XMPP XEP-0184 style — the send answers only acceptance and a separate signal comes at delivery)** — closest to industry practice. Reason for rejection = **unnecessary in this design.** The synchronous drain already gives that answer in the same call. A receipt is the solution for systems where send and delivery are separated in principle (brokers · federation), and we own the recipient process directly, so there is no reason to separate. If remote or external agents attach and ownership breaks, we add it non-destructively then (v2 candidate).
- **Limit the drain to this one letter (do not touch the older ones ahead in the queue)** — the sender's burden is minimal but **the order breaks** (mine goes out before the older ones). This is exactly the behavior ADR-0121 decision 2 forbade, so it does not hold.

## 근거

- **User decision (2026-08-01)** — the original text is in the status line. The user directly rebutted 0124's reason for rejection ("그 턴에 다 처리 가능하잖아"), and the main agent re-examined it and confirmed that the reason for rejection was weak.
- **The basis for the rejection reason ("the sender pays for someone else's backlog") being small at this scale:** the mailbox message lane cap = 100 per recipient (a spec §5 policy constant), message rate = human-conversation level (the same as the basis on which the module header justifies the single lock). **The quantity is unverified** — the actual latency is measured at implementation (§영향 unverified ① below).
- **The mid-turn injection risk is not something this decision creates.** "At the injection moment it may be swallowed by the other side's modal widget or input editing" was **already recorded as "known and accepted" by ADR-0116 decision 7** and is hung in spec §7 as a measured item. Pushing everything in at once does not increase the exposure either — a batch goes out in one go anyway. **The user's observation (2026-08-01): the party that handles this problem is the agent management layer, not mail** ("에이전트 매니저 쪽에서 푸시하기 전에 대기하든가"), and this is the direction **ADR-0113** already settled (turn state = general agent state → promoted to shared in core, mail only subscribes. Start = a separate slice after the send overhaul). This ADR does not conflict with that promotion — only the place that asks the gate needs to change.
- **The real value of `delivered` (which 0124 underestimated):** 0124 wrote "there is no path along which the sending agent would act differently on seeing `delivered`/`pending`". But **the difference between the two is not a behavior branch but observation reliability** — in a world where only `pending` comes back, "it did not go because the other side was asleep" and "it went" can never be told apart, and that distinction is first-class information when a person reads the log.

## 영향 / 불변식

- **The injection code is one set.** The synchronous drain and the asynchronous flush are just two occasions calling **the same drain routine**. Making send-specific injection code separately violates this decision, and the "two paths" problem 0124 removed recurs.
- **The drain runs outside the lock.** Loading is inside the lock, the drain after the lock is released. `DeliveryPort` is not called while holding the lock (module header §single lock · the spirit of ADR-0006).
- **★Invariant (do not remove) — the flush duplicate-entry guard is a premise of this decision.★** The drain entry withdraws if that recipient's in-flight remains, and leaves the doorbell as a deferred marker (`service.rs` — `in_flight_len(recipient) > 0` → `deferred_flush` → break). **In the synchronous drain this guard becomes more important** — if two sending threads drain the same recipient at the same time, the batches overlap and the order inverts. The letter of the side that withdrew is carried out in the winner's batch so nothing is lost, and **the side that withdrew does not know whether its own letter was injected, so it answers `pending`** (a conservative answer — it may in fact have been delivered. A false `pending` is safer than a false `delivered`).
- **The 4 `failed` kinds keep being decided before queue loading** — no such name · ambiguous same name · mailbox exceeded · `REQUEST_CAPACITY`. If `REQUEST_CAPACITY` is deferred to later, **an untracked request gets delivered** (canonical = spec §3 item 5).
- **The surface where the cap applies widens** — in the direct-send era `can_admit` ran only in the parking branch, so with an empty queue + idle even the 101st was simply injected (mailbox.rs made it explicit as "that is not a cap violation"). With everything loaded, **every send passes the cap gate** → `MAILBOX_FULL` increasing is **a design consequence, not a regression.**
- **Idle gate skipping stays** (ADR-0116 decision 7) — the class without a turn signal is not asked about busy. It is applied at drain time.
- **Tests that flip are moved, not deleted** — the seat-reservation assertion (`a_direct_injection_holds_a_seat_...`) vanishes, but the **"no isolation" (`parked_len == 0`)** that its closing sealed must necessarily be provided again in the new structure. If the assertion is deleted, the seal is lost.
- **Unverified (must be confirmed at implementation):** ① the actual latency the synchronous drain adds to the sender's response time (**maximum batch = cap−1 parked + this 1 = a cap-sized drain** is the worst. ★The first-edition wording "the worst case where the cap is full" was disproved by measurement (2026-08-04, step-log S18.15) — the point where the cap is **full** is a rejection at the entry, so the drain is **0 items** and it is the **minimum**, not the worst★) ② whether, in concurrent sends, the side that withdrew answers `pending` and the letter goes out in the winner's batch (loss 0 · order kept) ③ whether failed-injection items are not trapped until the next occasion (no isolation) ④ whether, in an `@all` send with many recipients, the per-recipient drains do not delay each other.
