# ADR-0080: LLM control surface architecture — Bash→engram-ctl→daemon WS (direct to backend) + daemon opaque-relay→app ViewManager (UI)

- 상태: **폐기 (Superseded by ADR-0085)** — the control channel ingress pivoted from the engram-ctl CLI (token, WS) to an in-band output marker (M3) (security, speed). This ADR stayed at proposed (not confirmed) and its headline mechanism was replaced. **Note: discarded = limited to the engram-ctl ingress** — the UI opaque-relay and the two authority domains defined below survive through ADR-0081 (confirmed). ~~제안 (2026-07-13, basis: `/research` medium + two Codex adversarial reviews + claude-code-guide grounding — confirmed if it passes `/review prd`)~~
- 관련: CLAUDE.md §5(LLM-우선 제어) · ADR-0014 (daemon CLI-via-Bash direction) · ADR-0035 (layout authority = src-tauri ViewManager) · ADR-0068 (slot spatial vocabulary) · ADR-0011 (agentClient control surface) · PRD `docs/process/S17-llm-control-surface/spec/prd.md` · step-log S17 · spike `scripts/engram.mjs` · daemon WS auth `crates/engram-dashboard-daemon/src/ws.rs`

## 맥락
§5 requires "every feature is LLM-controllable", and in the release build that collapses. The control handles (`window.__engramLayout`, `__engramCmd`) live inside the webview, but the only bridge by which an external process (the spawned child claude) can reach them is `scripts/cdp.mjs` (a dev-only remote debugging port), and the release `tauri.conf.json` has no such port, so it dies entirely. The child claude is a separate process and cannot reach `window.*` directly. That is, it is the gap §5 foretold: "the temporary path until the formal control surface" (CDP) disappears in release.

At the same time, authority is split across two processes: backend (spawn/kill/list/preset) = the daemon (`AgentManager`, which already has a WS server), UI/layout (split/tab/focus) = the app (`ViewManager`, ADR-0035 — the daemon is ignorant of View and slot). For an external LLM to control the UI, the command must reach the app.

## 결정
**Invocation:** `child claude의 Bash 도구 → 컴파일 Rust `engram-ctl`(protocol crate 공유) → 데몬 WS(토큰 auth)` (that is, the child claude's Bash tool → compiled Rust engram-ctl (shares the protocol crate) → daemon WS (token auth)). The model acts only through text/tool-use, and here the Bash tool is that structured action. `engram-ctl` is the WS client (portfile discovery, authentication, command vocabulary), and Bash only executes that program (the way `curl` does HTTP).

**Two authority domains + routing:**
- Backend = direct to the daemon (`engram-ctl → 데몬 WS → AgentManager` (engram-ctl → daemon WS → AgentManager)). Portable to PC and mobile.
- UI = **daemon opaque-relay**. The daemon forwards the UI payload to the target app connection **without interpreting it** → the app applies it through **the same ViewManager path** as a local Tauri command → the result is collected by correlation. The daemon stays ignorant of the UI (ADR-0035 preserved), and only its role expands to "an opaque broker between two clients (CLI↔app)".

**Command model (two layers):** a domain layer (agent, preset — identical on all devices) + a presentation layer (layout — semantic operations on the logical view-tree, no coordinates, ADR-0068 spatial vocabulary + a per-device capability gate). `list_commands` returns the commands available on the current device.

**Observation and results:** a shell cannot catch a stream across turns, so finite primitives (`wait --until`, `events poll --cursor`, `output tail --after-seq`) + an honest JSON envelope (`{v,ok,requestId,result}`/`{error{code,retryable}}`). UI success is confirmed only after the ViewManager applies it.

**Provisioning:** when the daemon (parent) spawns a child, it hands down the control channel (an ephemeral env overlay — `profile.env` is forbidden because agents.json stores plaintext). MVP authentication = **the current single master token** (full authority) — per-child scope is a non-goal (below).

**Scope (MVP):** the exposed targets = **only the commands whose behavior already exists in the authority**. No new backend/`ViewManager` operations are built, only a release-safe command path — backend = every wire command of `AgentManager` (spawn/kill/interrupt/write/resize/list + input lease + profile/preset CRUD + snapshot, `manager.rs`/`connection_core.rs`), UI = every command of `ViewManager` (tabs/windows/slots/content/popout + read queries get_view/list_tabs/list_windows/snapshot, `layout/manager.rs`/`commands/layout.rs`). Of the §5 gaps, those not attached to an authority (theme change 〔explicitly declined in v1〕 · render mode override · layout save/restore 〔unimplemented〕 · tree navigation 〔read-only〕) are explicitly deferred (new wiring needed). **MVP premise = a single client (app) instance:** assume the UI-authority app connected to the daemon is one — targeting multiple app instances is outside the MVP (deferred). Thanks to this premise the target of a UI command is uniquely determined, and the opaque-relay routing below needs no app selection logic.

## 거부한 대안
- **MCP over HTTP** — the daemon talks to its own local child claude that it spawned, so the HTTP+JSON-RPC+handshake ceremony is excessive (parent and child are on the same machine). The token concern was weakened by Claude Code's tool-search defer by default, but for a single local app MCP's interoperability value is wasted. **Local stdio MCP is deferred, not rejected** — reconsider if the command catalog grows or "narrow tool permissions/typed schemas instead of a broad Bash" becomes important (the cross-family review's counterargument recorded).
- **chat-text parsing** (claude spits commands out as conversation text and a watcher parses them) — fragile and hallucination-prone. Tool-use is the formal structured channel, so text parsing is inferior.
- **CDP-in-release** (opening the remote debugging port in the release build too) — a security exposure where any local process can attach and run arbitrary JS/invoke + an extension of the temporary path we originally meant to remove. (The Chrome 136 hardening basis is Chrome's and is unverified on WebView2.)
- **An app-owned separate endpoint for the UI** (the app opens its own control server) — a second endpoint, with discovery and auth duplicated. The daemon opaque-relay reuses the existing daemon↔app WS, so the cost is lower, and on mobile the remote daemon reaching the phone app has this as its only path, so the relay also wins on portability.

**Per-child permission scope (R7) authorization placement — deferred (non-goal, a risk accepted knowingly), analysis preserved.** A single local PC = a single trust boundary, so the MVP does no fine-grained authorization at all and allows the current single master token full authority — here we **accept knowingly** the risk that one prompt-injected child can kill sibling agents, write, and operate the whole UI (child↔child lateral movement) with the shared master token ("single PC" covers only the outer boundary and not an internally contaminated child; premise = local, trusted content). Reintroduction = mobile/remote, details and user reconfirmation = `docs/tracking.md` T-11 (note of 2026-07-14). Placements examined: **(lean, the likely future answer)** the daemon only **stamps identity** with a per-child token (keeping UI-semantic ignorance = ADR-0035 preserved), and authorization (scope) is by the UI-authority owner `ViewManager` — consistent with the opaque-relay. **(a, rejection candidate)** a coarse daemon gate in parallel = authorization is spread across the daemon and the client. **(b, rejection candidate)** a direct client endpoint = unsuitable for mobile (the phone app's only path is through the remote daemon). If the MVP routing is kept as relay-through-daemon (child→daemon→`ViewManager`), lean/(a) stay open and only (b) is foreclosed, which is harmless — ADR-0080 already has that shape.

## 근거
- OSS survey (`/research` medium): CLI→daemon-socket (tmux ISC/zellij MIT) is a mature pattern, and MCP's real worth is "interop between parties that do not know each other", so it is excessive for a single in-house app.
- Codex adversarial review (repo measurement): the daemon WS already has token auth (`ws.rs`), `engram.mjs` proves a release-safe path, but `AgentCommand` has no layout commands and `ViewManager` is in src-tauri so the UI needs a separate path — resolved by the opaque-relay. A compiled Rust CLI is better than a Node spike as a release artifact.
- claude-code-guide grounding: the model acts only through text/tool-use, and the stock claude tools = built-in (Bash)+MCP. That is, there is no "native tool without MCP", and the non-MCP structured action = the Bash tool.

## 영향 / 불변식
- **The daemon stays UI-ignorant (ADR-0035):** the relay must be an opaque passage that does not parse the UI payload. Putting a `LayoutNode` command into `AgentCommand` breaks this boundary — the UI envelope is a separate opaque type the daemon does not know. **The R7 deferral cleans this boundary:** since the MVP does no fine-grained authorization at all, the contradiction "daemon opaque-relay (UI-semantic ignorance) ↔ per-child scope" disappears (= the `/review prd` BLOCK resolved by deferral, T-11).
- **Execute at the authority owner:** backend = the daemon, UI = the app ViewManager. Whether a human click (invoke) or the LLM (engram-ctl→WS→relay), it converges on the same handle at the end (§5 single control surface).
- **No coordinates exposed:** presentation commands are logical-tree semantic operations only. Putting pixels or window numbers into the command vocabulary breaks device portability (ADR-0068).
- **release gate:** no dependence on CDP/devtools. `engram-ctl` depends only on the daemon WS (which survives regardless of build).
- **Non-goal (deferred, a risk accepted knowingly):** per-child permission scope (R7) = `docs/tracking.md` T-11 (reintroduced at the mobile/remote stage, user reconfirmation 2026-07-14). MVP = the current single master token with full authority — accept the child↔child lateral movement risk of an injected child and keep it deferred (premise = local, trusted content).
- **The concurrency mechanism = TRD-level, resolved on top of the ViewManager single authority:** requestId dedup (at-most-once), result correlation, timeout reconciliation, and so on are TRD-level problems, not architecture decisions, and are solved on top of the sequential application by the `ViewManager` single authority (ADR-0035) — since the single authority fixes the order, no distributed consensus is needed.
- **Undecided (TRD):** portfile ACL, event journal, the exposed vocabulary and discovery of the command catalog (the target operations are fixed by "Scope (MVP)" above), broker routing (app identity/lease, multiple windows, offline), stale-ref semantics (addressing closed/killed views and slots), R6 robustness (idempotency, partial-application atomicity, ordering/concurrency, mixed-version negotiation). Security judgment is outside this ADR's scope.
