# ADR-0157: Unknown fields in command arguments — reject at the entrance, be tolerant in the wiring

- 상태: 확정 (2026-08-14, basis: user decision — surfaced in round 3 of S20 Step 1 adversarial review)
- 관련: TRD S20 §4-③ (field-addition rule) · §6 Step 2 (the behavior-unchanged promise) · `crates/engram-dashboard-daemon/src/control/agent.rs` (current entrance defense) · ADR-0156 (the daemon does not parse arguments or help) · step-log S20.3

## 맥락

TRD §4-③ pinned down that no `deny_unknown_fields` is put on any argument struct. The reason is **version difference** — if an unknown field sent by a new caller breaks an old owner, additive evolution does not hold, so the old owner ignores unknown fields and runs with the old meaning.

But the daemon's current `/control` entrance does the exact opposite: it **rejects unknown arguments** (`guard` + `reject_unknown_fields` in `control/agent.rs`). Today `engram agent new --cwd C:/x --target alpha` is bounced with "new does not use: target". This is the only net that catches a human or LLM mistyping a name.

When Step 2 replaces the verb match with a command table, that net disappears. The same call creates the agent while quietly ignoring `target` and **reports success**. The caller receives a success response and does not know something different from the intent happened. That is, the 「동작 불변」 (behavior unchanged) promised by TRD §6 Step 2 does not hold as written. Round 3 of the adversarial review surfaced that this conflict is **recorded in no document**.

**[Pointer correction 2026-08-16 — decision unchanged]** The two functions `guard` and `reject_unknown_fields`, which the paragraph above and the 「거부한 대안」 below really point to, were **deleted in S20 Step 2 slice 3** (that wall itself was replaced by a table lookup) — do not look for them by those names. What bears the same rejection now is `CommandTable::check_args` (`crates/engram-dashboard-command/src/table.rs`), and the `/control/agent` entrance calls it (`handle_agent` in `crates/engram-dashboard-daemon/src/control/agent.rs`). **Only the location of the real thing changed, and this ADR's decision and basis are unchanged** — the requirement in 「영향 / 불변식」 below (when the table is swapped, the rejection must stand with it) was met by that call.

## 결정

**Split 「모르는 칸」 (unknown fields) by origin — one rule is divided into two layers.**

- **At the entrance a human or LLM types into (the CLI and the LLM calling surface), reject fields not in the declaration.** The rejection list is not newly made but is **derived per verb from the set of declared attributes** that `CommandSpec` already holds.
- **In internal wiring (the wire between hops), ignore as TRD §4-③ says and run with the old meaning.** Additive evolution holds as it is in this layer.

## 거부한 대안

- **Put `deny_unknown_fields` on the argument struct** — version difference breaks. A field that is in fact new from a new caller hard-fails the old owner and additive evolution does not hold (exactly the original basis on which TRD §4-③ forbade this form). Typos are caught but evolution dies.
- **Apply the pure additive rule to all layers (ignore unknown fields everywhere)** — it loses the typo defense that really exists today. Measured: `guard` and `reject_unknown_fields` in `control/agent.rs` are rejecting now, and TRD §6 Step 2 promised unchanged behavior. This option breaks that promise, and what is lost is not 「오류 메시지 하나」 (one error message) but **a malfunction reported as success**.
- **The daemon pulls the arguments apart and checks them** — a hard-constraint violation. The daemon parses neither arguments nor the help string (ADR-0156). It looks only at the name on the outer cover.

## 근거

「모르는 칸」 had two origins but there was one rule. **A field sent by a caller with a newer version is rightly ignored, and a field a human or LLM mistyped is rightly rejected.** If one rule tries to cover both, one of them breaks either way — reject everything and evolution dies, ignore everything and typos are reported as success.

If the boundary is drawn by **layer**, both stand. The entrance is where what a human or LLM has just typed arrives, so it is safe to read 「모르는 칸 = 오타」 (unknown field = typo), and the wiring between hops is where counterparts with a version split arrive, so tolerance is right.

The basis for derivation already exists too — since `CommandSpec` holds the set of declared attributes, there is no need to make new data for the rejection list. Not making a second, hand-maintained list is the practical reason this method was chosen.

## 영향 / 불변식

- **The rejection list is derived from the declaration — no hand-maintained copy is made.** If a copy is made, every time a verb is added two places diverge, and the diverged side quietly lets things through.
- **The daemon still does not pull arguments apart** (the ADR-0156 hard constraint unchanged). Derivation and checking are the work of the side that owns the table.
- **TRD §4-③ is not discarded** — the application scope of that rule is only narrowed to 「내부 배선」 (internal wiring). Putting `deny_unknown_fields` on an argument struct is still forbidden.
- **When Step 2 replaces the verb match with a table, this rejection must stand with it for the 「동작 불변」 of TRD §6 Step 2 to hold.** If only the table is swapped and the rejection is not set up, that promise is deployed broken.
- **The boundary rule (TRD §4-③) is still alive** — an extension that adds a field and changes behavioral meaning must be a new name, not a field addition.
