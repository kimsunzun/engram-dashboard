# ADR-0206: The connection receive loop hands commands off instead of holding them — input writes are carried by a dedicated per-agent writer

- 상태: 확정 (2026-09-18, basis: OSS survey + 3-person adversarial review (deep) + measured)
- 관련: `crates/engram-dashboard-net/src/ws.rs` · `crates/engram-dashboard-daemon/src/connection_core.rs` · `crates/engram-dashboard-agent/src/transport/input_queue.rs` · `crates/engram-dashboard-agent/src/manager.rs:70` · survey `docs/research/connection-dispatch-concurrency-survey-2026-09-17.md` · symptom record `docs/refactoring/socket-head-of-line-blocking-2026-09-17.md` · ADR-0001 · ADR-0012 · ADR-0038 · ADR-0082 · ADR-0088 · ADR-0129 · ADR-0190 · ADR-0201

## 맥락

The per-connection WS receive loop read the next frame **only after the handler for one frame had completed**. And the activation handler waited for the entire agent handshake on the spot — measured typical about 2.2 seconds, upper bound 15 seconds (`LINK_RESOLUTION_BACKSTOP`, `crates/engram-dashboard-agent/src/manager.rs:70`).

In the meantime **all other commands** that the same client sent piled up unread in the daemon's receive buffer — input bound for **other** agents, a kill, yet another activation. Output is a separate write task and was unaffected, so the symptom was "the screen is alive but typing does not register".

The connection was not dropped. Since the 15-second upper bound is below the keepalive idle timeout of 50 seconds (`crates/engram-dashboard-net/src/ws.rs:128`), there was a 35-second margin — meaning the stall did not even turn into a reconnect, and just sat quietly stopped.

The second axis was the transport. The `send_input` of PTY·stdio did an **OS write on the caller thread**, and shared the writer by wrapping it in a `Mutex`.

## 결정

We stop running command handling serially in the connection receive loop. There are two interlocking pieces.

**1. Daemon.** The per-connection WS receive loop decodes a frame, **hands it off, and reads the next at once.** A bounded queue feeds a **single consumer task**, and that consumer runs the handlers **in arrival order**. `Kill` is carried on a separate small lane so that cancellation is not starved. When saturated, it **rejects the frame out loud** — returning an error carrying its own `request_id`, neither dropping it nor quietly piling it up. The long-running activation variants are detached from the ordered lane.

**2. Transport.** The PTY·stdio backends get a **per-agent bounded input queue + a dedicated writer thread that owns the writer.** `send_input` puts into the queue and returns — it does not do the OS write on the caller thread. The codex backend is already in this shape, so we did not touch it.

## 거부한 대안

- **(a) Just leave it serial** — none of the peers does it this way (7 in the survey). The cost is an input stall the user feels, of seconds, on every activation.
- **(b) Spawn a task per frame (unbounded)** — it loses arrival order, and **no layer below can restore the order** (there is no layer that carries a wire sequence number). It also loses the admission bound the serial loop happened to provide, and the risks the review enumerated multiply as they are.
- **(c) A per-entity (agent) dispatch queue map** — we considered it seriously, and it is the shape Orleans·Akka use. But that is a form for **thousands of distributed entities**. zellij left a comment on the cost of a per-key map — adding or removing a key halts everything ("everything is halted, that's life"). We do not need it at our scale, and the ordering guarantee it would buy **has already been bought by the per-agent writer of piece 2.**
- **(d) Ticket / deferred completion** — reply "accepted" at once and deliver the result later by `request_id`. It removes the stall without touching the loop, but it changes **what ADR-0201 decided** (the activation response = the decision that it is ready) and hands every client a two-stage state machine.
- **(e) tmux-style park-and-resume** — keep one lane but park the item and **return** from the loop. The most conservative and a real precedent, but **the waiting itself remains** — it does not remove the queue but moves it.

## 근거

1. **The end-to-end argument addresses this question directly.** Saltzer/Reed/Clark 1984 has a subsection "Guaranteeing FIFO message delivery", and there it says that to guarantee order, "an independent mechanism at a **higher level than the communication subsystem**" must control the order of actions. Low-level order guarantees are "justified only as performance enhancements". ★We state the limit honestly★ — what that paper says is that **transport FIFO alone is not enough**, not that serialization at the dispatch layer can never be a means of correctness. The paper itself calls this argument "not an absolute rule". What it settles for us is one thing: **the place where we were serializing was low-level, and there it was spending performance instead of buying correctness.**
2. **7 peers in the survey, 0 with the same shape as ours.** wezterm mux (`dispatch.rs` — returns straight to reading after `process_one`) · rust-analyzer (4-way dispatch by request kind) · jsonrpsee (spawn per frame) · zellij (the route thread forwards to the subsystem channel) · paseo (does not wait for dispatch) · herdr (a thread per connection) · tmux (deliberately serial, but **parks the item and returns from the loop** — does not hold). ★The two corrections forced by the adversarial review★: zellij **waits synchronously for completion** on some actions (a 1-second timeout, unbounded for some), and herdr blocks per connection so there is no multiplexing — neither qualifies for the "hand off at once" cell.
3. **Input order is a per-PTY property, and every peer owns it per session, not per connection.** wezterm = a per-pane `Mutex<Box<dyn Write + Send>>` · zellij = one writer thread behind a per-`terminal_id` queue · tmux = a per-pane bufferevent · herdr = a per-PTY actor. ★No project wrote "order" as the reason for separating the writer★ — the reason zellij states is deadlock ("some programs get deadlocked if you write into their STDIN while reading from their STDOUT").
4. ★**The `portable-pty 0.8.1` we pinned itself forces single ownership**★ — checked against the registry cache, not a clone. `take_writer` can be called only once (the doc block at `src/lib.rs:98`, whose sentence is line 101 "It is invalid to take the writer more than once"), unix makes the second call bail (`src/unix.rs:321`), and Windows ConPTY rejects it (`src/win/conpty.rs:106`). The `Box<dyn Write + Send>` it returns is `Send` but **not `Sync`.** Our way of sharing it by wrapping it in a `Mutex` was using it against this contract, and **a form where one thread owns it matches the contract.**
5. **RFC 9112 §9.3.2 does not exempt us.** ★The discarded draft of our survey wrote "exempt", which was wrong and the review caught it★. §9.2 explains that HTTP/1.1 depends on response arrival order because it has no request identifier, but that does not lift §9.3.2's "parallel only for safe methods" for us. What carries over to us is narrower: what that constraint binds is the **response delivery order**, not the processing order. LSP 3.17 states the same split explicitly — it allows parallel execution under the condition "as long as this reordering doesn't affect the correctness of the responses", and gives `definition` vs `rename` as its own counterexample.
6. **We counted our dispatch directly.** Of the 30 `AgentCommand` variants, those that truly need arrival-order handling are **only 5 bundles** — stdin writes going to one agent · lease acquire/release before input · subscribe/unsubscribe of one agent · command register vs update · `StopDaemon` goes last. And **all five are fast.** The slow ones do not require order. So once the blocking write is taken out of the lane, **a single order-keeping consumer costs almost nothing.**

**Measured**

- Re-activation typical about 2.2 seconds. The hard upper bound of a blocked activation is `LINK_RESOLUTION_BACKSTOP` = 15 seconds, which is lower than the keepalive idle 50 seconds, so the stall has never killed a connection (35-second margin).
- ★A ConPTY write stuck on a child that never reads stdin is released by `shutdown()`★ — within about 15ms with `ERROR_BROKEN_PIPE`, 4 runs. This closes the leak concern that code alone could not answer (a thread + handle per dead agent) — since `take_writer` moves the handle out, the master drop does not close it, and `ClosePseudoConsole` works indirectly. A regression test with no ignore marker pins this fact.
- We reproduced the submit-pacing regression against a **healthy child** — a 512KiB body took 500.37ms to drain, and the submit CR merged into the read of the body's tail (the last read 778 bytes).

## 영향 / 불변식

- ★The meaning of `Ok` from `send_input` has changed from "wrote" to "received".★ The submit path (mail delivery) waits for the actual write and buys back the old meaning — an ordinary `WriteStdin` does not buy it. **ADR-0088's delivery observation record stands on this distinction** — the doc of `WriteOutcome` now spells out that per-verb split (`crates/engram-dashboard-agent/src/types.rs`).
- **The worst-case mail delivery latency grew to about 10.5 seconds** (body confirmation 5 seconds + pacing 0.5 seconds + submit confirmation 5 seconds). The flush timeout **does not cancel bytes that have entered the queue**, so a timeout + retry can become a double delivery — we set the budget generously because a duplicate is worse than a retry.
- On one connection, `WriteStdin(X)` right after `SpawnProfile(X)` now **races** (since we detached activation). The `Spawned`/`Error` ack is the ordering contract. (The double-spawn race of ADR-0082 is a separate matter that existed before and is not closed here.)
- **Two new bounds were created and both are policy** — the inbound frame queue, the per-agent input byte cap. Both **reject out loud and do not drop** — a quiet drop is a family that `docs/process/S21-codex-backend/trd-phase2a.md` already rejected, and the discipline ADR-0190 set ("do not drop input — return it as an error when the cap is exceeded or readiness ends up failing") applies as is.
- **There are 3 OS threads per agent** (writer·watcher·pump). What binds is not the number of threads but **memory** — since the per-agent input cap stands beside the replay ring's cap, the worst case per agent is **the sum of the two**.
- **The invariants were not touched** — the review confirmed that the ADR-0001 kill causality (2 verbs) is as it was. Transport isolation (ADR-0129) is as it was too.
- The writer loop **takes its write target as a closure** — so that it can be driven and verified without a child process, and the seam discipline of ADR-0012 is the reason.
- **The code anchors are not yet put in.** Four `// TODO(ADR)` markers are waiting — `crates/engram-dashboard-net/src/ws.rs:77`·`:690` and `crates/engram-dashboard-daemon/src/connection_core.rs:187`·`:224`. Swapping those spots for `// ADR-0206` is the follow-up.
