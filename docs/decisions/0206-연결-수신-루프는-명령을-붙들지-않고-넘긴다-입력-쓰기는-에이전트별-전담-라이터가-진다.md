# ADR-0206: 연결 수신 루프는 명령을 붙들지 않고 넘긴다 — 입력 쓰기는 에이전트별 전담 라이터가 진다

- 상태: 확정 (2026-09-18, 근거: OSS 서베이 + 3인 적대 리뷰(deep) + 실측)
- 관련: `crates/engram-dashboard-net/src/ws.rs` · `crates/engram-dashboard-daemon/src/connection_core.rs` · `crates/engram-dashboard-agent/src/transport/input_queue.rs` · `crates/engram-dashboard-agent/src/manager.rs:70` · 서베이 `docs/research/connection-dispatch-concurrency-survey-2026-09-17.md` · 증상 기록 `docs/refactoring/socket-head-of-line-blocking-2026-09-17.md` · ADR-0001 · ADR-0012 · ADR-0038 · ADR-0082 · ADR-0088 · ADR-0129 · ADR-0190 · ADR-0201

## 맥락

연결당 WS 수신 루프가 프레임 하나의 **핸들러 완료를 기다린 뒤에야** 다음 프레임을 읽었다. 그리고 활성화 핸들러는 에이전트 핸드셰이크 전체를 그 자리에서 기다렸다 — 실측 전형 약 2.2초, 상한 15초(`LINK_RESOLUTION_BACKSTOP`, `crates/engram-dashboard-agent/src/manager.rs:70`).

그 사이 같은 클라이언트가 보낸 **다른 모든 명령**이 데몬 수신 버퍼에 읽히지 않은 채 쌓였다 — **다른** 에이전트로 갈 입력도, kill 도, 또 다른 활성화도. 출력은 별도 write 태스크라 영향이 없었고, 그래서 증상이 "화면은 살아 있는데 타이핑이 먹지 않는다" 였다.

연결이 끊기지는 않았다. 15초 상한이 keepalive idle timeout 50초(`crates/engram-dashboard-net/src/ws.rs:128`) 아래라 35초 여유가 있었다 — 멈춤이 재연결로도 전환되지 않고 그냥 조용히 멈춰 있었다는 뜻이다.

두 번째 축은 통로였다. PTY·stdio 의 `send_input` 이 **호출자 스레드에서 OS write** 를 했고, 라이터를 `Mutex` 로 감싸 공유했다.

## 결정

명령 처리를 연결 수신 루프에서 직렬로 돌리는 것을 그만둔다. 맞물린 두 조각이다.

**1. 데몬.** 연결당 WS 수신 루프는 프레임을 디코드해 **넘기고 곧바로 다음을 읽는다.** 유계 큐가 **단일 소비자 태스크**를 먹이고, 그 소비자가 핸들러를 **도착 순서대로** 돌린다. `Kill` 은 별도의 작은 레인으로 날라 취소가 굶지 않게 한다. 포화하면 프레임을 **소리 내어 거절한다** — 자기 `request_id` 를 실은 오류로 돌려보내지, 버리지도 조용히 쌓아 두지도 않는다. 오래 도는 활성화 변종은 순서 레인에서 떼어 낸다.

**2. 통로.** PTY·stdio 백엔드가 **에이전트별 유계 입력 큐 + 라이터를 소유하는 전담 라이터 스레드**를 갖는다. `send_input` 은 큐에 넣고 돌아온다 — 호출자 스레드에서 OS write 를 하지 않는다. codex 백엔드는 이미 이 모양이라 손대지 않았다.

## 거부한 대안

- **(a) 그냥 직렬로 둔다** — 피어 중 이렇게 하는 곳이 없다(서베이 7곳). 대가는 활성화 때마다 초 단위로 사용자가 체감하는 입력 정지다.
- **(b) 프레임마다 태스크를 띄운다(무제한)** — 도착 순서를 잃는데 **그 아래 어느 층도 순서를 복원하지 못한다**(wire 순번을 나르는 계층이 없다). 직렬 루프가 우연히 제공하던 수용 상한도 함께 잃고, 리뷰가 열거한 위험이 그대로 곱해진다.
- **(c) 엔티티(에이전트)별 dispatch 큐 맵** — 진지하게 검토했고 Orleans·Akka 가 하는 모양이다. 그러나 그것은 **분산된 수천 엔티티**용 형상이다. zellij 는 키별 맵의 대가를 주석으로 남겼다 — 키를 더하거나 빼면 전부가 멈춘다("everything is halted, that's life"). 우리 규모엔 필요 없고, 이것이 사 줄 순서 보장은 **조각 2의 에이전트별 라이터가 이미 사 놓았다.**
- **(d) 티켓 / 지연 완료** — 즉시 "접수했다"로 답하고 결과는 나중에 `request_id` 로 배달. 루프를 안 건드리고 멈춤을 없애지만, **ADR-0201 이 정한 것**(활성화 응답 = 준비됐다는 판정)을 바꾸고 모든 클라이언트에 2단계 상태 기계를 떠넘긴다.
- **(e) tmux 식 park-and-resume** — 레인 하나를 유지하되 항목을 세워 두고 루프에서 **돌아온다**. 가장 보수적이고 실제 선례이지만, **기다림 자체는 남는다** — 큐를 없애는 게 아니라 옮긴다.

## 근거

1. **end-to-end 논변이 이 질문을 직접 다룬다.** Saltzer/Reed/Clark 1984 에 "Guaranteeing FIFO message delivery" 라는 소절이 있고, 거기서 순서를 보장하려면 "an independent mechanism at a **higher level than the communication subsystem**" 이 행위 순서를 통제해야 한다고 말한다. 저수준 순서 보장은 "justified only as performance enhancements" 다. ★한계를 정직하게 적는다★ — 그 논문이 말하는 것은 **transport FIFO 만으로는 부족하다**이지, dispatch 층 직렬화가 결코 정확성 수단일 수 없다는 말이 아니다. 논문 자신이 이 논변을 "not an absolute rule" 이라 부른다. 우리에게 확정해 주는 것은 하나다: **우리가 직렬화하고 있던 자리가 저수준이었고, 거기서 그것은 정확성을 사는 대신 성능을 쓰고 있었다.**
2. **피어 서베이 7곳, 우리와 같은 모양은 0.** wezterm mux(`dispatch.rs` — `process_one` 뒤 곧장 읽기로 복귀) · rust-analyzer(요청 종류별 4갈래 dispatch) · jsonrpsee(프레임마다 spawn) · zellij(route 스레드가 서브시스템 채널로 전달) · paseo(dispatch 를 기다리지 않음) · herdr(연결당 스레드) · tmux(의도적으로 직렬이지만 **항목을 세워 두고 루프에서 돌아온다** — 붙들지 않는다). ★적대 리뷰가 강제한 정정 둘★: zellij 는 일부 액션에서 **완료를 동기로 기다린다**(1초 타임아웃, 일부는 무제한)이고, herdr 는 연결당 블로킹이라 멀티플렉싱이 없다 — 둘 다 "즉시 넘김" 칸에 들어갈 자격이 없다.
3. **입력 순서는 PTY 단위 속성이고, 모든 피어가 그것을 연결이 아니라 세션 단위로 소유한다.** wezterm = pane 별 `Mutex<Box<dyn Write + Send>>` · zellij = `terminal_id` 별 큐 뒤 라이터 스레드 하나 · tmux = pane 별 bufferevent · herdr = PTY 별 actor. ★어느 프로젝트도 라이터를 분리한 이유로 "순서" 를 적어 두지 않았다★ — zellij 가 밝힌 이유는 교착이다("some programs get deadlocked if you write into their STDIN while reading from their STDOUT").
4. ★**우리가 핀한 `portable-pty 0.8.1` 자체가 단일 소유를 강제한다**★ — 클론이 아니라 레지스트리 캐시에서 대조했다. `take_writer` 는 한 번만 부를 수 있고(`src/lib.rs:98` 의 doc 블록, 그 문장은 101 행 "It is invalid to take the writer more than once"), unix 는 두 번째 호출을 bail 시키며(`src/unix.rs:321`), Windows ConPTY 는 거절한다(`src/win/conpty.rs:106`). 돌려주는 `Box<dyn Write + Send>` 는 `Send` 지만 **`Sync` 가 아니다.** 그것을 `Mutex` 로 감싸 공유하던 우리 방식은 이 계약을 거슬러 쓰는 것이었고, **스레드 하나가 소유하는 형태가 계약과 맞는다.**
5. **RFC 9112 §9.3.2 는 우리를 면제하지 않는다.** ★우리 서베이의 폐기된 초안이 "면제된다"고 적었는데 그것이 틀렸고 리뷰가 잡았다★. §9.2 는 HTTP/1.1 이 요청 식별자가 없어 응답 도착 순서에 의존한다고 설명하지만, 그것이 §9.3.2 의 "parallel only for safe methods" 를 들어 주지는 않는다. 우리에게 옮겨 오는 것은 더 좁다: 그 제약이 묶는 것은 **응답 배달 순서**이지 처리 순서가 아니다. LSP 3.17 이 같은 분할을 명시한다 — "as long as this reordering doesn't affect the correctness of the responses" 조건으로 병렬 실행을 허용하고, 그 자신의 반례로 `definition` vs `rename` 을 든다.
6. **우리 dispatch 를 직접 셌다.** `AgentCommand` 변종 30개 중 도착 순서 처리가 진짜로 필요한 것은 **5묶음뿐**이다 — 한 에이전트로 가는 stdin write · 입력 전 lease 획득/해제 · 한 에이전트의 subscribe/unsubscribe · command register vs update · `StopDaemon` 은 마지막. 그리고 **그 다섯은 전부 빠르다.** 느린 것들은 순서를 요구하지 않는다. 그래서 블로킹 write 를 레인 밖으로 빼고 나면 **순서 지키는 단일 소비자 하나가 비용을 거의 안 낸다.**

**실측**

- 재활성화 전형 약 2.2초. 막힌 활성화의 경성 상한은 `LINK_RESOLUTION_BACKSTOP` = 15초이고 keepalive idle 50초보다 낮아, 멈춤이 연결을 죽인 적은 없다(여유 35초).
- ★stdin 을 끝내 안 읽는 자식에게 물린 ConPTY write 는 `shutdown()` 으로 풀린다★ — 약 15ms 안에 `ERROR_BROKEN_PIPE`, 4회 실행. 이것이 코드만으로는 답할 수 없던 누수 우려(죽은 에이전트마다 스레드 + 핸들)를 닫는다 — `take_writer` 가 핸들을 밖으로 옮기므로 master drop 이 그것을 닫지 않고, `ClosePseudoConsole` 이 간접적으로 일한다. 무시 표시 없는 회귀 테스트가 이 사실을 못 박는다.
- 제출 페이싱 회귀를 **건강한 자식** 상대로 재현했다 — 512KiB 본문이 빠지는 데 500.37ms 가 걸렸고, 제출 CR 이 본문 꼬리 read 에 합쳐졌다(마지막 read 778 바이트).

## 영향 / 불변식

- ★`send_input` 의 `Ok` 뜻이 "썼다" 에서 "받았다" 로 바뀌었다.★ 제출 경로(우편 배달)는 실제 쓰기를 기다려 옛 뜻을 되산다 — 보통의 `WriteStdin` 은 안 산다. **ADR-0088 의 배달 관측 기록이 이 구분 위에 선다** — `WriteOutcome` 의 doc 이 지금 그 동사별 갈림을 명시한다(`crates/engram-dashboard-agent/src/types.rs`).
- **최악 우편 배달 지연이 약 10.5초로 늘었다**(본문 확인 5초 + 페이싱 0.5초 + 제출 확인 5초). flush 타임아웃은 **큐에 들어간 바이트를 취소하지 않으므로**, 타임아웃 + 재시도가 이중 배달이 될 수 있다 — 중복이 재시도보다 나쁘기 때문에 예산을 넉넉히 잡았다.
- 한 연결에서 `SpawnProfile(X)` 직후 `WriteStdin(X)` 은 이제 **경합한다**(활성화를 떼어 냈으므로). `Spawned`/`Error` ack 이 순서 계약이다. (ADR-0082 의 double-spawn 경합은 이전부터 있던 별건이고 여기서 닫히지 않는다.)
- **새 상한이 둘 생겼고 둘 다 정책이다** — 인바운드 프레임 큐, 에이전트별 입력 바이트 상한. 둘 다 **버리지 않고 소리 내어 거절한다** — 조용한 드롭은 `docs/process/S21-codex-backend/trd-phase2a.md` 가 이미 기각한 부류이고, ADR-0190 이 정한 규율("입력을 버리지 않는다 — 상한을 넘거나 준비가 끝내 실패하면 그때 오류로 돌린다")이 그대로 적용된다.
- **에이전트당 OS 스레드가 3개다**(라이터·워처·펌프). 묶이는 제약은 스레드 수가 아니라 **메모리**다 — 에이전트별 입력 상한이 replay 링의 상한 옆에 나란히 서므로, 최악은 에이전트마다 **그 둘의 합**이다.
- **불변식은 건드리지 않았다** — ADR-0001 kill 인과(2동사)가 그대로임을 리뷰가 확인했다. 통로 격리(ADR-0129) 도 그대로다.
- 라이터 루프는 쓰기 대상을 **클로저로 받는다** — 자식 프로세스 없이 구동해 검증할 수 있게 한 것이고, ADR-0012 의 seam 규율이 그 이유다.
- **코드 앵커는 아직 안 박혔다.** `// TODO(ADR)` 표식 넷이 대기 중이다 — `crates/engram-dashboard-net/src/ws.rs:77`·`:690` 와 `crates/engram-dashboard-daemon/src/connection_core.rs:187`·`:224`. 그 자리를 `// ADR-0206` 으로 갈아 끼우는 것이 후속이다.
