# ADR-0241: A tool's end result is carried as a new wire variant ToolResult, only for codex failures and refusals — no version bump, and our own rejections are attributed by the transport and shown separately as refusals

- 상태: 확정 (2026-09-27, basis: user decisions U2 · U2-a · U7 · acceptance of the known limits · sampling second ⓐ (TRD `docs/process/S21-chat-ux/trd.md` §1 · §11) + main decisions ⑧ ⑪ (TRD §11) + reading of the upstream codex source (main `41f9084` · tag `rust-v0.156.1` · not run) + TRD 5th-edition review FIX applied (TRD §12) · before implementation · before the B5 sampling · if it stalls, the affected decision is amended by a new ADR) · 부분 폐기 by ADR-0243 (decision 12: for an interrupted claude tool row, the interrupted display row gives the context below it)
- 관련: TRD `docs/process/S21-chat-ux/trd.md`(§1 U2 · U2-a · U7 · §4-3 · §4-7 · §6 · §7 B5 · FE-2 · I1 · §8-2 F3 · §9 F3 · §10 0241 · §11 ⑥ ⑧ ⑨ ⑩ ⑪ · §12) · research `docs/research/chat-ux-four-features-2026-09-27.md`(§3 · §8) · ADR-0239(tool kind `category` — the summary of the same group · split off because the axis differs) · ADR-0237(interrupt-row emphasis U8 — context beside a late failure) · ADR-0238(claude interrupt `TurnEnd{Interrupted}`) · ADR-0203(codex history item — one vocabulary table) · ADR-0004(backend knowledge isolation) · ADR-0051(row kind ↔ rail) · ADR-0127(turn observation · 30-minute fail-open) · ADR-0231(N11 stop after an error · codex transport lock order) · ADR-0234(the fan-out exception of emitted lines) · ADR-0173(orange warning token `--status-blocked`) · `docs/tracking.md` T-43(neutralizing the claude result) · T-44(chat approval) · T-12(Wait redesign) · step-log S21 · Amended by ADR-0243 (decision 12: for an interrupted claude tool row, the interrupted display row gives the context below it)

## 맥락
To put 「오류 N」 on the head of a tool-call group (ADR-0239), the end result of every call must reach the frontend. claude already carries the result body as a vendor block (`tool_result`) and the frontend reads that shape (the `isError` of `buildToolResultMap`). For every tool item, codex emits `item/completed` with the end status under the same item id after `item/started`, but our translator **deliberately emits nothing** on `ItemOrigin::Completed` of a tool item (`backend/codex/decoder.rs:262-263` · `:623` — so as not to draw one call twice). The history gate (`ItemOrigin::History`) also emits only `ToolCall`. So there is no route for codex's end status to reach the frontend.

Unlike the recommendation (「안 한다 — codex 묶음은 개수만」), the user decided **to do it this time** [사용자 U2 2026-09-27]. The user's reason: the convention (the 「· N failed」 of codex TUI · t3code) is a count in the summary + which call failed when expanded, and the codex translator is simply discarding the `item/completed` that carries the end status.

On top of that, **our own rejection** overlaps. The dashboard has no approval UI, so the codex transport rejects every server request with `METHOD_NOT_FOUND` (`backend/codex/transport.rs:3054-3087` · for every incoming request `:3629`). codex closes that rejection as `failed` for a command and `declined` for a file change (「근거」 below — source reading) — so with the vendor status alone, a command has the same shape as a real failure, and a file change has the same shape as codex's own refusal. Right now nothing shows on the screen (likely — not measured · research §8-1).

Also the end **can come after the turn end** (measured — a command that started at line 27 of `codex/fixtures/steer_m6.jsonl`, after its turn was interrupted at line 32, closes at line 50, after the next turn's `turn/completed` (line 49), with the old turn id · `status: completed` · `exitCode: 0` · 17 seconds after the interrupt).

## 결정
Notation — **[사용자]** = a decision the user answered · **[메인]** = an orchestrator decision · **[고름]** = an internal implementation the TRD picked. Scope = the end result codex carries and its display. The claude translator is not changed (decision 6).

1. **Wire shape = a new variant `ToolResult { id: String, outcome: ToolOutcome }`** [고름] — in the agent `OutputEvent` and the wire `StructuredEvent`, with the same shape. It points to the earlier `ToolCall` by `id` (it is not a new row). `id` is not an `Option` — if there is no call to point to, no event is emitted.
   ```rust
   pub enum ToolOutcome {
       Completed,
       Failed,
       Declined, // 에이전트(벤더)가 스스로 실행을 거부했다
       Refused,  // 우리(호스트)가 승인 요청을 거절해 실행되지 않았다 — 번역기는 내지 않고 통로가 바꿔 쓴다(결정 8)
   }
   ```
   TS touchpoints = the generated `ToolOutcome.ts` (`"Completed" | "Failed" | "Declined" | "Refused"`) · `{ "type": "ToolResult", id: string, outcome: ToolOutcome }` in `StructuredEvent.ts`.
2. **codex mapping = one function `tool_outcome(item, kind) -> Option<ToolOutcome>`** — shared by the two gates `Completed` and `History` (ADR-0203 「두 번째 어휘표를 만들지 않는다」).

   | Vendor `status` | → | Note |
   |---|---|---|
   | `failed` | `Failed` | for all five tool variants · if it is an id we rejected, the transport changes it to `Refused` (decision 8) |
   | `declined` | `Declined` | only `commandExecution` · `fileChange` have it in the schema — if it comes from another variant, a drift count · if it is an id we rejected, the transport changes it to `Refused` |
   | `completed` | `Completed` | ★not emitted★ (decision 3) |
   | `inProgress` | — | an item on a history page that is still running |
   | `interrupted` (`collabAgentToolCall`) | — | the turn-outcome row already shows the interrupt |
   | no field (`webSearch`) | — | routine |
   | any other string · not a string | — | `observe(tool-status:…, Drift)` |

   - ★**The decision is the vendor `status` alone — we do not read `exitCode`**★ [고름]. We do not read `mcpToolCall.error` · `dynamicToolCall.success` either, for the same reason.
   - **Emission**: the `Started` gate = as today (`ToolCall`) · the `Completed` gate = one `ToolResult` if `tool_outcome` is `Failed`/`Declined` (the translator does not emit `Refused`), otherwise, as today, 0 events + a routine count · the `History` gate = `[ToolCall, ToolResult?]` in this order. `id` is the same `bounded_id` as the `ToolCall` — if it is filtered out and missing, there is no row to point to, so nothing is emitted and a `Malformed` count is made.
3. **We emit only failures and refusals** [고름] — `Completed` is kept only as a wire vocabulary (a place for the follow-up of decision 6 to use). ★No `ToolResult` = do not read it as success★ — absence means 「모름」 (an old daemon · pushed out of the ring · interrupted so the end did not come).
4. **`OutputEvent::ToolResult { .. } => None` in the two turn classifiers (`claude/mod.rs:538` · `codex/mod.rs:1203`).**
   - ★`Progress` forbidden★ — the end also comes after the turn end (the measurement in the context), and if it were counted as progress, 「턴 중」 would turn on again and the mail would be blocked until the 30-minute fail-open (CLAUDE.md 「턴 관측 정리」 · the last paragraph of 「대기 입력 상태」). Because it is `None`, it does not rely on arrival order.
   - ★`Failed` forbidden★ — a tool failure is an ordinary step of the agent. If it were counted, one failed search would set the stop after an error (`last_end_failed`) and the mail would stop until the next clean turn (ADR-0231 N11).
   - An event the transport rewrote as `Refused` is also the same `None` — the rewriting changes only the outcome field, and which gate the event goes out through, the ordinary one or the one without observation (the `ours` decision at `transport.rs:3659-3670`), is also unchanged.
5. **We neither raise `PROTOCOL_VERSION` nor filter** — the same judgment as `TurnEnd` (`protocol/src/messages.rs:743-763`) · `QueuedInput` (`:782-785`) (daemon→shell one direction · the old side has nothing to misread). We put that one line in the doc of the new variant. The price = with a new daemon + an old shell, for every codex failed/refused call the accumulator's default branch leaves a 「표시할 수 없는 신호」 line (if consecutive, only the count on one line grows · that frame does not touch the waiting display) · with an old daemon + a new shell there is just no codex error display. This price was raised to the user as the trade-off of U2 (TRD §1 U2 — we reduce it by emitting only failures and refusals).
6. **We do not change claude this time** [고름] — we do not build the plan where the claude translator also emits the same `ToolResult` from the `tool_result` block (rejected alternatives). The claude error count comes, as today, from the frontend parsing (the `isError` of `buildToolResultMap`). A neutral result that carries the body is a follow-up (`docs/tracking.md` T-43).
7. **Refusal = marked separately · two outcomes** [사용자 U2-a · the outcome split = 4th-edition review FIX · adopted by main] — it is not that the tool ran and failed, it is that it was not executed.
   - **`Refused`** = our rejection · reason line 「대시보드가 승인 요청을 처리하지 않아 실행되지 않음」 (the wording of U2-a — moved to the `Refused` side in the 5th edition that split the outcomes · main).
   - **`Declined`** = a refusal not in memory (codex's own refusal — guardian review · network policy etc. · vendor preparation failure · the restoration and cap push-out in the limits below) · reason line 「실행되지 않음」 [사용자 2026-09-27 · 5th-edition light re-check — it replaced main's 5th-edition wording 「codex 가 실행을 거부함」].
   - **Badge · color · counting are the same for both**: in the place of the red `Error` badge, `t('chat.toolDeclined')` (「거부됨」) · text · border = `var(--status-blocked)` (the orange warning token — dark `#d29922` · light `#9a6700` · e-ink is the body color · ADR-0173) · the head (`RowHeader`) keeps the default tone — not painted red · the group summary `chat.toolGroupDeclined` (「거부 {count}」) counts `refused` and `declined` together and comes after 「오류 N」 · **it is not included in the error count**. [고름] We do not build a new token (the e-ink neutralization is already in it).
   - **Reason line**: one line inside the same line box, right below the head button (`text-xs` · `text-muted`) · **visible even when folded** · DOM marker `data-tool-declined-reason` = the reason key (`"chat.toolRefusedReason"` | `"chat.toolDeclinedReason"`). ★Tell the origin apart by this key — do not tell it apart by text★: 「실행되지 않음」 is the same as the tail of our reason, so a text-contains check cannot tell the two origins apart. Line root `data-tool-mark="failed" | "declined"` (`refused` is also `"declined"`). [고름] The wording is fixed per origin — the vendor item has no reason field.
   - Constant `DECLINED_MARK: 'own' | 'error' = 'own'` (head of `chat/toolRuns.ts`) — `'error'` is kept as the switch of alternative A (count both refusals as errors, red badge · no reason line).
8. **Attribution of our rejections — the codex transport remembers the item id of an approval request it rejected and emits its end rewritten as `Refused`** [고름 — place = a reader-only field · main ⑧ accepted · rewriting rule = main 5th edition].
   - **Only two requests are remembered** — `item/commandExecution/requestApproval` · `item/fileChange/requestApproval`. Conditions: `params.itemId` is a string and within `MAX_ID_BYTES` (128) · a command approval only when `approvalId` and `networkApprovalContext` are missing or `null` (a sub-command approval is not a rejection of the parent item's execution · and a network approval's handler does not emit an end) · the rejection line actually went into the control queue (if `refuse` returns early with `closed`, or on overflow, it is not recorded). Any other request · no `itemId` → no attribution (only the rejection, as today).
   - **Place = one reader-only (`Reader` — `transport.rs:3041-3049`) field** `refused: RefusedItems` — in the same vein as `first_turn` and outside the state lock (`State`). The writing side (`refuse`) and the reading side (the `item/completed` notification of the same `handle_line`) are both the reader thread, so the memory always stands before the end. `refuse` goes from `&self` → `&mut self` + an argument `params: Option<&Value>`. The two method-name constants go in `protocol.rs`.
   - **Shape · cap** — `VecDeque<String>` · cap `REFUSED_ITEM_SLOTS = 16` (when it overflows, the oldest is dropped · debug log) · ★an `itemId` already in memory is not put in again★ (a harmless defensive rule — 4th-edition review low). Usually it is 0–1 entries.
   - **Rewriting · clearing** — in the notification branch of `handle_line`, one line after translation and before the boundary extraction. If `params.item.id` of `item/completed` is in the set, it is **taken out** (regardless of the end status — the end line is the clearing place) and `ToolResult { id, outcome: Failed | Declined }` inside `events` is rewritten as `Refused`. If the translator emitted nothing (`completed` etc.), only the memory is erased. ★It is not cleared at the turn end★ [고름]. A new incarnation = a new reader = an empty set.
   - **The translator does not know this set** [고름] — the translator stays a pure translator that receives only notification lines (the translator does not emit `Refused`).
   - **There is no switch — the attribution is always built** (5th edition). Even if the vendor closes our rejection as `declined`, the attribution is needed to choose the right reason — for a file change it already is.
9. **We accept four known limits** [사용자 2026-09-27 · main recommendation — one bundle with U7 · we do not grow the attribution mechanism further] — the set is empty in each incarnation and the vendor item has no reason field. A re-subscribe replay within the same incarnation receives the `Refused` in the ring as it is, so it is correct.
   - ① **A command in history** — in the resumed history there is **no** command row that we rejected (it is neither 「오류」 nor 「거부됨」) (likely — source reading `rust-v0.156.1`). A row that was 「거부됨」 live disappears, and the group count and 「거부 N」 each go down by one.
   - ② **A command pushed out by the cap** — its late `failed` end is not in memory, so it is `Failed` (「오류」).
   - ③ **A file change in history** — it remains in history as `declined` and becomes `Declined` (likely — source reading `rust-v0.156.1`) — the badge and counting are the same and only the reason is 「실행되지 않음」. We lose our reason but it is not false.
   - ④ **A file change pushed out by the cap** — the same 「거부됨 · 실행되지 않음」 as ③.
   - The right fix = `docs/tracking.md` T-44 (if the dashboard stops auto-rejecting, this attribution will most likely become unnecessary).
   - ★The frame of the decision★ — the user decided in the frame of the 4th edition (on reactivation · cap push-out, our rejection turns into 「오류」). Right after the decision, main told the user the facts it had corrected (a rejected command row is not in history, so it disappears when reopened · a rejected file change closes as `declined`), the user raised no objection, and went on to decide the wording of the `Declined` reason (TRD §11 ⑨ · §12).
10. **Approval inside the chat is the next task** [사용자 U7] — 「다음 과제로 빼자. 지금 많이 엮여있어」 (`docs/tracking.md` T-44). In this round too the dashboard auto-rejects codex approval questions and only shows the rejected call as 「거부됨」.
11. **A codex command that closes late as `failed` after being interrupted = a red 「오류」 as it is** [사용자 2026-09-27 — option ⓐ] — 「일단 밑에 중단됨 줄이 있는데 뭐가 문제라는거야?」. Even after an interrupt the command process stays alive and closes with its real `exitCode` (likely — source reading), so with a non-zero exit the late end is `failed`. That end is attached to that row as an ordinary red 「오류」, and the group head counts 「오류 1」. The 「중단됨」 row of that turn right below (ADR-0237 decision 6 — emphasis) gives the context, and since the command actually failed, it is not a false display. **No new mechanism** — we add no rule to the accumulator, and the attach path (decision 12) is also unchanged.
12. **A tool interrupted by claude's Esc (`tool_result` `is_error:true`) = the same rule as decision 11** [메인 decision · delegated by the user 2026-09-27 — 「너가 생각하는 방향으로 하고 나중에 보고 개선하면 되지」] — that row keeps wearing today's red `Error` badge (`isErr = result?.isError === true`), and when a group stands, the head counts 「오류 1」 · the emphasized 「중단됨」 row right below gives the context. Reason = applying the user's ⓐ reasoning as it is · one rule for both backends · no new mechanism. We do not re-classify `is_error` inside an interrupted turn.
13. **Frontend — we attach the result to the existing row, and attaching is not 「새 내용이 왔다」.**
   - The accumulator `tool` item gets a field `resultMark: 'failed' | 'declined' | 'refused' | null` (in the same vein as `TurnOutcomeMark` — a normal completion has no mark) [고름 · 5th edition — the mark knows the origin, which is needed to tell the reason lines apart].
   - `ToolResult` branch: find the `tool` item with the same `id` from the back and change `resultMark` by copy-on-write (an unknown word → `null` + warn · if not found, it is discarded). **It does not create a new item** → `rowKindOf` · rail · `isRenderedItem` unchanged. It does not touch `turnDone`.
   - ★**`feed` returns `false` — whether it attached or could not find it**★ [3rd-edition review Designer FIX · user agreed 2026-09-27] — the return value of `feed` is used at `RichSlot.tsx:222` only as the signal that releases the waiting display. If a late end of a previous turn's tool arrives right after the user sends new text and before the new turn answers, with `true` the new turn's Wait display would turn off without an answer. The re-drawing of the row is unchanged (`RichSlot` calls `setItems` first regardless of the return value). We fix the doc of `feed` and the call-site comment at `RichSlot.tsx:218-221` to the new meaning (`false` = a frame that does not release the wait). We do not change Wait's own rule (`docs/tracking.md` T-12).
   - Summary: the `errors` of `summarizeGroup` = calls with `resultMark === 'failed'` or with `isError` from the claude parsing · `declined` = `resultMark` is `'declined'` or `'refused'`. The expanded row `ToolItemRow` has `isErr = result?.isError === true || mark === 'failed'` (codex has no Out field).

## 거부한 대안
**Wire shape**
- **An optional `status` field on `ToolCall` + accumulator id merge** [고름] — at the end it would have to emit `ToolCall` once more. Since the two turn classifiers count `ToolCall` as progress (`claude/mod.rs:541` · `codex/mod.rs:1206`), an end that comes after the turn end would turn 「턴 중」 on again and become a 30-minute blockage path. An old shell would draw **one more of the same tool row** per end — worse than the 「표시할 수 없는 신호」 line (the content is wrong).
- **A `Structured{kind:…}` escape hatch (including imitating the claude `tool_result` shape)** [고름] — the same two classifiers count `Structured` entirely as progress (the same reason we do not put queued-input events in the escape hatch — `types.rs:94-97`). If built in the claude shape, an old shell would also draw the badge, but it would spread the vendor shape to the codex translator and grow the leak of research §3-1.
- **Raise the version to filter** (6 → 7 · `protocol/src/lib.rs:121`) — the only thing the shell tells the daemon is the `protocol_version` in the first auth frame (`net/src/auth.rs:33-38`), and the daemon disconnects if it is not equal (`net/src/ws.rs:348-363`) · the `capabilities` of `Hello` goes daemon→shell and is `None` now (`connection_core.rs:2214-2220`). So within one version there is no value to tell shells apart. If we raise the version, an old shell cannot connect at all and there is nothing to filter, but we would cut off the everyday development combination (an old daemon + a new shell — discovery refuses reuse `discovery/src/lib.rs:446`) for one line of display.
- **Emit every end** (including `Completed`) [고름] — one more event per codex tool call, and the old shell's 「표시할 수 없는 신호」 line would be attached to **every** call, while the screen gains nothing — the display is only the error and refusal counts and the badge.
- **claude also emits a status-only `ToolResult`** [고름] — the result **body** is still read from the vendor block (the Out of the expanded row `StructuredTextView.tsx:262` · the skip of `rowKindOf` `:390`). A neutral event that carries only status cannot lower that parsing to an old-daemon fallback, and **the same error bit lives in two places** (one side goes stale). claude emits a result for **every** call, so the ring events and the old shell's undisplayable lines grow by the number of claude calls. It does **not grow** today's leak — codex does not ride the vendor shape.
- **Decide by `exitCode`** [고름] — if we re-classify a non-zero exit as a failure ourselves, a decision different from the vendor's stands (t3code also looks only at `status` — `apps/server/src/provider/Layers/CodexAdapter.ts:1013-1019`).

**Refusal display**
- **Count refusals together with errors** (alternative A — precedent Zed · vibe-kanban · paseo · research §8-2) [사용자 U2-a — chose B] — being blocked by permission and a real failure look the same, and every rejection in our app is our own policy (there is no approval window — research §8-3), so red makes people look for a bug that is not there. A had the advantage of no extra work. It remains as the switch `DECLINED_MARK = 'error'`.
- **One reason for one `Declined`** (4th-edition design) [4th-edition review FIX — two reviewers · adopted by main] — the false-reason defect where our reason is attached even to codex's own refusals (guardian · network policy).
- **`Declined` reason 「codex 가 실행을 거부함」** (main's 5th-edition wording) [사용자 2026-09-27 · 5th-edition light re-check] — a frontend string must be a neutral word without a backend name (`structuredAccumulator.ts:25` · ADR-0004). It is false on documented paths — a restored rejection of our file change · a pushed-out rejection of our file change · the vendor's Declined report of a preparation failure (`core/src/tools/events.rs:445-452@v0.156.1`). If the claude `ToolResult` (T-43) comes, it inherits the codex name.

**Attribution of our rejections**
- **Build chat approval this time** [사용자 U7 — **not a rejection but the next task** (T-44)] — 「다음 과제로 빼자. 지금 많이 엮여있어」. Building it adds approval requests · an answer path · UI as new, and entangles with this round's attribution · turn observation · waiting display.
- **Decide a refusal by the item shape (`failed` + `exitCode:null` + `aggregatedOutput:null`)** (main's proposal that resolves splits 2 and 3 of the 4th-edition review in one go) [메인 5th edition · the reason order was fixed by the light re-check] — it would read other paths that produce the same shape (a thread unload · when the approval callback is dropped by a rollback `beh:2032-2038@v0.156.1` · a guardian timeout `beh:376-396@v0.156.1`) as our rejection and attach a false reason. A rejected command is not in the resumed history, so restoration would not help either — what it gains is only one command pushed out by cap 16 live.
- **Preserve the origin through history restoration** (4th-edition review Designer — if you reopen the same conversation the badge and summary counts change) [사용자 — accepted as a known limit (decision 9)] — the right fix is T-44.
- **A switch that does not build the attribution if the installed build sends `declined` for our rejection** (4th edition) [메인 5th edition] — once the outcomes split in two, the attribution is always needed to choose the right reason. A file change already closes as `declined` (source reading).
- **Put the rejection set in the transport `State`** [고름 — main ⑧ accepted] — the writing side (`transport.rs:3629` → `refuse`) and the reading side are both the reader thread, so there is nothing for a lock to guard. `State` is the critical section that the writer · `send_input` · the reader share (the doc at `:382-384`), so only the lock span and a cell of the 「소유권 분할」 table would grow (correct but gains nothing).
- **Inject a shared set into the translator** (a shared `Arc<Mutex<…>>` like claude's `TurnGate`) [고름] — it is one thread, yet one more lock is added and the translator tests get tied to transport state.
- **Clear the set at the turn end** [고름] — the end comes after the turn end too (measured `steer_m6` line 50). If cleared, that late end would become a red 「오류」.

**The late end after an interrupt** (the option labels = TRD §11 ⑩ · the user's decision ⓐ rejected the four below)
- **ⓑ-1 Hide the late result of an interrupted turn** — a real failure would not be seen and new logic is needed.
- **ⓑ-2 Show the late failure as that row's 「중단됨」** — a rule is needed (the user: without a separate mechanism). A history page carries no turn outcome (`backend/codex/decoder.rs:1179-1183` · ADR-0203), so when reopened the application would not hold.
- **ⓑ-3 At the moment of the interrupt, mark every still-running row as 「중단됨」** — the trigger is the moment of the interrupt, not the late end. The translator emits nothing for success (decision 3), so the frontend cannot tell a codex row that ended in success from a still-running row — a new success signal or memory is needed.
