# ADR-0264: 데이터 루트를 컴포넌트별 state/run 으로 나누고 옛 데이터는 옮기지 않는다

- 상태: 확정 (2026-10-02, 근거: 사용자 결정 2026-10-02 (`docs/research/storage-management-survey-2026-10-02.md` 「0. 결정」) + TRD `docs/process/S21-storage/trd.md` §2 · §3 · §11 (리뷰 2회 반영 — 설계자 · 파괴자) + P1 코드 리뷰 뒤 사용자 결정 2026-10-02 (폴더 이름 store → 업계 표준 config/state · 개발 루트 `.engram-dev` — 결정 2 · 3 · 8) + 사용자 결정 2026-10-02 (옛 데이터는 옮기지 않고 버린다 — 첫 부팅 이전 걷음 · 결정 5 · 6, TRD §14-5))
- 관련: Amends ADR-0136 (결정 3에 run 폴더 규칙과 agents.json 사본 패턴 추가 · 결정 2 번복 — 개발 루트 `.engram-data` → `.engram-dev`, 결정 8) · Amends ADR-0135 (결정 1의 잠금 파일 자리 — `daemon\run\daemon.json` 하나, 결정 6) · ADR-0134(데이터 루트 위치 — 그대로 유지, 이 결정은 그 안쪽 배치만 정한다) · ADR-0024(`default_data_dir` 의 단일 출처 = discovery) · ADR-0129(net — 단일 인스턴스 가드 소유) · ADR-0175(base 입주 조건) · ADR-0230(플랫폼 중립) · TRD `docs/process/S21-storage/trd.md` · 조사 `docs/research/storage-management-survey-2026-10-02.md` · `crates/engram-dashboard-discovery/src/layout.rs` · step-log S21

## 맥락

데이터 루트(릴리스 `<exe>\data` · 개발 `<워크트리>\.engram-data` · 시험 `ENGRAM_DATA_DIR` — ADR-0134 · ADR-0136)의 안쪽이 **평면**이다. 지켜야 할 명부·프리셋·거절 기록(`agents.json` · `presets.json` · `usage_rejects.json`)과, 기동마다 새로 만들거나 쓸리는 것 — 잠금+접속 파일 `daemon.json`(WS 토큰) · 스폰 부착 파일 `mcp-config\`(토큰) · 임시 `usage-probe\` — 가 한 폴더에 섞여 있고, 셸 파일(`ui-settings.json`)과 로그도 같은 자리다(조사 §1 인벤토리).

저장 관리 작업(설정 · 화면 상태 · 웹뷰 폴더 — TRD S21-storage)이 셸 쪽 영속 파일을 늘린다. 무엇을 어디에 둘지 규칙이 먼저 서야 한다. 경로 계산도 흩어져 있었다 — net 잠금 획득 · 데몬 MCP 설정 · base 로그 초기화가 각자 데이터 폴더를 받아 안에서 이름을 붙였다(TRD §2-2).

평면 배치는 이미 배포된 바이너리가 쓰고 있다. 처음 설계는 그것을 첫 부팅에 옮기고 옛 바이너리와 섞이는 경우를 막는 장치(완료 표지 · 옛 자리 잠금 · 두 자리 읽기)를 함께 깔았다. 구현과 코드 리뷰 3회를 거치며 그 장치가 경계 사례를 계속 낳았고, 사용자가 **데이터가 아직 정립되지 않았으니 옛 데이터는 버린다**고 정했다(2026-10-02).

## 결정

1. **데이터 루트 위치 = 포터블 유지.** ADR-0134 · ADR-0136 그대로다(릴리스 `<exe>\data` · 개발 `<워크트리>\.engram-dev` — 개발 쪽 이름만 결정 8 이 바꾼다). 설치형(Program Files + OS 표준 폴더)으로 가지 않는다. 이 결정은 루트 **안쪽 배치**만 정한다.
2. **배치 = 컴포넌트 먼저, 종류 다음.**
   ```
   <root>\
   ├─ daemon\
   │  ├─ state\          agents.json · presets.json · usage_rejects.json (+ .corrupt-* 사본)
   │  └─ run\            daemon.json(잠금 + 발견 · WS 토큰) · mcp-config\(토큰) · usage-probe\
   ├─ shell\
   │  ├─ config\         취향 — settings.json · (장래) slots\ · themes\
   │  ├─ state\          기억 — state.json(화면 상태)
   │  └─ run\            생길 때만 — 지금 없음
   ├─ webview\           WebView2 사용자 데이터 폴더 자리(옮기는 일은 뒤따르는 웹뷰 폴더 결정)
   └─ logs\              daemon-*.log · app-*.log (위치 현행 그대로)
   ```
   데몬은 아직 `config\` 가 없다 — 장래 조정값이 생기면 `daemon\config\` 다. 로그는 최상위 `logs\` 에 둔다(프로세스마다 파일이 따로다 · 데몬과 클라이언트가 다른 기계로 갈라지면 각 기계의 `logs\` 에 제 종류만 남는다).
3. **규칙 = `config\` · `state\` 는 지키고 `run\` 은 버려도 된다.** 폴더 이름은 업계 표준을 따른다 — systemd `ConfigurationDirectory=` · `StateDirectory=` · `RuntimeDirectory=` · XDG `CONFIG_HOME` · `STATE_HOME` · `RUNTIME_DIR`(https://specifications.freedesktop.org/basedir/latest/ · systemd.exec man page). **가름 기준: config = 취향**(「어떻게」 — 지우면 기본값으로 돌아간다) · **state = 프로그램이 기억하는 것**(「무엇이 있나 · 어땠나」 — 에이전트 명부는 사용자가 만들었어도 state 다. Docker 의 `/var/lib` 와 같다). 기존 `presets.json` 은 자리만 `daemon\state\` 로 정하고 새 프리셋 구조는 만들지 않는다. 토큰 든 파일(`daemon.json` · `mcp-config\`)은 `daemon\run\` 에만 둔다.
4. **경로의 단일 출처 = discovery 의 `DataLayout`(새 모듈 `layout`).** 디렉터리와 **둘 이상의 프로세스가 보는 파일**(`daemon.json` — 데몬이 쓰고 셸 · 스크립트가 읽는다)은 `DataLayout` 이 계산한다. **한 저장소만 쓰는 파일 이름은 그 저장소가 소유**하고 받은 디렉터리 안에서만 붙인다(`agents.json` · `presets.json` · `usage_rejects.json` — 이름까지 끌어오면 agent crate 가 discovery 를 의존해야 한다). net 은 discovery 를 의존할 수 없으므로(discovery → net) 잠금 파일 경로를 인자로 받는다. discovery 공개 함수(`ensure_daemon` · `daemon_status` · `read_live_daemon` · `daemon_stop` · `send_stop`)는 루트를 그대로 받고 안에서 `DataLayout` 을 쓴다. OS 가름은 지금처럼 `default_data_dir` 안에만 있고 `DataLayout` 은 `Path::join` 뿐이다.
5. **옛 데이터는 옮기지 않고 버린다 — 새 코드는 옛 파일을 읽지도 옮기지도 지우지도 않는다.** 대상 = 릴리스 `<exe>\data\` 의 평면 파일(`agents.json` · `presets.json` · `usage_rejects.json` · 루트 `daemon.json` · `mcp-config\` · `usage-probe\`)과 개발 루트 `.engram-data\` 통째. 첫 부팅 이전 · 완료 표지 · 옮겨 들이기/보존 규칙 · 대소문자 변형 처리는 없다. 새 데몬은 새 자리 디렉터리만 만들고 빈 명부로 시작한다. 옛 바이너리와 새 바이너리는 상태 · 잠금 · 토큰 파일을 하나도 공유하지 않으므로 서로 간섭하지 않는다 — 옛 데이터가 새 바이너리에 보이지 않는 것은 **의도**다. 그래서 단일 인스턴스 배제(ADR-0134)는 이제 **한 배치 버전 안에서만** 성립한다 — 옛 배치 데몬과 새 배치 데몬은 서로 다른 잠금 파일을 쥐어 같은 루트에서 함께 돌 수 있고, 상태 · 토큰 파일은 공유하지 않으며 함께 쓰는 것은 `logs\`(pid 로 갈리는 파일 이름)뿐이다. 옛 파일 정리는 사용자 몫이다(이 워크트리의 `.engram-data` 는 사용자가 손으로 지웠다).
6. **잠금은 하나 — `daemon\run\daemon.json`.** 옛 루트 `daemon.json` 은 잡지도 자르지도 않는다. ADR-0135 결정 1(잠금 파일 = 접속 파일)은 그 파일에 대해 그대로이고 자리만 옮긴다. discovery 와 스크립트(`scripts/engram.mjs` 등)는 **새 자리 하나만** 읽는다 — 두 자리를 골라 읽는 판정은 없다.
7. **`.gitignore` — `daemon\run\` 하나는 폴더 규칙으로 막는다.** `**/data/daemon/run/` 을 더하고, 명부는 꼬리 패턴 `**/data/daemon/state/agents.json*` 로 막는다(`.corrupt-*` 사본도 같은 평문 env 를 싣는다). 개발 루트는 `/.engram-dev/` 를 통째로 막는다. 옛 줄(`.engram-data/` · `**/data/daemon.json` · `**/data/agents.json*`)은 **남긴다** — 새 코드가 옛 파일을 지우지 않으므로, 다른 워크트리 · 압축을 푼 옛 배포판에 남은 폴더와 토큰 든 평면 파일이 계속 무시되어야 한다. ADR-0136 결정 3(비밀이 든 파일 이름으로 막는다)의 원칙은 살아 있고, `daemon\run\` 만 예외로 폴더 규칙이다 — 경로가 구체적이라 무관한 폴더를 삼키지 않는다.
8. **개발 데이터 루트 이름 = `.engram-dev`**(옛 `.engram-data` — ADR-0136 결정 2 번복). 관행 = 릴리스 이름 + `-dev`(herdr `herdr-dev` · orca `orca-dev`). `engram` 은 저장소 루트 · 검색 · ignore 에서 겹치지 않게 남기고, 개발 식별자 `com.engram.dashboard.dev` 와도 맞는다. **이름을 바꾸지 않는다** — `.engram-dev` 는 새로 시작하고 옛 `.engram-data` 는 결정 5 대로 그대로 둔다.

## 거부한 대안

- **설치형 — Program Files + OS 표준 폴더(`%APPDATA%` · `%LOCALAPPDATA%`) 기본.** 배포가 ZIP 한 덩이 · 한 사용자다. OS 폴더를 쓰는 이유(Program Files 쓰기 불가 · 설치기의 갱신 · 여러 사용자 · 로밍)가 지금은 해당되지 않는다. 피어가 OS 폴더를 쓴다는 것만으로는 근거가 안 된다 — VS Code 도 ZIP 배포에서는 포터블 `data/` 를 지원한다(조사 §2-4). OS 폴더로 가면 워크트리별 격리를 환경변수로 따로 지켜야 한다(조사 §2-5 — 워크트리 격리를 하는 피어는 없고 우리 격리가 더 강하다). ★기각 근거의 강도 = **약함**(정책 서술 — 정량 · 실측 · 코드 아님)★ — 사용자가 조사 §3 축 1 의 선택지 (가) OS 폴더 기본 + 포터블 표식 · (나) 포터블 유지 · (다) OS 폴더만 을 받고 (나)를 골랐다. **재론 조건 = 성숙 후 · 보안 필요가 생길 때.**
- **Tauri 2.12 의 `appDirectoriesOverride` 로 앱 디렉터리를 한 번에 재지정.** 우리 Tauri 2.11.3 소스에 없다(`tauri-2.11.3/src/path/desktop.rs:238-260` — 식별자만 붙인다). 처음 나온 릴리스가 2.12.0 이라 업그레이드가 선행이다(조사 §2-6). 기각 근거 = 코드(레지스트리 소스 대조).
- **종류 먼저 — `state\daemon\` · `run\daemon\`(XDG 식).** 데몬과 클라이언트가 장차 다른 기계로 갈라질 수 있고, 컴포넌트 먼저면 `daemon\` 을 폴더째 옮길 수 있다. ★기각 근거의 강도 = **약함**(장래 대비 서술)★ — 사용자 결정.
- **폴더 이름 `store` 유지.** 표준 용어가 아니다 — systemd · XDG 가 쓰는 말은 config · state · runtime 이고, 표준 이름이면 가름 기준(취향 / 기억 / 버려도 됨)이 이름에 실려 따로 설명할 필요가 없다. 기각 근거 = 사용자 결정(업계 표준 우선).
- **개발 루트 `.engram-data` 유지.** 이름만으로 디버그용인지 알 수 없다. 기각 근거 = 사용자 결정.
- **개발 루트 `.data-dev`.** 흔한 이름이라 검색 · ignore 규칙에서 다른 것과 겹친다. 기각 근거 = 사용자 결정.
- **평면 유지.** 지킬 것(명부)과 버려도 되는 것 · 토큰 든 것이 한 폴더에 섞인다. 기각 근거 = 코드(현행 배치 — 조사 §1).
- **첫 부팅 이전(구현까지 했다가 걷음).** 데몬이 기동 때 옛 평면 state 를 `rename` 으로 옮기고 완료 표지를 맨 마지막에 쓰며, 옛 루트 `daemon.json` 도 0바이트로 쥐어 옛 바이너리를 막고, discovery 는 두 자리를 읽어 고르는 설계였다(개발 루트는 `.engram-data` → `.engram-dev` 이름 바꾸기까지). 기각 근거 = **사용자 결정**(데이터가 아직 정립되지 않았다 — 지킬 만한 옛 데이터가 없다) + **그 장치의 비용**: 코드 리뷰 3회 내내 경계 사례가 새로 나왔다 — 대소문자만 다른 옛 파일 이름 · FAT 계열에서의 이름 바꾸기 · 링크 · 옛/새 바이너리가 섞인 채의 잠금 순서와 경합 · 표지 뒤 낙오 파일의 옮겨 들이기/보존 · 0바이트 옛 잠금의 읽기 해석. 같은 판정이 데몬 · discovery · 스크립트 세 곳에 퍼졌다. 이 결정이 그 대안의 하위 갈래(「둘 다 있으면 새 것」 · 「새 자리 잠금 하나만」 · 「복사하고 옛 것을 남긴다」 · 「옛 자리 `daemon.json` 을 지워 본다」 · 「run 것도 옮긴다」)를 함께 무의미하게 만든다 — 그 기각 사유들은 이전을 한다는 전제 위의 것이었다. **재론 조건 = 지킬 데이터가 생긴 뒤 배치를 다시 바꿀 때** — 그때는 이 항목의 경계 사례 목록에서 시작한다.
- **옛 데이터를 지운다(버리되 새 코드가 치운다).** 새 코드가 옛 파일을 만지는 순간 「무엇이 우리 것인가」 판정(전용이 아닌 `ENGRAM_DATA_DIR` · 같은 이름의 남의 파일)과 옛 바이너리가 쥔 파일의 실패 처리가 되살아난다. 기각 근거 = 논리(결정 5 — 읽지도 지우지도 않아야 옛 코드와의 접점이 0 이다).
- **경로 정본을 base 에.** 폴더 이름은 도메인 지식이라 base 입주 조건(도메인 지식 0)을 어기고, 셋째 입주자는 ADR-0175 「거부한 대안」 첫 항목의 재심을 부른다. 기각 근거 = 코드 규칙(base `src/lib.rs` 헤더의 입주 조건).

## 근거

- **사용자 결정 2026-10-02** — 포터블 유지 · 컴포넌트 먼저 · state 는 지키고 run 은 버린다 · 토큰 든 파일은 `daemon\run\`(조사 보고서 「0. 결정」).
- **사용자 결정 2026-10-02 (P1 코드 리뷰 뒤)** — 폴더 이름을 업계 표준으로(`daemon\store\` → `daemon\state\` · 셸은 `shell\config\` 와 `shell\state\` 로 가른다) · 개발 루트 `.engram-dev` · `presets.json` 은 자리만 정한다 · 로그는 최상위 `logs\` 유지(결정 2 · 3 · 8).
- **사용자 결정 2026-10-02 (옛 데이터 버림)** — 「옛 데몬 데이터는 신경 쓰지 마, 날려도 됨, 아직 데이터 정립 안 됐으니」. 첫 부팅 이전 · 완료 표지 · 옛 자리 잠금 · 두 자리 읽기 · 개발 루트 이름 바꾸기를 걷는다(결정 5 · 6 · 8 · TRD §14-5).
- **조사(`/research` medium · cross-family 적대 리뷰 1회, 판정 BLOCK → 정정 반영)** — 기본은 OS 표준 폴더지만 포터블은 배포 형태에 딸린 선택이다(VS Code ZIP 의 `data/` · Windows Terminal 별도 포터블 배포, §2-4). 「피어가 OS 폴더를 쓴다」를 우리 ZIP 배포를 바꿀 근거로 쓴 것은 적대 리뷰가 정정했다. dev/release 분리와 워크트리 격리는 §2-5.
- **TRD 리뷰 2회(설계자 · 파괴자)** — 대응표 = TRD §14. 그중 이전 관련 항목(F2 · F3 · discovery 두 경로)은 결정 5 로 무의미해졌다.

## 영향 / 불변식

- **폴더 이름은 디스크 계약이다** — 바꾸면 그 아래 데이터가 고아가 된다. 다음에 배치를 바꿀 때는 그 시점에 지킬 데이터가 있는지부터 묻는다(「거부한 대안」 첫 부팅 이전의 재론 조건).
- **새 코드에 옛 평면 경로가 없다** — `DataLayout` 에 옛 경로 함수가 없고, 데몬 · discovery · 스크립트가 옛 자리를 이름으로 부르지 않는다. 옛 경로를 다시 들이면 결정 5 를 뒤집는 것이다.
- **같은 루트에서 옛 데몬과 새 데몬이 함께 돌 수 있다** — 잠금 파일이 다르므로 서로를 막지 않는다. 각자 자기 명부만 보며, 같은 자리를 공유하는 것은 최상위 `logs\` 뿐이다(파일 이름의 겹침 여부는 확인하지 않았다). 섞어 쓰는 것은 지원 대상이 아니고, 막는 장치도 두지 않는다.
- **업그레이드 안내:** 업그레이드 전 트레이에서 데몬을 끈다 — 새 도구는 옛 배치의 데몬을 보지 못한다(수동 종료 1회).
- **하향은 지원하지 않는다** — 옛 바이너리는 옛 평면 파일을 그대로 쓰고 `daemon\state\` 는 보지 않는다. 새 바이너리에서 만든 에이전트는 옛 바이너리에 보이지 않는다.
- **새 데몬 둘의 경합** — 먼저 뜬 쪽이 레코드를 발행하기 전(잠금 획득 ~ 발행)이면 뒤엣것은 `AlreadyRunning` 이 아니라 `FileBusy` 로 나간다(오늘도 같은 구간이 있다). 그래서 `FileBusy` 로그 문구는 「다른 프로그램, 또는 아직 발행 전인 다른 데몬이 쥐고 있음」이다.
- **바뀌는 경계:** net 잠금 획득은 데이터 폴더가 아니라 잠금 파일 경로를 받는다 · 데몬 MCP 설정 함수는 `mcp-config` 폴더를 받는다 · base 로그 초기화는 `logs` 폴더를 받는다. 셸 호출부는 discovery 공개 함수가 루트를 그대로 받으므로 바뀌지 않는다.
- **ADR-0136 결정 3의 대가가 갈린다** — 비밀 파일 이름이 무시 규칙의 열쇠라는 결합은 `agents.json*` 에 남고, `daemon\run\` 아래는 폴더 규칙이 덮어 새 토큰 파일이 그 아래 생기면 따로 줄을 더할 필요가 없다. `agents.json*` 의 꼬리 `*` 를 빼지 않는다.
- **ADR-0135 의 공유 모드 규칙은 새 자리 잠금에 그대로다.**
- **스크립트 · 문서:** 데몬 접속 파일을 찾는 스크립트(`scripts/engram.mjs` 등)는 새 경로 하나만 본다. CLAUDE.md 「백엔드 모듈 맵」 discovery 줄에 `DataLayout` 을 적는다.
- **코드 앵커 = `// ADR-0264`** — 경로 단일 출처(discovery `layout`) · 데몬 기동의 새 자리 잠금. 잠금 파일 = 접속 파일 자체는 ADR-0135, 무시 규칙의 파일 이름 원칙은 ADR-0136 을 함께 가리킨다.
