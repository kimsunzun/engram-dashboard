# ADR-0264: Split the data root into per-component state/run and do not migrate old data

- 상태: 확정 (2026-10-02, basis: user decision 2026-10-02 (`docs/research/storage-management-survey-2026-10-02.md` 「0. 결정」) + TRD `docs/process/S21-storage/trd.md` §2 · §3 · §11 (two review rounds applied — designer · destroyer) + user decision 2026-10-02 after the P1 code review (folder name store → industry-standard config/state · dev root `.engram-dev` — Decisions 2 · 3 · 8) + user decision 2026-10-02 (old data is discarded, not migrated — first-boot migration withdrawn · Decisions 5 · 6, TRD §14-5)) · 부분 폐기 by ADR-0271 (Decision 4's discovery DataLayout single source) · 부분 폐기 by ADR-0269 (the second reason for the rejected alternative of putting the path source of truth in base) · 부분 폐기 by ADR-0284 (Decision 1's reject-record file) · 부분 폐기 by ADR-0291 (Decision 2's diagram, the name of the corrupt copy)
- 관련: Amends ADR-0136 (adds the run folder rule and the agents.json copy pattern to Decision 3 · reverses Decision 2 — dev root `.engram-data` → `.engram-dev`, Decision 8) · Amends ADR-0135 (the lock file place of Decision 1 — one `daemon\run\daemon.json`, Decision 6) · ADR-0134 (data root location — kept as is, this decision decides only the layout inside it) · ADR-0024 (the single source of `default_data_dir` = discovery) · ADR-0129 (net — owns the single-instance guard) · ADR-0175 (base admission condition) · ADR-0230 (platform neutrality) · TRD `docs/process/S21-storage/trd.md` · research `docs/research/storage-management-survey-2026-10-02.md` · `crates/engram-dashboard-discovery/src/layout.rs` · step-log S21 · Amended by ADR-0271 (Decision 4's discovery DataLayout single source) · Amended by ADR-0269 (the second reason for the rejected alternative of putting the path source of truth in base) · Amended by ADR-0284 (Decision 1's reject-record file) · Amended by ADR-0291 (Decision 2's diagram, the name of the corrupt copy)

## 맥락

The inside of the data root (release `<exe>\data` · dev `<워크트리>\.engram-data` · test `ENGRAM_DATA_DIR` — ADR-0134 · ADR-0136) is **flat**. What must be kept — the registry, presets and reject record (`agents.json` · `presets.json` · `usage_rejects.json`) — and what is newly created or swept at every startup — the lock+connection file `daemon.json` (WS token) · the spawn attachment file `mcp-config\` (token) · the temporary `usage-probe\` — are mixed in one folder, and the shell file (`ui-settings.json`) and the logs are in the same place (research §1 inventory).

The storage management work (settings · screen state · webview folder — TRD S21-storage) increases the persistent files on the shell side. The rule for what goes where has to be set first. Path calculation was also scattered — net's lock acquisition · the daemon's MCP config · base's log initialization each received the data folder and attached names inside (TRD §2-2).

The flat layout is already used by deployed binaries. The first design moved it at first boot and laid down, together with it, devices to prevent mixing with old binaries (a completion marker · an old-place lock · reading from two places). Through the implementation and three code reviews, those devices kept producing boundary cases, and the user decided that **since the data is not yet settled, old data is discarded** (2026-10-02).

## 결정

1. **Data root location = stay portable.** ADR-0134 · ADR-0136 as is (release `<exe>\data` · dev `<워크트리>\.engram-dev` — only the dev-side name is changed by Decision 8). We do not go to an installed layout (Program Files + OS standard folders). This decision decides only the **layout inside** the root.
2. **Layout = component first, kind next.**
   ```
   <root>\
   ├─ daemon\
   │  ├─ state\          agents.json · presets.json · usage_rejects.json (+ .corrupt-* 사본)
   │  └─ run\            daemon.json(잠금 + 발견 · WS 토큰) · mcp-config\(토큰) · usage-probe\
   ├─ shell\
   │  ├─ config\         취향 — settings.json · (장래) slots\ · themes\
   │  ├─ state\          기억 — state.json(화면 상태)
   │  └─ run\            생길 때만 — 지금 없음
   ├─ webview\           WebView2 사용자 데이터 폴더 자리(옮기는 일은 뒤따르는 웹뷰 폴더 결정)
   └─ logs\              daemon-*.log · app-*.log (위치 현행 그대로)
   ```
   The daemon does not have a `config\` yet — if tunable values appear in the future, it will be `daemon\config\`. Logs go in the top-level `logs\` (each process has its own file · if the daemon and the client split onto different machines, each machine's `logs\` keeps only its own kind).
3. **Rule = `config\` · `state\` are kept and `run\` may be thrown away.** Folder names follow the industry standard — systemd `ConfigurationDirectory=` · `StateDirectory=` · `RuntimeDirectory=` · XDG `CONFIG_HOME` · `STATE_HOME` · `RUNTIME_DIR` (https://specifications.freedesktop.org/basedir/latest/ · systemd.exec man page). **Separation criterion: config = preference** (the 「어떻게」 — delete it and it returns to defaults) · **state = what the program remembers** (the 「무엇이 있나 · 어땠나」 — the agent registry is state even though the user made it. It is the same as Docker's `/var/lib`). The existing `presets.json` only gets its place decided as `daemon\state\`, and no new preset structure is made. Files holding tokens (`daemon.json` · `mcp-config\`) go only in `daemon\run\`.
4. **The single source of paths = discovery's `DataLayout` (new module `layout`).** Directories and **files that two or more processes see** (`daemon.json` — the daemon writes it and the shell and scripts read it) are computed by `DataLayout`. **A file name used by only one store is owned by that store** and attached only inside the directory it receives (`agents.json` · `presets.json` · `usage_rejects.json` — pulling the names in too would make the agent crate depend on discovery). Since net cannot depend on discovery (discovery → net), it receives the lock file path as an argument. The discovery public functions (`ensure_daemon` · `daemon_status` · `read_live_daemon` · `daemon_stop` · `send_stop`) take the root as is and use `DataLayout` inside. The OS separation stays only inside `default_data_dir` as now, and `DataLayout` is only `Path::join`.
5. **Old data is discarded, not migrated — the new code neither reads, moves, nor deletes old files.** The targets = the flat files of the release `<exe>\data\` (`agents.json` · `presets.json` · `usage_rejects.json` · root `daemon.json` · `mcp-config\` · `usage-probe\`) and the whole dev root `.engram-data\`. There is no first-boot migration · completion marker · move-in/preserve rule · case-variant handling. The new daemon creates only the new-place directories and starts with an empty registry. The old binary and the new binary share no state · lock · token file at all, so they do not interfere with each other — that old data is invisible to the new binary is **intended**. So single-instance exclusion (ADR-0134) now holds **only within one layout version** — an old-layout daemon and a new-layout daemon hold different lock files and can run together on the same root, they do not share state or token files, and the only thing they use together is `logs\` (file names split by pid). Cleaning up old files is the user's job (this worktree's `.engram-data` was deleted by the user by hand).
6. **There is one lock — `daemon\run\daemon.json`.** The old root `daemon.json` is neither held nor truncated. ADR-0135 Decision 1 (lock file = connection file) is unchanged for that file, and only the place moves. Discovery and the scripts (`scripts/engram.mjs` etc.) read **only the one new place** — there is no decision choosing between two places.
7. **`.gitignore` — `daemon\run\` alone is blocked by a folder rule.** Add `**/data/daemon/run/`, and block the registry with the tail pattern `**/data/daemon/state/agents.json*` (the `.corrupt-*` copies carry the same plaintext env). The dev root is blocked as a whole with `/.engram-dev/`. The old lines (`.engram-data/` · `**/data/daemon.json` · `**/data/agents.json*`) are **kept** — since the new code does not delete old files, the folders and the token-bearing flat files that remain in other worktrees and in unpacked old distributions must keep being ignored. The principle of ADR-0136 Decision 3 (block by the name of the file that holds secrets) is alive, and only `daemon\run\` is the exception with a folder rule — the path is specific, so it does not swallow unrelated folders.
8. **Dev data root name = `.engram-dev`** (formerly `.engram-data` — reverses ADR-0136 Decision 2). The convention = release name + `-dev` (herdr `herdr-dev` · orca `orca-dev`). `engram` is left so as not to overlap in repository root · search · ignore, and it also matches the dev identifier `com.engram.dashboard.dev`. **The old folder is not renamed** — `.engram-dev` starts fresh and the old `.engram-data` is left as is per Decision 5.

## 거부한 대안

- **Installed layout — Program Files + OS standard folders (`%APPDATA%` · `%LOCALAPPDATA%`) as the default.** Distribution is one ZIP · one user. The reasons for using OS folders (Program Files not writable · installer updates · multiple users · roaming) do not apply now. That peers use OS folders is not a basis by itself — VS Code also supports a portable `data/` in its ZIP distribution (research §2-4). Going to OS folders means worktree-by-worktree isolation would have to be kept separately by environment variables (research §2-5 — no peer does worktree isolation and our isolation is stronger). ★Strength of the rejection basis = **weak** (a policy statement — not quantitative · measured · code)★ — the user received the options of research §3 axis 1, (가) OS folder default + portable marker · (나) stay portable · (다) OS folder only, and chose (나). **Condition to revisit = after maturity · when a security need arises.**
- **Re-pointing the app directory in one go with Tauri 2.12's `appDirectoriesOverride`.** It is not in our Tauri 2.11.3 source (`tauri-2.11.3/src/path/desktop.rs:238-260` — it only appends the identifier). The first release that has it is 2.12.0, so an upgrade must come first (research §2-6). Basis for rejection = code (a check against the registry source).
- **Kind first — `state\daemon\` · `run\daemon\` (XDG style).** The daemon and the client may split onto different machines in the future, and with component first, `daemon\` can be moved as a whole folder. ★Strength of the rejection basis = **weak** (a future-readiness statement)★ — user decision.
- **Keeping the folder name `store`.** It is not a standard term — the words systemd and XDG use are config · state · runtime, and with standard names the separation criterion (preference / memory / may be thrown away) rides on the name and needs no separate explanation. Basis for rejection = user decision (industry standard first).
- **Keeping the dev root `.engram-data`.** The name alone does not tell that it is for debugging. Basis for rejection = user decision.
- **Dev root `.data-dev`.** It is a common name, so it overlaps with other things in search and ignore rules. Basis for rejection = user decision.
- **Keeping the flat layout.** What must be kept (the registry), what may be thrown away, and what holds tokens are mixed in one folder. Basis for rejection = code (the current layout — research §1).
- **First-boot migration (implemented and then withdrawn).** The design was: at startup the daemon moves the old flat state with `rename` and writes a completion marker last, it also holds the old root `daemon.json` as 0 bytes to block old binaries, and discovery reads two places and chooses (for the dev root, even renaming `.engram-data` → `.engram-dev`). Basis for rejection = **user decision** (the data is not yet settled — there is no old data worth keeping) + **the cost of that device**: through all three code reviews new boundary cases kept appearing — old file names differing only in case · renaming on FAT-family filesystems · links · lock order and races with old/new binaries mixed · move-in/preserve of stragglers after the marker · the reading interpretation of the 0-byte old lock. The same decision spread over three places: daemon · discovery · scripts. This decision also makes that alternative's sub-branches (「둘 다 있으면 새 것」 · 「새 자리 잠금 하나만」 · 「복사하고 옛 것을 남긴다」 · 「옛 자리 `daemon.json` 을 지워 본다」 · 「run 것도 옮긴다」) meaningless — the reasons for rejecting those were on the premise that a migration is done. **Condition to revisit = when the layout is changed again after there is data to keep** — start then from this item's list of boundary cases.
- **Deleting old data (discard it, but the new code cleans it up).** The moment the new code touches old files, the decision of 「무엇이 우리 것인가」 (a non-dedicated `ENGRAM_DATA_DIR` · someone else's file of the same name) and the failure handling of files held by the old binary come back. Basis for rejection = logic (Decision 5 — only if it neither reads nor deletes is the contact point with old code zero).
- **The path source of truth in base.** Folder names are domain knowledge, so it violates base's admission condition (zero domain knowledge), and a third tenant would call for a re-review of the first item of ADR-0175 「거부한 대안」. Basis for rejection = code rule (the admission condition in the header of base `src/lib.rs`).

## 근거

- **User decision 2026-10-02** — stay portable · component first · state is kept and run is thrown away · files holding tokens go in `daemon\run\` (research report 「0. 결정」).
- **User decision 2026-10-02 (after the P1 code review)** — folder names to the industry standard (`daemon\store\` → `daemon\state\` · the shell is split into `shell\config\` and `shell\state\`) · dev root `.engram-dev` · `presets.json` only gets its place decided · logs stay in the top-level `logs\` (Decisions 2 · 3 · 8).
- **User decision 2026-10-02 (old data discarded)** — 「옛 데몬 데이터는 신경 쓰지 마, 날려도 됨, 아직 데이터 정립 안 됐으니」. Withdraw the first-boot migration · completion marker · old-place lock · two-place reading · renaming of the dev root (Decisions 5 · 6 · 8 · TRD §14-5).
- **Research (`/research` medium · one cross-family adversarial review, decision BLOCK → corrections applied)** — the default is OS standard folders, but portable is a choice tied to the distribution form (VS Code ZIP's `data/` · Windows Terminal's separate portable distribution, §2-4). The adversarial review corrected the use of 「피어가 OS 폴더를 쓴다」 as a basis to change our ZIP distribution. dev/release separation and worktree isolation are in §2-5.
- **Two TRD review rounds (designer · destroyer)** — correspondence table = TRD §14. Among them, the migration-related items (F2 · F3 · discovery's two paths) became meaningless because of Decision 5.

## 영향 / 불변식

- **Folder names are a disk contract** — if changed, the data under them is orphaned. The next time the layout is changed, first ask whether there is data to keep at that time (the revisit condition of 「거부한 대안」 first-boot migration).
- **The new code has no old flat paths** — `DataLayout` has no old-path function, and the daemon · discovery · scripts do not call the old places by name. Bringing an old path back overturns Decision 5.
- **An old daemon and a new daemon can run together on the same root** — the lock files differ, so they do not block each other. Each sees only its own registry, and the only place they share is the top-level `logs\` (whether the file names overlap was not checked). Mixing them is not a supported case, and no device blocks it either.
- **Upgrade notice:** before upgrading, turn off the daemon from the tray — the new tools cannot see a daemon of the old layout (one manual shutdown).
  - (2026-10-02 user judgment — the user is the only user, so no release-note notice is placed · TRD §14-7)
- **Downgrade is not supported** — the old binary keeps using the old flat files and does not look at `daemon\state\`. Agents made with the new binary are invisible to the old binary.
- **A race between two new daemons** — if it is before the one that started first has published the record (lock acquisition ~ publication), the later one exits with `FileBusy`, not `AlreadyRunning` (the same interval exists today). So the `FileBusy` log text is 「다른 프로그램, 또는 아직 발행 전인 다른 데몬이 쥐고 있음」.
- **Boundaries that change:** net's lock acquisition receives the lock file path, not the data folder · the daemon's MCP config function receives the `mcp-config` folder · base's log initialization receives the `logs` folder. The shell call sites do not change, since the discovery public functions take the root as is.
- **The cost of ADR-0136 Decision 3 splits** — the coupling that the secret file's name is the key of the ignore rule remains for `agents.json*`, and under `daemon\run\` the folder rule covers it, so when a new token file is created under it there is no need to add a separate line. Do not remove the tail `*` of `agents.json*`.
- **ADR-0135's shared-mode rule applies as is to the new-place lock.**
- **Scripts · documents:** the scripts that look for the daemon connection file (`scripts/engram.mjs` etc.) look at only one new path. Write `DataLayout` in the discovery line of CLAUDE.md 「백엔드 모듈 맵」.
- **Code anchor = `// ADR-0264`** — the single source of paths (discovery `layout`) · the new-place lock at daemon startup. The anchor also points to ADR-0135 for lock file = connection file itself, and to ADR-0136 for the file-name principle of the ignore rule.
