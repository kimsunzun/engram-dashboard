# ADR-0264: Split the data root into per-component state/run, and do not move the old data

- 상태: 확정 (2026-10-02, basis: user decision 2026-10-02 (`docs/research/storage-management-survey-2026-10-02.md` 「0. 결정」) + TRD `docs/process/S21-storage/trd.md` §2 · §3 · §11 (reflects 2 reviews — designer · destroyer) + user decision 2026-10-02 after the P1 code review (folder name store → industry-standard config/state · development root `.engram-dev` — decisions 2 · 3 · 8) + user decision 2026-10-02 (old data is discarded, not moved — first-boot migration withdrawn · decisions 5 · 6, TRD §14-5)) · 부분 폐기 by ADR-0271 (the discovery DataLayout single source in decision 4) · 부분 폐기 by ADR-0269 (the second reason of the rejected alternative of putting the canonical path source in base) · 부분 폐기 by ADR-0284 (the rejection record file of decision 1) · 부분 폐기 by ADR-0291 (the corrupt-copy name in the diagram of decision 2)
- 관련: Amends ADR-0136 (decision 3 gains the run-folder rule and the agents.json copy pattern · decision 2 reversed — the development root name is `.engram-dev` (the old `.engram-data` is not moved)) · Amends ADR-0135 (the lock file location of decision 1 — a single `daemon\run\daemon.json`, decision 6) · ADR-0134(data root location — kept as is; this decision settles only the layout inside it) · ADR-0024(the single source of `default_data_dir` = discovery) · ADR-0129(net — owns the single-instance guard) · ADR-0175(base residency conditions) · ADR-0230(platform neutrality) · TRD `docs/process/S21-storage/trd.md` · survey `docs/research/storage-management-survey-2026-10-02.md` · `crates/engram-dashboard-discovery/src/layout.rs` · step-log S21 · Amended by ADR-0271 (the discovery DataLayout single source in decision 4) · Amended by ADR-0269 (the second reason of the rejected alternative of putting the canonical path source in base) · Amended by ADR-0284 (the rejection record file of decision 1) · Amended by ADR-0291 (the corrupt-copy name in the diagram of decision 2)

## 맥락

The inside of the data root (release `<exe>\data` · development `<워크트리>\.engram-data` · test `ENGRAM_DATA_DIR` — ADR-0134 · ADR-0136) is **flat**. What must be kept — the registry, presets and rejection record (`agents.json` · `presets.json` · `usage_rejects.json`) — and what is recreated or swept at every start — the lock+connection file `daemon.json` (WS token) · the spawn attachment folder `mcp-config\` (token) · the temporary `usage-probe\` — are mixed in one folder, and the shell file (`ui-settings.json`) and the logs sit in the same place (survey §1 inventory).

Storage management work (settings · screen state · webview folder — TRD S21-storage) increases the persistent files on the shell side. The rule for what goes where has to be set first. Path computation was also scattered — net lock acquisition · the daemon MCP config · base log initialization each received the data folder and named things inside it (TRD §2-2).

The flat layout is used by the already-shipped binaries. The first design came with devices to move it at first boot and to prevent mixing with old binaries (completion marker · old-location lock · reading both locations). Through implementation and 3 code reviews those devices kept producing boundary cases, and the user decided **the data is not yet settled, so old data is discarded** (2026-10-02).

## 결정

1. **Data root location = stay portable.** ADR-0134 · ADR-0136 stand as they are (release `<exe>\data` · development `<워크트리>\.engram-dev` — decision 8 changes only the development name). We do not go to an installed layout (Program Files + OS standard folders). This decision settles only the **layout inside** the root.
2. **Layout = component first, kind second.**
   ```
   <root>\
   ├─ daemon\
   │  ├─ state\          agents.json · presets.json · usage_rejects.json (+ .corrupt-* 사본)
   │  └─ run\            daemon.json(잠금 + 발견 · WS 토큰) · mcp-config\(토큰) · usage-probe\
   ├─ shell\
   │  ├─ config\         취향 — settings.json · (장래) slots\ · themes\
   │  ├─ state\          기억 — state.json(화면 상태)
   │  └─ run\            생길 때만 — 지금 없음
   ├─ webview\           WebView2 사용자 데이터 폴더 자리(옮기는 일은 뒤따르는 웹뷰 폴더 결정)
   └─ logs\              daemon-*.log · app-*.log (위치 현행 그대로)
   ```
   The daemon has no `config\` yet — if a tunable appears later it goes to `daemon\config\`. Logs go in the top-level `logs\` (each process has its own file · if the daemon and the client split onto different machines, each machine's `logs\` keeps only its own kinds).
3. **Rule = `config\` · `state\` are kept, `run\` may be discarded.** Folder names follow the industry standard — systemd `ConfigurationDirectory=` · `StateDirectory=` · `RuntimeDirectory=` · XDG `CONFIG_HOME` · `STATE_HOME` · `RUNTIME_DIR`(https://specifications.freedesktop.org/basedir/latest/ · systemd.exec man page). **Dividing criterion: config = preference**(「어떻게」 — delete it and it returns to the defaults) · **state = what the program remembers**(「무엇이 있나 · 어땠나」 — the agent registry is state even though the user made it. Same as Docker's `/var/lib`). The existing `presets.json` only has its place fixed at `daemon\state\` and no new preset structure is made. Files holding tokens (`daemon.json` · `mcp-config\`) are placed only in `daemon\run\`.
4. **Single source of paths = discovery's `DataLayout` (new module `layout`).** Directories and **files that two or more processes look at** (`daemon.json` — the daemon writes it, the shell and scripts read it) are computed by `DataLayout`. **A file name used by only one store is owned by that store**, which attaches it only inside the directory it receives (`agents.json` · `presets.json` · `usage_rejects.json` — pulling the names in would make the agent crate depend on discovery). net cannot depend on discovery (discovery → net), so it receives the lock file path as an argument. The public discovery functions (`ensure_daemon` · `daemon_status` · `read_live_daemon` · `daemon_stop` · `send_stop`) take the root as is and use `DataLayout` inside. The OS split stays only inside `default_data_dir` as now, and `DataLayout` is nothing but `Path::join`.
5. **Old data is discarded, not moved — the new code neither reads, moves nor deletes old files.** Targets = the flat files of release `<exe>\data\` (`agents.json` · `presets.json` · `usage_rejects.json` · root `daemon.json` · `mcp-config\` · `usage-probe\`) and the development root `.engram-data\` as a whole. There is no first-boot migration · completion marker · move-in/preserve rule · case-variant handling. The new daemon creates only the new-location directories and starts with an empty registry. The old and new binaries share none of the state · lock · token files, so they do not interfere — that old data is invisible to the new binary is **intended**. So the single-instance exclusion (ADR-0134) now holds **only within one layout version** — an old-layout daemon and a new-layout daemon hold different lock files and can run together on the same root, share no state · token files, and the only thing they write to in common is `logs\` (file names split by pid). Cleaning up old files is the user's job (this worktree's `.engram-data` was deleted by the user by hand).
6. **One lock — `daemon\run\daemon.json`.** The old root `daemon.json` is neither taken nor truncated. ADR-0135 decision 1 (lock file = connection file) holds as is for that file and only its location moves. discovery and scripts (`scripts/engram.mjs` etc.) read **only the one new location** — there is no decision that picks between two locations.
7. **`.gitignore` — `daemon\run\` alone is blocked by a folder rule.** Add `**/data/daemon/run/`, and block the registry with the tail pattern `**/data/daemon/state/agents.json*` (the `.corrupt-*` copies carry the same plaintext env). The development root is blocked as a whole with `/.engram-dev/`. The old lines (`.engram-data/` · `**/data/daemon.json` · `**/data/agents.json*`) are **kept** — since the new code does not delete old files, the folders and the token-bearing flat files left in other worktrees · unzipped old distributions must keep being ignored. The principle of ADR-0136 decision 3 (block by the name of the file that holds secrets) stays alive, and only `daemon\run\` is an exception with a folder rule — the path is specific, so it does not swallow unrelated folders.
8. **Development data root name = `.engram-dev`**(old `.engram-data` — reverses ADR-0136 decision 2). Convention = release name + `-dev`(herdr `herdr-dev` · orca `orca-dev`). `engram` is left alone so as not to collide in the repository root · search · ignore, and it matches the development identifier `com.engram.dashboard.dev`. **We do not rename** — `.engram-dev` starts fresh and the old `.engram-data` is left as is per decision 5.

## 거부한 대안

- **Installed layout — Program Files + OS standard folders (`%APPDATA%` · `%LOCALAPPDATA%`) as the default.** Distribution is a single ZIP and one user. The reasons for using OS folders (Program Files not writable · installer updates · multiple users · roaming) do not apply now. That peers use OS folders is not enough as a basis — VS Code also supports a portable `data/` in its ZIP distribution (survey §2-4). Going to OS folders means worktree isolation has to be kept separately with environment variables (survey §2-5 — no peer does worktree isolation, and our isolation is stronger). ★Strength of the rejection basis = **weak**(a policy statement — not quantitative · measured · code)★ — the user received the options of survey §3 axis 1 (ga) OS folder default + portable marker · (na) stay portable · (da) OS folder only, and chose (na). **Reopen condition = after maturity · when a security need arises.**
- **Reassign the app directory in one go with Tauri 2.12's `appDirectoriesOverride`.** It is not in our Tauri 2.11.3 source (`tauri-2.11.3/src/path/desktop.rs:238-260` — it only appends the identifier). The first release with it is 2.12.0, so an upgrade has to come first (survey §2-6). Rejection basis = code (registry source cross-check).
- **Kind first — `state\daemon\` · `run\daemon\`(XDG style).** The daemon and the client may later split onto different machines, and with component-first the `daemon\` folder can be moved as a whole. ★Strength of the rejection basis = **weak**(a statement about future preparation)★ — user decision.
- **Keep the folder name `store`.** It is not a standard term — what systemd · XDG use is config · state · runtime, and with a standard name the dividing criterion (preference / memory / may be discarded) rides on the name with no separate explanation. Rejection basis = user decision (industry standard first).
- **Keep the development root `.engram-data`.** The name alone does not tell that it is for debugging. Rejection basis = user decision.
- **Development root `.data-dev`.** It is a common name, so it collides with other things in search · ignore rules. Rejection basis = user decision.
- **Keep it flat.** What must be kept (the registry), what may be discarded, and what holds tokens are mixed in one folder. Rejection basis = code (the current layout — survey §1).
- **First-boot migration (implemented, then withdrawn).** The design had the daemon move the old flat state with `rename` at startup and write the completion marker last, also hold the old root `daemon.json` at 0 bytes to block old binaries, and have discovery read both locations and pick (the development root even renamed `.engram-data` → `.engram-dev`). Rejection basis = **user decision** (the data is not yet settled — there is no old data worth keeping) + **the cost of those devices**: throughout 3 code reviews new boundary cases kept appearing — old file names differing only in case · rename on FAT-family file systems · links · lock order and races with old/new binaries mixed · move-in/preserve of stragglers after the marker · reading a 0-byte old lock. The same decision spread over three places: daemon · discovery · scripts. This decision also makes the sub-branches of that alternative (「둘 다 있으면 새 것」 · 「새 자리 잠금 하나만」 · 「복사하고 옛 것을 남긴다」 · 「옛 자리 `daemon.json` 을 지워 본다」 · 「run 것도 옮긴다」) meaningless — those rejection reasons stood on the premise that a migration is done. **Reopen condition = when the layout is changed again after data worth keeping exists** — then start from this item's list of boundary cases.
- **Delete the old data (discard it, but have the new code clean it up).** The moment the new code touches old files, the decision 「무엇이 우리 것인가」 (a non-dedicated `ENGRAM_DATA_DIR` · someone else's file with the same name) and the failure handling for files held by an old binary come back. Rejection basis = logic (decision 5 — it must neither read nor delete so that the contact point with old code is 0).
- **Put the canonical path source in base.** Folder names are domain knowledge, which violates base's residency condition (0 domain knowledge), and a third resident invites a re-examination of the first item of ADR-0175 「거부한 대안」. Rejection basis = code rule (the residency condition in the header of base `src/lib.rs`).

## 근거

- **User decision 2026-10-02** — stay portable · component first · keep state and discard run · token-bearing files go in `daemon\run\`(survey report 「0. 결정」).
- **User decision 2026-10-02 (after the P1 code review)** — folder names to the industry standard (`daemon\store\` → `daemon\state\` · the shell is split into `shell\config\` and `shell\state\`) · development root `.engram-dev` · `presets.json` only gets a place · logs stay at top-level `logs\` (decisions 2 · 3 · 8).
- **User decision 2026-10-02 (discard old data)** — 「옛 데몬 데이터는 신경 쓰지 마, 날려도 됨, 아직 데이터 정립 안 됐으니」. Withdraws first-boot migration · completion marker · old-location lock · reading both locations · renaming the development root (decisions 5 · 6 · 8 · TRD §14-5).
- **Survey (`/research` medium · one cross-family adversarial review, verdict BLOCK → corrections applied)** — the default is the OS standard folder, but portable is a choice tied to the distribution form (VS Code ZIP's `data/` · Windows Terminal's separate portable distribution, §2-4). Using 「피어가 OS 폴더를 쓴다」 as grounds to change our ZIP distribution was corrected by the adversarial review. dev/release separation and worktree isolation are in §2-5.
- **2 TRD reviews (designer · destroyer)** — correspondence table = TRD §14. The migration-related items among them (F2 · F3 · discovery's two paths) became meaningless because of decision 5.

## 영향 / 불변식

- **The folder name is a disk contract** — changing it orphans the data under it. The next time the layout changes, first ask whether there is data to keep at that point (the reopen condition of the first-boot migration in 「거부한 대안」).
- **The new code has no old flat path** — `DataLayout` has no old-path function, and the daemon · discovery · scripts do not name the old location. Bringing an old path back would reverse decision 5.
- **An old daemon and a new daemon can run together on the same root** — the lock files differ, so they do not block each other. Each sees only its own registry, and the only place they share is the top-level `logs\` (whether file names overlap has not been checked). Mixed use is not supported, and no device blocks it either.
- **Upgrade note:** stop the daemon from the tray before upgrading — the new tooling cannot see a daemon of the old layout (one manual shutdown).
  - (2026-10-02 user judgment — the user is the only user, so no release-note notice is put in · TRD §14-7)
- **Downgrade is not supported** — an old binary keeps using the old flat files and does not look at `daemon\state\`. Agents created by the new binary are not visible to the old binary.
- **Race between two new daemons** — if it happens before the one that started first publishes its record (lock acquisition to publication), the later one exits with `FileBusy` rather than `AlreadyRunning` (the same window exists today). So the `FileBusy` log text is 「다른 프로그램, 또는 아직 발행 전인 다른 데몬이 쥐고 있음」.
- **Boundaries that change:** net lock acquisition takes the lock file path instead of the data folder · the daemon MCP config function takes the `mcp-config` folder · base log initialization takes the `logs` folder. Shell call sites do not change because the public discovery functions still take the root as is.
- **The cost of ADR-0136 decision 3 is split** — the coupling that secret file names are the key of the ignore rule remains for `agents.json*`, and under `daemon\run\` the folder rule covers everything, so no separate line is needed when a new token file appears there. The tail `*` of `agents.json*` is not removed.
- **ADR-0135's shared-mode rule stays as is for the new-location lock.**
- **Scripts · docs:** scripts that look for the daemon connection file (`scripts/engram.mjs` etc.) look at one new path only. `DataLayout` is written on the discovery line of CLAUDE.md 「백엔드 모듈 맵」.
- **Code anchor = `// ADR-0264`** — the single source of paths (discovery `layout`) · the new-location lock at daemon startup. The lock file = connection file itself points to ADR-0135, and the file-name principle of the ignore rule points to ADR-0136 together.
