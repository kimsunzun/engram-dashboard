# ADR-0264: Split the data root per component into state/run and do not migrate old data

- 상태: 확정 (2026-10-02, basis: user decision 2026-10-02 (`docs/research/storage-management-survey-2026-10-02.md` 「0. 결정」) + TRD `docs/process/S21-storage/trd.md` §2 · §3 · §11 (two review rounds applied — designer · destroyer) + user decision 2026-10-02 after the P1 code review (folder name store → industry-standard config/state · dev root `.engram-dev` — decisions 2 · 3 · 8) + user decision 2026-10-02 (old data is discarded, not migrated — first-boot migration withdrawn · decisions 5 · 6, TRD §14-5)) · 부분 폐기 by ADR-0271 (decision 4's single source of discovery DataLayout) · 부분 폐기 by ADR-0269 (second reason for the rejected alternative of a path canon in base) · 부분 폐기 by ADR-0284 (decision 1's rejection record file) · 부분 폐기 by ADR-0291 (decision 2's corrupt-copy name in the diagram) · 부분 폐기 by ADR-0323 (third category added)

## 맥락

The inside of the data root (release `<exe>\data` · dev `<워크트리>\.engram-data` · test `ENGRAM_DATA_DIR` — ADR-0134 · ADR-0136) is **flat**. What must be kept — the registry, presets and rejection record (`agents.json` · `presets.json` · `usage_rejects.json`) — and what is recreated or swept on every launch — the lock+connection file `daemon.json` (WS token) · the spawn attach file `mcp-config\` (token) · temporary `usage-probe\` — are mixed in one folder, and the shell file (`ui-settings.json`) and the logs sit in the same place (research §1 inventory).

The storage management work (settings · screen state · webview folder — TRD S21-storage) adds more persistent files on the shell side. A rule for what goes where has to exist first. Path computation was also scattered — the net lock acquisition, the daemon MCP config and the base log initialization each received a data folder and named files inside it themselves (TRD §2-2).

The flat layout is already used by the deployed binary. The first design moved it on the first boot and laid down, together with that, mechanisms that prevent mixing with the old binary (a completion marker · a lock at the old location · reading from two locations). Over implementation and three code review rounds those mechanisms kept producing edge cases, and the user decided that **the data is not settled yet, so old data is discarded** (2026-10-02).

## 결정

1. **Data root location = stay portable.** ADR-0134 · ADR-0136 stay as they are (release `<exe>\data` · dev `<워크트리>\.engram-dev` — only the dev name is changed by decision 8). We do not move to an installed layout (Program Files + OS standard folders). This decision fixes only the **layout inside** the root.
2. **Layout = component first, kind second.**
   ```
   <root>\
   ├─ daemon\
   │  ├─ state\          agents.json · presets.json · usage_rejects.json (+ .corrupt-* 사본)
   │  └─ run\            daemon.json(잠금 + 발견 · WS 토큰) · mcp-config\(토큰) · usage-probe\
   ├─ shell\
   │  ├─ config\         취향 — settings.json · (장래) slots\ · themes\
   │  ├─ state\          기억 — state.json(화면 상태)
   │  └─ run\            생길 때만 — 지금 없음
   ├─ webview\           WebView2 사용자 데이터 폴더 자리(옮기는 일은 뒤따르는 웹뷰 폴더 결정)
   └─ logs\              daemon-*.log · app-*.log (위치 현행 그대로)
   ```
   The daemon has no `config\` yet — if tuning values appear later it will be `daemon\config\`. The log stays in the top-level `logs\` (each process has its own file · if the daemon and the client are split across machines, each machine's `logs\` keeps only its own kinds).
3. **Rule = `config\` · `state\` are kept and `run\` may be discarded.** Folder names follow the industry standard — systemd `ConfigurationDirectory=` · `StateDirectory=` · `RuntimeDirectory=` · XDG `CONFIG_HOME` · `STATE_HOME` · `RUNTIME_DIR` (https://specifications.freedesktop.org/basedir/latest/ · systemd.exec man page). **Dividing criterion: config = preference** (「어떻게」 — deleting it returns to defaults) · **state = what the program remembers** (「무엇이 있나 · 어땠나」 — the agent registry is state even though the user made it. Same as Docker's `/var/lib`). The existing `presets.json` only gets its location fixed as `daemon\state\`, and no new preset structure is created. Files that hold tokens (`daemon.json` · `mcp-config\`) go only in `daemon\run\`.
4. **Single source of paths = discovery's `DataLayout` (new module `layout`).** Directories and **files that two or more processes look at** (`daemon.json` — the daemon writes it and the shell and scripts read it) are computed by `DataLayout`. **A file name used by only one store is owned by that store** and is attached only inside the directory it receives (`agents.json` · `presets.json` · `usage_rejects.json` — pulling the name in as well would make the agent crate depend on discovery). Since net cannot depend on discovery (discovery → net), it receives the lock file path as an argument. The public discovery functions (`ensure_daemon` · `daemon_status` · `read_live_daemon` · `daemon_stop` · `send_stop`) take the root as it is and use `DataLayout` inside. The OS split stays only inside `default_data_dir` as today, and `DataLayout` is only `Path::join`.
5. **Old data is discarded, not migrated — new code neither reads, moves nor deletes old files.** Targets = the flat files of the release `<exe>\data\` (`agents.json` · `presets.json` · `usage_rejects.json` · root `daemon.json` · `mcp-config\` · `usage-probe\`) and the whole dev root `.engram-data\`. There is no first-boot migration · completion marker · move-in/keep rule · case-variant handling. The new daemon only creates the new-location directories and starts with an empty registry. The old and new binaries share none of the state · lock · token files, so they do not interfere with each other — that old data is invisible to the new binary is **intended**. So single-instance exclusion (ADR-0134) now holds **only within one layout version** — an old-layout daemon and a new-layout daemon hold different lock files, so they can run together on the same root; they do not share state · token files, and the only thing they use in common is `logs\` (file names split by pid). Cleaning up old files is the user's job (this worktree's `.engram-data` was deleted by hand by the user).
6. **There is one lock — `daemon\run\daemon.json`.** The old root's `daemon.json` is neither taken nor truncated. ADR-0135 decision 1 (lock file = connection file) stays as is for that file and only its location moves. discovery and scripts (`scripts/engram.mjs` etc.) read **only the one new location** — there is no decision that picks between two locations to read.
7. **`.gitignore` — only `daemon\run\` is blocked by a folder rule.** Add `**/data/daemon/run/`, and block the registry with the tail pattern `**/data/daemon/state/agents.json*` (the `.corrupt-*` copy also carries the same plaintext env). For the dev root, `/.engram-dev/` is blocked as a whole. The old lines (`.engram-data/` · `**/data/daemon.json` · `**/data/agents.json*`) are **kept** — since new code does not delete old files, folders left in other worktrees and in unpacked old distributions, and the token-bearing flat files, must keep being ignored. The principle of ADR-0136 decision 3 (block by the name of the file that holds secrets) is alive, and only `daemon\run\` is an exception with a folder rule — the path is specific, so it does not swallow unrelated folders.
8. **Dev data root name = `.engram-dev`** (formerly `.engram-data` — reverses ADR-0136 decision 2). Convention = release name + `-dev` (herdr `herdr-dev` · orca `orca-dev`). `engram` stays so that it does not overlap in the repository root · search · ignore, and it also matches the dev identifier `com.engram.dashboard.dev`. **The name is not changed** — `.engram-dev` starts fresh and the old `.engram-data` is left as it is per decision 5.

## 거부한 대안

- **Installed layout — Program Files + OS standard folders (`%APPDATA%` · `%LOCALAPPDATA%`) by default.** Distribution is one ZIP · one user. The reasons for using OS folders (Program Files not writable · installer updates · multiple users · roaming) do not apply now. That peers use OS folders is not by itself a ground — VS Code also supports a portable `data/` for ZIP distribution (research §2-4). Going to OS folders means worktree isolation has to be kept separately through environment variables (research §2-5 — no peer does worktree isolation, and our isolation is stronger). ★Strength of the rejection ground = **weak**(policy statement — not quantitative · not measured · not code)★ — the user took options (a) OS folder default + portable marker · (b) stay portable · (c) OS folder only from research §3 axis 1 and chose (b). **Condition to revisit = after maturity · when a security need arises.**
- **Redirect the app directory at once with Tauri 2.12's `appDirectoriesOverride`.** It is not in our Tauri 2.11.3 source (`tauri-2.11.3/src/path/desktop.rs:238-260` — only the identifier is attached). The first release that has it is 2.12.0, so an upgrade must come first (research §2-6). Rejection ground = code (checked against the registry source).
- **Kind first — `state\daemon\` · `run\daemon\` (XDG style).** The daemon and the client may later split across machines, and with component first `daemon\` can be moved as a whole folder. ★Strength of the rejection ground = **weak**(statement about future preparation)★ — user decision.
- **Keep the folder name `store`.** It is not a standard term — what systemd · XDG use is config · state · runtime, and with a standard name the dividing criterion (preference / remembered / may be discarded) is carried by the name and needs no separate explanation. Rejection ground = user decision (industry standard first).
- **Keep the dev root `.engram-data`.** The name alone does not tell that it is for debugging. Rejection ground = user decision.
- **Dev root `.data-dev`.** It is a common name, so it overlaps with other things in search · ignore rules. Rejection ground = user decision.
- **Keep it flat.** What must be kept (the registry) and what may be discarded · what holds tokens are mixed in one folder. Rejection ground = code (current layout — research §1).
- **First-boot migration (implemented, then withdrawn).** The design was that the daemon moves the old flat state with `rename` at startup, writes the completion marker last, also holds the old root's `daemon.json` at 0 bytes to block the old binary, and discovery reads two locations and picks one (for the dev root, even renaming `.engram-data` → `.engram-dev`). Rejection ground = **user decision** (the data is not settled yet — there is no old data worth keeping) + **the cost of that mechanism**: new edge cases kept appearing through all three code review rounds — old file names that differ only in case · rename on FAT-family file systems · links · lock order and races while old and new binaries are mixed · move-in/keep of stragglers after the marker · reading semantics of a 0-byte old lock. The same decision was spread over three places: daemon · discovery · scripts. This decision also makes the sub-branches of that alternative (「둘 다 있으면 새 것」 · 「새 자리 잠금 하나만」 · 「복사하고 옛 것을 남긴다」 · 「옛 자리 `daemon.json` 을 지워 본다」 · 「run 것도 옮긴다」) meaningless — their rejection reasons were built on the premise that migration happens. **Condition to revisit = when the layout is changed again after there is data worth keeping** — start then from this item's list of edge cases.
- **Delete old data (discard it, but new code cleans it up).** The moment new code touches old files, the 「무엇이 우리 것인가」 decision (`ENGRAM_DATA_DIR` that is not dedicated · another party's file with the same name) and the failure handling of files held by the old binary come back. Rejection ground = logic (decision 5 — only by neither reading nor deleting is the contact point with old code zero).
- **Path canon in base.** Folder names are domain knowledge, so it breaks the base admission condition (zero domain knowledge), and a third tenant calls for a re-examination of the first item of ADR-0175 「거부한 대안」. Rejection ground = code rule (the admission condition in the base `src/lib.rs` header).

## 근거

- **User decision 2026-10-02** — stay portable · component first · state is kept and run is discarded · token-bearing files go to `daemon\run\` (research report 「0. 결정」).
- **User decision 2026-10-02 (after the P1 code review)** — folder names to the industry standard (`daemon\store\` → `daemon\state\` · the shell splits into `shell\config\` and `shell\state\`) · dev root `.engram-dev` · `presets.json` only gets its location fixed · the log stays in the top-level `logs\` (decisions 2 · 3 · 8).
- **User decision 2026-10-02 (old data discarded)** — 「옛 데몬 데이터는 신경 쓰지 마, 날려도 됨, 아직 데이터 정립 안 됐으니」. First-boot migration · completion marker · lock at the old location · reading from two locations · dev root rename are withdrawn (decisions 5 · 6 · 8 · TRD §14-5).
- **Research (`/research` medium · one cross-family adversarial review, decision BLOCK → corrections applied)** — the default is OS standard folders, but portable is a choice tied to the distribution form (VS Code's `data/` for ZIP · Windows Terminal's separate portable distribution, §2-4). Using 「피어가 OS 폴더를 쓴다」 as a ground to change our ZIP distribution was corrected by the adversarial review. dev/release separation and worktree isolation are in §2-5.
- **TRD review, two rounds (designer · destroyer)** — response table = TRD §14. Of these, the migration-related items (F2 · F3 · the two discovery paths) became meaningless through decision 5.

## 영향 / 불변식

- **The folder names are a disk contract** — changing them orphans the data below. The next time the layout is changed, first ask whether there is data worth keeping at that point (「거부한 대안」 the condition to revisit for first-boot migration).
- **New code has no old flat paths** — `DataLayout` has no old path functions, and the daemon · discovery · scripts do not call the old locations by name. Bringing an old path back reverses decision 5.
- **An old daemon and a new daemon can run together on the same root** — the lock files differ, so they do not block each other. Each sees only its own registry, and the only thing they share is the top-level `logs\` (whether file names overlap was not checked). Mixing is not supported, and no mechanism blocks it.
- **Upgrade notice:** before upgrading, turn off the daemon from the tray — the new tooling does not see a daemon of the old layout (one manual shutdown).
  - (user judgment 2026-10-02 — the user is the only user, so no release-note notice is made · TRD §14-7)
- **Downgrade is not supported** — the old binary keeps using the old flat files as they are and does not look at `daemon\state\`. Agents made with the new binary are not visible to the old binary.
- **Race between two new daemons** — if it is before the first one publishes its record (from lock acquisition to publishing), the later one exits with `FileBusy` rather than `AlreadyRunning` (the same window exists today). So the `FileBusy` log wording is 「다른 프로그램, 또는 아직 발행 전인 다른 데몬이 쥐고 있음」.
- **Boundaries that change:** net lock acquisition receives the lock file path, not the data folder · the daemon MCP config function receives the `mcp-config` folder · base log initialization receives the `logs` folder. The shell call sites do not change, since the public discovery functions take the root as it is.
- **The cost of ADR-0136 decision 3 is split** — the coupling that a secret file name is the key to the ignore rule stays in `agents.json*`, and under `daemon\run\` the folder rule covers it, so when a new token file appears there no separate line has to be added. The tail `*` of `agents.json*` is not removed.
- **ADR-0135's shared-mode rule stays as is for the new-location lock.**
- **Scripts · docs:** scripts that look for the daemon connection file (`scripts/engram.mjs` etc.) look at the one new path only. `DataLayout` is written in the CLAUDE.md 「백엔드 모듈 맵」 discovery line.
- **Code anchor = `// ADR-0264`** — the single source of paths (discovery `layout`) · the new-location lock at daemon startup. That the lock file = the connection file itself points to ADR-0135, and the file-name principle of the ignore rule points to ADR-0136.
