# ADR-0130: 데몬 lib 추가 분리 보류 — 목적은 net 분리로 달성, 응용 층은 소비자 없음

- 상태: 확정 (2026-08-05, 근거: 사용자 결정 + 데몬 crate 내부 의존 그래프 전수 실측)
- 관련: Amends ADR-0129 (결정 2와 3 보류) · ADR-0020(경계 부식 이력 — 이 결정이 그 교훈의 적용 범위를 좁힌다) · ADR-0110(컴파일러 강제 벽 idiom) · ADR-0029(에이전트 호스트 = 데몬 프로세스) · step-log S18.24

## 맥락

ADR-0129는 데몬 lib을 3층(네트워크 lib · 에이전트 시스템 lib · 얇은 조립 바이너리)으로 가르기로 정했다. **결정 1(네트워크 lib)은 이행됐다** — `engram-dashboard-net` 이 에이전트 어휘 0으로 독립했고, 그 crate lib.rs 헤더의 격리 게이트가 이를 강제한다.

결정 2·3(응용 층 lib 추출 + 조립 얇게)에 착수하기 전, 사용자가 범위를 되물었다: *"내가 요구했던 net 분리는 됐잖아. 나머지를 리팩터링하는 이유가 뭐냐."* 이 물음에 답하려고 데몬 crate 내부 의존 그래프를 전수 실측했고, 그 결과가 아래 근거다. **사용자 결론: "거기까지는 오버"** — 데몬 crate를 더 쪼개지 않는다.

## 결정

**ADR-0129의 결정 2·3을 보류한다.** `engram-dashboard-daemon` 은 응용 층(연결 코어 · 연결 어댑터 · 상태 팬아웃 · 메시징 호스트 · 제어 평면)과 조립을 **한 crate로 유지**한다.

- 결정 1과 그 격리 게이트는 **그대로 유효**하다 — 이 ADR은 결정 1을 건드리지 않는다.
- 보류는 **폐기가 아니다** — 아래 §영향의 재개 조건 중 하나라도 관측되면 ADR-0129의 목표 모양을 다시 꺼낸다. ★어휘 주의★: ADR-0129 상태줄에 찍힌 `부분 폐기 by ADR-0130` 은 `/adr` 스크립트의 **정형 도장 문구**이고, 이 관계의 실질은 보류다. 그 도장을 "결정 2·3이 죽었다"로 읽지 말 것.

## 거부한 대안

- **제어 평면만 별도 crate로 추출(옵션 A)** — 실측상 가장 싸다. `control/` 은 다른 데몬 모듈로 나가는 간선이 0인 leaf라 **순환 없이** 떨어지고(들어오는 간선 쪽은 import 경로를 고쳐야 한다 — 세 모듈에서 온다), `net` 과 맞닿지도 않아 `frame_port` feature 문제를 비껴간다. **버린 이유:** 싸다는 것이 해야 할 이유가 되지 못한다 — 제어 평면만 따로 쓸 소비자가 없고(§근거), ADR-0129 결정 2가 그린 모양(응용 전체를 한 lib으로)과도 달라 결정이 하나 더 늘어난다. 얻는 것은 예방 효과뿐인데 그 예방 논거가 이 덩어리엔 약하다(§근거).
- **ADR-0129 완주(옵션 B)** — production 순환이 반증되면서 이 안의 주된 리스크는 사라졌다(설계 변경이 아니라 이사다). **버린 이유:** 리스크가 낮아진 것이지 필요가 생긴 것이 아니다. 소비자 부재는 그대로고, 여기에 두 결정이 딸려온다 — `frame_port` 를 `server` feature 밖으로 뺄지(공개 API 변경이라 미루면 비싸진다), 그리고 조립부가 레지스트리와 팬아웃을 둘 다 들지 않게 하는 정공법.
- **아무 기록 없이 그냥 중단** — ADR-0129만 읽는 다음 세션이 "결정 2·3 미이행"을 보고 같은 조사를 처음부터 다시 돈다. 이 ADR 자체가 그 재론을 막는 못이다.

## 근거

**① 원래 목적은 달성됐고 측정됐다.** ADR-0129의 문제제기는 *"데몬은 중계기여야 하고 다른 시스템에서 재활용돼야 하는데 백엔드 전체가 됐다"* 였다. `net` 분리 후 `discovery` 의 정상 의존 폐포가 122 → 110 crate 로 줄고 async 런타임 계열이 0줄이 됐다(재확인 = `crates/engram-dashboard-discovery/Cargo.toml` 주석의 게이트 명령).

**② 나머지 두 덩어리엔 소비자가 없다.** `net` 분리에는 실제 소비자가 있었다(`discovery`·`src-tauri` 가 네트워크만 필요한데 전부를 지고 있었다). 제어 평면도 중계 층도 따로 가져다 쓸 소비자가 현재 없고 계획에도 없다.

**③ 벽이 없어도 경계가 이미 서 있다(실측 2026-08-05).** 기록돼 있던 모듈 순환 2건이 **production 빌드에서는 반증**됐다 — 둘 다 `#[cfg(test)] mod tests` 안의 픽스처가 옆 모듈로 손을 뻗어 생긴 것이고, 기본 빌드의 의존 그래프는 단방향 DAG다. 특히 `control/` 은 다른 최상위 데몬 모듈로 나가는 간선이 **0**이다.

재확인 명령:
```bash
# control/ 이 control 밖 데몬 모듈을 참조하는가 (기대: 0줄)
#   ★경로 접두를 crate:: 만으로 좁히지 말 것★ — control/mod.rs 에서 super:: 는 크레이트 루트라
#   `use super::connection_core::X` 가 같은 간선인데 빠져나간다(그 디렉토리가 실제로 super:: 형태를
#   쓴다). 좁은 판이 2026-08-05 리뷰에서 적출됐다 — 트리거는 과탐이 낫지 미탐은 조용해서 위험하다.
#   ★-U 를 빼지 말 것★ — rustfmt 가 폭 넘는 import 를 `use crate::{⏎ connection_core::A,⏎};` 로 쪼개면
#   접두와 모듈명이 다른 줄에 앉아 단일행 패턴은 못 문다(이 repo 엔 rustfmt.toml 이 없어 기본 래핑이 돈다).
#   매치가 나오면 그 줄이 그 파일의 `#[cfg(test)]` 시작 줄보다 앞인지 볼 것 — 뒤면 테스트 픽스처라 합법.
#   양성 대조의 한계: 경로를 src/ 로 넓히면 실간선이 잡히지만 그 간선은 **전부 crate:: 형태**라
#   super:: 갈래가 죽어도 이 대조는 통과한다. 접두를 좁히는 개정을 이 대조로 승인하지 말 것.
rg -U -n "(crate|(super::)+)::[^;]*\b(connection_core|agent_conn|status_fanout|messaging_host)\b" crates/engram-dashboard-daemon/src/control/
# connection_core 가 production 에서 옆 모듈을 참조하는가
#   (매치가 전부 그 파일의 `#[cfg(test)] mod tests` 시작 줄 이후면 production 순환 없음 — 줄 번호를 여기 박지 말 것)
#   접두·-U 주의사항은 위 명령과 동일하다 — connection_core.rs 도 크레이트 루트의 직계라 super:: 가 같은 간선이다.
rg -U -n "(crate|(super::)+)::[^;]*\b(status_fanout|messaging_host)\b" crates/engram-dashboard-daemon/src/connection_core.rs
```

**④ 부식 논거가 이 두 덩어리엔 약하다.** ADR-0129가 crate 벽을 택한 근거는 ADR-0020의 부식 이력이었다 — 연결 코어를 carrier-중립 모듈로 선언해뒀는데 제어 평면과 메시징이 같은 crate로 흘러들었다. **그 부식의 원인은 축이 같았다는 것이다**(연결을 처리하다 보니 연결 위에서 할 일이 옆에 쌓였다). 제어 평면은 **별개 입구**다 — 웹뷰의 WS 를 거치지 않고 자체 HTTP 리스너로 에이전트 안의 LLM 요청을 받는다(`crates/engram-dashboard-daemon/src/control/mcp_server.rs` 의 `TcpListener::bind` 지점). 같은 부식 경로를 타기 어렵다.

**⑤ 규모가 착시였다.** ADR-0129 본문의 "약 8,000줄"은 테스트 포함 총량이다. 기본 빌드 기준 데몬 crate의 production 코드는 그보다 작고, 그중 절반 가까이가 leaf 인 제어 평면이다(2026-08-05 측정 — 숫자는 시점값이라 여기 고정하지 않는다. 재측정 = 각 파일의 `#[cfg(test)] mod tests` 시작 줄 기준 분할).

## 영향 / 불변식

- **ADR-0129 결정 1은 살아 있다.** `engram-dashboard-net` 의 격리 게이트(정본 = 그 crate `src/lib.rs` 헤더)는 그대로 유지·실행된다. 이 ADR은 그 게이트를 완화하지 않는다.
- **`daemon` crate 이름과 내용물의 어긋남을 기록해 둔다.** 데몬 살림의 **구현**(단일 인스턴스 가드·portfile)은 결정 1로 `net` 이 가져갔다 — **그러나 그것들을 어느 순서로 부르는지는 여전히 이 crate 소유다**(`run()` 이 가드 획득 → data_dir → stale 검사 → bind → … 순서를 쥔다. 실제 호출 지점 = `daemon/src/lib.rs` 의 `instance::acquire` · `portfile::read`/`is_stale`/`write_atomic`). 지금 이 crate가 담는 것은 응용 층 + 조립 + 그 기동 순서이고, 프로세스로서의 데몬 진입점은 `main.rs` 다. **rename 은 하지 않는다** — 바이너리 이름은 정확하고, crate 이름을 바꾸면 `src-tauri` 의 데몬 클라이언트 테스트가 이 crate 이름을 직접 부르는 지점을 같은 변경에서 고쳐야 한다. 대신 crate 헤더가 이 경계를 한 줄로 밝힌다.
- **★재개 조건(하나라도 관측되면 ADR-0129 목표 모양을 다시 꺼낸다)★**
  1. 제어 평면 또는 중계 층을 **따로 쓸 소비자가 실제로 생긴다**(가정이 아니라 착수된 소비처).
  2. `control/` 에서 다른 최상위 데몬 모듈로 나가는 **production 간선이 생긴다**(= leaf 성질 붕괴 — §근거 ③의 첫 명령이 0줄을 잃는다).
  3. production 의존 그래프에 **순환이 생긴다**(테스트 블록 밖에서). ★이 조건만 단발 명령이 없다★ — 조건 2의 grep 은 `control/` 의 나가는 간선만 보므로 그 밖에서 생기는 순환(예: `status_fanout → messaging_host`)에는 울지 않는다. 재는 법 = 각 모듈의 크레이트 내부 참조(`crate::` **와 `super::` 양쪽** — 최상위 모듈에선 둘이 같은 곳을 가리킨다. 그룹 import 때문에 `rg -U` 필수)를 **그 파일의 `#[cfg(test)]` 시작 줄과 대조**해 production 간선만 남긴 뒤 방향을 확인하는 것(2026-08-05 실측이 이 방법으로 아래 DAG를 얻었다: `agent_conn → {connection_core, control}` · `connection_core → control` · `status_fanout → connection_core` · `messaging_host → {status_fanout, control}` · `control → 없음`).
  - **등록 상태(2026-08-05 — 이 줄이 정본):** **②만** `/qa` 바인딩(`.claude/skill-bindings/qa.md`)에 **재론 트리거**로 등록됐다 — *어기면 FAIL* 인 격리 게이트가 **아니라** "멈추고 이 ADR 을 재론하라"는 알림이라 판정 규칙이 반대다(매치를 회귀로 보고 되돌리지 말 것). **①은 기계화 대상이 아니고**(소비자 등장 = 사람 판단), **③은 여전히 미등록 — 자동으로 울지 않는다.** ②의 트리거가 0줄이라고 ③까지 깨끗하다고 읽지 말 것.
- **테스트 코드의 옆걸음은 결함이 아니다.** `#[cfg(test)]` 픽스처가 형제 모듈을 쓰는 것은 한 crate 안에서 합법이고, 이 결정 하에서는 고칠 이유가 없다. 다만 **재개할 때는 그 코드가 crate 경계를 넘게 되므로 재배치 대상**이라는 점을 기록해 둔다 — 재개 시 이 문단을 먼저 읽을 것.
- **`frame_port` 의 feature 소속 결정도 함께 보류된다.** ADR-0129 note 가 "슬라이스 2 전에 재검토"로 남긴 사안인데, 슬라이스 2가 보류되므로 그 시한도 함께 미뤄진다. 재개 시 **착수 전에** 결정할 것(공개 API 변경이라 나중에 하면 비싸다).
