# ADR-0021: Daemon lifetime — on-demand spawn + no auto-restart (tmux/wezterm model)

- 상태: 확정 (2026-06-17, basis: daemon-server prior-art survey [tmux/wezterm/emacs/gpg-agent/LSP] + user decision + extension of ADR-0015) · 부분 폐기 by ADR-0350 (결정 5 daemon_stop 명령과 영향의 stop 대체 순서)
- 관련: ADR-0015 (daemon persist-until-kill · console = detachable viewer · ensure-on-open) **extended/corrected** · ADR-0008 (S9 restore_all) · `crates/engram-dashboard-discovery/src/lib.rs` (ensure_daemon/Spawner — moved from src-tauri to the discovery crate in S12) · `src/api/wsTransport.ts` (connect/reconnect) · `crates/engram-dashboard-protocol` (StopDaemon) · Amended by ADR-0350 (결정 5 daemon_stop 명령과 영향의 stop 대체 순서)
- Scope: daemon (infrastructure) lifetime — auto-start / stop / crash handling. **A different axis from agent lifetime (ADR-0016/0019).**

## 맥락

The daemon stays resident and persists (ADR-0015). The problem: ensure-on-open called spawn **even in the reconnect loop**, so even when the user killed the daemon to turn it off, the GUI reconnect revived it at once → it could not be turned off. We tried to go with "revive on crash, leave off on intentional exit" (systemd on-failure), but **a raw kill (taskkill /F) and a crash cannot be told apart by exit code** — the attempt to tell them apart is itself unstable.

The prior-art survey concluded (tmux · wezterm · emacs · gpg-agent · LSP): **all of them use on-demand spawn + no auto-restart.** The reason — the state lives only in server memory, so a restart gives an empty server and is pointless. So the "user cannot turn it off" problem never arises (with no watchdog, kill = exit does not conflict). Auto-restart makes sense only when the state is **persisted on disk**, like dockerd.

## 결정

**The tmux/wezterm model. No auto-restart (watchdog). On-demand spawn only.**

1. **spawn (ensure) = explicit moments only:** "spawn if absent" happens only on an **intentional connection**: boot connection / the user's `daemon_start` / opening the dashboard. (wezterm `no_serve_automatically=false` = the pattern of auto-spawn on connection failure.)
2. **The reconnect loop = attach-only (never spawns):** when the daemon dies, the GUI reconnect only tries to **re-attach to the existing daemon**; if there is none, it does not spawn, shows the `down` state, and offers "Start". **This is the core fix for the "kill → respawn" friendliness problem** — ensure (explicit) and reconnect (attach-only) are separated.
   - **Clarification (2026-06-21): the "ban" is limited to spawn — re-lookup (no-spawn) is allowed.** If reconnect only knocks on the cached host:port, then when the daemon comes up with a **new port/token** through a hot-swap (replacing the whole daemon by `daemon_stop` → `daemon_start`) or a crash-respawn, it keeps knocking on the old address until it runs out of attempts → `down` (found in QA; stale until a page reload). So reconnect **re-looks-up** daemon.json through `read_daemon_info` (includes the token, **no-spawn** read-only) and **can follow** a daemon that moved or was respawned (still attach-only — it neither creates nor wakes the daemon). If there is no live daemon, it stays in backoff/exhausted → `down`. `discover_daemon` (which comes with spawn) is called **only by an explicit start** (reconnect must never call it). Implementation: `discovery::read_live_daemon` (no-spawn live reader) · `commands::read_daemon_info` · the read_daemon_info-first lookup in `wsTransport.openSocket(false)`.
     - Rejected alternative: **pinning the cache** (the old behavior) → on hot-swap or crash it cannot follow the new daemon and stays stale until a page reload (= explicit-start rediscover). The read-only re-lookup resolves this without breaking the spawn invariant.
3. **No auto-restart:** whether by kill or crash, a dead daemon **stays off.** Raw kill and crash are not told apart (impossible and unnecessary). Recovery is by **a fresh daemon + `restore_all` on the next explicit connection** (ADR-0008, sid `--resume`), which revives persistent agents — unlike tmux, the loss is not permanent.
4. **stop = explicit exit:** `daemon_stop` (tray / command / our handle) → StopDaemon (graceful) or kill → it dies and stays dead (reconnect does not revive it). Equivalent to systemd `systemctl stop`.
5. **command surface (§5 — the same handle for LLM, UI and tray, platform-neutral):** `daemon_start` (explicit ensure) · `daemon_stop` (StopDaemon) · `daemon_status` (alive/pid/port).
6. **Console (debug log):** ~~Windowless by default (`CREATE_NO_WINDOW` style).~~ ★Corrected by measurement (2026-06-19 dashboard8): "windowless by default" was false — the daemon is a **console-subsystem app** (`windows_subsystem` not set), so on a WMI spawn the OS attached a console window (even with `console=false`). WMI `Win32_Process.Create` rejects `CREATE_NO_WINDOW` (0x08000000) with RV=21 (a console app cannot be made windowless through WMI), so a flag cannot turn it off. **So console visibility is decided by the daemon exe's subsystem:** `#![cfg_attr(not(debug_assertions), windows_subsystem = "windows")]` (daemon/main.rs) → **debug = console app** (a WMI spawn brings a console window = logs are visible, kept by user decision) / **release = windows app** (no console window). `daemon_start(console:true)` (`CREATE_NEW_CONSOLE`, an allowed flag) is for *additionally* opening a separate console window.★ Unrelated to daemon lifetime (the minimal form of the ADR-0015 detachable viewer). **A runtime toggle (`set_daemon_console(on|off)`) is a follow-up** — turning the console on and off while the daemon is already running is not implemented (M-2: to change the console, today the only ways are the build mode (subsystem) or stop → start(console)).

## 거부한 대안
- **systemd on-failure / crash-only restart (this ADR's first draft):** raw kill and crash cannot be told apart by exit code → even with a desired-state flag as a workaround, a raw kill is still misclassified as a crash. Also, when the daemon dies the in-memory agents die too, so an auto-restart gives an empty daemon — the benefit is already covered by `restore_all` (restore on the next connection). It only adds complexity, so it was discarded.
- **An always-on watchdog process:** it brings back the "user cannot turn it off" problem. No prior art does it. Over-engineering.
- **A desired-state (daemon-config.json) file:** in model A, "stays off" holds naturally because *reconnect does not spawn* → no separate intent flag is needed. (If staying off after an app restart is wanted, add a small flag later — YAGNI for now.)

## 근거
- All five prior-art systems (tmux/wezterm/emacs/gpg-agent/LSP) converge on on-demand + no restart. wezterm (GUI and headless mux-server separated, the mux survives when the GUI closes, auto-spawn on connection failure) maps 1:1 onto the engram structure.
- engram persists sid/agents.json → when the daemon restarts, `restore_all` restores the agents. It already has the only benefit of "auto-restart on crash" (keeping state).
- spawn is abstracted by `trait Spawner` (discovery.rs) → neutral to model and platform. Another OS = add a Spawner implementation.

## 영향 / 불변식
- **ensure (spawn) and reconnect (attach-only) are separate** — the reconnect loop must never call spawn (if this breaks, the "cannot turn it off" bug returns).
- **The command path is also attach-only (B-1 fix, 2026-06-17):** `WsTransport.ensureReady()` (called before every command/subscribe/resize) is **attach-only** — it only reopens the socket with the cached host:port, and if there is no cache, or closedByUser/down, it rejects at once ("explicit start with daemon_start required"). It never discovers or spawns. Without this, after the daemon was turned off, a single keypress or a window resize (ResizeObserver → resizePty) alone respawned the daemon (B-1, reviewer-deep blocker).
- **spawn only at explicit entry points:** only `WsTransport.start()` (= `Transport.start`, delegated by `AgentClient.connect`) does discover (spawn if absent) + fills the cache + resets closedByUser/attempt. The one boot call (`clientFactory.bootstrapDaemonIfNeeded` → `daemonControl.start`) and the user's `daemon_start` (`DaemonControl.start`) go through it — equivalent to tmux `attach` starting the server. **The boot ensure is one explicit start, not a side effect of a command** (it is not mixed with the command path).
- **stop = graceful → disconnect → (check still-alive) fallback:** `DaemonControl.stop` does a graceful StopDaemon, then `client.disconnect()` (closedByUser=true → removes the 5 futile reconnect attempts, note3); if graceful was Acked, it checks still-alive with `daemon_status` and runs the taskkill fallback only if it is still alive (M-1, mitigates the graceful/taskkill race). If there was no graceful or it failed, it goes straight to the fallback.
- Daemon death = stays off. Recovery is explicit connection + restore_all. No watchdog/desired-state.
- Daemon infrastructure lifetime ≠ agent runtime auto-restart (ADR-0019 discarded). Do not confuse them.
- command is platform-neutral (Q1 boundary: command = neutral / tray and menu = platform view). The tray (#2) only calls this command.
- **Console = a spawn-time parameter only** (`daemon_start(console)`). The runtime toggle (`set_daemon_console`) is a follow-up, not implemented (M-2). Toggling the console does not affect daemon lifetime.
