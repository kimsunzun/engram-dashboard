# ADR-0279: The backend policy wall is the daemon's SpawnByCwd handler — shell slot spawn does not change its path

- 상태: 확정 (2026-10-06, basis: main decision under the user delegation 2026-10-06 「알아서 해 … 단계 착수」 + `/review trd full` round 3 PASS + code cross-check `cf693f4` + landing `8b48386`(2-1 U1 — `/review code full` round 3 PASS · `/qa standard` PASS · CI green))
- 관련: Amends ADR-0270 (the policy-wall path in decision 3) · Amends ADR-0219 (the claude-pinned door axis of decision 5) · ADR-0029(shell = daemon client) · ADR-0172(ad-hoc creation does not use 「마지막 실패」) · ADR-0012(seam · standalone harness) · `crates/engram-dashboard-daemon/src/connection_core.rs`(the `SpawnByCwd` handler) · `crates/engram-dashboard-agent/src/commands.rs`(`llm_creation_refusal` · `LLM_BACKEND_POLICY` · `verb_new`) · `src-tauri/src/layout/apply.rs`(`spawn_into` · `gate_backend`) · `docs/process/S21-crate-boundaries/trd-2-1-shell-agent-cut.md` §2-1 · §7 · step-log S21

## 맥락

ADR-0270 decision 3.1 wrote 「슬롯 스폰을 데몬의 `agent.new` 명령 경로로 바꾼다」 as the first unit of removing agent from the shell — to put the backend policy decision in one place in the daemon and delete the shell's policy check (`gate_backend`). When the 2-1 TRD checked it against the code (`cf693f4`), that path does not stand as is:

- ★**`agent.new` only registers**★(asleep state — `agent/src/commands.rs:194`). To start it, one more `agent.spawn {target}` is needed.
- **The daemon `SpawnByCwd` handler does not look at policy** — `spawn_command_by_cwd` → if missing, `MISSING_BACKEND` → `CoreProfile::new(.., auto_restore=false)` → `manager.spawn_agent(.., Fresh)`(`connection_core.rs:1455-1500`). Two places look at policy today — agent `verb_new` · shell `gate_backend`.
- **There are four paths that send `SpawnByCwd`** — two shell paths through the single shell `DaemonSpawner` (Tauri command `spawn_into` · bus verb `agent.spawnInto` — both pass the same `apply::spawn_into` → `gate_backend`) · frontend `slot.createAgentHere`(`src/commands/slotContentCommands.ts`) · frontend `agent.spawn`(`src/commands/agentCommands.ts`). The latter two are fixed to `'claude'` and do not pass the shell policy check. The frontend `agent.spawn` is one of the two doors that ADR-0219 decision 5 describes as 「일부러 claude 에 못박은」 (the other = `create_and_start` of the agent bus `agent.spawn` — it does not look at policy).
- **Shell slot spawn goes in the order 「검사 → 데몬 스폰 → 배치」**(`apply::spawn_into`) — if the spawn returns via `?`, placement is not reached, so the layout does not change (test `spawn_into_propagates_spawn_failure_untouched`). If the daemon answers with `Error`, `send_command` turns it into `Err(message)` and returns it, and the bus `agent.spawnInto` carries that text as `CONFLICT`.
- **The policy table `LLM_BACKEND_POLICY` opens both claude and codex, so there are 0 refusals today.**

So the place that keeps the intent of ADR-0270 (policy wall = daemon) had to be chosen again.

## 결정

1. ★**The daemon's `SpawnByCwd` handler calls the backend policy (in production = agent `llm_creation_refusal`) before the spawn (`manager.spawn_agent`), and answers with `Error` on refusal.**★ Place = right after the `MISSING_BACKEND` decision · before `CoreProfile::new`. ★The boundary is `spawn_agent`★ — that is where the ad-hoc profile goes into the registry and onto disk (the first item of 「영향」 below). `CoreProfile::new` only builds an in-memory value, so putting the call before it is a placement choice, not an invariant. It is an error path the shell already surfaces as is (「맥락」 above).
2. **The path · round trips · placement order of shell slot spawn stay as they are.** Slot spawn is not moved to `agent.new` — this decision takes the place of 「`agent.new` 명령 경로로 바꾼다」 in ADR-0270 decision 3.1. The order of decisions 3.2 · 3.3 (policy wall → delete shell check → reserved list) stays, and the 「셸의 정책 검사(`gate_backend`)를 지운다」 in 3.2 is the **policy part**, while the word net (`parse_backend`) stays in the shell.
3. **There are two daemon doors that look at policy** — `agent.new`(`verb_new`) · the `SpawnByCwd` handler. The home of the policy is still the single place `LLM_BACKEND_POLICY`.
4. ★**This door does not tell callers apart — no caller axis is added to the spawn packet for now**★(a cost accepted — 「영향」 below). ★**Reopen trigger = the day any backend is closed to LLMs or a declaration goes missing (`NO_POLICY_DECLARED`) — then a caller axis is added to the spawn packet.**★

## 거부한 대안

- **(a) Change slot spawn to two calls, `agent.new` + `agent.spawn {target}` (the text of ADR-0270 decision 3.1 as written).** Rejected = code — `agent.new` only registers (asleep state — `agent/src/commands.rs:194`) so there are two round trips, if the second fails an asleep orphan remains, the shell cannot use agent's argument type (`AgentNewArgs`) (the purpose of 2-1) so it would have to hand-build the argument JSON, and the frontend's `SpawnByCwd` slot paths (`slot.createAgentHere` · frontend `agent.spawn`) would still bypass policy.
  - ★**Do not bring these two back as reasons to reject this alternative — they do not hold in code**★(the corrected facts under 「근거」 below):
    - 「`agent.new` 의 `backend` 는 PascalCase 라 셸이 lowercase wire 낱말과 갈린다」 — the spelling does not diverge. This reason was withdrawn in review round 1 (F3).
    - 「슬롯 즉석 에이전트가 영속 프로필이 된다」 — `SpawnByCwd` also puts an ad-hoc profile into the registry and writes it to disk. 「영속 프로필이 되느냐」 is not the axis that separates (a) from this decision.
- **(b) Add a new daemon verb that does create-and-start in one call.** Rejected = it gains nothing over this decision and only increases the surface (main judgment). **Self-assessment of the rejection basis: weak** (a statement — no quantitative · measured · code basis). User confirmation 2026-10-06 — confirmed as marked weak.

## 영향 / 불변식

- ★**Invariant: the policy call comes before `manager.spawn_agent`**★ — the ad-hoc profile is put into the registry and written to disk inside it (`register_for_spawn` → `upsert_preserving_hierarchy` → `store.save`), so placing the call after it leaves a refused ad-hoc profile in the registry · on disk (the registration · save chain in 「근거」 above). `CoreProfile::new` only builds an in-memory value — putting the call before it is a placement choice (decision 1).
- **A refusal does not use 「마지막 실패」** — neither activation nor ad-hoc creation happened (ADR-0172 decisions 1 · 4).
- **The refusal text makes one trip through the daemon** — the daemon text goes to the caller without a prefix, so it has to stand on its own. It uses the frame of the shell text (「`backend '{word}' 는 아는 낱말이지만 이 표면으로는 지금 만들지 않는다 — {reason} 스폰 안 함.`」) as is, and `{word}` is obtained by wire enum serialization (always lowercase). The bus error code is `CONFLICT` as now.
- **Wire · catalog generations stay as they are** — `PROTOCOL_VERSION` · shell `CATALOG_VERSION` (neither the packet shape nor today's behavior changes).
- ★**Accepted cost — this door does not tell callers apart**★: the policy is named 「LLM 제어 표면」, but the daemon's `SpawnByCwd` does not know who sent it. So **human paths also see the same table** — what is newly reached is the two claude-pinned doors (`slot.createAgentHere` · frontend `agent.spawn` — the latter is the door that ADR-0219 decision 5 describes as 「일부러 claude 에 못박은」). The frontend `agent.spawnInto` is **not a new exposure** (the shell door already looks at the table without telling callers apart). As a result two doors of the same name diverge — frontend `agent.spawn` looks at the table and agent bus `agent.spawn`(`create_and_start`) does not. **Impact today 0** — the table closes nothing and claude is open. The reopen trigger is decision 4 above.
