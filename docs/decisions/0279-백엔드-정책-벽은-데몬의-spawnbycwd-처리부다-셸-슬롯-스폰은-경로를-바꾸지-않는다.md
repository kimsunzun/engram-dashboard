# ADR-0279: The backend policy wall is the daemon's SpawnByCwd handler — shell slot spawn does not change its path

- 상태: 확정 (2026-10-06, basis: main-session decision under user delegation 2026-10-06 「알아서 해 … 단계 착수」 + `/review trd full` round 3 PASS + code cross-check `cf693f4` + landing `8b48386` (2-1 U1 — `/review code full` round 3 PASS · `/qa standard` PASS · CI green)) · 부분 폐기 by ADR-0348 (decision 3)
- 관련: Amends ADR-0270 (decision 3's policy wall path) · Amends ADR-0219 (decision 5's claude-fixed door axis) · ADR-0029 (shell = daemon client) · ADR-0172 (ad-hoc creation does not use 「마지막 실패」) · ADR-0012 (seam · standalone harness) · `crates/engram-dashboard-daemon/src/connection_core.rs` (`SpawnByCwd` handler) · `crates/engram-dashboard-agent/src/commands.rs` (`llm_creation_refusal` · `LLM_BACKEND_POLICY` · `verb_new`) · `src-tauri/src/layout/apply.rs` (`spawn_into` · `gate_backend`) · `docs/process/S21-crate-boundaries/trd-2-1-shell-agent-cut.md` §2-1 · §7 · step-log S21 · Amended by ADR-0348 (decision 3)

## 맥락

ADR-0270 decision 3.1 wrote 「슬롯 스폰을 데몬의 `agent.new` 명령 경로로 바꾼다」 as the first unit for withdrawing agent from the shell — to put the backend policy decision in one place in the daemon and to delete the shell's policy check (`gate_backend`). When the 2-1 TRD checked it against the code (`cf693f4`), that path does not stand as it is:

- ★**`agent.new` only registers**★ (dormant state — `agent/src/commands.rs:194`). Launching needs `agent.spawn {target}` once more.
- **The daemon's `SpawnByCwd` handler does not look at the policy** — `spawn_command_by_cwd` → if absent `MISSING_BACKEND` → `CoreProfile::new(.., auto_restore=false)` → `manager.spawn_agent(.., Fresh)` (`connection_core.rs:1455-1500`). Today there are two places that look at the policy — agent `verb_new` · shell `gate_backend`.
- **There are four paths that send `SpawnByCwd`** — two shell paths that pass through the single shell `DaemonSpawner` (Tauri command `spawn_into` · bus verb `agent.spawnInto` — both pass through the same `apply::spawn_into` → `gate_backend`) · frontend `slot.createAgentHere` (`src/commands/slotContentCommands.ts`) · frontend `agent.spawn` (`src/commands/agentCommands.ts`). The latter two are fixed to `'claude'` and do not pass through the shell policy check. Frontend `agent.spawn` is one of the two 「일부러 claude 에 못박은」 doors in ADR-0219 decision 5 (the other = the `create_and_start` of the agent bus `agent.spawn` — it does not look at the policy).
- **Shell slot spawn goes in 「검사 → 데몬 스폰 → 배치」 order** (`apply::spawn_into`) — if the spawn returns early through `?`, it does not reach the placement, so the layout does not change (test `spawn_into_propagates_spawn_failure_untouched`). When the daemon answers `Error`, `send_command` turns it into `Err(message)` and returns it, and the bus `agent.spawnInto` carries that wording as `CONFLICT`.
- **The policy table `LLM_BACKEND_POLICY` opens both claude and codex, so today there are zero rejections.**

So the place that keeps the intent of ADR-0270 (policy wall = daemon) had to be chosen again.

## 결정

1. ★**The daemon's `SpawnByCwd` handler calls the backend policy (operation = agent `llm_creation_refusal`) before the spawn (`manager.spawn_agent`), and answers `Error` on rejection.**★ Position = right after the `MISSING_BACKEND` decision · before `CoreProfile::new`. ★The boundary is `spawn_agent`★ — that is where the ad-hoc profile goes into the registry · disk (the first item of 「영향」 below). `CoreProfile::new` only builds an in-memory value, so putting it before that is a placement choice, not an invariant. It is an error path that the shell already surfaces as is (「맥락」 above).
2. **The path · round-trip count · placement order of shell slot spawn stay as they are.** Slot spawn is not moved to `agent.new` — this decision stands in for 「`agent.new` 명령 경로로 바꾼다」 of ADR-0270 decision 3.1. The order of decisions 3.2 · 3.3 (policy wall → delete shell check → reserved list) stays as is, and the 「셸의 정책 검사(`gate_backend`)를 지운다」 of 3.2 covers only the **policy part**, while the word net (`parse_backend`) stays in the shell.
3. **The daemon doors that look at the policy are two** — `agent.new` (`verb_new`) · the `SpawnByCwd` handler. The home of the policy is still the single place `LLM_BACKEND_POLICY`.
4. ★**This door does not tell callers apart — no caller axis is added to the spawn packet for now**★ (the cost accepted — 「영향」 below). ★**Trigger to revisit = the day any backend is closed to the LLM or its declaration drops out (`NO_POLICY_DECLARED`) — then add a caller axis to the spawn packet.**★

## 거부한 대안

- **(a) Change slot spawn to `agent.new` + `agent.spawn {target}` two calls (the text of ADR-0270 decision 3.1 as written).** Rejected = code — `agent.new` only registers (dormant state — `agent/src/commands.rs:194`), so there are two round trips, if the second fails a dormant orphan remains, the shell cannot use agent's argument type (`AgentNewArgs`) (the purpose of 2-1) so it must build the argument JSON by hand, and the frontend's `SpawnByCwd` slot path (`slot.createAgentHere` · frontend `agent.spawn`) still bypasses the policy.
  - ★**Do not bring up the following two again as reasons to reject this alternative — they do not stand on the code**★ (the corrected facts in 「근거」 below):
    - 「`agent.new` 의 `backend` 는 PascalCase 라 셸이 lowercase wire 낱말과 갈린다」 — the spelling does not diverge. This reason was withdrawn in review round 1 (F3).
    - 「슬롯 즉석 에이전트가 영속 프로필이 된다」 — `SpawnByCwd` also puts the ad-hoc profile into the registry and writes it to disk. 「영속 프로필이 되느냐」 is not the axis that separates (a) from this decision.
- **(b) Add a new daemon verb that creates and launches in one step.** Rejected = it adds only surface with nothing gained over this decision (main-session judgment). **Self-assessment of the rejection ground: weak** (a statement — no quantitative · measured · code ground). User confirmation 2026-10-06 — confirmed as marked weak.

## 영향 / 불변식

- ★**Invariant: the policy call comes before `manager.spawn_agent`**★ — the ad-hoc profile goes into the registry and is written to disk inside it (`register_for_spawn` → `upsert_preserving_hierarchy` → `store.save`), so if it were placed after, a rejected ad-hoc profile would remain in the registry · on disk (the registration · save chain of 「근거」 above). `CoreProfile::new` only builds an in-memory value — placing it before that is a placement choice (decision 1).
- **Rejection does not use 「마지막 실패」** — neither activation nor ad-hoc creation took place (ADR-0172 decisions 1 · 4).
- **The rejection wording makes one trip through the daemon** — the daemon wording goes to the caller without a prefix, so it must stand alone. It uses the frame of the shell wording (「`backend '{word}' 는 아는 낱말이지만 이 표면으로는 지금 만들지 않는다 — {reason} 스폰 안 함.`」) as is, and `{word}` is obtained by wire enum serialization (always lowercase). The bus error code is `CONFLICT` as it is now.
- **The wire · catalog generations stay as they are** — `PROTOCOL_VERSION` · shell `CATALOG_VERSION` (neither the packet shape nor today's behavior changes).
- ★**Cost accepted — this door does not tell callers apart**★: the policy name is 「LLM 제어 표면」, but the daemon `SpawnByCwd` does not know who sent it. So **the human path also looks at the same table** — what is newly reached is the two claude-fixed doors (`slot.createAgentHere` · frontend `agent.spawn` — the latter is the 「일부러 claude 에 못박은」 door of ADR-0219 decision 5). Frontend `agent.spawnInto` is **not a new exposure** (the shell door already does not tell callers apart and looks at the table). As a result two doors with the same name diverge — frontend `agent.spawn` looks at the table and the agent bus `agent.spawn` (`create_and_start`) does not. **Zero impact today** — the table closes nothing and claude is open. The trigger to revisit is decision 4 above.
- **Place the trigger to revisit at the editing site** — a 「어느 줄의 `refusal` 을 `Some` 으로 바꾸거나 선언 없는 낱말을 들이기 전에 ADR-0279 를 다시 연다 — 데몬 `SpawnByCwd` 문이 사람 경로도 막는다」 was attached to the agent policy table doc (U1 `8b48386` — the `LLM_BACKEND_POLICY` doc of agent `commands.rs`).

  - The 「(ADR-0219 를 고친다 — …) 정책을 보는 문은 데몬 `agent.new` 하나가 된다」 of 「영향」 → **the daemon's two doors** — `agent.new` (`verb_new`) · the `SpawnByCwd` handler.
  - The code anchor 「슬롯 스폰의 `agent.new` 경로」 of 「영향」 and the GUI completion condition 「슬롯 스폰 경로 교체 뒤 레이아웃 불변」 are also read with this meaning (the policy wall in the `SpawnByCwd` handler · path unchanged).
  - The order of decisions 3.2 · 3.3 stays as is (decision 2 above).
