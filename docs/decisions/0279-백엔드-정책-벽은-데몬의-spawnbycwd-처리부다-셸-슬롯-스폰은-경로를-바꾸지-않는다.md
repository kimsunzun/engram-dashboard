# ADR-0279: The backend policy wall is the daemon's SpawnByCwd handler — the shell's slot spawn does not change its path

- 상태: 확정 (2026-10-06, basis: main's decision under the user's delegation 2026-10-06 「알아서 해 … 단계 착수」 + `/review trd full` round 3 PASS + code cross-check `cf693f4` + landing `8b48386` (2-1 U1 — `/review code full` round 3 PASS · `/qa standard` PASS · CI green))
- 관련: Amends ADR-0270 (the policy-wall path of decision 3) · Amends ADR-0219 (the claude-pinned door axis of decision 5) · ADR-0029(shell = daemon client) · ADR-0172(on-the-fly creation does not use 「마지막 실패」) · ADR-0012(seam · standalone harness) · `crates/engram-dashboard-daemon/src/connection_core.rs`(`SpawnByCwd` handler) · `crates/engram-dashboard-agent/src/commands.rs`(`llm_creation_refusal` · `LLM_BACKEND_POLICY` · `verb_new`) · `src-tauri/src/layout/apply.rs`(`spawn_into` · `gate_backend`) · `docs/process/S21-crate-boundaries/trd-2-1-shell-agent-cut.md` §2-1 · §7 · step-log S21

## 맥락

ADR-0270 decision 3.1 wrote 「슬롯 스폰을 데몬의 `agent.new` 명령 경로로 바꾼다」 as the first unit of moving the agent out of the shell — the aim was to put the backend policy decision in one place, the daemon, and delete the shell's policy check (`gate_backend`). When the 2-1 TRD checked it against the code (`cf693f4`), that path does not stand as written:

- ★**`agent.new` only registers**★ (a sleeping state — `agent/src/commands.rs:194`). Starting it needs one more `agent.spawn {target}`.
- **The daemon's `SpawnByCwd` handler does not look at the policy** — `spawn_command_by_cwd` → `MISSING_BACKEND` if absent → `CoreProfile::new(.., auto_restore=false)` → `manager.spawn_agent(.., Fresh)` (`connection_core.rs:1455-1500`). Two places look at the policy today — the agent's `verb_new` and the shell's `gate_backend`.
- **There are four paths that send `SpawnByCwd`** — two shell paths that go through the single shell `DaemonSpawner` (the Tauri command `spawn_into` · the bus verb `agent.spawnInto` — both go through the same `apply::spawn_into` → `gate_backend`) · the frontend `slot.createAgentHere` (`src/commands/slotContentCommands.ts`) · the frontend `agent.spawn` (`src/commands/agentCommands.ts`). The latter two are pinned to `'claude'` and do not go through the shell policy check. The frontend `agent.spawn` is one of the two doors that ADR-0219 decision 5 「일부러 claude 에 못박은」 (the other = `create_and_start` of the agent bus `agent.spawn` — it does not look at the policy).
- **The shell slot spawn goes in the order 「검사 → 데몬 스폰 → 배치」** (`apply::spawn_into`) — if the spawn returns through `?`, placement is never reached and the layout does not change (test `spawn_into_propagates_spawn_failure_untouched`). When the daemon answers with `Error`, `send_command` turns it into `Err(message)` and returns it, and the bus `agent.spawnInto` carries that text as `CONFLICT`.
- **The policy table `LLM_BACKEND_POLICY` opens both claude and codex, so refusals are zero today.**

So the place that keeps the intent of ADR-0270 (policy wall = daemon) had to be chosen again.

## 결정

1. ★**The daemon's `SpawnByCwd` handler calls the backend policy (in production = the agent's `llm_creation_refusal`) before the spawn (`manager.spawn_agent`), and answers with `Error` on refusal.**★ The place = right after the `MISSING_BACKEND` decision · before `CoreProfile::new`. ★The boundary is `spawn_agent`★ — that is where the on-the-fly profile gets onto the registry and the disk (the first item of 「영향」 below). `CoreProfile::new` only builds an in-memory value, so putting the call before it is a placement choice, not an invariant. It is an error path the shell already surfaces as is (「맥락」 above).
2. **The path, round-trip count and placement order of the shell's slot spawn stay as they are.** The slot spawn is not moved to `agent.new` — this decision replaces the 「`agent.new` 명령 경로로 바꾼다」 of ADR-0270 decision 3.1. The order of decisions 3.2 · 3.3 (policy wall → delete the shell check → reservation list) stays, and the 「셸의 정책 검사(`gate_backend`)를 지운다」 of 3.2 is the **policy part** only; the word net (`parse_backend`) stays in the shell.
3. **There are two daemon doors that look at the policy** — `agent.new` (`verb_new`) · the `SpawnByCwd` handler. The home of the policy is still the single place `LLM_BACKEND_POLICY`.
4. ★**This door does not distinguish callers — a caller axis is not added to the spawn packet now**★ (a cost we accept — see 「영향」 below). ★**Trigger to reopen = the day any backend is closed to the LLM or its declaration goes missing (`NO_POLICY_DECLARED`) — then a caller axis is added to the spawn packet.**★

## 거부한 대안

- **(a) Change the slot spawn to two calls, `agent.new` + `agent.spawn {target}` (the text of ADR-0270 decision 3.1 as written).** Rejected = code — `agent.new` only registers (a sleeping state — `agent/src/commands.rs:194`), so the round trips are two, if the second fails a sleeping orphan is left, the shell cannot use the agent's argument type (`AgentNewArgs`) (the purpose of 2-1) so it would have to build the argument JSON by hand, and the frontend's `SpawnByCwd` slot paths (`slot.createAgentHere` · frontend `agent.spawn`) would still bypass the policy.
  - ★**Do not bring these two back as reasons for rejecting this alternative — they do not hold in the code**★ (the corrected facts in 「근거」 below):
    - 「`agent.new` 의 `backend` 는 PascalCase 라 셸이 lowercase wire 낱말과 갈린다」 — the spelling does not diverge. This reason was withdrawn in review round 1 (F3).
    - 「슬롯 즉석 에이전트가 영속 프로필이 된다」 — `SpawnByCwd` also puts the on-the-fly profile on the registry and writes it to disk. 「영속 프로필이 되느냐」 is not the axis that separates (a) from this decision.
- **(b) Add a new daemon verb that creates and starts in one go.** Rejected = it only grows the surface without gaining anything over this decision (main's judgment). **Self-assessment of the rejection grounds: weak** (narrative — there is no quantitative, measured or code evidence). User confirmation 2026-10-06 — confirmed as marked weak.

## 영향 / 불변식

- ★**Invariant: the policy call comes before `manager.spawn_agent`**★ — the on-the-fly profile gets onto the registry and the disk inside it (`register_for_spawn` → `upsert_preserving_hierarchy` → `store.save`), so placing the call after it would leave a refused on-the-fly profile in the registry and on disk (the registration and save chain in 「근거」 above). `CoreProfile::new` only builds an in-memory value — putting the call before it is a placement choice (decision 1).
- **A refusal does not use 「마지막 실패」** — neither activation nor on-the-fly creation happened (ADR-0172 decisions 1 · 4).
- **The refusal text makes one trip through the daemon** — the daemon text goes to the caller without a prefix, so it has to stand on its own. It uses the frame of the shell text (「`backend '{word}' 는 아는 낱말이지만 이 표면으로는 지금 만들지 않는다 — {reason} 스폰 안 함.`」) as is, and `{word}` comes from the wire enum serialization (always lowercase). The bus error code is `CONFLICT`, as now.
- **The wire and catalog generations stay the same** — `PROTOCOL_VERSION` · the shell's `CATALOG_VERSION` (neither the packet shape nor today's behavior changes).
- ★**Cost we accept — this door does not distinguish callers**★: the policy is named 「LLM 제어 표면」 but the daemon's `SpawnByCwd` does not know who sent it. So **the human path also sees the same table** — what is newly reached is the two claude-pinned doors (`slot.createAgentHere` · frontend `agent.spawn` — the latter is the 「일부러 claude 에 못박은」 door of ADR-0219 decision 5). The frontend `agent.spawnInto` is **not a new exposure** (the shell door already sees the table without distinguishing callers). As a result two doors with the same name diverge — the frontend `agent.spawn` looks at the table and the agent bus `agent.spawn` (`create_and_start`) does not. **Zero impact today** — the table closes nothing and claude is open. The trigger to reopen is decision 4 above.
- **Put the reopen trigger at the edit site** — a note was added to the agent policy table doc: 「어느 줄의 `refusal` 을 `Some` 으로 바꾸거나 선언 없는 낱말을 들이기 전에 ADR-0279 를 다시 연다 — 데몬 `SpawnByCwd` 문이 사람 경로도 막는다」 (U1 `8b48386` — the `LLM_BACKEND_POLICY` doc in the agent's `commands.rs`).
- **This amends ADR-0270** —

  - In 「영향」, 「(ADR-0219 를 고친다 — …) 정책을 보는 문은 데몬 `agent.new` 하나가 된다」 → **two daemon doors** — `agent.new` (`verb_new`) · the `SpawnByCwd` handler.
  - The code anchor 「슬롯 스폰의 `agent.new` 경로」 and the GUI completion condition 「슬롯 스폰 경로 교체 뒤 레이아웃 불변」 in 「영향」 are also read in this sense (the policy wall in the `SpawnByCwd` handler · path unchanged).
  - The order of decisions 3.2 · 3.3 stays (decision 2 above).
  - The 「거부한 대안」 「셸 정책 검사를 그냥 지운다(슬롯 스폰 경로를 그대로 둔 채)」 stays rejected — the meaning of that alternative is to delete only the shell check **without a daemon wall**. The rejection reason 「정책을 보는 곳은 `agent.new` 하나뿐 · 슬롯 스폰이 `SpawnByCwd` 로 비켜 간다」 went stale after the U1 landing (two daemon doors — decision 3).

- **Why `MISSING_BACKEND` comes before the policy** — so that, for a request with an empty backend field (`backend: None`), a policy refusal does not hide the `MISSING_BACKEND` text 「어느 칸을 채우라」. The test `spawn_by_cwd_without_a_backend_is_refused` asserts that the policy is called zero times then.
