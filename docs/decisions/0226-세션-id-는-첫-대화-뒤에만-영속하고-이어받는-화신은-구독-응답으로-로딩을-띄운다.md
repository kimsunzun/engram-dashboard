# ADR-0226: 세션 id 는 첫 대화 뒤에만 영속하고 이어받는 화신은 구독 응답으로 로딩을 띄운다

- 상태: 확정 (2026-09-24, 근거: 사용자 결정 D1·D2·D5 + TRD 리뷰 5회(1~4차 FIX · 5차 PASS) — 아래 「근거」)
- 관련: Amends ADR-0008 (결정 첫 항 중 영속 시점만 발급은 spawn 그대로) · Amends ADR-0076 (결정 첫 항의 명시적 resume=true 존중과 둘째 항의 new_session_id 발급 영속 수단 및 영향의 ensure_session_id 불변식) · Amends ADR-0082 (결정 첫 항 중 손잡이 없는 이어받기 요청 및 영향의 Fresh 동사 이름) · Amends ADR-0145 (결정 1 빈 상태 판정 및 근거의 프로토콜 무변경 전제) · Amends ADR-0185 (결정 2 수령 지점 및 영향의 수령 단일점과 Phase 2 요구의 미강제 서술) · Amends ADR-0216 (결정 7 값 정책) · Amends ADR-0217 (결정 7 값 정책) · Amends ADR-0218 (결정 6 값 정책) · ADR-0083(시체 보존 — 입력 없이 끈 시체가 이제 다음 활성화에서 새 대화로 열린다) · ADR-0172(사전 판정 기각을 재론하지 않는 이유 — 아래 「근거」) · ADR-0204(ADR-0145 의 전제를 깬 쪽 — 아래 「맥락」) · `docs/process/S21-codex-backend/trd-resume-after-first-turn.md`(상세 설계 — `767a774`)

## 맥락

두 문제를 풀어야 했다. 뿌리는 하나다 — ★**「저장된 세션 id 가 있다」가 「이어받을 대화가 있다」를 뜻하지 않는다.**★

**P1 — codex 이어받기에서 챗 슬롯이 1.2~2.2초 동안 「새 에이전트」 첫 화면을 보였다 사라진다**(GUI 실측 4/4). claude 이어받기는 안 깜빡이고, 새 codex 는 첫 화면이 맞다.

- 인과: 명부 공표(`manager.rs:1447`) → 프론트 재부착 → 데몬이 링을 replay 하고 `ReplayComplete` 를 낸다(`connection_core.rs:1773`·`:1821`). claude 는 이력을 공표 **전에** 링에 심지만(`manager.rs:1375` → `:1834`), codex 는 통로가 공표 **뒤에** `thread/resume`(`transport.rs:810`)을 거쳐 이력을 넣는다(`:931`). 그 사이 챗 슬롯은 「복원 끝 + 0건 = 새 에이전트」(ADR-0145 결정 1 — `RichSlot.tsx:290`)로 첫 화면을 그린다. 지배항은 codex 자신의 `thread/resume` 왕복이다.
- ★ADR-0145 의 전제(「복원 끝 + 0건」이 새 에이전트를 정확히 가른다 — `0145:37`)를 **ADR-0204 가 말없이 깼다**★. ADR-0204 는 첫 화면·`ReplayComplete`·ADR-0145 를 언급하지 않는다.
- 프론트만 고치는 시도 둘은 실패했다(① = `32a76c9`(되돌림 `bdcf086`) · ② 는 화면 실측에서 실패(커밋 없음)): ① 「codex 이고 id 가 있으면 첫 화면 숨김」 → 새 codex 가 첫 화면을 잃었다(id 가 스폰 몇 초 뒤 기록된다) ② 부착 시점 래치 → 경합에 졌다 — 스폰 직후엔 프로필이 스토어에 없어 래치가 안 닫히고, 프로필이 도착할 때쯤엔 codex 가 이미 id 를 채워 「이어받기」로 굳는다.

**P2 — 한 마디도 안 하고 끈 에이전트는 다시 켤 수 없다.** 매번 「이어받을 대화가 없습니다」로 실패한다.

- codex app-server: `thread/resume` → `-32600 "no rollout found"` → `NoConversationToResume` 로 분류되고, 새 대화로 넘어가지 않는다(ADR-0082).
- claude: 스폰 때 우리가 `--session-id` 를 발급·**영속**하는데(`manager.rs:1238` → `profile.rs:674`) claude 는 첫 교환이 있어야 그 대화를 만든다(ADR-0172 맥락).
- codex 터미널: 락 회수가 대화 없이 몇 초 안에 id 를 잡아 영속한다(ADR-0218). 입력 없이 닫으면 재개가 exit 1 이다(`step-log.md:2442`).
- 사용자가 2026-09-21 에 「그냥 새 세션」 방향으로 고치기로 했다(같은 자리).

**그래서 영속 시점을 바꾼다.** 모드 선택은 이미 id 유무로 갈린다(`can_resume_profile` = 이어받기 축 ∧ id 존재 — `backend/mod.rs:704`). 그 입구는 두고 **id 를 언제 적느냐**만 바꾸면 「저장된 id 가 있다 ⟺ 이어받을 대화가 있다」가 한 규칙이 되고, id 없는 활성화는 Fresh 로 간다. 새 칸은 필요 없다 — 이미 있는 `backend_session_id` 다. P1 은 챗 슬롯이 「이 화신이 이어받으려고 떴나」를 알아야 풀리므로 그 사실을 구독 응답에 싣는다.

이 ADR 은 그중 **Phase A(D1 + D2 + D5)** 다. 이어받기가 「이어받을 대화가 없다」로 실패했을 때 자동으로 새 대화를 여는 D4 는 다음 라운드의 별도 ADR 이 맡는다(결정 10).

## 결정

1. ★**세션 id 는 첫 대화 뒤에만 영속한다(D1)**★ — 모든 백엔드·모드 공통(claude·codex × JSON·터미널). 「저장된 id 가 있다 ⟺ 이어받을 대화가 있다」. 모드 선택(`can_resume_profile`)은 바꾸지 않는다 — id 없음 → Fresh.
   - claude 는 스폰 때 뽑은 id 를 **메모리에만** 둔다. 뽑기는 맵을 안 건드리는 `ProfileRegistry::mint_session_id` 이고 발급 단일점은 registry 에 남는다. 값은 여전히 매번 새 uuid 다(ADR-0076 의 「Session ID already in use」 봉인 그대로).
   - Fresh 는 옛 값을 이력(`old_session_ids`)으로 밀고 빈 칸을 영속하는 release 동사로 시작한다 — 발급하는 backend 도 이제 칸을 비우고 시작한다. 이력 밀기라 ADR-0202 가 금한 파괴가 아니다.
   - Resume 은 저장값을 읽기만 한다 — 운영 경로에서 `ensure_session_id`·`new_session_id`(뽑아서 영속)를 걷는다.
2. **방아쇠 = 화신마다 하나인 「첫 제출 래치」(D3 — 구현에 위임된 자리의 고름).** 입력 둘·출력 하나다: `offer(id)`(이 화신의 id 가 알려졌다) · `note_submission()`(첫 사용자 턴이 상대에게 나가기 직전) — **둘 다 일어난 첫 순간에 한 번** commit 한다. 순서는 상관없다. ★제출 없이 화신이 끝나면 아무것도 영속되지 않는다★ — D1 이 원하는 결말이다.
   - 방아쇠는 **입력 경계** 하나다(백엔드 중립). 세션의 입력 두 동사가 `send_input` **앞에서** 센다. 우편 배달의 `Raw` 는 본문 뒤·제출 CR 바로 앞에서 센다(턴을 여는 것은 CR 이다).
   - 무엇이 턴 제출인가는 backend 지식이라 `InputEncoder::submits_turn` 에 둔다(ADR-0004): JSON 인코더 둘은 언제나 참(호출 1회 = 유저 턴 1개), `Raw` 는 CR 이 들어 있으면 참. ★이 CR 판정은 xterm 기본 키 인코딩에 매인다★ — 다른 키 인코딩 모드를 켜면 조용히 거짓이 된다.
   - offer 가 오는 자리: claude(두 모드) = 래치를 만드는 그 자리, `open_spawn` 보다 먼저(Fresh = 메모리의 값 · Resume = 저장값) · codex app-server = 통로 라이터가 핸드셰이크 응답에서 받는 자리(`record_session_id`) · codex 터미널 = 락 회수 스레드. offer 는 화신당 많아야 한 번이다(기록 포트의 계약 — `backend/mod.rs:189`).
   - 통로·백엔드의 계약은 바뀌지 않는다 — 둘은 여전히 「id 를 알게 되면 `SessionIdSink` 를 부른다」만 안다. 조립점이 그 자리에 래치의 수령 손잡이를 꽂는다.
3. ★**commit 은 비교-교체다.**★ 기존 기록 포트(`session_id_sink`)는 그대로 두고 그 안에서 부르는 동사만 `ProfileRegistry::commit_session_id(id, epoch, expected, new)` 로 바꾼다 — 새 기록 경로를 만들지 않는다. 화신 가드를 통과한 뒤, 칸이 이미 `new` 면 쓰지 않는다(쓸 것이 없다 — 예: claude Resume 의 offer 는 저장값 그대로다). 칸이 **이 화신이 시작할 때 본 값**(`expected` — release 뒤 본 값: Fresh = `None` · Resume = 저장값)일 때만 옛 값을 이력으로 밀고 `new` 를 써서 즉시 영속한다. 그 밖(다른 기록자가 먼저 바꿨다)이면 쓰지 않는다.
   - 화신 가드와 이력 밀기는 `observe_session_id` 와 **한 도우미**를 쓴다 — ADR-0217 결정 6(ADR-0218 결정 6 이 승계)의 「우회로를 새로 만들지 않는다」를 **준수**한다. 그 조항은 개정 대상이 아니다.
   - `observe_session_id`(덮어쓰기)는 claude `/clear` 추적기 몫으로 그대로 남는다(결정 5).
4. **commit 실패 규율.** 「포트는 화신당 많아야 한 번 불린다. 한 번 부르기 시작했으면(성공·거절·패닉 무엇으로 끝나든) 다시 부르지 않는다」.
   - 거절이면 턴은 나간다.
   - 패닉은 릴리스에서 데몬 종료(`panic = "abort"`)라 래치에 `catch_unwind` 를 두지 않는다.
   - 사용자 종료(데몬 셧다운 포함) 중의 제출은 세지도 보내지도 않는다 — 큐가 닫힌 뒤와 같은 `Err` 를 앞당긴다.
5. ★**claude `/clear` 는 D1 의 유일한 의도된 예외다(Q1 = (a))**★ — `/clear` 추적기(ADR-0008 결정 둘째 항)를 그대로 둔다. `/clear` 순간의 새 id 에는 아직 대화가 없는데도 곧바로 영속한다. 사유(사용자): `/clear` 는 옛 대화를 끝내는 사용자의 명시적 행위다. 대가: `/clear` 하고 입력 없이 끄면 다음 활성화가 실패한다 — 이 ADR 만이면 오늘과 같은 실패, D4 뒤에는 새 대화로 열린다.
6. ★**손잡이 없는 이어받기 요청은 새 대화로 연다 — 작성자의 고름이 아니라 D1 의 귀결이다.**★ D1 이 「저장된 id 없음 ⟺ 이어받을 대화 없음 → Fresh」로 정했고, 오늘 codex 우회가 같은 판단을 이미 「사용자 결정」으로 적어 두었다(`manager.rs:1989-1999`). 「세션 존재 → Resume」 모드 유도는 그대로다. shell 은 옛 길 그대로다.
   - ★보이는 결말이 바뀐다★: 손잡이 없는 claude 프로필에 `resume:true` 가 오면 오늘은 `Failed` + `NoConversationToResume`(claude JSON 기준 — 터미널이 그 분류에 닿는지는 미확인), 이후에는 `Started`(새 대화)다.
   - 손잡이는 spawn 안에서 한 번 읽고, 그 읽기가 권위다. 읽은 값이 없는데 backend 가 저장 손잡이로 이어받는 쪽이면 프로세스를 띄우기 **전에** `SpawnFailed` 로 거절한다 — claude 가 플래그 없이 떠 우리가 모르는 id 의 새 대화를 여는 일을 막는다.
7. ★**챗 슬롯은 「이 화신이 대화를 이어받으려고 떴나」를 구독 응답에서 받는다(D2)**★ — id 가 생길 때의 broadcast 가 아니다. 사유(사용자): 구독 응답은 replay·`ReplayComplete` 와 **같은 순서 스트림**을 타고, 값은 스폰 때 화신마다 고정된다.
   - 칸 = `SubscribeAck.continues_conversation: bool`(`#[serde(default)]`). 뜻 = 스폰 때 이어받을 손잡이를 실었다 — **이어받기의 성공 여부가 아니다.** 이름은 `SubscribeAction::Resume`(seq 이어받기)과 겹치지 않게 「resume」 낱말을 뺐다. 계산은 스폰의 손잡이 유무다(백엔드 중립).
   - ★표식과 replay 는 같은 화신에서 나온다★ — 구독 응답이 화신 표식과 이 칸을 **한 번의 조회**로 읽는다(`SubscribeReply { outcome, incarnation }`). 따로 읽으면 두 조회 사이의 화신 교체를 첫 화면/로딩 판정이 탄다.
   - 셸은 이 값을 복원 표식 프레임의 flags bit2(`0x04` — 길이 30 불변)로 나르고, 프론트는 `'live'` 통지의 info(`continuesConversation`)로 받는다. 없으면 거짓으로 읽는다.
   - broadcast 는 없다 — 프론트는 id 를 읽지 않고, commit 도 `ProfileListUpdated` 를 내지 않는다.
8. ★**이어받는 화신이 이력을 기다리는 동안 챗 슬롯은 새 공용 「로딩 패널」을 그린다(D5)**★ — 로딩 아이콘 + 선택적 텍스트 칸. 이번 용도는 **아이콘만, 텍스트 없음**. e-ink·reduced-motion 에서는 정지 아이콘. **시간 기반 지연 없음**(ADR-0038 · `0145:26`).
   - 판정(ADR-0145 결정 1 을 개정한다): `'live'` + 0건 + **이어받는 화신이 아님** → 빈 상태(첫 화면) · 이어받는 화신이면 행을 그리는 첫 항목(또는 입력·화신 종료)까지 로딩 패널. 행을 그리지 않는 항목은 대기를 끝내지 않는다 — 실측상 이어받기의 첫 라이브 프레임이 `Usage` 다. 대기 꼬리의 판정도 같은 기준으로 맞춘다.
   - 대기가 끝나는 넷: 첫 이력 항목 도착 · 사용자 입력 · 화신 종료(지금의 막이 이긴다) · D4 재시작(새 화신 → 표식 거짓 → 첫 화면).
   - **배치 = 대화 영역 가운데, 하단 입력창은 그대로 활성**(Q2 = (a) 선택으로 정해짐 — (가)/(나)를 Q2 와 함께 제시, 2026-09-24).
9. **이어받았는데 이력이 0건으로 온 화신은 입력할 때까지 로딩이 남는다(Q2 = (a)).** 새 「이력 끝」 신호를 만들지 않는다. 사유(사용자 — 「공수가 크지 않는쪽으로해. 그럴 확률이 거의 없다는거잖아」(오타만 고침)): 품이 적고 드문 경우다(이력 조회 예산 초과·실패, claude transcript 판독 실패). 이 결정은 입력창이 살아 있는 결정 8 의 배치에 기댄다 — 빠져나갈 길이 입력이다.
10. **단계(Q5 = (a)) — 이 ADR 은 Phase A(D1 + D2 + D5)다.** D4(이어받기가 「이어받을 대화가 없다」 부류로 실패하면 같은 활성화 안에서 새 대화)는 다음 라운드의 별도 ADR 이 ADR-0082 를 그 부류에 한해 개정한다. 이 ADR 만 착지했을 때:
    - 손잡이가 **있는** 이어받기는 활성화 결말·기록·처분이 오늘과 같다. 챗 슬롯이 막 전까지 첫 화면 대신 로딩을 그리는 것만 다르다.
    - D1 이전에 영속된 옛 쓰레기 id, 그리고 이 결정이 새로 만드는 쓰레기(제출로 셌는데 대화가 없는 경우 — 신뢰 모달의 Enter · 붙여넣기 · 영속 뒤 제출 쓰기 실패 · 첫 답 전 kill 인데 claude 가 아직 대화를 안 만든 경우 · `/clear` 후 말없이 끔)는 오늘과 같은 실패로 남는다. 단 오늘은 입력 없이 끈 **모든** 세션이 이 실패였고, 이 뒤에는 이 부분집합만 남는다.
11. ★**codex 터미널 예외 — 「첫 턴 전 영속」이 그 칸에서만 성립하지 않는다.**★ id 가 락 회수로만 오고(ADR-0218), 파킹 우편이 있으면 첫 턴이 언제나 먼저다. 그 칸의 commit 은 제출과 락 회수 중 **늦은 쪽**에 난다. ADR-0218 대비 회귀는 아니다 — 오늘도 그 칸의 id 는 회수 순간에만 생긴다.

## 거부한 대안

출처를 항목마다 적는다 — 「사용자 결정」 = 사용자가 고르거나 버린 것 · 「리뷰 지적·고름」 = 리뷰 지적을 받아, 또는 D3·내부 구현 위임 안에서 작성자가 고른 것 · 「실측 실패(되돌림)」 = 실제로 시도했다가 화면 실측에서 실패해 되돌리거나 버린 것.

- **commit 에 덮어쓰기 동사(`observe_session_id`)를 쓴다** — 그 동사는 무조건 교체라, 첫 제출 **전에** 다른 기록자가 칸을 바꿨으면 commit 이 스폰 때 값으로 **되감는다.** 그 기록자가 실재한다 — claude 추적기가 대조 없이 쓴다(`daemon/src/lib.rs:289`). 「리뷰 지적·고름」
- **id 가 생길 때 broadcast 로 챗 슬롯에 알린다** — replay·`ReplayComplete` 와 같은 순서 스트림을 타지 않는다. 「사용자 결정」(D2)
- **화신별 「이력 끝」 신호**(명부 표식·스트림 내 표식 — D1+D2 가 대체한 설계) · 그것을 Q2 (b) 로 다시 여는 것. 「사용자 결정」(D1·D2 · Q2 = (a))
- **`/clear` 를 래치로 돌린다(Q1 (b))** — `/clear` 를 보면 저장된 id 를 비우고 새 id 는 다음 제출 때 영속한다. 헛시도가 없어지는 대신 추적기 콜백을 화신의 래치까지 잇는 배선이 붙는다. 사용자가 (a) 를 골랐다. 「사용자 결정」
- **슬롯 전체를 덮는 로딩** — 「대화 영역 가운데 + 입력창 활성」 배치가 이긴 대안이다. TRD 가 적은 귀결: 슬롯 전체를 덮으면 이력 0건 화신에서 빠져나갈 길(입력)이 없고, Q2 = (a) 가 그 배치에 기댄다. 「사용자 결정」(Q2 = (a) 선택으로 정해짐 — 사용자 2026-09-24. (가) 가운데 아이콘 + 입력창 활성 · (나) 슬롯 전체 덮기를 Q2 와 함께 제시)
- **codex `writer_loop` 에서 `turn/start` 직전을 방아쇠로** — codex JSON 한 칸만 덮는다. claude 두 모드와 codex 터미널의 통로(stdio·PTY)는 턴을 모르는 파이프라 같은 자리가 없어, 결국 입력 경계에 방아쇠를 하나 더 세워야 한다 — 방아쇠가 둘이 된다. 「리뷰 지적·고름」(D3 위임 안의 고름 — 오케스트레이터 원안을 작성자가 기각)
- **세션에 두 번째 화신 표식 칸**(`Incarnation` 을 세션 칸으로) — 기존 `epoch` 칸 옆에 표식이 둘이 되고, 둘이 갈리면 어느 쪽이 화신인지 모른다. 소유권 분할(`session=id/cwd/epoch/…`) 위반이다. `Incarnation` 은 응답을 만들 때 조립하는 값 타입으로만 둔다. 「리뷰 지적·고름」
- **래치에 `catch_unwind`** — 릴리스는 `panic = "abort"`(`Cargo.toml:35`)라 아무것도 잡지 않는 죽은 코드다. 「리뷰 지적·고름」
- ★**프론트 신호만으로 첫 화면을 가린다**★ — 두 번 시도해 둘 다 실패했다(① = `32a76c9`(되돌림 `bdcf086`) · ② 는 화면 실측에서 실패(커밋 없음) · 사유 = 머지 `9fa72dc` 본문 · `.claude/handoff/history/20260922-120942-v030-release-and-followups.md:62-74`). ① 「codex 이고 프로필에 `backend_session_id` 가 있으면 첫 화면을 숨긴다」 → 새 codex 가 첫 화면을 잃었다(id 가 새 스폰 몇 초 뒤에 적힌다) ② 붙는 순간의 참조 래치 → 경합에 졌다: 스폰 직후엔 프로필이 스토어에 없어 래치가 안 닫히고, 프로필이 도착할 때쯤엔 codex 가 이미 id 를 채워 놔 「이어받기」로 굳는다. 「실측 실패(되돌림)」 — 그래서 D2 는 화신이 태어날 때 정해지는 값을 구독 응답에 싣는다.

## 근거

- **사용자 결정 기록:** D1·D2·D3·D5(2026-09-23/24) · Q1 = (a) · Q2 = (a) · 로딩 배치 = 대화 영역 가운데 + 입력창 활성(Q2 = (a) 선택으로 정해짐 — (가)/(나)를 Q2 와 함께 제시) · Q5 = (a) — 뒤 넷은 2026-09-24.
- **상세 설계 = `docs/process/S21-codex-backend/trd-resume-after-first-turn.md`(`767a774`)** — 리뷰 5회(1~4차 FIX · 5차 PASS)를 거쳤다. 이 ADR 의 `file:line` 은 master `93f0f9f` 판독 기준이고, 이 결정을 박을 때 코드는 아직 바뀌지 않았다.
- **P1 실측(GUI 4/4)** — 재활성화 기준: 명부 공표 32–183 ms → replay 0 프레임으로 `ReplayComplete` +10 ms → 첫 화면 → `initialize` 341–587 ms → `thread/resume` 1393–2243 ms → 첫 라이브 프레임 = `Usage` → 첫 화면 사라짐 → 이력 +20–70 ms.
- **첫 턴 전의 대화에는 잃을 것이 없다** — codex rollout 은 첫 사용자 메시지부터 생긴다(`docs/reference/backend-capabilities.md` §1 — codex 0.154.0 자기 시험). claude 는 첫 교환 뒤에 대화를 만든다(ADR-0172 맥락). 그래서 ADR-0185 의 「크래시 창」(응답 수령 → 영속 사이 — `0185:21`)은 codex 터미널을 뺀 세 칸에서 녹아 없어진다 — 첫 턴이 영속 **뒤에** 나간다.
- ★**비교-교체가 ADR-0216 이 기각한 「빈 칸에만 쓴다」(`0216:61`)가 아닌 이유**★ — 기각된 규칙은 「칸이 비었을 때만 쓰고 값이 있으면 거절」이었다. 그 고장은 새 id 가 나오는 분기에서 손잡이가 낡아 두 번째 재개부터 **조용히** 깨지는 것이었다. 비교-교체의 `expected` 는 빈 칸이 아니라 **이 화신이 시작 때 본 값**이다 — release 뒤 본 값(Fresh = `None` · Resume = 저장값). 그래서 이어받기 화신의 **첫 offer** 가 저장값과 다른 id 를 내면(재개가 다른 id 를 돌려주는 경우) 칸 == `expected` 라 **교체된다** — 0216 이 지키려던 분기가 그대로 착지한다.
  - ★이 논증은 첫 offer 위에 선다★ — offer 는 화신당 한 번이고 포트도 화신당 많아야 한 번 불린다(결정 2·4). 「commit 이 성공하면 `expected` 가 그 값으로 따라온다」는 절은 방어용이라 이 논증을 떠받치지 않는다.
  - 거절하는 것은 시작 때 본 뒤·유일한 commit 전에 **다른 기록자**가 칸을 바꾼 경우뿐이다(claude 추적기의 표류·`/clear`). 포트가 화신당 많아야 한 번이라 그보다 앞선 commit 이 없고, commit 뒤의 추적기 쓰기에는 래치가 반응하지 않는다(그 값이 그대로 선다). 거기서 덮어쓰기를 하면 추적기 값을 스폰 때 값으로 **되감는다.**
  - codex 에는 추적기가 안 붙으므로(`assigns_sid` 게이트) 오늘의 codex 동작은 바뀌지 않는다.
- **ADR-0172 의 사전 판정 기각을 다시 여는 것이 아니다** — ADR-0172 가 버린 것은 「우리 관측을 새 칸에 영속해 활성화 전에 판정한다」다. 이 결정은 새 칸이 없다 — 이미 있는 `backend_session_id` 를 **언제** 적느냐만 바꾼다. 활성화는 여전히 id 가 있으면 이어받기를 **시도**하고, 실패는 여전히 시도한 자리에서 관측한다(ADR-0172 결정 1). 도장 없는 옛 항목(쓰레기 id)은 사전 판정이 아니라 D4 의 반응형 처리가 받는다. ADR-0008 이 금한 claude 파일 위의 기능 확장도 없다 — 무엇도 claude 파일을 읽어 판정하지 않는다.
