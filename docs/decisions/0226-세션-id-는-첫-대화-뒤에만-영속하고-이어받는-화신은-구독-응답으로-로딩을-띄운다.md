## 맥락

Two problems had to be solved. They have one root — ★**「저장된 세션 id 가 있다」 does not mean 「이어받을 대화가 있다」.**★

**P1 — in a codex resume, the chat slot shows the 「새 에이전트」 first screen for 1.2–2.2 seconds and then it disappears** (GUI measured 4/4). A claude resume does not flicker, and a new codex correctly shows the first screen.

- Causality: registry publication (`manager.rs:1447`) → frontend re-attach → the daemon replays the ring and emits `ReplayComplete` (`connection_core.rs:1773` · `:1821`). claude seeds the history into the ring **before** publication (`manager.rs:1375` → `:1834`), but for codex the channel puts the history in **after** publication, through `thread/resume` (`transport.rs:810`) (`:931`). In between, the chat slot draws the first screen as 「복원 끝 + 0건 = 새 에이전트」 (ADR-0145 decision 1 — `RichSlot.tsx:290`). The dominant term is codex's own `thread/resume` round trip.
- ★The premise of ADR-0145 (「복원 끝 + 0건」 distinguishes a new agent exactly — `0145:37`) was **broken silently by ADR-0204**★. ADR-0204 does not mention the first screen, `ReplayComplete`, or ADR-0145.
- Two attempts to fix only the frontend failed (① = `32a76c9` (reverted in `bdcf086`) · ② failed in on-screen measurement (no commit)): ① 「codex 이고 id 가 있으면 첫 화면 숨김」 → a new codex lost its first screen (the id is recorded a few seconds after spawn) ② an attach-time latch → lost the race — right after spawn the profile is not yet in the store so the latch does not close, and by the time the profile arrives codex has already filled in the id, which hardens into 「이어받기」.

**P2 — an agent shut down without a single word cannot be turned on again.** Every time it fails with 「이어받을 대화가 없습니다」.

- codex app-server: `thread/resume` → `-32600 "no rollout found"` → classified as `NoConversationToResume`, and it does not fall through to a new conversation (ADR-0082).
- claude: at spawn we issue and **persist** `--session-id` (`manager.rs:1238` → `profile.rs:674`), but claude creates that conversation only once there is a first exchange (ADR-0172 context).
- codex terminal: lock reclaim grabs the id and persists it within a few seconds with no conversation (ADR-0218). If closed without input, the resume exits with 1 (`step-log.md:2442`).
- On 2026-09-21 the user decided to fix it in the 「그냥 새 세션」 direction (same place).

**So the persistence time is changed.** Mode selection already splits on whether an id exists (`can_resume_profile` = resume axis ∧ id exists — `backend/mod.rs:704`). If that entrance is left alone and only **when the id is written** changes, then 「저장된 id 가 있다 ⟺ 이어받을 대화가 있다」 becomes one rule, and an activation without an id goes to Fresh. No new field is needed — it is the existing `backend_session_id`. P1 is solved only when the chat slot knows 「이 화신이 이어받으려고 떴나」, so that fact is carried in the subscribe response.

This ADR is **Phase A (D1 + D2 + D5)** of that. D4, which automatically opens a new conversation when a resume fails with 「이어받을 대화가 없다」, is handled by a separate ADR in the next round (decision 10).

## 결정

1. ★**The session id is persisted only after the first conversation (D1)**★ — common to all backends and modes (claude · codex × JSON · terminal). 「저장된 id 가 있다 ⟺ 이어받을 대화가 있다」. Mode selection (`can_resume_profile`) is not changed — no id → Fresh.
   - claude keeps the id drawn at spawn **in memory only**. The drawing is `ProfileRegistry::mint_session_id`, which does not touch the map, and the single point of issuance stays in the registry. The value is still a new uuid every time (the 「Session ID already in use」 seal of ADR-0076 stays as is).
   - Fresh starts with a release verb that pushes the old value into history (`old_session_ids`) and persists an empty slot — the issuing backend now also starts with the slot emptied. It is a history push, so it is not the destruction that ADR-0202 forbade.
   - Resume only reads the stored value — `ensure_session_id` and `new_session_id` (draw and persist) are removed from the operating path.
2. **The trigger = a 「첫 제출 래치」, one per incarnation (D3 — a choice in a spot delegated to the implementation).** Two inputs and one output: `offer(id)` (this incarnation's id became known) · `note_submission()` (just before the first user turn goes to the other side) — it commits **once, at the first moment both have happened**. The order does not matter. ★If the incarnation ends without a submission, nothing is persisted★ — the outcome D1 wants.
   - The trigger is **one input boundary** (backend-neutral). The two input verbs of the session count **before** `send_input`. For mail delivery, `Raw` counts after the body and just before the submit CR (it is the CR that opens a turn).
   - What counts as a turn submission is backend knowledge, so it lives in `InputEncoder::submits_turn` (ADR-0004): the two JSON encoders are always true (one call = one user turn), and `Raw` is true if a CR is in it. ★This CR decision depends on the default xterm key encoding★ — turning on another key encoding mode silently makes it false.
   - Where the offer arrives: claude (both modes) = the place that creates the latch, before `open_spawn` (Fresh = the in-memory value · Resume = the stored value) · codex app-server = the place where the channel writer receives it from the handshake response (`record_session_id`) · codex terminal = the lock-reclaim thread. An offer comes at most once per incarnation (the contract of the recording port — `backend/mod.rs:189`).
   - The contract of the channel and backend does not change — they still know only 「id 를 알게 되면 `SessionIdSink` 를 부른다」. The assembly point plugs the latch's receiving handle into that place.
3. ★**The commit is a compare-and-swap.**★ The existing recording port (`session_id_sink`) is left as is, and only the verb called inside it is changed to `ProfileRegistry::commit_session_id(id, epoch, expected, new)` — no new recording path is made. After passing the incarnation guard, if the slot is already `new`, nothing is written (there is nothing to write — for example, the offer of a claude Resume is the stored value as is). Only when the slot is **the value this incarnation saw when it started** (`expected` — the value seen after release: Fresh = `None` · Resume = the stored value) is the old value pushed into history, `new` written, and persisted immediately. Otherwise (another writer changed it first), nothing is written.
   - The incarnation guard and the history push use **one helper** with `observe_session_id` — this **complies with** the 「우회로를 새로 만들지 않는다」 of ADR-0217 decision 6 (inherited by ADR-0218 decision 6). That clause is not an amendment target.
   - `observe_session_id` (overwrite) remains as it is as the share of the claude `/clear` tracker (decision 5).
4. **Commit failure discipline.** 「포트는 화신당 많아야 한 번 불린다. 한 번 부르기 시작했으면(성공·거절·패닉 무엇으로 끝나든) 다시 부르지 않는다」 (the port is called at most once per incarnation; once the call has started, however it ends — success, rejection, or panic — it is not called again).
   - If it is rejected, the turn still goes out.
   - A panic is a daemon exit in release (`panic = "abort"`), so no `catch_unwind` is put on the latch.
   - A submission during a user shutdown (including a daemon shutdown) is neither counted nor sent — it brings forward the same `Err` as after the queue is closed.
5. ★**claude `/clear` is the only intended exception to D1 (Q1 = (a))**★ — the `/clear` tracker (the second item of the decision in ADR-0008) is left as is. The new id at the moment of `/clear` is persisted right away even though it has no conversation yet. Reason (user): `/clear` is the user's explicit act of ending the old conversation. Cost: if you `/clear` and shut down without input, the next activation fails — with this ADR alone, the same failure as today; after D4, it opens as a new conversation.
6. ★**A resume request with no handle is opened as a new conversation — this is a consequence of D1, not the author's choice.**★ D1 decided 「저장된 id 없음 ⟺ 이어받을 대화 없음 → Fresh」, and today's codex bypass already wrote the same judgment as a 「사용자 결정」 (`manager.rs:1989-1999`). The mode derivation 「세션 존재 → Resume」 stays as is. The shell is on the old path as is.
   - ★The visible outcome changes★: when `resume:true` arrives for a claude profile with no handle, today it is `Failed` + `NoConversationToResume` (on the claude JSON basis — whether the terminal reaches that classification is unconfirmed), and afterward it is `Started` (a new conversation).
   - The handle is read once inside spawn, and that read is authoritative. If there is no value read but the backend is the kind that resumes with a stored handle, it is rejected with `SpawnFailed` **before** the process is launched — this prevents claude from starting without the flag and opening a new conversation with an id we do not know.
7. ★**The chat slot receives 「이 화신이 대화를 이어받으려고 떴나」 in the subscribe response (D2)**★ — not in a broadcast when the id is created. Reason (user): the subscribe response rides the **same ordered stream** as the replay and `ReplayComplete`, and the value is fixed per incarnation at spawn.
   - Field = `SubscribeAck.continues_conversation: bool` (`#[serde(default)]`). Meaning = a handle to resume was loaded at spawn — **it is not whether the resume succeeded.** The word 「resume」 was left out of the name so it does not collide with `SubscribeAction::Resume` (seq resume). The computation is whether the spawn had a handle (backend-neutral).
   - ★The marker and the replay come from the same incarnation★ — the subscribe response reads the incarnation marker and this field in **one lookup** (`SubscribeReply { outcome, incarnation }`). If they are read separately, the first-screen/loading decision rides an incarnation swap between the two lookups.
   - The shell carries this value in flags bit2 (`0x04` — length 30 unchanged) of the restore-marker frame, and the frontend receives it as the info (`continuesConversation`) of the `'live'` notification. If absent, it is read as false.
   - There is no broadcast — the frontend does not read the id, and the commit does not emit `ProfileListUpdated` either.
8. ★**While a resuming incarnation waits for history, the chat slot draws a new shared 「로딩 패널」 (D5)**★ — a loading icon + an optional text field. For this use, **icon only, no text**. A static icon in e-ink and reduced-motion. **No time-based delay** (ADR-0038 · `0145:26`).
   - The decision (amends ADR-0145 decision 1): `'live'` + 0 items + **not a resuming incarnation** → the empty state (first screen) · if it is a resuming incarnation, the loading panel until the first item that draws a row (or an input, or the incarnation's end). An item that draws no row does not end the wait — in measurement, the first live frame of a resume is `Usage`. The decision of the waiting tail is aligned to the same criterion.
   - Four ways the wait ends: arrival of the first history item · user input · incarnation end (the current veil wins) · D4 restart (new incarnation → marker false → first screen).
   - **Placement = the center of the conversation area, with the bottom input box still active** (settled by choosing Q2 = (a) — (가)/(나) were presented together with Q2, 2026-09-24).
9. **An incarnation that resumed but whose history came back as 0 items keeps loading until you type (Q2 = (a)).** No new 「이력 끝」 signal is made. Reason (user — 「공수가 크지 않는쪽으로해. 그럴 확률이 거의 없다는거잖아」 (only a typo fixed)): it takes little effort and the case is rare (history lookup budget exceeded or failed, claude transcript read failure). This decision leans on the decision 8 placement where the input box is alive — the way out is input.
10. **Phases (Q5 = (a)) — this ADR is Phase A (D1 + D2 + D5).** D4 (when a resume fails in the 「이어받을 대화가 없다」 class, a new conversation within the same activation) will be a separate ADR in the next round, amending ADR-0082 for that class only. When only this ADR has landed:
    - For a resume that **has** a handle, the activation outcome, recording, and disposition are the same as today. The only difference is that the chat slot draws loading, instead of the first screen, until the veil.
    - Old garbage ids persisted before D1, and the garbage this decision newly creates (cases counted as a submission with no conversation — Enter on the trust modal · paste · a submit write failure after persistence · a kill before the first reply where claude has not yet created the conversation · shutting down silently after `/clear`) remain as the same failure as today. But today **every** session shut down without input was this failure, and after this only this subset remains.
11. ★**The codex terminal exception — that slot is the only one where 「첫 턴 전 영속」 does not hold.**★ The id comes only through lock reclaim (ADR-0218), and if there is parking mail, the first turn is always first. That slot's commit happens at the **later** of the submission and the lock reclaim. It is not a regression against ADR-0218 — today too the id of that slot arises only at the moment of reclaim.

## 거부한 대안

The source is written per item — 「사용자 결정」 = what the user chose or dropped · 「리뷰 지적·고름」 = what the author chose, on a review finding or inside D3 or the internal-implementation delegation · 「실측 실패(되돌림)」 = what was actually tried, failed in on-screen measurement, and was reverted or dropped.

- **Use the overwrite verb (`observe_session_id`) for the commit** — that verb is an unconditional replace, so if another writer changed the slot **before** the first submission, the commit **rewinds** it to the value at spawn. That writer exists — the claude tracker writes without comparing (`daemon/src/lib.rs:289`). 「리뷰 지적·고름」
- **Notify the chat slot by broadcast when the id is created** — it does not ride the same ordered stream as the replay and `ReplayComplete`. 「사용자 결정」 (D2)
- **A per-incarnation 「이력 끝」 signal** (a registry marker · an in-stream marker — the design D1+D2 replaced) · reopening that as Q2 (b). 「사용자 결정」 (D1 · D2 · Q2 = (a))
- **Run `/clear` through the latch (Q1 (b))** — when `/clear` is seen, the stored id is emptied and the new id is persisted at the next submission. In exchange for removing the wasted attempt, wiring is added that connects the tracker callback to the incarnation's latch. The user chose (a). 「사용자 결정」
- **Loading that covers the whole slot** — the 「대화 영역 가운데 + 입력창 활성」 placement is the alternative that won. The consequence the TRD wrote: if the whole slot is covered, there is no way out (input) for an incarnation with 0 history items, and Q2 = (a) leans on that placement. 「사용자 결정」 (settled by choosing Q2 = (a) — user 2026-09-24. (가) center icon + input box active · (나) cover the whole slot were presented together with Q2)
- **Trigger just before `turn/start` in the codex `writer_loop`** — it covers only the codex JSON slot. The channels (stdio · PTY) of the two claude modes and the codex terminal are pipes that do not know turns, so the same spot does not exist, and in the end one more trigger would have to be set at the input boundary — there would be two triggers. 「리뷰 지적·고름」 (a choice inside the D3 delegation — the author rejected the orchestrator's original proposal)
- **A second incarnation-marker field on the session** (making `Incarnation` a session field) — next to the existing `epoch` field there would be two markers, and if they diverge it is unknown which one is the incarnation. It violates the ownership split (`session=id/cwd/epoch/…`). `Incarnation` is kept only as a value type assembled when the response is built. 「리뷰 지적·고름」
- **`catch_unwind` on the latch** — release is `panic = "abort"` (`Cargo.toml:35`), so it is dead code that catches nothing. 「리뷰 지적·고름」
- ★**Hide the first screen with a frontend signal alone**★ — tried twice and both failed (① = `32a76c9` (reverted in `bdcf086`) · ② failed in on-screen measurement (no commit) · reason = the body of merge `9fa72dc` · `.claude/handoff/history/20260922-120942-v030-release-and-followups.md:62-74`). ① 「codex 이고 프로필에 `backend_session_id` 가 있으면 첫 화면을 숨긴다」 → a new codex lost its first screen (the id is written a few seconds after a new spawn) ② a reference latch at the moment of attaching → lost the race: right after spawn the profile is not in the store so the latch does not close, and by the time the profile arrives codex has already filled in the id, which hardens into 「이어받기」. 「실측 실패(되돌림)」 — so D2 carries in the subscribe response a value that is decided when the incarnation is born.

## 근거

- **User decision record:** D1 · D2 · D3 · D5 (2026-09-23/24) · Q1 = (a) · Q2 = (a) · loading placement = conversation area center + input box active (settled by choosing Q2 = (a) — (가)/(나) were presented together with Q2) · Q5 = (a) — the last four are 2026-09-24.
- **Detailed design = `docs/process/S21-codex-backend/trd-resume-after-first-turn.md` (`767a774`)** — it went through 5 reviews (rounds 1–4 FIX · round 5 PASS). The `file:line` references in this ADR are based on reading master `93f0f9f`, and when this decision was recorded the code had not yet changed.
- **P1 measurement (GUI 4/4)** — on reactivation: registry publication 32–183 ms → replay 0 frames, `ReplayComplete` +10 ms → first screen → `initialize` 341–587 ms → `thread/resume` 1393–2243 ms → first live frame = `Usage` → first screen disappears → history +20–70 ms.
- **There is nothing to lose in a conversation before the first turn** — a codex rollout exists from the first user message (`docs/reference/backend-capabilities.md` §1 — codex 0.154.0 self-test). claude creates the conversation after the first exchange (ADR-0172 context). So the 「크래시 창」 of ADR-0185 (between receiving the response and persisting — `0185:21`) melts away in the three slots other than the codex terminal — the first turn goes out **after** persistence.
- ★**Why the compare-and-swap is not the 「빈 칸에만 쓴다」 that ADR-0216 rejected** (`0216:61`)★ — the rejected rule was 「칸이 비었을 때만 쓰고 값이 있으면 거절」. Its failure was that in the branch where a new id appears, the handle goes stale and breaks **silently** from the second resume on. The `expected` of the compare-and-swap is not the empty slot but **the value this incarnation saw at start** — the value seen after release (Fresh = `None` · Resume = the stored value). So if the **first offer** of a resuming incarnation gives an id different from the stored value (when the resume returns a different id), slot == `expected`, so it **is replaced** — the branch that 0216 wanted to protect lands as it is.
  - ★This argument stands on the first offer★ — an offer is once per incarnation and the port is also called at most once per incarnation (decisions 2 and 4). The clause 「commit 이 성공하면 `expected` 가 그 값으로 따라온다」 is defensive and does not hold this argument up.
  - What is rejected is only the case where **another writer** changed the slot after the start and before the only commit (claude tracker drift · `/clear`). Since the port is at most once per incarnation, there is no earlier commit than that, and the latch does not react to tracker writes after the commit (that value stands). If an overwrite were done there, it would **rewind** the tracker value to the value at spawn.
  - No tracker is attached to codex (the `assigns_sid` gate), so today's codex behavior does not change.
- **This is not reopening ADR-0172's rejection of pre-decision** — what ADR-0172 discarded is 「우리 관측을 새 칸에 영속해 활성화 전에 판정한다」. This decision has no new field — it changes only **when** the existing `backend_session_id` is written. The activation still **tries** to resume if there is an id, and the failure is still observed at the place where it was tried (ADR-0172 decision 1). An old entry with no stamp (garbage id) is received not by a pre-decision but by D4's reactive handling. There is also no feature extension on the claude file that ADR-0008 forbade — nothing reads the claude file to decide.

## Corrections during implementation (2026-09-24 — Phase A landed)

- **Landing:** A1 `56a4e98` · A2 `495dba3` · A3 `b012e5a` · A4 `fc67cbe`. The meaning of decisions 1–11 did not change — ★but one clause of decision 8, 「e-ink·reduced-motion 에서는 정지 아이콘」, was reversed by a user decision (2026-09-24)★ (see the item 「로딩 스피너는 reduced-motion·e-ink 에서도 늘 돈다」 below — since this ADR had not yet been pushed to master, it is corrected here instead of under a new number). Below are the places where the implementation narrowed or filled in the words of the decision body — **the decision body is not edited; corrections pile up here.** The source of truth for the expression is the code (`RichSlot.tsx`), and the form written here is as of landing. Details and differences from the original plan = TRD §3-5 · §4-1 「구현 결과」, gates · numbers = this round's entry in the step-log.
- **Decision 8 「행을 그리는 첫 항목」 — a turn divider is not history.** History arrival = there is at least one item with `isRenderedItem(item) && item.kind !== 'separator'`. If a turn closes after only usage has arrived, the accumulator attaches a divider, but that row is a 12px spacer — if it were counted, the loading would clear and an empty board with no first screen would remain. The user bubble is the same row class (`'boundary'`) as the divider, so it is counted as history instead of being excluded by class. `isRenderedItem` itself is still `rowKindOf !== 'skip'` as is (one body with ADR-0051). 「리뷰 지적·고름」
- **Decision 8 「대기 꼬리의 판정도 같은 기준으로 맞춘다」 — narrowed to taking the tail down only while waiting for history.** There is no tail only while `historyPending = continuesConversation && !hasSent && !hasHistoryRow`, and otherwise the pre-A4 rule stays as is (`streaming = awaiting || (!turnDone && items.length > 0 && !historyPending)`) — if the marker is false, it is exactly the same as today. The TRD original (changing the tail condition itself to 「행을 그리는 항목이 있다」) would also change the tail of a slot with no marker, and the review verdicts split; it was adopted conservatively, and in round 2 the three reviewers agreed. The reason for taking it down with `historyPending` rather than the condition that draws the loading (`awaitingHistory` — restore finished ∧ no veil): if a tail gets in during a re-attach of the same incarnation's `'buffering'`, or in a window where only the panel briefly dropped under the veil, it flickers panel → tail → panel. 「리뷰 지적·고름」
- **Decision 8 placement — add a faint veil over the conversation area and put in no guidance text.** The placement (the icon at the center of the conversation area · input box active — the way out in decision 9) is as is. Veil = `bg-foreground/8` (the covered area is always empty, so a background-color family would be invisible) · `pointer-events-none` · placed inside the ScrollArea so that it covers only the conversation area and not the input box — this leans on the fact that the ScrollArea's Viewport and inner wrapper are not positioned, and the home of that invariant is the header of `src/components/ui/scroll-area.tsx`. Guidance like 「끄고 다시 켜기」 will be **decided when the abnormal case where history never arrives is actually reproduced.** 「사용자 결정」 (2026-09-24)
- **The ended veil (`SlotUnavailableVeil`) stays pointer pass-through.** Scrolling, selecting, and clicking behind the veil still work, and what is blocked is only input going to the dead agent — today the per-slot guard already does exactly that (no code change). ★ADR-0148 did not write why the veil is pointer pass-through★ (ADR-0165 「영향」 writes only that this fact and the input guard are separate) — that behavior is first fixed here as a user decision. 「사용자 결정」 (2026-09-24)
- **Relation to ADR-0148 — the loading decision folds in liveness.** Because `awaitingHistory` folds in agent absence, if a resuming incarnation dies while loading, under the veil is an empty conversation area (no mascot · first screen · spinner). It collides in appearance with 「빈 상태 판정에 생존 조건을 접지 않는다」 in ADR-0148 「영향」 (`0148:34`), but it is allowed: decision 8's 「화신 종료(지금의 막이 이긴다)」 and TRD §4-1 frontend test ⑤ (agent absent → veil, no loading) decided this. Reason = the loading spinner is an activity indicator, not content, so ADR-0148 decision 2 (content pinning) does not apply. The empty-state decision (`showEmpty`) still does not know liveness — ★so this is not an amendment of ADR-0148 (interpretation)★. 「리뷰 지적·고름」
- **The loading spinner always spins, even in reduced-motion and e-ink.** A4 stopped the rotation under the two conditions (the TRD §3-5 original), but the tree's rotating glyph had already removed the stop with 「멈춘 스피너는 멈춤과 구분되지 않는다」 (`agentGlyph.css`, user decision 2026-08-24) — to follow the same rule, the stop rule was removed (`loading-panel.css`). 「사용자 결정」 (2026-09-24)
