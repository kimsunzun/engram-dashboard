# ADR-0224: After a close, focus returns to the previous content cell, and control cells do not receive focus

- 상태: 확정 (2026-09-24, basis: user decision + peer survey `docs/research/layout-pane-focus-rules-survey-2026-09-24.md`) · **not yet implemented** (next session) · **1 open item — 「결정 5」 (decision 5), user confirmation before implementation**
- 관련: Amends ADR-0073 (clause deferring backend focus enforcement) · ADR-0035 (layout authority = src-tauri) · ADR-0066 (click-to-focus) · ADR-0067 (right-click leaves focus unchanged) · ADR-0068 (the reference point of relative direction tokens = focus) · ADR-0064 (control-content pop-out) · ADR-0148 (preserving the dead-agent screen) · ADR-0222 (boot = one focused empty cell — the tree is placed there) · ADR-0225 (the way to view the tree separately = tree slot pop-out) · `src-tauri/src/layout/manager.rs`(`make_view`·`split_slot`·`set_focused_slot`·`fixup_focus`·`set_slot_content`·`prepare_detached_view`) · `src-tauri/src/layout/types.rs`(`View`) · `src-tauri/src/layout/commands.rs`(`slot.focus`)

> ★**The 「레이아웃은 디스크 영속이 없으므로」 (since the layout has no disk persistence) at the end of 「영향 / 불변식」 is no longer a fact**★ (note 2026-10-04, decision unchanged). Since storage management P3b3 (`f9db35a`), the layout is persisted in `shell\state\state.json`, and a boot after a normal exit restores it without asking (TRD `docs/process/S21-storage/trd.md` §6). **The result 「이력도 앱을 다시 켜면 빈다」 (the history also empties when the app is restarted) stays as it is — its basis is now decision 1 (the history is kept only in shell memory and is not sent over the wire or to disk).** The persisted tab entry (`TabEntry` in `src-tauri/src/state/schema.rs`) carries only `focused_slot_id`. If the history is placed as a field of `View`, the persistence conversion (`src-tauri/src/state/convert.rs` — it spells out the fields of `View` by name) and the butt-joint test in `schema.rs` break at compile time — the answer is to drop that field in the writing-side conversion (`<칸>: _`) and fill it with an empty value in the reading-side conversion (where `View` is built), and to persist it a new ADR that changes decision 1 is needed. If it is placed in a separate map, which 「영향」 allowed, `View` stays as it is, so the build does not break.

## 맥락

The focused cell (the focus ring · the target of the tree's 「열기」 · the reference point of LLM relative directions) is one per view and the shell (`src-tauri`) owns it in memory (ADR-0035). It is separate from the DOM focus that keyboard input goes to.

Today, closing the focused cell sends focus to the tree's **first cell**. If the first cell is the agent tree, the focus ring appears on the tree, and then 「열기」 goes to the first empty cell and not to the cell the user was working in. The LLM's explicit focus (`slot.focus`) also accepts a control cell. ADR-0073 blocked only click focus in the frontend and deferred backend enforcement.

On 2026-09-23 a fix that sent automatic focus to 「자동 포커스를 첫 **콘텐츠** 칸으로」 (automatic focus to the first **content** cell) was made and then reverted — focus sat on an agent cell the user had never chosen, and 「열기」 overwrote that cell's screen.

Peer survey conclusion: there is no industry-common rule for focus after a close, and there are four families (the previously focused cell / the absorbing sibling · tree order / under the cursor / first cell · none). Many editors and multiplexers use the previously focused cell (the defaults of tmux · zellij · VS Code · Emacs). Tools that keep panels separately take control panels out of the work targets.

## 결정

1. **The shell keeps a focus-history container (a stack) per view.** Every time focus moves, the previous target is pushed. It is kept only in shell memory and is not sent over the wire or to disk — the screen receives only the resulting focused cell, as it does now.
2. **When the focused cell is closed, the history is scanned backward to return focus (fallback).**
   - If a **content cell** (an empty cell or an agent cell) that is still alive in the tree comes up, focus goes there. Cells that were already closed or moved to another window, and control cells, are skipped.
   - If none is found in the history, it is the **first empty cell**, and if there is none either, **no focus**.
   - Closing a cell that has no focus leaves focus as it is (identical across all peers).
3. **Control cells (the agent tree · the preset palette) do not receive focus** — the LLM's explicit focus is also rejected as a value. Excluding click focus (ADR-0073 decision 1) stays as it is.
4. **If the only cell of a new view is a control cell, it starts with no focus** — the window where a control cell was popped out (`prepare_detached_view`) is that case. Decision 3 implies it.
5. **Open — when the focused cell becomes a control cell through a content replacement** (`set_slot_content` — the most common path, placing the tree in the focused empty cell at boot). Under decision 3 focus must leave that cell, and where it goes splits in two (raised by the 2026-09-24 document review — before user confirmation):
   - (a) The same fallback as decision 2 (the previous content cell) — consistent, but if the previous cell is an agent cell, the tree's 「열기」 immediately changes that screen. It is **exactly the same scenario** as the regression reverted on 2026-09-23 (in `LR{A: 에이전트, B: 빈 칸(포커스)}`, turn B into the tree → focus A → 「열기」 overwrites A).
   - (b) No focus — 「열기」 goes to the first empty cell (or a notice if there is none) and is safe. In exchange, the reference point of relative direction tokens disappears.

## 거부한 대안

- **Keep the current behavior (first cell)** — the focus ring appears on the tree, and then 「열기」 goes to the first empty cell and not to the cell being worked in (survey option A). The user chose the previous-cell rule.
- **First empty cell only, no focus if none (option B)** — there is no overwrite risk, but if there is no empty cell the reference point for direction targeting disappears and focus does not return to the cell being worked in. The user judged 「직전 칸이 맞다」 (the previous cell is right).
- **A one-cell cache (the user's first proposal — "기존 포커싱 대상 캐싱" (caching the existing focus target))** — closing twice in a row leaves nowhere to return to the second time (herdr has this limit — the survey). The user settled on a 「이력 컨테이너」 (history container).
- **Two pointers — separate the keyboard focus from the work-target cell (option D, the VS Code · Zed · JetBrains shape)** — the wire, the frontend and the LLM surface would all have to be redone, and it inherits the risk of the previous-cell rule as is.
- **The absorbing-sibling rule (Vim · JetBrains · Windows Terminal)** — in our tree the sibling can be a tree cell, so an eligibility filter is needed anyway, and in that family (Neovim #20455) there are user complaints wanting the previous window.
- **The first content cell (what was put in and reverted on 2026-09-23)** — focus sat on an agent cell the user had never chosen and 「열기」 overwrote that screen (found in review).

## 근거

- User decision (2026-09-24): "직전칸이 맞긴한데" (the previous cell is right, though) · "이력 컨테이너에 저장했다가 폴백해주면 됨. 확정임" (just store it in a history container and fall back to it. Settled). The 「알려진 대가」 (known cost) below was explained to the user just before it was settled.
- Peer survey (medium · one cross-family adversarial review reflected) — the document above.
- Code facts (corrected by the 2026-09-24 document review): there are four places that **assign** focus (`make_view` initial value · `split_slot` · `set_focused_slot` · `fixup_focus`), and two more places that **change the eligibility** of the focused cell (`set_slot_content` — it can turn the focused cell into a control cell · `prepare_detached_view` — the only cell of a new view can be a control cell).

## 영향 / 불변식

- **Every path that moves focus pushes onto the history** — if a new path is made and the history update is left out, the fallback goes to the wrong cell. We recommend gathering the focus assignment into one helper (an implementation judgment).
- ★**A control cell can remain in the history**★ (when a content cell became a control cell by a content replacement) — the fallback filters it out **at read time** (decision 2). Do not substitute filtering only at push time.
- ★**If the history is placed in `View`, `#[serde(skip)]`·`#[ts(skip)]` is required**★ — `View` is a type exported with ts-rs (`src-tauri/bindings/View.ts`, subject to the CI generated-output sync gate) and goes out over the wire. If placed in a separate map, `close_tab`·`close_window`·`drop_detached_view` delete it together. The same cell is placed only once (focusing it again moves it to the top — size ≤ the number of cells of the view).
- The doc comment of `focused_slot_id` (「트리 첫 슬롯으로 폴백」, falls back to the tree's first slot — duplicated in `types.rs` · the generated binding `View.ts`) changes, so the binding is regenerated together.
- **Rejection goes out as a value** — a new `LayoutError` variant → the existing `CONFLICT` error code (`slot.focus` already declares `errors [CONFLICT]` — no change in the declaration). In the description of `slot.focus` that the LLM reads, write 「제어 칸(트리·팔레트)은 거절」 (control cells (tree · palette) are rejected). Existing tests that will change = `close_slot_focus_fallback_to_first` (`manager.rs`) · in some cases `close_root_slot_keeps_view_empty`.
- **When there is no focus, relative direction tokens (`left`, etc.) have no answer** (`spatial.rs` uses focus as the reference point) — the reason for rejecting option B remains as a residual in this decision too (history exhausted + no empty cell · a pop-out view with only one control cell). Corner words and cell ids still work for specifying.
- **Known cost:** if the previous cell is an agent cell, the tree's 「열기」 changes that cell's screen into the new agent (the agent process keeps running and stays in the tree). The survey saw this risk as **the same shape** as the reverted regression — the only difference is that the user had chosen that cell before (this ADR's distinction). If that cell is the preserved screen of a dead agent, it disappears (ADR-0148).
- Since the layout has no disk persistence, the history also empties when the app is restarted.
