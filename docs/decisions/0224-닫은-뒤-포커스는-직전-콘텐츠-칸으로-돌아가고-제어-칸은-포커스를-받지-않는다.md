# ADR-0224: 닫은 뒤 포커스는 직전 콘텐츠 칸으로 돌아가고 제어 칸은 포커스를 받지 않는다

- 상태: 확정 (2026-09-24, 근거: 사용자 결정 + 피어 서베이 `docs/research/layout-pane-focus-rules-survey-2026-09-24.md`) · **구현 전**(다음 세션) · **미결 1 건 — 「결정 5」, 구현 전에 사용자 확인**
- 관련: Amends ADR-0073 (백엔드 포커스 강제 보류 조항) · ADR-0035(레이아웃 권위 = src-tauri) · ADR-0066(click-to-focus) · ADR-0067(우클릭 포커스 불변) · ADR-0068(상대 방향 토큰의 기준점 = 포커스) · ADR-0064(제어 콘텐츠 팝아웃) · ADR-0148(죽은 에이전트 화면 보존) · ADR-0222(부팅 = 포커스된 빈 칸 하나 — 트리를 거기에 놓는다) · ADR-0225(트리를 따로 보는 길 = 트리 슬롯 팝아웃) · `src-tauri/src/layout/manager.rs`(`make_view`·`split_slot`·`set_focused_slot`·`fixup_focus`·`set_slot_content`·`prepare_detached_view`) · `src-tauri/src/layout/types.rs`(`View`) · `src-tauri/src/layout/commands.rs`(`slot.focus`)

## 맥락

포커스된 칸(포커스 링 · 트리 「열기」의 대상 · LLM 상대 방향의 기준점)은 뷰마다 하나이고 셸(`src-tauri`)이 메모리에 소유한다(ADR-0035). 키보드 입력이 가는 DOM 포커스와는 별개다.

지금 포커스된 칸을 닫으면 트리의 **첫 칸**으로 간다. 첫 칸이 에이전트 트리면 포커스 링이 트리에 뜨고, 그때 「열기」는 사용자가 작업하던 칸이 아니라 첫 빈 칸으로 간다. LLM 의 명시 포커스(`slot.focus`)도 제어 칸을 받는다. ADR-0073 은 클릭 포커스만 프론트에서 막고 백엔드 강제는 보류했다.

2026-09-23 에 「자동 포커스를 첫 **콘텐츠** 칸으로」 보내는 수정을 했다가 되돌렸다 — 사용자가 고른 적 없는 에이전트 칸에 포커스가 앉아 「열기」가 그 칸 화면을 덮어썼다.

피어 서베이 결론: 닫은 뒤 포커스의 업계 공통 규칙은 없고 네 계열이다(직전 포커스 칸 / 흡수 형제·트리 순서 / 커서 아래 / 첫 칸·없음). 에디터·멀티플렉서 다수가 직전 포커스 칸(tmux·zellij·VS Code·Emacs 기본)이다. 패널을 따로 두는 도구는 제어 패널을 작업 대상에서 뺀다.

## 결정

1. **셸이 뷰마다 포커스 이력 컨테이너(스택)를 둔다.** 포커스를 옮길 때마다 직전 대상을 쌓는다. 셸 메모리에만 두며 와이어·디스크에는 나가지 않는다 — 화면은 지금처럼 결과로 나온 포커스된 칸만 받는다.
2. **포커스된 칸을 닫으면 이력을 거꾸로 훑어 되돌린다(폴백).**
   - 트리에 아직 살아 있는 **콘텐츠 칸**(빈 칸·에이전트 칸)이 나오면 거기로 간다. 이미 닫혔거나 다른 창으로 옮겨진 칸, 제어 칸은 건너뛴다.
   - 이력에서 못 찾으면 **첫 빈 칸**, 그것도 없으면 **포커스 없음**이다.
   - 포커스 없는 칸을 닫으면 포커스는 그대로다(피어 전원 동일).
3. **제어 칸(에이전트 트리·프리셋 팔레트)은 포커스를 받지 않는다** — LLM 의 명시 포커스도 값으로 거절한다. 클릭 포커스 배제(ADR-0073 결정 1)는 그대로다.
4. **새 뷰의 유일한 칸이 제어 칸이면 포커스 없음으로 시작한다** — 제어 칸을 팝아웃한 창(`prepare_detached_view`)이 그 경우다. 결정 3이 함의한다.
5. **미결 — 포커스된 칸이 내용 교체로 제어 칸이 될 때**(`set_slot_content` — 부팅의 포커스된 빈 칸에 트리를 놓는 가장 흔한 경로). 결정 3에 따라 포커스는 그 칸을 떠나야 하는데, 어디로 갈지가 둘로 갈린다(2026-09-24 문서 리뷰가 제기 — 사용자 확인 전):
   - (a) 결정 2와 같은 폴백(직전 콘텐츠 칸) — 일관되지만, 직전 칸이 에이전트 칸이면 트리의 「열기」가 곧바로 그 화면을 바꾼다. 2026-09-23 에 되돌린 회귀(`LR{A: 에이전트, B: 빈 칸(포커스)}` 에서 B 를 트리로 → 포커스 A → 「열기」가 A 를 덮음)와 **정확히 같은 시나리오**다.
   - (b) 포커스 없음 — 「열기」는 첫 빈 칸(없으면 안내)으로 가 안전하다. 대신 상대 방향 토큰의 기준점이 사라진다.

## 거부한 대안

- **현행 유지(첫 칸)** — 포커스 링이 트리에 뜨고, 그때 「열기」가 작업하던 칸이 아니라 첫 빈 칸으로 간다(서베이 선택지 A). 사용자가 직전 칸 규칙을 골랐다.
- **첫 빈 칸만, 없으면 포커스 없음(선택지 B)** — 덮어쓰기 위험은 없지만, 빈 칸이 없으면 방향 지정의 기준점이 사라지고 작업하던 칸으로 돌아가지 않는다. 사용자가 「직전 칸이 맞다」고 판단했다.
- **한 칸 캐시(사용자의 첫 제안 — "기존 포커싱 대상 캐싱")** — 연달아 두 번 닫으면 두 번째에 돌아갈 곳이 없다(herdr 가 이 한계를 가진다 — 서베이). 사용자가 「이력 컨테이너」로 확정했다.
- **포인터 둘 — 키보드 포커스와 작업 대상 칸 분리(선택지 D, VS Code·Zed·JetBrains 모양)** — 와이어·프론트·LLM 표면을 전부 다시 짜야 하고, 직전 칸 규칙의 위험을 그대로 물려받는다.
- **흡수 형제 규칙(Vim·JetBrains·Windows Terminal)** — 우리 트리는 형제가 트리 칸일 수 있어 자격 필터가 어차피 필요하고, 그 계열(Neovim #20455)에 직전 창을 원하는 사용자 불만이 있다.
- **첫 콘텐츠 칸(2026-09-23 에 넣었다가 되돌린 것)** — 사용자가 고른 적 없는 에이전트 칸에 포커스가 앉아 「열기」가 그 화면을 덮어썼다(리뷰 적출).

## 근거

- 사용자 결정(2026-09-24): "직전칸이 맞긴한데" · "이력 컨테이너에 저장했다가 폴백해주면 됨. 확정임". 아래 「알려진 대가」는 확정 직전에 사용자에게 설명했다.
- 피어 서베이(medium · cross-family 적대 리뷰 1 회 반영) — 위 문서.
- 코드 사실(2026-09-24 문서 리뷰가 교정): 포커스를 **대입**하는 곳은 넷(`make_view` 초기값 · `split_slot` · `set_focused_slot` · `fixup_focus`)이고, 포커스된 칸의 **자격을 바꾸는** 곳이 둘 더 있다(`set_slot_content` — 포커스된 칸을 제어 칸으로 바꿀 수 있다 · `prepare_detached_view` — 새 뷰의 유일한 칸이 제어 칸일 수 있다).

## 영향 / 불변식

- **포커스를 옮기는 모든 경로가 이력에 쌓는다** — 새 경로를 만들 때 이력 갱신을 빠뜨리면 폴백이 엉뚱한 칸으로 간다. 포커스 대입을 한 도우미로 모으는 것을 권한다(구현 판단).
- ★**이력에 제어 칸이 남을 수 있다**★(내용 교체로 콘텐츠 칸이 제어 칸이 된 경우) — 폴백이 **읽을 때** 거른다(결정 2). 쌓을 때만 거르는 것으로 대신하지 말 것.
- ★**이력을 `View` 에 두면 `#[serde(skip)]`·`#[ts(skip)]` 필수**★ — `View` 는 ts-rs 로 내보내는 타입이고(`src-tauri/bindings/View.ts`, CI 생성물 sync 게이트 대상) 와이어로 나간다. 별도 맵에 두면 `close_tab`·`close_window`·`drop_detached_view` 가 함께 지운다. 같은 칸은 한 번만 둔다(다시 포커스하면 맨 위로 — 크기 ≤ 뷰의 칸 수).
- `focused_slot_id` 의 doc 주석(「트리 첫 슬롯으로 폴백」 — `types.rs` · 생성 바인딩 `View.ts` 에 복제)이 바뀌므로 바인딩도 함께 다시 굽는다.
- **거절은 값으로 나간다** — 새 `LayoutError` 변형 → 기존 `CONFLICT` 오류 코드(`slot.focus` 는 이미 `errors [CONFLICT]` 를 선언한다 — 선언 변경 없음). LLM 이 읽는 `slot.focus` 설명문에 「제어 칸(트리·팔레트)은 거절」을 적는다. 바뀔 기존 테스트 = `close_slot_focus_fallback_to_first`(`manager.rs`) · 경우에 따라 `close_root_slot_keeps_view_empty`.
- **포커스 없음이 되면 상대 방향 토큰(`left` 등)은 답이 없다**(`spatial.rs` 가 포커스를 기준점으로 쓴다) — 선택지 B 를 거부한 사유가 이 결정에도 잔여로 남는다(이력 소진 + 빈 칸 없음 · 제어 칸 하나뿐인 팝아웃 뷰). 모서리 낱말·칸 id 로는 계속 지정된다.
- **알려진 대가:** 직전 칸이 에이전트 칸이면 트리의 「열기」가 그 칸 화면을 새 에이전트로 바꾼다(에이전트 프로세스는 계속 돌고 트리에 남는다). 서베이는 이 위험을 되돌린 회귀와 **같은 모양**으로 봤다 — 차이는 그 칸을 사용자가 전에 고른 적이 있다는 것뿐이다(이 ADR 의 구분). 그 칸이 죽은 에이전트의 보존 화면이면 사라진다(ADR-0148).
- 레이아웃은 디스크 영속이 없으므로 이력도 앱을 다시 켜면 빈다.
