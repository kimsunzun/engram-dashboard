# ADR-0169: Chat style is configuration data, not a command, and the two pre-bus side doors are removed

- 상태: 확정 (2026-08-23, basis: user decision + measured) · 부분 폐기 by ADR-0265 (decision 1's ui.refresh path, the accepted cost, and the chatStyleStore invariant)
- 관련: Amends ADR-0051 (the claim that the LLM handle __engramChat and the human UI use the same actions) · Amends ADR-0055 (decision 3's clause keeping __engramLayout (agent invoke survives)) · Amends ADR-0035 (the §5 clause that the control surface is __engramLayout) · Amends ADR-0156 (the two chat reads cited as the reason for removing the side doors) · ADR-0167 (source of the classification rule) · S20 TRD §6 Step 5 · Amended by ADR-0265 (decision 1's ui.refresh path, the accepted cost, and the chatStyleStore invariant)

## 맥락

Before the bus, two global handles existed — `window.__engramLayout` (15 methods) and `window.__engramChat` (5 items). They do the same job as the command table (`window.__engramCmd`), so they are a second door, which conflicts with the single control surface of 「LLM-우선 제어」. The Step 5 plan was to **first promote what the commands did not cover, then delete both handles**, and the TRD listed the 5 chat items as promotion targets too.

The layout side went as planned. 10 of the 15 already had commands, and the remaining 5 (render modes) were promoted.

On the chat side the plan ran into ADR-0167. ADR-0167 decision 1 set a **classification rule** — things that create, split, or destroy (windows, splits) are commands; display state that the web layer can re-apply live (theme, later fonts) is data + refresh. All 10 chat styles are CSS variables, and all ten pass that gate (「refresh 한 번으로 눈앞에서 바뀌는가」 (does one refresh change it before the eyes?)). On top of that, the TRD itself wrote 「창별 값은 명령으로 표현되지 않는다」 (per-window values are not expressed as commands) in one paragraph and left `chat` as a bus target on the very next line, so the document contradicted itself.

## 결정

**Two things are decided together.**

**① The 10 chat styles (margins and font size) are not promoted to commands.** They go through configuration data + the `ui.refresh` path. That path does not exist yet for chat, so for now they are promoted nowhere.

**② The two pre-bus side doors are deleted** — `window.__engramLayout` and `window.__engramChat`. The former became pure duplication once all 15 were covered by commands; the latter is no longer a promotion target under ①, so it is removed without promotion. This lands the S20 Step 5 teardown.

Values and boot behavior are left alone — `chatStyleStore` stays, and so does the path that reads localStorage at boot and applies it to `:root`. The defaults are already the values the user tuned live and confirmed, so the screen does not change.

**Accepted cost: until a storage path exists, there is no way to change the chat style in a release build.** A dev build can still touch it through `window.__engram.chatStyle`. This is a live 「LLM-우선 제어」 gap, and recording it is half the purpose of this document.

## 거부한 대안

- **Make one command per option (`chat.style.get`·`set`·`patch`·`reset`·`defaults`)** — this was actually implemented and then dropped. ① User judgment: *"그런 옵션을 내가 제어하는건 저장되어있는거 한꺼번에 긁어서 보여주는것들도 있기 때문에 하나하나 커맨드는 낭비임"* — a settings UI reads the stored values all at once and shows them, so one command per item does not match how they are consumed. ② ADR-0167 decision 1 is a classification rule, not a deferral, so promoting would repeat the misclassification that ADR had just corrected. ③ Code basis: these values are per-window webview state, but a bus envelope is delivered only to the one host window the shell picks, and that host moves around while running (`Registered::repick` in `view_commands.rs`) — if promoted onto the bus, the write would go to another window's store and the call would answer `ok` while the screen did not change. **Do not revive the discarded implementation.**
- **Keep `__engramChat` until a storage system exists** — this was the first choice, and the user reversed it. The reason given for keeping it was 「지우면 제어 수단이 사라진다」 (deleting it removes the means of control), which was an overstatement: the screen does not change (default = the tuned and confirmed values, boot load kept), the dev-build handle remains, and **it is not a debugging tool**. The `dom` mode is different in nature — xterm is a canvas, so it turns output that `innerText` cannot read into a plain `<pre>` as an observation tool — but margins and font size are taste settings and do not get the same exemption. Keeping it only postpones the single-surface goal.
- **Add a destination argument to the frontend `slot.popout` to make up the side door's reach** — not added. The frontend and shell `slot.popout` differ in what they accept and what they give, so a 「한쪽만 맞춰 고치지 말 것」 (do not fix only one side) note sits side by side in both pieces of code, and merging them belongs to a later step that retires the frontend registry. Fixing only one side now only enlarges what that step has to move.

## 근거

- **ADR-0167 decision 1 is the source of this classification.** That ADR removed `theme.set` and `theme.toggle` as the physical examples of misclassification, and named 「나중에 폰트」 (later fonts) explicitly. Two of the 10 chat styles are `fontSize` and `lineHeight`.
- **★The reason `ui-settings.json` has no chat field is ADR-0167 decision 2★** — that decision limited itself to 「범위는 테마 하나. 폰트를 비롯한 다른 칸은 후속이다」 (scope is the theme only. Fonts and the other fields are follow-ups). **It is not because of ADR-0051** — that file (`src-tauri/src/ui_settings.rs`) first appeared with ADR-0166 on 2026-08-21, six weeks after ADR-0051 (2026-07-06). What 0051 rejected was **the cost at the time** of laying a new Tauri command + settings.json + emit loop for chat preferences; it is not a clause that blocks adding a chat field now. ★If this distinction is blurred, the next session will read it as 「챗 칸을 더하려면 0051을 폐기해야 한다」 (adding a chat field requires discarding 0051) — it does not.★
- **There is no human UI (measured).** The non-test consumers of `useChatStyleStore` are just the boot load (`main.tsx`) and the dev-build handle. There are zero subscribing components and zero corresponding commands. So deleting this handle does not break any human path. **The human half of the premise ADR-0051 relied on — 「사람 UI와 LLM이 같은 store 액션을 부른다」 (the human UI and the LLM call the same store actions) — was never realized in the first place** — that is the second reason this ADR partially amends 0051.
- **The boot path was confirmed by measured GUI run** (release build, session record — the only basis that cannot be re-checked from the repository). It read all ten `--chat-*` values inlined on `document.documentElement.style`. ★Do not measure with `getComputedStyle`★ — `theme.css` declares the same values as fallbacks, so it passes even when the boot path is dead. The discriminator is the inline style that only `applyToRoot` leaves behind.

## 영향 / 불변식

- **`window.__engramChat` and `window.__engramLayout` do not exist.** Residual gate = `rg "__engramLayout|__engramChat" src/ src-tauri/` → 0 lines.
- **Do not create commands for chat style.** That is the first alternative this ADR rejected. The place to build it is a settings item of the storage system.
- **Do not touch `chatStyleStore`** — the storage system will hook into it. That the write actions are reachable only in dev builds is the intended state, not dead code to clean up.
- **The control surface is not yet one.** More globals remain outside the bus, and that list is **recorded nowhere** — a hand-counted list goes stale (this time too it was counted as 「둘」 (two) and turned out to be three). The policy home is CLAUDE.md 「LLM-우선 제어」. ★**Among those remaining, `__ENGRAM_AGENT__` has a definition site that introduces itself as 「정식 §5 표면」 (the official §5 surface)** — nothing in the code marks it as a side door, so do not decide from the comment alone★ (it is the one of the two surfaces ADR-0055 decision 3 deferred that survived, and the `/qa` measurement recipe depends on it for profile creation and deletion).
- **What was lost is convenience, not capability.** `withGlobalTauri` is on, so CDP can call `list_tabs` and `move_slot_to_window` directly through `__TAURI__.core.invoke`. It just does not go through the command table. ★But the frontend `slot.popout` takes no destination argument, so **the command table alone** cannot move a slot to an existing window★ — 「15개가 전부 덮였다」 (all 15 are covered) is behavioral coverage, not contract agreement.
