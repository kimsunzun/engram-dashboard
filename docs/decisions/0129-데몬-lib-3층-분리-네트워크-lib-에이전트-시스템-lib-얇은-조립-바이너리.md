# ADR-0129: Split the daemon lib into three layers — network lib · agent-system lib · thin assembly binary

- 상태: 확정 (2026-08-04, basis: user's objection + measurement of all production code + the ADR-0020 boundary-erosion history) · 부분 폐기 by ADR-0130 (decisions 2 and 3 put on hold)
- 관련: ADR-0020(Stage 1 — extracting `ConnectionCore` as carrier-neutral. This decision promotes that intent to a crate boundary) · ADR-0110(split out the messaging kernel crate — same idiom: a compiler-enforced wall) · ADR-0029(agent host = daemon process — **not a revival**, see the impact section below) · ADR-0028(event bus single-push) · ADR-0127(preceding slice — tearing out the attach machinery shrinks the code to split by 592 lines) · `crates/engram-dashboard-daemon/src/ws.rs` · `connection_core.rs` · `control/` · `messaging_host.rs` · step-log S18.16 · Amended by ADR-0130 (decisions 2 and 3 put on hold)

## 맥락

The user's objection (2026-08-03): *"The daemon should be a relay that only carries the protocol, and it should be reusable in other systems, but at some point daemon = the whole backend."*

Measurement confirmed this. A breakdown of the **11,729 lines** of production build (the 7,142 lines of experiments and harness are already behind the `test-harness` feature gate, so they are excluded):

| Process upkeep | Assembly | WS server | `ConnectionCore` | Control plane | Messaging glue |
|---:|---:|---:|---:|---:|---:|
| 368 | 1,011 | 2,287 | 2,509 | 4,800 | 754 |

**Network upkeep is only a part, and everything else is agent vocabulary.** So "another system that needs only the network" that wants to reuse this crate has to drag in the control plane and messaging as well.

## 결정

1. **Daemon lib = network only.** Socket accept · Origin allowlist · auth handshake · connection lifetime · single writer per connection · shutdown signal · connection registry (fan-out) · portfile · single instance. There is **only one** opening upward — it takes in an **opaque frame** and passes it up, and sends one out over this connection. **It does not know agent vocabulary even as a type.**
   > **note (2026-08-04 · slice 0-1 measured · user approved):** The opaque-frame opening has **two shapes** — **per connection** (`frame_port::FrameSink`) and **all-connection fan-out** (the `ConnRegistry::broadcast_text` path). The "only one" above means *vocabulary isolation ends with one kind of thing (the opaque frame)*, and **does not mean there is a single surface** — the original text is written per connection ("sends one out over this connection"), so all-connection fan-out does not fit that sentence. The decision holds only if fan-out is a port too (porting just the per-connection path would leave it unmet). The target shape and invariants of the decision are unchanged, so this is not a discard (supersede) — it is an addendum to the wording. The fan-out port is **wired in decision 3 (thin assembly)**, because the status-notification and messaging flush sinks are injected when `AgentManager` is assembled and they share the registry.
2. **Agent-system lib.** `ConnectionCore` (protocol decode and dispatch) · `AgentManager` hosting · control plane (MCP · ingress · priming) · messaging glue.
3. **Executable binary = thin assembly.** It only wires the two together.

## 거부한 대안

- **Status quo (daemon = the whole backend)** — the user's objection itself is the reason to reject. Reuse is impossible, and a consumer that needs only the network layer takes on all of the agent vocabulary as a dependency.
- **Keep the boundary by module discipline and review, without splitting the crate** — **history has already refuted this.** ADR-0020 Stage 1 chose exactly that approach: it pulled `ConnectionCore` out of `ws.rs` into a carrier-neutral module, and that file's header **still** declares "does not know TcpStream/tungstenite/the codec". Yet in the meantime the control plane and the messaging glue flowed into the same crate. In this codebase, where a different coder session takes each task, **a boundary kept only by documents and review does not survive a change of session** — this is the same conclusion ADR-0110 reached on the messaging kernel, and it uses the same remedy as then (**a compiler-enforced wall**).
- **Two layers (daemon lib + everything else)** — one of the two libs ends up carrying the assembly responsibility, and that lib becomes "the place that knows everything" again. It would move the current problem to a new name. **Only by keeping a thin assembly binary separate** do the two libs stay ignorant of each other.

## 근거

- **The boundary intent is already in the code.** The `ConnectionCore` of ADR-0020 Stage 1 is designed to be carrier-neutral, and that declaration is alive in the file header. This decision does not invent a new design; it **promotes an existing boundary to a crate** — so the design risk is low.
- **Authentication is not an obstacle.** It is wedged into the agent command list as `AgentCommand::Auth` right now, and it only has to move to a handshake type owned by the daemon. **If only the wire JSON shape is kept, the frontend is unchanged** (the frontend does not know which crate a type lives in). So "the daemon lib does not depend on the protocol crate" holds practically for free.
   > **note (2026-08-05 · slice 1 measured · user approved):** The last sentence of this item — *So "the daemon lib does not depend on the protocol crate" holds practically for free.* — is **false now** (the original is not edited; it is corrected here). The network lib's (`engram-dashboard-net`) `protocol` dependency is **permanent**: `crates/engram-dashboard-net/src/portfile.rs` re-exports from protocol the shared struct `DaemonInfo` of daemon.json, and that struct is a two-process contract (the daemon writes it, the client reads it), so it cannot be moved into either crate. **Keep this apart from the carry-over of 0-4** — the `AgentCommand::Auth`/`PROTOCOL_VERSION` edge in `ws.rs` disappears when 0-4 (moving the auth types) is done, but the `portfile`↔`DaemonInfo` edge remains after that. That is, "no protocol dependency" was not a side benefit of this decision. The target shape and invariants are unchanged, so this is not a discard (supersede) — it is a correction of fact.
- **The preceding slice shrank the target.** Tearing out the turn-observation attach machinery with ADR-0127 took `ws.rs` down by 592 lines — work starts after the code to split has become that much smaller.

## 영향 / 불변식

- **Invariant:** **If an agent-vocabulary type appears in the daemon lib, this decision is violated.** The isolation gate is set in the same form as for the messaging kernel (ADR-0110) — 0 lines from a forbidden-import grep. The compiler catches it first, and the grep catches the paths that leak through comments and test-helper names.
   > **note (2026-08-05 · slice 1 measured · user approved):** The "0 lines from a forbidden-import grep" above differs from the gate actually set — slice 1 set **multiple gates**, and one of them is an **allowlist** whose expected value is not 0. *Why:* the invariant of this decision is at the **type level** (agent *vocabulary*), not the crate level. `portfile` legitimately needs `protocol::DaemonInfo` and two of core's process-liveness helpers (`agent::platform::pid_alive_with_start_time` · `current_process_start_time`), and none of the three is agent vocabulary — for the same reason the `discovery` crate already depends on `core` (precedent). So the core edge is bound by a **symbol allowlist**, not forbidden. *The three actual gates (source of truth = the header of `crates/engram-dashboard-net/src/lib.rs`):* ① 0 lines of references to daemon · messaging · discovery names in `src/` ② an allowlist pinning the core references in `src/` to the two symbols above ③ pinning this crate's workspace dependencies to protocol · core in the **resolved dependency graph** (based on `cargo tree` — it looks at package identity, not manifest text, so it withstands table forms, indentation, and rename workarounds). *★Known gap (found jointly by the two reviewers — not closed in this slice)★:* **there is no gate that bounds the use of `protocol` symbols.** So even if agent vocabulary grows along the permitted protocol edge, no gate fires. Once 0-4 moves the auth types, the only legitimate use left on that edge is `DaemonInfo`, so adding one more allowlist gate is the natural follow-up, but adding a gate is a scope expansion, so it is deferred to a separate decision — this note is the record of that reasoning. In addition, two places in the code (`net/Cargo.toml` · `net/src/lib.rs`) attribute "isolation is at the type level, not the crate level" to this ADR, and this note makes that attribution legitimate. The target shape and invariants are unchanged, so this is not a discard (supersede) — it is an addendum to the description of the gate implementation.
   > **note (2026-08-05 · 0-4 done + feature boundary measured · user approved):** Two sentences of the note directly above became false with 0-4 (commit `818cc0c`) — the original is not edited; they are corrected here. ① *"The three actual gates"* — 0-4 added **gate 4** (`rg "(A)gentCommand|(P)ROTOCOL_VERSION" crates/engram-dashboard-net/src/` → **0 lines**). The count is not swapped for a new number (a new number goes stale at the same speed — step-log S18.22) — **the source of truth for the gate list is the header of `crates/engram-dashboard-net/src/lib.rs`**, and the "three" in the note above is to be read only as a pointer to it. ② *"Even if agent vocabulary grows along the permitted protocol edge, no gate fires"* — now **only partly true**. Gate 4 fires on **those two names** `AgentCommand` and `PROTOCOL_VERSION` (down to substrings — intentional, the reason is in the lib.rs header). **There is still no general allowlist** bounding the other `protocol::` symbols, and the deferral recorded in the note above stays alive in full for all of the rest. ★Do not blur the boundary★ — growing gate 4 into a general allowlist is a separate decision (outside the scope of 0-4). ③ **The tension is not hidden:** the note above wrote "adding a gate is a scope expansion, so it is deferred to a separate decision", yet 0-4 set one narrow one. The range that gate bites is **only the two names 0-4 removed** — it is the regression guard of this work item itself, not the deferred general allowlist. Also, the known gap that the `lib.rs` header points to as `ADR-0129 Note A` is the ★known gap★ section of the note above (the label itself is not in this ADR).
   >
   > **0-4 done — the "does not know agent vocabulary even as a type" of decision 1 now holds.** The shape of the handshake frame is owned by `crates/engram-dashboard-net/src/auth.rs`, and the expected protocol version is not imported — `ws::handle_connection` has it **injected by value**. **The wire bytes did not move** — the old type and the new type were linked into one binary and their serialization output was compared (difference 0), the actual bytes of the JSON the frontend assembles by hand are identical, and passing authentication against a real daemon was measured (details = commit `818cc0c`). ★It does not conflict with the 2026-08-05 note in §근거★: what disappeared is the vocabulary edge of `ws.rs`, and the `net → protocol` edge of `portfile` ↔ `DaemonInfo` is **permanent**, as that note wrote.
   >
   > **The `auth` module went behind a Cargo feature boundary (user decision 2026-08-05).** `engram-dashboard-net` gets a `server` feature (default OFF, `default = []`), which puts the server upkeep and the async runtime behind it, and `auth` is not gated — the source of truth for what went behind it is the `[features]` comment in `crates/engram-dashboard-net/Cargo.toml` (do not count it again here). `discovery` and `src-tauri` declare the dependency as before with no flag (the default is empty, so they get only `auth`), and **`daemon`** opts in explicitly with `features = ["server"]`. *Why the default was emptied:* if `server` is ON by default, the commonly used dependency-declaration form (`{ path = … }`) quietly drags in the async runtime and every consumer has to remember to opt out — and that is exactly how the defect now being fixed came about. With an empty default, a consumer that needs the server row and forgets it gets a compile error — a loud failure instead of a silent regression. *Why it was needed:* with the auth types coming to `net`, `discovery` came to **depend on the WS server crate**, and the async runtime was pulled into its resolved tree, so `discovery`'s stated design property "it is synchronous, so it does not bring in an async runtime" quietly became false. *Measured:* the normal closure of `cargo tree -p engram-dashboard-discovery -e normal --prefix none --target all` goes from **122 → 110**, and filtering the same command with `rg -i "^(tokio|mio|tokio-tungstenite|futures-util) "` gives **0 lines** (the source of truth for the gate command = the comment in `crates/engram-dashboard-discovery/Cargo.toml`. Non-vacuity check = adding `--features engram-dashboard-net/server` brings those four back unchanged). ★Do not read the benefit beyond its range★: Cargo's feature union is **per invocation**, so a whole-workspace build still builds with that combination because the daemon turns `server` on — what is gained is that building/consuming `discovery` **alone** gets lighter and the property above stays true. `src-tauri` was also switched off, but **its tree does not shrink** (it already declares the async runtime for itself) — it is a statement of intent, not a measured gain. *Relation to the recorded alternative (an observation, not a reversal):* one of the costs of the **small dedicated handshake crate** that step-log S18.20 rejected was a permanent extra workspace member, and the feature boundary reaches a similar separation without that cost — the rejection decision itself stands. *Gate 3 is unaffected:* it reads with `--all-features`, so edges that became optional still show up and the expected value stays **exactly 3 lines** (re-measured). The target shape and invariants are unchanged, so this is not a discard (supersede) — it is a correction of fact + a record of the boundary.
- **No change to the frontend and wire contract is the premise.** Moving the auth types is free **only on the condition that the wire JSON shape is preserved**. The moment a change becomes necessary, stop and reopen the question — once the frontend is touched, this decision's cost calculation changes.
- **★This is not a revival of the embedded mode that ADR-0029 removed★** — what was removed is the *product form* (hosting agents inside the app process), not *crate reuse*. After this decision the product **still runs as a single daemon process**. A later session must not misread this as "in-proc hosting is back".
- **Open — splitting the implementation into slices (user approval before starting).** About 8,000 lines move across a crate boundary, so it will not finish in one slice. Before starting, re-measure the size and bring the split plan to the user. This ADR only fixes the **target shape** and does not set the implementation order.
