# ADR-0129: Daemon lib split into 3 layers — network lib · agent system lib · thin assembly binary

- 상태: 확정 (2026-08-04, basis: user's problem statement + measurement of all production code + the history of ADR-0020 boundary erosion) · 부분 폐기 by ADR-0130 (decisions 2 and 3 on hold) · 부분 폐기 by ADR-0310 (decision 1: where the network lib lives and who owns the auth frame)
- 관련: ADR-0020(Stage 1 — `ConnectionCore` carrier-neutral extraction. This decision promotes that intent to a crate boundary) · ADR-0110(messaging kernel crate split — same idiom: a compiler-enforced wall) · ADR-0029(agent host = the daemon process — **not a revival**, see the Impact section below) · ADR-0028(event bus single-push) · ADR-0127(preceding slice — tearing down the attach machinery removed 592 lines from the split target) · `crates/engram-dashboard-daemon/src/ws.rs` · `connection_core.rs` · `control/` · `messaging_host.rs` · step-log S18.16 · Amended by ADR-0130 (decisions 2 and 3 on hold) · Amended by ADR-0310 (decision 1: where the network lib lives and who owns the auth frame)

## 맥락

User's problem statement (2026-08-03): *"The daemon should be a relay that only carries the protocol and gets reused in other systems, but at some point daemon = the whole backend."*

Measurement confirmed this. Breakdown of the **11,729 lines** of the production build (the 7,142 lines of experiments and harness are already behind the `test-harness` feature gate, so they are excluded):

| Process lifecycle management | Assembly | WS server | `ConnectionCore` | Control plane | Messaging junction |
|---:|---:|---:|---:|---:|---:|
| 368 | 1,011 | 2,287 | 2,509 | 4,800 | 754 |

**Network lifecycle management is only a part, and everything else is agent vocabulary.** So another system that "needs only the network" would have to drag in the control plane and messaging wholesale to reuse this crate.

## 결정

1. **Daemon lib = network only.** Socket accept · Origin allowlist · auth handshake · connection lifetime · single writer per connection · shutdown signal · connection registry (fan-out) · portfile · single instance. There is **only one** hole through to the layer above — it takes an **opaque frame** and passes it up, and sends one out over this connection. **It does not know agent vocabulary even as types.**
   > **note (2026-08-04 · slice 0-1 measurement · user approved):** The opaque-frame hole has **two shapes** — **per connection** (`frame_port::FrameSink`) and **fan-out to all connections** (the `ConnRegistry::broadcast_text` path). The "only one" above means *vocabulary isolation ends in one kind of thing (the opaque frame)*, and **does not mean there is one surface** — the original text says "sends one out over this connection", written per connection, so fan-out to all connections does not fit that sentence. The decision holds only if fan-out is also a port (porting only the per-connection path leaves it unmet). The target shape and invariants of the decision are unchanged, so this is not a supersede — it is an addendum to the wording. The fan-out port is wired in **decision 3 (thin assembly)**, because the status-notification and messaging flush sinks are injected at `AgentManager` assembly time and share the registry.
2. **Agent system lib.** `ConnectionCore` (protocol decode and dispatch) · `AgentManager` hosting · control plane (MCP · ingress · priming) · messaging junction.
3. **The executable binary = thin assembly.** It only wires the two together.

## 거부한 대안

- **Status quo (daemon = the whole backend)** — the user's problem statement is itself the reason for rejection. Reuse is impossible, and a consumer that needs only the network layer carries all agent vocabulary as a dependency.
- **Do not split the crate; keep the boundary through module discipline and review** — **history has already refuted this.** ADR-0020 Stage 1 chose exactly that approach and pulled `ConnectionCore` out of `ws.rs` as a carrier-neutral module, and its file header **still** declares "does not know TcpStream/tungstenite/codec". Yet in the meantime the control plane and the messaging junction flowed into the same crate. In this codebase, where a different coder session takes each task, **a boundary kept only by documents and review does not survive a change of session** — ADR-0110 reached the same conclusion with the messaging kernel, and we use the same remedy as then (a **compiler-enforced wall**).
- **Two layers (daemon lib + everything else)** — one of the libs would take on the assembly responsibility, and that lib would again become "the place that knows everything". That only moves today's problem under a new name. **A separate thin assembly binary is needed** for the two libs to stay unaware of each other.

## 근거

- **The boundary intent is already in the code.** The `ConnectionCore` of ADR-0020 Stage 1 is designed to be carrier-neutral, and that declaration is alive in the file header. This decision does not invent a new design; it **promotes an existing boundary to a crate** — so the design risk is low.
- **Auth is not an obstacle.** Right now it is only caught in the agent command list as `AgentCommand::Auth`, and it can be moved to a daemon-owned handshake type. **If only the wire JSON shape is kept, the frontend is unchanged** (the frontend does not know which crate a type lives in). So "the daemon lib does not depend on the protocol crate" holds practically for free.
   > **note (2026-08-05 · slice 1 measurement · user approved):** The last sentence of this item — *So "the daemon lib does not depend on the protocol crate" holds practically for free.* — is **false now** (the original text is not edited; it is corrected here). The network lib's (`engram-dashboard-net`) dependency on `protocol` is **permanent**: `crates/engram-dashboard-net/src/portfile.rs` re-exports from protocol the shared struct `DaemonInfo` of daemon.json, and that struct is a two-process contract (the daemon writes it, the client reads it), so it cannot be moved into either crate. **Keep this apart from the carry-over to 0-4** — the `AgentCommand::Auth`/`PROTOCOL_VERSION` edge of `ws.rs` disappears once 0-4 (moving the auth types) is done, but the `portfile`↔`DaemonInfo` edge remains after that. So "no protocol dependency" was not a side benefit of this decision. The target shape and invariants are unchanged, so this is not a supersede — it is a factual correction.
- **A preceding slice already shrank the target.** The tearing down of the turn-observation attach machinery by ADR-0127 cut `ws.rs` by 592 lines — we start only after the split target has become that much smaller.

## 영향 / 불변식

- **Invariant:** **If an agent-vocabulary type appears in the daemon lib, this decision is violated.** The isolation gate is set up in the same form as for the messaging kernel (ADR-0110) — forbidden-import grep gives 0 lines. The compiler catches it first, and the grep catches the paths that leak through comments and test-helper names.
   > **note (2026-08-05 · slice 1 measurement · user approved):** The "forbidden-import grep gives 0 lines" above differs from the gate actually set up — slice 1 set up **multiple gates**, and one of them is an **allowlist** whose expected value is not 0. *Why:* the invariant of this decision is at the **type level** (agent *vocabulary*), not the crate level. `portfile` legitimately needs `protocol::DaemonInfo` and two process-liveness helpers of core (`agent::platform::pid_alive_with_start_time` · `current_process_start_time`), and none of the three is agent vocabulary — for the same reason the `discovery` crate already depends on `core` (precedent). So the core edge is bound not by a ban but by a **symbol allowlist**. *The actual three gates (canonical = the `crates/engram-dashboard-net/src/lib.rs` header):* ① 0 lines of daemon · messaging · discovery name references in `src/` ② an allowlist pinning the core references in `src/` to the two symbols above ③ pinning this crate's workspace dependencies to protocol and core in the **resolved dependency graph** (`cargo tree`-based — it looks at package identity, not manifest text, so it withstands table form, indentation and rename workarounds). *★Known gap (surfaced jointly by the two reviewers — not closed in this slice)★:* **there is no gate bounding `protocol` symbol usage.** So even if agent vocabulary grows along the permitted protocol edge, no gate fires. Once 0-4 has moved the auth types, the only legitimate use left on that edge is `DaemonInfo`, so adding one more allowlist gate is the natural follow-up, but adding a gate expands the scope and is deferred to a separate decision — this note is the record of that reason. In addition, two places in the code (`net/Cargo.toml` · `net/src/lib.rs`) attribute "isolation is at the type level, not the crate level" to this ADR, and this note makes that attribution legitimate. The target shape and invariants are unchanged, so this is not a supersede — it is an addendum to the description of the gate implementation.
   > **note (2026-08-05 · 0-4 complete + feature boundary measured · user approved):** Two sentences of the note directly above became false with 0-4 (commit `818cc0c`) — the original text is not edited; it is corrected here. ① *"The actual three gates"* — 0-4 added **gate 4** (`rg "(A)gentCommand|(P)ROTOCOL_VERSION" crates/engram-dashboard-net/src/` → **0 lines**). We do not swap the count for a new number (a new number rots again at the same speed — step-log S18.22) — **the canonical list of gates is the `crates/engram-dashboard-net/src/lib.rs` header**, and the "three" in the note above is to be read only as a pointer to it. ② *"even if agent vocabulary grows along the permitted protocol edge, no gate fires"* — this is now **only partly true**. Gate 4 fires on **those two names**, `AgentCommand` and `PROTOCOL_VERSION` (down to substrings — intended; the reason is in the lib.rs header). There is **still no general allowlist** bounding the other `protocol::` symbols, and the deferral recorded in the note above stays alive for all of the rest. ★Do not blur the boundary★ — growing gate 4 into a general allowlist is a separate decision (outside the scope of 0-4). ③ **We do not hide the tension:** the note above wrote "adding a gate expands the scope and is deferred to a separate decision", yet 0-4 set up one narrow gate. The range that gate bites is **only the two names 0-4 removed** — it is this work item's own regression guard, not the deferred general allowlist. In addition, the known gap that the `lib.rs` header points to as `ADR-0129 Note A` = the ★known gap★ section of the note above (the label itself is not in this ADR).
   >
   > **0-4 complete — decision 1's "does not know agent vocabulary even as types" now holds.** The shape of the handshake frame is owned by `crates/engram-dashboard-net/src/auth.rs`, and the expected protocol version is **injected by value** into `ws::handle_connection`, not imported. **The wire bytes did not move** — we linked the old type and the new type into one binary and compared the serialized output (diff 0), and measured that the actual bytes of the JSON the frontend assembles by hand are identical and pass auth against a real daemon (details = commit `818cc0c`). ★Does not conflict with the 2026-08-05 note in §근거★: what disappeared is the vocabulary edge of `ws.rs`, and the `net → protocol` edge between `portfile` ↔ `DaemonInfo` is **permanent**, as that note wrote.
   >
   > **The `auth` module moved behind a Cargo feature boundary (user decision 2026-08-05).** `engram-dashboard-net` gets a `server` feature (default OFF, `default = []`), and the server lifecycle management and the async runtime are put behind it, while `auth` is not gated — the canonical record of what went behind it is the `[features]` comment of `crates/engram-dashboard-net/Cargo.toml` (do not recount it here). `discovery` and `src-tauri` declare the dependency as-is without a flag (the default is empty, so only `auth` is received), and **`daemon`** opts in explicitly with `features = ["server"]`. *Why the default was emptied:* if `server` were ON by default, the commonly used dependency declaration form (`{ path = … }`) would silently pull in the async runtime and every consumer would have to remember to opt out — and that is exactly how the defect we are fixing now arose. With an empty default, a consumer that needs the server layer and forgets shows up as a compile error — a loud failure instead of a silent regression. *Why it was needed:* when the auth types came to `net`, `discovery` came to **depend on the WS server crate**, and the async runtime was dragged into its resolved tree, so `discovery`'s stated design property "it is synchronous, so it brings in no async runtime" silently became false. *Measured:* the normal closure of `cargo tree -p engram-dashboard-discovery -e normal --prefix none --target all` went **122 → 110**, and filtering the same command with `rg -i "^(tokio|mio|tokio-tungstenite|futures-util) "` gives **0 lines** (the canonical gate command = the `crates/engram-dashboard-discovery/Cargo.toml` comment. Non-vacuity check = adding `--features engram-dashboard-net/server` brings those four back unchanged). ★Do not read the benefit beyond its scope★: Cargo's feature union is **per invocation**, so a whole-workspace build is still built with that combination because the daemon turns `server` on — what we get is that building/consuming `discovery` **alone** gets lighter, and that the design property above stays true. `src-tauri` was also turned off at the same time, but **its tree does not shrink** (it already declares the async runtime as its own) — it is a statement of intent, not a measured benefit. *Relation to the recorded alternative (an observation, not a reversal):* one cost of the **small dedicated handshake crate** that step-log S18.20 rejected was a permanent new workspace member, and the feature boundary reaches a similar separation without that cost — the rejection decision itself stands. *Gate 3 is unaffected:* it is read with `--all-features`, so the edge that turned optional shows up as is, and the expected value stays **exactly 3 lines** (re-measured). The target shape and invariants are unchanged, so this is not a supersede — it is a factual correction + a record of the boundary.
- **The premise is that the frontend and wire contract do not change.** Moving the auth types is free **only on the condition that the wire JSON shape is preserved**. The moment a change becomes necessary, stop and reopen the discussion — the moment the frontend is touched, the cost calculation of this decision changes.
- **★This is not a revival of the embedded mode that ADR-0029 removed★** — what was removed is the *product form* (hosting agents inside the app process), not *crate reuse*. After this decision the product **still runs as a single daemon process**. A later session must not misread this as "in-proc hosting is back".
- **Open — splitting into implementation slices (user approval before starting).** About 8,000 lines move across the crate boundary, so it does not finish in one slice. Before starting, re-measure the size and bring the split plan to the user. This ADR fixes only the **target shape** and does not decide the implementation order.
