## 맥락

- **Stage 3 = remove net and attach the shell and daemon to transport.** It is work order 3 of the boundary refactoring (memo §10 「3. transport」) and its steps are 3-1 protocol cleanup → 3-2 shell attach → 3-3 daemon attach + net deletion. transport stands as an independent crate and has finished standalone verification, but it has zero consumers (ADR-0177 decision 1). The same work (handshake · keepalive · reconnection · pairing) exists in three copies: the shell's hand-written WS client (`daemon_client/connection.rs` · the synchronous stop client `stop.rs`) and the daemon's net server layer (`net/src/ws.rs`). net mixes the daemon-only server layer · an auth frame the shell also uses · daemon lifecycle management (single instance · daemon.json), and protocol embeds command's structs (ADR-0272 decided to remove this and put off the start to this stage).
- **The behavior shipped now is one shell + one local daemon (1:1), and multi-daemon is the very next stage.** The user instruction (2026-10-12) was to build a structure where one shell attaches to several daemons and daemons talk to each other, but to leave remote application · testing for a later track, and to split security by layer: encryption · peer authentication to be borrowed later from the Link layer, and authorization · pairing · Origin · resource caps to be our share (TRD head 「결정 출처」).
- **Before attaching, we found five defects in transport** (TRD §3-0 — static reading). None can be patched in an adapter — loss and ordering are already decided inside the crate.
  1. Loss on the receiving queue — the supervisor does `try_send` of messages and events onto one shared queue and only counts when it is full (`peer.rs:1224-1256`).
  2. Lifecycle events ride the same lossy queue.
  3. A stale command in the reconnect window — `ReconnectNow` empties only the queue of that moment and dials, so a command that came in during that window is used in the next generation (`machine.rs:281-292` — violates ADR-0195).
  4. There is no flush before close — `Peer::close` goes by the control channel and is heard first, and cleanup refuses the queue, so the stop Ack · Error put in earlier disappear (`peer.rs:282` · `:1177`).
  5. A handshake refusal is always `GaveUp` (`machine.rs:361-368`) — it cannot tell a refusal worth retrying from a final one.
- The TRD went through five editions (four review rounds · every reviewer FIX each time) and raised the user decision list D1~D26 in a form where the recommended option comes first (TRD §8-3). On 2026-10-31 we absorbed master and cross-checked again, and no decision's options or recommendation changed (only one line was added to the cost of D18 ① — decision 24).

### Stages

1. **D19 ① — Put all the transport reinforcement into a new stage 3-0.** Per-peer lossless inbox · lifecycle events · generation stamp · sent field · flush before close · refusal classification · Debug masking · receiving-side seam · ws accept hardening are all fixed in one go now, while there are zero consumers. 3-0 runs in parallel with 3-1. (user)

### Structure

2. **D1 ① — The receiving-side seam = a `Listener` trait + `Registry::attach`.** The `Registry::new` signature stays as is. An accepted peer starts in Handshaking, and at every end that is not Live (refusal · handshake deadline · link loss · loss after Live) it emits `Closed{generation, cause}` and removes itself from the registry — it does not dial again and does not enter the generation table. The accept loop · caps · rate policy are the consumer's (daemon's) share. (recommended option adopted — user delegation)
3. **D2 ① — Each relationship gets its own Wire · Registry · Listener.** Shell↔daemon = `ShellWire` / `DaemonWire` with today's vocabulary. The day the vocabulary of another relationship (daemon↔daemon) comes in, that relationship gets its own Wire · Registry · Listener — we do not build it this time (decision 6). (recommended option adopted — user delegation)
4. **D3 ① — A persistent daemon identity `DaemonId` + an appended field on `Hello`.** Create a UUID v4 once in the daemon state folder (the location is owned by the daemon's `DataLayout`) and announce it with `Hello{.., daemon_id: Option<String>}` (`#[serde(default)]` · `PROTOCOL_VERSION` unchanged · one field in the TS bindings). If the file is corrupted or deleted and a new identity is created, leave a loud warning log. `PeerId` stays as a name tag and the identity is bound to a key later (identity ≠ key). ★`DaemonId` is a claimed, unverified id, so we do not build persistent trust (an allowlist and so on) keyed on it — until it is bound to a key by pairing★. The shell handshake's comparison against the expected id rejects only when both exist and differ, and the local expectation is `None` throughout stage 3 (it is exercised only in in-memory tests). (recommended option adopted — user delegation)
5. **D4 ① — Build shell multi-daemon for real down to the adapter depth.** The shell adapter holds N peers in a single `Registry`, and the upper layers (`router` · `layout` · commands) see only the one main daemon `primary()`. Each daemon has its own queue and reconnection, the event/output routing state is keyed by `(DaemonKey, AgentId)`, and events and output of an `AgentId` that is not in the list of the sending daemon are dropped. A `CommandRequest` from a daemon that is not the main one is not applied and a refusal reply is sent. A test with two fake daemons measures this (3-2 U6). (user delegation — main-session judgment)
   - Reason: the multi-daemon stage follows right away. This depth — keeping N connections apart without mixing them (per-daemon queue · reconnection · `DaemonId` · events keyed by `(데몬, 에이전트)` · only the main daemon gets screen and commands · a two-fake-daemon test) — is needed however the next PRD answers registration · screen · remote · orchestration, so the risk of getting the shape wrong is low.
6. **D5 ③ — Daemon↔daemon is not built this time and is handed over to the multi-daemon stage.** Take the `PeerWire` skeleton · the protocol `peer` vocabulary (`PeerAuth` · `Identify` · `Ping`) · the daemon `link/peer.rs` · the second Listener out of 3-3 U7. The seams that remain = per-relationship Wire · Registry (decision 3) · `DaemonId` (decision 4) · transport's registry of N peers (ADR-0179 decision 3). (user delegation — main-session judgment · changed from TRD recommendation ①)
   - Reason: the shape of daemon↔daemon orchestration is decided by the upcoming multi-daemon PRD. If we build the `PeerWire` skeleton before that, the shape risks being wrong. transport already handles N peers, so even if daemon↔daemon is attached later, there is nothing to fix in transport again.
   - ★Fact record★: the user instruction of 2026-10-12 (TRD head 「결정 출처」 ①) was 「데몬끼리 서로 말하는 구조를 지금 3단계에서 세운다」. That conflict was raised to the user and the user confirmed ③ (2026-10-31 — 1:1 first · multi-daemon right after).

### Security

7. **D26 ② + D22 ② — Other OS users on the same PC are outside the stage-3 threat model.** 3-3 U2 only measures the data-folder ACL with `icacls` and records it. The data-folder owner · no ACL check · no owner check on the shell's reading of daemon.json (TRD §5 28) · the local DoS of filling the accept permits (R11 — while there is no 「다시 연결」 button, it freezes as `GaveUp`) are written as known limits in `docs/tracking.md` and in the user docs (「다른 사용자가 쓸 수 있는 폴더에 풀지 말 것」). ADR-0135's way of opening stays as is. Decision 14 (D23) and decision 15 (D25) go in regardless of this decision. (user)
   - User's reason: the next stage, multi-daemon (attaching to a daemon on another PC), has to redo the security design anyway — TLS · remote auth · device identity · permissions · where tokens live. The file-permission problem of another user on the same PC belongs to that redesign, and doing it now would fix the same place twice.
   - TRD's reason: this hole exists equally in net · daemon.json now and stage 3 does not widen it · the work of closing it (a platform security module + the discovery · start places) is independent of the connection machinery, so the cost is the same if built separately · the main path of port hijacking is closed by decision 15 regardless of the threat model.
8. **D6 ②′ — For authorization, only 「누구냐」 now: `admit` + keeping `Principal`.** `admit(attempt, &LinkInfo) -> Result<Principal, Refusal>` writes `Principal` (now `LocalClient` · later `PeerDaemon` · `Paired`) synchronously into the handshake value of attach, and the adapter moves it to a table next to ConnId at Live — if absent, refuse · close. We do not build a per-command `allow` but fix by name the places where policy will plug in: four command entrances (ⓐ `connection_core` dispatch ⓑ `call_daemon_command` (ADR-0157 checkpoint) ⓒ `/control/send` ⓓ `/control/messages`) + MCP tools (`/mcp`) + two read-only ones (`/control/commands` · `/control/help`). (recommended option adopted — user delegation)
9. **D7 ① — The auth decision is one module inside the daemon (`link/auth.rs` — decision trait + token · constant-time comparison · version), and the auth frame `AuthFrame` goes to protocol.** As in the end state of stage 3 (TRD §0 ①), the rest of net is also split up and the net crate is deleted — connection machinery = transport · daemon-only server layer (read task · per-connection lane · dispatch · bypass · fan-out) = daemon `link/server.rs` · single instance · daemon.json = daemon. The 「네트워크 lib」 of ADR-0129 decision 1 is scattered this way, and that decision's 「에이전트 어휘를 타입으로도 모른다」 is carried on by the edge-vocabulary gates ① ② of the daemon `link/` module. (recommended option adopted — user delegation)
10. **D8 ① — The Origin · Host check lives in the transport ws accept configuration.** `AcceptPolicy` is required and has no `Default` · the unchecked `WsListener::accept` is removed · a permissive policy has a name that states the risk (tentative `AcceptPolicy::permissive_unsafe()` · behind `test-support`) · `transport::ws::split_link` is lowered to `pub(crate)` · the values are given by the daemon. (recommended option adopted — user delegation)
11. **D9 ① — Put the new defenses in now:** upgrade deadline (from TCP accept · tentative 1 s — after that the auth deadline of 1 s is measured continuing from the end of the upgrade) · accept separation · three connection-count caps (waiting for upgrade · waiting for auth · total — an RAII guard tied to the peer's lifetime · when exceeded, the new one is closed) · two-way message cap of 16 MiB · Host check (DNS rebinding) · loopback assertion on the `ws://` Listener · accept policy required · refusal report (`AcceptRefusal` · per-branch time-window batched log · no token). Auth-failure rate limiting · TLS are deferred. (recommended option adopted — user delegation)
12. **D20 ① — Split auth failure in two.** Token mismatch = `Retryable` (uses the reconnect budget and resolves the connection info again — current shell behavior) · version mismatch = `Terminal` (does not use the budget · immediate popup). The kind is carried by the **close code** — 4001 = `Terminal` · a new entry (tentative 4006) = `Retryable` · an unknown refusal code = `Retryable` · a bare close = 「못 붙음」. The popup text is a fixed local wording per close code, and the text given by the peer goes only to details and logs. Because a local version mismatch is filtered by the daemon.json check before dialing, it becomes the same `Terminal` by way of `VersionMismatch` in the connection info → the Dialer refusal kind (tentative `DialFailure::Refused`) → `GaveUp(Rejected)` (the mechanism is main-session judgment). So the 「붙었다가 거절 = 예산 안 쓰고 첫 거절에서 즉시 팝업」 of ADR-0180 decision 5 narrows to version mismatch. The peer's wording is not trusted (`DecodeFailed.reason` = classification string · length cap on `Rejected.reason` · control characters removed). (recommended option adopted — user delegation)
13. **D21 ① — The release build rejects every upgrade that carries an Origin, and only the dev build uses an allowlist.** The production client does not send an Origin (likely · not measured — the `/qa full` of 3-3 U5 measures by log whether the received upgrade has an Origin). (recommended option adopted — user delegation)
14. **D23 ① — Remove the token from `DaemonInfoDto`** (3-2 U4 · all three of `discover_daemon` · `daemon_start` · `read_daemon_info` that return that DTO). What it blocks = the token going out to, or remaining in, the outside of the WebView (another process · a direct socket) · what it cannot block = control originating from the WebView (`forward_daemon_command` · `csp: null`). The non-production direct path `wsTransport.ts` can no longer do Auth (including the disposition of its test). (recommended option adopted — user delegation)
15. **D25 ① — Narrow the old-address fallback to sharing violations.** Only when someone else briefly holds daemon.json with sharing blocked (platform `fs::is_sharing_violation`) does it connect to the last known address. Missing · empty · corrupt · dead pid · access denied · other I/O error = one failure (budget) · no dial · re-read on the next attempt. Different version = `Terminal` (decision 12). So `current()` of the connection-info interface returns a branch, not an `Option` (tentative `Live · Busy · Absent · Unusable · VersionMismatch`). (recommended option adopted — user delegation)

### Streams · queues

16. **D10 ① — The two consumers do not use transport's stream layer.** The `stream_mark` of `ShellWire` · `DaemonWire` = `None` and `resume_stream` is not called. replay→live · gen fence · incarnation marker · seq continuity are carried, as now, by the daemon, the shell `replay_flight` and the frontend. The stream lifecycle management of ADR-0177 decision 3 and the loss signal / gap re-request of decision 9 stay in the crate but are left idle in the shell↔daemon relationship. (recommended option adopted — user delegation)
17. **D11 ②′ + D24 ② — The receiving queue = a per-peer lossless inbox + backpressure, and saturation handling is not put into transport.** This extends the 「유계 큐와 배압 신호」 of ADR-0177 decision 3 to the receiving side and removes the shared-queue loss. (user)
    - transport: returns a lossless inbox per peer (no hook). When it is full, only that peer's socket reads stop (TCP backpressure). The byte budget is a single count — `read_link` adds when it puts into the read-ahead queue and the consumer subtracts when it takes from the inbox · the decision on the 「더하기 전 물높이」 (fill level before adding) · per-connection transport-layer cap = B + M (tentative B = 16 MiB · M = one-message cap of 16 MiB) · the count cap remains for small-frame floods (tentative shell 512 · daemon accepted peer 16). Events and messages ride on one queue per peer in arrival order (the supervisor's per-peer order field). The end cause separates read end from write end (tentative `ReadFailed` · `WriteFailed`).
    - Daemon: `link/server.rs` moves net's `read_task` over as is for each connection and reads that peer's inbox instead of the socket — the per-connection lane · byte budget · saturation handling · `dispatch_task` · `bypass_task` · `finish_bypass_lane` are moved as code, constants included (priority lane full = keep waiting · ADR-0206 handling unchanged). Connection lifetime is split by end cause — read end = drain what remains (abort after a new cap, tentative 30 s) · write end = abort (net as is) · when the daemon ends first (`ConnFlow::Close` · `Unanswered` of `StopDaemon`) = the adapter does `close_after_flush(code)`.
    - Shell (D24 ②): one inbox-consumer task per daemon, which only hands over through a Channel. If a merged view is needed, the shell adapter merges with select (transport surface unchanged). Lifecycle events are applied only for that key's current handle · the main daemon's, and `replay_flight` is kept per `DaemonKey`.
18. **D12 ① — Put a 「보냈나」 (was it sent?) field in the disconnect error** (`RequestError::Disconnected{sent}` · 3-0 U2). The shell keeps the two texts it now distinguishes (result unknown · not sent). The same unit also puts in the generation stamp (the generation the caller captured — `notify_in` · `request_in` · decision 1). (recommended option adopted — user delegation)
19. **D13 ① — Fan-out saturation = drop that connection** (turn silent loss into a drop + full replay). It is the same choice as ADR-0177 decision 6. (recommended option adopted — user delegation)

### Policy values

20. **D14 ① — Inject 5 as the reconnect count in 3-2, and lower it to 3 the day the 「다시 연결」 button lands.** The 「기본 = 3회」 of ADR-0180 decision 4 is the value for when that button exists (decision 7 of the same ADR holds up the 3). With decision 12, a token refusal also uses this budget. (recommended option adopted — user delegation)
21. **D15 ① — Inject 30 s as the shared request deadline, and after measuring and recording the real spawn time in the 3-2 QA, decide the 8 s again separately.** Remove the `REPLY_TIMEOUT` (30 s) of `forward_daemon_command`, and the remaining handlers gain a cap they did not have. The 「명령 무관 공용 하나」 of ADR-0181 decision 1 stays as is and only the default of 8 s is put off. (recommended option adopted — user delegation)
22. **D16 ① — The outgoing queue of a peer the daemon accepted stays at 4608 (ring 4096 + 512)** — it is injected, overriding transport's default of 512. This decision fixes the 「큐 상한이 되감기 링보다 크면 안 되는 이유」 paragraph of the ADR-0177 rationale (rejected alternatives, decision 22). (recommended option adopted — user delegation)

### protocol (3-1)

23. **D17 ① — `OwnerToken` is a protocol copy** (newtype · serialized as the inner string as is = the same bytes). The shell and daemon edges convert it to and from the command type. It closes the open item that the ADR-0272 impact left in this TRD. (recommended option adopted — user delegation)

## 거부한 대안

The code locations are from reading the TRD 5th edition's base commit `7637db89` (lines that shifted after the master absorption are fixed by section B of the recheck). ★rejection basis weak★ = a rejection that is only prose, with no number · measurement · code ground.

- **Decision 1 (D19)**
  - ② 3-0 = only what the shell uses · receiving-side seam and accept hardening in 3-3 U3 — opens the 「지금 확정」 (fixed now) surface twice. By the time it opens the second time, the shell is already using that surface (now, with zero consumers, is the last cheap time to fix it — TRD R9).
  - ③ As in the 1st edition, inside each stage — 3-2 starts on top of the lossy shared queue. The 1st-edition remedy (`Dropped` → `reconnect_now`) creates a shell replay loop (`ReconnectNow` rewinds the budget to 0 — `machine.rs:272-292`) · starvation among daemons (what `registry.rs:6-9` tried to prevent) · unanswered loss on the daemon side (net `frame_port.rs:195-199`) · reporting delay (TRD §3-0 ①).
- **Decision 2 (D1)**
  - ② `Registry::new(.., listeners)` goes as far as accepting — the signature changes and the caps · rate would have to come in as crate policy values (policy is the consumer's share — ADR-0177 decision 4).
  - ③ The daemon runs a Link directly outside the registry — violates ADR-0179 decision 3 (same registry · same supervisor).
- **Decision 3 (D2)**
  - ② One union Wire + a `AuthFrame` role field — `decode` has no peer argument (`wire.rs:20-60`), so overlapping packet namespaces cannot be told apart · the shell knows the daemon-to-daemon vocabulary as types.
  - ③ One port + choosing the registry by peeking at the first frame after accept — needs a Link wrapper that puts the frame back so the handshake can read it again. ★rejection basis weak★
- **Decision 4 (D3)**
  - ② Create a key pair now and fingerprint = identity — brings in a cryptographic dependency we do not use now, and key rotation becomes identity rotation. ★rejection basis weak★
  - ③ Name tag only — there is no material for the shell to see the same daemon at two addresses or for daemons to refer to each other (`Hello` = only version · capabilities `messages.rs:433-438` · `PeerId` = an opaque string the consumer attaches `event.rs:19-23`).
- **Decision 5 (D4)**
  - ② Types · seam only — cheap, but the shell-side N stays unverified. The user instruction of 2026-10-12 said to measure multi-daemon with the transport in-memory harness and several daemons on one PC.
  - ③ Down to the screen · LLM — exceeds the scope of stage 3 (shipped behavior = one shell + one local daemon — user instruction 2026-10-12). The shape of the screen · LLM surface is decided by the multi-daemon PRD.
- **Decision 6 (D5)**
  - ① `PeerWire` skeleton + an in-memory two-registry test (TRD recommendation) — if the skeleton is built before the multi-daemon PRD decides the shape of daemon↔daemon orchestration, the shape risks being wrong, and since transport already handles N peers, attaching it later needs no rework of transport (main-session judgment). ★rejection basis weak — 「모양이 틀릴 위험」 is only prose, and the one fact that supports it is 「transport 재작업 없음」 (ADR-0179 decision 3 · registry of N peers)★
  - ② ① + a real second Listener (default off) + two real daemons on the same PC + dial direction · symmetry breaking — to the risk of ① are added a second port · a `daemon.json` entry · real-process tests. ★rejection basis weak (same as ①)★
- **Decision 7 (D26 · D22)**
  - D26 ① in scope — a proposal to put the D22 ① · TRD §5 28 · R11 measures into stage 3 to guard against a portable zip unpacked into a place others can write, such as a drive root · `C:\Tools` (the Windows default `C:\` ACL makes new subfolders inherit Authenticated Users modify — likely · not measured). It was discarded for the user's reason (it belongs to the security redesign of the multi-daemon stage and doing it now fixes the same place twice) and the TRD's reason (the hole is the same in net · daemon.json now and stage 3 does not widen it · the work is independent of the connection machinery, so the cost is the same if built separately). What it would have cost: a platform security module · `Win32_Security_Authorization` · revising ADR-0135's way of opening · touching both the shell and the daemon.
  - D22 ① at startup delete daemon.json and create it with `CREATE_NEW` + an owner-only security descriptor · owner of the opened handle · reparse point · link-count check — an option that applies only when D26 is ①.
  - D22 ③ As in the 1st edition, at remote time (measurement also deferred) — the TRD wrote no separate reason for rejection. The chosen ② measures now whether it is 「로컬 구멍일 수 있다」 (TRD §5 21 — not measured) and uses that as the basis of the known-limits record. ★rejection basis weak★
- **Decision 8 (D6)**
  - ① `Principal` + `allow` in the four entrances now — the signatures of the ADR-0157 entrance and its call sites and of the two mail routes would change now for a single decision that always allows. The 「dispatch 입구 한 곳」 that the 1st-edition ① relied on is not in the code (there are four entrances — `control/commands.rs:3-7` · `control/mcp_server.rs:55` · `:62`). Fixing only the entrance names costs the same later.
  - ③ None — the TRD wrote no separate reason for rejection. The chosen ②′ already has `Principal` next to ConnId, so the day a policy comes in, connection management is not touched (TRD §4) · it closes security review C3 (a new connection has no identity). ★rejection basis weak★
- **Decision 9 (D7)**
  - ② An auth crate — there is only one consumer, the daemon.
  - ③ Inside transport — violates ADR-0177 decision 4 (auth material stays outside).
- **Decision 10 (D8)**
  - ② (2nd edition) The daemon's own accept + a public `split_link` — anyone can make a Link with their own accept and bypass all the accept checks (`ws.rs:237` public · only three places inside the crate use it). Removed from the options in the 3rd edition.

## 영향 / 불변식

- **Five receiving-queue invariants** (3-0 U1 fixes them in the transport lib header — TRD §3-0 ①):
  1. An inbox consumer does not await `request()` — if backpressure stops that peer's reads, replies cannot come in and it deadlocks (requests go in a separately spawned task).
  2. While held by backpressure, that peer's silence decision stops — the blockage is on our side. When room opens up, `last_rx` is set to that moment.
  3. Events and messages ride on one queue per peer in arrival order.
  4. The daemon write deadline versus shell backpressure (R7) and its mirror (the shell also newly gets a write deadline of 5 s) are measured with real-socket tests (3-2 U4) — in-memory cannot imitate a TCP buffer.
  5. Every inbox is drained to the end (`Closed` · `None`) — the end is not judged by the `Peer::state()` watch alone. Conversely, if the consumer drops the inbox, the supervisor closes at once (a `Sender::closed()` branch in every wait loop).
