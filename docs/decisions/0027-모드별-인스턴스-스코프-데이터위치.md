# ADR-0027: Per-mode instance scope + data location — embedded = per folder / folder-local, daemon = global / user-global (discards ADR-0024 data sharing)

- 상태: 폐기 (Superseded by ADR-0029) — the embedded mode itself was removed, so "per-mode instance/data" became meaningless. The original proposal is kept as history. (Originally: 확정 2026-06-21 dashboard9)
- 관련: ADR-0026 (2-process topology) · ADR-0024 (daemon ownership · data — this ADR partly discards the data part) · ADR-0008 (sid control) · CLAUDE.md §5 · `docs/process/step-log.md` dashboard9 · Amends ADR-0024 (data location and sharing)
- Scope: **what unit** single-instance (duplicate launch) is held by, and **where** the runtime data (`.engram-data`) is placed. The two are one decision tied together by "who owns the agents."

## 맥락
ADR-0026 made it 2 processes (the embedded app + a separate daemon). While designing single-instance, it became clear that "instance scope (global vs per folder)" and "data location" are **the same decision** — the data location follows the entity that owns the agents. OSS survey: document/workspace apps (VS Code · JetBrains · Obsidian) = per folder/project; service/daemon (Docker · Tailscale) = global (per user). If the single-instance lock key is a "fixed app name" it is global; if it is a "path hash" it is per folder.

## 결정
**If the mode differs, the scope and data location differ.**

- **embedded (single mode) = per folder + folder-local data.**
  - Instance scope = **per folder**. Rerun in the same folder → block it and raise the existing window (`show()`+`unminimize()`+`set_focus()`). **A different folder → each independent instance is allowed.**
  - single-instance lock key = `{identifier} + hash(작업폴더)` (splits Tauri's default global key per folder).
  - Data = **the `.engram-data/` of the folder it was run in** (that folder owns its own agents).
- **daemon (agent mode) = global (per user) + user-global data.**
  - Instance scope = **one global** (the existing named mutex `Global\EngramDashboardDaemon-<user>`).
  - Data (release) = **the user area `%APPDATA%\com.engram.dashboard`** (like Tauri `app_data_dir`). The daemon is a per-user service like dockerd/tailscaled, so it is not tied to a folder.
- **Tray / X = hide are daemon mode only (UI behavior is also per mode — user decision, option B).** **embedded = an ordinary window app**: no tray, X = normal close/exit (cold restore on reopen). **daemon = tray-resident** (one global), X = hide (minimize to the tray), and agents survive in the daemon even if the window is closed. Rationale: embedded is a foreground session (ends when closed) and per-folder, so a tray would clutter N per folder + the daemon menu would be orphaned. Isomorphic to the VS Code (per-folder windows, no tray) / Docker Desktop (tray-resident) split. → ADR-0026's "X = hide · tray" is **mode-gated to daemon mode** (step 3). The current step-2 implementation (tray and X = hide unconditionally) must be disabled in embedded.
- **The agent store is separated across modes (not shared) — an intended design.** An agent created in embedded (folder-local) is not visible in the daemon (user-global). They are different scopes, so sharing would be more confusing. (User decision: "agents being shared is the strange thing.")
- **dev (debug) = both modes reference the "single (embedded) mode data" (user decision — resolves #4).** In dev the daemon also sees embedded's **folder-local `.engram-data`** (= the current `default_data_dir` debug behavior: walk up from the exe to the repo root). This is so that embedded↔daemon **mode-switching tests** during development use the same local data. **Only in release does the daemon branch to `%APPDATA%`.** (= dev is a single path regardless of mode, so the default_data_dir mode argument diverges only in release.)
- The `ENGRAM_DATA_DIR` override (the test-isolation escape hatch) is kept as is — top priority.

### Priority (direction for the default_data_dir redesign)
```
1. ENGRAM_DATA_DIR (테스트 격리 — 불변)
2. dev(debug):  실행 폴더의 .engram-data  (embedded·daemon 공통 — 스위칭 테스트)
3. release:
     - embedded:  실행(작업) 폴더의 .engram-data
     - daemon:    %APPDATA%\com.engram.dashboard
```
→ `default_data_dir()` **must know the mode (embedded/daemon)** (as an argument or a branch). Today it is a single mode-agnostic function, so the signature must change.

## 거부한 대안
- **embedded and daemon share data (the ADR-0024 original: the same `.engram-data`)** — embedded is tied to a folder while the daemon is global, so tying it to one folder breaks the daemon's globality. Agents leaking visibly across modes is also scope confusion. → Replaced by the per-mode split.
- **embedded also a single global (option 1)** — simple for tray and data safety, but it collides head-on with the user workflow of "bringing up each project (folder) separately." It amounts to abandoning the folder-based run model. Rejected.
- **A mixed daemon hub (option 3) now** — it covers one tray + per-folder in parallel, but the daemon↔client IPC and coordination are heavy. A territory for after the flip. For now keep it simple with embedded per folder + daemon global.

## 영향 / 불변식
- **Of ADR-0024's "data location" decision, "embedded and daemon share it (the same folder)" + "debug = repo root / release = next to the exe, converging (the three exes in the same folder)" are discarded** — replaced by this ADR. **But the rest of ADR-0024 (C1 detached/breakaway, C2 WS/lockfile liveness, C4 exit order, idle self-shutdown, token lockfile-only) remains valid.**
- The single-instance (embedded) lock key includes the **working-folder hash**. The 2nd in the same folder → delegate to the 1st via argv, then raise; a different folder → a new one is allowed.
- **The tray = daemon mode only (option B).** embedded has no tray → even with several folders the tray clutter is 0 (just several windows, VS Code style). The daemon is one global, so the tray is also one. Step 2's unconditional tray and X = hide are mode-gated to daemon mode in step 3.
- `.engram-data` must not be committed to git (keep `.gitignore`). The appdata path only for release-daemon.
- ~~Unresolved: the definition of the dev "run folder"~~ **Resolved (user decision):** in dev both modes reference **single (embedded) mode data = the current debug walk-up `.engram-data` as is** (daemon-dev too). Only release-daemon uses appdata. → The default_data_dir mode branch is needed **only in release**; dev keeps the existing behavior (implementation is simple).

## Supplement (2026-06-21, dashboard10 session — mode decision mechanism fixed, user decision + an industry-practice survey subagent)

Above we only wrote down "`default_data_dir()` must know the mode," and **what the app uses to know its own mode at start time** was undecided. Fixed this time:

- **Mode mechanism = a single exe + the launch argument `--mode={embedded|daemon}` (not separate exes).** With no argument, embedded is the default. Rust reads the argument/env at the very top of `tauri::Builder` (before plugin registration) and fixes the mode — the single-instance lock key, the tray gate, and the data_dir branch all depend on this one decision, and the single-instance plugin must be registered **first**, so the mode must be known earlier than that. Priority: **CLI `--mode` > env `ENGRAM_MODE` > default embedded.** The fixed mode is injected into the WebView (global `__ENGRAM_MODE__`) so that **the frontend (clientFactory) follows the Rust decision (Rust = single source of truth).** The current JS self-decision (localStorage/global) is demoted to a dev switching override only.
  - Rationale (industry-practice survey): Tauri's official `tauri-plugin-autostart` formally supports **argument injection** (`--hidden` style) at boot registration — no precedent for per-mode exe separation (double management of build, signing, update, single-instance). Branching "boot launch vs user launch" by the presence of an argument is practically the standard.
- **Immediate entry into daemon mode = Windows self-relaunch (relaunch with `--mode=daemon` via `app.restart()`).** The "switch to daemon mode" action in the tray/menu relaunches the app with that argument. It is **independent** of the autostart toggle (from the next login, `--mode=daemon --hidden`).
  - ★Safe because it is Windows-only (load-bearing)★: the two self-relaunch risks the survey pulled out are irrelevant to us — the macOS `restart` exit-only bug (#13923) is macOS-only so does not apply, and the argv loss (#7402) is limited to "after an update is applied" so is unrelated to mode switching. So even if self-relaunch is used as a frequent mode-switching path, it does not break on Windows (it would be an anti-pattern on another OS).
- **The autostart registration argument = `--mode=daemon --hidden`.** When `--hidden` (boot launch) is detected, the main window is not shown (tray only); a direct user launch shows the window.

### 거부한 대안 (supplement)
- **A separate exe per mode** — no industry precedent. Build artifacts, code signing, updater, and single-instance would have to be managed twice, and the two exes share 99% of the same code, so separation has no gain. A single exe + an argument is the standard.
- **Not building immediate daemon entry, only the autostart toggle (from the next login)** — the UX inconvenience of "I want to use the tray-resident form now but a reboot is needed." Windows self-relaunch is safe, so immediate switching is provided.
- **Put the mode in a persistent settings file (appdata) and toggle it in the UI** — the settings-file I/O would have to happen before the single-instance plugin registration (the earliest point), and immediate switching is impossible (a rerun is needed). The argument approach is earlier and simpler.

### 영향 / 불변식 (supplement)
- **The mode decision is once at the very top of `run()`** (argument parsing) → this value drives (a) the single-instance lock key choice (b) whether `build_tray` is called (c) whether `CloseRequested` does prevent_close (d) the `default_data_dir(mode)` argument (e) the WebView injection. The mode is invariant for the process lifetime (a switch = a new process via self-relaunch).
- **The in-proc data ownership problem of app-in-daemon-mode (a current limit — resolved at the flip):** pre-flip, agents are always embedded (in-proc) (TRD §0), so even if the app is in daemon mode it brings up an in-proc AgentManager. In release-daemon, if that store points at `%APPDATA%`, **dual ownership of appdata/agents.json with the real daemon process** is latent. Pre-flip, the daemon is not the agent host and daemon mode is not productively used, so the collision is dormant (not active). At the flip, app-in-daemon-mode does not bring up an in-proc store and becomes WS-only, which resolves it. → Step 3 lays down only the `default_data_dir(mode)` infrastructure and defers avoiding this dual ownership to the flip (main decision, reported).
