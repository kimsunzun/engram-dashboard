# ADR-0195: Commands that arrive while the connection is down are failed at once, not held

- 상태: 확정 (2026-09-11, basis: user decision + measured CI failure + survey of external practice)
- 관련: ADR-0006(lock discipline — `current_cmd_tx` stands on that discipline) · ADR-0088(transmission-completion evidence · receipts) · `docs/tracking.md` · step-log S21

## 맥락

The shell (the side that opens the window) and the daemon (the side that actually owns the agents) connect over a local WebSocket. When that socket drops, there is a handler that wakes the waiting commands as 「못 보냈음」 (“could not be sent”) — at the moment of the drop it sweeps the wait buffer and wakes them with an error (`src-tauri/src/daemon_client/connection.rs:621`(those already sent) · `:635`(those not yet sent)).

★**But that handler sweeps once at that moment and stops, and the channel the commands are put into outlives the socket.**★ So a command that arrives right after the sweep stays there and is **executed on the next connection.**

**This is not a rare race** — **every** command that arrives while reconnection is running (first delay 500ms, up to over ten seconds — `connection.rs:80`) ends up that way. If the daemon is swapped in between, **a command meant for daemon A is executed on daemon B, and the caller is told it succeeded.**

**Measured evidence** — CI went red on a docs-only commit (`ddf9e1f`) (run 34551918256 attempt 1), and the value that assertion printed was `Ok(Ack { request_id: … })`. The first connection was a mock server that does not respond, so that response came from **a socket established after the drop**. The rerun was green, and 90 local repetitions reproduced it 0 times (under 1%).

★**The code already states this decision and does not keep to it**★ — `current_cmd_tx` at `src-tauri/src/daemon_client/lifecycle.rs:262` is that. The comment above it says 「None = 연결 task 없음/**끊김**」 (“None = no connection task/**dropped**”) (`:257`), and one more line asserts 「★stale 송신 차단★ … 이 clone 은 **항상 current 연결의 채널**이다」 (“★stale send blocked★ … this clone is **always the channel of the current connection**”) (`:260`~`:261`). But what empties that channel is only **succession** (`bump_and_capture`) and **close** (`close`), and an ordinary drop and reconnect happens inside the same task and is neither of the two. The consumer `send_command` is written on the same premise — 「현재 활성 연결의 cmd_tx 를 얻는다(없으면 연결 안 됨/끊김)」 (“get the cmd_tx of the currently active connection (none means not connected/dropped)”) (`src-tauri/src/daemon_client/mod.rs:707`).

## 결정

**While the connection is down, commands are not accepted — they are returned at once with a 「연결 안 됨」 (“not connected”) error.**

- The sending endpoint is **closed along with the drop.** Until reconnection finishes and a new connection is up, the caller cannot put a command in.
- **Whether to send again is up to the caller.** The client does not hold commands on its behalf.
- ★**A command does not cross a connection boundary**★ — this is the invariant this decision protects.

## 거부한 대안

- **Hold them, then filter and send on reconnection by a generation marker** — the plan that discards what belongs to the old connection and wakes it with an error. The response side actually already has that marker check, so it is technically possible. ★**But external research found no precedent of this shape**★ — none of the client libraries with a reconnect queue checks, before flushing the queue, that 「큐를 흘리기 전에 돌아온 상대가 아까 그 상대인지」 (“the peer that came back is the same one as before”). The systems that deal with this problem **all raise a session-resume failure to the upper layer as one signal and let the caller rebuild** (three families: resume token + server rejection · request-id deduplication · only tells the boundary and leaves retry to the caller). A fourth shape that judges items inside the queue one by one has no precedent.
- **Hold and send on the next connection, as now** (current behavior) — the same user action sometimes becomes an 「미전송(재전송 안전) 오류」 (“unsent (safe to resend) error”) depending on timing, and sometimes becomes a **success report after being executed on a different daemon**. ★The nondeterminism itself is the defect.★

## 근거

- **Survey of external practice (light intensity, 2026-09-11)** — the axis that splits is not the ecosystem but **whether the call is a request that waits for a response or a fire-and-forget publish**. The families that wait for a response (RPC · DB drivers) **fail at once by default**, waiting is an explicit opt-in, and even that has a deadline. Only the fire-and-forget families (messaging · caches) queue by default. **Our commands are the former** — they wait for a response, have side effects (an agent starts), and the caller sees the result.
  - As the representative primary source, the gRPC docs were **checked against the original text** (by the main agent directly): 「without Wait-for-Ready it will **immediately return a failure**」 · 「The default is **without** Wait-for-Ready」 · 「The deadline still applies」 (https://grpc.io/docs/guides/wait-for-ready/). ★The survey was light, so it did not go through adversarial review, and items other than these three lines are the collector's self-reported confidence.★
- **The original intent of our code** — the comments in the context above (`lifecycle.rs:256`~`:261` · `mod.rs:707`). This decision is not a new policy but **a return to the intent already written down**.

## 영향 / 불변식

- ★**The behavior users feel changes**★ — pressing a command while reconnection is running now (if unlucky) succeeds silently, but from now on it **fails at once with 「연결 안 됨」 (“not connected”)**. The user's judgment is that this is more predictable.
- **That intermittently failing test becomes deterministic** — `buffered_command_on_disconnect_is_drained_not_executed_post_reconnect` at `src-tauri/src/daemon_client/tests.rs:2961`. It currently goes red under 1% of the time.
- **Two supplements are needed on the test side too** (a record, not something this ADR decides): ① the 「늦게 실행됐나」 (“was it executed late”) counter counts **only the new server**, so it cannot catch the case of reconnecting to the old server ② the failure message does not print which server responded, so when judging from the CI log this time we were lucky on one value.
- **To decide at implementation time** — whether to treat 「연결을 처음 세우는 중」 (“setting up a connection for the first time”) and 「끊겨서 재시도 중」 (“dropped and retrying”) the same or differently. Among external precedents, some wait in the former and fail at once only in the latter (gRPC's channel state distinction). ★This ADR decides only 「끊긴 동안」 (“while down”).★
- **Reopen triggers** — ① if a real demand arises on the caller side for 「끊기면 알아서 다시 보내 달라」 (“resend automatically if it drops”), it is then solved not by a client queue but by **a retry in the caller layer** ② if an idempotency key or deduplication is introduced for commands, this axis can be reopened.
