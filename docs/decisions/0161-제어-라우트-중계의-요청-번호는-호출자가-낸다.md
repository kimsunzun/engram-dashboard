# ADR-0161: The request number of a control-route relay is issued by the caller

- 상태: 확정 (2026-08-19, basis: findings of the 3-lens adversarial review + user decision)
- 관련: Amends ADR-0160 (who issues the request number) · `crates/engram-dashboard-daemon/src/bin/engram.rs:119`(client read deadline) · `crates/engram-dashboard-daemon/src/command_delivery.rs`(`DEFAULT_DEADLINE`·`SeatState::Retained`) · step-log S20

## 맥락

ADR-0160 laid down two clauses together, and **the two contradicted each other.** Decision 2 is 「`request_id`는 데몬이 발급한다」 (the daemon issues request_id), and the 영향 section says 「두 입구는 같은 자리·마감·**중복 방지**를 쓴다」 (the two entrances use the same seat, deadline and **duplicate prevention**). But the duplicate-prevention seat (`SeatState::Retained`) is engaged **only when the same number comes again**. If the daemon makes a new number for every HTTP request, that mechanism is **structurally never engaged** — the machinery is shared but the property is not carried over.

The review (3 lenses, a single family) found this contradiction together with the real damage path. The client read deadline (`bin/engram.rs:119`, 10 seconds) expires **always before** the daemon deadline (`DEFAULT_DEADLINE` 10 seconds + up to 1 second of sweeper tick) — it is not a race but a deterministic order. So in a slow-owner situation the caller receives a transport error instead of the daemon's `TIMEOUT`, and the contract wording of that error **recommends retrying.** The retry gets a new number and becomes an unrelated round trip, and **the same operation is applied twice** (two tabs · two slots).

## 결정

1. **The caller issues the request number.** The control route request body accepts an **optional** caller-specified number, and if present uses it as the `RequestId`. If absent, the daemon issues it as before (backward compatible).
2. **The CLI makes one number per logical call.** ★**The original latter half of this clause (「자기 재시도에서 그 번호를 그대로 다시 보낸다」 (on its own retry it sends that number again as is)) was a factual error and remains unmet**★ — the draft assumed the CLI has a retry loop, but measurement shows it **does not** (`post_json` has 3 call sites · the only `loop` is the chunked decode). For the CLI a retry means **re-running the process**, and then a new number is created. So duplicates are prevented **only within a single call**, and not between re-runs. There are two ways to open it — either the CLI newly exposes a surface that takes a number (a flag or environment variable), or the relay branch is made to retain the seat. **Both are open and are user-decision items** (as of 2026-08-19).
3. **The daemon relay deadline is strictly shorter than the client read deadline** — including the sweeper tick margin. State the relation between the two values in code (a constant or an assertion) so that a later edit cannot silently flip it.
4. **The envelope (`CommandEnvelope`) is still not touched.** What grows is only the control route's **HTTP request body**. ADR-0160's clause 「봉투 무변경」 (no envelope change) remains valid.
5. A number given by the caller is a **value from outside**, so validate and limit its length and character set.

## 거부한 대안

- **Only pull the deadline in and leave retry as is** — fixing the deadline makes a proper `TIMEOUT` arrive, which reduces the reason to retry *blindly*, but **if the caller really does retry it is still applied twice.** The guidance only gets better; the property does not come into being. The 「중복 방지 공유」 (duplicate prevention sharing) that the ADR-0160 영향 section promised is not satisfied by this option.
- **The daemon keeps a completed result for a short time and returns it for the same command** — the sturdiest, but it requires newly settling the decision criterion for 「같은 명령」 (the same command) (name + arguments? normalization?) and brings retention lifetime and capacity management. **It amounts to building a second duplicate-prevention machine when the existing seat mechanism is enough**, so it collides head-on with ADR-0160's 「입구별로 다른 장치를 만들지 않는다」 (do not build a different mechanism per entrance). Reopen it if a case where the seat does not suffice is measured.
- **Decide duplicates by caller identity** — identity comes from the key (`control/registry.rs:156-163`), but it cannot tell apart two *different* calls of the same agent. It is not a duplicate-decision axis.

## 근거

- ADR-0160's own internal contradiction (decision 2 ↔ 영향 1) was independently found by 2 of the 3 adversarial review lenses. The coder also self-reported the same point as an unmet completion criterion.
- The deadline inversion is **deterministic** — the client timer starts before the daemon timer (connection, parsing and `spawn_blocking` come first) and has the same length, and the daemon response comes after a 1-second tick. It is not a probabilistic race; the client always gives up first.
- User decision (2026-08-19) — of the three options, caller issuance was chosen.
- ★**The two factual errors of the draft were caught by review round 2**★ (2 of the 3 lenses independently found them): ① the absence of a CLI retry loop ② the relay branch has no seat retention. Both were confirmed by **code measurement**. The very ground on which this ADR was built was half wrong, so the latter half of decision 2 is left not as 「달성했다」 (achieved) but as **「미충족 + 두 갈래 미결」 (unmet + two open branches)** — if it is not written that way, the next session reads it as already blocked.
- ★**The review that produced this decision was a single family**★ — the non-lead family's quota was exhausted, so all three lenses are of the same lineage. No cross-family cross-check.

## 영향 / 불변식

- **It supersedes ADR-0160 decision 2.** Only that clause splits off, and the rest (control route extension · no envelope change · machinery sharing) remains valid.
- ★**This decision also supersedes the 「현재 기본 10초」 (currently 10 seconds by default) figure in the ADR-0160 영향 section**★ — decision 3 pulled the deadline in, so that number is stale. The actual value is owned by the code (`DEFAULT_DEADLINE` in `command_delivery.rs`), and what this ADR pins is not a number but an **inequality**.
- ★**The relay branch's duplicate prevention today is only 「진행 중 합치기」 (merging while in progress)**★ — the step that sets up seat retention (`SeatState::Retained`) exists **only in the daemon's own command branch**, and the relay branch erases the seat when the round trip ends. So **a re-query after the round trip has ended is applied again even with the same number.** This is the second reason decision 2's latter half is unmet, and it means the ADR-0160 영향 clause 「중복 방지를 공유한다」 (share duplicate prevention) is a state where **the machinery is shared but the property is not carried over.** Closing this gap would require making the relay branch retain as well, and that is a behavior change of the shared machinery, so a separate decision is needed.
- **The earlier ground that the seat table (in-progress seats) has no cap has weakened** — that ground was 「이 입구가 인증 경계 안」 (this entrance is inside the authentication boundary), and then inside meant *one trusted client*. Now it means *N agent credentials*. The relay's concurrent-in-progress cap was set on a **global axis** (not per credential), and whether that axis is right is open.
- **Requests without a number are still accepted** — backward compatibility is not broken. But the contract is the fact that duplicate prevention does not engage on that path.
- **The ordering of the two deadlines is the invariant.** Daemon relay deadline < client read deadline. If only one side is fixed, the `TIMEOUT` response becomes unreachable again, and the caller sees a false transport error.
- **The control route request body grows** — it is not the envelope, so the generated-output sync gate is unaffected. If this distinction blurs, ADR-0160's 「봉투 무변경」 breaks silently.
