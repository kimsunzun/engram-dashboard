# ADR-0287: All strip notices stack in a layer that covers the layout instead of pushing it — the layer is only as tall as the notice rows

- 상태: 확정 (2026-10-08, basis: user decision 2026-10-08 + this session's static reading (a search of the frontend source and the wording files — master `3a30a0c`). ★**Not a single line of code behavior was changed**★) · 부분 폐기 by ADR-0306 (the example of the covered screen below in decision 2, 「TabBar 등」)
- 관련: Amends ADR-0180 (of the invariant that separates what a notice covers only by popup eligibility, all the remaining strip notices) · Amends ADR-0276 (the basis of the layer-height invariant and the empty area outside the rows) · Amends ADR-0277 (of the open items, the remaining connection events) · ADR-0181 (one failed command is also a strip) · T-48 · T-50 (this ADR closes them — record = `docs/tracking-archive.md`) · TRD `docs/process/S21-storage/trd.md` §14-16 · §14-17 · §14-18 · TRD `docs/process/S21-transport-crate/trd.md` (the place that will produce the remaining connection events) · `src/components/layout/NoticeOverlay.tsx` (the covering layer) · Amended by ADR-0306 (the example of the covered screen below in decision 2, 「TabBar 등」)

## 맥락

ADR-0180 split the notice surface in two — a strip 「알린다」 (tells; it pushes the layout and does not cover), a popup 「네가 눌러야 한다」 (you have to press; it covers). Later on the same day (2026-10-06), two ADRs moved two strips to the covering side — the state-file notice (ADR-0276) and the connection-lost notice `ConnectionNotice` (ADR-0277). The reason the user gave in ADR-0276 was 「우리는 레이아웃을 고정시키고 그 고정된 상황에서 작업하는건데 팝업이 나오면 밀림」 — ★In ADR-0277 the session applied the same reason to the connection strip as a recommendation, and the user accepted with 「덮기로해.」 (the user did not give a reason separately — ADR-0277 「거부한 대안」)★.

The two left open items, and the user put them off with 「저장 시스템 다 하고 언급하면 될듯」 (2026-10-06). They were raised on 2026-10-08, after storage management (S21-storage) was finished.

- **T-48** — whether the remaining connection events that ADR-0180 decision 2 · ADR-0181 sorted to the strip side (a transient drop · retrying · a lost-notice · one failed command) should also go into the covering layer. The 「연결 띠」 of ADR-0277 pointed only at `ConnectionNotice`.
- **T-50 「줄 바깥 빈 영역」** — setting the height of the covering layer to just the notice rows (a click outside the rows goes to what is below) was a session judgment that came out of the implementation, not a user decision (ADR-0276 「영향 / 불변식」).

★Facts at the time of raising (static reading 2026-10-08 · master `3a30a0c`)★ — only two notices sit on the covering layer: the connection-lost notice and the state-file notice (main = `AppLayout` · popout = `PopoutPage`). The other four connection events of T-48 **have no on-screen display yet** — those notices are not in the frontend source (`src/components/**`) or the wording files (`src/i18n/**`). There is also no notice that pushes the layout by entering the flow (the other things that show up = the error panel that replaces the whole slot area · the loading panel · the absence curtain inside a slot — they are not notice strips).

## 결정

1. **Every notice that is not a popup (a strip) stacks in the covering layer (`NoticeOverlay`) without pushing the layout** (user decision 2026-10-08 — 「어 당연히 레이아웃 밀면 안된다니깐.」). In addition to the two that exist now (ADR-0276 · ADR-0277), **it is also hung in advance for the strip notices that do not exist yet — the four connection events of T-48 and any new strip that appears otherwise.** No separate decision is taken when a new strip is put on that layer.
2. **The height of the covering layer is only as tall as the notice rows drawn** — clicks do not go to what is under the area a row covers (the TabBar etc.), and closing it with ✕ makes it clickable again · the screen below where there is no row is clickable as usual · when the stack exceeds a certain height, it scrolls inside. ADR-0276's session judgment (a height of just the rows) is **confirmed as a user decision** (user decision 2026-10-08 — 「위에 줄이 있으면 해당 줄 뒤로 클릭을 못하는거잖아. x로 닫기도 하는거고.」). Scrolling on overflow was originally a user decision (2026-10-06 — 「일정 이상 나오면 스크롤」) · ★the cap value (now 1/3 of the window height) is still a session judgment★ (the comment at that spot in `NoticeOverlay.tsx`).
3. **What does not change** — the split of ADR-0180 decision 1 (strip = 「알린다」 · popup = 「네가 눌러야 한다」) and the popup eligibility of decision 2 (「사용자가 행동하지 않으면 영영 복구되지 않는가」) stay as they are. This ADR decides only **where** a strip is drawn, and does not touch which event is a strip and which is a popup.

## 거부한 대안

- **(T-48) Put the remaining connection events as a flow block (a strip that pushes the layout)** — the original shape ADR-0180 gave strips. User: 「당연히 레이아웃 밀면 안된다니깐」. It is on the same axis as the layout-fixing reason the user gave in ADR-0276 (in ADR-0277 the session applied that reason — 맥락).
- **(T-48) Ask again when that notice is actually built (do not decide now)** — the session put it up as an option (the recommendation was 「지금 원칙만 정하기」) and the user decided the principle now with the one line above. ★The user did not separately give the reason for dropping this alternative★ — the session's framing was 「같은 원칙을 이미 두 번 적용했으니 미루면 같은 질문을 다시 올릴 뿐이다」.
- **(T-50) Dim and block the rest of the screen while a notice is up (like a modal)** — the session put this up as an option alongside 「줄만 덮기(추천)」, and instead of choosing, the user retraced the current behavior (「뭔소리야? 위에 줄이 있으면 해당 줄 뒤로 클릭을 못하는거잖아. x로 닫기도 하는거고.」). The session took that as confirmation of the current behavior. ★The rejection reason is the session's framing — the user did not separately give a reason★: a strip is a 「알린다」 (tells) surface (ADR-0180 decision 1), so if work stopped every time the connection dropped briefly, it would be indistinguishable from a popup.
- **(T-50) A full-height transparent screen** — it also eats clicks outside the rows. That is the very incident ADR-0180 meant to prevent (the old overlay ate TabBar clicks so tab switching · creating · closing were blocked, and combined with a state whose reason does not go away it was blocked permanently — the context of that ADR).

## 근거

- User decision 2026-10-08 (the quotes of decisions 1 · 2 above — T-48 was the answer to 「원칙만 지금 정할까요?」, and for T-50 the session took the user's retracing of the current behavior in answer to the options question as confirmation).
- Static reading (2026-10-08 · master `3a30a0c`) — the 「올린 시점의 사실」 in the context. No on-screen measurement was done.
- ★**Not verified**★ — scrolling when the covering layer exceeds 1/3 was still not measured with the GUI (only a vitest structure test — the not-verified item of ADR-0277 「영향 / 불변식」 as it is).

## 영향 / 불변식

- **A new strip notice is put inside `NoticeOverlay`** — main lays down the layer in `AppLayout`, and the popout in `PopoutPage`. Putting it in as a flow block so that it pushes the layout violates this decision.
- **The layer is not made taller than the notice rows** — this is now a user decision (decision 2). To use a full-height screen or dim-and-block, reopen this ADR.
- **A covering strip must have a way to get out of the way** — the area a row covers cannot receive clicks, so without a way out it becomes the permanent block that ADR-0180 meant to prevent. For the two now, ✕ and the remembered dismissal are that way (ADR-0277 「영향 / 불변식」 · the head of `ConnectionNotice.tsx`).
- **Deferred (not a decision)** — the per-strip details for when the remaining four connection events are actually built. Example: whether a frequently shown strip such as 「재시도 중」 should vanish by itself, since it would be annoying if it covered the TabBar until ✕. Those strips come out of the work of attaching the transport crate to the shell (crate boundary refactoring step 3 · `docs/process/S21-transport-crate/trd.md`), and that TRD decides them then — decisions 1 · 2 of this ADR are laid down as the premise.
