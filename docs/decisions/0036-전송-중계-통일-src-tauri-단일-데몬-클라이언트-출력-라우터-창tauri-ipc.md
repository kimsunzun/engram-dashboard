# ADR-0036: Unified transport relay — src-tauri as the single daemon client + output router (windows = Tauri IPC)

- 상태: 확정 (2026-06-27, basis: `/research` deep report + user decision) · 부분 폐기 by ADR-0179 (the number of connections the daemon sees)
- 관련: ADR-0035 (layout authority = src-tauri — the authority counterpart of this decision) · ADR-0020 (single protocol + transport-neutral dispatch core · swappable carrier — this ADR amends the carrier topology) · ADR-0029 (daemon-only · the app = a daemon client) · ADR-0011 (agentClient control surface) · ADR-0028 (event bus single push) · `docs/research/multi-window-layout-authority-topology-research-2026-06-27.md` · step-log S14 · Amended by ADR-0179 (the number of connections the daemon sees)

## 맥락
When layout authority moved to src-tauri through ADR-0035, a topology mismatch showed up. Today **each window (WebView) connects to the daemon directly over WS** (`wsTransport.ts` attaches to the daemon with the browser WebSocket; src-tauri only tells where the daemon is and is outside the data path). But if layout goes through src-tauri while only agent output goes directly window ↔ daemon, then ① the topology is inconsistent ② routing is duplicated (src-tauri already holds the layout table of "which window views which agent", yet each window re-derives it) ③ if N windows view the same agent, there are N daemon subscriptions and N duplicates of the output (N times over the network with a remote daemon).

## 결정
**src-tauri holds a single WS connection to the daemon and fans output out to each window using the layout routing table it owns (ADR-0035).** Windows talk IPC only to src-tauri (both layout and agent) — zero direct daemon connections. The daemon sees one client, and the daemon subscription is once per agent (duplicates removed, local fan-out). Input (write/spawn/kill/resize) also goes window → invoke → src-tauri → daemon. The frontend carrier is replaced from `WsTransport(데몬 직결)` to **`TauriTransport` (via src-tauri)** (using the ADR-0011/0020 transport seam — the `agentClient` = `ProtocolClient` interface is unchanged). **src-tauri Rust owns the daemon's single WS connection, reconnection, subscription tracking, resubscribe, epoch, seq dedup, and routing** (the protocol semantics of the current TS `wsTransport.ts`/`protocolClient.ts` move to Rust). The window's `agentClient` keeps the ADR-0011 interface, but its implementation is a **thin client** on top of TauriTransport (the brain is Rust). **No phasing, no legacy interim** — the per-window direct connection (legacy) is not kept even temporarily, and the target structure is implemented right away (user decision 2026-06-27: "don't keep legacy, do it properly").

## 거부한 대안
- **Each window connects directly to the daemon over WS (current)** — N windows = N duplicated authentications/reconnects/discovers + N duplicate transmissions of output (N times over the network if remote) + each window re-derives the routing table src-tauri already has. Its only advantages (direct high-bandwidth output path · per-window failure isolation) are weak: (a) it is local IPC, so the cost of one relay hop is negligible (b) with a remote daemon, direct connection actually wastes bandwidth (c) if it truly becomes a bottleneck, a per-pane direct subchannel can be added later (Codex recommendation: "keep it central; add the option if profiling shows a bottleneck"). No gain for the cost.

## 근거
`/research` deep — a single authority + single-connection multiplexing is the practice: **LSP** (a single editor ↔ server connection multiplexes many documents, no connection per document), **Chromium** (the browser process is the single authority + Mojo fan-out to the renderers), **Wayland** (the compositor has a single socket). src-tauri owning layout (ADR-0035) = holding the routing table → output routing composes naturally (the daemon does not know "who is viewing", so it cannot route). In terms of remote-daemon (ADR-0029) bandwidth, the relay is clearly advantageous (output sent once → local fan-out).

## 영향 / 불변식
- **Single choke point:** all traffic (layout · agent I/O) passes through src-tauri. Direct window ↔ daemon connections are forbidden.
- **Daemon unchanged:** the daemon does not know the number of clients and sees only one connection. No change to the daemon core/protocol (agents only).
- **Carrier swap (amends ADR-0020):** the frontend daemon carrier = `WsTransport` direct → `TauriTransport` (src-tauri IPC). The `agentClient` (ADR-0011) interface and the single protocol are unchanged — the transport seam exists exactly for this (ADR-0020). The daemon single connection and the protocol semantics are **owned by src-tauri Rust** (moved from TS). The window `agentClient` is a thin Tauri client (the brain is Rust).
- **Output routing policy:** the src-tauri `OutputRouter` delivers by looking up `ViewManager` only to "the windows that show that agent for agentId". Nothing is sent to windows that do not show it.
- **Message policy (lock/gating) lives in the daemon:** the transport relay does not enforce policy — the agent message lock and the like are enforced by the daemon as the single choke point (src-tauri may only do a cache-based early-reject *optimization*; the authority is the daemon).
- **No phasing (user decision 2026-06-27):** the legacy per-window connection is not kept even temporarily, and the target structure is implemented right away. ★Relocating the transport layer (moving connection · reconnection · resubscribe · epoch · seq dedup to Rust) is **concurrency-critical** — the invariants of kill causality (ADR-0001) · finalize once (0005) · lock order (0006) · epoch resubscribe (0007) must be preserved without reproducing races, so **TDD + deep code review are mandatory** (a correctness gate, not a speed gate).★ Implementation order (without legacy, by dependency): ViewManager + layout (the foundation of the routing table) → DaemonClient + TauriTransport + OutputRouter (routing depends on ViewManager, ★concurrency-critical) → renderer · tabs · popups.
