## 맥락

When ADR-0178 flipped version mismatch to 「데몬이 핸드셰이크에서 끊는다」, it left **one popup on the client side**. But ★**there is no modal component to reuse**★ — in all of `src/`, `Dialog|Modal|AlertDialog|createPortal` has **0 matches** (measured). ★**That measurement says exactly that and nothing more — not 「덮는 표면이 하나도 없다」**★: in fact two already exist. The **slot context menu** covers the content with `position:'fixed'` + `zIndex 1000/1001` and closes on an outside click (`src/components/slot/SlotContextMenu.tsx:121` · `:224`), and the **native file dialog** (`open` of `@tauri-apps/plugin-dialog`) is called from three places (`src/commands/slotContentCommands.ts:6` · `src/commands/presetCommands.ts:6` · `src/commands/agentCommands.ts:5`). So what is missing is not **the act of covering** but ★**a reusable component on which a warning can be put**★, and therefore 「팝업을 띄운다」 is not one line of wording but **a job of building a new component**. And unless we also fix a rule for what is eligible for a popup, every later notification will crowd toward it.

The **notification** surface that exists now is **one strip** — `ConnectionNotice` (one line of wording + a close ✕, **no action button**, it only **reads** the connection state and sends no commands). And that strip ★**deliberately does not cover the screen**★: the previous edition was an `absolute top-0 z-50` overlay, so it hid the TabBar and ate its clicks, which **blocked tab switching, creation and closing**, and when it overlapped a state whose reason would not clear, it blocked them permanently. So it came down to a normal-flow block. ★**That 「덮지 않는다」 is a clause tied to that strip and not a principle of the whole repository**★ (canonical = `ConnectionNotice.tsx:10`, scope = that banner and that TabBar incident). The context menu above is the evidence — covering surfaces are already allowed. ★(2026-10-06 amendment mark) This paragraph is the fact as of this ADR — that strip now covers the layout in all three windows (ADR-0277 · user decision), and the `:10` above points to the edition before `9318b5c`★.

Current state of reconnection (measured): the shell tries **5 times at 500ms → 1s → 2s → 4s → 8s** (no jitter) and then is **permanently Down** — 15.5 seconds in total. And ★**there is no 「다시 연결」 button on the screen**★ — the API exists but no UI calls it, so once the budget is exhausted, **restarting the app is in effect the only recovery**.

## 결정

1. **There are two presentation surfaces.** ★**The strip (the existing `ConnectionNotice`) says 「알린다」, and the popup says 「네가 눌러야 한다」**★. The same event is not put on both surfaces at once — which one it appears on is itself the answer to 「내가 지금 뭘 해야 하나」.
2. ★**Popup eligibility = only 「사용자가 행동하지 않으면 영영 복구되지 않는 상태」**★.
   - **Eligible (→ popup)**: **version rejection** (ADR-0178) · **reconnect budget exhausted**.
   - **Not eligible (→ strip)**: a transient drop · retrying · loss notice · one command failing.
3. **The popup is built as a general-purpose component, and the warning is put on it as one use.** The user stated explicitly that they will **also use the popup for content display** later (2026-09).
4. **Reconnection splits by layer** — ★**the loop itself (backoff + jitter) is inside the `transport` crate**★ (ADR-0177 decision 3 as is — this decision does not move it). What the shell owns is ★**the count and the 「지금 다시 해라」 entry**★, and it **injects** those two into the crate. **Default count = 3.**
5. ★**A case that attached and was then rejected does not use the reconnect count; the popup comes immediately on the first rejection**★ — because retrying gives the same result. What burns the budget is 「붙지 못한다」, not 「붙었는데 거절당했다」.
6. **Version-mismatch popup = wording (문구) + close. No action (force-kill) button.**
7. ★**The popup that comes up when the reconnect budget is exhausted carries a 「다시 연결」 button**★ (the user proposed that form). **This is what holds up decision 4's 3 attempts** — without the button, 3 attempts simply means giving up faster. ★**Contrast with decision 6**★: the version-mismatch popup does not have this button (wording + close only). The two popups differ in shape by **whether there is something the user can do on the spot**.
8. ★**The popup decision is on the whole-app basis (앱 전체 기준)**★ (user decision 2026-09-06) — **if even one attached daemon remains, it is the strip**, ★**the popup only when all are lost**★. When one connection dies, **the user presses on the spot to reattach** — the per-connection reconnect affordance is on **the strip side**. (User's words: 「A 하나 죽어도 BC는 잘 동작되야지? 나중 기준으로 A쪽을 클릭해서 재연결을 할 수 있게 하던가 해야지.」)
   - ★**This is not a new criterion but the result of applying decision 2 as is**★ — the state of having lost one daemon is **not** a 「사용자가 행동하지 않으면 **영영** 복구되지 않는」 state. The app can keep being used with the remaining peers, and that one can be reattached from the strip.
   - ★**So even if N peers are rejected at the same time, there is one popup**★ — the unit of the decision is **the app, not the peer**, so popups piling up as many as the number of peers **structurally** cannot happen.
   - ★**The axis differs from decision 5 — not a contradiction**★. Decision 5 is 「그 상대를 언제 잃은 것으로 칠 것인가」 (immediately on the first rejection · does not burn the budget), and decision 8 is 「팝업을 언제 띄울 것인가」 (when all are lost). A rejected peer is counted as lost **immediately**, but that is not yet a popup.

## 거부한 대안

- ★**Put a 「데몬 강제 종료」 button on the popup**★ — rejected on four overlapping grounds.
  - **(a) The graceful shutdown command structurally cannot get there** — to send `AgentCommand::StopDaemon` one must pass authentication, and **a version mismatch is rejected exactly there.** `stop_with_sender` of discovery records that fact as it is and handles `VersionMismatch` as `NoTarget` (measured — `crates/engram-dashboard-discovery/src/lib.rs`).
  - **(b) The only means left is a forced kill, and the cost is large** — the agents that daemon was holding go down with it. They are restored by session identifier, but **output in progress is cut.**
  - **(c) We cannot attach, so we cannot even see the list of what is running** — the reason ADR-0158 decision 3 gave when it banned automatic kill (「무엇이 돌고 있는지 모른 채 죽이면 안 된다」) **holds in the worst way here.**
  - **(d) This combination itself is rare** (user judgment) — the app and daemon ship in the same deliverable, so we do not dig deeper. ★**But the exact fact behind (d) is written down separately**★: the cause of the mismatch is **not the deployment unit but the old daemon not dying and surviving** (ADR-0158's context already says so — 「갈리는 원인은 배포 단위가 아니라 데몬의 수명」). The fact that deployment is one bundle **does not prevent** this combination.
- **Every notification as a popup** — the rejected alternative of ADR-0158 already refuted it: **overnotification raises the warning-ignoring rate and in the end users switch off the app's notifications altogether.** That rejection stays valid in this ADR as well.
- **Build the popup as a warning-only component** — the user stated explicitly that a **content popup** will be needed later. If we build it dedicated, **we build the foundation twice.**
- **The daemon gives the reconnect count** — ★**a value to be used when we cannot attach cannot be received from a peer we cannot attach to**★. Moreover, **before the first connection there is nowhere to ask.** If the daemon gives it, it would be 「한 번 붙었을 때 받아 두는 값」 and **would not apply to a user starting for the first time.**
- **Keep 5 reconnect attempts** — since the popup gets a reconnect button, **being short costs little.** After 3.5 seconds the user can simply press again.

## 근거

- ★**A correction to ADR-0158 decision 3 — this ADR is not an exception to that clause**★. What that clause bans is 「**자동** kill」 (the original: 「데몬을 **자동으로** 죽이지 않는다」, and the invariant too: 「데몬을 **자동으로** 죽이는 경로를 만들지 않는다」). **A user pressing a button to kill is not caught by that clause.** ADR-0178 also wrote the same judgment (「팝업의 버튼을 사용자가 눌러 동의하는 형태는 그 금지의 취지와 어긋나지 않는다」). So the reason for rejection in decision 6 above is **(a)~(d), not 「금지돼 있어서」.** ★**The handoff memo of the last session wrote this wrongly as 「금지 경로」 — we cut that misreading here.**★
- ★**The reason a popup is dangerous is not that it is 「처음 덮는 것」 but that it is 「알림이 덮는 것」**★ — a covering surface already exists (the context menu and native dialog in the context). Those two are **something the user just called up**, so they close themselves, but a notification **arises without the user having called it.** The incident where `ConnectionNotice.tsx:10` (the edition before `9318b5c`) pinned down 「덮지 않는다」 was exactly that kind — a strip nobody called hid the TabBar and blocked operation, and if the reason did not clear, it blocked permanently. **So the eligibility criterion (decision 2) is the device that sets the scope of that exception** — without a criterion, 「중요해 보이는 것」 all flows to the covering side, and at that moment the operations that were blocked are blocked again. (ADR-0134 decision 4 is the **reason that component exists**, and the sentence 「덮지 않는다」 itself was not in that ADR's body but in this file's header (the edition before `9318b5c`) — ★do not confuse where it is quoted from★.)
- ★**One false measurement of ADR-0178 is corrected here**★ — the last item of the 「거부한 대안」 of that ADR (the client kills the old daemon and starts a new one) cited as reason ② 「**「그만 꺼져라」 — there is no protocol command corresponding to it** (measured 2026-09-04 — 0 Shutdown·Restart·Quit variants). **It is false** — `AgentCommand::StopDaemon { force, kill_agents, request_id }` exists (`crates/engram-dashboard-protocol/src/messages.rs:89`, the comment says 「데몬 종료(§5 LLM 제어)」), `build_stop_command` of discovery (`.../discovery/src/lib.rs:772`) builds it, and the shell calls it in `src/api/daemonControl.ts`. **The error is reading the literal fact that there are 0 variants with those names as 「그런 명령이 없다」.** ★**But the conclusion of that rejection does not change**★ — (a) above is the reason, and this ADR confirmed it against the real code: **even if** the command exists, a version-mismatched daemon **is not reached because it cannot get through authentication.** The correction stamp was put in the body of ADR-0178 (2026-09-06).
- **The basis of 3 attempts is the sum of 「짧아진 대기 + 사용자 손에 쥐어진 재시도」** — 5 attempts at 15.5 seconds are cut to 3 attempts at 3.5 seconds, and in exchange, when the budget is exhausted a popup comes up and the user can try again there. ★**The premise that makes this trade hold is that the current state has no place to try again**★ (measured — 「다시 연결」 UI absent).

## 영향 / 불변식

- ★**The popup eligibility criterion (decision 2) is the only wall of 「알림이 덮는 것」**★ — neither the compiler nor a gate guards it. When attaching a new notification, separate it by one question: 「사용자가 행동하지 않으면 영영 복구되지 않는가」. If not, it is a strip. ★**(2026-10-06 amendment mark) Two exceptions — the status-file notice (ADR-0276) and the connection strip (연결 띠) (ADR-0277 — main · pop-out · tree windows) are not popup-eligible yet cover the layout (both user decisions). Other notifications keep this wall as is**★. ★So among the non-popup notifications that exist now, none remains in the flow, and the distinction that separated strip from popup by 「덮느냐」 is gone — what remains of the separation in decision 1 is 「알린다」 versus 「네가 눌러야 한다」. Here 「연결 띠」 is today's single `ConnectionNotice`, and whether the remaining connection events that decision 2 sent to the strip (a transient drop · retrying · loss notice · one command failing — ADR-0181 also puts the last one in the strip) should also go into that covering layer is open (not a decision — user question · ADR-0277)★. ★(2026-10-08 mark) No longer an exception — non-popup notifications (the strip) stack in the covering layer, including the remaining connection events above (ADR-0287 decision 1 · user decision). Whether it is a strip or a popup is still separated by the eligibility of decision 2★. ★The 「알림이 덮는 것의 유일한 벽」 in this opening no longer separates whether it covers — the wall that keeps a covering strip from permanently blocking clicks is now the ADR-0287 「영향 / 불변식」 (layer height = only as tall as the notification lines · a covering strip has a way to move aside) (read the 「기준이 없으면 전부 덮는 쪽으로 흐른다」 of 「근거」 above as the same place)★
- ★**The breaking condition is not 「crate 안에 3 이 있는 것」 but 「셸이 그것을 덮을 수 없게 되는 것」**★ — ADR-0177 decision 4 wrote that policy values have **crate defaults and the consumer overrides them**, so a default of 3 on the crate side is not a violation but **the contract as is**. The violation is the injection path disappearing so that the value becomes **fixed**.
- ★**To change the reconnect cap, look at two places together**★ — `connection.rs:77` and `wsTransport.ts:352` each hold the same name and the same value, and 「5회」 is **also embedded in prose** in two places (`agentClient.ts:132` · `daemonControl.ts:92`). If only one is lowered to 3, **the two layers run on different budgets.**
- **Grow the notification surface but do not grow new global handles** — ADR-0158's invariant 「알림 표면은 새 전역 핸들을 늘리지 않고 기존 제어 표면에 얹는다」 was decided **alive** by ADR-0178, and this ADR continues it (CLAUDE.md 「LLM-우선 제어」). ★**But which surface the popup stands on was left open by ADR-0178 and this ADR does not decide it either**★.
- ★**Not verified**★:
  1. **We did not check whether the client actually receives and reads the rejection-reason frame** — ADR-0178's unverified item 1 stays alive as is. If it cannot read it, **the 「문구」 of decision 6 does not hold** (only close is left).
  2. **Decision 5 is the *policy* answer to ADR-0178's unverified item 2 (whether endless reconnection repeats after rejection)** — it does not use the count and stops at the first rejection. ★**We did not check how the current code actually runs**★.
  3. **We did not count what changing the reconnect constant from 5 to 3 shakes elsewhere** — the four places where the cap lives are written above (two constants, two prose), but **we did not measure which flow gives up first** when the value is lowered.
- ★**The decision maker is the shell, not the crate**★ (for whoever builds decision 8). 「앱 전체」 is **a screen concept**, and `transport` **only counts peers and does not know the app.** The crate gives only two inputs — **a registry lookup** (`Registry::peers()`) and **「지금 다시 해라」** (`Peer::reconnect_now()`). ★**The shell folds those two and decides**★. Canonical = the end of `docs/process/S21-transport-crate/trd.md` §5. **If we put 「전부 잃었나」 inside the crate, at that moment the crate knows the app** (a violation on the same axis as the ADR-0129 vocabulary isolation).
- **Peers do not share state with each other** — even if daemon A is in the given-up state, B is alive (TRD §5). Decision 8 is a rule where **the shell folds those independent states when looking**, not a meaning to bundle the peers' states into one.
