## 맥락

When ADR-0178 flipped a version mismatch to 「데몬이 핸드셰이크에서 끊는다」 (the daemon cuts at the handshake), it left **one popup on the client side**. But ★**there is no modal component to reuse**★ — `Dialog|Modal|AlertDialog|createPortal` has **0 matches** in all of `src/` (measured). ★**That measurement says exactly that and nothing more — it does not say 「덮는 표면이 하나도 없다」 (there is no covering surface at all)**★: in fact two already exist. The **slot context menu** covers the content with `position:'fixed'` + `zIndex 1000/1001` and closes on an outside click (`src/components/slot/SlotContextMenu.tsx:121`·`:224`), and the **native file dialog** (`open` of `@tauri-apps/plugin-dialog`) is called in three places (`src/commands/slotContentCommands.ts:6` · `src/commands/presetCommands.ts:6` · `src/commands/agentCommands.ts:5`). That is, what is missing is not **the act of covering** but ★**a reusable component on which a warning can be placed**★, so 「팝업을 띄운다」 (show a popup) is not a one-line piece of copy but **the work of building a component from scratch**. And unless a rule for what has popup eligibility is fixed together with it, every later notification will crowd into it.

The **notification** surface that exists now is **one strip** — `ConnectionNotice` (one phrase + a close ✕, **no action button**, it only **reads** the connection state and sends no command). And that strip ★**deliberately does not cover the screen**★: the previous version was an `absolute top-0 z-50` overlay, so it hid the TabBar and ate its clicks, which **blocked tab switching, creating and closing**, and combined with a state whose reason never clears it blocked them permanently. So it came down to a normal-flow block. ★**That 「덮지 않는다」 (does not cover) is a clause attached to that strip and is not a principle of the whole repository**★ (canonical = `ConnectionNotice.tsx:10`, scope = that banner and that TabBar incident). The context menu above is the proof — covering surfaces are already allowed. ★(2026-10-06 amendment mark) This paragraph is a fact as of this ADR — that strip now covers the layout in all three windows (ADR-0277 · user decision), and `:10` above points to the version before `9318b5c`★.

Reconnection today (measured): the shell tries **5 times at 500ms → 1s → 2s → 4s → 8s** (no jitter) and after that it is **permanently Down** — 15.5 seconds in total. And ★**there is no 「다시 연결」 (reconnect) button on the screen**★ — the API exists but no UI calls it, so once the budget is exhausted **restarting the app is effectively the only recovery**.

## 결정

1. **There are two presentation surfaces.** ★**The strip (the existing `ConnectionNotice`) says 「알린다」 (we notify), and the popup says 「네가 눌러야 한다」 (you must press)**★. The same event is not put on both surfaces at once — which one it appears on is itself the answer to 「내가 지금 뭘 해야 하나」 (what do I have to do now).
2. ★**Popup eligibility = only 「사용자가 행동하지 않으면 영영 복구되지 않는 상태」 (a state that never recovers unless the user acts)**★.
   - **Eligible (→ popup)**: **version rejection** (ADR-0178) · **reconnect budget exhausted**.
   - **Not eligible (→ strip)**: a temporary disconnect · retrying · a loss notice · one command failing.
3. **The popup is built as a general-purpose component and the warning is placed on it as one use.** The user stated explicitly that they will **use the popup to display content as well** later (2026-09).
4. **Reconnection splits by layer** — ★**the loop itself (backoff+jitter) is inside the `transport` crate**★ (ADR-0177 decision 3 as is — this decision does not move it). What the shell owns is ★**the count and the 「지금 다시 해라」 (do it again now) entrance**★, and it **injects** both into the crate. **Default count = 3.**
5. ★**A case where it attached and was then rejected does not use the reconnect count; the popup comes immediately on the first rejection**★ — because retrying gives the same result. What burns the budget is 「붙지 못한다」 (cannot attach), not 「붙었는데 거절당했다」 (attached but was rejected).
6. **The version-mismatch popup = phrase + close. No action (forced termination) button.**
7. ★**The popup that appears when the reconnect budget is exhausted has a 「다시 연결」 button**★ (the user proposed that form). **This is what holds up decision 4's 3 times** — without the button, 3 would just mean giving up sooner. ★**It contrasts with decision 6**★: the version-mismatch popup does not have this button (phrase + close only). The two popups differ in shape by **whether there is something the user can do on the spot**.
8. ★**The popup decision is on an app-wide basis**★ (user decision 2026-09-06) — **if even one attached daemon remains, a strip**, ★**a popup only when all are lost**★. When one connection dies, **you press on the spot to reattach** — the per-connection reconnect affordance is on **the strip side**. (User's words: 「A 하나 죽어도 BC는 잘 동작되야지? 나중 기준으로 A쪽을 클릭해서 재연결을 할 수 있게 하던가 해야지.」)
   - ★**This is not a new criterion but the result of applying decision 2 as is**★ — a state of having lost one daemon is **not** a state that 「사용자가 행동하지 않으면 **영영** 복구되지 않는」 (never recovers unless the user acts). The app can keep being used with the remaining peers, and that one can be reattached from the strip.
   - ★**So even if N peers are rejected at the same time there is one popup**★ — the decision unit is **the app, not the peer**, so popups piling up as many as there are peers **structurally** cannot happen.
   - ★**The axis differs from decision 5 — it is not a contradiction**★. Decision 5 is **「그 상대를 언제 잃은 것으로 칠 것인가」 (when to count that peer as lost)** (immediately on the first rejection · the budget is not burned), and decision 8 is **「팝업을 언제 띄울 것인가」 (when to show the popup)** (when all are lost). A rejected peer is counted as lost **immediately**, but that does not make it a popup yet.

## 거부한 대안

- ★**Attaching a 「데몬 강제 종료」 (force-quit daemon) button to the popup**★ — rejected on four overlapping grounds.
  - **(a) The command to shut down gracefully structurally cannot get through** — to send `AgentCommand::StopDaemon`, authentication must be passed, and **a version mismatch is rejected exactly there.** Discovery's `stop_with_sender` writes that fact down as it is and treats `VersionMismatch` as `NoTarget` (measured — `crates/engram-dashboard-discovery/src/lib.rs`).
  - **(b) The only remaining means is forced termination, and its cost is large** — the agents that daemon was holding go down with it. They are restored by session identifier, but **output in progress is cut.**
  - **(c) Since it cannot attach, it cannot even see the list of what is running** — the reason ADR-0158 decision 3 gave for banning automatic kill (「무엇이 돌고 있는지 모른 채 죽이면 안 된다」 (you must not kill it without knowing what is running)) **holds in its worst form here.**
  - **(d) This combination itself is rare** (user judgment) — the app and the daemon ship in the same deliverable, so we do not dig deep. ★**But the exact fact behind (d) is written down separately**★: the cause of the mismatch is **not the deployment unit but the old daemon not dying and surviving** (ADR-0158 맥락 already writes it that way — 「갈리는 원인은 배포 단위가 아니라 데몬의 수명」 (the cause of the split is not the deployment unit but the daemon's lifetime)). The fact that deployment is one lump **does not prevent** this combination.
- **Every notification as a popup** — ADR-0158's rejected alternative already refuted it: **over-notification raises the warning-ignore rate and in the end the user turns off the app's notifications altogether.** That rejection stays valid in this ADR as well.
- **Building the popup as a warning-only component** — the user stated explicitly that a **content popup** will be needed later. Building it dedicated means **building the foundation twice.**
- **The daemon gives the reconnect count** — ★**a value to use when it cannot attach cannot be received from a peer it cannot attach to**★. On top of that, **before the first connection there is nowhere to ask at all.** If the daemon gave it, it would become 「한 번 붙었을 때 받아 두는 값」 (a value received and kept once attached), which **does not apply to a user starting up for the first time.**
- **Keeping 5 reconnects** — since the popup gets a reconnect button, **the loss from being short is small.** The user can press again after 3.5 seconds.

## 근거

- ★**A correction to ADR-0158 decision 3 — this ADR is not an exception to that clause**★. What that clause forbids is 「**자동** kill」 (**automatic** kill) (original: 「데몬을 **자동으로** 죽이지 않는다」, and the invariant is also 「데몬을 **자동으로** 죽이는 경로를 만들지 않는다」). **The user pressing a button to kill is not caught by that clause.** ADR-0178 wrote down the same judgment (「팝업의 버튼을 사용자가 눌러 동의하는 형태는 그 금지의 취지와 어긋나지 않는다」). Therefore the reasons for rejection in decision 6 above are **(a) to (d), not 「금지돼 있어서」 (because it is forbidden).** ★**The previous session's handoff memo wrongly wrote this as a 「금지 경로」 (forbidden path) — that misreading is cut off here.**★
- ★**The reason a popup is dangerous is not that it is 「처음 덮는 것」 (the first to cover) but that it is 「알림이 덮는 것」 (notifications covering the screen)**★ — covering surfaces already exist (the context menu and native dialog in 맥락). Those two are **something the user just called up**, so they close themselves, but a notification **appears without the user calling it.** The incident for which `ConnectionNotice.tsx:10` (the version before `9318b5c`) nailed down 「덮지 않는다」 was exactly that kind — a strip nobody called hid the TabBar and blocked operation, and when the reason did not clear it blocked permanently. **So the eligibility criterion (decision 2) is the device that sets the scope of that exception** — without a criterion, everything 「중요해 보이는 것」 (that looks important) flows to the covering side, and at that moment the operations that were blocked are blocked again. (ADR-0134 decision 4 is the **reason that component exists**, and the sentence 「덮지 않는다」 itself was not in that ADR's body but in this file's header (the version before `9318b5c`) — ★do not confuse the citation sources★.)
- ★**One false measurement of ADR-0178 is corrected here**★ — the last item of that ADR's 「거부한 대안」 (the client automatically kills the old daemon and starts a new one) gave as reason ② 「**「그만 꺼져라」에 해당하는 프로토콜 명령이 없다**(실측 2026-09-04 — Shutdown·Restart·Quit variant 0)」. **It is false** — `AgentCommand::StopDaemon { force, kill_agents, request_id }` exists (`crates/engram-dashboard-protocol/src/messages.rs:89`, whose comment says 「데몬 종료(§5 LLM 제어)」), discovery's `build_stop_command` (`.../discovery/src/lib.rs:772`) builds it, and the shell calls it in `src/api/daemonControl.ts`. **The error is reading the literally true fact that there are 0 variants with those names as 「그런 명령이 없다」 (there is no such command).** ★**But the conclusion of that rejection does not change**★ — (a) above is the reason, and this ADR confirmed it in the real code: even **if** the command exists, it **cannot get through authentication to reach** a version-mismatched daemon. The correction stamp was put into the body of ADR-0178 (2026-09-06).
- **The basis of 3 is the sum of 「짧아진 대기 + 사용자 손에 쥐어진 재시도」 (a shorter wait + a retry placed in the user's hands)** — in exchange for cutting 5 attempts and 15.5 seconds to 3 attempts and 3.5 seconds, a popup appears when the budget is exhausted and a retry is possible from there. ★**The current code has no place for that retry**★ (measured — no 「다시 연결」 UI), and that is the premise that makes this exchange hold.

## 영향 / 불변식

- ★**The popup eligibility criterion (decision 2) is the only wall for 「알림이 덮는 것」 (notifications covering the screen)**★ — neither the compiler nor a gate guards it. When attaching a new notification, split it by one question: **「사용자가 행동하지 않으면 영영 복구되지 않는가」** (does it never recover unless the user acts). If not, it is a strip. ★**(2026-10-06 amendment mark) Two exceptions — the status-file guidance (ADR-0276) and the connection strip (ADR-0277 — main · popout · tree windows) are not popup-eligible yet cover the layout (both user decisions). Other notifications stay behind this wall as is**★. ★So among the non-popup notifications that exist now none remains in the flow, and the distinction that separated strip from popup by 「덮느냐」 (whether it covers) is gone — what remains of the split in decision 1 is 「알린다」 versus 「네가 눌러야 한다」. Here 「연결 띠」 (connection strip) is today's single `ConnectionNotice`, and whether the remaining connection events that decision 2 sent to the strip (a temporary disconnect · retrying · a loss notice · one command failing — ADR-0181 also puts the last on the strip) go into that covering layer too is open (not a decision — a user question · ADR-0277)★. ★(2026-10-08 mark) No longer an exception — non-popup notifications (strips) all stack in the covering layer, including the remaining connection events above (ADR-0287 decision 1 · user decision). Whether it is a strip or a popup is still decided by the eligibility of decision 2★. ★The 「알림이 덮는 것의 유일한 벽」 (the only wall for notifications covering the screen) in this item's head no longer separates whether it covers — the wall that keeps a covering strip from permanently blocking clicks is now ADR-0287 「영향 / 불변식」 (layer height = as much as the notification lines · a covering strip has a way to step aside) (read the 「기준이 없으면 전부 덮는 쪽으로 흐른다」 (without a criterion everything flows to the covering side) in 「근거」 above as the same place)★
- ★**The condition for breaking is not 「crate 안에 3 이 있는 것」 (3 being inside the crate) but 「셸이 그것을 덮을 수 없게 되는 것」 (the shell becoming unable to override it)**★ — ADR-0177 decision 4 wrote that policy values have **crate defaults and the consumer overrides them**, so a crate-side default of 3 is not a violation but **the contract as is**. The violation is the injection path disappearing so that the value becomes **fixed**.
- ★**To change the reconnect cap, look at two places together**★ — `connection.rs:77` and `wsTransport.ts:352` each hold the same name and the same value, and 「5회」 is embedded **in prose too** in two places (`agentClient.ts:132` · `daemonControl.ts:92`). If only one place is lowered to 3, **the two layers run with different budgets.**
- **Grow the notification surface but do not grow new global handles** — ADR-0158's invariant 「알림 표면은 새 전역 핸들을 늘리지 않고 기존 제어 표면에 얹는다」 (the notification surface rides on the existing control surface without adding a new global handle) was judged by ADR-0178 to be **still alive**, and this ADR continues it (CLAUDE.md 「LLM-우선 제어」). ★**But which surface the popup stands on was left undecided by ADR-0178 and this ADR does not decide it either**★.
- ★**Not verified**★:
  1. **It was not checked whether the client actually receives and reads the rejection-reason frame** — ADR-0178's unchecked item 1 is still alive as is. If it cannot read it, **decision 6's 「문구」 (phrase) does not hold** (only close remains).
  2. **Decision 5 is the *policy* answer to ADR-0178's unchecked item 2 (whether it reconnects endlessly after rejection)** — it does not use the count and stops at the first rejection. ★**How the current code actually runs was not checked**★.
  3. **What changing the reconnect constant from 5 to 3 shakes elsewhere was not counted** — the four places where the cap lives are written above (two constants, two prose), but **which flow gives up first when that value is lowered was not measured.**
- ★**The decider is the shell, not the crate**★ (for whoever builds decision 8 to see). 「앱 전체」 (the whole app) is **a concept of the screen** and `transport` **only counts peers and does not know the app.** The crate provides only two inputs — **the registry lookup** (`Registry::peers()`) and **「지금 다시 해라」** (`Peer::reconnect_now()`). ★**The shell folds those two to decide**★. Canonical = the end of `docs/process/S21-transport-crate/trd.md` §5. **If 「전부 잃었나」 (have all been lost) is put inside the crate, at that moment the crate comes to know the app** (a violation on the same axis as ADR-0129's vocabulary isolation).
- **Peers do not share state with each other** — even if daemon A is in the given-up state, B is alive (TRD §5). Decision 8 is a rule where the shell **folds and looks at those independent states**, not a meaning to bind the peers' states into one.
