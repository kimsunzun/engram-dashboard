# ADR-0024: Daemon ownership, liveness detection, exit, and data location — self-owned detached + WS/lockfile liveness + re-adoption

- 상태: 확정 (2026-06-18, dashboard6 session — user decision + `/consult` three-way cross-check job `20260618-151957-consult-tray-daemon-topology`) · 부분 폐기 by ADR-0271 (single discovery source for the data-location implementation line) · 부분 폐기 by ADR-0025 (C3 UI ensure ban) · 부분 폐기 by ADR-0027 (data location and sharing)
- 관련: ADR-0023 (topology) · ADR-0021 (on-demand · no restart) · ADR-0001 (kill 2 verbs · JobObject) · ADR-0008 (sid control) · CLAUDE.md §5 · `docs/process/S13-tray-lifecycle/tray-topology-trd.md` · Amended by ADR-0271 (single discovery source for the data-location implementation line) · Amended by ADR-0025 (C3 UI ensure ban) · Amended by ADR-0027 (data location and sharing)
- Scope: who owns/spawns the daemon, how its life and death are detected, the full-exit order, and where runtime data is stored.

## 맥락
With three processes (ADR-0023), the daemon must "survive even if the UI/tray-host dies." For that, the daemon must not be anyone's dependent child, and we must decide liveness detection, exit, orphan reclaim, and data location.

## 결정 (C1~C4 + data)
- **C1 — self-owned, detached.** The daemon is nobody's OS child (in particular not of a JobObject `KILL_ON_JOB_CLOSE`). Whoever ensures it, the spawn is detached. A singleton lock (lockfile: PID · port · generation/nonce) guarantees existence — if it is alive, attach as a no-op. Orphan prevention is **idle self-shutdown** (zero connections ∧ zero agents lasting N seconds, the tmux model ADR-0021).
  - **★Correction (2026-06-21 dashboard11) — idle self-shutdown is not implemented and not decided★:** The above "orphan prevention is idle self-shutdown" was **a sketch, not a decision**, and it is not in the code. Today's orphan prevention is only the singleton lockfile stale check (C2, *at the next ensure*) — active auto-exit (the daemon self-exits after zero connections ∧ zero agents for N seconds) is not implemented. The `idle_timeout` in `daemon/ws.rs` (default 50s) cuts a half-open WS *connection*; it is not a daemon process exit (beware the confusion). Also, ADR-0021's body has no idle self-shutdown decision (the only decision there is "no auto-restart") — so the "tmux model ADR-0021" citation is inaccurate (a tmux server also dies on the last session's end, not on an idle timer). Active reclaim of a true orphan (a daemon that nobody reconnects to) is a **follow-up undecided task** (idle self-shutdown opt-in — handoff §4-④, awaiting a user decision in the lifecycle-policy PRD). Adopting it needs a new ADR.
- **C2 — liveness = WS connection liveness (primary) + lockfile rediscovery.** The WS heartbeat/exit event is the primary signal. When the tray-host/UI restarts, it rediscovers by lockfile{PID · port · generation}, and **checks PID alive · port responds · generation matches, and if stale, cleans up and does a fresh spawn**. Do not rely on a parent-child exit signal alone.
- **C3 — desired-state is owned by the owner (tray-host); the UI must not ensure directly.** ~~The UI only connects. On a connection failure it asks the owner to ensure (or the owner ensures at boot/command). Remove the daemon ensure from the current UI bootstrap.~~ **★Discarded (Superseded by ADR-0025)★** — "the UI is on but there is no daemon" contradicts the user's intent. The UI **keeps** the one boot daemon ensure (the daemon is a singleton, so ensure from both the tray-host and the UI is safe). The respawn-during-exit race is blocked by C4 alone. Details and rationale are in ADR-0025.
- **C4 — full exit order:** owner state=Stopping → block ensure/open/start → full_shutdown to the UI (reconnect=false, ensure=false) → daemon graceful drain (reject new commands → clean up PTY children [ADR-0001 causality] → remove lock → exit, forced via Job after an upper-bound timeout) → confirm daemon exit → UI exit → tray-host exit.
- **Data location:** `.engram-data/` (`.gitignore` done). daemon.json (token) · agents.json, etc. ~~embedded and daemon share it (the same folder).~~ **Kept persistent (not volatile).**
  - **★Data location / sharing partly discarded (Superseded by ADR-0027, 2026-06-21)★:** "embedded and daemon share it (the same folder)" + the "debug = repo root / release = next to the exe, converging" below are discarded. They are replaced by a per-mode split — **embedded = the run folder's `.engram-data` (folder-local), daemon = release uses `%APPDATA%` (user-global), dev unified on the run folder.** Agents are not shared across modes. Details and rationale are in ADR-0027. (The rest of this ADR — C1 detached/breakaway · C2 liveness · C4 exit order · token policy, etc. — remains valid.)
  - **Implementation (fixed 2026-06-19 dashboard7, sub-step 2):** instead of path injection (the launcher passes `--data-dir`), **each process self-resolves** (`engram_dashboard_discovery::default_data_dir()`, a single source). Priority: ① `ENGRAM_DATA_DIR` override > ② **debug** = go up from `current_exe` to the repo root (`.git`/`[workspace]`)'s `.engram-data/` > ③ **release** = `.engram-data/` next to the exe folder > cwd fallback. The three exes (daemon/embedded/tray-host) converge on the same folder in the same build mode (invariant). Why injection is not used: all exes are co-located in `target/<profile>/`, so self-resolve is simpler and has zero injection wiring.
  - **The real purpose of `ENGRAM_DATA_DIR` = a test-isolation escape hatch** (not a deployment knob). Only a directly spawned (`std::process::Command`) daemon inherits it — a WMI-spawned daemon does not inherit env, so it has no effect (WMI tests are isolated with the default path + backup/restore).
  - **At deployment, the data location moves to appdata later (memo, undecided).** The reason it is the local `.engram-data/` now: during development, repo-level isolation so as not to dirty someone else's (a teammate's) appdata. The appdata move is a separate decision at the proper deployment (installer) stage.
- **Control "permission" model:** cooperative control = authenticated by a token the daemon issues in the lockfile (graceful StopDaemon, etc.). Forced = taskkill fallback (orphan risk, fallback only). The daemon WS binds to `127.0.0.1` (local only) — zero external exposure.

## 거부한 대안
- **The daemon = a child process of the tray-host/app + detection by OS wait (no polling needed)** — proposed by Gemini, rejected by the judge. **It contradicts detached survival**: if put in a JobObject KILL_ON_JOB_CLOSE, the daemon dies when the parent dies (survival violated). If not put in, the parent handle is cut when the tray-host restarts and lockfile rediscovery is needed anyway — "no polling needed" is false except on the happy path.
- **The UI spawns the daemon directly (current behavior)** — multiple-ensure race + ambiguity between orphan and intended daemon + respawn during exit. Replaced by C3.
- **embedded fully volatile (zero files)** — considered once, but the user rejected it (wants restore kept). embedded is persistent too.
- **Data = keep %APPDATA%\com.engram.dashboard** — right for a proper app (write permission · survives updates), but engram plans no installer + I:\ is a fixed writable drive, so a co-located internal folder is more visible and easier to manage. Go with `.engram-data/`.

## 근거
- The `/consult` blind judge: pulled out the C1/C2 "detached ↔ child-owned contradiction" as the key point; Claude's proposal (self-owned + WS liveness) is the most coherent, merged with the rediscovery robustness of GPT's proposal (generation/nonce · stale lock · race coverage). C4 exit order and respawn-race blocking are agreed by GPT/Claude (preventing a recurrence of the reason auto-restart was discarded).
- Forced-exit coverage (TRD §5b): tray-host kill → daemon survives → rerun re-adopts / idle self-clean / stale lock check = preventing unmanageable zombies like Discord's. **(※ Of these, idle self-clean is not implemented — see the C1 correction. The current effective set = re-adoption + the stale lock check.)**

## 영향 / 불변식
- Daemon spawn code **never puts the daemon in a kill-on-close Job** (C1). If violated, the daemon dies along with the parent = survival broken.
- Exit goes in the order **graceful command → confirm daemon death → forced fallback** (C4). No fire-and-forget (zombies).
- The token lives only in the lockfile, never in logs (the existing convention kept). The WS stays loopback-bound. Remote exposure is a future separate security task (security is first-class, security review required).
- `.engram-data/` must not be committed to git (registered in `.gitignore`).
