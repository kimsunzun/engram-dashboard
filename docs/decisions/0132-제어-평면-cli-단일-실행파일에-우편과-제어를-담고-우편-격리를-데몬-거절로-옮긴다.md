# ADR-0132: Control-plane CLI — put mail and control in a single executable and move mail isolation to a daemon rejection

- 상태: 확정 (2026-08-11, basis: user decision + 3 code measurements — see the basis below) · 부분 폐기 by ADR-0220 (the group-help discovery path)
- 관련: **execution form = ADR-0133**(the decision that actually implements decisions 3 and 5 — the daemon rejection gate and the all-agents wiring stand there) · Amends ADR-0128 (the constraint banning mail verbs in the control CLI) · ADR-0086(dual typed entrance — the origin of the CLI entrance · least-privilege default) · ADR-0094(bare-name grant · PATH injection) · ADR-0099(capability switch) · ADR-0126(abolishing CLI-bypass teaching) · ADR-0081(UI relay — not implemented) · ADR-0119(agent vocabulary) · `src-tauri/src/cli.rs`(the CLI mode to be removed) · `crates/engram-dashboard-daemon/src/bin/engram.rs`(to be renamed and extended) · `crates/engram-dashboard-core/src/agent/backend/claude.rs`(env · PATH injection) · step-log S19 · Amended by ADR-0220 (the group-help discovery path)

## 맥락

When ADR-0128 hard-unified the mail channel as a capability, it **left the channel of the control plane (spawn and so on) open**. The user's tentative direction was "CLI wherever possible", and this time it was confirmed as is — control is low-frequency, so there is no reason to keep the MCP tool schema resident in every agent's context.

Three things came to light at the start.

- **A control CLI surface already exists.** `src-tauri/src/cli.rs` already provides 4 verbs, `list`/`send`/`spawn`/`kill`, by doubling the release exe as the daemon control CLI (it reads daemon.json and connects straight over WS). If a new one were built, there would be two entrances doing the same job.
- **That `send` is not mail.** It is a key input that injects text into the target's stdin, so it has the same name as mail `send` but a different meaning.
- **The isolation means of ADR-0128 is incompatible with a single executable.** The isolation right now is "do not install `engram-send` at all for an MCP-capable spawn" (the PATH and env injection in `claude.rs` is for non-MCP spawns only), but if the control CLI is made a sibling binary and its parent directory is added to PATH, the mail CLI comes back to life under its bare name. PATH is a permission at the **directory level**, not the file level.

## 결정

1. **Unify the entrance.** The control-plane CLI is gathered into a single separate executable (`engram`). The CLI-doubling mode of `src-tauri/src/cli.rs` is **removed**, and its 4 verbs move to the new executable. The text-injection verb collides with mail `send`, so it is renamed.
2. **Mail and control go in one executable.** `engram-send` is renamed to `engram` and extended to carry the mail verbs and the control verbs together. Because there is only one executable, the problem of "exposing a sibling binary on PATH" itself disappears.
3. **Move the mail isolation means to a daemon rejection.** When a mail request arrives with the credential of an agent spawned with an MCP-capable backend, the **daemon rejects it**. Hiding the mail verbs from help is only a convenience laid on top of that, not enforcement. The channel unification of ADR-0128 (mail is split only by capability, no runtime switching or fallback) is kept as is — all that changes is **how it is enforced**.
4. **Discovery is group help.** Priming gets only one line, "if you need control, `engram help`", and does not enumerate the feature list. `engram help` gives the list of families, and `engram help <계열>` (family) gives the usage of that family (the CLI counterpart of MCP exposing its tool schema by itself).
5. **Control permission is open to all.** Every spawned agent can use the control verbs. Selective granting is opened by a separate decision when it becomes necessary.
6. **v1 scope = all of agent control.** All the verbs the daemon (`AgentManager`) already has — launch · rename · kill · list · create · delete · move in the hierarchy · put to sleep — are provided. The operating vocabulary uses agent vocabulary (ADR-0119: the word profile does not come out beyond the manager boundary).
7. **UI control and pixel control are separated into later steps in order.** ① **Functional** control of windows, tabs and slots (create · split · pull out) needs the daemon↔client relay (ADR-0081) laid first, so it is second ② control of **position and size** (pixels) has no concept at all in the app now and no layout disk persistence either, so it is third — it opens together with persistence when it becomes necessary.

## 거부한 대안

- **Extend the app executable's CLI-doubling mode** — it is cheap, with 0 new executables. But the name the agent types becomes the GUI app's name, and the constraint "if the first argument overlaps with a GUI argument, no window comes up" has to be managed permanently every time verbs grow. Unsuitable as a name for discovery.
- **Let the existing CLI and the new control CLI coexist** — nothing breaks right now. But there would be permanently two entrances doing the same job, so every fix to a verb has to be made in two places, and which one to teach the agent stays ambiguous.
- **Keep the control CLI as an executable separate from the mail CLI and separate the directories** (workaround ① noted in the ADR-0128 open item) — it does not touch the ADR-0128 constraint. But distribution and packaging grow to two directories, and discovery (help) splits into two as well.
- **Give up PATH injection and call only by absolute path + environment variable** (workaround ②) — the safest, but the agent's command line gets long and discoverability of the bare name drops. If a single executable is chosen, there is no sibling to be exposed in the first place, so the reason to pay this cost disappears.
- **Expose control as an MCP tool too** — the channel is unified with mail. But control is low-frequency while the tool schema is **permanently resident in every agent's context**. The reason mail is MCP (the volume going back and forth is large, so speed is a gain) does not apply to control.
- **Write the whole list of control commands in priming** — they would surely know. But every agent permanently pays the tokens for a list that it does not even use, priming has to be fixed every time verbs grow, and the longer it gets, the more the sentences that actually must be kept get buried.
- **Grant control permission selectively** — it fits least-privilege. But one more granting axis is added and the v1 scope grows. Openness can be narrowed later (by not teaching it or not installing it), but narrowing now makes v1 bigger.
- **Put UI functional control in v1 too** — it was within the scope the user requested. But measurement showed the relay is unimplemented (see the basis below), so it is not "just attaching an entrance to an existing thing" but laying wiring that does not exist. The CLI has to stand first for verbs to be put on it, so it comes later in order too.

## 근거

- **UI relay unimplemented (measured 2026-08-11).** `RegisterRole` · `UiApp` · `RelayUi` · `UiCommand` · `UiResult` all have 0 hits in `.rs` sources. `AuthFrame` has no role field, there is no relay arm in the `connection_core.rs` dispatch, and there is no inbound UI command handling in `src-tauri/src/daemon_client/`. `docs/reference/architecture-overview.md` also admits "the architecture is settled, and the code implementation is pending (diff 0)".
- **The daemon does not know the layout (measured).** `ViewManager` and `LayoutState` exist only in `src-tauri/src/layout/` and nowhere in all of `crates/`. The `AgentCommand`/`AgentEvent` vocabulary of protocol has no window, tab, or slot.
- **No coordinate concept (measured).** Of the 17 window, tab and slot verbs in `src-tauri/src/commands/layout.rs` and `popout.rs`, not one takes x/y/w/h. Pixel control is not adding an entrance but a new feature. The layout has no disk persistence either (in-memory — reset on client restart).
- **All agent control is in the daemon (measured).** `AgentManager` implements `create_agent` · `delete_agent` · `rename_agent` · `reparent_agent` · `spawn_agent` · `activate_profile` · `kill_agent` · `list_agents` and more, and the wire variants correspond. Name uniqueness and automatic suffixes already work (ADR-0119/0120/0123). The CLI is purely adding an entrance.
- **PATH exposure path confirmed (measured).** `ENGRAM_SEND_EXE` + the PATH prepend in `claude.rs` is called only for non-MCP (CLI-only) spawns — for an MCP-capable spawn the mail wiring is not installed at all (what ADR-0128 reflected). If merged into a single executable, this branch shifts from "what to install" to "what to allow".
- **Client-side hiding cannot be enforcement.** The party calling the CLI is the agent itself, so it can tamper with the command line and environment variables. That is why enforcement is placed in the daemon, which knows the credentials.

## 영향 / 불변식

- **Invariant (strengthened):** whether a mail verb is allowed is **decided by the daemon from the credential**. An implementation that depends on hiding or filtering on the CLI side is a violation — if it is breached, the channel unification of ADR-0128 collapses.
- **Invariant (kept):** the mail channel is split only by backend capability. No runtime switching or fallback (ADR-0128 decision 1 stays as is).
- The isolation **means** of ADR-0128 (not injecting mail wiring into an MCP-capable spawn) is replaced by this decision. Only that clause is partly discarded, and the body of the channel unification is valid.
- Removing `src-tauri/src/cli.rs` → the `is_cli_verb` branch and the leading decision in `main.rs` disappear with it. If there are external scripts that used those 4 verbs, they break.
- Renaming `engram-send` → the grant string (`Bash(engram-send:*)`) · the priming sentences · `ENGRAM_SEND_EXE` · the CLI process tests move together. The bare-name alignment invariant of ADR-0094 (the name taught = the name resolved through PATH) must be kept with the new name.
- **★Decision 1 narrowed — only two of the 4 verbs were ported, and the text injection did not get renamed but vanished (found in the review of piece ④, 2026-08-12)★:** Decision 1 wrote "its 4 verbs move to the new executable · the text-injection verb is renamed", but what was actually ported is **only `list` and `spawn`**. `kill` is covered by the decision 6 narrowing item below, and **the text-injection verb was not renamed and disappeared** — the `agent` family verbs of `engram` are five, list · spawn · new · rename · move, and the daemon endpoint has no corresponding verb either. `WriteStdin` remains only on the WS path, so its only real caller is the GUI. **The misreading this item is meant to prevent is a session that read only decision 1 looking for the "renamed injection verb", not finding it, and suspecting a regression that does not exist — or, the opposite, believing "it already exists" and not building it.**
- **★The "unified entrance" of decision 1 is not yet literal★:** `scripts/engram.mjs` keeps an **uncredentialed control surface** that connects straight from `daemon.json` → WS, and `run-dashboard-release.bat` points to it as the way to drive the release app. It is not in the distribution folder and calls itself a PoC, but its grammar is separate from `engram`, so **the "two entrances doing the same job" that decision 1 meant to prevent remain on this axis.** Its fate will be decided together with T-23's decision on human credentials.
- **★The gap sentence of the decision 6 narrowing is limited to the agent axis (corrected 2026-08-12)★:** "This gap closes the moment kill is opened" in the item below is **true only for agents**. Humans and scripts still cannot use `agent kill` even if it is opened — because the new CLI requires a per-agent credential, which humans do not have, and that is an axis unrelated to adding verbs. "If there are external scripts that used those 4 verbs, they break" in the same item also understates the size of the loss (there is no replacement at all). Source of truth = T-23.
- **★Decision 6 narrowed — put to sleep (kill) and delete (rm) dropped out of v1 (user decision 2026-08-11)★:** Decision 6 wrote "all the verbs the daemon has", but piece ② provided only **five — launch · rename · list · create · move in the hierarchy**. The reason for leaving out those two is **that their meanings are tangled with each other** — right now `delete_agent` deletes only the registry entry and **leaves the running process alive** (a ghost that is alive although gone from the registry). This conflicts with ADR-0122's "removing from the tree ends the life", an ADR that has put off its implementation time. In the days when it could only be done from the screen, a person saw it with their own eyes, but **if opened through the CLI, an agent will carelessly create ghosts.** Patching it with a guard at the entrance is a stopgap, so it was put off to **a dedicated step that settles the meaning and then opens both together.**
  - **The gap that arises meanwhile (intentional, recorded):** an agent **can launch but cannot stop through the CLI.** So when it hits the runaway cap (below), the only recovery path is the screen, and only for that stretch 「LLM-우선 제어」 is half-done. **This gap closes the moment kill is opened** — kill itself is already a fully defined operation (the profile stays and only the session ends) and has nothing to do with delete semantics. That is, the real reason for postponing is the rm side, and kill was tied in only to keep the pair together.
- **Known accepted risk 2 — grant prefix expansion (user decision 2026-08-11: accepted, not narrowed now):** with the shorter name, the **prefix matching** of `Bash(engram:*)` covers sibling executables too — `engram-dashboard` (`spawn` and `kill` remain in the old CLI mode) and `engram-dashboard-daemon`. Through distribution-folder co-location + the PATH prepend, bare-name resolution actually happens. The old name `engram-send` was long and caught only itself. **Why it is harmless now:** `--permission-mode bypassPermissions` is injected **unconditionally** (ADR-0097), so the grant itself is a NO-OP. **Why it was not narrowed:** the gain is unobservable (a list nobody looks at), narrowing by family requires first measuring whether the grant matcher allows a space in the prefix (unconfirmed — no speculative fixes, ADR-0038), and the most dangerous sibling disappears with the removal of `src-tauri/src/cli.rs` in decision 1. **The trigger to re-examine = the day that base flag is taken away** (claude.rs has already nailed down auto mode as a "transitional regime, the formal replacement is a constraint layer shared by all LLMs" — that work also opens this item). **1 unconfirmed item:** if a profile's `extra_args` specifies `--permission-mode` again, which side wins has not been verified (no such profile now).
- **Known accepted risk:** with control open to all, a single prompt-injected agent can kill its siblings or spawn without limit. T-11 (per-child permission scope) is already a deferred item on the same axis, and this decision widens that risk surface.
- **Tension with ADR-0086 — judged not to stamp it (2026-08-11):** that ADR's "expose only send_message to workers (least-privilege default)" speaks, by its wording, of the **range of MCP tool exposure**, and this decision is on the **CLI axis**, so they do not conflict directly. Moreover ADR-0086 itself already planned the later addition of control verbs, saying "this scope = send only, spawn/window moves and so on come **additively later**". Still, it is a fact that "open to all" is at odds with the least-privilege **tone** of that ADR, so it is left here. There are three reasons the partial-discard stamp was not put: ① it is a tension of tone, not a conflict of wording, so no clause can be specified ② the doc-aware adversarial reviewer, who held all the grounds of the decision, did not raise this tension as a defect ③ ADR-0086 already has one `Amended by`, and putting in a second would step again on the known defect (recurred 8 times) in which `adr.mjs index --write` quietly erases it from the index cell. **If this judgment was wrong, the symptom is** — a session that read only ADR-0086 trying to undo the control CLI exposure on the grounds of least-privilege. In that case, stamp it formally with this item as the basis.
- **Order of follow-ups (fixed by this ADR):** ① agent control CLI (this one) → ② functional control of windows, tabs, slots (ADR-0081 relay implementation first) → ③ position and size control (layout persistence first).
