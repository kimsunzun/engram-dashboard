# ADR-0300: The window number is the smallest number that no live window uses — the layout model holds it, releases it when the OS window is gone, and stores it together with the persistent id

- 상태: 확정 (2026-10-26, 근거: user decision 2026-10-17 (R1 — reuse the smallest free number · R2 — the label stays monotonic) · 2026-10-23 (Q3 — every window gets a number · main = always 1 · the place of the number marker · title shape / Q8 — store with the persistent id / review round 1 point ① — brief overlap during restore accepted) + main-agent decisions M1 · M2 · M3 · M24 (TRD §12-3) + PRD defaults (main-agent proposal — the restore side of D2 · the repair rule of D3 · D13 · R29) + implementation U1 `4cefce48` · U2 `f27de03c` · U8a `982e07a8` (number marker))
- 관련: PRD `docs/process/S21-window-chrome/prd.md` (edition 0.5 — R1 · R2 · R3 · R24 · R29 · D1 · D2 · D3 · D13 · W7 · W12 · AC1 · AC20 · AC25 · AC31 · AC38) · TRD `docs/process/S26-window-chrome/trd.md` (edition 0.3 — §2-4 invariant 1 · §3-3 · §3-4 · §4-1 · §5-6 · §5-7 · §7-3 · §12-3) · survey `docs/research/window-identity-display-2026-10-23.md` (Q3) · ADR-0299 (prewarmed window — it does not hold a number) · ADR-0301 (how to apply the OS title) · ADR-0302 (window arguments do not take the number) · ADR-0303 (the title row where the number marker stands) · ADR-0305 (failure before the first screen — why the D13 exception changed) · `src-tauri/src/layout/numbering.rs` · `src-tauri/src/layout/manager.rs` · `src-tauri/src/state/codec.rs` · step-log S26 · tracking T-66

## 맥락

A popout window's title was 「Engram — slot-popup-11」 — the window label is a monotonic counter, so the number does not come back when a window is closed, and that was visible to people (PRD §1 · code). The main window and a popout also looked the same (the user 2026-10-20 「똑같으니깐 뭐가 메인인지 모르겠네」 — tracking T-66 「창 구분」). If the OS title bar is removed (ADR-0303), there is nothing inside a window to tell windows apart, and the Windows 11 taskbar hides the button text by default (PRD Q3).

A person wants to say 「2번 창」, and the LLM must refer to a window by an id that is never reused (Q9 — ADR-0302). So a small number visible to people had to be kept separate from the label, and the lifetime · owner · storage of that number had to be decided.

## 결정

1. **The number of a new window = the smallest number that the live windows do not use** (user decision 2026-10-17 — R1). If 2 is closed out of 1 · 2 · 3, the next new window = 2. **Every window has a number and the main window is always 1** (user decision 2026-10-23 — Q3 · D1). **The number of a live window does not change** — when an earlier-numbered window closes, the others are not renumbered forward, and it stays the same across a restart (D2 · user decision 2026-10-23 — Q8). The internal label is monotonic as now and separate from the number (user decision 2026-10-17 — R2).
   - 「살아 있는 창」 = a window in the model (including hidden and minimized windows) **+ a closing window that has left the model but whose OS window is not yet gone** (D13 · PRD R1 — default, main-agent proposal).
   - A hidden prewarmed window is outside the model, so it does not hold a number — it receives one the moment it is taken over and enters the model, and if it is handed back it goes back without a number (PRD R1 · D13 — default, main-agent proposal · ADR-0299). A window withdrawn because opening failed or insertion was rejected never held a number.
2. **The owner of the number = the layout model** (main-agent decision M1) — the window entry field `WindowTabs.number` of `ViewManager` · the closing-window table `closing` · the pure calculation module `layout/numbering.rs` (`smallest_free` · `resolve_saved`). The number is received inside the same lock that inserts the window entry, so two windows made at the same time do not receive the same number. The paths that insert and remove go only through two private methods (`insert_window_entry` · `retire_window_entry(label, Os::{Alive, Gone})`) (TRD §2-4 invariant 1).
3. **The number is released when the OS window is really gone (`Destroyed`)** (D13 — left by main-agent decision M2). The paths that remove from the model (`window.close` · a close request · closing the last tab · self-closing at 0 tabs) hold the number in `closing` until then.
   - **A window whose OS window is already gone** (a boot-restore popout that could not be opened · a window that disappeared before the swap after a copy was accepted) is released at once without passing through `closing` — `drop_window_gone` (main-agent decision M24 · PRD D13 exception — default, main-agent proposal 2026-10-24).
   - If the `Destroyed` cleanup cannot run because any one of the four (`LayoutState` · the router · the channel registry · the daemon client) is missing, `release_window_number` is called on `LayoutState` alone to release it (TRD §4-1 · U2 review).
   - If `Destroyed` never comes, that number stays held until the end of the run — accepted (W7).
4. **Store the number in the screen state together with the persistent id and restore it at boot and at crash-copy acceptance** (user decision 2026-10-23 — Q8). An optional field `number` on the window entry of `shell\state\state.json` (writing is always a value · `STATE_VERSION` stays 1). Reading is lenient — only an integer `1..=999` is used (the upper bound = main-agent decision M3), any other value is none + a warning, and ★the window is not skipped★. Repair rule (D3 — default, main-agent proposal): main = always 1 (the stored value is not looked at) · a 1 written by a popout = none · if two or more wrote the same number, only the first in storage order keeps it · **the window that already holds it wins** (the restored window steps aside) · after all the valid numbers are set up first, the windows with none receive, in storage order, the smallest free number. Copy acceptance (`adopt_restored`) releases all the numbers of the old popouts (including those closing) and sets up the copy's numbers. The tab name · 「정한 이름인가」 · the persistent id · the number go into one snapshot (R29 — default, main-agent proposal).
5. **Where it is visible** (user decision 2026-10-23 — Q3): the number marker at the **right end of the tab row in the title row · right next to the window buttons, on its left** (number only · always · 「1」 even when there is one window · tabs shrink first and the marker stays · a draggable spot — ADR-0303) + the OS title 「<탭 이름> - Engram:<n>」 (how it is applied = ADR-0301) + `details[].number` of `window.list` (ADR-0302). When the number has two or three digits the marker widens accordingly and the number is not cut (R24 · AC38 — default, main-agent proposal).
6. **A brief moment when the same number shows on two windows during restore or copy acceptance is accepted** (user decision 2026-10-23 — 「어차피 잠깐 보이는거니 노상관」 · W12). The order of copy acceptance (show the copy window, then withdraw the old window) is not changed. What is prevented is only the overlap that remains after a closing window is gone (D3 · AC31).

## 거부한 대안

- **Do not store the number and renumber at every boot, starting from main in storage order** (PRD Q8 ② · edition 0.1 D3) — if you quit with 1 · 3, it starts as 1 · 2 and 「3번 창」 becomes 2. Rejected = user decision 2026-10-23 (Q8 ①).
- **Release the number when leaving the model, and hide the closing window first** (the rejected branch of PRD D13) — that the hide call returned is not an OS confirmation that it disappeared from the screen, so failure and lateness must be handled separately, and the hide must be inserted into every closing path (a close request · the direct destroy of `window.close` · the withdrawal of copy acceptance). PRD edition 0.2, which released 「모델에서 빠질 때」 without hiding, showed two windows with the same number (PRD round 2 review BLOCK). Strength of rejection = review (BLOCK) + description.
- **Remove D13 (holding the number of a closing window)** — the PRD left it that if the TRD finds it expensive it may be removed without a new user decision (it falls under the brief overlaps the user accepted). If removed, after an ordinary close the new window briefly shows the same number as the closing window, and AC20 ② has to be removed. What is kept costs one table in the model + two private insert/remove methods + one line in the `Destroyed` cleanup (main-agent decision M2 · TRD §4-1). Strength of rejection = description (cost calculation).
- **Hold a number in advance when the prewarmed window is built** (the other branch of PRD D13) — that number is blocked until it is taken over, and meanwhile, even if an earlier number becomes free, the prewarmed window comes out with the number it holds (main · 2 · prewarmed window 3: close 2 and open a new window and it is 3), which conflicts with 「살아 있는 창이 쓰지 않는 가장 작은 번호」 (user decision 2026-10-17) — numbering again at takeover makes it the same as this decision. Strength of rejection = conflict with the user-decided rule.
- **Make restore wait so the number frees only after `Destroyed`** (the rule that PRD review round 1 point ① raised) — the user accepted the brief overlap (「어차피 잠깐 보이는거니 노상관」). Commands refer to a window by the persistent id, not the number, so the overlap has no effect (Q9). Rejected = user decision 2026-10-23.
- **Remove a window whose OS window is already gone through the ordinary close (`close_window` → `closing`) too** (TRD edition 0.1) — that window's `Destroyed` has already passed or will not come, so the number stays held until the end of the run (TRD review Claude ⑥). Strength of rejection = code.
- **Other places to show the number** (the branches of PRD Q3 · the old main-agent proposal) — ① a marker at the left end of the tab bar + a number at the end of the title only when there are two or more windows: when the window count changes between 1 ↔ 2, the width available to tabs fluctuates · ② always show the marker: the adopted shape follows this 「늘」 but the place is the right, not the left (cost = 「1」 even with one window — accepted) · ③ only in the OS title (main = no number · edition 0.1 recommendation): it is not visible inside the window · ④ not shown (`window.list` only): people have no basis to say 「2번 창」 · the old main-agent proposal (「Engram N」 only when there are no tabs): the main window always keeps one empty tab and a popout closes when its tabs reach 0, so the number is practically never seen. Rejected = user decision 2026-10-23 (Q3).
- **A marker that decorates only the main window (color · badge)** — we found no peer that decorates the main window with a color or badge, and apps that have a main window tell windows apart by function or lifetime (survey identity conclusion 5 · PRD R24 — default, main-agent proposal). Telling main apart is filled by number 1 + the meaning of the main ✕ (ADR-0303). Strength of rejection = survey (no peer).

## 영향 / 불변식

- **Number calculation is done only inside `ViewManager` methods** (TRD §2-4 invariant 1) — do not write new code that directly `insert`s or `remove`s on the `windows` field (that field is `pub` only for tests and the read of the persistence conversion). If violated, `closing` and the set of live numbers diverge, so the same number goes to two windows or a number leaks.
- `closing` is not persisted. `window.list` does not list a closing window, so during that moment a number absent from `window.list` may not be free (if the closing 2 of 1 · 2 · 3 is still there, the new window = 4) — the help text says so (the cost of D13).
- The number is for conversation with people — it is not accepted as a window argument of commands (ADR-0302 · Q9).
- If you go back down to an older build, the number field disappears and at the next boot of this edition the windows are renumbered from main in storage order — accepted (storage TRD §12 R3 · TRD §3-3).
- A new window that appeared first within the first-paint time limit may not have the number marker yet (ADR-0305).
- Anchors — put `// ADR-0300` on `layout/numbering.rs` · the insert and remove private methods of `ViewManager` · `release_closing` · `drop_window_gone` · the lenient read of the stored number.
