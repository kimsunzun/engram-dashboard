# ADR-0307: LLM 명령 규칙 — 명령은 한 호출, 조회는 영역별로 바로 출력

- 상태: 확정 (2026-10-26, 근거: 사용자 대화 결정 · 조사 2 건)
- 관련: CLAUDE.md 「LLM-우선 제어」 · 정설 `docs/reference/llm-command-conventions.md` · 조사 `docs/research/llm-command-design-query-vs-action-2026-10-26.md` · `docs/research/pane-positional-addressing-2026-10-26.md` · ADR-0068(공간 지목 = 논리 핸들) · ADR-0132(이름 해석기 하나) · ADR-0285(CLI = 인증 + 배송) · ADR-0302(창 인자 번호 거부) · step-log S27 · tracking T-65

## 맥락
LLM 이 버스 · `engram` CLI 로 부르는 명령을 늘리기 전(첫 소비자 = T-65 슬롯 도킹 LLM 명령)에 공용 규칙을 세운다. 사용자 기준 = 「LLM 시나리오는 여러 번 거치지 않아야 실수가 적다」 · 호출 수와 컨텍스트에 싣는 양을 둘 다 줄인다. 지금 레이아웃 명령은 불투명 id 로만 대상을 받아 흔한 요청이 조회 + 명령 2~3 호출이 된다(예: `slot.focus` 는 먼저 `slot.resolveSpatial` · `slot.assignAgent` 는 `agent.list` 와 칸 id 조회). 사용자가 함께 물었다 — 조회 결과를 컨텍스트에 다 싣나, 밖(파일)으로 내고 bash 로 찾게 하나.

## 결정
규칙의 정본은 `docs/reference/llm-command-conventions.md` 이고 이 ADR 은 그 *왜* 를 남긴다.

1. **명령(쓰기) = 시나리오 하나에 한 호출.** 여러 단계는 명령 안에서 한다.
2. **대상은 LLM 이 이미 아는 말로 받는다** — 에이전트 이름 · 공간 낱말 · id. 명령이 안에서 id 로 푼다. 모호하거나 없으면 오류로 멈추고 후보를 싣는다. 말의 종류마다 인자를 따로 둔다(한 인자에 섞으면 이름 「left」 같은 것이 낱말과 부딪힌다 — 메인 결정).
3. **에이전트 이름은 데몬 명부의 해석기 하나로 푼다**(`resolve_in` 의미 — ADR-0132 의 「해석기 하나」를 따른다). 셸의 id→이름 캐시로 따로 풀지 않는다 — 그 캐시는 항목을 지우지 않아 죽은 에이전트 이름이 풀리고 중복 판정이 데몬과 갈린다(메인 결정 · 리뷰 지적).
4. **배치를 바꾼 명령의 응답에 바뀐 뒤의 배치를 싣는다** — LLM 이 결과를 추론하지 않게(사용자: 「결과를 콜백해주는것도 좋겠지」).
5. **조회(읽기) = 영역마다 하나 + 필터 인자, 결과는 컨텍스트에 바로 출력.** 부를 말을 모를 때만 조회한다.
6. **크면 파일로 넘기는 공용 안전장치 하나를 둔다 — 자리는 미정.** CLI 에 두면 ADR-0285 결정 1(CLI = 인증 + 배송 · 사용자 결정 2026-10-08)과 부딪히고, 파일을 쓸 데이터 위치도 사용자 결정이다. 자리 · 문턱은 구현 전에 정한다.
7. **명령 세부(이름 · 인자 · 응답 문구)와 출력 형식(텍스트 · JSON)은 메인이 LLM 이 잘 쓰는 쪽으로 정하고 보고한다**(사용자 위임: 「이건 llm인 너가 잘 아니 잘 지시되는쪽으로 알아서 하면 될듯」).
8. **칸은 에이전트 이름 · 공간 낱말로 부르고, 지금은 칸 번호로 지목하지 않는다**(사용자 결정 2026-10-26 — 「그거 그냥 일단 이름으로해」). 이름이 겹치는 지금의 결함(tracking T-45)은 오류 + 후보로 멈추고, 이름 → 내부 고유 id 전환(T-29 · T-45 — 사용자: 「데몬 이름은 내부에 고유 id로 할거임」)이 끝나면 사라진다. 번호 지목은 화면 칸 번호 표시를 설계할 때 다시 본다.

## 거부한 대안
- **열 · 행 좌표로 칸 지정(「x1 y2」 — 사용자 제안)** — 칸 배치가 격자가 아니라 분할 트리라 열마다 행 경계가 달라 「행 2」가 애매하다(코드 사실 — `src-tauri/src/layout/spatial.rs` 는 사각형 트리에서 위치를 파생한다). 조사한 도구(tmux · i3 · WezTerm · ace-window) 중 열 · 행 좌표로 지정하는 곳이 없었다(tmux 칸 번호 = 만든 순서 · 공간 토큰 = 모서리 · 가장자리 · 이웃 — 원문 확인). 사용자 수락 2026-10-26(조사 결과를 보고 「저게 지금 tmux 터미널 방식」 확인 뒤 번호 쪽으로 넘어감). 기각 강도 = 조사 + 코드.
- **조회 결과를 늘 파일로 내고 bash(grep · 부분 읽기)로 찾게 하기** — 영역 하나의 결과가 작다(아래 「근거」의 어림). 파일로 넘기는 선례의 문턱(LangChain Deep Agents 20,000 토큰)에 한참 못 미친다. 파일 + 검색은 호출을 늘리고(조회 + 찾기 ≥ 2), 찾을 말을 알면 핀포인트 조회가 한 번에 끝내며, 모르면 어차피 전체를 읽어야 한다. 큰 경우는 결정 6 의 안전장치가 덮는다. 사용자 수락 2026-10-26(「ㅇㅇ 알았어 일단 그렇게 조회하고」). 기각 강도 = 정량 어림.
- **칸 번호로 지목하기(화면 위치 순 번호 · 응답으로 최신 번호 받기) — 지금은 하지 않음** — ① 창 인자가 번호를 거부한 까닭(ADR-0302 결정 9 · 늦게 온 명령이 새로 생긴 같은 번호를 친다)이 칸 번호에 더 세게 걸린다 ② 코드의 순번은 칸 중심점 높이를 허용오차 없이 비교해 크기 조절만으로도 바뀐다(`src-tauri/src/layout/spatial.rs` · ADR-0068 결정 1 의 한계). 이름으로 충분하다. 기각 강도 = 코드 + 사용자 결정(결정 8).
- **묶음 실행(명령 목록 한 번에) · 스크립트 시스템 — 지금은 만들지 않음** — 시나리오마다 명령 하나로 흔한 요청이 한 호출로 끝나므로 쓸 곳이 아직 없다. 스크립트(변수 · 조건 · 반복)는 우리 규모에 과하다. 같은 두세 호출이 실제로 반복되면 그 시나리오를 명령 하나로 만들고, 그래도 모자랄 때 묶음을 다시 꺼낸다. 기각 강도 = 사용자 결정(「일단 1번만」) — 정량 근거는 없다.
- **모든 영역을 한꺼번에 내는 전체 출력 — 지금은 만들지 않음** — 영역별 조회로 충분하고 쓸 곳이 없다. 만들게 되면 그 크기가 결정 6 의 파일 + 검색이 맞는 경우다. 기각 강도 = 사용자 결정(「영역별로 잘 나누면 되겠네」).

## 근거
- 공급자 권고: 여러 단계를 한 도구로 묶기(`schedule_event`) · 고칠 방법을 말하는 오류 · 페이지 · 필터 · 잘라내기 + 합리적 기본값 · 넓은 검색 한 번보다 작고 겨냥한 검색 여러 번 — [Anthropic, Writing tools for agents](https://www.anthropic.com/engineering/writing-tools-for-agents)(원문 확인). 같은 글의 「자연어 이름이 암호 같은 id 보다 낫다」는 주로 *돌려주는 문맥* 쪽 문장이라 이름 *지목* 의 직접 근거로는 약하다(조사 보고서의 적대 리뷰 지적).
- 이름 지목 · 모호하면 오류 = tmux 대상 해석(원문 확인). 이동 뒤 새 id 를 응답으로 돌려주는 피어 = herdr `pane move`(원문 확인).
- 크기 문턱형 파일 넘김 = LangChain Deep Agents(20,000 토큰 넘으면 경로 + 앞 10 줄 · 원문 확인) · Cursor(긴 출력을 파일로 · 문턱 비공개). Claude Code 의 25,000 토큰은 응답 **상한**이지 파일로 넘기는 문턱이 아니다.
- 전체 상태를 늘 파일로 내는 선례(Playwright CLI — 명령마다 스냅숏 파일 링크)도 있다 — 우리 결과 크기에선 호출만 는다고 보아 따르지 않았다.
- **조회 크기 어림(2026-10-26 · 메인 · 토크나이저 실측 아님):** 창 × 탭 × 칸 = 1×2×4 · 2×4×6 · 4×5×8(칸 8 · 48 · 160). 텍스트 = 창 줄 + 탭 줄 + 칸마다 `<번호> <에이전트 이름>`(이름 ≈ 10 글자) · JSON = 창 · 탭 · 칸마다 UUID 를 실은 객체(창 id · 탭 id · 칸 id · 에이전트 id). 토큰 ≈ 글자 수 ÷ 3.5(텍스트) · ÷ 3(JSON). 결과 = 텍스트 ≈ 50 · 240 · 760 토큰 · JSON ≈ 500 · 2,850 · 9,200 토큰. 실제 토크나이저 · 실제 조회 모양에서 수십 % 어긋날 수 있으나 파일 문턱(20,000)과의 자릿수 차이는 남는다.
- 조사 상세 · 적대 리뷰(codex, 판정 FIX → 반영) = 관련 줄의 두 보고서. 이 ADR 과 정설은 `/review doc light`(판정 FIX → 반영)를 거쳤다.

## 영향 / 불변식
- 새 LLM 명령 · 조회는 `docs/reference/llm-command-conventions.md` §5 확인 목록을 지난다.
- **구현은 아직 없다** — 이름 지목, 응답의 배치, 파일 안전장치는 T-65 이후 구현 몫이다. 지금 코드는 id 만 받고 CLI 는 몸통을 그대로 찍는다.
- 데몬은 UI 명령 몸통을 해석하지 않는다(ADR-0081 · ADR-0156) — 응답 모양은 셸 처리기에서 한다.
- **이번에 손댈 코드는 레이아웃(창 · 탭 · 칸) 명령이다** — 에이전트 쪽 명령은 이미 이름을 받는다(데몬 `resolve_in`). 바뀌는 것 = 기존 레이아웃 명령이 이름 · 공간 낱말을 받게 · 셸의 이름 풀기(데몬 왕복) · 새 명령(옮기기 `tab.dock` · 배치 조회) · 응답 모양(바뀐 배치 · 오류 후보) · `prompts/engram-help.md`.
- 셸은 agent crate 를 의존하지 않으므로(ADR-0270) 이름 풀기는 데몬 왕복이 된다(결정 3) — 길은 구현 때 정한다.
