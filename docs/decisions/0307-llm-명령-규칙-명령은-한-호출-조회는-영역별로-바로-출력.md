# ADR-0307: LLM command rules — a command is one call, a query prints directly per area

- 상태: 확정 (2026-10-26, basis: user conversation decision · two research reports)
- 관련: CLAUDE.md 「LLM-우선 제어」 · canonical convention `docs/reference/llm-command-conventions.md` · research `docs/research/llm-command-design-query-vs-action-2026-10-26.md` · `docs/research/pane-positional-addressing-2026-10-26.md` · ADR-0068 (spatial targeting = logical handle) · ADR-0132 (one name resolver) · ADR-0285 (CLI = authentication + delivery) · ADR-0302 (window argument rejects numbers) · step-log S27 · tracking T-65

## 맥락
Before adding more commands that the LLM calls through the bus and the `engram` CLI (the first consumer = T-65 slot-docking LLM commands), we set common rules. The user's criterion = 「LLM 시나리오는 여러 번 거치지 않아야 실수가 적다」 · reduce both the number of calls and the amount loaded into the context. Today the layout commands take their target only by an opaque id, so a common request becomes a query plus a command, 2–3 calls (e.g. `slot.focus` first needs `slot.resolveSpatial` · `slot.assignAgent` needs `agent.list` and a pane id lookup). The user also asked — are the query results all loaded into the context, or put outside (a file) for bash to search?

## 결정
The canonical source of the rules is `docs/reference/llm-command-conventions.md`, and this ADR keeps their *why*.

1. **A command (write) = one call per scenario.** Several steps are done inside the command.
2. **A target is accepted in words the LLM already knows** — an agent name · a spatial word · an id. The command resolves it to an id inside. If it is ambiguous or missing, it stops with an error and carries the candidates. Each kind of word gets its own argument (mixed into one argument, a name like 「left」 would collide with a word — main-agent decision).
3. **An agent name is resolved by the one resolver over the daemon's registry** (`resolve_in` semantics — it follows ADR-0132's 「해석기 하나」). It is not resolved separately by the shell's id→name cache — that cache never deletes entries, so a dead agent's name resolves and the duplicate decision diverges from the daemon's (main-agent decision · review finding).
4. **The response of a command that changed the layout carries the layout after the change** — so the LLM does not have to infer the result (user: 「결과를 콜백해주는것도 좋겠지」).
5. **A query (read) = one per area + a filter argument, and the result is printed directly into the context.** Query only when you do not know the word to call.
6. **Put in one common safeguard that hands off to a file when the result is large — its place is undecided.** Putting it in the CLI collides with ADR-0285 decision 1 (CLI = authentication + delivery · user decision 2026-10-08), and the data location the file is written to is also a user decision. The place and threshold are decided before implementation.
7. **Command details (names · arguments · response wording) and the output format (text · JSON) are decided by the main agent on the side the LLM uses well, and reported** (user delegation: 「이건 llm인 너가 잘 아니 잘 지시되는쪽으로 알아서 하면 될듯」).
8. **A pane is called by agent name · spatial word, and for now is not targeted by pane number** (user decision 2026-10-26 — 「그거 그냥 일단 이름으로해」). The present defect where names overlap (tracking T-45) stops with an error + candidates, and goes away once the switch from name → internal unique id (T-29 · T-45 — user: 「데몬 이름은 내부에 고유 id로 할거임」) is done. Targeting by number is looked at again when designing the on-screen pane number display.

## 거부한 대안
- **Specify a pane by column · row coordinates (「x1 y2」 — the user's suggestion)** — the pane arrangement is a split tree, not a grid, so row boundaries differ per column and 「행 2」 is ambiguous (code fact — `src-tauri/src/layout/spatial.rs` derives positions from a rectangle tree). Of the tools surveyed (tmux · i3 · WezTerm · ace-window), none specifies by column · row coordinates (tmux pane number = creation order · spatial token = corner · edge · neighbor — checked in the original text). User accepted 2026-10-26 (after seeing the research result and confirming 「저게 지금 tmux 터미널 방식」, moved to the number side). Rejection strength = research + code.
- **Always put query results in a file and have bash (grep · partial read) find them** — the result for one area is small (the estimate under 「근거」 below). It is far below the threshold of the precedent that hands off to a file (LangChain Deep Agents 20,000 tokens). File + search increases calls (query + find ≥ 2), a pinpoint query finishes in one if you know the word to search for, and if you do not know it you have to read everything anyway. The large case is covered by decision 6's safeguard. User accepted 2026-10-26 (「ㅇㅇ 알았어 일단 그렇게 조회하고」). Rejection strength = quantitative estimate.
- **Targeting by pane number (a number in on-screen position order · receiving the latest numbers in the response) — not done for now** — ① the reason the window argument rejected numbers (ADR-0302 decision 9 · a late command hits a newly created same number) applies even more strongly to pane numbers ② the sequence number in the code compares the pane center heights with no tolerance, so it changes with a mere resize (`src-tauri/src/layout/spatial.rs` · the limit of ADR-0068 decision 1). Names are enough. Rejection strength = code + user decision (decision 8).
- **Batch execution (a list of commands at once) · a scripting system — not built for now** — with one command per scenario a common request ends in one call, so there is no place to use it yet. A script (variables · conditions · loops) is excessive for our scale. If the same two or three calls actually repeat, make that scenario one command, and bring batching back only if that is still not enough. Rejection strength = user decision (「일단 1번만」) — there is no quantitative basis.
- **A full output that emits all areas at once — not built for now** — per-area queries are enough and there is no place to use it. If it does get built, its size is the case that decision 6's file + search fits. Rejection strength = user decision (「영역별로 잘 나누면 되겠네」).

## 근거
- Provider recommendations: bundle several steps into one tool (`schedule_event`) · errors that say how to fix · pages · filters · truncation + reasonable defaults · several small targeted searches rather than one broad search — [Anthropic, Writing tools for agents](https://www.anthropic.com/engineering/writing-tools-for-agents) (checked in the original text). That article's 「자연어 이름이 암호 같은 id 보다 낫다」 is mainly a sentence about the *context returned*, so it is weak as direct grounds for name *targeting* (a finding from the research report's adversarial review).
- Name targeting · error when ambiguous = tmux target resolution (checked in the original text). A peer that returns the new id in the response after a move = herdr `pane move` (checked in the original text).
- Size-threshold file handoff = LangChain Deep Agents (over 20,000 tokens, path + first 10 lines · checked in the original text) · Cursor (long output to a file · threshold not disclosed). Claude Code's 25,000 tokens is a response **cap**, not a threshold for handing off to a file.
- There are also precedents that always put the full state in a file (Playwright CLI — a snapshot file link per command) — at our result size, we judged that only calls would grow, so we did not follow it.
- **Query size estimate (2026-10-26 · main agent · not a tokenizer measurement):** windows × tabs × panes = 1×2×4 · 2×4×6 · 4×5×8 (panes 8 · 48 · 160). Text = a window row + a tab row + `<번호> <에이전트 이름>` per pane (name ≈ 10 characters) · JSON = per window · tab · pane an object carrying UUIDs (window id · tab id · pane id · agent id). Tokens ≈ character count ÷ 3.5 (text) · ÷ 3 (JSON). Result = text ≈ 50 · 240 · 760 tokens · JSON ≈ 500 · 2,850 · 9,200 tokens. It may be off by tens of percent with a real tokenizer and a real query shape, but the order-of-magnitude gap from the file threshold (20,000) remains.
- Research details · adversarial review (codex, verdict FIX → reflected) = the two reports in the related line. This ADR and the canonical convention went through `/review doc light` (verdict FIX → reflected).

## 영향 / 불변식
- A new LLM command · query goes through the `docs/reference/llm-command-conventions.md` §5 checklist.
- **There is no implementation yet** — name targeting, the layout in the response, and the file safeguard are post-T-65 implementation work. The current code takes only ids, and the CLI prints the body as is.
- The daemon does not interpret UI command bodies (ADR-0081 · ADR-0156) — the response shape is done in the shell handler.
- **The code to touch this time is the layout (window · tab · pane) commands** — the agent-side commands already take names (daemon `resolve_in`). What changes = existing layout commands accept names · spatial words · name resolution in the shell (a daemon round trip) · new commands (move `tab.dock` · layout query) · response shapes (the changed layout · error candidates) · `prompts/engram-help.md`.
- Since the shell does not depend on the agent crate (ADR-0270), name resolution becomes a daemon round trip (decision 3) — the path is decided at implementation.
