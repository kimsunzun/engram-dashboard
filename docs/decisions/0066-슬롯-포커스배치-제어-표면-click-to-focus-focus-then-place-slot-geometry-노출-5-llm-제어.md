# ADR-0066: Slot focus and placement control surface — click-to-focus + focus-then-place + slot geometry exposure (§5 LLM control)

- 상태: 확정 · 부분 폐기 by ADR-0067 (Decision 2 focus-then-place · Decision 5 cross-window place target → right-click context menu) · 부분 폐기 by ADR-0068 (Decision 3: exposing geometry {x,y,w,h} coordinates first → logical-plan direction, neighbor and order handles first; coordinate system and measured pixels deferred) (2026-07-10, basis: 2 user decisions (placement = focus-then-place first + drag later · focus intensity 65%) + `/research medium` OSS survey (VS Code, JetBrains, tmux, Zellij, i3/sway, wezterm) + Codex adversarial review) · 부분 폐기 by ADR-0168 (focus ring intensity lowered to 40 percent)

## 맥락

Three gaps came from one root (the absence of a focus concept):
1. **Focus is not moved by a click.** `focused_slot_id` is set only as a side effect of structural changes (boot, tab creation, split, close) (`manager.rs` fixup_focus/make_view/split/close). There is no click→focus wiring, so the user cannot move the "selection". Runtime check: clicking another slot leaves `focused_slot_id` unchanged.
2. **There is no way to put a tree agent into a slot.** There is no interaction to place an agent tree item into a specific slot. To "put it in the current focus", a real focus concept must come first.
3. **There is no surface for interpreting a spatial instruction to the LLM ("put it at the bottom right").** Slots are exposed only as opaque ids, so a natural-language spatial reference cannot be turned into an id.

Because this is a major §5 control surface decision, we built the basis with `/research medium` (OSS survey → option set → user decision). In the Codex adversarial review the survey surfaced FIX items (2 overstatements, 4 omissions) → after the correction, the verdict was to keep the direction.

## 결정

Make focus, placement and spatial targeting a **single control surface where a human click and an LLM command move the same handle** (§5).

1. **Focus = click-to-focus.** Backend `manager.set_focused_slot(view, slot)` + the `focus_slot` Tauri command (ADR-0035 authority — reflected by emit, no optimistic update). Called when a slot pane is clicked. Auto-focus on split/creation is kept (the default across the industry). Registered in the registry as the `slot.focus` command, so a human, the palette, keybindings and the LLM (`__engramCmd.run('slot.focus', …)`) share the same handle.
2. **Placement = focus-then-place first, drag later.** Click a slot (focus) → double-click/Enter a tree agent → `assign` to the focused slot (ADR-0011). It is a single command surface (`focus_slot` + `assign`), so a human and the LLM take the same path. Drag-and-drop later adds only a "mouse convenience input" (calling the same assign command).
3. **LLM spatial targeting = expose slot geometry.** Expose each slot's `{id, x, y, w, h}` through the control surface (`__engramLayout` / a query command) → the LLM derives the target id by numeric reasoning ("bottom right" = max of x+w·y+h) → commands by id. (Direction sugar commands (in the style of tmux `{bottom-right}`) are a lower-priority option.)
4. **Focus display intensity = 65%.** The border is always `1px --border` + `inset box-shadow color-mix(accent 65%)` (0 layout shift). Raised from the initial "subtlest (40%)" — the basis is below.
5. **The cross-window active target resolves as (last-focused window) → (that window's active tab) → (that tab's `focused_slot_id`) (last-focused-wins).** ★Consistent with ADR-0057★: we **do not revive** the global `active_view_id` that ADR-0057 removed. ViewManager tracks only the **window label whose slot was focused last** (window level — the same layer as the ADR-0057 per-window active), and the "placement target slot" is **derived** from the `focused_slot_id` of `windows[마지막 focus 창].active` (the per-window active tab) (not a new global View pointer). Each View remembers its own `focused_slot_id` independently. Slot click → that window becomes the "last-focused window" + the focused_slot_id of that window's active tab is updated. If the window is switched without a click (alt-tab etc.), the target follows the focus that window's active tab remembered (per-window memory — not pinned to the previous window's slot). Visual = only the active slot of the last-focused window gets full emphasis (65% inset), and the focused_slot of other windows/views is dimmed memory (no simultaneous equal rings). Same shape as the VS Code active editor group (owned per window) (§Rationale).

## 거부한 대안

- **focus-follows-mouse (tiling WM pattern, i3/sway default):** per the survey, GUI editors (VS Code, JetBrains) use click-to-focus without exception. In a click-driven dashboard, follow-mouse causes wrong focus just from the mouse passing over. Rejected.
- **Drag-only placement:** ① §5 surface split — the LLM cannot drag, so a separate command path is needed (the control surface forks). ② WCAG 2.2 SC 2.5.7 = a drag feature requires a non-drag single-pointer alternative. ③ Drag has edge drop-zone precision and multi-monitor bug issues. → Drag only as an **auxiliary input** on top of the command (focus-then-place). Drag-only rejected.
- **Group-number placement UI ("3번 슬롯에 열기") (open in slot 3):** mature app UIs expose relative directions ("to the side"/"opposite"), not absolute numbers (numbers exist in the API — VS Code ViewColumn 1~9). For us opaque slot ids + geometry fit better. Number UI rejected.
- **Direction-only spatial target (geometry not exposed):** direction primitives (select-pane -R etc.) are relative moves, so they cannot pinpoint "bottom right" in one shot. A geometry snapshot is more portable and general (tmux/i3 take this path). But it is not that a one-shot spatial target like the tmux `{bottom-right}` token is impossible altogether (Codex correction) → direction sugar is left open as lower priority. Geometry-first, direction-only rejected.
- **Too subtle a focus display (40% inset):** the weak focus display of GUI editors (VS Code #24586, JetBrains IDEA-102931) is a recurring UX complaint, so 40% is a "can't be seen" trap. Raised to 65% (subtle but identifiable). 40% rejected.
- **Placement by policy/command rather than last-focus (JetBrains, Emacs):** JetBrains opens a new file on the **opposite side** of the focused split (official docs — "focus in the left split → opened in the right split"). Emacs `display-buffer` fully customizes buffer placement with a policy function (choosing or creating a window without selecting it). Mature alternatives, but ① at odds with the §5 single control surface (the policy layer is a separate axis) ② inconsistent with the user's mental model ("it goes where I clicked") ③ awkward to express the LLM's "put at the bottom right" as a policy function. last-focused-wins adopted, policy placement rejected.
- **A single global active variable across windows (ignoring window switches):** the Codex adversarial review REFUTED "single global active target across windows is standard" — every surveyed tool has per-window/per-container scope + memory (tmux per-window active pane, i3 `focused_inactive`, browser per-window active tab). If the target stays pinned to the previous window's slot on a window switch, it violates the convention. Moreover this **revives the global `active_view_id` that ADR-0057 already removed**, conflicting with a confirmed decision (doc review FIX-1). → adopted the derivation (last-focused window)→(per-window active tab)→(`focused_slot_id`) (Decision 5), single global variable rejected.

## 근거

- **OSS survey grounding:** click-to-focus (common to GUIs), two-way placement (mouse drag + keyboard focus-then-open; VS Code docs state "opens in the active group, click first"), and geometry-based spatial reasoning (tmux `list-panes -F`, i3 IPC rect) were confirmed by multiple sources.
- **Codex adversarial review correction:** F8 ("direction alone cannot give bottom right") was judged an overstatement by the tmux `{bottom-right}` token → reflected as direction sugar at lower priority. Added the WCAG 2.5.7 and NN/g latency (direct manipulation 0.1s) caveats.
- **§0 criterion (low risk, long horizon):** the command surface and geometry seam are laid down now (expensive to change later). Direction sugar and drag come after measurement.
- **Cross-window re-survey (2026-07-10):** that last-focused-wins is the standard for placement targets was cross-confirmed by multiple independent tools (VS Code, tmux, wezterm, Zellij, i3/sway, screen, kitty, browser) — confidence 'certain'. VS Code is the closest same shape (per-window active editor group + per-group memory + inactive dimming). Codex (research) and the doc review gave FIX on the "single global variable across windows" framing (risk of reviving the global `active_view_id` that ADR-0057 removed) → corrected to the derivation (last-focused window)→(per-window active)→(`focused_slot_id`) (Decision 5).

## 영향 / 불변식

- **Focus, placement and geometry go through the control surface (command / `__engramLayout`)** — a human click and the LLM use the same handle (§5). The UI does not shake the store directly.
- **Backend authority (ADR-0035):** `focused_slot_id` and assign are owned by the backend, no optimistic frontend update → reflected by emit. **But the focus click round trip is direct manipulation, so it must feel immediate, within ~100ms (loopback) or with optimistic visual feedback** (NN/g). Check this latency target in implementation and QA.
- **Active target = backend derivation (ADR-0035 authority · ADR-0057 per-window active is canonical):** placement target = the `focused_slot_id` of `windows[마지막 focus 창].active` — the backend ViewManager owns and resolves it (the ADR-0035 layout authority is unchanged). The canonical source for the concrete per-window active model = ADR-0057 (reviving the global `active_view_id` is forbidden). If the frontend holds a separate "active" state, it is a §5 violation (rejected in review). The first slice (click-to-focus) is only the `focused_slot_id` wiring (set_focused_slot to be added); last-focused-window tracking + place are later slices.
- **Drag is an auxiliary input on top of the command** — if a drag path bypasses the assign command and creates separate state, it is a §5 violation (rejected in review).
- **Keep auto-focus-on-split** — coexists with click-refocus (not a replacement).
- A `// ADR-0066` anchor on load-bearing paths.
- **Remaining unimplemented (what this ADR opens):** direction sugar commands · drag-and-drop · keyboard directional focus movement are later (this ADR fixes only the surface and priority).
