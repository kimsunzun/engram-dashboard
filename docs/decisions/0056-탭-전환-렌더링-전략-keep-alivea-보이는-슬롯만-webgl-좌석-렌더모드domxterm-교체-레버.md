# ADR-0056: Tab-switch rendering strategy — keep-alive (A) + WebGL seats only for visible slots, with the render mode (dom/xterm) as a swap lever

- 상태: 확정 (2026-07-09, basis: same-model (xterm.js) OSS survey + measured WebGL seats in a real WebView2 + user decision)
- 관련: PRD `docs/process/B-wezterm-tabs/PRD.md` (Phase 2 tabs) · ADR-0046 (per-view routing and replay — the cold-tab escape hatch) · ADR-0055 (command registry — the render-mode lever sits on it) · CLAUDE.md §5 (LLM control) · §2 (a slot picks its renderer by capability) · `src/components/slot/TerminalSlot.tsx` (WebglAddon + onContextLoss→DOM fallback) · `src/store/eventBus.ts` (`__engramLayout.setRenderMode`/`toggleDomMode` — the existing render-mode surface) · step-log 2026-07-09

## 맥락
In the WezTerm-style window > tab > slot structure (PRD B-tabs), one window shows only the active tab. We must decide **how to treat the terminals of tabs that are not visible (hidden)** — keep them alive (instant switching, data preserved) vs discard and revive them (light, switching delay). Our slot terminal uses xterm.js + WebglAddon (the GPU renderer). The browser (WebView2/Chromium) limits **concurrently active WebGL contexts with a hard cap**, so keeping many terminals alive can run into this cap. The maximum scale the user assumes = **3 windows × 2 tabs × 4 slots** → at most 24 terminals *alive* at once, and at most 12 terminals *visible* at once (3 windows × 1 active tab × 4 slots).

## 결정
- **Tab switching = keep-alive (A).** **Keep the xterm instances (buffer, data) of inactive tabs alive without disposing them** (hidden only). Output keeps accumulating in the xterm internal buffer even while hidden, and xterm's IntersectionObserver pauses only the render loop → **switching is instant and lossless, no replay needed.**
- **WebGL seats only for "visible slots".** Give the GPU context (= the scarce seat) only to active/visible terminals, and **when a tab is hidden, give back that slot's WebGL** (the data buffer is kept, only the seat is released). A hidden tab does not render anyway, so releasing the seat costs nothing visually. At most 12 visible ≤ 16 seats, so **the cap is never exceeded.**
- **The render-mode (dom/xterm) swap = exposed as a lever.** The override that forces a slot renderer to dom (plain text)/terminal (xterm) **already exists as `__engramLayout.setRenderMode`/`toggleDomMode`** (a frontend-only override). Wrap it as a command in the Phase 1 command registry (ADR-0055) so humans and the LLM call it the same way (§5). This lever is the manual control point for "deliberately turning some terminals to DOM to save seats" + "structured/tree content is DOM".
- **Do not build advance pooling/tiering now.** The rule above (seats only for visible ones) is safe at the user's maximum scale by itself, so elaborate renderer pooling and cold-tab replay tiering are **not implemented until measurement reveals a problem** (YAGNI). If needed, the escape hatch already exists (ADR-0046 per-view replay = the cold-tab reconstruction path).

## 거부한 대안
- **B (replay first) — unmount inactive tabs and reconstruct from the backend buffer on switch:** minimal memory and seats, but a reconstruction delay on every switch + loses the "always alive" feel. None of the same-model apps (VS Code/Tabby/Hyper) uses this approach for everyday tab switching (only for reload/reconnect). At our scale (≤12 visible) A is enough → rejected. (It stays as the cold/bulk escape hatch = ADR-0046.)
- **Advance 3-tier renderer pooling (active = WebGL / warm = DOM / cold = backend):** nobody in the same-model ecosystem does advance pooling — all are keep-alive + a reactive fallback on context loss. The user's maximum scale fits within 16 seats, so building a pool in advance is over-engineering (an unverified optimization = an empty shell, CLAUDE.md §0) → rejected (revisit if measurement shows a problem).
- **Port the WezTerm native model directly (the mux owns the grid, the GUI is a stateless renderer):** WezTerm is a native GPU app, so the parser (mux) and the renderer are separated, and "keep only the state, draw lazily" comes naturally. In xterm.js the parser and renderer are one `Terminal` object, so that separation does not carry over as it is, and there is no API to swap the buffer for other data → a direct port is impossible. (The grounds for why we must look at same-model = xterm.js apps.)
- **naive-A (keep WebGL even for hidden tabs):** if the WebGL seat is not given back when hidden, it still counts → 24 alive exceeds 16 → the oldest 8 lose their context (the reactive DOM fallback works, but it is non-deterministic and churns). Avoided deterministically by "release the seat on hiding" → naive-A rejected.

## 근거
- **Measured (primary):** in a real WebView2, creating WebGL2 contexts up to 40 → **exactly 16 survive and 24 are lost, oldest first** (cdp eval, 2026-07-09). Our runtime's GPU seats = 16 confirmed. At most 12 visible ≤ 16 → always safe.
- **Same-model OSS survey (xterm.js, WezTerm excluded):** the VS Code integrated terminal (`terminalInstance.ts`: calls `xterm.raw.write` unconditionally even when hidden, never disposes), Tabby (`left:-1000%` offscreen, `*ngFor` retained), Hyper (offscreen + IntersectionObserver), Theia (Phosphor visibility) — **all keep-alive (A)**. The WebGL cap is handled **reactively** in all of them (context-loss → canvas/DOM fallback), with no advance pooling. Our `TerminalSlot` also already has `onContextLoss(()=>webgl.dispose())`→DOM fallback.
- **"Don't draw what is not visible":** xterm's IntersectionObserver automatically pauses the render loop when offscreen/hidden → the drawing cost of a hidden tab ≈ 0. So keeping it alive is cheap, and if only the seat is released, even the only hard resource (the WebGL seat) is not tied up.

## 영향 / 불변식
- **Phase 2 tab implementation invariant:** when a tab is hidden, the xterm instance is kept and **WebGL (WebglAddon) is disposed**. When the tab is shown, reattach + `fit()`+`refresh()`. The number of visible slots is by design always ≤ 16 seats (3 windows × 4 slots = 12) — a layout that breaks this cap (raising the maximum windows/slots) requires revisiting this ADR.
- **Cold/bulk escape hatch:** if the scale exceeds this assumption and measurement shows a problem, layer on unmounting inactive tabs + reconstruction by ADR-0046 per-view replay (B tiering) — not implemented now, only the infrastructure exists.
- **The render-mode lever = a command:** forcing dom/terminal exposes `setRenderMode` (existing) as an ADR-0055 registry command (e.g. `slot.setRenderMode`). Slot contents that are not terminals (agent tree, diff, structured view) are DOM to begin with, so they take zero WebGL seats — consistent with the slot content kind model (follow-up PRD).
- **load-bearing anchor:** put a `// ADR-0056` anchor on the WebglAddon load/dispose path in `TerminalSlot.tsx` (when wiring tab visibility).

## Implementation settled and verified (2026-07-16)
We actually implemented and verified the Phase 2 visibility wiring (`TerminalSlot.tsx`). The design (above) stands as it is, and two implementation details were settled:

- **Releasing the seat is deterministic only if `loseContext()` is called explicitly (load-bearing).** xterm's `WebglAddon.dispose()` only detaches the canvas/layer and does not call `WEBGL_lose_context.loseContext()` (source checked · PixiJS #8215) → with dispose alone the seat stays occupied non-deterministically until GC. So we call `loseContext()` directly *before* dispose.
- **Capture the GL context at attach time.** React clears the host ref to null *before* the passive `useEffect` cleanup, so looking up the canvas through `containerRef` in the unmount cleanup finds it already null and the seat release fails → capture the GL context into a ref at the moment of attach (= becoming visible), and release uses that.
- **Trigger = IntersectionObserver.** Confirmed by measurement that IO fires on a hide (display:none) transition (both toggling self and toggling an ancestor div = the WindowLayout way).

**Measured (primary, cdp — real WebView2):** ① after releasing 8 with loseContext and creating 8 new ones, all 8 untouched ones survived = deterministic seat release confirmed (cap 16 reconfirmed). ② IO fires on a display:none ancestor toggle. ③ E2E: spawned terminal attach (WebGL 1) → tab hidden (canvas 0, instance alive) → return (WebGL 1 reattached), a lossless cycle.

**Alternatives additionally rejected during implementation:**
- **detach-DOM-but-keep-instance (detach only the DOM and keep the instance):** the live Terminal strongly references the node, so it is not GC'd → the memory gain ≈ 0 while only taking on the reattach risk. No large-app precedent either → rejected (H = keep display:none).
- **dispose-instance-on-hide (destroy the instance itself when hidden):** loses the warm buffer → on return, replay reconstruction (only up to the daemon cache cap) + flicker. It gives up the instant, lossless benefit of keep-alive, so it is for scale only → rejected.
