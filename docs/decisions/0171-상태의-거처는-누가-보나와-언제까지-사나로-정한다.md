# ADR-0171: State's home is decided by who needs to see it and how long it must live

- 상태: 확정 (2026-08-19, basis: user decision + 3 measured cases with the same root)
- 관련: CLAUDE.md 「LLM-우선 제어」·「창 구성」 · ADR-0035/0057 (layout backend ownership) · ADR-0149 (S23 known limits) · ADR-0172 (first application of this criterion)

## 맥락

We were bitten three times in the same way.

- When the app is restarted or a tab is popped out, the slot does not learn that the agent has exited and stays on 「연결 중」 — because that memory lives only in the renderer component (ADR-0149 §영향).
- When a slot is split, the preserved conversation disappears — the conversation is in component state, and the split unmounts that component (same place).
- Defects keep recurring, such as the waiting indicator that keeps spinning after exit.

All three are the result of putting state local to a component. Fixing them one by one invites a fourth — without a criterion, state gets placed in the nearest spot every time (that component).

Two facts force the placement. **The pop-out window and the tree window are separate webviews and do not share frontend storage** — state that must cross windows cannot live in the frontend. And **state that exists only in the frontend cannot be read by the LLM**, which is in friction with the 「LLM-우선 제어」 stance.

## 결정

Four layers are named as places to put state, and when creating new state, two questions decide the place.

**Layers**

1. **Component-local** — only while that screen is mounted. Gone on split, pop-out, and remount.
2. **Per-window store** — kept beyond component lifetime within one window. Gone when the window closes. Not shared between windows.
3. **Daemon memory** — daemon lifetime. Survives an app window restart, and all windows see the same value. The LLM can read it.
4. **Disk** — persistent across reboots.

**Two questions**

- **Who needs to see it** — if only one window, up to layer 2 is possible. If multiple windows or the LLM need to see it, layer 3 or above.
- **How long must it live** — while mounted (1) / while the window lives (2) / while the daemon lives (3) / forever (4).

**Layer 1 is in principle not used.** Only pure rendering byproducts remain (things recomputed if lost, like measured values and animation progress).

## 거부한 대안

- **Decide case by case (the status quo)** — the 3 measured cases above are all products of this approach. The decision point is "this component right now" every time, so the default got fixed at layer 1.
- **Store screen state in the frontend** — the pop-out window and the tree window are separate webviews and do not share storage. In particular, layout is *the relationship between windows*, so placing it inside a window does not even make the definition hold. Moreover, layout is already nailed down as backend-owned (ADR-0035/0057), and moving it to the frontend would remove the surface through which the LLM manipulates windows, tabs, and slots.

## 근거

- **Measured** — the 2 limits recorded in ADR-0149 §영향 (wrong display on restart or pop-out, conversation loss on split) + 3 defects around the waiting indicator during S23.
- **Code** — the pop-out window is a separate window created at runtime, not by configuration (CLAUDE.md 「창 구성」). Layout and tabs have the backend as authority, so the frontend subscribing to those events directly is treated as an exception (CLAUDE.md 「프론트 구조」).
- **Stance** — 「LLM-우선 제어」: the frontend owns rendering and does not own control.

## 영향 / 불변식

- **When introducing new state, leave the answers to the two questions** — one line in an ADR or a code comment. Without answers, the place has not been decided.
- **State placed in layer 1 is used only on the premise that it disappears on split, pop-out, and restart.** If that premise does not hold, move it up to layer 2 or above.
- This criterion applies as is to the follow-up items (cleaning up the waiting indicator overall · persisting layout state) — for both, choosing the place is the first fork of the design.
