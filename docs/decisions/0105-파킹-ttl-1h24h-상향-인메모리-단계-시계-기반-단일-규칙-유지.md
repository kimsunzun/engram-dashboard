# ADR-0105: Raise the parking TTL from 1h to 24h — in-memory stage, keeping the single clock-based rule

- 상태: 확정 (2026-07-25, basis: a /research light precedent survey + user decision — see the basis section below)
- 관련: Amends ADR-0103 (parking TTL 1h → 24h — in-memory stage only) · ADR-0104(idle gate — the busy wait came to share the TTL, which triggered the re-review) · spec §5 policy constants

## 맥락

With C2 (the idle gate, ADR-0104), a message for a recipient that is "alive but in the middle of a turn" also shares the parking TTL, so a review remark (the C2 deep review info item of 2026-07-25) pointed out that a message arriving during a turn longer than 1 hour could expire. The existing 1h was a balance value without precise grounds (typo cleanup · memory hygiene · preventing belated delivery). At the user's instruction, the expiry-policy precedents of similar systems were surveyed with /research light, and then the decision was made.

## 결정

**Parking TTL = 24h** (changing the single `PARK_TTL` constant). **No expiry exemption rule** — keep the single clock-based rule (the same whether absent or busy-waiting). The cap of 100 per recipient · the notice cap exception · recording `expired` in the ledger on expiry (no silent loss) all stay unchanged. **Once a persistence (disk) stage comes, this is to be redesigned** (the user's explicit statement — this value is for the in-memory stage only).

## 거부한 대안

- **Keep 1h + exempt live recipients from the sweep (liveness-aware TTL)** — it would become a self-made design with no precedent in any of the 6 surveyed systems (RabbitMQ · SQS · Kafka · Postfix · ejabberd · LLM frameworks) (RabbitMQ documents explicitly that it never delivers TTL-expired messages even when a consumer is connected). Against the doubling of the rule (clock + liveness), most of the benefit is absorbed by raising to 24h.
- **Keep the current 1h** — there is a risk that long turns, sleeping teammates and instructions given before spawn expire. Unusually short against industry defaults (SQS 4 days · Kafka 7 days · Postfix 5 days).
- **No expiry (the same as the RabbitMQ default)** — a typo recipient's message would survive until the daemon restarts and pollute the `messages` query. 24h covers pre-spawn instructions and long turns, and also cleans up.

## 근거

- Precedent survey (/research light, 2026-07-25, grounding passed — 4 figures cross-checked by the main agent). By system:

| System | Default retention | Liveness exemption | On expiry |
|---|---|---|---|
| RabbitMQ (AMQP) | No expiry (no default TTL) | None (expired items not delivered even to a connected consumer — documented explicitly) | DLX records the reason, sender not notified |
| AWS SQS | 4 days (max 14 days) | None (visibility timeout and retention are separate axes) | Silent deletion |
| Kafka | 7 days (log.retention.hours=168) | None | Silent segment deletion |
| Postfix (email) | 5 days (maximal_queue_lifetime) | None | **Bounce notice to the sender** |
| ejabberd (mod_offline) | Time-based expiry not confirmed (only a count cap confirmed) | Not confirmed | Not confirmed |
| LLM frameworks (AutoGen etc.) | Not found (abstained — official repo not surveyed) | — | — |

  The gist: no precedent at all for a liveness-aware exemption (all clock-based) · the industry compromise for expiry handling = DLX-style "record the reason, no notification" (isomorphic to our ledger `expired`) · 1h is on the short side against precedents, and units of days are the practice.
- Because it is the in-memory stage, the cost of a long TTL is ~0: the cap of 100 already bounds memory, and everything vanishes on a daemon restart. Belated delivery (a day-old message) is for the receiving LLM to judge.
- User decision (2026-07-25): "어차피 나중에 저장구조 들어가면 변경해야 됨. 24시간으로."

## 영향 / 불변식

- `PARK_TTL` (mailbox.rs) = 24h — **applied together with the C2 commit** (the constant + updating the existing "why 1h" comments in 3 places + an accompanying `// ADR-0105` anchor are mandatory; if the code is still 1h at the time of this ADR's commit, the code is lagging behind). The boundary meaning (`>=` = expires exactly on reaching the TTL) · the expiry ledger record · cap admission-only stay as in ADR-0103/0104 decisions.
- A v2 candidate memo: a notice to the sender on expiry (the email bounce precedent — the nature of our system is closest to correspondence) — to be reopened together at the persistence redesign.
