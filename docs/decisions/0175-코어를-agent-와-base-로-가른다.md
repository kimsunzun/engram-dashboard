## 맥락

`engram-dashboard-core` (30 files · 20,790 lines · 10,423 production lines, measured 2026-08-25) is **the daemon's agent runtime**, yet four consumers of entirely different character depend on all of it. The surfaces they actually touch do not overlap:

| Consumer | Distinct symbols | What |
|---|---|---|
| `daemon` | **94** | `agent::*` 91 · `persistence` 2 · `logging` 1 |
| `src-tauri` (shell) | **13** | `logging` 4 · `replay_flight` 8 · `agent::commands::COMMAND_SPECS` 1 |
| `net` | **2** | both `agent::platform::*` (PID liveness) |
| `discovery` | **1** | `agent::platform::pid_alive_with_start_time` |

That is, what the shell, net, and discovery reach is **only the bottom infrastructure**, yet because of it they depend on the entire agent runtime. The core has **zero optional dependencies** (zero feature gates), so `portable-pty`, Job Object, and `tracing-subscriber` come along into client builds as is.

There is also a reverse case — `replay_flight` (860 lines) lives in the core but **only the shell uses it** (the daemon has zero compile dependency, with only one prose comment: `daemon/src/connection_core.rs:1494`). The reason for keeping it that its file header gives is *"thanks to this location, tests run headless — src-tauri tests do not run"*, which is **a premise that died when ADR-0174 (2026-08-24) set up the shell test target.**

## 결정

1. **Create `engram-dashboard-base`** (a leaf crate) — `logging` (692 lines) + the PID decision helper of `platform` (`process.rs`, 325 lines). The `regex` and `tracing-subscriber` that logging carried, and the `windows` that the PID helper carried, move out together.
2. **Rename `engram-dashboard-core` → `engram-dashboard-agent`.** What remains = the whole agent runtime (lifetime · pump · backend · transport · domain model · `commands` · `types` · `persistence`) + the **Job Object wrapper** (`platform/windows.rs` — kept because its consumers are only inside `agent`). The inner `agent/` module is folded up to the crate root (to prevent the overlap `engram_dashboard_agent::agent::types`).
3. **`replay_flight` moves into the shell as a module** (it is not promoted to a crate). The 4-line re-export in `src-tauri/src/daemon_client/replay_flight.rs` is replaced by the real thing, so consumers' import paths do not change. The dead reason for keeping it in the header and the path in the daemon comment are fixed in the same commit.
4. **The shell → `agent::commands::COMMAND_SPECS` edge is kept this time.** But not left alone — it is removed in a **later step of the same branch**: after putting a `ui.` prefix on commands the webview answers so that name collisions disappear themselves (decision 5), the filter that reads that constant is deleted.
5. **The command name prefix `ui.` is put only on those the webview answers.** The daemon (`agent.*`) and shell (`tab.*`·`slot.*`) are left as is.
6. **Add a weight criterion to the crate decision (user decision 2026-08-25):** *libs are balanced to be similar in weight, and **a single-file lib is not created.*** This clause is the common ground of the 3 rejected alternatives below.

Execution order (same branch) = ① rename ② create `base` ③ move `replay_flight` ④ `ui.` prefix ⑤ remove the edge + app-surface notice on collision.

## 거부한 대안

- **`engram-dashboard-logging` and `engram-dashboard-platform` as separate independent crates** (blind reviewer GPT's recommendation · the doc-aware reviewer also went the same direction with 「덩어리별 판정」) — **rejected by user decision**: *"기능 추가할 때마다 모듈 만들 순 없다. 과해지면 그때 분리하자."* And splitting off only logging would make a **single-file lib**, which hits decision 6. ★**This rejection diverges from the expectation in ADR-0151 §영향**★ — it says *"decide per chunk — there is no ground to lump the three into one, and several small crates with purpose names may come out (also avoid the `bevy_core` failure)"*, and this decision puts the two into one bag. **The basis of this rejection = user judgment, not measurement (self-assessment: weak).** So it is stated as a place that can be reopened — reopening condition = when a third resident tries to move into `base`.
- **Create `engram-dashboard-agent-command`** (split off only the 110 lines of declarations so the shell's `agent` dependency becomes 0 — GPT's recommendation 2) — rejected for hitting decision 6 (no single-file lib). Decisions 4 and 5 (prefix + filter deletion) achieve the same goal without adding a crate.
- **`replay_flight` as an independent crate** (the doc-aware reviewer's recommendation — ADR-0151 §영향 named it *"replay state machine, 610 lines"* and pointed to it as a bottom-crate candidate, and the reviewer checked line counts at the ADR-time commit and confirmed it is the same target) — rejected for hitting decision 6 (366 production lines in a single file). ★**It was not rejected because it has one consumer**★ — ADR-0151 decision 1 had already discarded that axis with *"do not ask whether there is an actual consumer right now"*. The rejection axis is **weight**.
- **Do not split; turn heavy dependencies optional with cargo features** (option C) — rejected. ① It is only a build optimization, not an alternative for the ownership boundary (GPT) ② **the shell holds `daemon` as a dev-dependency** (`src-tauri/Cargo.toml:97`), so features unify and the gain disappears in `cargo test -p engram-dashboard` (measured by the doc-aware reviewer) ③ `#[cfg(feature)]` would have to be scattered inside a 9,277-line crate, so it is more invasive than creating a crate.
- **Conversely, merge crates** (option D — such as returning `command` to the core) — rejected. The two reviewers agreed, and the reason for `command`'s existence was already nailed down by ADR-0155 (it can be used independently and prevents cycles). **But folding `discovery` (T-10) is not covered by this rejection** — it is a separate matter that stays alive, and by GPT's measurement the actual extent of use turned out larger than the T-10 description (`daemon/src/lib.rs:62,428` · `daemon/src/control/priming.rs:288`).
- **`-core`·`-common`·`-util`·`-sys` instead of `base`** — `-core` is Rust's first-choice idiom (`tracing-core`·`futures-core`), but in that idiom it means *"the minimal kernel of that abstraction"*, which does not fit cross-cutting infrastructure like logging + PID, and even if the rename leaves the name empty, it blurs which side all the old records point to. `-common` and `-util` are grab-bag names. `-sys` is a reserved convention in Rust meaning C FFI bindings.
- **Put `daemon.` and `shell.` prefixes too, for symmetry** — rejected, two grounds: ① `agent.spawn` is a name the LLM and users actually type, so renaming would break existing usage, docs, and keybindings (the webview side **is already filtered out of bus registration**, so the external cost is 0) ② whether it is the daemon or the shell is a **location**, and locations change — if `tab.create` is later moved to the daemon, the `shell.` prefix becomes false and needs another rename. `ui.` is not a location but a category ("the attached UI answers"), so it survives a move.
- **A `webview.` prefix** — it stamps the technology WebView2 into the name, and becomes false the moment a mobile client attaches.

## 근거

- **Per-consumer symbol measurement** (the §맥락 table above) — `rg -o "engram_dashboard_core::[A-Za-z0-9_:]+" | sort -u` + supplement for aliases and brace expansion. `net` is exactly 2 (`portfile.rs:86` production + 2 inline test places), `discovery` is 1 (`lib.rs:1012`) — **both are PID helpers only, so decision 1 brings the `agent` dependency to 0.** This is the confirmed result of this cleanup.
- **Core internal cohesion measurement** — `logging` has 0 outgoing references · 1 incoming line (`transport/stdio.rs:30`), `platform` has 0 outgoing references · 2 incoming lines, and `replay_flight` has **0 incoming and 0 outgoing**. All three can be detached without shaking the rest. On the other hand, lifetime·pump ↔ transport ↔ backend is a **module-level cycle** (12,685 lines), so it is kept inside one crate (both reviewers agreed).
- **Visibility measurement** — **0** `pub(crate)`/`pub(super)` items in `logging` and `platform`. Nothing needs promoting across the crate boundary.
- **`replay_flight` is not a wire contract** — its file header states: the boundary marker tag 255 is a **shell↔webview Channel-internal contract** that does not exist in the daemon codec. The daemon does not know that tag.
- **trd full review by 2 reviewers** (2026-08-25) — doc-aware (Claude) `BLOCK` · blind (GPT) `FIX`. Many defects of the original plan (`base` holding all of logging + platform, with only `-core`/`-common` considered as name alternatives) came out here and were reflected in the decisions above. The one remaining conflict (whether `replay_flight` is a crate) was decided by the user as decision 6.
- **Why the `COMMAND_SPECS` filter is needed right now** — the daemon **bounces a registration packet whole** if even one name it answers itself is in it (`connection_core.rs:675` `refuse_names_i_answer` — it does not drop only the overlapping ones). Since `agent.spawn` and `agent.rename` really exist in the frontend registry (`src/commands/agentCommands.ts:41,76`), removing the filter first would bounce the registration at every boot, and **the shell's window, tab, and slot names would not get onto the registry at all.** So the prefix (decision 5) comes **before** the edge removal (decision 4).

## 영향 / 불변식

- **Dependency graph (target):** `base`·`command`·`messaging` = leaves · `protocol → command` · `agent → command, base` · `net → base, protocol` · `discovery → base, protocol, net` · `daemon → agent, base, protocol, discovery, messaging, net, command` · `src-tauri → base, command, protocol, discovery, net` (+ 1 `agent` symbol until decision 4 is closed).
- **`base` move-in conditions (nailed into the header):** ① two or more consumers ② zero domain knowledge ③ no references among themselves inside this crate. ★**When a third resident appears, reopen the first item of the 「거부한 대안」 (rejected alternatives) above**★ — that is the point where it steps onto the `bevy_core` path.
- **Gates that the rename silently breaks (fix them together in the same commit):**
  - `.github/workflows/ci.yml:399` — the messaging isolation regex hand-writes the crate name alphabet. If the new name is not added, a hole opens in the wall.
  - `ci.yml:481-498` — the core symbol allowlist for net (exactly 2 lines). If, after the rename, it is changed to 「0줄 기대」 (expect 0 lines), it becomes a **dead gate that cannot be broken by any violation** → retarget it to `engram_dashboard_agent::`, but ★**the expected value stays 2**★. The number of symbols net bites did not change with the rename — only the path got shorter from `::agent::platform::` to `::platform::` through module folding. **Lowering to an expectation of 0 and newly setting up an `engram_dashboard_base::` allowlist comes after `base` of decision 1 actually stands and the PID helper has moved there** (the same sentence is also nailed into the comment of that gate in `ci.yml`).
  - `ci.yml:271-272` — the `crates/engram-dashboard-core/bindings/` path of the generated-artifact sync gate.
  - **`.claude/skill-bindings/qa.md`** — the **two core isolation gate spots** in this file (the `use tauri` line of the standard block + the 「코어 격리 불변식」 section at the very end), unlike CI, have no path-absent branch, so after the rename they **sweep a nonexistent path and read as a pass**.
