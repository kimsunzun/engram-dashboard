# ADR-0033: Verification and recording skill infrastructure — two layers (skeleton + binding) + adr hybrid

- 상태: 확정 (2026-06-26, basis: research (adr-tooling) + dogfood review/qa)
- 관련: CLAUDE.md 「구현 실행 규약」·「설계 결정 기록 (ADR)」 · `.claude/skills/{research,review,qa,adr}/` · `scripts/adr.mjs` · ADR-0031 (review system) · step-log

## 맥락
We needed a reusable skill set to run the development steps (PRD → TRD → code → verification). The old `tp`/`tr` (monolithic orchestrators) were discarded because the AutoFlow they carried over was unusable, and the review system was already settled by ADR-0031 as "two-party adversarial review by opus + Codex". The remaining decision = **how to structure** these skills, and in particular what form to give a skill with a large mechanical share, such as ADR recording.

## 결정
The four skills research/review/qa/adr are fixed as follows:
- **Two-layer structure** — a generic skeleton (`references/flow.md`, no stack-specific content) + a project binding (`references/bindings/<project>.md`). But **research is generic-only** (it has no real project commands, so no binding is needed — integration happens in CLAUDE.md). **Only review/qa/adr have a binding**, and another project reuses the skeleton by adding only its binding.
- **Axis** — research = intensity (light/medium/deep) · review = stage (prd/trd/code/doc) × intensity · qa = intensity (quick/standard/full) · adr = **operation** (new/supersede/lint).
- **Only adr is a deterministic-script hybrid** — clerical work (numbering, index regeneration, bidirectional supersede, lint) is done by `scripts/adr.mjs` (deterministic); the decision between full and partial discard and the body prose are done by the skill (LLM).
- **Self-improving feedback loop** — a defect found while using a skill is not fixed on the spot (risk of misjudgment) but accumulated in `feedback.md` → applied with user approval when a related topic reappears.
- **Research absorbs prior-art** — add a design-decision mode (OSS survey → constraint-fit table + rejected candidates → ADR) to research, and discard the prior-art skill.

## 거부한 대안
- **A monolithic orchestrator (tp/tr style)** — huge and opaque, a path that has already failed once. Replaced by a combination of skills + CLAUDE.md conventions.
- **A single layer (hard-code the stack in the skill)** — rot + no reuse in other projects. Two layers keep the skeleton stack-neutral.
- **adr as a pure skill (the LLM does numbering, index, supersede, everything)** — **data corruption was demonstrated** in `/review code` (one side of a bidirectional link missing · number collisions · false lint on compound statuses). So the deterministic parts were pushed down into a script.
- **adr as a pure script** — the machine cannot do the decision between full and partial discard or the body prose. Hence the hybrid.
- **An "intensity" axis for adr (parallel to the other skills)** — ADR recording is deterministic, so there is no depth tradeoff of "roughly / thoroughly". The meaningful axis is the operation.

## 근거
- **research (`docs/research/adr-tooling-hybrid-research-2026-06-26.md`)** — adr-tools is the thin-hybrid reference, and the "machine (clerical) / judgment boundary" is consistent across the industry (2015~2026) (Claude + Codex converge). Partial discard follows the bidirectional Amends link convention.
- **dogfood** — each skill was verified with review/qa. In particular, adr got a `/review code` FIX (6+ data corruption cases) → fixed → qa measurement PASS (32 ADRs of real data lossless, index --write idempotent).

## 영향 / 불변식
- Skill = **generic skeleton (zero stack)** + (review/qa/adr) **binding**. **research is generic-only with no binding** (no real project commands). A new project only adds a binding file (no skeleton changes).
- The single source for adr mechanical work = `scripts/adr.mjs`. The LLM does not create numbers, indexes, or bidirectional links by hand (that is why the first draft broke).
- **Verification status:** whether these skills are actually better than a single model has not yet been checked by a controlled comparison = "a hypothesis with a basis". It needs to be proven by a real-use backtest.
