# ADR-0113: Promote turn-state (busy) observation to shared — facts are shared, policy belongs to the consumer, wiring belongs to the daemon

- 상태: 확정 (2026-07-29, basis: user decision — messaging learning Q&A session, implementation timing = a separate slice after the send overhaul (ADR-0111/0112)) · 부분 폐기 by ADR-0119 (home of the shared facility) · 부분 폐기 by ADR-0127 (decision 3 home of the wiring)
- 관련: ADR-0111·0112(send overhaul — this promotion is the slice after it) · ADR-0104(decision 3 idle gate — messaging is the first consumer of this state) · ADR-0110(kernel lib isolation — keep the port structure) · CLAUDE.md §5(LLM-우선 제어 — consistent with exposing the state on the control surface) · `crates/engram-dashboard-messaging/src/busy.rs`(the current owner — the move target) · Amended by ADR-0119 (home of the shared facility) — **the home is settled as the core. Do not read "core/daemon side" in decision 1 as an open fork** · Amended by ADR-0127 (decision 3 home of the wiring) — **the round trip is gone, so the classification moved to the core backend seam and only relaying is left to the daemon. `TurnProbe` and `TapHost` are gone, so do not read "keep the port layout" in decision 3 as a living contract**

## 맥락

"Is the recipient in the middle of a turn right now" (busy/idle) is a general state of an agent, yet its observation table (BusyTracker) currently lives inside the messaging kernel — because the only consumer was the mail delivery gate (ADR-0104 decision 3). But consumers that want the same state are already visible: the UI's "lock/queue chat input during a turn", slot state display, the LLM control surface (§5). As long as it is inside messaging, they cannot reach it (the kernel is isolated with no workspace dependency — ADR-0110). The user's proposal (2026-07-29): "BusyTracker는 순수 에이전트 상태만 서빙하고, 그에 대한 처리는 메시지 내부에서, 이벤트 연결은 데몬에서." (BusyTracker serves only pure agent state, the handling of it is done inside messaging, and the event wiring is done in the daemon)

## 결정

**Promote turn-state observation to shared by splitting it three ways:**

1. **Fact = shared** — promote the table of "turn-progress observations per (agent, epoch)" to a shared facility on the core/daemon side. This layer serves only observed facts and holds no interpretation or policy.
2. **Policy = inside the consumer** — each consumer decides how to interpret the facts. Messaging's existing policy (positive-knowledge-only "idle if unknown" · the busy cap of the 30-minute sweep · the flush doorbell) stays inside messaging as it is. Other consumers (input lock, etc.) set their own fallback and cap separately.
3. **Wiring = the daemon** — attaching the output-stream tap and connecting the turn signals (progress/end) is handled by the daemon (the messaging_host family in the assembly room). The kernel port (TurnProbe/BusyGate) layout is kept, but the signal source changes to the shared facility.

**Implementation timing = a separate slice after the send overhaul (ADR-0111/0112) is implemented and verified** (the user's fork choice).

## 거부한 대안

- **Keep as is (owned inside messaging)** — follow-up consumers such as the UI input gate cannot use the same state, and would have to build the observation wiring a second time when needed (two sets of wiretaps on the same output stream).
- **Share the policy too (the shared layer decides busy/idle judgment, fallback, and cap)** — the cost of a wrong call differs per consumer: for messaging, "not going > going late", so a fallback and a 30-minute cap that collapse toward delivery are right, but an input lock may want a different cap and release rule. Putting policy in the shared layer forces one consumer's value judgment on everyone.
- **Operate on it at the same time in the same slice as the send overhaul** — it is a structural refactor independent of the mail semantics surgery, so the review/QA scope and the regression surface grow needlessly. Risk separation (the user's choice).

## 근거

- User decision (2026-07-29): the shared promotion + the three-way split + naming the follow-up consumer ("채팅 한꺼번에 입력되지 못하도록 막는 곳" — the place that blocks chat from being entered all at once) are all the user's own words. The fork choice = "split into a separate slice".
- The move cost is structurally low: the kernel already handles turn state only behind the TurnProbe (signal receiving end) / BusyGate (query seam) ports, and the real wiring is owned by the daemon adapter (ADR-0110) — moving the owner does not shake the pipeline.
- A fact the current busy.rs header states itself: positive-knowledge-only and the 30-minute cap are policy derived from messaging's value judgment ("not going is the worst") — the grounds for needing the fact/policy split.

## 영향 / 불변식

- **The shared layer = facts only** — putting policy such as fallback, cap, or doorbell in the shared layer violates this decision. Consumer policy goes in consumer code.
- **Messaging consumer policy unchanged** — even after the promotion, messaging's "idle if unknown", 30-minute cap, and flush doorbell behavior must be observably identical (the promotion = a move of the owner, not a change of semantics).
- **Inherit the callback discipline** — the turn-signal callback runs on the output pump thread: only a small lock-section update + a non-blocking notification (the current busy.rs discipline). If this discipline is loosened in the sharing, all agents' output backs up behind the delivery work.
- **§5 consistent** — the shared state must be exposable as an LLM control/observation surface (no hiding it as UI-only).
