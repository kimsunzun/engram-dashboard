# ADR-0150: The registry owner is a client-made identifier — on disconnect, remove it without a trace

- 상태: 확정 (2026-08-17, basis: user decision 2026-08-17)
- 관련: Amends ADR-0156 (keeping a trace of a disconnected name) · Amends ADR-0155 (owner token derivation) · CLAUDE.md 「LLM-우선 제어」 · `docs/process/S20-command-bus/trd.md` §3-7·§4-② · `crates/engram-dashboard-command/src/roster.rs` · `crates/engram-dashboard-daemon/src/command_roster.rs` · `crates/engram-dashboard-daemon/src/agent_conn.rs`

## 맥락

ADR-0156 decision 3 said: 「끊긴 주인의 이름에 만료를 두지 않는다 — 자취로 남기고 **재등록 시 last-wins로 덮는다**」 (a disconnected owner's name gets no expiry — it stays as a trace and **is overwritten by last-wins on re-registration**). **That premise does not hold.**

The owner token is derived from the connection id (`command_roster.rs` `owner_of` — ADR-0155). So when the same client disconnects and reconnects, it gets a **new connection id → a new owner token**, and to the daemon it is a stranger. The result is not overwriting but **piling up**.

There is no means to clear what piles up. The cap (`MAX_NAMES` 4096) counts **the number of names**, and traces eat into that share too (pinned by a test). There is neither expiry nor a reclaim path, so the registry fills **permanently** — once the cap is reached, every new name registration is rejected and **only a daemon restart resolves it**. For a client with 60 lines, about 68 reconnects get there.

**It has not shown up yet** — the registration wire (`RegisterCommands`/`UpdateCommands`/`ListCommands`) and the daemon's receiving side are in place, but there are **zero senders** (comment in `protocol/src/messages.rs`: "받는 쪽만 서 있다"). It shows up in Step 3, when the shell starts registering. So **fixing it now is cheapest — there is no sender yet that would break.**

## 결정

1. **The client makes its own identifier, keeps it, and sends it in the first greeting (the `Auth` frame).** No issuing and no pairing. **It is not a secret** — authentication is still done by the daemon's shared token. This value is for **correlation**, not authorization.
2. **The daemon keeps that value in one slot per connection and uses it as the registry owner key.** It replaces the connection-id derivation.
3. **When a connection drops, that owner's registrations are removed — no trace is left.**
4. **Registration is not merged into the first greeting.** It is sent as a separate registration message **right after** authentication passes.
5. **The kept identifier's only consumer this time is the registry.** It is not used in lookup commands, event exposure, screen display, or authentication decisions (user instruction — a scope fence).
6. **Because it is a value received in the first greeting, an entry check (length cap, character set) is added.**

## 거부한 대안

- **A. Keep the trace and push out the oldest when the cap is reached** — Cheapest because the wire does not change, but a 「지운 이름」 (deleted name) and a 「원래 없던 이름」 (name that never existed) cannot be told apart, so the diagnostic message says something false. ★Strength of the rejection basis = **weak** (descriptive)★ — the user was given A and this decision as options and chose this decision.
- **B. Only record it and do not fix it** — The judgment was that the chance of reaching it is low because there are currently zero registrants. But if it is fixed after senders exist, **both sides of the wire must be matched**. The reason for rejection is that now is cheapest.
- **C. The daemon issues a unique token per client** — ㉠ An issuing and delivery procedure would have to be built new. The current structure is 「데몬이 토큰 하나를 파일에 적고, 그 파일을 읽을 수 있으면 들어온다」 (the daemon writes one token to a file, and whoever can read that file gets in), so **file access permission is the entry permission**. ㉡ **Mobile is not launched by the daemon**, so there is no moment to hand it over — a pairing procedure such as QR or code entry is needed. It is not one field but **one feature**. ㉢ Being a secret, it cannot be placed where the LLM reads, so it cannot be used to say 「어느 클라인가」 (which client) either. If it becomes needed later, the reason will be **security (revoking access for a lost device), not distinction**, so it is a separate agenda item.
- **D. Put the identifier in the existing owner field of the registration message** — The cheapest place, since the contract need not be opened. The main agent recommended this option and **the user rejected it with 「이 값은 명령 밖에서도 쓴다」** (this value is used outside commands too). A place reached only at registration time does not fit that use.
- **E. Merge the command list into the first greeting** — The goal 「붙는 순간 등록 끝」 (registration is done the moment it connects) is right, but if the token and the list arrive in one frame, **the list is parsed before the token is verified**, which widens the attack surface. The same effect is had at no cost by **sending right after authentication** (decision 4).
- **F. Put a time expiry (TTL) on traces** — **ADR-0156 alternative C already rejected this and this decision does not revive it.** The trigger we adopted is not time but **the event of connection end**. The problem of different answers going out to the same question depending on timing (the rejection reason in 0156) does not arise.
- **G. Several owners per name + send to every owner that has it + several results** — **Deferred** in this scope (a reservation, not an exclusion). The user is also considering a 「하나 연결하면 하나 끊는」 (connect one, disconnect one) direction, so **simultaneous multi-client connection itself is not settled**. The current data structure has one owner per name (the later registrant wins) and stays as it is.

## 근거

**Measured in code (2026-08-17, three investigation subagent runs).**

- Owner token = derived from the connection id (`command_roster.rs` `owner_of`) · the wire's `owner` field is **used only for a log warning and then discarded** (`connection_core.rs` `note_claimed_owner`).
- Cap 4096 = **the number of names** (key count of `BTreeMap<String, Registration>`). That traces eat their own share is **pinned by a test**.
- **No** expiry or GC path. A code comment states outright "데몬 재시작 말고는 안 풀린다" (nothing but a daemon restart clears it).
- Disconnect detection = `agent_conn.rs` `on_disconnect` → `detach`, **exactly one place** (the other hits are tests).
- First greeting payload = `{token, protocol_version}`, **only two fields**, and **frozen by a golden test**. The web (`src/api/wsTransport.ts`) and the desktop shell (`src-tauri/src/daemon_client/connection.rs`) **send the same value** — right now the daemon cannot even tell those two apart.
- The frontend connection token is **a shared secret generated once per daemon process and written to a file** (checked against the same value on every connection). It is a **separate system** from the agent control channel token (issued per spawn), and the code explicitly forbids sharing them.

**Why this differs from the old rejections in ADR-0155.**

- **Alternative B (an owner field in the declaration)** rejected duplication in the **compile-time declaration** ("정의 위치가 곧 주인", the definition site is the owner). This decision is the **identifier of a runtime connection**. The connection id cannot be known to the client and does not span reconnects, so it is **not duplication** — there is no other source to replace it.
- It also differs from **alternative F (a direction field on the envelope)**. That was a field carried **on every message**, where the field and the connection could disagree about the truth; this is a property **once per connection lifetime**. The truth of routing is still the connection.

## 영향 / 불변식

- **★ADR-0156 is amended only in decision 3.★** Clauses that stay alive: **opaque bundling of `help`** (decision 1) · **value reading included in v1** (decision 2) · the hard constraint that the daemon stays opaque · additive extension of the frontend registry. **Do not read all of 0156 as dead from the stamp alone.**
- **★ADR-0155 is amended only in owner token derivation.★** The declaration next to the producer · three-step delivery · no execution at the receiving place · runtime registration only · the hard constraint of no handlers in `static` are **all still valid**.
- **The first-greeting wire widens by one field (additive).** **The golden test is updated in the same commit** — that test going red is the intended signal.
- **Fix both clients together** — fixing only one makes them diverge.
- **The per-connection state (`ConnectionSession`) gains one identifier slot.**
- **Disconnect handling changes only `detach`** — keeping a trace → removal. **Do not create a second removal point** (the causality would split).
- **★What we accepted: we lose the distinction between 「그런 명령 없음」 and 「주인이 자리 비움」.★** The reason ADR-0156 kept traces was exactly that distinction, and this decision gives it up. In exchange, 「아무도 안 받음」 is decided **from live registrations only**. If that distinction becomes truly necessary, we resolve it **not by reviving traces** but by putting a connection list in the response (outside this scope — the fence of decision 5).
- **A connection that did not send the identifier makes its owner from the connection id as now (fail-open).** No strict-match gate is put in place — with fail-closed, every registration becomes impossible (this repository has already suffered the same failure).
- **If the same identifier comes from two connections, the later registration wins** (current behavior kept — no new code).
- **The existing `owner` field of the registration message is still ignored.** Removing it is also a contract change and gains nothing — leave a comment with the reason.
- **The entry cap is on a different axis from ADR-0152** — what 0152 decided to put no cap on is the caller string **going out in a rejection response**, while this is a value **coming in before authentication**. Do not mix them.
- **Attach the code anchor `// ADR-0150`** to the registry owner derivation · the `detach` removal point · the first-greeting identifier validation.
