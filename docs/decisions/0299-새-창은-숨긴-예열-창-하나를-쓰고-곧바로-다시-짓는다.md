# ADR-0299: 새 창은 숨긴 예열 창 하나를 쓰고 곧바로 다시 짓는다

- 상태: 확정 (2026-10-21, 근거: 사용자 결정(「예비창을 띄워줘」 · 조사 `docs/research/slot-docking-drag-ux-followups-2026-10-21.md` 부록 「결정(사용자 2026-10-21): 예열 창 — 앱이 뜰 때 숨긴 창 하나를 늘 유지하고, 바탕화면 놓기의 새 창은 그 창을 쓴 뒤 곧바로 다시 하나 짓는다.」) + 같은 조사 §1(새 창 지연 구간 표 · 줄이는 길 표)) · 어느 새 창이 쓰나 = (b) 새 label 로 여는 새 창 전부 · 활성화 없이 여는 창도 포커스 없이 z 만 올려(사용자 결정 2026-10-21 · 결정 5 · TRD §9-3 예열 F1 · I4)
- 관련: Amends ADR-0296 (결정 5 중 예비 창 걷기) · TRD `docs/process/S21-slot-docking/trd.md`(7판 개정 2026-10-21 — §3-9 · §7 U4a′–U4d′ · §8-5 M14–M22 · §9-3) · 옛 예열 조사 `.claude/handoff/attachments/slot-docking-popout-prewarm-research-2026-10-19.md`(미추적) · 첫 화면 문 `src-tauri/src/first_paint.rs:1-3`(사용자 결정 2026-10-19 「창은 내용과 함께 뜬다」) · CLAUDE.md 「LLM-우선 제어」

## 맥락

U3 뒤 사용자 실측(2026-10-21) — 바탕화면 놓기의 새 창이 늦다. 조사 §1(표본 `slot-popup-9` · 개발 빌드)의 구간: dragend → 보임 ≈ 0.6 s = WebView2 창 · 컨트롤러 짓기 ≈ 0.16 s(실측 1) · 개발 서버 모듈 적재 · 실행 ≈ 0.27 s · 마운트 · 직렬 IPC ≈ 0.10 s · 첫 화면 문 ≈ 0.03 s. 릴리즈 추정(미측) = dragend → 보임 ≈ 0.33–0.42 s. 대부분이 창 짓기 + 페이지 적재다(조사 결론 1 — 확신 = 가능성 높음).

부팅 때 지어 두는 예비 창(`slot-popup-1`)이 있지만 새 끌기 경로는 그것을 쓰지 않고 매번 새로 짓는다(`reused=false` — 조사 결론 2 · 로그 · 코드). 옛 엔진의 예비 창은 「준비됨」이 되지도 않는다 — 준비 판정(`src-tauri/src/dock/parked.rs:36-43`)이 크롬 보고까지 요구하는데, 그 보고는 마운트되지 않은 옛 훅 `useTabDrag.ts` 가 부르는 `frameReport.ts` 에서만 나간다(설계 초안 · 코드 독해). ADR-0296 결정 5 와 TRD 7판 U4a–U4c 는 이 예비 창을 걷기로 했었다. 옛 예열 조사(2026-10-19)와 이번 조사 결론 2 는 같은 길(숨긴 예열 창 채택 — Electron `show:false` · Chrome spare renderer)을 가리킨다.

## 결정

1. **앱이 뜰 때 숨긴 예열 창 하나를 늘 유지한다. 바탕화면 놓기의 새 창은 짓지 않고 그 창에 탭을 넣어 보인다 — 새 label 로 여는 다른 새 창도 같은 창을 쓴다(결정 5). 쓴 뒤 곧바로 다음 예열 창을 하나 짓는다**(사용자 결정 2026-10-21 — 「예비창을 띄워줘」 · 조사 부록 「앱이 뜰 때 숨긴 창 하나를 늘 유지하고, 바탕화면 놓기의 새 창은 그 창을 쓴 뒤 곧바로 다시 하나 짓는다」 — `docs/research/slot-docking-drag-ux-followups-2026-10-21.md:109`. 사용자 말이 덮는 것은 바탕화면 놓기의 새 창까지다).
2. **예열 창이 없으면 지금처럼 새로 짓는다** — 폴백 길은 바꾸지 않는다 · 단 포커스 없는 요청의 폴백 새 창은 포커스 없이 짓고 올리기만 한다(결정 5 · TRD I30)(같은 조사 「줄이는 길」 표 A 의 단점 줄 「0.5 s 안의 연속 끌기는 새로 짓기로 떨어짐」 — `docs/research/slot-docking-drag-ux-followups-2026-10-21.md:37` · 경우 = TRD §3-9).
3. **창은 내용과 함께 뜬다** — 예열 창도 탭을 넣고 첫 화면을 그린 뒤에 보인다. 빈 틀을 먼저 보이지 않는다(사용자 결정 2026-10-19 — 기록 = `src-tauri/src/first_paint.rs:2-3` 의 주석). 기다리는 동안은 숨긴 채다 — 화면 밖 대기 자리를 두지 않는다(사용자 결정 2026-10-19 — 기록은 코드 주석 하나뿐이고 문서에는 없다. 그 주석은 TRD §7 U4c′-2 가 옮겨 지금 `src-tauri/src/commands/spare.rs:74` 에 있다(옛 자리 `commands/dock.rs:119` — 그 파일은 없어졌다) — 이 결정이 문서 기록이 된다).
4. **안내 창(옛 엔진의 투명 덮개 창)은 그대로 걷는다** — HTML5 길은 안내를 페이지 안에 그린다(TRD §4-4).
5. **어느 새 창이 예열 창을 쓰나 = (b) 새 label 로 여는 새 창 전부**(사용자 결정 2026-10-21 — 「예비창 하나 갖고잇으면 그런것도 자동으로 적용되는거 아님?」 → 메인이 (b) 로 정리해 확인 → 「ㅇㅇ 시작해.」 · TRD §9-3 예열 F1) — 놓기(바탕화면 · 출처 dragend · 우리 웹뷰 안 칸 가운데 놓기의 새 창 `NewWindow{by: Drop}` 포함) + 메뉴 「팝업으로 분리」 + LLM `slot.popout` · `window.create` · 뒤에 T-65 `tab.dock`. 고르지 않은 것 = (a) 바탕화면 놓기 · 출처 dragend 의 새 창만(사용자 말 그대로) — 새 창 여는 세 길(놓기 · T-65 = 적용 서비스 `open_new_window` · 메뉴 · LLM `slot.popout` = `move_slot_to_window` · LLM `window.create` = `create_window`)이 모두 같은 창 포트(`WindowHost`)를 지나므로 포트에 맡기면 세 길이 함께 쓴다 · (a) 는 놓기에만 켜는 표시를 더해야 하고, 메뉴 · LLM 길이 마우스 길과 다르게 군다(CLAUDE.md 「LLM-우선 제어」 · 옛 판은 세 길이 `open_new_window` 하나를 지난다고 잘못 적었다). 대가 = 메뉴 팝아웃 바로 뒤의 끌기 새 창은 다음 예열 창이 아직 안 지어져 새로 짓기(오늘 속도)로 떨어진다. **이 「새 창」은 지금 열 창을 새로 만드는 길이다 — 저장된 창 되살리기는 들지 않는다**(메인이 정함 · TRD §3-9) — 부팅 ⑨ 복원과 런타임 크래시 사본 수락은 지금처럼 새로 짓는다: 창 포트(`WindowHost`)를 지나지 않는 다른 길이고(크래시 사본 수락은 포트 `RestoreWindows`), 저장된 자리 + 미룬 최대화를 지을 때 입히며, 부팅 복원은 예열 창이 지어지기 전에 돈다. **활성화 없이 여는 새 창도 예열 창을 쓴다 — 보일 때 포커스를 빼앗지 않고 z 만 맨 위로 올린다**(사용자 결정 2026-10-21 「ㅇㅇ 그래 포커스 뺏지말고, 순서만 위로올려.」 — 뒤의 T-65 `tab.dock`(`FocusPolicy::Keep`)과 우리 앱이 전경이 아닐 때 LLM 이 여는 창이 묻던 것 · 그래서 (b) 가 통째로 선다) — 활성화(`set_focus`)는 활성으로 연 맡김이고 전경이 우리 프로세스일 때만이다(가짜 Alt 로 전경을 빼앗지 않는다 · TRD §9-3 I4 · I5) · 예열 창이 없어 새로 지어도 같다 — 포커스 없이 짓고 올리기만 한다(TRD I30). 올리기만으로 남의 앱 전경 창 위에 서는지는 미측이다(Windows 전경 잠금 규칙 — TRD §8-5 M22 · 안 서면 정지 조건 §9-1 · 우회를 지어내지 않는다).

## 거부한 대안

- **예열 없음(지금 그대로 — 새 창마다 새로 짓기)** — 잰 지연이 남는다: 개발 dragend → 보임 ≈ 0.6 s(표본 1 실측 + 로그 3 회 일치 · 조사 §1) · 릴리즈 추정 0.33–0.42 s(미측). 그 대부분인 짓기 + 적재 몫은 미리 지어 두지 않으면 빠지지 않는다(조사 결론 1). 기각 강도 = 실측(지연 구간).
- **B — 끌기가 출처 창을 떠날 때 미리 짓기**(조사 「줄이는 길」 표) — 우리 창에 놓으면 헛짓기다(코드 — 우리 웹뷰가 받은 놓기는 새 창을 만들지 않는다). 짓기가 메인 스레드를 ≈ 160 ms 묶어(실측 1 · 옛 스파이크 S8 fresh 163–222 ms) 끄는 동안 다른 창의 동기 명령이 선다. 기각 강도 = 실측(짓기 ≈ 160 ms) + 코드(헛짓기).
- **활성화 없이 여는 새 창은 예열 창 대신 새로 짓기**(옛 TRD I4 · 사용자에게 올린 갈래 A) — 뒤에서 새로 지은 창이 남의 앱 뒤에 설 수 있다고 들은 뒤 사용자가 기각했다(「ㅇㅇ 그래 포커스 뺏지말고, 순서만 위로올려.」). 기각 강도 = 사용자 결정.
- **뒤에서 연 창을 `set_focus` 로 활성화**(tao `force_window_active` 의 가짜 Alt 로 전경을 빼앗음) — 사용자가 치고 있던 앱의 키보드 포커스를 빼앗는다. 기각 강도 = 사용자 결정(같은 인용 「포커스 뺏지말고」).
- **올리지 않고 옛 z 자리 그대로 보이기** — 전경 앱 뒤에 설 수 있다. 기각 강도 = 사용자 결정(같은 인용 「순서만 위로올려」).

## 근거

- 조사 `docs/research/slot-docking-drag-ux-followups-2026-10-21.md` §1 구간 표 — 짓기 ≈ 160(실측 1) · 개발 모듈 폭포 ≈ 185 + 실행 → DOMContentLoaded ≈ 80(실측) · 직렬 데이터 사슬 ≈ 77(끝점 실측 + 코드) · 첫 화면 문 ≈ 33(실측). 메뉴 「팝업으로 분리」 = 375 ms — 같은 길.
- 관행 — 옛 예열 조사(2026-10-19 · 미추적 · 확신 = 가능성 높음): 숨긴 예열 창 1 개 → 채택 → 콘텐츠 커밋 뒤 show → 곧바로 재예열 · 재예열 중이면 cold 폴백(Electron 공식 · Lody PR #811 · Chrome spare RenderProcessHost · WebView2 성능 문서).
- **기대 이득은 가설이다** — 옛 스파이크 S8 「pool」(보임 p50 35.8 ms · 깜빡임 0)은 이미 그려 둔 화면 밖 창을 옮겨 온 다른 흐름의 값이고, 숨긴 창의 첫 보임은 잰 적이 없다(조사 결론 2 · `.claude/handoff/attachments/spike-chrome-drag-2026-10-18.md:78-96`). 빠질 것으로 보는 몫 = 짓기 ≈ 160 + 개발 모듈 적재 ≈ 270 · 남는 몫 = 직렬 IPC ≈ 77 + 문 ≈ 33(추정 — TRD §8-5 M14 가 잰다).

## 영향 / 불변식

- **ADR-0296 결정 5 의 「예비 창」 걷기를 뒤집는다.** 결정 5 의 나머지(창 이동 루프 · 훅 · 셸 끌기 세션 · 커서 밑 창 판정 · 기하 보고 걷기)와 안내 창 걷기는 그대로다.
- **TRD 7판 U4a–U4c 를 U4a′ · U4b′ · U4c′-1 · U4c′-2 · U4d′ 로 다시 짠다**(TRD §7) — 옛 엔진 걷기 먼저 · 채택 마지막 · 어느 단위 뒤에 멈춰도 초록. 웹 대기 모드를 남기므로 옛 §7 의 「웹이 대기 모드를 먼저 걷으면 예비 창이 탭 0 개로 스스로 닫히고 셸이 다시 짓는 고리」 위험이 없어진다.
- **메모리** — 숨은 WebView2 하나가 늘 산다. 크기는 미측이다(TRD §8-5 M18). 그 수치는 사용자에게 올린다 — 「늘 하나」를 다시 볼 만큼 크면 정지 조건이다(TRD §9-1 · §9-3 예열 F3 · F4).
- **다시 짓기의 메인 스레드 점유**(≈ 160 ms)가 채택한 창이 보인 직후에 놓인다 — 크기 미측(TRD §8-5 M17).
- **LLM** — 새 표면이 없다. 예열 창은 창 포트(`layout::apply::WindowHost`) 뒤의 셸 어댑터에 살고, 버스 `slot.popout` · `window.create` 도 같은 적용 함수 · 같은 포트를 지난다. 예열 창은 맡기기 전까지 모델 밖이라 `window.list` · `state.json` 에 나오지 않는다. 맡긴 뒤에는 적용 서비스가 모델에 넣은 때부터 나온다 — 채택 확정까지의 짧은 틈은 새로 지어 첫 화면을 기다리는 창과 같고, 그 틈에는 셸 풀의 술어(트레이 · 자리 기록 · 창 역할 답)가 모델보다 이긴다(TRD §3-9 「자리별 차례」 — 옛 판의 「채택 전까지 모델 밖」은 그 틈을 빠뜨렸다).
- **플랫폼** — 예열 창 코드에 `cfg` 가 없고 새 OS 호출도 없다 — 맡긴 창의 z 올리기는 platform 에 이미 있는 `window::place_window` · `ZOrder` 를 쓰므로(`ZOrder::Top` · 활성화 없이 — 결정 5 · TRD §9-3 I4 · I29) **그 둘은 걷지 않고 남긴다**(TRD §7 U5 — 옛 판은 활성화 없는 새 창을 새로 지어 둘이 필요 없다고 적었다). 전경 판정은 `window::foreground_is_current_process`. macOS · WebKitGTK 의 숨긴 웹뷰 동작과 올리기는 미검이다.
- 조사 「줄이는 길」 표의 C(첫 화면 재료를 실어 보냄) · D(경로별 코드 분할) · E(첫 화면 문 rAF 하나로)는 이 결정이 정하지 않는다 — 채택도 기각도 아니다.
- 앵커 — 예열 창 풀 · 창 포트의 예열 메서드 · 채택 확정(`committed`)에 `// ADR-0299` 를 단다.
