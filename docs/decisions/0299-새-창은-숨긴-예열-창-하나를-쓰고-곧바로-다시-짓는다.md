# ADR-0299: A new window uses one hidden prewarmed window and rebuilds the next one right away

- 상태: 확정 (2026-10-21, 근거: user decision (「예비창을 띄워줘」 · survey `docs/research/slot-docking-drag-ux-followups-2026-10-21.md` appendix 「결정(사용자 2026-10-21): 예열 창 — 앱이 뜰 때 숨긴 창 하나를 늘 유지하고, 바탕화면 놓기의 새 창은 그 창을 쓴 뒤 곧바로 다시 하나 짓는다.」) + §1 of the same survey (the new-window latency segment table · the shortening-paths table)) · which new windows use it = (b) every new window opened with a new label · a window opened without activation also only gets raised in z, without focus (user decision 2026-10-21 · decision 5 · TRD §9-3 prewarm F1 · I4)
- 관련: Amends ADR-0296 (removing the spare window in decision 5) · TRD `docs/process/S21-slot-docking/trd.md` (edition 7 revision 2026-10-21 — §3-9 · §7 U4a′–U4d′ · §8-5 M14–M22 · §9-3) · old prewarm survey `.claude/handoff/attachments/slot-docking-popout-prewarm-research-2026-10-19.md` (untracked) · first-paint gate `src-tauri/src/first_paint.rs:1-3` (user decision 2026-10-19 「창은 내용과 함께 뜬다」) · CLAUDE.md 「LLM-우선 제어」

## 맥락

The user's measurement after U3 (2026-10-21) — the new window from a desktop drop is slow. The segments in survey §1 (sample `slot-popup-9` · dev build): dragend → shown ≈ 0.6 s = building the WebView2 window and controller ≈ 0.16 s (measurement 1) · dev server module load and execution ≈ 0.27 s · mount and serial IPC ≈ 0.10 s · first-paint gate ≈ 0.03 s. Release estimate (not measured) = dragend → shown ≈ 0.33–0.42 s. Most of it is window building + page loading (survey conclusion 1 — confidence = likely).

There is a spare window built at boot (`slot-popup-1`), but the new drag path does not use it and builds a new one each time (`reused=false` — survey conclusion 2 · log · code). The spare window of the old engine never even becomes 「준비됨」 — the ready decision (`src-tauri/src/dock/parked.rs:36-43`) also requires the chrome report, and that report goes out only from `frameReport.ts`, which is called by the old hook `useTabDrag.ts` that is not mounted (design draft · code reading). ADR-0296 decision 5 and TRD edition 7 U4a–U4c had decided to remove this spare window. The old prewarm survey (2026-10-19) and conclusion 2 of this survey point to the same path (adopt a hidden prewarmed window — Electron `show:false` · Chrome spare renderer).

## 결정

1. **Always keep one hidden prewarmed window when the app starts. For the new window of a desktop drop, do not build one — put the tab into that window and show it — the other new windows opened with a new label use the same window too (decision 5). Right after using it, build the next prewarmed window** (user decision 2026-10-21 — 「예비창을 띄워줘」 · survey appendix 「앱이 뜰 때 숨긴 창 하나를 늘 유지하고, 바탕화면 놓기의 새 창은 그 창을 쓴 뒤 곧바로 다시 하나 짓는다」 — `docs/research/slot-docking-drag-ux-followups-2026-10-21.md:109`. What the user's words cover goes as far as the new window of a desktop drop).
2. **If there is no prewarmed window, build a new one as now** — the fallback path is not changed · but the fallback new window of a request without focus is built without focus and is only raised (decision 5 · TRD I30) (the downside line of table A in the same survey's 「줄이는 길」, 「0.5 s 안의 연속 끌기는 새로 짓기로 떨어짐」 — `docs/research/slot-docking-drag-ux-followups-2026-10-21.md:37` · cases = TRD §3-9).
3. **The window appears together with its content** — the prewarmed window too is shown only after the tab is put in and the first screen is drawn. An empty frame is not shown first (user decision 2026-10-19 — recorded in the comment of `src-tauri/src/first_paint.rs:2-3`). While waiting, it stays hidden — no off-screen waiting spot is kept (user decision 2026-10-19 — the only record is one code comment and it is not in a document. TRD §7 U4c′-2 moved that comment and it is now at `src-tauri/src/commands/spare.rs:74` (the old place `commands/dock.rs:119` — that file is gone) — this decision becomes the document record).
4. **The guide window (the transparent overlay window of the old engine) is removed as is** — the HTML5 path draws the guide inside the page (TRD §4-4).
5. **Which new windows use the prewarmed window = (b) every new window opened with a new label** (user decision 2026-10-21 — 「예비창 하나 갖고잇으면 그런것도 자동으로 적용되는거 아님?」 → the main agent summarized it as (b) and confirmed → 「ㅇㅇ 시작해.」 · TRD §9-3 prewarm F1) — drop (desktop · source dragend · including the new window `NewWindow{by: Drop}` of a drop on the middle of a cell inside our webview) + the menu 「팝업으로 분리」 + LLM `slot.popout` · `window.create` · later T-65 `tab.dock`. What was not chosen = (a) only the new window of a desktop drop · source dragend (the user's words as they are) — the three paths that open a new window (drop · T-65 = the application service `open_new_window` · menu · LLM `slot.popout` = `move_slot_to_window` · LLM `window.create` = `create_window`) all go through the same window port (`WindowHost`), so if it is left to the port the three paths use it together · (a) would need an added flag turned on only for the drop, and the menu and LLM paths would behave differently from the mouse path (CLAUDE.md 「LLM-우선 제어」 · the old edition wrongly wrote that the three paths go through the single `open_new_window`). Cost = the drag new window right after a menu popout falls back to building fresh (today's speed) because the next prewarmed window is not built yet. **This 「새 창」 is the path that creates a window to open now — restoring a saved window is not included** (decided by the main agent · TRD §3-9) — boot ⑨ restore and the runtime crash-copy acceptance build fresh as now: they are other paths that do not go through the window port (`WindowHost`) (crash-copy acceptance is the port's `RestoreWindows`), and the saved position + the deferred maximize are applied when building, and boot restore runs before the prewarmed window is built. **A new window opened without activation also uses the prewarmed window — when shown, it does not take focus and is only raised to the top of z** (user decision 2026-10-21 「ㅇㅇ 그래 포커스 뺏지말고, 순서만 위로올려.」 — what the later T-65 `tab.dock` (`FocusPolicy::Keep`) and the window the LLM opens while our app is not in the foreground were asking · so (b) stands as a whole) — activation (`set_focus`) is a hand-over opened as active, and only when the foreground is our process (no taking the foreground with a fake Alt · TRD §9-3 I4 · I5) · the same when it is built fresh because there is no prewarmed window — it is built without focus and only raised (TRD I30). Whether raising alone puts it above another app's foreground window was measured (2026-10-21 · TRD §8-5 M22 · `/qa full` · unlocked session): when Notepad was the foreground, the bus `window.create` · `slot.popout` new windows 30/30 (both prewarmed and built fresh) did not take focus (`GetForegroundWindow` stayed Notepad) and stood **right below** the foreground window · above the other windows — the raise call succeeds (no 「z 를 올리지 못하고」 warn) and Windows keeps the foreground window on top (cause is a guess · not proven). The user then decided (2026-10-21 — after being shown the stack 「1. 지금 쓰는 창 2. 새 창 3. 나머지」, 「내가 타자치는거 밑에 가면 좋은거 아님?」): this behavior is accepted as intended — the stop condition is lifted.

## 거부한 대안

- **No prewarm (as now — build fresh for every new window)** — the measured latency remains: dev dragend → shown ≈ 0.6 s (sample 1 measurement + 3 log runs agree · survey §1) · release estimate 0.33–0.42 s (not measured). Most of it, the building + loading share, does not go away unless built in advance (survey conclusion 1). Strength of rejection = measurement (latency segments).
- **B — build in advance when the drag leaves the source window** (the survey's 「줄이는 길」 table) — it is a wasted build if dropped on our window (code — a drop received by our webview does not create a new window). The build holds the main thread for ≈ 160 ms (measurement 1 · old spike S8 fresh 163–222 ms), so synchronous commands of other windows stall during the drag. Strength of rejection = measurement (build ≈ 160 ms) + code (wasted build).
- **For a new window opened without activation, build fresh instead of using the prewarmed window** (old TRD I4 · branch A raised to the user) — the user rejected it after hearing that a window freshly built in the background can end up behind another app (「ㅇㅇ 그래 포커스 뺏지말고, 순서만 위로올려.」). Strength of rejection = user decision.
- **Make the new window briefly always-on-top (`HWND_TOPMOST` → `NOTOPMOST`) to put it over the foreground window** — a new window pops up over the window the user is typing in and fights Windows' foreground protection. Strength of rejection = user decision (2026-10-21 「내가 타자치는거 밑에 가면 좋은거 아님?」 — below the foreground window is the intended behavior). Not tried.
- **Activate the window opened in the background with `set_focus`** (taking the foreground with the fake Alt of tao `force_window_active`) — it takes keyboard focus from the app the user was typing in. Strength of rejection = user decision (the same quote 「포커스 뺏지말고」).
- **Show it at its old z position without raising** — it can end up behind the foreground app. Strength of rejection = user decision (the same quote 「순서만 위로올려」).

## 근거

- Survey `docs/research/slot-docking-drag-ux-followups-2026-10-21.md` §1 segment table — build ≈ 160 (measurement 1) · dev module waterfall ≈ 185 + execution → DOMContentLoaded ≈ 80 (measured) · serial data chain ≈ 77 (endpoint measured + code) · first-paint gate ≈ 33 (measured). The menu 「팝업으로 분리」 = 375 ms — the same path.
- Practice — the old prewarm survey (2026-10-19 · untracked · confidence = likely): one hidden prewarmed window → adopt → show after the content commit → re-prewarm right away · cold fallback while re-prewarming (Electron official · Lody PR #811 · Chrome spare RenderProcessHost · WebView2 performance docs).
- **The expected gain is a hypothesis** — the old spike S8 「pool」 (shown p50 35.8 ms · flicker 0) is a value of a different flow that moved over an off-screen window that was already drawn, and the first show of a hidden window was never measured (survey conclusion 2 · `.claude/handoff/attachments/spike-chrome-drag-2026-10-18.md:78-96`). The share expected to go away = build ≈ 160 + dev module load ≈ 270 · the share that remains = serial IPC ≈ 77 + gate ≈ 33 (estimate — TRD §8-5 M14 measures it).

## 영향 / 불변식

- **It reverses the removal of the 「예비 창」 in ADR-0296 decision 5.** The rest of decision 5 (removing the window move loop · hook · shell drag session · window-under-cursor decision · geometry reporting) and removing the guide window stay as they are.
- **TRD edition 7 U4a–U4c are rebuilt as U4a′ · U4b′ · U4c′-1 · U4c′-2 · U4d′** (TRD §7) — remove the old engine first · adopt last · green after stopping at any unit. Because the web wait mode is kept, the risk in the old §7, 「웹이 대기 모드를 먼저 걷으면 예비 창이 탭 0 개로 스스로 닫히고 셸이 다시 짓는 고리」, is gone.
- **Memory** — one hidden WebView2 is always alive. Its size is not measured (TRD §8-5 M18). That number is raised to the user — if it is large enough to reconsider 「늘 하나」, it is a stop condition (TRD §9-1 · §9-3 prewarm F3 · F4).
- **Main-thread occupation of the rebuild** (≈ 160 ms) falls right after the adopted window is shown — size not measured (TRD §8-5 M17).
- **LLM** — no new surface. The prewarmed window lives in the shell adapter behind the window port (`layout::apply::WindowHost`), and the bus `slot.popout` · `window.create` also go through the same apply function · the same port. Until handed over, the prewarmed window is outside the model, so it does not appear in `window.list` · `state.json`. After handover it appears from the time the application service puts it into the model — the short gap until adoption is confirmed is the same as a window freshly built and waiting for its first screen, and in that gap the predicates of the shell pool (tray · position record · window role answer) win over the model (TRD §3-9 「자리별 차례」 — the old edition's 「채택 전까지 모델 밖」 missed that gap).
- **Platform** — there is no `cfg` in the prewarmed window code and no new OS call — raising z of the handed-over window uses `window::place_window` · `ZOrder` that already exist in platform (`ZOrder::Top` · without activation — decision 5 · TRD §9-3 I4 · I29), so **those two are not removed and stay** (TRD §7 U5 — the old edition wrote that the two are not needed because a window without activation is built fresh). The foreground check is `window::foreground_is_current_process`. The hidden-webview behavior and raising on macOS and WebKitGTK are unchecked.
- C (carry the first-screen material along) · D (per-path code splitting) · E (first-paint gate with a single rAF) in the survey's 「줄이는 길」 table are not decided by this decision — neither adopted nor rejected.
- Anchors — put `// ADR-0299` on the prewarmed window pool · the prewarm method of the window port · adoption confirmation (`committed`).
