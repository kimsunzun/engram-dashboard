# ADR-0152: Put no length cap on the caller string echoed back in a rejection response

- 상태: 확정 (2026-08-17, basis: user decision 2026-08-17)
- 관련: ADR-0157 (unknown fields in command arguments — rejected at the entrance) · ADR-0150 (entry cap — **a different axis, in the opposite direction**) · ADR-0156 (opaque bundling of `help`) · CLAUDE.md 「LLM-우선 제어」 · `docs/process/S20-command-bus/trd.md` **§4-②** (the place this decision is recorded) · clause 6 of §3-7 in the same document (**the opposite axis** — the entry cap on the first-greeting identifier. Its direction is the opposite of this one)

## 맥락

The guidance text (`hint`) of a rejection response carries **the string the caller sent, with no limit.** This topic has come back up **four rounds in a row**, and every time the claim 「여기가 유일한 상한 자리」 (this is the only place for a cap) turned out wrong.

**A previous session put a cap in and then reverted it.** After building the whole envelope it **cut the tail at the end**, and that tail contained **the executable command at the end of the guidance text, whole** (measured **5182B → 4122B**, **zero** command quotations in the result).

**It was settled this session that the reader is an LLM agent.** The CLI **prints the response body to standard output without processing**, and the agent we spawned reads it (code comment: "읽는 쪽이 LLM이라 파싱이 아니라 독해 대상"). A bounce body can carry **information the sending agent reads and uses to correct itself**. So if the tail is cut, unlike a human who asks back "it got cut off", **the agent's next action vanishes entirely.**

**Leaking places measured (2026-08-17) = 5.** Three on the command-bus side (unknown verb · broken body · the core's targeting failure and collision token) + one on the mail side (group not found — it is a **different envelope type**, so the same cap does not reach it) + ★**a 5th not in the record** — the mail 「수신자 모호」 (recipient ambiguous) guidance puts the recipient name, with no limit, in the **per-row hint inside a success envelope**★.

## 결정

1. **Put no length cap on the caller string echoed back in a rejection or guidance response.** Keep the current behavior.
2. **If a problem actually arises, raise it again then** (user: "나중에 문제 생기면 얘기해").
3. **★Change the name of the scope — it is not 「거절 문구 상한」 but 「호출자가 보낸 문자열을 되돌려주는 모든 자리」 (every place that returns a string the caller sent).★** The next time this topic is opened, investigate exhaustively under this name. If the scope is set as 「거절」, **the 5th place (inside a success envelope) structurally is not caught.**
4. **Do not write 「여기가 유일한 상한 자리」 (this is the only place for a cap).**

## 거부한 대안

- **A. Cut the tail at the envelope render point** — A previous session **actually executed it and reverted it.** Measured 5182B→4122B, the executable command at the end of the guidance text vanished with zero backticks. Because the reader is an LLM, that loss is not "hard to read" but **"loss of the next action"**. ★Strength of the rejection basis = **quantitative measurement**★.
- **B. Put an individual cap at each place where the caller string lands** — Technically the right shape, and it does not damage the guidance text. **But there are 5 places, and two of them have a different envelope type or are inside a success envelope, so one cap does not cover them.** The user's judgment: **do not do it, since there is no real damage now.** ★Strength of the rejection basis = **weak** (a statement that damage is absent) — accepted because it is an easily reversible hold★.
- **C. Put the cap in through a common utility for the two envelopes** — A variant of B. Held for the same reason. The two envelopes share **only the shape** `{code, hint}` and their **types are separate** (code comment "에러 축만 공유"), so the commonization itself carries separate work.

## 근거

- **Unlimited echo is a property that existed before this piece** — it is not a new regression. Not fixing it does not make the state worse.
- **The revert remains as a quantitative measurement** (5182B→4122B, zero backticks). This number is the basis for not repeating the same mistake.
- **We confirmed in code that the two kinds of envelope are separated by type** — putting a cap on one side leaves the other side as it is. The intuition "fix one place and it is done" does not hold in this structure.

## 영향 / 불변식

- **★Do not confuse with ADR-0150's entry cap★** — 0150 **puts** a cap and a character-set limit on a value **coming in before authentication** (the client identifier in the first greeting). This ADR **puts no** cap on a value **going out**. **Their directions are opposite, so they do not contradict each other.** Trying to merge the two into one rule breaks one of them.
- **Next time a cap is put in, put it at the place where the caller string lands, not at the end of the envelope.** Cutting at the end of the envelope is an approach that has already failed.
- **Do not forget the 5th place** — the mail 「수신자 모호」 is **not a rejection but a per-row guidance inside a success response**.
- **The ban on 「여기가 유일한 상한 자리」 is a hard rule** — it was false four rounds in a row. To count the places, do not copy the record but **sweep the code again.**
- This decision is **a record of something decided not to be done.** If the next session brings it up again as "there is no cap", read here first.
