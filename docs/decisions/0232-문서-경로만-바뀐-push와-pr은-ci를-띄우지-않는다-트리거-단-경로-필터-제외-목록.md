# ADR-0232: A push or PR that changes only docs paths does not start CI — a trigger-level path filter exclusion list

- 상태: 확정 (2026-09-26, basis: user decision + one round of adversarial review) · 부분 폐기 by ADR-0285 (the include_str basis for rejecting a blanket md exclusion)
- 관련: `docs/research/ci-docs-skip-conventions-2026-09-26.md`(survey of mature OSS — done after the decision) · `on.push.paths` in `.github/workflows/ci.yml` (canonical list) · `on.pull_request.paths` in the same file (same list) · `src/util/launcherWiring.test.ts`(the test that reads the revived file) · `docs/tracking.md` T-18(branch protection — not adopted) · CLAUDE.md 「CI — push하면 자동으로 돈다」·「브랜치·커밋」(exception to the merge rule) · `.claude/skill-bindings/qa.md` 「CI와의 분담」 · Amends ADR-0131 (decision 2: excludes pushes and PRs that change only docs paths from the every-push scope) · Amended by ADR-0285 (the include_str basis for rejecting a blanket md exclusion)

## 맥락

The workflow starts all 3 verification jobs on a Windows runner on **every push to any branch** — a push that edits only CLAUDE.md or `docs/` is no exception. Measured = a commit of 11 doc files took 6 min 44 s and went green (2026-08-23 — the record that was written, until this decision, in the numbering-reservation item of `.claude/skill-bindings/adr.md`).

- **Raised by the user (2026-08-26 — it was posted as the 「CI 실행 범위」 item of `docs/todo.md`):** even if only docs change, all 3 verification jobs run in full. Runner cost is zero (public repo), but the waiting is irritating.
  - The observation that item also recorded — that day CI ran five times for docs work, and four of them were caused by **pushing commits one at a time** (each push makes `concurrency` cancel the earlier run and start a new one). Pushing them together runs it once. This still applies, after this decision, to pushes that mix in files outside docs. That item (`docs/todo/ci-scope.md`) was resolved by this decision and deleted.
- **User requirement (2026-09-26):** run CI only when a file that affects CI changes.

## 결정

1. **Put a trigger-level `paths` on `on.push` and `on.pull_request`, in the shape of an exclusion list.** The first entry `'**'` includes every path, then four paths are removed (`docs/**` · `CLAUDE.md` · `README.md` · `.claude/**`), and **at the very end** the one file `.claude/skill-bindings/qa.md` is revived. If **all** changed files are inside the removed paths, the workflow does not start; if even one is outside (including the revived file), everything runs exactly as before. The draft had the `paths-ignore` shape and was changed to this shape after the adversarial review (first item of the rejected alternatives below).
   - **Why it was revived** — that file is a CI test input. `src/util/launcherWiring.test.ts`, which the frontend job's `npm test` runs, reads the commands inside the fences of that file and asserts on them (`describe('the /qa GUI gate procedure …')`). If it is left out, a push that changes only that file does not run the test that checks that file.
   - **Why `paths` and not `paths-ignore`** — the documentation recommends 「제외만 할 때 `paths-ignore`, 포함과 제외를 섞을 때 `!` 를 붙인 `paths`」, and the two cannot be placed together on one event (basis ⑤). Some projects revive with `!` inside `paths-ignore` (Node), but the documentation does not guarantee that behavior — it was left as undecidable (`docs/research/ci-docs-skip-conventions-2026-09-26.md`). `'**'` is the same as the default behavior when there is no path filter (basis ⑤), so this shape is still an exclusion list — every unknown path falls to 「돈다」.
2. **The canonical list is `on.push.paths` in `ci.yml`.** Other documents only point to that place and do not copy the entries. `on.pull_request.paths` is kept identical, including order.
3. **A `v*` tag push and `workflow_dispatch` are unaffected** — path filters are not evaluated on a tag push (basis ① below), and `workflow_dispatch` has no path filter. The release trigger and the 3 verification jobs before it run as before.

## 거부한 대안

- **`paths-ignore` alone** (the draft's shape — listing the four paths as they are) — reviving one file inside a removed path cannot be written in a shape the documentation guarantees (basis ⑤). It was changed after the adversarial review caught `qa.md` as a CI test input (basis below). Strength of the rejection basis = documentation (the shape GitHub recommends — not a prohibition).
- **An inclusion list (allowlist — list only the paths that touch CI positively in `paths:`. Different from the `'**'` + `!` shape of decision 1)** — rejected by the user (2026-09-26). The basis below was presented by the session that day, and the user accepted it when choosing the exclusion list (「그래 그럼 제외 목록으로 가자. 저렇게 4개면 된다는거잖아. 진행해」). The user gave no separate basis.
  - **The direction of being wrong is opposite.** If one entry is missed in an inclusion list, the gate **silently disappears** for changes to that path. If one is missed in an exclusion list, it **merely runs once more**.
  - **The paths that touch CI are scattered and not visible from names alone.** About 15 of the 23 tracked items at the root touch CI (surveyed 2026-09-26). Among them are non-obvious ones such as `prompts/*.md` (the second alternative below) · `rust-toolchain.toml` (the backend job reads the channel and asserts on it) · `vitest.config.ts` · `.gitattributes` (line-ending handling touches the fmt and binding sync gates — ★this item is a judgment and was not measured★).
  - **The list has to be fixed every time a new file appears at the root.**
  - Strength of the rejection basis = measured (the root item survey) + code (`include_str!` below).
- **Blanket exclusion of `**/*.md`** — the basis below was presented by the session on 2026-09-26, and the user accepted it when choosing the four-path list (the same utterance as above). The extension does not separate docs from shipped items. `prompts/engram-help.md` is baked into the binary with `include_str!` (`crates/engram-dashboard-daemon/src/bin/engram.rs:231`), and it is in the release manifest together with `prompts/agent-priming.md` (`scripts/build-release.ps1:50`). If these are excluded, a push that changes the help text or the priming has no gate. Strength of the rejection basis = code.
- **Job-level skipping** (the workflow always starts, and the first step checks the changed paths and skips jobs) — **presented to the user and not chosen. The user gave no separate reason for rejecting it.** Only the costs that can be stated as fact are left.
  - Gained: the run record is left as 「skipped」 · a job skipped by a condition is reported as 「Success」 (basis ④), so it is compatible with branch protection that requires checks · the merge-rule exception in 「영향」 below is not needed.
  - Paid: one runner start per push + change-detection logic (written by us or a third-party action).
  - ★Strength of the rejection basis = weak★ (it hangs on none of quantity, measurement or code). If revisit trigger ① below comes, this alternative is the first candidate.

## 근거

- **User decision (2026-09-26)** — the exclusion-list method · the four excluded paths · rejection of the inclusion list.
- **Adversarial review (2026-09-26 — Claude doc-aware + Codex blind, both FIX)** — the `paths` shape of decision 1 and the revival of `qa.md` fix the defect this review caught.
- ★**What reads the removed paths — the draft missed one**★. The draft grepped `.github/workflows/ci.yml` · `scripts/build-release.ps1` · `scripts/*.mjs` · `src-tauri/tauri.conf.json` · `src-tauri/build.rs` · Rust/TS sources and wrote 「네 경로를 읽는 것이 없다」, which was wrong — the adversarial review caught that `src/util/launcherWiring.test.ts:76` reads `.claude/skill-bindings/qa.md`. After the review, string literals pointing at the removed paths were swept again in code, scripts and workflows (`*.ts`·`*.tsx`·`*.rs`·`*.mjs`·`*.js`·`*.ps1`·`*.bat`·`*.yml`), and that one was the only thing that reads a file (the `"README.md"` in `crates/engram-dashboard-daemon/tests/engram_cli.rs` is a CLI argument string). ★Paths assembled at runtime cannot be seen this way★.
- **Repository state (`gh api`, 2026-09-26)** — public · no branch protection on master · 0 rulesets.
- **GitHub behavior — confirmed from the official documentation** (viewed 2026-09-26):
  - ① **Path filters are not evaluated on tag pushes** — "Path filters are not evaluated for pushes of tags." (https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#onpushpull_requestpull_request_targetpathspaths-ignore) Same section: if `branches` and a path filter are both set, it runs only when **both** are satisfied.
  - ② **How the changed-file list is built** — push uses a two-dot diff, PR uses a three-dot diff. Push to an existing branch = compare the head and base SHAs directly · push of a new branch = "a two-dot diff against the parent of the ancestor of the deepest commit pushed" · PR = compare the latest version of the topic branch with the commit where that branch was last aligned with the base. If no files changed, it does not run. (https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#git-diff-comparisons)
  - ③ **Limits** — if a push exceeds 1,000 commits it **always runs** · if diff generation times out it **always runs** · if the diff exceeds 3,000 files and the files the filter matches are not within the first 3,000 the filter returned, it **does not run** (same URL). For the third, ours has the `paths` shape, so the document's sentence applies as is — an accepted exception (see 「영향」 below).
  - ④ **The check of a workflow skipped by a path filter stays 「Pending」, and a PR that requires that check is blocked from merging.** The document's prescription = "Avoid requiring workflows that can be skipped." By contrast, **a job skipped by a condition (`if`) is reported as 「Success」.** (https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/troubleshooting-required-status-checks#handling-skipped-but-required-checks · the same sentence is also in the `paths` section of the workflow-syntax page above)
  - ⑤ **Exclusion in `paths`, and order** — `paths` and `paths-ignore` cannot be used together on one event · it recommends `paths-ignore` when only excluding and `paths` with `!` when mixing inclusion and exclusion · the filter pattern rules in general: "`!`: At the start of a pattern makes it negate previous positive patterns." · order is the meaning — a `!` pattern after a positive match removes, and a positive pattern after being removed by `!` revives · `'**'` is "the default behavior when you don't use a path filter". (same page as ① — the `paths` section and the filter pattern section)
- **Interpretation drawn from the documentation (confidence = likely)** — a push to an existing branch looks only at the range that push moved (reading the head and base of ② as the SHAs before and after the push — the document does not state that base is the pre-push SHA). So if only docs are pushed after a code push, no new run is created, and the verdict on the code is held by the earlier run. Since there is no new run, the cancellation of the earlier run by `concurrency` does not happen either. Not measured.
- ★**Survey of mature projects — done after the decision**★ — the deleted to-do (`docs/todo/ci-scope.md`) wrote down as a procedure to investigate with `/research` which of path filters and job-level skipping mature projects choose and why. It was not done at decision time (the user never explicitly said to skip it), and the user asked 「보통 그렇게 하나」, so it was done the same day = `docs/research/ci-docs-skip-conventions-2026-09-26.md`. Conclusion: it is within the convention for repositories without required checks · the samples that require checks mostly used job-level detection + an aggregation job (the same as the candidate of revisit ①) · if docs are a test input, the convention is not to exclude that path or to exclude it narrowly (Node `doc/` · Ruff) — the same purpose as our revival of `qa.md`. The settings were left as they are and only the exaggerated wording of this ADR was reduced. The two unknowns that to-do said to resolve before starting (does a path filter apply to a tag push · the trap where a required check is stuck at 「Pending」) were answered from the official GitHub documentation instead of the survey (①·④).

## 영향 / 불변식

- **Exception to the merge rule (CLAUDE.md 「브랜치·커밋」)** — a change that touches only the removed paths has no CI run, so it can be merged without green. But only when that was confirmed by a machine, and the canonical source for the confirmation command and the handling of 「빨강·취소 뒤 문서만 push」 (starting it by hand with `workflow_dispatch`) is that section.
- **A change that touches only the removed paths is seen by no gate — this decision stands on the premise that no gate reads the removed paths.** If a file a gate reads is inside a removed path, it is revived at the end of the list (now = `qa.md` alone). Also when adding an exclusion, first check whether anything reads below it. `.claude/**` also covers non-doc settings (`.claude/settings*.json` etc.) — no gate that reads them came out of the re-check above.
- **Put the reviving line at the very end of the list** — if a `!` line is added after it, it is removed again (basis ⑤).
- **Keep the push-side and PR-side lists identical, including order** — if only one side is fixed, push and PR run on different changes.
- **Accepted exception — the 3,000-file limit (basis ③)** — if the diff exceeds 3,000 files and the files matching the filter are not within the first 3,000, it does not run even for a push that mixes in code. Such a push is started by hand with `gh workflow run ci.yml --ref <브랜치>`.
- **Renames — likely: both the old path and the new path are evaluated** — the documentation does not say, and two unofficial sources (a third-party issue with attached run records — a PR event case · a community answer) report evaluation of both sides (`docs/research/ci-docs-skip-conventions-2026-09-26.md` 「결론 — 우리 문서에서 고칠 것」). If so, the worry below does not hold. If instead it evaluates only the new name, CI does not start for a push containing only such a move, and the breakage of builds and tests that relied on the moved file shows up only at the next code push.
- **Revisit triggers**
  - ① **When introducing branch protection or a ruleset that requires this workflow's checks** — current state = `docs/tracking.md` T-18 (user decision: not adopted · source = ADR-0131 open item ②). If adopted, the PR of a branch that changed only docs is stuck at 「Pending」 and the merge is blocked (basis ④). Reopen this decision then. Candidate = job-level skipping.
  - ② **When a CI job that checks docs paths appears** (e.g. the docs lint/CI that `docs/handbook/documentation-system.md:40` wrote down as 「나중」) — that job never runs on a push that changes only docs. Reopen this decision then.
  - ③ **When a file below a removed path becomes a gate input** — revive that file at the end of the list (the invariant above).
  - ④ **When a new docs-only directory appears** — add it to the list. Before adding, first confirm that nothing reads below that path (the invariant above).
