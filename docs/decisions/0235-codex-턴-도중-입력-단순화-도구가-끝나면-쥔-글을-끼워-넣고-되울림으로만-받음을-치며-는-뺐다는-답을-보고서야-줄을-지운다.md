## 맥락
The codex mid-turn input that ADR-0231 · ADR-0234 decided (P2 `3014247` · P8 `37ecc5e`) piled up several mechanisms inside the path — boundary decision and hand-over policy (`HandOverPolicy` · span `Zone` · operating default `AtEarliestBoundary` · answer-span holding `ANSWER_SEGMENT_HOLDS`), the per-turn settlement that waits for the steer response (`settling` · `steers_owed`), the follow-up turn debt that issues an empty `turn/start` for text that was only recorded, the unknown-acceptance stage (`Stage::Unconfirmed` · anomaly counter), the stop after error that is cleared only when a user turn succeeds, and the M15 instrumentation. `transport.rs` was about 12.9k lines and P2 added about 2.1k lines of production code (handoff 2026-09-26 17:47).

After P8 the user said we should look at simplification together (「다끝난뒤에 단순화 한번 나하고 얘기해보자」), and on the spot rejected this design as over-engineering — 「도저히 파일 여러개 필요한 구현이 아닌데」 · 「그냥 도구하나 사용 이벤트 끝나면 그냥 슬쩍 끼워넣으라고」. After running the peer survey (`docs/research/codex-mid-turn-input-peer-implementations-2026-09-26.md`) we decided again with the user (decisions below), and cut the codex path down into sequential pieces S1–S5 (`24e8b7e` `4dd4b18` `7104a93` `860bb89` `11dd46b` `d725be2` · range `d65ddee..d725be2` 24 files +2202/−4166 (excluding .claude)). The ✕ rule for rows that got the answer that they could not be removed was decided separately afterwards (`071f50a`).

★One user decision was overturned within the same round★ — S3b (`860bb89`) deleted text without an echo from a turn that ended in failure, following 「실패는 지워 … 에러 났는데 뭔가 대기목록에 뜨는것도 이상하잖아」, and the user soon after switched to option B (「B가 크게 구현 힘들지 않으면 해」 — keep everything even on error and stop) (`a4a386b` · reflected in S4 `11dd46b`). This ADR records B.

★Three alternatives that ADR-0231 rejected come back to life through this decision★ — not a contradiction but a user reversal. ① 「구간별 ✕」 (hide ✕ after handing over — rejected by the user 2026-09-25) → 「보냄 행은 ✕ 없음」 in decision 7. ② 「누른 창에서도 결말까지 남긴다」 (rejected in Q7 follow-up) → 「뺐다는 답을 보고서야 지운다」 in decision 7. ③ 「오류 뒤 기다림을 도착 사건으로 푼다」 ([Picked] rejection) → 「다음 사용자 글이 푼다」 in decision 4 — the reason for that rejection (remaining items go out on their own because of text removed by ✕) is written as is under 「받아들인 결과」 below.

## 결정
The notation follows the ADR-0231 legend — **[User]** = a decision the user answered · **[Picked]** = an internal implementation the implementation or plan picked itself. Scope = the codex JSON (`TransportOwned`) path. On the claude path, only the frontend ✕ rule that both backends share (decision 7) changes.

1. **Hand-over time = the tool end of the running turn — the t3code shape** [User]. User text typed mid-turn is held by the path (list row 「대기」 · nothing is sent to codex), and when a tool item (`is_tool_item`) of our thread's **current turn id** gets `item/completed`, the trigger (`steer_due`) is raised and the writer hands over **all** held user text in the order typed — one `turn/steer` per item · each with its own `clientUserMessageId`. A tool end before the turn id arrives is not counted (there is no `expectedTurnId`). Parallel tools also trigger at each end. Mail is not steered (it goes out at Idle). There is no boundary decision · span · answer-span holding — text typed in a turn without tools waits for the turn end.
2. **Receipt = one echo · the text is always visible** [User] — 「내가 입력하고 대기가 되던가 창에 뜨던가 해야됨. 붕뜨면 안됨. 그게 가장 중요」. Text is always a list row or a bubble, and there is no moment when it is neither. The only way out of the list by receipt is the echo of a codex `userMessage` carrying its `clientId` (`Delivered` → the row leaves and a bubble appears at the end of the conversation). A successful steer response moves nothing.
3. **Text that ended without an echo goes back to the held place — regardless of the shape of the end** [User — option B]. If the turn closes without an echo for handed-over text (any of `Completed` · `Unknown` · `Interrupted` · `Failed` · `Rejected` · `Unanswered`), or the steer is rejected (−32600 · not steerable · turn id mismatch) or the write fails, that text returns in place (order typed) to 「대기」 and ✕ stands again. Text that ✕ has reached is not returned but becomes `Dropped{Withdrawn}`. Handed-over mail leaves without an event (as is). A bubble drawn while idle (Direct) is also not erased but held and sent again next time. There is no settlement · unknown acceptance · debt. A turn where a rejection or write failure occurred is marked (`steer_refused`) so the same turn does not send again repeatedly [Picked].
4. **Stop after error = set at a failure end and cleared by the next user text** [User]. `Failed` · `Rejected` · `Unanswered` set the path slot `halted: bool` (only for incarnations that meet the floor). While it stands, Idle opens no turn at all (held user text · mail). It is cleared at the moment user text enters (`push_pending`) · when the path closes — ✕ and time do not clear it. A cut-off (`Interrupted`) · `Completed` · `Unknown` do not set it. **Cut-off = the vendor Esc** — the held text and the returned text go out immediately at the next Idle (「esc누르는게 도구 기다리기 귀찮고 내꺼 빨리 푸쉬할려고」). An error stop (e.g. usage limit) does not send on its own. The door through which mail enters the path = the kernel `last_end_failed` is unchanged.
5. **Text left at the turn end goes in one turn** [User]. Idle opens the next turn with the oldest user `Held` (`turn/start`), and once that turn id is known, it hands the rest into that turn at once (raising the trigger — the decision 1 path). Idle order = user `Held` → mail.
6. **Three list row states = waiting (✕) · sent (no ✕) · bubble** [User]. The sent marker is the ring event `QueuedInputEvent::HandedOver{id, sent}` [Picked] — it is emitted after writing a steer · `turn/start` and after returning to the held place, and the value is not decided by the caller: the item's current stage is read again, and if it changed it is emitted again (`publish_hand_over` — the ring's last marker = the last stage). Registry row `QueuedRow.sent` · the list query word `sent`, so sent also survives reattach and pop-out. `PROTOCOL_VERSION` is not raised (6 as is) [Picked].
7. **✕ = the line is removed only after seeing the answer that it was removed — both backends (shared by the frontend)** [User — ✕ option A] — 「a를 하자 … X누르는것도 목록에서 실제로 빼는거 보고 빼야될듯 그냥 무조건 없애는게 아니라」.
   - A sent row has no ✕ (handed-over text cannot be taken back and leaves only by receipt).
   - When ✕ is pressed, the row stays (✕ disabled) and leaves only when the backend's removal event (`Dropped{Withdrawn}` · `CancelAnswered{removed:true}`) arrives — it is not hidden at once. For a codex held row, the path's `withdraw` emits `Dropped{Withdrawn}` at once. Claude leaves only when the CLI cancel answer says it was removed, otherwise it stays until `Delivered`.
   - **A row that got the answer that it could not be removed is drawn like a sent row (no ✕)** [User] — claude `removed:false` · `CancelFailed`, a codex row where ✕ overlapped with the hand-over (`TooLate` → `CancelAnswered{removed:false}`) — both live and on reattach. 「이미 넘어가면 codex와 같이 못누르게 하면 되지 않음?」. Only the frontend changes (the list query and ring event already carry `not_removed` — `071f50a`).
   - LLM control is unchanged — `CancelQueuedInput` · `ListQueuedInputs` (no row slot was added, and `"sent"` was added to the values of row `state` — `ListedState::Sent`).
8. **Codex below the floor (below 0.140 — no `clientId` in the echo) = this whole feature is off and behavior is today's** [User]. The floor decision is left as it is.
9. **Instrumentation = one debug line per item** [Picked — plan item 11]. `tracing::debug!(target: "engram::codex_steer")` · stages `tool_start` · `tool_end` (number held) · `steer` · `write_failed` (a steer could not be written) · `refused` · `echo` · `held_again` (the shape of the end) · it carries the turn id and the agent id (`agent`), and the message is one Korean line per stage (reflecting code review 2026-09-27 — so that lines can be told apart even when one daemon runs several codex agents, and so that a write failure is visible to those who look only at this instrumentation). It replaces the M15 instrumentation (`engram::codex_handover`). Purpose = the open question in 「영향」 below.
10. **No UI stop button or shortcut for now** [User] — 「나중에 단축키 시스템 만들때 넣을거임」.
11. **Ask first about anything beyond this design** [User] — 「단순하게 가고 복잡할것같으면 먼저 나에게 보고해」. If a new state · a new event variant · a wire/`PROTOCOL_VERSION` change · a new mechanism beyond the slots written here becomes necessary, report to the user before building it.

## 거부한 대안
- **Keep the P2/P8 codex design as is** (ADR-0231 decisions 2 · 7 · 9 · ADR-0234 decisions 1 · 4) [User] — 「도저히 파일 여러개 필요한 구현이 아닌데」 · 「그냥 도구하나 사용 이벤트 끝나면 그냥 슬쩍 끼워넣으라고」. Size: `transport.rs` about 12.9k lines (P2 added about 2.1k lines of production code) versus peers' same feature at 150–1.8k lines (t3code about 450 — the survey's comparison table, with the size confidence attached to the table) · result of the removal 24 files +2202/−4166 (excluding .claude). Reasons per part:
  - **Boundary decision · hand-over policy · span · answer-span holding** (`HandOverPolicy` · `Zone` · `AtEarliestBoundary` · `ANSWER_SEGMENT_HOLDS`) — no peer measures the boundary or bets on a timing race (survey conclusion 3 · certain): the vendor relies on the core folding it in at the loop head, and t3code only checks whether a new `tool.completed` is visible.
  - **Turn-end settlement** (waiting for the steer response · `settling` · `steers_owed`) — the echo of an accepted steer comes before `turn/completed` (vendor source 0.156.1 · all 3 M10 hits were 4.5–4.8 ms before — the ADR-0231 rejected alternative 「턴 끝 탐침」) → text without an echo at the turn end was not accepted. The vendor TUI also settles by the `clientId` echo, not the steer response (survey 2-1 · certain).
  - **Follow-up turn debt** (empty `turn/start`) — it is not in the peers we checked (vendor TUI · t3code · vibe-kanban), and the vendor TUI also accepts that loss (survey conclusion 2 · uncertain — paseo · Zed not surveyed).
  - **Unknown-acceptance stage** (`Stage::Unconfirmed` · anomaly counter) — the same basis as settlement (no echo at the turn end = not accepted), and the single return of decision 3 takes its place. The N10 · N12 (a) · N13 (b) answers of ADR-0231 have lost their subject in codex.
  - **Discarding the handed-over text of an interrupted turn** (`Dropped{Interrupted}` — the landed behavior observed in attempt 7 of the P2 local QA) — 「esc누르는게 도구 기다리기 귀찮고 내꺼 빨리 푸쉬할려고」. The vendor TUI's Esc also merges the waiting steers into one turn and resubmits after the interrupt (survey 2-1 · certain).
  - **Deleting the text of a turn that ended in failure** (the codex share of ADR-0231 decision 6 · once the user decision 「실패는 지워 … 에러 났는데 뭔가 대기목록에 뜨는것도 이상하잖아」 — implemented in S3b `860bb89` and reverted) [User] — option B 「B가 크게 구현 힘들지 않으면 해」: keep everything even on error and stop (decisions 3 · 4).
  - **Error-handling options A · C** — the wording presented did not remain in the record (`simplify-plan.md` · handoff). What remains is only the adopted B and the 「실패는 지워」 it replaced.
- **Vendor immediate steer** (Enter in the Codex CLI TUI · the paseo default — `turn/steer` the moment it is typed) [User — **not a rejection but a deferral**] — 「일단 t2code 방식으로 해보되 도구3에서 받으면 그냥 공식벤더로 해야되는걸 고민해야될듯」 (「t2code」 = t3code · the user's typo — the quote is verbatim). The basis for trying the tool end first: codex falls on the same boundary even when held until the tool end (M7 10/10 — ADR-0231 context) · while it is held, ✕ takes the text back (the ADR-0231 rejected alternative 「codex 를 도구 시작에 넘긴다」 — 「✕ 창이 더 길다」) · under `Immediate` in the P2 QA, a handed-over row stayed gray for about 30 seconds and ✕ erased the row but the text went through anyway (handoff 2026-09-26 17:47 QA observation). **Revisit condition** = if the open question in 「영향」 below is answered as 「도구 1 뒤에 친 글이 도구 3 뒤에야 든다」, the user will consider vendor immediate steer.
- **Hold only until the turn end** (survey shape ③ — vibe-kanban · paseo queue · vendor TUI Tab · the old queue of ADR-0190) [User] — the user directed the tool end (quote above), and the principle 「받을 수 있는 가장 이른 때 전달」 (ADR-0231 decision 2 — a user principle · this ADR does not change it) and M7 10/10 (handing over at the tool end falls on the same boundary) stand as they are.
- **Remove the line at once when ✕ is pressed** (ADR-0231 decision 4 — hide at once in every window) [User — chose ✕ option A] — 「… X누르는것도 목록에서 실제로 빼는거 보고 빼야될듯 그냥 무조건 없애는게 아니라」. The observation in the P2 QA that ✕ erased the row but the text went through anyway is an example of this shape (the same source as the item above). The verbatim of ✕ option B is not in the record, and this item is written as the 「무조건 없앰」 that the quote contrasts with.
- **Put ✕ on sent rows too** (ADR-0231 decision 3 — always on every item of the list · a handed-over codex item is removed from the list only) [User — decision 7] — handed-over text cannot be taken back. A feature to cancel an already handed-over item is not in the peers we checked (vendor TUI · t3code · vibe-kanban), and ✕ exists only while the client holds the item (survey conclusion 4 · uncertain — paseo · Zed not surveyed).
- **Return a row that got the answer that it could not be removed to an ordinary row** (the S5 `d725be2` landed shape) [User] — the ✕ that stands again does nothing when pressed (a cancel is already pending in the session — a dead ✕ · the `071f50a` commit body). 「이미 넘어가면 codex와 같이 못누르게 하면 되지 않음?」.
- **Hold text typed at the instant of a tool end until the next boundary** (cut the id and arrival baseline at the tool-end moment — two codex lenses of `/review code deep` 2026-09-27 raised it as FIX and the claude lens did not point it out) [User] — 「코드 간편한 방향으로 x 오래 안살려도됨. 다음 경계까지 붙잡는건 공수가 크잖아.」. Text typed in the few ms while the writer empties the held text at the tool end also goes into the same boundary by steer (`take_steer_locked`), so its ✕ disappears early. That text gets an answer — after a tool end the next sampling comes (`/qa full` GUI T2: steer 0.1 ms after tool 1 ended · echo 3.9 s before tool 2). Cost = text typed in that window cannot be taken back with ✕.

## 영향 / 불변식
- **Path shape (`State` in `backend/codex/transport.rs`)** — `pending` (stages `Held` · `InFlight{gen, turn_id}`) · `steer_due` · `halted: bool` · `steer_refused` · floor decision · two-stage emit. Removed: `HandOverPolicy` · `Zone` · `ANSWER_SEGMENT_HOLDS` · `Segment` · `Signal` · `with_hand_over` · `HAND_OVER_POLICY` · the decoder `ItemClass` (→ `is_tool_item`) · M15 instrumentation · settlement (`Settling` · `SteerOwed` · `settling` · `steers_owed`) · debt (`unanswered` · `follow_up_owed` · `Opening::FollowUp` · fixture `record_only_m10.jsonl`) · `Stage::Unconfirmed` · anomaly counter. Kept: the floor decision · two-stage emit (`Queued` before `Delivered`) and the fan-out exception of the emit line `order` (ADR-0234 decision 5 as is) · `witness_first_turn` (ADR-0233) · the single place that opens a turn, `take_turn_locked` (ADR-0193).
- **What breaks if violated**
  - If an item is moved or removed by a successful steer response, the row disappears before the echo and there is text that is neither on the list nor in the conversation (violates decision 2).
  - `close_turn_items` writes a separate branch for each shape of end (not lumped with `_`) — when a new end appears, the compile must stop so that the disposition of that end is decided. The names `close_turn_items` · `end_turn_if` and the places that go to Idle are counted by the source-scan test `every_place_that_idles_a_turn_is_accounted_for`.
  - If the hand-over marker is emitted with a fixed value, the stale value of the party that emitted late stays as the ring's last marker (handed-over text as 「대기」 · held text as 「보냄」 without ✕) — `publish_hand_over` reads again and keeps the last marker = the last stage. The marker is emitted only for list items that finished emitting (it does not get ahead of `Queued` in the ring).
  - The helpers of the codex path tests (`trace` · `list_ops`) filter out `HandedOver` to keep the meaning of exact-match assertions — if a list event variant is added, filter it the same way.
- **Accepted results** (arising from the simple rules — the user confirmed them one by one, 2026-09-27)
  - The stop is cleared at the moment user text enters (before: it was cleared only when that user turn succeeded). If that turn is cut off, mail already in the path may go out. [User] 「ㅇㅇ 심플하잖아 그게 구현도」.
  - Even if the text that cleared the stop is removed with ✕, the stop does not stand again and the text held earlier goes out (the reason for rejection of 「도착 사건으로 푼다」 that ADR-0231 rejected, as is). The text on which ✕ was pressed does not itself leak — if it is still held text it is removed, and if it is handed-over text there is no ✕. [User] 「ㅇㅇ」.
  - An idle bubble (Direct) whose `turn/start` failed stays and goes out again with the next user text. It is outside the list, so it has no ✕. ★Accepted for now, but watch the frequency★ — [User] 「이건 나오는거 보고 대응하자. 많이 나오면 나중에 개선」. The deferred alternative = on failure, take the bubble back and return it to a held line on the list (a mechanism to erase the bubble and stand the line again would be newly introduced).
  - It is not a separately standing rule — the rule is one, 「다음 기회에 넣는다」, and the incoming event kind decides that opportunity (tool completion → steer · turn end → next turn).
