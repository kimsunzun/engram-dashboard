# ADR-0277: The connection-lost notice also overlays the layout instead of pushing it — in every window

- 상태: 확정 (2026-10-06, basis: user decision 2026-10-06 + implementation `9318b5c` code review (`/review code full` · 2 families · post-review change check PASS) · GUI QA J1–J5 (scratch data folder · three windows) · CI run 37404870999) · 부분 폐기 by ADR-0287 (the remaining connection incidents among the open items) · 부분 폐기 by ADR-0306 (「main 과 팝아웃에서는 TabBar 를 가린다」 of decision 2, the position basis under Impact, and the position fact in the basis GUI QA)
- 관련: Amends ADR-0180 (the connection banner within the invariant that decides what a notification covers only by popup eligibility) · Amends ADR-0276 (the connection banner within the scope of decision 5) · ADR-0134 decision 4 (why that banner exists) · ADR-0181 (a single command failure is also a banner — 「열린 것」) · TRD `docs/process/S21-storage/trd.md` §6-5 ③ guard item (screen shape) · §14-17 · `src/components/layout/NoticeOverlay.tsx` (the overlay layer — shared by the three windows) · `src/components/layout/ConnectionNotice.tsx` (head — ✕ and the closed memory) · `src/components/layout/AppLayout.tsx` · `src/pages/PopoutPage.tsx` · `src/pages/TreePage.tsx` · step-log S21 · Amended by ADR-0287 (the remaining connection incidents among the open items) · Amended by ADR-0306 (「main 과 팝아웃에서는 TabBar 를 가린다」 of decision 2, the position basis under Impact, and the position fact in the basis GUI QA)

## 맥락

The connection-lost notice (`ConnectionNotice` — 「데몬에 연결하지 못했습니다」 + reason + ✕) appears in all of the main · popout · tree windows (boot runs per window and the failure reason arrives per window — ADR-0134). ADR-0180 wrote this banner as a flow block that does not overlay (because the old edition of that banner was an overlay and ate TabBar clicks — the context of that ADR · the `ConnectionNotice.tsx:10` head of that time · how to read it = `git show 9318b5c^:src/components/layout/ConnectionNotice.tsx`), and on top of that it set up the wall that 「알림이 덮는 것」 is decided only by popup eligibility. ★Changing that banner from an overlay to a flow block (2026-08-14 · `485f84c`) was not a user decision but a session change (user's remark 2026-10-06 — ADR-0276 context)★.

ADR-0276 (the same day) changed only main's state-file notice to overlay and left the connection banner in the flow — decision 5 left it open as 「연결 띠도 덮을지는 정하지 않았다 — ADR-0180 을 뒤집는 일이라 사용자에게 올렸고 답을 기다린다」. So in main the flow connection banner pushed the layout, and the overlaying state-file notice sat on top of the layout cell below it.

## 결정

1. **The connection-lost notice also overlays the layout and does not push it** (user decision 2026-10-06). In asking whether to overlay the connection banner too, the session pointed out ① that it reverses ADR-0180 (a banner announces and pushes the layout · only a popup overlays) and ② that the banner also appears in the popout and tree windows, and recommended 「전부 덮기」, saying that the reason the user gave in ADR-0276 (「우리는 레이아웃을 고정시키고 그 고정된 상황에서 작업하는건데 팝업이 나오면 밀림」) still holds. The user: 「덮기로해.」.
2. **Scope = every window where that banner appears — main · popout · tree.** The question above raised the three windows together and the user's answer is to that one question — it was not chosen window by window. Overlaying covers the TabBar in main · popout and, in the tree window, the upper part of the list below the header line — close it with ✕. (2026-10-08 mark — the tree window has no target since the ADR-0225 implementation `ab332a1`) ★(2026-10-26 mark) In main · popout the banner now covers the upper part of the canvas below the title bar and does not cover the title bar (tab bar · drag area · window buttons) — ADR-0306 (user decision 2026-10-26)★
3. ★**The implementation below is a session judgment — the user did not choose it**★ (`9318b5c`):
   - **One overlay layer is shared by the three windows** (2026-10-08 mark — the tree window has no target since the ADR-0225 implementation `ab332a1`) — `NoticeOverlay`. Inside a wrapping `div` (inline `position:absolute` · top/left/right 0 · z 40 · `drop-shadow`) is a Radix ScrollArea (viewport `max-h-[33vh]`), and inside it a cell that stacks the notice lines (`flex-col gap-px` · `bg-background` — the app background shows through the 1px gap between lines). The layer's height is only as much as the drawn lines. Stacking · scrolling on overflow · `33vh` are the layer of ADR-0276 taken over as it is.
   - **main (`AppLayout`)** = the connection banner → the state-file notice are stacked in that order in one layer (inside the `inert` wrapper that is locked while asking). The reason the connection banner is on top = if the daemon cannot be reached nothing else works, so it has to be read first (the comment at that spot).
   - **Popout (`PopoutPage`)** = give the content box `position:relative` and put the layer on top of it.
   - **Tree (`TreePage`)** = a new box below the header line (`flex:1` · `minHeight:0` · `position:relative`) holds the layer and the list together. (2026-10-08 mark — the tree window has no target since the ADR-0225 implementation `ab332a1`)
   - **Line contract** = the background is opaque (it is drawn on top of the background the layer lays down to draw the gap) · the text cell breaks lines anywhere (`wrap-anywhere` — so a long path with no break point does not push the ✕ out of the window). The tests assert it for both notices.

## 거부한 대안

- **Flow block (a banner that pushes the layout — the shape ADR-0180 gave the connection banner · the shape of the three windows until just before `9318b5c`)** — the rejection reason is the one the user gave in ADR-0276 for the state-file notice (「우리는 레이아웃을 고정시키고 그 고정된 상황에서 작업하는건데 팝업이 나오면 밀림」). ★Applying that reason to the connection banner was the session's framing (「같은 이유가 그대로 성립한다」), and the user answered that recommendation with 「덮기로해.」 — the user did not give a separate reason for the connection banner★.

## 영향 / 불변식

- ★**ADR-0180's wall (「알림이 덮는 것」 is decided only by popup eligibility) now has two exceptions — the state-file notice (ADR-0276) · the connection banner (this ADR)**★. ★**So of the non-popup notifications that exist now (these two), none stays in the flow and pushes the layout — the distinction that separated banners and popups by 「덮느냐」 is gone**★. What remains of the split in ADR-0180 decision 1 is 「알린다」 (banner) versus 「네가 눌러야 한다」 (popup — only states that are released when the user presses · eligibility = decision 2 · buttons = decisions 6 · 7). ★Every other new notification stays as the invariant of ADR-0276 — to put it on the overlay side a separate decision is needed★ (what this ADR moved is the one connection banner). ★(2026-10-08 mark) Now all non-popup notifications (banners) stack in the overlay layer — no separate decision is needed when putting a new banner on (user decision 2026-10-08 · ADR-0287 decision 1)★.
- ★**This ADR's 「연결 띠」 = the single `ConnectionNotice` component that exists today**★ (the banner that carries the daemon-connection failure reason — ADR-0134 decision 4). It does not mean putting the other connection incidents that ADR-0180 decision 2 · ADR-0181 routed to the banner side (a transient disconnect · retrying · a loss notice · a single command failure) into this layer — see the open items below. ★(2026-10-08 mark) Now those incidents also go into this layer — ADR-0287 decision 1 (user decision 2026-10-08 · T-48 closed)★.

Canonical source = the head of `ConnectionNotice.tsx`.
- **The three invariants of the layer (the wrapping `div` holds the position · height is only as much as the lines · z 40) are as in ADR-0276, and their canonical comment moved from `AppLayout.tsx` to `NoticeOverlay.tsx`.**
- **The position reference is laid by the call site** — the layer attaches to the top of the nearest positioned ancestor. If `position:relative` is removed from that ancestor (main's layout cell · the popout's content box · the tree's list box), the layer attaches to a reference further out and covers a different place. The tests of the three windows assert the layer's computed position (absolute · the top of the reference cell) and the cell's place (the composition of children in the flow — in main · popout only that cell · in the tree the header line and that cell · the cell's `flex:1` · `minHeight:0` · `position:relative`) — ★the size is not measured★. That the cell's size stays the same when a notice appears was measured by the GUI QA with `getBoundingClientRect()` (「근거」 above). ★(2026-10-26 mark) The position reference is now not the call site's cell but the cell below the title bar inside `WindowLayout` — the call site passes the layer as `notices`, and the loading · boot-failure screen is in the same place (ADR-0306)★
- **main's layer is inside the wrapper that is locked (`inert`) while asking** — while the restore modal is up, the ✕ of both notices is blocked too. The modal exists only in main.
