## 맥락

ADR-0273 decided to separate the engram CLI (`engram.exe` — the control-plane CLI that a spawned agent calls from its own shell) from the daemon package and make it a standalone package that produces one exe (work order 2-3 · the charter of this step). Its decisions 4 · 5 assumed the CLI keeps using the install-location rule (`find_install_root`), and decided to put a copy of that rule on the CLI side, which leaves the daemon crate, and bind it with a same-path test. Until then 2-2 had left a CLI → daemon lib temporary edge (ADR-0282 「영향」).

There was one place where the CLI called that rule — `engram help` found and read the body file `prompts/engram-help.md` by itself and rendered it (ADR-0212 — an external file + a fallback to an `include_str!` embedded copy · decision 3 「데몬도 자격증명도 안 탄다」 · the ADR that first wrote that property = ADR-0133 decision 2 (「help의 자격증명 검사보다 먼저 답한다는 성질」 — S19.2 piece ①)). TRD draft 3 of 2-3 weighed three options for where to put that rule on the CLI side (base · only the walk in base · a CLI copy).

The user (2026-10-08): **the CLI's role is only authentication + delivery.** The CLI is an entrance that exists because the agent has no other way to reach the daemon (a stand-in for MCP) — it is not the place to hold content (screens). So the daemon produces the help screen, and if the daemon cannot be reached or there is no credential, help fails like the other commands (no help-specific fallback · no embedded copy). This move is done inside 2-3 **before** the package move — so that the CLI leaves the daemon package already thin.

As a result the CLI has no place left that calls the install-location rule, and the weighing above (D4 of TRD draft 3) folded away along with its subject.

## 결정

(The skeleton of 1 · 2 = user decision 2026-10-08. The details inside them (contract · source · rejection codes · output channel · stdin order) and 3 ~ 6 = main's decisions under the user's delegation 2026-10-07 · the qa binding edit = user approval 2026-10-08 · the names belong to the landed code)

1. **The CLI's role = authentication + delivery — the daemon produces the help screen.** Add a control route `/control/help` to the daemon, and move the body-file reading · section parsing · required-section check · CRLF folding · screen words and aliases · rendering into the daemon's `control/help.rs`. The CLI `help` sends one screen word and prints the received screen with the same `println!` as now — it does not check the word. What remains in the CLI is only the shape rules (the position of the help token · the stand-alone call rule · a word that starts with the help token or `-` is not a screen word → local `BAD_ARGS`).
   - **The contract = one set of constants in agent `types.rs`** — `CLI_HELP_ROUTE` (`/control/help`) · `CLI_HELP_TOPIC_KEY` (`topic`) · `CLI_HELP_SCREEN_KEY` (`screen`). A session-less POST · the same bearer as the sibling routes · not mail (a credential with mail blocked must still be able to read the mail screen) · the response is always 200 + JSON (success `{"screen": …}` · rejection `{"status":"error","code","hint"}`). ★`topic` is required (null = the table of contents) and unknown keys are rejected★ (duplicate keys are rejected too — U1 landing) — so that a misspelling is not quietly folded into the table of contents. The tolerance of unknown fields in ADR-0157 is the job of wiring that crosses a build boundary; here ADR-0100 ships the CLI and the daemon as one build, so the purpose is to catch a mismatch. If a new CLI sends an unknown key to an old daemon, it receives `INVALID_ARGUMENT` — the same kind as the version-mismatch handling in 2 below. The existing five control routes are left hand-matched (this decision binds only the new route).
   - **The source = injected by the assembly.** The daemon's `lib.rs` builds `HelpSource::from_install_root()` at the same place as priming and passes it in. The existing five-argument server function keeps its signature and is renamed `start_mcp_server_without_help` (so that a production caller calling that version stands out in review — the source of that version answers every request with `INTERNAL` and leaves one warn line at startup), and the injecting version `start_mcp_server_with_help`, which takes the source, is added. The injecting version has four call sites — `lib.rs` · the `tests/mail_gate.rs` fixture · the priming harness bin `roundtrip_smoke` · `priming_smoke` (so that a real primed agent can type `engram help` as the priming teaches). The other 21 sites change by name only.
   - **The daemon carries the path shape as is** — the shape of ADR-0212 decision 3 (the environment-variable override first · the install-root walk + the fixed relative path `prompts/engram-help.md` · a failed override does not fall down to the fixed path · absolute paths only). `ENGRAM_HELP_FILE` is now the env of the daemon process.
   - **It is read on every request** — the daemon lives long. If it were read only once at startup, the purpose of ADR-0212 (「재빌드 없이 반영」) would regress to 「재시작해야 반영」. The cost = one body-file read per call. At startup the resolved path is read once as a check, and `info` is left if it is normal, `warn` if it cannot be read, a section is missing or the path cannot be built (a diagnostic, not a decision).
   - **The screen is not chosen by the caller** — the daemon knows who the caller is (which agent · whether mail is allowed), but help does not use it. This route does not revive the per-caller filter that ADR-0220 decision 4 removed.
   - **Rejection codes** — an unknown screen word = `INVALID_ARGUMENT` (decided before the body is read — the vocabulary is the code) · the body is unusable (file missing · required section missing · no source) = `INTERNAL`. Neither a half screen nor a stale copy is produced (the ban on half screens is ADR-0212 decision 4 as is).

2. **Every command that calls the daemon fails the same single way — including help · exit 1.** The three failures go through the same output function.
   - **No credential** — `NO_TOKEN` · `NO_CONTROL_URL`. The help branch was moved after the credential check.
   - **The daemon cannot be reached** — `CONNECT_FAILED` · `INCOMPLETE_RESPONSE`. The form that had been written by hand three times was gathered into one common function `fail_unreached` (so that a fifth caller is not written by hand).
   - ★**The daemon does not know the route (404 — version mismatch) = `PROTOCOL_MISMATCH`**★ — it borrows the command vocabulary (`ErrorCode::ProtocolMismatch`). It is the same discipline as the CLI borrowing `UNKNOWN_COMMAND` from the daemon vocabulary (the same fact = the same code), and a typo and a version mismatch are not mixed into one code.
   - There is neither a help-specific fallback nor an embedded copy (`include_str!`). An argument-shape error (`BAD_ARGS`) does not need the daemon, so it ends locally before the credential.
   - ★**The output channel = the current common envelope (one JSON line on stdout + exit code) — this is main's decision, and it differs from the wording of the user's instruction.**★ The user's instruction wording was 「stderr 로 보고」. If the channel were moved, the failure output of all commands · the CLI header contract (「CLI 가 스스로 내는 반려는 항상 stdout 봉투 · 기계 판정은 exit code」) · the tests that measure that envelope would change together, which goes beyond the scope of this step. 「한 길 · 0 이 아닌 종료 · help 폴백 없음」 stands as is. stderr is used only for diagnostic lines, as now. If a later session reverts it with 「사용자는 stderr 라 했다」, the cost is the three above.
   - **stdin order** — `mail send --body-stdin` reads stdin **after** the credential (parsing → credential → stdin → network). This prevents a call without a credential from hanging on a stdin that is never closed and never reaching the common path. The cost = the error priority changes — no credential + empty stdin is `NO_TOKEN`, not `BAD_ARGS`.
   - **Two known limits** — ① With an old daemon + a new CLI, a credential with mail blocked (all of today's MCP branch) receives `MAIL_NOT_ALLOWED` on help (code reading · not verified — TRD §9). It is fail-closed, where the old daemon folds a control path outside its list into the mail gate (a credential with mail open gets 404 → `PROTOCOL_MISMATCH`). The CLI does not reread that as a version mismatch (「거부한 대안」). That window stands only during development — in a shipped build the daemon and the CLI are in one folder · one build (ADR-0100). The condition for it to stand = when only engram.exe was rebuilt next to a long-running daemon. ② In a development build whose `CARGO_TARGET_DIR` is outside the checkout, help is all `INTERNAL` — the daemon's install location falls to that target folder and there is no `prompts/` there. It is the same branch as priming already turning off under the same condition, and the startup warn leaves that state in the log.
   - ★**Landing condition**★ — loopback HTTP must reach the daemon from the shell of a codex app-server agent (workspace-write sandbox). If it is blocked, this decision has not landed — in that case this decision takes away the mail contract screen (`engram help mail` — the place the two MCP tool descriptions point to) from codex agents that use mail through MCP. Result = it reaches (「근거」).

3. **Package shape** — name `engram-dashboard-cli` (folder `crates/engram-dashboard-cli` · the prefix is ADR-0273 decision 2 (the gate that counts members by name prefix) · `-cli` is a role word) · bin only (no lib target) · file place `src/bin/engram.rs` as is (explicit `[[bin]] name = "engram"`) · `tests/engram_cli.rs` also goes to the same package (`CARGO_BIN_EXE_engram` sees only the bin of the same package · it starts the real exe, so for a local command use `-- --test-threads=4`) · dependencies = agent (command vocabulary · help contract constants) · command (request number) · serde_json · no dev dependencies. Daemon · base direct · tokio: zero. Version = the product version (5 below).

4. **Build entrances**
   - **The release script (`scripts/build-release.ps1`) = two calls, daemon and CLI, each with its own `Invoke-Step`.** If both are put in one block, that function looks at the exit code at the end of the block only once, so a later call's success covers an earlier call's failure, and the existence check accepts a stale exe from a previous build. The cost = the two calls differ in the serde_json feature set, so agent · command are rebuilt in the CLI call (it is a release profile, so release time grows — the width is not verified).
   - ★**The release launcher `scripts/rebuild-run-release.bat` is also two calls — changed from the TRD design (one call) (the story is in U2 of 「근거」).**★ The `target\release\` that this launcher uses is the folder the release script assembles, and the two build graphs (the combined `-p 데몬 -p CLI` · CLI alone) write the same hashless output file `target\release\engram.exe`. Whether a later CLI-alone build overwrites, with that file, a unit that cargo judged 「최신」 was not measured — splitting into two calls makes that question disappear along with its subject (the output of the combined build is never placed in that folder). Each call has its own failure check. The debug launcher (`rebuild-run-debug.bat`) is one call (`-p engram-dashboard-daemon -p engram-dashboard-cli`).
   - **The build command in the `roundtrip_smoke` harness's guidance text = `cargo build -p engram-dashboard-cli`.**
   - ★**One run of the release script + a standalone start of the release daemon = required before the master merge.**★ That script and the version gate run in CI only on a tag push — if it first breaks there, that tag is abandoned (a tag cannot be reused).
   - **The edit of the build command in the qa binding = user approval (2026-10-08).**

5. **Gates** (three places — `ci.yml` · CLAUDE.md 「빌드·검증 명령」 · the qa binding. Canonical source = the corresponding step in `ci.yml`)
   - **The cli dependency cap = a name-set match (agent · cli · command).** Lines are not counted — if only the number is counted, then even if the daemon enters the command slot it is still three and the point of this step (daemon zero) is not seen.
   - **Add cli to the two loops of the test-feature production-graph gate (base · platform)** — the packages that produce a production binary become three (daemon · shell · cli).
   - **One cli-zero line in platform gate ⑦** — the CLI is a synchronous crate, and not pulling in tokio is the reason it left the daemon. On top of what the agent line already covers, it covers the CLI's own direct third-party dependencies.
   - **Put the cli manifest in the version gate** — the code does not read the version now, but there is a standalone shipped artifact (engram.exe), so it does not fall under the library criterion of 「일부러 뺀 것」. The cost = one more manifest to fix at each release, and if it is missed it shows up only after the tag is pushed and that tag is abandoned.
   - **A standalone-stand step** — cli is built and tested separately with `-p`. ① Does it stand without the feature union with the daemon (the reason this package stands apart) ② If the `engram_cli` target holding the file-name guard disappears, it dies with 「no test target」 (a missing target becomes a failure, not silence).

6. **The bin-only exception to 「새 crate 는 이름 알파벳에 더한다」** — cli is not added to the messaging-isolation regex (three places: `ci.yml` · the qa binding · CLAUDE.md). With no lib target, nobody can call it as `engram_dashboard_cli::…`, and there is no place where what that regex blocks (messaging calling another crate) could hold. The name is added on the day a lib is set up on such a member. The reason for choosing the exception = a main judgment so that the alphabet does not create the misreading 「이 멤버를 부를 수 있다」 (the strength of the grounds on the rejected side is in 「거부한 대안」).

## 거부한 대안

(Only what the user · main gave was carried over — source = TRD 2-3 §7 and the §2-1 · §2-5 · §2-9 · §2-10 · §8 it points to)

- **The CLI keeps rendering the help body (decision 1).** Rejected = user decision — the CLI holds content (a violation of role = authentication + delivery).
- **If the daemon is down, the CLI produces a minimal embedded screen (decision 2).** Rejected = user decision — the same reason, and it is useless for only help to be alive when all the other commands fail (priming already teaches 「`engram` 명령이 계속 실패하면 우회하지 말고 주인에게 알린다」). ★But this rejection was tied to the codex measurement★ — if the codex sandbox had blocked loopback, only help would have stayed alive locally and the conclusion would have been different. The measured result is that it reaches (「근거」). The 「요란하게 죽어도 결과는 같다 — 표면 없이 떠난다」 in ADR-0212 「거부한 대안」 is the logic of a time when help could live apart from the other commands.
- **The daemon covers a broken body with an embedded copy (`include_str!`) (decisions 1 · 2).** Rejected = user decision (「내장 사본 없음」) — what is not moved to the daemon = the `include_str!` copy · `warn_help_fallback` · `OnceLock` (cache — decision 1 「요청마다 읽는다」) (TRD §2-9 ②). Result (TRD §2-9 ⑥) = a shipped build whose body file is missing or broken answers help with a rejection (it is now loud). A build with the file missing was quiet before (the copy covered it) and the release tripwire caught that silence · a broken body (a missing section) is caught by the test that reads that file (CI — before, the embedded-copy test, now the daemon test). The way it shows in production = the rejection hint `help text unavailable — <사유>; report this to the owner` + the daemon log warn.
- **Keep the screen-word list in the CLI and put it in the rejection text (decision 1).** Rejected = the vocabulary becomes two sets, in the daemon and the CLI. The CLI's rejection text points to `engram help` instead of the list.
- **The server builds the help source inside, from the install location (decision 1).** Rejected = tests become tied to the place of the test exe · `CARGO_TARGET_DIR`. With injection by the assembly, the test supplies a known body.
- **Increase the arguments of the server function (decision 1).** Not chosen — all 25 call sites would have to build and pass the source. The rename touches 21 sites but is only a text substitution, and a caller that does not call help has no reason to build a source. The cost of the chosen option = if the production assembly mistakenly calls `start_mcp_server_without_help`, help is always `INTERNAL` — that place is the single `lib.rs`, and the name · the startup warn · the byte comparison catch it.
- **The CLI rereads a `MAIL_NOT_ALLOWED` coming from help as a version mismatch (known limit ① of decision 2).** Rejected = it is the CLI rereading the meaning of a daemon rejection — semantic decisions belong to the daemon alone.
- **Issue the 404 as `UNKNOWN_COMMAND` (decision 2).** Rejected = if 「표에 그 이름이 없다(오타)」 and 「데몬 빌드가 이 입구를 모른다」 are mixed into one code, the caller starts fixing a perfectly good name.
- **Create a new CLI-specific code for the 404 (`ROUTE_NOT_FOUND`, etc.) (decision 2).** Not chosen — the vocabulary has a word of the same meaning (`PROTOCOL_MISMATCH`) (TRD §2-10 3).
- **Report failures on stderr — the user's instruction wording as is (decision 2).** Not chosen in this step (main decision) — the reason and the cost of reverting are in the output-channel item of decision 2.
- **The package name `engram-dashboard-engram` (decision 3).** Rejected = it overlaps in reading with the product name 「Engram Dashboard」, so what the 「engram 패키지」 points to becomes blurred. Strength of the rejection grounds = narrative only (no quantitative · measured · code evidence — weak).
- **Move the source to `src/main.rs` (decision 3).** Rejected = the path changes and the tails of the old ADR pointers break (ADR-0273 「영향」 wrote that that path points to the same file of the new package).
- **lib + bin (decision 3).** Rejected = there is no consumer that would call the lib. A one-file lib falls under ADR-0175 decision 6.
- **Make the release build one call (`-p 데몬 -p CLI` + two `--bin`) (decision 4).** Rejected = the cargo behavior in the form where `--bin` is applied to two packages was not checked (not verified), and the CLI would be built with the daemon's feature set. If the release time of two calls becomes a problem, look again (TRD §8 O10).
- **Set the cli version to `0.1.0` and take it out of the version gate — like a library (decision 5).** Not chosen — it was included by the gate's own criterion that there is a standalone shipped artifact. The cost is the version-gate item of decision 5 (TRD §8 O4).
- **Set up the CLI's async zero separately as `cli gate 2` (decision 5).** Not chosen — it is the same function · same decision, so it goes in the one step of platform gate ⑦. Instead, the 「대상」 description in the platform header embraces what is not a platform consumer (the CLI's own direct third-party dependencies) (TRD §8 O7).
- **Add cli to the messaging regex — the rule 「새 crate 는 이름을 더한다」 as is (decision 6).** Not chosen. ★Strength of the rejection grounds = moderate★ — there is no harm in adding it, and it has the advantage of making the rule simpler. Choosing the exception was a main judgment to prevent misreading.

## 영향 / 불변식

- **The CLI calls not a single line of the daemon lib and has no install-location rule.** The CLI → daemon lib temporary edge of ADR-0282 「영향」 was removed together with the edge when U1 moved help to the daemon (it was not replaced with a copy). 「설치 위치 규칙」 drops out of the dependencies of ADR-0273 decision 4, and decision 5 (a CLI-side copy + the same-path test) has no subject. The 「CLI 쪽 사본과 같은 경로 시험은 ADR-0273 이 진다」 in ADR-0271 「영향」 no longer has that burden, and the 「ADR-0273 뒤에는 설치 위치를 자기 사본으로 가져」 in the first item of 「거부한 대안」 is read as 「CLI 는 사본도 갖지 않는다」. The daemon's `find_install_root` and ADR-0282 decision 3 (the shell copy is bound by a same-path test) stay as they are.
- **This amends ADR-0212.** Decision 3 「cwd 를 안 보고 데몬도 자격증명도 안 탄다」 is reversed — the path-resolution shape is carried by the daemon as is, and the CLI's help goes to the daemon with the credential. Decision 4 「파일이 없거나 깨졌으면 내장 사본으로 답한다」 is also reversed — no copy · if the body is unusable, a rejection (the ban on half screens stays · the reason the copy was not moved to the daemon and the way it shows in production are in 「거부한 대안」, 「데몬이 내장 사본(`include_str!`)으로 깨진 본문을 덮는다」). - **The boundary with ADR-0156 · ADR-0081 — not a violation.** ADR-0156 said it is a violation if daemon code parses · validates · branches on the `help` blob of a command registered by a client, and ADR-0081 says the daemon does not parse the UI payload.
