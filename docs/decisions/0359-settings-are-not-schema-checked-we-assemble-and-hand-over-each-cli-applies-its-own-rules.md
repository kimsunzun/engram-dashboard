# ADR-0359: Settings are not schema-checked — we assemble and hand over, each CLI applies its own rules

- 상태: 확정 (2026-11-11, 근거: user decision 2026-11-11 (S25 step 7, P4 review question 1))
- 관련: Supersedes ADR-0332 · child TRD `docs/process/S25-preset-library/trd-asset-library.md` §3-6 · parked P4 branch `v0.5.0/wip/s25-p4-schema-validate-parked` (`002cd9f9`) · Amends ADR-0334 (decision 3 schema source and CLI version check and raw text to JSON and the port merge and unknown-key handling and the fetch port) · Amends ADR-0336 (jsonschema row and ureq row) · Amends ADR-0323 (decisions 2 and 3) · Amends ADR-0331 (decision 3 schema dimming) · Amends ADR-0324 (decision 8) · Amends ADR-0311 (decision 4 schema fetch port) · Amends ADR-0314 (decision 7 schema errors)

## 맥락
ADR-0332 had Engram check every settings asset (claude raw-text JSON · codex `-c` lines) against the CLI's JSON schema and block the run on a type or range error. Step 7 P4 implemented it (`validate.rs`, `jsonschema` 0.60.2, +26 packages) and needed nine deep-review rounds: a supported-keyword gate, `$ref` limits, work and copy budgets, merged-value attribution, a refresh mutex. Its open questions showed the check is stricter than the CLIs (a value the CLI may accept is refused) and adds policy of its own (split settings failing `required` per asset, refused newer schema copies, keywords outside the gate). Asked whether a wrong value should keep blocking the run, the user asked why Engram filters at all instead of following the CLI's own rules. Main then reported the project's own measurement (`docs/research/settings-asset-validation-spike-2026-10-17.md`): claude does **not** report a bad `--settings` object — a type error anywhere in it makes claude discard the whole object silently. The user kept the decision after seeing that and stated the principle it rests on: 「셋팅 잘못해서 넘어가는건 기존 클로드에도 있던 버그잖아. 그런거 말고 조합을 잘못해서 문제라던가 그런것 위주로 봐야지」 · 「클로드나 코덱스 독립적으로 하는거 말고 우리가 해서 문제가 되는부분만 체크로하면 될것같음.」 (user 2026-11-11). Before the decision main also showed the full width — one bad asset drops every other attached asset's settings and `engram:/settings/default`, because Engram merges them into one `--settings` file (ADR-0328) — and the user accepted: 「ㅇㅇ 클로드나 코덱스 독립적으로 하는거 말고 우리가 해서 문제가 되는부분만 체크로하면 될것같음. 진행해.」

## 결정
1. **Principle — Engram checks only the problems its own assembly creates.** A wrong settings value written by the author is the CLI's own behaviour — exactly what happens when the author uses claude or codex alone — and is out of scope. So Engram does not check settings assets against any schema — not claude's, not codex's; the CLI handles a wrong key or value by its own rules, including claude's silent discard (근거).
2. Engram's job is to assemble the launch materials correctly and hand them over. It checks what its assembly can break — the command-line length and characters the line cannot carry (the command-line guard and length bound, incl. whether the codex terminal line can carry the merged instructions file with the built-in priming — `command_line_fits` · `codex-priming-unsafe-char`), same-name skills across the roots it hands over, and preset folders it cannot read — and what it needs to build the materials at all: YAML syntax of an asset, the shape it reads (front matter · fields · the codex `-c` line shape), the codex skill format (with codex's repair rules — ADR-0336 row `SKILL.md`). The codex line-shape refusal `codex-config-line-invalid` (no `=`, an empty key, a leading `-`) is such a shape/guard check, not a value check: the same `split_config_line` refuses a line starting with `-`, which would be read as an option, and every `-c` line Engram puts on the command line goes through it. **Not checked at run time**: the claude settings merge Engram performs and the settings it injects (`engram:/settings/default`) — the merge is deterministic code covered by unit tests (the merge tables in `backend/claude/settings.rs`), and its result reaches claude like any author's value.
3. Nothing downloads, caches or refreshes schemas. No notice exists for unknown keys, an older schema or a missing schema.
4. The decision applies to every backend, present and future — a new backend gets no schema check by default.

## 거부한 대안
- **Keep ADR-0332: block on a type or range error** — the check is stricter than the CLI and its maintenance is large (P4: 9 review rounds, 5 open policy questions). User 「구지 우리가 필터링을 해서 유지보수를 힘들게 하기보다는 그냥 클로드 룰을 따르자」. 약함 — 사용자 직접 기각.
- **Keep the check, warn only (⚠, never block)** — presented as option B; the same maintenance cost, for author errors the user rules out of scope (decision 1). The user chose to drop the check for both backends. 약함 — 사용자 직접 기각.
- **Block only files that carry permission rules (`permissions.deny` etc.), warn on the rest** — presented as option C because claude skips an invalid file whole, so a deny rule in it is lost until the file is fixed. User 「만약에 문제가 있으면 클로드에서 못하게 막았겠지」. 약함 — 사용자 직접 기각.
- **Drop the check for claude only, keep codex's** — presented; user 「우리는 잘 조합해서 넘기는 것에 집중하자. 문제 생기면 codex claude가 알아서 그쪽룰로 처리하게. 그쪽에서 룰이 잘 되있는걸 구지 우리가 막을 필요는 없다고 생각.」 약함 — 사용자 직접 기각.
- **Run `claude --settings <merged file> doctor` before a launch and cache the verdict by content + CLI version** (≈ 2 s on a changed settings set; reads undocumented output text — the exit code does not carry the verdict) — presented by main 2026-11-11 after the measurement below. The user ruled author errors out of scope (「셋팅 잘못해서 넘어가는건 기존 클로드에도 있던 버그잖아. 그런거 말고 조합을 잘못해서 문제라던가 그런것 위주로 봐야지」 · 「클로드나 코덱스 독립적으로 하는거 말고 우리가 해서 문제가 되는부분만 체크로하면 될것같음.」). 약함 — 사용자 직접 기각.

## 근거
- User decision 2026-11-11 (quotes above), kept after the user saw the measured silent discard (맥락).
- **Measured CLI behaviour** (`docs/research/settings-asset-validation-spike-2026-10-17.md` — claude 2.1.284, codex-cli 0.156.1, Windows, `-p` / `exec` mode):
  - claude `--settings`: a type error anywhere in the object ⇒ **the whole object is discarded silently** — exit 0, nothing in stderr or in `--debug-file` (`{"cleanupPeriodDays":"ten","model":"haiku"}` ran with the default model); broken JSON ⇒ exit 1 `Invalid JSON provided to --settings`; an unknown key ⇒ only that key is ignored, the rest applies. The interactive (terminal) mode was not measured — whether it shows a warning there is unknown. For settings files on disk, issue reports describe a 「Found N invalid settings files」 warning (anthropics/claude-code #14798 · #10096 · #88564 — read from issue pages, not measured).
  - codex `-c`: an unknown key ⇒ a warning, the run continues; an enum error (`approval_policy=bogus`) ⇒ exit 1 before the model call; a wrong free-string value (`model_reasoning_effort=hihg`) ⇒ passes locally, exit 1 at the API.
- Cost seen: P4 as coded is 17,060 inserted lines across 12 files (parked commit `002cd9f9`).

## 영향 / 불변식
- Step 7 P4 shrinks to the hand-over checks of decision 2; the schema part is parked on `v0.5.0/wip/s25-p4-schema-validate-parked` (do not merge; reuse parts from it).
- Not added: `jsonschema`, and `ureq` for schema fetching (ADR-0336 rows); step 17 (schema files `{cli_version, etag, schema}`) is dropped; `daemon\cache\` has no first occupant (ADR-0323); the asset-library fetch port for schemas is not built (ADR-0311 decision 4).
- The settings-check port (ADR-0334 decision 3) loses every schema-only member: the schema source, the CLI version probe, unknown-key handling, merge origins, and also `raw_to_json` and the port method `merge`, which had no caller outside the schema check (checked in code — child TRD §3-9a, B32); agent's `toml` dependency goes with `raw_to_json`. The claude merge the launch uses (the backend's own free function), the codex skill format and the command-line guard stay.
- Reason codes `settings-unknown-key` · `settings-schema-outdated` · `settings-schema-unavailable` and the schema dimming notice (ADR-0331 decision 3) are not built. A new schema re-check as a `Catalog` change (ADR-0324 decision 8) does not exist. Stored per-file errors are parse and shape errors and the command-line guard's refusals of a raw field (e.g. `codex-config-not-a-list` · `codex-config-line-invalid` · `codex-config-unsafe-char`) — never a schema error (ADR-0314 decision 7).
- **Accepted consequence, at full width** (per decision 1): Engram merges every attached preset's claude settings and `engram:/settings/default` into one `--settings` file (ADR-0328), so one bad value in any one asset makes claude drop **all** of those settings for that launch — including Engram's own injected values and any deny rules — silently, with exit 0 in `-p` mode (terminal mode not measured). A codex enum error stops the run before the model call; a wrong free-string value fails at the API; an unknown codex key only warns.
- Same-topic text in decisions and sections this record does not amend, now history: ADR-0311 decision 6 (the async-import gate tied to the schema fetch) and its 「영향」 (the "schema refresh thread" in the daemon assembly order); ADR-0336 「영향」 (the new packages `jsonschema` · `ureq` · its TLS stack and `winreg`, the async-import gate decided at the schema-fetch stage, and the license / claude-schema items to confirm). Read them with this record.
- Do not add a schema check, a schema fetch or a schema-based notice for a backend without a new ADR.
