# ADR-0135: The single-instance lock file also carries the connection info

- 상태: 확정 (2026-08-14, user decision — the precedent survey + adversarial verification refuted the two-file structure) · 부분 폐기 by ADR-0264 (the lock file location of decision 1 — moved to the single `daemon\run\daemon.json` · no exclusion lock at the old location)
- 관련: Amends ADR-0134 (merge the connection-key file into the lock file) · ADR-0024(daemon discovery · portfile) · ADR-0129(net crate — owns the single-instance guard · portfile) · `crates/engram-dashboard-net/src/instance.rs` · `crates/engram-dashboard-net/src/portfile.rs` · Amended by ADR-0264 (the lock file location of decision 1 — moved to the single `daemon\run\daemon.json` · no exclusion lock at the old location)

## 맥락

When ADR-0134 moved the single instance to a lock file inside the data folder, **there became two files** — the lock file (`instance.lock`, proof of folder ownership) and the connection key (`daemon.json`, port and token). During implementation, if the lock file could be deleted or renamed, a second daemon would create a new file, lock it, and come in, putting two daemons on one folder, so **delete sharing was denied** on the lock file.

That combination created a **dead end**. If the data folder is deleted while the daemon is running — which is the action the README used to guide as the way to reset — the registry and the connection key are deleted and only the lock file remains. The daemon is alive and holds the folder, but the connection address is gone, so the client can **neither attach (no address) nor shut it down (the shutdown path uses the address).** A newly started daemon cannot get the lock and quietly exits, and restarting the app is the same. There was no escape other than the task manager. If antivirus, backup, or sync removes only the connection key, it is the same state.

As a first response, a **periodic job in which the daemon republishes the vanished connection key byte-identically** was put in, but the user pointed out that "something I deleted keep coming back is not the behavior I want", and it moved on to a precedent survey.

## 결정

1. **Merge the lock file and the connection-key file into one** — the very file the daemon holds the lock on also carries the port and token. The client reads that one file and attaches.
2. **The file content is still not an identity** — identity is only the state of "holding that file" (ADR-0134 decision 3 kept), and the content is just the data needed for connecting. Copies each hold their own file, so there is no identity collision.
3. **Locking method = restricted share mode** (reads allowed, writes and deletes denied). The client has to read, so a range lock (`try_lock`) cannot be used — a range lock blocks even other processes' reads.
4. **There is no connection-key self-repair (periodic republishing).** The merged file is not deleted, so there is nothing to bring back.
5. **Deleting the data folder while running is not a supported action** — the README states "delete it after fully quitting the app".

## 거부한 대안

- **★Connection-key self-repair — the daemon periodically republishes the vanished file (adopted 2026-08-14 → rejected the same day)★** — a running app rewriting a file the user just deleted is **reported as a bug** in every case surveyed (VS Code #251284 · Zed #9568 · rclone #6754 · GitHub Desktop #4602). In particular, the GitHub Desktop case was reported **even though the content was byte-identical** — the issue is not the content but the act of quietly rewriting. The XDG specification states explicitly that the only thing that may be brought back is a cache. Basis for rejection = precedent survey (many external primary sources).
- **Daemon self-exit — it dies by itself if the connection key vanishes (the PostgreSQL way)** — the most plausible of the candidates, and PostgreSQL does indeed exit immediately when `postmaster.pid` is absent. But the adversarial verification **refuted the analogy**: what Postgres watches is **the interlock itself**, and its absence would allow a second server, whereas in our case the interlock (the lock) is held intact and only an auxiliary discovery file has vanished, so the situation differs. In addition, that exit of Postgres is documented as an **emergency exit that needs recovery**, not a routine means, and it **cannot distinguish** antivirus quarantine or sync deletion from a user deletion, so it becomes a crash loop. Basis for rejection = primary sources (Postgres source and docs) + adversarial verification.
- **Notice only — the app announces the situation and the user force-quits** — even if the app notices the situation, it **does not know which process to kill** (that number was in the deleted connection key). Finding it by name and killing it would kill the daemon of another folder too. Practically it becomes "use the task manager", and a defect of the same structure remains unresolved in VS Code Remote-SSH (vscode-remote-release #11538 — its own "kill server" command needs the same dead socket and fails). Basis for rejection = code (the shutdown path depends on the address) + precedent.
- **Do nothing (the Jupyter way)** — Jupyter writes the connection file once at startup and does not look at it again, so if that file is deleted it becomes **permanently undiscoverable** even though the server is alive (`jupyter_client/connect.py` write-once guard · `jupyter_server/serverapp.py` removes only on the shutdown path). It is the same state as the deadlock we hit, and that is what we mean to eliminate. Basis for rejection = source check.
- **Move the connection surface itself to a named pipe (the Docker `\\.\pipe\docker_engine` way)** — it cannot be deleted from the explorer and disappears with the last handle, so the problem vanishes at the root. But it is a replacement of the transport method, so it is outside this scope (the operating transport is fixed = ADR-0036). **It is kept as an alternative worth reopening** — it is looked at together when the remote · mobile axis is handled. Basis for rejection = scope (not quantitative).
- **Write a unique key value in the lock file and use that value as the identity** — ADR-0134 already rejected it (on copy the key is copied too, so two different installations claim the same identity). **Do not confuse it with this decision** — what is put in the file this time is not identity but connection data, and the authority to decide is still holding the lock.
- **Keep the range lock (`try_lock`) + a separate connection-key file** — the current state. The dead end above remains, and the range lock **blocks even other processes' reads**, so merging is itself impossible (MS `LockFileEx` document: an exclusive range lock denies both reads and writes of other processes). Basis for rejection = primary document + measurement (a reviewer reproduced a copy failure while the lock was held).

## 근거

- **The precedent is on the side of merging** — PostgreSQL's `postmaster.pid` is an interlock and at the same time holds the port, the socket directory, the listen address, and the shared-memory identifier. We created the problem by splitting it into two files.
- **The adversarial verification found this as a "missing dominant option (severity critical)"** (cross-family review, 2026-08-14). Until then the candidate set was only bringing it back, self-exit, and notice, and all three were symptom responses.
- **The problem disappears structurally** — if a file that cannot be deleted carries the connection info, the state "the lock is alive but there is no address" cannot be created. Bringing back, self-exit, and notice all become unnecessary.
- User decision (2026-08-14): the behavior of a deleted file coming back is not wanted.

## 영향 / 불변식

- **Lock acquisition = open with a restricted share mode (`FILE_SHARE_READ` alone).** Another daemon requests write access, so it is denied (sharing violation). ★Do not open `FILE_SHARE_WRITE` together with it★ — that flag means precisely "allow other processes' write opens", so the exclusion quietly disappears (measured 2026-08-14: with share 3, a second daemon just walks in).
- **The condition on the reading side — it is not "pass if read-only".** Share decisions are bidirectional, so the reading side also has to **allow write sharing together** to pass. If it opens read-only while narrowing the share, that read is also denied (measured). All the real read paths now pass because the default share of the standard library and shell tools allows read, write, and delete — **when adding a new read path, do not narrow the share.** **Do not open delete sharing** — if opened, the lock file can be deleted and a second daemon comes in with a new file (ADR-0134 decision 3 collapses).
- **A third party's restrictive open must be told apart from a truly duplicate daemon.** If antivirus or an indexer briefly opens with a narrow share, our open fails too — after a short retry, open the file read-only, and if a valid record and a live pid are visible, report "already running", otherwise "temporarily locked". This classification is for diagnosis, not an identity decision.
- **Atomic replacement (temp file + rename) cannot be used** — the daemon is holding that file, so the rename is denied. The daemon writes in place through the handle it holds. **So the client can see partially written content** — it has to treat a parse failure as "not ready yet" and keep polling (there is already a 50ms polling).
- **Write only after lock acquisition.** If the order is reversed, the writes of two daemons get mixed.
- **The following three clauses of ADR-0134 §영향 are void with this decision:** notifying by a dedicated exit code (not implemented — the client pre-check replaces it) · the connection key records its own owning folder (a data-folder-path field is not put into the portfile) · keeping `ENGRAM_INSTANCE_KEY` for test isolation (removed — the folder scope replaces it, and isolation is done by `ENGRAM_DATA_DIR`).
- **The release delay on a network share stays as it was** — if a client PC dies holding the lock, the file server holds the handle until the session and durable-handle timer (minutes). Restarting in the meantime bounces off as "already running".
- **If the folder is deleted while running, the registry is deleted but the daemon rewrites it from memory** — it does not work as a reset. Chrome too tells users, about its profile lock, to "delete it after fully quitting", and the survey found **no product that documents deleting while running as a supported action.** The README states this.
- **Moving or renaming the folder is also denied while the daemon is running** (a directory rename requires delete-compatible sharing of the files inside). The README's "if you move the folder as a whole, it comes along" applies only with the app off.
