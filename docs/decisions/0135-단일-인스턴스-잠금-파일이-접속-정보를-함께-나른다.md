# ADR-0135: 단일 인스턴스 잠금 파일이 접속 정보를 함께 나른다

- 상태: 확정 (2026-08-14, 사용자 결정 — 선례 서베이 + 적대 검증이 두 파일 구조를 반증)
- 관련: Amends ADR-0134 (연결키 파일을 잠금 파일에 통합) · ADR-0024(데몬 발견·portfile) · ADR-0129(net crate — 단일 인스턴스 가드·portfile 소유) · `crates/engram-dashboard-net/src/instance.rs` · `crates/engram-dashboard-net/src/portfile.rs`

## 맥락

ADR-0134가 단일 인스턴스를 데이터 폴더 안 잠금 파일로 옮기면서 **파일이 둘이 됐다** — 잠금 파일(`instance.lock`, 폴더 소유권 증명)과 연결키(`daemon.json`, 포트·토큰). 구현 중 잠금 파일을 지우거나 이름을 바꿀 수 있으면 두 번째 데몬이 새 파일을 만들어 잠그고 들어와 한 폴더에 데몬 둘이 생기므로, 잠금 파일에 **삭제 공유를 거부**했다.

그 조합이 **막다른 골목**을 만들었다. 데몬을 켜둔 채 데이터 폴더를 지우면 — README가 초기화 방법으로 안내하던 동작이다 — 명부와 연결키는 지워지고 잠금 파일만 남는다. 데몬은 살아서 폴더를 쥐고 있는데 접속 주소가 사라져, 클라이언트는 **붙지도(주소 없음) 끄지도(끄기 경로가 주소를 쓴다) 못한다.** 새로 띄운 데몬은 잠금을 못 얻어 조용히 종료하고, 앱을 재시작해도 같다. 작업 관리자 외에 탈출구가 없었다. 백신·백업·동기화가 연결키만 치워도 같은 상태다.

1차 대응으로 **데몬이 사라진 연결키를 바이트 동일하게 다시 발행하는 주기 작업**을 넣었으나, 사용자가 "지운 게 계속 되살아나는 건 원하는 동작이 아니다"라고 지적해 선례 조사로 넘어갔다.

## 결정

1. **잠금 파일과 연결키 파일을 하나로 합친다** — 데몬이 잠금을 쥐는 그 파일이 포트·토큰을 함께 나른다. 클라이언트는 그 파일 하나를 읽어 붙는다.
2. **파일 내용은 여전히 신원이 아니다** — 신원은 "그 파일을 잡고 있다는 상태"뿐이고(ADR-0134 결정 3 유지), 내용은 접속에 필요한 데이터일 뿐이다. 복사본은 각자 자기 파일을 잡으므로 신원 충돌이 없다.
3. **잠금 방식 = 공유 모드 제한**(읽기 허용, 쓰기·삭제 거부). 클라이언트가 읽어야 하므로 구간 잠금(`try_lock`)을 쓸 수 없다 — 구간 잠금은 다른 프로세스의 읽기까지 막는다.
4. **연결키 자가복구(주기 재발행)를 두지 않는다.** 합친 파일은 지워지지 않으므로 되살릴 일이 없다.
5. **켜둔 채 데이터 폴더를 지우는 것은 지원 동작이 아니다** — README가 "앱을 완전히 종료한 뒤 지우라"고 명시한다.

## 거부한 대안

- **★연결키 자가복구 — 데몬이 사라진 파일을 주기적으로 다시 발행 (2026-08-14 채택 → 같은 날 기각)★** — 실행 중인 앱이 사용자가 방금 지운 파일을 다시 쓰는 동작은 조사한 사례 전부에서 **버그로 신고**돼 있다(VS Code #251284 · Zed #9568 · rclone #6754 · GitHub Desktop #4602). 특히 GitHub Desktop 건은 **내용이 바이트 동일해도** 신고 대상이었다 — 쟁점은 내용이 아니라 말없이 다시 쓰는 행위다. 되살려도 되는 선은 캐시뿐이라는 것이 XDG 규격의 명시다. 기각 근거 = 선례 서베이(외부 1차 출처 다수).
- **데몬 자진 종료 — 연결키가 사라지면 스스로 죽는다(PostgreSQL 방식)** — 후보 중 가장 그럴듯했고 실제로 Postgres가 `postmaster.pid` 부재 시 즉시 종료한다. 그러나 적대 검증이 **유비를 반증**했다: Postgres가 감시하는 것은 **인터록 그 자체**이고 그 부재는 두 번째 서버를 허용하지만, 우리 경우는 인터록(잠금)을 멀쩡히 쥔 채 부속 발견 파일만 사라진 것이라 상황이 다르다. 더해 Postgres의 그 종료는 **복구가 필요한 비상 종료**로 문서화돼 있지 일상 수단이 아니며, 백신 격리·동기화 삭제를 사용자 삭제와 **구분할 수 없어** 크래시 루프가 된다. 기각 근거 = 1차 출처(Postgres 소스·문서) + 적대 검증.
- **안내만 — 앱이 상황을 알리고 사용자가 강제 종료** — 앱이 상황은 알아채도 **어느 프로세스를 죽여야 하는지 모른다**(그 번호가 지워진 연결키에 있었다). 이름으로 찾아 죽이면 다른 폴더의 데몬까지 죽인다. 실질적으로 "작업 관리자를 쓰세요"가 되며, 같은 구조의 결함이 VS Code Remote-SSH에 미해결로 남아 있다(vscode-remote-release #11538 — 자체 "서버 종료" 명령이 같은 죽은 소켓을 필요로 해 실패). 기각 근거 = 코드(끄기 경로가 주소 의존) + 선례.
- **아무것도 안 하기(Jupyter 방식)** — Jupyter는 접속 파일을 시작 시 한 번 쓰고 다시 보지 않아, 그 파일이 지워지면 서버가 살아 있어도 **영구 발견 불가**가 된다(`jupyter_client/connect.py` 쓰기 1회 가드 · `jupyter_server/serverapp.py` 종료 경로에서만 제거). 우리가 겪은 교착과 같은 상태이고, 그것이 우리가 없애려는 것이다. 기각 근거 = 소스 확인.
- **이름 있는 파이프로 접속 표면 자체를 옮기기(Docker `\\.\pipe\docker_engine` 방식)** — 탐색기로 지울 수 없고 마지막 핸들과 함께 사라지므로 문제가 원천 소멸한다. 그러나 전송 방식 교체라 이번 범위 밖이다(운영 transport 고정 = ADR-0036). **재론 가치가 있는 대안으로 남긴다** — 원격·모바일 축을 다룰 때 함께 본다. 기각 근거 = 범위(정량 아님).
- **잠금 파일에 고유 키 값을 적고 그 값을 신원으로 쓰기** — ADR-0134가 이미 기각(복사하면 키까지 복사돼 서로 다른 두 설치가 같은 신원을 주장한다). **이번 결정과 혼동하지 말 것** — 이번에 파일에 싣는 것은 신원이 아니라 접속 데이터이고, 판정 권한은 여전히 잠금 보유다.
- **구간 잠금(`try_lock`) 유지 + 별도 연결키 파일** — 현행. 위 막다른 골목이 남고, 구간 잠금은 다른 프로세스의 **읽기까지 막아** 합치는 것 자체가 불가능하다(MS `LockFileEx` 문서: 배타 구간 잠금은 다른 프로세스의 읽기·쓰기를 모두 거부). 기각 근거 = 1차 문서 + 실측(리뷰어가 잠금 보유 중 복사 실패를 재현).

## 근거

- **선례가 합치는 쪽이다** — PostgreSQL `postmaster.pid`는 인터록이면서 동시에 포트·소켓 디렉터리·수신 주소·공유메모리 식별자를 담는다. 우리가 문제를 두 파일로 쪼개서 만든 것이다.
- **적대 검증이 이를 "누락된 지배적 선택지(severity critical)"로 적출**했다(cross-family 리뷰, 2026-08-14). 그 전까지 후보군은 되살리기·자진 종료·안내 셋뿐이었고 셋 다 증상 대응이었다.
- **문제가 구조적으로 사라진다** — 못 지우는 파일이 접속 정보를 나르면 "잠금은 살아 있는데 주소가 없다"는 상태를 만들 수 없다. 되살리기·자진 종료·안내가 전부 불필요해진다.
- 사용자 결정(2026-08-14): 지운 파일이 되살아나는 동작은 원하지 않는다.

## 영향 / 불변식

- **잠금 획득 = 공유 모드 제한 열기(`FILE_SHARE_READ` 단독).** 다른 데몬은 쓰기 접근을 요청하므로 거부된다(sharing violation). ★`FILE_SHARE_WRITE`를 함께 열지 말 것★ — 그 플래그의 뜻이 정확히 "다른 프로세스의 쓰기 열기를 허용한다"라 배제가 조용히 사라진다(실측 2026-08-14: 공유 3이면 두 번째 데몬이 그냥 들어온다).
- **읽는 쪽 조건 — "읽기 전용이면 통과"가 아니다.** 공유 판정은 양방향이라, 읽는 쪽도 **쓰기 공유를 함께 허용**해야 통과한다. 읽기 전용으로 열면서 공유를 좁히면 그 읽기도 거부된다(실측). 지금 모든 실제 읽기 경로가 통과하는 것은 표준 라이브러리·셸 도구의 기본 공유가 읽기·쓰기·삭제를 전부 허용하기 때문이다 — **새 읽기 경로를 추가할 때 공유를 좁히지 말 것.** **삭제 공유를 열지 말 것** — 열면 잠금 파일을 지우고 두 번째 데몬이 새 파일로 들어온다(ADR-0134 결정 3이 무너진다).
- **제3자의 제한적 열기와 진짜 중복 데몬을 구분해야 한다.** 백신·인덱서가 좁은 공유로 잠깐 열면 우리 열기도 실패한다 — 짧은 재시도 후, 파일을 읽기 전용으로 열어 유효한 레코드와 살아 있는 pid가 보이면 "이미 실행 중", 아니면 "일시적으로 잠김"으로 갈라 보고한다. 이 판정은 진단용이지 신원 판정이 아니다.
- **원자적 교체(임시 파일 + rename)를 쓸 수 없다** — 데몬이 그 파일을 붙잡고 있어 rename이 거부된다. 데몬은 보유 중인 핸들로 제자리에 쓴다. **그래서 클라이언트는 부분적으로 쓰인 내용을 볼 수 있다** — 파싱 실패를 "아직 준비 안 됨"으로 보고 폴링을 계속해야 한다(이미 50ms 폴링이 있다).
- **쓰기는 잠금 획득 뒤에만.** 순서가 뒤집히면 두 데몬의 쓰기가 섞인다.
- **ADR-0134 §영향의 다음 세 조항은 이 결정과 함께 무효다:** 전용 종료 코드로 알린다(구현하지 않는다 — 클라이언트 사전 점검이 대신한다) · 연결키가 자기 소유 폴더를 기록한다(portfile에 데이터 폴더 경로 필드를 넣지 않는다) · `ENGRAM_INSTANCE_KEY`를 테스트 격리용으로 남긴다(제거했다 — 폴더 범위가 이를 대신하고 격리는 `ENGRAM_DATA_DIR`이 한다).
- **네트워크 공유의 해제 지연은 그대로다** — 클라이언트 PC가 잠금을 쥔 채 죽으면 파일 서버가 세션·durable handle 타이머(분 단위)까지 핸들을 붙잡는다. 그 사이 재시작은 "이미 실행 중"으로 튕긴다.
- **켜둔 채 폴더를 지우면 명부는 지워지지만 데몬이 메모리에서 다시 쓴다** — 초기화로 동작하지 않는다. 크롬도 프로필 잠금에 대해 "완전히 종료한 뒤 지우라"고 안내하며, 조사에서 **켠 채 지우기를 지원 동작으로 문서화한 제품은 없었다.** README가 이를 명시한다.
- **폴더 이동·이름 변경도 데몬 실행 중에는 거부된다**(디렉터리 rename이 내부 파일의 삭제 호환 공유를 요구한다). README의 "폴더째 옮기면 따라온다"는 앱을 끈 상태에 한한다.
