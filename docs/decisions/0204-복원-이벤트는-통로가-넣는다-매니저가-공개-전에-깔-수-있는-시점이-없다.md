# ADR-0204: The transport inserts the restore events — there is no point at which the manager can lay them down before publication

- 상태: 확정 (2026-09-16, basis: coder refutation + independent verification by 2 reviewers — call chain traced)
- 관련: Amends ADR-0203 (the spot where the restore events attach) · ADR-0079(the claude precedent — the manager seeds before spawn) · ADR-0019(registration order: sessions insert before the pump) · ADR-0005·ADR-0113·ADR-0127(what seed does not touch) · ADR-0044/0045/0198(synthetic user echo) · `backend/codex/transport.rs` · `session.rs::start_pump`

## 맥락

When ADR-0203 decided 「codex 이력은 app-server 에 페이지로 요청한다」 (“codex history is requested from the app-server in pages”), it wrote the **attach spot** the same as claude's:

> The spot where it attaches is the same as claude's — the backend hands over the restore events and the manager seeds **before** launching the child (the order invariant of ADR-0079 is kept).

**That spot does not exist.** It came to light only when we got into implementation, the coder refuted it by the call chain, and two reviewers each confirmed it.

1. The writer thread that runs the handshake is launched by `AgentTransport::start`.
2. The only thing that calls `start` is `session.start_pump()`, and that is the **last statement** of `spawn_session`.
3. `sessions.insert` (publication) comes **before** that, and it has to — a session that dies instantly must be on the registry first so that the pump's `finish` can be reaped (ADR-0019).
4. The writer needs a reader to route responses to the waiters, and **that reader is the pump.**

So for codex there is no **「공개 전에 상대가 살아 있는 시점」** (“point at which the peer is alive before publication”). For claude, the history is a file on disk and can be read even without a process, so that spot held, and that difference decides this decision.

★To make that spot we would have to reverse ADR-0019 — a much bigger decision than screen restore.★

## 결정

**The transport inserts the restore events directly.** The attach spot is not the manager but **the transport's connection-establishment section**, **just before it declares ready (`Ready`)**.

- `resume_transcript_events` is **left empty** for codex — the claude path does not change by a single byte.
- The door we insert through is **the fanned-out side**, not `core.seed`. `seed` puts only into the ring and does not send to subscribers, so if we write **after publication**, a subscriber that attached in between and already took an empty replay never sees the past.
- That door does the seq issuance and ring push inside the replay lock and **does not touch state·finalize·turn observation** (ADR-0005/0113/0127) — it keeps the properties that seed kept, as they are.

★**「공개 전」 (“Before publication”) has become 「문 열리기 전」 (“before the door opens”), and the two are not the same**★ — what changes is under 「영향」 below.

## 거부한 대안

- **Exactly as ADR-0203 wrote — the manager seeds before publication** — **impossible** (the chain above). At the time of writing we thought the claude precedent could be moved as is, and did not see that the difference between the two backends' history sources — a file vs a process — leads to an ordering constraint.
- **Reverse ADR-0019 and defer publication until after the pump** — then a session that dies instantly ends without being on the registry and is not reaped. Rejected as an exchange that opens the reap invariant for the sake of screen restore.
- **Put in through `core.seed` after publication** — it goes into the ring but a subscriber that attached in between does not see it (above). The purpose is screen restore, yet there would be cases where it does not reach the screen.
- **Make a second path that goes into the ring just for restore** — it is on the same axis as the line ADR-0203 already drew with 「새 어휘표·새 파서를 만들지 않는다」 (“do not make a new vocabulary table·new parser”). We use one existing door.

## 근거

- The call chain was **refuted first by the coder and confirmed independently by two reviewers** (`start_pump` = one `transport.start` line · the last statement of `spawn_session` · the insert before it and the ADR-0019 reason comment).
- The ground for choosing the fan-out door is structural — `seed`'s 「팬아웃 안 함」 (“no fan-out”) is safe **only on the premise that it is written before publication**. If used as is at a spot where that premise has broken, it silently does not reach the screen.

## 영향 / 불변식

- **ADR-0203's 「무엇을·어디서 받나」 (“what and where we receive from”) remains valid** — we request pages from the app-server and do not read rollout files. What this ADR changes is only one clause: **where we put what we received.**
- ★**「문 열리기 전」 (“Before the door opens”) is not the same as 「공개 전」 (“before publication”) — the door does not block what enters the ring**★. What the door blocks is **going out to the peer**. So other things can enter the ring even while the history is going in:
  - **The synthetic user echo** (ADR-0044/0045/0198) — if the user types in that window, the echo goes in directly by `core.emit`, and the transport accepts input even while connecting and queues it. Then **the line just typed is drawn on top of the restored old conversation.** Right after a manual re-activation, that slot has focus, so this is a common path.
  - **Notifications the peer sends on its own** — that they do not come today is the measurement of ADR-0203, but ★that is an **observation of vendor behavior**, not a structural guarantee★. The codex CLI updates itself and the protocol has no version field.
- A restore failure **does not break activation** — it returns only what it collected and does not raise `Err`. ★But if that rule swallows even 「연결이 죽었다」 (“the connection died”) as a partial success, it would **declare a dead transport as Ready** — separating 「페이지가 안 왔다」 (“the page did not come”) from 「연결이 사라졌다」 (“the connection vanished”) is the premise of this rule★.
- Receiving the history **shares the handshake budget.** If it used its own, readiness would exceed the activation backstop and **a successful resume would be recorded as a failure and reaped** (that path of ADR-0201). Cost = a slow handshake shortens the restored screen.
  - **Worst case to readiness = budget + polling interval × 2** (11 seconds with today's values, backstop 15 seconds). ★**The point is that the overrun is not once but twice**★ — the spot that receives the success response does not look at the deadline again, and **there is no budget-0 check between** the handshake's two requests. What blocks a third overrun is the first check of the history receive, so if one more request is added, this value grows with it. ★**This figure was derived by reading the code and has never been measured.**★ (Corrected 2026-09-16 — the 10.5 seconds first written counted the overrun as once. The cross-verification reviewer caught it with a concrete path, and the doc-aware reviewer and the coder both passed over it with 「매 반복 다시 계산하니 누적 불가」 (“it is recomputed every iteration so it cannot accumulate”).)
