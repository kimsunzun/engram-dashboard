# ADR-0084: Re-activation (resume) epoch bump + apply_disposition epoch-guard — blocking the demotion of a live session by a stale reap and the missed frontend resubscribe

- 상태: 확정 (2026-07-14, basis: in the ADR-0083 review, a cross-family (codex) reviewer and a deep lifecycle lens, two in all, independently converged on the finding — `bump_epoch` has 0 production callers + the reap↔re-activation auto_restore race)
- 관련: Amends ADR-0019 (apply_disposition epoch-guard added — so that a stale reap cannot demote a re-activated live session) · ADR-0007 (epoch map-replacement resubscribe — reconfirms that a re-activation respawn is also subject to that invariant) · ADR-0083 (automatic deletion discarded — made the corpse re-activation path actually reachable, exposing this gap) · ADR-0082 (fresh-fallback discarded — removing `fallback_fresh` removed the only `bump_epoch` caller) · `agent/manager.rs` (spawn_agent epoch, activate_profile resume) · `agent/reaper.rs` (apply_disposition) · `src/components/slot/TerminalSlot.tsx` (subscription deps)

## 맥락
When ADR-0083 changed to "the reaper does not delete the profile on any exit (corpse preservation)", **the path of re-activating (resume) a terminated agent became actually reachable for the first time** (before, kill→profile deletion→`profile not found` on re-activation blocked it from reaching this path). When that path was adversarially verified in review (three adversarial reviewers, including cross-family codex), two defects surfaced — both come from one root: **the epoch does not go up on re-activation**.

1. **Epoch reuse → missed frontend resubscribe (violates ADR-0007).** `spawn_agent` only **reads** the epoch from the profile and does not raise it (`manager.rs`). The only caller that originally raised the epoch on every respawn was the `fallback_fresh` respawn of the fresh-fallback, and ADR-0082 deleted that caller when it discarded the fresh-fallback → `bump_epoch` is left as only a definition with **0 production callers**. As a result, when a corpse is re-activated in the **same slot**, the new session has the **same `[agentId, epoch]`** as the dead session. Since the frontend subscription effect deps are `[viewId, agentId, epoch]` (ADR-0007), if none of the three changes the resubscribe does not run, so **the output of the resumed new session does not attach to the screen and the old seq/cursor state may be wrongly applied to the new stream**. That is, even if ADR-0083 removes the "failure (profile not found)", the re-activation ends with an **empty slot** and cannot reach the user's goal ("see the conversation by resuming it").
2. **The reap↔re-activation auto_restore race.** The reaper's `reap_one` removes and releases the session inside the sessions write-lock, **then** writes `apply_disposition` (= the `auto_restore=false` downgrade) outside the lock. If another connection re-activates in between, the new session insert + `auto_restore=true` (true on activation, ADR-0019 §decision 3) runs first, and **the late-arriving `apply_disposition` of the old reap demotes that live session to `auto_restore=false`** → on daemon restart that live agent is missing from boot restore. sessions.remove blocks such stale handling with an epoch-guard (ADR-0007/0019), but `apply_disposition` has no such guard, so if the epoch does not go up they cannot even be told apart.

## 결정
1. **Re-activation (resume) bumps the epoch.** A session leaving the map through a reap and a new session entering with the same AgentId through re-activation is a **map replacement** → apply the ADR-0007 invariant ("epoch +1 on every map replacement of the same AgentId") as is. The resume respawn (and any future respawn path) calls `bump_epoch` right before creating the new session to change `[agentId, epoch]`. The frontend resubscribes with the changed epoch and, after `terminal.reset()`, receives replay→live anew.
2. **Add an epoch-guard to `apply_disposition`.** The reaper carries `ReapMsg.epoch` through to the disposition application and lowers `auto_restore` **only when the current profile/session epoch matches the reaped epoch** (a mismatch = a new session whose epoch rose through re-activation in between → leave it alone). It extends the same principle as the sessions.remove epoch-guard (ADR-0007/0019) to the disposition layer.
3. **State the invariant explicitly:** state "epoch++ on every respawn (including re-activation and resume)" as a respawn case of ADR-0007, and anchor (`// ADR-0084`) `bump_epoch` no longer as dead but as a required call site of the re-activation path.

## 거부한 대안
- **Do not raise the epoch (status quo)** — since re-activation is a resume, keep "same conversation = same epoch". Rejected: (1) whether a resume or a fresh, **a session leaving the map and a new one entering is a physical replacement**, so the frontend subscription instances split (matches the "map replacement" definition of ADR-0007) (2) the resubscribe does not run, giving an empty slot + wrong application of the old seq/cursor (3) the very discriminator on which to build the apply_disposition epoch-guard disappears, so the race cannot be blocked either.
- **The frontend uses the removal from the `agent-list-updated` list as the resubscribe trigger** — the frontend detects the corpse leaving the list and resubscribes. Rejected: it is a frontend patch that bypasses the epoch contract (ADR-0007), so the contract splits in two with the backend respawn invariant (rot). Also the race (#2) is a backend problem and cannot be blocked by the frontend.
- **Move apply_disposition inside the lock to block only the race locally** — perform the disposition inside the sessions lock without an epoch-guard. Rejected: violates the ADR-0006 lock order (ProfileRegistry mutate = disk IO outside the lock) + the missed resubscribe (#1) is still not solved. Since the two defects share one root (the epoch not rising), fix the root.

## 근거
- **Cross-family convergence:** the deep lifecycle lens (Claude) and the blind reviewer (codex/GPT) independently found the epoch reuse **without knowing each other's results** — high confidence. codex additionally found the auto_restore race (#2) separately.
- **Code confirmation:** `bump_epoch` has 0 production callers (`rg bump_epoch` → only the definition + a unit test; the former only caller `fallback_fresh` was removed by ADR-0082). `spawn_agent` only reads `profiles.get(...).epoch`. `apply_disposition` is an `update_with` regardless of the epoch.
- **ADR-0007 consistency:** this decision is not the creation of a new rule but the **restoration + explicit statement** of the "epoch++ on every respawn" invariant that ADR-0082 broke by mistake. Only the apply_disposition epoch-guard is a new amendment to the ADR-0019 reaper refinement.

## 영향 / 불변식
- **Re-activation = epoch++.** The Resume branch of `activate_profile` (and the resume respawn entry point) calls `bump_epoch`. The frontend `[agentId, epoch]` resubscribe (ADR-0007) holds on corpse re-activation too → the resume output attaches to the screen.
- **apply_disposition epoch-guard.** Conditioned on `ReapMsg.epoch` — a stale reap cannot demote a live session whose epoch rose through re-activation. The downgrade-only property (ADR-0019) is kept, only a condition is added.
- **`bump_epoch` revived (not dead).** Mark the required call site with the `// ADR-0084` anchor — so the next session cannot mistake it for "unused" and delete it.
- **Regression tests (mandatory):** ① on kill→re-activation the new session's epoch is greater than the dead session's (assert epoch++) ② in a situation of reap followed by re-activation (different epoch), a stale `apply_disposition` does not demote the live session's `auto_restore` (epoch-guard) ③ on re-activation with the claude backend, `build_command_spec(Resume, sid=Some)` actually assembles `--resume <sid>` (reinforcing the weak Shell test of ADR-0083 regression ③ — demonstrating the sid is passed).
- **Unresolved (out of scope):** whether the frontend slot keeps holding the corpse's agentId after a kill (the trigger condition for same-slot re-activation) and the corpse vs reserved visual distinction (ADR-0082/0083 §open item ①) are left as frontend tasks. This ADR fixes the backend epoch and disposition contract.
