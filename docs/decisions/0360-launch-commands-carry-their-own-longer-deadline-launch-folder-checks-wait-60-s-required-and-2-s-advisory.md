# ADR-0360: Launch commands carry their own longer deadline — launch folder checks wait 60 s required and 2 s advisory

- 상태: 확정 (2026-11-11, 근거: user decisions 2026-11-11 (S25 step 7, after the folder-timeout convention check) — 「시간을 늘려」, values 「시간은 60초로 하던지」; 「Base 쪽에 공용으로」 clarified the same day as a later file-based settings loader, not today's home — 「base에 가는건 나중에 설정로드 할수있는 이후인데?」 · 「파일 읽어노는 구조? 자체는 base에 있고, 설정은 공용 설정으로 할지 crate 당 설정으로할지 어쨋든 파일로 빠지는거잖아.」; the reply bound and caller wait recomputed in the draft-10 review)
- 관련: ADR-0181 (one shared shell-link request timeout) · ADR-0341 (a folder that cannot be read blocks the launch) · ADR-0154 (command delivery) · ADR-0348 (create-and-start body) · ADR-0324 (lock waits, M47) · child TRD `docs/process/S25-preset-library/trd-asset-library.md` D1 · B25 · R15 · `crates/engram-dashboard-daemon/src/command_delivery.rs` `DEFAULT_DEADLINE`

## 맥락
Before a launch, Engram checks the folders a preset names (ADR-0341): the library root when a library preset is attached, each folder entry (exists, listing), and for codex the files Engram reads for it (`AGENTS.md`, skills). These "required" checks block the launch when a folder does not answer. "Advisory" checks (working-folder canonicalize, codex's own skill roots for the same-name notice) are skipped when they do not answer.
Their time limits came from the command bus, not from the folders: the `engram` CLI gives up after 10 s of silence (`CLI_CONTROL_READ_TIMEOUT_SECS`), and the daemon holds a 7 s reply seat (10 − 1 sweep − 2 margin, `DEFAULT_DEADLINE`) for the commands it relays to another owner and for commands that arrive on the socket entrance. The CLI's own launch verbs (`engram agent spawn` on `/control/agent`, `engram call agent.spawn` on `/control/call`) are answered directly, with no seat, inside the CLI's 10 s. The launch folder checks were sized to fit 7 s: 5 s required + 1 s advisory (D1 · B25).
A successful launch also waits inside activation, after the folder checks: a resume watches for an early exit for 3 s (`EARLY_EXIT_WINDOW`, agent `manager.rs`), and a codex launch waits for its link with a 15 s backstop (`LINK_RESOLUTION_BACKSTOP`, same file). The shell's daemon link waits 30 s for every request (`REQUEST_TIMEOUT`, `src-tauri/src/daemon_client/connection.rs`), "until agent spawn time is measured (ADR-0181)".
The user pointed out that a slow or misbehaving PC, a sleeping HDD or a sleeping NAS can exceed 5 s while the folder is fine, and that an agent launched while nobody is at the PC then simply fails: 「느리거나 제대로 동작되지 않는 pc가 있는데 사람이 없을때 에이전트가 실패하면 무한 막히는거잖아.」
Convention check (2026-11-11, worker survey — issue reports and vendor docs, no source read): no app defines a pre-launch folder timeout. Claude Code waits without a limit on a dead `additionalDirectories` drive (anthropics/claude-code #48361), JetBrains and Git for Windows have no timeout, Obsidian fails after 90–100 s, and the Windows SMB client gives up on one request after 60 s (`SessTimeout`, Microsoft "SMB 2.x and SMB 3.0 timeouts"). No library cancels a blocked file call; the common pattern (tokio `spawn_blocking` + `timeout`, OpenDAL `TimeoutLayer`) abandons the call, as Engram's bounded IO already does.

## 결정
1. **A requirement, not per-entrance values.** (a) One launch replies within the launch reply bound (decision 2), and a caller that waits **directly** on one launch waits at least the launch caller wait. (b) **Where one wait contains another, the outer wait ≥ the inner wait + the hop margin** — the ordering the code already pins for the webview round trip inside a daemon seat (`src-tauri/src/view_commands.rs:75-82`, test `the_webview_deadline_fits_inside_the_daemon_seat` in `src-tauri/tests/layout_commands.rs:5224`). If it inverts, the daemon answers `TIMEOUT` while the owner still runs, the owner's late outcome finds no seat, and a same-id retry can send a second envelope. A launch = creating and starting an agent, or starting or resuming an existing one (`agent.spawn`, the shell-owned `agent.spawnInto`, the shell link's `Spawn` / `SpawnByCwd` / `SpawnProfile`). Every other command keeps the 7 s seat and the CLI's 10 s. Step 8 derives each entrance's values from (a) and (b) while it changes that code (the entrance list with today's symptoms is in the child TRD §12). The title's "carry their own deadline" is read in this sense. (Narrowed in the draft-11 re-review, user 2026-11-11 「알아서 해 어쨋든 나중에 결국 다 적용되는거잖아」: per-entrance numbers produced new cases two review rounds running, so this ADR keeps the rule and step 8 picks the numbers.)
2. **Launch reply bound = 85 s** (`LAUNCH_REPLY_BOUND_SECS`) = the required folder wait 60 + the advisory folder wait 2 + the resume early-exit window 3 + the codex link backstop 15 + 5 s slack (parsing, locks, spawning, the reply). **Launch caller wait = 88 s** (`LAUNCH_CALLER_WAIT_SECS`) = 85 + the 1 s sweep + the 2 s margin — the direct caller's wait, by the arithmetic `fits_caller_silence_window` enforces today for (7 s, 10 s); step 8 parameterizes that guard's caller window so it holds for (85 s, 88 s) and for every seat step 8 sets. A nested path's waits (a relay seat, the owner's link wait inside it, the CLI around the seat) are not fixed here — they follow decision 1 (b). (Recomputed in the draft-10 review: the first text had 65 s / 68 s, which left out the activation waits.)
3. **Launch folder checks: 60 s for the required phase, 2 s for the advisory phase**, per launch, replacing 5 s and 1 s. 60 s = the point where the Windows SMB client gives up on a request by itself, so waiting longer gains nothing. Worst case for a launch with a dead folder: 60 + 2 = 62 s of folder waiting, then a block (nothing spawns). Worst case for a success: 60 + 2 + 3 + 15 = 80 s before the reply, inside 85 s.
4. Folder reads outside a launch (resolving presets for a listing, other commands under the 7 s default) keep their 5 s budget.
5. The rule stays one rule for both backends: the required phase blocks, the advisory phase skips; failures are listed together in one reply.
6. **The launch time values are internal constants in agent `types.rs`**, beside `CLI_CONTROL_READ_TIMEOUT_SECS`. The two folder waits are the inputs; the launch reply bound and the launch caller wait are derived from them and from the two activation constants as `const`s, so the chain cannot drift. asset-library, the daemon and the CLI already depend on agent, so no crate rule or CI gate changes; the shell does not depend on agent (ADR-0270 decision 1), so it holds its own value pinned against agent's by a test (step 8 — the test reaches the agent value through a daemon-side public constant or a new shell dev-dependency on agent; step 8 chooses). Nothing moves to `base` now. Later, a generic settings-file loading mechanism lives in `base` (domain-free file loading, which fits ADR-0269); the setting values live in files — one common settings file or per-crate settings files, decided then — and the launch folder wait is read from that file instead of the constant (tracking T-105). The existing 10 s / 7 s defaults stay where they are.

## 거부한 대안
- **Keep 7 s / 5 s / 1 s** — a slow PC or a sleeping disk blocks a launch whose folders are fine, and an unattended agent fails. User 「느리거나 제대로 동작되지 않는 pc가 있는데 사람이 없을때 에이전트가 실패하면 무한 막히는거잖아.」 · 「시간을 늘려」. 약함 — 사용자 직접 기각.
- **Required 30 s, launch deadline 35 s (main's first proposal)** — covers a sleeping HDD and most NAS wake-ups; main raised it to the SMB ceiling because, with nobody waiting, a longer wait costs little and a failed launch costs much; both values were shown to the user, who chose 60 s (「시간은 60초로 하던지」). 약함 — 사용자 직접 기각.
- **Do not check claude folder entries; let claude load them** — claude waits without a limit on a dead folder (#48361), and codex folders are read by Engram anyway, so a generous bound is needed regardless; it would also split ADR-0341 decision 6 by backend. Presented; the user chose longer times. 약함 — 사용자 직접 기각.
- **Answer the launch at once and report folder results later** — changes the launch reply contract and every caller. Presented; not chosen.
- **User settings for the waits now** — convention exposes such timeouts as advanced settings (Claude Code env variables such as `MCP_TIMEOUT` · `BASH_DEFAULT_TIMEOUT_MS`, VS Code `remote.SSH.connectTimeout` — from main's knowledge, docs not reopened), but Engram has no file-based settings loading for these values (the only settings are the shell's UI keys — ADR-0265) and the values are chained, so it is deferred; the user agreed (「어 나중에 한다고 치고」).
- **Raise the global 7 s default for every command** — other commands gain nothing, and a hung command would hold its caller for 88 s; a launch-only bound keeps 7 s for everything else.

## 영향 / 불변식
- Child TRD: D1's 5 s and B25's 1 s become 60 s and 2 s (P6 constants `IoBudget`); the worst case per blocked launch becomes 62 s, a success at most 80 s, both inside 85 s. B28 (a success loses its notices when it comes after whoever waits gives up) now applies to a direct caller at 88 s and to a seat or outer caller at the value step 8 sets. R15 (lock waits are not budgeted) keeps its meaning against 85 s.
- Step 8 meets decisions 1–2 entrance by entrance and chooses the values (child TRD §12 entrance list): the CLI waits at least the launch caller wait for `agent spawn` and `call agent.spawn` (answered directly — no daemon seat; a reply past it is cut by the CLI, which only a lock stall can cause — R15, accepted); for the relay of the shell-owned `agent.spawnInto`, the daemon seat ≥ the shell's inner `SpawnByCwd` wait (itself around a launch of ≤ 85 s) + the two daemon↔shell hops, and the CLI's wait ≥ that seat + the sweep + the margin; the socket entrance's seat for a launch name ≥ the launch it holds, and its caller's wait ≥ the seat + the sweep + the margin (equality allowed throughout, as the pinned test and `fits_caller_silence_window` use `<=`; the seat mechanism is step 8's — e.g. a deadline declared with the verb, or a caller-set field added to `CommandEnvelope` in the `command` crate; the envelope has no such field today); the shell link waits for `Spawn`, `SpawnByCwd` and `SpawnProfile` at least the launch caller wait by **raising its one shared request timeout** — ADR-0181 decision 1 (a user decision, reaffirmed by ADR-0310 D15) keeps one request timeout regardless of command kind and rejected per-command deadlines, and ADR-0181's 근거 prescribes raising the cap when a measured spawn overflows it; every shell request then fails only after that longer wait (accepted). A per-request deadline would need a user decision amending ADR-0181 decision 1 and ADR-0310 D15 and is not planned. `fits_caller_silence_window` is parameterized by the caller window.
- Restore at boot has no caller; it uses the same folder budgets.
- A dead required folder now costs every launch that names it up to 60 s before the block — accepted.
- The values live in agent `types.rs` (decision 6; asset-library P6 adds them). `base`, its tenancy (ADR-0269) and the CLI crate gate (ADR-0273, `ci.yml` "cli gate 1") are unchanged.
