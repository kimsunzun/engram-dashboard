# ADR-0163: Incarnation identity is an unordered random token — skip on read, write a zero placeholder

- 상태: 확정 (2026-08-21, basis: code measurement `profile.rs`·`manager.rs` + user decision) · 부분 폐기 by ADR-0291 (the mutate closure site that decision 7 points to)
- 관련: Amends ADR-0007 (two clauses: epoch +1 increment on every map replacement, and the resubscribe deps) · `crates/engram-dashboard-core/src/agent/profile.rs:165-186`(field declaration · meaning) · `profile.rs:600-610`(single issuing point) · `profile.rs:613-616`(zero-placeholder serialization) · `profile.rs:618-623`(random extraction) · `crates/engram-dashboard-core/src/agent/manager.rs:893-899`(the only call site) · ADR-0084(reap epoch-guard) · ADR-0086(control channel token) · ADR-0113(turn observation table) · ADR-0164(attach trigger) · CLAUDE.md 「핵심 불변식」 · Amended by ADR-0291 (the mutate closure site that decision 7 points to)

## 맥락

**Incarnation** = the event of a process standing up anew under one AgentId. The consumer guards all use this one value to tell "is the output stream being read now the same as the stream from before" — the reap epoch-guard (ADR-0084) · the control channel token (ADR-0086) · the turn observation table (ADR-0113) · the frontend re-attach and rotation decision (ADR-0164).

The old convention (ADR-0007) set this as an **ordered counter**: +1 on every map replacement for the same AgentId. If that value is put on disk, **the counter restarts from 0 when the daemon restarts**, so a restored agent wears the same value as the old one again. A client that stayed attached mistakes it for "the same stream" and keeps the old progress cursor, and since the new session's frames are numbered from 0 again, **all of them drop out in dedup** — that slot stays empty until the app is launched again (`profile.rs:170-175`).

## 결정

1. **Incarnation identity = a 32-bit opaque token drawn fresh for each incarnation.** The single issuing point is `ProfileRegistry::epoch_for_spawn` (`profile.rs:600`), and the only production call site is `AgentManager::spawn_agent` (`manager.rs:894`) — regardless of mode (Fresh/Resume). The random number is taken from the first 4 bytes of a uuid v4 (`profile.rs:618-623` — so as not to bring in a new random-number crate).
2. **Comparison is match/mismatch only.** Do not derive "newer" from the order of two values — the value is random, so that derivation does not hold. The same goes for assertions (`crates/engram-dashboard-core/tests/activation.rs:366-367` — tightening it with `assert!(new > old)` turns it red half the time).
3. **What is guaranteed is one adjacency guarantee.** A freshly drawn token **differs from the immediately preceding incarnation** (the while loop at `profile.rs:604-606`). Global uniqueness is not a guarantee but a probability (2^-32), and if it hits, that one agent's incarnation guards are disabled for the duration of one incarnation (observation contamination · token collision · missed resubscribe).
4. **Skip on read** — `#[serde(skip_deserializing)]`. The value on disk is ignored. An old `agents.json` with no value and one carrying the old counter are both read as they are, so **there is no migration**.
5. **On write, do not skip; always send `0` along** — `serialize_zero_placeholder` (`profile.rs:613-616`). The previous release's struct declared this field **required**, so a file without the key breaks parsing with `missing field`, and persistence moves that file aside as `.corrupt-<ts>` and starts from an **empty list**, and the next save overwrites it so the profiles, session ids and tree parents vanish altogether. The reason for `0` = it is the old counter's "never re-spawned" state, so it is harmless even if an old binary trusts it as is.
6. ★**This asymmetry (does not read but writes) is intentional — do not "tidy it up".**★ If it is aligned to either side, the failure mode of 4 or 5 comes straight back.
7. **The decision and the commit are made inside one lock** (the `mutate` closure at `profile.rs:601-609`). If split in two, a `remove` can slip in between and plant a token in a vanished profile, or the comparison with the previous value is made against the old map.

## 거부한 대안

- **Unconditional reset — keep no identity and clear the screen and cursor on every re-attach** (rejected by the user — the rejection itself is the user's decision, but the reasons that follow are reverse-inferred from the code and are not grounds the user gave). Without identity, "continue viewing the same incarnation" and "a different incarnation" cannot be told apart, so even a slot that was cut off briefly and came back is cleared every time. On the path where the daemon restarted, that clearing is a permanent loss — the ring to revive from is already gone (`src/components/slot/TerminalSlot.tsx:315-318`). The current code treats "touch neither the screen nor the progress cursor" as an explicit invariant, which is the opposite side (`src/api/protocolClient.ts:547-551`).
- **The client infers "has this agent ever vanished"** (rejected by the user — the rejection itself is the user's decision, but the reasons that follow are reverse-inferred from the code and are not grounds the user gave). There is a real split where absence cannot be observed — a re-spawn while the connection stays attached. Then the frame side simply drops a token mismatch, so a live slot cannot draw a single byte after the re-spawn (`protocolClient.ts:585-587` — the only place that recognizes a re-spawn is the registry observation).
- **PID** (rejected by the user). The token must be fixed **before the process stands up** — command assembly (`build_command_spec`) injects that value as the control channel token, so issuance comes earlier than that (`manager.rs:894` → `:901`). There is no PID at that moment. Moreover the OS reuses PIDs, so even if it were deferred until usable, the collision hole of the old counter would come straight back.
- **A 16-byte guid** (rejected by the user). The backward-compatibility device of decision 5 holds **only when the field width is `u32`** — the previous-release reader swallowing `0` as the old counter is the whole of that device. If widened to 16 bytes, that reader goes down the `.corrupt` path again. The cost of staying at 32 bits is only decision 3's 2^-32.

## 근거

- **Code measurement (2026-08-21).** Field declaration and meaning `profile.rs:165-186` · random issuance `profile.rs:618-623` · adjacency guarantee loop `profile.rs:604-606` · zero placeholder `profile.rs:613-616` · the only call site and the issuing moment `manager.rs:893-899` (→ `:901` spec assembly).
- **Regression guard.** `crates/engram-dashboard-core/tests/activation.rs:361-367` asserts "reactivation = map replacement = a new token" only as **different** (the ban on ordering assertions is embedded in the test comment).
- The description of the failures the old counter caused remains at `profile.rs:170-175` (mistaken identity → old cursor kept → all new frames dropped in dedup → empty slot) and `profile.rs:176-181` (key missing → `.corrupt` → empty list → registry lost).

## 영향 / 불변식

- **Match/mismatch only.** Nowhere in code, tests or documents are two tokens compared by order. Comparing them invents the nonexistent fact of "newer".
- **No read · write is `0`.** A change that aligns this asymmetry to one side is a regression (decision 6).
- **Issue in one place only.** If `epoch_for_spawn` is scattered across call sites, a new call site will omit it again (measured: WS `Spawn` and boot restore were omitted that way — `profile.rs:594-597`). Do not mistake it for dead code and delete it.
- **Consumer guard list** = ADR-0084 · ADR-0086 · ADR-0113 · ADR-0164. If the adjacency guarantee breaks, these four are disabled together for the duration of one incarnation.
- **Do not put this token in the frontend resubscribe deps** — the reason and the cost are in ADR-0164, which is the source of truth.
- **Remaining debt (a fact — not something this ADR decides):** the field name is still literally `epoch`. It is a name that reads as an ordered counter, so it clashes head-on with the meaning above. Renaming is a separate item and `docs/backlog.md` tracks it.
