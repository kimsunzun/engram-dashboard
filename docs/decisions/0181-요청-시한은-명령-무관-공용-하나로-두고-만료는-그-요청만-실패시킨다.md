# ADR-0181: The request deadline is one shared value, independent of the command, and expiry fails only that request

- 상태: 확정 (2026-09-06, basis: user decision + static-read measurement in this session. ★**Not one line of code was changed**★)
- 관련: ADR-0177 decision 4 (policy values — ★**the crate has defaults and the consumer overrides them**★. This deadline is that slot) · ADR-0158 decision 5 (every request gets a deadline + errors carry a correlation marker — ★**the clause ADR-0178 decided as 「산다」, and this ADR sets the real value of that deadline**★) · ADR-0162 (no response is resolved by a **status query**, not by a result store) · ADR-0159 (retry directive = safe × useful — automatic resend is blocked at the **safe** leg) · ADR-0161 decision 3 (★do not confuse★ — that deadline inequality is the daemon deadline versus the CLI read deadline on the **control relay route**, not the shell request deadline this ADR covers) · ADR-0180 (popup eligibility — one command failing is a **strip**) · ★**the real location of the current 30-second cap**★ = `src-tauri/src/commands/agent.rs:263` (`REPLY_TIMEOUT`, applied in only one place, `forward_daemon_command`) · `crates/engram-dashboard-protocol/src/messages.rs` (the number of `AgentCommand` branches · `AgentCommand::CommandOutcome`:296 · `AgentEvent::CommandReply`:531 · `AgentEvent::Error` · `AgentEvent::SubscribeFailed`) · `src-tauri/src/daemon_client/protocol_state.rs:32` (`reply_outcome` — which replies wake a pending request with Err) · `src-tauri/tests/daemon_client_pending.rs` (★regression net for the colliding-number **succession** — not the regression net for the ban on reusing numbers★) · step-log S21

## 맥락

Once the `transport` crate (ADR-0177) takes over request/response correlation, someone has to decide **「답이 안 오면 언제 포기하나」 (when do we give up if no answer comes?)**.

★**Correction — the first draft of this ADR said 「요청별 시한이 아예 없다」 (there is no per-request deadline at all). That is false.**★ (measured 2026-09-06). **There is one** — `forward_daemon_command` wraps `send_command` in `REPLY_TIMEOUT = 30초` (`src-tauri/src/commands/agent.rs:263`). On top of that, the comment at that spot states as its own reason for existing ★**exactly the case this ADR was about to claim 「안 덮인다」 (is not covered)**★ — 「연결은 살아있는데 데몬이 그 request_id 응답만 누락」 (the connection is alive but the daemon drops only that request_id's response). So the problem is not that **there is no deadline** but that ★**the deadline exists in only one place**★:

- **`forward_daemon_command` (the general command bridge) — has a 30-second cap.**
- **The per-type handlers (`agent_spawn` · `agent_kill` · `agent_interrupt` · `agent_write_stdin` · `set_envelope_format` …) — call `client.send_command(cmd).await` bare. No cap.**

★**This mismatch is itself the strongest ground for decision 1 (one shared value)**★ — what happens when each command gets its own value already exists in the code as a real artifact. The neighboring caps on other axes (handshake · connect, the replay progress deadline (ADR-0046), the control relay deadline inequality (ADR-0161 decision 3)) do not apply here.

On the other hand, **the covered part is also large** — when the connection drops, **every** waiting request and every unsent buffered request is woken with Err. So **the case where the daemon dies is already handled.** What this deadline targets is ★**the case where 「연결은 멀쩡한데 그 요청만 답이 없는」 (the connection is fine but only that request gets no answer)**★, and **widening that from one place to all places** is this decision.

That case has actually happened — a colliding `request_id` made a waiting slot **hang forever**, so every command after it was cut off and there was no reconnect, measured in the GUI (2026-08-18). That path is fixed and the `daemon_client_pending` test is its regression net.

## 결정

1. ★**The cap on waiting for a request response = one shared value, independent of the command kind. Default 8 seconds.**★ It is a **policy value** injected from outside the `transport` crate (ADR-0177 decision 4).
2. **On expiry, wake only that request with an error and keep the connection.** Whether the connection is alive is **watched separately by keepalive** (ADR-0177 decision 3) — the request deadline is not the decider of connection health.
3. ★**Do not resend automatically**★ — no response means not 「실패했다」 (it failed) but ★**「모른다」 (we do not know)**★. The daemon may actually have processed it and **only the reply failed to arrive**, so an automatic resend **creates a duplicate** (two agents start). The next decision is made by **the user looking at the list again**.
4. **A reply that arrives late, after expiry, is discarded. That request number is not reused.**
5. **The 「기다리는 중」 (waiting) indicator — ★proposed default 1 second, to be confirmed in the shell work phase★.** This value is **the screen's share, so it is outside the crate**, and what this ADR fixes is not the number but ★**the structure in which showing and giving up are different points in time**★ — 「기다리는 중」 appears at about 1 second, and we give up at 8 seconds. **That structure is confirmed and the 1 second is still a proposal.**

## 거부한 대안

- ★**A different deadline per command kind**★ — `AgentCommand` has **30** branches (measured 2026-09-04). That means managing 30 values by hand, **deciding one more every time a command is added**, and with no measurements, **all those values would be guesses.** User decision: *"그거 하나당 언제 초로 해, 그냥 공용으로."*
- **Cut the connection on expiry** — ★**one slow request would cut a perfectly healthy connection**★. Connection health is watched by **a separate axis, keepalive**. If the request deadline also takes on that role, two failures get blurred into one signal.
- **Automatic resend after expiry** — the **duplicate creation** problem of decision 3 above. No response does not mean 「안 됐다」 (it did not happen), so a resend can apply **the same operation twice**.
- **A 30-second cap** — the user **judged it too large**. ★**This is not a hypothesis but the current value**★ — `forward_daemon_command` uses 30 seconds today (`src-tauri/src/commands/agent.rs:263`), and the comment there records its own reasoning: 「정상 경로의 왕복은 loopback 에서 수 ms 라 30s 에 절대 안 닿는다 · 넉넉히 잡아 **느린 데몬을 타임아웃으로 오판하지 않으면서** 무한 hang 만 확정적으로 끊는다」 (a normal-path round trip takes a few ms on loopback, so it never reaches 30s · set generously so that **a slow daemon is not misjudged as a timeout** while only an infinite hang is cut off for certain). ★**That reasoning holds only when 「포기 시점 = 사용자가 처음 이상을 눈치채는 시점」 (the moment of giving up = the moment the user first notices something is wrong)**★ — decision 5 **separates the indicator out at 1 second**, which changes that premise. The anomaly is already visible at 1 second, so the cap only needs to be **large enough to avoid misjudging**, and 30 seconds is far larger than that. So the reason for rejection is not 「30초가 틀렸다」 (30 seconds was wrong) but ★**「그 값을 정당화하던 구조가 이 결정으로 달라졌다」 (the structure that justified that value changed with this decision)**★.

## 근거

- **Do not measure the deadline value as 「데몬 죽음을 얼마나 빨리 알아채나」 (how fast do we notice the daemon's death)** — a disconnect wakes every waiter with Err, so that side is already covered. What this value measures is **silence** alone.
- ★**The place where silence is real is written in the protocol**★ — ★`AgentCommand::CommandOutcome`★ (`crates/engram-dashboard-protocol/src/messages.rs:296` — ★**not an `AgentEvent`. It is a reply the shell sends back to the daemon, so the direction is the opposite**★), which carries a command's **outcome**, **has no `request_id` field of its own**, so putting it in the wait matching **leaves no counterpart to wake and ends in a permanent wait**, and the code comment there **admits it itself** (measured — messages.rs:284-287). The correlation key is inside `reply`.
- ★**Practically only one reply wakes a pending request with Err, and it is a string**★ — the shell's `reply_outcome` maps ★`AgentEvent::Error { message, .. }` **alone** to Err and passes everything else through as Ok★ (measured — `src-tauri/src/daemon_client/protocol_state.rs:32`). The two beside it are on a different axis: `AgentEvent::SubscribeFailed { agent_id, reason }` **has no request_id, so it is not a matching target in the first place** (the comment on its `reason` states 「사람이 읽는 진단 문자열 — 기계 분기 금지, 문구는 예고 없이 바뀐다」 (a human-readable diagnostic string — no machine branching, the wording changes without notice)), and the `Err` of `AgentEvent::CommandReply` (messages.rs:531) ★**really does have `code` and `retry` fields a machine can read**★ (its TS contract, messages.rs:298). ★**So do not lump it as 「실패 답장에는 코드가 없다」 (failure replies carry no code)**★ — there is a place where the code exists, and it is only that **the path that wakes pending is one string**, which is the fact this decision stands on. And either way, **what the deadline guards against is not the case where it arrives but ★the case where it never arrives★.**
- **The ground for 8 seconds is the user's judgment** — the user judged the first proposal of 30 seconds 「너무 크다」 (too large), and settled on 8 seconds after confirming the structure that ★**once the indicator appears at 1 second, the cap is a safety net and is not felt**★. So this value is not 「사용자가 기다리는 시간」 (the time the user waits) but **「영영 안 오는 것을 끊어 내는 자리」 (the place where something that never arrives gets cut off)**.
- **The ban on automatic resend gives the same answer by ADR-0159's yardstick** — in safe × useful, automatic resend is ★**blocked at the safe leg**★ (the same operation can be applied twice). ADR-0162 closed the same problem as 「결과 저장소 대신 상태 조회」 (status query instead of a result store). ★**Both ADRs are decisions about the control relay route, and this ADR does not claim to extend those clauses to the shell path.**★
- ★**Not checked — we have never measured how many seconds an agent spawn actually takes**★. Of the 30 branches, **that one alone** could plausibly exceed 8 seconds. **After applying it, measure, and raise the cap if it overflows.**

## 영향 / 불변식

- ★**Do not reuse numbers** (decision 4)★ — if the number of an expired request is reused, **a late old reply is misattributed as the counterpart of the new request.** Expiry only wakes the waiter; it does **not mean that number is dead on the wire**. ★**`daemon_client_pending` is not the regression net for this clause**★ — what that test measures is **succession of a colliding number** (the old waiter wakes with an error instead of hanging and the new request takes over that number), and the ban on reuse after expiry is **still caught by no test.**
- **Do not put `AgentCommand::CommandOutcome` into wait matching** — if it goes in, then even with a deadline **it always ends only by expiry** (there is no counterpart to wake). The canonical source is the comment on that variant.
- **Deadline expiry does not change the connection state** (decision 2). If expiry triggered a reconnect, the reconnect budget of ADR-0180 decision 4 would **burn down because of a single request.** The notification is also a strip, not a popup (ADR-0180 decision 2 — 「명령 하나 실패」 (one command failing) is not covered).
- **The indicator (1 second) and giving up (8 seconds) live in different layers** (decision 5) — the indicator belongs to the shell/screen, giving up to `transport`. ★**Do not change one value and adjust the other to match**★ — they are not two scales measuring the same thing but **different jobs**.
- ★**When applying this, decide together what to do with the current 30 seconds**★ — the `REPLY_TIMEOUT` in `forward_daemon_command` is a live value, so bringing in the shared 8 seconds **lowers** that spot and **gives the remaining handlers a cap they did not have.** Both changes have to land in one commit for 「공용 하나」 (one shared value) to actually hold.
- ★**Not verified**★:
  1. **The real time an agent spawn takes** (see 「근거」 above) — the only substantive risk of 8 seconds is here.
  2. **All of the reading is static** — we did not launch a request and reproduce an expiry.
