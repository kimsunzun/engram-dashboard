# ADR-0181: The request deadline is one shared value regardless of command (명령 무관 공용 하나), and expiry fails only that request

- 상태: 확정 (2026-09-06, basis: user decision + this session's static-reading measurement. ★**Not a single line of code was changed**★) · 부분 폐기 by ADR-0310 (decision 1: default of the shared deadline) · 부분 폐기 by ADR-0369 (decision 1 one shared value for launch requests)
- 관련: ADR-0177 decision 4 (policy values — ★**the crate has defaults and the consumer overrides them**★. This deadline is that place) · ADR-0158 decision 5 (a deadline on every request + a correlation mark on errors — ★**the clause ADR-0178 decided as 「산다」 and this ADR sets the actual value of that deadline**★) · ADR-0162 (no response is resolved not by a result store but by a **status query**) · ADR-0159 (retry instruction = safety × usefulness — automatic resend gets caught on the **safety** leg) · ADR-0161 decision 3 (★do not confuse★ — that deadline inequality is the daemon deadline of the **control relay route** versus the CLI read deadline, not the shell request deadline this ADR deals with) · ADR-0180 (popup eligibility — one command failing is a **strip**) · ★**the actual form of the current 30-second cap**★ = `src-tauri/src/commands/agent.rs:263` (`REPLY_TIMEOUT`, hung on `forward_daemon_command` only) · `crates/engram-dashboard-protocol/src/messages.rs` (the number of `AgentCommand` branches · `AgentCommand::CommandOutcome`:296 · `AgentEvent::CommandReply`:531 · `AgentEvent::Error` · `AgentEvent::SubscribeFailed`) · `src-tauri/src/daemon_client/protocol_state.rs:32` (`reply_outcome` — which reply wakes a pending request with Err) · `src-tauri/tests/daemon_client_pending.rs` (★the regression net for the **succession** of an overlapping number — not the regression net for the ban on reusing numbers★) · step-log S21 · Amended by ADR-0310 (decision 1: default of the shared deadline) · Amended by ADR-0369 (decision 1 one shared value for launch requests)

## 맥락

Once the `transport` crate (ADR-0177) takes over request/response correlation, someone has to decide **「답이 안 오면 언제 포기하나」**.

★**Correction — the draft of this ADR wrote 「요청별 시한이 아예 없다」. That is false**★ (measured 2026-09-06). **There is one** — `forward_daemon_command` wraps `send_command` with `REPLY_TIMEOUT = 30초` (`src-tauri/src/commands/agent.rs:263`). Moreover the comment at that spot gives ★**exactly the case this ADR meant to claim 「안 덮인다」**★ as its own reason for existing — 「연결은 살아있는데 데몬이 그 request_id 응답만 누락」. So the problem is not **no deadline** but ★**the deadline exists in only one place**★:

- **`forward_daemon_command` (the general command bridge) — has a 30-second cap.**
- **The per-type handlers (`agent_spawn`·`agent_kill`·`agent_interrupt`·`agent_write_stdin`·`set_envelope_format` …) — call `client.send_command(cmd).await` bare. No cap.**

★**This mismatch itself is the strongest ground for decision 1 (one shared value)**★ — what happens when each command gets its own is already in the code as a real example. The neighboring caps on other axes (handshake·connect, the replay progress deadline (ADR-0046), the control-relay deadline inequality (ADR-0161 decision 3)) do not apply here.

On the other hand, **the covered part is also large** — when the connection drops, **all** pending requests and the unsent buffer are woken with Err. So **the case of the daemon dying is already handled.** What this deadline aims at is ★**the case of 「연결은 멀쩡한데 그 요청만 답이 없는」**★, and **widening that from one place to all** is this decision.

That one case actually happened — a GUI measurement (2026-08-18) where an overlapping `request_id` made a waiting slot **hang permanently**, after which every command stopped and there was no reconnect either. That path was fixed and the `daemon_client_pending` test is the regression net.

## 결정

1. ★**Request reply wait cap = one shared value regardless of command kind. Default 8 seconds.**★ It is a **policy value** injected from outside the `transport` crate (ADR-0177 decision 4).
2. **On expiry, wake only that request with an error and keep the connection.** Whether the connection is alive is **seen separately by keepalive** (ADR-0177 decision 3) — the request deadline is not the decider of connection health.
3. ★**Do not resend automatically**★ — no response is not 「실패했다」 but ★**「모른다」**★. The daemon may have actually processed it with **only the reply failing to arrive**, so an automatic resend **creates a duplicate** (two agents come up). The next decision is made **by the user looking at the list again**.
4. **A reply that arrives late after expiry is discarded. That request number is not reused.**
5. **「기다리는 중」 indicator — ★proposed default 1 second, confirmed at the shell work stage★.** This value is **the screen's job, so outside the crate**, and what this ADR fixes is not a number but ★**the structure that showing and giving up are at different points in time**★ — at about 1 second 「기다리는 중」 appears, and at 8 seconds it gives up. **That structure is confirmed and the 1 second is still a proposal.**

## 거부한 대안

- ★**A different deadline per command kind**★ — there are **30** `AgentCommand` branches (measured 2026-09-04). We would manage 30 values by hand, **have to decide one more each time a command is added**, and with no measurement **all those values would be guesses.** User decision: *"When do we set seconds for each of them, just make it shared."*
- **Drop the connection on expiry** — ★**one slow request drops a perfectly good connection**★. Connection health is seen by **a separate axis called keepalive**. If we put that role on the request deadline too, two failures are mashed into one signal.
- **Automatic resend after expiry** — the **duplicate creation** problem of decision 3 above. No response does not mean 「안 됐다」, so a resend may apply **the same operation twice**.
- **A 30-second cap** — the user **judged it large**. ★**This is not a hypothesis but the current value**★ — `forward_daemon_command` uses 30 seconds today (`src-tauri/src/commands/agent.rs:263`), and the comment at that spot gives its own ground: 「정상 경로의 왕복은 loopback 에서 수 ms 라 30s 에 절대 안 닿는다 · 넉넉히 잡아 **느린 데몬을 타임아웃으로 오판하지 않으면서** 무한 hang 만 확정적으로 끊는다」. ★**That ground holds only when 「포기 시점 = 사용자가 처음 이상을 눈치채는 시점」**★ — decision 5 **splits the indicator off at 1 second**, and that premise changes. The anomaly is already visible at 1 second, so the cap **only needs to be large enough to avoid a misjudgment**, and 30 seconds is far larger than that. So the reason for rejection is not that 「30초가 틀렸다」 but ★**「그 값을 정당화하던 구조가 이 결정으로 달라졌다」**★.

## 근거

- **We do not measure the deadline value by 「데몬 죽음을 얼마나 빨리 알아채나」** — a disconnect wakes all waiters with Err, so that side is already covered. What this value measures is **silence** alone.
- ★**The place where silence really exists is written in the protocol**★ — ★`AgentCommand::CommandOutcome`★ (`crates/engram-dashboard-protocol/src/messages.rs:296` — ★**not `AgentEvent`. It is a reply the shell hands back to the daemon, so the direction is opposite**★), which carries a command's **outcome**, **has no `request_id` field of its own**, so if it were put into wait matching, **there is no partner to wake and it becomes a permanent wait** — the code comment **admits this itself** (measured — messages.rs:284-287). The correlation key is inside `reply`.
- ★**There is effectively only one reply that wakes a pending request with Err, and it is a string**★ — the shell's `reply_outcome` ★maps **only** `AgentEvent::Error { message, .. }` to Err and passes everything else on as Ok★ (measured — `src-tauri/src/daemon_client/protocol_state.rs:32`). The two beside it are on different axes: `AgentEvent::SubscribeFailed { agent_id, reason }` **has no request_id and is not a matching target to begin with** (the comment on its `reason` states 「사람이 읽는 진단 문자열 — 기계 분기 금지, 문구는 예고 없이 바뀐다」 explicitly), and the `Err` of `AgentEvent::CommandReply` (messages.rs:531) ★**really has `code`·`retry` fields a machine can read**★ (that TS contract, messages.rs:298). ★**So do not lump it together as 「실패 답장에는 코드가 없다」**★ — the code has a place where it exists, and only that **the path that wakes pending is a single string** is the fact this decision stands on. And either way, **what the deadline guards against is not the case where it arrives but ★the case where it never arrives★.**
- **The ground for 8 seconds is user judgment** — the user judged the 30 seconds first proposed 「너무 크다」, and set 8 seconds after confirming the structure that ★**if the indicator comes up at 1 second, the cap is a safety net and is not felt**★. So this value is not 「사용자가 기다리는 시간」 but **「영영 안 오는 것을 끊어 내는 자리」**.
- **The ban on automatic resend gets the same answer by ADR-0159's decision yardstick too** — in safety × usefulness, automatic resend ★**gets caught on the safety leg**★ (the same operation may be applied twice). ADR-0162 also closed the same problem with 「결과 저장소 대신 상태 조회」. ★**Both ADRs are decisions about the control relay route, and this ADR does not claim to extend those clauses to the shell path.**★
- ★**Unverified — we have never measured how many seconds an agent spawn really takes**★. Of the 30 branches, **only that one** could exceed 8 seconds. **If it overflows when measured after attaching, raise the cap.**

## 영향 / 불변식

- ★**Do not reuse numbers** (decision 4)★ — if the number of an expired request is reused, **an old reply arriving late is misattributed as the partner of the new request.** Expiry only wakes the waiter, **and does not mean that number is dead on the wire**. ★**`daemon_client_pending` is not the regression net for this clause**★ — what that test measures is **the succession of an overlapping number** (the old waiter wakes with an error instead of hanging, and the new request takes over that number), and the ban on reuse after expiry is **not yet caught by any test**.
- **Do not put `AgentCommand::CommandOutcome` into wait matching** — if you do, even with a deadline it **always ends only in expiry** (there is no partner to wake). The canonical source is the comment on that variant.
- **A deadline expiry does not change the connection state** (decision 2). If expiry triggered reconnection, the reconnect budget of ADR-0180 decision 4 would **burn down because of one request.** The notification too is a strip, not a popup (ADR-0180 decision 2 — 「명령 하나 실패」 is not eligible).
- **The indicator (1 second) and giving up (8 seconds) live in different layers** (decision 5) — the indicator is shell/screen, giving up is `transport`. ★**Do not adjust one value and then set the other to follow it**★ — they are not two scales measuring the same thing but **different jobs**.
- ★**When applying, decide together what to do with the current 30 seconds**★ — the `REPLY_TIMEOUT` of `forward_daemon_command` is a live value, so bringing in a shared 8 seconds **lowers** that spot and the remaining handlers **gain a cap they did not have.** Both changes must land in one commit for 「공용 하나」 to actually hold.
- ★**Unverified**★:
  1. **The real time an agent spawn takes** (「근거」 above) — the only real risk of 8 seconds is here.
  2. **All the reading is static** — we did not actually launch a request and reproduce an expiry.
