# ADR-0167: Per-window theme is kept in the settings file and entries of dead windows are swept at boot

- 상태: 확정 (2026-08-23, basis: user decision) · 부분 폐기 by ADR-0265 (decisions 1, 3, 6, 7 and 8) · 부분 폐기 by ADR-0302 (the popout label shape in the 근거 section, the counter 「앱을 띄울 때마다 1 부터 다시 세는」 (that restarts counting from 1 each time the app is launched))
- 관련: ADR-0166(the UI settings file as the source of truth — this ADR **extends** it) · ADR-0155(command bus) · ADR-0057(per-window tab ownership) · CLAUDE.md 「LLM-우선 제어」 · `src-tauri/src/ui_settings.rs` · `src-tauri/src/commands/settings.rs` · `src-tauri/src/commands/popout.rs` · `src-tauri/src/view_commands.rs` · `src/commands/themeCommands.ts` · step-log S20 · Amended by ADR-0265 (decisions 1, 3, 6, 7 and 8) · Amended by ADR-0302 (the popout label shape in the 근거 section, the counter 「앱을 띄울 때마다 1 부터 다시 세는」)

> ★**The premise shared by decision 6 and 「근거」, 「레이아웃은 디스크 영속이 없다」 (the layout has no disk persistence), are no longer true**★ (note 2026-10-04, decision unchanged). From storage management P3b3 (`f9db35a`) the layout is persisted in `shell\state\state.json` and a boot after a normal shutdown restores even popouts (source of truth = TRD `docs/process/S21-storage/trd.md` §6). **The conclusion of the sweep still stands — only the ground changed:** the sweep runs at the very start of the user setup and the windows of restored popouts are opened after it (TRD §6-5 ⑨ · `src-tauri/src/lib.rs` setup), and a restored popout also gets its label fresh on every run (`PopupCounter` — TRD §6-3). So a non-declared label in the file at the moment of the sweep is still, by definition, entirely dead. The sweep itself is lifted in P3d as ADR-0265 decision 7 says — because the per-window theme moves into the window entry (`WindowTabs.attrs`) and dies together with the window.

## 맥락

The theme is currently **a single global value** in `<data_dir>/ui-settings.json`, and `ui.refresh` pushes that one value to every window (ADR-0166). What the user wants is to **pick one window and change the theme of that window only**.

The drawing layer can already do it — every window has its own document and wears its own `data-theme`, so it is **already physically independent**. What is missing is only **a way to name one window**.

So this ADR answers two questions: **on which path** to put the way to name a window, and how to close the **wrong application after a restart** that follows the moment a value is stored keyed by window name.

## 결정

1. **The per-window theme is settings data, not a command.** It rides on the existing file + `ui.refresh` path. The rule that splits them = **things that create, split and remove (windows, splits) are commands and Rust carries them. Display state that the web layer can re-apply while alive (theme, later font) is data + refresh.** The decider used at the fork = **「refresh 한 번으로 눈앞에서 바뀌는가」 (does one refresh change it before your eyes)** — a value that needs a remount or window re-creation is not put on the data path.
2. **The scope is the theme alone.** Fonts and the other slots are follow-ups.
3. **`ui.refresh` spreads each window's own value per window** — it replaces the current shape of pushing one value to all windows.
4. **The boot query knows 「어느 창이 묻는가」 (which window is asking).** Today `get_ui_settings` has no window argument, so **a newly made popout has no way at all to receive its own value.** Tauri hands the window over for free.
5. **Take down the `theme.set` and `theme.toggle` declarations.** They are **the real instance of the misclassification** that decision 1 named — expressing display state as a command. In addition **structurally it cannot name a non-host window** (a bus command declared by the frontend is executed only in the host window the shell chose). Of the four commands Step 4 put on the bus two come down and `tab.next` and `slot.empty` remain, so **the bus path stays covered by tests.**
6. ★**Entries of dead windows are swept at boot — not at refresh.**★ `ui.refresh` is the job of re-reading settings, so deleting entries there does not fit that job, and it **races** — if an agent writes in advance the entry of a window still being created, that entry is deleted before the window arrives. At boot the decision is free: the layout has no disk persistence, so **at the moment of boot there is not a single popout**, and thus the popout entries in the file at that time are **by definition all dead**.
7. **Windows the settings declare (`main`·`agent-tree`) are excluded from the sweep.** Those windows are always there, and excluding them removes the very risk that 「창이 아직 안 떴을 수 있다」 (the window may not have appeared yet).
8. **The write of the sweep is atomic** (temp file + rename) — even if it dies mid-write, no half file is left.

## 거부한 대안

- **Attach a `window` argument to `theme.set`.** Structurally impossible — it is a bus command declared by the frontend, so the envelope reaches **only the host window the shell chose** (the host reselection in `src-tauri/src/view_commands.rs`), and a non-host window has no means to execute that command. Before that, by the criterion of decision 1 it is **the wrong category.**
- **Make a separate shell-declared command for per-window theme.** ★Weak ground for rejection — prose only★: it is a usability argument that two theme commands would remain and the caller would have to pick one of the two every time, and the rest repeats 「범주가 틀렸다」 (the wrong category) (decision 1). There is no quantitative or measured ground.
- **Persist the per-window theme keyed by runtime label but do not sweep.** The wrong application in 「근거」 below occurs as is — the theme of `slot-popup-1` from yesterday is silently applied to a popout that opens first today.
- **Sweep on every refresh.** ★Weak ground for rejection — prose only★: it is a scenario argument that it races with an agent that wrote in advance the entry of a window about to open, and there is no measurement. In addition it blurs what 「설정을 다시 읽는 일」 (the job of re-reading settings) is (decision 6).
- **Split the storage into a persistent file + a session file so the volatile part is never persisted.** ★Weak ground for rejection — prose only★: it is a comparison argument that the boot sweep gives the same result with fewer parts, and a judgment that it is early now. **It was not discarded but left as a live option at the fork in 「영향 / 불변식」 below.**
- **Widen the answer's `source` slot to express 「이 창엔 항목이 없다」 (this window has no entry).** ADR-0166 pinned the two-branch reasons as an invariant. There is no need to widen either — a window with no entry folds to the global value, so **the existing two branches hold as they are.**

## 근거

- **★The reason the sweep is needed (do not shorten this)★** — the popout window label is made by **a process-local counter that restarts counting from 1 each time the app is launched** (`slot-popup-1`·`slot-popup-2`… — `PopupCounter` in `src-tauri/src/commands/popout.rs`). And the layout is not persisted. So **the same label after a restart points to a different window.** Without the sweep, the theme saved yesterday under `slot-popup-1` is **silently applied** to the popout that opens first today — whatever that window is. **The distinction matters: an orphan entry of a closed window is itself harmless** (there is no live window to receive that value) — **what is not harmless is the wrong application after a restart.**
- **Why pin it now, not later** — a proper storage and persistence scheme is coming soon. It too will hold data **keyed by window identity**, and the person implementing it is **likely not to know** this risk. Pinning the decision with its reason and hanging one anchor line in the code is how a future implementer meets this risk.
- **★The relation to ADR-0166 — misread twice in conversation★** — ADR-0166 decision 3 wrote that **the shell only reads**, and `src-tauri/src/ui_settings.rs:6-10` wrote that the absence of a write path is intentional. ★That is not an independent prohibition that the app must never write.★ The reason written there is **write contention** — if *the on-screen theme toggle* starts saving to the file, the outside agent's editor and the screen would fight over the same file, and 「누가 마지막에 썼나」 (who wrote last) was not within that pilot's scope. In addition **「쓰는 쪽 없음」 (no writing side) is not in ADR-0166's 영향/불변식 section** — it is a scope statement of the pilot, not an invariant. That reason **does not reach the boot sweep**: it does not persist the toggle, the screen is not involved, and the write happens once at boot. So this ADR **extends** ADR-0166 — ★it stamps no discard and is not a reversal.★
- **There is nothing to touch in the drawing layer** — every window has its own document and `data-theme`, so per-window application already holds physically. What this decision adds is **only the means of naming**.
- **The ground that the boot-time decision is free** — from the single fact that the layout has no disk persistence, 「부팅 순간 팝아웃 0 개」 (0 popouts at the moment of boot) follows, and from there 「그때 있는 팝아웃 항목 = 전부 죽은 것」 (popout entries present at that time = all dead) comes out **without a decision**. Exempting the declared windows (decision 7) also removes the remaining risk that 「창이 아직 안 떴을 수 있다」 (the window may not have appeared yet).
- **The ground that bus coverage is kept** — what comes down is two of the four (`theme.set`·`theme.toggle`) and `tab.next` and `slot.empty` remain.
- **★No measured ground — this is a decision pinned before implementation.★** This ADR does not yet have the kind of backing that ADR-0166 had, such as GUI measurement. Targets to confirm at implementation = per-window value delivery · whether the boot sweep skips the declared windows · the atomicity of the sweep write.

## 영향 / 불변식

- **Do not put 「refresh 한 번으로 눈앞에서 바뀌지 않는 값」 (a value that does not change before your eyes with one refresh) on the data path** — what needs a remount or window re-creation is a command (decision 1). If breached, the data path bypasses the place ADR-0166 pinned as no remount.
- **The sweep runs only at boot — do not put it on the `ui.refresh` path** (decision 6). If breached, the entry of a window about to open is deleted before the window arrives.
- **Do not sweep entries of windows the settings declare (`main`·`agent-tree`)** (decision 7). If breached, the 「창이 아직 안 떴을 수 있다」 (the window may not have appeared yet) decision revives.
- **The sweep write is atomic** — temp file + rename. If breached, a crash during boot leaves a half settings file.
- **Hang a `// ADR-0167` anchor wherever data is held keyed by window identity** — both the sweep code and any future place that persists a value by window identity. This risk is not visible from the code alone, and the anchor is the only surface through which the next implementer reaches this document.
- **The answer's `source` keeps two branches** (ADR-0166 invariant). A window with no entry folds to the global value.
- **A future fork — if app-side writes grow beyond the boot sweep**, the contention ADR-0166 chose not to resolve becomes real. There are two roads and **both are open and neither is taken for now**: ① **split the file** — so that the data the app writes and the data the agent writes do not share one document. ② **gather writes into one serialized task** — so that 「누가 마지막에 썼나」 (who wrote last) has a single answer. That this is the fork a future storage scheme will meet — **making the next implementer see this instead of rediscovering it** is the purpose of this item.
- **The header 「쓰기 경로 없음」 (no write path) at `src-tauri/src/ui_settings.rs:6-10` must be read together with this ADR** — reading that sentence alone misreads the boot sweep as prohibited (this actually happened twice).
