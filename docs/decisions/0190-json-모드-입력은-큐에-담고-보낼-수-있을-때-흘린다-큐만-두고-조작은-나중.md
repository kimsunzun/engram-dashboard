# ADR-0190: json 모드 입력은 큐에 담고 보낼 수 있을 때 흘린다 — 큐만 두고 조작은 나중

- 상태: 확정 (2026-09-09, 근거: 사용자 결정 + 실측 타이밍 + T-28 선례) · 부분 폐기 by ADR-0193 (결정 4 의 「턴이 도는가는 코어가 이미 안다」 조항 (큐 해제 판정을 코어 단독으로 좁힌 부분))
- 관련: ADR-0044(json 모드 배선) · ADR-0189(codex 통로) · ADR-0187(app-server 통로 확정) · ADR-0127(턴 관측 사실 층) · `docs/tracking.md` T-28 · step-log S21 · Amended by ADR-0193 (결정 4 의 「턴이 도는가는 코어가 이미 안다」 조항 (큐 해제 판정을 코어 단독으로 좁힌 부분))

## 맥락

codex app-server 는 프로세스가 뜬 뒤에도 **바로 말을 걸 수 없다** — `initialize` 왕복(실측 약 130ms)과 `thread/start` 왕복이 끝나야 `thread.id` 를 알고, 그것 없이는 `turn/start` 요청을 **만들 형태 자체가 없다**(ADR-0187). 그 구간에 입력이 오면 보낼 곳이 없다.

**그 구간에 입력이 실제로 온다.** 사람이 130ms 창에 칠 일은 드물지만 LLM 경로는 그렇지 않다 — 이 저장소에 이미 **T-28**「갓 스폰된 터미널 수신자가 배달된 편지를 제출하지 않는다」가 있고, 원인이 같은 축이다(수신자가 준비되기 **492ms 전에** 제출이 쓰였다, 실측).

★**사용자 지적이 문제의 모양을 바꿨다**★ — 「준비 전 입력」은 특수 케이스가 아니다. **턴이 도는 중에 온 입력과 같은 상황**이고(둘 다 「지금 못 보낸다」), 다른 것은 **언제 흘려보내나**뿐이다. 실제 터미널 프로그램도 여러 줄을 미리 받아 두고 턴이 끝나면 밀어 넣는다. 그러니 둘을 하나로 합친다.

## 결정

**json 모드의 입력을 큐에 담고, 보낼 수 있게 되면 흘린다. 큐 자체는 json 모드 공통이다 — codex 전용이 아니다.**

- **「준비된 뒤에 쏘라」는 규칙을 만들지 않는다.** 그 규칙을 두면 부르는 쪽마다 준비 여부를 알아야 해서 로직이 복잡해진다. **부르는 쪽은 그냥 보내고, 큐가 알아서 담는다.**
- **입력을 버리지 않는다.** 상한을 넘거나 준비가 끝내 실패하면 그때 오류로 돌린다(`send_input` 이 이미 `Result` 다).
- ★**「지금 보낼 수 있나」를 transport 구현체가 신고하는 축을 하나 만든다**★ — 판정은 각 구현체 안에서 하되(codex = `thread/start` 응답을 받았고 턴이 안 돈다 / claude json = 턴이 안 돈다) 축은 공용이다.
- **「턴이 도는가」는 코어가 이미 안다.** 큐가 그 사실을 **읽는다**(`AgentManager::turns()` 접근자가 이미 있다).
- ★**이번에 만드는 것은 큐뿐이다**★ — 항목 빼기 · ESC 로 대기분 전부 밀기 · 순서 바꾸기 같은 **조작은 만들지 않는다.** 흘려보내는 룰도 「보낼 수 있게 되면 순서대로」까지다.
- **PTY 통로는 이번 범위 밖이다**(그쪽 증상 = T-28).

## 거부한 대안

- **준비 전 입력을 즉시 오류로 돌려준다** — 단순하지만 ★**그 입력이 사라진다**★. 가장 나쁜 결과이고, T-28 이 이미 그 부류의 사고를 기록해 두었다. 사용자 결정으로 기각.
- **큐를 codex 구현체 안에만 둔다** — 2a 범위가 작아지지만 **같은 문제를 두 곳에서 다르게 풀게 된다.** claude json 모드도 턴 중 입력이라는 같은 상황을 갖는다. 사용자 판정 = 공통으로 둔다.
- **「준비됨」을 전 계층 공용 신호로 승격해 T-28 까지 함께 푼다** — T-28 이 스스로 「수신자 준비됨 신호가 없어 **조사부터 시작하는 단독 주제**」로 표시해 두었다. 그것을 2a 로 끌어들이면 범위가 확 커진다. 지금은 json 모드로 한정한다.
- **큐 조작(빼기·전부 밀기)까지 이번에 만든다** — 사용자 보류. 「나중에 다른 claude·codex 앱들을 보고 편한 쪽을 판단한다」. ★**큐가 있으면 어떤 조작 규칙도 나중에 얹을 수 있다**★는 것이 지금 큐만 두는 근거다.

## 근거

- 타이밍 실측 = `.claude/handoff/attachments/codex-measurements-2026-09-09.md`(`initialize` 약 130ms · `thread/start` 왕복 · `turn/interrupt` 18ms).
- T-28 의 원인 규명(데몬 debug 로그): 로스터 등장 약 1ms 뒤에 제출이 쓰였고 그 세션의 CLI 는 그로부터 약 492ms 뒤에 초기화를 끝냈다. **준비 이전 입력이 실재하는 경로임을 이 저장소가 이미 실측했다.**
- ADR-0127 저촉 확인 — 그 결정이 고정한 것은 턴 관측을 **지우는 호출 지점 둘**이다. 큐는 **읽기만** 하므로 그 규칙 밖이고, 읽는 소비자가 하나 늘 뿐이다(기존 소비자 = 메시징 busy 게이트).

## 영향 / 불변식

- ★**claude json 모드의 동작이 바뀐다**★ — 지금은 입력을 즉시 밀어 넣는다. 큐가 생기면 턴 중 입력이 즉시 나가지 않고 대기한다. **이것이 이 ADR 이 codex 전용이 아닌 이유이자, 사용자 확인을 받은 이유다.**
- **쓰기 창구는 여전히 하나다.** 큐는 그 앞에 붙는다 — 단일 writer 규율(ADR-0189)과 부딪히지 않는다.
- ★**우편 파킹과 기능이 겹친다**★ — 우편은 수신자가 바쁘면 편지를 파킹해 두고 상한(30 분 fail-open)까지 기다린다. 큐가 생기면 **대기 자리가 둘**이 된다. **지금은 둘을 따로 둔다** — 나중에 우편 쪽을 고칠 것을 전제로 한 사용자 결정이고, 그때 어느 쪽으로 합칠지 판단한다. ★그 판단 전까지 「편지가 두 번 대기한다」가 실재할 수 있음을 알고 간다.★
- **상한을 정해야 한다** — 큐 길이와 대기 시간 상한. ★값과 초과 시 동작(오류 반환)은 구현 시 정하고 근거를 코드 주석에 남긴다.★ 상한이 없으면 준비가 끝내 안 되는 세션에서 입력이 영구히 매달린다.
- **화면에 대기 중임을 알릴 수단이 필요하다** — 지금 프론트에 그 개념이 없다. 없으면 사용자는 자기 입력이 사라진 것처럼 본다. ★범위·모양은 후속.★
- **이 결정을 다시 열 트리거** — ① 우편 쪽을 고칠 때(위 중첩) ② 큐 조작을 실제로 붙일 때(그 룰이 이 ADR 의 「순서대로」를 대체한다) ③ PTY 통로까지 넓힐 때(T-28).
