# ADR-0190: json-mode input goes into a queue and is released when it can be sent — only the queue now, controls later

- 상태: 확정 (2026-09-09, basis: user decision + measured timing + the T-28 precedent) · 부분 폐기 by ADR-0193 (the clause 「턴이 도는가는 코어가 이미 안다」 of decision 4 (the part that narrowed the queue-release decision to the core alone)) · 부분 폐기 by ADR-0231 (user input mid-turn is held only until the earliest boundary · Idle user-first · halted · reopen trigger ② fired)
- 관련: ADR-0044 (json-mode wiring) · ADR-0189 (codex channel) · ADR-0187 (app-server channel settled) · ADR-0127 (turn-observation fact layer) · `docs/tracking.md` T-28 · step-log S21 · Amended by ADR-0193 (the clause 「턴이 도는가는 코어가 이미 안다」 of decision 4 (the part that narrowed the queue-release decision to the core alone)) · Amended by ADR-0231 (user input mid-turn is held only until the earliest boundary · Idle user-first · halted · reopen trigger ② fired)

## 맥락

Even after the process is up, the codex app-server **cannot be spoken to right away** — the `initialize` round trip (measured about 130ms) and the `thread/start` round trip must finish before `thread.id` is known, and without it there is **no form even to build** a `turn/start` request (ADR-0187). If input arrives in that span, there is nowhere to send it.

**Input really does arrive in that span.** A person rarely types in a 130ms window, but the LLM path is different — this repository already has **T-28**「갓 스폰된 터미널 수신자가 배달된 편지를 제출하지 않는다」, and the cause is on the same axis (the submit was written **492ms before** the receiver was ready, measured).

★**The user's point changed the shape of the problem**★ — 「준비 전 입력」 (input before ready) is not a special case. It is **the same situation as input that arrives while a turn is running** (both are 「지금 못 보낸다」 (cannot send now)), and the only difference is **when to release it**. Real terminal programs also take several lines in advance and push them in when the turn ends. So we merge the two into one.

## 결정

**Put json-mode input into a queue and release it when it can be sent. The queue itself is common to json mode — it is not codex-only.**

- **Do not make a rule 「준비된 뒤에 쏘라」 (fire only after ready).** With that rule every caller would have to know whether it is ready, and the logic gets complicated. **The caller just sends, and the queue takes it in by itself.**
- **Do not discard input.** If the cap is exceeded or readiness ultimately fails, it is turned into an error at that point (`send_input` is already a `Result`).
- ★**Create one axis on which the transport implementation reports 「지금 보낼 수 있나」 (can it send now)**★ — the decision is made inside each implementation (codex = the `thread/start` response was received and no turn is running / claude json = no turn is running), but the axis is common.
- **「턴이 도는가」 (Is a turn running) is already known by the core.** The queue **reads** that fact (the `AgentManager::turns()` accessor already exists).
- ★**What we build this time is only the queue**★ — **we do not build controls** such as removing an item · pushing out all pending items with ESC · reordering. The release rule also goes only as far as 「보낼 수 있게 되면 순서대로」 (in order once it can be sent).
- **The PTY channel is out of scope this time** (its symptom there = T-28).

## 거부한 대안

- **Return an error immediately for input before ready** — simple, but ★**that input disappears**★. It is the worst outcome, and T-28 has already recorded an incident of that kind. Rejected by the user's decision.
- **Keep the queue only inside the codex implementation** — the 2a scope gets smaller, but **the same problem would be solved differently in two places.** claude json mode also has the same situation of input mid-turn. User decision = make it common.
- **Promote 「준비됨」 (ready) to a signal common to all layers and solve T-28 along with it** — T-28 itself marked this as 「수신자 준비됨 신호가 없어 **조사부터 시작하는 단독 주제**」 (a standalone topic that **starts with investigation** because there is no receiver-ready signal). Pulling it into 2a would blow the scope up. For now it is limited to json mode.
- **Build the queue controls (remove · push out all) this time too** — the user put them on hold. 「나중에 다른 claude·codex 앱들을 보고 편한 쪽을 판단한다」. ★**With a queue in place, any control rule can be layered on later**★ is the ground for having only the queue now.

## 근거

- The timing measurement = `.claude/handoff/attachments/codex-measurements-2026-09-09.md` (`initialize` about 130ms · `thread/start` round trip · `turn/interrupt` 18ms).
- The cause established for T-28 (daemon debug log): the submit was written about 1ms after the roster appearance, and that session's CLI finished initialization about 492ms after that. **This repository has already measured that input before ready is a real path.**
- ADR-0127 conflict check — what that decision fixed is **the two call sites that erase turn observation**. The queue only **reads**, so it is outside that rule and the only change is one more reading consumer (the existing consumer = the messaging busy gate).

## 영향 / 불변식

- ★**The behavior of claude json mode changes**★ — now it pushes input in immediately. Once the queue exists, mid-turn input does not go out immediately but waits. **This is why this ADR is not codex-only, and why we took the user's confirmation.**
- **The write endpoint is still one.** The queue attaches in front of it — it does not collide with the single-writer discipline (ADR-0189).
- ★**It overlaps in function with mail parking**★ — mail parks a letter when the receiver is busy and waits up to the cap (30 minutes fail-open). With the queue there are **two waiting places**. **For now we keep the two separate** — a user decision that presupposes fixing the mail side later, and at that time we decide which way to merge them. ★Until that decision, we go on knowing that 「편지가 두 번 대기한다」 (a letter waits twice) can really happen.★
- **A cap has to be set** — a queue length and a wait time cap. ★The values and the behavior on exceeding (returning an error) are decided at implementation and the ground is left in a code comment.★ Without a cap, input hangs forever in a session that never becomes ready.
- **We need a way to show on the screen that it is waiting** — the frontend has no such concept now. Without it the user sees their input as if it vanished. ★Scope and shape are follow-up.★
- **Triggers to reopen this decision** — ① when the mail side is fixed (the overlap above) ② when queue controls are actually attached (that rule replaces the 「순서대로」 (in order) of this ADR) ③ when widening to the PTY channel (T-28).
