# ADR-0220: Restructure the surfaces agents read into four families and remove the mail visibility filter

- 상태: 확정 (2026-09-23, basis: user decision) · 부분 폐기 by ADR-0285 (the table-of-contents screen place in decision 2 and the first item of the consequences)
- 관련: Amends ADR-0126 (separating CLI and MCP spelling) · Amends ADR-0132 (group help discovery path) · Amends ADR-0133 (mail visibility filter) · Amends ADR-0211 (instruction-sheet pointer and splitting mail into sub-pages) · Amends ADR-0212 (file name and section marker shape) · Amends ADR-0213 (the ban on engram help mail in the instruction sheet) · Amended by ADR-0285 (the table-of-contents screen place in decision 2 and the first item of the consequences)

## 맥락

There were three surfaces from which an agent learns the contract — priming (resident) · MCP tool descriptions (resident) · the `engram help` screen (on demand). The three **carried the same contract several times over**, and even when we wanted to shrink them, it was not settled which one to shrink.

On top of that, three problems overlapped.

1. **The help machinery was big.** The body was cut into 17 sections and a fixed assembly table joined them together for each screen, and the code for that assembly and validation alone was about 280 lines of `engram.rs` (4.7% of the whole) and 16 tests. Only mail had 4 sub-pages, and their ids were derived from the verb token, so adding a sub-topic in the code meant also adding two sections to the file for it to load.
2. **The screen was conditional, so humans and agents saw different things.** Whether mail showed in the list was decided by the `ENGRAM_MAIL` marker planted at spawn (ADR-0133 decision 1). Without the marker the default is 「보임」 (shown), so **the screen a human typed in a shell had mail and the agent's screen did not.** This session showed the user the wrong screen several times because of that mistaken assumption.
3. **There was no place to learn windows, tabs, splits and themes.** They stood only as one line in the root list and had no screen of their own, so an agent had to quiz `engram commands` one by one for the arguments of 17 layout commands.

## 결정

1. **There are five screens, in one-to-one correspondence with the file sections** — `root` (table of contents) · `mail` · `agent` · `window` · `theme`. Rendering is not assembly but **picking one section**. The mail sub-pages and their derived ids are removed.
2. **Priming points at the four families directly, each by its own command** (four lines such as `engram help mail`). ★No surface carries guidance to type a bare `engram help`★ — it removes the round trip of calling the table of contents first without knowing which chapter to look at. The table-of-contents screen itself stays (the place where someone who has not seen the priming types in a shell).
3. **The division of labor per surface is nailed down.** MCP tools carry **only the argument descriptions**, and their source of record is the per-field description of the input schema. All other contract (how to read the response rows · the envelope · the pitfalls) is carried entirely by the help screen. Priming carries only the pointer and what cannot be learned anywhere else.
4. **The mail screen is always visible.** The `ENGRAM_MAIL` marker is removed on both the injection and the reading side, and `MailSurface` is deleted. ★Enforcement is not touched★ — the `mail_allowed` derivation · the credentials · the daemon rejection stay as they are. The marker was an education axis, not enforcement.
5. **The CLI mail verbs stay as code but are not taught on any screen.** They are revived if a non-MCP backend actually appears later.

## 거부한 대안

- **Have the agent read the help file directly (`cat`/grep)** — ★there is no means to tell it the path★. The help file of an installed build is in `prompts/` next to the executable, and its absolute path depends on where the user unpacked it, so there is no fixed value. There is **zero** machinery that substitutes a path into the priming body (measured), and the codex terminal injection path rejects backslashes, so it **cannot carry a Windows absolute path at all**. claude passes a file path and not the body, so substituting would add a new step of reading and rewriting. `engram help <계열>` is one binary on PATH, so that problem does not exist in the first place.
- **Push the help body into residency like priming** — the on-demand 8.7 KB would become resident, which runs straight against the purpose of this round. Besides, ★it is not possible as is today★ — the body has 20 double quotes and the codex terminal injection guard rejects `"` (measured).
- **Keep the per-topic sub-pages** (`mail send`/`status`/`pending`/`recv`) — the size per screen gets smaller, but the machinery that supports that assembly is about 280 lines and 16 tests. The value does not reach that price.
- **Remove the table-of-contents screen and let priming take its place** — there remains the place where someone who has not seen priming types in a shell. We keep the table of contents as a file section.
- **Keep the marker** — the human screen and the agent screen keep splitting and the same mistaken assumption repeats. The thing to hide is also gone — the screen now teaches only the MCP tools and writes not a single line of CLI verbs.
- **Leave the marker code as a comment instead of deleting it** — code in a comment is not seen by the compiler, so it quietly rots when its surroundings are refactored, and it cannot be used as is when revived. The grounds for reviving are carried by git history and this ADR.

## 근거

- **Machinery measured** — `engram.rs` 5,959 → 5,682 lines (−277). After the restructure, `--bin engram` 122 and `--test engram_cli` 41, all green.
- **Resident portion measured** — the two tool descriptions together, roughly 820 characters → 220 characters. The five lines removed were duplicates 1:1 of the per-field descriptions in the input schema, and the schema side is more detailed (`@here`/`@all` · the deadline lower bound · reply exclusivity).
- **Injection guard measured** — the codex terminal path rejects `'` `"` `%` `\`. This is the basis that blocked the two alternatives above.
- **We checked that every command written on the screen really exists against the catalog** — `tab.next` and `slot.empty` are registered by the frontend bus and so do not show up in a source grep, but exist at runtime.
- **The screen was teaching an argument that does not exist** — the draft wrote `agent new --backend`, but the hyphen form accepts only `--cwd` and `--name`. We resolved it by unifying the agent chapter to the dotted form, and this is the real-occurrence basis for 「한 파일 안에 두 호출 꼴이 섞이면 안 된다」 (two call shapes must not be mixed within one file).

## 영향 / 불변식

- ★**There are five sections and they correspond one-to-one with the screens**★ — if even one is missing, the whole file is rejected and the built-in copy goes out (no half screen — ADR-0212 decision 4 as is). When a new family is added, `HelpTopic` and `required_section_ids` in the code and the file sections are increased together.
- ★**The home of the argument contract is the per-field description of the input schema, one place**★ — if arguments are written again in the tool description text, from then on there are two copies, and on the day they diverge there is no telling which is true. Pinned = `the_send_message_entry_teaches_its_own_call` in `crates/engram-dashboard-daemon/src/control/mcp_server.rs`.
- ★**The home of 「`pending` 으로 상대 상태를 단정하지 말고 조회하라」 (ADR-0211 decision 2) (do not conclude the other side's state from the pending list; query it) moved to the help screen**★ — the contract is valid and only the surface moved. Pinned = `the_mail_screen_teaches_the_reply_contract` in `crates/engram-dashboard-daemon/src/bin/engram.rs`. If both places are empty, no surface is left that teaches that ban.
- ★**Do the four commands that priming points at actually parse and render?**★ — pinned = `the_priming_pointer_names_a_help_entry_that_actually_renders` in the same file. If it breaks, the agent never finds the surface **with no error at all** (both sides are fine within their own files).
- **This decision does not touch mail enforcement** — the `mail_allowed` derivation (`control/mod.rs`) and the daemon rejection (`mcp_server.rs`) stay as they are. The remaining decisions of ADR-0133 (the rejection response does not announce an alternative channel) also live on.
- ★**`ControlEndpoint.mail_allowed` stays with zero production readers**★ — Rust does not warn, so it looks like a dead field, but when a non-MCP backend appears, that axis comes alive again. If it is deleted, the next design is built treating that boundary as nonexistent. `TokenBinding.mail_allowed` on the credential side is a **separate field** and the rejection middleware keeps reading it.
- ★**This time we revived the line that ADR-0213 forbade**★ — that ADR nailed down 「지시서가 `engram help mail` 을 가리키면 그 줄은 자기 독자에게 **항상 실패한다**」 (if the instruction sheet points to the mail help screen, that line **always fails** for its own reader). Its basis was that the injection condition (`wants_priming = uses_mail && accepts_mcp_config`) and the exposure condition (`mail_allowed = uses_mail && !accepts_mcp_config`) are exclusive, so an agent that received the instruction sheet has the marker off without exception. **Decision 4 killed that premise** — without the marker the screen comes up unconditionally. That is why we stamped a partial-discard seal on that clause. ★An edit that tries to revive the marker should reread this line first★ — the moment it is revived, the four lines of priming become false again.
- ★**This ADR does not decide the language of agent-facing surfaces (the switch to Korean)**★ — priming and the two tool descriptions became Korean, but **the field descriptions of the input schema are still English**, so the language is split within one tool. Hangul reduces the character count but may be more expensive in tokens (≈1 character/token vs ≈4 characters/token) and has not been measured with a tokenizer yet. **The user postponed it to 「나중에 영어로」** (later, in English) — it will be fixed then in a separate ADR. Do not read the current state as a decision.
