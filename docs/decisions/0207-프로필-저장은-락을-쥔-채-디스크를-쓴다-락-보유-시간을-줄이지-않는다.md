# ADR-0207: Profile saves write to disk while holding the lock — we do not shorten the lock hold time

- 상태: 확정 (2026-09-18, basis: user decision + code measurement) · 부분 폐기 by ADR-0291 (accepting the growth of in-lock work and a worst-case time that reaches re-open trigger ②, and rationale 3 (the only write that does not go through `mutate`))
- 관련: ADR-0071(`store.save` runs while the map lock is held — this ADR reconfirms its `:27` **acceptance judgment** and does not touch its `:32` prohibition clause) · ADR-0006(lock order) · ADR-0119(single entrance to the agent registry) · ADR-0172(a failure is recorded where it failed) · `crates/engram-dashboard-agent/src/profile.rs:365-374` · `crates/engram-dashboard-agent/src/manager.rs:710-726` · Amended by ADR-0291 (accepting the growth of in-lock work and a worst-case time that reaches re-open trigger ②, and rationale 3 (the only write that does not go through `mutate`))

## 맥락

`ProfileRegistry` (`crates/engram-dashboard-agent/src/profile.rs:375-376`) guards the profile map with a single std `Mutex`, and every mutation path that touches disk (`mutate` `:391` · `mutate_if` `:402`) calls `store.save` **while holding the lock** (`:397` · `:408`). That save is JSON serialization → temp-file write → `sync_all` (fsync) → rename → directory fsync (`crates/engram-dashboard-agent/src/persistence/mod.rs:57-83`). Reads take the same lock (`list` `:413`), so **while a save is running, a task that reads the registry queues on that lock.**

★"The save is synchronous, so nothing can arrive at the same time" is a misreading★ (「저장이 동기니까 동시에 올 일이 없다」) — the daemon runs on a `#[tokio::main]` multi-threaded runtime, and while the save holds its own thread, tasks on other worker threads keep running. Synchronous means *that call holds that thread*, not *only one call arrives at a time*.

One of the queued reads is on the **critical path of mail sending**: `AgentManager::roster()` (`crates/engram-dashboard-agent/src/manager.rs:710`) goes through `profiles.list()` (`:726`), and the comment at that spot already says so (`:719` — 「이 조회는 우편 발송의 임계 경로에 있다」, "this lookup is on the critical path of mail sending"). 「프로필 하나를 저장하는 동안 편지 배달이 선다」 (letter delivery stalls while one profile is being saved) holds structurally.

This concern came up again from the coder side — after ADR-0071 had already decided this same structure and accepted its cost. The coder **refused the instructed fix and escalated it to a user decision** (commit `4967847` body — 「지시한 수정(락 안 디스크 쓰기를 유계로)이 ADR-0071 이 명시로 금지한 것이다」, "the instructed fix (bounding the in-lock disk write) is what it explicitly prohibits"), and ★that refusal was right★. **This ADR is the record that closes the re-discussion raised that way.**

## 결정

**Leave it as it is.** We make no change that shortens the lock hold time — we do not move the save out of the lock, do not switch to a read-only lock, and do not defer or batch the save. We **reconfirm** the acceptance judgment of ADR-0071 — that ADR already knew this cost and took it (`:27` 「advisory: save 중 map read 가 블록되지만 로컬 소형 파일이라 무시 가능」, "advisory: map reads block during save, but it is a small local file so it can be ignored"). ★**That sentence is not in the code as such**★ — `profile.rs:373-374` goes only as far as 「로컬 소형 파일이라 lock 보유 중 IO 비용도 무시 가능」 ("it is a small local file, so the IO cost while holding the lock can be ignored") and **does not say that blocked reads are accepted.** The only place that explicitly accepted the stalling of reads is ADR-0071:27.

★**What this decision closes is the 「지연」 (latency) axis only**★ — ADR-0071's consistency decision (the save is done **inside** the lock) is untouched by this ADR and stands as it is.

## 거부한 대안

- **(a) Move the save out of the lock to shorten the hold** — ADR-0071 already rejected it (`:20` — 「lock-hold 시간 단축이라는 이점은 로컬 소형 파일 IO 라 무의미하다」, "the benefit of shortening lock-hold time is meaningless because it is IO on a small local file") and explicitly prohibits reverting it (`:32`). If we take only a snapshot inside the lock and then release it, then when two mutations overlap, the in-memory state and the broadcast are the latest while only the disk is left stale (that order is written down at `profile.rs:366-370` — we do not move it here again). **It is not up for re-discussion** — to revert it, re-opening ADR-0071 comes first.
- **(b) Switch to a write that does not touch disk** — `set_last_failure` (`profile.rs:632`) is in fact that shape and even has a dedicated regression test (`:1120` `set_last_failure_reports_change_and_never_writes_to_disk`). But what makes it work is that the field is `#[serde(skip)]`, so **it is not a persisted field in the first place** (`:198-210`). It is a technique that cannot be used for persisted fields.
- **(c) Offload on the caller side** — **already applied** (`crates/engram-dashboard-daemon/src/command_delivery.rs:1366`, reason comment `:1351` — 「이 표의 핸들러는 프로필 락을 쥔 채 디스크를 쓰고」, "the handlers in this table write to disk while holding the profile lock"). But this is **a measure that protects the runtime worker threads and does not shorten the lock hold time** — other tasks waiting on the same lock still queue. So it is adopted, and yet it does not solve the problem this item points at.
- **(d) Make reads cheap (`RwLock` · snapshot cache · save debounce)** — it has never been written down as a candidate anywhere in this repository. All three bring in a new failure mode: a cache adds invalidation points, a debounce loses data if a crash happens inside the unsaved window, and an `RwLock` blocks reads just the same because the save takes the write lock anyway. **Above all, the thing to fix has never been observed, so choosing now would bring in an unfounded move.**

- **(e) Split the save unit — one file per profile instead of a single `agents.json`** — ★this branch **keeps** ADR-0071's 「락 안 저장」 (save inside the lock) while reducing the size of one write, so it is caught by none of the rejections (a) to (d)★. Even so we do not adopt it now: ① the thing to reduce (the lock hold time) has still **never been measured** ② atomicity no longer ends with a single `rename` — today one file is swapped out whole, so 「전부 아니면 전무」 (all or nothing) comes for free (`persistence/mod.rs:57-83`), but once it is split across several files, a new partially-applied state appears whenever one change spans several files. **It trades consistency for latency, and we do not know how much the latency side is worth.**

★Strength of the rejections★ — (a), (b) and (c) are tied to existing decisions and code measurement. **(d) and (e) rest mainly on 「측정이 없다」 (there is no measurement), so they are relatively weak** — which is why the re-open triggers below leave room for those two.

## 근거

1. **Consistency is already closed, and latency is the one axis left.** The ordering problem (stale overwrite) was solved by ADR-0071 with 「락 안 저장」 (save inside the lock), and that wall stands as it was.
2. **Writes happen only on lifecycle events.** The places that **call `mutate`/`mutate_if` directly** are 10 places in `profile.rs` (`:441 :465 :482 :537 :572 :600 :654 :672 :707 :746`). ★Do not confuse this with the list of public entry points★ — some, like `rename` (`:553`), go through `update_with`, so there are more entry points than that. Whichever way you count, the nature is the same: **all of them are create, delete, rename, parent change, session id acquire/update/observe, and incarnation update, and no path runs on every output chunk or state transition.** For an overlap to happen, a read has to arrive at the very moment an agent is created or deleted.
3. **Updating the failure record does not touch disk** — `set_last_failure` (`:632`) takes only the lock and does not call `store.save` (`:628-629` describes it as 「`mutate` 를 타지 않는 유일한 쓰기」, "the only write that does not go through mutate"), and a dedicated regression test measures that (`:1120`).
4. **There is neither an observed incident nor a measurement.** This item came out of reading the code and has never been reproduced at runtime.
5. **The scale ceiling is small.** The registry ceiling is `MAX_ROSTER_SIZE = 512` (`manager.rs:270` — measured) and what is saved is a single small local JSON file (`persistence/mod.rs:57-83`). ★**「실사용 프로필 6~15건」 (6 to 15 profiles in real use) is a local in-session observation and has no basis in the repository — leave it unverified**★. What rationale 5 leans on is not that figure but the fact that **the ceiling of 512 × the size of one profile** is still a small file.

## 영향 / 불변식

- **ADR-0071's 「`store.save` 를 lock 밖으로 빼지 말 것」 (do not move the save out of the lock) remains in force.** This ADR only reconfirms that prohibition and does not relax it.
- **The property that registry reads stall during a save stays open** — the mail-recipient decision (`manager.rs:710` → `:726`) is that path. ★Do not create documents or comments that write it as 「없다」 (there is none)★ — it was accepted, not removed.
- ★**There is already one comment that reads that way**★ — `manager.rs:522-523`, 「그래도 메일 배달은 막히지 않는다 … `roster()` 는 락 없이 부를 수 있고 배달 경로가 그렇게 쓴다」 ("even so mail delivery is not blocked … roster() can be called without a lock and the delivery path uses it that way"). **The lock there is `name_allocation`, not the profile Mutex.** Read as a bare sentence, it makes it look as if the property this ADR accepted does not exist — **the session that decides trigger ① will meet this comment first.** That comment is true in its own context, so it is not changed; we leave the fact that it is a trap here.
- **The same shape exists in `PresetRegistry` too** (`crates/engram-dashboard-agent/src/preset.rs:80-84` — `store.save` inside the lock). The title and decision of this ADR are narrowed to profiles, but **ADR-0071's prohibition stands for both.** If the same concern is raised under the preset name, apply rationales 1 to 5 as they are.
- **Swallowing an fsync failure with `tracing::error!` is outside the scope of this decision** (a separate matter — `persistence/mod.rs`).
- **Re-open triggers — if any one of the three holds, open it again.**
  1. **Read latency during a save is actually observed** — letter delivery visibly stalling or registry lookups freezing.
  2. **The lock hold time of one save is measured and confirmed to exceed the ms range** (Windows fsync spikes and security-software hooking are the candidates).
  3. **The save file is no longer 「소형」 (small)** — rationale 5 is the premise of this decision. The open item that `old_session_ids` has no ceiling directly shakes that premise (the record of that open item = ADR-0202:42 · `docs/process/step-log.md:2299` ③. The field itself is at `profile.rs:170`).
- ★**We limit what the triggers open**★ — whichever of ①, ② or ③ is pulled, **what gets re-opened is (d) and (e), not (a).** Even though ③ aims at the rejection basis of ADR-0071:20 (「로컬 소형 파일 IO 라 무의미하다」, "it is IO on a small local file, so it is meaningless"), we do not open (a) directly because of that — **to go back to out-of-lock IO, re-opening ADR-0071 comes first**, and this ADR does not change that order.
