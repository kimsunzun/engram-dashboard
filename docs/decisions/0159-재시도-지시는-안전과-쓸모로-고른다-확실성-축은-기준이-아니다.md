# ADR-0159: The retry instruction is chosen by safety and usefulness — the certainty axis is not the criterion

- 상태: 확정 (2026-08-18, basis: user decision 2026-08-18 — of the two axes, the retry axis was chosen as the source of truth + measured (the current code and vocabulary table at the three places))
- 관련: ADR-0154(the decision that chose the answer for the torn window · this decision closes that open item) · ADR-0155(error vocabulary · the same 3 steps at every hop) · ADR-0150(the name of a disconnected owner disappears from the registry) · `crates/engram-dashboard-command/src/error.rs`(the third column of the vocabulary table = `default_retry` · `RetryMode`) · `crates/engram-dashboard-command/src/route.rs`(`handler_panicked` · `forwarding_unknown`) · `crates/engram-dashboard-daemon/src/command_roster.rs`(`sink_of`) · `docs/process/S20-command-bus/trd.md` §4-④(certainty) · §4-⑥(default deadline 10 seconds) · §4-⑦(error vocabulary) · Amends ADR-0154 (certainty classification open item)

## 맥락
When ADR-0154 pinned the answer for the torn window (a race where the lookup answered `Available` but the path to reach the owner had vanished) as `OUTCOME_UNKNOWN`, it put its main ground on the **retry axis, not certainty**. And in the same section it opened one open item — ★the certainty classification of 「봉투가 나간 적 없다」 (the envelope never went out) splits within the same file★.

The places where it splits are two, in real code:

- `handler_panicked` in `route.rs` emits `ErrorCode::Internal` (the third column of the vocabulary table = `retry Never`) on the ground 「이 홉에서 **확실히** 실패했다(봉투가 나간 적이 없다)」 (this hop **definitely** failed (the envelope never went out)).
- The answer ADR-0154 set for the torn window takes the **same condition** (the envelope never went out), folds it into 「불명」 (unknown), and emits `OUTCOME_UNKNOWN` (`retry SameRequestId`).

Whether to unify the certainty rule of the two places was open, and until then 0154's choice **leaned** on the retry axis, not on certainty. Without a criterion, every next case splits again between the two axes — from the moment the open item is opened, that cost of reopening the debate attaches to every case.

The user raised one concern along with opening this open item — 「재시도를 허용하면 무한이 될 수 있다」 (if retry is allowed it can become infinite). How that concern is handled is the first item of the 「영향」 section.

## 결정
**The retry instruction is chosen by the retry axis.** The deciding yardstick = ★「다시 물어볼 가치 = 안전 × 쓸모」 (the value of asking again = safety × usefulness)★.

- **Safety** — it is asking again with the same `request_id`, so there is no risk of the same operation being applied twice.
- **Usefulness** — the answer may change with time (the peer can attach again, or the result is not yet settled).
- **If both are true, 「같은 id로 다시 물어라」 (ask again with the same id); if either is false, 「끝(재시도 금지)」 (end (no retry)).**
- ★「봉투가 나갔는가」 (Did the envelope go out) (the certainty axis) is **not the criterion** of this decision★ — it can be used in an explanation, but it **does not decide the code choice**.

Applying this yardstick, the three existing places split as they are:

| Place | Safety | Usefulness | Decision | Code |
|---|---|---|---|---|
| Local handler panic — `handler_panicked` in `route.rs` | true | ★false★ — asking again does not change the answer | end | `INTERNAL`(`retry Never`) · **status quo** |
| Panic during forwarding / correlation key mismatch — the `forwarding_unknown` branch in `route.rs` | true | true — whether it was applied is unsettled | again | `OUTCOME_UNKNOWN`(`retry SameRequestId`) · **status quo** |
| Torn window — the lookup says `Available` but there is no path to reach it (the race where `sink_of` in the daemon's `command_roster.rs` answers absence) | true | true — the owner can attach again | again | `OUTCOME_UNKNOWN` · **status quo** — this decision backs the answer ADR-0154 chose with a criterion |

**That the safety term is true at all three places is given by the mechanism** — because the only retry it permits is 「같은 id로의 재질의」 (re-asking with the same id) (the `RetryMode` documentation in 「근거」 below). So what actually splits is **the usefulness term alone**.

★**Today's code does not change by a single line**★ — what changes is **what the next case is decided by**.

## 거부한 대안
- **Make the certainty axis the source of truth** (choose by 「봉투가 나갔는가」 (did the envelope go out)) — a proposal to unify the two split places by certainty alone. **Reason for rejection:** the torn window stands on the 「봉투가 나간 적 없다」 (the envelope never went out) side, so by that yardstick it becomes 「끝」 (end), and then the caller gets ★a permanent failure in front of an owner that is about to come back to life★. It would require reversing the answer ADR-0154 chose.
- **Carry both axes** (choose the code by certainty, and send the retry instruction separately) — the contract already has the two slots `code` and `retry` (`CommandError` in `error.rs` = code + message + retry instruction), so **the representation itself is possible**. **Reason for rejection:** being representable is different from the decision criterion becoming two — when deciding, ★which axis wins is still not settled★. The open item does not close; it stays with only its name changed.

## 근거
- **User decision (2026-08-18)** — of the two axes, the retry axis was chosen as the source of truth. This ADR is the transcription of that decision, and the decisions at the three places are the result of applying that yardstick, not newly chosen values.
- **Measured — the real form of 「안전」 (safety) is already written in the contract.** The `RetryMode` documentation in `error.rs`: ★「`SameRequestId`는 「안전하게 재실행해도 된다」가 아니다」★ (SameRequestId is not "safe to re-execute") — it means that whether it was applied is **unknown**, so it must be asked again **only with the same id** (retrying with a new id can apply the same operation twice). That is, the retry permission is **not a permission to re-execute but a permission to re-query**, and that is why the safety term holds as a mechanism.
- **Measured — the current values at the three places** (this decision passes them through as they are):
  - The vocabulary table in `crates/engram-dashboard-command/src/error.rs` — `Internal => "INTERNAL" retry Never` · `OutcomeUnknown => "OUTCOME_UNKNOWN" retry SameRequestId`. The retry instruction comes out **on the same line as the code**.
  - `crates/engram-dashboard-command/src/route.rs` — `handler_panicked` → `ErrorCode::Internal` · `forwarding_unknown` → `ErrorCode::OutcomeUnknown` · the correlation key mismatch branch → `ErrorCode::OutcomeUnknown`.
  - The documentation of `sink_of` in `crates/engram-dashboard-daemon/src/command_roster.rs` — 「조회가 `Available`을 답한 뒤 여기서 부재가 나오는 경합에서 호출자는 `OUTCOME_UNKNOWN`으로 답한다(ADR-0154)」 (in the race where the lookup answered Available and absence then comes out here, the caller responds with OUTCOME_UNKNOWN).

## 영향 / 불변식
- **★What stops infinity is not the error code★ — the division of labor is split.** In this contract, allowing retry means **not re-execution but a re-query with the same id**, and what stops infinity is the **deadline** (TRD §4-⑥ — the deadline is set by the caller and is **10 seconds by default**) and the **caller-side cap**. Do not try to stop infinity by narrowing the retry instruction to 「끝」 (end) — what this yardstick measures is safety and usefulness, not a count.
- **The default is already the failure side.** An unknown code is lowered to `INTERNAL`·`retry: never` (the `error.rs` header — the decoder accepts an unknown code but lowers it that way). So applying this yardstick is not widening retry but **choosing the places to raise from the narrow default**.
- **Today's diff = documentation and anchors only.** The code, behavior and wire values at all three places stay as they are. A commit that changes the code of one of the three places on the basis of this ADR is outside the scope of this decision.
- **Code anchor `// ADR-0159`** — `handler_panicked`·`forwarding_unknown` in `route.rs` · `RetryMode`·`default_retry` in `error.rs`. ★**Add only the anchor and do not fix the existing explanations**★ — those sentences are the certainty statements of each place, and this decision does not erase them.
- **The certainty statements remain as an explanatory layer.** The sentence in the `default_retry` documentation, 「「재시도해도 되나」 (may we retry) is a function of **certainty** (TRD §4-④)」, states the reason **the retry instruction is gathered in one place**, and this decision does not touch it. ★If the two readings split, this ADR is the criterion for choosing the code★ — certainty can **explain** that choice but **cannot decide** it.
- **ADR-0154's open item is closed — it is closed by not unifying.** The two places keep their different certainty statements as they are. What splits is the **certainty statement**, not the **decision**, and the decision is made by this one yardstick. So 0154's choice (torn window = `OUTCOME_UNKNOWN`) becomes not 「기댈 축이 없어 임시로 고른 값」 (a value chosen provisionally because there was no axis to lean on) but **a value that applies the source-of-truth criterion as is**.
