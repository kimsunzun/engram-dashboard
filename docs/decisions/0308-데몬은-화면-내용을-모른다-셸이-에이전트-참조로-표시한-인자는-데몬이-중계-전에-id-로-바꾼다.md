# ADR-0308: The daemon does not know screen content — an argument the shell marks as an agent reference is converted to an id by the daemon before relaying

- 상태: 확정 (2026-10-27, basis: user decision 2026-10-27 · research `docs/research/agent-name-resolution-relay-vs-callback-2026-10-27.md`)
- 관련: Amends ADR-0081 (the argument non-parsing in the daemon-opaque clause (conversion of agent-reference arguments allowed)) · Amends ADR-0156 (the hard constraint against daemon parsing in decision 1 and the rationale (exception for agent-reference fields)) · ADR-0035 (layout authority = shell) · ADR-0132 (one name resolver) · ADR-0270 (the shell does not depend on the agent crate) · ADR-0307 (LLM command rules) · TRD `docs/process/S28-llm-layout-commands/trd.md` · step-log S28

## 맥락
Once LLM layout commands (T-65 · S28) choose panes · tabs by agent **name** (ADR-0307), name → id resolution became necessary. The daemon holds the name registry (ADR-0132 — the resolver is in the daemon alone), and the shell holds the screen layout (ADR-0035). The first implementation (S28 U3a · U3b — uncommitted) was of the form where **the shell, while handling a command, asks the daemon back** (an `agent.resolve` round trip) — to keep the wording of ADR-0081 · ADR-0156 that the daemon does not open shell command arguments. The deadline, the pending-slot cleanup, and the old-daemon handling attached to that asking back produced defects in every code review (the cleanup method alone stayed unresolved three times in a row), and the user asked 「데몬이 이름을 id 로 바꿔 넘기면 되지 않나」. On investigation, the wording of those two ADRs was a means, and the purpose was 「데몬은 셸(화면)을 모른다」 — the user: 「결국에는 화면에 있는 내용을 모른다는 것만 있으면 되잖아」.

## 결정
1. **The principle kept = the daemon does not know screen content (the window · tab · pane layout and its meaning).** ADR-0081 · ADR-0156's 「데몬 opaque 유지」 is read by this principle.
2. **When the shell registers a command, it marks the 「에이전트 참조」 arguments separately** — not inside the help string but in a **separate field of the registration packet** (e.g. a list of agent-reference argument names). The help stays an opaque string (that part of ADR-0156 is unchanged).
3. **Before relaying a shell command, the daemon converts only the marked arguments from name to id with the resolver of its own registry (`resolve_in` — ADR-0132) and passes them on.** All the daemon knows is 「이 칸은 내 에이전트를 가리킨다」; it does not know whether it is a pane target or a tab target. If it does not resolve (missing · name overlap), the daemon does not relay and answers with that error (including candidates — the ADR-0307 rule).
4. **A change that requires the daemon to know screen content is asked of the user first** (user decision 2026-10-27 — 「그걸 위해 뭘 할때는 나한테 물어봐야되는거지」). What this ADR allows goes only as far as changing references to the daemon's own domain (agents).
5. Details (the shape of the marking field · error wording · a thread that does not block registry reads) are decided in the S28 TRD — main-agent decision (user delegation).

## 거부한 대안
- **The shell asks the daemon back while handling (the S28 U3a · U3b implementation)** — a circular daemon → shell → daemon round trip arises, and code for that round trip's deadline · cleanup of abandoned pending slots · handling an old daemon (which does not know `agent.resolve`) gets attached. In code review, the pending-slot cleanup method stayed open three times in a row (the squared cost of a size threshold · never cleared below the boundary · test-precision BLOCK after switching to a time period), and error-wording · retry-hint conversion piled up on the shell side. External convention too is mostly to resolve once at the boundary and send only ids down (research report). Rejection strength = review measurement + research + user decision.
- **The shell resolves directly with the shell's id → name cache** — the cache never deletes entries, so a dead agent's name resolves and the duplicate decision diverges from the daemon's — it violates ADR-0132 (one resolver). Rejection strength = code (`agent_names` in `layout/manager.rs`).
- **Leave the wording of ADR-0081 · ADR-0156 as is and keep the daemon opaque** — keeping the principle (not knowing the screen) does not need all of that wording, and the price is the complexity of the asking back above. Rejection strength = user decision.

## 근거
- Research (light · two checked in the original text): Fowler 「smart endpoints and dumb pipes」 + 「Remote calls are more expensive … remote APIs need to be coarser-grained」 · in Kubernetes the API server mutates before storage so downstream receives a normalized object (mutation guidance = be idempotent · avoid side effects · avoid dependency cycles). Substituting on a generic marking alone conflicts least with the relay principle.
- Code costs and benefits (research report 「우리 코드에서의 손익」): one relay point (`command_delivery::deliver`) · no bypass path · 8–10 files · the shell's asking-back · deadline · pending-slot cleanup code goes away.

## 영향 / 불변식
- **Crate dependencies are unchanged** — the marking is put in the command tooling crate (`command`) that the daemon and shell already share. The daemon does not depend on shell code, and the shell does not depend on the agent crate (ADR-0270).
- **Registry reads must not block the relay path** — path normalization of a sleeping profile can take long (`manager.rs` docs) → it runs on the side of the blocking work.
- The name → id moment is outside the shell's apply lock and id → pane is inside — the same property as with asking back (TOCTOU is guarded by `locate` inside the shell's apply lock).
- S28's uncommitted U3a · U3b were rewritten under this decision in S28 U3 (removing the asking-back · deadline · pending-slot cleanup code, and moving to the marking field · conversion before relay).
