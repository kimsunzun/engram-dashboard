# ADR-0185: The session-restore invariant is issuer-neutral — codex receives and uses the thread id it was issued

- 상태: 확정 (2026-09-09, basis: user decision — 「고치고 진행」) · 부분 폐기 by ADR-0186 (the clauses in two principle documents) · 부분 폐기 by ADR-0226 (the receiving point in decision 2, the single receiving point in the impact section, and the unenforced description of the Phase 2 requirement) · 부분 폐기 by ADR-0233 (withdraws, for codex JSON, the Phase 2 requirement in the impact section to persist before the first turn)
- 관련: Amends ADR-0008 (sid issuer) · ADR-0082 (resume early-exit endpoint) · CLAUDE.md 「세션 복원」 · `docs/reference/architecture-overview.md` 「세션 복원 / 활성화」 · `docs/process/S21-codex-backend/trd.md` §0 (Phase 2 scope) · `crates/engram-dashboard-agent/src/profile.rs:165,629` · Amends ADR-0076 (the premise that we issue the sid) · Amends ADR-0082 (the sid-issuing clause among the higher-level decisions that survive) · Amended by ADR-0186 (the clauses in two principle documents) · Amended by ADR-0226 (the receiving point in decision 2, the single receiving point in the impact section, and the unenforced description of the Phase 2 requirement) · Amended by ADR-0233 (withdraws, for codex JSON, the Phase 2 requirement in the impact section to persist before the first turn)

## 맥락
When Phase 2 starts codex as a resident JSON server (`codex app-server`), session restore opens up. But **codex does not let the client specify the thread id** — among the 27 properties of `ThreadStartParams` there is not one of id · threadId · sessionId · name · title, and the documentation says `Thread.id` is issued by codex as a UUIDv7. A request to add that parameter (`session_id` + a `--session-id` flag, with an implementation) was filed upstream, but an OpenAI maintainer closed it (openai/codex#15767).

The problem is our own sentence. CLAUDE.md 「세션 복원」 and the ground of ADR-0008 are written as 「복원 정확성은 **우리가 통제하는** sid에만 의존한다」 (restore correctness depends only on a sid **that we control**), so taken literally codex cannot come under this principle, and all of Phase 2 reads as a violation of the principle.

## 결정
1. **Rewrite the invariant to be issuer-neutral** — 「복원은 **프로필에 저장된 backend sid 단독**에 의존한다. 그 sid를 누가 발급하는지는 백엔드가 정한다.」 (Restore depends **solely on the backend sid stored in the profile**. Who issues that sid is decided by the backend.) claude's is issued by us and passed with `--session-id` (ADR-0008 as is), and codex's is received from the thread-creation response and stored.
2. **The receiving point of the codex sid is the existing `observe_session_id`** (`profile.rs:629`) — **do not create a new field, a new mapping or a new file.** That function already does 「백엔드가 정한 sid를 관측해 옛 값을 이력으로 밀고 즉시 persist」 (observe the sid the backend decided, push the old value into the history and persist at once). ★**But the wiring up to that point does not exist — this decision requires three things of Phase 2**★:
   - ① **Receiving wiring** — thread-creation response → `observe_session_id`. Today that function's only production caller is the claude `/clear` watcher (`daemon/src/lib.rs:288`), and ★**that watcher cannot be codex's receiving path**★ — because `backend::session_id_source` is a file poller that requires **the reference sid that we issued** (`expected_sid: Uuid`) (`backend/mod.rs:348-353`). codex's id comes in a JSON-RPC response. So ★**this one item turns receiving on — neither ② nor a tracker is needed**★.
   - ② **Splitting `needs_session()`** — this one flag doubles as *we issue · a watcher attaches · resume is possible*. ★**Do not write this down as 「수령을 막는 원인」 (the cause that blocks receiving)**★ — the primary reason a watcher does not attach for codex is that the `sid` on the line before it (`manager.rs:1075`) is `None` (`:955-962`), and `if needs` (`:1076`) is not even evaluated. The reason to split is a different one: for Phase 2 to make `restore_one` see codex as resumable, this flag has to be turned on, and turning it on **also turns on issuing**, so a uuid that codex does not use gets planted.
   - ③ ★**A guard at the activation entrances**★ — `commands.rs:521` and `connection_core.rs:1126` derive `SpawnMode::Resume` by looking at **the stored sid alone** and do not look at `needs_session()` (boot restore `manager.rs:1376` does). If a sid is planted with ③ missing, `spawn_agent` does not pass the sid (`manager.rs:954-962`) and `build_spec` ignores `_mode` (`backend/codex/mod.rs:93`), so **a new conversation opens.** ★**And there is not one marker on the wire saying that it is a new conversation**★ — neither `AgentSpawnOk` (`commands.rs:807-814`) nor `AgentEvent::Spawned` (`protocol/src/messages.rs:468-471`) carries whether it resumed. ★**Do not grep for `resumed`**★ — that name is a single local variable of a `#[cfg(test)]` test double at `commands.rs:1090`. And the comment at `commands.rs:519-520` describes the danger of **the two entrances using different rules**, so it does not cover this gap — the two entrances use the same rule, and the problem here is that that rule does not look at `needs_session()`.
3. Fix two principle documents — the first sentence of CLAUDE.md 「세션 복원」 · the first sentence of `docs/reference/architecture-overview.md` 「세션 복원 / 활성화」.

## 거부한 대안
- **Write codex in as the only exception to the principle** — the user saw this option and chose 「고친다」. Writing an exception **makes the document create a branch that is not in the code**: both `backend_session_id` and `observe_session_id` are already neutral structures that do not know the issuer, so 「codex는 예외」 (codex is an exception) is a divergence that exists only in a sentence. And if a third backend asks for the same road, the exception becomes the rule.
- **Create our own id (E) and add a new on-disk mapping `E → codex thread id(T)`** — the adversarial review raised it as option 4. **That mapping already exists**: our id = `AgentId`, the backend id = `backend_session_id` (`profile.rs:165`), and the mapping between the two = the profile record itself. ★**But the cost option 4 was charged with, 「T를 받고 커밋하기 전 크래시하면 복원 불가」 (if it crashes after receiving T and before committing, restore is impossible), remains as is in this decision too**★ — `observe_session_id` is atomic only *after it is called* (`mutate_if` → `store.save`), and the open window is **between receiving the response and the call**, which that function cannot bear. So the reason for rejecting option 4 is not the crash window but only one thing, **that the mapping is already the profile record**. That window is borne by the 「영향」 below as a Phase 2 requirement.
- **Append a 「서버 발급 + 프로토콜 응답 수령 + 우리가 보관」 (server issues + protocol response received + we keep it) branch to the principle** — the adversarial review decided this was a **rationalization** (widening the definition of control). In fact there is no place to add a branch — the question the original invariant answered was 「복원이 무엇에 의존하나」 (what does restore depend on), and the issuer was not in it. This decision does not widen the principle but writes down its original meaning.
- **Do not do Phase 2** — resume, structured chat and mail would all be blocked. The three share one root (the resident JSON stream), so it is not an option to give up just one — the reason mail was turned off in Phase 1 is also 「턴을 관측할 수 없다」 (turns cannot be observed), the same root (TRD §4-3).

## 근거
- **Schema + upstream rejection** — `ThreadStartParams` has 0 id-family properties (the JSON schema codex itself emits) + the issue asking to add that parameter was closed by a maintainer's decision (openai/codex#15767). It is not 「아직 없다」 (not yet) but **「넣지 않기로 했다」 (upstream decided not to add it)**, so there is no option of waiting.
- **The code is already neutral** — `backend_session_id: Option<Uuid>` (`profile.rs:165`) has no field to write the issuer in, and `observe_session_id` (`profile.rs:629`) is used for claude `/clear` tracking and already does 「백엔드가 바꾼 sid를 받아 즉시 persist」 (receive the sid the backend changed and persist at once). **What this round changed is only the documents.** ★**But do not read it as 「그래서 코드 변경이 0이다」 (so the code change is 0)**★ — a data structure being issuer-neutral is different from the wiring standing, and that difference is the three items of decision 2.
- **The premise on which ADR-0008 rejected an option does not exist for codex** — the reason that ADR dropped 「claude 자동 sid에 의존」 (depend on claude's automatic sid) was *there is no way to know that sid* (only polling `sessions/<pid>.json`). codex gives the id **in the response** to thread creation — the premise that it cannot be identified does not hold.

## 영향 / 불변식
- **Invariant (revised) — what holds now is up to here:** restore depends **solely** on the backend sid stored in the profile. The issuer is decided by the backend.
- **Phase 2 requirement (not an invariant yet):** persist the sid received in the response **before allowing the first turn** — the span in between is the unrestorable span. ★**Nothing enforces this right now**★ — the name `turn/start` appears nowhere in this repository's code or documents, and the ground is schema reading alone. Do not cite it as an established invariant.
- **The claude path does not change by even one line** — the `--session-id` issuing of ADR-0008 · the best-effort grade of the tracking file · the 3s early-exit window · the cold boot restore policy all remain valid. What this ADR amended is **the one clause saying the issuer must be us**.
- **Do not create a new mapping or a new field** — if you do, it becomes a double source with the profile record, and the next session cannot tell which is canonical.
- **Not checked (at the time this ADR was confirmed):** we have **never actually created a thread with app-server and received an id.** Only the `initialize` round trip was measured (Windows stdio, exit code 0 when stdin is closed). The actual field shape of the thread-creation response is confirmed as the first gate of Phase 2 — if it differs there, decision 2 wobbles (decision 1 stands on the schema and the upstream rejection, so it stays as is).
- **The 「sid 발급 단일 권위점」 (single authority point for sid issuing) of ADR-0076 is a claude-axis statement** — codex is not issued by us, so `spawn_agent` does not plant a sid (`needs_session()` = false), and instead **the single receiving point is `observe_session_id`**. ★**The trap 「codex Fresh가 `new_session_id`로 엉뚱한 uuid를 심는다」 (codex Fresh plants a wrong uuid with new_session_id) opens the moment `needs_session()` is flipped to true**★ — for now `spawn_agent` structurally cannot reach it (the `if needs` at `manager.rs:954-962`). But Phase 2 has to turn that flag on to make `restore_one` see codex as resumable, and since one flag doubles as three things, **it must be split before turning it on** (decision 2 ②). If it is turned on without splitting, a uuid that codex does not use is put into the profile and the tracker polls a file that does not exist (`docs/process/S21-codex-backend/trd.md:537`).
- ★**The comment at `backend/codex/mod.rs:141-144` (and `:56-58`) says the opposite of this decision**★ — 「호출자가 sid를 못 정하므로 무손실 복원이 성립하지 않는다(실측)」 (lossless restore does not hold because the caller cannot decide the sid (measured)). Decision 1 decides that the issuer is irrelevant to restore holding, so that sentence is stale. **This round changed only documents, so that comment is still there — Phase 2 fixes it together with the `// ADR-0185` anchor.** That spot is the text a Phase 2 session reads first, so leaving it would pass the decision on in an overturned state.
- **The code anchor is still 0** — `rg "ADR-0185" crates/ src/ src-tauri/` → 0 lines. This means one of the two discovery surfaces CLAUDE.md names is empty, and filling it belongs to the same round (Phase 2) as the comment fix above.
- **Two documents still carry the pre-revision framing — their dispositions differ.**
  - `docs/process/S21-codex-backend/trd.md` (§0 reason for holding resume · M2 「claude 계약이 codex엔 성립하지 않는다」 · §413) — **a record as of Phase 0·1, so it is not fixed.** The Phase 2 TRD takes this ADR as input and replaces that framing.
  - ★`docs/reference/structure/agent-backend.md:140,146`★ — this one is **not a point-in-time record but the canonical per-topic detail for this axis** (ADR-0197), and the overview sends readers down here. Yet it explains `capabilities().session.resume` as 「무손실 복원 가능 여부」 (whether lossless restore is possible), tied to the issuer. **A pointer to this ADR must be added in the next round** — if not, a newer document explains this axis with the pre-revision invariant.
