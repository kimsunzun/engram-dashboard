# ADR-0216: The codex session id is read from the TUI status line, and the hook is removed

- 상태: 확정 (2026-09-20, basis: codex-cli 0.155.1 measured + pump code measured — see 「근거」 below) · 부분 폐기 by ADR-0217 (status-line recovery channel and scanner replaced) · 부분 폐기 by ADR-0226 (decision 7 value policy)
- 관련: Supersedes ADR-0210 · Amends ADR-0208 (hook recovery path and the adopt empty-slot policy replaced) · ADR-0004 (isolating backend knowledge) · ADR-0185 (codex does not issue an id) · ADR-0203 (vendor storage formats are not read) · ADR-0006 (lock order) · ADR-0079 (seq is emitted inside the replay lock) · ADR-0127 (turn observation has only two points) · ADR-0207 (profile writes save to disk while holding the lock) · ADR-0214 (mail attachment relies on the same override rule) · ADR-0215 (instruction-sheet attachment relies on the same fail-open rule) · `crates/engram-dashboard-agent/src/transport/pty.rs` · `crates/engram-dashboard-agent/src/backend/codex/mod.rs` · `docs/reference/structure/agent-backend.md` · step-log S21 · Amended by ADR-0217 (status-line recovery channel and scanner replaced) · Amended by ADR-0226 (decision 7 value policy)

## 맥락

ADR-0208 set up a hook as the session-id recovery path for terminal-mode codex. ADR-0210 registered that hook through the launch argument `-c` and decided to get trust from codex's own TUI review screen. Both stood on measurements, and all the machinery was wired.

The problem is **what that trust review is keyed on**. codex hashes the hook **command string** and asks a human to approve it, and our command string contains **our exe's absolute path**. The distribution unpacks into a folder named after the tag (`engram-dashboard-v0.3.0/`), so the path changes with every release, and so **the approval screen comes up again with every release.** And while that screen is up, terminal-mode codex does not start at all — the agent does not start until the user presses approve.

★**This is not a defect nobody knew about. It is a price ADR-0210 explicitly accepted.**★ In its 「거부한 대안」, while rejecting a wrapper script, it wrote 「설치 경로가 바뀔 때마다 심사 프롬프트가 한 번 더 뜬다. 업그레이드가 버전 박힌 폴더로 가는 배포라면 매 릴리스마다」 (the review prompt comes up one more time every time the install path changes. If the upgrade goes to a version-stamped folder, on every release), and it even left a reopening coordinate: **「재론하려면 그 빈도가 실제로 문제가 되는지부터 재고 저울질할 것」 (to reopen this, first measure whether that frequency is actually a problem, and then weigh it again).** This ADR reopens it at that coordinate.

The answer to the reopening ended up not being 「래퍼를 홈에 깐다」 (lay a wrapper in the home directory), because this round found by measurement a **channel that bypasses the approval axis itself**. If `thread-id` is put in the codex setting `tui.status_line`, **the full 36-character thread id is printed in the TUI status line.** It is a **setting value, so it has no command string, nothing to hash, and so it is not caught by the trust gate.** And since it is passed with `-c`, it writes not a single character to disk.

## 결정

**Recovery path = our PTY reads the TUI status line that we turned on. The hook is removed entirely, both its registration and its receiving side.**

1. **Spawn adds `-c tui.status_line=['thread-id']`** — ★**the value is a TOML literal string (single quotes)**★. Double quotes are also valid TOML, but once they are inside an argv element they get caught by the Windows command-line re-quoting (basis = see 「근거」 below). It is added to terminal mode only (app-server gets the id directly from the `thread/start` response), it is attached **「뒤」 (after) the user passthrough** (with a duplicated `-c`, the later one wins), and if the user supplied the same key, **a warning is left saying we overrode it.** This inherits ADR-0210 decision 3 as is — silent overwriting is still forbidden.

2. **The scanner scans the byte slice the pump read 「직전」 (just before) `emit`, and keeps its state only inside the pump thread.** It does not touch `finalized`, does not emit seq, and does not add turn-observation call sites.

   ★**But 「락을 잡지 않는다」 (does not take a lock) does not cover the whole recovery — writing the value into the profile always takes a lock.**★ That write path saves the entire registry to disk while holding the registry-wide mutex (this is the intended design of ADR-0207). So **the pump does not call that write directly** — it hands the captured value over by a **non-blocking handoff** (an unbounded channel send, etc.), and another thread does the actual write. The pump is the sole PTY reader, so one stall here **puts backpressure on the child process.**

   ★**And what the pump closure holds must be only cheap handles**★ — one sender on the outgoing side, and **one shared flag on the incoming side** (decision 5 ⓑ uses it). If it **holds a lock that is unwrapped with `expect`**, like the profile registry, then a pump panic **poisons a global lock that reaches other agents too.** The pump's unwind-safety justification comment stands by enumerating 「무엇을 붙드는가」 (what it holds), so when what it holds changes, that comment is fixed together with it.

3. **The scanner is written not to panic.** The insertion point is inside `catch_unwind`, so if it blows up there, **a perfectly healthy codex session is reported as `Failed` and its output is cut off.** It uses no indexing or slicing that can go out of range, and if a step that can fail remains, that failure **ends by turning the scanner off — it is not propagated.**

4. ★**The scanner carries its own carry-over.**★ The pump buffer is a fixed 4096 bytes and each `read` result goes out as its own independent event, so **a 36-character id can be split across two reads** — there is no code in that loop that joins them. At least 35 bytes are passed to the next call. **Because this is what is printed on the screen, ANSI escapes can sit between the id characters, so the escapes are stripped before matching** (the state of that state machine also continues across chunks).

5. ★**The arming window is closed by three conditions — whichever comes first.**★ ⓐ recovery succeeds ⓑ **the first user input that entered the PTY** ⓒ a byte budget of **1 MiB**. ⓑ is the key — the first-match rule is safe **because the window structurally contains no user or model content**, and until the user types the first character, all that is on screen is codex's own decoration. If it were closed by ⓐ alone, that window would stay open for the whole conversation.

   ★**Known remainder — there is one branch where ⓑ does not close.**★ The latch is raised **only when the input was accepted into the queue** (a rejected input never sent a single character to the PTY, so there is no reason to close the window). But **if the user's first action is a paste larger than the queue limit**, that input is rejected before anything is pushed, and **the user has clearly started interacting but the window stays open.** Even on that path, **the user's bytes never reach the screen** (they never left our process), so the practical premise of ⓑ is alive, and the remaining defenses are ⓐ and ⓒ. ★**Still, this is a 「창을 넓히는」 (widening the window) direction, so it is named here — if it is found later, it becomes the coordinate for reopening.**★

   ★**The signal for ⓑ cannot be seen by the pump alone — the writing is done by a separate writer.**★ So there is **one shared flag** that the writer sets and the pump reads (this is the 「들어오는 쪽 값싼 손잡이」 (cheap incoming handle) that decision 2 allows). Without that flag only ⓐ and ⓒ remain, and then 「창 안에 사용자 내용이 없다」 (there is no user content in the window) is true **only until the budget fills**, which breaks half of the defense against reopening. The 1 MiB of ⓒ is **a ceiling that closes a false-positive window, not a cost measure** — the initial screen draw does not get anywhere near it, so it is a margin value.

6. **The codex knowledge stays in `backend/codex`.** The transport has only a **generic observer slot** that passes bytes along, and does not know what is being looked for. 「백엔드 전용 코드는 없앨 수 없고 한 곳에 모을 수 있을 뿐」 (backend-specific code cannot be eliminated, only gathered in one place) (ADR-0004) applies to this decision as is.

7. ★**The recovered value overwrites.**★ This channel does not inherit ADR-0208 decision 2's 「빈 칸에만 쓰고 다른 값이 있으면 거절한다」 (write only into an empty slot, and reject if another value is there). What that rule blocked was **a descendant that inherited the env token reporting under someone else's name**, and this channel **structurally has no such threat** — the bytes come directly from that agent's own PTY, and no third process that could impersonate the reporter exists on the path. There is a separate, positive reason for choosing overwriting (the same item in 「거부한 대안」 below).

8. **No branch fails the spawn.** Whether the key could not be loaded, the status line does not arrive, or the id is never captured, only a warning is left and the spawn proceeds. The result of not capturing is the existing behavior as is — `backend_session_id` stays empty, so a resume opens a new conversation, and that fact is reported as `RestoreOutcome::Started`. Inherits ADR-0210 decision 4.

9. **The hook machinery is removed entirely** — the hook override builder · the `engram hook session-start` CLI verb · the `/control/hook` route · its receiving module · its tests. ★**But the order is a condition**★: wire the new channel, and delete only **after confirming the id recovery with your own eyes in the GUI measurement**. If the measurement is red, do not delete — stop.

★**ADR-0210's decision 3 and the fail-open half of decision 4 are passed on by this decision as a general rule and keep living here — they do not die along with that ADR being discarded.**★ Both already bear load in places unrelated to the hook: codex **mail attachment** relies on **「override 는 passthrough 뒤에 붙이고 덮으면 경고한다」 (the override is attached after the passthrough, and a warning is left if it overrides)** (ADR-0214), and **instruction-sheet injection** relies on **「어떤 갈래로도 스폰을 실패시키지 않는다」 (no branch fails the spawn)** (ADR-0215). The code anchors and the related lines of those two ADRs still point to `ADR-0210` by name, so **when a reader who followed the discard stamp reaches this ADR as the successor, that rule must be here.** Moving the anchors to `ADR-0216` is done together in the round of decision 9.

★**But do not read it as 「3·4 가 통째로 살았다」 (3 and 4 lived in full) either**★ — decision 4 bundled two rules, and of those **the 8.3 short-path half actually dies together with the hook exe path.** **Only the fail-open half** lives on. What died is registration and trust (decisions 1, 2, 5, 6) plus the path half of decision 4.

## 거부한 대안

- ★**Leave the hook as it is**★ — that it works is measured, and it is not a defect either. The rejection reason is **one thing, user experience**: the approval hash bites on our exe's absolute path, and the tag is stamped into the distribution folder, so **the approval comes up again with every release, and until then terminal codex does not start.** This round re-evaluates the price ADR-0210 accepted and reverses it.
- ★**The 「출력·TUI 스크래핑」 (output / TUI scraping) that ADR-0208 rejected — we state exactly how much of that rejection reason remains for this channel**★. The reason of that item was not reading the screen itself but **「첫 매치 · 검증 0 · 파일 탐색 폴백까지 달아 놨다」 (first match · zero verification · even a file-search fallback attached)** (the precedent octoally), and the larger principle was 「not-found 를 wrong-found 로 조용히 바꾸는 tie-break 를 두지 않는다」 (do not put in a tie-break that silently turns not-found into wrong-found).
  - **Two things disappear:** ① **we declared the target by setting** — we are not picking up something that happens to be on the screen, we are receiving **the item we told it to show**. ② **There is no fallback** — if not found, it is left not found, and no second path that rummages through files is built (ADR-0203 already closed that door).
  - ★**One thing remains — and we do not claim to have removed it: this channel too has a tie-break. 「첫 매치가 이긴다」 (the first match wins)**★ It was not removed but **made harmless by narrowing the window**, and that window is the three of decision 5. What those three guarantee is **「창 안에 사용자·모델 내용이 구조적으로 없다」 (the window structurally contains no user or model content)**, not 「후보가 하나뿐이다」 (there is only one candidate). ★**So a change that widens the window (keeping it armed · removing input detection · enlarging the budget) turns this decision back toward octoally — a session that wants to remove one of those three should look at this line first.**★
  - **「전체 36자가 온전하다」 (The whole 36 characters is intact) is a screen measurement, not a property of the byte stream.** The output is rendered, so escapes can sit between the id characters, and that axis is handled by decision 4's ANSI stripping, but **whether that is actually the case is unverified until the GUI measurement** (「미검」 below). When it is wrong, the outcome is not contamination but **failing to capture** (decision 8).
- **Receive it through `tui.terminal_title`** — parsing is easier this way. It comes as a clean OSC escape (ESC ] 0 ; value BEL), so the delimiters are clear and there is no need to feel through screen text by its shape. ★**Rejected = measurement**★: **it is truncated to 32 characters** (29 characters + an ellipsis, the last 7 hex lost). The truncation is **fixed regardless of the screen width.** There is a workaround that searches lock file names by the 29-character prefix to restore the whole, but **the mechanisms become two and the second reads the vendor store**, so it falls under the item below.
- **The orca way — grant hook trust through codex's own RPC** (write the `currentHash` that `hooks/list` returned into `hooks.state` through `config/batchWrite`). ★**That it runs to the end is measured**★ — `trustStatus` changed to `trusted`, persisted in a new process too, and the hook fired cleanly. There was no gate at all. ★**Rejected = the trust key is position-based**★: the key is `<sourcePath>:<이벤트>:<groupIndex>:<handlerIndex>`, so **if someone inserts a hook above our hook, two things happen at once** — our hook is shifted out of place and does not run, and **the hash we wrote attaches to that person's hook, which never passed their review.** We would end up approving on someone else's behalf. The character of ADR-0210 decision 5, that we record an approval no human gave, also remains as is.
- **The herdr way — lay a fixed-path wrapper script in the user's home** — the trust hash covers the **hook definition** and not the **script content**, so trust survives an upgrade and becomes **one approval for life**. The benefit is real. ★**Rejected = it lays a file in the user's home**★ — inherits ADR-0210 decision 1 (「사용자 기기에 파일을 하나도 만들지 않는다」 (create no file at all on the user's machine)).
- **Read the rollout JSONL · `state_5.sqlite` · lock-file directory to find the id** — inherits ADR-0208's rejection as is (storage format mid-migration · turns not-found into wrong-found). ★**Not read even for cross-checking**★ — ADR-0203 closed the vendor store entirely with 「codex 이력은 app-server 에 요청해서 받는다. rollout 파일을 읽지 않는다」 (codex history is requested from the app-server. Do not read the rollout file.) What the previous session compared against lock file names was **a one-time measurement to judge whether to trust the channel**, and is not a runtime path.
- **Write only into an empty slot (inherit ADR-0208 decision 2)** — what decision 7 above reversed. ★**The resume behavior is not unmeasured — that `codex resume <id>` keeps the same id is measured**★ (survey §10-8: it does not waver with repeated resumes, and the rollout keeps being appended to the single original). **On that branch, overwriting is a proven no-change.** What remains unmeasured is **what fork produces** (that survey itself wrote 「안 봤다」 (did not look)) and **whether the status line prints the id again on a resume spawn**. Overwriting **lands correctly on all three branches** — the same id gives no change, a new id points at the live thread, and if nothing is printed the existing value stays as it is. Writing only into an empty slot, on the new-id branch, **leaves the handle stale and breaks from the second resume on, and that failure is silent.** ★We chose the side that is harmless on the known branch and safe on the unknown branch.★
- **Remove the version from the release assembly folder name** — a workaround that fixed the hook command string to eliminate re-approval. Rejected = this decision removes the hook itself, so that axis becomes meaningless. The cost (users who kept several versions side by side get overwritten) disappears with it.

## 근거

- ★**This ADR is the measurement source of record — it is not in a survey document.**★ The numbers for the status_line channel are **measured in the previous session but were not promoted to a survey document** (`docs/research/codex-instruction-injection-2026-09-20.md` covers only instruction-sheet delivery), and were written only in the session handoff. Copying them here is the only persistence of those numbers. **No description of the method (fake model server · isolated CODEX_HOME) was left anywhere** — to re-measure, the method has to be built again first.
- **codex-cli 0.155.1 measured (previous session):** the full 36-character thread id is printed on the screen · **about 0.3 seconds after spawn · before the first turn · before the rollout file even exists** · fully matches the lock file name (4 cross-checks) · stays intact at 36 characters even when the terminal width is narrowed to 60 columns.
- ★**A wrong item name is not an error but a silent ignore**★ — `thread-name` looks plausible but is **invalid**. The valid ones are `thread-id` (`session-id` is a legacy alias) · `thread` · `thread-title`. The way to check = `codex doctor -c 'tui.status_line=["thread-id"]' --json` returns the parse result. In the same family, **an unknown `-c` key is not rejected but silently ignored**, and checking that a key exists needs `--strict-config`.
- **Confirmed this session:** we confirmed that the installed codex is **0.155.1**, the same as at measurement time (`codex --version`).
- ★**What we actually load is the single-quote form — that too was measured separately.**★ The previous-session measurement above measured the **double-quote** form with `codex doctor -c 'tui.status_line=["thread-id"]' --json`, and what the code loads is `tui.status_line=['thread-id']`. ★**Leaving that difference alone splits 「측정한 것」 (what was measured) from 「싣는 것」 (what is loaded)**★ — a wrongly written key is not an error but a **silent ignore**, so it can stay green while split. So the implementation round re-measured it with an isolated home: `codex --strict-config -c "tui.status_line=['thread-id']" app-server --stdio` → **exit 0**, and the control `totally_bogus_root_key=1` → **exit 1 · `unknown configuration field`**. `codex doctor` does not accept `--strict-config` (`unexpected argument`). **The reason for choosing single quotes is Windows command-line re-quoting** — survey §10-9 already measured that a TOML literal string survives byte for byte the `cmd.exe /c` + `.cmd` shim round trip.
- ★**What `--strict-config` checks is the key, not the item name**★ — the invalid `thread-name` also passes with exit 0 (measured in the implementation round). That flag cannot catch the validity of an item name, so the 「조용한 무시」 (silent ignore) item above stays in force as is.
- **Code measured (this round's survey):** the pump reads with a fixed `[0u8; 4096]` buffer and sends each `read` result out as an independent `TerminalBytes` — there is no code in that loop that joins them (`crates/engram-dashboard-agent/src/transport/pty.rs:286-301`). The carry-over requirement of decision 4 comes from here. There is **no code today that looks into terminal bytes while they are live** — turn classification explicitly ignores them (`backend/codex/mod.rs:1192`) and no decoder is attached in terminal mode.
- ★**The GUI measurement has not been done yet**★ — separately from this decision standing, that the id is actually captured in the real app was **not confirmed at the time this ADR is written.** The order condition of decision 9 guards that spot.

- **One adversarial reviewer (doc-aware).** ★**Because the target is a decision document, the cross-family blind slot was excluded by the convention — this is a review where cross-verification did not hold.**★ That one reviewer decided FIX, and decisions 2, 3, 4, 5 of this ADR, the reopening defense in 「거부한 대안」, and the four items of 「영향」 are the result of fixing what that review pointed out (including one re-verification — that round caught the signal path of decision 5 ⓑ and the exaggeration of half of decision 4). In particular, that review caught that ★**the statement that 「락을 하나도 잡지 않는다」 (no lock at all is taken) covers the whole recovery**★ and ★**the claim that 「후보를 고르는 규칙이 아예 없다」 (there is no rule for choosing a candidate at all)**★ were both wrong.

## 영향 / 불변식

- ★**The two decision predicates are still flipped only as a pair**★ — `can_resume_stored_session` and `capabilities().session.resume`. Even when the channel changes, this pair stays as it is (inherited from ADR-0208·0210).
- **`assigns_session_id()` is still false** (ADR-0185). This decision is not 「우리가 id 를 발급한다」 (we issue the id) but 「codex 가 발급한 id 를 화면에서 읽는다」 (we read, from the screen, the id codex issued).
- ★**The third term of the Fresh give-back decision is now true 「우연히」 (by accident)**★ — `supports_control_channel || declares_link` (`crates/engram-dashboard-agent/src/manager.rs:465-469`) is an enumeration that asks 「이 화신에 그 칸을 채울 경로가 있나」 (does this incarnation have a path to fill that slot), and codex passes because it keeps the control channel on **for MCP mail**. After this decision, the path by which codex fills the slot is the PTY, **not** the control channel. The answer is right and the reason is wrong — the hole that ADR-0208 described as 「컴파일러가 못 잡는다. 진짜 축을 선언하는 칸이 없다」 (the compiler cannot catch it. There is no slot that declares the real axis) is demonstrated once more here. **If a change comes that turns off codex's control channel, look at this line first.**
- **None of the five pump invariants is touched by the scanner** — finalize is once, by the pump alone (ADR-0005) · seq is emitted inside the replay lock (ADR-0079) · fan-out holds no lock (ADR-0006) · replay sending is exclusive to the subscribe side · there are only two turn-observation call sites (ADR-0127). If the scanner touches even one of these, that is a regression.
- ★**The user's screen changes**★ — the thread id becomes visible in the codex TUI status line. If the user had set their own `tui.status_line`, our value overrides it (the later one wins) and leaves a warning. `-c` cannot merge lists, so the user's items disappear in that spawn.
- ★**The last paragraph of the ADR-0208 decision block is alive — it does not fall under the partial-discard clause.**★ That paragraph is turning on `supports_control_channel` in codex and moving `inject_cli_entrance` to the shared backend place, and **that is the only path by which `ENGRAM_TOKEN` and `ENGRAM_CONTROL_URL` get into the codex spawn env.** If it is turned off, mail dies entirely and **the outcome is not an error but silence.** That paragraph begins with 「이 결정에 딸린 결과다」 (this is a consequence attached to this decision) and sits as text inside the discarded decision block, so **do not delete it together when deleting the hook.**
- **It inherits the `old_session_ids` remainder, and this decision adds one more growth path.** The open item that ADR-0208 left as 「상한이 없고 증가 경로가 하나 늘었다」 (no upper bound, and one growth path was added) is still true, and decision 7's overwriting pushes in **one more entry per incarnation each time codex issues a new id.** ★**And decision 7 breaks the premise in the `adopt_session_id` header comment, 「`old_session_ids` 를 건드리지 않는다 — 쓰는 갈래는 빈 칸뿐」 (does not touch the old-ids list — the only branch that writes is the empty slot)**★ — that comment is cleaned up together with the code in the round of decision 9.
- **Deleting the hook changes the regression-net numbers** — when the hook integration suite file disappears, the number of workspace test result lines drops. The numbers in CLAUDE.md 「빌드·검증 명령」 are updated in the same round.
- ★**The structure reference document still teaches the hook channel**★ — `docs/reference/structure/agent-backend.md` lists `-c hooks.SessionStart=…` in the spawn argv table, and explains the terminal-mode handle as 「codex 가 띄우는 `SessionStart` 훅이 제어 평면으로 되돌려 적어 준다」 (the session-start hook that codex launches writes it back to the control plane). **It is fixed together in the round of decision 9** — if not fixed, the repository's structure source of record points at a channel that does not exist.
- ★**The deletion cut the pointers to the 「정본」 (source of record) — we write down here the place to revive it.**★ **Three** documents, in **six lines**, point to the header of `crates/engram-dashboard-daemon/src/control/hook.rs` as the **narrative source of record for the hook misattribution threat model**, and decision 9 deleted that file entirely — ADR-0208 (the related line · 맥락 · three in 영향) · `docs/research/codex-session-id-recovery-survey-2026-09-19.md` (two) · `docs/process/step-log.md` (one). ★**How to find them = `rg "control/hook.rs" docs/`**★ — a hand-written list goes stale, so if the numbers disagree, trust this command. **If that narrative is needed again, take it from git history — `git show 0975d77:crates/engram-dashboard-daemon/src/control/hook.rs` (roughly lines 14-37).** Not fixing the pointing side is intentional: the clause holding that pointer is **a clause this ADR has already discarded** (the hook recovery path), and dated survey documents are records of that time and are not edited after the fact.
- **Four things remain unverified:** ① **what fork produces, and whether the status line prints the id again on a resume spawn** — ★that resume **keeps the same id is itself measured** (survey §10-8)★. But that measurement was **made through the hook channel**, and whether the status line is painted on resume too was not looked at separately ② **the behavior when several items are placed in the status line or the screen is narrowed further** — only measured with `thread-id` alone ③ ★**whether the id arrives contiguously in the byte stream**★ — the measurement was screen-based, and if escapes get in, decision 4's stripping has to absorb them ④ **GUI measurement** (the condition of decision 9, and it closes ② and ③ together).
