## 맥락

- **같은 일을 하는 사본이 넷이고 동작이 다르다.** 버전 붙은 JSON 데이터 파일 넷 — 셸 설정 `shell\config\settings.json` · 화면 상태 `shell\state\state.json` · 데몬 `daemon\state\agents.json` · `presets.json` — 의 읽기 규칙(BOM · 크기 상한 · 버전 문 · 손상 판정) · 원자 쓰기 · 손상 사본이 셸 `src-tauri/src/fsutil.rs` · `settings/store.rs` · `state/codec.rs` 와 agent `persistence/mod.rs` · `persistence/presets.rs` 로 갈라져 있었다. 버전 없음 · 새 판 · BOM · 상한 · 손상 사본의 이름과 시점 · 임시 이름 · 잠김 재시도가 파일마다 다르다(TRD §2-1 · §2-2 — 트리 `78ed761` 실측).
- **알려진 결함.** agent 적재가 자기 판과 다른 `schema_version` 을 만나면 빈 목록으로 시작하고, 첫 변경의 저장이 그 파일을 사본 없이 덮는다(`persistence/mod.rs:115-122` · `profile.rs:377-396`). 그 파일이 새 판이면 새 판의 명부가 사라진다. 읽기 IO 실패도 같은 길(빈 목록 → 덮음)이다.
- **platform 밖 마지막 운영 OS 분기.** 셸 `fsutil.rs` 의 잠김 판정 `cfg!(windows)`(`:320`)가 ADR-0275 결정 15 의 시한부 예외로 남아 있었다.
- **저장 실패가 보이지 않는다.** `ProfileStore::save` · `PresetStore::save` 는 `()` 이고 실패는 구현 안에서 로그만 남는다 — `mutate` 가 맵에 먼저 적용하므로 저장이 실패해도 메모리 변경은 성공처럼 남고 재시작에 사라진다(`profile.rs:304-309` · `:387-407`).
- 이 범위는 TRD 1-1 의 미룬 것 D1 · D2 · D3(손상 사본 · 셸 쓸어 담기 · 원자 쓰기)과 TRD 1-3 §5-1 U-W(원자 쓰기 통일)를 이어받는다. 같은 범위에 덤 둘이 들었다 — agent 자식 띄우기 세 벌(stdio · pty 는 무리 넣기가 실패하면 띄운 자식이 무리 밖에서 산다)과 셸 손 락 오염 복구 · 상태 기록기 자기 시계.

## 결정

> **출처 표기.** 「사용자」 = 사용자 결정 2026-10-08~10(TRD §1 — 재론하지 않는다) · 「메인 판단(위임)」 = 사용자가 「성숙 프로그램 관행대로 · 메인이 정하고 보고」로 넘긴 세부를 메인이 채택한 것(2026-10-10 · TRD §3-5) · 「메인 결정」 = 메인이 위임 「성숙한 프로그램 관행대로」 아래 정한 것 — 리뷰 1 라운드 취합(첨부 r1)과 그 밖에서 정한 것(예: 오염 복구 12번째 자리 `layout/apply.rs:247` · `writable` · net 범위 · 손자 추적 항목 — 결정 14 · 15) · ★「잠정」 = 리뷰 2 · 3 · 4 라운드 취합에서 메인이 정한 것 — 기댄 위임은 항목에 따라 「관행대로」 · 「막히면 간단한 건 자의적으로」(자율 모드) 둘 중 하나 또는 둘 다다 · **사용자 확인 대기**(첨부 r2 · r3 · TRD 머리의 6판 개정)★. 이름(`OsHooks` · `Spec` · `Claim` · `Entry` · `refusing` 등)은 전부 TRD 의 가안이다.

### 거처

1. **데이터 파일 넷의 규칙을 구현 하나로 모은다 — base 새 입주자 `file`**(사용자 — 「Base에 넣어야지. 나중에 쪼갤려면 base에서 쪼개야지.」). 읽기 · 버전 판정 · 원자 쓰기 · 복사 · 손상 사본 · 임시 쓸기 · 「덮어도 되나」 판정이 전부 `file` 에 서고 셸 · agent · 데몬이 같은 함수를 부른다(1a · 1b). 파일 이름 · 자리 · 스키마 · 버전 키 이름(`$version` · `version` · `schema_version` — 지금 그대로라 있는 파일이 계속 읽힌다)은 각 주인이 쥔다. `file` 이 아는 이름은 두 꼴뿐이다 — 임시 `<이름>.tmp<pid>.<번호>` · 사본 `<이름>.corrupt`. 2판의 새 crate 안은 철회됐다(거부한 대안 A).
2. **OS 에 따라 갈리는 셋 — 잠김 판정 `is_busy` · 다시 하기 `retry_busy` · 폴더 동기화 `sync_dir` — 은 platform `fs` 다**(사용자 1d · 1f · 5 — `sync_dir` 와 `OsHooks` 모양은 메인 판단(위임) · R10). base 는 platform 을 부르지 못하므로(입주 조건 ②) `file` 의 IO 함수는 다시 하기와 폴더 동기화를 **부르는 쪽이 넘기는 인자 `OsHooks`** 로 받는다. 운영 값은 crate 마다 상수다 — 셸 · 데몬 하나씩 · agent 둘(적재 읽기 몫 — 결정 4 의 R14). 그래서 셸 `fsutil.rs` 의 `cfg!(windows)` 가 걷혀 platform 밖 운영 OS 분기가 0 이 된다 — **ADR-0275 결정 15 의 시한부 예외를 닫는다**. ★`OsHooks` 는 운영 상수를 위한 fn 포인터 그대로 두고, 상태를 쥔 시험 가짜는 base 안 비공개 클로저 이음매로만 넘긴다(D15 · 잠정)★.
   - **데이터 파일 밖의 두 소비자.** 데몬 `control/mcp_config.rs` 의 토큰 파일은 평범한 `fs::write` 에서 통일 원자 쓰기(`write_atomic`)로 바뀐다(사용자 1e) — 같은 수명 · 같은 꼴인 세션 설정 조각도 함께 옮긴다(메인 판단(위임)). ★토큰이 임시 파일에도 잠깐 실린다 — 같은 폴더 · 같은 ACL · 실패면 지운다★. ★지금의 `create_dir_all` 은 R11 이 `write_atomic` 에 든 뒤(U3)에만 걷는다 — 먼저 걷으면 새 데이터 루트에서 첫 에이전트 스폰이 실패한다★. 1d 의 다른 소비자 agent `usage/scratch.rs` 는 base 를 거치지 않고 platform `retry_busy` 를 직접 부르며, ★잠김 아닌 오류는 더는 다시 하지 않는다 — U6 파일럿이 실제 실패 코드를 먼저 잰다(TRD §8-2 1)★.
3. **ADR-0269 결정 6 「지킬 것」을 고친다 — base 가 `serde_json` 을 들인다**(사용자 5). 읽기 판정이 `Value` 를 보기 때문이다. 구조체 ↔ JSON 직렬화 · `serde` derive · ts-rs 는 여전히 주인이 한다. 같은 결정으로 ADR-0269 결정 2 표의 `file` 행(`set_aside_corrupt(path, stamp_ms)` · 「원자적 쓰기는 platform 으로」) · 결정 6 둘째(시각은 인자로 — 고정 이름이라 해당 없음) · 넷째(원자적 쓰기는 platform 이 생긴 뒤 1-3 으로) · 「영향」의 사본 목록이 바뀐다. **ADR-0266 결정 8(원자 쓰기 거처 = platform)도 base `file` 로 개정한다** — 그 근거였던 「함수 안의 OS 분기 한 줄」이 platform `is_busy` 로 떨어지고 base 는 그 결과를 인자로 받기만 하기 때문이다.

### 읽기 · 쓰기 규칙 (정본 = TRD §3-5 의 R1~R17 표)

4. **R1~R15 = 메인 판단(위임)** — 관행 또는 지금 확정된 셸 규칙을 근거로 메인이 채택했다(2026-10-10 · R2 · R7 · R8 은 메인이 따로 다시 확인했다 — TRD §8-1 2 · 4). 요지:
   - **R1** 버전 없음 = 1 판 · **R3** 앞 판은 그 판 리더가 있을 때만 읽고 없으면 손상(지금 넷 다 `current = 1` · `version` 은 앞 판 리더와 함께만 올린다) · **R4** 버전 값은 정수 값인 수만(`1` · `1.0`) · **R5** 앞머리 BOM 하나는 무시하고 쓰지 않는다.
   - ★**R2 새 판(`found > current`)이 쓴 파일은 네 파일 모두 읽지도 · 덮지도 · 떠 두지도 않는다**★ — 메모리는 기본값 · 빈 목록이고 그 파일 쓰기는 거절한다(설정 = 쓸 때마다 다시 읽으므로 파일이 바뀌면 풀림 · 상태 = 그 실행 동안 저장 없음 · agents · presets = 그 실행 동안 읽기 전용 — 결정 6). **TRD S21-storage §6-5 · §12 R3(새 판 `state.json` 은 떠 두고 덮는다 · 하향 지원 안 함)를 뒤집고, ADR-0265 결정 4 · ADR-0274 의 「모르는 `$version` · `version` = 통째로 못 쓸 파일」에서 새 판을 뺀다.** 위 알려진 결함이 이것으로 닫힌다. 화면 상태에는 새 상태값 `newer`(버스 `restore.status` 의 `state_file`)와 안내가 생긴다.
   - **R6** 상한 = 읽기 상한 = 쓰기 상한 — 넘는 원문은 쓰지 않는다(설정 64 KiB · 상태 4 MiB 그대로 · agents.json 16 MiB · presets.json 4 MiB 새로).
   - **R7** 손상 = JSON 아님 · 객체 아님 · 상한 초과 · UTF-8 아님 · 버전 꼴 틀림 · 리더 없는 앞 판 · ★주인 모양 검사 실패 — 모양 검사는 `Spec` 에 살고 `parse` 가 부르므로 적재 · 저장 직전 재판정 · 상태 기록기 재판정 어디서나 같은 손상 정의다(D1 · 잠정)★. **읽기 IO 실패는 손상이 아니라 저장 거절이다**(그래서 agent 의 「읽기 실패 → 빈 목록 → 덮음」도 함께 닫힌다).
   - **R8** 쓰기 판정 = Missing · 쓸 수 있음 → 쓴다 · 손상 → 떠 두고 쓴다 · 새 판 · 읽기 실패 → 거절. ★적재가 Missing · 손상이었고 이 실행이 아직 한 번도 안 쓴 동안(`Claim::NotYet`)에 쓸 만한 파일이 놓여 있으면 덮기 전에 떠 둔다 — 사본 이름은 ADR-0274 의 고정 `.corrupt` 그대로(D14 · 잠정)★. 떠 두기가 실패하면 설정 · agents · presets 는 그 쓰기를 실패시키고(원본 그대로) 상태만 진행한다(ADR-0274 「영향」 대가 2 · 상태 = TRD S21-storage 의 사용자 결정 D8 그대로).
   - **R9** 손상 사본 = ADR-0274 그대로(고정 `<이름>.corrupt` · 복사 · 덮어쓰기 · 첫 쓰기 직전)를 agents · presets 에도 쓴다(사용자 1c — 두 번째 손상이 첫 사본을 덮는 것을 받아들였다). agent 는 「적재 때 `.corrupt-<ms>` 로 이동 · 누적」에서 「첫 저장 직전 복사」로 바뀐다.
   - **R10** 원자 쓰기 = 같은 폴더 임시 → 담고 `sync_all` → rename → 부모 폴더 동기화(platform `sync_dir` — POSIX = 폴더 `sync_all` · Windows = 명시 무동작 · 결과 무시) · 실패 · 건너뜀이면 임시를 지운다. **R11** 폴더는 쓰는 쪽이 쓸 때 만들고(`write_atomic` · `copy_atomic` 안) 적재 · 판정은 아무것도 만들지 않는다 — 상태 기록기와 떠 두기도 실행 중 지워진 폴더를 다시 만든다.
   - **R12** 임시 이름 = `<이름>.tmp<pid>.<번호>` · 남은 임시는 그 파일 주인이 기동 때 쓴다(산 남의 pid 는 둔다) · 옛 고정 이름 `agents.json.tmp` · `presets.json.tmp` 는 저장소가 같은 자리에서 직접 지운다(`sweep_temps` API 는 그대로) · agent 의 `write_lock` 은 걷고 저장소가 새로 갖는 상태(적재 거절 · ★마지막 재판정 거절(D6 · 잠정)★ · ★`Claim`(D14 · 잠정)★ · 로그 표시)를 잎 락 하나 「저장소 상태 칸」에 둔다 — 락 순서 = `래치 → expected 칸 → profiles|presets → 저장소 상태 칸`.
   - **R13** 잠김 판정 = `PermissionDenied` + Windows 원시 32 · 33. **R14** 다시 하기 = 첫 시도 + N 번 · 고정 간격 · 마지막 뒤에 자지 않음 · 잠김 아닌 오류는 바로 · 예산은 부르는 쪽이 넘긴다 — 데이터 파일 5 × 20 ms(base `file` 의 상수) · ★agents · presets 의 적재 읽기만 첫 시도 + 19 번 × 50 ms(파일마다 약 1 초 — 거기서 남은 잠김은 그 실행 내내 읽기 전용이 되므로, D7 · 잠정)★ · 임시 폴더 지우기 19 × 10 ms. **R15** 거절 로그 = 거절 상태에 드는 순간 error 한 번 · 같은 까닭이 이어지는 동안 debug · 쓰기가 한 번 성공하면 처음부터.
5. **R16 저장 직전 재판정 · 프로세스 간 잠금 없음**(메인 결정). 쓰기 정책을 적재 때 정해 들고 있지 않고, 쓰기마다 그 직전에 지금 파일을 다시 읽어 R8(모양 · `Claim` 포함)로 판정한다. 프로세스 간 잠금(파일 잠금 · 잠금 파일)은 두지 않는다 — 한 데이터 폴더의 각 파일을 쓰는 프로세스는 하나다: `daemon\` 아래는 데몬(단일 인스턴스 가드를 레지스트리를 만들기 전에 쥔다) · `shell\` 아래는 셸. ★셸 쪽 근거의 주는 single-instance 플러그인이고(그 뮤텍스는 데이터 폴더가 아니라 **번들 식별자** 단위다 — 식별자가 다른 빌드는 데이터 폴더부터 다르다) 셸 실행 잠금 `state/lock.rs` 는 보조다(C1 · 리뷰 3 라운드 잔손질 · 잠정)★. ★**실행 중 바깥 편집은 지원하지 않는다** — 데몬 · 앱이 떠 있는 동안 사람 · 동기화 도구가 네 파일을 바꾸면 다음 저장이 덮는다(마지막 작성자가 이긴다 · 지금과 같다 · 고치려면 끄고 고친다). 재판정이 잡는 것은 그 편집이 새 판 · 못 읽는 파일 · 손상을 만든 경우뿐이다(C1 · 잠정)★.
6. **R17 agents · presets 의 저장 거절 = 읽기 전용 모드**(메인 결정).
   - 적재 판정이 거절(새 판 · 읽기 실패 — 적재 읽기 예산 뒤에도 남은 잠김 포함)이면 **그 실행 내내 읽기 전용**이다. 메모리 명부는 비고, 부르는 쪽 있는 변경은 적용 전에 오류로 돌아온다. ★데몬 재시작으로만 풀린다(메인 확인 · 잠정)★ — 재판정은 「지금 파일이 쓸 만한가」만 보고 「메모리가 그 파일에서 왔나」를 모르므로, 뒤에 파일이 읽히게 됐다고 재판정만으로 풀면 빈 명부가 진짜 명부를 덮는다.
   - 저장소 상태가 버스 명부 `agent.list` 에 실린다. ★값은 셋이다 — 쓸 수 있음 · 읽기 전용(적재 거절) · 이번 쓰기 거절(가안 `refusing` — 적재는 됐는데 마지막 저장의 재판정이 거절)과 까닭(D6 · 잠정 · 낱말은 구현에서)★. 화면 명부에는 싣지 않는다.
   - **부르는 쪽 있는 변경**(버스 · WS · 그 둘이 부른 띄우기 경로) = 사본에 적용 → 저장 → `Ok` 일 때만 커밋. ★`Err` 이면 거절이든 쓰기 IO 실패(디스크 가득 · 잠김 예산 초과)든 메모리를 그대로 두고 오류를 돌려준다(TRD §8-3 의 메인 결정 「예」 · 잠정)★.
7. ★**부르는 쪽 없는 내부 변경은 저장의 어떤 `Err`(쓰기 IO 실패 · 저장 직전 재판정 거절)에도 메모리에 적용하고 dirty 를 세운다 — 다음 성공 저장이 싣는다**(D2 → E1 · 잠정)★. 대상 = 첫 제출 래치의 세션 id 기록 · claude 파일 감시자의 세션 id 추적 · reaper 의 `auto_restore` 내리기 · 띄운 뒤 `auto_restore` 올리기 · 부팅 복원의 띄우기 경로(결정 8). 오늘의 자가 치유(저장이 실패해도 메모리는 남고 다음 저장이 디스크를 맞춘다)를 내부 입구에 그대로 남긴다. 디스크는 매 쓰기의 재판정이 지킨다 — 거절이 풀린 뒤의 첫 성공 저장에만 dirty 명부가 실린다. 적재 거절(읽기 전용)이면 명부가 비어 내부 변경의 대상이 없다.
   - dirty 는 레지스트리 맵 옆(같은 profiles · presets 락)에 둔다 — 「메모리가 디스크보다 앞섰다」는 레지스트리만 아는 사실이고 세우고 지우는 자리가 전부 그 락 안이라 새 락 · 새 간선이 없다. 부르는 쪽 있는 변경이 `Err` 로 돌아가도 밀린 dirty 변경은 지워지지 않는다.
   - **종료 때 남은 dirty 는 잃는다** — 종료 경로에 마지막 저장을 더하지 않는다(지금 동작 그대로 · 리뷰 3 라운드 잔손질 · 잠정). ★dirty 동안은 「변경 없음」으로 답한 `mutate_if` 도 저장한다(잠정 채택 — TRD §8-2 10)★.
   - 결과 불변식 = 「메모리 명부 = 마지막으로 성공한 디스크 + (dirty 면) 그 뒤의 내부 변경」.
8. ★**부팅 복원은 내부 변경으로 치고, 수동 깨우기와 함께 닿는 한 공유 함수(`spawn_agent_watching_link`)에 정책 인자 하나(가안 `Entry` — 부르는 쪽 있음 · 내부)를 실어 가른다 — 입구별 사본(복원 전용 띄우기 함수)을 두지 않는다**(E1 · E3 · 잠정)★. 부팅 때 그 경로의 저장이 거절 · 실패해도 메모리에 적용 + dirty 하고 띄우기를 이어 간다. 지금 운영 데몬은 부팅 자동 복원을 부르지 않는다(기본 OFF) — 규칙은 그 함수가 다시 불릴 때를 위해 정하고 시험으로 지킨다.
9. ★**변경 뒤 부수효과는 `Ok` 일 때만 돈다**(D3 · 잠정)★ — 명부 브로드캐스트 · 버스 `roster_changed` · WS `DeleteProfile` 의 메시징 삭제 정리 훅(ADR-0116 결정 3 — 지우지 못한 프로필을 정리하면 산 프로필의 메시징이 깨진다). ★단 ADR-0172 가 활성화 **실패** 때도 요구하는 알림(버스 깨우기 · 만들고 띄우기의 활성화 뒤 알림)과 WS 활성화 뒤 브로드캐스트는 이 규칙 밖이다 — 「마지막 실패」는 명부로만 흐르기 때문이다(E2 · 잠정)★.
10. ★**띄우기 경로의 세 변경(명부 등록 · 화신 표식 · 옛 손잡이 이력화)은 「셋 다 아니면 전무」로 묶지 않는다**(D8 · 잠정)★. 화신 표식(`epoch_for_spawn`)은 디스크에 의미 있게 실리지 않으므로(읽기 건너뜀 · 쓰기 `0` 자리채움) `mutate` 를 타지 않고 락만 잡아 표식을 간다 — 저장 없음(`set_last_failure` 꼴). 등록이 성공한 뒤 이력화가 실패하면 등록을 되돌리지 않는다 — 「명부에 오른 채 안 뜬 에이전트」이고 지금 프로세스 열기 실패 뒤와 같은 끝 모양이다. ★만들고 띄우기(`create_and_start`)의 부분 성공은 지금의 계약 그대로다 — 등록을 되돌리지 않고(되감기는 둘째 삭제 경로) 오류 문구가 회복 길을 나른다. 새 장치를 두지 않는다(리뷰 4 라운드 · 잠정)★.
11. ★**락 안 작업이 느는 것을 수락한다**(D4 · 잠정)★ — 저장 한 번이 profiles · presets 락 안에서 그 파일 다시 읽기 · 파싱 · 모양 검사 · 손상이면 떠 두기 · 각 단계의 잠김 다시 하기를 더 한다. 보통 = 작은 파일 읽기 한 번 더 · **최악 = 잠김 다시 하기의 잠만 약 0.4 초**(5 × 20 ms 고리 넷) + IO + 상한까지의 파싱 두 번. 그동안 명부 조회(우편 발송의 임계 경로)가 선다. 판정과 쓰기가 같은 락 안이어야 두 저장이 겹치지 않고, 최악은 그 파일이 잠긴 동안뿐이며 저장은 수명 사건에서만 돈다.
12. ★**상태 기록기도 저장 직전마다 다시 판정한다**(D5 · E5 · 잠정)★ — 기록기의 파일 이음매(`StateFiles`)에 state.json 읽기와 떠 두기 두 연산을 더한다 · 새 판 거절은 코덱이 거절한 스냅숏처럼 다음 화면 변경까지 기다린다(주기마다 다시 읽지 않는다) · 읽기 실패 거절만 디바운스 뒤 다시 판정한다 · 떠 두기가 실패해도 그 쓰기는 한다(R8 — 상태는 TRD S21-storage 의 사용자 결정 D8 그대로).

### 덤 둘

13. **agent 자식 띄우기 세 벌을 하나로 — codex 의 가드(무리 넣기가 실패하면 띄운 자식을 끈다)를 stdio · pty · codex 셋 모두의 규칙으로**(사용자 2g). 가드가 끄는 것은 직속 자식뿐이고 Windows 의 claude · codex 는 `cmd.exe /c <CLI>` 로 떠 실제 CLI 가 손자이므로, **가드 `Drop` 이 먼저 platform `process::kill_tree` 로 자식 트리째 끈다**(메인 판단(위임) — TRD §3-7 · Windows 밖은 지금처럼 직속 kill 로 물러선다). 띄운 뒤의 모든 `?` 는 가드 아래 · 가드는 통로가 서기 전의 실패 경로만 다룬다 — kill 인과(ADR-0001) 무변경.

## 거부한 대안

거부 근거는 TRD(§3-1 · §3-5 · §3-7 · §3-9 · §8-1)와 리뷰 취합 첨부에 적힌 것만 옮긴다.

- **A — 새 crate `engram-dashboard-datafile`(2판의 결정)** — 사용자 결정(「Base에 넣어야지. 나중에 쪼갤려면 base에서 쪼개야지.」). ADR-0269 결정 1 이 미룬 「목적별 작은 crate 로 쪼개기」를 이 자리에서 먼저 하는 셈이었다. 2판이 셌던 대가(워크스페이스 멤버 11 → 12 · 등록 게이트 넷 · 회귀 결과 줄 +2)도 사라진다.
- **B — 기존 둘에 나눠 넣기**(원자 쓰기 · 복사 · 떠 두기 · 임시 · 쓸기는 platform `fs` · 읽기 · 판정은 base `file`) — ADR-0266 결정 2(platform 의 입주 기준 = OS 의존 여부): 그 장치들은 OS 무관이고, 그 안의 OS 몫인 잠김 판정 한 줄은 `is_busy` 로 이미 platform 에 떨어졌다. ★3판이 함께 들었던 사유 둘(「`.corrupt` 이름은 도메인 지식이다」 · 「부르는 쪽이 두 crate 를 각자 잇는다」)은 base 를 고른 근거와 서로 어긋나 뺐다(D12 · 잠정)★.
- **C — 전부 platform 에 + `serde_json` 허용** — platform 의 서드파티 규칙(`windows` · `tracing` 뿐 — 그 crate 헤더 「의존」)이 깨지고 OS 층에 JSON 정책이 든다.
- **D′ — 판정 함수(`is_busy`)만 넘기고 다시 하기 고리와 예산은 base `file` 이 쥔다** — platform `retry_busy` 는 scratch · net 의 몫으로 남으므로 고리가 둘이 되고, 1d(「잠깐 쥐어졌다」 재시도 = platform 정책 하나)를 어긴다.
- **2판이 지금 모양(부르는 쪽이 재시도를 넘긴다)을 기각했던 사유 둘 — 다시 봐 거둔다.** ① 「base 에 어차피 `serde_json` 이 든다」 = 사용자가 ADR-0269 결정 6 「지킬 것」을 고쳤고, base 를 운영 의존으로 부르는 셋(셸 · agent · 데몬)이 이미 `serde_json` 을 끌어 `Cargo.lock` 새 패키지가 0 이다. ② 「부를 때마다 platform 재시도를 들고 오는 이음매는 의존을 피하려고만 생긴다」 = 이음매는 crate 마다 상수 하나로 끝나고, 같은 꼴이 이미 있으며(셸 `sweep_temps` 가 platform 의 PID 생존 판정을 인자로 받는다 — `state/boot.rs:105-110`) 그 이음매가 그대로 시험 이음매다(ADR-0012). 남는 대가 = 운영 `OsHooks` 에 아무것도 안 하는 재시도를 넘겨도 컴파일이 서므로 crate 마다 「재시도가 잠김 오류를 실제로 다시 한다」 시험 하나를 둔다.
- **새 판도 떠 두고 덮기(R2 앞의 상태 · 설정 규칙)** — 관행 = 새 판이 쓴 파일을 옛 판이 덮지 않는다(SQLite 는 머리의 쓰기 판이 자기보다 큰 DB 를 읽기 전용으로 연다 · Firefox 는 새 판이 쓴 프로필을 옛 판이 열지 않는다). 상태의 크래시 사본은 이미 그렇게 한다(TRD S21-storage N6). ★기각 근거 약함 — 관행 인용은 원문 대조를 하지 않았다(기억 인용 · 미검 — TRD §8-2 3)★.
- **한 예산으로 맞추기(R14)** — 근거가 서로 다르다: 데이터 파일 = 지금 셸 규칙(ADR-0265 결정 4) · 임시 폴더 지우기 = scratch 의 200 ms 실측 예산 · net 열기 = 「5번 시도 · 최악 400 ms(클라이언트 5 s 폴링 안)」 · 적재 읽기 = 셸의 데몬 찾기 마감 5 초에서 거꾸로 정한 값.
- **적재 때 정한 쓰기 판정을 들고 있기(2판)** — 두 가지가 샌다: ① 실행 중에 파일이 새 판으로 바뀌어도 덮는다 ② 손상이라 「떠 두고 쓴다」로 정한 값을 들고 있으면 첫 저장 뒤 우리 정상 파일을 저장마다 `.corrupt` 로 떠 두어 진짜 손상 사본을 지운다(리뷰 1 라운드 codex).
- **프로세스 간 잠금(파일 잠금 · 잠금 파일)** — 결정 5 의 단일 작성자 가드(데몬 단일 인스턴스 가드 · 셸 single-instance 플러그인)와 겹치는 장치다.
- **파일 신원(파일 id · 수정 시각 · 크기)이나 내용 지문을 적재 · 쓰기 때 기억해 저장 직전에 대조하고, 다르면 그 저장을 거절하거나 다시 적재하기**(C1 · 잠정) — 메인 결정: 관행대로 감지 장치를 두지 않는다(앱이 소유한 상태 파일은 실행 중 바깥 편집을 지원하지 않고 마지막 작성자가 이긴다 — Firefox `prefs.js` · Chrome `Preferences`). 지금 동작과 같아 회귀가 아니고, 다시 적재 갈래는 아래 「실행 중 다시 적재」와 같은 정합 설계(명부 · 화면 · 산 세션)가 든다. ★기각 근거 약함 — 관행 인용은 기억 인용 · 미검이고 나머지는 서술이다★.
- **저장 거절 = 로그만 · 메모리 변경은 성공처럼 · 재시작하면 사라짐(2판 · 지금 동작)** — 호출자(사람 · LLM)가 「바꿨다」고 믿은 변경이 재시작에 사라진다(`ProfileStore::save` 가 `()` — `profile.rs:304-309`). 모양은 SQLite 가 읽기 전용으로 연 DB 에 쓰기를 오류로 돌려주는 것과 같다(기억 인용 · 미검).
- **먼저 묻고 적용(쓸 수 있나만 확인한 뒤 맵에 적용 → 저장)** — 확인과 저장 사이의 쓰기 실패(디스크 가득 · rename 잠김 예산 초과)가 다시 「메모리만 바뀜」을 만든다.
- **실행 중에 다시 적재해 읽기 전용을 푼다** — 명부가 실행 중에 바뀌어 화면 · 산 세션과의 정합을 따로 설계해야 한다(재판정만으로 푸는 길은 결정 6 의 덫에 걸린다). ★기각 근거 약함 — 서술뿐★.
- **내부 변경도 전부-아니면-전무(3판)** — 첫 제출 래치 머리의 전제(「포트는 반환이 없어 결과가 래치에 돌아오지 않고, 같은 입력이면 답도 같으므로 재시도할 것이 없다」 — `session_id_latch.rs:14-16`)가 깨지고, 일시 실패 하나가 세션 id · `auto_restore` 를 영영 잃는다(리뷰 2 라운드 D2).
- **내부 변경도 저장 직전 재판정이 거절하면 적용하지 않고, 부팅 복원은 그때 `Failed`(4판)** — 재판정의 짧은 읽기 잠김 하나가 reaper 의 `auto_restore=false`(`reaper.rs:135`)를 버려, 메모리의 `true` 가 다음 저장에 실리고 죽은 에이전트가 다음 부팅 복원 대상으로 되살아난다(`manager.rs:2003-2010` 의 「올림 → 펌프 → reaper 내림」 순서가 막으려던 크래시 루프). 래치의 세션 id 도 버려지고(ADR-0226) 부팅 복원이 실패한다. 새 판 파일 위에 우리 명부를 쓰지 않는 것은 매 쓰기의 재판정이 이미 지킨다(리뷰 3 라운드 E1).
- **부팅 복원 전용 띄우기 함수(입구별 사본)** — 부팅 복원은 수동 깨우기와 같은 동사를 일부러 쓴다. 사본은 ADR-0082 · ADR-0201 · ADR-0202 가 막은 「입구마다 판정이 갈려 하나가 뒤처진다」를 되살린다(리뷰 3 라운드 E3).
- **(g) 멈춘 채 띄우기(platform `spawn::prepare_tree_root` · `TreeRoot` — 사용량 조회의 선례)로 바꾸기** — 넣기 전에는 손자가 생길 수 없어 성공 경로의 틈까지 닫지만, portable-pty(pty 통로)는 멈춘 채 띄우는 길이 없고 stdio · codex 의 성공 경로를 바꾸는 일이라 2g(가드 규칙)의 범위를 넘는다.
- **1d 의 base `writable` `retry_if_vanished` 도 platform 정책으로** — 잠김 재시도가 아니라 `NotFound` 일 때 한 번 더 하는 것이다(검사 도중 남이 폴더를 지우는 경합 — `writable.rs:86-97`). OS 규칙이 없어 platform 헌장(OS 의존 여부)에 안 맞고, ADR-0282 가 그 자리를 base 로 정했다 — 넣으려면 platform 에 OS 무관 코드가 들어간다.

## 근거

- **현황 실측**(트리 `78ed761` — TRD §2): 사본 목록 · 동작 차이 표 · 기록과 어긋난 사실(ADR-0266 결정 8 둘째 항목 「`set_aside_corrupt` 는 rename 하나로 OS 분기가 없다」는 ADR-0274 가 떠 두기를 복사로 바꾼 뒤 거짓이었다 · ADR-0269 「영향」 · ADR-0266 결정 8 의 사본 목록에 있던 `usage_service/reject_store.rs` 는 ADR-0284 가 걷었다).
- **무게 · 그래프**: base 를 운영 의존으로 부르는 셋이 이미 `serde_json` 을 끌어 `Cargo.lock` 새 패키지 0(`cargo tree --locked -i engram-dashboard-base` 와 각 `-p … -e normal`, 2026-10-10). 셸 · agent · 데몬은 base · platform 을 이미 직접 의존한다(`cargo tree --depth 1`, 2026-10-10) — 새 워크스페이스 간선 0 · 새 crate 0 · 회귀 결과 줄 증가 0.
- **리뷰**: TRD `/review trd full` 5 라운드 — 1 라운드 codex BLOCK · Claude FIX 13(첨부 r1) → 2 라운드 codex FIX 1 · Claude FIX 15(첨부 r2) → 3 라운드 codex FIX 1 · Claude FIX 4 + 잔손질 7(첨부 r3) → 4 라운드 doc-aware PASS · codex FIX 1 → 5 라운드 codex PASS · doc-aware FIX(글 고침만 · 재리뷰 없이 확정 — 재수정 상한 도달). 2 · 3 라운드는 두 리뷰어의 지적이 겹치지 않고 서로 보완했다(첨부 r2 · r3 — 대립 없음).
