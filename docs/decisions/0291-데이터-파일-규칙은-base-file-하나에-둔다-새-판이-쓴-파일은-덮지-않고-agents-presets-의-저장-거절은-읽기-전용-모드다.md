## 맥락

- **There are four copies doing the same job, and they behave differently.** For the four versioned JSON data files — the shell settings `shell\config\settings.json` · the screen state `shell\state\state.json` · the daemon's `daemon\state\agents.json` · `presets.json` — the read rules (BOM · size cap · version clause · corruption decision) · atomic write · corrupt copy were split among the shell's `src-tauri/src/fsutil.rs` · `settings/store.rs` · `state/codec.rs` and the agent's `persistence/mod.rs` · `persistence/presets.rs`. No version · a newer version · BOM · cap · the name and timing of the corrupt copy · the temp name · busy retry differ from file to file (TRD §2-1 · §2-2 — measured on tree `78ed761`).
- **A known defect.** When the agent load meets a `schema_version` different from its own, it starts with an empty list, and the save of the first change overwrites that file without a copy (`persistence/mod.rs:115-122` · `profile.rs:377-396`). If that file is from a newer version, the newer version's registry disappears. A read IO failure takes the same road (empty list → overwrite).
- **The last production OS branch outside platform.** The busy decision `cfg!(windows)` (`:320`) in the shell's `fsutil.rs` remained as the time-limited exception of ADR-0275 decision 15.
- **A save failure is invisible.** `ProfileStore::save` · `PresetStore::save` return `()` and a failure only leaves a log inside the implementation — `mutate` applies to the map first, so even when the save fails the in-memory change remains as if it succeeded and disappears on restart (`profile.rs:304-309` · `:387-407`).
- This scope takes over the deferred items D1 · D2 · D3 of TRD 1-1 (corrupt copy · shell sweeping up · atomic write) and U-W (unifying atomic write) of TRD 1-3 §5-1. Two extras came into the same scope — the three copies of agent child launching (in stdio · pty, if putting the child into the group fails, the launched child lives outside the group) and the shell's hand-written lock-poisoning recovery · the state recorder's own clock.

### Home

1. **Gather the rules of the four data files into one implementation — a new base resident, `file`** (user — 「Base에 넣어야지. 나중에 쪼갤려면 base에서 쪼개야지.」). Reading · version decision · atomic write · copy · corrupt copy · temp sweeping · the 「덮어도 되나」 decision all stand in `file`, and the shell · agent · daemon call the same functions (1a · 1b). File names · locations · schemas · version key names (`$version` · `version` · `schema_version` — unchanged, so existing files keep being read) are held by each owner. `file` knows only two name shapes — temp `<이름>.tmp<pid>.<번호>` · copy `<이름>.corrupt`. The new-crate proposal of edition 2 was withdrawn (rejected alternative A).
2. **The three that split by OS — the busy decision `is_busy` · retry `retry_busy` · directory sync `sync_dir` — belong to platform `fs`** (user 1d · 1f · 5 — the shape of `sync_dir` and `OsHooks` is main's judgment (delegation) · R10). Since base cannot call platform (residency condition ②), the IO functions of `file` take retry and directory sync as an **argument `OsHooks` that the caller passes**. The production value is a constant per crate — one each for the shell · daemon, two for agent (the load-read share — R14 of decision 4). So the `cfg!(windows)` in the shell `fsutil.rs` is removed and the production OS branches outside platform become 0 — **this closes the time-limited exception of ADR-0275 decision 15**. ★`OsHooks` stays a fn pointer for production constants, and a test fake that holds state is passed only through a private closure seam inside base (D15 · provisional)★.
   - **Two consumers outside the data files.** The token file of the daemon `control/mcp_config.rs` changes from a plain `fs::write` to the unified atomic write (`write_atomic`) (user 1e) — the session-config fragment, which has the same lifetime and the same shape, is moved together (main's judgment (delegation)). ★The token is also briefly carried in the temp file — same folder · same ACL · deleted on failure★. ★The current `create_dir_all` is removed only after R11 is in `write_atomic` (U3) — removing it earlier makes the first agent spawn fail in a new data root★. ### Read · write rules (source of truth = the R1~R17 table of TRD §3-5)

4. **R1~R15 = main's judgment (delegation)** — main adopted them on the basis of practice or the shell rules now confirmed (2026-10-10 · R2 · R7 · R8 were separately re-confirmed by main — TRD §8-1 2 · 4). In outline:
   - **R1** no version = version 1 · **R3** an earlier version is read only when a reader for that version exists, otherwise it is corrupt (all four now have `current = 1` · `version` is raised only together with an earlier-version reader) · **R4** a version value is only a number that is an integer value (`1` · `1.0`) · **R5** a single leading BOM is ignored and not written.
   - ★**R2 a file written by a newer version (`found > current`) is neither read, overwritten, nor set aside, for all four files**★ — memory is the default · an empty list and writes to that file are refused (settings = re-read on every write, so it is released when the file changes · state = no saving during that run · agents · presets = read-only during that run — decision 6). **This overturns TRD S21-storage §6-5 · §12 R3 (a newer-version `state.json` is set aside and overwritten · no downward support), and removes the newer version from 「모르는 `$version` · `version` = 통째로 못 쓸 파일」 of ADR-0265 decision 4 · ADR-0274.** The known defect above is closed by this. The screen state gets a new status value `newer` (`state_file` of the bus `restore.status`) and a notice.
   - **R6** cap = read cap = write cap — raw text over it is not written (settings 64 KiB · state 4 MiB unchanged · agents.json 16 MiB · presets.json 4 MiB new).
   - **R7** corrupt = not JSON · not an object · over the cap · not UTF-8 · wrong version shape · an earlier version with no reader · ★owner shape check failure — the shape check lives in `Spec` and `parse` calls it, so it is the same corruption definition everywhere: load · re-decision just before saving · the state recorder's re-decision (D1 · provisional)★. **A read IO failure is not corruption but a save refusal** (so the agent's 「읽기 실패 → 빈 목록 → 덮음」 is closed together).
   - **R8** write decision = Missing · writable → write · corrupt → set aside and write · newer version · read failure → refuse. ★If the load was Missing · corrupt and, while this run has not yet written once (`Claim::NotYet`), a usable file is sitting there, it is set aside before overwriting — the copy name is ADR-0274's fixed `.corrupt` as it is (D14 · provisional)★. If setting aside fails, settings · agents · presets fail that write (the original stays as it is) and only state proceeds (ADR-0274 「영향」 cost 2 · state = the user decision D8 of TRD S21-storage as it is).
   - **R9** corrupt copy = ADR-0274 as it is (fixed `<이름>.corrupt` · copy · overwrite · just before the first write) is used for agents · presets too (user 1c — the user accepted that a second corruption overwrites the first copy). For the agent, it changes from 「적재 때 `.corrupt-<ms>` 로 이동 · 누적」 to 「첫 저장 직전 복사」.
   - **R10** atomic write = same-folder temp → write contents and `sync_all` → rename → parent folder sync (platform `sync_dir` — POSIX = folder `sync_all` · Windows = explicit no-op · result ignored) · on failure or skip the temp is deleted. **R11** the folder is created by the writer at write time (inside `write_atomic` · `copy_atomic`) and load · decision create nothing — the state recorder and the set-aside also recreate a folder deleted while running.
   - **R12** temp name = `<이름>.tmp<pid>.<번호>` · leftover temps are swept by that file's owner at startup (a live other pid is left alone) · the old fixed names `agents.json.tmp` · `presets.json.tmp` are deleted directly by the store at the same place (the `sweep_temps` API is unchanged) · the agent's `write_lock` is removed, and the state the store newly holds (load refusal · ★last re-decision refusal (D6 · provisional)★ · ★`Claim` (D14 · provisional)★ · log marker) is put in one leaf lock, the 「저장소 상태 칸」 (store state cell) — lock order = `래치 → expected 칸 → profiles|presets → 저장소 상태 칸`.
   - **R13** busy decision = `PermissionDenied` + Windows raw 32 · 33. **R14** retry = first attempt + N times · fixed interval · no sleep after the last · a non-busy error is returned immediately · the budget is passed by the caller — data files 5 × 20 ms (a constant of base `file`) · ★only the load read of agents · presets is first attempt + 19 times × 50 ms (about 1 second per file — a busy state remaining there makes it read-only for the whole run, so D7 · provisional)★ · temp folder deletion 19 × 10 ms. **R15** refusal log = one error when entering the refusal state · debug while the same cause continues · from the start once a write succeeds.
5. **R16 re-decision just before saving · no cross-process lock** (main's decision). The write policy is not decided at load time and held; at every write, just before it, the current file is read again and decided by R8 (including shape · `Claim`). No cross-process lock (file lock · lock file) is put in — each file of one data folder has one process that writes it: under `daemon\` the daemon (it holds the single-instance guard before creating the registry) · under `shell\` the shell. ★The main basis on the shell side is the single-instance plugin (its mutex is per **bundle identifier**, not per data folder — a build with a different identifier already has a different data folder) and the shell run lock `state/lock.rs` is auxiliary (C1 · review round 3 minor touch-up · provisional)★. ★**Outside editing while running is not supported** — if a person · a sync tool changes the four files while the daemon · app is up, the next save overwrites it (the last writer wins · same as now · to fix it, shut down and then fix). What the re-decision catches is only when that edit produced a newer version · an unreadable file · corruption (C1 · provisional)★.
6. **R17 the save refusal of agents · presets = read-only mode** (main's decision).
   - If the load decision is a refusal (newer version · read failure — including a busy state that remains even after the load read budget), it is **read-only for that whole run**. The in-memory registry is empty, and a change that has a caller returns an error before it is applied. ★It is released only by a daemon restart (main's confirmation · provisional)★ — the re-decision looks only at 「지금 파일이 쓸 만한가」 (is the file usable now) and does not know 「메모리가 그 파일에서 왔나」 (did the memory come from that file), so if it were released by the re-decision alone once the file became readable later, an empty registry would overwrite the real registry.
   - The store state is carried in the bus registry `agent.list`. ★There are three values — writable · read-only (load refusal) · refusing this write (tentative name `refusing` — loaded, but the re-decision of the last save refused) and the cause (D6 · provisional · the words in the implementation)★. It is not carried in the screen registry. ★Landing (U5b-2b · provisional): cell `store { agents, presets }` · status `Writable` | `ReadOnly` | `Refusing` · cause `Newer` | `Unreadable` · `file_version` · agent `catalog_version` 6 → 7★
   - **A change that has a caller** (bus · WS · the launch path those two call) = apply to a copy → save → commit only on `Ok`. ★On `Err`, whether a refusal or a write IO failure (disk full · busy budget exceeded), memory is left as it is and the error is returned (the main decision 「예」 of TRD §8-3 · provisional)★. The entrance names = `try_*` of the registry · manager (U5b-1 · provisional).
   - ★**2026-10-11 amendment (user decision) — that error is split by where the refusal came from.**★ A refusal at load (`StoreError::ReadOnly` — read-only for this whole run) = `CONFLICT` 「다시 해도 같다 — 파일을 고치거나 바꾸고 데몬을 다시 띄운다」 · a refusal of the re-decision just before writing (a new variant `StoreError::Refused` — split from `ReadOnly` in the U5b-2 review), when unreadable = `CONFLICT` 「대개 잠깐 쥔 잠김 — 조금 뒤 다시」 · when a newer version = `CONFLICT` 「그 파일이 있는 동안은 다시 해도 같다」 · a write IO failure = `INTERNAL`. Unreadable for the shell settings (`settings.set` · `settings.reset`) is also `CONFLICT` by the same rule (shell `catalog_version` 16 → 17). Since the daemon relay lowers the retry cell of every reply it relays to `never` (`command_delivery::send_reply` · ADR-0159), this distinction is carried to the caller by the wording and the help text. The place of the mapping = `store_command_error` · `store_error_reason` in `agent/src/commands.rs` (used by both bus and WS).
7. ★**An internal change with no caller is applied to memory on any `Err` of the save (write IO failure · re-decision refusal just before saving) and sets dirty — the next successful save carries it**(D2 → E1 · provisional)★. The targets = recording the session id of the first-submit latch · the session id tracking of the claude file watcher · the reaper's lowering of `auto_restore` · raising `auto_restore` after launching · the launch path of boot restore (decision 8). Today's self-healing (even if a save fails the memory remains and the next save brings the disk into line) is left as it is at the internal entrances. The disk is protected by the re-decision of every write — the dirty registry is carried only by the first successful save after the refusal is released. If the load is refused (read-only), the registry is empty and the internal changes have no target.
   - dirty is placed next to the registry map (under the same profiles · presets lock) — 「메모리가 디스크보다 앞섰다」 is a fact only the registry knows and the places that set and clear it are all inside that lock, so there is no new lock · no new edge. Even when a change that has a caller returns `Err`, the pending dirty changes are not erased.
   - **Dirty left at shutdown is lost** — no final save is added to the exit path (same as current behavior · review round 3 minor touch-up · provisional). ★During dirty, even a `mutate_if` that answered 「변경 없음」 saves (provisionally adopted — TRD §8-2 10)★.
   - ★Landing (U5b-1a · main's decision · provisional — awaiting user confirmation)★: the internal entrances = the existing registry verbs made dirty-aware, and the entrances with a caller = `try_*`. ★presets has no dirty★ — there is no internal preset change, so the preset registry has only `try_*` (it departs from 「같은 profiles · presets 락」 above and the TRD's 「presets 같은 꼴」).
   - Resulting invariant = 「메모리 명부 = 마지막으로 성공한 디스크 + (dirty 면) 그 뒤의 내부 변경」 (in-memory registry = the last successful disk + (if dirty) the internal changes after it).
8. ★**Boot restore is treated as an internal change, and it is split, together with manual wake-up, by putting one policy argument (tentative name `Entry` — has a caller · internal) on the shared function that both reach (`spawn_agent_watching_link`) — no per-entrance copy (a restore-only launch function) is made**(E1 · E3 · provisional)★. 9. ★**Side effects after a change run only on `Ok`**(D3 · provisional)★ — the registry broadcast · the bus `roster_changed` · the messaging deletion cleanup hook of WS `DeleteProfile` (ADR-0116 decision 3 — cleaning up for a profile that was not deleted breaks the messaging of a live profile). ★But the notifications that ADR-0172 requires even on an activation **failure** (the notification after activation in the bus wake-up · create-and-start) and the broadcast after WS activation are outside this rule — because the 「마지막 실패」 (last failure) flows only through the registry (E2 · provisional)★.
10. ★**The three changes on the launch path (registry registration · incarnation marker · archiving the old handle into history) are not bound as 「셋 다 아니면 전무」 (all three or none)**(D8 · provisional)★. 11. ★**Accept that in-lock work grows**(D4 · provisional)★ — one save, inside the profiles · presets lock, additionally does re-reading that file · parsing · shape check · setting aside if corrupt · the busy retry of each step. Meanwhile the registry query (the critical path of mail dispatch) stands still. The decision and the write must be inside the same lock so that two saves do not overlap, and the worst case is only while that file is busy, and saves run only on lifecycle events.
12. ★**The state recorder also re-decides just before every save**(D5 · E5 · provisional)★ — two operations, reading state.json and setting aside, are added to the recorder's file seam (`StateFiles`) · a newer-version refusal waits until the next screen change like the snapshot the codec refused (it does not re-read every period) · only a read-failure refusal is re-decided after the debounce · even if setting aside fails the write is done (R8 — for state, the user decision D8 of TRD S21-storage as it is).

## 거부한 대안

Only what is written in the TRD (§3-1 · §3-5 · §3-7 · §3-9 · §8-1) and the review roll-up attachments is carried over as rejection grounds.

- **A — a new crate `engram-dashboard-datafile` (the decision of edition 2)** — user decision (「Base에 넣어야지. 나중에 쪼갤려면 base에서 쪼개야지.」). It would have done here, ahead of time, the 「목적별 작은 crate 로 쪼개기」 that ADR-0269 decision 1 deferred. The costs edition 2 counted (workspace members 11 → 12 · four registration gates · regression result lines +2) also disappear.
- **B — split it into the existing two** (atomic write · copy · set-aside · temp · sweep in platform `fs` · read · decision in base `file`) — ADR-0266 decision 2 (the residency criterion of platform = OS dependence): those mechanisms are OS-independent, and the busy-decision line that was the OS share inside them has already fallen to platform as `is_busy`. ★The two reasons edition 3 added together (「`.corrupt` 이름은 도메인 지식이다」 · 「부르는 쪽이 두 crate 를 각자 잇는다」) conflicted with the grounds for choosing base and were removed (D12 · provisional)★.
- **C — everything in platform + allow `serde_json`** — it breaks platform's third-party rule (only `windows` · `tracing` — the header 「의존」 of that crate) and puts JSON policy in the OS layer.
- **D′ — pass only the decision function (`is_busy`) and let base `file` hold the retry loop and budget** — platform `retry_busy` remains for scratch · net, so there would be two loops, and it violates 1d (the 「잠깐 쥐어졌다」 retry = one platform policy).
- **The two reasons edition 2 rejected the current shape (the caller passes the retry) — reviewed again and withdrawn.** ① 「base 에 어차피 `serde_json` 이 든다」 = the user amended ADR-0269 decision 6 「지킬 것」, and the three that call base as a production dependency (shell · agent · daemon) already pull in `serde_json`, so new packages in `Cargo.lock` are 0. ② 「부를 때마다 platform 재시도를 들고 오는 이음매는 의존을 피하려고만 생긴다」 = the seam ends with one constant per crate, the same shape already exists (the shell `sweep_temps` takes platform's PID liveness decision as an argument — `state/boot.rs:105-110`) and that seam is itself the test seam (ADR-0012). The remaining cost = since it compiles even if a retry that does nothing is passed to the production `OsHooks`, each crate gets one test, 「재시도가 잠김 오류를 실제로 다시 한다」.
- **Also set aside and overwrite a newer version (the state · settings rule before R2)** — practice = an older version does not overwrite a file written by a newer version (SQLite opens a DB whose header write version is larger than its own as read-only · Firefox's older version does not open a profile written by a newer version). The crash copy of state already does so (TRD S21-storage N6). ★The rejection basis is weak — the practice citations were not checked against the originals (citations from memory · unverified — TRD §8-2 3)★.
- **Fit it with one budget (R14)** — the bases differ: data files = the current shell rule (ADR-0265 decision 4) · temp folder deletion = scratch's 200 ms measured budget · net open = 「5번 시도 · 최악 400 ms(클라이언트 5 s 폴링 안)」 · load read = a value set backward from the shell's 5-second deadline for finding the daemon.
- **Hold the write decision made at load time (edition 2)** — two things leak: ① even if the file changes to a newer version while running, it is overwritten ② if the value decided as 「떠 두고 쓴다」 because of corruption is held, after the first save our normal file is set aside as `.corrupt` on every save and erases the real corrupt copy (review round 1 codex).
- **A cross-process lock (file lock · lock file)** — a mechanism that overlaps with the single-writer guard of decision 5 (the daemon single-instance guard · the shell single-instance plugin).
- **Remember the file identity (file id · modified time · size) or a content fingerprint at load · write, compare just before saving, and if different, refuse that save or reload** (C1 · provisional) — main's decision: following practice, no detection mechanism is put in (a state file the app owns does not support outside editing while running and the last writer wins — Firefox `prefs.js` · Chrome `Preferences`). It is the same as the current behavior so it is not a regression, and the reload branch would need the same consistency design as 「실행 중 다시 적재」 below (registry · screen · live sessions). ★The rejection basis is weak — the practice citations are from memory · unverified and the rest is description★.
- **A save refusal = log only · the memory change as if it succeeded · lost on restart (edition 2 · current behavior)** — a change the caller (a person · an LLM) believed was 「바꿨다」 disappears on restart (`ProfileStore::save` is `()` — `profile.rs:304-309`). The shape is the same as SQLite returning an error for a write to a DB opened read-only (citation from memory · unverified).
- **Ask first and then apply (check only whether it is writable, then apply to the map → save)** — a write failure between the check and the save (disk full · rename busy budget exceeded) again produces 「메모리만 바뀜」.
- **Reload while running to release read-only** — the registry would change while running and the consistency with the screen · live sessions must be designed separately (the road of releasing by the re-decision alone falls into the trap of decision 6). ★The rejection basis is weak — description only★.
- **Internal changes also all-or-nothing (edition 3)** — the premise at the head of the first-submit latch (「포트는 반환이 없어 결과가 래치에 돌아오지 않고, 같은 입력이면 답도 같으므로 재시도할 것이 없다」 — `session_id_latch.rs:14-16`) breaks, and a single transient failure loses the session id · `auto_restore` for good (review round 2 D2).
- **If the re-decision just before saving refuses, an internal change is not applied either, and boot restore becomes `Failed` then (edition 4)** — one short read-busy state in the re-decision throws away the reaper's `auto_restore=false` (`reaper.rs:135`), so the `true` in memory is carried by the next save and a dead agent is revived as a next-boot-restore target (the crash loop that the 「올림 → 펌프 → reaper 내림」 order at `manager.rs:2003-2010` was meant to prevent). The latch's session id is also thrown away (ADR-0226) and boot restore fails. Not writing our registry over a newer-version file is already protected by the re-decision of every write (review round 3 E1).
- **A boot-restore-only launch function (a per-entrance copy)** — boot restore deliberately uses the same verb as manual wake-up. A copy would revive what ADR-0082 · ADR-0201 · ADR-0202 blocked, 「입구마다 판정이 갈려 하나가 뒤처진다」 (review round 3 E3).
- **(g) Switch to launching suspended (platform `spawn::prepare_tree_root` · `TreeRoot` — the precedent of usage queries)** — before the put no grandchild can appear, so it closes even the gap on the success path, but portable-pty (the pty channel) has no way to launch suspended and it changes the success path of stdio · codex, which goes beyond the scope of 2g (the guard rule).
- **(g) The guard kills the whole child tree with `taskkill /T` (platform `process::kill_tree`) (the original of decision 13)** (★main's decision (delegation) 2026-10-10 · provisional — awaiting user confirmation★) — `taskkill` weaves the tree only from parent ids (WMI `ParentProcessId`) and does not look at start times. Processes carrying the id of a dead parent are common on this PC (measured by the U7 reviewer 2026-10-10), so under a `cmd.exe` that received that id again it could kill even someone else's tree (e.g. `explorer.exe`).
- **(g) Scan descendants from a pid snapshot and kill them** (platform `process::subtree` takes an identity list, re-reads each descendant's start time, and kills by that handle — the U7 first amendment) (★main's decision (delegation) 2026-10-10 · provisional — awaiting user confirmation★) — if a pid in the list ends and passes to another process after the snapshot and before the re-read, or a pid of a middle descendant passes before it is expanded, it aims at someone else (two U7 second-round reviews). Descendants launched after the put are ended by the group without pids, so all this means additionally covers is the descendants launched before the put.
- **Also make base `writable` `retry_if_vanished` of 1d a platform policy** — it is not a busy retry but doing it once more on `NotFound` (the race where someone else deletes the folder during the check — `writable.rs:86-97`). It has no OS rule so it does not fit the platform charter (OS dependence), and ADR-0282 set that place in base — putting it in would put OS-independent code in platform.
