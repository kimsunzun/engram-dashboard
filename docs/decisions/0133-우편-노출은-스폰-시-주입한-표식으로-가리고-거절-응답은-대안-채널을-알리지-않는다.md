# ADR-0133: Mail exposure is hidden by a marker injected at spawn, and the rejection response does not announce the alternative channel

- 상태: 확정 (2026-08-12, basis: user decision + 3 code measurements — see the basis below) · 부분 폐기 by ADR-0220 (mail visibility filter) · 부분 폐기 by ADR-0285 (the credential-free nature of help in decision 2, and the reason for rejecting the daemon lookup in the first rejected alternative)
- 관련: ADR-0132(decision 3 daemon-side mail rejection · decision 5 control open to all — this ADR is their execution form) · ADR-0128(decision 1 channel unification kept · the isolation means of decisions 2 and 3 were already replaced by ADR-0132) · ADR-0086(no identity claims — the sender is derived only from the token) · ADR-0126(mutual exclusivity of priming) · `crates/engram-dashboard-core/src/agent/backend/claude.rs`(`inject_cli_entrance`) · `crates/engram-dashboard-daemon/src/bin/engram.rs`(`render_help`) · step-log S19 · Amended by ADR-0220 (mail visibility filter) · Amended by ADR-0285 (the credential-free nature of help in decision 2, and the reason for rejecting the daemon lookup in the first rejected alternative)

## 맥락

To open ADR-0132 decision 5 (control open to all), the single executable `engram` has to be wired into **every spawn**. But that executable also carries the mail family (decision 2) — the means used so far to isolate mail, "do not install the CLI wiring for an MCP-capable spawn", **loses its very footing.** So decision 3 (the daemon-side credential rejection) becomes a precondition.

The rejection alone is half of it. As ADR-0128 recorded, **the primary control on this axis is "do not teach it"** (removing the physical wiring is an auxiliary that reduces the accidental-discovery surface), and the daemon rejection is the enforcement that backs it up. But decision 4 set the discovery means as **group help** — priming teaches "if you need control, `engram help`", so **teaching the agent to look at the list is something that happens for the first time this round.** If the list is the same for everyone, an MCP-capable agent discovers the mail family there, and the primary control collapses this round.

Three things came to light by measurement at the start (the basis section): help is a pure local render that does not know the daemon, the CLI is designed not to claim its own identity, and the presence or absence of a credential cannot separate the two classes (if control is opened, everyone receives a credential).

## 결정

1. **The list is given differently depending on the caller.** In the `engram help` of an agent spawned with an MCP-capable backend, **the mail family does not appear.** The same list is not given to everyone while relying only on rejection.
2. **The means of separating is a single marker injected at spawn.** When the daemon launches an agent, it sends whether mail is allowed in an environment variable, and the CLI **reads that value locally** to split the render. **It does not query the daemon to give the list** — it keeps the property of help, "answers before the credential check" (ADR-0132 piece ①).
3. **The rejection response does not announce the alternative channel.** What is returned when mail is rejected by credential goes only as far as "this credential cannot use mail", and **does not contain the name of the counterpart channel** such as MCP · `send_message`. If a case is observed where an agent receives only the rejection and gives up on mail or malfunctions, the wording policy is reopened then (user decision 2026-08-12 — "just tell them it can't be used, fix it later if a problem comes up").

## 거부한 대안

- **Query the daemon when giving the list** — the answer is authoritative (it is the only party holding the lookup table). But ① **a policy for "when no answer is received" is newly needed** — a stretch in which the daemon is busy or stalled without having died is real (the agent is alive then), and it must be newly decided whether to show everything, show nothing, and how long to wait ② authentication, communication, and failure handling get attached to the simple path that now only reads arguments and prints characters ③ a person opening the usage from a shell without the daemon would no longer work. **Availability is not a reason for rejection** — if the daemon dies, its child agents die with it (basis), so "an agent without a daemon" does not exist. Mistaking this and citing availability as the ground puts the weight of the two alternatives wrongly.
- **Give the list identically to everyone and rely only on rejection** — the structure is the simplest and no marker is needed. But it **gives up the primary control ("do not teach it")** and bets everything on the single daemon rejection. Having the agent constantly see "a feature that exists but that I cannot use" is also a state this project is trying to remove from priming.
- **Split by the presence of a credential** — right now no credential is put into an MCP-capable spawn at all, so "no credential means no mail" holds. But with ADR-0132 decision 5, **if control is opened, everyone receives a credential**, so presence/absence can no longer separate the two classes. This is why a new marker is needed.
- **Have the rejection response guide to the alternative channel** — the agent can recover immediately, so it is kind. But that is itself an **act of teaching the counterpart channel**, and it would **bypass through the rejection path** the unit tests that seal the two priming files so that they do not even mention each other's channel (the real gate of ADR-0128).

## 근거

- **help is a pure local render (measured 2026-08-12).** `render_help` in `engram.rs` only substitutes the tool-name slots of constant strings (`HELP_ROOT`/`HELP_MAIL`/`HELP_AGENT`) — there is no network or authentication path. So attaching a lookup is not "adding a branch" but changing its nature.
- **The CLI does not claim its own identity (measured).** The `engram.rs` header states it as an ADR-0086 invariant — there is no `--as`-type flag, and the sender and "me" are all derived by the daemon from the token. So the only material the CLI has to decide by itself "I am mail-capable" is **what was injected into it**.
- **If the daemon dies, the agents die too (measured).** The daemon puts its child PTYs into a `KILL_ON_JOB_CLOSE` Job (the comment at `crates/engram-dashboard-discovery/src/lib.rs:376` + case1 at `crates/engram-dashboard-daemon/tests/ws_e2e.rs:2337` asserts it with a real process). The daemon itself, spawned via WMI, does not inherit the parent Job, so it survives even if the client shell dies — the direction of death is one-sided.
- **The injection spot already exists (measured).** `inject_cli_entrance` in `claude.rs` carries `ENGRAM_TOKEN` · `ENGRAM_CONTROL_URL` · `ENGRAM_CLI_EXE`. It is currently not called for an MCP-capable spawn, and 3 tests seal that.

## 영향 / 불변식

- **Invariant: enforcement is only the daemon rejection, and the marker is a teaching means.** The marker is attached to the agent's own process, so it **can be tampered with, and the tampering is accepted** — if the marker is removed, mail appears in the list, but the daemon rejects the actual sending. **An implementation that depends on the marker filter for enforcement is a violation** (the same axis as "depending on hiding or filtering on the CLI side is a violation" in ADR-0132 §영향).
- **Invariant: the rejection response does not contain the name of the alternative channel.** It is on the same axis as the priming mutual-exclusivity test, and if broken, that seal is bypassed through the rejection path.
- **The "teaching = wiring" equality breaks and goes back to "teaching ⊆ wiring".** The wiring (executable · credential) goes to everyone and only the teaching (the list) splits. Because **ADR-0132 §영향 has already stamped a partial-discard mark** on the isolation means of ADR-0128 decisions 2 and 3, no new stamp is added here — this ADR is the execution form of that replacement. The body of the channel unification (ADR-0128 decision 1) remains valid as is.
- **Code spots — those whose direction flips.** The equality invariant comment in `claude.rs` (near `accepts_mcp_config`) and the 3 tests that seal "it is a violation if the CLI env is loaded into an MCP-capable spawn" flip in meaning with this decision. Do not delete them — **rewrite them under the new contract (wiring for everyone + only mail hidden by the marker)**. If they are simply deleted, neither side is sealed.
- **Implementation complete (2026-08-12).** The branch "do not install the CLI wiring for an MCP-capable spawn" in `claude.rs` **no longer exists** — the wiring goes to everyone, and what actually blocks mail is only the credential rejection of the daemon auth middleware (the `ControlRoute::is_mail` gate in `control/mcp_server.rs`). Accordingly, the warning item "★decision 3 is not yet implemented★" in ADR-0132 §영향 was also removed. **Do not read the rejection gate as an "auxiliary means" on the basis of this paragraph** — it is now the only enforcement.
- **Reopen trigger** — if a case is observed where an agent that received only the rejection gives up on mail or does something off, the wording policy of decision 3 is reopened.
