# ADR-0265: Settings live in one shell settings.json and are written only through four generic commands

## 맥락

The settings file is the shell's single `ui-settings.json` — `{"theme":…, "windows":{label:…}}`, with a flat root layout (TRD §3-5). Outside agents edit that file directly, and the shell only re-reads it on `ui.refresh` (ADR-0166 decision 3). The frontend holds the authority over chat style and persists it in localStorage (ADR-0051). Since ADR-0169 removed the side door that moved chat style over the bus, a release build has no way to change chat style (that ADR's 「받아들인 대가」).

ADR-0167 wrote that as app-side writes grow, an outside editor and the app will fight over one file, and left two forks open (split the file · funnel writes to one place). The storage-management work (ADR-0264 · TRD S21-storage) sets up `shell\config\` as the place for preferences, so it is time to answer that fork.

User decision (2026-10-02, survey 「0. 결정」): settings = `shell\config\settings.json` — values that people or LLMs set, only what differs from the default. Keys are namespaces. Access is through four generic commands only, and adding a setting means registering one line in a schema. The path where an LLM edited `ui-settings.json` directly is abolished. Only the storage layer knows the file. Chat style moves from localStorage to here. A theme changed on screen is also saved — global default = `settings.json` · per window = that window's entry in `state.json`.

## 결정

1. **Location = the single file `shell\config\settings.json`** (`DataLayout::shell_config_dir` — ADR-0264). Write only what differs from the default. The file = a flat object of dotted keys + a reserved key — `{"$version":1, "theme.default":"light"}`.
2. **One setting = one line in a schema table** (the static table in `src-tauri/src/settings/registry.rs` — key · kind · default · description). **This table is the source of truth for defaults.** A key = a lowercase namespace + dots (`theme.*` · `chat.style.*`), and the last segment keeps the existing spelling. There are 12 initial keys — `theme.default` (choices `dark` · `light` · `e-ink`, default `dark`) + 11 `chat.style.*` keys (decision 9). `CssLength` declares its range per unit — `px` is required, `rem` only when that key accepts it (`em` has the same range as `rem`). A unit that is not declared is `INVALID_ARGUMENT`.
3. **Wire contract — a value is always one canonical string.** The values that get, the answer to set, and notifications carry are in canonical form.

   | Kind | Accepted input | Canonical form | JSON written to the file |
   |---|---|---|---|
   | `Choice` | a choice word, case-insensitive | exactly the table's spelling (`e-ink`) | string |
   | `CssLength` | surrounding whitespace allowed · a number + the unit that key declares (case-insensitive) · within that unit's range | shortest decimal + lowercase unit (`15px` · `0.9rem` · `-1rem`), no `+` | string |
   | `CssNumber` | a number with no unit | shortest decimal (`1.45`) | string |

   There are three errors — unknown key = `NOT_FOUND` · format or range violation = `INVALID_ARGUMENT` (the expected format goes in the message) · disk write failure = `INTERNAL` (memory and `rev` unchanged, no notification). **Whether to write is decided by the disk, and `changed` by the effective value** — if the effective value is the same as now, the result is `changed:false` · `rev` unchanged · no notification, but if the file differs from the target (a value edited outside · an unusable value that was folded away · a non-canonical spelling), only the file is corrected and written. If the effective value changes and the file is already at the target, nothing is written and only `changed:true` and the notification go out. If the file cannot be read (a read IO failure · a file that is unusable as a whole), a write happens only when the effective value changes (on a read IO failure, that write is `INTERNAL`). Receiving a value equal to the default deletes that key from the file. `reset` follows the same decision. One call = one file — a future `reset` spanning two files is rejected with `INVALID_ARGUMENT`.
4. **Only the storage layer knows the file** (`settings/store.rs`). No path-branching function is added for now. A write = **read-modify-write** under the write-serializing lock (`io`) (the file is re-read every time and only the received key is changed) and is atomic (temp file → `sync_all` → rename · if the rename fails with access denied, a sharing violation or a lock violation, retry up to 5 times at 20 ms intervals · `write_atomic` lives in the shell-shared `fsutil.rs`). If the text to write exceeds 64 KiB, nothing is written and the result is `INTERNAL`. **If the file is missing or unusable as a whole, a new file is rebuilt from all the effective overrides in memory** — so deleting the file while running is not a reset (the next call that writes the file restores the values exactly as they are visible), and a key deleted by hand from an intact file is not restored (that edit wins at the next boot — session default, TRD §10 F20). Tolerance per item — unknown keys are ignored but left in the file as they are · an unusable value for a known key is folded to the default with a warn (the file stays as is until it is overwritten) · the read size cap is 64 KiB · a leading UTF-8 BOM is ignored · `$version` is the number 1 (`1.0` also counts as 1). **A file that is unusable as a whole is not touched at load** (memory takes the defaults), **and the first write sets the original aside as `settings.json.corrupt-<ms>` and then atomically swaps in a new file at that location** — if the name collides, `-<n>` is appended and an earlier copy is never overwritten · the copy is `sync_all`'d before the swap-in, so there is never a moment without a file · if setting aside fails, that write is `INTERNAL` and the original stays as it is. An original over 1 MiB is not set aside (an error is logged and the file is then swapped · the cap is also enforced during the copy), and if the copy this process set aside just before is still in that place and is byte-identical to the current original (length · modification time are only a pre-filter), it is not set aside again (session default — TRD §10 F21). This reverses ADR-0166 decision 9 「`.corrupt` 없음」.
5. **Four commands + the Tauri shell wrapper, one service.** Add them to one block of the shell command table (`layout/commands.rs`) and raise `catalog_version` to 10.

   | Command | effect | args → answer |
   |---|---|---|
   | `settings.get` | Read | `{key?}` → `{rev, items:[{key, value, is_default}]}` |
   | `settings.set` | Write | `{key, value}` → `{rev, key, value, changed}` |
   | `settings.reset` | Write | `{key}` → `{rev, reset:[key…]}` |
   | `settings.schema` | Read | `{key?}` → `{items:[{key, kind, default, choices, min, max, description}]}` |

   `key` = an exact key or a prefix ending in a dot. `reset` requires a key (there is no reset-all). The human path uses the same service — it is the `#[tauri::command] settings_get/set/reset/schema` wrapper (ADR-0081 decision 3), and the frontend uses it. The service is loaded **read-only** before the Tauri builder and managed (it exists before the webview's first invoke — ADR-0102), and writing is turned on in `setup`.
6. **Change notification = `settings:changed {rev, items}` after commit.** After releasing the state lock, it is sent to every webview under the notification-order lock (`announce`) — notification order = `rev` order. `rev` is a monotonic number that rises on every write that changes an effective value. Subscribe first → then pull with `settings_get`. The receiver applies an item only when its rev is greater than the last `rev` it applied for that key (a key seen for the first time is applied as is · the `settings_get` answer is also judged per item by the answer's `rev`) — the answer is not discarded as a whole. The authority over chat style moves to the shell — `chatStyleStore` becomes the **applier** that attaches `chat.style.*` to CSS variables (the `CSS_VAR_BY_KEY` whitelist is owned by the frontend) and writing goes through `settings_set`. The localStorage reads and writes and the dev handle `window.__engram.chatStyle` are removed. `chatStyleStore` is taken out of ADR-0035's frontend-only exception list (`docs/reference/architecture-overview.md:578`).
7. **Theme — global is a setting, per-window is state.** Effective theme (window W) = W's window theme ?? `theme.default`. The shell computes it and keeps using the existing per-window delivery (pull `get_ui_settings` + push `ui:settings-updated`). A `theme.default` write and a per-window write each finish their own saving and then call the same function `push_effective_themes()`, which recomputes the effective value of every window and pushes it — the last push = the last read, so even if the two writes interleave, no stale combination is left on screen. **A changed theme is saved** — global = `settings.set theme.default <값>` · per window = the shell command `window.setTheme {window, theme}` (`theme:null` = clear the override) · query `window.getTheme {window}` → `{theme, effective}`. The per-window value goes into that window's model entry and **dies with the window** — a boot sweep is no longer needed. The reason the per-window theme is a fifth path outside the four commands = that value is state, not a setting, and the state file is rewritten wholesale by the machine, so it cannot be a hand-edit path. Today's screen has no UI that changes the theme (ADR-0167 decision 5). The per-window part (`window.setTheme`/`getTheme` · abolishing the sweep) lands in L3 (P3d) — until then ADR-0167 decisions 3, 6 and 7 stay alive in code.
8. **Old values are not handled (U1).** `settings.json` starts from the defaults and is not filled from `ui-settings.json`. The shell ignores that file's `theme` whether it is present, absent or unusable — today a single unusable `theme` rejects the whole file and the per-window slot is thrown away with it, so the parser does not look at `theme`. That file stays alive as the home of the per-window slot during L2, and from P3d the shell neither reads nor writes it. The leftover file is not handled separately. The chat style's localStorage values are not imported either. There is no migration code.
9. **`chat.style.*` is a temporary namespace (U2).** The 11 keys as they are now (`railRowPt` · `plainRowPt` · `userPy` · `userPx` · `userMy` · `railGutter` · `railLineOffset` · `railDotTop` · `fontSize` · `lineHeight` · `waitStripH`) and their defaults are carried over as they are. Only `lineHeight` is `CssNumber`, and `railLineOffset` allows negative values. The chat area will later be split up and rebuilt, and the chat layout will eventually be freely composed as a plugin, so these keys will be replaced — no polishing of key names · grouping · ranges. The `--chat-*` fallback in `theme.css` (for first paint) stays.

## 거부한 대안

- **One command per value.** ADR-0169 already rejected it — the reason is in the first item of that ADR's 「거부한 대안」.
- **Direct file editing + `ui.refresh`.** An outside editor and the app fight over one file. Of the fork ADR-0167 left (split the file · funnel writes to one place), this picks 「쓰기를 한 곳으로」. Abolishing the direct-edit path is a user decision (survey 「0. 결정」).
- **localStorage.** User decision (survey 「0. 결정」 — 「챗 스타일을 localStorage 에서 여기로」). Basis: (no record).
- **Daemon ownership.** Display settings belong to the shell, and the daemon holds only the definitions that go in when it launches an agent — user decision (survey 「0. 결정」).
- **Settings and state in one file.** Splitting the settings people edit from the state the machine writes by purpose is common to peers (survey §2-1 — VS Code · Windows Terminal · JetBrains · Zed · herdr). orca put them in one file and then had to split off a side file because of frequently changing data (survey §4). The user decision also split the two into different files (`settings.json` · `state.json`).
- **Add arbitrary JSON to the declaration macro to carry values (F1).** The type alphabet of the declaration macro has no arbitrary JSON (`command/src/macros.rs:37-47`) — so a value is carried as one canonical string (decision 3).
- **Lay down an empty path-branching function early.** For now all keys go to one file. When another file is needed, it is split only inside the storage layer together with its first key, so call sites are not touched.
- **Importing old values** (`ui-settings.json` · chat-style localStorage). User decision U1 — there is a distributed build (v0.1.0–v0.3.2), but the only user is the user themself, so there is no user data to protect (user judgment 2026-10-02).
- **Redesigning the chat-style keys.** User decision U2 — it is a temporary namespace that will be replaced by the chat-area rewrite and the plugin layout.

## 영향 / 불변식

- **The only ways to write settings are the four commands and the Tauri wrapper that calls the same service.** Direct file editing + `ui.refresh` is not revived as a settings path. A new setting adds one line to the schema table — no command is made per value.
- **Only `settings/store.rs` knows the file's name and location.** If another file is needed, the split happens only inside that module.
- **Because a write is read-modify-write, it does not erase unknown keys** — other keys edited outside the app are not reflected while it runs and are read at the next boot.
- **An unreadable file is overwritten only after its original is kept** — load does not touch it, and the first write sets it aside as `.corrupt-<ms>` and then swaps in the new file (an original over 1 MiB is not set aside and an error is left · the cap is also enforced during the copy — TRD §10 F21).
- **A notification happens after commit · outside the write lock and the state lock · inside the notification-order lock (`rev` order) — the notification port must not block and must not write settings (deadlock).** If the disk write fails (`INTERNAL`), neither memory, `rev`, nor the notification changes.
- **Theme pushing is computed in one place only, `push_effective_themes()`.** That function's theme gate lock is the outermost — while holding it, briefly read and release the settings state lock (`state`) → briefly read and release the `ViewManager` and tree-cell locks → emit per window. A settings write calls the push after releasing all of the settings' locks.
- **It is reachable only while the shell is up** (the same property as `ui.refresh` today).
- **The cost of U2** — since there is no cross-check test, nothing verifies (a) that the `theme.css` fallback equals the table's defaults or (b) that the table's 11 keys equal the frontend `CSS_VAR_BY_KEY`. If the key sets drift apart, `settings.set chat.style.X` answers `changed:true` but nothing changes on screen.
- **The chat rewrite that removes `chat.style.*` also takes on the file cleanup** — a key dropped from the table is an unknown key, so the storage layer keeps it, and `reset` on an unknown key is `NOT_FOUND`, so it cannot be erased by command.
- **ADR-0169's 「받아들인 대가」 (a release build has no way to change chat style) is resolved** — chat style changes through `settings.set`.
- **Code anchor = `// ADR-0265`** — the settings storage layer · the schema table · the command block.
