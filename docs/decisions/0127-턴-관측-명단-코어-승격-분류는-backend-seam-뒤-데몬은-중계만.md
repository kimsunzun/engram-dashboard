# ADR-0127: Promote the turn-observation roster to core, classification behind the backend seam, the daemon only relays

- 상태: 확정 (2026-08-03, basis: user decision — settled the home of classification behind the backend seam, the signal vocabulary stays a single shared one) · 부분 폐기 by ADR-0231 (adding a turn-error signal and a last_end_failed slot)
- 관련: Amends ADR-0110 (the TapHost port of decision 3 and the classification home of decision 4) · Amends ADR-0113 (the wiring home of decision 3) · ADR-0119 decision 4 (home of the fact layer = core — this ADR enforces it) · ADR-0004 (backend knowledge is behind the `backend/` dispatch) · ADR-0104 decision 3 (idle gate = the first consumer of this roster) · ADR-0005 (finalize once) · ADR-0006 (lock order) · ADR-0007 (epoch) · code anchors `crates/engram-dashboard-core/src/agent/turn.rs` · `agent/backend/mod.rs` · `agent/output_core.rs` · Amended by ADR-0231 (adding a turn-error signal and a last_end_failed slot)

## 맥락

The observation roster that holds "is the recipient in a turn right now" lived in the messaging kernel (`busy.rs`). The kernel is nailed down not to depend on workspace crates (ADR-0110 decision 2), so it cannot see the core output stream directly. So the daemon, in the middle, attached a tap to the output, classified output events into turn signals and fed them back to the kernel port (`TurnProbe`) — a round-trip structure.

Because of that one round trip, **the whole attach machinery** came with it: duplicate-subscription prevention · epoch re-verification at the wiring point (`StaleEpoch`) · blocking ghost-tap leaks · failure retry · queueing an attach request at every roster diff (`ws.rs`). This machinery existed not for observation itself but for "carrying the signal across the wall".

Meanwhile the source of the turn-end signal is already in core — `OutputEvent::MessageDone` is produced by the core's backend layer. ADR-0119 decision 4 settled core as the home of the agent fact layer, and ADR-0113 foretold this promotion as "facts = shared / policy = consumer / wiring = daemon". If the roster is moved next to the source, the round trip disappears and the attach machinery loses its reason to exist.

The first implementation put the classifier in core but **outside** the backend seam, and the adversarial review pulled that out as an ADR-0004 violation (rejected alternative b below). The user decided "put it in the isolation place, but the signal enum is shared", which became the current form.

## 결정

1. **Fact layer = owned by core.** `TurnObservations` holds `AgentId → {epoch, 턴 진행 여부, 마지막 신호 시각}` and `AgentManager` owns one. This layer serves only observed facts and has no policy such as thresholds or fallbacks.
2. **Classification = behind core's backend seam.** The mapping from output events to turn signals sits behind `AgentBackend::turn_classifier` + the `backend_for` dispatch, and `backend/claude.rs` owns the claude mapping. **The signal vocabulary (`TurnSignal`) is a single shared definition in core** and is not duplicated per backend (user decision). The trait default = no signal, so a backend that does not define a mapping is silent by default.
3. **Wiring = inside core (`OutputCore::emit`), the daemon only relays.** What the daemon has is only the fact-lookup adapter (`ManagerTurnFacts`) and the delivery of turn end → mail doorbell, and it has neither state nor policy.
4. **Policy = stays in messaging.** "If unknown, idle" · the 30-minute cap · the flush doorbell all stay in the kernel. But the 30-minute cap is implemented as a kernel-internal decision ledger, **without destructively erasing the shared roster** (complying with ADR-0113 decision 2 — other consumers see the same roster).
5. **Cleanup = `OutputCore::finish` (the finalize winner path) erases its own entry.** The reaper's roster cleanup is removed. The call points that erase are **deliberately two** — `finish` (the owner) and the finalize re-check path of `emit` (it takes back what it just put in). That the two take **the same table mutex** is itself the argument that closes the race with a late insertion after termination (see the basis below). If a third caller is added, the causality splits.
6. **The responsibility of raising the epoch at every generation change is borne by one place, the manager's spawn seam.** It is not scattered across call sites — the two guards below all depend on "new generation = new epoch", and if this premise is kept by call-site discipline, it is punctured again every time a new call site appears (it was in fact punctured — see the basis below). The decision axis is **"has this agent ever had a generation in this process"**.
7. **Roster updates follow the emission order (`seq`).** The entry also holds the `seq` it was last applied at, and **a signal with an older `seq` in the same epoch is discarded.** `seq` is assigned by `emit` inside the replay lock, so it is the canonical emission order, and without this rule the order inversion made by `emit`'s two callers (the output pump · the injection thread that emits the input echo) would pin a finished turn as "in progress". The `seq` comparison is done **only when the epoch is the same** — a new generation restarts `seq` from 0, so comparing across generations would make the live generation permanently unobserved.

## 거부한 대안

- **(a) Keep classification in the daemon (the original plan of ADR-0110 decision 4)** — the daemon would have to write into the core roster, so "core owns the facts" blurs and the fact-update path goes outside core. The reason the original plan chose the daemon was *"the messaging kernel must not know the backend"*, but core is the place that knows backends anyway, so that reason does not apply to core.
- **(b) Put classification in core but outside the backend seam** — the first implementation did this and the adversarial review pulled it out. A `Structured` event is a per-backend escape hatch, and if it is seen as "in progress" without distinguishing kinds, then even if codex or gemini leaks one metadata line outside a turn, that agent is pinned as false-busy and mail is blocked until the 30-minute cap releases it. It violates ADR-0004, and because of the location it cannot be fixed without reopening core.
- **(c) Duplicate the signal enum per backend** — rejected by the user. If the vocabulary splits, the consumer has to know which backend it is, and the isolation is inverted.
- **(d) Keep the reaper cleanup** — the reaper is woken only by the reap message `finish` sends, so it is always later and redundant. More importantly, the cleanup must sit at the same point as the `finalized` flag so that the race with a late insertion is closed **by order** (see the basis below).
- **(e) Keep the attach concept in core** — core is already attached to its own output pipe, so "subscription" is meaningless. It would amount to moving the attach machinery into core and planting it, and most of the code reduction of this promotion would vanish.
- **(g) Epoch decision axis = "is it registered in the registry"** — this was the predicate first written and **an existing test caught it red** (`tests/activation.rs::reactivate_after_kill_bumps_epoch` — a profile that was only created and never spawned has no earlier generation even though it is registered). Registration is the axis of name uniqueness, not of generation change. For the same reason **no value that persists on disk** (profile existence · last start time · saved sid) can be the axis — right after boot, in a new process, all of them over-decide. The axis must be "has it had a generation in this process", so the carrier is a field of the profile struct that is **dropped from the storage format** (`#[serde(skip)]` — it shares the profile's life but cannot survive a reboot.
- **(i) Keep the decision marker in a separate table of the manager** — the actual first implementation did this (`Arc<Mutex<HashSet<AgentId>>>`) and the review broke it three ways: if a profile deletion intervenes during a spawn, ① the marker vanishes and the epoch is not raised, or ② the epoch cannot be obtained and **falls to 0**, so the live generation has a lower number than the corpse (every guard runs backwards — the live generation's observations are discarded wholesale), or ③ the marker goes back in after the deletion and an entry that nobody can erase piles up. The root cause is that **the marker's life plays separately from the profile's life**, so instead of adding ordering, the marker was moved into the profile so that it vanishes atomically with the deletion. Lesson: if two states must have the same life, do not tie them with a lock; merge them into one value.
- **(h) Raise it at death (reap)** — considered as an alternative that creates no new state, but **the reaper's disposition guard breaks**: applying the disposition tells the live generation apart by `프로필 epoch == 회수된 epoch`, and if it is raised at death that comparison is permanently off.
- **(f) Leave the order inversion open and let "the last observation decide"** — the pre-promotion structure was like this and was documented so (the old tap also saw the same unordered fan-out). A delay in which parking is not released until the 30-minute cap actually occurs, and since `emit` already assigns an emission-order number inside the replay lock, it could be closed **without adding a lock or an allocation**. The cost was practically 0, so there was no reason to keep parity.

## 근거

- The round trip was needed because of the kernel no-dependency wall (ADR-0110 decision 2), and when the roster comes to core the round trip itself disappears. Measured: removing the attach machinery gave `ws.rs` −592 lines · `busy.rs` −1129 lines.
- The source of the turn-end signal (`OutputEvent::MessageDone`) is already produced by the core backend layer — classification is an extension of that knowledge, not new knowledge.
- ADR-0119 decision 4 settled core as the home of the fact layer. This ADR is its enforcement.
- The basis on which the late-insertion race is closed is not an atomic flag but **the roster mutex**: the mutex puts `emit`'s insertion and `finish`'s cleanup in a total order, and in the order where the cleanup comes first, the cleanup's unlock (release) makes a synchronizes-with relation with the insertion's lock (acquire), so the `finalized` swap happens-before `emit`'s load → the load cannot read `false`. The adversarial review (the concurrency specialist lens) verified both orders.

## 영향 / 불변식

- **Observation scope invariant** — only a session that actually emits turn signals creates an entry (a session with a structured decoder). It is the same set as the pre-promotion attach targets (`Running|Exiting` + structured-output capability).
- **Messaging policy semantics observably the same** — the promotion is a move of ownership, not a change of semantics. If the 30-minute cap erases the shared roster, this decision is violated.
- **The roster lock is a leaf** — the turn-signal callback runs on multiple threads, **including the output pump thread** (the input echo calls `emit` on the injection thread). Keep the critical section minimal and make no external call while holding the lock (ADR-0006).
- **Finalize once invariant (ADR-0005)** — the roster cleanup is placed only on the winner path. If the cleanup is detached from that point, the order proof in the basis above breaks.
- **Both guards depend on "new generation = new epoch"** — the epoch axis discards older generations, and the `seq` axis restarts from 0 when the generation changes. So if an epoch is reused, a dead generation overwrites a live one (high `seq`) or the live generation's observations are discarded wholesale (high epoch). ADR-0007 already wrote this rule but **it was in fact not being kept** — the review found paths in the spawn command and restore branches that did not raise it, and that is why decision 6 unified the seam. **It must not fall to 0 in a situation where the epoch cannot be obtained (e.g. the profile vanishes mid-spawn)** — 0 is the oldest value and flips the order.
- **The decision marker is a field of the profile** — "has it ever had a generation" vanishes only by profile deletion and not by reclaiming (reap) (a revived corpse is exactly the case this rule must catch). If it is placed in a separate table, the lives split and a race arises (rejected alternative (i)).
- **★A deleted AgentId must not be registrable again★** — the marker *recording* (after a successful spawn) is a different critical section from the epoch *decision*, so if a deletion intervenes between them, a live session without a profile remains and the marker is lost. The only reason this is harmless is that **there is no entry to spawn again with a deleted id** — every creation path makes a new uuid, and the spawn command carries only the id and reads the live registry. **If a command is added in which the client sends the profile body, this premise breaks and epoch reuse revives.**
- **There is one place that obtains the epoch axis** — `ProfileRegistry::epoch_for_spawn` (decision · increment · read in one critical section). If the bump is scattered across call sites again, a new path will miss it again.
- **The epoch monotonic rule breaks at `u32` wraparound** — `epoch_for_spawn` is `wrapping_add`, so after `u32::MAX → 0` that agent is permanently unobserved (absorbed into immediate delivery), and it takes restarting one agent 2^32 times to get there. Recorded as unhandled.
- **A missing wiring is blocked by a compile error** — a core without wiring records and emits nothing, so if the wiring is left out that agent is reported as permanently "idle" and mail is injected mid-turn. It is a silent failure, so it is blocked by structure.
