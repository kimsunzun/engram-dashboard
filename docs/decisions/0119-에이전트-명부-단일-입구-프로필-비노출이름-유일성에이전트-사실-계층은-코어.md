# ADR-0119: 에이전트 명부 단일 입구 — 프로필 비노출·이름 유일성·에이전트 사실 계층은 코어

- 상태: 확정 (2026-07-31, 근거: 사용자 결정 — "관리가 2개가 있으면 안 돼", "프로필이 외부로 노출되면 안 되고 내부에서 처리되게")
- 관련: Amends ADR-0113 (공용 시설 거처) — 0113이 열어둔 "코어/데몬측" 갈림길을 이 ADR이 코어로 확정 · ADR-0110(메시징 커널 격리 — 포트 구조 불변) · ADR-0116(입구 3분기 — 판정 소스가 이 명부로 바뀐다) · ADR-0120(이름 유일성 범위) · ADR-0006(락 순서) · ADR-0029(에이전트 호스트 = 데몬) · `crates/engram-dashboard-core/src/agent/manager.rs` · `crates/engram-dashboard-daemon/src/messaging_host.rs`

## 맥락

같은 에이전트가 시스템 안에서 **두 가지 표현**을 갖는다: 살아 있으면 `AgentManager.sessions`의 세션이고, 잠들어 있으면 `ProfileRegistry`의 프로필이다. 어느 쪽도 "에이전트 전원"을 혼자 말하지 못한다.

그래서 "전체 에이전트와 각자의 생사"가 필요한 소비자는 **두 소스를 스스로 합쳐야** 한다. 실제로 그 합성이 지금 데몬 어댑터 안에 손으로 들어가 있다 — `messaging_host.rs::addressing_sources()`가 산 세션 목록을 뜨고, 전체 프로필 목록을 뜨고, id 차집합으로 "잠든 이름"을 만든다. 그 계산은 우편 전용이라 트리는 쓰지 못하고, 프론트는 자기대로 두 배열(산 에이전트 · 프로필)을 받아 `mergeTreeNodes`로 다시 합친다. **같은 합성이 최소 두 곳에 중복돼 있다.**

여기에 더해 프로필이 `manager.profiles()` 접근자로 밖에 열려 있어, 데몬 명령 처리부가 프로필 타입을 직접 만진다(운영 코드 기준 외부 접근 지점 12곳, 그중 10곳이 `connection_core.rs` 한 파일). 프로필은 원래 **껐다 켤 때 복원하기 위한 저장 수단**인데, 잠든 에이전트가 그 안에만 존재하는 탓에 사실상 "존재하는 에이전트 명부" 역할을 겸하게 됐다. 한 타입이 두 일을 하고, 그 사실이 이름에 드러나지 않는다.

이름 유일성(ADR-0115)도 강제할 자리가 없다. 프로필마다 이름이 붙는데 명부가 하나가 아니라 검사 지점이 흩어진다.

## 결정

**1. `AgentManager`가 에이전트 명부의 단일 소유자다.** 명부의 항목은 에이전트 하나이고, 살아 있으면 세션이 붙고 잠들어 있으면 안 붙는다. 프로필 레지스트리는 매니저 **안으로** 들어가고 `manager.profiles()` 접근자는 제거한다. 바깥에서 프로필 타입을 직접 만지는 경로를 없앤다.

**2. 통합 조회 하나를 매니저가 제공한다** — "전체 에이전트 + 각자 살아있음/잠듦". 지금 데몬 어댑터가 손으로 하던 차집합 계산이 이 조회 안으로 들어오고, 어댑터는 포워딩만 남는다. 우편·트리·후속 소비자가 **모두 이 하나를 본다**.

**3. 이름 유일성은 매니저가 강제한다** — 생성·스폰·개명 시 명부 전체(잠든 것 포함)에서 검사한다. 범위·표기 규칙은 ADR-0120.

**4. 에이전트에 관한 "사실" 계층의 자리는 코어다** — 존재·생사가 코어에 있고, 턴 상태(ADR-0113)도 같은 자리에 얹는다. 데몬은 그 사실을 wire로 옮기고 배선하는 역할만 한다.

**5. 조작은 에이전트 어휘로 한다.** 만들기·지우기·이름 변경·계층 이동·띄우기·죽이기 — 프로필이라는 단어가 매니저 경계 밖으로 나오지 않는다. 프로필은 저장 구현 디테일로 내려간다.

**6. `AgentManager`를 타입으로 쪼개지 않는다**(실측 근거는 아래 근거절). 내부를 "빈껍데기 에이전트 하나"로 완전 통합하는 것도 지금은 하지 않는다 — 부르는 쪽이 전부 위 단일 입구를 지나가게 만든 뒤, 필요해지면 무파괴로 바꾼다.

## 거부한 대안

- **현행 유지(두 소스를 소비자가 각자 합침)** — 같은 합성이 데몬 어댑터와 프론트에 중복돼 있고, 두 조회 사이에 spawn·종료·삭제가 끼면 **같은 발송의 두 수신자가 다른 세계를 본다**(ADR-0116 결정 2가 금지한 부류). 소비자가 늘수록 사본이 늘고 한쪽만 고쳐지는 drift가 확정적이다.
- **`AgentManager`를 여러 타입으로 분리**(예: 세션 I/O 전담 타입을 떼어냄) — 실측상 응집도가 깨끗하게 갈리는 선은 I/O 버킷 하나뿐인데(9개 메서드 전원이 `sessions` 필드만 접촉), 그걸 떼면 **같은 락으로 보호되는 맵을 두 타입이 나눠 갖는다**. 지금 ADR-0006 락 규율(Arc clone 후 즉시 해제·중첩 금지)이 한 파일에서 감사 가능한 것이 방어의 핵심인데 그 성질을 잃는다. 얻는 것보다 잃는 것이 크다.
- **내부까지 즉시 통합(`Agent { 정의, 세션: Option<..> }` 단일 맵)** — 개념적으로는 가장 깨끗하지만, 프로필 맵은 **락을 쥔 채 디스크에 저장한다**(동시 변경이 옛 스냅샷으로 디스크를 덮는 경쟁을 닫으려고 그렇게 돼 있다). 세션 맵과 한 락으로 합치면 **디스크 쓰기가 세션 조회를 막는다.** 세션 조회를 타는 것은 봉투 주입(write)·구독·조회 명령 경로다(출력 펌프 자체는 `OutputCore`에 직접 넣으므로 이 조회를 타지 않는다 — 교차검증 지적으로 정정). 우편 배달이 이 조회 위에 있으므로 프로필 저장이 배달을 막는 결합이 생긴다. **한 클래스는 되지만 한 락은 안 된다** — 인터페이스를 먼저 하나로 모으면 내부 통합은 나중에 무파괴로 가능하므로 순서를 뒤로 미룬다.
- **통합 뷰를 데몬에 두기**(현행 `addressing_sources`를 그대로 두고 트리도 그걸 쓰게) — 코어는 데몬을 의존할 수 없으므로(순환) 코어 쪽 소비자는 영영 닿지 못하고, 턴 상태를 코어에 두기로 한 결정 4와도 어긋나 사실 계층이 두 crate로 쪼개진다.
- **프로필 조작 명령까지 없애기** — "프로필 비노출"을 문자 그대로 적용하면 트리의 이름 변경·계층 이동·삭제 경로가 끊긴다. 노출 금지의 취지는 **다른 시스템이 프로필을 판단 근거로 삼지 말라**는 것이므로, 조작은 유지하되 어휘를 에이전트로 바꾼다.
- **프리셋도 함께 분리** — `presets` 필드가 매니저 안에서 아무 버킷도 안 건드리는 완전 분리 상태라 후보로 검토했으나, **사용자 판단으로 제외**: "아직 시스템으로 안 들어가 있음 … 나중에 비대해질 때 분리를 고민하자"(2026-07-31). *코드가 없다는 뜻은 아니다* — 데몬 CRUD와 프론트 컴포넌트는 이미 존재한다(교차검증 확인). "아직 자리를 잡지 않았다"는 판단으로 읽고, 미정착 기능을 지금 옮겨 편입 때 또 만지는 것을 피한다(step-log 적립).

## 근거

- 사용자 결정(2026-07-31): "관리가 2개가 있으면 안 돼. 프론트도 한 개 갖고 관리해야 편리해지지" · "프로필이 외부로 노출되면 안 되고 내부에서 처리되게" · "프로필은 그냥 저장 데이터야 … 이걸 기준으로 뭔가 하면 안 됨" · "처음 시작해보면 전부 비활성이니 프로필하고 교감하는 게 맞네. 근데 결국 UI와 프로필하고의 연결이잖아" · "일단 프리셋 아직 시스템으로 안 들어가 있음 … 나중에 비대해질 때 분리를 고민하자".
- **분리 여부는 실측으로 판정했다**(사용자가 판단을 위임, 2026-07-31). `manager.rs`는 1320줄인데 **운영 코드부의 순수 코드는 574줄**이다 — 주석 421줄·빈 줄, 그리고 230줄짜리 테스트 모듈을 뺀 수치다(교차검증으로 산식 명시). 무거운 로직은 이미 형제 파일에 나가 있다(`output_core.rs` 1303 · `profile.rs` 1477 · `reaper.rs` 323 · `session_tracker.rs` 500). 매니저는 이미 조립부지 만능 객체가 아니다 — "무겁다"는 인상은 주석 밀도와 허브 위치에서 온다.
- **응집도 실측:** I/O 메서드 9개는 전원 `sessions` 필드 하나만 접촉하고 나머지 9개 필드를 전혀 안 본다(유일하게 깨끗한 경계). 생성자 주입된 의존(`status_sink`·`profiles`·`presets`·`tracker`·`control`)은 이미 밖에서 조립돼 들어온다.
- **A1이 얹는 무게는 작고, 빼는 것이 더 크다:** 통합 조회는 데몬 어댑터의 8줄짜리 차집합 계산을 옮기는 것이고 유일성은 검사 하나다. 반면 `profiles()` 제거는 외부 접근 12곳을 통째로 닫는다.
- 락 규율 근거: `ProfileRegistry::mutate`가 "lock을 풀기 전에 save"를 명시적 설계로 삼는다(동시 변경 교차로 디스크가 stale로 덮이는 race를 닫기 위함). 이것이 위 "한 락 금지"의 실측 근거다.

## 영향 / 불변식

- **명부는 하나다** — "전체 에이전트 + 생사"를 만드는 곳은 매니저 한 곳뿐이다. 소비자가 산 목록과 프로필 목록을 각자 떠서 합치면 이 결정 위반이다(그 중복이 이 ADR의 발생 원인).
- **프로필 타입은 매니저 경계를 넘지 않는다** — 판단 근거로 쓰는 것도, 접근자로 꺼내는 것도 금지. 조작은 에이전트 어휘 명령으로만.
- **락 구조 불변** — `sessions`와 프로필 맵은 각자의 락을 유지한다. 하나로 합치면 디스크 쓰기가 세션 조회를 막는다(ADR-0006 규율 위반).
- **★이 통합 조회는 ADR-0116이 기각한 "원자적 단일 뷰"가 아니다★** — 0116은 "입구에서 세션·프로필 원자적 단일 뷰 구성"을 **락 순서 규약을 건드린다는 이유로 기각**하고, 두 조회 사이 경합 잔여분은 TTL 24h로 유계임을 수용했다. 이 ADR은 **조회를 한 입구로 모을 뿐 원자성을 주지 않는다**(두 맵의 락은 그대로 갈라져 있다). 그 TTL 유계 수용은 **그대로 유효하다** — "이제 통합됐으니 원자적으로 만들자"는 0116이 이미 기각한 방향이다.
- **메시징 커널 격리 불변**(ADR-0110) — 커널은 여전히 `AgentManager`를 모른다. 포트 구조는 그대로고 데몬 어댑터가 얇아질 뿐이다.
- **동작 불변이 수용 기준** — 이 슬라이스는 내부 재배치다. 기존 회귀 테스트가 **손대지 않고 그대로 초록**이어야 하며, 새 테스트는 새로 생기는 계약(이름 유일성 · 통합 조회)에만 붙인다.
- **후속 소비자의 자리** — 턴 상태(ADR-0113)는 이 명부 옆 코어 사실 계층에 얹는다. 프론트 단일 목록화는 별도 슬라이스(명령 어휘 변경이 화면에 닿으므로 GUI 실측 필요).
- 미검증(구현 때 확인): 통합 조회가 프로필 fs 접근을 발송 임계 경로에 들이지 않는지(현 `addressing_sources`의 "표시명 있으면 fs 무접근" 단축이 유지돼야 한다).
