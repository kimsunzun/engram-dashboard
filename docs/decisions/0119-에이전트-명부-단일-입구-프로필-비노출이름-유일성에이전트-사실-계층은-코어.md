# ADR-0119: A single entry for the agent registry — profiles not exposed, name uniqueness, the agent fact layer belongs to the core

- 상태: 확정 (2026-07-31, basis: user decision — "관리가 2개가 있으면 안 돼" (there must not be two managements), "프로필이 외부로 노출되면 안 되고 내부에서 처리되게" (profiles must not be exposed outside and must be handled internally))
- 관련: Amends ADR-0113 (home of the shared facility) — this ADR settles the "core/daemon side" fork that 0113 left open as the core · ADR-0110(messaging kernel isolation — the port structure is unchanged) · ADR-0116(3-branch entry — the decision source changes to this registry) · ADR-0120(scope of name uniqueness) · ADR-0006(lock order) · ADR-0029(agent host = daemon) · `crates/engram-dashboard-core/src/agent/manager.rs` · `crates/engram-dashboard-daemon/src/messaging_host.rs`

## 맥락

The same agent has **two representations** inside the system: if alive, it is a session in `AgentManager.sessions`, and if asleep, it is a profile in `ProfileRegistry`. Neither side alone can say "all agents".

So a consumer that needs "all agents and the liveness of each" has to **merge the two sources itself**. In fact, that merge is currently hand-written inside the daemon adapter — `messaging_host.rs::addressing_sources()` takes the live session list, takes the full profile list, and builds the "sleeping names" by an id set difference. That computation is for mail only, so the tree cannot use it, and the frontend receives its own two arrays (live agents · profiles) and merges them again with `mergeTreeNodes`. **The same merge is duplicated in at least two places.**

On top of that, profiles are open to the outside through the `manager.profiles()` accessor, so the daemon command handling touches the profile type directly (12 external access points in production code, 10 of them in the single file `connection_core.rs`). A profile is originally **a storage means for restoring when turned off and on again**, but because a sleeping agent exists only inside it, it has in effect doubled as the "registry of existing agents". One type does two jobs, and that fact does not show in its name.

There is also no place to enforce name uniqueness (ADR-0115). Each profile carries a name, but there is not one registry, so the check points are scattered.

## 결정

**1. `AgentManager` is the single owner of the agent registry.** An item in the registry is one agent: if alive, a session is attached; if asleep, none. The profile registry moves **inside** the manager and the `manager.profiles()` accessor is removed. The paths that touch the profile type directly from outside are eliminated.

**2. The manager provides one unified lookup** — "all agents + whether each is alive/asleep". The set-difference computation that the daemon adapter did by hand moves into this lookup, and the adapter is left with only forwarding. Mail, the tree, and follow-up consumers **all look at this one**.

**3. The manager enforces name uniqueness** — at create, spawn, and rename, it checks across the whole registry (sleeping included). The scope and notation rules are in ADR-0120.

**4. The home of the "fact" layer about agents is the core** — existence and liveness are in the core, and turn state (ADR-0113) is also put in the same place. The daemon only carries those facts onto the wire and does the wiring.

**5. Operations are done in agent vocabulary.** Create, delete, rename, hierarchy move, launch, kill — the word profile does not come out beyond the manager boundary. The profile goes down to a storage implementation detail.

**6. Do not split `AgentManager` by type** (the measured basis is in the rationale section below). Fully merging the internals into "one empty-shell agent" is also not done now — after making all callers pass through the single entry above, change it non-destructively if it becomes needed.

## 거부한 대안

- **Keep as is (consumers merge the two sources each on their own)** — the same merge is duplicated in the daemon adapter and the frontend, and if a spawn, exit, or delete slips in between the two lookups, **the two recipients of the same send see different worlds** (a class that ADR-0116 decision 2 forbade). The more consumers there are, the more copies there are, and drift where only one side is fixed is certain.
- **Split `AgentManager` into several types** (e.g., carve out a type dedicated to session I/O) — by measurement, the only line where cohesion splits cleanly is the one I/O bucket (all 9 methods touch only the `sessions` field), but carving it out makes **two types share a map protected by the same lock**. The core of the defense is that the current ADR-0006 lock discipline (release right after an Arc clone · no nesting) is auditable in one file, and that property would be lost. What is lost is more than what is gained.
- **Merge the internals immediately (`Agent { 정의, 세션: Option<..> }`, a single map)** — conceptually the cleanest, but the profile map **saves to disk while holding the lock** (it is that way to close the race where a concurrent change overwrites the disk with an old snapshot). Merging it with the session map under one lock makes **a disk write block session lookups.** What goes through session lookup is the envelope injection (write), subscribe, and query command paths (the output pump itself goes straight into `OutputCore`, so it does not take this lookup — corrected by a cross-check finding). Since mail delivery sits on this lookup, a coupling arises where profile saving blocks delivery. **One class is fine, but one lock is not** — if the interface is gathered into one first, the internal merge is possible later non-destructively, so the order is deferred.
- **Put the unified view in the daemon** (keep the current `addressing_sources` as is and have the tree use it too) — the core cannot depend on the daemon (a cycle), so a consumer on the core side could never reach it, and it also conflicts with decision 4, which puts turn state in the core, so the fact layer would be split across two crates.
- **Remove even the profile operation commands** — applying "profiles not exposed" literally would cut the tree's rename, hierarchy move, and delete paths. The purpose of the exposure ban is **that other systems must not take profiles as their basis for decisions**, so keep the operations but change the vocabulary to agent.
- **Split off presets too** — the `presets` field is in a fully separated state inside the manager, touching no bucket, so it was considered as a candidate, but it was **excluded by the user's judgment**: "아직 시스템으로 안 들어가 있음 … 나중에 비대해질 때 분리를 고민하자" (it is not yet in the system … let us think about splitting when it grows bloated) (2026-07-31). *That does not mean there is no code* — the daemon CRUD and the frontend component already exist (confirmed by cross-check). Read it as the judgment "it has not settled in yet", avoiding moving a not-yet-settled feature now and touching it again at integration (recorded in the step-log).

## 근거

- User decision (2026-07-31): "관리가 2개가 있으면 안 돼. 프론트도 한 개 갖고 관리해야 편리해지지" (there must not be two managements. The frontend should manage with just one too, so it is convenient) · "프로필이 외부로 노출되면 안 되고 내부에서 처리되게" (profiles must not be exposed outside and must be handled internally) · "프로필은 그냥 저장 데이터야 … 이걸 기준으로 뭔가 하면 안 됨" (a profile is just stored data … we must not do anything based on it) · "처음 시작해보면 전부 비활성이니 프로필하고 교감하는 게 맞네. 근데 결국 UI와 프로필하고의 연결이잖아" (at first start everything is inactive, so interacting with profiles is right. But in the end it is the connection between the UI and the profiles) · "일단 프리셋 아직 시스템으로 안 들어가 있음 … 나중에 비대해질 때 분리를 고민하자" (for now, presets are not yet in the system … let us think about splitting when it grows bloated).
- **Whether to split was decided by measurement** (the user delegated the judgment, 2026-07-31). `manager.rs` is 1320 lines, but **the pure code of the production section is 574 lines** — the figure after removing 421 lines of comments and blank lines, and the 230-line test module (the formula stated through cross-check). The heavy logic is already in sibling files (`output_core.rs` 1303 · `profile.rs` 1477 · `reaper.rs` 323 · `session_tracker.rs` 500). The manager is already an assembler, not an omnipotent object — the impression of "heavy" comes from comment density and its hub position.
- **Cohesion measurement:** the 9 I/O methods all touch only the single `sessions` field and look at none of the other 9 fields (the only clean boundary). The constructor-injected dependencies (`status_sink` · `profiles` · `presets` · `tracker` · `control`) are already assembled outside and brought in.
- **The weight A1 adds is small, and what it takes away is larger:** the unified lookup moves the 8-line set-difference computation of the daemon adapter, and uniqueness is a single check. On the other hand, removing `profiles()` closes all 12 external access points at once.
- Lock discipline basis: `ProfileRegistry::mutate` takes "save before releasing the lock" as an explicit design (to close the race where interleaved concurrent changes overwrite the disk with stale data). This is the measured basis for the "no single lock" above.

## 영향 / 불변식

- **There is one registry** — the only place that builds "all agents + liveness" is the manager. If a consumer takes the live list and the profile list on its own and merges them, it violates this decision (that duplication is what caused this ADR).
- **The profile type does not cross the manager boundary** — both using it as a basis for decisions and pulling it out through an accessor are forbidden. Operations are only by agent-vocabulary commands.
- **Lock structure unchanged** — `sessions` and the profile map each keep their own lock. Merging them into one makes disk writes block session lookups (violating the ADR-0006 discipline).
- **★This unified lookup is not the "atomic single view" that ADR-0116 rejected★** — 0116 **rejected "building an atomic single view of sessions and profiles at the entry" on the ground that it touches the lock-order convention**, and accepted that the race leftovers between the two lookups are bounded by the TTL 24h. This ADR **only gathers the lookup into one entry and does not give atomicity** (the locks of the two maps stay split). That acceptance of TTL boundedness **remains valid** — "now that it is unified, let us make it atomic" is a direction 0116 already rejected.
- **Messaging kernel isolation unchanged** (ADR-0110) — the kernel still does not know `AgentManager`. The port structure is as it was, and the daemon adapter only gets thinner.
- **The acceptance criterion is unchanged behavior** — this slice is an internal rearrangement. The existing regression tests must stay **green untouched**, and new tests are attached only to the newly arising contracts (name uniqueness · the unified lookup).
- **Place for follow-up consumers** — turn state (ADR-0113) is put in the core fact layer next to this registry. Making the frontend a single list is a separate slice (the command vocabulary change reaches the screen, so GUI measurement is needed).
- Unverified (to confirm at implementation): whether the unified lookup avoids bringing profile fs access into the send critical path (the shortcut "no fs access if a display name exists" of the current `addressing_sources` must be kept).
