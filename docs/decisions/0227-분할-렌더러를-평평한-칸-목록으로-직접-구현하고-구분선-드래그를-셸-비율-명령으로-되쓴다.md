# ADR-0227: Implement the split renderer directly as a flat slot list, and write divider drags back through a shell ratio command

- 상태: 확정 (2026-09-24, basis: user decision (renderer D · D1~D6) + peer surveys `docs/research/split-layout-library-survey-2026-09-24.md` · `docs/research/split-resize-policy-survey-2026-09-24.md` + TRD adversarial review PASS in 3 rounds · R11 user decision 2026-09-24) · 부분 폐기 by ADR-0260 (the ratio limit 0.1~0.9 in decision 2 and in the impact section)
- 관련: Amends ADR-0223 (the Allotment key in decision 2 and the promotion remount clause in the impact section) · Amends ADR-0068 (decision 3 and the rejected alternative of backend-projected px, and the measured-pixel and minimum-slot clauses in the impact section) · ADR-0035 (layout authority = shell) · ADR-0056 (tab keep-alive — the flat structure lives only inside one view) · ADR-0148 (preserving the dead agent's screen) · ADR-0012 (isolation harness) · TRD `docs/process/S21-flat-split-renderer/trd.md` · `src/components/layout/ViewLayoutRenderer.tsx` · `src-tauri/src/layout/` (`types.rs` · `tree.rs` · `manager.rs` · `apply.rs` · `spatial.rs` · `commands.rs`) · Amends ADR-0140 (the allotment-mapping truth boundary in the impact section) · Amends ADR-0168 (decision 7, the allotment sash tokens) · Amended by ADR-0260 (the ratio limit 0.1~0.9 in decision 2 and in the impact section)

## 맥락

The split tree of one view (split `id` · `dir` · `ratio` · two children) is owned by the shell, and the screen draws a snapshot (ADR-0035). The renderer drew that tree as a **recursive component** — a structure with one `allotment` per split (`ViewLayoutRenderer.tsx`).

Three kinds of problems kept recurring in this shape.

1. **Squashed first frame** — a newly mounted `allotment` draws one frame before it decides the slot sizes (upstream unresolved #820). It was blocked with the ratio `defaultSizes`, but that is static analysis only and there is no measurement on screen (library survey F1 · F2).
2. **Remount of surviving slots on close or promotion** — when a sibling subtree is promoted into its parent's place, the React ancestor path changes and the whole subtree is mounted again. The terminal inside it re-subscribes, and the dead agent's screen that ADR-0148 preserved disappears (ADR-0223 「영향」 · the renderer comment 「알려진 한계 ①」).
3. **Direction is decided only at mount** — so the split instance had to be keyed by `${id}:${dir}` and built anew (ADR-0223 decision 2).

Tabs already have no remount (ADR-0056). So the problem is **inside one view**.

Separately, a size changed by dragging a divider was written back nowhere. The sources of this scope limit are:
- `docs/process/step-log.md:776` — unresolved ① of that slice.
- `:2506` — 「드래그 크기 되쓰기는 나중(사용자 결정)」.
- The parenthesis in ADR-0223 decision 2 — 「드래그 크기는 백엔드에 안 돌아간다」.
- The renderer comment `ViewLayoutRenderer.tsx:291` — this comment points to ADR-0063, but ADR-0063's body has no such clause.

The shell knew only the ratio 0.5, and the LLM had no way to change sizes (CLAUDE.md 「LLM-우선 제어」).

## 결정

1. **Renderer = a flat slot list + absolute placement by rectangles the shell computes. Implement it directly and bring in no new library** (library survey option D).
   - All slots of a view are drawn as **a slot-id-keyed list under one parent**. The order is slot id order.
   - Dividers are an **overlay** drawn after the slots in split id order. They take no layout space.
   - Positions are the normalized bounding rectangles the shell puts in the snapshot. The screen does not recompute the tree geometry.
   - Close, split, promotion, and direction change neither remount surviving slots nor move them in the DOM.
2. **A dragged size is written back to the shell (D1).**
   - During a drag the screen previews by split id, and on release it calls the ratio command **once**.
   - The shell clamps the ratio to 0.1~0.9, writes it to the tree, and notifies as usual.
   - The LLM uses the same command. For concurrent writes, the last write in shell arrival order wins.
3. **The shell holds the pixel geometry of the slots (D1+).**
   - The window canvas px is reported only when it changes and is kept in the window entry.
   - The fixed UI metrics (measured frame border · minimum slot px) are received once at initialization.
   - Slot px = canvas × normalized rectangle. The shell does not ask the UI, and bakes in no px constants.
4. **Minimum slot = each of the two sides (whole subtrees) of the dragged split is 30px (D2).**
   - During a drag the screen enforces it (D2 — user decision).
   - It is accepted that dragging an outer divider can push a deep slot below 30px (D2).
   - The shell also clamps under the same condition when it knows the canvas and metrics (the values are what the screen sent). This is an **internal decision main added in the TRD review** — it is not the user's D2. It is of the same nature as the representability rule (see 「영향」 below).
5. **There is no keyboard adjustment of dividers (D3).** Adjustment is only by mouse (human) and the ratio command (AI).
   - No relative increment command is added either. The user chose 「A 안(추가 명령 없음)」: 「사실 AI에게도 크게 필요한 기능은아닌데 어쨋든 키보드로는 필요없고 마우스 AI 가 되도록해. A안이 되는건가?」.
6. **There is no minimum window size (D4).** Slots shrink proportionally all the way down, and the screen always equals the shell ratio.
7. **Double-clicking a divider = 50:50 through the same command (D5).**
8. **DOM order = slot id order (D6).** Existing slot containers do not move in the DOM — only the position values change, new slots are inserted, and closed slots are removed. It is accepted that the Tab and screen-reader order differs from the screen order.
9. **Splits that make a small slot are also allowed (R11).** The split proceeds even if the resulting slot is below `min_pane_px`. The only thing blocked is the extreme where one side reaches a representable width of 0 — the f64 representability rule, `SplitTooDeep`. Source: user — 「0이되는 극단적인 상황만 막으면 될것같아 일단은」.

## 영향 / 불변식

**Renderer (screen)**

- ★**Slots are a slot-id-keyed list under one parent, in slot id order. Dividers are keyed by split id, in split id order**★ — if it is changed to tree pre-order, then during an LLM reconstruction the divider node holding the pointer capture is moved and `lostpointercapture` fires. If slots are nested in a tree shape, the remount that decision 1 solved comes back.
- **No `transform` or `contain` on a slot ancestor** — `SlotContextMenu` is `position:fixed`, so the coordinate system would break.
- **Outer frame = the rectangle as is + `data-slot-id` + click and right-click handlers, no border. Inner `data-slot-border` = border · centering · content.** If the border is put back on the frame, it overlaps its neighbors in 0~1px slots. If the handlers are moved inside, the cdp recipe and tests miss.
- **The screen does not compute tree geometry** — it draws the shell rectangles, and only the drag preview linearly remaps the shell rectangles.
- **The direction-mapping truth boundary of ADR-0140 moves.** The old place was the renderer's allotment mapping `vertical={dir === 'top_bottom'}` (ADR-0140 「영향」). The new place is one spot in the shell's `geometry.rs` — `left_right` → x-axis split (a on the left), `top_bottom` → y-axis split (a on top). If this is flipped, then even when the menu, types, and tests agree, the screen and the shell neighbor computation are both reversed together.
- **ADR-0168 decision 7 (allotment sash tokens) loses its subject.** The `--separator-border` · `--focus-border` overrides at `src/index.css:33-40` are removed together with allotment. The new divider uses the theme tokens directly — line `var(--border)`, hover and drag `var(--accent)` — so it follows all three themes as they are.
- **ADR-0148 memory and menu state live in the slot component keyed by slot id** — they survive after split, close, and promotion. A popout is still remounted because it has a new slot id and a new webview.

**Shell**

- **The ratio is `f64`, the share of the a-side (left/top) slot, 0.1~0.9.** The limits go to the screen through the snapshot (`ratio_min/max`).
- **Shell px minimum clamp** (an internal decision main added in the TRD review — the user's D2 is on the screen drag side): when the canvas and metrics are known, `split.setRatio` clamps the two sides of the dragged split to at least `min_pane_px`. If either of the two is unknown, it clamps only the ratio.
- **Representability rule** (an internal decision main made in the TRD review):
  - A split whose new boundary does not lie strictly inside the target box is rejected with `SplitTooDeep`.
  - A ratio write that **newly** creates a zero-area leaf is `TooSmall` and makes no change.
  - `spatial.rs` decides by exact adjacency. A zero-area leaf drops out of the neighbor and corner tokens and stays in the order roster.
  - Without this rule, neighbors and order go silently wrong in deep chains (ADR-0068 「영향」:43 ①②).
- **Result of the ratio command = `outcome` (`Applied` · `Unchanged` · `TooSmall`).** The returned version is the version of the snapshot the apply service took **inside the same lock**. If the global counter is read again, the screen preview waits for the wrong version.
- **The canvas and metrics are kept in `WindowTabs`.**
  - The report commands do not take the window label as an argument (`tauri::Window`).
  - They are not put on the command bus (it is measurement, not control). They neither raise the version nor notify.
  - A zero-size canvas is ignored, and the metrics are range-checked.
  - The source of truth of `min_pane_px` is the screen.

**New surface**

- Bus `split.setRatio {view_id, split_id, ratio} → {ratio, outcome}` · `split.list {view_id} → splits[{split_id, dir, ratio, a_slots, b_slots}]`. `catalog_version` 7 → 8. The roster golden is in `src-tauri/tests/layout_commands.rs`.
- Tauri `set_split_ratio` · `report_window_canvas` · `report_ui_metrics`.
- Snapshot `slot_rects` · `split_rects` · `ratio_min` · `ratio_max`. The new bindings `SlotRect.ts` · `SplitRect.ts` · `SplitRatioApplied.ts` are guarded by the CI bindings sync gate.

**Relation to older decisions**

- **It deliberately departs from the measured-pixel clauses of ADR-0068 decision 3 and 「영향」 (`:21` · `:41`).**
  - Normalized coordinates are carried in the snapshot, and the shell computes px.
  - The measurement is not a per-slot rect but one canvas pair per window, and it is a **latest value with no version**.
  - The authority is still the shell tree. The measurement is a single multiplying factor, so it is not a dual authority.
  - The possible delay is a 100ms debounce, and the current consumer (the px minimum clamp) tolerates an error of that size.
  - When px is exposed to the LLM, the version is checked again.
- **It revives the alternative ADR-0068 rejected, 「백엔드 투영 물리 px」 (`:26`).**
  - The reason for the rejection then was 「정확하려면 ViewManager 가 gutter·sash·min-size·collapse 까지 모델링해야 해 렌더 엔진 로직 중복·drift 위험」.
  - In this design that reason does not hold. The renderer draws the shell's rectangles **as they are** (the screen computes no geometry of its own). Dividers are an overlay that takes no space, so there is no need to model gutter or sash. The border thickness is not assumed; the screen's measured value is received. There is no collapse.
  - So the difference between shell px and screen px is only rounding (at most 1 CSS px per boundary).
- **ADR-0068 `:28` (「정규화 논리좌표 ≠ 실제 렌더 크기 — sash·min-size·border 때문에」) is resolved by structure.** The screen draws the shell rectangles as they are, the sash is a zero-space overlay, and the border is measured. Min-size only limits the shell ratio itself and does not detach rendering from the ratio.
- **ADR-0068 「영향」:43 (resize commands enforce a UX minimum slot size) → REPLACED — not satisfied.**
  - The minimum-size enforcement applies only to **the two sides of the dragged split**. A deep slot going below 30px is accepted (D2), and splits that make a slot below 30px are also allowed (R11).
  - Defects ① and ② that `:43` warned about are fixed not by the minimum size but by **exact adjacency**. `EPS` and `edge_eq` in `spatial.rs` are removed.
- **ADR-0223 decision 2** (Allotment key) and **the promotion remount clause in 「영향」** — discarded. The discard stamp is already in the ADR-0223 header (`fad7a7f`). This time its scope was widened to the promotion remount clause in 「영향」 — the ADR body is not overwritten (`docs/decisions/README.md:13`). Decision 1 (split id) stays and is used as the divider and preview key.
- **The scope limit on drag write-back** — resolved by decision 2. The source of the limit is `step-log.md:776` · `:2506` and the parenthesis in ADR-0223 decision 2, written in 「맥락」. It is not ADR-0063 — the ADR-0063 citation in the renderer comment `ViewLayoutRenderer.tsx:291` is wrong, and that comment disappears with the renderer replacement.
