## 맥락

뷰 하나의 분할 트리(분할 `id`·`dir`·`ratio`·두 자식)는 셸이 소유하고 화면은 스냅샷을 그린다(ADR-0035). 렌더러는 그 트리를 **재귀 컴포넌트**로 그렸다 — 분할마다 `allotment` 하나를 두는 구조다(`ViewLayoutRenderer.tsx`).

이 모양에서 세 부류가 반복됐다.

1. **쭈그러진 첫 프레임** — 새로 마운트된 `allotment` 가 칸 크기를 정하기 전에 한 프레임을 그린다(상류 미해결 #820). 비율 `defaultSizes` 로 막았지만 정적 분석까지이고 화면 실측은 없다(라이브러리 조사 F1·F2).
2. **닫기·승격 때 살아남은 칸의 재마운트** — 형제 서브트리가 부모 자리로 올라가면 React 조상 경로가 바뀌어 통째로 다시 마운트된다. 그 안의 터미널은 재구독하고, ADR-0148 이 보존하던 죽은 에이전트 화면은 사라진다(ADR-0223 「영향」 · 렌더러 주석 「알려진 한계 ①」).
3. **방향이 마운트 때만 정해진다** — 그래서 분할 인스턴스를 `${id}:${dir}` 로 key 해 새로 지어야 했다(ADR-0223 결정 2).

탭은 이미 재마운트가 없다(ADR-0056). 그러니 문제는 **뷰 하나 안**이다.

별개로, 구분선을 끌어 바꾼 크기는 어디에도 되써지지 않았다. 이 범위 제한의 출처는 다음과 같다.
- `docs/process/step-log.md:776` — 그 슬라이스의 미해결 ①.
- `:2506` — 「드래그 크기 되쓰기는 나중(사용자 결정)」.
- ADR-0223 결정 2 의 괄호 — 「드래그 크기는 백엔드에 안 돌아간다」.
- 렌더러 주석 `ViewLayoutRenderer.tsx:291` — 이 주석은 ADR-0063 을 가리키지만, ADR-0063 본문엔 그런 조항이 없다.

셸은 비율 0.5 만 알고, LLM 은 크기를 바꿀 길이 없었다(CLAUDE.md 「LLM-우선 제어」).

## 결정

1. **렌더러 = 평평한 칸 목록 + 셸이 계산한 사각형으로 절대 배치. 직접 구현하고 새 라이브러리는 들이지 않는다**(라이브러리 조사 선택지 D).
   - 한 뷰의 칸 전부를 **한 부모 아래 slot id key 목록**으로 그린다. 순서는 slot id 순이다.
   - 구분선은 칸 뒤에 split id 순으로 그리는 **오버레이**다. 레이아웃 공간을 먹지 않는다.
   - 위치는 셸이 스냅샷에 싣는 정규화 경계 사각형이다. 화면은 트리 기하를 다시 계산하지 않는다.
   - 닫기·분할·승격·방향 전환이 살아남은 칸을 재마운트하지도 DOM 에서 옮기지도 않는다.
2. **드래그한 크기는 셸에 되쓴다(D1).**
   - 드래그 중에는 화면이 split id 로 미리보기를 하고, 뗄 때 비율 명령을 **한 번** 부른다.
   - 셸은 비율을 0.1~0.9 로 클램프해 트리에 쓰고 평소처럼 통지한다.
   - LLM 도 같은 명령을 쓴다. 동시 쓰기는 셸 도착 순서의 마지막 쓰기가 이긴다.
3. **셸이 칸의 픽셀 기하를 가진다(D1+).**
   - 창 캔버스 px 는 바뀔 때만 보고받아 창 항목에 둔다.
   - UI 고정 지표(틀 테두리 실측 · 최소 칸 px)는 초기화 때 한 번 받는다.
   - 칸 px = 캔버스 × 정규화 사각형. 셸은 UI 에 묻지 않고, px 상수를 박지 않는다.
4. **최소 칸 = 끌린 분할의 두 쪽(서브트리 통째)이 각각 30px(D2).**
   - 드래그 중엔 화면이 강제한다(D2 — 사용자 결정).
   - 바깥 구분선을 끌어 깊은 칸이 30px 아래로 가는 것은 감수한다(D2).
   - 셸도 캔버스·지표를 알 때 같은 조건으로 클램프한다(값은 화면이 보낸 것). 이것은 **TRD 리뷰에서 메인이 더한 내부 결정**이다 — 사용자 D2 가 아니다. 표현 가능성 규칙과 같은 성격이다(아래 「영향」).
5. **구분선 키보드 조절은 없다(D3).** 조절은 마우스(사람)와 비율 명령(AI)뿐이다.
   - 상대 증감 명령도 두지 않는다. 사용자가 「A 안(추가 명령 없음)」을 골랐다: 「사실 AI에게도 크게 필요한 기능은아닌데 어쨋든 키보드로는 필요없고 마우스 AI 가 되도록해. A안이 되는건가?」.
6. **창 최소 크기는 없다(D4).** 칸은 끝까지 비례로 줄고, 화면은 늘 셸 비율과 같다.
7. **구분선 더블클릭 = 같은 명령으로 50:50(D5).**
8. **DOM 순서 = slot id 순(D6).** 기존 칸 컨테이너는 DOM 에서 움직이지 않는다 — 위치 값만 바뀌고, 새 칸은 끼워 넣고, 닫힌 칸은 뺀다. Tab·스크린리더 순서가 화면 순서와 다른 것은 감수한다.
9. **작은 칸을 만드는 분할도 허용한다(R11).** 결과 칸이 `min_pane_px` 미만이어도 분할한다. 막는 것은 한쪽이 표현 가능한 폭 0 이 되는 극단뿐이다 — f64 표현 가능성 규칙, `SplitTooDeep`. 출처: 사용자 — 「0이되는 극단적인 상황만 막으면 될것같아 일단은」.

  - **재론 조건:** 작은 칸 조작 불가가 실제 문제로 보고되거나, LLM 반복 쪼개기가 관측될 때.
  - **재론 때의 피어 증거(메인 코드 확인):**
    - tmux 는 「no space for a new pane」으로 분할을 거절한다(`tmux/layout.c:1410`, `cmd-split-window.c:153`).
    - zellij 는 명시 분할에서 칸이 최소 크기(`MIN_TERMINAL_WIDTH`·`MIN_TERMINAL_HEIGHT` = 5 — `zellij-server/src/tab/mod.rs:154-155`)의 2 배에 못 미치면 거절한다(`zellij-server/src/panes/tiled_panes/mod.rs:697-747` 의 `can_split_pane_*` — 로컬 클론 `bf8d23a` 확인).
    - 참고: zellij 의 자동 배치(새 칸 자리 찾기 `find_room_for_new_pane`)도 같은 부류의 조건을 쓴다(`tiled_pane_grid.rs:1374-1377`). 명시 분할의 근거는 아니다.
- **D6 — 화면 순 DOM**
  - 기존 컨테이너가 바뀌지 않는 게 좋다. 출처: 사용자 — 「기존 컨테이너가 변경이 되지 않는게 좋지」.
  - 뒷받침(정책 조사 F6):
    - orca `pane-split-scroll.ts:83-93` 원문은 두 가지를 적는다. 분할 때 터미널 컨테이너를 옮기면 브라우저가 `scrollTop` 을 지운다. 그리고 Chromium 이 한도 근처에서 가장 오래된 WebGL 컨텍스트를 `contextlost` 없이 죽이므로, orca 는 옮기기 **전에 미리** WebGL 을 해제했다가 다시 붙인다.
    - DOM 이동이 포커스를 잃게 한다는 것은 Chrome `moveBefore()` 블로그가 출처다(정책 조사 F6 경유).
  - 성격: **중**(피어 코드 주석 + 브라우저 벤더 글 — 우리 실측 없음).

## 영향 / 불변식

**렌더러(화면)**

- ★**칸은 한 부모 아래 slot id key 목록이고 slot id 순이다. 구분선은 split id key·split id 순이다**★ — 트리 전위 순으로 바꾸면 LLM 재구성 때 포인터 캡처를 쥔 구분선 노드가 옮겨져 `lostpointercapture` 가 난다. 칸을 트리 모양으로 중첩하면 결정 1 이 푼 재마운트가 되살아난다.
- **칸 조상에 `transform`·`contain` 금지** — `SlotContextMenu` 가 `position:fixed` 라 좌표계가 깨진다.
- **바깥 틀 = 사각형 그대로 + `data-slot-id` + 클릭·우클릭 핸들러, 테두리 없음. 안쪽 `data-slot-border` = 테두리·중앙정렬·내용.** 틀에 테두리를 되돌리면 0~1px 칸에서 이웃과 겹친다. 핸들러를 안쪽으로 옮기면 cdp 레시피와 테스트가 빗나간다.
- **화면은 트리 기하를 계산하지 않는다** — 셸 사각형을 그리고, 드래그 미리보기만 셸 사각형을 선형 재사상한다.
- **ADR-0140 의 방향 매핑 진실 경계가 옮겨 간다.** 옛 자리는 렌더러의 allotment 매핑 `vertical={dir === 'top_bottom'}`(ADR-0140 「영향」)이었다. 새 자리는 셸 `geometry.rs` 의 한 곳 — `left_right` → x 축 분할(a 왼쪽), `top_bottom` → y 축 분할(a 위)이다. 여기가 뒤집히면 메뉴·타입·테스트가 맞아도 화면과 셸 이웃 계산이 함께 반대가 된다.
- **ADR-0168 결정 7(allotment sash 토큰)은 대상이 사라진다.** `src/index.css:33-40` 의 `--separator-border`·`--focus-border` 덮어쓰기는 allotment 와 함께 걷는다. 새 구분선은 테마 토큰을 직접 쓴다 — 선 `var(--border)`, 호버·드래그 `var(--accent)` — 그래서 세 테마를 그대로 따른다.
- **ADR-0148 기억·메뉴 상태는 slot id key 인 칸 컴포넌트에 산다** — 분할·닫기·승격 뒤에도 살아남는다. 팝아웃은 새 slot id·새 웹뷰라 여전히 재마운트된다.

**셸**

- **비율은 `f64`, a 쪽(왼쪽/위) 칸의 몫, 0.1~0.9.** 한계는 스냅샷(`ratio_min/max`)으로 화면에 간다.
- **셸 px 최소 클램프**(TRD 리뷰에서 메인이 더한 내부 결정 — 사용자 D2 는 화면 드래그 쪽이다): 캔버스·지표를 알면 `split.setRatio` 가 끌린 분할의 두 쪽을 `min_pane_px` 이상으로 클램프한다. 둘 중 하나라도 모르면 비율 클램프만 한다.
- **표현 가능성 규칙**(TRD 리뷰에서 메인이 정한 내부 결정):
  - 새 경계가 대상 상자 안에 엄격히 들지 않는 분할은 `SplitTooDeep` 로 거절한다.
  - **새로** 면적 0 잎을 만드는 비율 쓰기는 `TooSmall`·무변경이다.
  - `spatial.rs` 는 정확 인접으로 판정한다. 면적 0 잎은 이웃·모서리 토큰에서 빠지고 순서 명단에는 남는다.
  - 이 규칙을 빼면 깊은 사슬에서 이웃·순서가 조용히 틀린다(ADR-0068 「영향」:43 ①②).
- **비율 명령의 결과 = `outcome`(`Applied`·`Unchanged`·`TooSmall`).** 반환 version 은 적용 서비스가 **같은 락 안에서 뜬 스냅샷**의 version 이다. 전역 카운터를 다시 읽으면 화면 미리보기가 엉뚱한 version 을 기다린다.
- **캔버스·지표는 `WindowTabs` 에 둔다.**
  - 보고 명령은 창 label 을 인자로 받지 않는다(`tauri::Window`).
  - 명령 버스에 올리지 않는다(측정이지 제어가 아니다). version 을 올리지도 통지하지도 않는다.
  - 0 크기 캔버스는 무시하고, 지표는 범위를 검사한다.
  - `min_pane_px` 의 정본은 화면이다.

**새 표면**

- 버스 `split.setRatio {view_id, split_id, ratio} → {ratio, outcome}` · `split.list {view_id} → splits[{split_id, dir, ratio, a_slots, b_slots}]`. `catalog_version` 7 → 8. 명단 골든은 `src-tauri/tests/layout_commands.rs`.
- Tauri `set_split_ratio` · `report_window_canvas` · `report_ui_metrics`.
- 스냅샷 `slot_rects` · `split_rects` · `ratio_min` · `ratio_max`. 새 바인딩 `SlotRect.ts`·`SplitRect.ts`·`SplitRatioApplied.ts` 는 CI 바인딩 sync 게이트가 지킨다.

**옛 결정과의 관계**

- **ADR-0068 결정 3 과 「영향」의 실측 픽셀 조항(`:21`·`:41`)에서 의도적으로 벗어난다.**
  - 정규화 좌표가 스냅샷에 실리고, 셸이 px 를 계산한다.
  - 실측은 칸별 rect 가 아니라 창당 캔버스 한 쌍이고, **버전 없는 최신값**이다.
  - 권위는 여전히 셸 트리다. 실측은 곱하는 배율 하나라 이중 권위가 아니다.
  - 늦을 수 있는 폭은 디바운스 100ms 이고, 지금 소비자(px 최소 클램프)가 그만큼의 오차를 견딘다.
  - px 를 LLM 에게 내보낼 때 버전을 다시 본다.
- **ADR-0068 이 거부한 대안 「백엔드 투영 물리 px」(`:26`)를 되살린다.**
  - 그때 거부한 사유는 「정확하려면 ViewManager 가 gutter·sash·min-size·collapse 까지 모델링해야 해 렌더 엔진 로직 중복·drift 위험」이었다.
  - 이 설계에선 그 사유가 성립하지 않는다. 렌더러가 셸의 사각형을 **그대로** 그린다(화면이 기하를 따로 계산하지 않는다). 구분선은 공간을 먹지 않는 오버레이라 gutter·sash 모델링이 필요 없다. 테두리 두께는 가정하지 않고 화면이 잰 값을 받는다. 접힘(collapse)은 없다.
  - 그래서 셸 px 와 화면 px 의 차이는 반올림(경계당 최대 1 CSS px)뿐이다.
- **ADR-0068 `:28`(「정규화 논리좌표 ≠ 실제 렌더 크기 — sash·min-size·border 때문에」)은 구조로 해소된다.** 화면이 셸 사각형을 그대로 그리고, sash 는 공간 0 오버레이, 테두리는 실측이다. min-size 는 셸 비율 자체를 제한할 뿐 렌더를 비율에서 떼어 놓지 않는다.
- **ADR-0068 「영향」:43(리사이즈 명령은 UX 최소 칸 크기 강제) → 대체(REPLACED)한다 — 충족이 아니다.**
  - 최소 크기 강제는 **끌린 분할의 두 쪽**에만 걸린다. 깊은 칸이 30px 아래로 가는 것은 감수했고(D2), 30px 미만을 만드는 분할도 허용한다(R11).
  - `:43` 이 경고한 결함 ①②는 최소 크기가 아니라 **정확 인접**으로 고친다. `spatial.rs` 의 `EPS`·`edge_eq` 는 걷는다.
- **ADR-0223 결정 2**(Allotment key)와 **「영향」의 승격 재마운트 조항** — 폐기. 폐기 도장은 ADR-0223 헤더에 이미 박혔다(`fad7a7f`). 이번에 그 범위를 「영향」의 승격 재마운트 조항까지 넓혔다 — ADR 본문은 덮어쓰지 않는다(`docs/decisions/README.md:13`). 결정 1(split id)은 유지하고, 구분선·미리보기 key 로 쓴다.
- **드래그 되쓰기 범위 제한** — 결정 2 로 해소한다. 제한의 출처는 「맥락」에 적은 `step-log.md:776`·`:2506`·ADR-0223 결정 2 괄호다. ADR-0063 이 아니다 — 렌더러 주석 `ViewLayoutRenderer.tsx:291` 의 ADR-0063 인용은 잘못이고, 그 주석은 렌더러 교체와 함께 사라진다.
