# ADR-0202: Do not erase activation evidence — neither the stored handle nor the failure record

- 상태: 확정 (2026-09-15, basis: user decision + independent findings by two reviewers + mutation verification)
- 관련: ADR-0201 · ADR-0082(keep the failure cause so an LLM can analyze·escalate) · ADR-0185(the issuer of the sid is neutral) · ADR-0173(if running, "running" wins) · `profile.rs::upsert_preserving_hierarchy` · `manager.rs::note_activation_result`

## 맥락

One principle was broken in two places separately. **Overwriting the ground to go back to.**

1. **The stored handle is destroyed.** The helper that re-seats a profile preserved only four fields (`parent_id`·`display_name`·`epoch`·`last_failure`) and `backend_session_id` was not among them. So a thread id that arrived after the caller took a snapshot was **not ignored but overwritten and written to disk.** The next resume opens the old thread.
2. **The failure record is erased by a success decision.** When activation was decided a success, it cleared `last_failure`. But that success decision itself could be wrong (the context of ADR-0201), and at the moment it was wrong, **the clue for finding the cause disappeared along with it.**

The two are the same mistake. One erases 「무엇을 이어받을지」 (“what to resume”), the other 「지난번에 왜 실패했는지」 (“why it failed last time”).

## 결정

**The activation path does not erase evidence.**

- **Preserve the stored handle.** Put `backend_session_id` into the preserved set of profile re-registration. **Put its history (`old_session_ids`) in too** — the two are updated as a pair in the same action, so if only one is kept, the displaced handle is lost (half of the loss we meant to preserve against).
- **A success does not erase the failure record.** The question the record answers is 「지난 활성화 시도가 어떻게 끝났나」 (“how did the last activation attempt end”), and 「지금 돌고 있다」 (“it is running now”) is not an answer to that question. The only things that invalidate it are **when the next failure overwrites it** and **when the profile itself disappears**.

User ground (2026-09-15, verbatim): if it is overwritten, there is no way to restore it later in case the reason turned out to be something else.

## 거부한 대안

- **Trust the caller's snapshot as it is (keep the status quo)** — this is the behavior this decision fixes. Two reviewers independently confirmed it is 「무시가 아니라 파괴」 (“destruction, not ignoring”), and the overwritten value goes down to disk.
- **Change only the reading side to the registry** — we tried this first and it **effectively did nothing**: since re-registration had already overwritten, not one line of the new read ran in the overwritten range. The coder pointed it out and two reviewers confirmed.
- **Erase the record on success (keep the status quo)** — erasing is favorable for a 「깨끗한 화면」 (“clean screen”), but when the success is wrong it is an **irreversible loss**. The opposite error (a stale failure remaining beside a perfectly healthy agent) is visible and fixable.
- **Auto-expire after a set time·count** — there is no measurement to justify the expiry condition. Rejected because it would make one more groundless constant.

## 근거

- Two reviewers (doc-aware · cross-family blind) pointed at the handle destruction **each independently**, and the coder reached the same conclusion before being instructed.
- **Mutation verification**: if the two preservation lines are removed, `spawn_preserving_upsert_does_not_revert_a_handle_recorded_after_the_snapshot` breaks. If we revert so success clears the record, `an_optimistic_success_does_not_clear_the_failure_record` breaks.
- The effect of preservation on claude is **not zero but an improvement**: `ensure_session_id` reads the live value instead of the snapshot, so a re-activation after a drift has been recorded resumes with the drifted sid instead of the stale sid. We corrected what we once reported as 「영향 없음」 (“no effect”) and wrote it in two places in the code.

## 영향 / 불변식

- The preserved set is a **shared helper**, so all backends change together. That is why this decision was put up to the user for approval.
- **「자동으로 지우는 것이 없다」 (“Nothing is erased automatically”) is true only within the link axis.** ★When this line was first written it said 「아직 참이 아니다 — Fresh 가 여전히 지운다」 (“not yet true — Fresh still erases”), and half of that was closed the same day★ (as ADR-0201's decision came to cover Fresh too). **The remaining half is intended** — backends that do not declare a link (claude·shell·stdio·codex terminal) still erase on success, and that is the content of 「claude 경로를 바이트 단위로 그대로 둔다」 (“leave the claude path unchanged byte for byte”). That is, **the erasing rule differs per backend** and the difference follows the link axis.
- `last_failure` is not a value only the screen looks at — it rides on the profile wire and **the control LLM reads it** (the field ADR-0082 made for that consumer). ADR-0173's 「도는 중이면 도는 중이 이긴다」 (“if running, 'running' wins”) is a **rendering** rule, so it overrides only the human UI. When a stale record remains beside a running agent, there is **no indication** telling that it is stale.
- `old_session_ids` has no upper bound, and with this decision it becomes **monotonically increasing** (what the snapshot happened to trim away is gone). It is a pre-existing defect and whether to cap it is undecided.
