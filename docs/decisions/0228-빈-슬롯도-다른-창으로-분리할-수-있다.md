# ADR-0228: An empty slot can also be detached into another window

- 상태: 확정 (2026-09-24, basis: user decision — let empty slots be detached into another window too)
- 관련: Amends ADR-0065 (the slot.popout empty-slot trim in decision 1) · ADR-0057 (popout — the window owns the tab) · ADR-0064 (slot menu descriptor · the common item `'*'` single source) · `src/commands/slotCommands.ts` (menu contribution) · `src-tauri/src/layout/manager.rs` (`prepare_detached_view`) · `src-tauri/src/layout/apply.rs` (`move_slot_to_window`)

## 맥락
An empty slot could not be detached (popped out) into another window. Two layers blocked it.

1. **Menu** — ADR-0065 decision 1 attached `hideOn: ['empty']` to `slot.popout`. The reason is one line: 「`slot.popout`(팝업 분리)도 빈 칸을 팝아웃해 실익이 낮다.」
2. **Shell core** — `prepare_detached_view` rejected an empty slot with `SlotNotFound`. No ADR decided this rejection — the code comment itself said 「이걸 정한 ADR 은 없고 메뉴 숨김만 ADR-0065」.

In addition, the apply service (`move_slot_to_window`) turned **every** error from the prepare step into the single message 「빈 슬롯은 다른 창으로 옮길 수 없음」, so even when the slot or the view really did not exist, it looked like the empty slot's fault.

User request (2026-09-24): 「별도의 팝업창 띄우는게 슬롯에 컨텐츠가 있어야지만 분리가 되는데 그냥 빈 슬롯도 분리되게 해줘.」

## 결정
1. **Detach empty slots too.** Remove `hideOn: ['empty']` from `slot.popout` in the menu. **Keep the empty-slot trim of `slot.empty` (clear)** — clearing an empty slot again is still meaningless (the rest of ADR-0065 decision 1 stays alive).
2. **Remove the empty-slot rejection in the shell core.** Detaching an empty slot takes the same path as a content slot — one slot (content = empty slot) is created in a new tab of the new window, and the original slot is closed exactly as when a content slot is detached (the neighboring slot takes over its space, and if it was the only slot in **that tab**, an empty slot with a new id remains — closing is per tab (view)). The user did not separately decide this closing behavior — it is a **session interpretation** that reads the request's 「분리」 as the same move as for a content slot, and no different rule was made for the empty slot alone (such as leaving the original slot and only opening the new window).
3. **A rejection in the prepare step returns the real cause.** If the slot or view does not exist, its error message (「slot 없음: …」 · 「view 없음: …」) goes through as is — the same way as the sibling apply functions. The command bus carries an apply failure as `CONFLICT`, as it does now (the header rule of `src-tauri/src/layout/commands.rs` — do not choose the code by the message).

## 거부한 대안
- **Keep blocking empty-slot detach (keep ADR-0065 decision 1)** — the only reason for blocking it was the one line 「실익이 낮다」, and it was not a technical constraint. The user wanted empty slots to be detachable. Nature of the rejection basis = **user decision (preference)**.

## 근거
- **Downstream does not assume an agent (checked in code)** — the popout page reads only the window name and draws the window layout (the same path as `window.create`, which makes an empty window). The tab name comes from the window name (「Popup N」). Output subscription sweeps only agent slots, so there is nothing to do for an empty slot.
- **The move-safety check also holds for an empty slot** — if the original slot gets filled while the window is being created (outside the lock), the commit step fails the check 「원래 칸이 아직 옮긴 내용과 같은가」 (is the original slot still the same as the moved content?) and does not close the original slot. The filled content survives (pinned by an integration test).
- Two `/review code full` reviewers (Claude invariant breaker + GPT blind) both PASS — zero defects, only low observations.

## 영향 / 불변식
- **LLM path** — the bus `slot.popout` and the screen-command registry `slot.popout` go to the same apply service. There is no new surface (「LLM-우선 제어」).
- **The command-list generation (`catalog_version`) stays at 7** — the `slot.popout` declaration (summary · arguments · response · error codes) did not change by a single character, and the generation is raised **when a declaration changes** (`crates/engram-dashboard-command/src/macros.rs:31`). The old empty-slot rejection was not written anywhere in the declaration. Do not reopen this judgment with the logic of the generation 6 and 7 comments, 「동작이 다른 셸은 같은 세대를 말하지 않는다」 — in those two cases the declaration wording changed together.
- **Known behavior (not a defect):**
  - Detaching the only empty slot of a tab leaves an empty slot with a new id in that tab and opens one new window — effectively the same as `window.create`. Repeating it keeps creating empty windows (all of them created only by user or LLM requests). An LLM holding the original slot id gets 「slot 없음」 afterward — detaching a content slot is the same.
  - A rejected detach also uses up one popup number (the number is drawn before the prepare step — a pre-existing, monotonic counter, so harmless).
  - Detaching the same empty slot twice very quickly opens two windows and closes the original slot only once — the same race a content slot already tolerates has this shape (pre-existing).
- **Code anchors** — `// ADR-0228` is in the menu contribution (`slotCommands.ts`) · the shell prepare step (`manager.rs`) · the apply service (`apply.rs`) · the new tests.
