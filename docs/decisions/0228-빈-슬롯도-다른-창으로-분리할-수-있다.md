# ADR-0228: 빈 슬롯도 다른 창으로 분리할 수 있다

- 상태: 확정 (2026-09-24, 근거: 사용자 결정 — 빈 칸도 다른 창으로 분리되게)
- 관련: Amends ADR-0065 (결정 1 의 slot.popout 빈 칸 트림) · ADR-0057(팝아웃 — 탭은 창이 소유) · ADR-0064(슬롯 메뉴 descriptor · 공통 항목 `'*'` 단일 출처) · `src/commands/slotCommands.ts`(메뉴 기여) · `src-tauri/src/layout/manager.rs`(`prepare_detached_view`) · `src-tauri/src/layout/apply.rs`(`move_slot_to_window`)

## 맥락
빈 칸은 다른 창으로 분리(팝아웃)할 수 없었다. 막는 층이 둘이었다.

1. **메뉴** — ADR-0065 결정 1 이 `slot.popout` 에 `hideOn: ['empty']` 를 달았다. 사유는 한 줄이다: 「`slot.popout`(팝업 분리)도 빈 칸을 팝아웃해 실익이 낮다.」
2. **셸 코어** — `prepare_detached_view` 가 빈 칸이면 `SlotNotFound` 로 거절했다. 이 거절을 정한 ADR 은 없었다 — 코드 주석이 스스로 「이걸 정한 ADR 은 없고 메뉴 숨김만 ADR-0065」라고 적고 있었다.

덧붙여 적용 서비스(`move_slot_to_window`)가 준비 단계의 **모든** 오류를 「빈 슬롯은 다른 창으로 옮길 수 없음」 한 문구로 바꿔 돌려줘서, 칸이나 뷰가 실제로 없을 때도 빈 칸 탓으로 보였다.

사용자 요청(2026-09-24): 「별도의 팝업창 띄우는게 슬롯에 컨텐츠가 있어야지만 분리가 되는데 그냥 빈 슬롯도 분리되게 해줘.」

## 결정
1. **빈 칸도 분리한다.** 메뉴에서 `slot.popout` 의 `hideOn: ['empty']` 를 걷는다. **`slot.empty`(비우기)의 빈 칸 트림은 유지한다** — 빈 칸을 또 비우는 것은 여전히 무의미하다(ADR-0065 결정 1 의 나머지는 살아 있다).
2. **셸 코어의 빈 칸 거절을 걷는다.** 빈 칸의 분리는 콘텐츠 칸과 같은 경로를 탄다 — 새 창의 새 탭에 칸 하나(내용 = 빈 칸)가 생기고, 원래 칸은 콘텐츠 칸을 분리할 때와 똑같이 닫힌다(옆 칸이 자리를 이어받고, **그 탭**의 유일한 칸이었으면 새 id 의 빈 칸이 남는다 — 닫힘은 탭(뷰) 단위다). 이 닫힘 동작은 사용자가 따로 정하지 않았다 — 요청의 「분리」를 콘텐츠 칸과 같은 이동으로 읽은 **세션 해석**이고, 빈 칸에만 다른 규칙(원래 칸을 남기고 새 창만 연다 등)을 두지 않았다.
3. **준비 단계의 거절은 실제 원인을 돌려준다.** 칸·뷰가 없으면 그 오류 문구(「slot 없음: …」·「view 없음: …」)가 그대로 간다 — 형제 적용 함수들과 같은 방식이다. 명령 버스는 적용 실패를 지금처럼 `CONFLICT` 로 옮긴다(`src-tauri/src/layout/commands.rs` 머리 규칙 — 메시지로 코드를 고르지 않는다).

## 거부한 대안
- **빈 칸 분리를 계속 막는다(ADR-0065 결정 1 유지)** — 막은 사유가 「실익이 낮다」 한 줄뿐이고 기술 제약이 아니었다. 사용자가 빈 칸도 분리되길 원했다. 기각 근거의 성격 = **사용자 결정(선호)**.

## 근거
- **하류가 에이전트를 가정하지 않는다(코드 확인)** — 팝아웃 페이지는 창 이름만 읽어 창 레이아웃을 그린다(빈 창을 만드는 `window.create` 와 같은 경로). 탭 이름은 창 이름에서 나온다(「Popup N」). 출력 구독은 에이전트 칸만 훑으므로 빈 칸에는 할 일이 없다.
- **이동 안전 확인이 빈 칸에도 선다** — 창을 만드는 동안(락 밖) 원래 칸이 채워지면, 커밋 단계가 「원래 칸이 아직 옮긴 내용과 같은가」에서 어긋나 원래 칸을 닫지 않는다. 채워진 내용이 살아남는다(통합 테스트로 박았다).
- `/review code full` 2인(Claude 불변식 breaker + GPT blind) 모두 PASS — 결함 0, 낮은 관찰만.

## 영향 / 불변식
- **LLM 경로** — 버스 `slot.popout` 과 화면 명령 레지스트리 `slot.popout` 이 같은 적용 서비스로 간다. 새 표면은 없다(「LLM-우선 제어」).
- **명령 목록 세대(`catalog_version`)는 7 그대로다** — `slot.popout` 선언(요약·인자·응답·오류 코드)이 한 글자도 안 바뀌었고, 세대는 **선언이 바뀔 때** 올린다(`crates/engram-dashboard-command/src/macros.rs:31`). 옛 빈 칸 거절은 선언 어디에도 적혀 있지 않았다. 「동작이 다른 셸은 같은 세대를 말하지 않는다」는 세대 6·7 주석의 논리로 이 판단을 다시 열지 말 것 — 그 두 번은 선언 문구가 함께 바뀌었다.
- **알려진 동작(결함 아님):**
  - 탭의 유일한 빈 칸을 분리하면 그 탭엔 새 id 의 빈 칸이 남고 새 창이 하나 열린다 — 사실상 `window.create` 와 같다. 되풀이하면 빈 창이 계속 생긴다(모두 사용자·LLM 요청으로만 생긴다). 원래 칸 id 를 쥔 LLM 은 그 뒤 「slot 없음」을 받는다 — 콘텐츠 칸 분리도 같다.
  - 거절된 분리도 팝업 번호 하나를 쓴다(번호를 준비 단계 전에 뽑는다 — 선재 · 단조 카운터라 무해).
  - 같은 빈 칸을 아주 빠르게 두 번 분리하면 창 둘이 열리고 원래 칸은 한 번만 닫힌다 — 콘텐츠 칸의 같은 경합이 이미 감수하는 모양이다(선재).
- **코드 앵커** — `// ADR-0228` 이 메뉴 기여(`slotCommands.ts`)·셸 준비 단계(`manager.rs`)·적용 서비스(`apply.rs`)·새 테스트에 있다.
