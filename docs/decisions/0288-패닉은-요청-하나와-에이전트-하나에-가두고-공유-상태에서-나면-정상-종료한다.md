# ADR-0288: Confine a panic to one request and one agent, and exit normally when it comes from shared state

- 상태: 확정 (2026-10-10, basis: user decision 2026-10-10 · research `docs/research/panic-policy-peers-2026-10-08.md`) · 부분 폐기 by ADR-0289 (decision 3, normal exit on a shared-state panic) · 부분 폐기 by ADR-0290 (the return of decision 3 voids the partial discard by ADR-0289) · 부분 폐기 by ADR-0292 (the confinement scope of decisions 1 and 2, and decision 3)
- 관련: ADR-0005 (terminal transition · notification by the pump alone) · ADR-0019 (exit classification has a single consumer, the reaper · `shutting_down`) · ADR-0127 (turn observation cleanup = only two points) · ADR-0275 decision 1 (base `sync` = reclaim without a warning) · research `docs/research/panic-policy-peers-2026-10-08.md` · Amended by ADR-0289 (decision 3, normal exit on a shared-state panic) · Amended by ADR-0290 (the return of decision 3 voids the partial discard by ADR-0289) · Amended by ADR-0292 (the confinement scope of decisions 1 and 2, and decision 3)

## 맥락

The release build has `panic = "abort"` in the workspace `[profile.release]` (`Cargo.toml:41`), so a panic anywhere in daemon code kills the daemon instantly. The agent processes are in a `KILL_ON_JOB_CLOSE` Job (`crates/engram-dashboard-platform/src/group/mod.rs:38`) and all die together with the daemon — one bug ends every running agent.

Code that confines already exists — the output pump wraps its own body in `catch_unwind`, and on a panic it transitions that agent to `Failed` with `core.finish` (`crates/engram-dashboard-agent/src/transport/pty.rs:274` 「B-2」 · the same form `transport/stdio.rs:305` · `backend/codex/transport.rs`), and the daemon panic hook comment states 「데몬 전체는 죽이지 않는다 — 연결 task 패닉은 tokio 가 격리하고 pump 패닉은 Failed 로 전이」 (`crates/engram-dashboard-daemon/src/lib.rs:455-457`). But in an abort build neither `catch_unwind` nor tokio's task isolation catches anything, so that intent holds only in debug · test builds.

While scoping boundary refactoring A, trying to decide 「락 오염 때 패닉할지 복구할지」, it became clear that the question above it (how the app behaves when a panic happens) comes first. The user's direction = 「패닉에 의한 종료는 최대한 하지 않는다」.

## 결정

Panics are split by the scope of the place where they occurred.

1. **One request** — a panic that occurs while handling one command · query · connection ends only that request as a failure, and the daemon keeps running.
2. **One agent** — a panic that occurs in code that serves only one agent cleans up only that agent, and the other agents keep running.
3. **Shared state** — a panic that occurs while changing state that the whole daemon shares takes the **existing normal exit path** (the same exit signal as `StopDaemon` · the tray 「데몬 끄기」). No dedicated mechanism is built for this tier.
4. **When Rust aborts** (a second panic while handling a panic, etc.) the process just exits. Agent cleanup is done by the Job, as now. No dedicated mechanism is built.

For 1 · 2 to hold, the daemon release build must be unwind (research report 「메커니즘 사실」). The following are decided in the TRD — the tier boundary (what is 「에이전트 하나」 (one agent) and what is 「공유 상태」 (shared state)) · how lock poisoning is handled · the shape of the user notice for 1 · 2 · the **unwind scope** (the first item of 「영향」 below — a user decision).

## 거부한 대안

- **Keep the current abort** — it directly contradicts the user's direction (minimize panic exits). (Main's explanation: one bug kills every running agent — Job `KILL_ON_JOB_CLOSE`, confirmed in code.)
- **Keep the daemon alive even on a panic from shared state and prompt a restart with a strong warning** — this was the user's first proposal. The user heard the practice and chose exit. The practice heard = within the research scope there was no precedent that 「전체를 살려 두고 마무리를 안내」 (conclusion 1 · confidence 「가능성 높음」), and the peers that exit on a panic from anywhere are the majority (group (가)). (Main's explanation — the risk shown to the user: if it keeps running in a half-changed memory state, other agents turn strange, and if that state is carried to disk by a save, even a healthy `agents.json` gets overwritten. The file itself is an atomic write, so a panic does not break it.)
- **Split the agent PTY into a process outside the daemon** (VS Code pty host style) — put up as an option and the user did not choose it. (Main's explanation: the structural change is large — on Windows the process that created the PTY must hold it, CLAUDE.md 「참조 구현」.)

## 근거

- Peer survey (`docs/research/panic-policy-peers-2026-10-08.md` · reflects 8 FIXes from the codex adversarial review): confining one request (rust-analyzer · sccache · tower-http — tower-http is the counterexample that confines even handlers holding shared state) and confining and supervising a unit (ractor · the VS Code extension host · Chrome) are common. Several peers exit when a panic happens (anywhere) (zellij · Alacritty · Zed · wezterm — four confirmed), and vector catches it and shuts down in an orderly way. ★Counterexample★: herdr · atuin · helix rely on std default behavior with neither an isolation boundary nor a panic hook, so on a non-main thread panic only that thread dies and they keep running without a notice (herdr = the daemon peer closest to ours · likely — the shape 「살려 두되 안내 없음」). The user decided after hearing 「다들 종료한다」 and this counterexample came out after the decision — the user was told (2026-10-10).
- The peers that survive are all unwind builds (same report).
- The dedicated mechanisms of 3 · 4 (an exit time limit · notifying the shell of the reason · marking it for the next boot restore) were put off by the user as 「나중에 — 복원 시스템과 연관」.

## 영향 / 불변식

- **The unwind scope is open (TRD · user decision)** — `panic` is in one place, the workspace `[profile.release]`, and a Cargo profile override cannot give a per-package `panic`. So making only the daemon unwind needs a separate profile and build invocation, and changing the whole workspace makes the shell · CLI unwind too — background thread · task panics in the shell would no longer kill the window, so shell behavior changes visibly to the user (ADR-0281 also wrote on the premise of shell abort). The change in executable size was not measured either.
- **Audit again the decisions · comments written on the premise of abort** — once unwind is in, that premise falls apart. How to find them = `rg -n 'panic = "abort"' docs/decisions crates src-tauri/src`. Examples (not exhaustive): base `sync` header contract 3 · the S2(a) rejection reason of ADR-0275 · ADR-0262 K7 (two curtains rely on abort) · ADR-0226 (rejected the latch `catch_unwind` as dead code) · ADR-0199 · ADR-0142 · ADR-0233 · ADR-0281 · code `session_id_latch.rs` · `backend/codex/transport.rs` · `backend/claude/leftover.rs` · `transport/input_queue.rs` · `daemon/src/control/registry.rs`. Amendment links (`/adr link`) are attached when the TRD · implementation actually changes that premise.
- **2 is an open problem outside the pump** — the pump's own panic is already confined inside the pump and the pump calls `finish`, so it does not break ADR-0005 (pump alone) · ADR-0127 (two cleanup points). What the TRD must decide is the agent-only code outside the pump (writes · the output parser · the latch · paths that serve one agent while holding a shared lock). Creating a third cleanup caller such as a supervisor is the causal branching that ADR-0127 forbids.
- **The path of 3 must run to the end even on a poisoned shared lock** — the current normal exit path cannot tolerate poisoning (example: `sessions.read().expect(…)` in `shutdown_all` — `crates/engram-dashboard-agent/src/manager.rs:2943`). If that path panics again on another thread, it is not a Rust abort and so does not fall under 4, and since the time limit is also put off, the daemon can be left neither running nor dead. This is not a decision to bring in a time limit; it means the lock poisoning policy (TRD) must close this hole.
- **3 takes the next boot restore as it does now** — a normal exit sets `shutting_down` first so the reaper does not touch profiles (ADR-0019 · `manager.rs:2933-2937`), so the next boot revives those agents as usual. Showing the panic reason is the share of the deferred mechanism.
- 3 uses the normal exit path as it is, so the known failure of that path (`docs/tracking.md` T-52 — the exit result arrives as `Timeout` instead of `DaemonClosed` · the daemon actually goes down) is looked at together.
