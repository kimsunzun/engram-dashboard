# ADR-0288: 패닉은 요청 하나와 에이전트 하나에 가두고 공유 상태에서 나면 정상 종료한다

- 상태: 확정 (2026-10-10, 근거: 사용자 결정 2026-10-10 · 조사 `docs/research/panic-policy-peers-2026-10-08.md`) · 부분 폐기 by ADR-0289 (결정 3 공유 상태 패닉의 정상 종료)
- 관련: ADR-0005(terminal 전이 · 알림은 펌프 단독) · ADR-0019(종료 분류는 reaper 단일 소비자 · `shutting_down`) · ADR-0127(턴 관측 정리 = 두 지점뿐) · ADR-0275 결정 1(base `sync` = 경고 없이 되찾기) · 조사 `docs/research/panic-policy-peers-2026-10-08.md` · Amended by ADR-0289 (결정 3 공유 상태 패닉의 정상 종료)

## 맥락

배포판은 워크스페이스 `[profile.release]` 의 `panic = "abort"`(`Cargo.toml:41`)라 데몬 코드 어디서든 패닉이 나면 데몬이 즉사한다. 에이전트 프로세스는 `KILL_ON_JOB_CLOSE` Job 에 들어 있어(`crates/engram-dashboard-platform/src/group/mod.rs:38`) 데몬과 함께 전부 죽는다 — 버그 하나가 돌던 에이전트 전체를 끝낸다.

가두는 코드는 이미 있다 — 출력 펌프는 자기 본체를 `catch_unwind` 로 감싸 패닉이면 `core.finish` 로 그 에이전트를 `Failed` 로 전이시키고(`crates/engram-dashboard-agent/src/transport/pty.rs:274` 「B-2」 · 같은 꼴 `transport/stdio.rs:305` · `backend/codex/transport.rs`), 데몬 패닉 훅 주석은 「데몬 전체는 죽이지 않는다 — 연결 task 패닉은 tokio 가 격리하고 pump 패닉은 Failed 로 전이」를 적는다(`crates/engram-dashboard-daemon/src/lib.rs:455-457`). 그러나 abort 빌드에서는 `catch_unwind` 도 tokio 의 태스크 격리도 아무것도 잡지 않아, 그 의도는 debug · 시험 빌드에서만 성립한다.

경계 리팩터링 A 범위 정리 중 「락 오염 때 패닉할지 복구할지」를 정하려다 그 위의 질문(패닉이 나면 앱이 어떻게 행동하나)이 먼저라는 것이 드러났다. 사용자 방향 = 「패닉에 의한 종료는 최대한 하지 않는다」.

## 결정

패닉을 난 자리의 범위로 가른다.

1. **요청 하나** — 명령 · 조회 · 연결 하나를 처리하다 난 패닉은 그 요청만 실패로 끝내고 데몬은 계속 돈다.
2. **에이전트 하나** — 한 에이전트만 섬기는 코드에서 난 패닉은 그 에이전트만 정리하고 나머지 에이전트는 계속 돈다.
3. **공유 상태** — 데몬 전체가 함께 쓰는 상태를 바꾸다 난 패닉은 **기존 정상 종료 경로**를 탄다(`StopDaemon` · 트레이 「데몬 끄기」와 같은 종료 신호). 이 단계를 위한 전용 장치는 만들지 않는다.
4. **Rust 가 abort 하는 경우**(패닉 처리 중 또 패닉 등)는 그냥 종료된다. 에이전트 정리는 지금처럼 Job 이 한다. 전용 장치는 만들지 않는다.

1 · 2 가 성립하려면 데몬 배포판이 unwind 여야 한다(조사 보고서 「메커니즘 사실」). 다음은 TRD 에서 정한다 — 단계 경계(무엇이 「에이전트 하나」이고 무엇이 「공유 상태」인가) · 락 오염 처리 방식 · 1 · 2 의 사용자 고지 모양 · **unwind 범위**(아래 「영향」 첫 항목 — 사용자 결정).

## 거부한 대안

- **현행 abort 유지** — 사용자 방향(패닉 종료 최소화)과 정면으로 어긋난다. (메인 설명: 버그 하나가 돌던 에이전트 전부를 죽인다 — Job `KILL_ON_JOB_CLOSE`, 코드 확인.)
- **공유 상태에서 난 패닉도 살려 두고 강한 경고로 재시작을 유도** — 사용자의 첫 제안이었다. 사용자가 관행을 듣고 종료로 정했다. 들은 관행 = 조사 범위에서 「전체를 살려 두고 마무리를 안내」하는 선례는 없었고(결론 1 · 확신도 「가능성 높음」), 어디서 난 패닉이든 종료하는 피어가 다수다(무리 (가)). (메인 설명 — 사용자에게 제시한 위험: 반쯤 바뀐 메모리 상태로 계속 돌면 다른 에이전트가 이상해지고, 그 상태가 저장으로 디스크에 실리면 멀쩡한 `agents.json` 까지 덮인다. 파일 자체는 원자적 쓰기라 패닉으로는 안 깨진다.)
- **에이전트 PTY 를 데몬 밖 프로세스로 분리**(VS Code pty host 식) — 선택지로 올렸고 사용자가 고르지 않았다. (메인 설명: 구조 변경이 크다 — Windows 는 PTY 를 만든 프로세스가 쥐어야 한다, CLAUDE.md 「참조 구현」.)

## 근거

- 피어 서베이(`docs/research/panic-policy-peers-2026-10-08.md` · codex 적대 리뷰 FIX 8건 반영): 요청 하나를 가두는 것(rust-analyzer · sccache · tower-http — tower-http 는 공유 상태를 쥔 핸들러까지 가두는 반례다) · 단위를 가두고 감독하는 것(ractor · VS Code 확장 호스트 · Chrome)은 흔하다. 패닉이 나면(어디서든) 종료하는 피어가 여럿이고(zellij · Alacritty · Zed · wezterm — 확인된 넷), vector 는 잡아서 질서 있게 끈다. ★반례★: herdr · atuin · helix 는 격리 경계도 패닉 훅도 없이 std 기본 동작에 기대 비주 스레드 패닉 때 그 스레드만 죽고 알림 없이 계속 돈다(herdr = 우리와 가장 가까운 데몬 피어 · 가능성 높음 — 「살려 두되 안내 없음」 모양). 사용자는 「다들 종료한다」를 듣고 정했고 이 반례는 결정 뒤에 드러났다 — 사용자에게 알렸다(2026-10-10).
- 살아남는 피어는 전부 unwind 빌드다(같은 보고서).
- 3 · 4 의 전용 장치(종료 시간 제한 · 셸 사유 고지 · 다음 부팅 복원 표시)는 사용자가 「나중에 — 복원 시스템과 연관」으로 미뤘다.

## 영향 / 불변식

- **unwind 범위는 열려 있다(TRD · 사용자 결정)** — `panic` 은 워크스페이스 `[profile.release]` 한 곳에 있고 Cargo 프로필 override 는 패키지별 `panic` 을 못 준다. 그래서 데몬만 unwind 로 하려면 별도 프로필과 빌드 호출이 필요하고, 워크스페이스 전체를 바꾸면 셸 · CLI 도 unwind 가 된다 — 셸의 배경 스레드 · 태스크 패닉이 더는 창을 죽이지 않게 되어 셸 동작이 사용자 눈에 바뀐다(ADR-0281 도 셸 abort 를 전제로 적었다). 실행 파일 크기 변화도 재지 않았다.
- **abort 를 전제로 쓴 결정 · 주석을 다시 감사한다** — unwind 가 되면 그 전제가 무너진다. 찾는 법 = `rg -n 'panic = "abort"' docs/decisions crates src-tauri/src`. 예(전수 아님): base `sync` 헤더 계약 3 · ADR-0275 S2(a) 기각 사유 · ADR-0262 K7(막 둘이 abort 에 기댄다) · ADR-0226(래치 `catch_unwind` 를 죽은 코드로 기각) · ADR-0199 · ADR-0142 · ADR-0233 · ADR-0281 · 코드 `session_id_latch.rs` · `backend/codex/transport.rs` · `backend/claude/leftover.rs` · `transport/input_queue.rs` · `daemon/src/control/registry.rs`. 개정 링크(`/adr link`)는 그 전제를 실제로 바꾸는 TRD · 구현 때 단다.
- **2 는 펌프 밖이 열린 문제다** — 펌프 자신의 패닉은 이미 펌프 안에서 가둬지고 펌프가 `finish` 를 부르므로 ADR-0005(펌프 단독) · ADR-0127(정리 지점 둘)을 깨지 않는다. TRD 가 정할 것은 펌프 밖의 에이전트 전용 코드(쓰기 · 출력 해석기 · 래치 · 한 에이전트를 섬기며 공유 락을 쥐는 경로)다. 감독자 같은 세 번째 정리 호출자를 만들면 ADR-0127 이 금하는 인과 분기다.
- **3 의 경로는 오염된 공유 락에서도 끝까지 가야 한다** — 지금 정상 종료 경로는 오염을 견디지 못한다(예: `shutdown_all` 의 `sessions.read().expect(…)` — `crates/engram-dashboard-agent/src/manager.rs:2943`). 그 경로가 다른 스레드에서 다시 패닉하면 Rust abort 가 아니라 4 에 들지 않고, 미룬 시간 제한도 없어 데몬이 돌지도 죽지도 않는 채 남을 수 있다. 시간 제한을 들이는 결정이 아니라, 락 오염 정책(TRD)이 이 구멍을 닫아야 한다는 것이다.
- **3 은 다음 부팅 복원을 지금처럼 탄다** — 정상 종료는 `shutting_down` 을 먼저 세워 reaper 가 프로필을 손대지 않으므로(ADR-0019 · `manager.rs:2933-2937`) 다음 부팅이 그 에이전트들을 평소처럼 되살린다. 패닉 사유 표시는 미룬 장치 몫이다.
- 3 은 정상 종료 경로를 그대로 쓰므로 그 경로의 알려진 실패(`docs/tracking.md` T-52 — 끄기 결과가 `DaemonClosed` 대신 `Timeout` 으로 온다 · 데몬은 실제로 내려간다)를 함께 본다.
