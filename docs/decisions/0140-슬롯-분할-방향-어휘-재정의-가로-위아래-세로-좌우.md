# ADR-0140: 슬롯 분할 방향 어휘 재정의 (가로 = 위아래, 세로 = 좌우)

- 상태: 확정 (2026-08-17, 근거: 사용자 결정)
- 관련: Amends ADR-0063 (부팅 기본 레이아웃 방향 어휘) · ADR-0065(빈 슬롯 메뉴 구성) · Amends ADR-0064 (분할 command id)

## 맥락

슬롯 우클릭 메뉴의 `가로 분할`·`세로 분할`이 사용자가 기대한 것과 반대로 동작했다. 사용자가 헷갈린다고 제보했고(2026-08-17), 원인은 업계에 상반된 두 관례가 공존하기 때문이다.

- **tmux 관례** — `split-window -h`(horizontal) = 패널이 **수평으로 나열**(좌/우). 축 기준.
- **vim 관례** — `:split`(horizontal) = **수평 분할선**이 생겨 위/아래로 쌓임. 분할선 기준.

구현 당시 코드는 tmux 관례였다. `SplitDir::Horizontal` = 좌/우, `SplitDir::Vertical` = 상/하이고(`src-tauri/src/layout/types.rs`), 프론트가 `<Allotment vertical={dir === 'vertical'}>`로 그대로 매핑했다(`ViewLayoutRenderer.tsx`). 한국어 라벨은 `가로 분할 → horizontal`, `세로 분할 → vertical`로 직결돼 있어 `가로 분할`이 좌/우 배치를 만들었다.

문제는 라벨만이 아니다. `horizontal`/`vertical`이라는 어휘 자체가 두 관례 사이에서 어느 쪽인지 이름만으로 판정되지 않는다 — 그래서 코드를 읽는 쪽도, 메뉴를 누르는 쪽도 매번 되짚어야 했다.

## 결정

**방향 어휘를 "축"이 아니라 "결과 배치"로 표현한다.** 축 기반 이름(`Horizontal`/`Vertical`)을 버리고 배치 기반 이름을 쓴다 — 이름이 결과를 직접 말하면 관례 논쟁 자체가 사라진다.

1. **한국어 라벨 = vim 관례.** `가로 분할` = 가로줄(수평 분할선)이 생겨 **위/아래**로 나뉨. `세로 분할` = **좌/우**로 나뉨. 라벨 단어(가로·세로)와 메뉴 순서(가로 먼저)는 유지한다.
2. **방향 타입 개명.** `SplitDir { Horizontal, Vertical }` → `SplitDir { LeftRight, TopBottom }`. wire 표현은 serde snake_case로 `"left_right"`/`"top_bottom"`. 프론트 매핑은 `vertical={dir === 'top_bottom'}`.
3. **command id도 배치 기준.** `slot.split.h`/`slot.split.v` → `slot.split.topBottom`/`slot.split.leftRight`. `h`/`v` 한 글자는 개명 후 반대를 가리키게 되므로 남길 수 없다.
4. **최종 결선** — `가로 분할` → `slot.split.topBottom` → `TopBottom` → 위/아래. `세로 분할` → `slot.split.leftRight` → `LeftRight` → 좌/우.
5. **부팅 기본 레이아웃은 배치가 바뀌지 않는다** — AgentList(좌) + Empty(우) 그대로이고, 그 방향값이 `LeftRight`로 개명될 뿐이다. ADR-0063이 이를 "가로 분할"이라 부른 대목만 어휘가 뒤집힌다.

## 거부한 대안

- **tmux 관례 유지(가로 = 좌/우)** — 사용자가 "가로라고 하면 가로줄이 생겨서 위아래로 분리되는 게 편하다"고 명시적으로 골랐다(2026-08-17). 어느 관례든 절반은 헷갈리므로 이 프로젝트 사용자의 직관을 정본으로 삼는다.
- **라벨↔방향 매핑만 뒤집고 `Horizontal`/`Vertical` 이름 유지** — 변경 파일이 1개로 끝나 가장 싸지만, 코드에 모순이 박힌다: `types.rs`의 `Horizontal = 좌우` 주석이 살아 있는 채로 `가로 분할` 메뉴가 `Vertical`을 보내게 된다. 다음 세션이 이 불일치를 "버그"로 읽고 되돌릴 좌표를 남기는 형태다. 실제로 이 ADR을 쓰게 만든 원인이 이름과 결과의 불일치였으므로, 불일치를 한 겹 더 쌓는 선택은 문제를 재생산한다.
- **가로/세로 어휘 폐기 + VS Code식 방향 라벨(`오른쪽에 분할`·`아래에 분할`)** — 애매함이 원천 제거되는 가장 안전한 안이지만, 사용자가 "가로 단어만 있으면 되고 나머진 관례대로"라고 어휘 유지를 지정했다(2026-08-17). 라벨 어휘는 사용자 결정 사항이라 세션이 뒤집지 않는다.

## 근거

- **사용자 결정(2026-08-17)** — 라벨 의미와 어휘 유지 둘 다 사용자가 직접 지정했다.
- **개명 비용이 닫혀 있다는 코드 근거** — 레이아웃 타입은 `src-tauri` 안에서만 정의되고 `engram-dashboard-protocol`을 포함한 6개 crate 어디에도 `SplitDir`가 없다(데몬은 View를 모른다 — 설계 불변식). 게다가 CLAUDE.md 「LLM-우선 제어」가 적은 대로 레이아웃은 디스크 영속이 없어 인메모리뿐이다. 따라서 wire enum 개명이 외부 소비자·저장된 데이터를 깨지 않는다.
- **현재 동작을 이름이 아니라 코드로 확인했다** — `spatial.rs`의 이웃 계산 테스트(`horizontal_split_left_right_neighbors`·`vertical_split_up_down_neighbors`)와 `ViewLayoutRenderer.tsx`의 allotment `vertical` prop 매핑이 서로 일치했다. 개명은 이 두 지점의 기대값을 함께 갱신해야 한다.

## 영향 / 불변식

- **이름이 결과를 말한다 — 이 불변식이 이 ADR의 전부다.** `TopBottom`은 항상 상/하, `LeftRight`는 항상 좌/우다. 축 기반 어휘(`horizontal`·`vertical`·`h`·`v`)를 방향 값·command id·타입 이름에 되살리지 않는다. 되살리면 관례 충돌이 그대로 복귀한다.
- **한국어 라벨은 관례 매핑이라 코드에서 자명하지 않다.** `가로 분할 → TopBottom`은 vim 관례를 알아야 납득되는 결선이므로, 그 매핑 지점(`slotCommands.ts`)에 `// ADR-0140` 앵커를 단다. 앵커 없이 보면 "라벨이 뒤바뀐 버그"로 읽힌다.
- **allotment 매핑이 유일한 진실 경계다** — `vertical={dir === 'top_bottom'}`. 여기가 뒤집히면 메뉴·타입·테스트가 전부 맞는데도 화면만 반대가 된다.
- **`src-tauri/bindings/`는 아무도 지키지 않는다 — 손으로 맞추고 GUI 실측으로만 확인된다.** CI의 ts-rs sync 게이트는 `crates/engram-dashboard-protocol/bindings/`만 diff하고 이 폴더는 덮지 않으며, 이 폴더를 만드는 `export_bindings_*` 테스트는 `engram-dashboard` 패키지 소속이라 로컬·CI 양쪽 테스트 명령에서 제외돼 있고 그 타깃 자체가 `0xc0000139 STATUS_ENTRYPOINT_NOT_FOUND`로 죽는다(실측 2026-08-17). 그 결과 이 폴더는 HEAD에서 이미 낡아 있었다. 여기 wire 문자열을 틀리면 **어떤 테스트도 CI도 잡지 못하고** `split_slot` invoke가 런타임에 serde 거부로 실패한다 — 레이아웃 타입을 다시 개명하는 세션은 생성물을 손으로 맞춘 뒤 실제 창에서 확인해야 한다. (`LayoutNode.ts`는 `SplitDir`를 이름으로만 참조하므로 이 개명에 안 바뀐다.)
- **ADR-0063 decision 2 재해석** — "부팅 기본 = 가로 분할 [AgentList(좌) · Empty(우)]"의 *배치*는 유효하고 *어휘*만 폐기다. 새 어휘로 읽으면 그 배치는 `LeftRight`(= 세로 분할)다.
