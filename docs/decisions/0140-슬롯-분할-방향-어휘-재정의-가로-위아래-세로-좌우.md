# ADR-0140: Redefine the slot split direction vocabulary (가로 = top/bottom, 세로 = left/right)

- 상태: 확정 (2026-08-17, grounds: user decision) · 부분 폐기 by ADR-0222 (decision 5 boot default layout arrangement) · 부분 폐기 by ADR-0227 (the allotment mapping truth boundary in 영향)
- 관련: Amends ADR-0063 (boot default layout direction vocabulary) · ADR-0065(empty slot menu composition) · Amends ADR-0064 (split command id) · Amended by ADR-0222 (decision 5 boot default layout arrangement) · Amended by ADR-0227 (the allotment mapping truth boundary in 영향)

> ★**The statement in 「근거」, 「레이아웃은 디스크 영속이 없어 … wire enum 개명이 외부 소비자·저장된 데이터를 깨지 않는다」 (the layout has no disk persistence, so renaming the wire enum does not break external consumers or stored data), is no longer true**★ (note 2026-10-04, decision unchanged). Since storage management P3b3 (`f9db35a`), the layout is persisted in `shell\state\state.json`, and that file carries the serde names of `LayoutNode` · `SplitDir` · `SlotContent` as they are (node `type` · `left_right` · `top_bottom` · slot content `type`) — `SplitDir` · `SlotContent` use serde as is, and a test binds the node shape to be the same JSON as `LayoutNode` (TRD `docs/process/S21-storage/trd.md` §6-1 · `src-tauri/src/state/schema.rs`). Renaming those names now breaks the stored screens — a tab whose node shape or split direction cannot be resolved is skipped as a whole (TRD §6-2), a slot whose content kind cannot be resolved stands as 「이 판이 모르는 내용」 (empty cell · occupied), and a field with a default silently returns to its default value. The rename in this ADR predates persistence (2026-08-17), so none of this applied. To rename again, leave the old name readable with `#[serde(alias = "옛 이름")]` [unverified — alias on a variant of an internally tagged enum · same line of the TRD] — ★raising `version` alone is not enough★: the codec accepts only files of the same number, so a raised version loses the whole stored screen (TRD §6-1 「이름 바꾸기 규칙」).

## 맥락

In the slot right-click menu, `가로 분할` and `세로 분할` behaved the opposite of what the user expected. The user reported being confused (2026-08-17), and the cause is that two opposing conventions coexist in the industry.

- **tmux convention** — `split-window -h` (horizontal) = panes **laid out horizontally** (left/right). Axis-based.
- **vim convention** — `:split` (horizontal) = a **horizontal split line** appears and the panes stack top/bottom. Split-line-based.

At implementation time the code followed the tmux convention. `SplitDir::Horizontal` = left/right, `SplitDir::Vertical` = top/bottom (`src-tauri/src/layout/types.rs`), and the frontend mapped it as is to `<Allotment vertical={dir === 'vertical'}>` (`ViewLayoutRenderer.tsx`). The Korean labels were wired directly as `가로 분할 → horizontal`, `세로 분할 → vertical`, so `가로 분할` produced a left/right arrangement.

The problem is not only the labels. The vocabulary `horizontal`/`vertical` itself cannot be decided from the name alone as to which of the two conventions it follows — so both the reader of the code and the person clicking the menu had to work it out each time.

## 결정

**Express the direction vocabulary by "resulting arrangement," not by "axis."** Drop the axis-based names (`Horizontal`/`Vertical`) and use arrangement-based names — when the name directly states the result, the convention dispute itself disappears.

1. **Korean labels = vim convention.** `가로 분할` = a horizontal line (a horizontal split line) appears and splits **top/bottom**. `세로 분할` = splits **left/right**. The label words (가로·세로) and the menu order (가로 first) are kept.
2. **Rename the direction type.** `SplitDir { Horizontal, Vertical }` → `SplitDir { LeftRight, TopBottom }`. The wire representation is `"left_right"`/`"top_bottom"` by serde snake_case. The frontend mapping is `vertical={dir === 'top_bottom'}`.
3. **The command id is arrangement-based too.** `slot.split.h`/`slot.split.v` → `slot.split.topBottom`/`slot.split.leftRight`. The single letters `h`/`v` would point to the opposite after the rename, so they cannot stay.
4. **Final wiring** — `가로 분할` → `slot.split.topBottom` → `TopBottom` → top/bottom. `세로 분할` → `slot.split.leftRight` → `LeftRight` → left/right.
5. **The boot default layout does not change its arrangement** — it is still AgentList (left) + Empty (right), and only its direction value is renamed to `LeftRight`. Only the passage where ADR-0063 calls this "가로 분할" has its vocabulary flipped.

## 거부한 대안

- **Keep the tmux convention (가로 = left/right)** — the user explicitly chose "가로라고 하면 가로줄이 생겨서 위아래로 분리되는 게 편하다" (gloss: when it says 가로, a horizontal line appears and separates top/bottom, which is comfortable) (2026-08-17). Whichever convention is used, half of people get confused, so the intuition of this project's user is taken as canon.
- **Flip only the label↔direction mapping and keep the names `Horizontal`/`Vertical`** — the cheapest since the change ends at one file, but it embeds a contradiction in the code: the `Horizontal = 좌우` comment in `types.rs` stays alive while the `가로 분할` menu sends `Vertical`. It takes the form of leaving coordinates for the next session to read this mismatch as a "bug" and revert it. Since the cause that made this ADR necessary was the mismatch between the name and the result, choosing to pile one more layer of mismatch reproduces the problem.
- **Abolish the 가로/세로 vocabulary + VS Code-style direction labels (`오른쪽에 분할`·`아래에 분할`)** — the safest option since ambiguity is removed at the source, but the user specified keeping the vocabulary: "가로 단어만 있으면 되고 나머진 관례대로" (gloss: only the word 가로 is needed and the rest by convention) (2026-08-17). The label vocabulary is the user's decision, so a session does not overturn it.

## 근거

- **User decision (2026-08-17)** — the user specified both the label meaning and keeping the vocabulary directly.
- **Code grounds that the rename cost is closed** — the layout types are defined only inside `src-tauri`, and `SplitDir` is in none of the 6 crates, including `engram-dashboard-protocol` (the daemon does not know the View — a design invariant). Moreover, as CLAUDE.md 「LLM-우선 제어」 states, the layout has no disk persistence and is in-memory only. So renaming the wire enum does not break external consumers or stored data.
- **The current behavior was checked in code, not by name** — the neighbor-calculation tests in `spatial.rs` (`horizontal_split_left_right_neighbors`·`vertical_split_up_down_neighbors`) and the allotment `vertical` prop mapping in `ViewLayoutRenderer.tsx` matched each other. The rename must update the expected values at these two points together.

## 영향 / 불변식

- **The name states the result — this invariant is the whole of this ADR.** `TopBottom` is always top/bottom, `LeftRight` is always left/right. Axis-based vocabulary (`horizontal`·`vertical`·`h`·`v`) is not brought back into direction values · command ids · type names. If it is brought back, the convention clash returns as it was.
- **The Korean labels are a convention mapping, so they are not self-evident in code.** `가로 분할 → TopBottom` is a wiring that is only convincing if you know the vim convention, so a `// ADR-0140` anchor is put at that mapping point (`slotCommands.ts`). Seen without the anchor, it reads as a "bug where the labels are swapped."
- **The allotment mapping is the single truth boundary** — `vertical={dir === 'top_bottom'}`. If this is flipped, only the screen comes out opposite even though the menu, types and tests are all correct.
- **No one guards `src-tauri/bindings/` — it is matched by hand and confirmed only by GUI measurement.** The CI ts-rs sync gate diffs only `crates/engram-dashboard-protocol/bindings/` and does not cover this folder, and the `export_bindings_*` tests that produce this folder belong to the `engram-dashboard` package, so they are excluded from both the local and the CI test commands, and that target itself dies with `0xc0000139 STATUS_ENTRYPOINT_NOT_FOUND` (measured 2026-08-17). As a result this folder was already stale at HEAD. If a wire string here is wrong, **no test or CI catches it** and the `split_slot` invoke fails at runtime with a serde rejection — a session that renames the layout types again must match the generated files by hand and then confirm in a real window. (`LayoutNode.ts` refers to `SplitDir` by name only, so it does not change with this rename.)
- **ADR-0063 decision 2 reinterpreted** — the *arrangement* of "boot default = 가로 분할 [AgentList (left) · Empty (right)]" remains valid and only the *vocabulary* is discarded. Read in the new vocabulary, that arrangement is `LeftRight` (= 세로 분할).
