# ADR-0268: Each crate calls tracing directly for logs, and base owns only the output configuration

- 상태: 확정 (rewritten 2026-10-03 · replaces the first version `ebfdafc` that was committed but not pushed (2026-10-02 · wrap logging behind a base entry point · the first item of 「거부한 대안」 below), basis: user decision 2026-10-03 (「로그 감싸지 마」 — reverses decision candidate 3 of `docs/refactoring/architecture-discussion-2026-09-26.md`) + user decision 2026-10-02 (masking goes at the place that prints · do not pull in base for logging) + survey `docs/research/low-level-crate-logging-2026-10-02.md` + log-state measurement master `a226f63` · span measurement `d5ac725`) · 부분 폐기 by ADR-0275 (the base lock-poison-recovery warning line in the impact)
- 관련: ADR-0138 (synchronous writes to the release log file — rejecting the 「마스킹 · 레닥션 레이어」 stays, and it is one of the grounds decision 4 relies on) · ADR-0175 decision 1 (logging is in base) · ADR-0266 (platform crate — calls `tracing` directly) · ADR-0267 (command · messaging depend on base only when they need it — logging is not that reason) · ADR-0269 decision 4 (the warning log of lock-poison recovery) · `crates/engram-dashboard-base/src/logging/mod.rs` (subscriber installation · `EnvFilter` · `mask_secrets`) · `docs/reference/logging-conventions.md` (「보안」) · `docs/tracking-archive.md` T-1 (masking is not wired into the sink and the caller calls it explicitly) · big section A (logging system design — memo 「큰 절」) · survey `docs/research/low-level-crate-logging-2026-10-02.md` · step-log S21 · Amended by ADR-0275 (the base lock-poison-recovery warning line in the impact)

## 맥락

Besides base, six crates depend directly on `tracing` — agent · daemon · discovery · messaging · net · the shell. There are about 530 log macro call sites (daemon 193 · agent 129 · shell 125 · net 38 · messaging 34 · discovery 9 — roughly, including the `tracing::` path, measured at master `a226f63`). `command` · `protocol` · `transport` have 0.

What is held centrally is the **output configuration** — subscriber installation · level filter · file · format · changing the level while running are decided in one place, base's `logging` module (`crates/engram-dashboard-base/src/logging/`).

Secret masking is not applied centrally — the file writer writes the bytes it receives as they are (`FileSinkWriter::write` in `logging/mod.rs`), and for masking the printing side chooses to call `mask_secrets`. That arrangement is already settled — T-1 implemented it as 「sink 에 배선하지 않고 호출자가 명시 호출」, and ADR-0138 rejected 「로그용 마스킹 · 레닥션 레이어 추가」 (the token is already in the same folder in plain text · instead 「우리가 쓰는 문장에는 자격증명을 넣지 않는다」).

The user (2026-09-26): 「로그 라이브러리를 왜 직접 쓰냐고. 나중에 컨트롤이 안 되잖아」. This concern produced the first version of this ADR (2026-10-02 — wrap logging behind a base entry point · the first item of 「거부한 대안」 below), and the user reversed it before the push (2026-10-03 — 「로그 감싸지 마」).

## 결정

1. **Logs are not wrapped — each crate calls the `tracing` facade directly** (user 2026-10-03 — 「로그 감싸지 마」). This is exactly the shape of the code now.
2. **base owns only the output configuration** (user 2026-10-03) — subscriber installation · level filter · file · format · changing the level while running (`crates/engram-dashboard-base/src/logging/`).
3. **Turning groups on and off is done not by wrapping but by `tracing`'s target** (the main session's answer to the user's question 2026-10-03 — can groups be turned on and off if they are gathered). The module path of the call site is the default target, and the `EnvFilter` that base installed (`crates/engram-dashboard-base/src/logging/mod.rs` — reading `RUST_LOG` `:401` · changing the level while running `:436`) filters by it. If a grouping different from module boundaries is needed (for example, mail), add `target: "<묶음>"` to the call. The category vocabulary is decided by big section A (logging system design).
   - Basis (code) — `tracing` keeps target · module_path · file · line as **static metadata (the callsite) fixed per place where the macro is called**. If the call site calls the macro directly, the module at that place becomes the target as it is.
4. **Secret masking goes at the place that actually prints** (user 2026-10-02 — 「base는 그걸 모르고 실제 찍는 곳에 걸어야 되는 거 아님?」 · 「매번 파싱해서 체크할 수는 없잖아 내부에서」). base's writer does not parse messages. base's `mask_secrets` stays as a generic tool that the calling side chooses to use — its patterns are generic vendor key formats (`sk-` · `AKIA` · `ghp_` etc. · Bearer tokens), so it has no domain knowledge (`mask_secrets` in `logging/mod.rs`).
5. **No gate of 「`tracing` 직접 의존은 base 만」 is set** (user 2026-10-03 — a consequence of decision 1).

## 거부한 대안

- **base provides the log entry point on its own path and every log goes through it (a macro with three arguments: risk level · category · message · direct `tracing` dependency only for base — blocked by a gate).** ★This is the first version of this ADR★ (written 2026-10-02 · memo decision candidate 3 · not pushed — this rewrite replaces that version). Rejected = user decision (2026-10-03 — 「로그 감싸지 마」). Reasons:
  - **Peer practice** — low-level crates call the `log` / `tracing` facade directly: wezterm `portable-pty` · rust-analyzer `stdx` · `cargo-util` · zed `util` · ripgrep · alacritty · nushell. No place in the sample routes call sites through a shared util crate (survey §1 — certain).
  - **Official guidance** — both the `log` and `tracing` docs say 「라이브러리는 facade 만 링크하고, 실행 파일이 백엔드를 설치한다」 (survey §4 — checked against the original text).
  - **Three of the control concerns of 2026-09-26 are covered even without wrapping** — ① output control already lives in one place in base (decision 2) ② masking was settled to be at the place that prints (decision 4) ③ changing the backend (subscriber · format · file) only touches base — because `tracing` itself is a facade.
  - **Wrapping would force platform to depend on base just for logging** — the user (2026-10-02): 「로그 때문에 Base 전체를 그렇게 포함시키는게 말이 안 됨」. platform has zero workspace dependencies (ADR-0266).
  - ★**Two things are not covered, and the cost is borne by the user decision 「로그 감싸지 마」 (2026-10-03)**★ — ① changing the facade (`tracing`) itself means fixing all call sites (about 530) (「영향」 below) ② logging rules (field names · format) cannot be enforced at the entry point. Both were in the original concern of memo decision candidate 3 (「로그 라이브러리 교체나 로그 규칙(필드 이름·형식) 강제」). Forcing a category argument on every call also falls under ② — it is replaced by the convention of adding `target:` where needed (decision 3), but being a convention, omitting it is not blocked. The ground for accepting ① is the main session's narrative that 「facade 교체는 드물다」 (said that way to the user before the decision), and it is not measured — **own assessment of the rejection basis: weak** (narrative).
- **Split out only the entry point into a small log-only crate — base · platform depend on only that (survey branch B).** Rejected = that is also wrapping, so the user decision 「로그 감싸지 마」 (2026-10-03) covers it + no peer precedent was confirmed — the closest, rustc's `rustc_log`, was seen only through a search summary (`docs/research/low-level-crate-logging-2026-10-02.md` §1 · 「한계 · 공백」).
- **Automatically apply masking to every line at the base writer stage (opt-in → default — the old main-session proposal of memo decision candidate 3).** Rejected = two user decisions (2026-10-02) — 「base는 그걸 모르고 실제 찍는 곳에 걸어야 되는 거 아님?」 (the printing side knows what is secret) · 「매번 파싱해서 체크할 수는 없잖아 내부에서」 (the cost of running a regex on every line — not measured). And the rejection reason of ADR-0138 still stands — the token is already in the same folder in plain text, so masking the log copy is redundant defense inside the same trust boundary (logic).

## 영향 / 불변식

- **There is no migration work** — the conversion of about 530 places to the base entry point that the first version planned (side work) and its final gate disappear.
- **The remaining cost: changing the facade (`tracing`) itself to something else still means fixing all call sites (about 530)** (main session's narrative). What ③ of the first item of 「거부한 대안」 covers extends only to replacing the backend (subscriber · format · file).
- **Direct `tracing` dependencies stay as they are now** — base · agent · daemon · discovery · messaging · net (behind an optional feature — `optional = true`) · the shell. If `command` takes on logging, it likewise depends directly on `tracing` only — it does not need to depend on base (ADR-0267).
- **The platform crate (ADR-0266) also calls `tracing` directly** — the `Drop` warning of `RmSession` (the `impl Drop for RmSession` in `crates/engram-dashboard-agent/src/platform/file_holders.rs`) moves over as `tracing::warn!` unchanged. There is no platform → base edge.
- **base's lock-poison-recovery warning (ADR-0269 decision 4) also calls `tracing::warn!` directly** — base already depends on `tracing`, so `sync` does not call base's `logging` module. No cross-references between residents (residency condition ③) still holds.
- **Test-side log observation stays as it is** — there is no reason to move the places where tests implement a `tracing` subscriber directly to capture logs (the daemon's `src/log_capture.rs` — its header comment also counts the two remaining copies `command_roster` · `control::mod` · agent `backend/codex/transport.rs` · `backend/claude/leftover.rs` · the shell's `daemon_client/usage_interest.rs` · `settings/tests.rs` — how to find them = `rg "impl (tracing::)?(subscriber::)?Subscriber for" crates src-tauri/src` (the forms that spell out the path split into three — `tracing::subscriber::` · `tracing::` · an imported `subscriber::` · 9 places, `56cb265`) · `with_default`).
- **ADR-0138 is not amended** — the synchronous writer · the folder is passed by the caller · the `LogKind` closed set · rejecting the masking layer all stay as they are.
- **The `tracing::` examples and field conventions of `docs/reference/logging-conventions.md` are exactly the shape of this decision** — there is nothing to move. The practical rule for adding a `target:` grouping (decision 3) is borne by that document.
- **The daemon's unused `tracing-subscriber` declaration (CLAUDE.md 「의존성」) is not tied to the migration** — it stays as an item in memo §11 and is looked at in step 4 (daemon cleanup).
- **Open item — big section A (logging system design):** the category · risk-level scheme and its vocabulary (the names of the `target:` groups in decision 3) · the entry point for changing the level while running.
- **Code anchor = `// ADR-0268`** — the head of base's `logging` module (the place that holds the output configuration).
