# ADR-0037: Location of transport semantics — Rust-only guard, thin frontend ProtocolClient

- 상태: 확정 (2026-06-27, basis: S14 module ① spike D1 user decision — option A)
- 관련: Amends ADR-0020 (decision 3: location of protocol semantics — JS ProtocolClient → Rust (DaemonClient/protocol_state)) · ADR-0036 (unified transport relay — this ADR fixes the location of its guard) · ADR-0011 (agentClient control surface — interface unchanged) · ADR-0029 (daemon-only, embedded carrier removed) · CLAUDE.md §5 · spike `docs/process/S14-multi-page-layout/module1-transport-spike.md` §5(D1) · Amended by ADR-0046 (the clause on where seq dedup/progress lives: Rust-only → per-view lastDeliveredSeq in the webview — the epoch first-stage filter stays in Rust)

## 맥락
ADR-0036 decided to unify the transport relay as src-tauri's single daemon client (+ `OutputRouter`), but left open **where to run the protocol semantics (dedup/epoch/seq guards, etc.)** (spike D1). ADR-0020 decision 3 gathered these semantics "in one place", a carrier-independent JS `ProtocolClient`; after that, ADR-0029 (daemon-only) removed the embedded carrier, and ADR-0036 made the structure one in which **a single Rust connection fans out to N windows**. If the semantics stay in JS in this structure, the guard runs N times, once per window (after routing), or the semantics are duplicated in two places → the "single connection, processed once" benefit of ADR-0036 disappears. So the guard location must be pinned down.

## 결정
The protocol semantics — request_id pending matching · seq high-water dedup · epoch guard · resubscribe (resume) · reject pending on disconnect — are **owned solely by Rust `DaemonClient` + `protocol_state`**. They are applied **once, before** `OutputRouter` routing on the daemon's single WS connection, and only clean output chunks are fanned out to the N windows. The frontend `ProtocolClient` shrinks to a thin carrier (`TauriTransport`), and **the `agentClient` interface that components depend on (ADR-0011) is kept to the letter** (only the implementation location moves JS → Rust; call sites are not modified).

With this, in ADR-0020 decision 3, "gather the protocol semantics in one place (the JS ProtocolClient)", *that one place* moves from JS to Rust (the rest of 0020's decisions — the single protocol · ConnectionCore message-level extraction · embedded racing serialization · no bypass of lease/viewport · crate location — remain valid).

## 거부한 대안
- **B (Rust first stage + JS defensive second stage)** — keep the existing JS guard as a second line of defense and add a first stage in Rust. The same guard semantics are **duplicated in two places**, Rust and JS, so there is a rot risk of updating only one side. It conflicts with the §5 single source of truth and the "brain = backend" stance.
- **C (JS only + Rust raw relay)** — Rust relays frames as they are and JS handles everything. For Rust to know which window to send to, it would have to **partially decode** the frames, and the guard runs **N times, once per window** → it halves the "single connection, processed once" benefit of ADR-0036, conflicting with the purpose of unification.

## 근거
§5 (brain = backend, frontend = pure I/O rendering) + ADR-0036 (unified relay, processed once before routing). Filtering once at the chokepoint where the single connection converges is the natural guard location in the N-window fan-out model — after routing (B/C) it would be duplicated/N times, proportional to the number of windows. Since the facade interface boundary of ADR-0011 is not touched (interface ≠ implementation), "thinning ProtocolClient" is not a violation of ADR-0011 but a move of the implementation location.

## 영향 / 불변식
- **ADR-0011 interface unchanged** — components and stores depend only on `agentClient` (no modification). Only the implementation locus inside the methods changes (JS → Rust).
- **Rust `protocol_state` preserves and ports ADR-0020 R2 (seq dedup/high-water — based on `lastDeliveredSeq`, the baseline is not touched by replay_from) and R3 (epoch guard/Resume — no resubscribe with epoch=null).** The two TS test files (`src/api/wsTransport.test.ts` · `protocolClient.test.ts`, 40+ cases) are the specification for the Rust port.
- **Concurrency-critical** — the daemon-owned parts of ADR-0001 (kill's 2 verbs) · 0005 (finalize once) · 0006 (lock order) · 0007 (epoch) are independent of the client (the client only sends Kill, handles Ack and does seq dedup). The `OutputRouter` update happens after the ViewManager lock is dropped (ADR-0006 preserved).
- **Accompanying internal decisions (D2~D5, spike §5):** D2 `ProtocolClient` ≈ `TauriTransport` (dependent on D1 = A) · D3 routing carrier = Tauri Channel (emit_to rejected, multi-window per-window safety confirmed with context7 + QA full measurement gate) · D4 the JS InProc mock is discarded (its purpose moves to the Rust headless unit T3) · D5 `commands/discovery.rs` ensure_lock is kept for now → removed if it is dead after confirming T2/T5 single DaemonClient.
