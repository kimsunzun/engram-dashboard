# ADR-0214: Open codex mail in both directions over MCP — turn approval off with a per-server spawn argument

- 상태: 확정 (2026-09-20, basis: user decision + codex 0.155.0 measured on 3 paths + code measurement)
- 관련: ADR-0116(no turn signal → inject immediately without a gate · decision 7) · ADR-0209(open send and receive together) · ADR-0133(mail surface gate) · ADR-0213(the `eg_` prefix) · ADR-0094(grant single source) · ADR-0097(claude is bypassPermissions) · ADR-0210(hook trust — a separate axis) · `crates/engram-dashboard-agent/src/backend/codex/mod.rs` · `crates/engram-dashboard-daemon/src/control/mod.rs:184` · step-log S21

## 맥락

codex was left out of mail entirely — `uses_mail` and `reads_messages` were both `false`, so a letter sent to a live codex agent **did not even queue up and was bounced at the entrance as 「수신자 없음」 (no recipient)** (the registry filter at `messaging_host.rs:165`).

The reason written on that `false` was 「바쁜 때를 못 가린다 — 터미널 모드에 턴 신호가 없다」 (it cannot tell busy time — terminal mode has no turn signal). ★**But that reason applies equally to terminal claude, and terminal claude already receives**★. Delivery is pushing bytes into the PTY (`session.rs:251` body → `confirm_written` → 500ms → submit byte), and claude and codex go through **the same code**. And ADR-0116 decision 7 had already nailed down 「턴 신호 없음 → 게이트 없이 즉시 주입」 (no turn signal → inject immediately without a gate) as policy, and in that ADR's rejected alternatives **「관측할 수 없으니 배달할 수 없다」 (we cannot observe it, so we cannot deliver) is explicitly rejected**. That is, what was blocking it was not a mechanical constraint but **two declaration lines**.

The one real remaining problem was **the sending side**. Receiving is us pushing, so there is no place for a gate to sit, but sending is **the agent calling our tool**, so it is caught by codex's approval policy.

## 결정

1. **Open codex mail in both directions** — `uses_mail`·`reads_messages`·`accepts_mcp_config` all `true`. This keeps the 「보내기·받기를 함께」 (send and receive together) that ADR-0209 required.
2. **The mail means is MCP (not the CLI mirror)** — a CLI call is **about 0.3 seconds slower per call** (user measurement), and mail has frequent round trips of request, reply and confirmation, so that difference accumulates.
3. **MCP tool approval is turned off with a spawn argument** — we add `default_tools_approval_mode='approve'` to the server override. **The scope is `mcp_servers.engram` alone**, and `approvalPolicy: on-request` and `sandbox: workspace-write` are left as they are — shell and exec approvals stay alive.
4. **Separate the 「파일을 쓰나」 (does it write a file) axis** — a new slot `writes_mcp_config_file` (default `false`, `true` only for claude). `accepts_mcp_config` derives only the mail routing (`mail_allowed = uses_mail && !accepts_mcp_config`).
5. **Make the existing switch that turns MCP off reach codex too** — the backend does not re-read the environment variable and looks at **the single observable signal** left by the decision the daemon made (does the endpoint hold the MCP grant for our server). If there is no grant, it **does not emit the override.**
6. **If the entrance cannot be built, close the codex spawn** — it fails only when 「엔드포인트가 있고 · MCP grant 가 있고 · 그런데 오버라이드 문자열을 만들 수 없다」 (there is an endpoint · there is an MCP grant · and yet the override string cannot be built). **No endpoint at all, or no grant, is a normal spawn** (a codex running without mail · the case turned off by the switch). For claude, the daemon's file-write `?` already does the same job, so this seam covers **only backends that do not write a file**.

## 거부한 대안

- **Open mail through the CLI mirror** — if `accepts_mcp_config=false` is kept, `mail_allowed` turns on, `engram mail send` opens, and even `engram help mail` works for codex (which does not work for claude). But **about 0.3 seconds per call** is added and mail has frequent round trips. *Rejection basis = user measurement.*
- **Open it for app-server (json) mode only** — it was the recommendation at one point. Its basis was 「터미널엔 턴 신호가 없다」 (terminal has no turn signal), but **that premise was wrong** (see the context section above), and then it switched to 「터미널에선 승인 다이얼로그에 답할 길이 없다」 (in terminal there is no way to answer the approval dialog), but **that also disappeared when `approve` removed the gate on all three paths**. *Rejection basis = measured twice.*
- **Let the user press once per spawn** — it actually holds (the dialog comes up in the agent terminal and the dashboard already shows that screen). But with `approve` there is no need to press, and ★**the `codex exec` path cannot be opened this way**★ (no human, so it fails unconditionally). *Rejection basis = measurement.*
- **`--dangerously-bypass-approvals-and-sandbox` or `-s danger-full-access`** — the gate is lifted, but it is **global**, so shell command approval and the sandbox are opened along with it. It is the same class as the precedent where ADR-0210 rejected `--dangerously-bypass-hook-trust` for the same reason. *Rejection basis = measurement + prior ADR.*
- **`default_tools_approval_mode='auto'`** — a valid value, but it **does not lift the gate** (measured). There are four valid values, `auto | prompt | writes | approve`, and **only `approve`** lifts it. ★The conclusion once reached, 「설정으로는 못 끈다」 (it cannot be turned off by settings), came from pointing at this value wrongly★ — we write it here to prevent the same misdiagnosis.
- **Register with `codex mcp add` to obtain trust** — the stored shape of the registered copy and the spawn-injected copy is **byte-for-byte the same**, and even when registered it **asks just the same** (measured). Registration does not buy trust. *Rejection basis = measurement.*
- **Have us detect the dialog and fire the keys** — it can be detected by the window title changing to `Action Required`, but ★**the same title comes up for shell approval too**★ (measured). You would have to look at the body to tell them apart, and it is cheaper to make it not appear in the first place with `approve`. *Rejection basis = measurement.*
- **Build a turn signal first** — ADR-0116 decision 7 already rejected that premise, and the fact that terminal claude runs without it is the corroboration. *Rejection basis = prior ADR + code measurement.*
- **Keep deriving the file write from `accepts_mcp_config`** — codex does not read that file (it receives the token via env), and the moment it is turned on, **a plaintext Bearer token JSON accumulates on disk at every spawn** with the default ACL, and since that write is **fail-closed**, if it fails the whole spawn dies. *Rejection basis = code measurement.*

## 근거

- **Delivery path measurement** — `service.rs:1691` `port.inject` → `messaging_host.rs:133` → `manager.rs:2580` → `session.rs:251` (body write → flush → 500ms → submit byte). No backend branch. There is **no** pulling path (`eg_messages` is a ledger query, not an inbox).
- **Turn signal measurement** — `output_core.rs:341` classifies `OutputEvent`, and in terminal mode only `TerminalBytes` flows, so **for both claude and codex the signal is 0** (`claude/mod.rs:499`·`codex/mod.rs:758`). The busy gate **falls to idle** when there is no observation (`busy.rs:178`) — that is, nothing stays in the queue forever and it is delivered immediately.
- ★**Approval gate measurement (codex 0.155.0, a throwaway `CODEX_HOME`)**★ — we stood up a stub MCP server and ran each of the three paths. Without `approve`: the TUI shows the dialog 「Allow the engram MCP server to run tool "eg_messages"?」, `codex exec` dies instantly with 「MCP tool call requires approval, but approval policy is never」, and app-server sends `mcpServer/elicitation/request`. With `approve` added, **the request disappears on all three paths** and the tool call reached the stub and a marker came back.
- **「항상 허용」 (Always allow) is not left on disk** — we compared hashes of the whole home before and after approval, and there was no trace of approval and **a new process asks again**. So the persistent path is **the spawn argument only**.
- **There is no approval at attach time** — `initialize` and `tools/list` pass with no review. Approval is attached **when called**. (Hooks are the opposite shape — there is a review at attach time. ADR-0210.)
- **Token handling** — the command line carries **only the env variable name** and the value goes through `ENGRAM_TOKEN`. In measurement, the token appeared only in the `Authorization: Bearer` header and was nowhere in the URL, the body or argv.

## 영향 / 불변식

- **Receiving is the same code regardless of backend** — this decision does not change that path. All that changed is **whether it gets on the registry** (`reads_messages`).
- ★**Accepted risk: an envelope can be injected mid-turn**★ — if the TUI is in a modal state (approval prompt · menu · plan confirmation), a widget can eat it. **Terminal claude already accepts the same level**, and ADR-0116 decision 7 stated it as a cost explicitly. codex does not get worse.
- ★**This decision does not touch hook trust**★ — `default_tools_approval_mode` sits under `mcp_servers.<서버>`, so it is dedicated to the MCP tool axis. The trust of the `SessionStart` hook for resume-id retrieval is separate and ADR-0210 owns it.
  - ★**But it was measured in this round that the same technique works on the hook axis too — we pass it to the next chunk**★. If you plant `trusted_hash` under `hooks.state` keyed by 「훅 출처:이벤트:순번」 (hook origin:event:ordinal), **that hook actually runs with no review screen** (measured twice — without planting, 「Hooks need review」; with planting, it passes + a marker is created). The scope is **that one hook**, and if the command is changed the hash differs and it is not covered, so it is a different thing from the global flag ADR-0210 rejected. ★**Price = the hash cannot be computed**★ — we tried matching 8 candidates and failed, and **the only way is to run codex once and read it back**. That is, every time the hook command string changes, the hash has to be taken again, and if it is not, **it quietly goes back to the review screen**. That synchronization burden is a separate decision matter, so we did not put it in today's scope. **One side measurement** — `projects."<경로>".trust_level` is a real key and was already `trusted`, yet **the hook review came up all the same** (project trust does not cover hooks).
- **`reads_messages()` cannot tell modes apart** — the method does not take `command`, so it cannot distinguish terminal from app-server. For now both just need the same answer, so there is no problem, but **the day we have to split it by mode, we must widen the signature or move the capability to the session side.**
- **The combination `accepts_mcp_config == true` + `writes_mcp_config_file == false` became legal** — codex is its legitimate case. But if a new backend turns on the former and **forgets** the latter, MCP is quietly not attached. The type cannot prevent this and **the declaration table (tripwire) is the only barrier**.
- **Document drift** — the codex column of `docs/reference/structure/agent-backend.md` was out of step with reality (this round created it). It was updated in the same round, and in the process **two cells that were stale independently of this round** (`can_resume_stored_session`·`capabilities().session.resume` — both had been written as 「app-server 만」 (app-server only) but are now `true` in both modes) were fixed along with it.
- ★**The instruction document is not actually loaded into codex — though the daemon ledger records it as 「가르쳤다」 (taught)**★. `wants_priming` becomes true for codex and `priming_file` is put in the endpoint, but the codex backend does **not translate** it into argv (there is no place to put it — the key that takes a path replaces the default prompt, and all the other candidate keys are rejected). So the invariant 「프라이밍이 가르치는 우편 채널 = 그 스폰이 쓸 수 있는 우편 채널」 (the mail channel priming teaches = the mail channel that spawn can use) is true only **vacuously** on this line. Today, what fills that gap is **the tool description** (ADR-0211), and it carries only 「어떻게 부르나」 (how to call) and cannot carry 「무엇을 해야 하나」 (what to do) (that behavior rules planted in a description are ignored is ADR-0211's measurement). **The path by which codex receives the instruction document remains unresolved.**
- **We found one pre-existing asymmetry but did not touch it in this round** — the `shell` backend has `reads_messages=false` yet inherits the trait default `true` for `uses_mail`. It is the shape that ADR-0209 wants to eliminate, with only sending open and receiving closed, but since `supports_control_channel=false` it cannot actually enter the mail plane and so is harmless. The declaration table has no `shell` row, so **nothing asserts this** — it is a place to look at together the next time that row is set up.
- **One regression net was turned into a synthetic one** — `a_backend_outside_the_mail_plane_gets_control_but_no_mail` (`daemon/tests/mail_gate.rs`) writes `{false,false,false}` in by hand. That is **because no backend declares that combination now**, and as a result this test **cannot catch drift in the real declarations.** The 「우편 평면 밖」 (outside the mail plane) path has live coverage of 0 until some backend enters that state again.
- **Verification (incomplete)** — we have not yet seen a real claude ↔ real codex round-trip mail even once. All the measurements were with a stub server and a separate harness. **That round trip is the real verification of this ADR, and it remains together with the GUI measurement.**
