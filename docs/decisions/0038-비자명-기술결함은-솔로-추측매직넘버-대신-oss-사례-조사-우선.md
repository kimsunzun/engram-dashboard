# ADR-0038: For non-trivial technical defects, survey OSS precedents first instead of solo guessing or magic numbers

- 상태: 확정 (2026-06-28, basis: the S14 flaky TOCTOU case + cross-family research)
- 관련: CLAUDE.md "참조 구현" section · `docs/reference/debugging-conventions.md` (practice rules) · `.claude/skills/qa/references/bindings/engram.md` (trigger binding) · `docs/research/toctou-concurrency-test-verification-research-2026-06-28.md` (basis) · `docs/process/step-log.md` (S14)

## 맥락
During S14 QA, when we hit the flaky TOCTOU test (`toctou_stress_reconnect_no_stale_down_clobber`), the main session fell into **solo debugging that tried to make it pass by adjusting a magic number (server hold 5ms → 50ms)**. The user stopped this and instructed "don't fix technical defects alone; solve them with reference to OSS cases", and `/research` (cross-family) reached the conclusion "loom is low-ROI for our async → unit level + deterministic tests is the right answer", which solo tuning could never have produced.

The project already has a "reference implementation" principle (when implementing a new *feature*, survey mature OSS first), but that principle **applies only to feature implementation and not to *defect fixing***, so in debugging mode we drifted to symptom suppression (a magic-number band-aid) — that is the root gap. This convention is a **self-awareness behavioral guard** that a hook cannot enforce mechanically (a hook cannot judge the meaning of "typing a magic number"), so *how to make it discovered and triggered* is the core of the decision.

## 결정
When we meet a non-trivial technical defect (concurrency · race · perf/timing · memory · architecture, etc. — areas where *mature OSS has a canonical answer and naive fixes are often wrong*), do not remove the symptom by solo guessing or magic-number adjustment; **first survey how mature OSS solves the same class (`/research` · subagent), build the root-cause solutions as options, and then fix it.**

- **Trigger = 2 signals** (it fires if either is on): ① adjusting a magic number · timing constant · threshold · retry count to "make a failure/flaky/slowness pass" (= erasing only the symptom without understanding the root cause) · ② failing once with a speculative fix on a non-trivial technical defect and still trying to run further solo.
- **Excluded** (blocking over-triggering): trivial bugs with a clear cause · typos · deterministic fixes / project-specific business logic with no OSS precedent.
- **Delivery = 4 layers** (the same pattern as engram's documentation system = commenting/logging-conventions): discovery (a one-line stance in CLAUDE.md "참조 구현" + a reference pointer — auto-loaded every session) / **trigger** (a one-line trigger in the `/qa` engram binding — it turns on at the moment, since flaky · timing · perf failures *actually show up* there) / depth (the body of `reference/debugging-conventions.md`) / basis (this ADR).

## 거부한 대안
- **Only one line in CLAUDE.md (no trigger surface)** — CLAUDE.md loads every session so "discovery" happens, but a buried single line is weak at triggering *at that moment* (it depends on self-awareness, no hook is possible). Like this case, one knows the rule and still falls into a magic number → supplemented by adding a trigger line in the `/qa` flow where the signal actually appears.
- **A single location (only reference OR only ADR)** — engram's documentation system enforces the separation of "why (ADR) vs practice rules (reference canon)" (`docs/README.md`, the commenting-conventions + ADR-0032 pattern). With one place, the "why and rejected alternatives" disappear (reference only), or there is no place for the body of the practice rules (ADR only).
- **A domain-category trigger ("for concurrency work, OSS first")** — being an abstract classification, "is this that kind of work now" is ambiguous at every moment, so it cannot pin the trigger time. A behavioral signal (the moment of *typing* the magic number) is self-verifiable and hits this case directly.
- **Mechanical enforcement with a hook** — "trying to pass the symptom with a magic number" is a judgment of meaning, so a hook cannot catch it. So we go with a behavioral guard + a workflow (qa) trigger.
- **A strict trigger (2 signals + even a domain filter)** — it gets long and ambiguous, causing over/under-triggering. The 2 signals are the minimal self-verifiable form.

## 근거
- **The direct case:** flaky 5ms → 50ms solo tuning (anti-pattern) ↔ deriving loom low-ROI and deterministic units through `/research` (per the convention) — the latter gave the root solution + "knowledge that solo tuning could not obtain". Report `docs/research/toctou-concurrency-test-verification-research-2026-06-28.md`.
- **The project's own decision criterion:** CLAUDE.md §0 "low risk + long term → lay it down properly now (over-engineering allowed)" — a standing convention is low-risk and long-term, so the cost of laying it down in 4 layers now is small and the cost of losing the "why" is large.
- A **defect-fixing sibling rule** of "reference implementation" (OSS first for feature implementation) — extending the same principle to debugging.
- The split between discovery and trigger comes from the observation (this case) that *a self-enforced behavioral convention dies if it does not fire at that moment*.

## 영향 / 불변식
- **Add a trigger point to the `/qa` and (optionally) `/review` flows** — if one tries to pass a flaky/timing/perf failure with a magic number, stop and switch to an OSS survey. Without this trigger point the convention is only discovered and never fires (a dead convention).
- `docs/reference/debugging-conventions.md` new = the single source of the practice rules (body · trigger · exclusions). CLAUDE.md holds only a one-line stance + a pointer (no copy-paste of the body = rot prevention).
- **Composed with context hygiene:** when triggered, the survey is delegated to a subagent/`/research` (no broad direct survey by the main session) — this invokes the same mechanism as the global-rules "컨텍스트 위생" at the *defect-fixing* moment.
- If violated (erasing only the symptom with a magic-number band-aid): the root cause stays unsolved + a flaky/regression stays latent (it blows up again in the next session, like this baseline's ~1/20).
