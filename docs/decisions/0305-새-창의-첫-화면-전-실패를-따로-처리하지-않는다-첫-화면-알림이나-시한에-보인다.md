# ADR-0305: A failure before a new window's first paint is not handled separately — the window is shown on the first-paint notice or the deadline

- 상태: 확정 (2026-10-26, basis: user decision 2026-10-24 (T1 — 「웹 화면 프로세스가 죽는 드문 경우」) · TRD version 0.2 withdrew version 0.1's design and PRD version 0.5 withdrew the requirement (`d465933b`))
- 관련: PRD `docs/process/S21-window-chrome/prd.md` (version 0.5 — R1 · R6 · AC2 · no AC33 · D13 · head 「0.5판」 ①) · TRD `docs/process/S26-window-chrome/trd.md` (version 0.3 — head 「0.2판」 ① · §5-3 · §12-2 T1 · §12-4 ⑥ · §13 #1 · §14 「그리기 전에 보인 창」 · §15-1 · §15-3) · ADR-0299 decision 3 (a window appears together with its content — the first-paint gate) · ADR-0300 (window number — D13 exception) · ADR-0302 decision 10 (the creation reply) · `src-tauri/src/first_paint.rs` · step-log S26

## 맥락

PRD version 0.4 (default — the main agent's proposal · reflecting 2026-10-23 reviews 1 · 2) required that, if the webview of a new window that has received a number and entered the model dies or is decided to have failed before drawing its first paint, ① the call that created the window answers with a failure that carries the reason, ② the shell withdraws the OS window it created (even a warm window that was handed over, without returning it to the pool), and ③ it is removed from the model, the number is released immediately, and the tabs are sent back to the source window (if it is in the model and not closing) or else to main. That requires the window-creating call to wait until the first paint or the failure decision before answering. Today the first-paint gate does not treat it as a failure; even if the notice never arrives, it only shows the window at the deadline (1.5 s) (head of `first_paint.rs`).

TRD version 0.1 (2026-10-23 · before review) built that design — first-paint waiting · deadline failure · rollback (`WindowHost::await_painted` · `abort_new_window` · `TabsFate` · withdrawing the 1.5 s deadline show · the old U7). Many of the findings of the version 0.1 review (codex Designer · Claude Architect-breaker — both FIX) were tied to that design. ★The version 0.1 body is not in the repository — the withdrawn list is recorded in the TRD head 「0.2판」 ① · §15-1 · §15-3★.

## 결정

1. **A failure of a new window before its first paint (the webview dies before the first paint) is not handled separately** (user decision 2026-10-24 — T1 · 「웹 화면 프로세스가 죽는 드문 경우」). A new window is shown, as now, on the first-paint notice or the deadline (`first_paint::FALLBACK_REVEAL` — 1.5 s).
2. **The window-creating command does not wait for the first paint** — once it opens the OS window and puts it in the model, it answers success with `{ window, window_id, number }` (TRD §5-3 · ADR-0302 decision 10). Sequence = open (outside the lock) → insert (lock — receives the number) → notify (outside the lock — applies the title) → confirm (`settle_new_window`) → reply.
3. **A webview dying before or after the first paint is not treated as a creation failure** — that window is left as an empty window and a human closes it (TRD §14).
4. Accordingly, from PRD version 0.4 the following were withdrawn: R1's 「모델에 든 뒤 첫 화면 전 실패」 · R6's failure reply · AC33 · part of AC2's 「보이는 순간 번호가 있다」 · D13's exception 「한 번도 보이지 않은 창의 번호는 곧바로 빈다」 — D13's exception changed to 「OS 창이 이미 없는 창」 (ADR-0300 decision 3). The warm-window row's 「번호 없이 보이는 창이 없다」 was also withdrawn (PRD version 0.5 R1).

## 거부한 대안

- **First-paint waiting · deadline failure · rollback** (TRD version 0.1 §5-2 · §5-3 — the window-creating call waits for the first paint and then answers · if a deadline decides failure, it withdraws the opened window and sends the tabs back to the source window or main · `WindowHost::await_painted` · `abort_new_window` · `TabsFate` · withdrawing the 1.5 s deadline show · the old U7 — the shape of the requirements in PRD version 0.4 R1 · R6 · AC33) — the user decided not to handle it separately, calling it 「웹 화면 프로세스가 죽는 드문 경우」 (2026-10-24). Rejected = user decision 2026-10-24 (TRD §12-4 ⑥ lists this branch as a rejected alternative).
- **Catch the webview termination signal `ProcessFailed` and decide failure** (TRD §12-4 ⑥) — withdrawn by the same user decision. The TRD and PRD give no other rejection reason. Rejected = user decision 2026-10-24 (no other reason recorded).

## 근거

- User decision PRD §5-1 (2026-10-24 — T1) · TRD §12-2 T1.
- Of the version 0.1 review findings, those tied to this design (the failure-handling share of codex ③ · ④ · ⑥ · Claude ① · ② · ⑧) lost their subject with T1 (TRD §15-1). Version 0.1's U7 (first-paint waiting · rollback) was withdrawn, and the remaining 「만들기 답」 share became version 0.2's U6 (TRD §15-3).

## 영향 / 불변식

- **Accepted** (TRD §14 「그리기 전에 보인 창」): a new window that is shown first at the 1.5 s deadline may show only the background for a moment, without the number marker · title row · a window whose webview died is left as an empty window (a human closes it).
- The first-paint gate's notice · the 1.5 s deadline show stay as they are (ADR-0299 decision 3 — not changed).
- The minimum-window-width report is sent before the first-paint notice but has a wait cap (300 ms), so it does not block the first paint — a window shown early by the deadline · cap can be widened after it is shown (ADR-0303 decision 9 · accepted with T1).
- Bringing this handling back needs a new user decision and a new ADR — the reply shape of the three places that create a window (ADR-0302 decision 10) and the number lifetime (ADR-0300) change together.
