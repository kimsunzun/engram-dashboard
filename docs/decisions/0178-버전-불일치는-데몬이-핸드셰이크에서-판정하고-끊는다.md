# ADR-0178: The daemon decides a version mismatch at the handshake and cuts the connection

- 상태: 확정 (2026-09-04, basis: user decision — it came up in the design conversation for ADR-0177's `transport` crate, and **the same day the user overturned the draft**. ★**This ADR changed not a single line of code. Only two places were read — decision 2 and the two measured lines attached to the last item of 「거부한 대안」 are all of it, and the rest are the unverified items in 「영향 / 불변식」**★)
- 관련: Supersedes ADR-0158 · ADR-0158 decision 1 (version bump criterion = envelope grammar breakage — ★the premise this decision stands on★) · ADR-0158 decision 3 (no automatic daemon kill — still alive) · ADR-0158 decision 5 (a deadline on every request + correlation marked on errors — still alive) · ADR-0177 decision 3 (opaque handshake frame — this decision rides on that hook) · the `1006` item of ADR-0177 「거부한 대안」 (★do not confuse — the second item of 「근거」★) · ADR-0129 (net vocabulary isolation) · ADR-0179 (multi-client, multi-daemon — the decision is the daemon's alone, so it is independent of the number of peers) · `crates/engram-dashboard-net/src/ws.rs` (★the real decision code is already here★) · `crates/engram-dashboard-protocol/src/lib.rs` (`PROTOCOL_VERSION`) · `crates/engram-dashboard-discovery` (the daemon is rejected on a version mismatch — ★suspected second decider, unchecked★) · `AgentEvent::Hello` (the place for capability advertisement) · step-log S21

## 맥락

The problem ADR-0158 solved is still alive — the daemon's reason to exist is to survive the app being closed, so **a combination of a new app and an old daemon occurs normally.** Deployment is by unpacking an archive, so there is no step during installation that kills the daemon.

In that situation ADR-0158 chose **not to cut** — the daemon advertises its capabilities with `AgentEvent::Hello` right after connecting, the client does not send any command that is not in the advertisement, and a banner tells the user once at startup. What reopened this arrangement was ADR-0177. While settling **what the handshake of the new `transport` crate must decide**, it became clear that putting the version decision there means either the crate comes to know the version and capability vocabulary (the very leakage ADR-0129 forbade for net) or the consumer must inject a decision function.

**This session's draft kept 「끊지 않는다」 (do not cut) as it was and only moved the decision to request time.** The user overturned it (2026-09-04). Two reasons:

1. **A different version can cause malfunction.** **Cutting and telling** is better than quietly running wrong, and it is also simpler.
2. **And the fact that backs that judgment is inside this repository** — `PROTOCOL_VERSION` is bumped ★**only when the envelope grammar itself breaks**★ (ADR-0158 decision 1 — that clause is still alive). Then a version mismatch means not 「기능 몇 개 차이」 (a few features differ) but **the two sides cannot understand each other at all**, and the connection is unusable even while attached. ★**The ground that held up 「끊지 않는다」 weakens right here**★ — what not cutting was meant to protect (what works while attached still works) does not exist when the grammar is broken.

## 결정

**The daemon decides a mismatch at the handshake and cuts. The client receives the rejection reason and reports it with a popup.**

1. **The decider = the daemon alone.** The client puts its own version in the first frame, and if it does not **match the daemon's expected value exactly, the daemon sends the reason and cuts.** ★**No range or compatible interval is used**★ — the version goes up only 「말이 안 통할 때만」 (only when the two sides cannot talk), so there is nothing to look at in between.
2. ★**This is already implemented (measured 2026-09-04)**★ — the handshake in `crates/engram-dashboard-net/src/ws.rs` sends `handshake_error_frame("protocol_version mismatch: client {} != server {}")` and closes when `protocol_version != expected_protocol_version` (a test in the same file asserts that reason string — **the test was not run**). The expected value is an **injected value** supplied by the assembly code. That is, **this ADR approves that behavior as canonical; it does not create a new mechanism.** What changes is the layer above it, namely **the client's reaction**.
3. **There is no client-side version check.** The daemon **always** sees the client's number, so it **covers both directions (new client + old daemon / old client + new daemon) by the daemon alone.**
4. **No handshake reply (a frame where the daemon tells its own version) is created.** The rejection reason takes over that role. So the client **does not need to know the daemon version in advance**, and for this purpose **the dependency on the local port file is no longer needed either.**
5. **The client receives that rejection reason and shows a popup — this is the only part to build new.** The popup ★**offers 「데몬 재시작」 (restart the daemon)**★. 「새 버전을 받으세요」 (get the new version) is **wrong guidance** in most cases — when the app is updated, the new client and the new daemon **files are installed together, but the running daemon is still the old version**, so the user already has the new version in hand and what is needed is a restart.
6. **The capability advertisement is not used as the basis for the decision** — ADR-0158 decision 2 (`AgentEvent::Hello` advance advertisement + 「광고에 없으면 안 보낸다」 (do not send what is not in the advertisement)) dies here. ★**This does not mean to remove the advertisement mechanism itself right now**★ — the slot may stay as it is, and whether to remove it is a separate matter.

## 거부한 대안

- **Keeping ADR-0158's 「끊지 않고 한 번 알린다」 (do not cut, tell once)** — **the malfunction risk** is the first reason. And since the version goes up only when the envelope grammar breaks, **it cannot be used even while attached** — the gain not cutting was supposed to buy is absent under that condition. **Basis for rejection = user judgment + consistency with ADR-0158 decision 1** (as long as that decision is alive, a mismatch is a grammar breakage).
- **Decision at request time — ★the draft that remains in this file's file name★** — a way of returning a version error per command and reporting at the place where it failed. Its advantage was 「되는 건 되고 안 되는 것만 실패한다」 (what works works and only what does not fails), but ★**when the grammar is broken nothing works, so that advantage does not hold**★. On top of that, an error path and a notification policy must be managed per command, so it is **more complex** — the adoption reason 「심플한 쪽」 (the simple side) lay on the other side.
- **A check on both client and daemon** — justified as 「각자 상대가 낡았을 때를 막는다」 (each guards against the other side being stale), but ★**false**★: the daemon always sees the client's number, so it **covers both cases alone**. With both sides checking, the decision logic becomes two and **can disagree**. **Basis for rejection = measured** (decision 2 above — the daemon already covers both directions).
- **Advertising the daemon version in a handshake reply** — the rejection reason already carries that information. Adding a frame **grows the wire and creates one more compatibility clause, 「옛 데몬은 그 답장을 안 보낸다」 (an old daemon does not send that reply).**
- **The client automatically killing the old daemon and starting a new one** — ★**ADR-0158 decision 3 「데몬 자동 kill 금지」 (no automatic daemon kill) is still alive**★. A form where **the user presses a button in the popup to consent** does not conflict with the purpose of that ban (do not let it die without anyone knowing). ★**But whether to build that button is not decided by this ADR — undecided**★. Three reasons: ① restarting the daemon takes down the agents inside it (session restore takes them over, but not smoothly) ② ~~there is **no** protocol command that corresponds to 「그만 꺼져라」 (stop and shut down) (measured 2026-09-04 — `crates/engram-dashboard-protocol/src/messages.rs` has 0 Shutdown, Restart or Quit variants. `RestartPolicy` in the same file is the **agent restart policy**, so it is not this)~~ ★**Correction 2026-09-06 (ADR-0180) — this measurement is false**★: such a command **does exist** — `AgentCommand::StopDaemon { force, kill_agents, request_id }` (`messages.rs:89`, whose comment says 「데몬 종료(§5 LLM 제어)」), and discovery's `build_stop_command` (`crates/engram-dashboard-discovery/src/lib.rs:772`) builds it and the shell calls it in `src/api/daemonControl.ts`. ★**The error is reading the literally true fact that there are 0 variants *named* Shutdown, Restart or Quit as 「그런 명령이 없다」 (there is no such command).**★ **But the rejection this item supported still stands** — ③ below is the reason (when the grammar is broken that command also **does not get through**), and ADR-0180 confirmed it in the real code: sending `StopDaemon` requires passing authentication, a version mismatch is rejected there, and discovery's `stop_with_sender` treats `VersionMismatch` as `NoTarget`. **The only thing that changes is this one line of fact; the decision and the rejection are not reopened.** ③ even if it had existed, ★**it does not get through when the grammar is broken**★ — only a forced kill remains.

## 근거

- **Cutting is the safer side** — with a silent malfunction the user **cannot find the cause**. If it cuts and says why, at least the user knows what the problem is. The judgment is that failing to attach is better than causing damage that cannot be undone.
- **At handshake time the reason is actually delivered** — nothing is backed up yet, so the reason can be carried in the close frame. ★**This is a different situation from ADR-0177's 「큐가 꽉 찬 연결을 끊을 때는 사유가 전달되지 않는다」 (when a connection with a full queue is cut, the reason is not delivered) (RFC 6455 `1006`) — do not confuse them**★. The reason disappears there because of **congestion or abrupt termination**, and here it is the **first reply the server sends, chosen in the normal way**.
- **Remote becomes the same as local** — since the client **does not need to know the daemon version in advance** (decision 4), it is **the same path** even for a remote with no port file. Because the decision is the daemon's alone, the path does not split however many peers there are (ADR-0179).

- ★**Decision 4's exception clause 「모달은 앱이 아예 못 붙을 때만」 (a modal only when the app cannot attach at all) does not die and in fact triggers**★ — under the new decision the client **truly cannot attach.** That is, the popup sits inside the exception ADR-0158 dug for itself, and it also does not collide with the rejection reason for the alternative that ADR rejected, 「올리되 모달로 안내한다」 (bump it but guide with a modal) (a state that appears without the user asking for it belongs in a banner). **Whether the clause "no action button" lives or dies is undecided** — the last item of 「거부한 대안」 above left it open.

**ADR-0158's invariants section:**

- ★**Dies — 「광고에 없는 명령은 보내지 않는다」 (do not send a command that is not in the advertisement)**★. This discipline was the real code of the decision.
- **Dies — 「능력 광고 칸은 없어도 깨지지 않아야 한다」 (it must not break even without the capability advertisement slot)**. It was the clause that held up the decision, so it loses force with it. ★**This does not mean to delete the slot right now**★ (decision 6).
- **Lives — 「`PROTOCOL_VERSION` 상향은 봉투 문법이 깨질 때로 한정」 (raising PROTOCOL_VERSION is limited to when the envelope grammar breaks)**. ★If this dies the whole ADR collapses★ — once the version starts going up for feature differences too, 「불일치 = 말이 안 통함」 (mismatch = cannot talk) becomes false, and at that moment the 「끊지 않는다」 side becomes right again.
- **Lives — 「데몬을 자동으로 죽이는 경로를 만들지 않는다」 (do not create a path that kills the daemon automatically)**.
- **Lives — 「알림 표면은 새 전역 핸들을 늘리지 않고 기존 제어 표면에 얹는다」 (the notification surface rides on the existing control surface without adding a new global handle)** (CLAUDE.md 「LLM-우선 제어」). Only the point of notification moved; it still notifies — what a human sees and what an LLM reads must come from the same source. ★**But which surface that popup stands on was not decided by this ADR — undecided**★.
- **Kept as accrued — 「세대를 겹쳐 돌리고 옛 데몬은 자기 세션이 끝날 때까지 살려 둔다」 (run generations overlapping and keep the old daemon alive until its own sessions end)** (long-term direction, not in this scope). ★**This reversal raises its value**★ — since cutting was chosen, that is now the only way to solve 「데몬을 죽이지 않고도 새 앱이 일한다」 (the new app works without killing the daemon) structurally.

**ADR-0158's rationale section — where it parts:**

- **The fact stays but drops out of the decision basis — 「`AgentEvent::Hello` 가 데몬 전체 능력을 싣고 온다」 (AgentEvent::Hello carries the daemon's full capabilities)** (that ADR's measurement). It is still true but holds nothing up.
- ★**Collides head-on — 「업계 관행은 버전 숫자 하나로 전부 끊기에서 멀어져 있다」 (industry practice has moved away from cutting everything on a single version number)**★ (the `/research medium` conclusion of that ADR). This decision goes the opposite way from that practice. **We do not hide it — but it does not mean that survey was wrong; it means its premise does not fit us:** the cases surveyed are protocols where a version difference is a **feature difference**, and our version goes up **only on grammar breakage**. ★**This reinterpretation was not checked against the original survey by reopening it — unchecked**★.
- **Lives — 「무한 대기는 버전 문제로만 볼 수 없다」 (an infinite wait cannot be seen only as a version problem)** (deadlines and correlation prevent other failures). It is the pair of decision 5, so it lives with it.
- **Lives — 「고지 시점은 영향 범위를 따른다」 (the notice point follows the scope of impact)**. That principle is written as 「조건이 계속 유지되는 것이면 앱 차원에서 미리」 (if the condition keeps holding, at the app level in advance), and **the connection rejection popup is exactly at the app level** — this decision is closer to that principle than the draft (a notice at the request site).
- **Lives — the rejection of the alternative 「알림 없이 조용히 기능만 비활성」 (silently just disable features with no notice)** · **the rejection of 「버전 개념을 없앤다」 (abolish the version concept)**. Both remain rejected.
- ★**Half lives — the rejection of the alternative 「관례대로 (명령 추가로) 버전을 올린다」 (bump the version as is customary (for adding a command))**★. **The clause lives** (it is the flip side of decision 1 — adding a command still does not bump it). **But the back half of the sentence that held up that rejection, 「올리면 업그레이드하는 모든 사용자가 못 붙는다」 (if bumped, every user who upgrades cannot attach), is no longer an argument against** — because this decision **accepted** that everyone cannot attach when the version really splits. The remaining reason for rejection is **one only: 「명령 추가는 그 등급이 아니다」 (adding a command is not of that grade).**

### Other

- **Consistent with ADR-0177 decision 3** — `transport` **only carries the handshake frame, and 「계속할지 끊을지」 (whether to continue or cut) is decided by the consumer**. That hook is on the **server side**, and the daemon looks at the version there. That is, the crate still does not know the version vocabulary (ADR-0129's vocabulary isolation is kept). ★Conversely, moving the decision to the client would require the hook on both sides★ — decision 3 prevents that.
- **The only new thing to build is one client popup.** The daemon side approves what already exists (decision 2), and the wire does not grow either (decision 4).
- ★**Not verified — this session did not check code other than the two places above**★:
  1. **It was not checked whether the client actually receives and reads that rejection-reason frame now** (unchecked). If it does not read it, decision 5 becomes not 「팝업을 붙인다」 (attach a popup) but 「사유를 꺼내는 경로부터 만든다」 (first build the path that extracts the reason).
  2. **It was not checked whether the client keeps reconnecting endlessly after being rejected** (unchecked). If it does, the popup may appear on every attempt, so a separate display policy is needed.
  3. **An old client (no popup code) just sees it as cut and only keeps reconnecting** — it is old software, so **it cannot be fixed**. ★**Even so, it is better than malfunction — that is this decision's judgment**★ (user judgment 2026-09-04). It means the 「이유가 안 보이는 무한 재연결 중」 (endlessly reconnecting with no visible reason) seen at the 1→2 bump **is reproduced as is** on old clients.
  4. ★**Suspected second decider — it was not checked whether the 「버전 불일치 시 데몬 거부」 (the daemon is rejected on a version mismatch) path of `crates/engram-dashboard-discovery` is still alive**★ (unchecked). The 관련 line of ADR-0158 pointed to that path. If it is alive, the decision lives in **two places, the daemon handshake and discovery**, which is **the same kind of violation** as decision 1 (the decider = the daemon alone) and decision 3 (with two pieces of logic they disagree) — the first point to check for this decision is there.
