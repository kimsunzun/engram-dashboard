# ADR-0178: The daemon decides a version mismatch at the handshake and drops the connection

- 상태: 확정 (2026-09-04, basis: user decision — it came out of the design conversation about the `transport` crate of ADR-0177, and **the user reversed the draft the same day**. ★**This ADR did not change a single line of code. There are only two places it read — the two measured lines attached to decision 2 and to the last item of 「거부한 대안」 are all of it, and the rest are the unverified items of 「영향 / 불변식」**★) · 부분 폐기 by ADR-0342 (decision 5: client popup) · 부분 폐기 by ADR-0343 (the open restart button in the rejected alternatives)
- 관련: Supersedes ADR-0158 · ADR-0158 decision 1 (the criterion for bumping the version = breakage of the envelope grammar — ★the premise this decision stands on★) · ADR-0158 decision 3 (no automatic daemon kill — alive) · ADR-0158 decision 5 (a deadline on every request + a correlation mark on errors — alive) · ADR-0177 decision 3 (opaque handshake frames — this decision rides on that hook) · the `1006` item of 「거부한 대안」 in ADR-0177 (★do not confuse — the second item of 「근거」★) · ADR-0129 (net vocabulary isolation) · ADR-0179 (multi-client, multi-daemon — the decision is the daemon's alone, so it does not depend on the number of peers) · `crates/engram-dashboard-net/src/ws.rs` (★the actual decision code is already here★) · `crates/engram-dashboard-protocol/src/lib.rs` (`PROTOCOL_VERSION`) · `crates/engram-dashboard-discovery` (daemon rejection on version mismatch (버전 불일치 시 데몬 거부) — ★suspected second decision maker, unverified★) · `AgentEvent::Hello` (the place of capability advertisement) · step-log S21 · Amended by ADR-0342 (decision 5: client popup) · Amended by ADR-0343 (the open restart button in the rejected alternatives)

## 맥락

The problem ADR-0158 solved is still alive — the daemon exists to survive the app being shut down, so **a combination where only the app is new and the daemon is old occurs normally.** Deployment unpacks an archive, so there is no step in installation that kills the daemon.

In that situation ADR-0158 chose **not to drop the connection** — the daemon advertises capabilities with `AgentEvent::Hello` right after connect, the client does not send commands missing from the advertisement at all, and the user is told once with a banner at startup. What reopened this arrangement was ADR-0177. While deciding **what the handshake of the new `transport` crate has to decide**, it came out that if the version decision is put there, either the crate comes to know version and capability vocabulary (the very leak ADR-0129 forbade for net), or the consumer has to inject a decision function.

**This session's draft left 「끊지 않는다」 as it was and moved only the decision to request time.** The user reversed that (2026-09-04). Two reasons:

1. **A different version can cause misbehavior.** **Dropping and telling** is better than silently running wrong, and that is also simpler.
2. **And the fact that backs that judgment is inside this repository** — `PROTOCOL_VERSION` is bumped ★**only on a change that breaks the envelope grammar itself**★ (ADR-0158 decision 1 — that clause is alive). Then a version mismatch means not 「기능 몇 개 차이」 but that **they cannot talk to each other at all**, and even attached, it cannot be used. ★**The ground that held up 「끊지 않는다」 weakens right here**★ — what we tried to protect by not dropping (what works while attached still works) does not exist when the grammar is broken.

## 결정

**The daemon decides a mismatch at the handshake and drops the connection. The client receives the rejection reason and shows it in a popup.**

1. **Decision maker = the daemon alone.** The client puts its own version in the first frame, and if it does **not exactly match** the daemon's own expected value, the daemon **sends a reason and drops the connection.** ★**No range or compatible interval is set**★ — the version is bumped 「말이 안 통할 때만」, so there is nothing to look at in between.
2. ★**This is already implemented (measured 2026-09-04)**★ — if the handshake in `crates/engram-dashboard-net/src/ws.rs` finds `protocol_version != expected_protocol_version`, it sends `handshake_error_frame("protocol_version mismatch: client {} != server {}")` and closes (a test in the same file asserts that reason string — **we did not run the test**). The expected value is an **injected value** put in by the assembly part. So **this ADR approves that behavior as canonical; it does not build a new mechanism.** What changes is the layer above it, namely **the client's reaction**.
3. **We do not put a version check on the client side.** The daemon **always** sees the client's number, so it **covers both directions** (new client + old daemon / old client + new daemon) **by the daemon alone.**
4. **We do not create a handshake reply (a frame in which the daemon tells its own version).** The rejection reason takes over that role. So the client **does not need to know the daemon version in advance**, and for this purpose **the local port-file dependency also becomes unnecessary.**
5. **The client receives that rejection reason and shows a popup — this is the only part to build new.** The popup ★**proposes 「데몬 재시작」**★. 「새 버전을 받으세요」 is a **wrong instruction** in most cases — when the app is updated, the new client and new daemon **files are installed together, but the running daemon is still the old version**, so the user already has the new version in hand and what is needed is a restart.
6. **We do not use capability advertisement as the basis of the decision** — ADR-0158 decision 2 (`AgentEvent::Hello` pre-advertisement + 「광고에 없으면 안 보낸다」) dies here. ★**This does not mean tearing out the advertisement mechanism itself right now**★ — the field may stay as it is, and whether to remove it is a separate matter.

## 거부한 대안

- **Keeping 「끊지 않고 한 번 알린다」 of ADR-0158** — the **misbehavior risk** is the first reason. And since the version is bumped only when the envelope grammar breaks, **it cannot be used even while attached** — the gain we meant to get by not dropping does not exist under that condition. **Basis of rejection = user judgment + consistency with ADR-0158 decision 1** (as long as that decision is alive, a mismatch means a grammar breakage).
- **Request-time decision — ★the draft that remains in this file's filename★** — a way of returning a version error per command and telling the user at the place where it failed. Its advantage was 「되는 건 되고 안 되는 것만 실패한다」, but ★**when the grammar is broken nothing works, so that advantage does not hold**★. On top of that, an error path and a notification policy have to be managed per command, so it is **more complex** — the reason for adopting it, 「심플한 쪽」, lay on the opposite side.
- **Checking on both the client and the daemon** — justified by 「각자 상대가 낡았을 때를 막는다」 but ★**false**★: the daemon always sees the client's number, so it **covers both cases alone**. With both sides, the decision logic becomes two and **they can diverge**. **Basis of rejection = measured** (decision 2 above — the daemon already covers both directions).
- **Advertising the daemon version with a handshake reply** — the rejection reason already carries that information. Adding a frame **grows the wire and creates one more compatibility clause: 「옛 데몬은 그 답장을 안 보낸다」.**
- **The client automatically kills the old daemon and starts a new one** — ★**ADR-0158 decision 3 「데몬 자동 kill 금지」 is alive**★. A form where **the user presses a button in the popup to consent** does not conflict with the intent of that ban (not to die without anyone knowing). ★**But whether to build that button is not decided by this ADR — open**★. Three reasons: ① restarting the daemon takes down the agents inside it (they are picked up again by session restore, but not smoothly) ② ~~there is **no** protocol command corresponding to 「그만 꺼져라」 (measured 2026-09-04 — 0 Shutdown·Restart·Quit variants in `crates/engram-dashboard-protocol/src/messages.rs`. The `RestartPolicy` in the same file is an **agent restart policy**, so it is not this)~~ ★**Correction 2026-09-06 (ADR-0180) — this measurement is false**★: such a command **exists** — it is `AgentCommand::StopDaemon { force, kill_agents, request_id }` (`messages.rs:89`, the comment says 「데몬 종료(§5 LLM 제어)」), and `build_stop_command` of discovery (`crates/engram-dashboard-discovery/src/lib.rs:772`) builds it and the shell calls it in `src/api/daemonControl.ts`. ★**The error is reading the literal fact that there are 0 variants with the *names* Shutdown·Restart·Quit as 「그런 명령이 없다」.**★ **But the rejection this item held up still stands** — ③ below is the reason (when the grammar is broken, that command **does not get through either**), and ADR-0180 confirmed it against the real code: to send `StopDaemon` one must pass authentication, a version mismatch is rejected right there, and `stop_with_sender` of discovery handles `VersionMismatch` as `NoTarget`. **Only this one line of fact changes; the decision and the rejection are not reopened.** ③ Even if it had existed, ★**it does not get through when the grammar is broken**★ — only a forced kill is left.

## 근거

- **Dropping is safer** — with silent misbehavior the user **cannot find the cause**. If we drop and give the reason, at least they know what the problem is. The judgment is that failing to attach is better than causing damage that cannot be undone.
- **At handshake time the reason is actually delivered** — nothing is backed up yet, so the reason can be carried in the close frame. ★**This is a different situation from 「큐가 꽉 찬 연결을 끊을 때는 사유가 전달되지 않는다」 (RFC 6455 `1006`) that ADR-0177 dealt with — do not confuse**★. There the reason disappears because of **congestion or abrupt termination**, and here it is **the first response that the server normally chooses to send**.
- **Remote becomes the same as local** — since the client **does not need to know the daemon version in advance** (decision 4), it is **the same path** even for a remote that has no port file. Because the decision is the daemon's alone, the path does not split no matter how many peers there are (ADR-0179).

- ★**The exception clause of decision 4, 「모달은 앱이 아예 못 붙을 때만」, does not die; rather it is triggered**★ — under the new decision the client **really cannot attach.** So the popup lies inside the exception ADR-0158 dug for itself, and it does not collide with the rejection reason of the alternative that ADR rejected, 「올리되 모달로 안내한다」 (a state that arises without the user asking for it goes in a banner). **Whether the clause that says no action button is attached lives or dies is open** — the last item of 「거부한 대안」 above left it open.

**The invariants section of ADR-0158:**

- ★**Dies — 「광고에 없는 명령은 보내지 않는다」**★. This discipline was the actual form of the decision.
- **Dies — 「능력 광고 칸은 없어도 깨지지 않아야 한다」**. It is a clause that held up the decision, so it loses force along with it. ★**This does not mean deleting the field right now**★ (decision 6).
- **Lives — 「`PROTOCOL_VERSION` 상향은 봉투 문법이 깨질 때로 한정」**. ★If this dies, this whole ADR collapses★ — if the version starts being bumped for feature differences too, 「불일치 = 말이 안 통함」 becomes false, and at that moment the 「끊지 않는다」 side becomes right again.
- **Lives — 「데몬을 자동으로 죽이는 경로를 만들지 않는다」**.
- **Lives — 「알림 표면은 새 전역 핸들을 늘리지 않고 기존 제어 표면에 얹는다」** (CLAUDE.md 「LLM-우선 제어」). Only the moment of notifying has moved; it still notifies — what is shown to the person and what the LLM reads must have the same source. ★**But which surface that popup stands on is not decided by this ADR — open**★.
- **Kept as is, accrued — 「세대를 겹쳐 돌리고 옛 데몬은 자기 세션이 끝날 때까지 살려 둔다」** (long-term direction, not in scope this time). ★**This reversal raises its value**★ — since we chose the dropping side, that is now the only way to solve 「데몬을 죽이지 않고도 새 앱이 일한다」 structurally.

**The rationale section of ADR-0158 — where they part:**

- **The fact remains but drops out of the basis of the decision — 「`AgentEvent::Hello` 가 데몬 전체 능력을 싣고 온다」** (that ADR's measurement). It is still true but holds nothing up.
- ★**Collides head-on — 「업계 관행은 버전 숫자 하나로 전부 끊기에서 멀어져 있다」**★ (the `/research medium` conclusion of that ADR). This decision goes to the opposite side of that practice. **We do not hide it — but it does not mean that survey was wrong; it means the premise does not fit us:** the cases surveyed are protocols where a version difference is a **feature difference**, and our version is bumped **only on a grammar breakage**. ★**We did not reopen the survey source to check this reinterpretation — unverified**★.
- **Lives — 「무한 대기는 버전 문제로만 볼 수 없다」** (the deadline and correlation prevent a different failure). It is the pair of decision 5, so it lives with it.
- **Lives — 「고지 시점은 영향 범위를 따른다」**. That principle is written as 「조건이 계속 유지되는 것이면 앱 차원에서 미리」, and **the connection-rejection popup is exactly app-level** — this decision is actually closer to that principle than the draft (a notice at the request site).
- **Lives — the rejection of the rejected alternative 「알림 없이 조용히 기능만 비활성」** · **the rejection of 「버전 개념을 없앤다」**. Both stay rejected as they are.
- ★**Half lives — the rejection of the rejected alternative 「관례대로 (명령 추가로) 버전을 올린다」**★. **The clause lives** (it is the back side of decision 1 — we still do not bump on a command addition). **But the trailing sentence that held up that rejection, 「올리면 업그레이드하는 모든 사용자가 못 붙는다」, is no longer an argument against** — because this decision **accepted** that everyone fails to attach when the version has really split. The remaining reason for rejection is **only 「명령 추가는 그 등급이 아니다」**.

### Other

- **Consistent with ADR-0177 decision 3** — `transport` **only carries the handshake frame, and 「계속할지 끊을지」 is decided by the consumer**. That hook is on the **server side**, and the daemon looks at the version there. So the crate still does not know version vocabulary (ADR-0129 vocabulary isolation is kept). ★Conversely, if the decision is moved to the client, the hook is needed on both sides★ — decision 3 prevents that.
- **The only new thing to build is one client popup.** The daemon side approves what already exists (decision 2), and the wire does not grow either (decision 4).
- ★**Not verified — this session did not check code other than the two places above**★:
  1. **We did not check whether the client actually receives and reads that rejection-reason frame now** (unverified). If it does not, decision 5 becomes not 「팝업을 붙인다」 but 「사유를 꺼내는 경로부터 만든다」.
  2. **We did not check whether the client repeats endless reconnection after being rejected** (unverified). If it does, the popup may appear on every attempt, so a separate display policy is needed.
  3. **An old client (no popup code) just sees it as dropped and only repeats reconnection** — it is old software, so it **cannot be fixed**. ★**This decision's judgment is that this is still better than misbehavior**★ (user judgment 2026-09-04). It means that the 「이유가 안 보이는 무한 재연결 중」 that occurred at the 1→2 bump **is reproduced as is** in the old client.
  4. ★**Suspected second decision maker — we did not check whether the 「버전 불일치 시 데몬 거부」 path of `crates/engram-dashboard-discovery` is still alive**★ (unverified). The related line of ADR-0158 pointed at that path. If it is alive, the decision would sit in **two places, the daemon handshake and discovery**, which is **the same kind of violation** as decision 1 (decision maker = the daemon alone) and decision 3 (two logics diverge) — that is the first checkpoint of this decision.
