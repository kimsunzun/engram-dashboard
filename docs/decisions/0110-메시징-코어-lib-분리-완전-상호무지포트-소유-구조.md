# ADR-0110: Split the messaging core into a lib — fully mutually unaware, port-owning structure

- 상태: 확정 (2026-07-28, basis: user decision + a full measurement by 2 worker-scouts) · 부분 폐기 by ADR-0127 (the TapHost port of decision 3 and the home of the classification in decision 4) · 부분 폐기 by ADR-0231 (add inputs_pending and last_end_failed to the busy-decision facts)
- 관련: ADR-0012(module isolation) · ADR-0004(backend knowledge isolation) · ADR-0002(capability) · ADR-0104(busy gate) · step-log S18 2026-07-28 · CLAUDE.md §핵심 불변식(core tauri import 0 — a compiler wall of the same family) · Amended by ADR-0127 (the TapHost port of decision 3 and the home of the classification in decision 4) · Amended by ADR-0231 (add inputs_pending and last_end_failed to the busy-decision facts)

## 맥락
Messaging (v1) exists as a module inside the daemon crate (`src/messaging/`), and its boundary with the daemon internals is kept only by convention (review, load-bearing comments). In this project a different coder subagent writes the code each time, so convention alone risks the boundary eroding every time the session changes — the user's concern: "앞으로 짜는 것에서 이런 시스템을 고려해야 하는데 고려하지 않을 것 같다." (from now on we have to consider this kind of system in what we write, but I do not think we will) The stated direction: **"약속이 아니라 구조로 구조를 만들어야지."** (we must build the structure with structure, not with promises) Meanwhile there is a plan to introduce a chat system (a sibling system to messaging) and a plan to split out an independent mail service (backlog, referencing MCP Agent Mail), so it is concrete that the messaging kernel will get a second consumer.

## 결정
1. **Split the messaging core into the workspace's 6th lib crate.** Timing = after the remaining S18 acceptance measurement is done, as an independent slice (TRD-lite → coder/review/QA). The order is fixed so that the path the acceptance measurement verifies is not shaken during the move: learning mode → acceptance measurement → split slice.
2. **Fully mutually unaware (no core dependency):** the new lib depends on no workspace crate, core included (external dependencies = only uuid and tracing). The participant id is the lib's own alias (uuid-based), and the injection result is also defined as the lib's own type.
3. **Port-owning structure:** the **contract (trait) of each joint is owned by the lib** (DeliveryPort · BusyGate · TapHost · IdleNotifier · FlushTrigger + the identity/observation ports), and the **real adapters are owned by the host (the daemon)** (ManagerDeliveryPort · ManagerTapHost · the registry adapter — all move to the daemon). The daemon is the only assembly and wiring room.
4. **Separating backend knowledge in busy-turn observation:** classifying output events → turn signals (progress/end) is claude stream-json backend knowledge, so it moves to a daemon adapter, and the lib defines only the signal vocabulary (the progress/end receiving ends) (the same grain as ADR-0004). The busy invariants (positive-knowledge-only · blocking phantom busy · pump callback discipline · lock order) stay in the lib unchanged.
5. **Move the envelope layer:** the envelope layer that lived inside ControlIngress (wrap_message · EnvelopeFields · EnvelopeFormat · Entrance · new_msg_id · DeliveryObservation) moves to the lib — this resolves the messaging↔control module cycle, and puts the kernel parts the chat will share in the right place from day one.
6. **The entries (MCP server · engram-send · ws) and the assembly (lib.rs) stay in the daemon.** The chat system is designed as a sibling consumer of this lib (not a merge into a single system).

## 거부한 대안
- **Only add an rg isolation gate and keep the module (status quo)** — it is an after-the-fact check and a promise, so it can leak at every coder subagent session change. A crate boundary is a wall enforced by the compiler, which future sessions physically cannot breach even if they do not "consider" it. Rejected by the user ("약속이 아니라 구조로" — with structure, not with promises).
- **Partial unawareness that shares only the AgentId word** — measurement showed AgentId is a simple alias of `uuid::Uuid`, so the extra cost of full unawareness is effectively zero (the daemon call sites compile unchanged). With no cost difference, there is no reason to leave a hole in the wall.
- **Split immediately (before the acceptance measurement)** — it would shake the path the acceptance measurement verifies during the move. Right after the measurement pins down the current path is the safest time to move.
- **Merge even the chat into a single messaging system** — their invariants differ: mail = discrete letters + obligation semantics (reply-debt ledger · deadline · parking), chat = room/stream semantics (history · participants · fan-out). Share the kernel parts (envelope · Groups · identity), and keep the policy layers as siblings.
- **Put the production adapters in the lib** — the lib would come to know AgentManager, breaking full unawareness, and damaging the picture of a future independent mail service (a host without AgentManager). Adapters belong to the host.

## 근거
Full measurement by 2 worker-scouts (2026-07-28):
- `AgentId` = a `uuid::Uuid` type alias (not a newtype) → about 66 daemon↔lib boundary calls compile unchanged, so the boundary translation cost is effectively zero.
- The `AgentManager` touch points = only 2 adapters (ManagerDeliveryPort · ManagerTapHost) + a convenience constructor. `AgentStatus` is in 1 place inside an adapter (it vanishes from the lib together with the adapter move). `WriteOutcome` is in the DeliveryPort signature → the lib's own 4-field type + a copy in 1 adapter.
- ControlRegistry touch points = 2 methods (envelope format lookup · delivery observation record) → a small port.
- All side-effect axes measured as 0: serde/persistence 0 (all in-memory), async/tokio 0 (purely synchronous), platform cfg 0, src-tauri/frontend/protocol references 0, path pointers in docs 0.
- Scale: moving 6 messaging files with 16,733 lines (production 6.6k / tests 10.1k) + the envelope layer at about 240 lines. Logic changes are local to 3 places (narrowing the busy tap signal · the adapter move · the envelope move), and the rest is mechanical. Being a workspace-internal crate, unlike a public lib, there is no API freeze pressure (both sides are edited in one commit).
- Side benefits: a standalone isolated harness `cargo test -p <메시징 lib>` (consistent with ADR-0012), and the chat system is designed from the consumer's viewpoint from day one.

## 영향 / 불변식
- **Isolation gate (after the split):** zero workspace crate imports in the messaging lib (compiler-enforced) — in particular zero `AgentManager` imports. An attempt to violate it is a compile error = a forced stop to dig a port or ask the user is the design intent.
- The workspace members +1 → the commands that enumerate members must be updated (README.md · CLAUDE.md · `.claude/skill-bindings/qa.md` · docs/testing-strategy.md). The `test-harness` feature is declared by the lib itself (independent of the current pass-through via core).
- The busy invariants (positive-knowledge-only = idle if unknown · blocking phantom busy · callback discipline · the BUSY_MAX_TURN sweep) are **not changed** by this split — only the face of the signal entry changes. Do not reimplement these invariants outside the lib (in an adapter) (keep ports thin, policy in the lib).
- The required joints the host must plug in = the real delivery (DeliveryPort) · roster feeding (attach/forget/flush) · doorbell plumbing (the flush worker) · the sweep timer · the entries. Turn observation and envelope format are optional (fail-open fallback). Push delivery needs process ownership — a host without it is demoted to pull (to be revisited when the external service is planned).
