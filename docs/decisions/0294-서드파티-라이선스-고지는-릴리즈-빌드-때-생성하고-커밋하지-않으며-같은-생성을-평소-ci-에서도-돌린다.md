# ADR-0294: The third-party license notice is generated at release build time and not committed, and the same generation also runs in ordinary CI

- 상태: 확정 (2026-10-15, 근거: user decision + peer survey + 2-person adversarial code review)
- 관련: ADR-0100 (release manifest tripwire — this decision adds one notice file to the shipping list) · ADR-0131 (CI runner and job split — the tool installation stands inside that boundary) · ADR-0232 (CI path filter) · `scripts/gen-third-party-licenses.mjs` · `scripts/licenses/` · `scripts/build-release.ps1` step (0) · `.github/workflows/ci.yml` (`gates` · `release-build`) · survey = `docs/research/third-party-license-notice-generation-practice-2026-10-15.md` · tool selection survey = `docs/research/third-party-license-notice-survey-2026-10-15.md` · tracking = T-62 (★at the time this ADR was written, both exist only in commit `249d92cb` on the `v0.3.3/chore/misc` branch — when it lands on master, close T-62★) · Amends ADR-0100 (add the notice file to the shipping list of decision 2)

## 맥락
The distribution zip had no third-party license notice at all (T-62). Most licenses, MIT included, set as a condition 「저작권 표시와 허가 문구를 사본에 포함」. Rust crates go into the exe statically — the dependency graph of the three shipped exes is 322 crates (including proc-macros that run only at build time · measured 2026-10-15). There are 236 npm production dependencies (including build tools — `@tailwindcss/vite` is in `dependencies`).

The first decision (the user, the morning of 2026-10-15) was 「도구로 한 번 뽑아 커밋하고 갱신도 손으로 · 자동화는 나중」. Once the generation script was written, there was no step that needed a human hand, and the user changed it the same day with 「자동으로 다 해놨는데 뭔 손으로 해 · 릴리즈 뽑을 때 하면 되는 거 아님?」. The user then asked 「매번 뽑을 때 잘못 뽑히면 안 되는데 그런 위험은 없나 · 다른 곳은 어떻게 하나」, and the survey and the verification devices were added.

## 결정
1. **Generation time = release build.** Before the long build, `scripts/build-release.ps1` creates the notice with `scripts/gen-third-party-licenses.mjs` (output = under the cargo target folder · the old output is deleted first), adds `THIRD_PARTY_LICENSES.txt` to the shipping list (the ADR-0100 manifest), and ships it at the top of the release folder. **It is not committed to the repository.** The local release build and the CI `release-build` take the same path.
2. **The same generation also runs in ordinary CI.** The `gates` job runs the generator on every push and discards the output — so that a failure does not first show up in the release job after the tag (a tag cannot be retried · CLAUDE.md 「검증」).
3. **Tool versions are pinned.** cargo-about 0.9.2 (in CI = the Windows binary from the GitHub release · SHA-256 verified · the generator also checks the version) · generate-license-file 4.2.5 (a devDependency at the exact version — `package-lock.json` pins the transitive dependencies too).
4. **Scope = all dependencies that ship in the deliverable** (user decision 2026-10-15 · T-62). Rust = Windows target · build/dev dependencies excluded · our own workspace crates excluded. npm = production dependencies.
5. **Generation fails when something goes wrong (fail-closed).** What the generator rejects:
   - A license outside the allow list (`accepted` in `scripts/licenses/about.toml` — Rust and npm use the same list). ★GPL · LGPL · AGPL are not put on that list — whether to accept them is a user decision★.
   - A license that cannot be identified · our own crate mixed in · an npm text that is only a name · URL · SPDX document · a package the npm tool silently dropped · an omission found by cross-checking against the production dependencies of `package-lock.json` (for a peer-only production dependency that the npm tool skips, the generator ships it directly from that package's license file, and fails if it cannot find one) · a shipped text that does not match the license the package declares.
   - The key of an npm manual override (`scripts/licenses/glf.jsonc`) is an exact `이름@버전`, and it fails if that version is not among the installed production dependencies — so when a dependency is bumped, the old text does not silently remain. The Rust override files (`scripts/licenses/rust/`) also state an exact version and fail if they do not match or are not used.
   - A placeholder copyright (`<year>` · `<copyright holders>` and so on). The only exceptions are the 「synthesized」 item below and the standard line in the appendix of the Apache-2.0 text.
   - **synthesized item** = a crate whose published package really has no license file, so the standard text is shipped for it. It is shipped with a mark, and generation fails when a crate appears that is not in the list `scripts/licenses/synthesized-crates.txt`. For files whose names cargo-about did not recognize (`LICENSE_MIT` · `license-mit` and so on), the generator finds them directly in the crate folder and inserts them, and for those whose file exists only in the upstream repository, they are inserted through an override file that checks the version.
6. **What the tool cannot see is shipped as a hand-placed appendix** — `scripts/licenses/extra/`. Currently = the Microsoft WebView2 loader that `webview2-com-sys` links statically (LICENSE · NOTICE of SDK 1.0.3650.58). An appendix records the version of its matching crate, and fails if that version drops out of the dependency graph.

## 거부한 대안
- **Extract by hand and commit · update by hand** (the decision of the morning of the same day) — generation already ran without a human hand, so the only thing a manual step leaves is the risk that 「의존성을 바꾸고 다시 안 뽑으면 낡은 목록이 실린다」 (the user: 「자동으로 다 해놨는데 뭔 손으로 해」).
- **Minimal notice on the agent-tool side** (Codex CLI · herdr · t3code style — only code that was taken and modified · binaries shipped alongside) — the user chose the full dependency list (「외부에서 쓰는 것 표시도 해 놓을 겸」 · T-62).
- **Commit + CI freshness check** (Signal Desktop · libsignal — CI regenerates and runs `git diff --exit-code`) — the peers (the Rust desktop side that was surveyed — Zed and others) generate at release time, so we followed that practice (the user 2026-10-15). The advantage of this alternative (the notice content stays in the repository, so review · history tracking work) was not taken, and the price is a manual step of regenerating and committing the notice every time dependencies change. ★The grounds for rejecting it are weak because they rest on one practice★ — if a need to review notice changes arises, reopen this alternative first.

## 근거
- Peers (the survey report — only what the main agent confirmed in the originals): Zed generates with a bundled script, keeps the output in `.gitignore`, and a `check_licenses` job in PR CI runs the same script · it pins the cargo-about version in the script. ALVR also has the same generation check in PR CI. The sample is small, so we do not say 「주류」.
- When cargo-about 0.9.2 cannot find a license file, it substitutes the standard text and leaves only a `debug` log — `--fail` does not catch it, and the one sign is an empty `source_path` in the JSON (`src/generate.rs:141-155`). That is why the generator holds the synthesized list of decision 5 and the placeholder check.
- generate-license-file 4.2.5 only warns about and drops a package whose license it could not determine (`resolveNpmDependencies.ts:55-88`), and skips a package marked as peer before recording it (codex re-review) — that is why the `package-lock.json` cross-check and the direct shipping of peers exist.
- Defects caught by the 2-person adversarial code review (doc-aware + codex blind, 5 rounds): many of the 54 placeholder crates actually had real files · the WebView2 loader was missing · there was no npm allow list · a peer omission path.

## 영향 / 불변식
- **A local release build needs cargo-about 0.9.2** (`launch\빌드.bat` · `scripts/build-release.ps1`). If it is missing, step (0) prints the install command and stops.
- **When a dependency is added or bumped, the generation check in push CI decides first.** If a new crate comes out as synthesized, add it to the list or place an override file. If a new license is outside the allow list, it fails — widening the list is a user decision.
- **When bumping a tool version**, change the generator constant · the pinned version and SHA in `ci.yml` · `package.json` together (cargo-about: the generator checks the version and fails on a mismatch · generate-license-file: there is no version check, so only the output format check remains).
- The notice does **not guarantee** correctness — if a package author put in a wrong license file, the tool copies it as is.
