# ADR-0294: 서드파티 라이선스 고지는 릴리즈 빌드 때 생성하고 커밋하지 않으며 같은 생성을 평소 CI 에서도 돌린다

- 상태: 확정 (2026-10-15, 근거: 사용자 결정 + 피어 조사 + 2인 적대 코드 리뷰)
- 관련: ADR-0100(릴리즈 manifest tripwire — 이 결정이 배송 목록에 고지 파일 하나를 더한다) · ADR-0131(CI 러너·잡 분리 — 도구 설치가 그 경계 안에 선다) · ADR-0232(CI 경로 필터) · `scripts/gen-third-party-licenses.mjs` · `scripts/licenses/` · `scripts/build-release.ps1` 단계 (0) · `.github/workflows/ci.yml`(`gates` · `release-build`) · 조사 = `docs/research/third-party-license-notice-generation-practice-2026-10-15.md` · 도구 선택 조사 = `docs/research/third-party-license-notice-survey-2026-10-15.md` · 추적 = T-62(★둘 다 이 ADR 작성 시점엔 `v0.3.3/chore/misc` 브랜치 커밋 `249d92cb` 에만 있다 — master 에 들어오면 T-62 를 닫는다★) · Amends ADR-0100 (결정 2 배송 목록에 고지 파일 추가)

## 맥락
배포 zip 에 제3자 라이선스 고지가 하나도 없었다(T-62). MIT 를 비롯한 대부분의 라이선스가 「저작권 표시와 허가 문구를 사본에 포함」을 조건으로 건다. Rust crate 는 exe 에 정적으로 들어간다 — 배포 exe 셋의 의존 그래프가 crate 322 개다(빌드 때만 도는 proc-macro 포함 · 2026-10-15 실측). npm 운영 의존은 236 개다(빌드 도구 포함 — `@tailwindcss/vite` 가 `dependencies` 에 있다).

처음 결정(사용자 2026-10-15 오전)은 「도구로 한 번 뽑아 커밋하고 갱신도 손으로 · 자동화는 나중」이었다. 생성 스크립트를 만들어 보니 사람 손이 드는 단계가 없었고, 사용자가 같은 날 「자동으로 다 해놨는데 뭔 손으로 해 · 릴리즈 뽑을 때 하면 되는 거 아님?」으로 바꿨다. 이어 「매번 뽑을 때 잘못 뽑히면 안 되는데 그런 위험은 없나 · 다른 곳은 어떻게 하나」를 물어 조사와 검증 장치가 붙었다.

## 결정
1. **생성 시점 = 릴리즈 빌드.** `scripts/build-release.ps1` 이 긴 빌드에 들어가기 **전에** `scripts/gen-third-party-licenses.mjs` 로 고지를 만들고(산출 = cargo target 폴더 아래 · 옛 산출을 먼저 지운다), 배송 목록(ADR-0100 manifest)에 `THIRD_PARTY_LICENSES.txt` 를 더해 release 폴더 맨 위에 싣는다. **저장소에 커밋하지 않는다.** 로컬 릴리즈 빌드와 CI `release-build` 가 같은 경로를 탄다.
2. **같은 생성을 평소 CI 에서도 돌린다.** `gates` 잡이 push 마다 생성기를 돌리고 산출은 버린다 — 실패가 태그 뒤 릴리즈 잡에서 처음 드러나지 않게 하려는 것이다(태그는 재시도가 안 된다 · CLAUDE.md 「검증」).
3. **도구 버전을 고정한다.** cargo-about 0.9.2(CI = GitHub 릴리즈의 Windows 바이너리 · SHA-256 검증 · 생성기도 버전을 확인한다) · generate-license-file 4.2.5(정확한 버전의 devDependency — `package-lock.json` 이 하위 의존까지 고정한다).
4. **범위 = 배포물에 실리는 의존 전체**(사용자 결정 2026-10-15 · T-62). Rust = Windows 대상 · 빌드/개발 의존 제외 · 우리 워크스페이스 crate 제외. npm = 운영 의존.
5. **생성은 잘못될 때 실패한다(fail-closed).** 생성기가 거부하는 것:
   - 허용 목록(`scripts/licenses/about.toml` 의 `accepted` — Rust 와 npm 이 같은 목록을 쓴다) 밖 라이선스. ★GPL · LGPL · AGPL 은 그 목록에 넣지 않는다 — 받아들일지는 사용자 결정이다★.
   - 라이선스 판별 실패 · 우리 crate 혼입 · npm 본문이 이름 · URL · SPDX 문서뿐인 것 · npm 도구가 조용히 뺀 패키지 · `package-lock.json` 운영 의존과 대조한 누락(npm 도구가 건너뛰는 peer 전용 운영 의존은 생성기가 그 패키지의 라이선스 파일로 직접 싣고, 못 찾으면 실패한다) · 실은 본문이 패키지가 선언한 라이선스와 안 맞는 것.
   - npm 손 교체(`scripts/licenses/glf.jsonc`)의 키는 정확한 `이름@버전` 이고, 그 버전이 설치된 운영 의존에 없으면 실패한다 — 의존을 올리면 옛 본문이 조용히 남지 않는다. Rust 교체 파일(`scripts/licenses/rust/`)도 정확한 버전을 적고 어긋나거나 안 쓰이면 실패한다.
   - 자리표시 저작권(`<year>` · `<copyright holders>` 등). 예외는 아래 「synthesized」 항목과 Apache-2.0 본문 부록의 표준 줄뿐이다.
   - **synthesized 항목** = 게시된 crate 에 라이선스 파일이 정말 없어 표준 본문을 싣는 crate. 표시를 달고 실으며 `scripts/licenses/synthesized-crates.txt` 명단에 없는 crate 가 새로 생기면 실패한다. cargo-about 이 이름을 못 알아본 파일(`LICENSE_MIT` · `license-mit` 등)은 생성기가 crate 폴더에서 직접 찾아 넣고, 상류 저장소에만 파일이 있는 것은 버전을 확인하는 교체 파일로 넣는다.
6. **도구가 못 보는 것은 손으로 둔 부록으로 싣는다** — `scripts/licenses/extra/`. 지금 = `webview2-com-sys` 가 정적으로 링크하는 Microsoft WebView2 로더(SDK 1.0.3650.58 의 LICENSE · NOTICE). 부록은 대응 crate 버전을 적어 두고, 그 버전이 의존 그래프에서 빠지면 실패한다.

## 거부한 대안
- **손으로 뽑아 커밋 · 갱신도 손으로**(같은 날 오전의 결정) — 생성이 이미 사람 손 없이 돌아 손 단계가 남기는 것은 「의존성을 바꾸고 다시 안 뽑으면 낡은 목록이 실린다」는 위험뿐이다(사용자 「자동으로 다 해놨는데 뭔 손으로 해」).
- **에이전트 도구 쪽 최소 표시**(Codex CLI · herdr · t3code 처럼 가져와 고친 코드 · 같이 싣는 바이너리만) — 사용자가 의존성 전체 목록을 골랐다(「외부에서 쓰는 것 표시도 해 놓을 겸」 · T-62).
- **커밋 + CI 최신 검사**(Signal Desktop · libsignal — CI 가 다시 생성해 `git diff --exit-code`) — ★사용자 기각 사유 미수령(약함)★: 사용자는 「릴리즈 뽑을 때 생성」을 골랐을 뿐 이 대안을 따로 기각하지 않았다(2026-10-15 질문했으나 답 없음). 다시 꺼낼 땐 이 칸부터 사용자에게 묻는다 — 장점 = 고지 내용이 저장소에 남아 리뷰 · 이력 추적이 된다 · 단점 = 의존을 바꿀 때마다 다시 생성해 커밋하는 단계가 하나 붙는다.

## 근거
- 피어(조사 보고서 — 메인이 원문 확인한 것만): Zed 는 번들 스크립트가 생성하고 산출을 `.gitignore` 에 두며, PR CI 의 `check_licenses` 잡이 같은 스크립트를 돌린다 · cargo-about 버전을 스크립트에 박는다. ALVR 도 PR CI 에 같은 생성 검사가 있다. 표본은 작아 「주류」를 말하지 않는다.
- cargo-about 0.9.2 는 라이선스 파일을 못 찾으면 표준 본문으로 대신하고 `debug` 로그만 남긴다 — `--fail` 로 안 잡히고 표지는 JSON 의 `source_path` 가 비는 것 하나다(`src/generate.rs:141-155`). 그래서 결정 5 의 synthesized 명단과 자리표시 검사가 생성기에 있다.
- generate-license-file 4.2.5 는 라이선스를 못 정한 패키지를 경고만 하고 빼며(`resolveNpmDependencies.ts:55-88`), peer 로 표시된 패키지는 기록 전에 건너뛴다(codex 재리뷰) — 그래서 `package-lock.json` 대조와 peer 직접 싣기가 있다.
- 2인 적대 코드 리뷰(doc-aware + codex blind, 5 라운드)가 잡은 결함: 자리표시 crate 54 중 다수가 실제 파일을 갖고 있었다 · WebView2 로더 누락 · npm 허용 목록 부재 · peer 누락 경로.

## 영향 / 불변식
- **로컬 릴리즈 빌드에 cargo-about 0.9.2 가 필요하다**(`launch\빌드.bat` · `scripts/build-release.ps1`). 없으면 단계 (0)에서 설치 명령을 내고 멈춘다.
- **의존을 추가 · 올리면 push CI 의 생성 검사가 먼저 판정한다.** 새 crate 가 synthesized 로 나오면 명단에 더하거나 교체 파일을 둔다. 새 라이선스가 허용 목록 밖이면 실패한다 — 목록을 넓히는 것은 사용자 결정이다.
- **도구 버전을 올릴 땐** 생성기 상수 · `ci.yml` 의 고정 버전과 SHA · `package.json` 을 함께 바꾼다(cargo-about 은 생성기가 버전을 확인해 어긋나면 실패한다 · generate-license-file 은 버전 확인이 없어 출력 형식 검사만 남는다).
- 고지는 정확성을 **보장하지 않는다** — 패키지 저자가 라이선스 파일을 잘못 넣어 둔 경우는 도구도 그대로 옮긴다.
