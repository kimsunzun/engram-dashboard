# ADR-0260: 분할 비율 한계를 낮춰 칸 최소는 30px 하나만 남긴다

- 상태: 확정 (2026-09-30, 근거: 사용자 결정(실사용 피드백 · 두 쪽 모두 = 사용자 답 2026-09-30(이번 세션 — 원문 = `.claude/handoff/attachments/usage-slot-user-answers-2026-09-30.md`)) + 코드 정적 확인 — 화면 실측 없음)
- 관련: Amends ADR-0227 (결정 2와 영향의 비율 한계 0.1~0.9) · ADR-0259(같은 날 같은 피드백 — 사용량 슬롯 쪽) · ADR-0068(§0 극단 비율 방어 — FIX-4) · ADR-0140(방향 어휘 — a 쪽 = 왼쪽/위) · TRD `docs/process/S21-usage-limit-slot/trd.md` §3 #105 · TRD `docs/process/S21-flat-split-renderer/trd.md` §2c · §3 D1·D2·R11 · `src-tauri/src/layout/tree.rs` · `src-tauri/src/layout/manager.rs` · `src-tauri/src/layout/geometry.rs` · `src/components/layout/splitPreview.ts` · 인계 기록 `.claude/handoff/history/20260930-150000-사용량-슬롯-실사용-피드백-결정-구현-대기.md` · step-log S21

## 맥락
사용자가 사용량 슬롯을 위아래 분할의 한 칸에 두고 그 칸을 더 줄이려 했는데 줄지 않았다(실사용 피드백 2026-09-30).

셸은 분할 비율(a 쪽 몫 — ADR-0140)을 0.1~0.9 로 자른다(ADR-0227 결정 2 · herdr 선례 — flat TRD §2c). 소유 창의 캔버스와 지표를 알면 한 번 더 자른다. 두 쪽(서브트리 통째)이 각각 `min_pane_px`(화면 상수 `MIN_PANE_PX` = 30) 이상이 되게 하는 것이다. 허용 범위는 `[max(0.1, 30/L), min(0.9, 1 − 30/L)]` 이고, L 은 그 분할 상자의 그 축 px 이다. **L 이 300px 를 넘으면 비율 한계가 30px 보다 커서 이긴다** — 예를 들어 높이 900px 인 분할에서 위 칸은 90px 아래로 줄지 않는다. 화면 드래그도 같은 식으로 범위를 구한다. 스냅샷의 `ratio_min/max` 를 넣으므로 같은 자리에서 멈춘다.

**원인 확인 = 정적(코드)이고 가설과 맞는다.** 드래그로 멈춘 px 를 재는 화면 실측은 하지 않았다. 확인한 자리는 이렇다.
- 셸 상수 — `tree.rs:16-17`.
- 셸 클램프 — `manager.rs:460-476`.
- 화면 범위 — `splitPreview.ts:100-113` · `useSplitDrag.ts:186-206`.
- 화면이 받는 한계 — `viewStore.ts:296`.

칸 크기를 누르는 다른 벽은 레이아웃·슬롯 쪽에 없다(CSS 최소 높이 없음 — 캔버스의 `minHeight: 0` 뿐). 사용량 슬롯의 높이 폴백(ADR-0259 결정 6)은 칸 크기가 아니라 표시 단계를 바꿀 뿐이다.

## 결정
1. **분할 비율 한계를 낮춰, 칸 최소 30px(`MIN_PANE_PX`) 하나만 실제로 남게 한다.** 사용자 원문: 「아예 겹쳐서 올릴 수 없는 정도가 아니라면 괜찮다」(인계 기록 150000:20).
   - **두 쪽 모두 — 하한 `RATIO_MIN` 과 상한 `RATIO_MAX` 를 함께 풀어 어느 칸이든 30px 까지 준다(사용자 결정 — 사용자 답 2026-09-30).** 위(왼쪽) 칸의 벽은 하한이고 아래(오른쪽) 칸의 벽은 상한이다(ADR-0140).
   - **0 으로 없애지 않고 작은 양수로 남긴다** — 이유는 「영향」 첫 항. 값은 메인 결정(내부 상수)이다 — `0.01`/`0.99`(TRD §3 #105 ②).
2. **30px 최소는 그대로다** — 끌린 분할의 두 쪽이 각각 30px 이상이고 L < 60 이면 잠긴다(ADR-0227 · flat TRD D2). 30px 미만 칸을 만드는 **분할**은 전처럼 허용한다(flat TRD R11 — 이 결정이 건드리지 않는다).
3. **화면이 셸 상수를 베끼지 않는 구조는 그대로다** — 한계는 스냅샷 `ratio_min/max` 로 화면에 간다. 그래서 바꾸는 곳은 셸 상수 둘과 그 시험이다(화면 코드는 상수를 안 가진다 — 시험 고정값만 맞춘다).

## 거부한 대안
- **0.1~0.9 유지(ADR-0227 결정 2 · herdr `src/layout.rs:275-277` 선례)** — 사용자가 칸을 더 줄이려 했고 「아예 겹쳐서 올릴 수 없는 정도가 아니라면 괜찮다」고 했다(인계 기록 150000:20). 10% 한계가 L 300px 이상에서 30px 최소보다 큰 벽이 되는 것은 코드 사실이다(「맥락」).

## 근거
- **사용자 결정(2026-09-30)** — 인계 기록 `.claude/handoff/history/20260930-150000-사용량-슬롯-실사용-피드백-결정-구현-대기.md:20-21` · `.claude/handoff/history/20260930-153000-사용량-슬롯-실사용-피드백-결정-8건-구현-대기.md:20-21`.
- **코드 정적 확인** — 「맥락」의 자리들. 셸 시험도 같은 사실을 단언한다. 「바깥: L = 1000 → m/L = 0.1 이라 비율 한계가 이긴다」(`manager.rs:2367-2370` — m = 100 인 세계)와, 지표가 없을 때 0.01 요청이 `RATIO_MIN` 으로 잘리는 단언(`manager.rs:2414-2419`)이다.
- **같은 방향의 앞선 사용자 말(2026-09-24 — flat TRD §3 R11)** — 「너무 작아서 유저가 해당칸을 조작 못하는것도 문제긴 하겠네. 적당히 막던지.」 그 말은 30px 미만 칸을 만드는 **분할**에 대한 것이었다. 이번 결정도 30px 최소를 그 「적당히」의 자리로 남긴다.

## 영향 / 불변식
- **★비율 한계는 0 보다 커야 한다★** — 기하 `boundary` 는 트리에 직접 심은 극단값(0.0 등)을 이 한계로 잘라 면적 0 잎을 막는다(`geometry.rs:143-152`). 그 가드가 살아 있어야만 통과하는 시험이 있다(`spatial.rs:456` `degenerate_ratio_produces_no_zero_area_leaf` — ADR-0068 §0 FIX-4). 한계를 0 으로 두면 이 벽이 사라진다.
- **캔버스·지표를 모를 때는 비율 한계가 유일한 벽이다** — 보고 전이나 팝아웃 직후가 그렇다. px 클램프는 둘 다 알 때만 건다(`manager.rs:461-476`). 한계를 낮추면 그 틈에 LLM `split.setRatio` 가 30px 아래 칸을 만들 수 있다. 한계를 얼마나 낮추느냐가 그 틈의 크기다(메인 추론 — 값 선택의 대가, TRD §3 #105).
- **확정 쓰기의 면적 0 거름은 그대로다**(`set_split_ratio` ⑤ — 새로 면적 0 이 되는 잎이 있으면 `TooSmall`).
- **화면 드래그 = 셸과 같은 식·같은 입력**(ADR-0227) — 식을 한쪽만 바꾸지 말 것. 이번 변경은 식이 아니라 셸 상수만 바꾼다.
- **옛 서술이 남는 곳** — flat TRD 는 「0.1~0.9」를 결정·상수로 적는다(`docs/process/S21-flat-split-renderer/trd.md` §2c · §3 D1·D2 · 상수 목록). 이 ADR 이 그것을 개정한다. 코드 주석의 「0.1~0.9」(`src-tauri/src/layout/types.rs:87`)와 ★LLM 이 읽는 명령 요약★ `split.setRatio` 의 「셸이 0.1~0.9 로 자르고」(`src-tauri/src/layout/commands.rs:232`)는 구현 때 함께 고친다(TRD §3 #105). 요약 쪽은 가드 시험이 상수에서 지은 문자열(`format!("{}~{}", RATIO_MIN, RATIO_MAX)`)로 잰다(`src-tauri/tests/layout_commands.rs:1126-1144`) — 상수만 바꾸면 그 시험이 빨개진다.
