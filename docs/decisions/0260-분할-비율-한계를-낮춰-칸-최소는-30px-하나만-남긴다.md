# ADR-0260: Lower the split-ratio limit so that the 30px pane minimum is the only one left

- 상태: 확정 (2026-09-30, basis: user decision (real-use feedback · both sides = user answer 2026-09-30 (this session — source text = `.claude/handoff/attachments/usage-slot-user-answers-2026-09-30.md`)) + static code check — no on-screen measurement)
- 관련: Amends ADR-0227 (Decision 2 and the impact's ratio limit 0.1~0.9) · ADR-0259 (same day, same feedback — usage slot side) · ADR-0068 (§0 extreme-ratio defense — FIX-4) · ADR-0140 (direction vocabulary — side a = left/top) · TRD `docs/process/S21-usage-limit-slot/trd.md` §3 #105 · TRD `docs/process/S21-flat-split-renderer/trd.md` §2c · §3 D1·D2·R11 · `src-tauri/src/layout/tree.rs` · `src-tauri/src/layout/manager.rs` · `src-tauri/src/layout/geometry.rs` · `src/components/layout/splitPreview.ts` · handoff record `.claude/handoff/history/20260930-150000-사용량-슬롯-실사용-피드백-결정-구현-대기.md` · step-log S21

## 맥락
The user put the usage slot in one pane of a top-bottom split and tried to shrink that pane further, but it would not shrink (real-use feedback 2026-09-30).

The shell clamps the split ratio (side a's share — ADR-0140) to 0.1~0.9 (ADR-0227 Decision 2 · herdr precedent — flat TRD §2c). If it knows the owning window's canvas and metrics, it clamps once more. This makes each of the two sides (the whole subtree) at least `min_pane_px` (the screen constant `MIN_PANE_PX` = 30). The allowed range is `[max(0.1, 30/L), min(0.9, 1 − 30/L)]`, where L is the px of that split box on that axis. **When L is over 300px, the ratio limit is larger than 30px and wins** — for example, in a split 900px high, the top pane does not shrink below 90px. The on-screen drag finds its range by the same formula. It takes the snapshot's `ratio_min/max`, so it stops at the same place.

**The cause check = static (code), and it matches the hypothesis.** No on-screen measurement of the px where a drag stops was made. The places checked are these.
- Shell constants — `tree.rs:16-17`.
- Shell clamp — `manager.rs:460-476`.
- On-screen range — `splitPreview.ts:100-113` · `useSplitDrag.ts:186-206`.
- The limit the screen receives — `viewStore.ts:296`.

There is no other wall pressing on pane size on the layout or slot side (no CSS minimum height — only the canvas's `minHeight: 0`). The usage slot's height fallback (ADR-0259 Decision 6) changes the display stage, not the pane size.

## 결정
1. **Lower the split-ratio limit so that only the 30px pane minimum (`MIN_PANE_PX`) actually remains.** User's words: 「아예 겹쳐서 올릴 수 없는 정도가 아니라면 괜찮다」 (handoff record 150000:20).
   - **Both sides — loosen the lower limit `RATIO_MIN` and the upper limit `RATIO_MAX` together so that any pane can go down to 30px (user decision — user answer 2026-09-30).** The wall of the top (left) pane is the lower limit and the wall of the bottom (right) pane is the upper limit (ADR-0140).
   - **Do not remove it with 0; leave it as a small positive number** — the reason is the first item of 「영향」. The value is main's decision (an internal constant) — `0.01`/`0.99` (TRD §3 #105 ②).
2. **The 30px minimum stays as is** — each of the two sides of the dragged split is at least 30px, and if L < 60 it is locked (ADR-0227 · flat TRD D2). A **split** that makes a pane under 30px is still allowed as before (flat TRD R11 — this decision does not touch it).
3. **The structure in which the screen does not copy the shell constants stays as is** — the limit reaches the screen through the snapshot's `ratio_min/max`. So what changes is the two shell constants and their tests (the screen code holds no constants — only the tests' fixed values are adjusted).

## 거부한 대안
- **Keeping 0.1~0.9 (ADR-0227 Decision 2 · herdr `src/layout.rs:275-277` precedent)** — the user tried to shrink the pane further and said 「아예 겹쳐서 올릴 수 없는 정도가 아니라면 괜찮다」 (handoff record 150000:20). That the 10% limit becomes a wall larger than the 30px minimum at L of 300px or more is a code fact (「맥락」).

## 영향 / 불변식
- **★The ratio limit must be greater than 0★** — the geometry `boundary` clamps an extreme value planted directly in the tree (0.0 etc.) with this limit to prevent a zero-area leaf (`geometry.rs:143-152`). There is a test that passes only while that guard is alive (`spatial.rs:456` `degenerate_ratio_produces_no_zero_area_leaf` — ADR-0068 §0 FIX-4). If the limit is set to 0, this wall disappears.
- **When the canvas and metrics are unknown, the ratio limit is the only wall** — before the report or right after a pop-out is such a time. The px clamp is applied only when both are known (`manager.rs:461-476`). If the limit is lowered, in that gap the LLM `split.setRatio` can make a pane under 30px. How far the limit is lowered is the size of that gap (main's inference — the cost of choosing the value, TRD §3 #105).
- **The zero-area filter of the confirming write stays as is** (`set_split_ratio` ⑤ — if any leaf newly becomes zero-area, `TooSmall`).
- **On-screen drag = the same formula and the same input as the shell** (ADR-0227) — do not change the formula on only one side. This change changes only the shell constants, not the formula.
- **Where the old description remains** — the flat TRD writes 「0.1~0.9」 as a decision and a constant (`docs/process/S21-flat-split-renderer/trd.md` §2c · §3 D1·D2 · constant list). This ADR amends it. The 「0.1~0.9」 in a code comment (`src-tauri/src/layout/types.rs:87`) and, ★in the command summary the LLM reads★, `split.setRatio`'s 「셸이 0.1~0.9 로 자르고」 (`src-tauri/src/layout/commands.rs:232`) are fixed together at implementation (TRD §3 #105). The summary side is measured by a guard test against a string built from the constants (`format!("{}~{}", RATIO_MIN, RATIO_MAX)`) (`src-tauri/tests/layout_commands.rs:1126-1144`) — if only the constants change, that test goes red.
