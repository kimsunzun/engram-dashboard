# ADR-0115: Agent name uniqueness — auto-suffix a same name at spawn (follow-up slice)

- 상태: 확정 (2026-07-29, basis: user decision — implementation timing = a separate slice after the messaging send overhaul (ADR-0111/0114) is done) · 부분 폐기 by ADR-0120 (the scope of the uniqueness check) · 부분 폐기 by ADR-0123 (withdraw the ban on number reuse) · 부분 폐기 by ADR-0309 (the basis for rejecting an id parallel key)
- 관련: ADR-0101(WYSIWYA name addressing — this ADR completes the "name = unique key" premise) · ADR-0111·0114(the root fix for the fork that same-name ambiguity created) · ADR-0112(group resolution — the @all same-name exception is the thing to be eliminated) · the AgentManager spawn registration point (the `// ADR-0115` anchor when implemented) · Amended by ADR-0120 (the scope of the uniqueness check) · Amended by ADR-0123 (withdraw the ban on number reuse) · Amended by ADR-0309 (the basis for rejecting an id parallel key)

## 맥락

In messaging, addressing, the parking queue, the ledger, and the reply contract are all **keyed by name**, yet live agents with the same name are allowed, so an ambiguity class exists: a direct pick is rejected with `RECIPIENT_AMBIGUOUS`, and an @all broadcast does not deliver to any of the same-name names (the transitional rule of ADR-0114 decision 4). When the review found the @all × same-name conflict, the user decided to remove the root — instead of handling the ambiguity, make it never arise.

## 결정

**At spawn (new registration), if the live roster has the same name, rename it with an automatic suffix and register it.** Notation = `이름(1)`, `이름(2)` …. The number is **monotonically increasing from the maximum number observed for that name + 1** (no number reuse — even if "bob(1)" dies, the next is "bob(2)"). Implementation timing = a separate slice after the messaging send overhaul is done (the user: "메일 끝나고 할 일" — something to do after mail is finished).

## 거부한 대안

- **Reject a same-name spawn (return an error)** — it blocks a normal flow like spawning N workers from the same profile. An automatic suffix gets the same uniqueness without friction.
- **An entity (id) parallel key system** — a double-key redesign across all of messaging (parking · ledger · contracts), too costly (the same judgment as the ADR-0114 rejected alternative).
- **Keep as is (only state the ambiguity as a row failure)** — accepted only as transitional (ADR-0114 decision 4). In the long run, the system keeps carrying one error class.
- **Number reuse (fill an empty number)** — the confusion of "bob(1)" dying and coming back as a different entity. Monotonic increase blocks misreading the continuity of an entity.

## 근거

- User decision (2026-07-29): "스폰에서 같은 이름이면 (1)로 하던가 해서 동명이인 안 되게. 숫자는 가장 큰 것 있는 기준으로 계속 늘어나게. 메일 끝나고 할 일." (if the name is the same at spawn, make it (1) or so, so there are no namesakes. Keep increasing the number based on the largest one that exists. Something to do after mail is finished)
- Once name uniqueness holds: `RECIPIENT_AMBIGUOUS` becomes a dead letter · the @all same-name exception (ADR-0114 decision 4) disappears · the name-keyed system (parking · ledger · contracts) becomes complete with no extra device.

## 영향 / 불변식

- **In the live roster, the name = a unique key.** Reusing the name of a dead one is allowed — parking name inheritance and respawn delivery continuity (if the same name comes back, it receives the waiting letters) are kept.
- **An epoch swap is not a rename target** — restart/fresh fallback is a map swap of the same AgentId (ADR-0007), so it is not a new registration. The check applies only to new registration (the transitional overlap window is settled at implementation).
- The suffix counter is monotonically increasing per name — reuse is forbidden.
- Unverified (to confirm at implementation): whether the `(1)` notation conflicts with the name grammar, envelope rendering, and CLI comma splitting.
