# ADR-0309: 우편 내부 키는 에이전트 id — 가장자리 주소는 이름 그대로

- 상태: 확정 (2026-10-29, 근거: 사용자 결정 — S29 문답 2026-10-29 「하는 김에 한꺼번에」 · 기록 표시 = 보낼 때 이름)
- 관련: Amends ADR-0114 (id 키 기각 근거) · Amends ADR-0115 (id 병행 키 기각 근거) · Amends ADR-0116 (결정 3 정리 키와 이름 축 가드) · Amends ADR-0120 (파킹 키 id 기각 근거와 사문화 목록 3과 5) · ADR-0101(가장자리 주소 = 표시 이름 — 그대로) · ADR-0179(멀티 데몬 연결 — 우편 경로는 미정) · ADR-0308(에이전트 참조 인자를 데몬이 id 로) · `docs/process/S29-mail-id-keys/` · Amends ADR-0111 (결정 6 새 화신 판정 기준)

## 맥락

메시징은 받는 이를 입구에서 찾는다 — 깨어 있는 에이전트는 정확한 id 먼저, 그다음 유일한 이름으로 찾고, 잠든 에이전트는 **이름으로만** 찾는다(데몬이 잠든 쪽은 이름 목록만 넘긴다 — 그래서 잠든 에이전트를 정확한 id 로 부르면 지금은 `RECIPIENT_NOT_FOUND` 다). 찾은 뒤의 키는 섞여 있다(코드 확인 2026-10-29).
- **이름 키:** 대기 우편함의 큐 키 · 장부 기록 `MessageRecord` 의 보낸 이 · 받는 이 · 요청자 이름으로 여는 계약 실패 처리 · 잠든 수신자 앞 계약(받는 이 id 없음 — 이름 폴백으로 맞춘다).
- **이미 id:** 계약의 보낸 이 id(늘) · 깨어 있는 수신자 앞 계약의 받는 이 id · 회신 · 의무 대조는 id 먼저. 깨어 있는 수신자의 대기 우편에는 id 가 힌트로 덧붙는다.

ADR-0114 · 0115 · 0120 은 「id 를 키로 함께 싣기」를 「이름 유일성을 강제하는 편이 훨씬 싸다」는 이유로 기각했다.

이름 유일성(ADR-0115 · 0120)은 **한 시점의 겹침**만 막는다. **이름이 바뀌는 것**은 못 막는다(코드 확인 · 재현 안 함 · 가능성 높음).
- 잠든 에이전트 앞 대기 우편은 힌트 없이 이름에만 묶인다. 그 프로필 이름을 A → B 로 바꾸면 B 는 A 큐를 열지 않아 24h 뒤 조용히 만료된다.
- 바뀌어 비어 버린 이름 A 를 다른 프로필이 가져가 깨어나면 **그 에이전트가 남의 우편을 받는다** — ADR-0116 결정 1 · ADR-0120 이 막으려던 결말이 개명 경로로 열려 있다.
- 이름을 바꾼 에이전트 자신의 「보낸 대기 우편」이 우편 조회 목록에서 사라진다(장부가 보낸 이를 지금 이름으로 대조한다).
- 개명 사건은 메시징에 전달되지 않는다.

덧붙여 사용자는 나중에 멀티 데몬을 붙일 계획이다(다른 서버의 에이전트에게도 우편이 가야 한다). 서버마다 이름이 겹칠 수 있으니, 이름을 내부 키로 쓰면 그때 다시 갈아야 한다.

## 결정

1. **대기 우편함 · 장부 · 회신 계약의 내부 키는 에이전트 id(프로필 id — UUID)다.** 위 「이름 키」 넷이 모두 id 로 바뀌고, 잠든 수신자 앞 계약도 받는 이 id 를 갖는다. 같은 프로필을 다시 띄워도 id 가 같고 화신은 지금처럼 epoch 로 따로 가린다 — 그래서 대기 우편은 **같은 에이전트(같은 id)의 새 화신**에게 간다. ADR-0111 결정 6 의 「같은 이름의 새 화신」은 이름이 전역 유일하고 바뀌지 않는 동안 이것과 같은 말이고, 개명 · 삭제 뒤 같은 이름을 새로 가진 다른 에이전트는 받지 않는다(결정 5).
2. **가장자리 주소는 이름 그대로다(ADR-0101 불변).** LLM 이 보내는 주소 · 받은 우편의 보낸 이 표시 · 우편 조회 결과가 이름이다.
3. **이름 → id 변환은 받는 이를 찾는 입구 한 곳에서만 한다.** 그 뒤의 단계(배달 · 맡겨 두기 · 기록 · 삭제 정리)는 id 만 다룬다. 「받는 이는 이 데몬 안에 있다」는 가정도 그 입구 밖으로 퍼뜨리지 않는다 — 멀티 데몬 때 「여기 없으면 다른 데몬으로」 갈래가 그 한 곳에 끼어든다.
   - 데몬이 메시징에 넘기는 잠든 에이전트 목록은 이름 목록이 아니라 **(id, 이름) 쌍**이 된다. 그래서 잠든 에이전트도 정확한 id 로 부를 수 있게 된다.
   - `@all` 같은 무리 펼침은 명부의 id 로 바로 펼친다(이름 → id 왕복 없음).
4. **장부는 id 와 보낼 때 이름을 함께 적고, 우편 조회에는 보낼 때 이름을 보인다**(사용자 결정 — 지금 동작과 같다). 누구인지는 id 로 대조한다.
5. **따라오는 동작 변화(사용자 결정 — 한꺼번에):** 잠든 사이 이름이 바뀐 에이전트도 대기 우편을 받는다 · 옛 이름을 새로 가진 다른 에이전트에게 우편이 가지 않는다 · 이름을 바꿔도 자기가 보낸 대기 우편이 조회 목록에 남는다.
6. **프로필 삭제 정리는 id 로 판정하고 id 로 쓸어 간다** — ADR-0116 결정 3 의 정리 대상 ①(그 수신자 앞 파킹분) · ②(그가 요청자인 오픈 계약)를 id 로 찾고, 이름 축 가드(「그 이름을 가진 산 세션이 없음」)는 이름으로 쓸어 가던 시절의 장치라 걷는다. 정리 결과(`RECIPIENT_DELETED` · `reply_failed` · 판정 뒤 잔여분은 TTL `expired`)는 그대로다.
7. **이름 키를 보완하던 장치는 걷는다** — 깨어 있는 수신자의 id 힌트와 그 힌트로 큐를 훑는 경로 · 잠든 수신자 앞 계약의 이름 폴백 대조.

## 거부한 대안

- **이름 키 유지 — 이름 유일성(ADR-0115 · 0120)에 맡긴다** — 유일성은 한 시점의 겹침만 막고 개명은 못 막는다. 개명 뒤 잠든 수신자 우편이 사라지거나 남에게 가는 경로가 남는다(맥락 — 코드 확인).
- **잠든 수신자의 대기 우편에만 id 힌트를 붙이는 작은 수정** — 2~3 파일로 개명 문제의 잠든 쪽은 막는다. 사용자가 「하는 김에 한꺼번에」로 전체 전환을 골랐다(2026-10-29) — 힌트 장치 · 이름 축 가드 같은 이중 축이 그대로 남고, 멀티 데몬 때 다시 갈아야 한다.
- **우편 조회에 지금 이름을 보인다** — 조회할 때마다 id 로 지금 이름을 찾는다. 받는 이가 지워졌거나(멀티 데몬에서) 상대 서버가 꺼져 있으면 보일 이름이 없어 대체 규칙이 따로 필요하다. 우편 본문의 보낸 이 표시도 보낼 때 이름이라 둘이 어긋난다. 사용자가 보낼 때 이름을 골랐다(2026-10-29).
- **지금 우편 · 명부에 서버 칸을 넣는다** — 데몬이 하나라 값이 늘 「여기」다. 우편함 · 장부는 디스크에 저장하지 않아(코드 확인) 칸을 나중에 더해도 옮길 데이터가 없다. 서버 칸(명부의 「id → 서버」 · 받은 우편의 「들어온 연결」)은 멀티 데몬 착수 때 더한다(사용자 동의 2026-10-29).

## 근거

- 사용자 결정(2026-10-29): 「밖에서 이름 부르는 건 동일하고 내부에서 id 로 치환」 · 「하는 김에 한꺼번에」 · 기록 표시 = 보낼 때 이름 · 멀티 데몬은 나중이며 이번 작업이 그것을 막지 않을 것.
- 코드 확인(2026-10-29 · 정적 조사 둘과 문서 리뷰 하나가 교차 확인): 개명은 메시징을 부르지 않는다(데몬 `connection_core.rs` 의 개명 처리) · 잠든 수신자 파킹은 id 힌트가 없다 · 보낸 이 대조는 지금 이름(`service.rs` 의 우편 조회) · 프로필 삭제는 id 축과 이름 축을 함께 본다 · 우편함 · 장부에 디스크 저장이 없다 · 같은 프로필의 재기동은 id 가 같다(세션 id = 프로필 id · 화신 = epoch).
- 이전 기각(ADR-0114 · 0115 · 0120)의 근거는 「이중 키 재설계 비용 > 이름 유일성 강제 비용」이었다. 계약은 이미 id 를 반쯤 들고 있었고, 이 결정은 이중 키가 아니라 **키 교체**라 이중 축이 오히려 걷히고, 그 기각이 보지 못한 개명 경로를 닫는다.

## 영향 / 불변식

- **이름 유일성(ADR-0115 · 0120)은 그대로 유효하다** — 가장자리 주소가 이름이므로 이름이 겹치면 입구에서 받는 이를 못 고른다. 이 결정은 그 위의 내부 키만 바꾼다.
- **ADR-0120 「사문화 목록」과의 관계:** 3(이름 폴백)은 결정 7 로, 5(삭제 정리의 이름 축 가드)는 결정 6 으로 이 전환에서 걷힌다. 1 · 2 · 4(잠듦 층 동명 차단 · 산/잠듦 층위 우선 · loser 키)는 입구 쪽 이름 해석 장치라 키 교체와 별개다 — 코드에 남아 있으면 TRD 가 지금도 닿는지 보고 판정한다.
- **ADR-0120 의 거부한 대안 「잠들 때 이름을 반납」은 기각 근거 하나(이름 키 파킹이 남에게 간다)를 잃었다** — 그 대안을 다시 꺼낼 때는 이 근거를 빼고 다시 따진다(이름 유일성 쪽 근거는 그대로다).
- **동명 쌍둥이(서로 다른 에이전트가 같은 이름)는 서로 다른 수신자로 다룬다** — 이름 유일성 아래에서는 생기지 않아야 하지만 ADR-0122 의 삭제 구멍 · 옛 데이터로 아직 생긴다(동명은 미지원 — ADR-0116 결정 5). id 키에서 따라오는 결말(메인 판정 2026-10-29 · 사용자 자율 위임 중): `@all` 펼침 · 정확한 id 지목 · 등장 배달이 쌍둥이 각자에게 가고, 발신자 빼기는 id 로만 한다. **이름으로 부르면 지금처럼 `RECIPIENT_AMBIGUOUS`** 다 — 결정 2 의 이름 해석 규칙(ADR-0120 사문화 목록 1 · 2)은 남는다. 정본 목록 = TRD S29 §4 X0~X4.
- **id 는 서버를 넘어 유일해야 한다** — UUID 를 새로 뽑는 한 성립한다. 프로필을 다른 PC · 서버로 복사하는 기능이 생기면 복사본은 새 id 를 받아야 한다(그런 기능이 지금 있는지는 확인하지 않았다).
- 입구 해석기는 대문자 · 중괄호 UUID 를 받지 않고 ADR-0308 의 `resolve_in` 은 받는다. 코드가 이 차이를 알고 남겼다고 적어 두었다(agent `commands.rs` 주석 · 데몬 대조 시험) — 이 전환에서 맞출지는 TRD 가 그 사유를 보고 정한다.
- 멀티 데몬 때 할 일(이번 범위 아님): 명부의 「id → 서버」 · 받은 우편에 받는 순간 찍는 출처 서버 · 서버를 넘는 보낸 이 보증 · `이름@서버` 꼴 주소(ADR-0101 개정 — 사용자 결정).
