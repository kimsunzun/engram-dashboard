# ADR-0309: The internal mail key is the agent id — the edge address stays the name

- 상태: 확정 (2026-10-29, basis: user decision — S29 Q&A 2026-10-29 「하는 김에 한꺼번에」 · record display = the name at send time)
- 관련: Amends ADR-0114 (the rationale for rejecting an id key and decision 4) · Amends ADR-0115 (the rationale for rejecting a parallel id key) · Amends ADR-0116 (decision 3's cleanup key and the name-axis guard) · Amends ADR-0120 (the rationale for rejecting an id parking key and items 3 and 5 of the obsoleted list) · ADR-0101 (edge address = display name — unchanged) · ADR-0179 (multi-daemon connection — the mail path is undecided) · ADR-0308 (the daemon converts agent-reference arguments to ids) · `docs/process/S29-mail-id-keys/` · Amends ADR-0111 (decision 6's criterion for a new incarnation) · Amends ADR-0142 (decision 2, keeping the name axis)

## 맥락

Messaging finds the recipient at the entry point — an awake agent is found by exact id first, then by unique name, and a sleeping agent is found **by name only** (the daemon hands over only the list of names for the sleeping side — so calling a sleeping agent by its exact id is currently `RECIPIENT_NOT_FOUND`). The keys after it is found are mixed (code check 2026-10-29).
- **Name keys:** the queue key of the waiting mailbox · the sender, recipient, and requester names in the ledger record `MessageRecord` · contract-failure handling opened by the requester's name · the contract addressed to a sleeping recipient (no recipient id — matched by name fallback).
- **Already id:** the contract's sender id (always) · the recipient id of a contract addressed to an awake recipient · reply · obligation matching is id first. For an awake recipient's waiting mail, the id is attached as a hint.

ADR-0114 · 0115 · 0120 rejected 「id 를 키로 함께 싣기」 on the grounds that 「이름 유일성을 강제하는 편이 훨씬 싸다」.

Name uniqueness (ADR-0115 · 0120) prevents only an **overlap at one point in time**. It cannot prevent **a name changing** (code check · not reproduced · likely).
- Waiting mail for a sleeping agent is tied to the name only, with no hint. If that profile's name is changed from A to B, B does not open A's queue, and the mail silently expires after 24h.
- If another profile takes the vacated name A and wakes up, **that agent receives someone else's mail** — the outcome ADR-0116 decision 1 · ADR-0120 tried to prevent is open through the rename path.
- The renamed agent's own 「보낸 대기 우편」 disappears from the mail query list (the ledger matches the sender against the current name).
- The rename event is not delivered to messaging.

In addition, the user plans to attach multi-daemon later (mail must also go to agents on other servers). Names can overlap between servers, so using the name as an internal key would mean swapping it again then.

## 결정

1. **The internal key of the waiting mailbox · ledger · reply contract is the agent id (the profile id — a UUID).** The four 「이름 키」 above all become ids, and a contract addressed to a sleeping recipient also carries the recipient id. Even if the same profile is started again, the id is the same, and the incarnation is separated by epoch as now — so waiting mail goes to **a new incarnation of the same agent (the same id)**. ADR-0111 decision 6's 「같은 이름의 새 화신」 means the same thing as this while the name is globally unique and does not change, and it does not go to a different agent that newly holds the same name after a rename · deletion (decision 5).
2. **The edge address stays the name (ADR-0101 unchanged).** The address the LLM sends to · the sender display of received mail · the mail query result are names.
3. **The name → id conversion happens in one place only, the entry point that finds the recipient.** The steps after it (delivery · holding · recording · deletion cleanup) handle ids only. The assumption 「받는 이는 이 데몬 안에 있다」 is also not spread beyond that entry point — in multi-daemon, the branch 「여기 없으면 다른 데몬으로」 gets inserted into that one place.
   - The list of sleeping agents the daemon hands to messaging becomes **(id, name) pairs**, not a list of names. So a sleeping agent can also be called by an exact id.
   - A group expansion such as `@all` expands straight from the registry's ids (no name → id round trip).
4. **The ledger records the id and the name at send time together, and the mail query shows the name at send time** (user decision — the same as current behavior). Who it is is matched by id.
5. **Behavior changes that follow (user decision — all at once):** an agent whose name changed while asleep also receives its waiting mail · mail does not go to a different agent that newly holds the old name · even if the name is changed, the waiting mail the agent itself sent remains in the query list.
6. **Profile-deletion cleanup is decided by id and swept by id** — the cleanup targets of ADR-0116 decision 3, ① (the parked items addressed to that recipient) · ② (the open contracts where that recipient is the requester), are found by id, and the name-axis guard (「그 이름을 가진 산 세션이 없음」) was a device from the era of sweeping by name, so it is removed. The cleanup results (`RECIPIENT_DELETED` · `reply_failed` · the remainder after the decision is TTL `expired`) are unchanged.
7. **The devices that supplemented the name key are removed** — the awake recipient's id hint and the path that scans queues by that hint · the name-fallback matching of a contract addressed to a sleeping recipient.

## 거부한 대안

- **Keep the name key — leave it to name uniqueness (ADR-0115 · 0120)** — uniqueness prevents only an overlap at one point in time and cannot prevent a rename. After a rename, there remains a path where a sleeping recipient's mail disappears or goes to someone else (Context — code check).
- **A small fix that attaches an id hint only to waiting mail for sleeping recipients** — in 2–3 files it blocks the sleeping side of the rename problem. The user chose the full switch with 「하는 김에 한꺼번에」 (2026-10-29) — a dual axis such as the hint device · the name-axis guard stays as is, and it would have to be swapped again at multi-daemon.
- **Show the current name in the mail query** — each query would look up the current name by id. If the recipient has been deleted (in multi-daemon) or the other server is down, there is no name to show and a separate fallback rule is needed. The sender display in the mail body is also the name at send time, so the two would disagree. The user chose the name at send time (2026-10-29).
- **Put a server field into mail · the registry now** — there is one daemon, so the value would always be 「여기」. The mailbox · ledger are not stored on disk (code check), so even if the field is added later there is no data to migrate. The server field (the registry's 「id → 서버」 · the received mail's 「들어온 연결」) is added when multi-daemon work starts (user agreed 2026-10-29).

## 근거

- User decision (2026-10-29): 「밖에서 이름 부르는 건 동일하고 내부에서 id 로 치환」 · 「하는 김에 한꺼번에」 · record display = the name at send time · multi-daemon is later and this work must not block it.
- Code check (2026-10-29 · cross-checked by two static investigations and one document review): a rename does not call messaging (the rename handling in the daemon's `connection_core.rs`) · parking for a sleeping recipient has no id hint · the sender matching is by current name (the mail query in `service.rs`) · profile deletion looks at both the id axis and the name axis · the mailbox · ledger have no disk storage · restarting the same profile has the same id (session id = profile id · incarnation = epoch).
- The rationale of the earlier rejections (ADR-0114 · 0115 · 0120) was 「이중 키 재설계 비용 > 이름 유일성 강제 비용」. The contract was already half carrying the id, and this decision is a **key replacement**, not dual keys, so the dual axis is actually removed, and it closes the rename path those rejections did not see.

## 영향 / 불변식

- **Name uniqueness (ADR-0115 · 0120) remains valid** — since the edge address is a name, if names overlap, the recipient cannot be chosen at the entry point. This decision changes only the internal key above it.
- **Relation to the ADR-0120 「사문화 목록」:** 3 (name fallback) is removed in this switch by decision 7, and 5 (the name-axis guard of deletion cleanup) by decision 6. 1 · 2 · 4 (same-name blocking in the sleeping layer · live/sleeping layer priority · the loser key) are name-resolution devices on the entry side, independent of the key replacement — if they remain in the code, the TRD looks at whether they are still reached and decides.
- **ADR-0120's rejected alternative 「잠들 때 이름을 반납」 lost one rejection ground (name-key parking goes to someone else)** — when that alternative is brought back, reconsider it without this ground (the name-uniqueness ground is unchanged).
- **Same-name twins (different agents with the same name) are treated as different recipients** — under name uniqueness they should not occur, but they still occur through ADR-0122's deletion hole · old data (same names are unsupported — ADR-0116 decision 5). The outcome that follows from id keys (main-agent decision 2026-10-29 → user confirmation the same day — with `@all`, both twins silently receive it · targeting by name is `RECIPIENT_AMBIGUOUS` + 「사용자에게 알려라」 · targeting by exact id reaches only that agent): `@all` expansion · exact-id targeting · appearance delivery go to each twin, and removing the sender is done by id only. **Calling by name is `RECIPIENT_AMBIGUOUS` as now** — decision 2's name-resolution rules (ADR-0120 obsoleted-list items 1 · 2) remain. Canonical list = TRD S29 §4 X0~X4.
- **An id must be unique across servers** — it holds as long as UUIDs are newly generated. If a feature that copies a profile to another PC · server arises, the copy must receive a new id (whether such a feature exists now was not checked).
- The entry resolver does not accept uppercase · braced UUIDs, while ADR-0308's `resolve_in` does. The code notes that it knew of this difference and left it (comment in agent `commands.rs` · the daemon matching test) — whether to align it in this switch is decided by the TRD after looking at that reason.
- Work for multi-daemon (not in this scope): the registry's 「id → 서버」 · the origin server stamped on received mail at the moment of receipt · sender assurance across servers · `이름@서버` form addresses (an amendment of ADR-0101 — user decision).
