# ADR-0326: Emptying the trash and permanent deletion = hand over to the OS trash and let the OS decide — amends ADR-0322 Decisions 5 · 6 · 7

- 상태: 제안 (2026-10-31, basis: user decisions G47 (2026-10-31 「음? 일단 이미 삭제해서 간거라서 삭제하는거에 대해서 디테일하게 챙길 필요있음?」 → 「그냥 휴지통으로 보내고 삭제되던지 말던지는 다 os에서 알아서 하라고그래」) · G50 (2026-10-31 「그냥 휴지통말고 삭제하시겠습니까해」) · G12 (2026-10-20 — the original rule, returned to) + main M64 · M69 (thread — unchanged) · M79 · M83 · M85 (re-review r9 · reported) · M86 (re-review r10 · reported))
- 관련: Amends ADR-0322 (title and Decisions 5, 6 and 7) (+ the result wording of Decision 4 · rejected alternatives · consequences — see 「바뀌는 조항」 below) · ADR-0320 · ADR-0324 · ADR-0292 · ADR-0293 · CLAUDE.md 「플랫폼 중립」 · PRD R18 · TRD §1-6 OS trash row · 「결과 가름」 · §6-2 · §6-5 8 · 9 (U1 · U2) · §7 20 · §7 28

## 맥락
ADR-0322 had us separate failures of sending to the OS trash — permanently delete only on codes confirmed as 「휴지통 없음 · 꺼짐」, leave in `.trash` anything in use · denied · too large · unknown code (Decision 5 · G45 · M59), and place a `PreDeleteItem` guard so the engine does not delete (Decision 6 · M59 — the TRD narrowed it down to 「엔진은 `no_bin_confirmed` 만 돌려주고 platform 영구 삭제 함수가 지운다」 in M70). Then two questions remained for the user: that `.trash` on a volume without a trash could no longer be emptied from Engram (U1), and whether too large and unknown codes should also be left (U2). The user judged that the emptying target has already been deleted and moved to `.trash`, so there is no reason to look after the deletion method separately, and returned to the original rule of G12 (2026-10-20).

## 결정
1. Permanent deletion in emptying the trash and viewing the trash = hand the entries over to the OS trash of the daemon PC and **let the OS decide** — whether it puts them in the trash or cannot and deletes them as they are, it is Windows behavior as is (G47 · G12).
2. There is no guard — no `TSF_DELETE_RECYCLE_IF_POSSIBLE` check of `PreDeleteItem`, no decision that there is no trash, and no separate platform permanent-deletion step (G47).
3. Entry result = two values, **gone · remaining** + the original native code (for diagnostics only). What the OS rejected (an open file, denied, etc.) is left in `.trash` and reported per entry. The separation = before and after — a path that was already absent **before** the call is `NOT_FOUND` · one that is gone **after** the call is gone (M85). The check for existence runs **before** the thread and COM initialization — even if initialization fails, an entry that was absent before the call is `NOT_FOUND` (M86). Each entry calls its own `PerformOperations` (M66), so no entry is skipped with `FOFX_EARLYFAILURE` — we do not keep a not_attempted field (M85 · withdraws the field that G47 left). The result fields of M62 · M71 are folded into this shape.
4. The confirmation modal = a delete question that does not mention the trash — e.g. title 「영구 삭제」 · body 「항목 12개를 삭제하시겠습니까?」 · [Cancel] [Delete] (G50 — replaces the draft 「Windows 휴지통으로 보냅니다 — 휴지통이 없는 드라이브면 바로 지웁니다」 that G47 left · behavior as in Decision 1). N = the number of entries (lines) that the trash view shows — not the number of bundle folders · the same for empty-all (M79).
5. The calling means (`IFileOperation` directly · the `trash` crate) is measured again at implementation — per-entry failure reporting is still needed and the worry about a third `windows` copy remains (G47).
6. **Empty-all = only the bundle ids that the trash view showed** — the screen sends the bundle ids shown in the list and the daemon empties only those bundles · an entry deleted after the list stays in `.trash` (M83 · the N in the modal is also the shown lines — M79). A `library.emptyTrash` with neither `items` nor bundle ids is rejected — whoever calls it, the guarantee of M83 is kept (M86).
7. Unchanged: human-only · the shell-only bus command (ADR-0322 Decisions 1~3) · send as whole bundles, and for a bundle that failed, send the remaining entries again one by one (Decision 4) · lock and hand-over (the rest of Decision 7 · ADR-0324) · no automatic emptying (Decision 8) · thread = `std::thread::Builder::spawn` a new STA thread per call · failures as values · no new containment place (M64 · M69 · ADR-0292 · ADR-0293) · the OS split is inside one platform function (「플랫폼 중립」).

**Clauses that change (ADR-0322):**
- Title 「… 영구 삭제는 휴지통이 없다고 확정될 때만」 → 「… OS 가 정한다」.
- **Decision 5** (separating send failures) — replaced as a whole → Decisions 1 · 3 of this ADR. The 「확인 모달이 미리 말하는 것도 이 가름이다」 inside it → Decision 4.
- **Decision 6** — the guard is withdrawn (Decision 2). 「platform 이 `IFileOperation` 을 직접 부른다(M57)」 is not settled but measured again at implementation (Decision 5). 「OS 갈림은 platform 함수 하나 안」 stays.
- Decision 4 — the result of 「그 묶음 결과는 항목마다 싣는다」 = the two values of Decision 3. The re-sending shape stays.
- **Decision 7** — the bundles that empty-all empties = the bundle ids that the trash view showed (Decision 6 of this ADR · M83) · reject if there are neither `items` nor bundle ids (M86). The 「그 뒤 생긴 묶음은 건드리지 않는다」 · lock · hand-over · continuing with the copied-aside root even if `setRoot` intervenes stay.
- Rejected alternatives — 「세 HRESULT 로 갈라 「없음」 then permanently delete」 · 「보내기 전에 미리 확인」 the question disappears (we do not separate). The rejection of 「`trash` crate」 is reopened (Decision 5). The rejection of 「보내기가 안 되면 무엇이든 영구 삭제」 still stands because there is no deletion step on our side — in use and denied, which the OS rejected, remain (Decision 3).
- Consequences — first line 「그래서 뒤가 아니라 앞에 말한다(G12)」 → the modal asks as a delete (Decision 4). Pilot measurement list → the shortened list in 「영향」 below. Last line 「영구 삭제의 가름을 넓히면 G45 를 다시 연다」 → 「영향」 below.

## 거부한 대안
- **Separating by code ourselves to decide whether to delete** — 「휴지통 없음 · 꺼짐」 permanently delete only on confirmed codes · leave too large and unknown codes (M59 — the narrowed shape of the reason separation in ADR-0322 Decision 5 · G45) — user 「음? 일단 이미 삭제해서 간거라서 삭제하는거에 대해서 디테일하게 챙길 필요있음?」 → 「그냥 휴지통으로 보내고 삭제되던지 말던지는 다 os에서 알아서 하라고그래」 (G47).
- **The `PreDeleteItem` guard + a platform permanent-delete function after `no_bin_confirmed`** (M59 · M70 — ADR-0322 Decision 6 · TRD §1-6) — the same user words (G47).
- **(U1) A human-only 「그래도 영구 삭제」 confirmation for entries that could not be emptied because of the guard · (U2) approval to leave too large and unknown codes** — the questions disappeared (G47 — there is no guard, so the OS decides).
- **Mentioning the trash in the confirmation modal** (main's fill-in of G12 · the draft 「Windows 휴지통으로 보냅니다 — 휴지통이 없는 드라이브면 바로 지웁니다」 that G47 left) — user 「그냥 휴지통말고 삭제하시겠습니까해」 (G50).
- **Empty-all = everything that is in `.trash` at that moment** (the 「휴지통 잠금 아래 떠 둔 목록」 of ADR-0322 Decision 7) — basis (main 2026-10-31 — reported): the human confirmed the N entries seen in the modal (the shown lines — M79) · if we empty even what was deleted after the list, we irreversibly delete what was not confirmed (M83).
- **A not_attempted field** (what G47 left — M66 · M71) — each entry is called separately, so there is no entry to skip (M85).

## 근거
- User decisions G47 · G50 (2026-10-31) · G12 (2026-10-20 「휴지통 비우면 윈도우 휴지통으로 보내고 안되면 그냥 삭제되게」 — the rule returned to). M79 · M83 · M85 = main (re-review r9 — reported) · M86 = main (re-review r10 — reported).
- User reason (G47): the emptying target has already been deleted and moved to `.trash` — there is no reason to look after the deletion method separately.
- The reason of ADR-0322 「근거」 (leave it restorable even if an agent deletes by mistake — F9) stays — it is kept by emptying being human-only (ADR-0322 Decision 1 — unchanged).

## 영향 / 불변식
- This is behavior we accepted even if Windows deletes instead of using the trash — the 「사라짐」 in the result does not say whether it went into the trash.
- The pilot (9b) shrinks: does an OS call run under the daemon (thread — M64 · M69) · do open files remain · any UI dialog that appears is a failure (G47).
- When the calling means is chosen (Decision 5), the cost line of ADR-0322 「영향」 (`Win32_UI_Shell` · COM implementation · STA thread) changes accordingly.
- Reintroducing a separation, guard or deletion step on our side reopens G47. A change that puts emptying on the LLM surface still reopens ADR-0322.
- Places to fix accordingly (another worker's share — to confirm): TRD §1-6 OS trash row · the 「결과 가름」 table · §6-2 9b · §6-5 8 · 9 (U1 · U2) · the M70 sentence in §7 20 · §7 28 · the PRD R18 wording.
