# ADR-0326: 휴지통 비우기 · 영구 삭제 = OS 휴지통에 넘기고 OS 가 정한다 — ADR-0322 결정 5 · 6 · 7 개정

- 상태: 제안 (2026-10-31, 근거: 사용자 결정 G47(2026-10-31 「음? 일단 이미 삭제해서 간거라서 삭제하는거에 대해서 디테일하게 챙길 필요있음?」 → 「그냥 휴지통으로 보내고 삭제되던지 말던지는 다 os에서 알아서 하라고그래」) · G50(2026-10-31 「그냥 휴지통말고 삭제하시겠습니까해」) · G12(2026-10-20 — 되돌아간 원래 규칙) + 메인 M64 · M69(스레드 — 그대로) · M79 · M83 · M85(재리뷰 r9 · 보고) · M86(재리뷰 r10 · 보고))

## 맥락
ADR-0322 는 OS 휴지통 보내기의 실패를 우리가 갈랐다 — 「휴지통 없음 · 꺼짐」 으로 확정된 코드에서만 영구 삭제하고 쓰는 중 · 거부 · 너무 큼 · 모르는 코드는 `.trash` 에 남기며(결정 5 · G45 · M59), 엔진이 지우지 않게 `PreDeleteItem` 가드를 둔다(결정 6 · M59 — TRD 는 M70 으로 「엔진은 `no_bin_confirmed` 만 돌려주고 platform 영구 삭제 함수가 지운다」 까지 좁혔다). 그러자 휴지통 없는 볼륨의 `.trash` 를 Engram 에서 비울 수 없게 되는 것(U1)과 너무 큼 · 모르는 코드도 남길지(U2)가 사용자 물음으로 남았다. 사용자는 비우기 대상이 이미 지워 `.trash` 로 간 것이라 지우는 방식을 따로 챙길 까닭이 없다고 보고 G12(2026-10-20)의 원래 규칙으로 되돌렸다.

## 결정
1. 휴지통 비우기 · 휴지통 보기의 영구 삭제 = 항목을 데몬 PC 의 OS 휴지통에 넘기고 **OS 가 정한다** — 휴지통에 넣든, 넣지 못해 그대로 지우든 Windows 의 동작 그대로다(G47 · G12).
2. 가드가 없다 — `PreDeleteItem` 의 `TSF_DELETE_RECYCLE_IF_POSSIBLE` 검사 · 휴지통 없음 판정 · 따로 된 platform 영구 삭제 단계를 두지 않는다(G47).
3. 항목 결과 = **사라짐 · 남음** 둘 + 원 네이티브 코드(진단으로만). OS 가 거절한 것(열린 파일 · 거부 등)은 `.trash` 에 남기고 항목마다 알린다. 가름 = 앞뒤 — 부르기 **전에** 이미 없던 경로는 `NOT_FOUND` · 부른 **뒤** 없어진 것은 사라짐(M85). 있는지 먼저 보기는 스레드 · COM 초기화 **앞**에서 돈다 — 초기화가 실패해도 부르기 전에 없던 항목은 `NOT_FOUND` 다(M86). 항목 하나마다 제 `PerformOperations` 를 부르므로(M66) `FOFX_EARLYFAILURE` 로 건너뛰는 항목이 없다 — not_attempted 칸을 두지 않는다(M85 · G47 이 남겨 둔 칸을 걷음). M62 · M71 의 결과 칸을 이 꼴로 접는다.
4. 확인 모달 = 휴지통을 말하지 않는 삭제 물음 — 예 제목 「영구 삭제」 · 본문 「항목 12개를 삭제하시겠습니까?」 · [취소] [삭제](G50 — G47 이 남겨 둔 초안 「Windows 휴지통으로 보냅니다 — 휴지통이 없는 드라이브면 바로 지웁니다」 를 대신한다 · 동작은 결정 1 그대로). N = 휴지통 보기가 보이는 항목(줄) 수 — 묶음 폴더 수가 아니다 · 전부 비우기도 같다(M79).
5. 부르는 수단(`IFileOperation` 직접 · `trash` crate)은 구현 때 다시 잰다 — 항목마다 실패 보고는 여전히 필요하고 셋째 `windows` 사본 걱정은 그대로다(G47).
6. **전부 비우기 = 휴지통 보기가 보인 묶음 id 만** — 화면은 목록에 보인 묶음 id 를 보내고 데몬은 그 묶음만 비운다 · 목록 뒤에 지운 항목은 `.trash` 에 남는다(M83 · 모달의 N 도 보인 줄 — M79). `items` 도 묶음 id 도 없는 `library.emptyTrash` 는 거절한다 — 누가 부르든 M83 의 보장을 지킨다(M86).
7. 그대로인 것: 사람만 · 셸 전용 버스 명령(ADR-0322 결정 1~3) · 묶음째 보내고 실패한 묶음은 남은 것을 항목마다 다시 보낸다(결정 4) · 잠금 · 넘겨주기(결정 7 의 나머지 · ADR-0324) · 저절로 비우지 않음(결정 8) · 스레드 = 호출마다 `std::thread::Builder::spawn` 새 STA 스레드 · 실패는 값으로 · 새 가둠 자리 없음(M64 · M69 · ADR-0292 · ADR-0293) · OS 갈림은 platform 함수 하나 안(「플랫폼 중립」).

**바뀌는 조항 (ADR-0322):**
- 제목 「… 영구 삭제는 휴지통이 없다고 확정될 때만」 → 「… OS 가 정한다」.
- **결정 5**(보내기 실패의 가름) — 통째로 바뀐다 → 이 ADR 결정 1 · 3. 그 안 「확인 모달이 미리 말하는 것도 이 가름이다」 → 결정 4.
- **결정 6** — 가드를 걷는다(결정 2). 「platform 이 `IFileOperation` 을 직접 부른다(M57)」 는 확정이 아니라 구현 때 다시 잰다(결정 5). 「OS 갈림은 platform 함수 하나 안」 은 그대로.
- 결정 4 — 「그 묶음 결과는 항목마다 싣는다」 의 결과 = 결정 3 의 두 값. 다시 보내는 꼴은 그대로.
- **결정 7** — 전부 비우기가 비울 묶음 = 휴지통 보기가 보인 묶음 id(이 ADR 결정 6 · M83) · `items` 도 묶음 id 도 없으면 거절(M86). 「그 뒤 생긴 묶음은 건드리지 않는다」 · 잠금 · 넘겨주기 · `setRoot` 가 끼어도 떠 둔 루트로 계속은 그대로.
- 거부한 대안 — 「세 HRESULT 로 갈라 「없음」 이면 영구 삭제」 · 「보내기 전에 미리 확인」 은 물음이 사라진다(우리가 가르지 않는다). 「`trash` crate」 거부는 다시 연다(결정 5). 「보내기가 안 되면 무엇이든 영구 삭제」 거부는 우리 쪽 지우기 단계가 없어 그대로 선다 — OS 가 거절한 쓰는 중 · 거부는 남는다(결정 3).
- 영향 — 첫 줄 「그래서 뒤가 아니라 앞에 말한다(G12)」 → 모달은 삭제로 묻는다(결정 4). 파일럿 실측 목록 → 아래 「영향」 의 줄인 목록. 마지막 줄 「영구 삭제의 가름을 넓히면 G45 를 다시 연다」 → 아래 「영향」.

## 거부한 대안
- **우리가 코드로 갈라 지울지 정하기** — 「휴지통 없음 · 꺼짐」 확정 코드에서만 영구 삭제 · 너무 큼 · 모르는 코드는 남김(M59 — ADR-0322 결정 5 · G45 의 이유 가름을 좁힌 꼴) — 사용자 「음? 일단 이미 삭제해서 간거라서 삭제하는거에 대해서 디테일하게 챙길 필요있음?」 → 「그냥 휴지통으로 보내고 삭제되던지 말던지는 다 os에서 알아서 하라고그래」(G47).
- **`PreDeleteItem` 가드 + `no_bin_confirmed` 뒤 platform 영구 삭제 함수**(M59 · M70 — ADR-0322 결정 6 · TRD §1-6) — 같은 사용자 말(G47).
- **(U1) 가드에 걸려 못 비운 항목에 사람만 쓰는 「그래도 영구 삭제」 확인 · (U2) 너무 큼 · 모르는 코드 남김 승인** — 물음이 사라졌다(G47 — 가드가 없어 OS 가 정한다).
- **확인 모달에 휴지통을 말하기**(G12 의 메인 채움 · G47 이 남겨 둔 초안 「Windows 휴지통으로 보냅니다 — 휴지통이 없는 드라이브면 바로 지웁니다」) — 사용자 「그냥 휴지통말고 삭제하시겠습니까해」(G50).
- **전부 비우기 = 그 순간 `.trash` 에 있는 전부**(ADR-0322 결정 7 의 「휴지통 잠금 아래 떠 둔 목록」) — 근거(메인 2026-10-31 — 보고): 사람은 모달에서 본 N개(보인 줄 — M79)를 확인했다 · 목록 뒤에 지운 것까지 비우면 확인하지 않은 것을 되돌릴 수 없게 지운다(M83).
- **not_attempted 칸**(G47 이 남겨 둔 것 — M66 · M71) — 항목마다 따로 부르므로 건너뛸 항목이 없다(M85).

## 근거
- 사용자 결정 G47 · G50(2026-10-31) · G12(2026-10-20 「휴지통 비우면 윈도우 휴지통으로 보내고 안되면 그냥 삭제되게」 — 되돌아간 규칙). M79 · M83 · M85 = 메인(재리뷰 r9 — 보고) · M86 = 메인(재리뷰 r10 — 보고).
- 사용자 이유(G47): 비우기 대상은 이미 지워 `.trash` 로 간 것이다 — 지우는 방식을 따로 챙길 까닭이 없다.
- ADR-0322 「근거」 의 이유(에이전트가 잘못 지워도 되살리게 남긴다 — F9)는 그대로다 — 비우기가 사람만인 것(ADR-0322 결정 1 — 그대로)으로 지켜진다.

## 영향 / 불변식
- Windows 가 휴지통 대신 지워도 받아들인 동작이다 — 결과의 「사라짐」 은 휴지통에 들었는지를 말하지 않는다.
- 파일럿(9b)이 줄어든다: 데몬 아래 OS 호출이 도는가(스레드 — M64 · M69) · 열린 파일이 남는가 · 어떤 UI 대화상자든 뜨면 실패(G47).
- 부르는 수단을 고르면(결정 5) ADR-0322 「영향」 의 비용 줄(`Win32_UI_Shell` · COM 구현 · STA 스레드)이 그에 맞춰 바뀐다.
- 우리 쪽 가름 · 가드 · 지우기 단계를 다시 들이면 G47 을 다시 연다. 비우기를 LLM 표면에 올리는 변경은 여전히 ADR-0322 를 다시 연다.
- 따라 고칠 자리(다른 작업자 몫 — 확인): TRD §1-6 OS 휴지통 행 · 「결과 가름」 표 · §6-2 9b · §6-5 8 · 9(U1 · U2) · §7 20 의 M70 문장 · §7 28 · PRD R18 문구.
