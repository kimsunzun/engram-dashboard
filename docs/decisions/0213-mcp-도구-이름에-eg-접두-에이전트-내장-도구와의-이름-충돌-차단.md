# ADR-0213: The eg_ prefix on MCP tool names — blocking name collisions with the agent's built-in tools

- 상태: 확정 (2026-09-20, basis: user decision + measured codex tool list + code measurement) · 부분 폐기 by ADR-0220 (the instruction document's ban on engram help mail)
- 관련: ADR-0094(send grant seam — the 「단일 출처」 invariant nailed the canonical source of the name to the control channel entrance) · ADR-0004(isolating backend knowledge) · ADR-0097(bypassPermissions auto mode — the reason the grant is a NO-OP today) · `crates/engram-dashboard-daemon/src/control/mcp_server.rs:330,335` · `crates/engram-dashboard-agent/src/backend/claude/mod.rs:259`(basis comment for denying the built-in `SendMessage`) · `docs/process/S18-messaging-v1/spec/messaging-v1-spec.md` §6 · `docs/research/command-discovery-survey-2026-09-20.md` · step-log S21 · Amends ADR-0126 (removing the priming escalation pin) · Amended by ADR-0220 (the instruction document's ban on engram help mail)

## 맥락

The tool names the daemon advertised over MCP were `send_message` and `messages`. The former is **a name the agent runtime already uses for its own built-in tool**.

- **codex measurement (2026-09-20)** — when we asked codex itself for its tool list, besides `exec_command` and `exec` it had ★`send_message` · `spawn_agent` · `list_agents`★ as built-ins. That is, if we attach our MCP to codex, **there are two `send_message` in the same list**.
- **It has already blown up once with claude** — the comment at `crates/engram-dashboard-agent/src/backend/claude/mod.rs:259` writes the reason for adding `--disallowedTools SendMessage` as 「내장 `SendMessage`(PascalCase) 와 우리 `send_message`(snake_case) 가 이름이 겹친다」 ("the built-in SendMessage (PascalCase) and our send_message (snake_case) overlap in name"). **The collision was not only a codex problem, and on the claude side it was blocked with a deny flag.**
- Our CLI side does not have this problem — everything sits behind the `engram` executable, so the executable name itself is the prefix. The problem is **only the one MCP surface that stands side by side in the tool list**.

Changing the name now is the cheapest. MCP tool names are looked up fresh by `tools/list` in every session, so there is no stored state, and since we have not yet attached it to codex, a collision has never actually occurred.

## 결정

1. **Attach the short prefix `eg_` to MCP tool names** — `send_message` → **`eg_send`** · `messages` → **`eg_messages`**.
2. **Do not prefix the CLI and catalog names** — the `engram` executable is already the prefix, and catalog names like `agent.spawn` are a contract shared by the frontend registry, the golden tests and the documents.
3. **Leave the constant identifiers (`SEND_MESSAGE_TOOL`·`MESSAGES_TOOL`) as they are** — they are names that point to a role (「발신 도구」, "send tool") so they are still accurate, and since the 21 references are not touched, the diff gets smaller. What changes is the **value**, and the `#[tool]` **method name**, since rmcp takes the wire name from the method identifier as it is.
4. **Keep claude's `--disallowedTools SendMessage`** — this decision removes the *stated reason* for that deny (the name overlap), but the observed failure was claude **misfiring its own built-in tool**, so there is no basis that it will not recur just because the name changed. Whether to remove it is a separate decision after measurement.

## 거부한 대안

- **A long `engram_` prefix (`engram_send_message`)** — the meaning is clearer but it is long. 「괜히 길면 좋을 거 없다」 ("there is nothing good about being needlessly long") (user decision 2026-09-20). The purpose of the prefix is **telling apart within the same list**, and two characters are enough for that. *Rejection basis = user decision.*
- **Prefix the CLI and catalog names too (`engram eg.agent.spawn`)** — ① the `engram` executable is already a prefix, so it says the same thing twice ② catalog names are a contract shared by the frontend registry (`src-tauri/src/layout/commands.rs`), the golden tests and the documents, so all of them would follow ③ a tool call and a shell command are different name spaces in the first place, so **a collision does not hold**. *Rejection basis = code measurement.*
- **Leave the name and separate them only with an instruction-document sentence** (「네 내장 도구 말고 engram 것을 써라」, "use engram's, not your built-in tool") — ★a branch that ADR-0094 already rejected with the same logic★: permission and tool selection happen at the runtime, and **a prompt is not enforcement** (ADR-0093 C0 to C3 measurement — even when priming told it how to send, the runtime gate won). At the spot where the model **chooses by looking at the name**, a sentence is only supplementary. In fact, the corroboration is that on claude it was blocked not with a sentence but with a **deny flag**. *Rejection basis = prior ADR measurement + the actual code.*
- **Change it when we attach MCP to codex** — by then it would be fixing something that is running, and an already-spawned agent holds a grant with the old name. Now there is no stored state, so the cost is 0. *Rejection basis = code measurement (the transition exposure in 「영향」 below).*

## 근거

- **codex tool list measurement (2026-09-20)** — the answer obtained by directly asking codex CLI 0.155.0 for its own tool names: shell execution is `exec_command` (「`Bash` 는 도구 이름이 아니다 — `exec_command` 를 부르고 그 안에서 셸로 bash 를 고른다」, "Bash is not a tool name — call exec_command and choose bash as the shell inside it"), and as built-ins `send_message`·`spawn_agent`·`list_agents`·`wait_agent` and so on.
- **The claude-side precedent** — the deny-reason comment at `backend/claude/mod.rs:259` already records the same kind of collision.
- **Wire measurement — but there is only one unconditional piece of evidence.** After the name change, `d_mcp_and_cli_entrances_return_identical_json_for_messages_and_group` read `tools/list`, called with the new name and passed (confirmed on the wire, not only the constant). ★**`mcp_send_message_tool_happy_and_error` also passed locally, but do not count it as evidence**★ — if claude is absent it exits via `skip_no_claude` before the assertion, and CI excludes that test by name. That is, it is **evidence that runs only on machines with claude installed**. (An overstatement the adversarial review caught — the first draft wrote both as if they were unconditional evidence.)
- **The ADR-0094 「단일 출처」 (single source) invariant was being kept** — when we started the rename we suspected the 3 `"send_message"` literals in `backend/claude/mod.rs` of violating the invariant, but ★all of them were test fixtures inside `#[cfg(test)]`★. The only production path is `format!("mcp__{server}__{tool}")`, so the backend does not type the name. That suspicion was rejected, and the fixtures were updated along with it so that they keep mirroring the real thing.

## 영향 / 불변식

- **The canonical source of the name is still the control channel entrance definition** (ADR-0094 decision 4 · the invariant). This ADR changes only the *value* at that spot — the backend knows only the format (`mcp__{server}__{tool}`) and does not retype the name.
- **No breakage of stored or external contracts** — `ToolGrant` and `ControlEndpoint` have no serde derive, so they are not serialized, and the grant is recomputed at every spawn. This name is nowhere in TS, JSON, generated bindings or wire goldens. The HTTP routes `/control/send`·`/control/messages` are **CLI entrances and so a separate contract** and did not change.
- ★**One transition exposure**★ — an agent that is already up holds a grant spawned as `mcp__engram__send_message` until respawn. Since the grant is a NO-OP today by ADR-0097, it is not a functional breakage but **document drift**, though it would become a real problem if the grant layer is ever enforced. A daemon restart + respawn resolves it.
- ★**The escalation teaching vanished from the instruction document, and the pin that guarded it vanished with it**★ — in the same session, when we rewrote `prompts/agent-priming.md` as a discovery device, we stripped out 4 lines of behavior rules (reporting a broken channel · the duty to reply, etc.) on the user's instruction. The test that guarded them (the channel-failure escalation assertion in `control::priming::tests`) we first re-aimed at what the new instruction document guarantees, but ★**two adversarial reviews independently pointed out 「그 대체 단언은 바로 옆 테스트의 완전 중복이라 커버리지가 0 이다」 (that substitute assertion is a complete duplicate of the test right next to it, so its coverage is 0), and that remark was right, so we deleted the duplicate test**★. **There is currently no test guarding this axis.** What ADR-0126 decisions 2 and 5 nailed down as 「우회 금지·주인에게 보고」 (no workarounds · report to the owner) has dropped out of priming with no gate hanging on it (which is why this ADR stamped a partial-discard on that one). **The hole that decision 5 left as 「비-MCP 갈래에 에스컬레이션 교육 0줄」 (0 lines of escalation teaching in the non-MCP branch) has now widened to every branch** — a place to back-fill at the stage of opening mail.
- ★**When the instruction document points at mail, it must not use `engram help mail` — that line always fails for its own reader**★. Because the injection condition and the exposure condition are mutually exclusive: the instruction document is injected only when `wants_priming = uses_mail && accepts_mcp_config` (`control/mod.rs:222`), while the condition under which help shows mail is `mail_allowed = uses_mail && !accepts_mcp_config` (`:184`). **So an agent that received the instruction document is, without exception, `MAIL_MARKER_OFF`, and `engram help mail` bounces with `unknown help topic`.** The first draft of this round wrote exactly that line and the adversarial review caught it — now it points to what that reader actually has (the MCP tools `eg_send`·`eg_messages`). ★**As a bonus, that wrong line passed an existing gate**★: `mentions_mail_cli_surface` (`control/priming.rs:200`) looks at the adjacency of `engram` and `mail`, and the `help` sitting in between broke that match, so **the CLI-surface ban gate passed while staying green**.
- **The instruction document promises a conditional surface unconditionally (unresolved)** — window · tab · slot · `ui.refresh` are 17 registered by the shell, so **in a headless daemon they vanish as a whole list**. The instruction document writes them without qualification. This is a place to close together with the help-screen maintenance.
- **Document drift remains** — about 40 files in `docs/` carry the old name. What we fixed this time is only `S18 spec §6`, which the source comments point to as 「이름의 출처」 (the origin of the name); records such as ADRs and step-log were not touched, per the append-only convention (this ADR carries the rename).
- **Verification (incomplete — together with the codex wiring)** — ① when MCP is attached to codex, is `eg_send` chosen distinguishably from the built-in `send_message` ② ★**whether the instruction document must be split per backend, or the execution tool name can be left out entirely**★ — run the three: 「Bash 로 실행해라」 (run it with Bash) as it is · without a tool name · a per-backend delta, under the same conditions, and decide by **whether each agent actually types `engram`**. If codex types it even without a tool name, the delta is unnecessary and the instruction document stays one file.
