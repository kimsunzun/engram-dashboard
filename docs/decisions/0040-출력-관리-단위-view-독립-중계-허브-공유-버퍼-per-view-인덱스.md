# ADR-0040: Output management unit = independent per View (relay hub shared buffer + per-view index)

- 상태: **폐기 (Superseded by ADR-0046)** — the justification for keeping the mirror ("memory duplication is only ~2MB, so the benefit is small") was empirically refuted: the real cost was not memory but the complexity of synchronizing mirror ↔ daemon ↔ screen, and three bugs (ca3f325 · 23a8c47 · loss with multiple slots sharing) occurred in a row at this point. The reservation clause "absorb per-environment branching later" was also not fulfilled, so we switched to removing the PC mirror (user decision 2026-07-05). However, the principle "progress is independent per view", the daemon's single lossless stream, and the meaning "from the beginning = the retention floor" are inherited by ADR-0046. ~~확정 (2026-06-30, basis: medium research cross-family convergence + the `/review prd full` FIX applied + user decision)~~
- 관련: ADR-0035 (layout authority = the src-tauri client) · ADR-0036 (unified transport relay) · ADR-0037 (transport semantics Rust-only) · ADR-0007 (epoch resubscribe) · ADR-0029 (daemon = single owner of data, separate process) · PRD `docs/process/S14-multi-page-layout/output-view-buffer-prd.md` · research `.claude/skills/research/study-notes/20260630-multiview-relay-2layer-medium.md` · step-log S14

## 맥락
In S14 module ① we built the output plane that fans a single daemon connection out to N windows (T5~T7, ADR-0036). But a defect where output is lost when the same agent is viewed in several Views was reproduced repeatedly. The root is the **"unit" of output management** — it is currently bundled as *one subscription per agent + per-window progress tracking + resubscribing from the most-lagging window, `min(render_seq)`*. A freshly opened window is dropped from the min computation (asymmetry between a missing key vs an explicit `None`), and a high seq based on the leading window goes to the daemon, so the new window permanently loses the output before it. This is not a specific bug but a limit of the "per-agent bundle" unit itself, so changing only the subscription authority axis (WebView vs src-tauri) does not close it. The industry standard is "store content once centrally + progress as an independent index per subscriber, separating the transport sequence from the consumption progress".

## 결정
**Switch the output management unit from per-agent bundle → independent per View.** The relay hub (src-tauri) **keeps one collected copy** of each agent's output (a shared buffer, mirroring the daemon's lossless range with a dual cap `min(~2MB, ~4096건)`), and each View (window) holds only *how far it has read* (an index) of that buffer, **independently**. It subscribes to the daemon **only once** per agent, and the daemon is responsible only for a single lossless stream (no viewer identifier leaks to the daemon). A new window fills from the client buffer with its own index without re-requesting from the daemon — the definition of "from the beginning" is the **retention floor (the oldest retained point)**, and anything older has been evicted by the daemon too, so it cannot be provided from anywhere (same as the existing behavior). The truncated past is left as is without a screen indication, and new output while scrolled into the past is handled independently per window by terminal practice (keep position if scrolled, follow if following). = a combination of the VS Code pty host (a single replay buffer at the relay) + Kafka/Redis (a shared log + per-consumer offset).

The role of `min(render_seq)` changes: **daemon resubscribe point (current, the cause of the defect) → client buffer retention floor (eviction)**.

## 거부한 대안
- **One subscription per agent + per-window min aggregation (current structure)** — a new window is dropped from the min computation and loses the earlier output. A structural defect of the unit itself, confirmed by independent convergence of two families, opus (FIX) + Codex (BLOCK).
- **The frontend (WebView) subscribes to the daemon directly** — violates ADR-0035 "frontend = pure renderer, layout authority = src-tauri". Each window has an isolated JS context, so a split-brain.
- **Re-request from the daemon for every new window** — the user's remark "the structure is strange". In a two-tier relay model it is an unnecessary network round trip, and the resubscribe min aggregation is itself the cause of the loss defect above.
- **Dynamic retention + daemon 2-tier fallback** (the client keeps only what the attached windows need, and pulls anything beyond from the daemon's ReplayBuffer) — the OSS precedents for client ↔ daemon synchronization and eviction are uninvestigated, so it is high-cost and uncertain. Mirroring the daemon's retention range is enough. However, this rejection is valid only on the premise that "from the beginning" was lowered to the retention-floor basis — a requirement to restore all the way to the truly evicted past is an explicit non-goal.
- **Local zero-copy / per-environment (mobile remote vs local PC) branching** — the daemon ↔ src-tauri is a separate process even locally (ADR-0029), so the receive structure across the boundary is common, and the memory duplication (~2MB×N) is also small, so the benefit is small. Without bending the current architecture, absorb it later at the transport seam (a separate ADR after measurement). Consistent with the step-log "daemonization = the same infrastructure for remote/mobile, one loopback hop locally".

## 근거
A medium research (three Claude Sonnet branches + one Codex BLIND cross-check → opus adversarial verification) surveyed multi-view output of a two-tier relay model cross-family: "store content once centrally + an independent per-view index, separating the transport sequence from the consumption progress" is universal (based on direct citations of official sources such as VS Code/Kafka/Redis/Matrix, high confidence). For a direct two-tier precedent, the VS Code pty host is the closest (the relay solely owns the replay buffer, each renderer has an independent cursor). The user's design (one shared buffer + a per-view index) is consistent with this standard. In `/review prd full`, both Codex (User lens, blind) and opus (Tester lens, blind) judged FIX — they admitted the direction is right but independently converged on the "from the beginning, all of it ↔ buffer cap contradiction", and the PRD closed it by correcting to "from the beginning = the retention floor".

## 영향 / 불변식
- **Daemon = only a single lossless stream per agent.** No View · viewer · layout types leak into the daemon crate/protocol (keeping the ADR-0035/0036 UI-agnostic stance). The derivation of the daemon Subscribe `after_seq` on reconnect (client buffer newest vs oldest) is the lossless crux — to be settled first in the TRD.
- **Relay hub (src-tauri) = owns one shared buffer per agent + per-view indexes.** The retention amount is not proportional to the number of windows (dual cap). The hot-path fan-out must not send while holding the ViewManager lock (ADR-0006 preserved).
- **Epoch transition = buffer reset + reset of all window indexes** (ADR-0007). The race where an epoch reset overlaps a new window mount is blocked in the TRD by an ordering guarantee.
- **Existing concurrency invariants preserved** — ADR-0001 (kill's 2 verbs) · 0005 (finalize once) · 0006 (lock order) · 0007 (epoch). The daemon-owned parts are independent of the client.
- **★Risk (retrofit cost):** since the single shared buffer is raw bytes, when two windows of different sizes view the same agent, one window's resize can break the buffer's escape sequences in the other window (the PTY has a single cols/rows). The resize policy is a separate open item, but we pin as a risk that the "single shared buffer" assumption can break under multi-resize — if per-viewport branching becomes necessary, this decision must be retrofitted (a point both reviewers raised in common).
- **The current `output_window_seq.rs` (the per-agent min model) is a target for rework/discard** — scope settled in the TRD. Code anchors: attach `// ADR-0040` to the newly implemented parts.
