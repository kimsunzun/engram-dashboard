# ADR-0023: Tray/process topology — a pure-Rust tray-host + a detached daemon + the UI (window hide), 3 processes

- 상태: **폐기 (Superseded by ADR-0026)** — on 2026-06-19 in dashboard9 it was reversed to 2 processes (the tray merged into the Tauri app). The reason for separating (WebView memory) collapsed once we accepted a development workstation + hide; a separate tray is outside the §5 LLM control surface and has no precedent (all three `/consult` runs recommended merging, job `20260619-215927-consult-tray-app-merge`). **But this ADR's "separation of two planes", "daemon detached/breakaway", and "X = hide" are carried over unchanged by ADR-0026.** ~~확정 (2026-06-18, dashboard6 session — user decision + `/consult` job `20260618-151957-consult-tray-daemon-topology`)~~
- 관련: CLAUDE.md §5 (LLM control) · ADR-0020 (single protocol + carrier) · ADR-0021 (daemon on-demand lifetime) · ADR-0024 (daemon ownership and exit model) · commit `664d629` (closing main exits the app — this ADR adjusts it) · `docs/process/S13-tray-lifecycle/tray-topology-trd.md`
- Scope: in daemon mode, how to split the tray, UI, and daemon into processes, and how to decide the window-close and tray-menu behavior.

## 맥락
The requirement: "even if the UI is closed, the agents (work) stay alive, reopening reconnects, and the tray stays up at all times and handles exit." For this we had to decide (a) which process owns the tray, (b) what closing a window means, (c) the always-on process composition. The daemon separation infrastructure (WS · ConnectionCore · wsTransport · daemon crate) already exists from ADR-0020/0021.

## 결정
**Three always-on processes. But the tray-host is a pure Rust tray utility with no WebView.**
- **tray-host** (new, tao + tray-icon, no WebView): a launcher that stays resident from startup + the lifecycle owner. It launches / hides / removes the daemon and UI, observes state, and is the coordinator for full exit.
- **daemon** (the existing crate): holds the agent core, headless, detached (ADR-0024).
- **UI app** (the existing Tauri): the React window, pure I/O. **The X button = minimize (hide, the process stays)**. Single instance.
- Tray menu v1: ~~`[데몬 시작] [UI 열기(focus or spawn)] [UI 종료(UI만)] [전체 종료]`~~ **→ fixed at 6 items (2026-06-18 dashboard7 user decision):** `[데몬 켜기] [데몬 끄기] [UI 열기] [UI 닫기] ──(구분선)── [트레이 종료] [완전 종료]`. The menu reflects the model that the daemon is the main (persistent) part and the tray/UI are clients — **트레이 종료** = turns off only the tray process (the daemon and UI keep running detached, and are rediscovered by the lockfile at the next tray start, ADR-0024 C2), **완전 종료** = daemon + UI graceful (C4), then the tray. The labels are also unified as on/off and open/close. The tray is `add(command)` style — adding items comes later.
- **Adjusting commit `664d629` (main CloseRequested → `app.exit(0)`):** X changes to `hide() + prevent_close()`, and the real exit is only from the tray "전체 종료". (The hidden-window zombie problem that 664d629 was blocking is resolved by "only tray exit calls exit" instead of "X = exit".)

## 거부한 대안
- **App = tray shell, 2 processes (the UI owns the tray, the window hides):** the three cross-checks said "2 processes are generally simpler," and that is right. **But we did not adopt it** — the user's intent is not "crash survival" but **a launcher resident from login + only the tray always up without the WebView cost**. 2 processes would have to launch the full WebView (heavy) at every login. GPT and Gemini both state "if the tray-host is **pure Rust (no WebView)** it is justified; if it launches the Tauri app again, go with 2 processes" — we are pure Rust, so the justification condition is met.
- **Separate the Tauri app (WebView) as the tray-host:** exactly the option the cross-check opposed. Two WebViews, memory, deployment complexity. Not adopted (that is why the tray-host is pure Rust).
- **Attach the tray to the daemon (the daemon holds a GUI loop):** reverses the ADR-0021 windowless decision + winit main thread vs tokio conflict. Changes the nature of the daemon. Rejected.

## 근거
- `/consult` three runs (GPT·Gemini·Claude) + a blind judge: agrees with (a) "a separate tray-host is excessive → but justified if pure Rust". The three also agree that the cost of changing the entry point (autostart, deep link, single instance, updater) is large → stated as migration in §Impact.
- Standard pattern confirmed (Discord·Steam): X = minimize to tray, tray Quit = real exit. amd/gaia have the same structure (a light tray control panel + a background engine + graceful shutdown).

## 영향 / 불변식
- The tray-host **does not use a WebView** (pure Rust). If it does, it violates the cross-check conclusion that merging into 2 processes is right.
- The UI X button is **hide, not exit**. The real exit is only the tray "전체 종료" (the ADR-0024 order).
- **The entry point changes from the app to the tray-host** → the autostart registration · the single-instance guard (✅ implemented 2026-06-19 — see §Tray single instance below) · the deep link (`engram://`) · the updater · the code-signing surface are all affected. At implementation they are handled as migration items (TRD §7).
- Daemon ownership, life and death, exit, and data location are in ADR-0024.

## Tray single instance (2026-06-19 dashboard8 — implemented)
If the tray is run several times, several processes come up and icons pile up in the system tray (measured: 3 runs = 3 processes = 3 icons). It is guarded by the named mutex `Global\EngramTrayHost-<user>` — the second run detects the existing instance and yields with an immediate `exit(0)` (QA measured: the 2nd and 3rd exit 0, final count 1). The same pattern as the daemon's `instance.rs`, but **only the name is tray-specific** (separate from the daemon's `Global\EngramDashboardDaemon-<user>` → the daemon and tray can start at the same time). The env override (`ENGRAM_TRAY_INSTANCE_KEY`) is also separate from the daemon's (`ENGRAM_INSTANCE_KEY`) (test isolation). The code is `crates/engram-tray-host/src/instance.rs` (the tray holds its own — no extraction into a shared crate; the daemon's instance.rs is a pattern reference).

**★A different exit policy from the daemon (load-bearing — do not copy)★:** when guard creation fails (`CreateMutexW` returns a NULL handle on a system error, rare) — **the daemon does not start (exit 1)**, but **the tray logs a warning and proceeds (starts without the guard)**. The tray's singleness is a **UX** problem (duplicate icons), not data integrity, so no icon (losing the whole daemon/UI control entry point) > the duplicate risk. The daemon policy (singleness = a single writer of daemon.json/agents.json = integrity, ADR-0008) must not be copied to the tray as is.

Rejected alternative: **Do not start on Err (copying the daemon policy)** — for the tray, the cost of losing singleness (duplicate icons) is lighter than the cost of losing availability (no icon), so availability first is right (found by reviewer-deep, consistent with the user policy).
