# ADR-0141: Empty slot affordance = a lone centered icon (slot id text removed, click = the same menu as right-click)

- 상태: 확정 (2026-08-17, grounds: user decision) · 부분 폐기 by ADR-0143 (click target and icon interactivity) · 부분 폐기 by ADR-0144 (empty slot left-click menu opening)
- 관련: ADR-0065(empty slot menu composition) · ADR-0064(single contribution API of the slot menu) · ADR-0063(slot content arrangement control surface) · `src/components/layout/ViewLayoutRenderer.tsx` · Amended by ADR-0143 (click target and icon interactivity) · Amended by ADR-0144 (empty slot left-click menu opening)

## 맥락

An empty slot showed two lines of text in the center of the screen — `Slot 93d98776` (the first 8 characters of the slot UUID) and `— empty —`. User report (2026-08-17): you cannot tell what that text is by reading it ("Slot 넘버링?" — gloss: slot numbering?), and the path to fill an empty slot is not visible on screen. The only real fill path was right-click → `새 콘텐츠 ▶`, and left-click only moved focus — that is, even looking at an empty slot, the screen did not tell you the next action.

The first 8 characters of a slot id have no use for a person. The consumers that actually use that value (LLMs · automated callers) receive the full id from the layout snapshot, so they do not depend on the on-screen text.

## 결정

1. **Empty slot = a lone centered `+` icon.** Delete the two lines of text and delete the i18n key `common.viewEmpty` with them.
2. **A frameless icon.** Only the icon appears, not a button box with border and background.
3. **Click = the same menu as right-click, at the same coordinates.** Use the existing `setContextMenu({x, y})` state and the existing `SlotContextMenu` mount as they are — create neither a second menu nor a second assembly path.
4. **The right-click path is kept as it is** (`+` is an additional entry point, not a replacement).
5. **The icon click bubbles up to the container's focus-move handler** — a single click causes slot focus and menu opening together.
6. **The icon is excluded from the Tab focus order** (user decision 2026-08-17). This menu cannot be operated by keyboard, so if it were put in the order, Tab→Enter would open it and you would reach a dead end where you can neither close nor run it without a mouse.

## 거부한 대안

- **A real button with border and background** — the user stated explicitly that it is "진짜 버튼이 아니고 이미지가 가운데 뜨는 것" (gloss: not a real button, but an image that shows up in the center) (2026-08-17).
- **A `+`-only slimmed menu (content filling only) or inserting default content immediately on click** — the user allowed the same menu with "우클릭 메뉴같이 동일하게 메뉴 나와도 된다" (gloss: it is fine for the same menu as the right-click menu to come up) (2026-08-17). Moreover, a slimmed menu sets up a second menu assembly path outside the single contribution API of ADR-0064 — once the item composition splits into two places, every time an item is added to the menu one side gets missed.
- **Keep the slot id text + show the icon alongside** — removing that text was the starting point of the request (2026-08-17). People do nothing with that value, and consumers that need the value receive the full id from the layout snapshot.
- **Put the icon in the Tab order and add keyboard operation to the menu (Esc to close · arrow keys to move · Enter to run)** — the best option for keyboard accessibility and it also fills the existing defect of the right-click path. But the user chose exclusion from the order (2026-08-17). The menu component is outside the scope of this decision, and the absence of keyboard operation is not a problem this affordance created but a defect the right-click path had originally — fixing it by squeezing it in here would blur the ownership of the defect.
- **Put the icon in the Tab order and add only Esc to close** — the minimal option that only patches the dead end. Rejected by the same user decision. A menu that can only be opened but not run has weak reason to be in the order.

## 근거

- **User decision (2026-08-17)** — the user specified all three: the icon form, the same menu on click, and the text removal.
- **Code grounds for not growing the control surface** — `+` creates no new command and connects only to the registry's existing commands (`slot.fill.*`·`slot.split.*`·`slot.close`). It satisfies what CLAUDE.md 「LLM-우선 제어」 requires, "a new UI feature gets an LLM call path built with it, layered onto the existing surface," with zero new global handles.

## 영향 / 불변식

- **There is one menu opening path** — `setContextMenu`. `+` and right-click shake the same state. Adding a third path splits menu position and close handling.
- **The visual information of an empty slot is the `+` alone** — the slot id has disappeared from the screen. Debugging and GUI measurement that used to find slots by text use the layout snapshot or the accessible name.
- **The icon's accessible name has its own key** — the submenu container label of ADR-0065 (`slot.newContent`) is not reused. If it were reused, an edit that fixes that submenu label would silently change this button's name too, and a test that finds the element by that name would grab the wrong thing.
- **The icon is outside the Tab order — this absence is intended.** To bring it back, keyboard operation (at least Esc to close) must be put into the menu first. If the order is reversed, the door into a menu that cannot be left without a mouse gets wider.
- **But that door is not closed — the order exclusion blocks only the common path.** Even when it is out of the tab order, the element remains in the accessibility tree, so a screen reader user can still reach this button and activate it, and then meets a menu that can be neither closed nor run. To remove this remaining path too, the release condition above (at least Esc to close in the menu) must be met first, and at that time the order exclusion is withdrawn together — the two are one bundle.
- **If a menu overflows its anchor, it is flipped, not pushed.** If the anchor (the opening point) falls inside the menu rectangle, an item lands under the cursor, and since `+` is a left-click opener, a following double-click runs that item — if it hits close, the slot disappears. Only in the degenerate case where flipping still does not fit (the menu is larger than the viewport) does it fall back to pushing. This rule applies to the right-click path too — the position rule is not split per opener.
- **A click without coordinates also opens the menu at the icon's position** — even after removing it from the tab order, clicks called by code or assistive technology remain, and such a click arrives with coordinates `0,0`. If the coordinates were trusted as they are, the menu would open at the top-left of the viewport, so it checks whether the click has no coordinates and substitutes the icon position. **The decision is made not by whether the coordinates are 0 but by whether the click count is 0** — judging by coordinates cannot be told apart from actually pressing the top-left of the viewport.
