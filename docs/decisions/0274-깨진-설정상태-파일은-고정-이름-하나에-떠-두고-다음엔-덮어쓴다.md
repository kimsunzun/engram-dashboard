# ADR-0274: 깨진 설정·상태 파일은 고정 이름 하나에 떠 두고 다음엔 덮어쓴다

- 상태: 확정 (2026-10-03, 근거: 사용자 결정 F21 2026-10-02 (TRD `docs/process/S21-storage/trd.md` §10 F21) + 선례 원본 소스 확인 2026-10-02 + P3a 구현 `41348d9` 코드 리뷰(deep · 교차 family)·QA full)
- 관련: Amends ADR-0265 (결정 4 의 떠 두기 규칙) · ADR-0166 결정 9(「`.corrupt` 없음」 원안 — ADR-0265 가 이미 뒤집었다) · ADR-0167(원자 쓰기) · TRD `docs/process/S21-storage/trd.md` §5-3 · §6-2 · `src-tauri/src/fsutil.rs`(`copy_aside` · `copy_atomic`) · step-log S21

## 맥락

설정(`shell\config\settings.json`)과 화면 상태(`shell\state\state.json`)는 통째로 못 쓸 파일(JSON 아님 · 상한 초과 · UTF-8 아님 · 모르는 `version` 등)이면 기본값으로 시작하고, 그 위의 첫 쓰기가 원본을 옆에 떠 둔 뒤 그 자리를 갈아끼운다(ADR-0265 결정 4 · TRD §6-2).

ADR-0265 는 떠 두기를 이렇게 정했다 — 이름 `settings.json.corrupt-<ms>`(겹치면 `-<n>`) · 앞선 사본을 덮지 않음 · 1 MiB 를 넘는 원본은 떠 두지 않고 error 뒤 갈아끼움 · 이 프로세스가 직전에 떠 둔 사본과 바이트가 같으면 다시 뜨지 않음. 상태 쪽은 같은 함수에 상한 16 MiB 를 두기로 했다. 한도와 중복 생략은 **세션 기본값**이었고(§10 F21 「사용자 확인 대기」) 출처가 없었다.

P3a 가 떠 두기 함수를 셸 공용 `fsutil` 로 옮기는 자리에서 사용자에게 그 기본값을 물었고, 사용자는 「관행 따르면 될듯」으로 답했다.

## 결정

1. 통째로 못 쓸 파일은 첫 쓰기 전에 원본을 **고정 이름 하나 `<파일 이름>.corrupt`** 로 복사해 둔다(`settings.json.corrupt` · `state.json.corrupt`). 다음에 다시 깨지면 **그 사본을 덮어쓴다.**
2. **크기 한도 · 중복 생략 · 시각/번호 이름은 없다.**
3. 그대로인 것: 복사가 실패하면 그 쓰기는 실패하고 원본은 그대로다(설정) · 복사한 뒤 원자적으로 갈아끼우므로 파일이 없는 순간이 없다 · 읽기 자체의 IO 실패는 「못 쓸 파일」이 아니다(떠 두지도 덮지도 않는다).
4. 복사는 같은 폴더의 임시 파일로 흘려 담고(`sync_all`) rename 으로 갈아끼운다 — 반쯤 쓴 사본이 앞선 사본을 덮지 않는다(`fsutil::copy_atomic`).

## 거부한 대안

- **사본을 쌓기(시각 이름 `.corrupt-<ms>` · `-<n>`)** — 사용자: 「구지 쌓아야됨?」. 근거 = 선례 코드: Chromium · Firefox 둘 다 고정 이름 하나를 덮어쓴다(아래 근거).
- **1 MiB 를 넘는 원본은 떠 두지 않기** — 출처 없던 세션 기본값이었다. 근거 = 선례 코드: 두 구현 모두 크기 한도가 없다. 쌓이지 않으므로 「큰 사본이 데이터 폴더에 쌓인다」는 한도의 이유도 사라진다.
- **같은 바이트면 다시 뜨지 않기** — 사용자: 「똑같은 내용도 그냥 백업해도 상관없다」. 근거 = 선례 코드: 두 구현 모두 중복 확인이 없다. 고정 이름이라 같은 내용을 다시 떠도 사본이 늘지 않는다.
- **떠 두지 않고 그냥 덮기**(ADR-0166 결정 9 원안 · VS Code 는 깨진 설정에 쓰기를 거부한다) — 세션이 「그냥 덮으면 되는 것 아니냐」는 사용자 물음을 이 뜻으로 잘못 읽고 제안했으나, 사용자의 뜻은 「추가 처리 없이 매번 떠 둔다」였고 관행을 택했다.

## 근거

- Chromium `components/prefs/json_pref_store.cc` — JSON 파싱 오류면 파일을 `path.ReplaceExtension("bad")`(`Preferences.bad`)로 옮긴다. Windows 의 `base::Move` 는 `MOVEFILE_REPLACE_EXISTING` 이라 앞선 `.bad` 를 덮는다. 한도 · 중복 확인 없음(원본 소스 확인 2026-10-02).
- Firefox `modules/libpref/Preferences.cpp` — 파싱이 실패하면 `"Invalid" + 잎 이름`(`Invalidprefs.js`)으로 복사하고, 있으면 지운 뒤 복사한다. 한도 · 중복 확인 없음(같은 날 확인).
- VS Code `configurationEditing.ts` — 파싱 오류가 있는 설정에는 쓰기를 거부한다(떠 두지 않는다).
- 구현 실측(P3a QA full, 2026-10-03): 깨진 `settings.json` 을 두 번 다른 바이트로 넣고 설정을 바꿨을 때 `settings.json.corrupt` 하나가 매번 새 바이트로 덮였고(바이트 비교 일치) 새 `settings.json` 은 유효했다.

## 영향 / 불변식

- **대가 1** — 한 번 더 깨지면 앞선 사본을 잃는다(선례와 같다).
- **대가 2** — 사본 자리가 영구히 못 쓰는 상태면(읽기 전용 · 같은 이름의 폴더 · ACL) 복사가 실패해 그 파일의 쓰기가 계속 실패한다. 극단 경우로 받아들였다(사용자 원칙 「그런 것까지 가정하면 끝도 없음」 — 코드 리뷰 2026-10-03 지적분).
- 떠 두기는 `fsutil::copy_aside` 한 곳이다 — 설정 · 상태가 같은 함수를 부른다. 이름 규칙을 바꾸려면 그 함수 하나를 고친다.
- 크래시 사본 `state.crash.json`(TRD §6-7)은 이 결정과 별개다 — 그것은 「복원할까요?」의 대상이고 답이 거둔다.
