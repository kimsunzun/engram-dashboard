# ADR-0274: A broken settings or state file is set aside under one fixed name and overwritten next time

- 상태: 확정 (2026-10-03, basis: user decision F21 2026-10-02 (TRD `docs/process/S21-storage/trd.md` §10 F21) + precedent source check 2026-10-02 + P3a implementation `41348d9` code review (deep · cross-family) · QA full) · 부분 폐기 by ADR-0291 (widening the scope to four files, removing the new edition from files that cannot be written whole, and the set-aside location)
- 관련: Amends ADR-0265 (the set-aside rule of decision 4) · ADR-0166 decision 9 (the original 「`.corrupt` 없음」 plan — ADR-0265 already reversed it) · ADR-0167 (atomic write) · TRD `docs/process/S21-storage/trd.md` §5-3 · §6-2 · `src-tauri/src/fsutil.rs` (`copy_aside` · `copy_atomic`) · step-log S21 · Amended by ADR-0291 (widening the scope to four files, removing the new edition from files that cannot be written whole, and the set-aside location)

## 맥락

If the settings (`shell\config\settings.json`) or the screen state (`shell\state\state.json`) is a file that cannot be used as a whole (not JSON · over the limit · not UTF-8 · unknown `version` etc.), the shell starts from defaults, and the first write on top of it sets the original aside next to it and then swaps that spot (ADR-0265 decision 4 · TRD §6-2).

ADR-0265 set the set-aside like this — name `settings.json.corrupt-<ms>` (`-<n>` on collision) · do not overwrite earlier copies · an original over 1 MiB is not set aside, it is swapped after an error · if the bytes are the same as the copy this process set aside just before, do not set it aside again. For state, it was TRD §6-2, not ADR-0265, that [picked](internal implementation choice) a 16 MiB ceiling in the same function. The limit and the duplicate skipping were **session defaults** (TRD §10 F21 「사용자 확인 대기」) and had no source.

When P3a moved the set-aside function into the shell-shared `fsutil`, it asked the user about those defaults, and the user answered 「관행 따르면 될듯」.

## 결정

1. A file that cannot be used as a whole is copied, before the first write, to **one fixed name `<파일 이름>.corrupt`** (`settings.json.corrupt` · `state.json.corrupt`). If it breaks again next time, **that copy is overwritten.**
2. **There is no size limit · duplicate skipping · timestamp/number name.**
3. What stays: if the copy fails, that write fails and the original is left as it is (settings) · the swap is atomic after the copy, so there is never a moment when the file is missing · an IO failure of the read itself is not a 「못 쓸 파일」 (it is neither set aside nor overwritten).
4. **(Implementation choice — P3a · not a user decision)** The copy is streamed into a temporary file in the same folder (`sync_all`) and swapped in by rename — a half-written copy does not overwrite the earlier copy (`fsutil::copy_atomic`).
5. Together with ADR-0265 decision 4, this decision also replaces, in the 「못 읽는 파일은 원본을 남긴 뒤에만 덮는다」 item of that ADR's 「영향 / 불변식」 section, **the copy name (`.corrupt-<ms>`) and the 1 MiB exception** — that section restated the same rule. 「원본을 남긴 뒤에만 덮는다」 itself stays as it is.

## 거부한 대안

- **Accumulating copies (timestamp name `.corrupt-<ms>` · `-<n>`)** — the user: 「구지 쌓아야됨?」. Basis = precedent code: Chromium and Firefox both overwrite one fixed name (see Basis below).
- **Not setting aside an original over 1 MiB** — it was a session default with no source. Basis = precedent code: neither implementation has a size limit. Since copies do not accumulate, the limit's reason, 「큰 사본이 데이터 폴더에 쌓인다」, is gone too.
- **Not setting aside again if the bytes are the same** — the user: 「똑같은 내용도 그냥 백업해도 상관없다」. Basis = precedent code: neither implementation has a duplicate check. Because the name is fixed, setting aside the same content again does not grow the number of copies.
- **Not setting aside, just overwriting** (the original plan of ADR-0166 decision 9) — the user asked 「그냥 덮으면 되는거아냐?」, and the session misread this as meaning to overwrite without setting aside, and proposed that. What the user meant was to set aside every time without adding any special handling, and the convention was chosen.

## 근거

- Chromium `components/prefs/json_pref_store.cc` — on a JSON parse error it moves the file to `path.ReplaceExtension("bad")` (`Preferences.bad`). On Windows `base::Move` is `MOVEFILE_REPLACE_EXISTING`, so it overwrites an earlier `.bad`. No limit · no duplicate check (original source check 2026-10-02).
- Firefox `modules/libpref/Preferences.cpp` — when parsing fails it copies to `"Invalid" + 잎 이름` (`Invalidprefs.js`), deleting it first if it exists and then copying. No limit · no duplicate check (checked the same day).
- VS Code `configurationEditing.ts` — it refuses to write to settings that have a parse error (it does not set aside).
- Implementation measurement (P3a QA full, 2026-10-03): when a broken `settings.json` was put in twice with different bytes and the settings were changed, the single `settings.json.corrupt` was overwritten with the new bytes each time (byte comparison matched) and the new `settings.json` was valid.

## 영향 / 불변식

- **Cost 1** — if it breaks one more time, the earlier copy is lost (same as the precedents).
- **Cost 2** — if the copy location is permanently unwritable (read-only · a folder with the same name · ACL), the copy always fails. The cost differs by side:
  - **Settings** — if the set-aside fails, that write fails too (`INTERNAL` · original left as it is), so settings writes on top of a broken `settings.json` keep failing.
  - **State** — a set-aside failure is logged and boot continues (TRD §6-2 · §6-5 ④ · user decision D8), so the first write overwrites the broken original **without a copy**.
  - Both were accepted as extreme cases (user principle 「그런 것까지 가정하면 끝도 없음」 — raised in the code review 2026-10-03).
- The set-aside is in one place, `fsutil::copy_aside` — settings and state call the same function. To change the name rule, fix that one function.
- The crash copy `state.crash.json` (TRD §6-7) is separate from this decision — it is the subject of 「복원할까요?」 and the answer clears it.
