# ADR-0296: Slot docking tab drag, phase 1 = OS (HTML5) drag · move only once at drop · no shell sync during the drag

- 상태: 확정 (2026-10-20, 근거: user decision (showing the VS Code tab drag screen — 「그냥 이런식으로 1차적으로 할까 덜어내고? 드래그 목표지점이 정해졌을때 이동되는걸로. 동기화 하려니깐 빡센거 아냐」 · 「ㅇㅇ 그렇게하자」) + survey `docs/research/slot-docking-drag-ownership-peers-2026-10-19.md` (peers · techniques · the Windows look of OS drag, section E)) · 부분 폐기 by ADR-0297 (the scope of the invariant "zero shell calls during the drag") · 부분 폐기 by ADR-0299 (removing the spare window in decision 5)

## 맥락

By ADR-0295 decision 1, we implemented the desktop-Chrome-style drag (mouse capture · release makes a real new window · Windows window-move loop · attach to another window before the drop) up to TRD 6.3 U8. In measurement, defects repeated at the boundary between the shell (Rust) and the webview (React), which differs per window — on reattach, the model write was drawn before the web notification, so slot 0 showed for one frame (cause confirmed) · all tabs vanished (B1 · the web saw a tab bar of width 0 — cause unconfirmed) · attached and detached again after 11 ms (cause unconfirmed). The common root is that two processes split the judgment of one drag and sync state and geometry by IPC during the drag.

In the survey (`slot-docking-drag-ownership-peers-2026-10-19.md`) — both the peers where the renderer and the model owner are split (the old Chromium WebUI tab bar · Vivaldi) and the single-process peers (Firefox · Windows Terminal · VS Code) do not write the model during the drag and move only once at the drop · they leave moves between windows to OS drag and drop · the only place that does the Chrome style with the same split structure as ours is Chromium Webium, and it is an experimental feature that is off by default. The Chrome-style drag engine alone is about 10 thousand lines of hand-written code including tests (file line counts — platform move loop 2,129 · shell session + tests 3,717 · executor · spare window 1,265 · window-under-cursor decision 817 · drag commands 1,726 · web drag hook + tests 1,907 · geometry reporting 270), and the move loop · hook must be rewritten for each OS and it does not work on Wayland (Chrome also falls back to OS drag there — `ShouldDragWindowUsingSystemDnD`).

## 결정

1. **Tab drag phase 1 = WebView2 HTML5 (OS) drag and drop, VS Code style.** The drag image = the tab name label.
2. **The model changes only once, when the target is decided (at the drop).** The webview of the window that received the drop sends one command (tab · target window · position, or split position) to the shell, and the shell applies it once through the same application path as LLM commands (`layout::apply`). **There is no shell ↔ web sync during the drag** — drag state and tab-bar geometry are not sent to the shell.
3. **The preview (insertion position · docking strip) is drawn inside the window by the webview of the window that receives the drop, with its own dragover.**
4. **If dropped on no window, a new window at that position** — right after the drag ends, the shell reads the cursor position.
   - Even if another app accepts it, a new window · on the title bar or the border of our window = nothing happens (user decision 2026-10-20 — PRD Q38 · Q39 · TRD §3-5).
5. **Remove the Chrome-style drag engine** — the window move loop · hook · shell drag session · spare window · window-under-cursor decision · geometry reporting. What is removed and what is kept is canonical in the TRD — edition 7 does not remove platform `window::top_level_at` from the window-under-cursor decision and keeps it for the drop-end decision after dragend (TRD §3-5 · §5-1).
6. Decision 3 of ADR-0295 (the 10% docking strip at the cell edge) and decision 4 (attached size = original size · capped at half the cell) remain valid. What this decision replaces is only the **drag method of decision 1** (mouse capture · move loop · detach/attach · attach before drop · Esc revert and so on) and **decision 2** (stop if the Chrome method does not work). The active tab shape of decision 1 (top corner 10 · bottom curve 12 · separator rule) remains valid — it is the basis of the partial discard of ADR-0168 decision 5. The rest of decision 1 outside the drag (empty tab bar = window drag area · fixed width on consecutive closes) is canonical in PRD 4.9.

## 거부한 대안

- **Keep the Chrome style (ADR-0295 decision 1)** — defects repeated in the shell ↔ webview sync during the drag (the context above — one with the cause confirmed). The user: 「동기화 하려니깐 빡센거 아냐」. The hand-written engine is about 10 thousand lines (file line counts measured) and must be rewritten for each OS.
- **Keep the Chrome style + redesign only the boundary (Webium style — inside the tab bar is web · per window is shell · layout revision number snapshot · attach/detach slack strip)** — the sync during the drag only shrinks, it remains. The only precedent with the same structure, Webium, is an experimental feature that is off by default (`chrome_features.cc` #1960 `FEATURE_DISABLED_BY_DEFAULT`), has several crash fixes between 2026-05 and 2026-08, and its geometry reporting has no revision number, so the same hole as our B1 is open (survey · source comparison). The user chose OS drag for phase 1.
- **Hold the drag source in Rust native OLE to reach the Firefox level (arrow cursor · telling Esc from a drop outside the window · no bounce-back animation)** — not done in phase 1: it is the road of building it ourselves again (the user: 「덜어내고」). The drag source of WebView2 is inside the WebView2 browser process, so the shell cannot hook it (`drag_source_win.cc` #29-31), and the native drag plugin we looked at earlier (crabnebula) had a defect that blocks the main thread (`slot-docking-drag-mechanism-2026-10-16.md` §1). If needed after phase 1, we reopen it.

## 근거

- Checked against peer sources (main grounding) — the old Chromium WebUI tab bar `drag_manager.ts` #225-238 (one `moveTab` in `finish()`) · Firefox `drag-and-drop.js` (the model move only inside `handle_drop`) · Windows Terminal `TerminalPage.cpp` #6050-6062 · Chromium Webium `tab_drag_session.cc` #354-357 · `tab_strip.ts` #247.
- HTML5 drag spike measurement (2026-10-16 · WebView2) — the shell main thread was not blocked · target window dragover 60/s · coordinates exact · dragend fired in every case · it continued even when the source window was hidden.
- The Windows look of OS drag (survey section E) — the dotted box next to the cursor = the OLE default 「이동」 cursor · Chromium always uses the default cursor (`drag_source_win.cc` #29-31) · only Firefox uses a private hook for the arrow (`nsNativeDragSource.cpp` #95-114) · user observation (2026-10-20): it does not appear in Visual Studio and appears in VS Code.

## 영향 / 불변식

- **Accepted cost (VS Code level):** the dotted box next to the cursor · the detached tab follows as an image, not a real window (the image disappears over other apps) · Esc and a drop outside the window are the same signal in HTML (`dragend` · `dropEffect "none"`) · the Windows bounce-back animation on a drop outside the window · no Windows snap during the drag.
- **Zero shell calls during the drag is the invariant** — the shell receives only one drop command (+ the cursor read for a drop outside the window). If the path that sends geometry or state to the shell during the drag is revived, the reason for this decision (the boundary sync defect) comes back.
- **LLM path:** the drop command goes through the same application path as T-65 (CLAUDE.md 「LLM-우선 제어」).
- **Platform:** HTML5 drag is a web standard, so almost no OS-specific drag code is left. The behavior of HTML5 drag between windows in macOS (WKWebView) and WebKitGTK is unchecked — we measure it at porting.
- PRD and TRD are revised by this decision (the Chrome-style requirements · phases · code to remove).
