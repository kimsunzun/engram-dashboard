# ADR-0154: The daemon picks the target of command delivery with its own table

- 상태: 확정 (2026-08-18, basis: measured (where the sending abstraction is owned) + precedent (`route`'s own error vocabulary is a single value) + user decision 2026-08-18 — three branches were put forward with their costs and one was chosen) · 부분 폐기 by ADR-0159 (open item on the certainty classification)
- 관련: Amends ADR-0081 (premise that target addressing is unneeded) · ADR-0155 (the decision that set up the owner-token registry — this is not a reversal, it fills in the targeting that registry needs) · ADR-0150 (owner token derivation) · ADR-0036 (the shell has one daemon connection) · ADR-0006 (lock order — the new table follows this discipline too: lock, take a copy, release, and only then send) · `docs/process/S20-command-bus/trd.md` §3-2 (envelope) · §4-④ (owner absent) · §4-⑥ (deadline default 10 seconds) · Amended by ADR-0159 (open item on the certainty classification)

## 맥락
ADR-0081 decision 1 wrote in explicitly **"single app instance premise = target addressing unneeded"**. On top of that premise it decided only the lifetime and eviction of the relay routing table and **did not solve the targeting problem**.

**Lineage note — that clause passed through 0155 alive.** ADR-0155 partially replaced 0081 decisions 1 and 2, but what it killed was only the *registration method* of decision 1 (`RegisterRole{UiApp}`) and the 3-variant opaque envelope of decision 2 (ADR-0155 enumerates the dead clauses and the live clauses explicitly). **"Addressing unneeded" is in neither the dead list nor the live list** — while swapping the registration method for the owner-token registry, 0155 left out of the enumeration the problem of *reading that registry to target the owner*. Measurement backs up that hole: the lookup of the 3-step delivery (`Roster::lookup`) **is never called once on the daemon's operating path** — the daemon does not call that 3-step (`route`) at all, and the only hop that actually runs it today is the shell. So the target of partial discard in this decision is not 0155 but 0081, and with respect to 0155 it is not a reversal but **a late filling-in of the targeting that registry needs**.

**What is discarded is not the premise but the conclusion drawn from it.** The single-app-instance premise itself is true and this decision does not touch it — **the shell opens only one connection to the daemon however many windows it has** (module header of `src-tauri/src/daemon_client/mod.rs`: 「창이 몇 개든 데몬엔 연결 1개」. ADR-0036 invariant). What dies is the one drawn from it, **"target addressing unneeded"**.

**The basis for the discard is not how many connections there are but that the design already requires targeting.** The 3-step delivery of ADR-0155 decision 3 carries that requirement on its face — 「없으면 `roster.owner_of(&env.name)` → 있으면 **그 주인 쪽 연결로 `link.send`**」 (`docs/process/S20-command-bus/trd.md:329`, §3-5 routing). And the reason 0155's rejected alternative G rejected 2-step routing was exactly **「보낼 곳이 하나뿐이라는 전제」** (the premise that there is only one place to send), and the TRD repeats the same sentence (`trd.md:332`). So **the targeting requirement is already inside the settled delivery rule, regardless of the size of the connection set** — 0081's "unneeded" collides head-on with that rule. This argument holds even with only one connection, so it does not lean on the measured terrain.

One fact backs it in real terms: the dev and release shells use **different single-instance lock names**, so coexistence is actually reachable (`docs/process/step-log.md:1794` accumulated item ㊅ — the release-build app and this worktree's debug build take different locks, so two shells exist at the same time as separate clients).

**The v1 scope is not changed by this decision.** Multiple app instances are still something v1 does not do, and the policy is last-wins alone (`docs/process/S20-command-bus/trd.md:61`). What this decision fills in is not 「여럿을 지원한다」 (we support several) but 「배달 규칙이 이미 요구하는 주인 연결을 어떻게 집어내나」 (how to pick out the owner connection the delivery rule already requires). If a *conclusion* that was used on that premise is left standing where the premise stays alive, the next session will read "targeting is unneeded" as a basis.

## 결정
When delivering a command envelope to a single owner shell, **the daemon owns a connection id → send channel table inside itself and sends by targeting with that table.** The boundary of the network layer (net crate) is not changed.

**Identity of the table — one lock, inside `Shared` of `CommandRoster`.** The table is not made a separate struct with a separate lock; it goes into `Shared` of the daemon's `CommandRoster` **under the same lock** as the registry, and **the key is `ConnId`**. (Whether `live` is widened into a table with values or one more slot is added, being inside that is enough — what this decision fixes is **the lock and the key**, not the field layout.) Basis: that place already put `live` in the same `Mutex` for the reason 「명부와 **한 잠금 아래** 있어야 확인과 변경 사이가 벌어지지 않는다」 (it must be **under one lock** with the registry so that no gap opens between check and change), and `detach` already uses the shape 「살아 있는 명단에서 빼고 그 주인의 이름을 명부에서 지운다 — **둘은 한 잠금 안에서** 일어난다(겹쳐 도는 등록이 그 사이로 못 들어온다)」 (it removes from the live list and erases that owner's names from the registry — **the two happen inside one lock** (a concurrently running registration cannot get in between)) (both in `command_roster.rs`). Putting it under the same lock makes TRD `:521-524`'s 「명부 제거 지점은 한 곳뿐」 and ADR-0150's 「`detach` 한 곳만」 hold as they are **without a workaround argument**. ★**It is not put in `Roster` of the tool crate `engram-dashboard-command`**★ — that crate does not know `ConnId` at all (zero references), and putting it in would break that crate's **zero-workspace-dependency ceiling gate**.

**The path from owner token to connection** — delivery hands `OwnerToken` to `link` (the `OwnerLookup::Available(owner)` branch of the tool crate's `route`) but the table's key is `ConnId`. The way to connect the two is pinned down: **the daemon records the `OwnerToken → ConnId` correspondence at `attach` time** (that place holds both) **and looks up by that record.** ★**Do not parse the `"conn-"` prefix of the token string**★ — that the token is derived from the connection id today is true (`CommandRoster::owner_of`), but the place that wrote that derivation itself pinned down **「이 파생은 오늘의 잠정 규칙이고 슬라이스 B가 대체한다」** (this derivation is today's provisional rule and slice B replaces it). If routing is tied to the string format, delivery breaks the moment that replacement comes, and the recorded correspondence survives even if the origin of the token changes. **This requires two new accessors** (`sink_of`, which finds the outlet by owner, and `attached_owner`, which asks from outside for the stored token) — the public surface of `CommandRoster` before this decision (`new`·`owner_of`·`attach`·`detach`·`register`·`update`·`entries`) had **neither**. What data structure holds the correspondence (an inverse index, or equality comparison with the stored token) is not fixed by this decision — what is fixed is two things: **record it when attaching** and **do not parse the prefix**. The concrete form of 「키가 바뀐다」 (the key changes) in re-discussion trigger ② is this correspondence record.

**Scope of the partial discard of ADR-0081** — what is discarded is one narrow conclusion of decision 1, **「대상 주소지정 불요」** (target addressing unneeded). Addressing is needed, and the daemon holds the means. Two things are stated explicitly:
- **The 「단일 앱 인스턴스 전제」 (single app instance premise) item in the impact section of 0081** (if multiple apps, the target is ambiguous · outside the PRD scope, follow-up · the policy for more than one role registration is undecided in the TRD) **is outside the discard scope of this decision.** Whether that item lives or dies is not decided here — this decision does not support several apps; it lays down the means of targeting that the already-settled delivery rule (0155 decision 3) requires.
- **The authoritative source for what dies and what lives of 0081 is the impact section of ADR-0155** (0155 declares so itself). The live clauses are not enumerated again here — **a partial enumeration makes the omitted clauses read as dead.**

## 거부한 대안
- **Add unicast to the network layer** — A per-connection-id sender map already exists in the net crate (`ConnRegistry`), and what is exposed is only the one full broadcast (`FrameFanout::broadcast_text`, implemented by `ConnRegistry`). Putting "send to one" at the place where the table is looks more honest as a layout. **Reason rejected — there is no need to change that layer at all (measured).** The 「특정 연결로 보내는 핸들」 (handle that sends to a specific connection) that delivery needs already comes into the daemon's hands, and to keep it one need only clone the `Arc`, and **the daemon already does that clone today** (「근거」 section). Opening a new function in net creates the same capability **in a second place**. A secondary reason: if that crate's boundary changes, it must be passed through the isolation gates again (**the authoritative source for the gate list and expected values = the header of `crates/engram-dashboard-net/src/lib.rs`** — the count is not taken here). There is no reason to shake a boundary that has no reason to change at that cost. **But this alternative is not dead** — if a unicast consumer other than the daemon appears, moving the capability to that place is right (that moment is the re-discussion trigger).
- **Broadcast to everyone and let the receiver pick and run only its own** — Use the existing broadcast as is, and only the shell whose owner value in the envelope is its own runs it. The least code added. **Precedent — ADR-0081 itself already rejected the same option**: the first item of its rejected alternatives 「**broadcast + 앱 필터** — 데몬이 UI 명령을 전 연결에 broadcast하고 앱이 자기 것만 필터. 시끄럽고(다른 연결·창이 다 봄) 대상 지정이 아니라 필터라 다중 창·비-앱 연결로 명령이 샌다.」 There is no new ground to overturn that rejection here. Two additional reasons:
  - ① **Every connection sees other parties' command requests.** ★**The daemon not reading it and it not reaching the receiving connection are different things**★ — under ADR-0155 decision 6 `name` is exposed on the outer cover and `args` is **opaque to the daemon**. But opaque only means *the daemon does not interpret it*, and those bytes **flow as they are to the receiving connection.** A connection that does not execute still receives, verbatim, what another client ordered with what arguments — that is the leak reason.
  - ② **It must be torn out in the next step.** The reference value of the pick-and-run discipline is owner, but ADR-0150 moved that value from connection derivation to **a client-authored identifier**, and slice B makes it real. The moment the reference value goes outside the connection, 「자기 것만 고른다」 (pick only its own) cannot be told apart from its own corpse or a namesake counterpart (accumulated items ㉱·㉲). On top of that, dev and release coexistence is already reachable. The cost saved now will be paid then with interest.

## 근거
- **Measured — the crate that owns the sending abstraction `OutboundSink` is the daemon, not net** (the trait in the daemon's `connection_core.rs`). At the point where a connection attaches, the daemon receives that connection's frame-send handle as an argument, but ★the form received is a **borrowed reference**★ — net's `ConnectionHandler::on_connect<'a>(&'a self, conn_id: ConnId, frames: &'a Arc<dyn FrameSink>)` (`crates/engram-dashboard-net/src/frame_port.rs`). The comment there pins it down: **a sink that outlives the connection cannot be made from a borrowed reference and needs a `'static` shared handle.** So to keep it in a table the `Arc` must be cloned, and **the daemon already does that clone explicitly today** (`FrameOutboundSink::new(frames.clone())` in `AgentConnection::on_text`). That is, no new capability has to be acquired; it just makes the clone already being done once more at keeping time — this is the real-code basis of "there is no need to change the net boundary".
- **Re-verification coordinates — written by symbol** (line numbers go stale with one commit. `docs/process/step-log.md:1781`):
  - **Sending abstraction:** `OutboundSink` (daemon `connection_core.rs`) · its implementation `FrameOutboundSink` and the connection lifetime hooks `on_connect`/`on_disconnect` (daemon `agent_conn.rs`)
  - **Where the table goes:** `CommandRoster` and its `live` table (daemon `command_roster.rs` — currently `BTreeMap<ConnId, LiveConn>` and under one lock with the registry)
  - **Lookup of the 3-step delivery:** `Roster::lookup` (tool crate `roster.rs`). ★**Zero calls on the daemon operating path**★ — the daemon does not call `route`. That the daemon has **zero lines** of code that 「명부에서 주인을 찾아 그 연결로 봉투를 쓰는」 (finds the owner in the registry and writes the envelope to that connection) is the hole this decision fills (`docs/process/step-log.md:1787` accumulated item ㊀).
  - **Where the lock discipline is already pinned:** `FrameFanout::broadcast_text` of `ConnRegistry` (net `ws.rs` — take a snapshot, release the lock, send) · `OutputCore::emit` (core `output_core.rs` — same wording. ★`subscribe`-type functions in the same file are the **intended opposite**★ — they send the replay while holding the subscriber lock. The new table follows the `emit` side's discipline)
  - **The same warning next to the structure this decision widens:** the file header of the daemon's `command_roster.rs` (lock, call once, release at once — if the guard is let out, one delivery stops registration, connection cleanup and lookup altogether) · **the authoritative source of that warning = the comment on the `OwnerLookupSource` trait in the tool crate's `roster.rs`** (the same wording in `route.rs` is a repetition of it)
- **User decision (2026-08-18)** — three branches were put forward with their costs and this one was chosen.

## 영향 / 불변식
- **The registry's duty widens.** The place that until now knew only "who owns which command" now also knows "how to reach that connection". Since it was the place already holding the list of 「지금 살아 있는 연결」 (connections alive now) under the same key (`ConnId`), in form it is closer to **raising that value-less list into a table with values** (in fact `live` went from a set to `BTreeMap<ConnId, LiveConn>`), but it is true that one duty was added.
- **The derivation point is fixed at `attach` alone.** The owner token is computed once when attaching and **stored**, and after that none of `detach`·`register`·`update` derives it again but reads the stored value. It is a single-source invariant of the same grain as ADR-0150's 「제거 지점은 한 곳뿐」, and **this is exactly what makes the replacement in re-discussion trigger ② safe** — if derivation is scattered in several places, on the day slice B changes the token's origin only some would be swapped and it would quietly come up empty-handed, and that empty hand cannot be told apart from 「주인이 없다」 (there is no owner).
  - **★This rule extends outside the registry too, and the part that extends looks like security★** — the check that compares the owner value a client wrote and sent by itself now also uses the **stored value** as the reference (the comparison function takes the stored value instead of the derived value as an argument, and two call sites feed it). If compared against the derived value, on the day storage leaves derivation **an honest client gets caught and an impostor passes** — the direction flips exactly the opposite way.
  - **There is no machine in that layer that blocks a reversion.** The call site itself wrote down 「저장소 어느 테스트도 이 되돌림을 안 잡는다」 (no test in the repository catches this reversion). So this item is an invariant kept not by a test but by **the reader** — that is why it is put in the ADR.
  - **Consequence — `ConnectionSession::owner_token` has no operating consumer left** (called only by tests). It remains only as a policy description. ★But the status of the `owner` field in the registration message is unchanged★ — it is still **for warning logs only** and is not used for routing or authorization. ADR-0150's 「기존 `owner` 칸은 계속 무시한다」 (the existing owner field is still ignored) is not touched by this decision.
- **The cost of choosing a strong handle is two, and the compiler catches neither.** These are duties ADR-0006 does not cover — that discipline's clauses are about the act of **sending**, while the two below are about the act of **holding**.
  - **① Do not run a destructor in the critical section.** A handle pushed out by replacement or removal is dropped **after** the lock is released (the table does not know what that destructor does).
  - **② ★Do not hold the handed-out copy across a round trip★.** When targeting, the table takes a copy and hands it to the delivering side, and **after handing it out there is no means to take it back.** If that copy is put in a wait slip and the reply is awaited, it **outlives `on_disconnect`**, and one surviving sender copy makes the writer of the disconnected connection unable to end itself, so **the connection leaks.** So the delivery side's contract is **take it, use it at once, and throw it away**. ★What enforces this contract is neither the compiler nor the net crate★ — the only place this sentence is written today is a test comment in net, but **the code that must keep it (the delivery point) is still zero lines, and the session that will write it reads this ADR, not `ws.rs`.** That is why it is written here.
- **The lock discipline gains one more object it applies to.** The discipline itself is not newly made — lock, take a copy, release, and only then send (ADR-0006). The warning that breaking it makes one delivery stop registration, connection cleanup and lookup altogether is already in code too (coordinates = 「근거」 section).
- **There become two tables** (connection id → path to reach, request id → origin connection and deadline). The former is inside `Shared` of `CommandRoster`, so it uses **one lock** with the registry and `live`, and the latter is a separate table hanging on one round trip. ★**Do not merge the two**★ — their lifetime units differ (TRD `:523`: a sweep entry hangs on one round trip and also disappears at its deadline, while a registry registration hangs on one connection and disappears only on its end. If merged, one deadline would erase the vocabulary).
- **Cleanup does not add to the registry's single removal point.** Two live constraints are kept as they are — 「**sweep과 명부는 다른 표다** … 여전히 합치지 말 것 … **명부 제거 지점은 한 곳뿐이다** — sweep 경로에 두 번째 제거를 얹지 않는다」 (`docs/process/S20-command-bus/trd.md:521-524`) and 「**끊김 처리는 `detach` 한 곳만** 바꾼다 … **두 번째 제거 지점을 만들지 않는다**」 (ADR-0150 impact section). ★Cleanup of the new slot is **not a second removal of the registry, but the same `detach` also emptying another slot of the same struct**★ — since it happens atomically under one lock, **the order of putting in and taking out between the two slots creates no observable window.** That is the value of choosing one lock.
  - **But the order itself is left in code** (the path to reach stands first, and when reaping, the registry goes first). Under one lock no one can see the middle, so **today it is not a correctness argument but a defense** — if the table is ever split outside the lock, it closes in advance the window that would open then. There is a precedent where a reversal produced a **silent defect** (CLAUDE.md 「등록 순서」 — if registry listing comes later than pump start, a session that exits immediately is not reaped and the runtime gives no signal at all).
- **★Still, a torn window remains — because of the delivery discipline, not the lock layout.★** `route` **deliberately releases the registry lock between lookup and delivery.** A test pins that property — `the_roster_is_not_held_while_the_link_is_in_flight` in the tool crate's `route.rs` (the reason is in that fn's doc: if delivery holds the registry, one slow counterpart stops registration, connection cleanup and other deliveries altogether). If `detach` comes in at that gap, it becomes a state where **lookup answered `Available` but the path to reach has vanished**. The answer then is pinned down:
  - **Answer with `OUTCOME_UNKNOWN`** (TRD `:514` — certainty **unknown**, `retry: same-request-id`). ★**This is a chosen value, not a measured one**★ — the direction argument below chooses it, and the next item supports it.
  - **Main basis — choose on the retry axis.** `OUTCOME_UNKNOWN` **permits asking again with the same `request_id`** (dedup absorbs that retry), while codes of the certain-failure family **forbid** retry. In this race the owner **can simply reattach**, so a same-id retry is **both safe and useful** — forbidding it gives the caller a permanent failure in front of a name that will come back to life. This one property decides the choice. ★Do not choose on certainty semantics (applied or not)★ — that axis has an open item below and cannot be leaned on now.
  - **Supporting precedent (measured) — the error vocabulary `route` *makes by itself* is a single value.** In that delivery branch the errors `route` itself generates are only `forwarding_unknown` (both the case where building the future blows up and the case where it blows up on the first poll are folded here) and the correlation-key mismatch branch, and **both are `ErrorCode::OutcomeUnknown`**. ★**Do not read this as 「그 경로에 다른 코드가 없다」 (there is no other code on that path) — that is false**★: `ErrorCode::OwnerUnavailable` is alive in the same crate's vocabulary (`error.rs`, `retry: AfterCondition`), and `route` **passes through as is** the reply of a link implementation that sends that code. Moreover the two places above are **catastrophe nets**, so their conditions are the opposite of ours (`forwarding_unknown` doc: 「**봉투는 이미 선을 탔을 수 있으므로** 이 홉의 확실성은 「불명」이다」). So this is not a basis that decides the decision but **a precedent of the same grain**.
  - **Not `UNKNOWN_COMMAND`.** That code means 「명부에 살아 있는 등록이 없다」 (there is no live registration in the registry) and is `retry: never` (TRD `:468`·`:484`), and issuing it for a name that lookup has just answered `Available` is a **false certainty** — exactly what the certainty slot in §4 is meant to prevent. ★But 「조회가 `Available`을 답했다」 only **rules out** this code and does not **choose** `OUTCOME_UNKNOWN`★ — what chooses is the direction argument above.
  - **Not `OWNER_UNAVAILABLE` either.** The TRD saw this race as that code's 「자연스러운 미래 소유자」 (natural future owner) but left it open (`trd.md:870`·§4-⑦ `:570`). **This decision closes that item, but closes it by deciding, not by measuring** — ★the daemon's delivery stretch is zero lines today, so that stretch was not measured★. That code has been **unreachable** since the 3rd edition (§4-⑦ `:569`) and reviving it is outside this decision's scope, and **no new error code is made either.** If an implementation issues another code, that is a violation of this ADR.
  - **★Open → closed (ADR-0159, 2026-08-18) — the certainty classification of 「봉투가 나간 적 없다」 (the envelope never went out) splits within the same file★.** `handler_panicked` in `route.rs` issues `ErrorCode::Internal` (retry forbidden) on the ground 「이 홉에서 **확실히** 실패했다(봉투가 나간 적이 없다)」 (it **certainly** failed at this hop (the envelope never went out)). The answer for the torn window pinned down by this decision folds the **same condition** into unknown. **This decision did not set the criterion for that distinction** — whether to unify the certainty rules of the two places is open, and until then the basis of the choice above is not certainty but the **retry axis**.
    - **★The closed answer = ADR-0159★** — it closed on **not** unifying. The sole measure is 「다시 물어볼 가치 = 안전 × 쓸모」 (value of asking again = safe × useful), and the certainty axis may be used for explanation but does not decide the code choice. The two places keep their different certainty descriptions as they are. **Consequence — the retry axis, the basis of the choice above, is not provisional but authoritative, and the codes of the three places (local panic · delivery panic · torn window) are all status quo by that measure too.**
- **What we accept — state of the same nature lives in two places.** Since net's `ConnRegistry` already holds a per-connection sender map, this decision makes a per-connection send channel **in a second place** (cleanup duties also become two). Reason accepted: **while the daemon is the only unicast consumer, not shaking the boundary is cheaper.** When there are two consumers, removing the duplication wins, so it is handed to re-discussion trigger ①.
- **★One change did actually go into net — comments only★.** This decision claims 「net 경계를 안 흔든다」 (it does not shake the net boundary) even counting the gate cost, so it accounts in advance for a net file showing in the commit diff: it is **added `///` comments inside `mod tests`** of `ws.rs` (+11/−1) and **the public API, behavior and dependencies are all unchanged**. What was added is the 「내준 사본」 (handed-out copy) contract above and an admission that the test cannot keep that clause for us. Both isolation gates were rechecked and passed. **The boundary was not shaken; the documentation inside the boundary grew.**
- **★The deadline goes into the same change★.** A commit that puts down the second table (request id → origin connection and deadline) **without a deadline** is forbidden — if only targeting is implemented and reclaiming is deferred, the moment envelopes start to flow a full queue turns a request into **an infinite wait**. 「보낸 쪽이 자기 마감시각으로 회수한다」 (the sender reclaims by its own deadline) (TRD §4-⑥ — the deadline is set by the caller and the **default is 10 seconds**), which justifies that reclaiming, **has no implementation in the daemon today** (`docs/process/step-log.md:1788` — grep for envelope-related deadline/timeout gives zero lines). Targeting and the deadline are one change.
- **Attach the code anchor `// ADR-0154`** to the new slot (connection id → path to reach in `Shared`) · the owner-token correspondence record (`attach`) · the delivery point · the cleanup point (`on_disconnect`). ★The delivery point is zero lines today★ — attach it together in the commit that makes the place where the daemon finds the owner in the registry and writes the envelope to that connection.
- **This decision is limited to the daemon hop.** The shell-side registry is **always empty** today (`Hop::roster` in `src-tauri/src/daemon_client/inbound.rs` — the comment says 「언제나 비어 있다(오늘)」 (always empty (today))) and the delivery target of that hop is the webview, so it is a separate matter. **Do not invent a different mechanism for the shell hop** — the basis is ADR-0155 decision 3 (no special case per hop).
- **Re-discussion trigger ①** — a consumer that uses unicast appears outside the daemon, even one → re-discuss rejected alternative 1 (moving the capability to the network layer).
- **Re-discussion trigger ②** — when the shell's own identifier (slice B) becomes real, the table's key may change from `ConnId` to that identifier → then re-discuss this decision's key choice. **The real surface of the re-discussion is the one `OwnerToken → ConnId` correspondence that `attach` records** — it is the place where that value is swapped from connection-id derivation to the first-greeting identifier, and forbidding `"conn-"` parsing and tying the derivation point to `attach` alone confine that swap to one place. **One open item is attached that must be decided at the same moment: when one owner has several connections, to which connection to send.** Today it is unreachable because `owner_of` is 1:1 with the connection, and the current lookup returns **the one with the smallest connection id**, but that is a by-product of table order, not a policy (the code marks that place as undecided).
