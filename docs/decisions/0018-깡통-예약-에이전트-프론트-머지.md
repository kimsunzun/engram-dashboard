# ADR-0018: Empty-shell (reserved) agent = the tree representation of a saved profile + double-click activation (frontend merge, no backend change)

- 상태: 확정 (2026-06-16, basis: the dashboard4 session conversation — the user presented the concept, then delegated after adversarial review)
- 관련: ADR-0016(lifetime model: saved = kept alive · spawn separated) · ADR-0007(epoch resubscribe) · ADR-0017(shells are not persisted) · `agent/profile.rs` · `commands/profile.rs` · `src/components/agent/AgentTree.tsx` · `src/store/agentStore.ts`
- Scope: decide the implementation approach for the UX "split a plan document across N agents, but do not spawn them all at once; reserve them as empty shells → the user activates them one by one with a double-click". **Frontend only, zero backend/protocol changes.**

## 맥락
After reading a plan document, we want to reserve 30 claude agents but not start them all at once, to avoid running many claude instances at the same time. We only save them as empty shells (empty slots) and activate them with a double-click when needed. The investigation found that **the reserve → activate plumbing already exists**: the backend has `create_claude_profile` (upsert only, no spawn) · `spawn_profile` (spawn from a saved profile) · `list_profiles` · `delete_profile`, all complete, and the agentClient/embeddedClient interfaces are complete too. The gap is only that **the frontend tree renders only running agents (AgentInfo) and does not show saved profiles.**

## 결정
1. **An empty shell = a saved `AgentProfile` (not spawned).** Reuse the existing `CreateProfile`/`spawn_profile` plumbing. No new backend plumbing or protocol variants.
2. **The "Reserved/waiting" state is synthesized by the frontend** — `listProfiles()` ∖ `agents[]` (running). We **do not** add a non-running state to the backend `AgentStatus` enum or the protocol.
3. **Tree = profiles ∪ running.** An agent is in exactly one bucket, running XOR reserved (no duplicates). Double-click a reserved node → `spawnProfile(id, resume=false)` → it moves to running. Running nodes keep the existing behavior (select/right-click). An ad-hoc shell without a profile (SpawnByCwd) is also still shown from `agents[]`.
4. **A reservation is created with `auto_restore=false`.** It is excluded from the boot auto-spawn (restore_all only starts auto_restore ones) → it stays an empty shell even after a reboot. The user can toggle it with `set_profile_auto_restore` if wanted.
5. **Since there is no profile-change event**, after create/delete/activate we refetch with `listProfiles`, and load once at boot, to refresh the store. The transition to running is handled by the existing `agent-list-updated`.
6. **Do not touch AgentSession** — do not create empty sessions in advance.

## 거부한 대안
- **Create empty AgentSessions in advance and keep them in the session map (hollow + an `IsValid()` guard).** AgentSession owns a `Box<dyn AgentTransport>` (a live PTY handle) + an `Arc<OutputCore>` (a running pump), so an empty state is not in the design (`session.rs:39-41`). The deciding blow is **it cannot be serialized** — persisting an empty shell is fundamentally impossible with the session container, so a profile would have to be kept separately anyway, which makes it two copies instead (the exact opposite of the "manage in one place" motivation). Besides that: conflicts with finalize-once and epoch resubscribe, and a TOCTOU while filling. The IsValid guard only blocks read/write and does not solve the serialization and state-owner problems. (It is the standard pattern in the Unreal UObject world, but Rust prefers to remove invalid states through types, and the serialization requirement blocks it regardless of language.)
- **Add a backend `AgentStatus::Reserved`.** It can already be expressed with the two lists of profiles/agents → duplication. `AgentStatus` is the place for the lifetime of a running session (pump alone emits terminal), so mixing in a non-running state blurs its meaning.

## 근거
- Investigation (Explore): the backend and the agentClient interface are complete, and the gap is in the frontend (the store has no profiles field, eventBus does not subscribe to profiles, the tree renders only running agents). So the smallest change surface is the frontend.
- LLM-first control (§5) undamaged: the control surface for reserving and activating (`create_claude_profile`/`spawn_profile`) can already be controlled by the LLM via invoke. This frontend UI is only a supplementary input through which a human operates the same handles.

## 영향 / 불변식
- **Zero backend regressions** (no change) — no impact on core/protocol tests.
- The persistence unit of an empty shell = `AgentProfile` (agents.json). Shells are still not persisted (ADR-0017).
- An activation spawn issues an epoch → the frontend `[agentId, epoch]` resubscribe (ADR-0007) as is.
- Turning off = deletion (ADR-0016). Deleting a reserved empty shell = `delete_profile`.

## Follow-ups / known limits (confirmed after implementation by reviewer-deep + QA measurement)
- **An activated empty shell does not automatically return to an empty shell when it exits, and re-activation is blocked until it is killed.** The spawn guard (`manager.rs:90-100`) looks only at whether an entry exists in the sessions map (regardless of liveness), and the `done_rx` supervisor that reaps ended sessions is not implemented (ADR-0016 §37 "awaiting approval"), so a repeated `spawn_profile` call is rejected as "already running". The current path: right-click the ended node and kill → the session is removed → it returns to an empty shell → re-activate. **This belongs to the runtime death observation/restart/reap decisions that ADR-0016 parked** — it is not worked around within this frontend scope, and the current behavior was recorded as a regression guard through a merge test.
- **A profile created by an external party/LLM through a daemon command is not reflected live in the human tree.** Profile create/delete does not emit a broadcast event like `agent-list-updated`, so it is refreshed only when the same client calls `refreshProfiles()` directly (the Sidebar create form calls it → the human path is reflected immediately, OK). To keep LLM-first control (§5) alive, the daemon would have to broadcast `ProfileListUpdated` — a backend/protocol follow-up (out of scope this time).
