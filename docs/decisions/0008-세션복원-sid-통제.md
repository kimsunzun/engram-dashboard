# ADR-0008: Session restore — we control the sid, the tracking file is best-effort

- 상태: 확정 (S9, daemon-lifetime context added 2026-06-15) · 부분 폐기 by ADR-0185 (who issues the sid) · 부분 폐기 by ADR-0226 (of the first item of the decision, only the persist timing; issuing at spawn stays as is)
- 관련: CLAUDE.md S9 메커니즘 · `backend/claude.rs` · `profile.rs::ProfileRegistry` · `session_tracker.rs` · ADR-0015(daemon lifetime) · Amended by ADR-0082 (resume early-exit → fresh-fallback clause removed: a failure goes straight to the end state (usually `Exited{code≠0}` — not `Failed`), no automatic fresh re-spawn) · Amended by ADR-0185 (who issues the sid) · Amended by ADR-0226 (of the first item of the decision, only the persist timing; issuing at spawn stays as is)

## 맥락
A claude session must be restored without loss after a restart. Who controls the session id (sid) decides the accuracy of the restore.

## 결정
- At spawn, **we issue and persist the sid with `--session-id <uuid>`** → on restart, restore with `--resume <uuid>`.
- If claude changes the sid via `/clear`, poll `~/.claude/sessions/<pid>.json` to catch up and **persist immediately** (best-effort).
- If the resume exits early (a terminal state within the 3s window), treat it as a failure and fall back to fresh with a new sid (end state Failed, no recursion).

## 거부한 대안
- **Rely on claude's automatic sid** — we cannot control it, so at restore time we cannot tell which session it was.
- **Make `sessions/<pid>.json` a first-class dependency** — if it cannot be read, the restore itself fails. So it is demoted to best-effort.

## 근거
Restore accuracy depends **only on the sid we control**. If the tracking file cannot be read, it degrades without damage (only tracking turns off). S9 fable review M-1: a successful resume is a TUI and does not exit inside the window, so a terminal state inside the window is a failure signal regardless of the exit code.

## 영향 / 불변식
- **Do not *extend* functionality with `sessions/<pid>.json`** — its best-effort grade is fixed.
- The resume early-exit window = 3s (`EARLY_EXIT_WINDOW`).

## Daemon-lifetime context supplement — boot-restore policy (2026-06-15, ADR-0015)
The daemon is persist-until-kill (ADR-0015), so **restore fires only "on a daemon cold boot"** — only when the daemon has actually died and come back, through a PC reboot or an explicit `shutdown`. Opening and closing the app window or reconnecting does not kill the daemon, so claude sessions **keep running inside the daemon and no restore fires** (no refresh every time in normal use — the same shape as the Emacs daemon / Zellij server keeping processes alive). This structurally removes the previous session's "close the console → daemon dies → restore again" churn.

**Boot-restore policy ~~= 3-mode option~~ → discarded (Superseded by ADR-0016, 2026-06-16):**
- The ~~3 modes (auto / off / ask) × auto_restore flag~~ design was **discarded**. "Ask (prompt whether to restore when the UI opens)" is an **anti-pattern that makes the UI the restore trigger** (the consult decision), so it was dropped; in the sid-instance model (ADR-0016) it is simplified to "restore every saved non-suspended instance automatically, delete the ones you do not want alive". `auto_restore` is redefined not as a 3-mode flag but as "automatic wake-up on/off" (false when the guard suspends). **For the boot-restore behavior, see ADR-0016.**

**Boot restore is one-shot per session — no separate counter is needed.** The existing ladder (`--resume` → if it exits early within 3s, one fresh fallback → if that also fails, end state Failed, no recursion) is itself the guard. Even on failure, it is shown once in the tree as Failed and stops.

**Distinction (do not confuse):** "automatically reviving an agent that was running and died at runtime" is a **separate feature (auto-restart)** and needs a backoff + a maximum-count limit → **TODO (gate, after the core is stable).** Do not mix it with boot restore (one-shot).
