# ADR-0134: Put the release data folder in an engram-data subfolder of the run folder + base the single-instance scope on the data folder

## 맥락

**The user has to run a debug daemon for development while using the release distribution.** Right now that does not work — the one that starts later says "already running" and exits by itself.

The cause is that the single-instance decision looks **only at the user name** (`instance.rs:39-40` — `Global\EngramDashboardDaemon-<USERNAME>`). Yet the comment written as its basis (`instance.rs:8-11`) is *"the data-folder uniqueness boundary is per user (`%APPDATA%`), so there is one mutex per user"*. **That premise is already broken** — `default_data_dir()` uses `.engram-data/` at the repository root in debug and `%APPDATA%` in release, so the data folder is already split by build. That is, the decision is wider than the resource it actually contends over (the registry file).

The second problem is that the release is **half portable**. ADR-0100 assembles a "portable folder", but the data stays in `%APPDATA%`, so even if the folder is deleted, the registry and presets stay alive. The user's requirement is fully portable ("for now I want portable").

Historically this axis was handled by ADR-0027 (embedded = per folder / folder-local, daemon = global / user-global), and ADR-0029 removed the embedded mode and **threw away the folder-local concept along with the mode axis**. This decision does not revive the mode axis, and adopts folder-local without modes.

## 결정

1. **Release data folder = `engram-data/` under the run folder.** `%APPDATA%\com.engram.dashboard` is not used. If the distribution folder is deleted, no trace is left.
2. **The data is bundled into one subfolder** — it is not scattered next to the exe. If the distribution files (3 exes + `prompts/`) and the user data are mixed in the same place, overwriting with a new version's archive becomes dangerous, and data of a save-like nature is going to grow.
3. **Single instance = hold the OS lock on a fixed lock file inside the data folder.** Abandoning the user-name criterion stands as it was, and **we do not decide what *identifies* the folder** — a file with a fixed name is put in the data folder, and the daemon holds the OS lock on that file for the lifetime of the process. A second daemon cannot take the same file and backs off. The file's **content is not an identity** (if the content were used as identity, a copy would claim the same identity).

   Because path-alias resolution is delegated to the OS, normalization, fingerprints, and owned-path comparison all become unnecessary. Copies each have their own file and coexist normally, a move is harmless because the file goes along, and when the daemon dies the OS releases the lock automatically (no stale-entry decision is needed). As a side effect, **even a daemon on another computer is excluded over a network share** — a named mutex is valid only within one computer and cannot block this case.
4. **If the data folder is not writable, do not fall back and fail clearly.** It tells the user to unpack it in a writable location.
5. **Existing `%APPDATA%` data is not migrated.** The first release (v0.1.0) was on 2026-08-09 and the project is not accepting outside contributors or users.
6. **Debug behavior is unchanged** — `.engram-data/` at the repository root is kept. The `ENGRAM_DATA_DIR` override stays as is too.

## 거부한 대안

- **Keep the user-name-based single instance (current)** — the release and debug daemons cannot coexist, so it fails the requirement. Basis for rejection = code (`instance.rs:39-40` looks only at `USERNAME`).
- **Give a different key each time with the `ENGRAM_INSTANCE_KEY` environment variable (current workaround)** — it is already possible, but it has to be handled each time **paired** with the data-folder variable, and if forgotten, one side quietly exits (it looks like a normal exit, not an error). Basis for rejection = code (`INSTANCE_KEY_ENV` was introduced for test isolation and is not an operating path).
- **Base the single-instance decision on the *run folder*** — the user's first proposal. If the release is unpacked in two places, two daemons come up, and if the data folder is pointed at the same place through an environment variable, they **write the same registry file at the same time.** The resource actually contended over is the data folder, so the criterion has to be that. If decision 1 is adopted, the two folders practically coincide in the release and the result is the same, but the criterion has to be written as the data folder for it to split correctly on the override path too. Basis for rejection = code and logic.
- **Fall back to `%APPDATA%` on a write failure** — it always starts, but in exchange it becomes "I deleted the folder but the registry is still alive", and that is exactly the confusion this decision means to remove. Basis for rejection = **user policy decision** (not quantitative or measured — see the reopen condition in 「영향」 below).
- **Just leave the data next to the exe** — one fewer folder is created, but it mixes with the distribution files. Basis for rejection = **user policy decision** + overwrite risk.
- **Implement a path for migrating existing data** — there is practically nothing to move. Basis for rejection = quantity (four days since the release went out, outside users not accepted).
- **Change to the `Local\` namespace** — it is limited to the logon session, so in an RDP or elevated session two daemons come up on the same data folder. The reason ADR-0029 chose `Global\` is still valid, so it is kept. Basis for rejection = code comment (`instance.rs:8-11`).
- **★Make the mutex name from a fingerprint of the data-folder path (adopted 2026-08-13 → rejected 2026-08-14)★** — it was the original plan for decision 3 and went as far as two rounds of implementation. The reason for rejection is that **the problem setting itself was wrong** — there is no need to identify the folder and name the lock; if a file inside the folder is locked, the OS resolves the path alias. The burdens this approach forced: the code has to converge every notation of case · `..` · 8.3 · junction · subst · mapped drive (miss even one and there are two daemons on the same registry), the identity changes when the folder is moved and deadlocks, and staleness has to be decided by string comparison. Basis for rejection = precedent survey + MS primary documents (the basis section below).
- **Write a unique key value inside the folder and use that value as the identity** — it removes normalization but **gives a wrong answer on copy** (the key is copied too, so two different installations claim the same identity → one cannot start). Exactly the wrong direction for a portable distribution. There is also a corruption path where, if only the key file is deleted, a second one starts next to a live daemon. Basis for rejection = logic + copying is the normal use of portable.
- **Make the lock name from the OS directory's real identifier (`FILE_ID_INFO`)** — it avoids the notation problem at the root, but it is still in the "identify and name" family, so it cannot get the benefits of a file lock (exclusion across network shares · automatic release). In addition, the 64-bit ID has **no uniqueness guarantee on ReFS** (MS text), its behavior is uncertain on non-NTFS and network shares, and no production precedent for this use was found. **There is room to keep it as an auxiliary verification means** (an adversarial-review point — do not discard it on the wording "reusable" alone).

## 근거

- **The decision's scope was out of step with the actually contended resource** — the premise the mutex comment itself cited as its basis (`데이터 폴더 = 사용자 단위` (data folder = per user)) is already void because of the per-build branch in `default_data_dir()`. This decision is a correction that aligns the decision with the actual resource.
- **It completes ADR-0100's "portable folder" as the name says** — right now the data stays outside, so portable is only half.
- User decision (2026-08-13): running the release and debug daemons at the same time + fully portable.
- **Precedent survey (2026-08-14, `/research` medium + adversarial verification by a different family)** — the basis for flipping decision 3 to a file lock.
  - **Locking a file inside the resource is overwhelmingly the practice.** PostgreSQL (`postmaster.pid` in the data directory) · LevelDB (`LOCK` in the DB directory) · Git (`index.lock`) all use a file inside the resource without hashing the path. **The first collection misclassified them as "path-string approaches", and the adversarial verification caught that misclassification** — in fact they are approaches that never run into the identification problem in the first place.
  - **A real case where path-hash identity failed:** an issue where VS Code `workspaceStorage` buckets split because of symlinks and extension state diverges (microsoft/vscode#313681, unresolved).
  - **MS primary document:** `BY_HANDLE_FILE_INFORMATION` — "File IDs are not guaranteed to be unique over time, because file systems are free to reuse them" · "The 64-bit identifier in this structure is not guaranteed to be unique on ReFS."
  - **The reach of a named mutex:** `Global\` is only global across the sessions of one computer, **not global across computers.** If two PCs use the same network-share folder, each gets a mutex in its own kernel and both start. A file lock is mediated by the file server.
  - **Three of my errors that the adversarial verification overturned:** ① the sampling bias of "the industry does not block it, so the risk is rare" (most of the targets are POSIX servers where the operator controls the path, and moreover they use file locks and so do not run into this problem) ② the unmeasured claim that "the actual exposure is narrow" (launching a mapped-drive shortcut and a UNC shortcut of a network folder separately is ordinary user behavior) ③ the assumption that lowercasing is safe — Windows too can be **case-sensitive per folder**, so two different folders can be folded into one.

## 영향 / 불변식

- **The data folder is added to the co-location invariant** (an extension of ADR-0100) — run folder = the parent of the data folder. To the existing constraint that moving a single executable out on its own prevents it from finding its daemon and CLI companions, "cannot create the registry" is added.
- **★Void as of 2026-08-14★ The two lines below are consequences of the discarded fingerprint approach and no longer hold** — since no lock name is made, there is no fingerprint or normalization. Kept for history only.
  - ~~Because a path cannot be put directly into the mutex name, a fingerprint is put in instead, and because the folder cannot be read from the name alone, the folder path is left in the startup log.~~
  - ~~The input of the fingerprint must be a normalized absolute path, and if the notation diverges, two daemons come up on the same registry.~~
- **The lock file lives inside the data folder** — it is not in the distribution archive and is created at runtime. The `engram-data/` rule of `.gitignore` covers it too.
- **Keep leaving the data folder path in the startup log** — it was introduced as the price of the fingerprint being unreadable, but now it stays because it is the only means for a person to confirm "which folder was taken". However, a release daemon has nowhere for its log to go, so this line alone does not allow diagnosis (the diagnosis item below).
- **If only `ENGRAM_DATA_DIR` is specified, a third daemon is separated automatically too** — there is no need to carry a key variable separately. ~~`ENGRAM_INSTANCE_KEY` is kept for test isolation.~~ **★Void as of 2026-08-14 (ADR-0135)★** — it was removed. Since no lock name is made, there is no name to override, and test isolation is done by `ENGRAM_DATA_DIR` alone.
- **The distribution archive has no `engram-data/`** (created at runtime) — the extra-file tripwire of `scripts/build-release.ps1` checks only at packaging time, so it is unaffected.
- **★Correction (found in review · 2026-08-13)★ Reassembly = data reset.** The tripwire statement above is right, but it **missed the clean regeneration of the same script (`Remove-Item -Recurse -Force $ReleaseDir`).** The data now lives inside the assembly output folder, so the loop assemble → run → reassemble burns the registry and presets without warning. **No preservation logic is added** (user decision 2026-08-13 — "fine to wipe it"). The assembly script is a development and packaging path, not the distribution user's path, so it keeps the clean-regeneration contract. **Reopen condition:** if a habit of real use out of the assembly folder arises, flip to preservation.
- **★Correction (found in review · 2026-08-13)★ A normalization failure is a failure, not a degrade.** The original plan of 「지문의 입력은 정규화된 절대경로여야 한다」 (the input of the fingerprint must be a normalized absolute path) above was to degrade to a non-canonical absolute path when canonicalize fails, but that degrade path **performs no normalization at all**, so it lets through the very corruption mode this decision itself named "the only risk point" (two daemons on the same folder). A situation where normalizing a folder that was just created successfully fails is already abnormal, so **it does not proceed with a quietly diverged fingerprint and aborts startup.**
- **The README needs a fix** — the current "it is stored in `%APPDATA%\com.engram.dashboard` … to delete it completely, delete this too" becomes false.
- **★Void as of 2026-08-14 (ADR-0135) The line below is a consequence of the discarded fingerprint approach and does not hold — that field was not put in the portfile. The merged file follows the folder, so the deadlock written here does not arise at all. Kept for history only.** ~~**Implementation consequence (2026-08-13) — the connection key records its own owning folder.**~~ A normalized data-folder path field is attached to the portfile, and if the recorded path differs from the current folder, it is **decided stale**. Reason: if a portable folder is moved as a whole, the fingerprint diverges and the new daemon gets the lock, but the old connection key that came along still points at the old daemon that is still alive, so a deadlock arises in which the new daemon can never start. An old file without the field is decided by pid liveness as before (backward compatible).
- **★Void as of 2026-08-14 (ADR-0135) A dedicated exit code was not implemented — it was built, but there was no display slot on the screen so the user's experience stayed the same. Instead the dashboard actually writes to its own data folder before starting the daemon and shows the failure reason in the window. Below is for history only.** ~~**Implementation consequence (2026-08-13) — if the data folder is not writable, tell by a dedicated exit code.**~~ Because the "notifies" of decision 4 does not hold in the release — the release daemon has no console and its log goes only to the screen with the default level at warning or above, so the error reaches nowhere and the client sees only a connection timeout with no cause. So only this failure ends with a dedicated exit code and the client reads it and shows the cause. **There is a narrow race window in the observation** — if the daemon dies too fast and the process handle cannot be taken, it degrades to the old behavior (timeout).
- **Unresolved — two copies of the distribution.** If a folder that has been run once is copied as a whole, the connection key goes along, and the copy's client **attaches to the original daemon** (it does not start its own daemon). That is because the client does not look at the folder identity, and this decision did not create it. To fix it, the fingerprint-computation rule would have to be placed in the client too, but if replicated in two places there is a risk of endless daemon restarts when they diverge, so promotion to a shared layer is needed and the felt behavior changes. **It is handled together with the axis "the UI explicitly chooses which daemon to attach to" (remote · mobile)** (user judgment 2026-08-13 — keep as is for now).
- **Reopen condition** — decision 4 (no fallback) and decision 2 (subfolder) are **policy judgments**, not quantitative or measured. If "I installed it in the program files folder and it won't start" actually repeats once outside users appear, decision 4 is reopened. Until then, no fallback is put in arbitrarily.
