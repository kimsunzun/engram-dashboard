# ADR-0134: 릴리스 데이터 폴더를 실행 폴더 하위 engram-data 로 + 단일 인스턴스 스코프를 데이터 폴더 기준으로

- 상태: 확정 (2026-08-13, 사용자 결정 — 릴리스 배포판을 완전 포터블로) · 부분 폐기 by ADR-0135 (연결키 파일을 잠금 파일에 통합)
- 관련: Amends ADR-0029 (단일 인스턴스 스코프와 릴리스 데이터 폴더 위치 대체) · ADR-0027(모드별 인스턴스/데이터 — 폴더-로컬 아이디어의 출처, ADR-0029가 전체 폐기) · ADR-0100(릴리즈 패키징 포터블 폴더 · co-location 불변식) · ADR-0024(데몬 데이터 위치 — 데이터위치 조항은 0027이 이미 폐기) · ADR-0129(net crate — 단일 인스턴스 가드 소유) · `crates/engram-dashboard-discovery/src/lib.rs`(`default_data_dir`) · `crates/engram-dashboard-net/src/instance.rs`(named mutex) · Amends ADR-0100 (런타임 데이터 위치를 실행 폴더 하위로 대체) · Amended by ADR-0135 (연결키 파일을 잠금 파일에 통합)

## 맥락

**사용자가 릴리스 배포판을 쓰면서 동시에 개발용 디버그 데몬을 돌려야 한다.** 지금은 안 된다 — 나중에 뜬 쪽이 "이미 실행 중"이라며 스스로 종료한다.

원인은 단일 인스턴스 판정이 **사용자 이름만** 본다는 것이다(`instance.rs:39-40` — `Global\EngramDashboardDaemon-<USERNAME>`). 그런데 그 근거로 적힌 주석(`instance.rs:8-11`)은 *"데이터 폴더 단일성 경계가 사용자 단위(`%APPDATA%`)이므로 mutex 도 사용자당 하나"* 다. **그 전제는 이미 깨져 있다** — `default_data_dir()`은 디버그에서 저장소 루트의 `.engram-data/`를, 릴리스에서 `%APPDATA%`를 쓰므로 데이터 폴더는 빌드별로 이미 갈려 있다. 즉 판정이 실제로 다투는 자원(명부 파일)보다 넓다.

두 번째 문제는 릴리스가 **반쯤 포터블**이라는 것이다. ADR-0100이 "포터블 폴더"로 조립하지만 데이터는 `%APPDATA%`에 남아, 폴더를 지워도 명부·프리셋이 살아 있다. 사용자 요구는 완전 포터블이다("당분간은 포터블을 원함").

역사적으로 이 축은 ADR-0027이 다뤘고(embedded=폴더별/폴더-로컬, daemon=전역/유저-global), ADR-0029가 embedded 모드를 없애며 **모드 축과 함께 폴더-로컬 개념도 버렸다**. 이번 결정은 모드 축을 되살리지 않고, 모드 없이 폴더-로컬을 채택한다.

## 결정

1. **릴리스 데이터 폴더 = 실행 폴더 하위 `engram-data/`.** `%APPDATA%\com.engram.dashboard`를 쓰지 않는다. 배포판 폴더를 지우면 흔적이 남지 않는다.
2. **데이터는 하위 폴더 하나로 묶는다** — exe 옆에 흩어놓지 않는다. 배포 파일(exe 3개 + `prompts/`)과 사용자 데이터가 같은 자리에서 섞이면 새 버전 압축을 덮어쓸 때 위험하고, 앞으로 세이브 성격의 데이터가 늘어날 예정이다.
3. **단일 인스턴스 = 데이터 폴더 안의 고정 잠금 파일을 OS 잠금으로 보유한다.** 사용자 이름 기준을 폐기하는 것은 그대로이고, **폴더를 무엇으로 *식별*할지를 우리가 정하지 않는다** — 데이터 폴더 안에 정해진 이름의 파일을 두고 데몬이 그 파일의 OS 잠금을 프로세스 수명 동안 쥔다. 두 번째 데몬은 같은 파일을 잡지 못해 물러난다. 파일 **내용은 신원이 아니다**(내용을 신원으로 쓰면 복사본이 같은 신원을 주장한다).

   경로 별칭 해석을 OS에 위임하므로 정규화·지문·소유 경로 비교가 전부 불필요해진다. 복사본은 각자 자기 파일을 가져 정상적으로 공존하고, 이동은 파일이 따라가므로 무해하며, 데몬이 죽으면 OS가 잠금을 자동 해제한다(낡은 항목 판정이 필요 없다). 부수 효과로 **네트워크 공유에서 다른 컴퓨터의 데몬까지 배제된다** — named mutex는 한 컴퓨터 안에서만 유효해 이 경우를 막지 못한다.
4. **데이터 폴더에 쓸 수 없으면 폴백하지 않고 명확히 실패한다.** 쓰기 가능한 위치에 풀라고 알린다.
5. **기존 `%APPDATA%` 데이터를 이전하지 않는다.** 첫 릴리스(v0.1.0)가 2026-08-09이고 외부 기여·사용자를 받지 않는 상태다.
6. **디버그 동작은 무변경** — 저장소 루트의 `.engram-data/` 유지. `ENGRAM_DATA_DIR` override도 그대로.

## 거부한 대안

- **사용자 이름 기준 단일 인스턴스 유지(현행)** — 릴리스와 디버그 데몬이 공존 못 해 요구를 못 채운다. 기각 근거 = 코드(`instance.rs:39-40`이 `USERNAME`만 본다).
- **`ENGRAM_INSTANCE_KEY` 환경변수로 매번 열쇠를 다르게 주기(현행 우회)** — 이미 가능하지만 데이터 폴더 변수와 **짝지어** 매번 챙겨야 하고, 빠뜨리면 조용히 한쪽이 종료된다(오류가 아니라 정상 종료로 보인다). 기각 근거 = 코드(`INSTANCE_KEY_ENV`는 테스트 격리용으로 도입된 것이고 운영 경로가 아니다).
- **단일 인스턴스 판정을 *실행 폴더* 기준으로** — 사용자 최초 제안. 릴리스를 두 곳에 풀면 두 데몬이 뜨는데, 데이터 폴더를 환경변수로 같은 곳에 지정한 경우 **같은 명부 파일을 동시에 쓴다.** 실제로 다투는 자원은 데이터 폴더이므로 기준도 그것이어야 한다. 결정 1을 채택하면 릴리스에서 두 폴더가 사실상 일치해 결과는 같지만, 기준을 데이터 폴더로 적어야 override 경로에서도 옳게 갈린다. 기각 근거 = 코드·논리.
- **쓰기 실패 시 `%APPDATA%`로 폴백** — 항상 뜨는 대신 "폴더를 지웠는데 명부가 살아 있다"가 되고, 그게 이 결정이 없애려는 혼란 그 자체다. 기각 근거 = **사용자 정책 결정**(정량·실측 아님 — 아래 「영향」의 재론 조건 참조).
- **데이터를 exe 옆에 그냥 두기** — 폴더가 하나 덜 생기지만 배포 파일과 섞인다. 기각 근거 = **사용자 정책 결정** + 덮어쓰기 위험.
- **기존 데이터 이전 경로 구현** — 옮길 대상이 실질적으로 없다. 기각 근거 = 정량(릴리스 나간 지 나흘, 외부 사용자 미수용).
- **`Local\` 네임스페이스로 바꾸기** — 로그온 세션 한정이라 RDP·권한상승 세션에서 같은 데이터 폴더에 두 데몬이 뜬다. ADR-0029 시절 `Global\`을 택한 근거가 그대로 유효해 유지. 기각 근거 = 코드 주석(`instance.rs:8-11`).
- **★데이터 폴더 경로의 지문으로 mutex 이름 만들기 (2026-08-13 채택 → 2026-08-14 기각)★** — 결정 3의 원안이었고 두 라운드 구현까지 갔다. 기각 이유는 **문제 설정 자체가 틀렸다는 것** — 폴더를 식별해 잠금에 이름을 붙일 필요가 없고, 폴더 안 파일을 잠그면 OS가 경로 별칭을 해석한다. 이 방식이 강요하던 부담: 대소문자·`..`·8.3·정션·subst·매핑드라이브 표기를 코드가 전부 수렴시켜야 하고(하나라도 놓치면 같은 명부에 데몬 둘), 폴더 이동 시 신원이 바뀌어 교착하며, 낡음 판정을 문자열 비교로 해야 한다. 기각 근거 = 선례 서베이 + MS 1차 문서(아래 근거 절).
- **폴더 안에 고유 키 값을 적어두고 그 값을 신원으로 쓰기** — 정규화는 없애지만 **복사에서 틀린 답을 낸다**(키까지 복사돼 서로 다른 두 설치가 같은 신원을 주장 → 하나가 못 뜬다). 포터블 배포에 정확히 나쁜 방향. 키 파일만 지워지면 살아 있는 데몬 옆에 두 번째가 뜨는 손상 경로도 생긴다. 기각 근거 = 논리 + 복사가 포터블의 정상 사용.
- **OS 디렉터리 실체 식별자(`FILE_ID_INFO`)로 잠금 이름 만들기** — 표기 문제를 원천 회피하지만 여전히 "식별해서 이름 붙이기" 계열이라 파일 잠금의 이점(네트워크 공유 간 배제·자동 해제)을 못 얻는다. 더해 64비트 ID는 **ReFS에서 고유성 미보장**(MS 원문), 비-NTFS·네트워크 공유에서 동작 불확실, 그리고 이 용도의 프로덕션 선례를 찾지 못했다. **보조 검증 수단으로는 남길 여지가 있다**(적대 리뷰 지적 — "재사용 가능" 문구만으로 폐기하지 말 것).

## 근거

- **판정 범위가 실제 경합 자원과 어긋나 있었다** — mutex 주석이 스스로 근거로 든 전제(`데이터 폴더 = 사용자 단위`)가 `default_data_dir()`의 빌드별 분기로 이미 무효다. 이 결정은 판정을 실제 자원에 맞추는 정정이다.
- **ADR-0100의 "포터블 폴더"를 이름대로 완성한다** — 지금은 데이터가 밖에 남아 포터블이 반쪽이다.
- 사용자 결정(2026-08-13): 릴리스와 디버그 데몬 동시 실행 + 완전 포터블.
- **선례 서베이(2026-08-14, `/research` medium + 다른 family 적대 검증)** — 결정 3을 파일 잠금으로 뒤집은 근거다.
  - **자원 안의 파일을 잠그는 것이 압도적 관행이다.** PostgreSQL(데이터 디렉터리의 `postmaster.pid`) · LevelDB(DB 디렉터리의 `LOCK`) · Git(`index.lock`) 전부 경로를 해시하지 않고 자원 내부 파일을 쓴다. **1차 수집은 이들을 "경로 문자열 방식"으로 잘못 분류했고, 적대 검증이 그 오분류를 적출했다** — 실제로는 애초에 식별 문제를 겪지 않는 방식이다.
  - **경로 해시 정체성이 실패한 실사례:** VS Code `workspaceStorage`가 심링크로 버킷이 분열해 확장 상태가 갈리는 이슈(microsoft/vscode#313681, 미해결).
  - **MS 1차 문서:** `BY_HANDLE_FILE_INFORMATION` — "File IDs are not guaranteed to be unique over time, because file systems are free to reuse them" · "The 64-bit identifier in this structure is not guaranteed to be unique on ReFS."
  - **named mutex의 사정거리:** `Global\`은 한 컴퓨터의 세션 간 전역일 뿐 **컴퓨터 간 전역이 아니다.** 두 PC가 같은 네트워크 공유 폴더를 쓰면 각자 자기 커널의 mutex를 얻어 둘 다 뜬다. 파일 잠금은 파일 서버가 중재한다.
  - **적대 검증이 뒤집은 내 오류 셋:** ① "업계가 안 막으니 위험이 드물다"는 표본 편향(대상 대부분이 운영자가 경로를 통제하는 POSIX 서버이고, 게다가 파일 잠금을 써서 이 문제를 안 겪는다) ② "실제 노출은 좁다"는 미측정 주장(네트워크 폴더의 매핑 드라이브 바로가기와 UNC 바로가기를 각각 실행하는 것은 평범한 사용자 행동이다) ③ 소문자화 안전 가정 — Windows도 **폴더별 대소문자 구분**이 가능해 서로 다른 두 폴더를 하나로 접을 수 있다.

- **기동 로그에 데이터 폴더 경로를 남기는 것은 유지한다** — 지문 불가독의 대가로 도입했지만, 이제는 "어느 폴더를 잡았나"를 사람이 확인할 유일한 수단이라는 이유로 남는다. 단 릴리스 데몬은 로그가 나갈 곳이 없어 이 줄만으로는 진단이 안 된다(아래 진단 항목).
