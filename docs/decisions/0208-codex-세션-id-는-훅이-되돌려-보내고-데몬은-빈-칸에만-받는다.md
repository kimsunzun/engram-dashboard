# ADR-0208: The codex session id is sent back by a hook, and the daemon accepts it only into an empty slot

- 상태: 확정 (2026-09-19, basis: commit `75bdfda` · codex-cli 0.155.0 measured 3 times) · 부분 폐기 by ADR-0210 (hook registration boundary and merging of hook diagnostics) · 부분 폐기 by ADR-0216 (replaces the hook retrieval path and the adopt empty-slot policy)
- 관련: CLAUDE.md 「백엔드 확장」 · ADR-0185(neutral issuer) · ADR-0086(control plane token) · ADR-0004(isolating backend knowledge) · ADR-0083(profile corpse preservation) · `crates/engram-dashboard-agent/src/backend/codex/mod.rs:169-171` · `crates/engram-dashboard-daemon/src/control/hook.rs` · `crates/engram-dashboard-agent/src/profile.rs:780` · step-log S21 · Amended by ADR-0210 (hook registration boundary and merging of hook diagnostics) · Amended by ADR-0216 (replaces the hook retrieval path and the adopt empty-slot policy)

## 맥락

When codex is launched in terminal mode, the conversation does not continue after a restart. The cause is the issuer — codex itself issues the identifier needed to resume (ADR-0185), and the terminal path has no channel through which it can tell us that value. app-server mode receives it in the `thread/start` response, so it has few channels to worry about (ADR-0189), but terminal mode has no such round trip.

So the question to ask is 「그 번호를 어떻게 알아내나」 (how do we find out that number). The survey concluded that ★the dangerous thing is not the technique but 「못 찾았을 때 하나 고르는 tie-break」 (a tie-break that picks one when nothing was found)★ — the moment something like `가장 최근 mtime` (most recent mtime) or `첫 매치` (first match) is attached, that technique **converts not-found into wrong-found**, and that conversion is entirely silent. The worst-case scenario, in which a new conversation is reported as 「이어받음」 (resumed), arises only through exactly this path.

There are only two techniques that **do not invent** a value from ambiguous evidence, and both are **propagation**, not inference: ① the supervisor issues the id in advance and injects it (the claude way) ② the supervisor plants a correlation token in env and the child's hook carries it and sends it back. ① cannot be used because codex has no such flag (see 「거부한 대안」 below). What remains is ②.

★**But ② does not eliminate misattribution — this ADR fixes that limit in place, having accepted it**★. The planted token is the **per-agent control plane token** (ADR-0086), and since env is automatically inherited by all children, the hook of a **sub-agent** launched by the agent reports with **the same token, byte for byte**. There is no means to tell the two apart. The canonical source for the threat model and the defenses that do not exist is the header of `crates/engram-dashboard-daemon/src/control/hook.rs` (roughly lines 14 to 37), and we do not unfold it here again — what this ADR carries is 「그래서 무엇을 수용했나」 (so what did we accept) (see 「영향 / 불변식」 below).

## 결정

**Retrieval path = codex's `SessionStart` hook reports to us, and correlation is carried by the env token the supervisor planted (`ENGRAM_TOKEN`).** Measured basis = ★codex injects none of its own env into the hook process — it is pure inheritance★. So the planted token arrives as it is. The four items below are the mechanism that hangs off that one decision and must not be read detached from it.

1. **The `/control/hook` route — identity is the existing bearer middleware alone, and a report from 「자기 세션 id 를 스스로 발급하는 백엔드」 (a backend that issues its own session id) is rejected.** The envelope has no "who" field (if it did, any descendant that inherited env could report under another's name — ADR-0086 「from 은 토큰에서만 파생」, "from is derived only from the token"). ★The eligibility decision comes **before** the value decision★ — if reversed, an ineligible call would get a different answer depending on the result of uuid parsing, and that axis could be probed from outside. The axis that separates eligibility is **not the backend name but a predicate** (`SessionStartRecorder::assigns_own_session_id`) — claude is rejected because that predicate is true, and the route code has no branch on backend names (ADR-0004).

2. **`adopt_session_id` — writes only into an empty slot, and rejects when a different value is present (it does not overwrite).** The sibling `observe_session_id`, which the channel uses, keeps overwriting as it is, so **the app-server channel always wins** — that one is 「우리 통로가 상대에게서 직접 받아 온 값」 (a value our channel received directly from the other side), so overwriting is right, while this one is 「상대가 대신 띄운 다른 프로세스가 보고한 값」 (a value reported by a different process the other side launched on its behalf), and there is no means to confirm that the process really is this agent. ★What is blocked is only 「이미 찬 칸」 (a slot that is already filled), and 「먼저 온 것이 이긴다」 (first come wins) has not been removed★ — the empty-slot branch is exactly first-wins and that is the known limit. If a sub-agent's hook inherits the same token and arrives first, that value sits there. There is no axis today to tell lineage apart (the 7 hook payload fields have no such field — measured).

3. **The `engram hook session-start` CLI — exit 0 on every branch, and not one character to stdout.** The hook is a **child** of codex, and we have never measured how that program handles an abnormal exit of a hook (implementations that stop startup do exist). Having the user's conversation fail to appear because one report failed is far more expensive than the value of that report. ★If the first token is of this family, **even a parse rejection** ends with that code★ — if only that branch fell out with exit 1, the contract would be half a contract. The reason for sealing stdout is separate: there are implementations that read a hook's stdout and inject it into the session (measured on the claude family), and if our envelope leaked into model input that would be a worse accident. stdin is **cut at 64 KiB and the run continues** — if the cut breaks the JSON, it sends an empty value and the daemon records that fact. If we stopped here, that event would be recorded nowhere (since stdout and the exit code are both sealed).

4. **A Fresh spawn returns that slot — but the decision also requires 「이 화신에 그 칸을 채울 경로가 있나」 (is there a path to fill that slot in this incarnation).** Without the return, a backend whose issuance axis is off opens a new conversation for every incarnation while the slot stays filled with the first incarnation's value, so from the 2nd round on every report is rejected as 「이미 다른 값이 있다」 (a different value is already there). That rejection log is the **only after-the-fact means of telling nested accidents apart**, so if it is printed at every normal restart the signal becomes noise. ★Do not use `assigns_session_id == false` alone as the decision★ — shell falls under that condition and breaks the ADR-0083 regression (`crates/engram-dashboard-agent/tests/activation.rs`). The third term prevents that.

Turning on `supports_control_channel` for codex is also a consequence that hangs off this decision — the assembly point skips provision on that slot, so if it is off, `ENGRAM_TOKEN` and `ENGRAM_CONTROL_URL` disappear wholesale from the codex spawn env. Together with that, we moved the CLI-entrance injection (`inject_cli_entrance`) from the claude folder to the shared place in `backend/mod.rs` — because those three (three env values + PATH prepend) contain no backend knowledge at all (ADR-0004). **Translation** such as `--mcp-config` is that program's grammar, so it stays in the claude folder.

## 거부한 대안

- **Read the rollout JSONL / `state_5.sqlite` and pick the 「가장 최근」 (most recent)** — it silently turns not-found into wrong-found. Precedent shows that ending (octoally unconditionally adopts the first match · zero verification). The standards-side basis is head-on as well — RFC 9413 (IAB, Maintaining Robust Protocols) rejects the interpretation of 「모호한 입력을 추론된 의도로 처리하라」 (handle ambiguous input as inferred intent). On top of that, that storage format is **mid-migration** (measured: `threads.history_mode` mixes legacy/paginated · `codex migrate-rollouts` exists) — if we read the files directly, we get bitten by that migration.
- **The supervisor issues the id in advance and injects it (the claude way)** — codex has **no** such flag (measured, confirmed twice independently). If we turned it on, the manager would issue our uuid and persist it in the profile, but codex never uses that value even once, and after that the resume decision would stand on that fake value. This is the spot that ADR-0185 nailed down with `assigns_session_id=false`.
- **Output / TUI scraping** — of the three peers, only octoally does it. It is first match · zero verification, and **it even bolted on a file-search fallback** — a confession that scraping alone was not enough.
- **Use the profile's parent lineage for correlation** — that parent is **conceptual and is not physically connected** (user confirmed 2026-09-18). And even if it were physical, it could not be used: among the 7 hook payload fields (`session_id`·`transcript_path`·`cwd`·`hook_event_name`·`model`·`permission_mode`·`source`) there is not a single field that speaks of lineage (measured).
- **Receive hook reports only on the app-server (JSON) path** — ★**the user chose the path shared by both modes**★ (「통일성이 중요하니 훅 시스템이 공용이면 공용으로 받아라」, "uniformity matters, so if the hook system is shared, receive through the shared path", 2026-09-18). ★This item is not a technical rejection but a user decision★: the assistant **gave a dissenting opinion** — 「JSON 모드는 이미 튼튼한데 약한 길로 바꾸는 것」 (JSON mode is already robust, and this is switching to a weaker road) — **and the user reconfirmed.** We record its price together here — ① granting hook trust becomes **mandatory** (if it is not recorded, both modes lose resume) ② the behavior of a 「번호를 못 받은 세션」 (session that did not receive a number) has to be defined (switching the decision predicate is the answer — see 「영향」 below).
- **Copy herdr's `CODEX_THREAD_ID` nesting guard** — that variable **does not exist in codex-cli 0.155.0** (0 hits in all strings of the binary — measured). If copied, it would always read as unset and the guard would separate nothing.
- **Compute the hook trust hash ourselves** — reproduction is possible (sha256 of normalized JSON), but **the precedent (orca) broke on every codex release, abandoned its own computation, and switched to the app-server RPC path.** We skip that trial and error.

## 영향 / 불변식

- ★**The two decision predicates are flipped only as a pair**★ — `can_resume_stored_session` (`crates/engram-dashboard-agent/src/backend/codex/mod.rs:174`) and `capabilities().session.resume` (same file `:391`). That warning is embedded in the code (`:169-171` and its counterpart `:381-383`). If only one is turned on, **a new conversation that was never resumed is reported as 「이어받음」 (resumed)**, and if only one is turned off, a spawn that actually resumes is reported as a 「새 대화」 (new conversation).
- ★**Hook registration and trust granting are stage 2 — so `/control/hook`, `engram hook session-start` and their tests are unreachable in production today**★. The number of lines in the repository that plant `SessionStart` is 0. **This is not unfinished but an intended boundary** — we set up the receiving endpoint first and put the hooking-up part later. If there is no trust, the hook is ★skipped in complete silence★ (no error, no prompt, no log, exit code 0 — measured).
- **Two known residual holes (both are carried by this decision):**
  - **The daemon's actual rejections (`Conflict`·`NotEligible`·`Unreadable`) are all HTTP 200** (the route contract = 「항상 200 + JSON」 (always 200 + JSON), `control_hook_handler` in `crates/engram-dashboard-daemon/src/control/mcp_server.rs`). So they fall under the CLI's `(200..300)` success decision and the `daemon refused the report` diagnostic **never appears even once** (`run_hook` in `crates/engram-dashboard-daemon/src/bin/engram.rs`). What that 2xx gate actually catches is **401 only** — transport-layer failures (missing credentials · connection failure · response parse failure) do not go through that gate but fall to a **sibling error branch**. Since the two merge into the same one-line diagnostic, **the operational conclusion is the same and only the mechanism differs.**
  - **The third term of the Fresh-return decision is a hand-maintained enumeration** — `supports_control_channel || declares_link` (`crates/engram-dashboard-agent/src/manager.rs:465-469`). If a third reporting path appears, it has to be added here, and if it is not, only that backend is silently rejected from the 2nd-round incarnation on. **The compiler cannot catch it** — there is no slot that declares the true axis (「상대가 우리에게 id 를 말할 수 있나」 (can the other side tell us the id?)).
- ★**Accepted limit: this path prevents misattribution only by half — do not trust a defense that does not exist**★. What is blocked is only a report that arrives **after the slot is already filled**, and **while the slot is empty, whoever arrives first wins** — if a sub-session's hook arrives before the parent's, the child's value sits there and the parent is rejected afterward. Because there is no means to tell them apart (same token · same env · no lineage field in the payload). ★That empty-slot window opens **once per incarnation** — because the Fresh return empties that slot, and that is a **conscious choice**★: if we cut the window to once, **a rejection log would be printed at every normal restart** from the 2nd-round incarnation on, burying a real nesting accident (that log is the only after-the-fact means of telling it apart — decision 4 above). Of the two, we chose the side that keeps the signal alive. App-server mode practically has no such window (the channel sink always fills in the same value first — measurement ④ above). **The canonical description of the threat model and the defenses that do not exist = the header of `crates/engram-dashboard-daemon/src/control/hook.rs`**, and this ADR only points to it.
- **`old_session_ids` has no ceiling, and one more growth path was added** (one per incarnation for codex terminal). It has the same root as the existing open item.
