# ADR-0057: Tab ownership model — per-window tabs + unique ownership (owner-index hybrid)

- 상태: 확정 (2026-07-09, basis: PRD/TRD B-tabs + `/research` OSS survey + `/review prd` and `/review trd deep` adversarial verification + user decision)
- 관련: Amends ADR-0035 (ViewManager internal model: global active_view_id (main-only) + window_bindings → per-window active + view_owner/windows tab ownership) · ADR-0056 (tab rendering keep-alive — the higher-level ground for the routing "receive all tabs") · ADR-0046 (view-direct replay · routing is label-agnostic) · ADR-0006 (lock order) · ADR-0055 (command registry — where tab commands register) · `docs/process/B-wezterm-tabs/PRD.md`·`TRD.md` · step-log B-tabs

## 맥락
Of the WezTerm-style three layers **window (popup) → tab (= `View` in code) → slot (split pane)**, "window" and "slot" work, but the layer between them, **"per-window tabs"**, is missing. The current `ViewManager` = one global `active_view_id` (main only) + `window_bindings` (binds an auxiliary/popup window to one fixed View). That is, with **one global active view + popup = a fixed view**, there is no concept at all of "a window has a tab list and switches within it". Before entering layout B Phase 1 (tabs), we must settle **where and how tabs are owned** (a coarse-grained design → ADR).

## 결정
**D-1 = option C (owner-index hybrid).** Change the inside of `ViewManager` to the following:
- `views: HashMap<ViewId, View>` — the global View pool (id lookup).
- `view_owner: HashMap<ViewId, WindowLabel>` — View → owning window (**unique ownership enforced**, a cached reverse index).
- `windows: HashMap<WindowLabel, WindowTabs { tabs: Vec<ViewId>, active: ViewId }>` — per-window tab list + that window's active tab.

**Main is also an ordinary window with no special treatment** (D-2 — remove the global `active_view_id`, unify as `windows["main"]`). **A View belongs to exactly one tab of exactly one window (unique ownership).** `ViewId` is a global UUID so that follow-ups (moving between windows, save/restore) can be layered on. Window close rule (D-3): main always has at least 1 tab (non-closable), and a popup window closes too when its last tab is closed — in both cases **the agent (daemon process) survives** (§5 hands/brain split).

## 거부한 대안
- **A — per-window ownership (ref-list = ownership):** each window has only `{ tabs: Vec<ViewId>, active }` and the tabs Vec doubles as ownership. It is a literal translation of WezTerm (MuxWindow owns the tab list) and so valid, but **pretending "the ref-list is ownership" blurs the concept and cannot enforce unique ownership by type** (a View appearing in two windows' tabs is prevented only by a runtime assert). C pins **unique ownership as a type-level invariant** (exactly 1 window per View) with the separate `view_owner` map, and also gives an **O(1) reverse lookup** of the owning window for view-id-keyed commands (`assign_agent`/`split_slot`/`close_slot`). (The recommendation was raised from A to C on a Codex `/review prd` suggestion.)
- **B — global pool + mapping (shared tabs):** `tabs: HashMap<TabId, Tab>` + `windows: { tab_ids, active }`. Advantageous for "showing the same tab in two windows at once" and workspace switching, but **GC and syncing in two places are complex**. That sharing requirement is **not in the current use cases**, so it is over-engineering (not low risk — room for sync defects). Since `ViewId` is a global UUID, if it ever becomes truly necessary, B/moving between windows can be extended gradually later.

## 근거
- **OSS survey (`/research`):** WezTerm (a global mux registry + MuxWindow owns the tab list, window↔tab 1:1) · VS Code (EditorGroup owned per window, strictly per-window) · tmux (the server owns everything, M:N sharing) · zellij (Screen holds tabs in a BTreeMap, active is per client). **Per-window tab ownership + a global UUID tab ID** is the model proven by WezTerm and VS Code, and since there is no advanced sharing requirement, global-pool complexity is unnecessary.
- **Adversarial verification:** in `/review prd` (User lens Opus + Tester lens Codex), the need to settle the ownership invariant (one View = one window) was raised and option C (unique ownership enforced by type) was proposed → the recommendation was raised. In `/review trd deep` (3 reviewers: Designer blind = Codex · Architect-breaker + migration/concurrency specialist = Opus doc-aware) and the re-review, the spec gaps on migration, routing reversal, concurrency rollback and multi-tab cleanup leaks passed after the FIXes were applied.

## 영향 / 불변식
- **ADR-0035 partially amended:** the inside of `ViewManager` `(views · active_view_id · window_bindings)` → `(views · view_owner · windows)`. **The global `active_view_id` is removed** (replaced by per-window active). The **core of ADR-0035 is unchanged** (layout authority = src-tauri · the daemon is UI-agnostic · JS is a pure renderer · lock-after-emit).
- **Routing:** in `output_router.rs`, the allowance for "one View routed to two windows at once (active-main + a binding)" is removed → unique ownership. Rebuild walks **all tabs of each window** (active + hidden) for routing (derived from ADR-0056 keep-alive — hidden tabs also receive and switching is lossless). The subscription delta keeps ADR-0046 (the wire only does Unsubscribe on 1→0, and Subscribe is `request_replay` alone).
- **Invariants (`// ADR-0057` anchors in code):** ① two-way consistency `view_owner[v]==L ⟺ windows[L].tabs ∋ v` ② unique ownership (one owner per View) ③ `windows[L].active ∈ windows[L].tabs` ④ main has at least 1 tab + is non-closable (`close_window("main")` forbidden) ⑤ multiple agent references allowed (the same `agent_id` can be assigned to two Views → two windows see the same agent, with independent progress, ADR-0046 — a different matter from the "one View in two windows" ban (invariant ②)).
- **Ownership updates always as a pair** — never update `windows[L].tabs` ↔ `view_owner[v]` separately (breaks invariant ①). Detailed implementation, migration, command surface and the concurrency contract = TRD B-tabs.
- **Follow-up (out of scope):** moving tabs between windows (D-4) · save/restore of tab/window placement (D-5) — only room to extend through the global-UUID `ViewId` is secured.
