# ADR-0322: Emptying the trash and permanent deletion are human-only — a shell-only bus command · whole bundles to the OS trash · permanent deletion only when it is confirmed that there is no trash

- 상태: 제안 (2026-10-31, basis: user decisions F9 / B8 (2026-10-19 「휴지통으로 가되 휴지통 비우기를 llm으로 쏘지 못하게 막자는거지」) · G9 · G11 · G12 (2026-10-20) · G21 (2026-10-29) · P13 · G44 (2026-10-31 「괜찮은데」) · G45 (2026-10-31 「열려있음 지우지 않고, 휴지통이 없으면 영구 삭제」) + main M6 · M24-7 · M26 · M46 · M47 · M50 · M52 · M53 · M55 · M57 · M59 (reported) · research `docs/research/junction-recycle-bin-atomic-write-2026-10-31.md`) · 부분 폐기 by ADR-0326 (title and Decisions 5, 6 and 7)
- 관련: ADR-0320 (delete = a `.trash` bundle) · S25 draft Q (unnumbered — webview → daemon bus round trip) · ADR-0324 (trash lock · hand-over) · CLAUDE.md 「LLM-우선 제어」 · 「플랫폼 중립」 · PRD R18 · TRD `docs/process/S25-preset-library/trd.md` §1-4 `store.rs` · flow ④ · §1-6 OS trash row · §1-7 `library.emptyTrash` · §1-11a scenario 10 · finding 17 · §6-2 · §6-5 2 · 5 · §7 28 · Amended by ADR-0326 (title and Decisions 5, 6 and 7)

## 맥락
A delete goes to a `.trash` bundle and can be restored (ADR-0320). Emptying and permanent deletion cannot be undone — if an agent calls them by mistake, we lose data. Also, on Windows, sending to the trash may delete instead of using the trash, or fail, depending on the volume and the file state.

## 결정
1. Emptying the trash and permanent deletion are done only by humans — the shell-only bus command `library.emptyTrash {items?}`. The daemon rejects anything that comes in through the control route. It is not in the agent command table, the priming or `engram help`. There is no new wire variant (M6 · M26).
2. We do not add an exception list or mechanism to the principle 「LLM-우선 제어」. We accept that the LLM bypasses it through outside tools (WS · `rm`) (G21 · P13).
3. Delete (→ `.trash`) · viewing the trash · restore (`library.restore`) are also done by the LLM and the CLI (G11). No other `library.*` can point under `.trash`.
4. **Emptying = send to the OS trash of the daemon PC.** Empty everything = send the bundle folder `<UTC>-<id>` as a whole — in the OS trash each bundle becomes one entry (a folder that holds the original path) and the result is also per bundle (G44 · M52). `items` = only the entries given for that bundle. If sending a bundle as a whole fails, the **remaining** entries of that bundle are sent again one by one so that one open or locked file blocks only itself, and the result for that bundle is carried per entry (M55).
5. **Separating send failures** (G45 · M59): permanent deletion is done **only on codes that are confirmed** as 「이 볼륨엔 휴지통이 없다 · 꺼져 있다」. In use · access denied · too large · **all unknown codes are not deleted but left in `.trash`**, and the original HRESULT is reported per entry. This separation is also what the confirmation modal says in advance (the 「안 되면 지움」 of G12 = only when there is no trash).
6. **OS trash call = platform calls `IFileOperation` directly** (M57) — `FOFX_RECYCLEONDELETE` + a progress sink (per-entry results through `PreDeleteItem` · `PostDeleteItem`). On `PreDeleteItem` there is a guard that cancels if the 「가능하면 휴지통」 marker (`TSF_DELETE_RECYCLE_IF_POSSIBLE`) is absent — the same guard as Electron and Qt, but **not verified**, so it is measured in the pilot (M59). The OS split is inside one platform function (「플랫폼 중립」).
7. **Emptying takes neither the library lock nor a ticket** — `.trash` is outside `Catalog`. The bundle list is copied aside once under the trash lock (bundles created after that are not touched · an entry restored away before its turn is simply absent for empty-all, and for `items` that entry `NOT_FOUND` · even if `setRoot` intervenes in the meantime, it continues with the path of the root copied aside), the trash lock is taken and released per bundle, and it is handed over to the moves and restores that wait — shape = ADR-0324 Decision 9 (M46 · M47 · M50 · M52 · M53).
8. It does not empty automatically (G11). The human screen = 「🗑 휴지통」 at the very bottom of the left area → view the trash (G9).

## 거부한 대안
- **Emptying in the agent command table (`engram`)** — the LLM could delete permanently (§7 28).
- **Adding a mechanism or exception list to the human-only guard** — user 2026-10-29 (G21 — the LLM can always bypass through outside tools).
- **Writing it as the 「의도된 예외」 of a CLAUDE.md principle** (the old F9 · R18 frame) — G21 · M24-7 withdrew it.
- **Making deletion itself human-only** — LLM and CLI deletes go to `.trash` and can be restored, so there is no reason to block them (user — F9).
- **Automatic emptying such as after 30 days** (practice — Notion · Apple Photos) — user 「일단 유저가 비우게 나중에 필요하면 추가하고」 (G11 — a later thought).
- **Putting the trash entrance inside the 「…」 menu** — no peer that keeps it only inside a menu was found (G9).
- **Not opening restore on the bus** (main's proposal of 2026-10-19) — there is no harm, so we open it (G11).
- **Permanently deleting anything if sending fails** (the first reading of G12 — also deleting on in-use and permission failures) — user 「열려있음 지우지 않고, 휴지통이 없으면 영구 삭제」 (G45 · TRD §6-5 open item 5 closed).
- **Splitting by three HRESULTs (no trash `0x8027003A` · in use `0x80070020` · denied `0x80070005`) and permanently deleting if 「없음」** (the first shape of M57) — the codes do not split cleanly: `0x8027003A` is 「휴지통을 찾지 못했거나 쓸 수 없음」, and volumes with recycling off, items too large and sharing violations each have their own code variants → narrowed to permanently deleting only on confirmed codes and leaving the rest (M59 · research — codex review).
- **Checking 「휴지통을 쓸 수 있나」 in advance before sending** — there is no means to trust (`SHQueryRecycleBinW` sees only the content · `GetDriveType` is only for filtering — a USB looks like a fixed disk, and a redirected network folder may also have a trash) (M59 · research).
- **The `trash` crate 5.2.9** (MIT) — there is no per-entry report (it bundles `DeleteItem` into one `PerformOperations` call) · no `FOFX_RECYCLEONDELETE` · `FOFX_EARLYFAILURE` (even if it fails after deleting part, it reports as one lump) · `FOF_WANTNUKEWARNING` + `FOF_NO_UI` behavior is unclear in a windowless daemon · a per-thread STA `CoInitializeEx` panics at `RPC_E_CHANGED_MODE` · a third `windows` copy (0.62) (M57 · research). ★The 「실패가 전부 `Error::Unknown`」 of M57 was fixed by the research review — a failure is `Error::Os{code}` and only 「성공했는데 취소됨」 is Unknown★ — the remaining ground for rejection is that there is no per-entry report.
- **Emptying holds the library write lock and the trash lock throughout · retaking per bundle without hand-over** — the lock-side rejection = ADR-0324 (M46 · M47 · M50).

## 근거
- Reason = if an agent deletes by mistake, we leave it restorable (F9 · user 2026-10-19).
- G12 「휴지통 비우면 윈도우 휴지통으로 보내고 안되면 그냥 삭제되게」 · G11 「일단 유저가 비우게 나중에 필요하면 추가하고. 윈도우 휴지통 생각하면됨」 · G44 · G45.
- Research junction-recycle-bin (medium · codex review FIX): `IFileOperation` directly = likely · the key assumption (the guard reveals in advance what it cannot send) is not verified — that marker is only 「가능하면 휴지통」, not proof · `PerformOperations` can return success even after cancel, so `GetAnyOperationsAborted` is also checked · `FOFX_EARLYFAILURE` does not undo entries it already finished.

## 영향 / 불변식
- Windows may silently fall back to permanent deletion, so we cannot always know what happened — that is why we speak before, not after (G12). How much the guard and per-entry results close that gap is measured by the pilot.
- **Pilot measurement (M57 · M59 · research)**: on volumes without a trash (FAT32 USB) · volumes with recycling off · items too large · removable · network: the `PreDeleteItem` marker · `hrDelete` · `psiNewlyCreated` · `GetAnyOperationsAborted` · the list of 「확정된 휴지통 없음 코드」 · whether `FOF_ALLOWUNDO` is needed · whether sending a bundle folder holding an open file as a whole moves only part and returns the failure (M52 · M55 — sending again per entry relies on that failure return · TRD §6-2).
- Cost: the `Win32_UI_Shell` feature of `windows` + a COM implement macro + a dedicated STA thread (inside platform — research).
- A delete or restore that arrives during emptying waits only while one bundle is being sent (ADR-0324). If even one bundle is long, the next step = move the copied-aside bundles into a hidden folder inside `.trash` and then send without a lock (only when measurement calls for it — finding 17 · M47).
- A change that puts emptying on the LLM surface (command table, priming, help) reopens this decision. Widening the separation of permanent deletion (also deleting on in-use and denied) reopens G45.
