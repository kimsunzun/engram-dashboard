# ADR-0322: 휴지통 비우기 · 영구 삭제는 사람만 — 셸 전용 버스 명령 · OS 휴지통엔 묶음째 · 영구 삭제는 휴지통이 없다고 확정될 때만

- 상태: 제안 (2026-10-31, 근거: 사용자 결정 F9 / B8(2026-10-19 「휴지통으로 가되 휴지통 비우기를 llm으로 쏘지 못하게 막자는거지」) · G9 · G11 · G12(2026-10-20) · G21(2026-10-29) · P13 · G44(2026-10-31 「괜찮은데」) · G45(2026-10-31 「열려있음 지우지 않고, 휴지통이 없으면 영구 삭제」) + 메인 M6 · M24-7 · M26 · M46 · M47 · M50 · M52 · M53 · M55 · M57 · M59(보고) · 조사 `docs/research/junction-recycle-bin-atomic-write-2026-10-31.md`)
- 관련: ADR-0320(삭제 = `.trash` 묶음) · S25 초안 Q(미채번 — 웹뷰 → 데몬 버스 왕복) · ADR-0324(휴지통 잠금 · 넘겨주기) · CLAUDE.md 「LLM-우선 제어」 · 「플랫폼 중립」 · PRD R18 · TRD `docs/process/S25-preset-library/trd.md` §1-4 `store.rs` · 흐름 ④ · §1-6 OS 휴지통 행 · §1-7 `library.emptyTrash` · §1-11a 시나리오 10 · 발견 17 · §6-2 · §6-5 2 · 5 · §7 28

## 맥락
삭제는 `.trash` 묶음으로 가서 되살릴 수 있다(ADR-0320). 비우기 · 영구 삭제는 되돌릴 수 없다 — 에이전트가 잘못 부르면 잃는다. 또 Windows 휴지통 보내기는 볼륨 · 파일 상태에 따라 휴지통 대신 지우거나 실패한다.

## 결정
1. 휴지통 비우기 · 영구 삭제는 사람만 한다 — 셸 전용 버스 명령 `library.emptyTrash {items?}`. 데몬은 제어 라우트로 온 것을 거절한다. 에이전트 명령 표 · 프라이밍 · `engram help` 에 없다. 새 wire 변형이 없다(M6 · M26).
2. 원칙 「LLM-우선 제어」 에 예외 목록 · 장치를 더하지 않는다. LLM 이 바깥 도구(WS · `rm`)로 우회하는 것은 받아들인다(G21 · P13).
3. 삭제(→ `.trash`) · 휴지통 보기 · 되살리기(`library.restore`)는 LLM · CLI 도 한다(G11). 그 밖의 `library.*` 는 `.trash` 아래를 가리키지 못한다.
4. **비우기 = 데몬 PC 의 OS 휴지통으로 보낸다.** 전부 비우기 = 묶음 폴더 `<UTC>-<id>` 를 통째로 보낸다 — OS 휴지통엔 묶음마다 한 항목(원래 경로를 품은 폴더)이 들고 결과도 묶음마다다(G44 · M52). `items` = 그 묶음의 준 항목만. 묶음 통째 보내기가 실패하면 그 묶음에 **남은 것**을 항목마다 다시 보내 열린 · 잠긴 파일 하나가 저만 걸리게 하고, 그 묶음 결과는 항목마다 싣는다(M55).
5. **보내기 실패의 가름**(G45 · M59): 영구 삭제는 「이 볼륨엔 휴지통이 없다 · 꺼져 있다」 로 **확정되는 코드에서만** 한다. 쓰는 중 · 접근 거부 · 너무 큼 · **알 수 없는 코드는 전부 지우지 않고 `.trash` 에 남기고** 항목마다 원 HRESULT 를 알린다. 확인 모달이 미리 말하는 것도 이 가름이다(G12 의 「안 되면 지움」 = 휴지통이 없을 때만).
6. **OS 휴지통 호출 = platform 이 `IFileOperation` 을 직접 부른다**(M57) — `FOFX_RECYCLEONDELETE` + 진행 sink(`PreDeleteItem` · `PostDeleteItem` 으로 항목마다 결과). `PreDeleteItem` 에서 「가능하면 휴지통」 표식(`TSF_DELETE_RECYCLE_IF_POSSIBLE`)이 없으면 취소하는 가드를 둔다 — Electron · Qt 와 같은 가드이나 **미검**이라 파일럿에서 잰다(M59). OS 갈림은 platform 함수 하나 안(「플랫폼 중립」).
7. **비우기는 라이브러리 락도 번호표도 잡지 않는다** — `.trash` 는 `Catalog` 밖이다. 묶음 목록은 휴지통 잠금 아래 한 번 떠 두고(그 뒤 생긴 묶음은 건드리지 않는다 · 차례 전에 되살려 나간 항목은 전부 비우기면 그냥 없고 `items` 면 그 항목 `NOT_FOUND` · 그 사이 `setRoot` 가 끼어도 떠 둔 루트의 경로로 계속), 휴지통 잠금을 묶음마다 잡고 놓으며 기다리는 옮기기 · 되살리기에 넘겨준다 — 꼴 = ADR-0324 결정 9(M46 · M47 · M50 · M52 · M53).
8. 저절로 비우지 않는다(G11). 사람 화면 = 왼쪽 칸 맨 아래 「🗑 휴지통」 → 휴지통 보기(G9).

## 거부한 대안
- **비우기를 에이전트 명령 표(`engram`)에** — LLM 이 영구 삭제할 수 있다(§7 28).
- **사람만 가드에 장치 · 예외 목록을 더하기** — 사용자 2026-10-29(G21 — LLM 은 바깥 도구로 늘 우회할 수 있다).
- **CLAUDE.md 원칙의 「의도된 예외」 로 적기**(옛 F9 · R18 틀) — G21 · M24-7 이 걷었다.
- **삭제 자체를 사람만** — LLM · CLI 삭제는 `.trash` 로 가서 되살릴 수 있으므로 막을 까닭이 없다(사용자 — F9).
- **30일 같은 자동 비우기**(관행 — Notion · Apple 사진) — 사용자 「일단 유저가 비우게 나중에 필요하면 추가하고」(G11 — 나중 생각).
- **휴지통 입구를 「…」 메뉴 안에** — 메뉴 안에만 둔 피어를 못 찾았다(G9).
- **되살리기를 버스에 열지 않기**(2026-10-19 메인 제안) — 해가 없어 연다(G11).
- **보내기가 안 되면 무엇이든 영구 삭제**(G12 의 처음 읽기 — 쓰는 중 · 권한 실패도 지움) — 사용자 「열려있음 지우지 않고, 휴지통이 없으면 영구 삭제」(G45 · TRD §6-5 미결 5 닫힘).
- **세 HRESULT(휴지통 없음 `0x8027003A` · 쓰는 중 `0x80070020` · 거부 `0x80070005`)로 갈라 「없음」 이면 영구 삭제**(M57 의 첫 꼴) — 코드가 깨끗이 갈리지 않는다: `0x8027003A` 는 「휴지통을 찾지 못했거나 쓸 수 없음」 이고 재활용이 꺼진 볼륨 · 너무 큰 항목 · 공유 위반은 각자 다른 코드 변종이 있다 → 확정된 코드만 영구 삭제 · 나머지는 남김으로 좁혔다(M59 · 조사 — codex 리뷰).
- **보내기 전에 「휴지통을 쓸 수 있나」 미리 확인** — 믿을 수단이 없다(`SHQueryRecycleBinW` 는 내용만 본다 · `GetDriveType` 은 거르기용일 뿐 — USB 가 고정 디스크로 보이고 리디렉션 네트워크 폴더에도 휴지통이 있을 수 있다)(M59 · 조사).
- **`trash` crate 5.2.9**(MIT) — 항목마다 보고가 없다(`DeleteItem` 을 묶어 `PerformOperations` 한 번) · `FOFX_RECYCLEONDELETE` · `FOFX_EARLYFAILURE` 가 없다(일부 지운 채 실패해도 한 덩어리 보고) · 무창 데몬에서 `FOF_WANTNUKEWARNING` + `FOF_NO_UI` 동작 불명 · 스레드마다 STA `CoInitializeEx` 가 `RPC_E_CHANGED_MODE` 에서 패닉 · 셋째 `windows` 사본(0.62)(M57 · 조사). ★M57 의 「실패가 전부 `Error::Unknown`」 은 조사 리뷰가 고쳤다 — 실패는 `Error::Os{code}` 이고 「성공했는데 취소됨」 만 Unknown 이다★ — 거부의 남은 근거는 항목마다 보고가 없다는 것이다.
- **비우기가 라이브러리 쓰기 잠금 · 휴지통 잠금을 내내 쥠 · 넘겨주기 없이 묶음마다 다시 잡기** — 잠금 쪽 거부 = ADR-0324(M46 · M47 · M50).

## 근거
- 이유 = 에이전트가 잘못 지워도 되살릴 수 있게 남긴다(F9 · 사용자 2026-10-19).
- G12 「휴지통 비우면 윈도우 휴지통으로 보내고 안되면 그냥 삭제되게」 · G11 「일단 유저가 비우게 나중에 필요하면 추가하고. 윈도우 휴지통 생각하면됨」 · G44 · G45.
- 조사 junction-recycle-bin(medium · codex 리뷰 FIX): `IFileOperation` 직접 = 가능성 높음 · 핵심 가정(가드가 못 보내는 것을 미리 드러낸다)은 미검 — 그 표식은 「가능하면 휴지통」 일 뿐 증명이 아니다 · `PerformOperations` 는 취소 뒤에도 성공을 돌릴 수 있어 `GetAnyOperationsAborted` 도 본다 · `FOFX_EARLYFAILURE` 는 이미 끝낸 항목을 되돌리지 않는다.

## 영향 / 불변식
- Windows 는 말없이 영구 삭제로 물러날 수 있어 무엇이 일어났는지 늘 알 수는 없다 — 그래서 뒤가 아니라 앞에 말한다(G12). 가드 · 항목별 결과가 그 틈을 얼마나 막는지는 파일럿이 잰다.
- **파일럿 실측(M57 · M59 · 조사)**: 휴지통 없는 볼륨(FAT32 USB) · 재활용 꺼진 볼륨 · 너무 큰 항목 · 이동식 · 네트워크에서 `PreDeleteItem` 표식 · `hrDelete` · `psiNewlyCreated` · `GetAnyOperationsAborted` · 「확정된 휴지통 없음 코드」 의 목록 · `FOF_ALLOWUNDO` 필요 여부 · 열린 파일이 든 묶음 폴더를 통째로 보낼 때 일부만 옮기고 실패를 돌려주는지(M52 · M55 — 항목마다 다시 보내기가 그 실패 반환에 기댄다 · TRD §6-2).
- 비용: `windows` 의 `Win32_UI_Shell` feature + COM implement 매크로 + 전용 STA 스레드(platform 안 — 조사).
- 비우는 도중 온 삭제 · 되살리기는 묶음 하나 보내는 동안만 기다린다(ADR-0324). 묶음 하나도 길면 다음 걸음 = 떠 둔 묶음을 `.trash` 안 숨은 폴더로 옮긴 뒤 락 없이 보내기(실측이 부를 때만 — 발견 17 · M47).
- 비우기를 LLM 표면(명령 표 · 프라이밍 · help)에 올리는 변경은 이 결정을 다시 연다. 영구 삭제의 가름을 넓히면(쓰는 중 · 거부도 지움) G45 를 다시 연다.
