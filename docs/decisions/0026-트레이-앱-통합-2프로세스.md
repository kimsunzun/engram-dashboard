# ADR-0026: Tray/process topology re-decided — merge the tray into the Tauri app (2 processes), daemon separate (discards ADR-0023)

- 상태: 확정 (2026-06-19, dashboard9 session — user decision + `/consult` three-way cross-check job `20260619-215927-consult-tray-app-merge`) · 부분 폐기 by ADR-0229 (only the target-window scope that X and show/hide cover)
- 관련: ADR-0023 (discarded, replaced by this ADR — Supersedes ADR-0023) · ADR-0024 (daemon ownership and exit — this ADR reaffirms the invariants) · ADR-0022 (unified command registry) · ADR-0025 (boot daemon ensure) · ADR-0013 (tmux reference) · CLAUDE.md §5 (LLM control) · `docs/process/step-log.md` dashboard9 · Amended by ADR-0229 (only the target-window scope that X and show/hide cover)
- Scope: in daemon mode, how to split the tray, UI, and daemon into processes. It reverses ADR-0023's "3 processes (a separate pure-Rust tray)" decision.

## 맥락
ADR-0023 split the tray into a **separate pure-Rust process** (tray / Tauri UI / daemon = 3 processes). The **only justification** for the split was "keep a login-resident tray always up without the WebView memory (~150MB)."

While implementing S13 sub-step 2 and designing "tray → open/close the UI window," it became clear that for a separate tray process to control a window of a separate UI process, **cross-process IPC** is needed. An OSS survey on this (VS Code · Docker · Tailscale · Syncthing · Zellij): **there is practically no precedent for splitting the tray and GUI into separate processes** (all are one process, or the tray = the daemon binary). At the same time the reason for the split (WebView memory) collapsed in this product's context — the target is a developer workstation (plenty of RAM), and we already accept "closing the UI = hide (the WebView stays resident while the window is up)," so the only span a separate tray saves is "the time after boot when the UI was never opened."

## 결정
**Merge into 2 processes.**
- **The local app (Tauri)** = the system tray + the main window are owned by **one process** (the Tauri v2 native tray). Login-resident (autostart). The tray menu (daemon on/off · UI show/hide · full exit) is entirely inside this app.
  - **Window show/hide = in-process `window.show()/hide()`** — no cross-process IPC needed.
  - **X = hide** (prevent_close); the real exit is only the tray "완전 종료".
- **The daemon** = a separate backend (the agent host). Detached, **surviving independently** of the app's life and death (ADR-0024 as is). The app only ensures/connects to the daemon and **does not own it**.
- **Daemon choice is a client (app) side profile/context.** client:daemon = 1:N. Only the local daemon is lifecycle-managed; a remote daemon is a connect/disconnect target (future).

### Invariants kept (the real assets that survive from ADR-0023 — preserved regardless of the merge)
1. **Separation of two planes (load-bearing).**
   - **Local control plane:** daemon lifecycle (on/off/health) · app window · autostart control. Transport = named pipe/unix socket (OS user boundary authentication) or, for the merged app, an **in-process function call**. IPC is exposed only as the external (LLM/CLI) control surface.
   - **Remote data plane:** agent I/O (PTY output/input · spawn/kill/resize · attach/replay). Transport = WS (embedded→local WS→remote WSS); remote requires token/mTLS.
   - **Do not route local window/tray control onto the remote data channel.** "Show window" never goes out to a remote daemon.
2. **The daemon is not the app's OS child (ADR-0024 C1 reaffirmed).** Detached spawn; **never** put the daemon in a Windows Job `KILL_ON_JOB_CLOSE` (`CREATE_BREAKAWAY_FROM_JOB`/a separate Job). If violated, every app crash, update, or restart wipes out the in-progress agent PTYs.
3. **The data plane is swapped behind the transport seam (`agentClient`).** embedded/local WS/remote WSS share the same interface. Connection *choice* is the client's (profile); connection *implementation* is behind the seam (whether the frontend holds the socket directly is an impl detail, not a contract).
4. **§5 — tray action = Tauri command.** A native tray popup is not WebView DOM, so cdp cannot click it directly. All tray actions are wired to commands/store (the ADR-0022 registry) so the LLM calls and verifies them through the same command surface.

## 거부한 대안
- **Keep ADR-0023's 3 processes (a separate pure-Rust tray)** — the reason for the split (WebView memory) collapsed under a development workstation + accepting hide. A separate tray has no WebView, so it is outside the §5 LLM control/cdp surface (a principle violation waiting to happen), and in S13 it already created cross-process race debt such as graceful off · icon race · console visibility. It also has no precedent. All three `/consult` runs recommended merging. The scenario where keeping it is justified (the tray must be up right after boot + the GUI is rarely opened + RAM is extremely scarce) is the opposite of this product.
- **Tie the daemon to the same Job Object as the app and exit together via `KILL_ON_JOB_CLOSE`** (proposed by Gemini) — rejected by the judge. In trying to solve the secondary problem of "preventing orphan daemons," it is a **head-on violation of "the daemon survives independently of the app" (ADR-0024 C1, the core requirement)**. If the app dies, all agents die. The daemon is detached+breakaway, and orphans are solved by lockfile/health rediscovery + idle self-shutdown.
- **The frontend (WebView/JS) connects to the daemon directly, bypassing the local Rust transport seam** (proposed by Gemini) — conflicts with the fixed architecture (the `agentClient` seam, ADR-0011/0020). "Who attaches to which daemon" (client choice) and "where the socket implementation lives" (behind the seam) are different layers. Keep choice at the client and implementation behind the seam.
- **2 processes but tray↔UI over a named pipe** (option B1 considered before the merge) — merging into one process makes the IPC itself disappear into a function call, so it is unnecessary. The merge is simpler.

## 근거
- The `/consult` blind judge: all three favored the rollback (3→2). Ruling on the disputed points — daemon lifecycle is detached+breakaway (GPT·Claude right, Gemini's KILL_ON_JOB_CLOSE a fatal error), the data plane is the transport seam (Claude coherent), WebView2 hidden is "resident · cost exists · measurement needed" (GPT·Claude right, Gemini's optimistic assertion of automatic suspension rejected). Most trusted = Claude.
- OSS code/docs survey (three subagents): no precedent for tray+GUI as separate processes. Backend choice is always client-side (Docker context · VS Code remoteAuthority · Syncthingtray connection config, 1:N). No case of routing local control to a remote backend.

## 영향 / 불변식
- The `engram-tray-host` crate (a separate process) is **removed**. The logic to keep (the MenuAction intent model · icon state mapping · to_grayscale) moves to the src-tauri tray module. single-instance is replaced by `tauri-plugin-single-instance`.
- The entry point = the merged app. The **autostart** (`tauri-plugin-autostart`, tray only via `--hidden` at boot), **single-instance** (raise a hidden window = `show()`→`unminimize()`→`set_focus()` + avoiding Windows focus-stealing), and **updater** (the daemon survives the app restart and the app reconnects to it) surfaces are all tied to this app.
- "UI closed + only the tray survives" is expressed by one process (window hide or destroy, the tao event loop remains). It is Windows-only, so the macOS last-window-quit policy is irrelevant.
- **Four pre-implementation spike measurements:** ① WebView2 idle/hidden memory, ② hidden-window raise (focus stealing), ③ local daemon reconnect during an updater restart, ④ rediscovery and re-attach of an existing daemon after an app crash. If they pass, the merged topology is confirmed.
- ADR-0024 (daemon ownership and exit) · 0025 (boot ensure) remain valid — now the *merged app* is the actor for that ensure/stop. The tray commands join the ADR-0022 registry.
