# ADR-0120: Widening the scope of agent name uniqueness — globally unique, sleeping profiles included

- 상태: 확정 (2026-07-31, basis: user decision — "그냥 에이전트 트리에서 에이전트 이름은 오로지 하나로 둘 거임" (in the agent tree, an agent name will simply be only one)) · 부분 폐기 by ADR-0123 (withdraw the ban on number reuse) · 부분 폐기 by ADR-0309 (the basis for rejecting an id parking key, and dead-letter list items 3 and 5)
- 관련: Amends ADR-0115 (the scope of the uniqueness check) · Amends ADR-0116 (same-name blocking at the sleeping layer) · ADR-0119(a single registry entry — the place to enforce uniqueness) · ADR-0101(WYSIWYA name addressing) · Amended by ADR-0123 (withdraw the ban on number reuse) · ADR-0122(the uniqueness exception on the deletion path — time-limited. Do not read the "global uniqueness" of this ADR as unconditionally true) · `crates/engram-dashboard-core/src/agent/manager.rs`(the `// ADR-0120` anchor when implemented) · Amended by ADR-0309 (the basis for rejecting an id parking key, and dead-letter list items 3 and 5)

## 맥락

When ADR-0115 decided to attach an automatic suffix to a same name at spawn, it defined the uniqueness scope as **"the live roster"** only. A same name among sleeping profiles was left unstated.

That gap is not theoretical. The everyday flow creates it as is: spawn `bob` → `bob` goes to sleep (the profile remains) → respawn `bob` (there is no `bob` in the live roster, so it passes) → when that one also sleeps, there are **two sleeping `bob`s**. A state where two different profiles have the same name arises by the normal path.

As a result, the complexity that ADR-0115 meant to erase is only half erased. To fill that gap, ADR-0116 decision 1 added **same-name blocking at the sleeping layer** (if there are two or more sleeping profiles with the same name, do not park and give `RECIPIENT_AMBIGUOUS`) and **a layer priority** (for a same name that spans live and sleeping, the roster layer wins), but these machines are all unnecessary if same names never arise in the first place.

The user's mental model was different from this from the start: a name points to **one logical agent**, and even if the session changes through a handoff, the name stays. "산 것과 잠든 게 이름이 같을 수가 있음? 이름은 1개뿐이라니깐" (Can a live one and a sleeping one have the same name? I keep saying there is only one name) — the system was not enforcing that model.

## 결정

**1. Widen the uniqueness check target to the whole registry — global uniqueness including both live agents and sleeping profiles.** If the same canonical name is found, attach an automatic suffix exactly by the ADR-0115 rule (`이름(1)`, monotonically increasing from the maximum observed number + 1).

**2. Widen the check points — create, spawn, and rename, all of them.** ADR-0115 said "the check applies **only to new registration**", but a rename path really exists (tree rename), so if names collide there, uniqueness breaks. This clause amends 0115.

**3. A sleeping profile also occupies a name.** If you launch a new one while `bob` is asleep, it becomes `bob(1)`. To use the name `bob` again, either **restore** that item and use it (it is the same agent, so that is the normal path) or **delete** it from the tree. **The "reusing the name of a dead one is allowed" in ADR-0115 §impact is discarded by this decision** — as long as the profile remains, that name is not dead (parking name inheritance and respawn delivery continuity still hold through the *restore* path).

**4. The same-name clause at the sleeping layer in ADR-0116 decision 1 becomes a dead letter.** The same-name blocking at the sleeping layer and the layer priority lose their very occurrence condition.

The remaining clauses of ADR-0115 (the automatic suffix method · monotonic number increase · the ban on number reuse · an epoch swap is not a rename target) are **still valid as is**.

## 거부한 대안

- **Keep uniqueness only for the live roster (the ADR-0115 original)** — a sleeping same name keeps arising by the normal path, so half of the same-name defense machinery remains. The intent of redefining 0115 as a "complexity deletion slice" becomes half-hearted.
- **Allow a sleeping same name but carry the entity id in the parking key too** — it needs a double-key redesign across the whole name-keyed system (parking · ledger · contracts). It is a direction that ADR-0114 and 0115 already rejected for the same reason, and enforcing uniqueness is much cheaper.
- **Give the name back when going to sleep (keep the profile but release the name occupation)** — a letter parked for a sleeping counterpart waits under the name key, and if another agent takes that name in the meantime, **a new agent receives someone else's letter instead of the restored original owner.** That is the very outcome ADR-0116 decision 1 tried to block.
- **Reject the spawn itself when a same name arises (return an error)** — ADR-0115 already rejected it (it blocks a normal flow like spawning N workers from the same profile). An automatic suffix gets the same uniqueness without friction.
- **Keep the check points at new registration only (the 0115 original)** — if a rename causes a collision, uniqueness is breached, and that path really exists. As long as the check is placed in one place (the registry), there is no reason to split the points.

## 근거

- User decision (2026-07-31): "그냥 에이전트 트리에서 에이전트 이름은 오로지 하나로 둘 거임." (In the agent tree, an agent name will simply be only one.) The basis was also given in the earlier Q&A — "구분을 해야 되는 게 핸드오프로 세션이 자꾸 변경될 거야. 이름은 1이고." (what needs to be told apart is that the session will keep changing through handoffs. The name is 1.)
- **A handoff does not conflict with this decision** (code measured): even if an agent swaps sessions, the profile id is invariant for life and the name stays too (the `AgentProfile.id` comment — "이 id는 프로세스·세션이 바뀌어도 평생 유지된다" (this id is kept for life even if the process/session changes), as the code says). Only the epoch goes up, so no name duplicate arises.
- **Confirmed in code that the gap really exists:** none of the profile create, upsert, or rename paths has a registry-wide canonical name duplicate check (confirmed by cross-check).

## 영향 / 불변식

- **The canonical name is unique across the whole registry** — live or sleeping. The check point is the single manager that owns the registry (ADR-0119).
- **A sleeping profile occupies a name** — the name reclaim paths are only restore or delete. This is not a cost but intended semantics (same name = same agent).
- **What becomes a dead letter — this list is canonical** (removal targets at implementation). The complexity diagnosis of the earlier session pointed to 6 items, carried over as is:
  1. **Same-name blocking at the sleeping layer** (ADR-0116 decision 1)
  2. **The live/sleeping layer priority** (the same clause)
  3. **Only the same-name guard of the name fallback** (the "no fallback when the name is shared" defense that the `allow_name_fallback` flag turns on) — ★**the name fallback arm itself must not be deleted**★: a contract addressed to a sleeping recipient has no entity id (`recipient_id == None`), so matching it by name is a **production path** (measured by cross-check — the "name fallback wiring" in the original list was an over-pointing)
  4. **The control-character prefix of the loser key** (the device that separates same-name parking keys)
  5. **The name-axis guard of deletion cleanup** (ADR-0116 decision 3 already stated "unnecessary once 0115 enforces uniqueness")
  6. **The A8/M3 defense** (resolution first · visible failure — what ADR-0116 decision 5 left as "not promoted to policy, kept as a defense")

  In addition, the occurrence path of `RECIPIENT_AMBIGUOUS` disappears (the code can stay as a defense, but it becomes unreachable).
- **★Existing persisted data does not satisfy this invariant — the removal order is load-bearing★**: the canonical name is **derived from the cwd basename** when there is no display-name override, so two profiles pointing at the same folder are automatically the same name even without a rename. It is highly likely that `agents.json` already holds same-name sleeping profiles. Therefore **remove the dead-letter list above only after the existing data normalization is done** — if the order is reversed, the very path that 0116 decision 1 and the rejected alternatives of this ADR together tried to block, *"whichever is restored first quietly receives someone else's letter"*, opens as is. **The normalization method = do not build it (user decision 2026-07-31): "현재 프로필 실작업 단계가 아니라서 아무 필요없다." (it is not the stage of real work with profiles right now, so it is not needed at all.)** Since there is not yet any real-use profile data that must be preserved, **no migration device is built**, and if same names remain in the existing `agents.json`, just clean them up and move on. Therefore the constraint "remove only after normalization" above is **effectively lifted**. ★But it is conditional★ — if the same situation arises after real-use data has accumulated (e.g., upgrading a shipped build), a normalization design is needed then. Do not read this decision as "migration is unnecessary forever".
- **When removing, check not "whether it turns red" but "whether it has quietly become meaningless"** — an unreachable branch stays green. For each item in this list, judge individually whether the corresponding test is still meaningful.
- **The remaining clauses of ADR-0115 are alive** — this ADR amends only three clauses: the check scope, the check points, and reusing the name of a dead one. Do not read 0115 as discarded wholesale.
- Unverified (to confirm at implementation): whether the `(1)` notation conflicts with the name grammar, envelope rendering, and CLI comma splitting (carried over as is from the unverified item ADR-0115 left).
