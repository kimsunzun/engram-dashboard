# ADR-0068: LLM spatial target = logical plan (ViewManager) direction/neighbor/order handles first (geometry coordinate exposure deferred)

- 상태: 확정 (2026-07-11, basis: `/research medium` (design-decision mode) OSS survey (tmux, zellij, kitty, i3/sway, wezterm, VS Code, JetBrains) + Codex adversarial review FIX corrections + user decision ("the plan alone is enough")) · 부분 폐기 by ADR-0227 (Decision 3, and the rejected alternative on backend-projected px and the measured pixels and minimum cell clauses in Consequences)
- 관련: Amends ADR-0066 (Decision 3: LLM spatial target = exposing geometry {x,y,w,h} coordinates first → amended to logical-plan-based direction/neighbor/order handles first (coordinate system and measured pixels deferred)) · CLAUDE.md §5 (LLM-first control) · ADR-0035 (layout authority = client Rust ViewManager) · ADR-0022/0055 (command registry) · ADR-0011 (agentClient assign) · `src-tauri/src/layout/manager.rs` (ViewManager) · step-log "LLM 공간 타깃 = 논리 도면 방향·이웃·순서 핸들" · Amended by ADR-0227 (Decision 3, and the rejected alternative on backend-projected px and the measured pixels and minimum cell clauses in Consequences)

## 맥락

ADR-0066 Decision 3 set "LLM spatial target = expose slot geometry `{id,x,y,w,h}` through the control surface → the LLM derives a slot id by numeric reasoning ('bottom right' = max of x+w·y+h)", and pushed direction/neighbor sugar commands to **lower priority**. A re-check before starting implementation exposed two problems:

1. **Terminology confusion.** The "backend ViewManager" that ADR-0035/0066 use is **not the agent-hosting daemon (server) but the Rust-side layout owner of the client (the src-tauri shell)**. Layout is UI state that differs per window, so it is a **client concern** unrelated to the daemon. The question "who knows the coordinates" in this decision is not on the daemon-client axis but a problem of the **Rust (ViewManager) ↔ JS (frontend React) boundary inside one client process**.

2. **Coordinate exposure = over-design relative to the stated need.** The real need is "put it at the bottom right → slot id", and that is not coordinate arithmetic but **a decision on relative position and order**. It can be solved from the logical tree (split structure and ratios) that ViewManager already owns, without introducing a coordinate system. Actual render pixels are known only to the frontend (the "building"), but the logical structure is something ViewManager decides as its owner (the "plan"), so it knows it without a frontend round trip.

## 결정

The primary control surface for LLM spatial targets = **direction, neighbor and order handles that ViewManager (client Rust) computes from its own logical layout tree**. Exposing a geometry coordinate system and measured pixels is **deferred**.

1. **Primary surface = handles derived from the logical plan** — each slot's neighbors (left/right/up/down neighbor slot ids) · order (ordinal) · direction tokens (in the style of tmux `{bottom-right}`/`{left-of}`). It maps "bottom right", "to the right of this slot" and "the leftmost" to slot ids by logical relations. No coordinate arithmetic is needed.
   - **ordinal definition (fixed by code review FIX-2):** the **global lexicographic** index of each leaf center `(center_y, center_x)` (top → bottom, ties left → right). It is a global sort by center, not a tree pre-order — the leaf rects are disjoint so the center pairs are unique and deterministic. It is a total order definition that accepts that, in an asymmetric split, a full-height column can slip in between the ordinals of the left column's slots (column/row cohesion is not guaranteed). Resolving the bottom-right/corner tokens is independent of this (minimum corner distance).
2. **Computed by = ViewManager** — these handles are derived from the tree that ViewManager already owns (0 frontend round trips · independent of pixels/DPI). A human click and the LLM share the same command surface (§5), and the authority is the backend (ADR-0035).
3. **Measured pixels and a coordinate system = deferred** — a measured `getBoundingClientRect` rect or a new normalized coordinate system is added as a separate capability when a **real pixel-space use case** appears (screenshot coordinate mapping, pixel intersection decisions, comparison with external AX/CDP coordinates). The model then = the frontend reports the measured rect to ViewManager as a **versioned observation** (the authority is still ViewManager, the frontend only observes — §5). If a normalized `[0,1]` logical rect is needed, it can be derived from the same tree, but the primary one is symbolic handles.

## 거부한 대안

- **The frontend `getBoundingClientRect` as the primary coordinate source:** ① authority direction reversed — if the frontend holds the layout truth it violates §5 (frontend = pure I/O) and ADR-0035 (backend authority). ② staleness during window resize/animation, CSS-px vs device-px (×devicePixelRatio) ambiguity (WebView2 DPI). ③ an unnecessary round trip for the stated need ("bottom right"). → deferred to a separate use case where pixels are truly needed, and even then only as "observation reporting" (not authority).
- **Backend-projected physical px (ratio→px via `inner_size`+`scale_factor`):** to be accurate, ViewManager would have to model gutters, sashes, min-size and collapse too → duplication of render engine logic and risk of drift. Excessive for a coarse direction target. Deferred.
- **Geometry coordinate exposure as primary (the ADR-0066 Decision 3 original):** the OSS precedent of "the layout authority owns logical coordinates" is **not the LLM's basis but each engine's internal circumstances** (a terminal = a cell grid, a compositor = pixels), so it is weak as a basis for our presentation choice. The pane targets of real automation clients use **symbolic direction/neighbor/order tokens**, not raw coordinate arithmetic (tmux `{bottom-right}`, kitty `neighbor:right`, i3 `focus left`). Introducing a coordinate system is over-design relative to the real need → flipped to direction, neighbor and order handles first.
- **"Normalized logical coordinates satisfy every spatial reference":** an overstatement (Codex adversarial review High). Min-size constraints, collapsed slots, sash/border/scrollbar and terminal chrome make the actual render size diverge from the ratio — "the widest one" and pixel-space intersection independently need a measured rect. That i3 exposes **both** `percent` (ratio) and `rect` (pixels) is corroboration. → Separate normalized logic as a coarse order surface and pixels as a separate surface (deferred).

## 근거

- **`/research medium` (design-decision mode) OSS survey:** tmux (`#{pane_left}` cells · server-owned + `{bottom-right}`/`{left-of}` tokens) · zellij (`PaneInfo` cells · engine-owned + `move-focus`) · kitty (a `neighbor` direction graph + `num` ordinal as the **primary control surface**) · i3/sway (`rect` pixels + `percent` ratio **both** + `focus` direction) · wezterm (mixed cells+px, a warning not to trust px on Windows) · VS Code (`setEditorLayout` ratio `size` 0~1, no pixel-rect API for editor groups — #208658) · JetBrains (`Splitter.myProportion` ratio). → The authority owns the logic, and symbolic direction/neighbor/order dominates as the target.
- **Codex adversarial review FIX corrections:** VS Code #94817 is closed (the basis for the absence of a pixel-rect is #208658) · allotment `onChange`=px is not stated in the docs (downgraded) · "normalized logic fully satisfies" is an overstatement (rejected alternative 4 above).
- **§0 criterion (low risk, long horizon):** direction, neighbor and order handles = low risk and clear demand → laid down now. Coordinate system and measured pixels = uncertain and an unverified use case → not even a shell is made, deferred (filled in by measurement when a real use case appears).
- **Fact/interpretation split:** "i3/sway use pixels because, being compositors, pixels are the native unit" is a survey interpretation (not direct evidence, Codex's point) — it supports the decision but is not cited as established fact.

## 영향 / 불변식

- **Spatial target handles are owned and computed by ViewManager (client Rust)** — a human click and the LLM use the same command surface (§5). The frontend only renders and does not hold the layout truth (ADR-0035). If the frontend holds separate "spatial state", it is a §5 violation (rejected in review).
- **Neighbor/order/direction handles = derived from the logical tree** — independent of pixels, DPI and window size, 0 frontend round trips.
- **When measured pixels are added (future)** — the frontend's measured rect is a **versioned observation** (not layout truth): it goes stale when the window size/render epoch changes, and the ViewManager authority is unchanged (no dual authority — ADR-0035).
- **Unimplemented (what this ADR opens):** the actual implementation of the neighbor/ordinal/direction token commands and the measured-pixel capability are later slices. This ADR fixes only the direction and priority.
- **★Constraint when introducing a resize command (cross-family review ①②)★:** spatial computation uses an absolute epsilon (`EPS=1e-4`) in the `edge_eq`/overlap decisions. If some leaf is squeezed to a width/height `< EPS`, two defects appear — (①) if that leaf is split again, the orthogonal-axis overlap of the two child slots is exactly `EPS`, so it drops out of `overlap > EPS` (strict) → the up/down or left/right neighbor cannot be found. (②) a sub-EPS-width slot is skipped over, because `edge_eq` misjudges the slot beyond it as "adjacent". **A per-split ratio clamp (`[EPS,1-EPS]`) cannot defend against this** — a leaf's absolute size = the product of the ratios along the path, so with nesting it goes down to sub-EPS. **The canonical fix = the resize command enforces a UX minimum cell size** (a drag below that = removal/snap, tmux/i3 precedent — the value is set in an ADR after OSS research). At that time, the minimum size and the behavior when going below it (removal vs snap) are a user decision (§5 felt behavior).
- **Representative-neighbor asymmetry = by design (cross-family review ③):** if a slot faces two slots in one direction (in an L-shape, the full-height left column faces the 2 right upper/lower cells), `neighbor_in_dir` returns **only one representative neighbor** — on a tie, the first candidate in traversal is kept. So an asymmetry arises where `rb.left==left` but `left.right==rt(≠rb)`. This is a necessary property of the single-representative-neighbor model, not a defect, and the `spatial.rs` neighbor_in_dir doc and the test `l_shape_bottom_right_neighbors` state and accept it (round-trip reciprocity is not guaranteed).
