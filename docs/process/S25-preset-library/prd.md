## 1. What · Why

- Instructions (`.md`) · skills (folders with `SKILL.md`) · settings (`.yaml`) are bundled into named **presets**, and an agent only attaches presets. The backend (claude · codex) is a value chosen when the agent is created and is fixed — a setting has only per-backend raw-text fields and the field matching the agent's backend is used (the model too is inside that field — R5 · R44 · user 2026-10-18). The aim is to stop aligning the same rules · skills · settings by hand per agent, and instead fix them in one place and use them for many. (메모 6 · 26 · 2026-10-18)
- **Library** = one folder (one root — R7 · G36). On first start the daemon creates an empty `library\` inside the distribution folder and sets it as the library; the user can switch to another folder (R8 · R9 · G35). Components and presets are files (assets) inside it, and sharing means handing over the folder (exporting · importing only the needed files with their references = after S25 — §2 · G37). Outside content used as a component is copied or cloned into the library (G37). Two things live outside the library: the Engram built-in preset 「기본」 (R43), and **folder entries** — a preset may name any folder, inside or outside the library, which the backend reads in place at launch; a folder entry is not a library asset (R56 · ADR-0341). Because the backend is an agent value, an agent can be created and run even when the library is empty. (메모 53 · 74 · 127)
- The old 「프리셋」 (working folder favorites — ADR-0061 · `presets.json` · `src/components/slot/PresetPalette.tsx`) and the picker that selected it are removed, and the new scheme uses the name — old data is simply discarded (G32). The agent tree pane menu item 「에이전트 생성 ▸」 itself stays (R44). The superseding ADRs (ADR-0061 · ADR-0070) are for the TRD. (메모 43 · 44 · 122)

A preset is also a file inside the library (exception = built-in, R43). **Instructions = every `.md` wherever it is** (including those inside skill folders · free content · no format · exception = `SKILL.md` itself — it stands in for that skill, R12 · `.txt` is not an instruction — user 2026-10-17). **Files that are not of our kinds do not appear in the list** (pictures · `.json` · `.txt` · scripts etc. · also inside skill folders · also `.yaml` files that lack `kind` or cannot be read at all — user 2026-10-17). 「오류」 + reason (e.g. 「오류 · YAML 3줄」) applies only to broken files that are `kind: preset` · `kind: settings` and to unknown `kind` values (likely typos). **If there is a file at the path being pointed to but it cannot be read, it is always 「오류」 — not 「찾을 수 없음」** (M14 · review #4 — so that a preset with one wrong indent does not become 「찾을 수 없음」 and leave the user relinking to another file instead of fixing the typo) — `kind` is found leniently even in broken YAML (form = TRD) · a `.yaml` file whose `kind` still cannot be found does not appear in the list, but if a preset · agent points to it, that line is 「오류」. YAML is the direction, final in the TRD. (메모 74 · 76)
  - **Settings validation — light · inside the daemon only · the CLI is not run** (user 2026-10-18 「가볍게하는걸로하고 나중에 문제되면 차후에 고려하자」 · 「안되면 그냥 어느정도 미스매칭 각오하고 별도로 라이트하게」 — withdraws the 10-17 pre-launch CLI check (`claude --settings … doctor` · `codex debug models` / `codex doctor`), its pass record, and the block reason 「설정 실행 직전 검사 실패」 · measured = `docs/research/settings-asset-validation-spike-2026-10-17.md`). ① Syntax (YAML) → ⛔ error 「N째 줄」 ② Schema — claude = SchemaStore `claude-code-settings.json` (a community-maintained copy that the official docs point to · it lags behind claude — `docs/research/claude-settings-schema-source-2026-10-18.md`) · codex = the release `config-schema.json` of the installed version. A type · range error of a key the schema knows → **⛔ error — blocks launch** (「막어」 — claude silently discards the whole `--settings` if even one value has the wrong type · measured) · unknown key = claude shows nothing (SchemaStore misses many new keys) · codex only ⚠ (does not block — same as 10-17). **When to validate = every time Engram reads the content** (the cheap-check practice of VS Code · JetBrains) — first scan (everything) · refresh (files changed by tag) · edit inside Engram (immediately) · launch (the attached settings — already read) · everything again when the schema changes. **Schema location = the distribution ships the current version, one per backend, and updates it in the background** (user 2026-10-20 「일단 지금 하나 넣어두고 알아서 버전비교해서 업뎃하라고 하면 되지 않음? … 실패하면 기존걸로 하고」 · P10 — replaces the old 「실제로 필요할 때 내려받기」) — so validation always runs even offline. The daemon reads the installed CLI version (once at start · when it changes) and updates the schema it holds **in the background** (nobody waits): codex = if the installed version differs from the version it holds, that version's `config-schema.json` · claude = SchemaStore files do not exist per CLI version, so if the claude version changed since the last check, it downloads the latest again. On failure it keeps using what it has (the downloaded one or the distribution's). If there is no schema at all, it checks only the YAML syntax and shows a dimmed 「스키마 검사 안 됨」 — it does not block just because there is no schema. We accept that the daemon newly uses outbound network (P10). **Launch does not wait for the download** (P10-ADD) — it validates with the schema it has, and while the schema it has is an older version than the installed CLI, it does not block unknown keys and shows a dimmed 「이 판 스키마로는 확인 못 함」 · it blocks only type · range errors of known keys · when a new schema arrives it re-validates immediately (⛔ recomputed too — E4 · P8). **The merged claude settings are validated too** (R5 — even if each piece passes, if the merged one breaks the schema, the error is shown on the later asset that brought it in · M14 · review #19). **Values that cannot be put on the command line also count as 「오류」** (M8) — a codex `-c` line that is not safe in cmd (both modes) and a launch that exceeds the command-line length are not silently dropped but blocked with a settings 「오류」. There is no 「검사」 · 「모두 검사」 menu and no `library.validate` — refresh (F5 · right-click 「새로 고침」 · `library.refresh`) takes that role · there is no 「검사 필요」 state either (the check is nearly free, so it runs on every read) (session proposal · no objection). There is no re-reading on editor focus (「너무 복잡하게 할 필요는 없는것같아」 — outside edits show at refresh · launch). A runtime error (exit code + stderr) does not attach ⛔ to the settings line — it is shown only to the agent (exit code + stderr raw text · user 2026-10-18 — withdraws the 10-17 「그 설정 줄 ⛔」). The icon is shown in the name field of the list and the reason in the tooltip · detail card (e.g. 「3째 줄 · …」). Schema errors · syntax errors are the launch block reason 「오류」 (E4).

A **folder entry** (R56) is the exception: a folder that exists but cannot be read (access denied · a network share that does not answer in time) shows 「폴더를 찾을 수 없음」 and blocks with reason ① like a missing folder (ADR-0341 decision 6 · E4 addendum).
- **R2** Components → preset (a preset can contain presets · references, not copies) → agent (several presets). Components are added only in the preset edit area, and an agent only attaches presets. The backend does not come through a preset — it is an agent value (chosen at creation · fixed — R44 · user 2026-10-18 「그건 에이전트가 골라야지」). (메모 26 · 39 · 그림 §1)
- **R3** Reference = one form of path separated by `/` from the very top of the library (e.g. `스킬/리뷰/review`) · no scope limit. Rejected = a path relative to the preset file · name references · ID files — a skill is shared by several presets, the same name is common in a folder browser, and an item's identity is its place. (메모 101–103 · 그림 §5)
- **R4** Validation after expansion — cycle = error · if the same preset arrives by two routes, it counts once · **the same component path also counts once** (if instructions · skills · settings are included in several presets with the same path, only the first place in the expanded order remains — M14 · review #18) · the only conflict = two or more skills of the same name (different paths) — since Engram lays skills down as per-name folders, they really collide on our side regardless of the CLI. **Expanded order** = in the order attached to the agent, depth first, with each preset's nested presets before its own (D1) — e.g. if A · B are attached to an agent in that order, A = {nested C · instruction x} · C = {instruction y} · B = {instruction x · instruction z}, the instructions are loaded in the order y · x · z, and B's x is dropped because it already appeared (M14). **Skill name** = `name` in the `SKILL.md` front matter (trim leading and trailing spaces and collapse repeated spaces to one) · if absent, the folder name — the same-name decision compares the name lowercased with characters outside `[a-z0-9_-]` replaced by `-` (matching the case handling of Windows junctions · claude's character replacement) · a name outside the 1–64 character range `[a-z0-9-]` is 「오류」 — **only when it is loaded for a backend that rejects that name (codex JSON)** (the place of the check = the backend settings validation — TRD) · the same-name decision above (character-replacement comparison) always applies regardless of backend (M13 · P7 · review #24 · M24). The conflict check looks only at lines actually loaded for that agent (backend marks — R54 · M20) · a codex JSON agent also receives the skills of nested presets and takes part in the conflict check (M13). There is no model conflict check (R5 · user 2026-10-18 — the old 「백엔드 설정 둘 이상」 conflict was withdrawn). Instructions · settings are appended in the order they were added (if there are backend marks, per preset that preset's common lines and then that backend's lines — R54 · G51). (메모 9 · 26 · 2026-10-18)
- **R5** A settings asset = `description` + only per-backend raw-text fields (claude = the settings JSON to pass with `--settings` · codex = the `-c` list) — there are no formal `backend` · `model` fields (user 2026-10-18 — withdraws the formal fields of memo 79). Only the field matching the agent's backend is used, and they are joined in the order added — **the claude field is merged in attach order into one settings file and passed as one `--settings` — the later value wins · lists are merged** (objects = merged recursively · lists = appended in attach order with equal values collapsed to one · other values = the later preset wins · no per-key rules — user 2026-10-18 「이어붙이기 진행」 · so a later preset cannot remove `engram` from `allowedMcpServers` — accepted) (Engram-priority rule · no hidden settings fragment — TRD T10 · user 2026-10-18 「프리셋으로 해줘. 사실 감추는 설정이 있으면 안되지.」 · the Engram link keys are left visible in the claude field of the 「기본」 preset — R32) · the merged claude settings are also validated against the schema (R1 · M14) · the codex field appends the `-c` list. Unlike instructions · skills, the backend distinction of settings is the field inside the file as it is (the backend mark on a preset line is only for instructions · skills — R54 · G29). Model · effort are also placed inside that field (e.g. claude field `model: claude-opus-5-5` · codex field `- model=gpt-5.5` · `- model_reasoning_effort=high`) — the reason for having a field per backend is to swap in the field that fits the agent's backend, and the agent does not choose the model (「근데 model을 왜 에이전트가 골라」). Engram does not interpret the raw text or check it for conflicts (the content is the user's responsibility) — even if two settings put a model in the same backend field, there is no conflict check — for claude the later value remains at merge time (above) · for codex it is whatever the CLI does (「클로드 쪽에서 허용하면 허용인거고 안되면 충돌인거지」 · to check it, a per-CLI comparison table would have to be fixed at every CLI update). If a model is put in, the CLI starts with that model — the JSON picker does not lock it (R35 · user 2026-10-18). Key names are placeholders. (메모 79 · 81 · 167 · 2026-10-18 · 그림 §8)
- **R6** Status marks = conflict (cannot be used as is) · not found (「찾을 수 없음 · [다시 연결] ×」 — R19) · error (cannot be read — a file that exists but cannot be read is always an error · settings schema error · a skill codex cannot load — R1 · E4) · dimmed (already added · cannot be added · not loaded for this agent's backend — R31 · R54 · P12). **There is no warning (notify-only) category** (user 2026-10-18 — R22 · R45 · exceptions = the ⚠ for unknown codex keys in settings validation — R1 · the notice of instructions · skills that the codex terminal did not load — R37 · an exception the user made, P4-FINAL). The old 「다시 연결됨(확인할 때까지 그 줄에 붙는 표시)」 was withdrawn — a line is either not found or fine (D10 · convention — 2026-10-18 · on 2026-10-19 the scan's candidate-suggestion line was also withdrawn — R19). 「찾을 수 없음」 appears only where a place points to a missing file (preset line · agent slot) — not in the folder list. **Lifting an inner error** — a preset line that contains a not-found or error inside it shows a red error count badge even when collapsed (VS Code Explorer practice · user 2026-10-18 — R31 · E4) · the same problem also appears one line each in the problem list above the edit area (R51). (메모 86 · 그림 §12)
- **R43** **Built-in assets** — live in a fixed fake path namespace outside the library (e.g. `engram:/…` — form = TRD). The real files sit in one `builtin\` folder of the distribution as files of the same form as the library (preset `.yaml` · instruction `.md` · settings `.yaml`), and the fake path points to those files (main session decision 2026-10-20 — reported). Built-in = only the default preset 「기본」 (R32) (user 2026-10-18 — the old 「claude 기본」 · 「codex 기본」 backend presets were withdrawn: their content was only `backend` and the backend is now an agent value — R44). It exists even when no library is selected. **In the library slot tree, default = hidden** (user 2026-10-20 — R11) — only in a number where the 「…」 menu ☐ 「기본 제공 보기」 is turned on, it appears as a separate read-only root 「Engram 기본 제공」 under the library tree (browsing · detail only — no edit · move · delete · rename · new · drop · but **copy** to the library is allowed — the way to make my own preset modelled on the 「기본」 · R17 · P6 · M14 · edition 2) · in library search too, it appears with a 「기본 제공」 mark only in a number where it is turned on (main session decision 2026-10-20 — reported · matches 「숨김」). View-by-expansion only (R27) · folder magnifier and R28 are off · it cannot be added inside another preset (it only attaches to agents) · `engram` is referred to by the fake path. A person attaches it from the pinned 「기본 제공」 list at the top of the search under `+` in the agent slot (one 「기본」 · always present regardless of the 「기본 제공 보기」 on/off) — this and the empty 「기본」 field are the way to reattach a detached default preset (D8). 「기본」 loads different priming per backend through backend marks (R54) (M20). If the distribution's `builtin\` cannot be found, it launches without priming — it does not block (M7). (default E7 · E17)
- **R54** **Backend marks on instructions · skills — common · claude · codex** (new feature · user 2026-10-30 「프리셋에 하는게 맞지 싶은데」 · G29 · research = `docs/research/per-agent-instructions-practice-2026-10-30.md`) — each instruction · skill line inside a preset can carry one backend mark: none = common · `claude` · `codex`. **The mark lives in the preset — it is not written in the asset file** (files that were fetched are not touched · the same file can be used differently per preset · there is no front matter to strip — G29). Settings stay as now: the `claude:` / `codex:` fields inside the file (R5). **Loading order = per preset — that preset's common lines, then that preset's lines for that agent's backend** (user 2026-10-31 「공용 전용이 그렇게 쓰이는게 아니라 공용으로 안되는걸 덧붙이는 느김이라 aa bb 가 맞을듯?」 · G51) — presets are loaded one by one in the expanded order (R4), and within each preset the common lines are followed by the backend lines · they are appended, not overwritten (M20). Example: if A · B are attached to an agent in that order, A = {instruction a1 · instruction a2 (claude)} · B = {instruction b1 · instruction b2 (claude)}, a claude agent loads a1 · a2 · b1 · b2 in that order (reverses the old 「펼친 프리셋 전체에 걸쳐 공통 줄 전부 다음 백엔드 줄 전부 — a1 · b1 · a2 · b2」 (main 2026-10-31 M24) · rejected = common first across everything (M24) · backend lines first (Roo Code) — backend lines add what that preset's common lines cannot cover, so they sit right after them · user 2026-10-31 G51). **The purpose of having a mark** (user 2026-10-31 「프리셋이 메인세션 프리셋인데 로컬모델이 구져서 제대로 안들으면 클로드랑 다르게 덧붙이는 느낌으로 해야되는거 아니면 각각 쓰거나」 · G51) = an addition for a backend that follows the preset poorly (e.g. give a weaker model extra lines that claude does not need) — it is added on top of that preset's common lines · if the content differs a lot per backend, make separate presets instead of a mark. The conflict check (R4) looks only at lines actually loaded for that agent · the agent preset slot shows lines not loaded for that agent's backend dimmed (the same dimming as P12 — R31) · the codex terminal still loads no instructions · skills, and codex-marked lines also go into the 「빠진 것」 of the notice (R37) · the built-in 「기본」 also loads per-backend priming through this mark (R32 · R43) (M20). A line in the preset YAML = a bare path (common) or a path + backend (form = TRD). LLM = the backend argument of the add command (omitted = common) + one command to change the mark (name = TRD — M20 · R39). The form shown in the edit area (three groups: common / claude only / codex only · changing by drag or right-click) is looked at again in the client phase (M20). Convention (research) = 「공통 기본 + 에이전트별 예외」 is an existing form — rulesync does the same thing with the front matter `targets` of rule · skill files · we found no precedent that puts the mark on the bundle (preset) side · merging is almost always appending, and Roo Code, which documents the order, is specific first → common last (the opposite of ours).

- **R56** **Folder entry in a preset** (user 2026-11-01 「폴더 경로 지정하면 거기있는 폴더를 해당 에이전트 룰로 파싱하는거하고, 고정경로 저장하는거. 결국 Claude 나 codex 가 폴더 지정하는것과 같은 옵션임」 · 2026-11-04 · ADR-0341 decisions 1 · 6) — a preset can hold folder entries: each is an absolute folder path, inside or outside the library (e.g. a company-rules folder and a personal-rules folder), kept in entry order. **Invariant constraints (principles — walls to keep)**
- Data (scan · presets · settings content · references · relink · built-in assets) is **owned by the daemon**. The client does not read the disk and only displays, and what it holds is only view state (folder · selection · sort · history · pane widths) (the old 「개인 데이터(컬렉션) — 항목 키에 데몬 신원」 is after S25 together with collections — G34). The screen is a package, so even when it is off the daemon features stay as they are (R55). (메모 58–59 · 71 · 87)
- The client · daemon are on the same PC for now. The screen does not call OS dialogs · open with the default program · reveal in Explorer directly but goes through one request (now = OS default · switched off for remote) — this same-PC helper is screen only and is not a daemon command (R39 · M21). (메모 60 · 63)
- Third-party libraries are always wrapped behind our own component. (메모 93 · 113)
- Backend knowledge lives in one place, 「백엔드 확장」 · per-OS behavior (default program · junction) in the 「플랫폼 중립」 OS layer — deletion does not use the OS recycle bin and moves to `.trash` inside the library (R18 · 2026-10-19) · the sending of a person's emptying · permanent delete to the OS recycle bin is one OS-layer function (macOS = Trash — later · R18 · 2026-10-20). (principle)
