### 1-1. Design rule — backend extensibility (user 2026-11-11)

User: 「나중에 백엔드 계속 추가될텐데 최대한 공용화로 하고(예를들어 ENUM 추가하면 모두 자동으로 되게 한다던가.)」. **Adding a backend to agent (a new `AgentCommand` variant, its `backend_word`, its `SettingsCheck` in `settings_checks()`) must make tags, settings raw fields, the selection of what an agent loads, the hand-over checks and the notices work with no asset-library change.** A new backend gets no schema check (ADR-0359 decision 4). Concretely:

- A backend tag and a settings raw-field name are **strings**; asset-library accepts a word only if the backend registry knows it, and compares case-insensitively through it. No `enum Backend` in asset-library.
- **The registry is reached through one seam, `Backends`** (§3-3a): `for_word(word)` and `all()`. Production = `AgentBackends`, which calls agent `settings_check_for` / `settings_checks()` (`backend/mod.rs:770-781`); tests inject a registry with a fake third backend. `format`, `validate`, `resolve`, `refs` and the service take `&dyn Backends` (the service holds an `Arc<dyn Backends>` from `LibraryValues`); **no asset-library code calls `settings_check_for` / `settings_checks()` directly** except `AgentBackends` (reviewed in §8-3).
- Everything that differs per backend or mode comes from a port answer: `loads` · `accepts_skill_name` · `command_line_args` · `command_line_fits` · `skill_format` · `folder_entry_blocks` · `working_folder_blocks` · `folder_listing_at_launch` · `folder_load_set` (incl. its `carried` rows) · `native_skill_roots` · `root_skills` · and the notice codes (`notice_codes`, §3-9). (Draft 8 also listed `merge` / `merge_origins` · `unknown_keys` · `raw_to_json` · `schema_source` · `version_probe` — schema-check answers, removed by ADR-0359 · §3-9a.) asset-library branches only on those answers, never on the backend word.
- **No `claude` / `codex` literal in asset-library outside tests and the built-in content files** (reviewed in §8-3).

Draft 1 broke this in two places (§10-2 B20): asset-library would have chosen the three codex-named notice codes (`CODEX_TERMINAL_OMITTED` · `CODEX_TERMINAL_FOLDER_OMITTED` · `CODEX_SAME_NAME_SKILLS`, `launch.rs:350-360`) by knowing that the backend is codex, and the draft named the working-folder refusal code as if asset-library owned it. Draft 2 broke it in two more (review round 1): the registry was called as a global, so the fake-third-backend tests could not be written (must 10 → `Backends`), and `check` could only tell claude's natively loaded folder files from codex's carried ones by the backend (must 9 → `folder_listing_at_launch` + `FolderLoadSet.carried`). Prose that says "codex terminal" / "claude merged" describes what today's port answers produce, not branches in the code.

**Nobody calls the crate yet.** No daemon edge, no command, no manager wiring. Every launch stays Noop until step 8. Build and the full regression stay green because nothing outside the crate's own tests reaches the new code, and the agent additions are additive (existing callers and goldens unchanged; the default `LaunchKitSource` methods delegate to today's `check` / `prepare`).

**Read** (`read.rs`):

- **Parse options, one place** (`format::options()`): `strict_booleans: true` (G49) and `non_finite_float_policy: PassThrough` (premise 40 — a `.nan` / `.inf` anywhere, even in a key Engram does not model, does not fail the read). Item shapes: a plain string or `{path, backend}` (M20) — read through an intermediate value enum so a wrong shape is a line problem with its line, not a whole-file failure (B5: `untagged` loses `Spanned` positions — §6-2 L1041).
- An entry that is not a string or a map with a string `path`, or whose tag word is unknown, or whose `path` does not parse, is a **line problem** and is recorded in `unmodeled` with its list and index; it is not in the typed list. The writer passes it through untouched (below).
- Raw fields are kept by name and value only; which field is "this backend's" is decided later by `Backends::for_word(name)` for the agent's word, case-insensitively. A field whose name no backend knows is kept and ignored (a later backend may claim it — §1-1).
- **`folders`**: each item must be a string; `normalized` = `platform::fs::normalize_folder` (§3-10). A relative path or a `LibPath` = `FolderPathError` → broken line ② (§1-2), still in `folders` (it is modeled — a string). A non-string entry = `unmodeled`. Missing key = empty list.
- **Reader codes as landed (P3)** — besides `yaml-syntax` · `kind-unknown` · `wrong-kind` · `backend-tag-unknown` · `folder-path-relative`: `field-invalid` (a top-level field Engram reads has the wrong shape — `version` missing, not a whole number in `u32`, `description` not a string, a list key that is not a list), `item-shape-invalid` (a list entry that is neither a string nor a map with a string `path`), `item-path-invalid` (an entry spelling that is not a reference — also the row of an attached preset spelling that does not parse, P8 — §3-7), `backend-tag-not-allowed` (a tag in `presets` or `settings`). The preset reader also refuses a multi-document file and content after an explicit `...` with `preset-multi-document`; the settings reader reports the same as `yaml-syntax`. All in B8.

`rewrite_lists`:
1. Strip a leading U+FEFF and remember it; remember the line ending (CRLF if the first line break is `\r\n`, else LF; mixed endings are written as the first one — the file is rewritten anyway).
2. Parse the text into `Node` (`format::options()`). More than one document ⇒ `MultipleDocuments` (code `preset-multi-document`, write nothing). Not a top-level map with `kind: preset` ⇒ `NotAPreset`.
3. **Number guard** (must 4 (c) · premise 39): any `Float` node whose value is integral and whose magnitude is ≥ 2^63 ⇒ `NumberOutOfRange` (code `preset-write-number-range`, `args` = the node path), nothing written. The tree cannot tell a 21-digit integer literal (already rounded by the reader) from a written float such as `1e20`, so both are refused rather than kept as text: keeping the literal would need the source text of the scalar, which serde-saphyr does not hand to a visitor. The refusal names the key; the user edits that value by hand. Other floats keep their `f64` value (digits beyond `f64` precision in a float literal are formatting, ADR-0358).
4. Replace only the five list nodes (`presets` · `instructions` · `skills` · `settings` · `folders`) in place — an absent key is appended after the last present one; an emptied list is written as `[]`. **Every other key, known or not, stays as the parsed node in its original order** (ADR-0358 「영향」). Each new list is built entry by entry:
   - **Item identity** (must 4 (a)): an item with `origin = Some(i)` starts from the original entry node `i` of that list; an item with `origin = None` takes the first original **modeled** entry of the same list with the same `target` spelling that no other item has taken (this covers `preset.save`, whose lists come from a client without origins), else it is new. Identity never depends on the tag or the position, so a reorder and a tag change keep the item's node.
   - **Writing an item from its node**: a map node keeps every key it had, in order (unknown keys inside an item map survive); the **modeled values are written from the item** — the `path` value is replaced when the item's `target` spelling differs from the node's (a relink or reference rewrite `old.md` → `new.md` keeps the item's other keys and changes the path — round 2 must 7), and the `backend` value is set, added (after `path`) or removed. A string node is replaced by the item's spelling; with a tag it becomes `{path, backend}`. A folder entry (always a string node) is written from `FolderItem.path`; 9a passes `FolderRef.raw` through for every entry the edit does not touch, so an untouched entry keeps its original spelling (parent §1-2: a read never rewrites the file text), and only a new or changed entry is stored in the normalized form. A map node that loses its tag and has no other key than `path` becomes a string again; with other keys it stays a map. A new item = a string, or `{path, backend}` with a tag.
   - **Unmodeled entries** (must 4 (b)): every original entry in `unmodeled` that is not in `drop_unmodeled` is copied as its original node, anchored after the nearest original entry before it that is still in the new list (or at the head of the list when none is). A list key that only holds unmodeled entries keeps them.
5. Serialize with `to_string_with_options(&node, ser_options! { indent_step: 2 })` — `yaml_12` stays `false`, so strings that a YAML 1.1 reader would take as booleans or numbers are quoted.
6. **Round-trip check** — re-parse the output into `Node` and compare with the tree from step 4 by `Node::same`; any difference ⇒ `RoundTrip` (code `preset-write-mismatch`), nothing written.
7. Re-apply the line ending (LF → CRLF if remembered) and the BOM.

**Why the round-trip check stays**: ADR-0333's gate existed to catch `yaml-edit`'s broken outputs and is gone with it. A different risk remains: a serializer that writes a scalar a reader takes back as another value (a numeric-looking string, a float's text, an ambiguous plain scalar) would silently change a user's file — the one failure ADR-0358 does not accept. The check costs one parse of a small file. It cannot see a loss that happened at read time (premise 39), which is why step 3 exists.

What is lost on a rewrite, by decision (ADR-0358): comments, blank lines, quoting style, flow vs block style, key spacing, anchors/aliases (expanded — values equal), merge keys (`<<` expanded — values equal), explicit tags (`!!str` etc. — the tagged value stays), the sign of a NaN. Indentation becomes 2 spaces.

`FsStore` = walkdir + std + base `write_atomic` / `copy_atomic` with `OsHooks { retry: platform retry_busy, sync_dir: platform sync_dir }`.

- **Link policy (U1 (a)) on every path** (must 5): only the **configured library root** may be a link — `follow_root_links(true)` for a full scan only. A partial scan first **draws `seq()`** and then runs `first_link(root, under)`: if `under` or any folder between the root and it is a link, nothing is walked, `under` goes into `skipped_links`, and the drawn number is recorded as a **sequenced absence of the whole range** (`ScanResult.absent_ranges`); the apply removes a range item only when that number is later than the item's `read_seq` (the same result a full scan gives, which never enters that link — round 4 must 1). The same rule covers a partial scan whose `under` is gone: the number drawn before opening `under` becomes the range's absence when the open answers `NotFound`; any other error puts the range in `kept`. Inside a walk `follow_links(false)`; an entry that is a link (file or directory — `StdLaunchFs::is_link` semantics) is not entered and not listed but recorded in `skipped_links`, which `refresh` returns. `first_link` checks each component below the root with `symlink_metadata` (cheap, local); `MemStore` models links. It is the **one** component test used by the partial scan, the `list` safety net, `check`'s overlay reads and every late merge (§6).
- `filter_entry` drops what `admits` refuses (names starting with `.`, `base::file::is_temp_name` names). The same `admits` + `first_link` + kind sniff gate the safety net and late merges, so a late merge admits only paths the scan would admit.
- **Per-folder listing sequence** (must 6 · ADR-0324 decision 5 · premise 47): walkdir opens a folder (`fs::read_dir`) inside the `next()` call that **yields** that folder's entry, and reads its entries in later calls. So the scan draws `seq()` **before every `next()` call**; when the call yields folder D, the number drawn before it becomes `listed_at[D]` — it precedes every read of D's entries, which is ADR-0324's "the number from before it listed that folder". A file inside the scan range that the listing does not contain counts as read 「absent」 at `listed_at[its parent]` (or, when the parent itself is gone, at the `listed_at` of its nearest listed ancestor). One number per scan (draft 2's `listed_seq`) could not do this: a deep folder listed late would carry an early number and lose to a check that read the file before it was deleted. (Draft 3 drew the number when the folder was yielded — after walkdir had already opened it.) **Where this is tested**: the production boundary on a real `FsStore` (P5 — a file of D deleted inside the `seq` draw that precedes the yield of D is not listed, and `listed_at[D]` is that draw; it fails if walkdir ever reads a folder earlier); the merge interleavings on `MemStore` with hooks (P7).
- **A failed read keeps what was known** (recommended): a folder in `errors` (permission, a transient IO error, an enumeration that fails part-way) keeps its previous items unchanged in the scan's apply — for a part-way failure, the items the walk did list are taken and the rest of that folder's previous items are kept; a single file whose metadata or read fails keeps its previous item. They are outside what the scan could see, so a transient error never turns them into a false 「찾을 수 없음」; `refresh` reports the error.
- `trash` is a same-root rename (B8 · G31).
- **As landed (P5 — departures the coder reported, accepted in review)**: the root's key in `listed_at` is `None` (`HashMap<Option<LibPath>, u64>` — an empty `LibPath` is not valid), and `errors` · `kept` use `Option<LibPath>` the same way; `ScanListing` also carries `root`, `absent_ranges` and a per-entry `seq` (`ScanEntry.seq`); `ScanResult` adds `folders`, `no_kind` and `scanned_at`; catalog keys are `catalog::key` (the relative spelling's key), not `LibPath::key(root)`. **Library read cap** (user 2026-11-12): a library file is read through the store with `LIBRARY_READ_CAP` = 16 MiB (`lib.rs`); a longer file is a failed read — its item is kept as it was and the scan reports the error. Internal constant; a setting later (tracking T-105).

- Expansion order, dedup at first place, cycle, per-preset tag order (G51), conflicts on loaded skills only, notices, folder lines, block ④ (a library preset attached while `root` ≠ `Ok`). **Block ④ stands alone** (ADR-0361 decision 1 — user 2026-11-12; replaces parent §1-3 8 "④ beside ①–③"): `resolve` returns early with `Resolution { problems: [④], ..default }` — no expansion, no item or folder rows, no rows for unparsed attached paths, no notices; nothing is computed from the catalog while the root is unusable. - **Budgets** (ADR-0360 — amends D1 · B25): a **launch** waits at most **60 s required + 2 s advisory** (agent `types.rs` `LAUNCH_REQUIRED_FOLDER_WAIT_SECS` · `LAUNCH_ADVISORY_FOLDER_WAIT_SECS` — the inputs from which agent derives the launch reply bound, 85 s, and the launch caller wait, 88 s — §3-10); a **read computation** outside a launch keeps **5 s** (decision 4) — and 5 s is also the aged-worker cutoff below ("one full limit"). The same values hold for every bounded folder operation: stat, listing, canonicalize, file read. As landed (P6 · P7), `BoundedIo::new(limit, launch, list_cap, ops, spawn)` takes them (production `IO_LIMIT` = 5 s · `LaunchWaits::LAUNCH` · `LIST_CAP`), so tests shorten them there; `LibraryValues` has no `io_limit` / `launch_waits`. A read computation's advisory allowance is `READ_ADVISORY_WAIT` = 1 s. (Draft 9: one limit of 5 s for both, D1 — replaced U2's 10 s.)
- **One budget per launch** (D1): a launch is `check_before_create` → `prelaunch` (up to `PRELAUNCH_ATTEMPTS` checks) → `prepare` → the manager's working-folder canonicalize — premises 10 · 42. All of them run in one `LaunchScope` (§3-9) holding one `LaunchIo` from `begin_launch()`, so they share **one 60 s required budget and one answer set** (ADR-0360): a folder answered earlier in the launch is not asked again in the same launch (a second check after an attachment change asks only the new keys, on the time left). A read computation outside a launch — `resolve_preset`, `resolve_agent` (`agent.presets`, `preset.get`), `resolve_agents` (tree ⛔ over many agents — §3-11) — calls `begin_read()` once and gets one 5 s budget for the whole computation. **Advisory IO has its own allowance** (2 s per launch — next bullet) and is never charged to the required budget. So the user-visible worst case of folder IO per blocked launch is **60 s required + 2 s advisory = 62 s, then a block (nothing spawns)**; a successful launch adds the activation waits (the 3 s resume window, the 15 s codex link backstop — premise 54) and reaches its reply after at most 80 s, **inside the 85 s launch reply bound** (ADR-0360 — 5 s slack for parsing, locks, spawning and the reply); a check already blocked by its required work skips the advisory phase (B30), so a blocked reply needs at most 60 s **when no earlier check of the launch used advisory time**; the launch-wide bound stays 62 s. (Draft 9: 5 s + 1 s = 6 s inside the 7 s bus slot.)
- **The budget is charged only by IO waiting** (must 3): a batch waits until at most `now + left`, then subtracts the time it actually waited. Time spent waiting for the library lock, the gate, parsing or any other work is never charged, so a read-lock stall (ADR-0324 M47 — accepted) cannot use up the budget and turn a healthy folder into ①. **When nothing is left, no worker starts**: every key the `LaunchIo` has not already got answers at once `Unreadable("not checked (budget spent)")` — a diagnostic distinct from `Unreadable("timeout")` (an op that was started and did not answer in time). Both count as unreadable for the rules below.
- **Two phases per check — required first, advisory on its own allowance** (class B rule, round 3). **Required** = everything whose failure blocks the launch: the library-root stat (only with a library preset attached), folder-entry stats, listings (when `folder_listing_at_launch`) and the port's reads of folder-entry files, and `prepare`'s material reads. **Advisory** = everything that only feeds a notice or a best-effort value: the working-folder canonicalize, native-root discovery and the native roots' stats, listings, reads and canonicals, and the canonicals of folder-entry roots (same-name identity). The **required phase** runs first and alone — no advisory key shares its batches or its waiting — and waits until its keys answer or the launch budget is spent. The **advisory phase** starts only after the required phase of that check finished, and waits at most `advisory_left` — 2 s **per launch** (`LAUNCH_ADVISORY_FOLDER_WAIT` — ADR-0360; draft 9: `ADVISORY_WAIT` = 1 s) (one allowance across every check and the prepare of the launch), **kept apart from the required budget** (main, round 3): advisory waiting is never charged to `left`, so every required stage of the launch — a second `prelaunch` attempt, `prepare`'s material reads — has the untouched required budget, whatever the advisory phases used. Required work never waits for advisory work, and advisory work never takes required time. The cap is kept (my call — B25): without it, a dead native root (e.g. `<CODEX_HOME>/skills` on a dead share — premise 50) would delay **every** launch of that agent for as long as advisory work were allowed to wait; with it, every launch pays at most 2 s, and that time never comes out of the required 60 s.
- **An advisory answer that is missing is never substituted** (class B rule 3): no canonical cwd ⇒ the launch uses the raw `profile.cwd` (logged only — no launch notice; B29, user 2026-11-12) and native-root discovery and the same-name comparison are **skipped for this launch** (logged; the ADR-0355 hint is lost for that launch — accepted); a root (folder-entry skill root or native root) whose canonical identity is unknown is **excluded** from the same-name comparison (logged) — never compared by its lexical path, which could manufacture a collision between two spellings of one folder (ADR-0355 requires canonical dedup). The library root's canonical path is asked in the same advisory `canonical_all` batch as the other roots of the comparison (as landed, P9 — draft 12 said "with the store"); unanswered = the library's skills are left out of the comparison, logged.
- **Required wins over advisory for one key** (class B rule 5): a key asked both ways is required. Only real op answers are stored in the `LaunchIo` (an `Ok`, an OS error, or a required-phase timeout); an advisory "not checked", or an advisory wait that ended before the op answered, is **never stored**, so a later required ask of the same key asks again (joining the in-flight worker if one runs). This removes an order dependency: the outcome of a required key no longer depends on whether an advisory ask of the same key happened earlier in the launch (e.g. a native root that is also a folder entry, or a cwd that is also a folder entry, asked first by an earlier check's advisory phase). **No worker starts for an advisory key once the advisory allowance is spent** — it answers "not checked" at once.
- **Concurrent per batch**: a call takes every distinct key it needs at once, starts one worker per key that has no call in flight, and waits on all of them against the same deadline. N unreachable folders therefore cost one budget in total, not N budgets.
- **Entry lifetime** (must 2): the in-flight map holds only calls that are running. A new call inserts its `Pending` under the `inflight` lock, **releases the lock, then spawns** the worker. The worker removes its entry (only if the map still holds the same `Arc` — `Arc::ptr_eq`) when it completes; joiners hold their own `Arc<Pending>` and read the answer from it. A completed answer lives only in the `LaunchIo` that asked for it and dies with it, so a folder that answered `Missing` is asked again by the next launch (a folder created in between is seen). The worker's job owns a **completion guard** whose `Drop` fills an empty answer (`Unreadable("worker panicked")`) and wakes every waiter under the `Pending`'s answer mutex, **releases it, then** takes `inflight` to remove the entry — the two mutexes are taken one after the other, never nested. The guard runs on a panic and also when `Spawn::spawn` fails and drops the job unrun (the answer is then `Unreadable("spawn failed")` — as landed, the OS error is logged, not carried in the answer). **Joining a running worker depends on the ask** (round 4 must 2 — required wins): a **required** ask always joins a pending worker for its key, whatever the worker's age, and waits for it up to the remaining required budget — so a key an advisory ask started earlier (even in an earlier check of the launch, or a hung one from an earlier launch) still answers a required ask the moment the op returns. An **advisory** ask does not join a worker that has already run longer than one full limit: it answers "not checked" at once (no advisory time is spent on an op that is probably hung) — the cutoff applies only to advisory asks, within a launch and across launches. Either way there is still one worker per key (the worker removes its entry when it returns; the next caller after that starts fresh), so abandoned workers stay bounded by the distinct keys that hang.
- **Bounded file reads** (must 1): the port passes **folder-relative** paths to `read` (`settings_check.rs:65-67`), so the closure handed to `folder_load_set` / `root_skills` joins the folder root and keys by the absolute path: `|rel| io.read_one(&launch_io, &root.join(rel), need, false)` — `need` = `Required` for a folder entry (required phase), `Advisory` for a native root (advisory phase). `prepare`'s read of a folder instruction file is `read_one(…, Required, true)`. **A fresh read never joins a pending worker** (round 5): a read that began before the fresh request could return the bytes from before an atomic replacement and let it escape the stamp comparison, so a fresh ask always starts its own worker (one extra worker for that key is allowed; it is not registered for joiners). Each read is one key on the same budget and per-file cap (a named constant — as landed `folder.rs` `READ_CAP` = 16 MiB; over it = an error the port records as `unsure`). The port calls `read` one file at a time, and each call waits only for the time left of its phase, so a held file read still ends the whole check inside the budget. **What a read timeout becomes depends on the call site**: the closure returns `ErrorKind::TimedOut` and the port files that row as `unsure` (its rule — premise 43); asset-library, which owns the closure, then marks a **folder entry** `Unreadable("timeout")` ⇒ ① for the launch, and leaves a **native root** out of the comparison (B24). A read error that is not a timeout (permission, file too large) stays the port's `unsure` row — a preview mark, no block, as today. **A failed worker is no answer** (as landed, P9 — main): every unanswered read — timeout, not checked (budget spent), spawn failed, worker panicked — reaches the closure as `ErrorKind::TimedOut`, so a folder entry is ① and a native root is left out, never an `unsure` preview row about a file nobody read (P6 had mapped a spawn failure to `Other`).
- **Over the budget = unreadable = block ①** for the whole launch, for a **folder entry** (ADR-0341 decision 6, user re-confirmed 2026-11-11 「그냥 하나 막혀도 전체 막는게 좋겠지? 구지 무리하게 실행하는것보다는」). The **library root** is stat'ed only when the profile attaches at least one library preset (an attachment that is not `engram:/…`); a root stat that does not answer = `RootState::Unavailable("timeout")` ⇒ ④. Without a library preset the root is not asked (it decides nothing). A **native skill root**: unanswered = left out of the comparison and logged; no block (B24). The **working folder**: unanswered = the raw `profile.cwd`, logged only; **no block, no notice** (B29 — main, round 3; the draft-9 notice withdrawn by the user 2026-11-12) — a cwd timeout never appears as a folder-entry ① line, because it is not asked in the required phase where ① lines come from.
- **Listing cap 10,000 entries**: `FolderOps::list` walks depth-first with std `read_dir` per level — **not** walkdir's `sort_by`, which collects a whole level into memory inside `push` before the walk can count it (`walkdir-2.5.0/src/lib.rs:913-921`, premise 52). Each level reads at most the remaining cap entries, then sorts what it read **files first, then folders, each by name**, so a folder's own files (`AGENTS.md`, `CLAUDE.md`) and its `.agents` · `.claude` · `.codex` folders come before `.git` or `node_modules` (`.` sorts before letters); memory stays bounded by the cap. Past the cap the listing stops and is marked `truncated` (a level cut part-way is sorted only over what was read); the preview says it is partial, nothing blocks (U2), and the launch reply carries the notice `folder-listing-partial` (`args` = `{folder}`) (B22). The port keeps the listing order in its result (`settings_check.rs:65`), so preview rows follow this order. **An unreadable folder below the entry is skipped** (ADR-0363 — user 2026-11-12, after a convention survey: codex skill discovery, ripgrep, find, git and walkdir skip and warn): below the listed folder, a subfolder whose read fails (at open or part-way — the entries already read are kept) or an entry whose type cannot be read is left out, named in `FolderListing.skipped` (one warning per listing), and the walk goes on; the launch reply carries `folder-listing-skipped` (`args` `{folder, paths}` — the sentence names the first three paths, then 「외 n개」; own wording — ADR-0364); no block. The listed folder itself unreadable at open or part-way through its own level still fails the listing ⇒ ① (ADR-0341 decision 6). An entry whose type cannot be read counts toward the cap.
- **Folder IO never runs under the library lock** (§6); a test fake op asserts `try_write` on the library lock succeeds while it runs.

7. **Decide** (no IO): `folder_load_set(…, YamlFrontMatter, mode)` per listed folder entry — its **`carried`** rows give the instruction file and the extra skill roots the plan carries (never `loads`, which is the preview — must 9), its `omitted` gives a `codes.folder_omitted` notice; the same-name comparison over the roots whose canonical identity is known (library skill names + folder `skill_names` + `root_skills` per answered native root, each `SKILL.md` kept once per canonical path — step-6 hand-over (a)) gives one `codes.same_name` notice per name; `command_line_args` + `command_line_fits` with `cwd` = the decided cwd (canonical, else raw) and `instructions` = `merge_instructions(…)` over what this mode loads; `working_folder_blocks(decided cwd, mode)` (hand-over (d); `materialize` re-applies the rule on the cwd it gets — ADR-0353); `folder_entry_blocks` per folder. The decided cwd is stored in the scope for `working_folder`. **The two refusal rows not about a library file carry a kind tag** in `BlockReason.item` (ADR-0361 decision 3 — user 2026-11-13): `command-line:<backend word>` for the `command_line_fits` refusal and `working-folder:<path>` for `working_folder_blocks`, both with an empty `via`. **The merged instructions put each folder entry's carried instruction file right after the own instruction lines of the preset that lists the folder at its first place** (`ResolvedFolder.instructions_at` — parent §1-5; user 2026-11-13 「A 하고 B 폴더가 있으면 순서대로해야지.」); the judged text, `plan.instructions` and `prepare_in`'s file come from one source list.
8. **Hand off the late merge** (main, round 2 — ADR-0366 decision 2; as landed it runs right after step 4, see there): `check_in` puts the overlay and the noted numbers in a **take-once slot** (`Arc<Mutex<Option<MergeWork>>>`) that lives outside the job, and spawns a short-lived merge job (through the `Spawn` seam) that holds only a clone of the slot's `Arc`. The job takes the work out of the slot, then takes the library write lock **normally** — it waits behind any writer, so a contended lock delays the merge but never drops it — applies the conditional late merge per item (§6) — positive observations only, never a removal (B31) — and ends. The launch never waits on the write lock. If `Spawn::spawn` fails (it consumes and drops the boxed job), `check_in` still holds the slot, takes the work out itself and runs the merge inline (logged — the one case where `check` may wait on the lock; it needs an OS thread-creation failure). The slot makes the merge run exactly once whichever side takes it.
9. Problems ⇒ `Err(LaunchBlocked)` in the §1-3 8 order; else `Ok(LaunchPlan { real: true, … })`. When `loads.instructions == BuiltinPrimingOnly`, the plan carries no instruction sources; when `loads.skills == false`, the plan carries no skills; the omitted ones of both go into one `codes.omitted` notice (hand-over (b)). Notices carry identity-only `args` (premise 12) — except `builtin-unavailable`'s `why`, a diagnostic that enters the fingerprint on purpose (built-ins are read once; a changed failure shows the notice again — ADR-0361 「영향」). The plan's `stamp` records the SHA-256 of every **material source** (B7 · must 7 · round 2 must 3): the library preset, settings and instruction files the resolution used, the `SKILL.md` of every skill the plan carries, and each folder instruction file in `carried` — the files `PrepareError::Stale` is about (premise 49). Files read only for a notice or the preview (native-root `SKILL.md` files, a folder entry's files outside `carried`, claude folder files) are not stamped, so their change never makes `prepare` stale.

**`prepare_in`**: no library lock (must 7). Create `<launch_root>\<id>-<epoch>\`; re-read each source in the plan's `stamp` (library files with the store; a folder instruction file with `read_one(…, Required, fresh: true)` on the scope's budget) and compare the SHA-256 with the stamp — gone (not found, not a file) or different bytes ⇒ `Stale` (byte-exact: an in-place edit of the same length with the same mtime is caught; ADR-0336 sha2); **a folder read that timed out or was not checked (budget spent) ⇒ `Failed("folder-timeout: <folder>")`** (main, round 2 — a slow read is not a changed source; `Stale` keeps its documented meaning, premise 49); write the merged instructions file with `merge_instructions` from the bytes just read (priming first when `include_priming`, then the plan's sources in order — §1-5 L318); `instructions_hash` = B9; `last_applied_instructions_hash = None` (hand-over (e)); `include_priming = true` ⇒ always an `instructions_file` (hand-over (e)). Other failures ⇒ `Failed`.

**`release`** / **`sweep_launch_dir`**: walk the volatile folder depth-first without following links; every entry `StdLaunchFs.is_link` reports is detached with platform `unlink_dir` (any depth — hand-over (f)); a launch root that is itself a link is reported, never enumerated (as landed — P9 review round 1 found the sweep enumerating it: data loss); then remove files and folders; errors are logged, left and listed in `SweepReport.left` (best effort, bounded, no retry, no lock, no panic — §5-2 4 (c2) ⑤). Idempotent.

## 4. Data shapes on disk

Unchanged from the parent §1-2 except the writer (ADR-0358).

- **Kinds** — §1-2 table. `.yaml`/`.yml` with top-level `kind: preset` / `kind: settings`; broken or unknown `kind` = 「오류」 row; no `kind` = not ours (not listed; `refresh` reports 「kind 없음」 for re-read ones); `SKILL.md` directly in a folder = skill (name per the OS rule — `same_path`); any other `.md` = instruction; names starting with `.`, base temp names and anything reached through a link inside the library (U1 — on every path, §3-5) are not scanned, listed or merged.
- **Preset** — `kind` · `version` · optional `description` · `presets` · `instructions` · `skills` · `settings` · `folders` · any other key (kept by edits). **Two item shapes** (M20): a string (common) or `{path, backend}` — only in `instructions` and `skills`; `backend` = any word the backend registry knows; a tag in `presets` / `settings` = broken line; other keys inside an item map are kept by edits. `folders` = plain absolute strings only.
- **Settings** — `kind` · `version` · optional `description` · raw fields named by backend word (case ignored; today `claude` = the settings object, `codex` = a list of `key=value` strings — the shape is the port's knowledge).
- **Folders read/write** — read into `FolderRef { raw, normalized }`; a read never rewrites the file; `resolve` keys by `path_key(normalized)`; writes (9a) store the normalized form for new or changed entries; untouched entries keep their raw spelling (9a passes it through — §3-4).
- **Edits rewrite the whole file** (ADR-0358 · §3-4 write): serde-saphyr serializer, 2-space indent, YAML 1.1-safe quoting, the original line ending and BOM kept; comments, blank lines, quoting and flow style are not kept; unmodeled keys (top level and inside items), their order, and list entries the reader could not model are kept; a multi-document file and a file holding an integer beyond 64 bits are refused.
- **Volatile layout** (written by `prepare` only): `<launch_root>\<id>-<epoch>\` + the merged instructions file (name B14); backend `materialize` adds the rest inside it.

## 6. Concurrency and IO

The rule set is ADR-0324 / parent §1-4 flow ① 「잠금」 ①–⑤, implemented once in `gate.rs` + `lib.rs`:

- **One `std::sync::RwLock<State>`** (`State` = `Arc<Catalog>` · the root `Option<PathBuf>` — as landed the root state is computed per read, not stored; draft 8's schema generation is gone — ADR-0359). Reads take it once; a write never happens while holding the read lock (no upgrade).
- **Class A rule — no whole-catalog swap, ever** (round 3; ADR-0324 decisions 4–5 · M34; recorded as ADR-0366 decision 1): **every write to `Catalog` is applied per item onto the current catalog under the write lock** (`Arc::make_mut`; items are `Arc<Item>`, so a clone forced by a reader holding the `Arc` is shallow). Per item the later `read_seq` wins; items outside a scan's range are untouched; derived data (`used_by`) is recomputed for the touched items only (`Catalog::recompute_derived`). Walking, reading and parsing stay outside the lock; only the apply is under it. No writer builds a catalog and swaps it in: a whole-catalog swap would revert every late merge and safety-net insert that landed while it was being built, because those do not move the change generation (draft 4 still let the scan do this). The writers, all through `Catalog::apply_items` / `apply_scan` / `remove`:
  1. **Scan apply** (first scan, `refresh`, the first scan after a root change): `ScanResult` built outside the lock; `apply_scan` under the write lock, only if the change generation is unchanged since the walk started (else rescan); raises the swap-in count before releasing.
  2. **`check`'s late merge** (the handed-off job — §3-8 step 8): `apply_items(overlay items, may_insert)` with the conditional rule below — **positive observations only; it never removes** (main, round 5 — B31 · ADR-0366 decision 2).
  3. **`list`'s safety net**: `apply_items([one item], may_insert)`, same rule.
  4. ~~**Schema re-check**~~ — not built (ADR-0359: no schema, so a settings verdict never changes without its file changing; ADR-0324 decision 8 amended). The numbering is kept so the references to writers 5 and 6 hold.
  5. **Changes in later steps** (9a edits, 9b ops, relink): per item under the write lock, with ticket, in-progress count and change generation (ADR-0324 「영향」) — this rule binds them. A change that removes an item draws its sequence under the write lock, so it is later than every read noted before it.
  6. **Root change — exclusive, a full fresh build, one publish** (main, round 6 · ADR-0366 decision 3; 9a `setRoot`, the first-start default root — parent L209 "the new root and its `Catalog`" in one write lock). The gate's `change_root(new_root, walk)`:
     0. **Stat first, outside the gate** (round 7 · recommended): before drawing its ticket, `change_root` stats the new root through `BoundedIo` (one 5 s budget); missing, not a folder, unreadable or unanswered ⇒ the root change is refused at once without ever holding the gate.
     1. **Exclusive from its ticket to its publish.** It enters only when every earlier ticket has finished and marks a root change in progress; every later change and scan waits behind it (FIFO), so a 9a edit ordered after `setRoot` can no longer enter during the walk and write into the old library (round 6 concurrency). Edits queued behind it may pass their own bus deadline and still run, as behind a first scan (parent finding 17). Readers keep reading the old root's catalog meanwhile — never an empty one.
     2. **A full fresh build.** The new root is walked with **empty tags**: every file is read fresh and keyed by the new root — no `Unchanged` against the old catalog, no `kept` items from it. (Draft 7 decided `Unchanged` against the old catalog's tags: changing `D:\lib` → `D:\lib\team` made `X.md` `Unchanged`, and the `clear` then dropped it — round 6 codex.)
     3. **One publish**, in one write lock: `clear` (items, tags, `used_by`, `refs_to`) + apply the fresh build + publish the new root + raise the root generation + set the first-scan state to "raised" (this also covers the first-start default root, which had never been raised). The apply needs **no change-generation recheck**: the exclusive ticket kept every change and scan out, and the only other writers that can run meanwhile — `check`'s late merges and `list`'s safety-net inserts — wrote into the catalog the `clear` discards, and any of them noted before the publish is discarded afterwards by the raised root generation (ADR-0324 decision 5).
     4. **A walk that fails at the root publishes nothing**: the old root and its catalog stay, the root change is refused (answered per ADR-0324 decision 6), and the ticket is released. **The exclusive ticket and "root change in progress" are released on every exit** — publish, failure at the root, error return, and a panic inside a contained test context — by a drop guard next to the P7 gate guard (the same shape as ADR-0324 decision 9's waiting-count guard). A folder of the new root whose walk fails is published without items (nothing of that root to keep) and `refresh` reports it. Readers that arrive at the first-scan entrance during a first-start root walk wait for that walk instead of queuing a second full scan.
     Class A's per-item rule does not apply here: the catalog is replaced only by a full build of a different root under an exclusive ticket, and the raised root generation discards every merge noted before it. (Draft 6 cleared before scanning — readers saw an empty catalog, ADR-0324 M48; draft 7 scanned first but let later changes in during the walk and reused old tags.)
  Re-checked against the rule: none of the writers builds a catalog and swaps it in; the only `Arc<Catalog>` clone left is a reader's (a scan reads current tags under a brief read lock to decide what to re-read, and writes nothing from that clone).
- **Scan-generation `Mutex` + `Condvar`** (a leaf — nothing else is taken while holding it; the library lock is never held while waiting on it): ticket counter (FIFO), scan in progress, changes in progress, change generation, root generation, swap-in count, first-scan state ("raised" = one full scan applied — set by a first scan or by a root change's publish), root change in progress (exclusive from its ticket to its publish — writer 6), queued refresh generations with their range. `notify_all` on every release.
- **Other leaves** (recommended): `BoundedIo`'s in-flight `Mutex`, each `Pending`'s answer `Mutex`, and a `LaunchIo`'s budget and answer `Mutex`es. None of them is held while taking another lock, while running an IO op, or while waiting.
- **Scan**: walk + parse **outside** the library lock into a `ScanResult` (no catalog); the apply (ADR-0324's "swap-in") runs under the write lock **only if** the change generation is unchanged since the scan started (else rescan); it raises the swap-in count before releasing; it writes items inside its range only and per item: a `Fresh` item wins when its `read_seq` is later than the current item's; an `Unchanged` entry writes nothing; an item the listing did not contain is removed only when its folder's `listed_at` is later than its `read_seq` (§3-5 · must 6). Folders and files in `kept` (read errors) keep their current items.
- **First-scan join** at the entrance of every `Catalog`-reading method (`list` · `resolve_preset` · `resolve_agent` · `resolve_agents` · later 9a edits) — before any ticket, count or lock. `check` is **not** an entrance and never waits for a scan (ADR-0324 decision 6 — tested with a scan held at the gate).
- **Refresh merging** (⑤ — ADR-0324 decision 7's "fold" means this join, ADR-0366 decision 4; a queued generation that does not cover the refresh is never widened): a `refresh` joins a covering generation that is queued and not yet walking; a covering walk already in progress ⇒ its own ticket. Before the first scan is raised, a folder `refresh` goes through the first-scan entrance (and re-checks "raised" on waking).
- **Conditional late merge** (④) — writers: `check`'s fresh bytes and `list`'s one-path safety net. Both note the three numbers **before** the disk read; in the short write lock: change or root generation moved ⇒ discard all; only the swap-in count moved ⇒ discard inserts of paths not in `Catalog`, keep updates of existing items when `read_seq` is later. **In every case the later `read_seq` wins over an item already in `Catalog`, even when the three numbers are unchanged** (an item a scan applied with a later read must not be replaced by an older read). **Admission** (must 5): a late merge and the safety net take only paths that pass `admits`, `first_link` (no link below the root) and the kind sniff — a path the scan would not admit is never merged; the safety net answers it as a skipped or broken row with the code `path-through-link` (a link) or not at all (a dot or temp name). **`check`'s merge is handed off** to a short-lived job that takes the write lock normally (main, round 2 — §3-8 step 8): a contended lock delays it, nothing skips it, and the launch never waits on it. The gate API gives the noted numbers: `gate.numbers() -> Numbers` before the read, `late_merge(noted, f)` under the write lock.
- **Every removal is sequenced, and only scans and changes remove** (round 4 must 1 · round 5): (a) an item of a scan range that the listing does not contain — `listed_at[its parent]`, or of its nearest listed ancestor when the parent is gone; (b) a partial scan whose `under` is a link inside the library — the seq drawn before `first_link`, as `absent_ranges` (draft 5 had no number here); (c) a partial scan whose `under` is not found — the seq drawn before opening it, as `absent_ranges` (draft 5 had no number here either); (d) a folder that became a link inside a walk — its former items are absent from the listing of the link's parent, so (a) covers them; (e) **`check` removes nothing** (main, round 5): its handed-off merge carries positive observations only; a file `check` found missing stays in `Catalog` until a scan or a change removes it (draft 6's sequenced check-time absence is dropped — §10-2 B31); (f) a change (9a / 9b) that deletes or moves an item — its seq is drawn under the write lock; (g) a root change — the catalog is cleared (writer 6), no per-item removal; (h) a missing library root removes nothing (`RootState::Unavailable` ⇒ ④ — a transient outage must not empty the catalog); (i) a failed read (`kept`) removes nothing. `remove` refuses any removal whose number is not later than the item's `read_seq`. Removals therefore come only from scans (listing absences, `absent_ranges`) and changes (9a/9b deletes and moves, the root change).
- **What the conservative insert rule costs — stated per landing order** (round 2 must 5). ADR-0324 decision 5 discards an insert when a swap-in (a scan's apply) intervened, and step 7 keeps that rule unchanged. With a file X created after the scan listed its folder (scan `listed_at` = 12, X absent; a check reads X at 15): **check's merge lands first** ⇒ X is inserted (read 15) and the swap-in keeps it (absent at 12 < 15) ⇒ X present; **the swap-in lands first** ⇒ the swap-in count moved, so the check's insert of X (not in `Catalog`) is discarded ⇒ X is not in `Catalog` until the next scan or a `list` safety net with no swap-in in between. The launch itself is unaffected (it used its overlay); only `Catalog`'s freshness lags. Admitting that insert would need the comparison "read_seq > the intervening scan's `listed_at[parent]`" kept per swap-in — a change to ADR-0324 decision 5's text, not taken here (the cost is one stale list row until the next refresh, and the rule is the one the ADR's six review rounds settled).
- ~~**Schema re-check** = a change~~ — dropped with writer 4 (ADR-0359).
- **Folder IO — bounded, concurrent, never under the library lock** (D1 · U2 · class B): every stat · listing · canonicalize · file read on a folder entry, a native skill root, the working folder or the library root goes through `BoundedIo`. One launch (all its checks, its prepare and the manager's working-folder canonicalize) has **one 60 s required budget**, and one read computation (`resolve_preset`, `resolve_agent`, `resolve_agents` for tree ⛔ over many agents) **one 5 s budget** (ADR-0360), each charged only by time spent waiting on that IO (must 3). Each `check_in` runs a **required phase** (the library-root stat when a library preset is attached; folder-entry stats; folder-entry listings and reads) and only then an **advisory phase** (working-folder canonicalize; native-root discovery from the canonical cwd; native-root stats, listings, reads; root canonicals) on its own advisory allowance (2 s per launch, never charged to the required budget) — never mixed in one batch (§3-8). Worst case per blocked launch: 60 s required + 2 s advisory = 62 s, then a block; a success at most 80 s with the activation waits, inside the 85 s launch reply bound (ADR-0360). One in-flight call per key; each distinct key once per launch (a required ask is never answered by a stored advisory miss); a folder entry unanswered when the budget is spent = unreadable = ① (§3-8 for the root, the cwd and native roots).
- **Library files** inside the root are read with the store directly (local by assumption — a network root is R4).
- **Pre-write checks** — `format::write::rewrite_lists` refuses out-of-range integers and re-parses its own output and compares it with the edited tree before returning (§3-4 steps 3 · 6); `FsStore::write_atomic` stats the parent first: missing ⇒ `NotFound` (nothing created). The gap between that stat and base's folder creation remains (B4).
- **Lock order** with the manager (ADR-0324): asset-library lock → manager locks, one direction; `check_in` holds no manager lock and calls only registry reads (`launch.rs:549-551`); its handed-off merge job takes only the library write lock. `prepare_in`, `working_folder` and `release` take no library lock.
