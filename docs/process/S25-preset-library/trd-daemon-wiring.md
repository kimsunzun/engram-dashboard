## 0. Scope

Lands: the daemon builds `LibraryService` and plugs it as the manager's `LaunchKitSource`; the manager runs one launch scope per launch; the first-turn instructions hash is recorded; the launch waits follow ADR-0360 at every Engram-owned entrance; the debug QA hook leaves. Not here: a library root (`LibraryValues.root = None` until 9a), the first-start default root and `daemon_id` (9a), any command that attaches a library preset (9a/10a — no step-8 create entrance carries one: `agent.spawn` takes `target`/`cwd`/`name` (agent `commands.rs`), `SpawnByCwd` takes `cwd`/`backend`, and `AgentProfile::new` attaches only 「기본」), the R5 priming sentence (10a), the webview showing launch notices (11), the agent tree's ⛔ and `failed_reason` (§2-4 6 — open for step 13, §8 B3). ## 2. Manager (agent crate)

- **One scope per launch**: `kits.begin_launch()` once at the head of `manager.rs` `spawn_agent_watching_link`, after the spawn reservation and the "already running" check (no IO before either). Every launch passes through that function — create (`create_and_activate` → `ensure_registered`), restore (`spawn_fresh_settled`), resume (`resume_no_fallback`) — so this one call meets child §12 D1. The scope is dropped when the function returns.
- The scope reaches `check_before_create` (via `ensure_registered`), both `prelaunch` attempts and `prepare` through `check_in` / `prepare_in`. One scope = one `LaunchIo`, which keeps each folder answer for the whole launch (`folder.rs` module rules; `phase`) — a key asked once is not asked again within that launch; library files are re-read by every check (the overlay — asset-library `launch.rs` `read_overlay`).
- `let cwd = dunce::canonicalize(&profile.cwd)…` (after the registry re-read) becomes `self.launch.kits.working_folder(&scope, &profile.cwd)` on the re-read profile. The agent crate keeps its `dunce` dependency (the trait default uses it).
- **First-turn instructions hash** (step-6 hand-over (a); same commit as real kits — §7 U3): the manager wraps `latch.first_turn_sink()`; after the inner sink runs, it records `kit.instructions_hash` once when `latch.first_turn_delivered() == Some(true)` (skipped when the hash is `None`). Since the latch keeps the first report (`session_id_latch.rs` `first_turn_sink`), `false` then `true` records nothing. `first_turn_delivered` therefore becomes a production reader: its `TODO(TRD S25 §5-2 4 (b))` and `allow(dead_code)` go. New `ProfileRegistry::record_instructions_hash(id, incarnation, hash) -> bool`, modelled on `record_notice_fingerprint` (incarnation guard, no write when equal, save failure stays dirty). Separate from the session-id commit, which is unchanged. Backend-neutral (ADR-0004). Removes the `manager.rs` `TODO(TRD S25 §5-2 4 (b))`.
- Source guards to rewrite (not delete): `manager/prelaunch.rs` counts of `.kits.check(` / `.kits.prepare(` (→ `_in`) and its pin on `dunce::canonicalize(&profile.cwd)`; `manager.rs` pins on `Some(latch.first_turn_sink())`.
- Out of scope: `TODO(TRD S25 §5-2 4 (a))` (command/env from the re-read registry) — not a step-8 hand-over.

## 4. Launch entrances (ADR-0360)

Rule: a direct caller waits ≥ the launch reply bound + the margin; where waits nest, outer ≥ inner + margin (equality allowed). Current values verified at `c1e4b532`. Shell side = §8 C2 (decided 2026-11-14: launch requests only get a per-request deadline; ordinary requests keep 30 s).

**The derivation chain** (user condition, §8 C2 — every launch wait is a sum of named constants from one base and one margin; no independent literal):

| Name (placeholder) | = | Value | Used by |
|---|---|---|---|
| base `LAUNCH_REPLY_BOUND_SECS` | the ADR-0360 budgets (folder waits 60 + 2, `EARLY_EXIT_WINDOW` 3, `LINK_RESOLUTION_BACKSTOP` 15, slack 5) — already derived | 85 | the daemon's seat for its own launch-class name |
| margin `LAUNCH_MARGIN_SECS` | `DAEMON_SWEEP_SECS + DAEMON_CALLER_MARGIN_SECS` (1 + 2) — the same quantity as two daemon↔shell hops (`VIEW_HOP_MARGIN` precedent) | 3 | every step below |
| W1 `LAUNCH_CALLER_WAIT_SECS` | base + margin (redefined as this sum; value unchanged) | 88 | shell `Spawn` / `SpawnByCwd` / `SpawnProfile`; the shell's inner wait in the relay |
| W2 `LAUNCH_RELAY_SEAT_SECS` | W1 + margin | 91 | the daemon's seat for a relayed launch-class name (`agent.spawnInto`) |
| W3 `LAUNCH_RELAY_CALLER_WAIT_SECS` | W2 + margin | 94 | the CLI for every launch verb (B7); reserved for the shell's wait on a launch-class socket envelope (deferred — B14) |

Outside the chain, unchanged: the shell's ordinary `REQUEST_TIMEOUT` 30 s (ADR-0181 — ordinary requests), the daemon's `DEFAULT_DEADLINE` 7 s and the CLI's 10 s (ADR-0161 chain). Changing a budget moves the base and therefore W1–W3; changing the margin moves all three.

**Where each constant lives** (the shell does not depend on agent — ADR-0270 d1; ADR-0360 d6 prescribes "the shell holds its own value pinned against agent's by a test"):
- agent `types.rs` owns base, margin, W1–W3 (`const` sums). The daemon (seats, guard) and the CLI (its wait) read them directly.
- daemon re-exports base, margin and W1–W3 as `Duration` for the shell's tests (B8 — reached through the shell's daemon dev-dependency, not production code).
- shell (`src-tauri`) restates base and margin as its own two named constants and derives its W1 by the same sum (its W3 comes with B14) in production code (beside `REQUEST_TIMEOUT` in `daemon_client/connection.rs`). The pin test asserts the restated base and margin **equal** the daemon re-exports, so a base change in agent fails the shell's tests until the restatement moves — the one hop where "moves by itself" is "moves or CI tests go red" (§8 C2 note).

Interfaces:
- **Deadline class, declared with the verb** (§8 B5; ADR-0155 d1/d3 and its rejected alternative C ㉠ — the daemon does not statically know shell or screen names): the declaration macro gains a deadline-class attribute (default = ordinary; one more class = launch), carried on `CommandSpec`, on `CommandDecl` as an additive serde-default field beside `agent_args` (ADR-0308 precedent; `help` stays opaque to the daemon — `CommandDecl` doc), and in the schema entry (`spec_item_json`), which clients read — the CLI's call form uses it (B15). An old registration reads as ordinary. Declared on `agent.spawn` (agent `commands.rs`) and `agent.spawnInto` (`src-tauri/src/layout/commands.rs`).
- daemon `command_delivery.rs`: `LocalCommands::claim` returns the class with the effect; the roster keeps the class from registration and `deliver` reads a relayed name's class with `CommandRoster::class_of` **before** `open`, so the seat is sized when it opens (B16). Seat = base for a launch-class name answered by the daemon's own table, W2 for a relayed one, `DEFAULT_DEADLINE` otherwise. **Retention** (`SeatState::Retained`, `retention()` — today the global deadline): a seat's retention window = its own seat duration (§8 B13). `fits_caller_silence_window(deadline, caller_window)` — `const` asserts for (7, 10), (base, W1), (W2, W3); `with_clock` checks its injected default against 10 s as today.
- transport (`crates/engram-dashboard-transport`): `Peer::request` / `request_in` take an optional per-request reply deadline; `None` = `Policy::request_timeout` (unchanged for every ordinary caller). The pending entry keeps its own duration and reports it on expiry (`on_timer` → `RequestError::TimedOut { after }` and `TransportEvent::RequestTimedOut` — today both carry the policy value), so a launch that waited 88 s does not say "30s 초과" (`link/errors.rs`). The transport has no open wait (`request_in` fails at once when unbound); the open wait is the shell's (next bullet).
- shell: one variant → deadline choice on the send path used by `forward_to_daemon` and the typed senders (`agent_spawn`, `DaemonSpawner`): `Spawn` / `SpawnByCwd` / `SpawnProfile` → W1, everything else — `Command{envelope}` included (B14 deferred) — `None`. The wait for the connection to open (`connection.rs` `opened_generation`, bounded by `link_policy().request_timeout`) stays 30 s for a launch too, then W1 bounds the reply (B17). `REQUEST_TIMEOUT` stays 30 s.
- CLI `engram.rs`: the call form reads the class from the catalog entry `run_invoke` already fetches and uses W3 for a launch-class entry's POST; `engram agent spawn` (the `/control/agent` path, no catalog) uses W3 directly; everything else 10 s. No static list of launch names (B15).
- Pins (shell, `src-tauri/tests/layout_commands.rs` beside `the_webview_deadline_fits_inside_the_daemon_seat`): (1) the shell's restated base and margin equal the daemon re-exports; (2) every pair in the chain holds outer ≥ inner + margin — (base, W1), (W1, W2), (W2, W3) — over the shell's derived values and the re-exports; (3) the shell's `agent.spawnInto` declaration carries the launch class.
- B28 holds: a successful launch whose reply comes after its caller gave up loses its notices — accepted (ADR-0360 「영향」).

## 6. User-visible changes (to confirm with the user before coding)

1. **Agents launch with 「기본」.** claude argv, before → after (stream-json, fresh):
   `… --mcp-config <data>\daemon\run\mcp-config\<id>-<e>.json --append-system-prompt-file <install>\builtin\instructions\priming.md --settings <data>\daemon\run\mcp-config\<id>-<e>.settings.json …`
   → `… --mcp-config <same> --append-system-prompt-file <data>\daemon\run\launch\<id>-<e>\instructions.md --system-prompt-snapshot off --settings <data>\daemon\run\launch\<id>-<e>\settings.json …`
   Example effect: resuming a week-old claude conversation now gives it the current priming text, not the one it started with (snapshot off — ADR-0316). `--system-prompt-snapshot` is confirmed in claude 2.1.284 `--help` (ADR-0316); the earliest version that has it is not known — an older CLI rejects the launch (K3).
2. **The hidden fragment is gone from the launch.** The one `--settings` is the merged visible `builtin\settings\default.yaml` claude field (`allowedMcpServers: [{serverName: engram}]`, `env.DISABLE_AUTOUPDATER: "1"`) (ADR-0328). The old fragment file is still written but not loaded (§3).
3. **codex**: JSON mode gets the priming as `developerInstructions` from the kit; on resume, `additionalContext` is sent only when the instructions changed since they were last delivered — so the first resume of an existing thread after the upgrade re-sends the priming once, later resumes do not. Terminal mode gets the same text via `-c developer_instructions` (ADR-0337). Nothing is written in the working folder.
4. **codex JSON same-name notice**: every codex JSON launch now runs the same-name skill check over codex's native roots (`<CODEX_HOME>\skills`, `~\.agents\skills`, and the per-folder roots from the cwd up to the project root — codex `settings.rs` `native_skill_roots`; asset-library `launch.rs` `same_names`), so `codex-same-name-skills` can appear with no library skill attached — e.g. two installed skills named `review` under `~\.codex\skills` and the project's `.agents\skills`. Wording approved at step 6 (parent §2-4 8).
5. **Missing `builtin\`**: the agent comes up without priming and the launch answer carries the notice `builtin-unavailable` (ADR-0361 d2) — e.g. `engram agent spawn` prints `알림(builtin-unavailable): 의도된 동작입니다. 대상 — …` once for that agent; the screen does not show notices until step 11.
6. **Shell: launches wait up to 88 s (up to 30 s more if the connection to the daemon is still opening); every other request still fails after 30 s as today** (§8 C2). E.g. activating an agent whose folder check is slow no longer fails at the shell after 30 s while the daemon goes on; renaming an agent while the daemon is stuck still shows its error after 30 s. The wait is derived from the daemon's launch budget (§4 chain), so it moves if the budget moves. There is no generic in-flight indicator; during a launch the only cue is the agent tree row's glyph (`AgentList.tsx`).
7. **CLI launch wait 10 s → 94 s** for `engram agent spawn` and the call form of any launch-class command (today `engram agent.spawn …`, `engram agent.spawnInto …`): "could not reach the daemon" comes only after 94 s of silence. The catalog fetch before a call form and every other CLI verb keep 10 s.
8. **New run folder** `<data>\daemon\run\launch\<id>-<epoch>\` per live agent; removed when the agent is reaped, swept at daemon boot.
9. **`ENGRAM_PRIMING_FILE`** on the daemon no longer changes claude/codex priming; the daemon logs one `warn` at boot when it is set (§8 B3).
10. Debug builds: `ENGRAM_QA_BLOCK_CWD` / `ENGRAM_QA_BLOCK_AFTER_ADD_CWD` no longer exist.

No open-source convention check was run: every user-visible value above is already set by an ADR or a recorded decision — 1–3 ADR-0316 · 0327 · 0328 · 0337; 4 ADR-0337 (same-name check) and parent §2-4 8; 5 ADR-0361 and parent §2-4 8; 6 is the user's decision C2 (2026-11-14), made after the convention research `docs/research/long-request-timeout-conventions-2026-11-14.md` (gRPC / Envoy per-call deadlines, sd-bus default + per-call override); 7 the ADR-0360 rule (user 2026-11-11) applied to §4; 9 follows from ADR-0327 d2.

- **B4** `begin_launch` at the head of `spawn_agent_watching_link` (§2). — the single funnel of all three launch kinds; one call, one drop.
- **B5** The launch seat is a deadline class declared with the verb and carried in the registration (§4). — ADR-0155 d1/d3 (the declaration lives with its producer; the daemon learns names only by runtime registration, rejected alternative C ㉠); ADR-0360 「영향」 names "a deadline declared with the verb"; the field follows ADR-0308's typed-field precedent; a caller-set envelope deadline would let any caller pick its seat. Clients read the same class from the schema entry (B15).
- **B6** One margin, 3 s = `DAEMON_SWEEP_SECS + DAEMON_CALLER_MARGIN_SECS` (the terms `LAUNCH_CALLER_WAIT_SECS` already adds), used at every step of the chain. — the same quantity as `VIEW_HOP_MARGIN` (two daemon↔shell hops, scheduling, serialization); one name keeps the chain a sum of one base and one margin (C2).
- **B7** One CLI launch wait (94 s) for all launch verbs. — one value; the direct verbs over-wait by 6 s only when the daemon is stuck.
- **B8** The shell restates base and margin and derives W1 in production; pins 1–2 reach agent values through daemon re-exports (base, margin, W1–W3), not a new shell→agent dev edge; pin 3 is shell-local. — ADR-0360 d6 prescribes a shell-held value pinned by a test; the `VIEW_REPLY_DEADLINE` precedent already uses the daemon dev-dependency.
- **B9** Hash recording is backend-neutral (§2). — ADR-0004; claude never reads the stored value.
- **B10** R4/R4b are manager-level tests: `create_and_activate` with a crafted profile whose `presets` names a library preset, a real `LibraryService` + `FsStore` over a temp root (ADR-0311 d4). R4: the preset's folder entry is missing → pre-create block, nothing created. R4b: the second check must ask a key the first did not (one `LaunchIo` keeps answers for the launch — §2), e.g. a scripted `FolderOps` whose first answer rewrites the temp preset to add a second, missing folder (the overlay re-reads presets on every check) → created asleep: the manager-level outcome is `NotStarted { created: true, error: LaunchBlocked }`. The wire shapes (`INTERNAL` + `agent_id` + `reasons`) stay covered by the step-20 fake-kit tests (`connection_core.rs` `BlockingKits` · `BlocksAfterTheAdd`). Live GUI re-run at 10a. — No step-8 entrance carries a library preset and the root is unset, so no live block-① trigger exists.
- **B11** Keep the hard-coded `DISABLE_AUTOUPDATER`; L7 is best effort. — observing the updater needs a pending update; the duplicate costs nothing.
- **B12** Tripwire in agent `backend/mod.rs` tests: every backend in `settings_checks()` is MCP-capable and uses mail (`accepts_mcp_config && uses_mail`). — real kits add the priming whenever 「기본」 is attached, bypassing the control channel's `wants_priming` (ADR-0126/0133: what priming teaches ⊆ what the spawn has); today claude and codex both satisfy it.
- **B13** Seat retention = the seat's own duration (§4). — `retention()` doc: the window to close is "deadline → `TIMEOUT` → same-id retry", whose natural length is that seat's deadline; with the global 7 s, an applied launch would hold its id only 7 s after the body completes, although its caller was told to wait up to 85–91 s, so a retry inside the caller's own window could launch again (ADR-0122).
- **B14 (deferred — main 2026-11-14)** The shell's wait for a launch-class `Command{envelope}` on the socket (W3), which needs the shell to learn a daemon-owned name's class at runtime (ADR-0155 — e.g. the class in the catalog's schema entry, cached from `ListCommands` / `CommandList`). Not built in step 8: no Engram caller sends such an envelope (the webview has no bus caller of daemon names), and the user's rule adds no branch that nothing needs. **Trigger: build it when an Engram caller first sends a launch-class envelope on the socket** (the class is already in the schema entry since B15).
- **B15** The CLI's launch wait comes from the class in the catalog entry `run_invoke` already fetches (W3 for a launch-class entry); `engram agent spawn` keeps W3 directly (its route has no catalog); the static launch-name list is dropped, and the schema entry carries the class in step 8. — a static list can drift from the runtime class (round 2); the fetch already happens, so no extra round trip.
- **B16** `deliver` reads a relayed name's class before `open` with a lock-scoped `CommandRoster::class_of(name)`, modelled on `agent_args_of` (`command_roster.rs` — "the lock ends inside this call"); `route` keeps its own lookup and `OwnerLookup` is unchanged (no shell implementor changes). Lock order: the roster lock is taken and released inside `class_of`, then `open` takes the seat-table lock — never nested. — the seat must be sized when it opens (module rule 1: open the seat before anything). Accepted: a re-registration in the microseconds between `class_of` and `route`'s lookup can mis-size one seat.
- **B17** A direct launch request waits the ordinary 30 s for the connection to open, then W1 for the reply. — nothing has been sent while it waits to open, so failing there is definite (no unknown outcome); the total is at most 30 s + W1, not W1 twice. **The relay's inner wait stays W1, so pin 2's (W1, W2) pair holds**: on the envelope's own connection the open wait is zero — `on_link_up` queues the command registration before it publishes `opened` (`connection.rs` `on_link_up`), and the daemon relays only to a registered owner, so the link that delivered the `agent.spawnInto` envelope is already open when `OwnedSpawner` sends `SpawnByCwd`. The 30 s + W1 case needs a reconnect between the envelope arriving and `SpawnByCwd` being sent; the shell's outcome is then bound to the old connection (`send_command_outcome` with the request's generation) and can never reach the seat, so the seat's `TIMEOUT` is the only answer either way.

**(c) User decisions.**
- **C1 (conditional — only if L8 measures codex's shell-tool timeout below 94 s).** Visible change: a codex agent's `engram agent spawn` is cut by its own tool while the launch goes on, and it reports a failure for an agent that may start. Options: (1) a priming line saying a launch can take up to 94 s and to run it in the background; (2) accept and document; (3) shorten the CLI launch wait — breaks ADR-0360 d1. Recommendation (1): it touches only `builtin\instructions\priming.md`, the one editable source (ADR-0327). If L8 shows ≥ 94 s, nothing is asked.
- **C2 — the shell's request timeout: decided by the user 2026-11-14 — launch requests only, derived chain.** The user: 「B를 하면 될것같은데」; after the convention research (`docs/research/long-request-timeout-conventions-2026-11-14.md` — per-call deadlines in gRPC / Envoy, sd-bus default + per-call override; option B there) 「아니 연속성을 하려면 기준점 + 추가시간? 그런식으로 되야되지 않냐는거지」 and 「어쨋든 ㄱㄱ」. So: ordinary shell requests keep the shared 30 s; `Spawn` / `SpawnByCwd` / `SpawnProfile` get a per-request deadline (launch-class socket envelopes — deferred, B14); every launch wait is base + margin sums (§4 chain) — the derived chain is the user's condition. Amends ADR-0181 d1 and ADR-0310 D15 — ADR-0369, §7. Context kept: ADR-0181 records the user judging 30 s already large; the shell side now follows the launch-only rule ADR-0360 set for the daemon bus.
  - Rejected: one shared timeout raised to 88 s for every shell request (the plan of drafts 1–2, main's decision under delegation) — ADR-0360 already rejected raising the global default for launches' sake, and every silent non-launch request would wait 88 s.
  - **How the condition is met**: every launch wait is base + margin in each crate that holds one — agent `types.rs` (W1–W3, read by the daemon and the CLI) and the shell (its own named base and margin, W1 by the same sum — ADR-0360 d6, B8; the shell does not depend on agent, ADR-0270 d1). A base change is one constant per crate: agent's sum moves on its own, and pin 1 (shell base and margin equal the daemon's re-exports) fails until the shell follows. No runtime wire field and no move to `command` (main 2026-11-14).
