폴더 확인 시간 규칙

라이브러리의 항목(프리셋·지침·스킬·설정)은 모두 라이브러리 폴더 안에 있다. 라이브러리 밖을 가리킬 수 있는 것은 프리셋의 폴더 항목 하나뿐이다(ADR-0341 — 예: 공유 드라이브의 규칙 폴더). 그 폴더가 느리거나 꺼져 있어도 실행 응답은 정해진 시간 안에 나가야 해서, 확인 시간을 두 갈래로 나눴다. 실행 하나(만들고 시작, 시작, 이어 하기)는 최악 85초 안에 응답하고, 그 실행을 바로 기다리는 쪽은 88초까지 기다린다(ADR-0360, 다른 명령은 그대로 7초). 85초 = 폴더 확인 62초 + 이어 하기의 조기 종료 감시 3초 + codex 연결 대기 상한 15초 + 여유 5초. 느린 PC나 잠든 디스크·NAS가 깨어날 시간을 주려고 늘렸다.

무엇을 확인하나시간답이 없으면
필수프리셋의 폴더 항목(있는지·목록·파일 읽기), 라이브러리 프리셋이 붙었을 때 라이브러리 루트, prepare의 원본 다시 읽기실행 하나에 합쳐서 최대 60초(Windows SMB가 요청 하나를 스스로 포기하는 시간). check가 여러 번 돌고 prepare까지 가도 이 60초를 나눠 쓴다. 이미 답을 받은 폴더는 다시 묻지 않는다. 실행이 아닌 읽기(목록에서 프리셋 풀어 보기 등)는 지금처럼 5초.폴더 하나만 늦어도 실행 전체를 막는다.
참고작업 폴더의 정식 경로(정션 풀기), 백엔드 기본 스킬 폴더(예: codex의 <CODEX_HOME>/skills), 같은 이름 스킬 비교용 정식 경로실행 하나에 따로 최대 2초. 필수 60초에서 빼 쓰지 않는다.건너뛴다. 대신할 값을 지어내지 않는다. 작업 폴더는 적힌 경로를 그대로 쓰고 로그에만 남긴다(B29). 스킬 폴더 비교는 이번 실행에서 뺀다.

폴더 여러 개는 동시에 확인한다. 열 개가 다 죽어 있어도 60초 한 번이면 끝난다. 폴더 목록이 10,000개를 넘으면 앞부분만 보고 알림을 낸다. 실행은 막지 않는다.

ADR-0360은 입구마다 숫자를 정하지 않고 조건과 순서 규칙만 정한다. 실행 하나는 85초 안에 응답하고, 그 실행을 바로 기다리는 쪽은 88초 이상 기다린다. 한 대기가 다른 대기를 감싸면, 바깥 대기 ≥ 안쪽 대기 + 홉 여유다. 이 규칙은 웹뷰 왕복이 데몬 응답 자리 안에 드는 곳에서 코드가 이미 지킨다(view_commands.rs의 VIEW_REPLY_DEADLINE과 테스트 the_webview_deadline_fits_inside_the_daemon_seat). 순서가 뒤집히면 주인은 아직 돌고 있는데 데몬이 TIMEOUT으로 답하고, 늦은 결과는 받을 자리가 없고, 같은 번호로 다시 부르면 봉투가 두 번 내려갈 수 있다. 입구마다의 값은 8단계가 그 코드를 고치면서 이 규칙으로 정한다. 입구별 숫자가 리뷰 두 번 연속 새 경우를 만들어, 사용자가 이렇게 정했다(알아서 해 어쨋든 나중에 결국 다 적용되는거잖아). 지금은 입구마다 기다리는 시간이 다르고, 8단계 전에는 오래 걸리는 실행에서 아래 증상이 난다.

동시성 규칙 두 개

메모리 목록은 읽기·쓰기 잠금 하나로 지킨다. 리뷰 3차에서 같은 종류의 버그가 두 번 연달아 나와서, 사례마다 고치는 대신 아래 두 규칙으로 묶었다.

A목록 쓰기는 항목 하나씩

목록에 쓰는 모든 일(훑기 반영, 실행 검사가 새로 읽은 내용, 목록 요청의 안전망, 나중 단계의 편집·이동)은 쓰기 잠금 안에서 항목 하나씩 적용한다. 같은 항목이면 나중에 읽은 쪽이 이긴다. 목록을 통째로 바꿔 끼우지 않는다.

예외는 루트 변경 하나다. 앞뒤 변경을 모두 기다리게 하고 혼자 돌며, 새 루트를 처음부터 전부 새로 읽은 뒤 한 번에 바꿔 끼운다. 그동안 읽는 쪽은 옛 목록을 본다. 빈 목록을 보는 일은 없다.

왜: 예전 설계는 훑기 결과를 통째로 바꿔 끼워서, 훑는 사이 들어온 다른 쓰기를 계속 잃었다.

B필수 먼저 혼자, 참고는 그 뒤에

실행을 막을지 정하는 확인(필수)을 먼저, 다른 것과 섞지 않고 돌린다. 알림이나 덤 값만 만드는 확인(참고)은 필수가 끝난 뒤 자기 몫 2초 안에서만 돈다. 필수는 참고를 기다리지 않고, 참고는 필수의 시간을 가져가지 않는다.

왜: 예전 설계는 두 확인을 한 묶음에 넣어서, 막을 이유가 없는 참고 확인이 필수 확인의 시간을 잡아먹고 실행을 막을 수 있었다.

ADR-0360 11-11실행 하나(만들고 시작, 시작, 이어 하기)는 85초 안에 응답하고, 그 실행을 바로 기다리는 쪽은 88초 이상 기다린다. 한 대기가 다른 대기를 감싸면 바깥 대기 ≥ 안쪽 대기 + 홉 여유. 다른 명령은 그대로 7초. 85초 = 폴더 60 + 2 + 이어 하기 감시 3 + codex 연결 대기 상한 15 + 여유 5, 88초 = 85 + 수거 주기 1 + 여유 2. 입구마다의 값과 방법은 8단계가 이 규칙으로 정한다(위 「실행 입구마다 기다리는 시간」). 실행 전 폴더 확인은 필수 60초 + 참고 2초로 늘렸다(막히면 최악 62초, 성공은 최악 80초). 실행이 아닌 읽기는 5초 그대로. 이 시간 값들은 지금은 agent types.rs의 내부 상수로 두고(CLI 10초 상수 옆), 응답 한도와 기다림은 폴더 대기 시간과 활성화 상수에서 계산한다. base는 건드리지 않는다. 나중에 설정 파일을 읽는 공용 구조가 base에 생기면 값은 파일로 옮긴다(공용 설정 하나로 할지 크레이트마다 둘지는 그때 정한다 — T-105). 리뷰에서 처음의 65초 · 68초가 활성화 대기를 빼먹은 것이 드러나 다시 셈했다.느리거나 제대로 동작되지 않는 pc가 있는데 사람이 없을때 에이전트가 실패하면 무한 막히는거잖아. 시간을 늘려 시간은 60초로 하던지 파일 읽어노는 구조? 자체는 base에 있고, 설정은 공용 설정으로 할지 crate 당 설정으로할지 어쨋든 파일로 빠지는거잖아.

아직 모르는 것

  • claude 터미널 모드에서 틀린 설정이 보이는지틀린 값은 CLI가 처리한다(ADR-0359). -p 모드에서는 claude가 --settings의 틀린 설정을 조용히 통째로 버린다고 실측됐다(docs/research/settings-asset-validation-spike-2026-10-17.md). 터미널(대화형) 모드에서 경고가 뜨는지는 재지 않았다.
  • 새 패키지의 라이선스 파일granit-parser · annotate-snippets · encoding_rs_io · relative-path · pulldown-cmark. P1·P3에서 라이선스 게이트를 로컬로 돌려 본다. (jsonschema와 그 딸린 패키지는 넣지 않는다.)
  • 새 판의 최소 Rust 버전serde-saphyr 2.1.1의 MSRV는 미확인 (툴체인은 1.95.0, serde-saphyr 2.0.0은 1.89).
  • NaN · -0.0을 다시 쓸 때의 출력TRD는 미확인 항목으로 따로 적지 않았고, P3 골든에서 「-0.0이 그대로 남는다」「NaN끼리는 같다」를 확인하기로 했다. NaN의 부호는 버리기로 정했다.
