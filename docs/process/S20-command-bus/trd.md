### 3-5. Routing (same in every process and every hop) ★revised★

```rust
pub async fn route(
    table: &CommandTable,          // 내 표
    roster: &Roster,               // ★추가★ 내가 아는 명부(없는 프로세스는 빈 명부를 넘긴다)
```

**Rule, 3 steps:**
1. `table.get(&env.name)` → if present, **run directly**.
2. If absent, `roster.owner_of(&env.name)` → if present, **`link.send` to that owner's connection**.
3. If neither, **error** (§4-②). ★Revised (Edition 3)★ Old edition (abbreviated): "**Tell apart** `UNKNOWN_COMMAND` / `OWNER_UNAVAILABLE`." → **That distinction was given up** (ADR-0150). If the registry has no live registration, it is just `UNKNOWN_COMMAND` — the name of a dropped owner is removed from the registry, so in the daemon's eyes it is the same as 「원래 없던 이름」.

The old edition had 2 steps ("run directly if present, send if absent") and **assumed there was only one place to send to**. When there are two hops (§3-8), that assumption breaks. The 3 steps are the same at every hop **with no special case**, so even if a new owner (e.g. a mobile client) attaches later, the delivery code does not change and **only one registration is added.**

### ⑧ Authorization per call ★new★

**Do not check once at registration and afterwards route only by session identifier.** Look at `name` on every envelope and authorize that call.

- **Ground (with sources):** the first draft of the research wrote "a permission check once at registration is common", but the adversarial review **refuted** it — a bus daemon checks policy when a message is routed between connections, a cluster API authorizes **per request**, and an RPC interceptor is inherently per-call (research §2 「권한 검사는 호출마다」 item + §9 refutation table row 3).
- **Why this design makes that possible:** because `name` is on the outer cover (§3-2). If the name were hidden inside, per-command authorization would be impossible at the root.
- **Scope:** v1 does not decide the policy content of 「어떤 자격이 어떤 명령을 부를 수 있나」 — that is a separate matter of the ADR-0086 (least-privilege) family and **as it is a security-policy decision it takes the responsible decision path.** What v1 confirms is only **the form that the check point is per call**.

### ⑨ Panic policy of the release profile ★new — user decision recorded★

**Keep `panic = "abort"` of the release profile** (root `Cargo.toml:24-30`). It is a user decision, and this TRD does not re-discuss it.

- **Ground:** the process state after a panic cannot be trusted. **Dying and coming back** loses less than keeping it alive in a dubious state and continuing — session restore pays that price (`docs/reference/architecture-overview.md` 「세션 복원 / 활성화」 · ADR-0008/0082/0185).
- ★**Consequence — in a release build the panic nets do not stand. That is intended.**★ The two panic nets — `guard_panic` that `blocking_handler` wraps (`crates/engram-dashboard-command/src/route.rs`, call site = the `blocking_handler` adapter in `table.rs` of the same crate) and `CatchUnwind` that `route()` wraps (`route.rs`) — ★do not pin line numbers, find by symbol name★ — are effective **only in development and test builds**. In release, a handler panic becomes **process exit** and not an error reply. Do not read the net as 「릴리즈에서도 답장 하나를 보장한다」 — in that build, §4-⑤'s 「한 `request_id`에 답장 하나」 is kept not by the net but by **the caller's deadline** (⑥).
- **So one convention stands: a command handler does not die by blowing up — it returns the error as a value.** The net is a safety net that covers mistakes, not an error path. Since the net disappears in release, if a panic is used as an error-delivery means, in that build **one agent's bad argument takes the daemon down.** The review checklist looks at this item (`.claude/skill-bindings/review.md` 「code 단계 게이트」).

## 7. Test strategy

ADR-0012 — every piece cuts external dependencies at a seam and has a standalone harness.

### ★Rule T-1 (hard constraint) — no global auto-registration table★

**Do not make a global table with handlers pre-embedded.** Each module exposes only `make_table(deps) -> CommandTable`, and real dependencies are **injected at assembly**.

- **Why a hard constraint:** if handlers are embedded in a global table, a test has **no place to plug in a fake manager.** To assert a single `agent.spawn`, a real `AgentManager` comes along, and then **the unit test launches a real process.** This is not a matter of taste but a direct violation of ADR-0012 「외부 의존을 seam으로 끊는다」.
- **Decision criterion (to look at in code review):** if a `static`/`lazy_static`/linker collection **holds `Arc<dyn CommandHandler>`, it is a violation.** What a linker collection may hold goes only up to `CommandSpec` (name, schema, errors).
- It is not that automatic collection is not used at all — **names and argument schemas automatic, implementation manual** is the whole of this rule.

## 8. Assumptions

### Assumption A — the daemon takes the list gathering ★revised — from undecided to adopted★

**Old edition:** "the default I put up now · waiting for the user's decision".
**Current edition:** **it is the adopted form.** The registration wire of the confirmed structure (§3-7) stands presupposing this form, and overturned judgment 3 (the daemon does not query the build list) makes sense only on top of it.

**Two grounds for adoption — they come from our structure, not from precedent:**
1. **The number of callers that would have to duplicate the merge logic goes down.** There are three or more callers — the `engram` CLI · the MCP mail path · the screen. If the three each write discovery and merge, the vocabulary splits again, and that is the very symptom being fixed now (「지금 상태(실측)」 ② of step-log.md 「사용자 방향 2026-08-12 — 통합 command 버스」).
2. **The 2-tier delivery stays uniform** (§3-8). If the daemon holds the registry, there is one rule per hop. If it goes to caller-side merging, 「누가 명부를 갖나」 differs per hop and special cases arise — the confirmed structure ④ (「특별 케이스 없음」) collapses.

### ★Three places that diverged from existing records — state after the revision★

**Contradiction 1 — the owner field. ★Resolved (old-edition claim withdrawn)★**

- **Old-edition claim:** even though step-log.md 「사용자 방향 2026-08-12」 recorded "owner designation is unnecessary — the definition location is the owner", it revives the `#[owner(Daemon|Shell|View)]` field. The ground was "if declarations are gathered in one place, protocol, **the definition location does not tell the owner**, so the field becomes necessary".
- **After the revision:** **with the centralization of declarations discarded, that ground vanished wholesale.** The definition location again tells the owner. The field is deleted (§2-2 · §3-1).
- **Lesson to keep:** the old edition's logic itself was right — 「중앙화하면 주인 칸이 필요하다」 is true. What was wrong was **the premise (centralization)**. That a proposal the user had withdrawn twice came back to life is not an accident but because the premise demanded it again, and changing the premise was the right answer. (Handoff 「do-not 2」.)

**Contradiction 2 — ADR-0081 「Opaque 결합 가드」. ★Withdrawn (no discard stamp needed)★**

- **Old-edition claim:** the ADR-0081 impact section and S17 TRD `trd.md:36` (「★Opaque 결합 가드(H)★」) nailed down that "the UI command enum + the payload→`ViewCommand` dispatch map are **only in `src-tauri`** — `engram-ctl`, the daemon relay and `core` **do not import** the UI enum", but this design puts the names and argument schemas of shell and screen commands in `protocol` and **the daemon and CLI depend on that crate**, so it conflicts with the literal guard → **"guard H needs a partial-discard stamp"** (though the judgment is the user's).
- **After the revision: that conclusion was wrong. No stamp is needed.**
- **Why the old reading was wrong — the conflict came not from 「이름이 겉봉으로 나온 것」 but from 「선언 위치」.** The old edition wrote two causes of conflict (① name exposure ② declaration location) side by side and read **both as touching the guard**. What the guard actually forbids is a **type import** ("does not import the UI enum"). ① is the daemon reading `name: String` from the outer cover, so it is **not a type import.** Only ② was a real violation, and as ② is discarded, the violation disappears.
- **What the daemon knows after the revision:** **only the name strings** of shell and screen commands, and those too it receives **by runtime registration** (§3-7). The UI types compiled in are 0. **The daemon depends on neither `src-tauri` nor the webview.** That is, the guard is **kept literally.**
- **One remaining extension (not a discard):** ADR-0081's envelope was purely opaque, and here `name` comes out on the outer cover. This is an additive extension of the **envelope form**, not of the guard (type coupling), and research §2 supports it (per-command authorization and observation hang on it — §4-⑧). `args` is still opaque, so the substance of ADR-0081 decision 2 lives on. (Handoff 「do-not 3」.)

**Contradiction 3 — ADR-0055's decentralization argument. ★Resolved★**

- **Old-edition claim:** ADR-0055 rejected the "enum-data single command (variant + central dispatch)" citing "**modifying a central enum + match + meta map for every new command** → violates the decentralized goal of features registering their own commands" (item 1 of ADR-0055 「거부한 대안」), and the old edition that gathers the catalog in protocol partly took that centralization back. The old edition's mitigating grounds were "one macro block reduces three-place edits to one place" + "execution-side registration is still decentralized", and it admitted "still the declaration became central".
- **After the revision:** **the declaration also became decentralized.** Each module declares its own commands in its own place and makes its own table — exactly what ADR-0055 meant to protect. It is **consistency**, not mitigation.
- **Addendum:** the "backend mirror = follow-up" clause of ADR-0055 had scheduled this work, so it is not a reversal but the actual implementation of that follow-up. The one line that diverged in the old edition (declaration centralization) is gone.
