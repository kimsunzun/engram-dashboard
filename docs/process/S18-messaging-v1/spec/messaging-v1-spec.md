## 0. 스코프 한 줄

**데몬이 살아 있는 동안** 에이전트 간 메시지가 확실히 가게 한다 — 봉투 정형화(XML) + 회신 계약(request) + 다중 수신자 발송(`@all` 포함) + 인메모리 메일박스(파킹·장부·조회). **영속화(디스크) 없음** — 에이전트 시스템 메모리 설계 때(사용자 결정).

## 1. 봉투 — 수신 LLM에게 보이는 것 (4종, XML 단일화)

```xml
<message from="qa-alpha">빌드 끝났음</message>
<message from="qa-alpha" id="m-7f3k" type="request" reply-by="10m">코드 짜고 회신해</message>
<message from="qa-bravo" in-reply-to="m-7f3k">다 짰음, 테스트 통과</message>
<message from="qa-alpha" to="@all">전원 리베이스 대기</message>
<notice>[engram] 요청 m-7f3k 기한(10m) 초과 — qa-bravo 회신 없음</notice>
```

- **표기 매핑(고정):** 툴/CLI 인자 = snake_case(`reply_to`·`reply_by`) → XML 속성 = kebab-case(`in-reply-to`·`reply-by`). 발신 인자 `reply_to`가 수신 봉투 속성 `in-reply-to`로 나타난다(요청자가 어느 요청의 답인지 상관하도록 노출).

- **노출 원칙: LLM의 행동을 바꾸는 필드만 보인다.** `id`는 request에만(회신에 필요), `to`는 **수신자가 둘 이상일 때만**(혼자 받은 편지가 아님을 알림), 시각·장부 상태는 내부 데이터.
- **`to` 노출 기준 = 수신자 수(그룹 여부 아님, ADR-0111 개편):** 그룹 전용 semantics가 폐지돼 `@all` 발송과 여러 명 직접 지목이 같은 경로다 → 노출 조건도 "그룹이면"이 아니라 **"수용 판정된(= 실패 행이 아닌) 수신자 2인 이상이면"**으로 통일한다. 세는 것은 결과 상태가 아니라 **수용 판정**이다 — `delivered`는 실제 주입 시점에야 확정되므로(§5) 그걸 기준 삼으면 봉투를 만들 때 아직 모르는 값을 참조하는 순환이 된다. 실패 행은 세지 않는다(못 받은 사람 때문에 남은 사람의 봉투 표기가 흔들리지 않게).
- **`to` 값 = 발송 시점 해석에서 확정·동결**(flush 때 재계산 금지 — 파킹분이 한참 뒤 주입돼도 발송 순간 표기 그대로): **전 수신자의 수용 판정이 끝난 뒤 1회 확정**해 그 발송의 모든 봉투에 동일하게 싣는다(수신자별 루프 도중 wrap 금지 — 첫 수신자가 미완성 `to`를 받는 사고 차단). 수용된 **명시 지목은 정규 이름**, **`@`주소는 펼치지 않고 토큰 그대로**(`@all`), **실패한 토큰은 제외**. 값의 나열은 **입력 표기 순**(`@all,x` — `results[]` 행 순서 축과는 별개다: 행은 §5 규칙, 봉투 값은 발신자가 쓴 순서). 펼친 명단을 대신 싣지 않는다 — 수신자 명단·역할 공개(cc)는 v2(§8).
- `<message>` = 동료 발신(from에게 회신 가능) / `<notice>` = 데몬 통지(from 없음 = 회신 대상 아님). 태그 분리로 "system" 가짜 발신자·이름 예약 문제를 구조적으로 제거. **notice 자기식별(사용자 결정 2026-07-26):** 본문 머리표 `[engram]` + 프라이밍에 "`<notice>` = 엔그램 데몬(시스템) 통지, `from` 없음이 표시, 회신 대상 아님" 1절.
- 포맷은 기존 wrap seam(ADR-0096)의 **Xml 변형을 기본값으로 전환 + 속성 확장**. 콜론 변형은 스위치로 잔존(삭제 아님). 이스케이프는 기존 XML 이스케이프 재사용.
- 전환 검증: `roundtrip-smoke` 재실행(LLM이 XML 봉투를 읽고 회신하는지 — 포맷 결합 부분만 재검증, 배관은 포맷 무관). **미검증 — §7 수용 기준의 구현 QA 항목.**

## 2. 타입 체계 — "데몬이 다르게 행동할 때만 타입"

| 표기 | 데몬 행동 |
|---|---|
| (기본, type 없음) | 통보 — 배달하고 끝 |
| `type=request` | 장부에 "미회신" 오픈(+ `reply_by` 있으면 타이머). **수신자별 독립 계약** — 다중 수신자·`@all`이면 계약 N개(ADR-0111 결정 5. 구 "단일 수신자만·그룹 거부" 폐기) |
| `in_reply_to=<id>` (필드, 타입 아님) | 회신 판정 → **수용된 회신만** 미회신 닫힘(`replied`). 도달 불가 확정 실패면 `reply_failed` 실패 종결 — 조건·예외는 §3 항목 7-④ |
| `<notice>` (데몬 전용) | 타임아웃 등 인프라 통지. 에이전트가 못 씀 |

- **refuse/failure는 타입 아님** — 회신 본문 소관("거절함/실패함"). **회신이 도달했다면** 내용이 거절이든 실패든 장부는 `replied`로 닫는다(계약 = "답을 했나"이지 "답이 무엇인가"가 아니다). 회신 *배달 자체가* 실패한 경우만 다른 축이다 — §3 항목 7-④. 필요 시 v2에서 사유 칸 추가(무파괴).
- **회신 매칭 = 엄격**: `in_reply_to` 있는 것만 인정. 프라이밍에 "request 회신엔 원본 id를 달아라" 규칙 보강(관대 매칭=우연 닫힘 오발 거부).
- 응답 계약 스펙트럼 중 채택 = 통보·요청 2종. 구독(→관측 인프라와 중복이라 영구 불채택 방향)·협상·진행보고 타입(스레드 일반 메시지로 무료 지원)·수신거부 ACL(에이전트 시스템 권한 설계 때)은 제외 — 근거 ADR-0103.

## 3. 회신 계약 (request)

1. 발송: `request` + 선택 `reply_by`(기간 표기 "10m"/"1h" — 데몬이 절대시각 환산. **하한 1분** = 타임아웃 감지 해상도(60s 스윕)와 정합 · **상한 30일** = 내부 시각 연산 안전 — 구현 결정 2026-07-26). 계약 필드(request/reply_to)는 **XML 봉투 전용** — 콜론/템플릿 포맷 활성 시 반려(속성이 떨어져 회신 불가·오탐 notice가 되므로).
2. 장부: 미회신(`awaiting_reply`) 오픈 — **수신자당 1건**. 다중 수신자 request는 **독립 계약 N개**가 열린다(ADR-0111 결정 5): 메시지 id는 N계약 공통(장부 = 메시지 1 : 배달기록 N 원칙 유지)이고 **계약 키 = `(메시지 id, 수신자)`** — 회신자가 누구냐로 계약이 갈린다. **계약 오픈 기준 = 그 수신자가 수용됐나**(★**이 절이 쓰는 "수용"의 정의** = 그 수신자의 결과가 실패 행이 아니다. **6차부터 수용의 응답 어휘는 `pending` 하나**이고, 옛 `delivered`|`pending` 병기는 직발송 시절 문구다 — ADR-0124. 아래 항목들은 이 정의를 그대로 쓴다★) — 실패 행(입구 반려·`MAILBOX_FULL`·`REQUEST_CAPACITY`)의 계약은 열지 않는다. **파킹(`pending`)은 수용이므로 계약을 연다** — busy든 잠듦이든(ADR-0116 결정 1) 동일하다: 언젠가 주입될 메시지라 회신 의무가 성립하고, 그래서 `reply_by` 기한 스윕도 정상 발화한다(시계는 발송 기준 — 아래 주입 타이밍).
3. 회신(`in_reply_to`)이 **수용**되면 → 그 **회신자의 계약만** `replied` 닫힘(다른 수신자 계약은 그대로 오픈 — 전체회신 없음). 수용되지 못한 회신의 처리는 항목 7-④.
4. `reply_by` 초과 → **발신자에게** `<notice>` 주입(수신자 재촉 아님 — 재촉 여부는 발신 LLM 판단). **다중 request의 타임아웃 통지는 계약별 1건 — 단건 request N발과 동일 규칙**(무응답 수신자 이름을 본문에 명시. 통지 병합 시스템은 만들지 않는다 — 예외 없는 단일 규칙이 우선). notice는 **전용 유계 레인**(반려 없음 — §5 정책 상수, ADR-0107. 구 "가득참 예외 통로" 문구 대체).
5. **기한 초과 ≠ 종결(ADR-0108):** 통지 후에도 계약은 회신까지 오픈 — 수신자의 미결 조회(`messages`)에 `timed_out`으로 계속 보인다. **동시 오픈 상한 512(전역)** 도달 시 **은퇴 가능 계약**(통지 완료분 또는 기한 없는 것 — 통지 의무 미발화분은 절대 불가) 중 최고령을 은퇴시키고 신규 수용(**이력 행은 유지·계약 추적만 제거** + 데몬 로그 잔존, 발신자 통지 없음). 다중 수신자 request는 **계약 N개를 계수**하며, 은퇴 불가 계약만으로 상한이 찬 상태면 그 수신자의 **수신자별 실패 행 `REQUEST_CAPACITY`**(전체 반려 아님 — §5 부분 진행. 계약을 못 연 수신자에겐 메시지도 배달하지 않는다: request의 본질이 회신 추적이므로 추적 없는 배달은 계약 위반). **이 판정은 큐 적재 *전*에 끝난다(6차 — ADR-0124):** 적재 후로 미루면 즉시 답할 수 없어 `pending`으로 흡수되고, 그 순간 **추적 없는 request가 배달된다**(계약을 못 연 수신자에겐 배달하지 않는다는 위 규칙이 무너진다).
6. LLM측 강제는 soft(프라이밍) — 보장은 데몬 장부 추적이 담당(액터 call/ask + FIPA reply-by의 증류).
7. **`reply_to`(회신 발송) 규칙 3줄:**
   - **① 수신자는 정확히 1명** — 회신은 원 요청자에게만 간다. `reply_to` + 다중 수신자(`@`주소 포함)는 `INVALID_SEND_ARGS` 전체 반려(펼침 결과가 1명이어도 마찬가지 — 표기 단계에서 막는다).
   - **② 매칭 실패는 배달을 막지 않는다** — 모르는 id·이미 닫힌 계약·발신자에게 그런 계약이 없는 경우, **메시지는 정상 배달되고 계약 쪽만 무동작**(no-op). 회신이 통째로 사라지는 편이 더 나쁘다.
   - **③ 같은 계약에 두 번째 회신** — 배달은 되고 계약은 무동작(이미 `replied`. 재닫힘·중복 통지 없음).
   - **④ 규칙 한 줄(ADR-0116 결정 2 · 사용자 결정 2026-07-30): 회신이 수용되면 계약 완료, 요청자 이름이 아예 없을 때만 실패 종결, 그 밖의 실패는 무동작.**
     - **수용**(정의 = 항목 2) → `replied` 닫힘. **파킹도 수용이다** — 요청자가 잠들어 회신이 파킹돼도 회신자의 의무는 그 시점에 이행됐다(꽂으면 완료). 그 뒤 요청자가 삭제돼 파킹된 회신이 치워지더라도 **계약은 `replied`로 남는다**(되돌리지 않는다 — 계약 축은 "답을 했나"에 답하고, "도착했나"는 배달기록이 `RECIPIENT_DELETED`로 정확히 적는다. 두 축이 각자 사실이라 장부가 거짓말하는 게 아니고, 종점 상태 되돌림은 전이 그래프가 금지하는 부류다 §6). **알고 수용한 성질**이며 추가 처리를 두지 않는다.
     - **`failed` + `RECIPIENT_NOT_FOUND`**(요청자의 프로필도 없다 = 그 이름은 세상에 없다) → 계약 **`reply_failed` 실패 종결**(오픈 목록·기한 스윕·512 계수에서 제거, 이력 잔존). 기다려도 갈 곳이 없다.
     - **그 밖의 실패**(`MAILBOX_FULL`·`RECIPIENT_AMBIGUOUS`) → **무동작 = 계약 오픈 유지.** 이 실패들은 도달 불가 확정이 아니라 그 순간의 환경이다(보관함이 지금 가득 / 동명) — 여기서 닫으면 회신자가 잠시 뒤 재시도해 **실제로 배달에 성공해도** 장부는 영영 "회신 실패"로 남고 요청자의 미결 목록에서도 사라진다(장부 거짓말의 반대 방향). 오픈 유지 = 추가 기계가 아니라 **아무것도 하지 않는 것**이며, 재시도 성공이 정상 경로로 계약을 닫는다. **좀비 걱정 없음** — 이 계약도 기한 통지가 발화하면 ADR-0108의 은퇴 대상(통지 완료분)에 편입되므로 상한을 영구 점유하지 않는다.
     - 회신 경로에서 **발생하지 않는 코드**: `REQUEST_CAPACITY`(회신은 `reply_to`↔`request` 상호배타라 계약을 열지 않는다) · `RECIPIENT_DELETED`(발송 응답이 아니라 조회 시점 코드 §6). 분류에 넣지 않는다.
     - **은퇴 표시·잠정 계약과의 접합(ADR-0108 결정 4 불변식 존중):** `reply_failed`는 **정산되지 않은 계약을 때리지 않는다** — 잠정(`provisional`)·은퇴 예정(`pending_retirement`) 표시가 붙은 계약의 수명은 그 가드 소유이므로, 실패 종결은 가드 정산 이후에만 적용된다(그 사이 도착한 실패 회신은 무동작).

## 4. 그룹 (= 주소 해석 매크로로 강등 — ADR-0111 결정 4 · ADR-0112 결정 1 · 두 어휘 분리 ADR-0121 결정 1)

- **그룹은 발송 경로가 아니라 주소 해석 단계의 매크로다.** `@주소` → 명단 펼침 → **§5의 다중 수신자 발송에 그대로 합류**(경로 1벌). 펼쳐진 멤버는 직접 지목한 수신자와 **완전히 동일하게** 처리된다.
- **펼침에서 발신자 제외(사용자 결정 2026-07-29 · ★이 조항의 정본은 이 문서다 — ADR-0111 결정 4 에는 이 문구가 없으니 거기서 찾지 말 것★):** `@주소`를 펼칠 때 **발신자 자신은 명단에서 뺀다**(두 어휘 모두 — ADR-0121) — 그룹 발송 = "나 빼고 전원". **직접 지목 자기발송은 그대로 허용**(`to`에 자기 이름을 명시하면 평소대로 배달된다 — 제외는 *펼침에만* 적용되는 규칙이지 자기발송 금지가 아니다. 둘이 겹쳤을 때의 결말은 아래 항목).
- **펼침 결과 0명은 그 자체로 에러가 아니다** — `GROUP_EMPTY`는 **최종 수신자 집합(펼침 + 명시 지목 합집합)이 비었을 때만** 난다. 펼침이 발신자만 빼고 아무것도 남기지 못할 때(`@here`면 산 게 발신자뿐, `@all`이면 명부가 발신자뿐): `to: ["@all"]` → 최종 0명 → `GROUP_EMPTY` 전체 반려 / `to: ["@all", "<자기이름>"]` → 펼침이 0명을 기여하고 명시 지목이 남아 **자기에게 1행 배달**(반려 아님).
- **동명 멤버 = 예외적으로 실패 행(ADR-0114 결정 4 — 과도기 규칙):** 펼침 결과에 같은 이름이 둘 이상 있으면(산 층 동명, 또는 `@all` 이 함께 읽는 **잠듦 층 동명** — ADR-0121) 그 이름은 **`RECIPIENT_AMBIGUOUS` 실패 행**이 된다 — "전원에게"의 명시적 예외다(임의로 한쪽을 고르거나 양쪽에 보내지 않는다. 어느 화신인지 발신자가 모르는 채 배달하는 편이 더 위험). *스폰 시 이름 유일성 보장(동명 자동 접미사 `이름(1)`·`이름(2)` — **ADR-0115**, 발송 개편 완료 후 별도 슬라이스)이 들어오면 이 모호성 부류 자체가 소멸한다 — 그때까지의 과도기 계약이다.*
- **그룹 전용 배달 규칙 폐지(폐지 사실의 정본 = 이 절):** 죽은 멤버 `skipped`(무반려 skip) 분기 **삭제** — `@here` 펼침은 **산 로스터만** 보므로(아래 명단 소스) "펼쳐진 멤버가 죽어 있다"는 상태가 스냅샷 한 장 원칙 하에서 발생하지 않고, `@all`이 함께 읽는 잠든 이름은 **애초에 죽은 멤버가 아니라 파킹 대상**이라 §5 분기 3이 정상 결말을 준다(ADR-0121 — skip 분기가 필요해지지 않는다). 이름을 직접 지목한 경우의 결말은 §5 분기 규칙이 단일하게 처리한다(그룹 전용 예외 없음). · 발송 순간 `(id,epoch)` **결박(bound_incarnation) 폐지**(아래 마지막 항목) · 방송 전용 fan-out 분기 없음. **이 분기들을 되살리면 ADR-0111 위반.**
- **명단 소스 = 내장 하나, 어휘는 둘(ADR-0121 결정 1)** — **무저장 즉석 계산**이고 둘 다 **− 발신자**다:
  - **`@all`** = **명부 전원**(산 것 **+ 잠든 것**). 산 몫은 §5 분기대로 배달/파킹되고 **잠든 몫은 파킹**돼 그 에이전트가 등장할 때 배달된다. 소스 = §5 로스터 스냅샷 + 프로필 잠든 이름 목록(같은 한 장, ADR-0116/0119).
  - **`@here`** = **지금 살아 있는 전원**(로스터만). 4차까지의 `@all` 동작이 이 어휘로 개명된 것이다.
  - **두 어휘가 같은 소스를 보면 ADR-0121 위반이다** — 이름이 "all"인데 잠든 상대가 빠지면 발신 LLM이 "전원에게 알렸다"고 믿고 놓치며, `@here`가 잠든 이름까지 읽으면 "지금 여기"의 뜻이 사라진다.
  - **`@all` 펼침은 같은 이름을 두 번 낼 수 있다(정상)** — 해석 소스는 넘겨받은 명단을 **verbatim** 돌려주고(가공 금지 — §4 해석 seam), 잠든 이름 목록 자체가 중복을 접지 않기 때문이다(ADR-0116/0120 과도기 방어). **결말은 그래도 한 행이다**: 동명 판정은 펼침 결과가 아니라 **잠든 이름 목록을 직접 세어** 하고, 같은 이름이 두 번 펼쳐져도 표기 중복은 한 행으로 접힌다 → 그 행이 `RECIPIENT_AMBIGUOUS` 실패 행이다. 즉 **펼침 단계에서 접든 안 접든 결과는 같다** — 접지 않는 이유는 "접으면 깨진다" 가 아니라 해석 층에 판정 지식을 흘리지 않는다는 seam 계약이다(동명 방어를 손볼 때 **펼침 결과가 아니라 잠든 이름 목록 쪽**을 봐야 한다).
- **사용자 정의 그룹(런타임 등록 명단 + `group` 관리 툴/CLI 서브커맨드 + ADR-0109 관리 semantics 일체)은 제거.** 저장형·이름붙인 그룹은 실수요가 서는 시점에 재설계한다(§8) — 그룹을 위한 구조를 미리 두지 않는다.
- **해석 = seam 유지**(ADR-0104 결정 1의 *방향*은 존속, 소스만 축소): "그룹 이름 → 멤버 목록" 해석 지점은 소스 플러그인 자리로 남기되 v1 소스는 **내장 하나**(어휘 `@all`·`@here` 둘을 그 소스가 소유한다 — 어느 어휘가 어느 명단을 읽는지는 **소스의 지식**이고 파이프라인은 두 명단을 다 넘긴다, ADR-0121). **폴더가 데몬 소유로 생기면 폴더 = 추가 소스**(`@폴더명` — 조직 방송의 정본 단위 예정)로 무파괴 확장. 하위 에이전트 계층은 주소 단위 **비채택**(ADR-0104 거부 대안 유지).
- **멤버십 = 이름 기반**(id 아님) — 주소 체계(WYSIWYA, ADR-0101)와 동일 원칙, 재스폰 생존.
- **`@` 네임스페이스는 예약** — 내장 어휘(`@all`·`@here`) 외의 `@이름`은 해석 실패 `GROUP_NOT_FOUND`, 최종 수신자 집합이 0명이면 `GROUP_EMPTY`. **둘 다 발송 단위 전체 반려**(혼용 `to`여도 마찬가지 — 나머지 수신자에게도 안 간다).
- **층위 구분(반려 vs 실패 행의 판별 기준 — ADR-0114 결정 3 · ADR-0116으로 세분):** **이름 층 = 런타임 상태**(표기는 정상) → **수신자별 처리** — 결말은 §5 분기 규칙이 정한다(배달 / 파킹 / 실패 행). **`@`주소 오류 = 주소 공간 오류**(존재하지 않는 주소 문법·오타 그룹명 = 발신자가 고쳐서 다시 보내야 하는 것) → **전체 반려**. 이 한 줄이 §5 부분 진행의 경계를 정한다.
- **그룹 request 금지(`GROUP_REQUEST_UNSUPPORTED`) 폐지** — `@all` 발송도 request 가능하다(수신자별 독립 계약 N개, §3). 회신은 항상 발신자 1인에게(전체회신 없음).
- **결박 폐지의 귀결**(ADR-0111 결정 6) — 파킹된 발송분은 같은 이름의 **새 화신(epoch)에게도 배달**된다(개인 편지와 동일 규칙). "발송 순간 화신에게만"이 필요해지면 v2 개인 메일 옵션(§8).

## 5. 메일박스 (인메모리)

**로스터 정의(한 줄 — 4차 개정):** 로스터 = **프로세스가 붙어 있는 에이전트 전원**(상태 `Running`·`Exiting` — busy도 포함). **구조화 출력 여부는 로스터 자격이 아니다** — 그건 "언제 넣을지"를 가르는 축일 뿐이다(아래 capability 하위규칙). 잠든(프로세스 닫힘·복원 가능) 세션과 아직 안 뜬 이름은 불포함.

**★턴 신호가 없으면 idle 게이트를 묻지 않는다 — 단 순서는 지킨다(사용자 결정 2026-07-30 + **ADR-0121 결정 2** · load-bearing)★:** idle 게이트는 **턴 경계를 관측할 수 있는 백엔드에만** 적용된다. 관측 수단(stream-json 턴 이벤트)이 없는 백엔드(터미널/콘솔 모드 등)는 **busy 판정을 시도하지 않는다**. **★주어 명시(6차 · ADR-0124)★ — "묻지 않는다"의 주체는 `flush 레인`이다.** 6차부터 발송 입구는 부류를 불문하고 busy를 아예 조회하지 않으므로(무조건 적재), 이 조항이 가르는 것은 **flush 레인이 그 수신자에게 게이트를 적용하는지**뿐이다. 근거: 그 CLI는 **자기 입력 큐를 갖고 있어서** 턴 진행 중에 들어온 입력을 물고 있다가 턴이 끝난 뒤 소비한다 → 우리가 idle을 관측할 필요가 애초에 없다(TUI 자신이 게이트다). 이 조항은 3차에서 "도달 불가"로 잘못 좁혀졌던 것을 원위치시킨 것이다(§8 wake 항목과 무관 — 그건 *잠든* 세션 이야기다).

**단 그 근거는 순서까지 덮지 않는다(ADR-0121 결정 2 — 요구는 그대로, 실현 방식만 6차에 교체 · ADR-0124):** "상대가 받을 준비가 됐나"와 "편지가 어떤 순서로 도착하나"는 다른 문제다. **요구:** 수신자 부류를 가리지 않고, 그 수신자 앞에 선행분(주입 실패 파킹·기한 통지·먼저 적재된 편지)이 있으면 새 발송이 앞지르지 못하며 **묵은 것부터 오래된 순으로 함께** 나간다(응답 행은 `pending`, 실제 배달은 flush 배치가 한다 — 경로 2벌 금지).
**실현 방식(6차에 바뀐 것):** 5차는 **발송 입구가 "앞에 뭐가 있나"를 보고** 합류 여부를 정했다(합류 판정). **6차 입구는 아무 조건도 보지 않고 전부 적재한다** — 그래서 **합류 판정이라는 장치 자체가 없어지고** 순서는 적재 순서로 자동 성립한다(ADR-0124 · 사용자 결정 "그냥 큐에 쌓고 뺄 때 한꺼번에 빼면 된다" — 아래 "발송은 전부 큐에 적재한다"). 위 요구는 그 구조에서 **판정 없이** 만족된다. 4차의 "대기·파킹·재시도 없이 한 번 쓰고 끝낸다 / 뒤돌아보지 않는다"는 **idle 게이트 축으로만** 유효하다.

**배치 도중 주입이 실패하면 그 지점에서 멈춘다(ADR-0121 결정 2):** 이미 나간 앞부분은 `delivered`로 남고, 실패 지점 이후는 파킹에 `pending`으로 남는다(다음 flush 계기에 재시도). **부분 성공을 전량 실패로 되돌리지 않는다** — `delivered → failed`는 전이 그래프상 불법이다(§6). 4차의 "재시도 없음"은 단건 전제였으므로 배치에서는 이 규칙이 그 자리를 대신한다.

**발송은 전부 큐에 적재한다 — 주입은 flush 레인 단독(불변식 — ADR-0124 · 6차 개정. 5차의 "직발송도 in-flight 회계에 든다(좌석 예약)" 조항을 대체한다):** 발송 진입점은 수신자별 판정을 마친 뒤 **락 안에서 큐에 넣고 끝난다** — 그 자리에서 상대 stdin에 쓰는 **직발송 지름길은 폐지**됐다. **발송 판정 경로가 직접 주입을 부르면 이 결정 위반이다**(주입은 flush 레인 소유).
- **순서 = 적재 순서.** 판정과 주입은 한 임계구역에 못 들어간다(락 규율 — 주입은 락을 놓고 불러야 한다. 락을 쥔 채 외부 호출을 하면 그쪽 락과 순서 역전·데드락). 5차는 그 사이에 생기는 경쟁 창("둘이 동시에 빈 큐를 보고 둘 다 직발송")을 좌석 예약으로 막았지만, 전부-큐가 되면 **창 자체가 없어져** **순서를 위한** 좌석·in-flight 회계·합류 판정이 필요 없다. **이 장치들이 다시 필요해졌다면 발송 경로가 둘로 갈라졌다는 신호다**(ADR-0124 §영향). *(보관함 cap의 "보관+주입중 합산"은 다른 축이다 — 순서 장치가 아니라 **cap 계수**이므로 이 조항이 폐지하지 않는다. 아래 정책 상수.)*
- **적재 직후 도어벨을 울린다.** flush 레인이 그 큐를 열 계기는 발송 자신이 만든다 — **울리지 않는 갈래가 남으면 그 편지는 다음 계기까지 갇힌다**(5차 맥락의 "주입 실패분 고립"이 직발송 폐지로 소멸하는지는 구현 때 테스트로 단언할 것 — §7 수용 기준).
- **귀결(알고 수용):** 같은 수신자에게 동시 버스트가 몰려도 **보관함 cap(수신자당 100건) 안에서는 전원 `pending`**이고 flush 레인이 오래된 순으로 배달한다(cap을 넘는 몫은 그 수신자만 `MAILBOX_FULL` 실패 행 — 아래 보관함 항목. "전원 `pending`"으로 잘라 적으면 cap과 모순된다). 5차가 좌석으로 치르던 대가("첫 건만 `delivered`, 나머지 99건은 `pending`")는 **응답 어휘에서 `delivered`가 사라지면서 함께 소멸**했다(§6) — 이제 `pending`은 지연 사유가 아니라 "접수됐다"는 정상 답이다.
- **cap의 적용 표면이 넓어진다(6차 귀결 — 알고 수용, cap 값은 불변):** 5차까지 보관함 cap 검사는 **파킹 갈래에서만** 돌았다 — 직발송은 cap 게이트를 지나지 않았고, "빈 큐 + idle이면 101번째도 즉시 주입되며 그것은 cap 위반이 아니다"가 명시 계약이었다. 전부-큐가 되면 **모든 발송이 cap 게이트를 지나므로** 5차에 통과하던 발송이 `MAILBOX_FULL`로 반려될 수 있다(cap 수치·회수 폐지는 그대로 — 값을 바꾸려면 별도 결정). 이 사실을 안 적어 두면 다음 세션이 늘어난 `MAILBOX_FULL`을 회귀로 오독한다.
- **예외(제거 금지):** 도어벨 트리거가 미배선인 조립(실험 bin·커널 단위 테스트)에서 **flush를 발신 스레드가 그 자리에서 동기 실행하는 갈래 전부**(트리거 부재 폴백 · 응답 확정 후 걸어둔 도어벨을 발신 스레드가 직접 비우는 드레인 포함)는 직발송이 아니다 — 그것은 *flush 레인을 그 자리에서 동기 실행*하는 것이고 단위 테스트가 결정성을 얻는 수단이다. "발신 스레드 주입"으로 오독해 걷어내면 커널 테스트 하네스가 비결정적이 된다(ADR-0124 §영향 — 예외를 특정 함수 하나로 좁혀 적지 말 것).

**영수증을 쥔 쪽이 유예 깨우기를 갚는다(불변식):** in-flight(배치 영수증 — 6차로 직발송 좌석은 폐지, 위 항목)를 쥔 동안 그 이름 앞 flush 를 시도한 쪽은 물러나며 표식만 남긴다. 정산 시 그 표식을 되울리지 않으면 깨우기가 증발해(lost wakeup) 뒤에 쌓인 편지가 다음 사건이나 TTL 까지 묶인다. ★**이 "물러남"이 곧 같은 수신자에 대한 flush 중복 진입 가드이고, 6차에는 순서 장치다**★ — 빼면 진행 중 배치의 잔여분을 새 배치가 앞질러 순서가 역전된다. ADR-0124 §영향의 금지("금지되는 것은 `직발송 좌석 예약`과 `직발송 합류 판정`의 재도입이다")는 **이것을 가리키지 않는다** — 같은 ADR 순서 bullet의 **하위 불변식(= 이 결정의 전제)**이 이 가드의 존치를 명령한다. **자기 주입 실패를 이유로 자기 도어벨을 누르는 것은 여전히 금지**(도달 불가해진 수신자에 재주입 반복) — 갚는 것은 *타인이 요청해 둔* 깨우기뿐이다.

**게이트 술어는 한 곳에서만 정의한다(불변식 — ADR-0121 §영향):** "이 부류는 idle 게이트를 묻지 않는다"를 판정하는 지점이 여럿이면 한쪽만 고쳐져 **두 지점이 다른 세계를 본다** — 그러면 큐에 쌓인 편지를 아무도 열지 않는다. 술어는 하나로 뽑고 판정 지점들이 그것을 부른다. **6차 정리(ADR-0124 — 5차의 열거 "발송 입구·주입 직전 재확인·flush 배치 게이트"를 대체):** 남는 판정 지점은 **flush 배치 게이트 하나**다 — **발송 입구는 이 술어를 부르지 않고**(무조건 적재), "주입 직전 재확인"은 직발송 경로와 함께 사라졌다. 지점이 하나여도 술어를 한 곳에 두는 규율은 유지한다(flush 레인 안에서 부류 판정·배치 게이트가 갈라지면 같은 사고가 재현된다).

- **알고 수용하는 대가(정직 명시):** 턴 신호가 없으면 ① 주입 시점에 **모달 상태**(권한 승인·메뉴·플랜 확인 다이얼로그)가 떠 있으면 우리 텍스트가 그 위젯에 먹힐 수 있다 ② 사람이 같은 화면에 타이핑 중이면 입력이 섞인다 ③ 여러 줄 봉투의 제출 처리가 붙여넣기 방식에 좌우된다. **"게이트로 미루지 않고 보낸다"가 채택된 방침**이며(사용자 결정 — 4차의 "뒤돌아보지 않는다"는 **idle 게이트 축으로만** 유효하다: 순서는 ADR-0121이 되돌렸다), 실제로 문제가 관측되면 그때 스파이크로 측정해 좁힌다(백로그). `delivered`는 여기서도 **실제 주입 시점**에 찍는다 — 읽혔는지는 어느 백엔드에서도 보장하지 않는 값이다.

**입구 판정 소스 = 로스터 + 프로필 목록, 물리 조회 2회(ADR-0116 — 4차 개정):** 로스터(= 상태 `Running`·`Exiting`인 세션 전원. **"세션 목록에 있음"이 아니다** — 종료된 세션도 reaper가 수거하기 전까지 목록에 남는다)에 없는 이름은 **프로필 목록**(트리에 저장된 에이전트 항목)으로 한 번 더 가른다 — 있으면 **잠듦 = 파킹**, 없으면 **없음 = 실패 행 `RECIPIENT_NOT_FOUND`**. 원칙 한 줄: **"살아 있으면 보내고, 나중에 살아날 수 있으면 기다리고, 없으면 시끄럽게 실패한다."**

**조회는 2회다(불변식):** 세션 스냅샷 1회 + 프로필 목록 1회. 세션 스냅샷을 두 번 뜨면 같은 발송의 두 수신자가 다른 세계를 보는 반쪽 판정이 재발한다(ADR-0111 결정 2 위반). 구조화 capability는 이 스냅샷의 **각 항목에 붙어 오는 속성**이라 별도 조회가 아니다 — 판정을 나누지 않고 "언제 넣을지"만 가른다 — **6차부터 그 "언제"를 정하는 주체는 flush 레인이다**(입구는 조회하지 않는다). ★5차까지 여기 있던 원칙 한 줄("받을 수 있으면 보내고 … 못 받거나 없으면 시끄럽게 실패한다")은 **삭제한다**★ — 입구를 수용 시점 축으로 서술해 6차와 정면 모순이고, "못 받으면 실패"는 어느 차수에서도 거짓이었다(busy·잠듦은 `failed`가 아니라 `pending`). 입구의 원칙은 위 :111 신원 축 한 줄이 유일 정본이다. 펼침 소스는 어휘가 가른다 — **`@here`는 로스터만, `@all`은 로스터 + 잠든 이름**(ADR-0121, §4).

- **프로필 쪽 이름 = 산 세션과 동일한 파생 규칙**(load-bearing): 잠듦 판정에 쓰는 이름은 산 에이전트의 canonical 이름과 **같은 헬퍼·같은 입력**으로 파생한다 — 헬퍼는 `canonical_name_or_id_fallback`(빈 override 무시 + placeholder degrade 가드 포함), 입력 cwd는 **canonicalize된 것**(산 이름은 스폰 때 정규화된 세션 cwd에서 나오는데 프로필에는 raw 경로가 들어올 수 있다). 어느 한쪽이라도 다르면 파킹 키(잠듦 시점 이름)와 복원 후 산 이름이 어긋나 편지가 주인을 못 만나고 24h 만료로 조용히 사라진다.
- **프로필 층에서도 동명은 모호 실패다(ADR-0116 결정 5 정합 — 과도기)**: 프로필 목록은 이름 유일성을 보장하지 않으므로(ADR-0115가 들어오기 전까지) **같은 이름의 잠든 프로필이 둘 이상이면 파킹하지 않고 `RECIPIENT_AMBIGUOUS` 실패 행**을 낸다. 이름 키로 파킹해 두면 **먼저 복원된 쪽이 조용히 받는다** — "어느 화신인지 발신자가 모르는 채 배달하는 편이 더 위험"(§4 동명 규칙)을 잠듦 층에서 뒤집는 구멍이라 막는다. 산 층·잠듦 층에 걸친 동명(산 1 + 잠든 1)은 **산 쪽이 이긴다**(로스터 판정이 먼저다 — 지금 받을 수 있는 실체가 있으면 그쪽이 수신자다).
- **스냅샷 사이의 경합 = 유계이므로 수용한다(정직 명시 — 4차):** 두 조회(세션 스냅샷·프로필 목록)는 서로 다른 순간이라 그 사이 spawn·삭제가 끼면 판정이 조금 낡을 수 있다. 조회는 **락 밖**에서 뜬다(모듈 절대 규율 — 입구가 외부 락을 들고 메시징 락을 잡으면 ADR-0006 락 순서가 깨진다. 정리 호출도 프로필 레지스트리 락을 해제한 뒤에 돈다). 그래서 **판정과 파킹 삽입 사이에 삭제가 끼면 그 항목은 삭제 정리의 스캔을 놓치고 남는다** — 임계구역은 스캔 중 끼어들기만 막고 스캔 이후 삽입은 막지 못한다. 이 잔여분의 결말은 **TTL 24h `expired`**이고(누수·오염 없음, 장부 종점 남음) `RECIPIENT_DELETED`가 아니다. 입구 원자적 뷰·삽입 시점 tombstone 재확인은 **비채택**(ADR-0116 거부한 대안) — 필요해지면 그때 추가한다. 반대 방향(판정 후 spawn)은 손해가 없다 — 파킹분이 등장 flush로 배달된다.

**수신자 해석 = 로스터 스냅샷 한 장(불변식, ADR-0111 결정 2):** 발송 1회당 로스터 스냅샷을 **하나만** 떠서 다중 수신자·`@` 주소 펼침·존재/동명 판정을 전원 일괄 처리한다(수신자별로 다시 뜨면 해석 도중 명단 변동에 의한 반쪽 판정이 재발한다 — 옛 그룹 스냅샷 원칙에서 존치된 조각). **프로필 목록 조회도 같은 원칙** — 발송 1회당 1회, 수신자별 재조회 금지(ADR-0116).

**`to` 원소 = 이름 또는 `@`주소(혼용 가능):** 목록의 각 원소는 에이전트 이름이거나 `@`주소이며, `@` 원소는 그 자리에서 펼쳐지고(**펼침에서 발신자 제외** — §4) 이름 원소와 **합집합**으로 합쳐진다. 해석 순서 = ① 콤마 분해(**CLI 입구 한정** — §6, MCP 배열 원소는 분해 없음)·트림 → ② `@` 원소 펼침(발신자 제외) → ③ 이름 원소와 합류 → ④ **중복 제거(수신자 1명 = 배달 1회·결과 1행)** → ⑤ 로스터 대조(존재·동명). 이 정규화는 **데몬 단일점**(두 입구 동일 결과). `@all`과 직접 지목이 겹쳐도 1행이고, 자기 이름 직접 지목은 펼침 제외와 무관하게 살아남는다(§4).

**행 순서 = 결정적(테스트 고정):** `results[]`는 ① **입력에 적힌 명시 토큰을 적힌 순서대로**, ② 그 뒤에 **`@`주소 펼침 결과를 이름 사전순**으로 잇는다. 중복 제거는 **먼저 나온 것을 남긴다**(명시 지목이 펼침 결과보다 항상 앞서므로, 겹친 수신자의 행 위치는 명시 위치를 따른다).

**수신자 1명당 3분기(다중 수신자는 이 판정을 수신자마다 1회씩 = fan-out, 경로 1벌 — ADR-0116으로 4차 개정 · 6차로 판정 축 정리):**

★**6차의 축 분리(load-bearing — ADR-0116이 뒤집힌 게 아니다)**★: 이 3분기는 **"이 수신자가 누구냐"(신원 축)**만 판정한다 — 없음 / 잠듦 / 산 것, 그리고 동명 모호. **ADR-0116 결정 1의 판정 트리는 그대로 살아 있다.** 6차에 사라진 것은 입구가 함께 보던 **"지금 받을 수 있나"(수용 시점 축)** 뿐이다: 발송 입구는 busy도 선행분도 보지 않고 **무조건 적재**하며, 언제 뺄지는 **flush 레인이 자기 게이트로** 정한다(ADR-0124). 그래서 2·3번은 **응답으로 구분되지 않고**(둘 다 `pending`) 차이는 flush 레인이 언제 빼느냐로만 남는다. 주입은 어느 분기든 flush 레인이 한다. **두 축을 다시 합쳐 입구에 "받을 수 있나" 판정을 되돌리면 ADR-0124 위반이다.**
1. **입구(ControlIngress) 반려 → 수신자별 실패 행** — 판정 근거는 위 두 소스뿐이고, 주입 성공 여부는 이 분기에서 보지 않는다(6차 — 그건 입구가 볼 수 없는 **flush 레인 축**이다: 3번 항목의 축 이동 설명).
   - **없음** — 로스터·프로필 **둘 다에 없다**(오타·미스폰·삭제됨) → `failed` + `RECIPIENT_NOT_FOUND`(ADR-0116 결정 1).
   - **동명 다수** → `RECIPIENT_AMBIGUOUS`(어느 층에서든 수신자별 행). **층이 겹치면 로스터 층이 이긴다** — 살아 있는 동명이 둘 이상이면 그 사실이 발신자가 고쳐야 할 것이다. **힌트의 카운트는 로스터 카운트**이므로 문구도 그렇게 라벨한다.
   - **스폰 전 선지시(예약 발송)는 프로필 없는 이름 한정 비지원**(§8). **깨우기(wake) 없음** — 잠든 수신자는 파킹될 뿐 깨우지 않는다(§8 v2 후보).
2. **산 수신자(로스터에 있음) — 적재하고 응답 행 `pending`.** 입구는 여기서 **busy도 선행분도 보지 않는다**(6차 · ADR-0124 — 5차까지 이 분기는 "지금 넣을 수 있으면 즉시 주입 `delivered`"였다). 적재 직후 도어벨이 울리고, **언제 빼는지는 flush 레인의 게이트**가 정한다 — 그 게이트에 두 갈래가 있고 **입구의 결과 어휘는 어느 쪽이든 같다**:
   - **턴 신호 있는 백엔드** — flush 레인이 idle 게이트를 본다(턴 중이면 그 배치를 미룬다 — 아래 주입 타이밍).
   - **턴 신호 없는 백엔드** — flush 레인이 **idle 게이트를 묻지 않는다**(사용자 결정 2026-07-30 · ADR-0116 결정 7 = 6차에도 유지). busy 판정을 하지 않으므로 이 부류는 **busy를 사유로 미뤄지는 일이 없다**. **단 순서는 부류 무관**이다 — 그 수신자 앞에 묵은 것이 있으면 오래된 순 한 배치로 함께 나간다(ADR-0121 결정 2: 게이트 생략 근거는 "받을 준비"만 덮고 "도착 순서"는 덮지 않는다. 그 CLI의 입력 큐는 *턴 중 타이밍*만 대신 처리하고 우리 큐의 순서는 대신 처리해 주지 않는다).
   - **장부**의 `delivered`는 어느 갈래든 **실제 주입 시점**(= flush 레인이 쓴 순간)에만 찍는다(아래 주입 타이밍) — **발송 응답에는 이 어휘가 없다**(§6). 두 축을 섞지 말 것.
3. **잠든 수신자(로스터엔 없지만 프로필 존재·복원 가능 — ADR-0116 결정 1, 잠듦 파킹) — 적재하고 응답 행 `pending`**, 복원될 때까지 큐에 머문다. 옛 "부재 파킹"과 다르다 — 프로필에 실재하는 이름만 수용하므로 오타가 조용히 쌓이는 경로는 없다.
   - **입구가 판정하는 것은 여기까지다(6차).** 5차까지 이 분기에 함께 적혀 있던 나머지 사유 — **busy**(턴 신호 있는 백엔드가 턴 진행 중) · **선행분 뒤 FIFO**(그 수신자 앞에 쌓인 것 + **이미 나가 있는 것** = 진행 중인 flush 배치. 6차로 직발송·좌석 예약이 없어져 "진행 중인 직발송" 항은 소멸했다 — 되살리지 말 것) · **주입(write) 실패** — 는 **삭제된 게 아니라 축이 옮겨졌다: 전부 flush 레인 축의 "아직 안 빠진 이유"**다(입구는 주입하지 않으므로 실패를 볼 수 없고, busy·선행분도 묻지 않는다). 재파킹 규칙 = 위 "배치 도중 주입이 실패하면 그 지점에서 멈춘다".
   - **flush 계기(부류 공통)** = **적재 직후 도어벨(6차 신설 — 주 계기, ADR-0124 결정 4: 뒤이은 발송이 적재하며 울린 도어벨이 이 큐도 함께 연다)** · idle 진입 · 재등장(스폰/복원/epoch — 기존 로스터 diff 기계). **주입 실패분에 별도 재시도 트리거는 없다 — 다음 flush 계기까지 대기**한다(v1 기존 동작 계승, 개선은 백로그).

**보관함(수신자당 100건) 초과** → **그 수신자만 즉시 실패 행 `MAILBOX_FULL`**(다중 수신자에서 **전체 반려로 승격하지 않는다**). **압력 회수(잔해 은퇴 후 수용)는 폐지**(ADR-0114 결정 1 — ADR-0107 결정 2 개정). 폐지 근거였던 "배달 불가 확정 잔해 = 공집합"이라는 **논리 주장은 4차 개정으로 약화됐다**: 프로필도 없는 이름은 여전히 입구에서 걸러지지만, 복원되지 않는 잠든 이름의 파킹분은 *복원 가능*이지 *복원됨*이 아니고(삭제 정리도 삭제 시점 단발이라 일부는 TTL까지 남는다 — 위 항목), 그 보관함이 100건까지 차면 이후 발신자들이 `MAILBOX_FULL`을 받는다(3차엔 불가능했던 상태). **유계 근거는 이제 논리 공집합이 아니라 TTL 24h + 보관함 cap이며**, 그 안에서 회수 폐지를 유지한다(회수 재도입을 재론하려면 이 문장을 근거로 새 결정을 박을 것). 정리는 **60초 주기 TTL 스윕 하나**(24h 경과분 `expired`)뿐. **산 메일 조용히 버리기 금지는 불변** — 모든 제거는 장부 종점을 남긴다(레코드가 이력 링에서 이미 밀려난 경우만 debug 로그로 강등 — best-effort, 제거 사실은 로그 잔존).

**부분 진행(ADR-0111 결정 3):** 수신자별 판정은 서로 독립 — 일부가 실패해도 **나머지 수신자에겐 그대로 배달**된다. 전체 반려는 **발송 자체의 문제**뿐: 인자 오류·상호배타 위반(`INVALID_SEND_ARGS`) · `BODY_TOO_LARGE` · 비XML 포맷에서의 계약 필드 · 주소 공간 오류(`GROUP_NOT_FOUND`/`GROUP_EMPTY` — 층위 근거는 §4) · `INTERNAL_ID_COLLISION`. **전원이 실패해도 응답 shape은 그대로**(`results[]` 전 행 `failed`) — 전체 반려로 승격하지 않는다(단일 수신자 발송도 예외 아님: **없는 이름** 1인 발송의 답은 `error`가 아니라 `failed` 행 1개다 = 경로 1벌. 잠든 1인 발송이면 `pending` 행 1개다 — 4차. **6차 보정: `pending`은 잠듦 전용 어휘가 아니다** — 산 수신자 1인 발송의 답도 `pending`이다(§6)).

**파킹의 운명:** **적재 직후 도어벨(6차 — 뒤이은 발송이 울린다)** · 수신자 idle 진입 · 재등장(epoch 교체) 시 자동 주입 `delivered`(**일괄·오래된 순** — 아래 주입 타이밍의 flush 규칙과 동일: 경로 2벌 금지, ADR-0104) / TTL 초과 `expired`(장부 잔존). **결박 없음** — 같은 이름의 새 화신이 받는다(ADR-0111 결정 6). **TTL은 파킹 사유 구분 없이 동일 적용 — 생존 기반 면제 없음**(시계 기반 단일 규칙, ADR-0105). **파킹된 request가 TTL로 `expired`돼도 그 계약은 오픈 유지** — 자동 닫힘 없음(발신자 통지는 `reply_by` 경로 소관, §3 항목 5).

**만료는 조용하다 — 알고 수용한 성질(사용자 결정 2026-07-30):** 파킹분이 24h TTL로 `expired`될 때 **발신자에게 능동 통지는 없다**(발송 응답의 `pending` + 이후 `messages` 조회가 전부). busy 파킹과 잠듦 파킹에 **같은 규칙**을 적용한다 — 잠듦은 "아무도 복원하지 않으면 조용히 만료"가 기본 결말이라는 점을 인지하고 그대로 둔다(규칙 하나 유지 > 파킹 사유별 예외). 개선 후보(만료 시 발신자 통지 · request 기한 통지에 "미배달" 구분 문구)는 **백로그** — 필요해지면 그때 추가한다. 이 항목이 없으면 다음 세션이 "누락"으로 오독한다.

**프로필 삭제 = 일괄 정리(ADR-0116 결정 3 — 4차 개정):** 발동 조건 = **삭제 ∧ ① 그 프로필의 세션이 로스터에 없음(id 축) ∧ ② 그 이름을 가진 산 세션이 없음(이름 축)** — 세 항의 논리곱이다(사용자 결정 2026-07-30 + 리뷰 R2 적출로 이름 축 추가). **두 축이 다 필요한 이유:** 게이트는 id 하나로 판정하는데 정리는 **이름 키로** 파킹 큐·계약을 쓸어가므로, 이름을 공유하는 산 세션이 있으면 그쪽 편지가 `RECIPIENT_DELETED`라는 **거짓 사유**로 죽고 그가 요청자인 계약이 실패 종결된다(동명이 아직 허용되는 과도기의 실경로 — ADR-0115가 뿌리를 제거하면 이름 축 가드는 불필요해진다). 두 축 검사가 원자적이지 않아도 무해하다 — 경합 시 결과는 "건너뜀"(안전 쪽)으로만 기울고, 정리는 두 축이 모두 죽었을 때만 발동한다. 프로필 삭제 커맨드는 실행 중 세션을 죽이지 않으므로(킬은 별도 커맨드) "트리 항목만 지웠고 프로세스는 살아 있는" 상태가 존재한다 — 그 상대는 **곧 idle이 되면 받을 수 있는 산 수신자**라서 정리 대상이 아니다(정리하면 배달될 메일을 죽이고 성립할 계약을 실패로 적는다 = 이 개정 취지의 정반대). 그 세션이 실제로 사라지는 시점엔 프로필도 없으므로 자연히 "없음" 부류로 수렴한다.

조건이 성립하면: ① **그 이름 앞 파킹분을 실패 종결** — 상태 `failed` + 코드 **`RECIPIENT_DELETED`**(장부 종점 기록 + 힌트 동봉, 아래 어휘 항목). "산 메일 조용히 버리기 금지" 불변식 유지 — 대기열에서만 사라지고 이력은 남아 발신자가 `messages{id}`로 사유를 본다. ② **그 이름을 회신 대상(요청자)으로 하는 오픈 계약을 `reply_failed`로 실패 종결**(회신 도달 불가 확정 — 오픈 목록·기한 스윕·512 계수에서 제거). 이미 `replied`로 닫힌 계약은 **되돌리지 않는다**(§3 항목 7-④ — 수용 = 완료). 단 §3 항목 7-④의 가드 규칙대로 **잠정·은퇴 표시 계약은 정산 후에** 적용한다. 회신자 쪽이 삭제된 계약은 **유지**한다 — 발신자는 기한 통지(§3 항목 4~5)로 무응답을 알게 되는 기존 경로가 살아 있다.

**정리는 삭제 시점 단발이다 — 재평가 트리거를 두지 않는다(정직 명시 · 4차):** 발동 조건은 삭제 그 순간에만 평가된다. 그래서 **프로필만 지운 산 세션이 나중에 죽는 경우**, 이미 쌓여 있던 파킹분·그 이름이 요청자인 오픈 계약을 거둬갈 사건이 없다 — 그 잔여분의 결말은 **TTL 24h `expired`**(계약은 기한 통지 후 ADR-0108 은퇴 대상 편입)이고 `RECIPIENT_DELETED`가 아니다. 대칭 트리거(로스터 이탈 ∧ 프로필 부재에서 재발화)는 **비채택** — 지금 필요한 최소만 만들고(사용자 방침 2026-07-30) 필요해지면 추가한다(백로그). **이 항목이 없으면 다음 세션이 "안 다룬 버그"로 읽는다.**

**삭제 UX(트리 삭제가 킬을 동반할지·강제/조용한 삭제 옵션)는 이 spec 범위 밖**(에이전트 수명 모델 소관 — 백로그). 위 조건식은 어느 UX가 되든 안전하다: 삭제가 킬을 동반하면 그 순간 둘 다 없어져 즉시 정리되고, 산 세션이 남는 경로에서도 오동작이 없다.

**주입 타이밍 = idle 게이트 + 일괄 flush (ADR-0104):**
- 수신자가 턴 진행 중(busy)이면 주입하지 않고 메일박스 대기 — `delivered`는 실제 주입 시점에만 찍는다(CLI 내부 stdin 큐로 밀어넣지 않음: 장부 정확성 + 배치 제어권 유지).
- **적재 직후 도어벨(6차 신설 — ADR-0124 결정 4)** · idle 진입(턴 종료) · 등장(스폰/epoch) 시 쌓인 메시지 **전부 일괄 주입**(오래된 순, 메시지마다 자기 봉투 — XML이라 배치 내 경계 명확). 1건씩 드리블 금지.
- busy/idle 관측 = 백엔드 capability(stream-json 턴 이벤트 기반). **관측 불가 백엔드는 게이트 없는 주입 폴백 — 이 조항은 4차에서 정식 복권됐다**(사용자 결정 2026-07-30 · 위 "턴 신호가 없으면 idle 게이트를 묻지 않는다" 항목이 정본). 3차가 이 부류를 로스터에서 제외해 폴백 지점을 도달 불가로 만들었던 것을 되돌린 것이다. **폴백은 게이트만 건너뛴다 — 선행 파킹분 합류(오래된 순 일괄)는 이 부류도 그대로 탄다**(ADR-0121 결정 2). capability 매트릭스 정본 = ADR-0002·0030(차이는 구조가 아니라 capability 유무).
- `reply_by` 시계는 발송 기준 유지(수신 지연과 무관 — 발신자 관점 계약).

**정책 상수(ADR-0107):** TTL **24h**(1h→상향, ADR-0105 — 인메모리 단계 한정, 영속화 때 재설계) · message 레인 수신자당 **100건**(보관+주입중 합산 — in-flight 회계) · **notice 전용 레인 64건**(20→상향, ADR-0114 결정 2 — 다중 request의 계약별 통지가 계약 수만큼 쌓이므로 20은 좁다. 반려 없음 — 초과 시 가장 오래된 통지를 은퇴하고 장부 `skipped` 기록. 주입 중 배치 창에서 **+1 일시 초과 허용**(명시 계약·자기수정). 구 "cap 예외" 대체 — 무계 통로 제거).

**장부(ledger):** 전 메시지 이력 링버퍼 **4096건**(1024→상향, 사용자 결정 2026-07-26 — 본문 전문 보관이라 최악(64KiB×4096) ≈ 256MiB 수용, 런타임 설정 노출·본문 절단 저장은 후속 항목) — 발신·수신·상태 전이 + 시각(`pending→delivered→replied` / `expired` / `skipped` / **`pending→failed`(삭제 정리 한정 — 4차, §6 전이 그래프)**). 상태 전이 시각이 곧 회신시각·발신시각 데이터(봉투 미노출). 링에서 밀려난 레코드의 종점 전이는 debug 로그로 강등(best-effort).

**실패 수신자도 장부에 남는다:** **모든 `failed` 행의 수신자**(입구 반려·`MAILBOX_FULL`·`REQUEST_CAPACITY`)를 **종점 상태의 배달기록 행으로 기록**한다(파킹은 없지만 기록은 있다 — 발신자가 나중에 `messages{id}`로 "누가 못 받았나"를 다시 볼 수 있어야 한다). 따라서 **장부 기대 행수 = 발신 응답 행수**로 맞아떨어지고, 실패 수신자를 안 남겨서 생기던 `may_be_truncated` 오탐이 사라진다(§6).

**flush 훅:** AgentManager의 에이전트 등장/epoch 전이에서 해당 이름의 pending 주입(기존 `write_stdin_observed` 경로 재사용).

**주의(ADR-0111로 반전 → ADR-0116으로 의미 축소):** `RECIPIENT_NOT_FOUND`는 **부활**하되(구 "단일 발송에서 소멸·파킹으로 대체" 문구 폐기) 4차 개정으로 의미가 좁아졌다 — **"프로필도 없는 이름"의 수신자별 실패 행 코드**다(잠든 세션은 파킹 `pending` — 이 코드를 내지 않는다). `RECIPIENT_AMBIGUOUS`(동명)도 같은 층, `BODY_TOO_LARGE`는 발송 단위 반려로 유지. 응답 어휘와 장부 어휘의 대응표는 §6.

## 6. 입구 — MCP 주력 · CLI 예비 (듀얼 입구 유지, ADR-0086)

**MCP 툴 2개 (ADR-0111 결정 4로 `group` 툴 제거 — 구 "툴 3개 상한" 갱신. 컨텍스트 비용: 디퍼드 로딩으로 상주 ~0 — 실측 2026-07-24, claude 2.1.170):**

```
send_message { to, body, request?, reply_by?, reply_to? }   # 발송 전부. reply_to↔request 상호배타
                                                            # to = 문자열 1개 | 문자열 배열. 각 원소 = 이름 또는 "@주소"(혼용 가능)
messages     { id? }                                        # id=상태 조회 / 무인자=내 미결(pending+awaiting_reply)
```

- **`to`의 복수 표기(확정):** MCP = `string | string[]` — **단일 문자열 형태는 그대로 유효**(하위 호환, 기존 호출 무변경. 단일 문자열도 이름·`@`주소 둘 다 가능). **각 원소는 이름 또는 `@`주소이고 혼용 가능** — `@` 원소는 펼쳐지고(발신자 제외, §4) 이름 원소와 합쳐진 뒤 중복 제거된다(§5 해석 순서). 빈 목록(`[]`·빈 문자열)은 `INVALID_SEND_ARGS`.
- **콤마 분해는 CLI 입구 전용:** CLI는 한 문자열 인자를 콤마로 쪼개 목록을 만든다. **MCP 배열 원소는 그대로 쓴다** — 원소 `"a,b"`는 **쪼개지 않고** 그 이름 하나로 취급한다(→ 그런 이름이 없으면 `RECIPIENT_NOT_FOUND` 행). 배열이라는 구조가 이미 경계를 주므로 이중 분해를 하지 않는다. 분해 이후의 정규화(트림·펼침·중복 제거·로스터 대조)는 **데몬 단일점**이라 두 입구 결과가 같다.

**CLI (예비 미러 + 사람 테스트):**
```bash
engram-send --to <수신자[,수신자…]> --body "..." [--request [--reply-by 10m]] [--reply-to m-xxxx]
#            수신자 = 이름 또는 @주소(혼용 가능) — 예: --to qa-alpha,@here
engram-send --to <수신자> --body-stdin <<'EOF' ... EOF      # 인용 지옥 회피(신규)
engram-send status <id> | pending
```

**발신 응답(두 입구 동일 JSON — 바이트 동일, 파리티 테스트 고정):** `{ id, results: [{to, status, code?, hint?}] }` — shape 불변, 수신자 1명당 1행. 상태 어휘 = **`pending|failed`**(6차 — ADR-0124로 **`delivered`가 발송 응답 어휘에서 제거**됐다: 모든 발송이 큐 적재로 끝나므로 정상 발송의 답은 `pending` 하나다. **장부 어휘의 `delivered`는 그대로**(= 실제 주입 시점, ADR-0104 — 아래 대응표·§5). **응답에서 사라졌다고 장부에서 지우면 배달 관측이 무너진다** — 두 축을 섞지 말 것):

- `pending` = **접수됨(간다)** — "큐에 적재됐다"는 뜻이고 **지연·이상 신호가 아니다**(6차). 실제 주입 여부는 이 응답이 답하지 않는다 → `messages{id}` 조회로 본다. 잃은 것은 "지금 당장 들어갔다" 대 "줄 서 있다"의 구분뿐이고, **오타·없는 상대는 여전히 `failed`로 즉시 온다**(ADR-0124 — 발신 LLM이 `delivered`/`pending`을 보고 다르게 행동할 경로가 없어 실질 영향이 작다는 판단. 되살리려면 별도의 **비동기 배달 영수증**이 정공법이고 v2 후보다: 지금 안 하는 것이지 틀려서 버린 게 아니다).
- `failed` = **신설**(ADR-0111 결정 3) — 그 수신자만 실패. 실패 행엔 **`code` 필수 + `hint`**. **발송 응답의 실패 코드는 4종**(`RECIPIENT_NOT_FOUND`·`RECIPIENT_AMBIGUOUS`·`MAILBOX_FULL`·`REQUEST_CAPACITY`)이고 **전부 큐 적재 *전* 판정이라 6차에도 즉시 반려된다**(ADR-0124 — "3종"으로 줄여 적지 말 것. `pending`으로 흡수되면 발신자가 오타를 영영 모르고, `REQUEST_CAPACITY`는 추적 없는 request가 배달된다 §3 항목 5). `RECIPIENT_DELETED`는 발송 응답이 아니라 조회 시점 코드다(아래). 행 코드:
  - `RECIPIENT_NOT_FOUND` — **로스터·산 명단·프로필 전부에 없는 이름**(오타·미스폰·이미 삭제됨). 잠든 세션은 이 코드가 아니다(`pending` 파킹 — ADR-0116).
  - *(`RECIPIENT_UNREACHABLE`은 4차 초안에서 잠깐 신설됐다가 **폐기**됐다 — 턴 신호가 없는 상대도 "게이트 없이 즉시 주입"으로 정상 배달 대상이 됐으므로 그 코드가 가리킬 상태가 없다. **6차 주석: 그 즉시 주입도 이제 flush 레인이 한다**(적재 후 도어벨) — 게이트에 걸리지 않는다는 성질은 그대로이므로 폐기 결론도 그대로다. 되살리지 말 것: ADR-0116 거부한 대안.)*
  - `RECIPIENT_AMBIGUOUS` — 동명 다수(산 층 또는 잠듦 층 — §5). **힌트 = "동명이인은 지원되지 않는다 · 재발송하지 말고 사용자에게 알려라"**(ADR-0116 결정 5 — exact-id 재발송 안내 아님). 과도기 코드 — ADR-0115로 사문화 예정.
  - `MAILBOX_FULL` — 보관함 100건 초과.
  - `REQUEST_CAPACITY` — 그 수신자의 계약을 열 수 없음.
  - **`RECIPIENT_DELETED` = 신설(4차 · ADR-0116 결정 4 · 사용자 결정 2026-07-30)** — **파킹돼 기다리는 동안 수신자가 삭제돼** 미배달 종결된 것. `RECIPIENT_NOT_FOUND`(보낼 때부터 없었다 = 입구 즉시 반려, 파킹된 적 없음)와 **시점이 다르다** — 발신자가 "이름을 잘못 썼구나"와 "기다리다 상대가 지워졌구나"를 구분해야 재발송 판단이 갈린다. **이 코드는 발송 응답이 아니라 `messages` 조회에서 처음 보인다**(발송 시점엔 `pending`이었다) — 그래서 조회 행에도 `code`와 함께 **힌트를 싣는다**: "파킹 대기 중 수신자가 삭제돼 미배달 종결 — 그 이름은 더 없으니 재발송은 무의미, 필요하면 사용자에게 알릴 것". 코드 이름만으로도 읽히고 힌트까지 보면 다음 행동이 나오게 하는 것이 요구사항이다(프라이밍 문서에도 이 어휘를 가르친다 — §7).
- `skipped`는 **응답 어휘에서 폐지**(그룹 멤버 skip 규칙과 함께 소멸 — §4). 장부 종점 어휘의 `skipped`는 다른 축이라 잔존 → 아래 대응표.
- **발송 단위 반려** = `{ status:"error", code, hint }` (`results` 없음) — 수신자별로 나눌 수 없는 문제만: `INVALID_SEND_ARGS`(계약 필드 문법·상호배타·비XML 포맷 위반·빈 수신자 목록·`reply_to`+다중 수신자) · `BODY_TOO_LARGE` · `GROUP_NOT_FOUND`/`GROUP_EMPTY`(주소 공간 오류 — 층위 근거 §4) · `INTERNAL_ID_COLLISION`(id 재생성 1회 후에도 충돌 — 사실상 미발생 가드).
- **파서 분기 기준(수용된 비대칭 — 명시):** 성공 응답엔 top-level `status`가 없고, 반려 응답엔 `results`가 없다 — 수신 측은 `status == "error"` 존재 여부로 분기한다(shape 통일은 하지 않는다, 기존 계약 유지).
- **미명세(6차 — 구현 슬라이스에서 결정할 것, 여기서 정하지 않는다):** 와이어 쪽 상태 열거는 아직 **3종을 하드코딩**한다(CLI 입구의 허용값 배열 · 데몬 control 입구의 파싱). `delivered`가 응답 어휘에서 **도달 불가**가 됐을 때 그 variant를 **은퇴시킬지 죽은 값으로 남길지는 ADR-0124가 정하지 않았다** — 남기면 위 "두 입구 바이트 동일·파리티 테스트" 고정은 그대로 통과하지만 계약 표면에 죽은 어휘가 남고, 지우면 와이어 호환·역직렬화 실패 경로를 함께 봐야 한다. **이 문서가 규정하는 것은 "발송 응답으로 그 값을 내지 않는다"까지다.**

**어휘 대응표 — 발송 응답(발송 어휘) vs `messages` 조회(장부 어휘):** 둘은 **다른 축**이다. 응답은 "그 발송 호출이 어떻게 끝났나"의 순간 스냅샷, 조회는 "그 배달기록이 지금 어디까지 갔나"의 장부 상태다.

| 발송 응답 status | 이어지는 장부 상태(조회 status) | 전이 |
|---|---|---|
| `delivered` — **6차: 발송 응답 어휘에서만 제거 → 이 행 도달 불가**(장부 어휘는 존치) | (해당 없음 — **장부에서 없어졌다는 뜻이 아니다**) | 발송 응답이 `delivered`를 내지 않으므로 이 행으로 *들어오는* 경로가 사라졌다(ADR-0124). 장부의 `delivered`는 멀쩡히 살아 **아래 `pending` 행 *안에서* 도달한다**(= 실제 주입 시점). **행을 지우지 않는 이유**: 지우면 다음 세션이 "장부에서도 `delivered`가 없어졌다"로 오독한다 |
| `pending` — **6차: 정상 발송의 유일한 답** | `pending` → `delivered` → (request면) `replied` / `expired` / **`failed`(+`RECIPIENT_DELETED`)** | 적재 → flush 시 주입(`delivered`) / TTL 24h 초과 시 `expired` / **삭제 정리 시 `failed`**(4차) |
| `failed` (+`code`) | 종점 그대로 기록(더 안 움직임) | 입구 반려·`MAILBOX_FULL`·`REQUEST_CAPACITY` |
| (없음 — 응답에 안 나옴) | `skipped` | 장부 전용 종점: notice 레인 64건 초과 은퇴 |

**장부 초기 상태 = 일률 `pending`(6차 — ADR-0124 결정 3):** 5차까지 직발송은 `pending`을 거치지 않고 곧장 `delivered`를 적었지만, 전부-큐가 되면 **모든 배달기록이 `pending → delivered`를 거친다.** 관측되는 귀결 둘: ① 위 표의 **`delivered`로 시작하는 행이 도달 불가**가 된다 ② **`messages` 무인자(= 내 미결) 조회에 모든 발송이 일시적으로 뜬다**(적재~주입 사이 창 — 알고 수용, 아래 무인자 항목). **바뀐 것은 시작점과 발송 호출의 반환 어휘뿐이고 종점 어휘·의미는 무변경**이다 — `delivered`는 여전히 "stdin에 썼고 전량 수용됐다"는 실제 주입 시점 기록이다(ADR-0104 · ADR-0121 결정 3). "장부 무변경"으로 뭉뚱그리지 말 것. **전이 그래프 자체는 이 개정에서 손대지 않는다**(ADR-0124가 합법 간선을 논하지 않는다 — 아래 4차 조항 그대로).

**상태 전이 그래프 개정(4차 — 구현 계약):** 합법 간선에 **`pending → failed`를 추가**한다 — 단 **삭제 정리(§5) 한정**이고 사유 코드는 `RECIPIENT_DELETED`다. 그 외 경로로 `failed`에 들어오는 간선은 여전히 없다(실패 행은 처음부터 그 상태로 기록된다 — "배달됐다가 실패로 돌아간" 불가능한 이력을 표현 가능하게 만들면 안 되므로 `delivered → failed`는 불법 유지). 이 한 간선을 여는 이유: 삭제 정리는 *이미 파킹된* 레코드를 사후에 종결하는 유일한 경로라 기록 시점 종점으로 표현할 수 없고, `expired`(시간 만료) 재사용은 사유가 거짓이 된다(거부한 대안 — ADR-0116).

- **계약 쪽 필드(배달 상태와 별개 축):** `awaiting_reply` = 그 수신자의 request 계약이 회신 대기 중 · `timed_out` = `reply_by`가 지나 발신자에게 통지까지 나갔으나 **계약은 여전히 오픈**(ADR-0108 — 종결 아님). 회신이 오면 둘 다 `replied`로 닫힌다. · **`reply_failed`(4차 신설, ADR-0116 결정 2·3)** = 계약 **실패 종결** 종점. 발화 경로는 **딱 둘**이다: ① 회신 발송 행이 **`RECIPIENT_NOT_FOUND`**(§3 항목 7-④) ② **요청자 프로필 삭제 정리**(§5 — 오픈 계약만 대상). 오픈 목록·기한 스윕·512 계수에서 제거되고 이력은 잔존한다. `replied`와 달리 "회신이 성립했다"를 주장하지 않는다. **그 밖의 회신 실패는 이 상태로 가지 않는다**(무동작 = 계약 오픈 유지 — §3 항목 7-④).

- **축 구분(혼동 방지 — load-bearing):** `reply_failed`는 **계약 축**의 종점이고 **배달 상태(`DeliveryStatus`) 어휘가 아니다.** 원 request의 배달기록은 그대로 `delivered`(또는 `pending`)에 머문다 — 그 메시지는 실제로 배달됐고, 실패한 것은 *회신 쪽*이다. 즉 `delivered → reply_failed` 같은 배달 상태 전이는 존재하지 않는다(그런 간선을 만들면 "배달됐다가 실패로 돌아간" 이력이 표현 가능해진다 — 위 그래프 규칙 위반). 계약 축과 배달 축은 별개 축이라는 이 절의 원칙 그대로다.
- `messages` 무인자 = 내 미결(`pending` + `awaiting_reply`) — **6차 귀결(알고 수용): 모든 발송이 `pending`으로 시작하므로 방금 보낸 것까지 일시적으로 여기 뜬다**(flush 레인이 빼면 사라진다 · ADR-0124 결정 3. 이 항목이 없으면 다음 세션이 "미결 조회가 오염됐다"로 오독한다). `messages{id}` = 그 메시지의 수신자별 행.

`REQUEST_CAPACITY`(동시 상한 512 — §3 항목 5)는 **발송 단위 반려에서 수신자별 행 코드로 이동**했다(다중 수신자 중 일부만 계약을 못 여는 상황이 정상 경로가 되므로). **제거된 어휘:** `GROUP_REQUEST_UNSUPPORTED` · `INVALID_GROUP_NAME`·`INVALID_MEMBER_NAME`·`GROUP_BUILTIN`·`INVALID_GROUP_ARGS`(다중 request 허용·group 툴 제거에 동반 — §4). **유지:** `MESSAGE_NOT_FOUND`(조회). 메시지 id 표기 = `m-` + base36 8자(수신 LLM이 `reply_to`로 옮겨 적는 값이라 단문형 — UUID 폐기). **CLI 신원 = `ENGRAM_TOKEN` 유일**(위장 플래그 없음 — 서버측 파생). `messages{id}` 응답은 수신자별 행 + `may_be_truncated`(발송 시점 기대 행수 대비 — 이력 링 유실 정직 공개. **실패 수신자도 장부 행을 남기므로 기대 행수 = 발신 응답 행수**로 맞는다, §5), 시각은 상대 초.

**allowedMcpServers 대책 (실측 2026-07-24 — 유저 전역 `[]`=전면 차단이 에이전트에도 적용됨):**
데몬이 스폰 시 `--settings`로 `{ "allowedMcpServers": [{"serverName":"engram"}] }` 조각을 **세션 한정 주입**(backend/claude.rs — 백엔드 지식 격리 ADR-0004 자리). **구현 확정(D, ADR-0109): 인라인 JSON이 아니라 파일 경로 주입**(Windows `cmd /c` 인용 붕괴 = 조용한 실패 모드 회피) — 조각 파일은 mcp-config 디렉토리·스윕·revoke 수명주기 동승(ADR-0099), 단일 키 유지(회귀 테스트 고정), 쓰기 실패는 warn+계속. 전역 파일 무변경·허용 범위 = 엔그램 스폰 에이전트뿐. merge 동작 라이브 실증 = 인수 런 항목(미검증).

## 7. 수용 기준

- busy 파킹→idle 진입/재등장(epoch 교체)→자동배달 시나리오 하네스(roundtrip-smoke 확장) green
- **idle 게이트·배치(중점 검증 — 2026-07-24 사용자 지시로 강화):** busy 중 도착 → 미주입·턴 종료 시 flush 관측 / 다건 누적 순서 보존(오래된 순)·일괄 주입 / 배치 내 request 포함 케이스 — 단위 + 실 claude 하네스 양쪽. (잠든 수신자 처리는 아래 전용 항목으로 이관 — 4차)
- 턴 진행 중 stdin 주입 시 CLI 큐잉 동작 실측 — **4차에서 다시 살아난 항목**(즉시 주입 폴백이 정식 경로가 됐으므로 그 근거 데이터가 필요하다). 측정할 것: ① 턴 중 주입분이 큐에 물렸다가 턴 후 소비되나 ② 모달 상태(권한 승인·메뉴·플랜 확인)에서 어디로 먹히나 ③ 여러 줄 봉투 제출이 온전한가 ④ 사람 타이핑 중 충돌 양상. **지금은 "그냥 보내고 뒤돌아보지 않는다"가 채택 방침이므로 이 실측은 사후 개선용**(문제가 관측되면 좁힌다).
- request→회신→`replied` 전이 + `reply_by` 초과→notice 주입 관측
- XML 봉투로 실 claude 왕복(포맷 전환 재검증) green
- **없는 이름 입구 반려(4차 개정):** **로스터·프로필 둘 다에** 없는 이름 → 응답 행 `failed`+`RECIPIENT_NOT_FOUND` · **파킹 큐에 안 실림**(장부에 `pending` 상태 레코드 없음 — 종점 `failed` 행은 남는다, §5) 단위테스트
- **로스터 술어 봉인(4차 신규 — 뮤테이션 실측으로 무방비 확인):** 종료된 세션(`Killed`/`Exited`/`Failed`)은 로스터에 **없어야** 하고(수거 전이라 목록엔 남아 있어도), 살아 있는 세션은 **구조화 출력 여부와 무관하게 있어야** 한다 — **실물 어댑터 레벨** 테스트(가짜 포트로 주입하면 이 술어를 타지 않아 원리적으로 초록)
- **잠든 수신자 파킹(4차 신규, ADR-0116 결정 1):** 로스터엔 없지만 프로필 존재 → 응답 행 `pending`·파킹 레코드 생성 · **wake 미발동** · 세션 복원(재등장) 시 flush로 `delivered` 전이 · **`@here` 펼침에는 불포함 / `@all` 펼침에는 포함**(ADR-0121 결정 1 — `@all`의 잠든 몫은 파킹되고 복원 시 배달) · request면 계약이 열리고 기한 스윕이 정상 발화 — 단위 + 실 claude 하네스(복원 경로)
- **잠듦 층 동명 차단(4차 신규 — ADR-0116 결정 5 정합):** 같은 이름의 잠든 프로필 2개 → 파킹 **안 됨**·`RECIPIENT_AMBIGUOUS` 실패 행(먼저 복원된 쪽이 조용히 받는 경로 부재 확인) · 산 1 + 잠든 1 동명 → **산 쪽으로 배달**(로스터 우선) 단위테스트
- **턴 신호 없는 백엔드 = idle 게이트 없음, 순서는 보장(4차 신규 → 5차 개정 ADR-0121 결정 2 → 6차 라벨 개정 ADR-0124):** 살아 있고 구조화 출력이 없는 에이전트 지목 → **busy 판정 없이 적재되고 응답 행은 `pending`**, 도어벨을 받은 flush 레인이 곧바로 빼 **장부가 `delivered`로 전이**(6차 — 5차의 "바로 주입되고 행은 `delivered`"는 응답 축 문구라 뒤집혔다. **뒤집힌 것은 응답 라벨뿐, "게이트 없이 즉시 나간다"는 성질은 그대로다**) · **busy 파킹 사유가 붙지 않는다**(그 부류엔 busy 파킹이 없다) · request면 계약도 정상 오픈 · **선행분이 없으면** 연속 2건도 한 배치로 즉시 나간다 · ★**선행분이 있으면 새 발송은 앞지르지 않는다**★ — 배달은 **묵은 것부터 오래된 순 한 배치**로 나간다(4차의 "둘 다 주입된다(선행분 대기 없음)" 항목은 5차 결정으로 **뒤집혔다**) · **게이트 술어의 판정 지점은 flush 레인 하나다**(6차 — 입구는 부르지 않는다. 부류를 안 가르는 술어가 두 곳에 흩어지면 큐에 든 편지를 아무도 열지 않는다, §5) 단위테스트 + 실 세션 통합(shell 스폰)
- **전부-큐 · 직발송 폐지(6차 신규 — ADR-0124. 5차 "직발송 좌석" 항목을 대체한다: 좌석 단언은 삭제가 아니라 아래 단언으로 *이전*됐다):** ① **발송 판정 경로가 직접 주입하지 않는다** — 빈 큐 + idle 수신자에게 보내도 응답 행은 `pending`이고 주입은 flush 레인이 한다(옛 `empty_queue_idle_send_still_injects_directly`·`idle_recipient_injects_immediately` 계열은 이 단언으로 교체 — **약화 금지**) ② **순서 = 적재 순서** — 동시 버스트가 같은 수신자를 지목해도 배달 순서가 적재 순서와 일치한다. **입구를 직접 겨눠 단언한다:** 발송 입구는 busy도 선행분도 보지 않고 **무조건 적재**한다(= 좌석 예약·직발송 합류 판정 코드가 **없다**). ★**flush 중복 진입 가드는 이 "없다"의 대상이 아니라 이 결정의 전제다**★ — 같은 수신자에 두 배치가 겹쳐 돌지 못하게 막는 in-flight 가드(§5 "영수증을 쥔 쪽이 유예 깨우기를 갚는다" 불변식이 그것이다)를 빼면 **진행 중 배치의 잔여분을 새 배치가 앞질러 순서가 역전**된다: 전부-큐가 된 뒤로 그것이 "배달 순서 = 적재 순서"를 성립시키는 장치이므로 **존치를 단언**한다(ADR-0124 §영향 순서 bullet의 하위 불변식 = 전제). 보관함 cap의 "보관+주입중 합산"도 다른 축이라 존치(§5) ③ ★**적재 직후 도어벨이 항상 울린다**★ — 울리지 않는 갈래가 없음을 단언(남으면 그 편지가 다음 계기까지 갇힌다) ④ **고립 없음 — 인과까지 단언할 것**(기계 없이 "안 갇힌다"만 적으면 테스트 작성자가 무엇을 볼지 모른다): flush 레인 *내부* 주입 실패분이 재파킹된 뒤 그 편지를 여는 계기는 **㉠ 뒤이은 발송의 적재 도어벨** · **㉡ 영수증 정산 때 되울리는 유예 표식**(그 사이 물러났던 flush 요청 — §5 "영수증을 쥔 쪽이 유예 깨우기를 갚는다") · **㉢ 기존 계기(idle 진입·재등장)** 셋뿐이고, 테스트는 **어느 것이 배치를 냈는지까지** 단언한다. ★**이 항목은 자기 도어벨을 허용한다는 뜻이 아니다**★ — 자기 주입 실패를 이유로 자기 도어벨을 누르는 것은 §5가 금지한다(도달 불가해진 수신자에 재주입 반복). 5차 좌석이 봉인하던 성질을 새 구조가 재제공하는지 = ADR-0124 §미검증 ①② ⑤ **버스트 응답 지연 없음** — 발송 호출은 적재까지만 하므로 flush 배치 크기가 응답 시간에 반영되지 않음(§미검증 ③) ⑥ **배치 영수증 정산 누락 없음(5차 "좌석 반납 누락 없음(분모 복구)" 단언의 *이전분* — 삭제 아님):** 좌석은 없어졌지만 배치 영수증 정산은 남았고, **6차부터는 모든 메시지가 그 경로를 지나므로 누락 위험은 사라진 게 아니라 커졌다.** 배달·실패·재파킹 **어느 결말에서도** 영수증이 정산되고 in-flight 분모가 복구됨을 단언한다(누락 = 분모가 영구히 부풀어 그 수신자 레인의 유입이 봉쇄된다) — 커널 단위(주입 hook 재진입으로 결정적 인터리빙) + 데몬 동시 버스트 통합
- **배치 부분 실패(5차 신규 — ADR-0121 결정 2):** 파킹 3건 배치 중 2번째 주입이 실패 → 1번째는 `delivered` 유지 · 2·3번째는 **나이 순서를 지킨 채** 큐로 복원되고 `pending` 유지 · **어느 행도 `failed`가 되지 않는다**(전량 실패 롤백 금지 — `delivered → failed` 불법, §6 전이 그래프) 단위테스트
- **두 방송 어휘(5차 신규 — ADR-0121 결정 1):** `@here` → 산 전원 − 발신자(잠든 이름 불포함) · `@all` → 로스터 + 잠든 이름 − 발신자(잠든 몫 `pending` → 복원 시 `delivered`) · **둘 다 발신자 행이 없다**(정본 = §4. 발신자와 동명인 잠든 프로필이 있어도 발신자에게 배달되지 않는다) · 해석 seam 계약 스위트가 "두 어휘가 다른 명단을 낸다"를 축으로 단언 단위테스트
- **회신 계약 규칙(4차 신규, ADR-0116 결정 2 + 사용자 결정 2026-07-30):** ① **수용 = 완료** — 잠든 요청자에게 회신 → `pending` 수용 + 계약 `replied` 정상 닫힘 ② 그 뒤 **요청자가 삭제돼 파킹된 회신이 `RECIPIENT_DELETED`로 치워져도 계약은 `replied` 유지**(되돌림 없음 — 알고 수용) ③ **`RECIPIENT_NOT_FOUND`만 실패 종결** — 요청자 프로필까지 없는 뒤 회신 → 행 `failed` + 계약 `reply_failed`(미결 조회에서 사라짐·기한 스윕 미발화·**512 계수 감소**·이력 잔존) ④ **그 밖의 실패는 무동작** — 보관함 가득/동명으로 회신 실패 → **계약 오픈 유지**, 그 뒤 재시도가 성공하면 정상 `replied` 닫힘(회귀 핵심) ⑤ 잠정·은퇴 표시 계약엔 실패 종결이 **적용되지 않음**(가드 정산 후에만) 단위테스트
- **프로필 삭제 일괄 정리(4차 신규, ADR-0116 결정 3 + 사용자 결정 2026-07-30):** ① 삭제 ∧ 로스터 부재 → 그 이름 앞 파킹분 `failed`+**`RECIPIENT_DELETED`**(장부 종점 + 힌트) · 그 이름이 요청자인 오픈 계약 `reply_failed` ② **삭제됐지만 세션이 살아 있으면 정리 안 됨**(파킹분 보존 → idle 전이 시 정상 배달 · 계약 오픈 유지) — 오동작 방지 회귀 ③ 회신자 쪽 삭제 계약은 유지 ④ **이미 `replied`인 계약은 정리가 건드리지 않음** 단위테스트
  - *(수용 명시분 — 테스트로 고정하지 않는다: 판정 후 삽입된 파킹분·삭제 후 뒤늦게 죽은 세션의 잔여분은 TTL `expired` 소관이다. "정리에 잡힌다"는 단언을 수용 기준으로 박으면 삽입-먼저 순서로만 통과하는 거짓 안심 테스트가 된다 — 리뷰 지적 반영.)*
- **`pending → failed` 간선(4차 신규):** 이 전이가 삭제 정리 경로에서 **합법**이고 그 외(예: `delivered → failed`, 임의 `pending → failed` 호출)에서는 **거부**됨을 단언 — 상태 전이 그래프 회귀
- **동명 힌트 문구(4차 개정, ADR-0116 결정 5):** `RECIPIENT_AMBIGUOUS` 힌트가 "재발송 말고 사용자에게 알려라" 안내(exact-id 재발송 안내 아님) 단위테스트
- **실패 행 장부 기록(신규):** `failed` 수신자도 장부 종점 행으로 남음 → `messages{id}` 행수 = 발신 응답 행수(`may_be_truncated` 오탐 없음) 단위테스트
- **다중 수신자 fan-out(신규):** 로스터 스냅샷 **1장**으로 전원 판정(해석 도중 명단이 바뀌어도 반쪽 판정 없음) · `@all` 펼침 경로가 직접 지목 발송과 **동일 코드 경로**임을 단언(그룹 전용 분기 부활 방지 회귀)
- **펼침 발신자 제외(신규 · 5차 보정):** `@all`·`@here` 발송 결과에 발신자 행이 없음 · 자기 이름 **직접 지목**은 여전히 배달됨 · **명부에 발신자뿐일 때**(잠든 이름도 없을 때) `to:["@all"]` → `GROUP_EMPTY` 전체 반려 **vs** `to:["@all","<자기이름>"]` → 반려 아님·자기에게 1행 배달(최종 집합 기준 규칙 회귀)
- **펼침 동명 예외(신규 · 5차 보정):** 펼침 결과에 동명이 둘 이상이면 그 이름은 `RECIPIENT_AMBIGUOUS` 실패 행(임의 선택·양쪽 배달 둘 다 아님) — 산 층 동명뿐 아니라 **`@all`이 함께 읽는 잠듦 층 동명**도 같다(잠든 이름 목록은 중복을 접지 않는다, §4)
- **혼용 `to` 중복 제거·행 순서(신규):** `["@all", "<이미 @all에 든 이름>"]` → 그 수신자 **배달 1회·결과 1행** · 행 순서 = 명시 토큰 입력 순 → 펼침 결과 사전순, 중복은 먼저 나온 자리 유지(결정성 고정)
- **층위 분리(신규):** 혼용 `to`에 **`@`오타**(`["@typo","산 이름"]`) → **전체 반려 `GROUP_NOT_FOUND`**(산 수신자에게도 안 감) **vs** **이름 오타**(`["없는이름","산 이름"]`) → 그 행만 `failed`·나머지는 정상 배달 · **잠든 이름 혼용**(`["잠든이름","산 이름"]`) → **응답은 두 행 다 `pending`**(6차 — 4차의 "잠든 행 `pending`·산 행 배달"은 응답 축 문구라 개정됐다), 차이는 장부에서만 드러난다: 산 쪽은 flush 레인이 곧바로 빼 `delivered`, 잠든 쪽은 복원 때까지 `pending`
- **부분 진행(신규 · 4차 보정 · 6차 라벨 개정):** 산 수신자 `pending`과 **없는 이름** 수신자 `failed` 행 공존(6차 — 산 수신자 행도 `pending`이다: 4차의 `delivered`/`pending` 병기는 직발송 시절 문구. 프로필이 남은 "죽은" 수신자도 `pending`) · 전원 실패도 `{id, results}` shape 유지(전체 반려 승격 없음) · 다중 수신자 `MAILBOX_FULL`이 **행 실패로만** 나타남(압력 회수 시도 없이 즉시 실패)
- **`reply_to` 규칙(신규):** 다중 수신자 + `reply_to` → `INVALID_SEND_ARGS` 전체 반려(`@`토큰 동반이면 펼침 결과가 1명이어도 반려 — 표기 단계 차단) · 모르는 id/이미 닫힌 계약으로 회신 → **배달은 성공·계약 무동작** · 같은 계약 2차 회신 → 배달 성공·계약 무동작
- **다중 request(신규):** N수신자 = 독립 계약 N개(계약 키 `(메시지 id, 수신자)`) — 한 명 회신 시 그 계약만 `replied`·나머지 오픈 유지 / 계약별 기한 notice N건 / `@all` request 허용
- **결박 폐지 회귀(신규):** busy로 파킹된 발송분이 같은 이름의 **새 epoch에 배달**됨(구 방송 소급 금지 분기가 남아 있으면 실패)
- cap/TTL/`MAILBOX_FULL` 단위테스트(압력 회수 코드가 남아 있지 않음 포함) · 기존 전 테스트 무회귀(`cargo test` 워크스페이스)
- `--settings` 주입 후 스폰 에이전트에서 send_message 툴 가시 + 호출이 데몬 도달(실측)
- **프라이밍 문서 개정(구현 슬라이스 필수 산출물):** `prompts/agent-priming.md`·`prompts/agent-priming-cli.md`에서 **group 툴 절 삭제** + **다중 수신자·다중 request 사용법**, **두 방송 어휘(`@here` = 나 빼고 지금 산 전원 / `@all` = 나 빼고 명부 전원 — 잠든 것 포함, 그 몫은 복원 시 배달, ADR-0121)**, **새 실패 행 어휘(`failed`+`code`)** 를 가르치도록 갱신 — 툴 표면이 바뀌었는데 프라이밍이 옛 사용법을 가르치면 에이전트가 없는 툴을 부른다. **4차 추가분:** 잠든 상대에게 보내면 `pending`으로 쌓였다가 복원 시 배달됨 · `RECIPIENT_DELETED`(기다리다 수신자 삭제 — 재발송 무의미) · `RECIPIENT_AMBIGUOUS`는 **동명 미지원이므로 재발송 말고 사용자에게 보고**. **6차 추가분(ADR-0124 — 5차의 "`pending` 사유가 셋이다(턴 중/잠듦/선행분 뒤 합류)" 문구는 이 결정으로 삭제됐다 — 응답이 `delivered`/`pending` 둘이던 시절의 안내라 지금은 정반대를 가르친다):** **정상 발송의 답은 `pending` 하나이고 `delivered` 응답은 없다.** `pending` = "접수됐고 간다"이지 **지연·이상 신호가 아니며**, 사유를 나타내지도 않는다 — **`pending`에서 상대 상태를 추론하는 것 자체가 오답**이다(상대가 살아 있고 유휴여도 `pending`이다. 옛 문구를 남겨 두면 에이전트가 `pending`을 보고 "상대가 턴 중이거나 꺼져 있다"고 **틀린 보고**를 한다). 실제 배달 여부가 필요하면 `messages{id}` 조회로 본다. **오타·없는 상대는 여전히 `failed`로 즉시 온다**는 점을 함께 가르친다 — 안 가르치면 에이전트가 "이제 아무 응답도 못 믿는다"로 과잉 일반화한다.

## 8. v2+ 확장 경로 (봉투 = XML 속성이라 전부 무파괴)

cc(수신자 역할 — 역할 명시 주입 필수, 리뷰 지적) · 다중 request **집계**(any/all — v1은 독립 계약 N개까지만) · 장부 사유 칸(refused/failed 구분) · thread_id(대화 묶음 — v1은 in_reply_to로 충분, 장부 TTL 확장 시 재검토) · ACL/수신거부 · 영속화(SQLite 예상) · 시스템 조작 버스 `engram_control`(S17) · **폴더 그룹 소스**(트리/폴더 데몬 소유화 시 `@폴더명` — 해석 seam에 소스 추가, ADR-0112 결정 1에서 방향 존치).

**ADR-0111/0112 개편으로 v2로 밀린 것(신규 — v1에 슬쩍 되살리기 금지):**
- **스폰 전 선지시(예약 발송) — 범위 = 프로필도 없는 이름 한정**(4차 보정): 트리에 항목이 있는 잠든 이름에게 미리 보내 두는 것은 이제 **정식 지원**(파킹 — ADR-0116 결정 1)이다. 미지원으로 남은 것은 **아직 만들지도 않은 이름**(프로필 부재)에게 보내 두기뿐이고, 부활시킬 땐 **명시 opt-in 인자**로만 노출한다(암묵 혼입 = ADR-0111 결정 1 위반).
- **메시지별 epoch 결박 옵션** — "발송 순간 화신에게만 배달"이 필요해지면 **개인 메일 옵션**(봉투/인자 확장)으로 무파괴 추가. 그룹 전용 규칙으로 되살리는 것은 금지(폐지 근거 = §4).
- **wake-on-request(재재정의)** — 잠든 수신자를 request 한정 깨워 배달. 잠듦 파킹 부활(ADR-0116)로 다시 **"파킹 대신 깨워서 즉시 배달"**이다 — 지금은 복원될 때까지 파킹 대기가 기본. 도입하려면 정식 재론.
- **저장형·이름붙인 그룹 재설계** — 이름 붙인 부분집합의 실수요가 서는 시점에(폴더 그룹이 1순위 후보) 해석 소스로 재도입한다. 그 전까지 저장소·관리 툴 표면을 미리 두지 않는다(ADR-0111 결정 4 · ADR-0112 결정 1).

## 9. 리서치 근거 요약 (2026-07-24, medium tier + cross-family 적대 리뷰)

- **수렴 코어(확실 — 3계보 교차확증):** 메시지 id·발신자·회신 상관(이메일 In-Reply-To ≡ FIPA reply-with/in-reply-to ≡ AMQP correlation-id). 회신 기한 = FIPA `reply-by` + 액터 call/ask 타임아웃의 선례.
- **타입 어휘:** FIPA 22 performative(산업 채택 실패) ↔ MCP 4종·A2A 무타입(본문이 의도 전달)의 스펙트럼에서 "데몬 행동 기준 최소형" 채택.
- **전원 생략 확인(LLM 프로토콜 2024-26):** priority·cc·TTL 봉투 필드 — 우리도 skip(priority는 AMQP 실무 경고도 근거).
- **선례:** Claude Code 팀 = 파일 수신함+idle 주입(우리 파킹·주입과 동형) · AMQP DLX = 만료를 사유 딱지로 장부화 · validated user-id = 발신자 데몬 각인(기구현).
- **적대 리뷰 교정 반영:** 그룹×회신계약 충돌(→v1 그룹 request 금지 — **2026-07-29 ADR-0111로 해제**: 회신이 어차피 1:1이라 다중 수신자 request는 독립 계약 N개로 성립, 전체회신 문제가 없어 옛 금지 근거가 소멸) · cc는 서술적 관례일 뿐(→v2로, 역할 명시 주입 전제) · in_reply_to 체인은 스레드 대체 불가(→thread_id v2 항목) · "MDN 사실상 사망"은 과장(교정됨).
- 상세 출처·확신도는 세션 리서치 산출(ADR-0103 참조 절)에 요약.
