## 0. Scope in one line

**While the daemon is alive**, make messages between agents get there reliably — envelope formalization (XML) + reply contract (request) + multi-recipient send (including `@all`) + an in-memory mailbox (parking · ledger · query). **No persistence (disk)** — to be done at the time of the agent-system memory design (user decision).

## 1. Envelope — what the receiving LLM sees (4 kinds, unified in XML)

```xml
<message from="qa-alpha">빌드 끝났음</message>
<message from="qa-alpha" id="m-7f3k" type="request" reply-by="10m">코드 짜고 회신해</message>
<message from="qa-bravo" in-reply-to="m-7f3k">다 짰음, 테스트 통과</message>
<message from="qa-alpha" to="@all">전원 리베이스 대기</message>
<notice>[engram] 요청 m-7f3k 기한(10m) 초과 — qa-bravo 회신 없음</notice>
```

- **Notation mapping (fixed):** tool/CLI arguments = snake_case (`reply_to` · `reply_by`) → XML attributes = kebab-case (`in-reply-to` · `reply-by`). The send argument `reply_to` appears as the received-envelope attribute `in-reply-to` (exposed so the requester can correlate which request this answers).

- **Exposure principle: show only fields that change the LLM's behavior.** `id` only on a request (needed for the reply), `to` **only when there are two or more recipients** (to signal that it was not a letter received alone), timestamps and ledger state are internal data.
- **The criterion for exposing `to` = the number of recipients (not whether it is a group, ADR-0111 overhaul):** the group-specific semantics were abolished, so an `@all` send and naming several people directly take the same path → the exposure condition is also unified, not "if it is a group" but **"if there are 2 or more recipients with an accepted decision (= not a failure row)"**. What is counted is the **acceptance decision**, not the result state — `delivered` is only fixed at the actual injection time (§5), so basing it on that would be a cycle referring, at the time of building the envelope, to a value not yet known. Failure rows are not counted (so that someone who could not receive does not shake the envelope notation of those who remain).
- **The `to` value = fixed and frozen in the send-time resolution** (no recomputation at flush — even if a parked item is injected much later, it keeps the notation of the moment of the send): **fixed once after the acceptance decisions of all recipients are finished** and carried identically in every envelope of that send (no wrapping in the middle of the per-recipient loop — blocks the accident where the first recipient receives an incomplete `to`). An accepted **explicit name is the canonical name**, an **`@` address is not expanded and stays as the token** (`@all`), and **failed tokens are excluded**. The values are listed in **input notation order** (`@all,x` — separate from the `results[]` row-order axis: rows follow the §5 rule, the envelope value follows the order the sender wrote). The expanded list is not carried in its place — disclosing the recipient list and roles (cc) is v2 (§8).
- `<message>` = a peer sender (can be replied to via from) / `<notice>` = a daemon notice (no from = not a reply target). Separating the tags structurally removes the "system" fake sender and the name-reservation problem. **notice self-identification (user decision 2026-07-26):** the body prefix `[engram]` + one clause in the priming: "`<notice>` = a notice from the engram daemon (the system); the absence of `from` is the marker; not a reply target".
- The format **switches the Xml variant of the existing wrap seam (ADR-0096) to the default + extends the attributes**. The colon variant remains behind a switch (not deleted). Escaping reuses the existing XML escaping.
- Switch verification: rerun `roundtrip-smoke` (whether the LLM reads the XML envelope and replies — only the format-coupled part is re-verified; the plumbing is format-independent). **Unverified — an implementation QA item in the §7 acceptance criteria.**

## 2. Type system — "a type only when the daemon behaves differently"

| Notation | Daemon behavior |
|---|---|
| (default, no type) | Notification — deliver and done |
| `type=request` | Opens an "unreplied" entry in the ledger (+ a timer if `reply_by` is present). **An independent contract per recipient** — with multiple recipients or `@all`, N contracts (ADR-0111 decision 5. The old "single recipient only · reject groups" is discarded) |
| `in_reply_to=<id>` (a field, not a type) | Reply decision → **only an accepted reply** closes the unreplied entry (`replied`). If delivery is a confirmed failure as unreachable, it is a `reply_failed` failure termination — conditions and exceptions in §3 item 7-④ |
| `<notice>` (daemon only) | Infrastructure notices such as timeouts. An agent cannot write it |

- **refuse/failure are not types** — they belong to the reply body ("declined / failed"). **If the reply arrived**, whether its content is a refusal or a failure, the ledger closes it as `replied` (the contract = "did you answer", not "what is the answer"). Only when *delivery of the reply itself* failed is it a different axis — §3 item 7-④. If needed, add a reason field in v2 (non-breaking).
- **Reply matching = strict**: only a message with `in_reply_to` counts. Reinforce the priming with the rule "attach the original id when replying to a request" (lenient matching = rejected because of accidental-close misfires).
- Of the response-contract spectrum, adopted = the 2 kinds, notification and request. Excluded: subscription (→ it duplicates the observation infrastructure, so the direction is permanent non-adoption) · negotiation · progress-report type (supported for free as ordinary messages in a thread) · opt-out ACL (at the time of the agent-system permission design) — rationale ADR-0103.

## 3. Reply contract (request)

1. Send: `request` + optional `reply_by` (duration notation "10m"/"1h" — the daemon converts it to an absolute time. **Lower bound 1 minute** = consistent with the timeout detection resolution (60s sweep) · **upper bound 30 days** = safety of internal time arithmetic — implementation decision 2026-07-26). The contract fields (request/reply_to) are **XML-envelope only** — rejected when the colon/template format is active (the attributes would drop, making reply impossible and producing false-positive notices).
2. Ledger: opens an unreplied (`awaiting_reply`) entry — **1 per recipient**. A multi-recipient request opens **N independent contracts** (ADR-0111 decision 5): the message id is common to the N contracts (the ledger principle of 1 message : N delivery records is kept) and the **contract key = `(메시지 id, 수신자 id)`** — contracts split by who the replier is (the key is the agent id, not the name. A contract addressed to a sleeping recipient also holds that id from the time it is opened, so even if the recipient is renamed, that contract's obligation remains — ADR-0309 decision 1). **Contract-open criterion = was that recipient accepted** (★**the definition of "accepted" used in this section = that recipient's result is not a failure row = `status ∈ {delivered, pending}`.** The items below use this definition as is★) — no contract is opened for a failure row (entrance bounce · `MAILBOX_FULL` · `REQUEST_CAPACITY`). **Parking (`pending`) is acceptance, so it opens a contract** — the same for busy or sleeping (ADR-0116 decision 1): it is a message that will be injected someday, so a reply obligation holds, and therefore the `reply_by` deadline sweep also fires normally (the clock is based on the send — see injection timing below).
3. When a reply (`in_reply_to`) is **accepted** → only that **replier's contract** closes as `replied` (the replier is matched to the contract by the sender id — there is no fallback of matching by name, ADR-0309 decision 7 · other recipients' contracts stay open — there is no reply-all). Handling of a reply that was not accepted is item 7-④.
4. `reply_by` exceeded → inject a `<notice>` **to the sender** (not nudging the recipient — whether to nudge is the sending LLM's judgment). **The timeout notice for a multi-request is 1 per contract — the same rule as N single requests** (the name of the non-responding recipient is stated in the body. No notice-merging system is built — a single rule without exceptions takes priority). The notice goes on a **dedicated bounded lane** (no bounce — §5 policy constant, ADR-0107. Replaces the old "full-case exception channel" wording).
5. **Deadline exceeded ≠ termination (ADR-0108):** even after the notice the contract stays open until a reply — it keeps appearing as `timed_out` in the recipient's pending query (`eg_messages`). When the **concurrent open cap of 512 (global)** is reached, the oldest of the **retirable contracts** (those already notified, or those with no deadline — never one whose notice obligation has not fired) is retired and the new one is accepted (**the history row is kept · only the contract tracking is removed** + the daemon log remains, no notice to the sender). A multi-recipient request **counts N contracts**, and if the cap is filled by non-retirable contracts alone, that recipient gets a **per-recipient failure row `REQUEST_CAPACITY`** (not a whole bounce — §5 partial progress. A message is also not delivered to a recipient for whom a contract could not be opened: the essence of a request is reply tracking, so delivery without tracking violates the contract). **This decision finishes *before* the queue enqueue (new in the 6th — the 7th inherits it as is, ADR-0125 §Impact):** if deferred until after enqueue, it could not answer immediately and would be absorbed into `pending`, and at that moment **a request without tracking is delivered** (the rule above — do not deliver to a recipient for whom a contract could not be opened — collapses). Even with the 7th's synchronous drain attached this order does not change — it is **decide → enqueue → drain**, and the drain can only promote an answer to `delivered`; it does not push the `failed` decision later.
6. Enforcement on the LLM side is soft (priming) — the guarantee is carried by the daemon's ledger tracking (a distillation of actor call/ask + FIPA reply-by).
7. **3-line rules for `reply_to` (sending a reply):**
   - **① Exactly 1 recipient** — a reply goes only to the original requester. `reply_to` + multiple recipients (including `@` addresses) is a whole bounce with `INVALID_SEND_ARGS` (even if the expansion result is 1 person — it is blocked at the notation stage).
   - **② A matching failure does not block delivery** — for an unknown id · an already closed contract · a case where the sender has no such contract, **the message is delivered normally and only the contract side does nothing** (no-op). A reply vanishing entirely is worse.
   - **③ A second reply to the same contract** — it is delivered and the contract does nothing (already `replied`. No re-close, no duplicate notice).
   - **④ One-line rule (ADR-0116 decision 2 · user decision 2026-07-30): if the reply is accepted the contract is complete; only when the requester's name does not exist at all is it a failure termination; any other failure is a no-op.**
     - **Accepted** (definition = item 2) → closes as `replied`. **Parking is also acceptance** — even if the requester is asleep and the reply is parked, the replier's obligation was fulfilled at that moment (plugging it in completes it). Even if the requester is later deleted and the parked reply is cleared, **the contract stays `replied`** (it is not reversed — the contract axis answers "did you answer", and "did it arrive" is recorded exactly by the delivery record as `RECIPIENT_DELETED`. Each of the two axes is its own fact, so the ledger is not lying, and reversing a terminal state is the class the transition graph forbids §6). This is a **property known and accepted**, and no additional handling is added.
     - **`failed` + `RECIPIENT_NOT_FOUND`** (the requester has no profile either = that name does not exist in the world) → the contract is a **`reply_failed` failure termination** (removed from the open list · the deadline sweep · the 512 count, history remains). There is nowhere to go however long one waits. *(The reply address is an edge, so it is a name — if the requester was renamed, a reply to the old name also ends this way, and if another agent took the old name, it is delivered to that agent. It is the same residual as before ADR-0309 — ADR-0309 decision 2 · TRD S29 §7.)*
     - **Any other failure** (`MAILBOX_FULL` · `RECIPIENT_AMBIGUOUS`) → **no-op = the contract stays open.** These failures are not a confirmed unreachable but the environment of that moment (the mailbox is full right now / same name) — if closed here, even when the replier retries a moment later and **actually succeeds in delivery**, the ledger would stay "reply failed" forever and the contract would also disappear from the requester's pending list (the opposite direction of a ledger lie). Staying open = not additional machinery but **doing nothing**, and a successful retry closes the contract through the normal path. **No zombie worry** — this contract too, once its deadline notice fires, joins the retirement targets of ADR-0108 (those already notified), so it does not occupy the cap permanently.
     - **Codes that do not occur** on the reply path: `REQUEST_CAPACITY` (a reply does not open a contract because `reply_to` ↔ `request` are mutually exclusive) · `RECIPIENT_DELETED` (a query-time code §6, not a send response). Do not put them in the classification.
     - **Junction with retirement marks and provisional contracts (respecting the ADR-0108 decision 4 invariant):** `reply_failed` **does not strike an unsettled contract** — the lifetime of a contract carrying a provisional (`provisional`) or scheduled-for-retirement (`pending_retirement`) mark is owned by that guard, so the failure termination applies only after the guard settles (a failure reply arriving in between is a no-op).

## 4. Group (= demoted to an address-resolution macro — ADR-0111 decision 4 · ADR-0112 decision 1 · two vocabularies separated ADR-0121 decision 1)

- **A group is a macro at the address-resolution stage, not a send path.** `@주소` → list expansion → **joins the multi-recipient send of §5 as is** (1 path). Expanded members are handled **exactly the same** as directly named recipients.
- **Sender exclusion in the expansion (user decision 2026-07-29 · ★the source of truth for this clause is this document — ADR-0111 decision 4 does not have this wording, so do not look for it there★):** when expanding an `@주소`, **the sender itself is removed from the list** (both vocabularies — ADR-0121 · **the sender is told apart by id** — another agent that merely shares the sender's name is not removed, ADR-0309 · TRD S29 X3) — a group send = "everyone but me". **Directly naming yourself is still allowed** (if you state your own name in `to`, it is delivered as usual — the exclusion is a rule applied *only to expansion*, not a ban on self-send. The outcome when the two overlap is in the item below).
- **An expansion result of 0 people is not itself an error** — `GROUP_EMPTY` occurs **only when the final recipient set (the union of expansion + explicit names) is empty**. When the expansion leaves nothing once only the sender is removed (for `@here` only the sender is alive; for `@all` the registry is only the sender): `to: ["@all"]` → final 0 → `GROUP_EMPTY` whole bounce / `to: ["@all", "<자기이름>"]` → the expansion contributes 0 people and the explicit name remains, so **1 row is delivered to yourself** (not a bounce).
- **Same-name members = each a different recipient (ADR-0309 — reversed 2026-10-29):** the expansion is done by the registry entry's **id** (no name → id round trip — ADR-0309 decision 3), so different agents with the same name (a same name in the live tier, or a **same name in the sleeping tier** that `@all` reads together — ADR-0121) are **different recipients** — each gets a row, and each is delivered · parked (the source of truth for the outcome list = TRD S29 §4 X1 · ADR-0309 Impact 「동명 쌍둥이」). **`RECIPIENT_AMBIGUOUS` now occurs only when calling directly by name** (§5 branch 1). Same names themselves are still unsupported — under name uniqueness (ADR-0115 · 0120) they should not arise, and arise only through the deletion hole of ADR-0122 · old data. *(The old rule = the transitional failure row of ADR-0114 decision 4: 「펼침 결과에 같은 이름이 둘 이상이면 그 이름은 `RECIPIENT_AMBIGUOUS` 실패 행 — "전원에게"의 명시적 예외」 (if the same name appears two or more times in the expansion result, that name is a RECIPIENT_AMBIGUOUS failure row — an explicit exception to "to everyone"). It belonged to when the name was the internal key and two entities had to be treated as one key, and ADR-0309 reversed it — do not revive it.)*
- **Group-specific delivery rules abolished (source of truth for the fact of abolition = this section):** the dead-member `skipped` (no-bounce skip) branch is **deleted** — an `@here` expansion sees **only the live roster** (name list source below), so the state "an expanded member is dead" does not occur under the one-snapshot principle, and a sleeping name that `@all` reads together is **not a dead member in the first place but a parking target**, so §5 branch 3 gives it the normal outcome (ADR-0121 — a skip branch does not become necessary). The outcome when a name is named directly is handled uniformly by the §5 branch rules (no group-specific exceptions). · The `(id,epoch)` **binding (bound_incarnation) at the moment of send is abolished** (last item below) · there is no broadcast-specific fan-out branch. **Reviving these branches violates ADR-0111.**
- **List source = one built-in, two vocabularies (ADR-0121 decision 1)** — **computed on the fly with no storage**, and both are **− sender**:
  - **`@all`** = **the whole registry** (alive **+ sleeping**). The live share is delivered/parked per the §5 branches, and the **sleeping share is parked** and delivered when that agent appears. Source = the §5 roster snapshot + the profile's sleeping-agent list (the same single snapshot, ADR-0116/0119 — the sleeping side comes over as (id, name) pairs, ADR-0309 decision 3).
  - **`@here`** = **everyone alive right now** (the roster only). The `@all` behavior up to the 4th was renamed to this vocabulary.
  - **If the two vocabularies look at the same source, that violates ADR-0121** — if a name is "all" but sleeping parties are missing, the sending LLM believes "I told everyone" and misses them, and if `@here` also reads sleeping names, the meaning of "right now, here" disappears.
  - **An `@all` expansion may produce the same name twice (normal)** — because the resolution source returns the list it was handed **verbatim** (no processing — §4 resolution seam), and the sleeping-agent list itself does not fold duplicates (the transitional defense of ADR-0116/0120). Since the list entries are (id, name) pairs, **two entries with the same name are two recipients with different ids** and each becomes one row (ADR-0309 — the same-name members item above). Duplicate folding is done by **id** — even if the same agent appears twice through a name reference and the expansion, it is one row (§5 resolution order ⑤). The reason for not folding is the seam contract of not letting decision knowledge leak into the resolution layer. *(The old statement 「동명 판정은 잠든 이름 목록을 직접 세어 하고 그 이름 = `RECIPIENT_AMBIGUOUS` 한 행」 (the same-name decision is made by directly counting the sleeping-name list, and that name = one RECIPIENT_AMBIGUOUS row) belongs to the name-key era — that count now remains only in the sleeping-tier same-name decision **when calling by name** (§5).)*
- **User-defined groups (runtime-registered lists + the `group` management tool/CLI subcommand + all of ADR-0109's management semantics) are removed.** Stored, named groups are redesigned when real demand arises (§8) — structure for groups is not laid down in advance.
- **Resolution = the seam is kept** (the *direction* of ADR-0104 decision 1 survives, only the sources shrink): the "group name → member list" resolution point stays as a source-plugin slot, but the v1 source is **one built-in** (that source owns both vocabularies `@all` · `@here` — which vocabulary reads which list is **the source's knowledge**, and the pipeline passes both lists, ADR-0121). **When folders become daemon-owned, a folder = an additional source** (`@폴더명` — planned as the canonical unit of organization broadcast) as a non-breaking extension. A sub-agent hierarchy is **not adopted** as an address unit (the rejected alternative of ADR-0104 stays).
- **Membership = registry entry (id, name)** — expansion is by id (ADR-0309 decision 3) and the address notation is the name as is (WYSIWYA, ADR-0101). The same profile comes back with the same id, so it is the same member across a respawn. *(The old phrase 「멤버십 = 이름 기반(id 아님)」 (membership = name-based, not id) was fixed by ADR-0309.)*
- **The `@` namespace is reserved** — an `@이름` other than the built-in vocabulary (`@all` · `@here`) is a resolution failure `GROUP_NOT_FOUND`, and `GROUP_EMPTY` if the final recipient set is 0. **Both are a whole-send bounce** (even with a mixed `to` — it does not go to the other recipients either).
- **Tier distinction (the criterion separating a bounce from a failure row — ADR-0114 decision 3 · subdivided by ADR-0116):** **name tier = runtime state** (the notation is normal) → **handled per recipient** — the outcome is decided by the §5 branch rules (delivery / parking / failure row). **`@`-address error = an address-space error** (an address syntax that does not exist · a mistyped group name = something the sender must fix and send again) → **whole bounce**. This one line sets the boundary of §5 partial progress.
- **The group-request ban (`GROUP_REQUEST_UNSUPPORTED`) is discarded** — an `@all` send can also be a request (N independent contracts per recipient, §3). A reply always goes to the 1 sender (no reply-all).
- **Consequence of abolishing binding** (ADR-0111 decision 6) — a parked send is **also delivered to a new incarnation (epoch)** of the same agent (same id) (the same rule as a personal letter · ADR-0309 decision 1 — the old phrase 「같은 이름의 새 화신」 (a new incarnation of the same name) means the same thing while the name is unique and unchanging. A different agent that newly takes that name after a rename · deletion does not receive it). If "only to the incarnation at the moment of send" becomes necessary, a v2 personal-mail option (§8).

## 5. Mailbox (in-memory)

**Roster definition (one line — 4th amendment):** roster = **every agent with a process attached** (state `Running` · `Exiting` — including busy). **Having structured output is not a roster qualification** — it is only the axis that splits "when to inject" (capability sub-rule below). Sleeping (process closed · restorable) sessions and names not yet up are not included.

**★Without a turn signal the idle gate is not asked — but order is kept (user decision 2026-07-30 + **ADR-0121 decision 2** · load-bearing)★:** the idle gate applies **only to backends whose turn boundaries can be observed**. A backend with no means of observation (stream-json turn events) (terminal/console mode, etc.) **does not attempt a busy decision**. **★Subject made explicit (new in the 6th → corrected in the 7th · ADR-0125)★ — the subject of "does not ask" is the `드레인` (the injection routine).** The 6th wrote this subject as `flush 레인`, but from the 7th **that drain also runs inside the send call** (synchronous drain — the sender thread calls the same routine). What the 6th set up correctly stays as is: **the send entrance does not query busy to decide enqueue, regardless of class** (unconditional enqueue). What this clause divides is **only whether the drain that follows the enqueue applies the gate to that recipient**, and the decision is the same whether that drain runs on the sender thread or on the async flush lane (the same routine). Rationale: that CLI **has its own input queue**, so it holds input that arrives mid-turn and consumes it after the turn ends → there was no need for us to observe idle in the first place (the TUI itself is the gate). This clause puts back in place what the 3rd had wrongly narrowed to "unreachable" (unrelated to the §8 wake item — that is about *sleeping* sessions).

**But that rationale does not cover order (ADR-0121 decision 2 — the requirement is as is, only the realization was replaced in the 6th and corrected in the 7th · ADR-0125):** "is the other side ready to receive" and "in what order do the letters arrive" are different problems. **Requirement:** regardless of recipient class, if there are earlier items in front of that recipient (injection-failure parking · deadline notices · letters enqueued earlier), a new send may not overtake them, and **the oldest go out together, in order of age** (the actual delivery is done by the drain batch — **two paths are forbidden**. That batch may run inside this send call or at a later flush trigger, and **either way it is the same routine**).
**Realization (what changed in the 6th — the 7th inherits it too):** the 5th had **the send entrance look at "what is in front"** and decide whether to join (the join decision). **The 6th entrance looks at no condition and enqueues everything** — so **the device of a join decision itself disappears** and order holds automatically as enqueue order (ADR-0125 inherits this gain as is · user decision "그냥 큐에 쌓고 뺄 때 한꺼번에 빼면 된다" (just pile it in the queue and take it all out at once when draining) — "A send is entirely enqueued" below). The requirement above is satisfied in that structure **without a decision**. **7th correction:** after the enqueue, **the same call drains that queue from the front**, so the older ones go out first and this letter goes out after them — order is still enqueue order, and **the response row is `delivered` if the drain confirmed that it injected this letter, and `pending` if it could not confirm** (definition = §6). The 4th's "write once with no waiting · parking · retry and be done / do not look back" is valid **only on the idle-gate axis**.

**If injection fails in the middle of a batch, it stops at that point (ADR-0121 decision 2):** the already-sent front part stays `delivered`, and after the failure point it stays in parking as `pending` (retried at the next trigger). **7th: the synchronous drain follows the same rule** — if this letter is **before** the failure point the response is `delivered`, and if **after** the response is `pending` (reason = injection failure, ADR-0125 decision 2). **A partial success is not rolled back to a full failure** — `delivered → failed` is illegal in the transition graph (§6). The 4th's "no retry" assumed a single item, so in a batch this rule takes its place.

**A send is entirely enqueued, and the same call drains that queue (invariant — ADR-0125 · 7th amendment. Replaces together the 6th's "injection belongs solely to the flush lane" clause and the 5th's "a direct send also falls under in-flight accounting (seat reservation)" clause):** after finishing the per-recipient identity decision, the send entry point **puts it at the queue tail inside the lock**, and **after releasing the lock drains that recipient's queue from the front as far as it can be injected, then returns.** The **direct-send shortcut that writes to the other side's stdin right after the decision stays abolished as in the 6th** (meaning there is no path that skips enqueue).
- **★There is one set of injection code (invariant — ADR-0125 §Impact)★:** the synchronous drain and the async flush are just **two triggers that call the same drain routine**. **What is forbidden is building send-specific injection code separately** (= two paths recurring), and **a sender thread running the shared drain routine is not a violation but this design itself.** ★The 6th wrote in this place "if the send decision path calls injection directly it is a violation (injection is owned by the flush lane)" but it was **reversed in the 7th** — stripping out the synchronous drain on the basis of that sentence would implement this amendment backwards.★
- **Enqueue inside the lock, drain outside the lock (invariant).** Do not call the `DeliveryPort` (injection) while holding the lock — making an external call while holding a lock risks order inversion and deadlock with that side's lock (module header §single lock · the spirit of ADR-0006).
- **Order = enqueue order.** The decision and the injection cannot enter one critical section (the lock discipline above). The 5th blocked the race window that arises between them ("two see an empty queue at the same time and both direct-send") with seat reservation, but once everything is queued, the **window itself disappears**, so seats and join decisions **for order** are not needed — it takes from the front, so the older ones go out first and this letter goes out after them. **If these devices become necessary again, it is a signal that the send path has split in two** (ADR-0125 — a gain inherited from 0124). *(The mailbox cap's "keep + injecting combined" is a different axis — it is a **cap count**, not an order device, so this clause does not abolish it. Policy constants below.)*
- **The share the drain could not send is handled by the doorbell (7th — a role demoted from the 6th's "doorbell right after enqueue is the main trigger").** The main path is the synchronous drain above, and the doorbell and the async flush lane **stay** as the trigger that opens **the share that could not go out on the spot** (mid-turn · sleeping · injection failure · and the share that **may remain** after stepping back from an overlapping drain — if the winning side's batch already sent it, there is nothing left even when opened). **If in any outcome there is no trigger to open that letter, it is stuck until the next event** — assert at implementation time, down to the causality, in a test that there is no isolation (§7 acceptance criteria · ADR-0125 §Impact unverified ③). *(**Unspecified (7th — not decided here):** whether, even after the synchronous drain became the main path, **the enqueue-time doorbell is rung unconditionally**, or only for the share the drain left behind, was not decided by ADR-0125. What this document specifies is only up to "a trigger that opens the share that could not go out necessarily exists".)*
- **Consequence (known and accepted):** even if a simultaneous burst hits the same recipient, **everyone is enqueued within the mailbox cap (100 per recipient)** and the drain delivers in order of age (the share beyond the cap is a `MAILBOX_FULL` failure row for that recipient only — the mailbox item below). The response is a **mix of confirmed and unconfirmed**: a letter the drain of its own call sent is `delivered`, and a share caught by the gate or one that stepped back from an overlapping drain is `pending`. The cost the 5th paid with seats ("only the first is `delivered`, the other 99 are `pending`") **disappeared when seat reservation was abolished** (the 6th's writing this disappearance as "because `delivered` vanished from the response vocabulary" is a misattribution — the vocabulary was restored in the 7th, and the reason for the disappearance is the seat abolition). `pending` is not an anomaly signal and **does not mean "it did not go"** — the definition is §6.
- **The surface where the cap applies widens (6th consequence — the 7th keeps it too, known and accepted. The cap value is unchanged):** up to the 5th, the mailbox cap check ran **only on the parking branch** — a direct send did not pass the cap gate, and "with an empty queue + idle, even the 101st is injected immediately and that is not a cap violation" was an explicit contract. Once everything is queued, **every send passes the cap gate**, so a send that passed in the 5th can be bounced with `MAILBOX_FULL` (**a design consequence, not a regression** — ADR-0125 §Impact. The cap number and the abolition of reclaim are as they are; changing the value takes a separate decision).

  ★**But do not read it as "`MAILBOX_FULL` increases across the board" — the newly caught range is narrow**★ (corrected by the user's remark on 2026-08-01): **if the recipient is idle, the drain empties the queue, so nothing accumulates in the mailbox and the cap never bites in the first place** — however much is sent, it is not caught, the same as the 5th. If the recipient is **mid-turn · sleeping**, in the 5th too it was parked and accumulated, so that too is **no different**. Only one case actually differs: **when several senders hit at once and the queue exceeds the cap before the drain catches up** — in the 5th a direct send bypassed the cap and went out, and in the 7th it is bounced. It is a range hard to reach at a human-conversation message rate, and if it actually becomes a problem, re-deciding the cap value is a separate decision then.
- **Exception (do not remove — in the 7th it is not an exception but part of the mainstream):** in an assembly where the doorbell trigger is unwired (experiment bin · kernel unit tests), **every branch in which the sender thread runs the drain synchronously on the spot** (the trigger-absent fallback · including a drain in which the sender thread itself empties a doorbell set after the response is fixed) is not a direct send — it is *running the shared drain routine on the spot*, and in the 7th it is **the same thing the normal send path does** and is also the means by which unit tests gain determinism. Misreading it as "sender-thread injection" and stripping it out makes the kernel test harness nondeterministic and **cuts off the normal path along with it** (do not narrow the exception by writing it as one specific function).

**The side holding the receipt pays back the deferred wake-up (invariant):** while in-flight (the batch receipt — direct-send seats abolished by the 6th, item above) is held, the side that attempts a drain for that recipient id steps back and leaves only a mark. If that mark is not echoed back at settlement, the wake-up evaporates (lost wakeup) and letters piled up behind are tied up until the next event or the TTL. ★**This "stepping back" is itself the guard against re-entering a drain for the same recipient, and in the 6th and 7th it is an order device**★ — without it, a new batch overtakes the remainder of a batch in progress and the order inverts. The ban ADR-0125 inherited ("re-introduction of `직발송 좌석 예약` and `직발송 합류 판정` is forbidden") **does not point at this** — the **sub-invariant (= the premise of this decision)** in the same ADR's order item commands the continued existence of this guard.
- **★In the 7th this guard becomes more important (ADR-0125 §Impact)★:** since the drain runs inside the send call, **two sender threads draining the same recipient at the same time became the everyday case**. If they overlap, the batches tangle and the order inverts, so **the losing side steps back.** The letter of the side that stepped back **is carried out in the winning side's batch, so nothing is lost**, and since the side that stepped back cannot know whether its letter was injected, it **answers the response as `pending`** — **a conservative answer that may actually have been delivered** (the adopted trade is that a false `pending` is safer than a false `delivered`).
- **Pressing one's own doorbell because of one's own injection failure is still forbidden** (repeated re-injection into a recipient that has become unreachable) — what is paid back is only a wake-up *someone else requested*.

**The gate predicate is defined in only one place (invariant — ADR-0121 §Impact):** if there are several points that decide "this class does not ask the idle gate", only one side gets fixed and **two points see different worlds** — then nobody opens the letters piled in the queue. Pull the predicate out into one and have the decision points call it. **6th cleanup → 7th correction (ADR-0125 — replaces the 5th's enumeration "send entrance · re-check right before injection · flush batch gate"):** the remaining decision point is **the single drain batch gate** — **the send entrance does not call this predicate to decide enqueue** (unconditional enqueue), and the "re-check right before injection" disappeared along with the direct-send path. ★The 6th wrote that one as the "flush batch gate", but in the 7th **the same drain also runs inside the send call** — even with two triggers (synchronous · asynchronous), **the routine is one set, so the decision point is still one**★. Even with one point, the discipline of keeping the predicate in one place is kept (if the class decision and the batch gate split inside the drain, the same accident recurs).

- **The price accepted, stated honestly:** without a turn signal ① if a **modal state** (a permission approval · menu · plan-confirmation dialog) is up at injection time, our text may be swallowed by that widget ② if a person is typing on the same screen, the input mixes ③ the submission handling of a multi-line envelope depends on the paste method. **"Send it without deferring to a gate" is the adopted policy** (user decision — the 4th's "do not look back" is valid **only on the idle-gate axis**: order was reversed by ADR-0121), and if a problem is actually observed, measure it then with a spike and narrow it (backlog). `delivered` is stamped **at the actual injection time** here too — whether it was read is a value no backend guarantees. **7th note (ADR-0125 rationale — blocks reopening):** the synchronous drain does **not increase** this exposure. ①~③ above are properties ADR-0116 decision 7 already recorded as "known and accepted" (§7 measured item), and a batch goes out all at once whichever trigger it runs on, so changing where the drain is does not change the amount of exposure. **The party that handles this problem is not mail but the agent-management layer** (the wait decision before injection — a follow-up slice to the promotion of turn state to shared, which **ADR-0113** confirmed), and when that promotion arrives, **only the place where the gate is asked needs to change** (mail only subscribes).

**Entrance-decision source = roster + profile list, 2 physical queries (ADR-0116 — 4th amendment):** a name not in the roster (= all sessions in state `Running` · `Exiting`. **It is not "in the session list"** — an ended session also stays in the list until the reaper collects it) is told apart once more with the **profile list** (the agent items saved in the tree) — if present, **sleeping = parking**, if absent, **nonexistent = failure row `RECIPIENT_NOT_FOUND`**. **Calling by an exact agent id is the same 3 branches** — if it is in id form, look first for a live id and then a sleeping id (if not found, resolve it as a name), and if it is a sleeping profile, it is parking. The id spelling is accepted the same as at the control entrance: uppercase · braces · no hyphens · `urn:uuid:` as well (ADR-0309 decision 3 · TRD S29 B6 · B7 — before the sleeping side came over as (id, name) pairs, calling a sleeping agent by id was `RECIPIENT_NOT_FOUND`). One line of principle: **"If it is alive, send; if it can come alive later, wait; if it does not exist, fail loudly."**

**The queries are 2 (invariant):** 1 session snapshot + 1 profile list. If the session snapshot is taken twice, the half-decision where two recipients of the same send see different worlds recurs (violation of ADR-0111 decision 2). The structured capability is an **attribute that comes attached to each entry of this snapshot**, so it is not a separate query — it does not split the decision and only separates "when to inject" — **from the 6th, the party that decides that "when" is the drain** (the entrance does not query to decide enqueue. 7th correction: that drain runs once right away inside this send call, and the share it could not send is continued by the flush of the next trigger). ★The one-line principle that was here up to the 5th ("send if it can receive … fail loudly if it cannot receive or does not exist") is **deleted**★ — it describes the entrance on the acceptance-time axis, which flatly contradicts the 6th and 7th (the entrance always enqueues), and "fail if it cannot receive" was false in every amendment (busy · sleeping is not `failed` but `pending`). The entrance's principle has as its sole source of truth the one line on the identity axis at the end of the item **"entrance-decision source = roster + profile list"** above ("if it is alive, send; if it can come alive later, wait; if it does not exist, fail loudly") (do not use line-number references, since they drift at amendment). The expansion source is split by vocabulary — **`@here` is the roster only, `@all` is the roster + sleeping agents** (ADR-0121, §4 — the sleeping side as (id, name) pairs, ADR-0309).

- **The name on the profile side = the same derivation rule as a live session** (load-bearing): the name used for the sleeping decision is derived with **the same helper and the same input** as a live agent's canonical name — the helper is `canonical_name_or_id_fallback` (including ignoring an empty override + the placeholder degrade guard), and the input cwd is the **canonicalized one** (the live name comes from the session cwd normalized at spawn, while the profile may receive a raw path). If either one differs, **a sleeping agent cannot be called by the name it had when alive** (the entrance cannot find that name in the sleeping tier → `RECIPIENT_NOT_FOUND`). *(A mismatch after parking no longer loses letters — the parking key is the id, not the name, so a restored agent opens its own queue even if its name differs, ADR-0309. The old phrase 「파킹 키(잠듦 시점 이름)와 복원 후 산 이름이 어긋나 24h 만료로 조용히 사라진다」 (the parking key (name at sleep time) and the live name after restore diverge and it silently vanishes through the 24h expiry) is a consequence of the name-key era.)*
- **Same names at the profile tier are also an ambiguity failure (consistent with ADR-0116 decision 5 — transitional)**: the profile list does not guarantee name uniqueness (until ADR-0115 comes in), so **when calling by name, if two or more sleeping profiles share that name, it does not park but produces a `RECIPIENT_AMBIGUOUS` failure row** — one name alone cannot pick which agent. Calling by the exact id parks to that one, and an `@all` expansion parks to each (ADR-0309 · TRD S29 X1 · X2). *(The old rationale 「이름 키로 파킹해 두면 먼저 복원된 쪽이 조용히 받는다」 (if parked by name key, whichever is restored first silently receives it) no longer holds once the parking key became the id — this rule remains as a name-resolution rule, ADR-0309 Impact · ADR-0120 dead-letter list 1.)* A same name spanning the live and sleeping tiers (1 live + 1 sleeping) is **won by the live one** (the roster decision comes first — if there is an entity that can receive now, that one is the recipient).
- **A race between snapshots = bounded, so accepted (stated honestly — 4th):** the two queries (the session snapshot · the profile list) are at different moments, so if a spawn or deletion slips in between, the decision may be slightly stale. The queries are taken **outside the lock** (an absolute module discipline — if the entrance holds an external lock and takes the messaging lock, the ADR-0006 lock order breaks. The cleanup call also runs after releasing the profile registry lock). So **if a deletion slips in between the decision and the parking insert, that item misses the deletion cleanup's scan and remains** — the critical section only blocks interleaving during the scan and cannot block an insert after the scan. The outcome of this residue is **TTL 24h `expired`** (no leak or contamination, the ledger terminal remains), not `RECIPIENT_DELETED`. An atomic view at the entrance and re-confirming a tombstone at insert time are **not adopted** (ADR-0116 rejected alternative) — add them if they become necessary. The opposite direction (spawn after the decision) costs nothing — the parked share is delivered by the appearance flush.

**Recipient resolution = one roster snapshot (invariant, ADR-0111 decision 2):** take **only one** roster snapshot per send, and handle multi-recipient · `@`-address expansion · existence/same-name decisions for everyone in one batch (if re-taken per recipient, the half-decision from a list change during resolution recurs — a surviving piece of the old group snapshot principle). **The profile-list query follows the same principle** — once per send, no per-recipient re-query (ADR-0116).

**A `to` element = a name or an `@` address (mixing allowed):** each element of the list is an agent name or an `@` address, and an `@` element is expanded on the spot (**the sender is excluded from the expansion** — §4) and combined as a **union** with the name elements. Resolution order = ① comma split (**CLI entrance only** — §6, no split for MCP array elements) · trim → ② expand `@` elements (sender excluded) → ③ join with the name elements → ④ resolve each element against the registry (existence · same name — an expanded element is already an id) → ⑤ **duplicate removal (1 recipient = 1 delivery · 1 result row)**. ★In S29 the order of ④ and ⑤ changed★ — the old order (duplicate removal → matching) folded by notation, but now the folding needs the resolved id. **1 recipient = the same id** (ADR-0309) — the folding key is the id if resolved, the notation if not (TRD S29 §2). So even if you write the same agent by name and by id together it is one row, and if you write one same-named name together with the id of one of them it is two rows, a name row (`RECIPIENT_AMBIGUOUS`) and an id row (delivery) (TRD S29 X2). This normalization is a **daemon single point** (the same result from both entrances). Even if `@all` and a direct name overlap it is 1 row, and a direct naming of your own name survives regardless of the expansion exclusion (§4).

**Row order = deterministic (fixed by tests):** `results[]` joins ① **the explicit tokens written in the input, in the order written**, then ② **the `@`-address expansion results in name lexicographic order**. Duplicate removal **keeps the one that appeared first** (explicit names always precede expansion results, so an overlapped recipient's row position follows the explicit position).

**3 branches per recipient (a multi-recipient send runs this decision once per recipient = fan-out, 1 path — 4th amendment by ADR-0116 · 6th tidied the decision axis · 7th corrected the home of the axis):**

★**Axis separation (new in the 6th · kept in the 7th — load-bearing. ADR-0116 was not reversed)**★: these 3 branches decide **only "who is this recipient" (the identity axis)** — nonexistent / sleeping / alive, and same-name ambiguity. **The decision tree of ADR-0116 decision 1 is still alive as is.** What disappeared from this branch is **only "can it receive now" (the acceptance-time axis)**: the send entrance looks at neither busy nor earlier items and **enqueues unconditionally**.
★**7th correction (ADR-0125)★ — where the acceptance-time axis lives:** the 6th wrote that axis went to **another lane (flush)**, but in the 7th **the drain that follows in the same call** looks at that axis (the sender thread runs the shared drain routine). So **the responses of 2 and 3 can split again** — for 2 (a live recipient), `delivered` if that drain **confirmed the injection**, `pending` if it **could not confirm** because of the gate · injection failure · an overlapping drain, and 3 (a sleeping recipient) is always `pending` (vocabulary definitions = §6). **What did not change:** in no branch does the gate split whether to enqueue — **returning "can it receive?" to the entrance to make it skip the enqueue (= reviving direct send) violates ADR-0125.**
1. **Entrance (ControlIngress) bounce → per-recipient failure row** — the decision basis is only the two sources above, and whether injection succeeded is not looked at in this branch (6th · 7th — that is the **drain axis**: the explanation of the axis move in item 3. In the 7th the drain runs in the same call, but its result only raises the response label to `delivered` and does not reopen this identity decision).
   - **Nonexistent** — **in neither** the roster nor the profile (typo · unspawned · deleted) → `failed` + `RECIPIENT_NOT_FOUND` (ADR-0116 decision 1).
   - **Multiple same names** → `RECIPIENT_AMBIGUOUS` (a per-recipient row at any tier — **only when calling by name**. An exact id reference · an `@` expansion decides the recipient by id, so it does not pass this decision, ADR-0309). **When the tiers overlap, the roster tier wins** — if there are two or more live same names, that fact is what the sender has to fix. **The hint's count is the roster count**, so the wording labels it that way.
   - **Pre-spawn advance instruction (reserved send) is unsupported only for names without a profile** (§8). **No wake** — a sleeping recipient is only parked, not woken (§8 v2 candidate).
2. **Live recipient (in the roster) — enqueue, then drain in the same call → `delivered` if the injection was confirmed, `pending` if not**(7th · ADR-0125 — ★the 6th's "enqueue and the response row is `pending`" was reversed★. Up to the 5th this branch was "if it can be inserted now, **direct send**, inject immediately `delivered`", and the 7th revives the label but **the path is enqueue-then-drain**). The entrance here too **looks at neither busy nor earlier items to decide enqueue** (the 6th gain kept). **When it is taken out is decided by that drain's gate** — the gate has two branches and **the enqueue is unconditional in either**:
   - **A backend with a turn signal** — the drain looks at the idle gate (if mid-turn, that batch is deferred → response `pending`, reason = mid-turn — injection timing below).
   - **A backend without a turn signal** — the drain **does not ask the idle gate** (user decision 2026-07-30 · ADR-0116 decision 7 = kept in the 6th and 7th too). Since it makes no busy decision, this class **is never deferred for busy** → it goes out on the spot together with earlier items and the response is usually `delivered`. **But order is class-independent** — if there are older items in front of that recipient, they go out together in one batch in order of age (ADR-0121 decision 2: the rationale for skipping the gate covers only "readiness to receive" and not "arrival order". That CLI's input queue handles only *mid-turn timing* on our behalf and does not handle the order of our queue for us).
   - The ledger's `delivered` is stamped, in either branch, **only at the actual injection time** (= the moment the drain wrote) (injection timing below). **The response's `delivered` points at the same event as "it was injected in this call's drain"**, but **the two axes are still different** (§6) — the response is a snapshot at the moment that call ended, and if it is injected at a later trigger the ledger becomes `delivered` even though the response was `pending`. ★The 6th's "this vocabulary is not in the send response" was reversed★ — do not mix up the two axes **being different** with **one of them lacking it**.
3. **Sleeping recipient (not in the roster but the profile exists and is restorable — ADR-0116 decision 1, sleeping parking) — enqueue and the response row is `pending`**, and it stays in the queue until restored (queue key = that agent's id — even if the name changes while asleep, the agent that wakes receives it, ADR-0309). Different from the old "absence parking" — only a name (or id) that actually exists in a profile is accepted, so there is no path for typos to silently pile up.
   - **What the entrance decides by *whether to enqueue* ends here (6th gain — kept in the 7th).** The remaining reasons that were written together in this branch up to the 5th — **busy** (a backend with a turn signal is mid-turn) · **FIFO behind earlier items** (what piled in front of that recipient + **what is already out** = a batch in progress. The other branch of `pending` (㉯ stepped back from an overlapping drain, unconfirmable) is not put among these three reasons here — the definition is §6. The 6th wrote "the entrance does not inject so it cannot see failure", but that part was reversed★. The re-parking rule = "If injection fails in the middle of a batch, it stops at that point" above.
   - **Drain triggers (common to all classes)** = **① the synchronous drain of the send call (the 7th main path — ADR-0125 decision 1: the drain of a following send also empties this queue from the front together)** · ② doorbell (new in the 6th — kept for the share that could not go out) · ③ idle entry (turn end) · ④ reappearance (spawn/restore/epoch — the existing roster diff machinery). **There is no separate retry trigger for an injection-failed share — it waits until the next trigger** (inherits the v1 existing behavior, improvement in the backlog).

**Exceeding the mailbox (100 per recipient)** → **only that recipient gets an immediate failure row `MAILBOX_FULL`** (in a multi-recipient send it is **not promoted to a whole bounce**). **Pressure reclaim (retire the debris, then accept) is abolished** (ADR-0114 decision 1 — amends ADR-0107 decision 2). The **logical claim** that was the basis for the abolition, "confirmed-undeliverable debris = the empty set", **was weakened by the 4th amendment**: a name with no profile is still filtered at the entrance, but the parked share of a sleeping name that is not restored is *restorable*, not *restored* (deletion cleanup is also a single shot at deletion time so some remain until the TTL — the item above), and if that mailbox fills to 100, later senders get `MAILBOX_FULL` (a state that was impossible in the 3rd). **The bounded-ness rationale is now not the logical empty set but the TTL 24h + the mailbox cap**, and within that the abolition of reclaim is kept (to reopen the reintroduction of reclaim, record a new decision on the basis of this sentence). Cleanup is **one 60-second periodic TTL sweep** only (24h-elapsed items `expired`). **The ban on silently discarding live mail is unchanged** — every removal leaves a ledger terminal (only when the record has already been pushed out of the history ring is it demoted to a debug log — best-effort, the fact of removal remains in the log).

**Partial progress (ADR-0111 decision 3):** per-recipient decisions are independent of each other — even if some fail, **the other recipients are delivered as is**. A whole bounce is only for **a problem with the send itself**: argument errors · mutual-exclusion violation (`INVALID_SEND_ARGS`) · `BODY_TOO_LARGE` · contract fields in a non-XML format · address-space errors (`GROUP_NOT_FOUND`/`GROUP_EMPTY` — tier rationale in §4) · `INTERNAL_ID_COLLISION`. **Even if everyone fails the response shape is the same** (all `results[]` rows `failed`) — it is not promoted to a whole bounce (a single-recipient send is no exception: the answer to a send to 1 person with a **nonexistent name** is not `error` but 1 `failed` row = 1 path. A send to 1 sleeping person gives 1 `pending` row — 4th. **`pending` is not a sleeping-only vocabulary** (6th correction — kept in the 7th): even a live recipient is `pending` if **mid-turn · injection failure** (㉮) or **stepped back from an overlapping drain** (㉯). **★Do not read these three as a flat list★ — ㉮ and ㉯ are mixed and the definition is §6** (counting the overlapping drain as a fourth in ㉮'s "three reasons" violates the §6 definition). ★But the 6th's addition here, "the answer to a send to 1 live recipient is also `pending`", was **reversed** — in the 7th it is `delivered` if the drain injected it (§6).★).

**The fate of parking:** on **the synchronous drain of a following send (the 7th main trigger — ADR-0125)** · doorbell (6th — for the share that could not go out) · recipient idle entry · reappearance (epoch replacement), auto-injection `delivered` (**batch · oldest first** — the same as the drain rule in injection timing below: two paths forbidden, ADR-0104) / over the TTL `expired` (the ledger remains). **No binding** — the new incarnation of the same agent (same id) receives it (ADR-0111 decision 6 · ADR-0309 decision 1 — it receives even if renamed while asleep, and a different agent that newly takes the old name does not). **The TTL applies equally regardless of parking reason — no liveness-based exemption** (a single clock-based rule, ADR-0105). **Even if a parked request goes `expired` by TTL, its contract stays open** — no automatic close (the sender notice belongs to the `reply_by` path, §3 item 5).

**Expiry is quiet — a property known and accepted (user decision 2026-07-30):** when a parked item goes `expired` by the 24h TTL, **there is no active notice to the sender** (the send response's `pending` + the later `eg_messages` query is all). The **same rule** applies to busy parking and sleeping parking — we recognize that for sleeping the default outcome is "quietly expires if nobody restores it" and leave it as is (keeping one rule > exceptions per parking reason). Improvement candidates (a sender notice on expiry · an "undelivered" distinguishing phrase in the request deadline notice) are in the **backlog** — add them if they become necessary. Without this item the next session would misread it as an "omission".

**Profile deletion = batch cleanup (ADR-0116 decision 3 — 4th amendment · decision · cleanup key = id, ADR-0309 decision 6):** trigger condition = **deleted ∧ that profile's session (same id) is not in the roster** — decided by one id and **swept by id**. *(The 4th was a three-term conjunction that added here 「② 그 이름을 가진 산 세션이 없음(이름 축)」 (② no live session has that name (name axis)) — extracted in review R2. Because cleanup **swept the parking queue · contracts by name key**, it was a guard blocking the path where a live session sharing the name had its letters killed under the false reason `RECIPIENT_DELETED` and contracts in which it was the requester were failure-terminated. Once cleanup sweeps by id, the live same-name's share is not a target in the first place, so ADR-0309 lifted that guard (ADR-0120 dead-letter list 5). So now even if a live same name exists, the deleted profile's share is cleaned up (in the 4th the whole cleanup was skipped) while the live same-name's parking · contracts stay, and even if deleted after a rename, that agent's parked share accumulated under the old name is cleaned up — TRD S29 B4.)* The profile-delete command does not kill a running session (kill is a separate command), so a state exists of "only the tree item was deleted and the process is alive" — that party is **a live recipient that can receive as soon as it becomes idle**, so it is not a cleanup target (cleaning up would kill mail that would be delivered and record a contract that would hold as failed = the exact opposite of the intent of this amendment). At the point when that session actually disappears the profile is also gone, so it naturally converges to the "nonexistent" class.

When the condition holds: ① **failure-terminate the parked share addressed to that id** — status `failed` + code **`RECIPIENT_DELETED`** (ledger terminal recorded + hint attached, vocabulary item below). The invariant "no silently discarding live mail" is kept — it vanishes only from the queue and the history remains so the sender sees the reason with `messages{id}`. ② **failure-terminate with `reply_failed` the open contracts in which that id is the reply target (requester)** (confirmed unreachable for the reply — removed from the open list · the deadline sweep · the 512 count). A contract already closed as `replied` is **not reversed** (§3 item 7-④ — accepted = complete). But per the guard rule of §3 item 7-④, **provisional · retirement-marked contracts are applied after settlement**. A contract whose replier was deleted is **kept** — the existing path where the sender learns of no response through the deadline notice (§3 items 4~5) is alive.

**Cleanup is a single shot at deletion time — no re-evaluation trigger is placed (stated honestly · 4th):** the trigger condition is evaluated only at that moment of deletion. So **when a live session whose profile alone was deleted dies later**, there is no event to sweep up the parked share already piled up · the open contracts in which it is the requester — the outcome of that residue is **TTL 24h `expired`** (the contract joins the ADR-0108 retirement targets after the deadline notice) and not `RECIPIENT_DELETED`. A symmetric trigger (re-firing on roster departure ∧ profile absence) is **not adopted** — build only the minimum needed now (user policy 2026-07-30) and add it if it becomes necessary (backlog). **Without this item the next session would read it as an "unhandled bug".**

**The deletion UX (whether deleting a tree item accompanies a kill · force/quiet delete options) is outside the scope of this spec** (belongs to the agent lifetime model — backlog). The condition above is safe whichever UX it becomes: if deletion accompanies a kill, both are gone at that moment and cleaned up immediately, and there is no malfunction on the path where a live session remains.

**Injection timing = idle gate + batch flush (ADR-0104):**
- If the recipient is mid-turn (busy), do not inject and wait in the mailbox — `delivered` is stamped only at the actual injection time (not pushed into the CLI's internal stdin queue: to keep ledger accuracy + batch control).
- On **the synchronous drain of the send call (the 7th main path — ADR-0125 decision 1)** · doorbell (new in the 6th — for the share that could not go out) · idle entry (turn end) · appearance (spawn/epoch), **inject everything piled up in one batch** (oldest first, each message with its own envelope — being XML, the boundaries inside a batch are clear). No dribbling one at a time.
- Busy/idle observation = a backend capability (based on stream-json turn events). **For a backend that cannot be observed, a gate-less injection fallback — this clause was formally rehabilitated in the 4th** (user decision 2026-07-30 · the item above "without a turn signal the idle gate is not asked" is the source of truth). It reverses the 3rd, which excluded this class from the roster and made the fallback point unreachable. **The fallback skips only the gate — joining earlier parked items (oldest-first batch) applies to this class as is** (ADR-0121 decision 2). Source of truth for the capability matrix = ADR-0002 · 0030 (the difference is not structure but the presence or absence of a capability).
- The `reply_by` clock stays based on the send (independent of receive delay — a contract from the sender's viewpoint).

**Policy constants (ADR-0107):** TTL **24h** (raised from 1h, ADR-0105 — limited to the in-memory stage, redesigned at persistence) · message lane **100 per recipient** (keep + injecting combined — in-flight accounting) · **notice dedicated lane 64** (raised from 20, ADR-0114 decision 2 — a multi-request's per-contract notices pile up as many as the contract count, so 20 is narrow. No bounce — when exceeded, retire the oldest notice and record the ledger `skipped`. **+1 temporary overshoot allowed** in the batch window in the middle of injection (explicit contract · self-correcting). Replaces the old "cap exception" — removes the unbounded channel).

**Ledger:** a history ring buffer of **4096** for all messages (raised from 1024, user decision 2026-07-26 — since the full body is kept, the worst case (64KiB×4096) ≈ 256MiB is accepted, exposing it as a runtime setting · storing truncated bodies are follow-up items) — sender · receiver (write the id and the **name at send time** together — matching is by id, the query display is the name at send time, ADR-0309 decision 4. Two exceptions: a failure row where the recipient could not be found has no recipient id, and a daemon notice has a nil sender id) · state transitions + time (`pending→delivered→replied` / `expired` / `skipped` / **`pending→failed` (limited to deletion cleanup — 4th, §6 transition graph)**. **7th: if the synchronous drain injects in the same call, a row can start as `delivered`** — the 6th's "initial state uniformly `pending`" was discarded, §6). The state transition times are themselves the reply-time and send-time data (not exposed in the envelope). A terminal transition of a record pushed out of the ring is demoted to a debug log (best-effort).

**Failed recipients also remain in the ledger:** **the recipient of every `failed` row** (entrance bounce · `MAILBOX_FULL` · `REQUEST_CAPACITY`) is **recorded as a delivery-record row in a terminal state** (there is no parking but there is a record — the sender must be able to see "who could not receive" again later with `messages{id}`). So the **ledger's expected row count = the send response's row count** matches, and the `may_be_truncated` false positive that arose from not keeping failed recipients disappears (§6).

**flush hook:** at the AgentManager's agent appearance/epoch transition, the pending injection for that **id** (reusing the existing `write_stdin_observed` path). Appearance decision = look at the roster diff as **id → incarnation marker** — an id that was absent just before, or a different incarnation of the same id, is an appearance, a rename (same id · same incarnation) is not an appearance, and even with several same names each flushes its own queue (ADR-0309 · TRD S29 X4 — the old 「이름이 유일할 때만 flush」 (flush only when the name is unique) skip was a device placed because a name-keyed queue could go to the wrong same-name agent, so it was lifted).

**Note (reversed by ADR-0111 → meaning narrowed by ADR-0116):** `RECIPIENT_NOT_FOUND` is **revived** (the old "disappears in a single send · replaced by parking" wording is discarded) but its meaning narrowed with the 4th amendment — it is **the per-recipient failure-row code for "a name with no profile either"** (a sleeping session is parked `pending` — this code is not emitted). `RECIPIENT_AMBIGUOUS` (same name) is on the same tier, and `BODY_TOO_LARGE` stays a send-unit bounce. The correspondence table of the response vocabulary and the ledger vocabulary is in §6.

**Send response (the same JSON from both entrances — byte-identical, fixed by a parity test):** `{ id, results: [{to, status, code?, hint?}] }` — shape unchanged, 1 row per recipient. Status vocabulary = **3 kinds `delivered|pending|failed`** (ADR-0125 decision 2). **The response axis and the ledger axis are different** — the response is a momentary snapshot of "how did that send call end", the ledger is "how far has that delivery record gone now" (= a record of the actual injection time, ADR-0104). The correspondence table below is the link between the two.

- `delivered` = **actually injected in this call's drain** (= written to stdin and fully accepted — ADR-0125 decision 2). **Only this is confirmed information.** In real use the recipient is usually idle, so most normal sends fall here.
- ★**`pending` = "this call could not confirm delivery" (single definition — load-bearing)**★. **`pending` does not mean "it did not go"** — it means *this response does not answer* whether it went or not, and a consumer reading it as "it definitely did not go" misreads it (the §7 priming explicitly blocks this misreading). It is also not a delay or anomaly signal — it is the normal answer that it was received without loss. Failing to confirm splits into two branches and **both are answered with the same single `pending`** (the wire value does not split):
  - **㉮ Stayed in the queue** — the case where it is certain it could not be inserted. **Three reasons (ADR-0125 decision 2):** ① **the recipient is mid-turn** (a backend with a turn signal) ② **the recipient is asleep** ③ **injection failure**. It goes out at the next trigger (**appearance · idle transition · the drain of a following send · doorbell**).
  - **㉯ Unconfirmable** — the case where it stepped back after **overlapping drains** of the same recipient. It cannot know whether its own letter went out in the winning side's batch, so it answers `pending` **conservatively** (**it may actually already have been delivered** — a false `pending` is safer than a false `delivered`: ADR-0125 §Impact · §5 "The side holding the receipt…"). **★Tracking memo (for a session that reads only the ADR)★:** ADR-0125 calls this answer a **"false `pending`"**, which is by the narrow vocabulary of decision 2 ("cannot be inserted now so **it stayed in the queue**"). **This spec widens the definition to "could not confirm delivery", which makes that answer true** — the behavior is the same and only the vocabulary is unified under the higher-level definition. If the ADR body's "false" and the "true" here seem to conflict, this memo is the source of truth.. **Do not insert this as a fourth into ㉮'s three reasons** — what decision 2 counts is the reasons for *staying in the queue*, and this is another branch split off from the higher-level definition "could not confirm".
  - **In either branch, actual injection is checked with an `eg_messages{id}` query.** A typo · a nonexistent party comes immediately as `failed`.
- `failed` = **new** (ADR-0111 decision 3) — only that recipient fails. A failure row has **`code` required + `hint`**. **The send response's failure codes are 4 kinds** (`RECIPIENT_NOT_FOUND` · `RECIPIENT_AMBIGUOUS` · `MAILBOX_FULL` · `REQUEST_CAPACITY`) and **all are decided *before* queue enqueue, so they are bounced immediately** (ADR-0125 §Impact — do not shorten it to "3 kinds". If absorbed into `pending`, the sender would never learn of a typo, and with `REQUEST_CAPACITY` a request without tracking is delivered §3 item 5). `RECIPIENT_DELETED` is not a send response but a query-time code (below). Row codes:
  - `RECIPIENT_NOT_FOUND` — **a name in none of the roster · the live list · the profiles** (typo · unspawned · already deleted). A sleeping session is not this code (`pending` parking — ADR-0116).
  - *(`RECIPIENT_UNREACHABLE` was briefly introduced in the 4th draft and then **discarded** — a party with no turn signal is also a normal delivery target through "immediate injection without a gate", so there is no state for that code to point to. That immediate injection is done by **the drain of the same call after enqueue** and does not hit the gate, so the discard conclusion stands. Do not revive it: ADR-0116 rejected alternative.)*
  - `RECIPIENT_AMBIGUOUS` — multiple same names (the live tier or the sleeping tier — §5 · **only when calling by name** — it does not occur on an `@` expansion · an exact id reference, ADR-0309). **Hint = "same-name people are not supported · do not resend, tell the user"** (ADR-0116 decision 5 — not an exact-id resend guide). A transitional code — to become dead letter via ADR-0115.
  - `MAILBOX_FULL` — mailbox over 100.
  - `REQUEST_CAPACITY` — that recipient's contract cannot be opened.
  - **`RECIPIENT_DELETED` = new (4th · ADR-0116 decision 4 · user decision 2026-07-30)** — terminated undelivered because **the recipient was deleted while waiting parked**. It differs in **timing** from `RECIPIENT_NOT_FOUND` (it did not exist from the time of sending = immediate entrance bounce, never parked) — the sender must distinguish "I wrote the name wrong" from "the party was deleted while I waited" for the resend judgment to split. **This code is first seen not in the send response but in an `eg_messages` query** (it was `pending` at send time) — so the query row also carries a **hint** along with the `code`: "terminated undelivered because the recipient was deleted while parked — that name no longer exists so resending is meaningless; tell the user if needed". The requirement is that it reads from the code name alone and that the next action comes out once the hint is seen (this vocabulary is also taught in the priming document — §7).
- `skipped` is **abolished from the response vocabulary** (disappeared along with the group-member skip rule — §4). The `skipped` in the ledger terminal vocabulary is on a different axis so it remains → the correspondence table below.
- **Send-unit bounce** = `{ status:"error", code, hint }` (no `results`) — only problems that cannot be divided per recipient: `INVALID_SEND_ARGS` (contract-field syntax · mutual exclusion · non-XML format violation · empty recipient list · `reply_to` + multiple recipients) · `BODY_TOO_LARGE` · `GROUP_NOT_FOUND`/`GROUP_EMPTY` (address-space errors — tier rationale §4) · `INTERNAL_ID_COLLISION` (a collision even after one id regeneration — a guard that practically never occurs).
- **Parser branching criterion (an accepted asymmetry — stated explicitly):** a success response has no top-level `status`, and a bounce response has no `results` — the receiving side branches on whether `status == "error"` exists (shape is not unified, the existing contract is kept).
- **Wire enumeration = the 3 kinds above as is** (the CLI entrance's allowed-value array · the parsing at the daemon control entrance hardcode it). There is no reason to touch it.

**Vocabulary correspondence table — send response (send vocabulary) vs `eg_messages` query (ledger vocabulary):**

| Send response status | Following ledger state (query status) | Transition |
|---|---|---|
| `delivered` | `delivered` → (if request) `replied` | This call's drain actually injected it → the ledger is also `delivered` at that moment. Since **`delivered → failed` is illegal**, this row does not move backward (transition graph below) |
| `pending` — this call could not confirm delivery (㉮ stayed in the queue / ㉯ unconfirmable) | `pending` → `delivered` → (if request) `replied` / `expired` / **`failed` (+`RECIPIENT_DELETED`)** — **for ㉯ it may already be `delivered` at query time** | ㉮ stayed in the queue → injected at the next trigger (appearance · idle transition · the drain of a following send · doorbell) (`delivered`) / `expired` on exceeding the TTL of 24h / **`failed` at deletion cleanup** (4th). ★**For ㉯ (stepped back from an overlapping drain), that letter is carried in the winning side's in-progress batch, so the ledger may already be `delivered`** — read it by adding **"the drain of the winning side running at the same time"** to the list of opening triggers★. **So writing "response `pending` ⇒ ledger `pending`" as an assertion makes a flaky test** |
| `failed` (+`code`) | Recorded at the terminal as is (does not move further) | Entrance bounce · `MAILBOX_FULL` · `REQUEST_CAPACITY` |
| (none — does not appear in the response) | `skipped` | Ledger-only terminal: retirement on exceeding the notice lane of 64 |

**The starting state of a ledger row (ADR-0125 decision 4):** with a synchronous drain, enqueue and injection are inside the same call, so **a row can start as `delivered`.** What could not be inserted stays `pending`. **Do not write "every delivery record necessarily passes through `pending`"** — that was a 6th clause and ADR-0125 discarded it (the two consequences that clause carried — the `delivered`-start row in the table above being unreachable · all sends being temporarily exposed in the no-argument `messages` — die with it).
**What did not change:** **the ledger's terminal vocabulary and meaning** — `delivered` is a record of the **actual injection time** meaning "written to stdin and fully accepted" (ADR-0104 · ADR-0121 decision 3). **The transition graph is also untouched** (ADR-0125 does not discuss legal edges — the 4th clause below as is). What changed is **only the row's starting point**.

**Amendment of the state transition graph (4th — implementation contract):** **`pending → failed` is added** to the legal edges — but **limited to deletion cleanup (§5)** and the reason code is `RECIPIENT_DELETED`. There is still no edge into `failed` by any other path (a failure row is recorded in that state from the start — since we must not make an impossible history of "delivered and then returned to failure" expressible, `delivered → failed` stays illegal). The reason for opening this one edge: deletion cleanup is the only path that terminates an *already parked* record after the fact so it cannot be expressed as a terminal at record time, and reusing `expired` (time expiry) would make the reason false (rejected alternative — ADR-0116).

- **Contract-side fields (an axis separate from the delivery state):** `awaiting_reply` = that recipient's request contract is waiting for a reply · `timed_out` = `reply_by` has passed and even the notice to the sender went out but **the contract is still open** (ADR-0108 — not a termination). When a reply comes both close as `replied`. · **`reply_failed` (new in the 4th, ADR-0116 decisions 2 · 3)** = the contract **failure-termination** terminal. There are **exactly two** firing paths: ① the reply send row is **`RECIPIENT_NOT_FOUND`** (§3 item 7-④) ② **requester profile deletion cleanup** (§5 — only open contracts are targets). It is removed from the open list · the deadline sweep · the 512 count and the history remains. Unlike `replied`, it does not claim "a reply was established". **Other reply failures do not go to this state** (no-op = the contract stays open — §3 item 7-④).

- **Axis distinction (to prevent confusion — load-bearing):** `reply_failed` is a terminal of the **contract axis** and **is not a delivery-state (`DeliveryStatus`) vocabulary.** The original request's delivery record stays at `delivered` (or `pending`) as is — that message was actually delivered, and what failed is *the reply side*. That is, a delivery-state transition like `delivered → reply_failed` does not exist (creating such an edge would make the history "delivered and then returned to failure" expressible — a violation of the graph rule above). It is exactly this section's principle that the contract axis and the delivery axis are separate axes.
- `eg_messages` with no argument = my pending (`pending` + `awaiting_reply`). **「내」 (My) is matched by id** — even if I rename, the pending items I sent and my contracts still show, and the row's `from` · `to` are the name at send time (ADR-0309 decisions 4 · 5). **The 6th's "since every send starts as `pending`, even what was just sent temporarily shows up" no longer holds** — a letter the synchronous drain inserted on the spot **does not stay** in `pending`, so what remains here is **only rows whose ledger is still `pending`**. ★Do not read this as "what really could not go out"★ — the no-argument query filters by the **ledger axis** (is the row `pending`), not the response axis (㉮/㉯). **For a sender who got `pending` as ㉯ (unconfirmable), if the winning side's batch already sent it, the ledger is `delivered` so it does not show here** — it is normal for the response and the query result to differ. That is, "pending" means not *undelivered* but *not yet a terminal in the ledger*. ★**But it is not "never shows up at all"**★: enqueue is inside the lock and drain outside the lock, so **a row may pass through `pending`** (the above "starting state of a ledger row" — it says a row "can" start as `delivered`, not that it always does), and if it passes through, **it may be visible to a third party's no-argument query running at the same time during the enqueue → drain window.** The exposure is only narrowed to that window and is not 0. *(**Unspecified** — whether a row actually passes through `pending`, i.e. whether the window exists, was not decided by ADR-0125. Confirm it in the implementation slice.)* `eg_messages{id}` = that message's per-recipient rows.
