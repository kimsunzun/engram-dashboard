CI 정규식 게이트가 tokio :: time 을 못 본다 — :: 양옆에 공백을 허용해 막는다

CI 의 소스 검사 몇 개는 rg 정규식으로 tokio:: 같은 경로를 찾는다. Rust 는 tokio :: time 처럼 :: 앞뒤에 공백을 넣어도 컴파일되는데, 지금 정규식은 붙은 형태만 찾는다. 이번 작업은 검사 여섯 개의 패턴에 \s* 를 넣어 공백형도 똑같이 잡게 한다.

대상검사 여섯. net gate 2a 는 이미 잡으므로 뺐다.§3 바꾸는 것
공백 허용 범위\s* = 같은 줄 안의 공백·탭. 줄 넘김은 뺐다.§3 바꾸는 것
미룬 것use tokio as rt; 같은 다른 이름 꼴은 이번에 안 고치고 새 할 일로 올린다.§4 안 하는 것
1 · 구멍

공백이 끼면 컴파일은 되고 정규식은 못 찾는다

C++ 에서 std :: vector<int> v; 가 컴파일되는 것과 같다. 경로 마디 사이 공백은 문법상 아무 의미가 없어서, 붙여 쓰든 띄어 쓰든 같은 코드다. 그런데 게이트는 텍스트를 본다. tokio:: 를 찾는 grep 은 tokio :: 를 지나친다.

이 게이트들은 「이 파일·crate 는 저 경로를 쓰지 않는다」 같은 구조 규칙을 지킨다. 예를 들어 replay_flight.rs 는 tokio·tauri·std::net 을 쓰면 안 된다. crate 의존성에는 tokio 가 들어 있으니 컴파일러는 막지 않는다. 일부 게이트는 이처럼 정규식이 유일한 벽이다(ci.yml 주석).

2 · 실제로 새는 자리

보통은 rustfmt 가 먼저 막는다. 새는 곳은 rustfmt 가 손대지 않는 구간뿐이다

CI gates 잡에는 cargo fmt --check 가 있다. rustfmt 는 Rust 판 clang-format 이다. 공백형을 보면 tokio::spawn 으로 고쳐 쓰려 하므로, 일반 코드의 공백형은 fmt 스텝에서 먼저 FAIL 한다.

rustfmt 가 손대지 않는 자리는 두 가지다. 중괄호 매크로 호출의 본문(m! { tokio :: spawn(f) } — 단순한 macro_rules! 본문은 rustfmt 가 고쳐 쓴다)과 #[rustfmt::skip] 구간이다. #[rustfmt::skip] 은 clang-format 의 // clang-format off 와 같은 역할이다. 이 두 자리의 공백형은 fmt 게이트와 정규식 게이트를 모두 통과한다.

3 · 바꾸는 것

검사 여섯 개의 패턴에서 :: 양옆에 \s* 를 넣는다

규칙은 하나다. 이름 뒤 :: 는 \s*::, 여러 마디 이름(std::net 등)은 마디 사이마다 \s*::\s*. 다른 부분(주석 가드, \b, 파일 존재 검사, 판정 case)은 그대로다. 예시 하나:

옛  ^(?:[^/]|/[^/])*?\b(tauri|tokio|engram_dashboard_[a-z_]+|std::net)::
새  ^(?:[^/]|/[^/])*?\b(tauri|tokio|engram_dashboard_[a-z_]+|std\s*::\s*net)\s*::
\s*
공백·탭 0개 이상. rg 는 한 줄씩 읽으므로 줄 넘김은 먹지 않는다.
\b
단어 경계. my_tokio::x 의 tokio 에는 걸리지 않는다. 그대로 둔다.
^(?:[^/]|/[^/])*?
줄 앞쪽에 // 가 없을 때만 매치 = 주석 밖만 본다. 그대로 둔다.

같은 패턴이 적힌 해설도 함께 고친다

옛 패턴 문자열은 ci.yml 밖에도 해설로 복사돼 있다. 이걸 그대로 두면 문서와 게이트가 어긋나므로 같이 고친다.

  • ci.yml 각 스텝의 해설 주석
  • 대상 헤더: engram-dashboard-base/src/lib.rs:55 · engram-dashboard-transport/src/lib.rs:48 · engram-dashboard-platform/src/lib.rs:169-171(+ :174 알려진 한계) · src-tauri/src/daemon_client/replay_flight.rs:51-54
  • docs/testing-strategy.md:50 · :179
  • docs/todo/doc-drift.md: 이 항목을 닫는다 · docs/todo/observed-only.md: §4 의 새 항목을 올린다

다른 S 의 process 문서, ADR, handoff, research 같은 역사 기록은 손대지 않는다. 코더는 이 목록을 출발점으로 옛 문자열을 다시 세고, 목록과 다르면 구현 전에 보고한다.

함정 하나. base 게이트에는 주석 가드가 없다. base lib.rs 헤더에 crate :: time 같은 예시 경로를 쓰면 게이트가 자기 헤더에 걸린다(헤더 :66 경고). 그래서 헤더에는 패턴을 괄호째 인용하는 지금 방식을 유지한다.

4 · 안 하는 것과 이유

이미 잡히는 곳과 구멍이 더 넓은 곳은 이번 범위에서 뺐다

use tokio as rt;
rt::spawn(f);                              // 정규식이 보는 이름은 rt — tokio 가 안 나온다
use std::{net::TcpStream, time::Instant};  // std 다음이 {  — std::net:: 꼴이 아니다(한 항목 묶음은 rustfmt 가 풀어 쓴다)
use std::net;                              // net 뒤가 ;  — 그 뒤 net::TcpStream 으로 쓴다
5 · 확인 방법

qa 가 새 ci.yml 을 실은 scratch worktree 에서 원문 스텝을 그대로 돌린다

표본 줄을 진짜 대상 파일에 넣지 않는다. 별도 worktree($QA_TMP/wt)의 실파일에 한 줄을 넣고, ci.yml 의 스텝 스크립트를 고치지 않고 그대로 돈다. 정규식만 따로 돌리는 것보다 CI 에서 실제로 도는 것과 같다.

검사가 여럿 든 스텝(shell gate 2 · platform gate 6 · net gate 2a)은 표본이 다른 검사를 건드리지 않는 자리에 넣고, FAIL 메시지가 대상 검사의 것인지 확인한다. 엉뚱한 검사가 FAIL 해도 FAIL 은 FAIL 이라, 메시지를 안 보면 틀린 증명이 된다.

6 · 위험과 진행

위험은 오탐과 CI 기준선 차이 둘이다

  • 오탐: 넓힌 정규식이 정당한 코드를 잡을 수 있다. AC2 · AC3 이 막는다. 리뷰어가 미리 넓힌 패턴을 지금 트리에 돌려 봤고, 옛 패턴과 결과가 같았다.
  • CI 기준선: jobs: 가 바뀌므로 이 커밋의 CI 결론이 master 기준선과 다르다. qa 바인딩 「전체 회귀 = CI」 규칙대로 판단한다.
  • 문자열 리터럴: "tokio :: x" 는 지금도 붙은 형태와 같은 취급을 받는다. 새 위험은 아니다.

브랜치 기준 = v0.5.0/chore/skill-apply. 통합은 skill-apply 다음이다. 구현은 코더 1명이 한 단위로 맡는다(파일이 겹친다). 단위가 끝나면 ci.yml YAML 파싱을 확인하고, 코더가 AC1 · AC3 표본 몇 개를 rg 로 한 번 돌려 본다. 최종 판정은 qa 가 한다. PRD+TRD 리뷰는 full(Claude + codex)로 2라운드 PASS 했고, 권고 3건(줄 번호 · worktree 에 변경 싣기 · FAIL 메시지 귀속)을 판 2 에 반영했다.
