## 2. Module boundaries

```
daemon A                                               daemon B
 control ingress (MCP eg_send · /control/send)          link/peer: accept gate → per-node receive queue
   └ messaging handle_send ─ Resolution::Remote          messaging: validate · backstop → handle_send(Remote, LocalOnly)
        └ RemoteDeliveryPort (non-blocking)                   ▲ verdict ◄─┐
 link/peer: Registry<PeerWire> ══ transport `iroh` (QUIC, node keys) ══ Registry<PeerWire>
   directory: publish own ─── DirSnapshot / DirDelta ──►  copy of A (read-only)
              copy of B (read-only) ◄───────────────────  publish own
 link (shell, WS loopback) — + same-account check      link (shell, WS loopback) — + same-account check
 ask_user: app (PC list slot visible) → OS approval dialog (platform) → wait
```

- **transport** — new `iroh` feature module beside `ws` (opt-in, off by default). Owns everything iroh: endpoint build from plain config values (secret key bytes · relay = default | none | URL · address lookup = default | none | URL · mDNS on/off · listen port · ALPN), `Dialer` / `Listener` / `LinkTx` / `LinkRx`, framing, close-code mapping, `LinkInfo::peer_key` (raw 32 key bytes), and a policy-free accept hook `accept_if(peer_key)` the consumer fills (§4-2). ★iroh types do not leave this module★ — the daemon's manifest gets no iroh dependency, so the adapter stays replaceable (PRD §6 vendor risk). Transport takes and returns raw key bytes; the ID text format is the daemon's (T34). Generic change: the supervisor's own ping / idle become optional in `Policy` (crate default unchanged — on; `Policy::check`'s `write_deadline < ping_interval < idle_timeout` applies only while they are on), so a consumer can rely on the link's own liveness (T44). No relationship policy here: no trust list, no tie-break, no PeerWire (ADR-0177 decision 4).
- **daemon `link/peer/`** (new, beside the shell `link/`) — per-account identity key and the ID text codec, per-account trusted-list store with its MAC, `PeerWire`, its own `Registry` + `Listener` (ADR-0310 D2), accept gate, per-frame membership check, dial-every-listed-peer, tie-break, online state, duplicate-identity detection, endpoint lifecycle (D7), per-node receive queues and `Mail` in-flight caps, the `peer.*` command table with its approval gate and pending requests, the messaging adapters (`RemoteDeliveryPort` adapter, remote entrance caller), the agent directory (publisher of this PC's directory + one read-only copy per trusted PC — §4-7).
- **daemon `ask_user`** (new, shared) — the one "ask the user" seam every request kind uses (§4-8): routes a question to the app while it shows a PC list slot, else to the platform's native approval dialog, else leaves it waiting. The peer module is its first user; it holds no peer knowledge.
- **messaging** — remote branch at the single resolution point (ADR-0309 d3) that reads the directory copies from the one `AddressingSources` snapshot (it does not own or sync them), a resolve scope on `handle_send` (`ResolveScope`, §4-4), `RemoteDeliveryPort`, verdict entry (remote-pending ledger state, verdict-time reply close — §4-6), remote entrance with validation and the per-PC backstop, node qualifier on `SenderIdentity`, the requester's node on request entries and the overdue notice it renders for a remote contract. Still zero workspace deps (ADR-0110).
- **platform** — new: seal / unseal a secret for the current OS account (Windows DPAPI `CryptProtectData` CurrentUser; macOS Keychain; Linux an owner-only 0600 file), the current account id (Windows SID) and machine id (`MachineGuid`), a native approval dialog (Approve / Deny / Deny and stop asking) that reports when no display exists, creating a file `CREATE_NEW` with an owner-only DACL passed at create (shell token, agent control files), and the Windows account that owns the other end of a loopback TCP connection (ADR-0266: OS-specific code lives here). S37 builds the Windows side; the Linux / macOS behaviour is defined here and built with T-118 / T-119.
- **protocol** — one additive peer-state broadcast for the app, carrying pending approval requests, behind a subscription (precedent `UsageSubscribe` / `UsageLimitsUpdated`); no daemon↔daemon vocabulary (§5 T6).
- **shell · frontend** — U4 only: relay the peer-state broadcast; the PC list slot (list, add / edit / remove, approvals, warnings). Every slot action that issues a gated `peer.*` is human-only on the frontend and never in the shell command table (§4-8).
- **daemon `link/` (shell link) · `instance` / `portfile` · `control/` (listener, `mcp_config`) · protocol `discovery` · shell `discovery` / `daemon_client`** — the changes on the app↔daemon side (P-H, §4-9): the shell token moves out of `daemon.json` into an owner-only per-account file (protocol `DaemonInfo` loses `token`, gains the owner account's SID); agent control files are written owner-only; the shell link and the control listener refuse a client whose process runs under another Windows account; the shell shows the other-account message from `daemon.json` alone. The loopback rule, the token handshake, `ShellWire` / `DaemonWire` stay as they are.
- **Untouched** — agent crate (ADR-0003), cli (the send path and its route are unchanged; the address is just a string), base (`file` used as is).

## 3. Data shapes

### 3-1. Persistent files (daemon state folder `<data root>\daemon\state\` — `DataLayout::daemon_state_dir`)

- **Per OS account and machine** (T37) — the identity key and the trusted list are stored per OS account and machine, named by both: `peer-key.<account>.<machine>` and `peers.<account>.<machine>.json` (`<account>` = the Windows account SID, the uid elsewhere; `<machine>` = Windows `MachineGuid`, Linux `/etc/machine-id`). Two accounts sharing one data folder (at different times — one daemon per data folder, ADR-0135, and a running daemon refuses another account's app, §4-9) each keep their own identity and list and never displace each other; a folder moved to another machine — also by a domain / Entra account, whose SID is the same everywhere — finds no file for that machine and starts fresh instead of raising a false "unreadable", and a roaming-DPAPI copy gets a different file, not a duplicate; files of other names are left untouched. This account's files under another machine id (a `MachineGuid` change, Windows reinstalled with the same SID, a folder moved between this account's machines) are detected and the user is asked through the ask-the-user seam whether to adopt them or start fresh — never automatically, because a roaming-DPAPI copy looks the same; adopting tries to unseal and falls into the X5 flow if that fails. A reinstall with a new SID finds no file of this account and starts fresh silently. A cloned VM or disk copies the machine id too; duplicate detection covers that case (§4-2). User 2026-11-20: 「ㅇㅇ 계정단위로해줘」 · 「계정마다 key 와 json을 만들자는거지? ㅇㅋㅇㅋ」.
- **Identity key** — `peer-key.<account>.<machine>` = the 32-byte secret sealed for the current account through one platform function (T20): Windows DPAPI CurrentUser, the blob stored in the file; macOS Keychain; Linux the raw secret in an owner-only 0600 file. Created once, on first need (first `peer.*` call or first add), written through platform (temp → sync → rename without replace). The daemon never replaces it on its own; only the human-approved regenerate below writes a new one. The PC's ID = the public half as text in the daemon's format (T34). What a load can find (T31):
  - no file for this account and machine, and none of this account under another machine id → no identity yet; a new one is made on first need, no prompt (a folder copied to another account's PC lands here); one of this account under another machine id → the adopt-or-fresh question above;
  - a file of this account and machine that cannot be unsealed because it is not this account's or its data is bad (DPAPI's not-yours / bad-data errors — forced password reset, reinstall, profile change), or that is corrupt → "key unreadable — it may come from another PC or account; a new key means re-pairing every PC" → the peer feature does not start, `peer.list` and the app say so, X5 flow;
  - the file missing while `peers.<account>.<machine>.json` lists PCs → treated as unreadable, never silently recreated;
  - a transient failure — lock / IO, or any other unseal error (DPAPI master key not yet available right after logon, domain controller offline) → retried with backoff; the feature stays off meanwhile and regenerate is not offered for it; it recovers with the old ID.
  A new key is made only on a human's OK (§4-8, X5): the old file is kept as a backup by rename to `….bak-<UTC time>` (a repeated regenerate never overwrites an earlier backup); the trusted list is not re-signed — its MAC no longer matches under the new key, so the accept question comes back on every start until a human accepts it (then it is re-signed); no extra state (T39); the result tells the user that every other PC must remove this PC's old ID and pair again.
- **Trusted list + network settings** — `peers.<account>.<machine>.json`, base `file` rules (ADR-0291: version key, cap, newer-version / unreadable = refuse to write; the feature does not start and `peer.*` writes answer `CONFLICT`). The file carries a MAC (T39: the file is `{version, mac, body}` with `body` the serialized list as a JSON string; HMAC-SHA256 over the exact bytes of `body`, key = HKDF-SHA256 of the identity secret with a fixed label, constant-time compare), checked on every load and rewritten on every save. A mismatch → "trusted list was changed outside Engram": the peer feature stays off and the daemon asks a human through the ask-the-user seam whether to accept the list as it now is (re-sign) — agents cannot resolve it. Another account cannot open this account's key, so it cannot forge the MAC; the check works without folder ACLs (exFAT) and the same on every OS. What the MAC is for (P-H, T46): it catches naive edits and other accounts' edits only — a process of the same account can unseal the key and recompute it, and rollback to an older correctly signed list is not defended (no comparable local tool does). A list whose key was unreadable is never verified that run, so after a regenerate it fails the MAC check under the new key and raises the accept question until a human accepts it. The accept question shows every entry with its ID and the network settings; a deny leaves the peer feature off. Shape:
  - `peers[]` = `{ id, name, address?, permission }` — `id` = the other PC's ID text (required, unique; our own ID is refused, §4-2); `name` = display name, used as the address suffix (required, unique case-insensitively, no `@`, no whitespace; matched case-insensitively when parsing `name@pc`, §4-3); `address` = optional `ip:port` direct address; `permission` = `"mail"` (only value accepted in v1; `"control"` reserved for the shell → remote daemon stage). `name` and `address` change in place through `peer.edit` (§4-2). Room for a later group record = a sibling top-level key, not a field on entries.
  - `network` = `{ port?, relay, address_lookup, mdns }` — `port` absent = the fixed default (§8 X1; the dev build, data root `.engram-dev`, has a different default from release — T35); `relay` / `address_lookup` = `"default"` (n0) | `"none"` | a URL (Syncthing `default` keyword precedent); `mdns` = bool, default `true`.
  - Why one file per account and machine: one owner (the peer module), one load/refuse rule, one writer. The daemon has no settings file today and shell settings cannot carry these — the daemon runs and links without the app (R13 · R3).
- **`daemon.json`** (`<data root>\daemon\run\daemon.json`; held by the single-instance guard, written in place and never deleted — ADR-0135, `instance.rs` `acquire_with` / `portfile.rs`) — stays the shared single-instance lock and discovery record: pid, port, protocol version and the owner account's SID, with no token. Its ACL stays inherited, so any account can open it after a crash (stale-pid rule unchanged) and read who owns a running daemon (T47; amends ADR-0135 decision 1).
- **Shell token** — `daemon-token.<account>` in the same run folder, created with `CREATE_NEW` and the owner-only DACL passed at create (no create-then-set window), through one platform function (Jupyter `secure_write` precedent). An existing token file that is not owner-only or not owned by this account is deleted and recreated; if it cannot be deleted the daemon refuses to start (covers pre-S37 folders and a file another account placed; a read handle left open on the old file object cannot read the new one). Per-account naming lets X and Y take turns in one folder: Y never needs to delete X's owner-only file.
- **Agent control files** — `daemon/run/mcp-config/*.json` (agent Bearer tokens, ADR-0086) are written through the same owner-only create function.
- Pending approval requests are not persisted (§4-8).

### 3-2. Link framing (transport `iroh`)

- One ALPN per relationship: `engram/peer/1` opened in v1; `engram/shell/1` reserved (not registered on the endpoint in v1). Unknown ALPN is refused by the QUIC handshake.
- One QUIC connection per link, one long-lived bi-stream opened by the dialer; the dialer writes a 1-byte preamble at once (the stream is invisible to the peer until a byte is written).
- Frame = kind byte (text · binary · keepalive) + u32 BE length + payload; max payload given by the consumer like `ws` `max_message_bytes` — PeerWire uses 512 KiB (T30: a 64 KiB body JSON-escaped at worst — every byte a control character written `\u00XX`, 6× — is 384 KiB, plus headroom for the other fields). Oversized or malformed inbound framing = close with `PROTOCOL_ERROR` (4005). The sending side checks the encoded size before sending, so its own oversized frame never closes the link (§4-3).
- Close: our `CloseCode` u16 ↔ QUIC application error code; reason truncated to an adapter-local byte cap (exact QUIC cap confirmed in U1). A peer-sent close with QUIC code 0 → `LinkRead::Closed(None)` (`link.rs`: `Closed` means the peer said so) → read as "could not connect / going away", never a terminal rejection; an idle-out or any other locally detected loss → `Err(LinkError)`, never `Closed` (`RejectKind::of` returns `None` only for 1000 · 1001 · 4000 — U1 maps 0 explicitly). The final `Reject{last}` frame is best-effort diagnostics; correctness never depends on it.
- Liveness (T44): the peer link relies on iroh's QUIC liveness — heartbeat 5 s, path idle 15 s direct / 30 s relay (`iroh-1.4.1` `socket.rs` `HEARTBEAT_INTERVAL` · `PATH_MAX_IDLE_TIMEOUT` · `RELAY_PATH_MAX_IDLE_TIMEOUT`) — and treats the connection close as the link loss. The PeerWire registry turns the supervisor's own ping / idle off; today they always arm (`peer.rs` wake and cut on `Policy::ping_interval` / `idle_timeout`), so U1 makes them optional in `Policy` (default on, `ws` unaffected) and relaxes `Policy::check`'s `write_deadline < ping_interval < idle_timeout` when they are off. `ping()` still writes a keepalive frame for any consumer that keeps supervisor pings. U1 confirms the connection itself closes when every path idles out (connection-level idle timeout) and that the adapter reports it as `Err(LinkError)`.
- Accept: QUIC accept → the consumer's `accept_if(peer_key)` predicate (before `accept_bi`; `false` closes the connection with `HANDSHAKE_REJECTED`, §4-2) → ALPN + bi-stream accept under a stream-accept timeout (value set in U1) → a ready queue bounded by a `PermitPool` (same shape as `WsListener`), so `Listener::accept` stays cancel-safe and neither unlisted nor silent dialers hold accept permits. `Accepted.info.peer_key` = the authenticated 32-byte endpoint id; `remote` = the observed socket address (diagnostics only).
- Dial target = the remote's raw 32-byte key + optional direct socket addresses; the daemon parses the `<id>` / `<id>@<ip:port>` text (T34). iroh verifies the remote key against the id on dial. The dialer never uses 0-RTT (`into_0rtt` forbidden: 0-RTT data is replayable, and a replayed `Mail` would be delivered twice).
- iroh build: `default-features = false` + `tls-ring` (no `portmapper`, no metrics). Presets: `N0` when relay and lookup are both `default`; otherwise `Minimal` + custom relay map / pkarr + DNS lookup / none. Typed peer addresses go in as direct addresses (memory lookup). Fixed port = `bind_addr` on `0.0.0.0:<port>` (+ `[::]:<port>`). mDNS = the separate crate `iroh-mdns-address-lookup` (§9 P3).

### 3-3. PeerWire vocabulary (daemon `link/peer/`, JSON text frames)

| Message | Direction | Fields (boundary level) |
|---|---|---|
| `Hello` | both (dialer first; acceptor answers after `Done`, the shell-link pattern) | `protocol_version` · `instance` (a random value of at least 64 bits drawn at daemon start — duplicate detection, §4-2; the directory `run` is the same value) — no node field; the node is the link key |
| `Mail` | request (tag = mail id) | `id` · `from {agent_id, name}` (no node — stamped from the link; `name` is the sending daemon's claim) · `rows[{tag, to}]` (≤ 64; `tag` = the sender's row index, frozen on its ledger row at send time; `to` = an agent name or id on the receiver) · `body` · `reply_to?` · `request {reply_by_raw}?` |
| `MailVerdict` | reply to `Mail` | `id` · rows `[{tag, outcome, recipient_id?, code?, reason?}]`, one per request row, matched by `tag`; outcome = `delivered` \| `held` \| `refused` \| `unknown_recipient`; `code` from a closed set (below); `reason` ≤ 512 bytes |
| `ReplyOverdue` | push, contract holder → the requester's node | `request_id` (the request mail id) — no text; the requester's daemon renders its own notice (§4-6) |
| `DirSnapshot` | push, each side right after the handshake; also the answer to `DirResync` | `run` · `rev` · `part` · `last` · `agents[{id, name, state}]` — the sender's whole directory, in parts when it exceeds the frame cap; `state` = `live` \| `sleeping` (the `agent.list` words) |
| `DirDelta` | push, owner → each linked PC | `run` · `rev` (= previous `rev` + 1) · `upsert[{id, name, state}]` · `remove[id]` — never sent between the parts of a snapshot; a delta that would exceed the frame cap goes as a multi-part snapshot instead |
| `DirResync` | push, copy holder → owner | — (asks for a fresh `DirSnapshot`) |
| `Probe` / `ProbeAck` | push pair, either side | `nonce` — proves a link alive (duplicate detection, §4-2); a push pair, so `Mail` stays PeerWire's only request (T23) |
| `Duplicate` | push on the kept link, and as the reject's `last` frame | `kind` (`duplicate` \| `suspected`) — the structured duplicate-identity warning (§4-2) |
| keepalive | both, only when a consumer keeps supervisor pings (PeerWire does not, T44) | `Frame::Keepalive` (never reaches `Wire::decode`) |

- One `Mail` per (send, remote PC) carries that PC's rows; one verdict answers it. Each row's `to` holds the bare name (or the id) — the sender strips `@pc` — and the verdict is matched by `tag`, never by the notation, so a stripped `@pc` or a `peer.edit` rename while the request is pending cannot misroute it (T26). The sender folds rows that name the same (PC, stripped token) into one (first appearance kept, as local dedup); a receiver that resolves two rows (an id and a name) to the same local agent delivers once and answers both tags with the same outcome and `recipient_id`.
- Directory frames carry no node field: whose directory it is = the link's key, so a PC can only write its own copy (R16, as R8 for mail). They carry nothing else about an agent (no cwd, parent, backend, repo, branch, activity). `run` / `rev` ordering and row validation: §4-7.
- Version: equal `protocol_version` required; mismatch = `Reject{Terminal}` with "version mismatch" (shown in peer state; redial re-armed on daemon start and on `peer.add`).
- Decode failure = drop the frame + log (`DecodeFailurePolicy::DropFrame`); a frame naming a non-`mail` permission action does not exist in the vocabulary (R9 by construction). There is no peer-written notice (T28).
- `held` = the receiver's local `SendStatus::Pending` (parked: recipient asleep, or live but the drain could not inject — busy; in memory, 24 h TTL, mailbox cap 100). Closed `code` set = `REMOTE_LIMIT` (§4-5: the per-PC backstop and the body cap) · the receiver's own row codes (`RECIPIENT_AMBIGUOUS` · `MAILBOX_FULL` · `REQUEST_CAPACITY`) · `REMOTE_REFUSED` (permission · id collision · validation failure, §4-4). The sender maps any code outside the set to `REMOTE_REFUSED`, and shows a peer's `reason` (truncated to the cap) labelled with the origin PC.

### 3-4. Sender-side result mapping (what the sending agent sees — R6)

| Result | `SendStatus` | code / hint |
|---|---|---|
| delivered | `delivered` | — |
| held | `pending` | hint: held on `<pc>`, recipient asleep or busy |
| refused | `failed` | the relayed code (closed set, §3-3) or `REMOTE_LIMIT` / `REMOTE_REFUSED` + the peer's reason labelled with the PC |
| unknown recipient | `failed` | `RECIPIENT_NOT_FOUND` — from the receiver: hint names the PC (a stale copy ends here too); not found anywhere: the existing local hint, plus the listed PCs whose directory is unknown this run (§4-7) |
| not delivered (no live link — also a bare name found only in a disconnected PC's copy; or the link dropped before the mail was handed to it, `RequestError::Disconnected{sent: false}`) | `failed` | new `PEER_OFFLINE` (hint names the PC). A PC in state `refused` gets its own hint: that PC does not list this PC's ID — add it there (not "offline"); `version mismatch` likewise names the cause |
| ambiguous across PCs (bare name, not local, in 2+ PCs' copies — a PC whose directory is unknown this run is not counted, D2; or an id listed by 2+ copies) | `failed` | `RECIPIENT_AMBIGUOUS`; hint lists the candidates `name@<pc>` (sorted) and says to resend with one — the local hint today gives only a count (`ambiguous_hint`); the cross-PC one adds candidates (`llm-command-conventions.md` §1-3) |
| unconfirmed (no verdict within the agent-facing wait, 7 s — T24; or the link dropped after the mail was handed to it, `Disconnected{sent: true}`; also a send to a PC that died abruptly, before its QUIC connection idles out — T44) | `pending` | hint: unconfirmed — may or may not have arrived; do not resend blindly |

- Keeps the three-word status vocabulary (spec §6); new codes = `PEER_OFFLINE` · `REMOTE_LIMIT` · `REMOTE_REFUSED` · `NAME_TOO_LONG` (the sending agent's name breaks the remote name rule, §4-4 — "rename the agent"). `BODY_TOO_LARGE` (today an entrance bounce) also appears as a row code when that PC's encoded `Mail` frame would exceed the cap; `REMOTE_LIMIT` also answers locally when the in-flight cap of `Mail` requests to that PC is reached (§4-3).
- Late verdicts (T23): the PeerWire `Mail` request has its own transport deadline, 120 s, separate from the 7 s agent-facing wait, because transport drops a reply that arrives after its request's deadline (`peer.rs` `route`, ADR-0181 d4). The deadline is the PeerWire registry's `Policy::request_timeout` (one value per registry, ADR-0181 d1; `Mail` is PeerWire's only request). A verdict that arrives after the agent was answered still updates the ledger row (visible in `eg_messages`) and the sender gets one daemon `<notice>` with the final outcome and code only (a peer's `reason` stays in tool results, never in the daemon's notice voice). Whether a row is reported in the answer or by a later notice is decided atomically under the messaging lock at the 7 s boundary, so each row is reported exactly once. Past the 120 s deadline, or when the link drops after sending, the row stays unconfirmed and the notice says the outcome is unknown. The notice goes through the existing notice lane, injected at the idle gate like the reply-deadline notice (ADR-0104) — user 2026-11-19: 「일단은 그냥 가자. 지금처럼」; turning such notices into deferred inputs that ride the next input without a turn is T-115. v1 sends no later receipt when held mail is finally injected (§8 X3).

## 4. Flows and concurrency

### 4-1. Endpoint lifecycle (D7 · R13)
The peer module starts the iroh endpoint only while `peers` is non-empty: at boot if the list has entries, on the first applied `peer.add`; it stops it (closing all links) when the last entry is removed. Creating the key file contacts nothing. `peer.setNetwork` restarts a running endpoint (directory copies are kept `disconnected` across it, §4-7). `peer.*` handlers finish on the first poll (T32): an applied `peer.add` / `peer.setNetwork` writes the file and hands the change to the peer module, an agent's call only records a request (§4-8); endpoint start and link results show in `peer.list`.

### 4-2. Links (R3 · R4)
- Dial: every listed peer gets a dialing `Registry::add` handle — reconnect without limit (`max_attempts = u32::MAX`, the shell precedent ADR-0346), backoff capped at 60 s and connect timeout 20 s (Reason Network `net.rs` 2→60 s · 20 s). A PC does not dial a node it already has a live link to: transport has no pause, so while an accepted link from that node is live the peer module removes that node's dialing handle (`Registry::remove`) and adds it again when the link ends; a re-arm trigger that fires meanwhile only marks the handle to be re-added.
- Accept gate: the daemon fills the adapter's `accept_if(peer_key)` predicate, called before `accept_bi` (Reason Network gates before `accept_bi`). Not listed (or permission ≠ `mail`) → the connection is closed with `HANDSHAKE_REJECTED` and the reason "not paired": no stream is accepted and no frame is read (R4); the dialer reads the code as `Terminal` (`RejectKind::of`) and gives up without spending budget. The refusal is logged with the key's ID text, throttled like the shell link's `AcceptRefusal` log (per-kind time-window batches — ADR-0310 D9; repeated identical failures throttled — ADR-0346 d5). Listed → bi-stream accept → attach with the PeerWire handshake. `Registry::attach` drops `LinkInfo`, so the peer module keeps `link label → node id` in its own per-link state.
- Liveness: a link ends when its QUIC connection closes (iroh idle-out included); there is no PeerWire-level ping (T44). A peer that hangs while its QUIC stack still answers is covered by the `Mail` deadlines (7 s → unconfirmed, 120 s late window).
- Tie-break without churn (T17): two live links for one node happen only when both PCs dial at once. When the second comes up within 5 s of the first (Reason Network `DIALED_TOGETHER`), keep the one dialed by the smaller ID and close the other with `GOING_AWAY`; outside that window the newer link replaces the older one (the older may be stale after an abrupt restart of the other side). Directory frames go on the chosen link only.
- Re-arm: a dial that ended in a terminal refusal is re-armed on: an accepted link from that node ending, `peer.add`, daemon start, and a slow retry every 10 min for a "not paired" refusal (a one-sided setup — the other PC adds this one later; Syncthing keeps redialing unknown devices) (T33).
- Online state per PC = `online` (≥1 live link) · `offline` · `refused` (terminal refusal from the other side) · `version mismatch` · `duplicate identity` · `endpoint error` (e.g. port in use).
- Duplicate identity (T40): every `Hello` carries the sender's `instance` (§3-3). Only fresh evidence counts: (a) the same node completes handshakes with two different instances and both connections are proven alive after the second handshake — the peer module sends `Probe` on the older link once it sees the new instance, and a `ProbeAck` within 10 s proves it alive (a late frame from the old instance proves nothing, and an abruptly restarted peer's old link never answers); or (b) an instance that was replaced comes back in a fresh handshake within 5 min. Either way the newer link is refused (terminal) and both sides warn. (c) Flap rule for copies that carry the same instance (a live VM clone, a snapshot restore): the same node's link replaced 3 times within 10 min → a "suspected duplicate" warning; links are not refused for it. Warnings travel as the structured `Duplicate` message — the reject's `last` frame and a push on the kept link — not as close-reason text (best-effort and shared with "not paired"); the warning first suggests looking for a second running copy, then offers regenerate (R20). A plain restart is not a duplicate. Two folder copies on the same machine and account load the same identity: the peer module takes a local named lock keyed by the identity at start, and the second copy's peer feature refuses with "this PC identity is already in use by another Engram copy on this PC". Our own ID offered to `peer.add` is a plain refusal ("that is this PC's own ID", as Syncthing), not a duplicate warning. The relay's `SameEndpointIdConnected` is not used (`iroh-1.4.1` only logs it). Agent ids duplicated by a copied data folder are refused per mail by R8 with a specific hint (§4-4) (T-123).
- Edit (`peer.edit`, T43): changes a PC's `name` (my label for that PC and the `@pc` suffix) and `address` in place; the ID, the live links and the directory copy stay; one signed file write. An address edit is open to agents; a rename is gated like `peer.add` (§4-8) — labels drive `name@pc` routing and the sender display, and three renames could swap two PCs. A rename answers that `name@<old>` addresses stop resolving (they get `RECIPIENT_NOT_FOUND`); bare names are unaffected; the other PC's label for this one is its own.
- Removal (`peer.remove`, T29): revoke in memory first — the gate and the per-frame check see it at once — close that node's handles and inboxes with `HANDSHAKE_REJECTED`, drop its copy, then save the list; a refused save is reported in the answer and the revocation stays for this run (R4 · AC7 ≤ 1 s). Open to agents (it narrows trust).
- Per-frame membership: every inbound frame is checked against the current list (Reason Network `on_wire` re-checks membership); a frame from a node that is no longer listed is dropped and that node's handles / inboxes are closed.
- Transport receiver invariants hold: the inbox-draining task never awaits `request` (sends run on spawned tasks); every inbox is drained to `None`.

### 4-3. Send (A side)
`handle_send` resolves each token once from one snapshot (`AddressingSources` = local roster + dormant + listed PCs + the directory copies, §4-6 · §4-7). `resolve_token` order (ADR-0309 d3 — 「여기 없으면 다른 데몬으로」; D2):
1. **`name@pc`** — the text after the last `@` matches a listed PC name (case-insensitive, like PC-name uniqueness) → `Resolution::Remote{node, name}` for that PC only. The explicit form wins over a local agent whose literal name is the whole token (R17 precedence, T8). The copy is not consulted: the receiver answers authoritatively (`unknown_recipient` → `RECIPIENT_NOT_FOUND`), and a disconnected PC gives `PEER_OFFLINE`.
2. **Local, unchanged** — id (live → asleep), then exact name (live layer, then asleep layer), with today's local `RECIPIENT_AMBIGUOUS`. Anything found locally ends here: a local agent always wins over a remote one of the same name (R5).
3. **id** (UUID-shaped, not local) → the copy that lists that id (ids are unique across PCs — ADR-0309) → `Remote`; listed by 2+ copies → `Resolution::Ambiguous` with the candidates `name@<pc>` (§4-7).
4. **Bare name** (not local) → exact, case-sensitive match against every copy, connected or disconnected, live or asleep, counted per PC: one PC → `Remote{node, name}` (that PC resolves its own duplicates and layers); two or more PCs → `Resolution::Ambiguous` across PCs with candidates `name@<pc>` (§3-4); none → `NotFound`. Disconnected copies count in the ambiguity check, so a PC going off never makes the same rule switch to another PC silently. A PC whose directory is unknown this run (no copy since the daemon started, X6) is not counted (D2 exception, P-B): the bare name goes to the one known PC with no extra hint; to reach the unknown PC's agent, write `name@pc`. Bare names stay refused when found on several PCs; an explicit fan-out `name@*` is T-117 (P-B0).
5. A chosen PC with no live link → immediate `PEER_OFFLINE` (below).

`@all` / `@here` never expand to remote agents (v1, local only). A remote row is recorded in the ledger in the remote-pending state (`to` = the notation, `to_id` = none until the verdict) without opening a contract (§4-6), then handed to `RemoteDeliveryPort::enqueue` — non-blocking, called outside the messaging lock (same discipline as `DeliveryPort`). The daemon adapter: no live link → immediate `PEER_OFFLINE` verdict; the sending agent's name breaks the remote name rule (§4-4) → that PC's rows `failed` with `NAME_TOO_LONG` ("name too long for remote mail — rename the agent"), nothing sent; 256 `Mail` requests already in flight to that PC (the transport pending table has no cap — `pending.rs` `Pending::insert`; T45) → `failed` with `REMOTE_LIMIT`, not sent; encoded `Mail` frame over the cap (§3-2) → that PC's rows `failed` with `BODY_TOO_LARGE`, nothing sent; else a PeerWire request on a spawned task under the 120 s transport deadline; verdict, `Disconnected` or deadline → the kernel's verdict entry transitions the row (§3-4 mapping). The control entrance answers the agent once every remote row has a verdict or the 7 s agent-facing wait — `CommandDeliveries::DEFAULT_DEADLINE` itself, not a copy, so `fits_caller_silence_window` binds it (T24) — counted from the control request's arrival has passed (AC6) — rows still without a verdict are reported unconfirmed, the transport request stays pending, and a later verdict goes through the verdict entry (ledger + one notice, §3-4). Local rows are unaffected by the wait.

### 4-4. Receive (B side)
Peer inbox → per-frame membership check (§4-2) → decode `Mail` → that node's receive queue, run off the inbox task because `handle_send` injects inline through the blocking `DeliveryPort::inject` (ADR-0125 d1). Order is kept per (node, recipient token): a frame waits only for earlier frames from that node that share a `to` token, so one stuck recipient does not stall the PC's other mail (two tokens naming one agent — an id and a name — are not ordered with each other); at most 4 frames per node run at once; the queue holds at most 64 frames per node, and a frame arriving at a full queue is refused whole with `REMOTE_LIMIT` ("receiver busy"). Then the messaging remote entrance with the link's node:
1. **Validation like ingress** (T27) — the checks control ingress makes today: `validate_contract` (request and `reply_to` exclusive, `reply_by` only with a request and within its range, non-empty `reply_to`), single-recipient reply (`reply_to_has_single_recipient`), non-empty `to`, the envelope-format check against the receiver's own format (`contract_unsupported_by_envelope`); plus ≤ 64 rows with unique `tag`s, `@all` / `@here` tokens refused, `from.name` within the remote name rule — non-empty, ≤ 256 bytes, no control characters (agent names have no local cap; `Roster::MAX_NAME_BYTES` is the command-name cap, not an agent-name rule; the sender enforces the same rule, so a long name fails locally, §4-3, and is left out of the published directory, §4-7) — `from.agent_id` not the nil id. A failure refuses the whole frame with `REMOTE_REFUSED` and the reason.
2. **R8** — `from.agent_id` must not be a local agent id, where "local" = the full manager roster (every profile, live shells included), not the mail-eligible `AddressingSources` set; no node claim exists in the frame. The refusal carries a specific hint: "this agent id also exists on this PC — copied data folder?".
3. **Backstop** (§4-5), then `handle_send` with `Entrance::Remote` and `ResolveScope::LocalOnly`. `SenderIdentity` stays `{peer_id, epoch}` and gains `node` = the link's node; the display `"<name>@<B's name for that PC>"` goes in as `handle_send`'s `sender_name` (the envelope shows the address the recipient replies to — R7). The link authenticates the PC; the agent name is the sending daemon's claim.
4. Per-row results → `MailVerdict`.

`Entrance` stays a log label (pipeline does not branch on it). ★Remote mail is resolved on local agents only — no forwarding to a third PC★: `handle_send` takes its own snapshot (`port.addressing_sources()`), so the caller cannot hand it an emptied one; the named seam is a `ResolveScope` argument (`All` for ingress, `LocalOnly` for the remote entrance) under which the listed PCs and the directory copies are ignored — steps 1, 3 and 4 of §4-3 cannot match, and a name the receiver does not have is `unknown_recipient`.

### 4-5. Inbound backstop (D5 revised · R9)
At the receiving side's resolution point (messaging remote entrance — policy in the lib, ADR-0110), one high per-PC backstop against a broken peer daemon (which could invent sender names): 600 mails/min per PC, whole frame refused; and the body cap of 64 KiB (same value as the local `MAX_BODY_BYTES` in `control/ingress.rs`; the sender already caps with `BODY_TOO_LARGE`, the receiver re-checks). Hit = `refused` + `REMOTE_LIMIT` with the limit as reason (AC10). No per-agent or per-pair limit: normal use never reaches one, and an LLM ping-pong loop runs at a few mails per minute, so a per-minute cap would not catch it — remote mail behaves like local mail, which has none; loop detection for both is T-121. Over the backstop v1 refuses; deferral comes with the outbox (T-120). One limits value injected by the daemon, ready for a later settings system; counters in memory, clock injected (`now: Instant`).

### 4-6. Ledger identity (boundary decision)
- Keys stay agent UUIDs — no node in any key. Rests on ADR-0309's 「an id must be unique across servers」 (fresh UUID v4 per profile); a remote frame reusing a local agent id is refused (R8).
- The node is a display/routing qualifier: `SenderIdentity` (`{peer_id, epoch}`) gains `node: Option<NodeRef>`; `NodeRef` = a messaging-local opaque fixed 32-byte value (the node key; the ID text is rendered from it) — not a uuid alias (§9 P2). `AddressingSources` gains the listed PCs `(NodeRef, name, connected)` and the directory copies (rows `(NodeRef, id, name, state)`) so resolution stays one snapshot; the daemon adapter (`messaging_host.rs` `ManagerDeliveryPort::addressing_sources`, which today builds both local lists from one `manager.roster()` call) fills them from the peer module in the same call — a third physical lookup beside the session snapshot and the profile list (ADR-0116), read under the peer module's own lock, never under the messaging lock.
- Sender-side rows (T26): remote rows are recorded without a recipient id and get their outcome later, so the ledger gains a remote-pending state whose transitions to delivered / held / failed are applied only by the verdict entry, picking the row by (mail id, row `tag`) frozen at send time (§3-3). Today the only edge into `Failed` is deletion cleanup's `Pending → Failed` (`can_fail_by_cleanup`), and a remote-held row cannot be local `Pending`, which the expiry sweep and the wake flush act on. Exact states: the ADR (U0 ⑥).
- Reply contracts live on the **receiving** daemon: `handle_send` there opens the contract for its recipient and the recipient's reply closes it there (closing is replier-side today). The sending daemon opens none for remote rows. The remote entrance stores the requester's node (from the link) on the request entry. A reply that goes to a remote requester closes the local contract at verdict time with ADR-0116 d2's rule: delivered or held → replied; `RECIPIENT_NOT_FOUND` → reply_failed; any other outcome → stays open (as `reply_disposition` `NoOp`). The requester's own "awaiting reply" view does not list remote requests in v1 (§8 X4).
- Overdue (T28): the receiving daemon sends `ReplyOverdue{request_id}` to the node recorded at request time (never by resolving the requester id), best-effort (lost if the link is down); the requester's daemon renders its own overdue notice from its template, naming the origin PC. No peer chooses notice text. The requester's daemon accepts a `ReplyOverdue` only for its own open remote request row sent to that node, and only once; the receiving daemon does not send it while a reply verdict for that contract is still in flight.
- Mail ids are unique per daemon only; a remote id that collides in the receiver's ledger → `REMOTE_REFUSED` (probability as for local collisions).
- Size: `SenderIdentity` + `MessageRecord` (optional node) + `AddressingSources` (PCs + copies) + one resolution variant + a cross-PC ambiguity hint + one port + verdict entry + row tags on remote rows + the remote-pending ledger state and its verdict-time transitions + the verdict-time reply close + the requester's node on request entries + the `ReplyOverdue` notice render + the `ResolveScope` argument on `handle_send` + remote entrance (validation) + a per-row kernel result for the remote entrance (row index and resolved recipient id — `RecipientResult` carries neither today, and the verdict needs both for tags and alias folding) + the per-PC backstop counter. `SenderIdentity` is `Copy` and passed by value (~60 uses in messaging and the daemon): `NodeRef` is a fixed 32-byte value so `Copy` survives (the ID text is rendered from it); a `String` would drop `Copy` and ripple through `handle_send`, `daemon_identity` and the daemon's `From<BoundIdentity>` (§9 P15). No key migration (mailbox and ledger are not persisted).

### 4-7. Agent directory sync (D2 · R16 · R17 · R18)

- **What is published** — this PC's directory = the same set local name resolution sees, by the adapter's own predicate (`ManagerDeliveryPort::addressing_sources`): live agents that read mail (a live shell is left out) and every dormant profile (a dormant shell is listed). Each row = `id`, `name`, `state` (`live` | `sleeping`); a row whose name breaks the remote name rule (§4-4) is omitted with a local warning. Nothing else leaves the PC (no cwd, parent, backend, repo, branch, activity).
- **Owner-only writes** — each PC is the only writer of its own directory. A copy changes only through `Dir*` frames on that PC's authenticated, chosen link (§4-2); frames carry no node, so no PC can write another PC's copy. Copies are never re-published: each PC sends only its own agents (no transitive gossip, no forwarding through a third PC).
- **Row checks on arrival** — a row whose id is a local agent id (the full manager roster) is dropped and logged; a row whose name breaks the remote name rule (§4-4: empty, over 256 bytes, control characters) is dropped and logged — a second line behind the publisher's own omission (local names are cwd basenames and may hold spaces or `@`, so no stricter charset). An id already listed by another PC's copy is kept in both and logged; a send to that id is refused as ambiguous with the candidates (§4-3 step 3) — dropping one would make the winner depend on which link came up first.
- **Lifecycle with links** — after the PeerWire handshake each side sends a `DirSnapshot`; it replaces the whole copy and marks it `connected`. While the link is up, the owner sends `DirDelta`s. When the PC's last live link ends, its copy is kept and marked `disconnected` (names still resolve → `PEER_OFFLINE`, R17). The next link's snapshot replaces it. A link replaced or closed by the tie-break changes nothing (the copy follows the node, not the link). A `peer.setNetwork` restart closes the links like any drop: copies are kept `disconnected` until the next snapshots. A `peer.edit` rename keeps the copy (it is keyed by node).
- **When a copy is dropped** — on `peer.remove` of that PC (together with the entry and its links), and when the endpoint stops because the last entry was removed. Copies live in memory only: after a daemon restart a PC has no copy (`unknown`) until it links again (§8 X6); an `unknown` PC is outside the bare-name count (§4-3 step 4).
- **Triggers, no timer** — the publisher recomputes its directory on every roster-composition change (create · delete · rename) — both the command path (`RosterChanged` / `control::agent::RosterBroadcast`, bus and CLI `agent.*`) and the shell WS path (`connection_core.rs` profile messages, which call `broadcast_profile_list` directly and bypass `RosterChanged` — §9 P14); U3b hooks one point both pass — and on live ↔ asleep transitions (session start / exit; exact hook confirmed in U3b — composition notices alone miss wake and exit, `RosterChanged` doc: 「waking does not change composition」). It diffs against the last published directory, coalesces bursts (~250 ms) and sends one `DirDelta` per linked PC; no change = no frame. A coalesced delta that would exceed the frame cap is sent as a multi-part snapshot instead, and no delta is sent between the parts of a snapshot. No periodic re-send (Reason Network's `presence_loop` checks every 2 s and re-sends every 60 s — not copied: the link is one ordered stream, so a snapshot per link plus deltas cannot drift).
- **Ordering and staleness** — a `connected` copy lags by at most the delta in flight; a `disconnected` copy is as of the link drop. Mail routed by a stale entry gets the receiver's authoritative answer (`RECIPIENT_NOT_FOUND` naming the PC); the sender is not re-routed automatically. `rev` counts per publisher run, and every snapshot / delta carries the run identity (`run` = the daemon's `instance`, drawn at start, §3-3). A delta applies only when its `run` equals the copy's and its `rev` = copy `rev` + 1; otherwise the holder keeps using the copy and sends `DirResync`, and the answering snapshot replaces it. A snapshot of the copy's own run with a `rev` below the copy's is ignored, so an old snapshot cannot replace a newer copy; a snapshot of another run replaces the copy (the publisher restarted). A multi-part snapshot replaces the copy only when its `last` part arrives.
- **Limits** — no entry cap: a directory larger than one frame goes as a multi-part snapshot (§3-3), so a copy is always complete (R16); memory = entries × PCs, all from the user's own PCs. Directory frames do not count against the mail backstop (§4-5).
- **LLM listing (R18)** — `peer.list` (U2's area query, T18) gains per PC `directory` = `connected` | `disconnected` | `unknown` and `agents[{name, id, state}]` sorted by name; its filter arguments pick one PC or leave the agent rows out (`llm-command-conventions.md` §2-2). `agent.list` stays local: it lives in the agent crate, which knows no peers (ADR-0003), and its rows carry cwd / parent that are not replicated. `prompts/engram-help.md` says so on both lines; `prompts/agent-priming.md` says that when the same name exists on several PCs the agent addresses it as `name@pc`.
- **Cost** — three directory messages, a publisher (recompute + diff + coalesce + parts), a copy store keyed by node, one `AddressingSources` field, the `peer.list` rows. Traffic = one snapshot per link-up + one small delta per change per linked PC; zero while idle. Memory = entries × PCs.

### 4-8. Trust changes and approvals (R19 · P-C)

- **Who may call what** (T41) — open to agents: `peer.list`, `peer.remove` (narrows trust), `peer.edit` of an address. Gated: `peer.add`, `peer.setNetwork`, `peer.regenerateKey`, `peer.edit` of a name — an agent's call creates a pending request; a human's call applies at once. Human-only: `peer.approve` / `peer.deny` (answer a request) and the trusted-list accept question (§3-1).
- **Human vs agent = a typed caller**, never an argument and never the `entrance` string (a log label; tests pass `"test"`): a socket-delivered call from a live shell connection (`caller: Some(ConnId)` from `ConnRegistry`, counting up from 1) = human; a control-route call carrying the agent token's `BoundIdentity` (`/control/call`, `/control/agent`, the agent-injected `ENGRAM_TOKEN`) = agent; the synthetic callers `CommandBus::invoke` allocates for relays (counting down from `u64::MAX`) are never human. `call_daemon_command` takes only `entrance` and `caller: Option<ConnId>` today, so U2 changes it to take that typed caller, and a request names the agent.
- **The app must not turn an agent call into a socket call** (U4): every slot action that issues a gated `peer.*` (add, approve, deny, accept-list, setNetwork, regenerateKey, rename) is `humanOnly` in `src/commands/registry.ts`, has no `help`, runs only through the human path (`runAsHuman` or a direct UI handler) and is never declared in the shell command table — so `window.__engramCmd.run`, the bus bridge and `/control/call` relays cannot reach it (`run` refuses `humanOnly`; a missing `help` only hides an entry, it does not block it).
- **Pending request** — kind + arguments + requesting agent + time + origin. The answer comes at once (first poll, T32): "requested — waiting for the user's approval (request `<id>`)". Origin marking (best-effort): when a remote mail reached that agent's session this run, the request says "after mail from `<pc>`" (the most recent such PC) — a hint for the human, not a security boundary. Expiry 24 h; cap 8 pending — a 9th is refused with a hint to ask the user, and a request identical to a pending one is not added twice; memory only (a restart drops them). `peer.list` lists pending requests. Every answer consumes the pending request atomically before applying it; an answer for an expired or already-answered request is ignored. After a deny, the same (agent, request kind) is refused for 10 min without asking; repeats while one is waiting are coalesced into "N requests waiting", and an answer applies only to the request on screen; OS dialogs are also rate-limited per request kind (at most one new dialog per kind per minute, the rest queue), because a per-agent cooldown is evaded by `agent.new`; a native dialog still open after its request was answered in the app or expired is dismissed, or marked stale where the platform cannot close it; "deny and stop asking for this agent this run" refuses that agent's gated calls until the daemon restarts.
- **Ask-the-user seam** (T42) — one daemon module for every question kind (trust requests, the trusted-list accept question, later kinds). Route, in order: the app while it currently shows a PC list slot (visible = in the active tab of a non-minimized window — that is what "subscribed" means) → the app shows it there (U4); else a desktop session → `platform`'s native approval dialog (a Rust native-dialog crate, no custom window; topmost without stealing focus where the OS allows — the foreground lock can put it behind other windows); else (no display, e.g. headless Linux) → the request waits until a human answers in the app or it expires. If the app detaches or the slot closes while a question is open, the question is rerouted to the dialog. One dialog at a time, run off the daemon's async tasks. Before U4 no app shows the slot, so questions go to the dialog. Question content: system-written text saying what is asked and what it allows, labelled "an agent asks" with the agent's id prefix; agent-supplied strings (agent name, PC name, URLs) quoted, on one line, length-capped; the other PC's full ID grouped for reading (not a short fingerprint — a short one can be ground); choices Approve / Deny / Deny and stop asking this agent, default Deny. The trusted-list accept question shows every entry with its ID and the network settings; a deny leaves the peer feature off. A human approve CLI for headless machines needs a credential agents never get (today `engram` authenticates only with `ENGRAM_TOKEN`) → later (T-118). Rejected: a daemon-opened terminal for yes/no (no precedent; opens behind other windows; a same-user agent can type into it).
- **Trust boundary = the OS account** (P-H, T46) — processes of the same account, agents with a shell included, are trusted and not defended against; the docs say so plainly (as hcom / Reason Network do). The gate stops the common path — an agent talked into a trust change through our commands — not a same-account process. The cheapest same-account bypasses: read the shell token file and open the shell link with it (calls then arrive as the human caller); attach to the WebView debugging port that `scripts/run-*.bat` open (`--remote-debugging-port=9223`) and drive the app; unseal the identity key (same account) and recompute the list MAC after editing `peers.<account>.<machine>.json`. Other accounts are kept out (§4-9).

### 4-9. Other OS accounts (R21 · P-H)

- **Boundary** — the OS account (§4-8). Other Windows accounts on the same PC are blocked on the app↔daemon link; folder-wide ACLs (`agents.json` etc.) stay outside S37.
- **Token file** (T47) — the shell token lives in the owner-only `daemon-token.<account>`, split from the shared `daemon.json` lock, and the agent control files are owner-only too (§3-1); another account can read neither.
- **Accept-time account check** (T48) — the shell link and the control HTTP listener check that a connecting client's process runs under the daemon's own Windows account and refuse otherwise, before the handshake, with "this daemon belongs to another Windows account — use a separate folder per account" (Tailscale / Windows ssh-agent read the client's token). Mechanism: platform takes the TCP-table row whose local endpoint is the observed client address (IPv4 — the listeners bind 127.0.0.1), opens the owning process and reads its token's user SID, and compares it with the daemon's own. Fail closed: a lookup that cannot read the client's account refuses with its own message ("could not verify the connecting app's account — run the app and Engram the same way, both elevated or both not"). An elevated administrator is not kept out. `LinkInfo::remote` is a diagnostics string, so T48 adds a typed accessor for the observed client socket address. Transport stays policy-free (the `ws` `AcceptPolicy` holds only Origin / Host data). Feasibility over loopback TCP is confirmed in U2; if it cannot be done cleanly, the owner-only files alone ship and the gap (a copied token from another account) is documented.
- **Shell side** — another account's shell reads `daemon.json` (no token in it): a live record whose owner SID differs from its own → the other-account message, without touching the token; a stale record (dead pid) → it may start its own daemon, so taking turns works after a crash too. The three read sites: `src-tauri/src/discovery/mod.rs` `FileReader::read`, `src-tauri/src/daemon_client/link/endpoint.rs` `judge`, `src-tauri/src/daemon_client/link/stop.rs`.
- **Folder sharing** — one daemon runs per data folder (single-instance guard, ADR-0135); two accounts sharing a folder take turns, and the per-account files (§3-1) keep their identities apart.
- **Debugging port** — the WebView debugging port that `scripts/run-*.bat` open (`--remote-debugging-port=9223`) is a dev-only, unauthenticated loopback listener that any local account can reach; documented (§8, PRD §6), not changed in S37.

## 8. Risks and items for the user beyond D1–D7

- X1 — **Default listen port** (decided 2026-11-19): a fixed default UDP port, changeable in `network.port`; port busy at start = `endpoint error` shown in `peer.list`, no silent fallback (Syncthing listens on 22000 by default; Reason Network / iroh default random). Reason: a typed peer address (the fallback when mDNS is blocked) needs a stable port. The number is an internal choice made in U1; the dev build gets a different default from release (T35).
- X2 — **Where the PC list lives in the app** (decided 2026-11-19): a new slot content type (like the usage slot). It only shows `peer.list` and calls `peer.*`; all behaviour stays in the daemon. User: 「새로운 슬롯이 있어야지 … 슬롯 플러그인 개념으로 가야지 기본적으로 돌아가는건 데몬에서 다 되고 클라쪽은 정제 및 표현」 — the slot-plugin structure itself is T-116.
- X3 — **No later receipt for held mail** (decided 2026-11-19): none, as for local held mail today. A sender that needs confirmation sends a request (reply contract) and gets the reply or the overdue notice — user: 「옵션에 따라 다르지 않음? 송수신 우편 옵션일때만 보내는거잖아」.
- X4 — **Request deadlines across PCs** (decided 2026-11-19): the contract lives on the receiving PC (today's structure, no extra work); the overdue report back is best-effort (lost if the link is down at that moment); the requester's awaiting-reply view does not list remote requests. User: 「거의 사용되지 않을것 같은데」 → simplest kept.
- X5 — **Unreadable or corrupt identity key** (decided 2026-11-19): never regenerate on its own. The peer feature stops; `peer.list` and the app show that the key cannot be read and that a new key means re-pairing every PC; on a human's OK (the app button, or an agent's `peer.regenerateKey` approved through §4-8) the old file is kept as a backup and a new key is created. A transient read failure recovers on a daemon restart with the old ID. What counts as unreadable under per-account sealing: §3-1. Conventions differ: Syncthing regenerates on any load failure (`LoadOrGenerateCertificate`), Reason Network stops on a corrupt key (`load_key`). User: 「이번만 파일을 못읽는다거나 그럴 수 있는데 날려버리면 … UI 쪽에 메세지 안내하고 유저가 ok 하면 백업만들고 새로 만들면」.
- X6 — **Directory copies are in memory only** (decided 2026-11-19, user: 「메모리에만」): after A restarts while B is off, A does not know B's agents until B reconnects ("no such agent" instead of "PC offline"), and B is outside the bare-name count until then (§4-3 step 4).

### Remaining risks

- Firewall: binding UDP on all interfaces may raise the Windows Firewall prompt; whether it appears for a WMI-launched daemon is unknown — if it never appears, inbound direct paths stay blocked and only outbound / relay paths work (U5 measures).
- OS dialog from the daemon: the daemon is started detached through WMI; whether its dialog shows on the user's desktop, and where (the foreground lock can put it behind other windows), is measured in U5. If it cannot show, questions wait for the app (AC14 then needs the app open).
- Duplicate detection reach: it needs both holders of one key to link to a common PC; a clone that only talks to PCs the original never links to is not detected. A cloned VM or disk keeps the machine id, so its files load there and only this detection catches it. The relay's `SameEndpointIdConnected` would have helped but `iroh-1.4.1` only logs it (`socket/transports/relay/actor.rs` — `warn!`), so it is not used.
- Same-account processes are trusted (§4-8, T46): an agent with a shell can read the shell token file, use the WebView debugging port, or unseal the key and recompute the list MAC; rollback of an older signed list is not defended.
- WebView debugging port: `scripts/run-*.bat` open `--remote-debugging-port=9223`, a dev-only, unauthenticated loopback listener any local account can reach; documented, not changed in S37.
- An elevated administrator is not kept out by the account check (T48), and a lookup that fails refuses (a mixed elevated / non-elevated pair of app and daemon cannot connect).
- The accept-time account check (T48) may not be cleanly doable over loopback TCP; then only the owner-only token file ships and a copied token from another account still connects (documented gap).
- Sealing loss: a Windows forced password reset loses the DPAPI key, so the identity becomes unreadable and every PC must be re-paired (X5 flow). A reinstall with a new SID starts fresh silently (the old files are not this account's); a `MachineGuid` change or a reinstall with the same SID finds this account's files under another machine id and asks whether to adopt them.
- Weight: +~172 crates (plan, certain) + the mDNS crate (unmeasured) + a native-dialog crate (unmeasured); exe delta unmeasured; CI build time grows (transport `--all-features` builds iroh).
- Corporate networks blocking UDP / multicast / the relay domain; n0 public servers rate-limited (PRD §6).
- Exposure with the n0 default (`relay` / `address_lookup` = `default`): n0's DNS server holds a record from this PC's ID to its home relay (no IP address by default), and the relay sees this PC's public IP address, its ID, the IDs it talks to and the traffic timing; mail content is end-to-end encrypted and the relay cannot read it. Setting both to `none` or to the user's own servers removes n0 from the path (R10).
- Every trusted PC (and every agent there, through `peer.list`) sees this PC's agent names, ids and live / asleep state (R16). Scope = the user's own PCs (R4); nothing else about an agent is sent (§4-7).
- Name shadowing and moves: a new local agent with a remote agent's name takes over that name's bare sends on this PC without warning (§4-3 step 2); a local agent whose literal name ends in `@<a listed PC name>` cannot be reached by that literal name once that PC is listed (step 1 — reach it by id); a bare name can go to the one known PC while another PC with the same name is still unknown this run (D2 exception — write `name@pc`); mail sent between a move and the delta gets `RECIPIENT_NOT_FOUND` from the old PC and is not re-routed.
- Shells in the directory: the published set follows the adapter predicate, so a shell profile shows as `sleeping` while dormant and drops out while live; remote mail to a dormant shell name parks and expires by TTL, as local mail does today (`messaging_host.rs` known residual).
- mDNS announces the PC's ID to the whole LAN (Reason Network keeps mDNS out of its debug log for that reason).

- P16 — daemon paths are under `crates/engram-dashboard-daemon/src/` (this TRD writes `link/peer/` etc. relative to it); `ShellWire` / `DaemonWire` are not in protocol — `DaemonWire` is in the daemon's `link/wire.rs`, `ShellWire` in `src-tauri/src/daemon_client/link/wire.rs`.
