## 2. Module boundaries

```
daemon A                                               daemon B
 control ingress (MCP eg_send · /control/send)          link/peer: accept gate → per-node receive queue
   └ messaging handle_send ─ Resolution::Remote          messaging: validate · limits → handle_send(Remote, LocalOnly)
        └ RemoteDeliveryPort (non-blocking)                   ▲ verdict ◄─┐
 link/peer: Registry<PeerWire> ══ transport `iroh` (QUIC, node keys) ══ Registry<PeerWire>
   directory: publish own ─── DirSnapshot / DirDelta ──►  copy of A (read-only)
              copy of B (read-only) ◄───────────────────  publish own
 link (shell, WS loopback) — unchanged                 link (shell, WS loopback) — unchanged
```

- **transport** — new `iroh` feature module beside `ws` (opt-in, off by default). Owns everything iroh: endpoint build from plain config values (secret key bytes · relay = default | none | URL · address lookup = default | none | URL · mDNS on/off · listen port · ALPN), `Dialer` / `Listener` / `LinkTx` / `LinkRx`, framing, close-code mapping, `LinkInfo::peer_key` (raw 32 key bytes), and a policy-free accept hook `accept_if(peer_key)` the consumer fills (§4-2). ★iroh types do not leave this module★ — the daemon's manifest gets no iroh dependency, so the adapter stays replaceable (PRD §6 vendor risk). Transport takes and returns raw key bytes; the ID text format is the daemon's (T34). No relationship policy here: no trust list, no tie-break, no PeerWire (ADR-0177 decision 4).
- **daemon `link/peer/`** (new, beside the shell `link/`) — identity key file and the ID text codec, trusted-list store (`peers.json`), `PeerWire`, its own `Registry` + `Listener` (ADR-0310 D2), accept gate, per-frame membership check, dial-every-listed-peer, tie-break, online state, endpoint lifecycle (D7), per-node receive queues, the `peer.*` command table, the messaging adapters (`RemoteDeliveryPort` adapter, remote entrance caller), the agent directory (publisher of this PC's directory + one read-only copy per trusted PC — §4-7).
- **messaging** — remote branch at the single resolution point (ADR-0309 d3) that reads the directory copies from the one `AddressingSources` snapshot (it does not own or sync them), a resolve scope on `handle_send` (`ResolveScope`, §4-4), `RemoteDeliveryPort`, verdict entry (remote-pending ledger state, verdict-time reply close — §4-6), remote entrance with validation and limits, node qualifier on `SenderIdentity`, the requester's node on request entries and the overdue notice it renders for a remote contract. Still zero workspace deps (ADR-0110).
- **platform** — new owner-only private file write (Windows DACL · elsewhere mode 0600) and its check / re-apply (ADR-0266).
- **protocol** — one additive peer-state broadcast for the app (precedent `UsageSubscribe` / `UsageLimitsUpdated`); no daemon↔daemon vocabulary (§5 T6).
- **shell · frontend** — U4 only: relay the peer-state broadcast; the peers panel.
- **Untouched** — agent crate (ADR-0003), cli (the send path and its route are unchanged; the address is just a string), base (`file` used as is), the shell↔daemon link and its loopback rule, `ShellWire` / `DaemonWire`.

## 3. Data shapes

### 3-1. Persistent files (daemon state folder `<data root>\daemon\state\` — `DataLayout::daemon_state_dir`)

- **Identity key** — `peer-key` (raw 32-byte secret). Created once, on first need (first `peer.*` call or first add); the daemon never replaces it on its own — only the user-approved regenerate below writes a new one. Written owner-only through platform (temp created with the private DACL → sync → rename without replace); on every load the owner-only DACL is checked and re-applied when it is wider. The PC's ID = the public half as text in the daemon's format (T34). Unreadable (lock / IO), corrupt, or missing while `peers` is non-empty (treated as unreadable — never silently recreated) → the peer feature does not start and `peer.list` says so; never regenerate on a read failure. A new key is created only on the user's OK (`peer.regenerateKey` or the app button, §8 X5): the old file is kept as a backup by rename (so it keeps its own DACL), and the result tells the user that every other PC must remove this PC's old ID and pair again.
- **Trusted list + network settings** — `peers.json`, base `file` rules (ADR-0291: version key, cap, newer-version / unreadable = refuse to write; the feature does not start and `peer.*` writes answer `CONFLICT`). Shape:
  - `peers[]` = `{ id, name, address?, permission }` — `id` = the other PC's ID text (required, unique); `name` = display name, used as the address suffix (required, unique case-insensitively, no `@`, no whitespace; matched case-insensitively when parsing `name@pc`, §4-3); `address` = optional `ip:port` direct address; `permission` = `"mail"` (only value accepted in v1; `"control"` reserved for the shell → remote daemon stage). Room for a later group record = a sibling top-level key, not a field on entries.
  - `network` = `{ port?, relay, address_lookup, mdns }` — `port` absent = the fixed default (§8 X1; the dev build, data root `.engram-dev`, has a different default from release — T35); `relay` / `address_lookup` = `"default"` (n0) | `"none"` | a URL (Syncthing `default` keyword precedent); `mdns` = bool, default `true`.
  - Why one file: one owner (the peer module), one load/refuse rule, one writer. The daemon has no settings file today and shell settings cannot carry these — the daemon runs and links without the app (R13 · R3).

### 3-2. Link framing (transport `iroh`)

- One ALPN per relationship: `engram/peer/1` opened in v1; `engram/shell/1` reserved (not registered on the endpoint in v1). Unknown ALPN is refused by the QUIC handshake.
- One QUIC connection per link, one long-lived bi-stream opened by the dialer; the dialer writes a 1-byte preamble at once (the stream is invisible to the peer until a byte is written).
- Frame = kind byte (text · binary · keepalive) + u32 BE length + payload; max payload given by the consumer like `ws` `max_message_bytes` — PeerWire uses 512 KiB (T30: a 64 KiB body JSON-escaped at worst — every byte a control character written `\u00XX`, 6× — is 384 KiB, plus headroom for the other fields). Oversized or malformed inbound framing = close with `PROTOCOL_ERROR` (4005). The sending side checks the encoded size before sending, so its own oversized frame never closes the link (§4-3).
- Close: our `CloseCode` u16 ↔ QUIC application error code; reason truncated to an adapter-local byte cap (exact QUIC cap confirmed in U1). QUIC implicit close (code 0) → `LinkRead::Closed(None)` → read as "could not connect / going away", never a terminal rejection (`RejectKind::of` returns `None` only for 1000 · 1001 · 4000 — U1 maps 0 explicitly). The final `Reject{last}` frame is best-effort diagnostics; correctness never depends on it.
- `ping()` sends a real keepalive frame (QUIC has no auto-pong); the transport supervisor's ping/idle stays the liveness rule.
- Accept: QUIC accept → the consumer's `accept_if(peer_key)` predicate (before `accept_bi`; `false` closes the connection with `HANDSHAKE_REJECTED`, §4-2) → ALPN + bi-stream accept under a stream-accept timeout (value set in U1) → a ready queue bounded by a `PermitPool` (same shape as `WsListener`), so `Listener::accept` stays cancel-safe and neither unlisted nor silent dialers hold accept permits. `Accepted.info.peer_key` = the authenticated 32-byte endpoint id; `remote` = the observed socket address (diagnostics only).
- Dial target = the remote's raw 32-byte key + optional direct socket addresses; the daemon parses the `<id>` / `<id>@<ip:port>` text (T34). iroh verifies the remote key against the id on dial. The dialer never uses 0-RTT (`into_0rtt` forbidden: 0-RTT data is replayable, and a replayed `Mail` would be delivered twice).
- iroh build: `default-features = false` + `tls-ring` (no `portmapper`, no metrics). Presets: `N0` when relay and lookup are both `default`; otherwise `Minimal` + custom relay map / pkarr + DNS lookup / none. Typed peer addresses go in as direct addresses (memory lookup). Fixed port = `bind_addr` on `0.0.0.0:<port>` (+ `[::]:<port>`). mDNS = the separate crate `iroh-mdns-address-lookup` (§9 P3).

### 3-3. PeerWire vocabulary (daemon `link/peer/`, JSON text frames)

| Message | Direction | Fields (boundary level) |
|---|---|---|
| `Hello` | both (dialer first; acceptor answers after `Done`, the shell-link pattern) | `protocol_version` — no node field; the node is the link key |
| `Mail` | request (tag = mail id) | `id` · `from {agent_id, name}` (no node — stamped from the link; `name` is the sending daemon's claim) · `to[]` (agent names/ids on the receiver, ≤ 64) · `body` · `reply_to?` · `request {reply_by_raw}?` |
| `MailVerdict` | reply to `Mail` | `id` · rows `[{to, outcome, recipient_id?, code?, reason?}]`; outcome = `delivered` \| `held` \| `refused` \| `unknown_recipient`; `code` from a closed set (below); `reason` ≤ 512 bytes |
| `ReplyOverdue` | push, contract holder → the requester's node | `request_id` (the request mail id) — no text; the requester's daemon renders its own notice (§4-6) |
| `DirSnapshot` | push, each side right after the handshake; also the answer to `DirResync` | `run` · `rev` · `part` · `last` · `agents[{id, name, state}]` — the sender's whole directory, in parts when it exceeds the frame cap; `state` = `live` \| `sleeping` (the `agent.list` words) |
| `DirDelta` | push, owner → each linked PC | `run` · `rev` (= previous `rev` + 1) · `upsert[{id, name, state}]` · `remove[id]` |
| `DirResync` | push, copy holder → owner | — (asks for a fresh `DirSnapshot`) |
| keepalive | both | `Frame::Keepalive` (never reaches `Wire::decode`) |

- One `Mail` per (send, remote PC) carries that PC's recipients; one verdict answers it. `to[]` holds the bare name (or the id) — the sender strips `@pc`.
- Directory frames carry no node field: whose directory it is = the link's key, so a PC can only write its own copy (R16, as R8 for mail). They carry nothing else about an agent (no cwd, parent, backend, repo, branch, activity). `run` / `rev` ordering and row validation: §4-7.
- Version: equal `protocol_version` required; mismatch = `Reject{Terminal}` with "version mismatch" (shown in peer state; redial re-armed on daemon start and on `peer.add`).
- Decode failure = drop the frame + log (`DecodeFailurePolicy::DropFrame`); a frame naming a non-`mail` permission action does not exist in the vocabulary (R9 by construction). There is no peer-written notice: the old `Mail{kind: notice}` is gone (T28).
- `held` = the receiver's local `SendStatus::Pending` (parked: recipient asleep, or live but the drain could not inject — busy; in memory, 24 h TTL, mailbox cap 100). Closed `code` set = `REMOTE_LIMIT` (§4-5, the body cap included) · the receiver's own row codes (`RECIPIENT_AMBIGUOUS` · `MAILBOX_FULL` · `REQUEST_CAPACITY`) · `REMOTE_REFUSED` (permission · id collision · validation failure, §4-4). The sender maps any code outside the set to `REMOTE_REFUSED`, and shows a peer's `reason` (truncated to the cap) labelled with the origin PC.

### 3-4. Sender-side result mapping (what the sending agent sees — R6)

| Result | `SendStatus` | code / hint |
|---|---|---|
| delivered | `delivered` | — |
| held | `pending` | hint: held on `<pc>`, recipient asleep or busy |
| refused | `failed` | the relayed code (closed set, §3-3) or `REMOTE_LIMIT` / `REMOTE_REFUSED` + the peer's reason labelled with the PC |
| unknown recipient | `failed` | `RECIPIENT_NOT_FOUND` — from the receiver: hint names the PC (a stale copy ends here too); not found anywhere: the existing local hint, plus the listed PCs whose directory is unknown this run (§4-7) |
| not delivered (no live link — also a bare name found only in a disconnected PC's copy; or the link dropped before the mail was handed to it, `RequestError::Disconnected{sent: false}`) | `failed` | new `PEER_OFFLINE` (hint names the PC). A PC in state `refused` gets its own hint: that PC does not list this PC's ID — add it there (not "offline"); `version mismatch` likewise names the cause |
| ambiguous across PCs (bare name, not local, in 2+ PCs' copies; or an id listed by 2+ copies) | `failed` | `RECIPIENT_AMBIGUOUS`; hint lists the candidates `name@<pc>` (sorted) and says to resend with one — the local hint today gives only a count (`ambiguous_hint`); the cross-PC one adds candidates (`llm-command-conventions.md` §1-3) |
| unconfirmed (no verdict within the agent-facing wait, 7 s — T24; or the link dropped after the mail was handed to it, `Disconnected{sent: true}`) | `pending` | hint: unconfirmed — may or may not have arrived; do not resend blindly |

- Keeps the three-word status vocabulary (spec §6); new codes = `PEER_OFFLINE` · `REMOTE_LIMIT` · `REMOTE_REFUSED`. `BODY_TOO_LARGE` (today an entrance bounce) also appears as a row code when that PC's encoded `Mail` frame would exceed the cap (§4-3).
- Late verdicts (T23): the PeerWire `Mail` request has its own transport deadline, 120 s, separate from the 7 s agent-facing wait, because transport drops a reply that arrives after its request's deadline (`peer.rs` `route`, ADR-0181 d4). The deadline is the PeerWire registry's `Policy::request_timeout` (one value per registry, ADR-0181 d1; `Mail` is PeerWire's only request). A verdict that arrives after the agent was answered still updates the ledger row (visible in `eg_messages`) and the sender gets one daemon `<notice>` with the final outcome. Past the 120 s deadline, or when the link drops after sending, the row stays unconfirmed and the notice says the outcome is unknown. The notice goes through the existing notice lane, injected at the idle gate like the reply-deadline notice (ADR-0104) — user 2026-11-19: 「일단은 그냥 가자. 지금처럼」; turning such notices into deferred inputs that ride the next input without a turn is T-115. v1 sends no later receipt when held mail is finally injected (§8 X3).

## 4. Flows and concurrency

### 4-1. Endpoint lifecycle (D7 · R13)
The peer module starts the iroh endpoint only while `peers` is non-empty: at boot if the list has entries, on the first `peer.add`; it stops it (closing all links) when the last entry is removed. Creating the key file contacts nothing. `peer.setNetwork` restarts a running endpoint (directory copies are kept `disconnected` across it, §4-7). `peer.add` / `peer.setNetwork` finish on the handler's first poll: they write `peers.json` and hand the change to the peer module; endpoint start and link results show in `peer.list` (T32).

### 4-2. Links (R3 · R4)
- Dial: every listed peer gets a dialing `Registry::add` handle — reconnect without limit (`max_attempts = u32::MAX`, the shell precedent ADR-0346), backoff capped at 60 s and connect timeout 20 s (Reason Network `net.rs` 2→60 s · 20 s). A PC does not dial a node it already has a live link to.
- Accept gate: the daemon fills the adapter's `accept_if(peer_key)` predicate, called before `accept_bi` (Reason Network gates before `accept_bi`). Not listed (or permission ≠ `mail`) → the connection is closed with `HANDSHAKE_REJECTED` and the reason "not paired": no stream is accepted and no frame is read (R4); the dialer reads the code as `Terminal` (`RejectKind::of`) and gives up without spending budget. The refusal is logged with the key's ID text, throttled like the shell link's `AcceptRefusal` log (per-kind time-window batches — ADR-0310 D9; repeated identical failures throttled — ADR-0346 d5). Listed → bi-stream accept → attach with the PeerWire handshake. `Registry::attach` drops `LinkInfo`, so the peer module keeps `link label → node id` in its own per-link state.
- Tie-break without churn (T17): two live links for one node happen only when both PCs dial at once. When the second comes up within 5 s of the first (Reason Network `DIALED_TOGETHER`), keep the one dialed by the smaller ID and close the other with `GOING_AWAY`; outside that window the newer link replaces the older one (the older may be stale after an abrupt restart of the other side). Directory frames go on the chosen link only.
- Re-arm: a dial that ended in a terminal refusal is re-armed on: an accepted link from that node ending, `peer.add`, daemon start, and a slow retry every 10 min for a "not paired" refusal (a one-sided setup — the other PC adds this one later; Syncthing keeps redialing unknown devices) (T33).
- Online state per PC = `online` (≥1 live link) · `offline` · `refused` (terminal refusal from the other side) · `version mismatch` · `endpoint error` (e.g. port in use).
- Removal (`peer.remove`, T29): revoke in memory first — the gate and the per-frame check see it at once — close that node's handles and inboxes with `HANDSHAKE_REJECTED`, drop its copy, then save `peers.json`; a refused save is reported in the answer and the revocation stays for this run (R4 · AC7 ≤ 1 s).
- Per-frame membership: every inbound frame is checked against the current list (Reason Network `on_wire` re-checks membership); a frame from a node that is no longer listed is dropped and that node's handles / inboxes are closed.
- Transport receiver invariants hold: the inbox-draining task never awaits `request` (sends run on spawned tasks); every inbox is drained to `None`.

### 4-3. Send (A side)
`handle_send` resolves each token once from one snapshot (`AddressingSources` = local roster + dormant + listed PCs + the directory copies, §4-6 · §4-7). `resolve_token` order (ADR-0309 d3 — 「여기 없으면 다른 데몬으로」; D2):
1. **`name@pc`** — the text after the last `@` matches a listed PC name (case-insensitive, like PC-name uniqueness) → `Resolution::Remote{node, name}` for that PC only. The explicit form wins over a local agent whose literal name is the whole token (R17 precedence, T8). The copy is not consulted: the receiver answers authoritatively (`unknown_recipient` → `RECIPIENT_NOT_FOUND`), and a disconnected PC gives `PEER_OFFLINE`.
2. **Local, unchanged** — id (live → asleep), then exact name (live layer, then asleep layer), with today's local `RECIPIENT_AMBIGUOUS`. Anything found locally ends here: a local agent always wins over a remote one of the same name (R5).
3. **id** (UUID-shaped, not local) → the copy that lists that id (ids are unique across PCs — ADR-0309) → `Remote`; listed by 2+ copies → `Resolution::Ambiguous` with the candidates `name@<pc>` (§4-7).
4. **Bare name** (not local) → exact, case-sensitive match against every copy, connected or disconnected, live or asleep, counted per PC: one PC → `Remote{node, name}` (that PC resolves its own duplicates and layers); two or more PCs → `Resolution::Ambiguous` across PCs with candidates `name@<pc>` (§3-4); none → `NotFound`. Disconnected copies count in the ambiguity check, so a PC going off never makes the same rule switch to another PC silently.
5. A chosen PC with no live link → immediate `PEER_OFFLINE` (below).

`@all` / `@here` never expand to remote agents (v1, local only). A remote row is recorded in the ledger in the remote-pending state (`to` = the notation, `to_id` = none until the verdict) without opening a contract (§4-6), then handed to `RemoteDeliveryPort::enqueue` — non-blocking, called outside the messaging lock (same discipline as `DeliveryPort`). The daemon adapter: no live link → immediate `PEER_OFFLINE` verdict; encoded `Mail` frame over the cap (§3-2) → that PC's rows `failed` with `BODY_TOO_LARGE`, nothing sent; else a PeerWire request on a spawned task under the 120 s transport deadline; verdict, `Disconnected` or deadline → the kernel's verdict entry transitions the row (§3-4 mapping). The control entrance answers the agent once every remote row has a verdict or the 7 s agent-facing wait has passed (AC6) — rows still without a verdict are reported unconfirmed, the transport request stays pending, and a later verdict goes through the verdict entry (ledger + one notice, §3-4). Local rows are unaffected by the wait.

### 4-4. Receive (B side)
Peer inbox → per-frame membership check (§4-2) → decode `Mail` → that node's serial receive queue (one per node, run off the inbox task because `handle_send` injects through the blocking `DeliveryPort::inject`; per-node order kept) → messaging remote entrance with the link's node:
1. **Validation like ingress** (T27) — the checks control ingress makes today: `validate_contract` (request and `reply_to` exclusive, `reply_by` only with a request and within its range, non-empty `reply_to`), single-recipient reply (`reply_to_has_single_recipient`), non-empty `to`, the envelope-format check against the receiver's own format (`contract_unsupported_by_envelope`); plus `to[]` ≤ 64 entries, `@all` / `@here` tokens refused, `from.name` non-empty, ≤ 128 bytes (`Roster::MAX_NAME_BYTES` precedent) and free of control characters, `from.agent_id` not the nil id. A failure refuses the whole frame with `REMOTE_REFUSED` and the reason.
2. **R8** — `from.agent_id` must not be a local agent id, where "local" = the full manager roster (every profile, live shells included), not the mail-eligible `AddressingSources` set; no node claim exists in the frame.
3. **Limits** (§4-5), then `handle_send` with `Entrance::Remote` and `ResolveScope::LocalOnly`. `SenderIdentity` stays `{peer_id, epoch}` and gains `node` = the link's node; the display `"<name>@<B's name for that PC>"` goes in as `handle_send`'s `sender_name` (the envelope shows the address the recipient replies to — R7). The link authenticates the PC; the agent name is the sending daemon's claim.
4. Per-row results → `MailVerdict`.

`Entrance` stays a log label (pipeline does not branch on it). ★Remote mail is resolved on local agents only — no forwarding to a third PC★: `handle_send` takes its own snapshot (`port.addressing_sources()`), so the caller cannot hand it an emptied one; the named seam is a `ResolveScope` argument (`All` for ingress, `LocalOnly` for the remote entrance) under which the listed PCs and the directory copies are ignored — steps 1, 3 and 4 of §4-3 cannot match, and a name the receiver does not have is `unknown_recipient`.

### 4-5. Limits (D5 · R9)
At the receiving side's resolution point (messaging remote entrance — policy in the lib, ADR-0110): per PC 60 mails/min (whole frame refused), per (remote agent, local recipient) pair 12 per 10 min (that row refused), body 64 KiB (same value as the local `MAX_BODY_BYTES` in `control/ingress.rs`; the sender already caps with `BODY_TOO_LARGE`, the receiver re-checks). Hit = `refused` + `REMOTE_LIMIT` with the limit as reason (AC10) — an oversized body included (one code for it, §3-3). Counters are in memory, clock injected (`now: Instant`).

### 4-6. Ledger identity (boundary decision)
- Keys stay agent UUIDs — no node in any key. Rests on ADR-0309's 「an id must be unique across servers」 (fresh UUID v4 per profile); a remote frame reusing a local agent id is refused (R8).
- The node is a display/routing qualifier: `SenderIdentity` (`{peer_id, epoch}`) gains `node: Option<NodeRef>`; `NodeRef` = a messaging-local opaque fixed 32-byte value (the node key; the ID text is rendered from it) — not a uuid alias (§9 P2). `AddressingSources` gains the listed PCs `(NodeRef, name, connected)` and the directory copies (rows `(NodeRef, id, name, state)`) so resolution stays one snapshot; the daemon adapter (`messaging_host.rs` `ManagerDeliveryPort::addressing_sources`, which today builds both local lists from one `manager.roster()` call) fills them from the peer module in the same call — a third physical lookup beside the session snapshot and the profile list (ADR-0116), read under the peer module's own lock, never under the messaging lock.
- Sender-side rows (T26): remote rows are recorded without a recipient id and get their outcome later, so the ledger gains a remote-pending state whose transitions to delivered / held / failed are applied only by the verdict entry, picking the row by mail id + its `to` token. Today the only edge into `Failed` is deletion cleanup's `Pending → Failed` (`can_fail_by_cleanup`), and a remote-held row cannot be local `Pending`, which the expiry sweep and the wake flush act on. Exact states: the ADR (U0 ⑥).
- Reply contracts live on the **receiving** daemon: `handle_send` there opens the contract for its recipient and the recipient's reply closes it there (closing is replier-side today). The sending daemon opens none for remote rows. The remote entrance stores the requester's node (from the link) on the request entry. A reply that goes to a remote requester closes the local contract at verdict time with ADR-0116 d2's rule: delivered or held → replied; `RECIPIENT_NOT_FOUND` → reply_failed; any other outcome → stays open (as `reply_disposition` `NoOp`). The requester's own "awaiting reply" view does not list remote requests in v1 (§8 X4).
- Overdue (T28): the receiving daemon sends `ReplyOverdue{request_id}` to the node recorded at request time (never by resolving the requester id), best-effort (lost if the link is down); the requester's daemon renders its own overdue notice from its template, naming the origin PC. No peer chooses notice text.
- Mail ids are unique per daemon only; a remote id that collides in the receiver's ledger → `REMOTE_REFUSED` (probability as for local collisions).
- Size: `SenderIdentity` + `MessageRecord` (optional node) + `AddressingSources` (PCs + copies) + one resolution variant + a cross-PC ambiguity hint + one port + verdict entry + the remote-pending ledger state and its verdict-time transitions + the verdict-time reply close + the requester's node on request entries + the `ReplyOverdue` notice render + the `ResolveScope` argument on `handle_send` + remote entrance (validation) + limiter. `SenderIdentity` is `Copy` and passed by value (~60 uses in messaging and the daemon): `NodeRef` is a fixed 32-byte value so `Copy` survives (the ID text is rendered from it); a `String` would drop `Copy` and ripple through `handle_send`, `daemon_identity` and the daemon's `From<BoundIdentity>` (§9 P15). No key migration (mailbox and ledger are not persisted).

### 4-7. Agent directory sync (D2 · R16 · R17 · R18)

- **What is published** — this PC's directory = the same set local name resolution sees, by the adapter's own predicate (`ManagerDeliveryPort::addressing_sources`): live agents that read mail (a live shell is left out) and every dormant profile (a dormant shell is listed). Each row = `id`, `name`, `state` (`live` | `sleeping`). Nothing else leaves the PC (no cwd, parent, backend, repo, branch, activity).
- **Owner-only writes** — each PC is the only writer of its own directory. A copy changes only through `Dir*` frames on that PC's authenticated, chosen link (§4-2); frames carry no node, so no PC can write another PC's copy. Copies are never re-published: each PC sends only its own agents (no transitive gossip, no forwarding through a third PC).
- **Row checks on arrival** — a row whose id is a local agent id (the full manager roster) is dropped and logged; a row whose name is empty, over 128 bytes or holds control characters is dropped and logged (local names are cwd basenames and may hold spaces or `@`, so no stricter charset). An id already listed by another PC's copy is kept in both and logged; a send to that id is refused as ambiguous with the candidates (§4-3 step 3) — dropping one would make the winner depend on which link came up first.
- **Lifecycle with links** — after the PeerWire handshake each side sends a `DirSnapshot`; it replaces the whole copy and marks it `connected`. While the link is up, the owner sends `DirDelta`s. When the PC's last live link ends, its copy is kept and marked `disconnected` (names still resolve → `PEER_OFFLINE`, R17). The next link's snapshot replaces it. A link replaced or closed by the tie-break changes nothing (the copy follows the node, not the link). A `peer.setNetwork` restart closes the links like any drop: copies are kept `disconnected` until the next snapshots.
- **When a copy is dropped** — on `peer.remove` of that PC (together with the entry and its links), and when the endpoint stops because the last entry was removed. Copies live in memory only: after a daemon restart a PC has no copy (`unknown`) until it links again (§8 X6).
- **Triggers, no timer** — the publisher recomputes its directory on every roster-composition change (create · delete · rename) — both the command path (`RosterChanged` / `control::agent::RosterBroadcast`, bus and CLI `agent.*`) and the shell WS path (`connection_core.rs` profile messages, which call `broadcast_profile_list` directly and bypass `RosterChanged` — §9 P14); U3b hooks one point both pass — and on live ↔ asleep transitions (session start / exit; exact hook confirmed in U3b — composition notices alone miss wake and exit, `RosterChanged` doc: 「waking does not change composition」). It diffs against the last published directory, coalesces bursts (~250 ms) and sends one `DirDelta` per linked PC; no change = no frame. No periodic re-send (Reason Network's `presence_loop` checks every 2 s and re-sends every 60 s — not copied: the link is one ordered stream, so a snapshot per link plus deltas cannot drift).
- **Ordering and staleness** — a `connected` copy lags by at most the delta in flight; a `disconnected` copy is as of the link drop. Mail routed by a stale entry gets the receiver's authoritative answer (`RECIPIENT_NOT_FOUND` naming the PC); the sender is not re-routed automatically. `rev` counts per publisher run, and every snapshot / delta carries the run identity (`run`, a random value drawn when the publisher starts). A delta applies only when its `run` equals the copy's and its `rev` = copy `rev` + 1; otherwise the holder keeps using the copy and sends `DirResync`, and the answering snapshot replaces it. A snapshot of the copy's own run with a `rev` below the copy's is ignored, so an old snapshot cannot replace a newer copy; a snapshot of another run replaces the copy (the publisher restarted). A multi-part snapshot replaces the copy only when its `last` part arrives.
- **Limits** — no entry cap: a directory larger than one frame goes as a multi-part snapshot (§3-3), so a copy is always complete (R16); memory = entries × PCs, all from the user's own PCs. Directory frames do not count against the mail limits (§4-5).
- **LLM listing (R18)** — `peer.list` (U2's area query, T18) gains per PC `directory` = `connected` | `disconnected` | `unknown` and `agents[{name, id, state}]` sorted by name; its filter arguments pick one PC or leave the agent rows out (`llm-command-conventions.md` §2-2). `agent.list` stays local: it lives in the agent crate, which knows no peers (ADR-0003), and its rows carry cwd / parent that are not replicated. `prompts/engram-help.md` says so on both lines.
- **Cost** — three directory messages, a publisher (recompute + diff + coalesce + parts), a copy store keyed by node, one `AddressingSources` field, the `peer.list` rows. Traffic = one snapshot per link-up + one small delta per change per linked PC; zero while idle. Memory = entries × PCs.

## 8. Risks and items for the user beyond D1–D7

- X1 — **Default listen port** (decided 2026-11-19): a fixed default UDP port, changeable in `network.port`; port busy at start = `endpoint error` shown in `peer.list`, no silent fallback (Syncthing listens on 22000 by default; Reason Network / iroh default random). Reason: a typed peer address (the fallback when mDNS is blocked) needs a stable port. The number is an internal choice made in U1; the dev build gets a different default from release (T35).
- X2 — **Where the PC list lives in the app** (decided 2026-11-19): a new slot content type (like the usage slot). It only shows `peer.list` and calls `peer.*`; all behaviour stays in the daemon. User: 「새로운 슬롯이 있어야지 … 슬롯 플러그인 개념으로 가야지 기본적으로 돌아가는건 데몬에서 다 되고 클라쪽은 정제 및 표현」 — the slot-plugin structure itself is T-116.
- X3 — **No later receipt for held mail** (decided 2026-11-19): none, as for local held mail today. A sender that needs confirmation sends a request (reply contract) and gets the reply or the overdue notice — user: 「옵션에 따라 다르지 않음? 송수신 우편 옵션일때만 보내는거잖아」.
- X4 — **Request deadlines across PCs** (decided 2026-11-19): the contract lives on the receiving PC (today's structure, no extra work); the overdue report back is best-effort (lost if the link is down at that moment); the requester's awaiting-reply view does not list remote requests. User: 「거의 사용되지 않을것 같은데」 → simplest kept.
- X5 — **Unreadable or corrupt identity key** (decided 2026-11-19): never regenerate on its own. The peer feature stops; `peer.list` and the app show that the key cannot be read and that a new key means re-pairing every PC; on the user's OK (app button or an LLM command) the old file is kept as a backup and a new key is created. A transient read failure recovers on a daemon restart with the old ID. Conventions differ: Syncthing regenerates on any load failure (`LoadOrGenerateCertificate`), Reason Network stops on a corrupt key (`load_key`). User: 「이번만 파일을 못읽는다거나 그럴 수 있는데 날려버리면 … UI 쪽에 메세지 안내하고 유저가 ok 하면 백업만들고 새로 만들면」.
- X6 — **Directory copies are in memory only** (decided 2026-11-19, user: 「메모리에만」): after A restarts while B is off, A does not know B's agents until B reconnects ("no such agent" instead of "PC offline").
- Firewall: binding UDP on all interfaces may raise the Windows Firewall prompt; whether it appears for a WMI-launched daemon is unknown — if it never appears, inbound direct paths stay blocked and only outbound / relay paths work (U5 measures).
- Weight: +~172 crates (plan, certain) + the mDNS crate (unmeasured); exe delta unmeasured; CI build time grows (transport `--all-features` builds iroh).
- Corporate networks blocking UDP / multicast / the relay domain; n0 public servers rate-limited (PRD §6).
- Exposure with the n0 default (`relay` / `address_lookup` = `default`): n0's DNS server holds a record from this PC's ID to its home relay (no IP address by default), and the relay sees this PC's public IP address, its ID, the IDs it talks to and the traffic timing; mail content is end-to-end encrypted and the relay cannot read it. Setting both to `none` or to the user's own servers removes n0 from the path (R10).
- Every trusted PC (and every agent there, through `peer.list`) sees this PC's agent names, ids and live / asleep state (R16). Scope = the user's own PCs (R4); nothing else about an agent is sent (§4-7).
- Name shadowing and moves: a new local agent with a remote agent's name takes over that name's bare sends on this PC without warning (§4-3 step 2); a local agent whose literal name ends in `@<a listed PC name>` cannot be reached by that literal name once that PC is listed (step 1 — reach it by id); mail sent between a move and the delta gets `RECIPIENT_NOT_FOUND` from the old PC and is not re-routed.
- Shells in the directory: the published set follows the adapter predicate, so a shell profile shows as `sleeping` while dormant and drops out while live; remote mail to a dormant shell name parks and expires by TTL, as local mail does today (`messaging_host.rs` known residual).
- mDNS announces the PC's ID to the whole LAN (Reason Network keeps mDNS out of its debug log for that reason).

### Open — waiting for the user (review 2026-11-19)

- P-A — **Portable folder copy clones identity** — DECIDED 2026-11-20 (user: 「ㅇㅇ A+B로 가」, same as Claude's recommendation; not yet folded into §3-1 / §5 / U2): (A) seal the key with the OS secret store behind one platform function — Windows: DPAPI `CryptProtectData` CurrentUser scope called directly (not Credential Manager: the `keyring` Windows store roams by default), blob stays in `data/peer-key`; macOS: Keychain; Linux: owner-only 0600 file (Secret Service is often absent on servers, keyutils does not persist). A copy (other PC or other Windows account) cannot unseal → "key unreadable — may come from another PC or account; a new key means re-pairing" → X5 flow. (B) duplicate detection on every OS for what A cannot stop (roaming domain profiles, Linux): relay `SameEndpointIdConnected` status, our own ID offered to `peer.add`, a peer presenting our own key → warning in `peer.list` and the app with the regenerate action. Precedents: Tailscale (TPM sealing "to make node cloning more difficult" + server-side duplicate node key badge), Chromium (DPAPI-wrapped key, copied profile cannot decrypt), Syncthing / Reason Network (plain file, self-connection dropped silently / no detection). Agent-id duplicates on copy stay a separate later item.
- P-B0 — **Bare name on several PCs** — DECIDED 2026-11-20 (user 「ㅇㅇ 그렇게 하면 될듯?」, same as Claude's recommendation): keep T8 — refuse `RECIPIENT_AMBIGUOUS` with `name@pc` candidates; users write bare names normally and add `@pc` only when refused. An explicit fan-out form `name@*` is wanted but deferred to T-117 (timing left to Claude). Precedents: Reason Network `pick`, hcom, ADR-0101 refuse; none fans out implicitly.
- P-B — **A PC whose directory is `unknown` is outside the ambiguity check**, so a bare name can silently go to another PC. Options: (a) refuse a non-local bare name while any listed PC is `unknown`; (b) keep and amend D2; (c) persist copies (reverses X6).
- P-C — **Trust-changing commands callable by any local agent** (`peer.add`, `peer.setNetwork`, `peer.regenerateKey`). Options: user confirmation in the app; screen-only; accept and record the risk. X5's "or an LLM command" depends on this; the regenerate command / button / tests are in T18 / U2 / U4 marked "LLM access per P-C".
- P-D — **Other OS users on the same PC** (ADR-0310 decision 7 / D26 deferred to this stage): which of `peers.json`, daemon settings, folder ACL S37 takes.
- P-E — **Editing a trusted PC's display name / address** (R2 has add / list / remove only).
- P-F — **AC6 after an abrupt peer death**: A shows the peer online until the idle cut (crate default ping 20 s / idle 50 s) and returns unconfirmed. Options: AC6 applies after A observes the PC offline; and/or explicit shorter ping / idle for the peer link.
- P-G — **D5 behaviour**: Reason Network defers mail past 60/min per machine; D5 / AC10 refuse it.

## 9. Plan vs code

- P1 — `DaemonId` / `Hello.daemon_id` (ADR-0310 D3, trd-3 3-3 U7) do not exist in code; the revising ADR replaces an unbuilt decision, nothing to migrate.
- P2 — plan's messaging `NodeId = uuid::Uuid`-style alias does not fit: the node identity is a 32-byte key → opaque `NodeRef`.
- P3 — mDNS is not an iroh 1.4.1 feature (features: `metrics` · `fast-apple-datapath` · `portmapper` · `tls-ring` · `tls-aws-lc-rs` · …); it is the separate crate `iroh-mdns-address-lookup` (Reason Network: 0.6 with iroh 1.4), not in the local registry.
- P4 — "remote mail in the existing mail UI": there is no mail UI in `src/`; mail is visible only as envelope text injected into the agent's slot.
- P5 — architecture.md 「`mail.*` = daemon」: no `mail.*` bus commands exist (mail goes through MCP `eg_send` and `/control/send`); the daemon declares no commands today (`control/commands.rs` head), so `peer.*` is the first daemon-declared table.
- P6 — no daemon settings file exists; port / helper URLs get a daemon-owned place (§3-1).
- P7 — platform has no owner-only ACL helper; T20 adds one.
- P8 — plan put tie-break tests in U1; tie-break is daemon policy (T17), U1 only proves two concurrent links stay distinct.
- P9 — plan's protocol `peer` vocabulary (from ADR-0310 D5) → daemon-owned PeerWire (T6).
- P10 — the 64 KiB body cap already exists locally (`control/ingress.rs` `MAX_BODY_BYTES`); remote reuses the value.
- P11 — plan's `peer.my_id` / `peer.status` → folded into `peer.list` (T18).
- P12 — the local `RECIPIENT_AMBIGUOUS` hint (`service.rs` `ambiguous_hint`) carries a count and "tell the user", not candidates; the cross-PC hint adds `name@pc` candidates because, unlike local duplicates, the sender can fix it in one resend.
- P13 — the roster-composition notice (`RosterChanged`) does not fire on wake / exit; the directory publisher needs a second trigger for live ↔ asleep (§4-7).
- P14 — `RosterChanged` fires only for command-table verbs (bus / CLI `agent.*`); profile changes made in the app over WS (`CreateProfile` · `DeleteProfile` · `RenameProfile` · `SpawnProfile` · `ReparentProfile` · …) go through `connection_core.rs` `broadcast_profile_list` and bypass it, so the directory publisher cannot hang on `RosterChanged` alone (§4-7).
- P15 — `SenderIdentity` derives `Copy` and is passed by value; a string `NodeRef` would drop it, so `NodeRef` is a fixed 32-byte value (§4-6 size).
- P16 — daemon paths are under `crates/engram-dashboard-daemon/src/` (this TRD writes `link/peer/` etc. relative to it); `ShellWire` / `DaemonWire` are not in protocol — `DaemonWire` is in the daemon's `link/wire.rs`, `ShellWire` in `src-tauri/src/daemon_client/link/wire.rs`.
