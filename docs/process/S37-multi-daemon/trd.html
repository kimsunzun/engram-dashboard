S37 기술 설계 — 내 PC끼리 에이전트 우편 (데몬 ⇄ 데몬, iroh)

각 PC의 데몬이 iroh로 서로 직접 연결해서, 한 PC의 에이전트가 다른 PC의 에이전트에게 우편을 보내고 답을 받는다. 앱 ⇄ 데몬 연결과 로컬 우편은 그대로 두고, 데몬 사이에 연결 하나를 새로 놓는 설계다.

S37 = 이 작업의 번호. U0–U5 = 구현 단위(7절). T-120 같은 번호 = 다음으로 미룬 작업의 추적 번호(8절). 데몬 = PC마다 하나 떠서 에이전트를 돌리는 백그라운드 프로세스. 앱 = 그 데몬에 붙는 창(shell + webview).

1무엇이 가능해지나

예: 집 PC의 Claude가 회사 PC의 Codex에게 「회사 PC에 있는 브랜치를 리뷰해 줘」라고 우편을 보내고, 리뷰 결과를 우편으로 받는다. 지금은 우편이 데몬 경계에서 멈춰서(로컬에 없는 이름 = RECIPIENT_NOT_FOUND) 사람이 PC 사이에 글을 옮겨야 한다.

  • 외부 계정·별도 설치 없음 — 연결·암호화·상대 인증은 데몬 안의 라이브러리(iroh)가 맡고, Engram은 「누구를 믿나」와 「무엇을 보내나」만 정한다.
  • 에이전트는 이름으로 부른다 — PC마다 다른 PC의 에이전트 목록 복사본을 들고 있어서, 맨 이름(reviewer)이 그 에이전트가 있는 PC로 간다. 특정 PC를 고르려면 reviewer@office.
  • 우편만 오간다. 다른 PC의 데몬을 앱으로 조종하는 것은 나중 단계이고, 같은 연결 위에 구조 변경 없이 얹는다.

2전체 구조

두 종류의 연결. PC 안의 앱 ⇄ 데몬은 지금처럼 127.0.0.1(loopback, PC 밖으로 안 나가는 주소)의 WebSocket이다. 바뀌는 것은 「접속한 앱이 데몬과 같은 Windows 계정인가」를 확인해서 아니면 거절하는 것 하나, 그리고 토큰이 공용 파일 daemon.json에서 계정별 파일로 옮겨 가는 것이다. PC 사이의 데몬 ⇄ 데몬은 새로 생기는 iroh 연결이다.

iroh를 게임 P2P에 대 보면. NAT 뒤에 있는 두 PC가 hole punch로 직접 연결을 시도하고, 안 되면 relay 서버가 중계한다 — 온라인 게임 P2P 세션의 punch-through + relay와 같은 역할이다. 다른 점: 상대를 IP 주소가 아니라 상대의 공개 키(= 그 PC의 ID)로 부르고, 연결 자체가 그 키로 인증·암호화된다. 직접 경로와 relay 경로를 함께 시도하고 직접 경로가 되면 직접으로 간다. 같은 LAN에서는 mDNS로 서로를 찾는다(기본 켜짐). 도우미 서버는 기본이 n0의 무료 공개 서버이고, 설정에서 내 서버 URL이나 none으로 바꿀 수 있다.

5흐름 두 개

5-1. 짝짓기 (pairing) — 에이전트가 요청하고 사람이 승인

신뢰는 쌍방이다. 두 PC가 각자 상대의 ID를 목록에 넣어야 연결된다(주소 ip:port는 선택). 사람이 앱에서 직접 추가하면 바로 적용되고, 에이전트가 peer.add를 부르면 요청만 남고 사람의 OK를 기다린다.

  • PC의 ID = 그 계정의 신원 키(32바이트 비밀키)의 공개 절반을 글자로 쓴 것. 키는 처음 필요할 때(첫 peer.* 호출 · 첫 추가) 한 번 만들고, 데몬이 스스로 바꾸지 않는다.
  • 목록에서 빼기(peer.remove)는 신뢰를 좁히므로 에이전트도 할 수 있고, 메모리에서 먼저 끊은 뒤 파일에 저장한다 — 저장이 실패해도 이번 실행 동안은 끊긴 상태다.
  • 연결된 동안 각 PC는 자기 에이전트 목록(id · 이름 · live/sleeping)만 보내고, 바뀔 때마다 DirDelta로 갱신한다. 주기적 재전송은 없다. 복사본은 메모리에만 있고, 연결이 끊겨도 disconnected로 남는다.

5-2. 우편 한 통 — 집의 a가 회사의 b에게

주소 풀기 순서 (보내는 쪽, 토큰마다 한 번):

  • 이름@pc — @ 뒤가 목록의 PC 이름(대소문자 무시)이면 그 PC로만. 같은 글자 이름의 로컬 에이전트보다 우선한다.
  • 로컬 — 지금과 똑같이 id, 이름 순. 로컬에 있으면 여기서 끝난다(로컬이 원격보다 우선).
  • id — 그 id를 가진 복사본의 PC로.
  • 맨 이름 — 모든 복사본에서 찾는다. 한 PC → 그 PC로. 두 PC 이상 → RECIPIENT_AMBIGUOUS, 후보 이름@pc를 알려 준다. 이번 실행에서 아직 목록을 못 받은 PC는 세지 않는다.
  • @all / @here는 로컬만.

보낸 에이전트가 보는 결과 (상태 단어는 기존 세 개 그대로, 새 코드 넷: PEER_OFFLINE · REMOTE_LIMIT · REMOTE_REFUSED · NAME_TOO_LONG):

delivered받는 에이전트에게 들어갔다.
held → pending받는 PC에 보관됨: 받는 에이전트가 잠들었거나 바쁘다. 메모리, 24시간.
PEER_OFFLINE → failed그 PC와 연결이 없다(꺼짐). 보관했다 나중에 보내지 않는다 — 바로 실패를 알린다.
unconfirmed → pending7초 안에 판정이 없거나, 보낸 뒤 연결이 끊겼다. 도착 여부를 모른다.
refused → failed받는 쪽 상한(REMOTE_LIMIT)·검사 실패(REMOTE_REFUSED) 등. 사유에는 어느 PC가 말했는지 붙는다.
RECIPIENT_NOT_FOUND / AMBIGUOUS그 PC에 없는 이름, 또는 여러 PC에 같은 이름 — 후보 이름@pc로 다시 보내라는 hint.

답장: b가 a@집으로 답하면 반대 방향으로 같은 길을 간다. 답 기한(reply contract)은 받는 PC 쪽에 열리고, 기한을 넘기면 받는 PC가 ReplyOverdue만 보내고 알림 문구는 보낸 PC가 스스로 만든다(상대 PC가 정한 글이 내 에이전트에게 데몬 목소리로 가지 않게).

6안전장치 한눈에

신뢰 경계 = OS 계정. 같은 계정의 프로세스(셸을 가진 에이전트 포함)는 믿고 막지 않는다. 다른 계정은 앱 ⇄ 데몬 연결에서 막고, 다른 PC는 신뢰 목록과 사람 승인으로 막는다.

내 계정 안 (같은 PC)

믿는다 — 막지 않는다
  • 앱 · 데몬 · 에이전트 · 다른 프로세스
  • 이 계정 프로세스는 토큰 파일을 읽거나, 키를 풀어 목록 MAC을 다시 계산할 수 있다 — 문서에 그대로 적는다.

같은 PC · 다른 Windows 계정

앱 ⇄ 데몬 연결에서 막는다
  • 접속할 때 상대 프로세스의 계정 확인 → 다르면 거절
  • 토큰 · 에이전트 토큰 파일 = owner-only → 못 읽음
  • 신원 키 = DPAPI 봉인 → 못 풀어서 목록 MAC 위조 불가

다른 PC

목록 + 사람 승인 + 우편만
  • 목록에 있는 PC의 키만 접속 통과
  • 목록을 넓히는 변경은 사람이 승인
  • 우편만 오가고, 받는 쪽 상한이 있으며 제3의 PC로 전달하지 않는다
장치막는 것못 막는 것 · 한계
계정 · 기계별 신원 키 (DPAPI 봉인)다른 PC나 다른 계정으로 복사된 폴더가 같은 신원으로 행세. 그런 폴더는 새 신원으로 시작한다.VM · 디스크 복제는 기계 id까지 복사된다 → 중복 신원 감지가 맡는다. Windows 강제 암호 재설정이면 키를 잃고 모든 PC와 다시 짝지어야 한다.
신뢰 목록 + accept gate목록에 없는 PC는 stream도 열리지 않는다. 목록에서 빼면 1초 안에 끊긴다. 들어오는 프레임마다 목록을 다시 본다.—
목록 파일 MAC손으로 고친 목록, 다른 계정이 고친 목록 → 기능을 끄고 사람에게 「이대로 받아들일까」를 묻는다(에이전트는 못 답함).같은 계정 프로세스의 재서명, 예전에 제대로 서명된 목록으로 되돌리기(rollback).
사람 승인 (peer.add · setNetwork · regenerateKey · 이름 바꾸기)에이전트가 말려들어 우리 명령으로 신뢰를 넓히는 흔한 길. 사람인지는 인자가 아니라 호출 경로(앱 연결 vs 에이전트 토큰)로 가린다.같은 계정 프로세스가 앱 토큰을 읽어 사람처럼 붙는 것, 개발용 WebView 디버깅 포트로 앱을 조종하는 것.
다른 계정 거절같은 PC의 다른 Windows 계정 앱이 내 데몬에 붙는 것. 계정을 못 읽으면 거절한다(fail closed).관리자 권한(elevated) 프로세스. 앱과 데몬 중 하나만 관리자로 돌면 연결이 안 된다. loopback에서 깔끔히 안 되면 owner-only 파일만 내고 남는 틈을 문서에 적는다.
받는 쪽 상한 · 검사고장 난 상대 데몬: PC별 600통/분, 본문 64 KiB, 보낸 에이전트 id가 내 PC 에이전트 id와 같으면 거절, 우편 외 동작은 메시지 종류에 없음.두 에이전트가 끝없이 주고받는 루프(분당 몇 통이라 상한에 안 걸림) — T-121.
중복 신원 감지같은 키 두 벌이 동시에 살아 있으면 새 연결을 거절하고 양쪽에 경고. 같은 기계 · 계정의 두 번째 폴더 복사본은 기계 전체 잠금으로 거절.두 복사본이 공통으로 연결하는 PC가 없으면 감지 못 한다.

도우미 서버가 n0 기본일 때 n0가 보는 것: relay는 이 PC의 공인 IP · ID · 대화 상대 ID · 트래픽 시각을 보고, 우편 내용은 종단 간 암호화라 못 읽는다. 둘 다 none이나 내 서버로 바꾸면 n0가 빠진다. 신뢰한 PC(와 그 PC의 에이전트)는 이 PC 에이전트의 이름 · id · live/sleeping을 본다. mDNS는 LAN 전체에 이 PC의 ID를 알린다.

PeerWire 메시지 (데몬끼리 주고받는 말)
메시지방향내용
Hello양쪽 (거는 쪽 먼저)프로토콜 버전, 데몬 시작 때 뽑은 무작위 instance(중복 감지용). PC 정보는 없다 — 연결의 키가 곧 PC.
Mail요청id, 보낸 에이전트(id · 이름 — PC는 연결에서 붙임), 받는 행 ≤ 64개(tag · to), 본문, 답장 대상, 답 기한 요청
MailVerdictMail의 답행마다 tag로 짝지은 결과: delivered | held | refused | unknown_recipient, 닫힌 코드 집합, 사유 ≤ 512바이트
ReplyOverdue기한 가진 쪽 → 요청한 PC요청 메일 id만. 알림 문구는 받은 데몬이 만든다.
DirSnapshot연결 직후 양쪽, DirResync의 답자기 에이전트 목록 전체(id · 이름 · live/sleeping), 프레임보다 크면 여러 조각
DirDelta주인 → 연결된 PC바뀐 행만, rev = 이전 + 1
DirResync복사본 가진 쪽 → 주인순서가 비면 전체 다시 달라고 함
Probe / ProbeAck양쪽예전 연결이 정말 살아 있는지 확인(중복 감지)
Duplicate남긴 연결 · 거절 마지막 프레임중복 신원 경고(duplicate | suspected)

프레임 = 종류 1바이트 + 길이 4바이트 + 내용, 최대 512 KiB(64 KiB 본문이 JSON escape로 최대 6배가 되는 경우를 담는 크기). 0-RTT는 쓰지 않는다 — 재전송된 Mail이 두 번 배달될 수 있어서.
