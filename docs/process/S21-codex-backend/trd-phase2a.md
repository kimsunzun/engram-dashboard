## 1. Why 2a comes first

```
Phase 0  터전 + 실측        (완료) 시험대 + 실 codex PTY 관측
Phase 1  배선              (완료) variant · dispatch · wire 칸 · 프론트 · 트립와이어
   ↓
Phase 2a 상주 서버 + 번역기  이 문서. 통로(= 상관까지 안에서 끝난다)·번역기·화면까지
   ↓     게이트: §9 의 첫 게이트(스레드를 만들어 id 를 받는다)
Phase 2b resume 배선 · 우편 · 승인 UI
   ↓
Phase 3  프론트 해석 회수 · 생성 경로 정리
```

**The briefing set the order** — 「상주 서버 + 번역기 먼저」. On top of that, two grounds this document adds:

★**The resume details cannot be designed now**★ — what they hang on was a single first gate: **actually creating a thread and receiving its id.** ★**The front half of that gate passed on 2026-09-09**★ — a `thread/start` response was received, and `result.thread.id` was a **UUIDv7** and equal to `thread.sessionId` (§2 L4). ★**But the back half remained**★ — `thread/resume` was **never called once.** Designing the wiring before that would be **writing sentences that measurement will overturn**, and that is the same judgment as putting Phase 0 first (`trd.md` §1: 「값어치는 「먼저 안다」가 아니라 「틀렸을 때 배선을 안 짓는다」다」).

★**And the receiving wiring of 2b is not 「먼저 떼어 낼 수 있는 것」**★ — the channel through which codex tells us a thread id is **the app-server response alone**`[실측]`. Without 2a **there is nothing to receive.** Today the only production caller of `observe_session_id` is the claude `/clear` watcher (`crates/engram-dashboard-daemon/src/lib.rs:288`), and that watcher cannot become codex's receiving path — because `session_id_source` is a file poller that requires **the reference sid we issued** (`expected_sid: Uuid`) (`crates/engram-dashboard-agent/src/backend/mod.rs:348-353`). That is, the dependency direction is one-way: **2a → 2b.** There is no reverse. ★But **the assembly shape that builds that callback** is inherited by codex as is — it is the recording path ADR-0189 chose (§5-6).★

### What the first gate of 2a can overturn — ★three of four rows have an answer★

| Observation | What shakes | Result |
|---|---|---|
| The creation response **carries no** id | The place where ADR-0185 **decision 2** (receiving point = the existing `observe_session_id`) and the ordering constraint of §6 would sit | ★**It did not shake**★ — it came as `result.thread.id` of the `thread/start` response`[실측]` |
| The id **is not a UUID** | The **type** of `backend_session_id: Option<Uuid>` (`crates/engram-dashboard-agent/src/profile.rs:165`) | ★**It did not shake**★ — it parses as UUIDv7`[실측]`. 「새 필드·새 매핑을 만들지 말 것」 stands as is |
| The id is **reissued** every turn | All of decision 2 + the §3 thread state machine | ★**It did not shake**★ — the second turn ran with the same `threadId``[실측]` |
| `thread/resume` **does not hold** after a sequential restart | All of Phase 2b (resume does not hold) · the `session.resume` capability | ★**Not yet observed**★ — §9-1 still carries this one row. **Decision 1 does not shake here either** — it is the answer to 「복원이 무엇에 의존하나」, so even if restore is impossible that sentence is not wrong, but instead **the feature of that axis disappears** |

★**Why decision 1 did not shake in any row**★ — it stands on **the schema (zero id-family properties in `ThreadStartParams`) + upstream rejection**, and the four above are all **response-side** observations (ADR-0185 itself wrote down that distinction).

★**2a carries this one ordering constraint**★ — one of the Phase 2 requirements of ADR-0185 「영향」 falls inside 2a: 「응답으로 받은 sid 는 **첫 턴을 허용하기 전에** persist 한다」. **2a is the only stage that owns that response**, so there is no other place to hang it. That ADR stamped it as 「아직 불변식이 아니다 — 성립한 불변식으로 인용하지 말 것」, and nothing enforces it now. **The point at which design becomes possible is 2a** — the place is the end of §6, and ★ADR-0189 fixed the object that carries that gate★ (the path implementation — §5-1 · §6-3).

## 3. Four state machines — process · connection · thread · turn

★**Do not merge them into one**★ — this separation is exactly what adversarial review HIGH 7 required. If merged, 「프로세스가 살아 있다」 comes to mean the same as 「턴이 진행 중이다」, and at the moment the two diverge (#40766: the process dies and the rollout is truncated but the stored thread remains in streaming`[문서]`) it becomes impossible to know which state to trust.

★**All four sit on top of today's ownership split of our three layers (session · core · transport) — that split is not changed**★ (CLAUDE.md 「핵심 불변식」 ownership split: transport = master/writer/child/shutdown/job · core = subscribers/replay/seq/status/finalized · session = id/cwd/epoch/cols/rows).

★**And the owner of three of the four now has a name — the `AgentTransport` implementation inside `backend/codex/`**★ (ADR-0189 · the **place that builds it and hands it to the assembly point** is ADR-0191 · §5). Editions 1 and 2 called this place by the **undecided name** 「codex 세션 드라이버」 and hung its home on §10-1, and that item has closed. ★**That it is not `StdioTransport` remains as is**★ — the 「transport 층은 stdout 바이트의 스키마를 모른다」 in that file's header is a description of **that general-purpose pipe implementation itself** and is still true (`crates/engram-dashboard-agent/src/transport/stdio.rs:7-9` · the ground of that re-reading = §5-4). **In the table below every 「codex 통로 구현체」 points to that one struct.**

★**There are four machines and the table has five lines — because the thread has two orthogonal axes**★. The old draft stretched those two axes into one line (`생성됨 → persist 됨 → 구독 중 → …`), but **persistence and subscription do not imply each other** — persisted but connection cut, cold resume (identity alive, runtime zero), and resubscription were not expressible in that linear listing. So we split by axis, and **the owner also splits along those axes.**

### ★Three states left out of our machine — 「구독 해제 → notLoaded → closed」★

The old draft's thread machine carried those three at the end. **We removed them.** All three are transitions that hang **after** `thread/unsubscribe` (correction B2 — the 30-minute clock is after that call, not stdio EOF), and ★**neither a place where we call that method nor a reason to call it exists anywhere in this document**★. The survey report does not write its caller either`[미확인]`.

- **So the three are kept only as 「서버 쪽 상태」** — if observed, they go in the log (the same treatment as 2 of §4-7), and are not used as a transition of our machine.
- ★**Leaving a state with no ground in the machine makes the implementer invent a trigger**★ — that is the failure on the opposite side of exactly the reason this document split §3 into four (if merged, it becomes impossible to know which state to trust).
- In our use case the occasion to let go of a thread is **process exit (= connection EOF)** alone, and what moves then is only the **runtime axis** of the table above.

★**「미확정」 is not in codex's vocabulary — it is a state we add**★. `TurnStatus` has only four values (S5) and none of them is 「모른다」. So this must not be written as a translation of a codex value, and must be set up as **our side's observation-failure state**. The closest thing in this repository today is 「None = 이 텍스트만으로는 종류를 단정할 수 없다」 of `resume_failure_kind` (`crates/engram-dashboard-agent/src/backend/mod.rs:147-164` · ADR-0172) — **the same discipline of expressing "unknown" with fail-open.**

### ★Where that 「미확정」 lives — it is a state of the path implementation and not the core's fact layer★

**Which state is whose vocabulary and where it lives:**

| State | Whose vocabulary | Where it lives |
|---|---|---|
| `completed` · `interrupted` · `failed` · `inProgress` | **codex** (`TurnStatus`) | Received on the wire and read by the path implementation |
| `idle` | Ours — codex does not give 「턴 없음」 as a state value (before `turn/started` is that) | **The path implementation** |
| **Undetermined** | ★Ours★ — observation failure | ★**The path implementation**★ |

★**It is an object that exists once per session, so there is an actual place for these four to sit**★ — that editions 1 and 2 called these states only by the name 「드라이버」 and left their home undecided is the gap ADR-0189 closed.

★**We do not add state to the core's fact layer — there is no place to add it**★. What that layer holds is `{epoch, in_turn, last_signal}` only three (`crates/engram-dashboard-agent/src/turn.rs:47-64` — the signal vocabulary is also only the two, `Progress`/`Ended`), and **putting 「미확정」 in there would require a third caller to erase it.** ADR-0127 decision 5 nailed that place down: the erase call sites are **intentionally two** (`OutputCore::finish` + the finalize recheck of `emit`) and 「세 번째 호출자를 늘리면 인과가 갈라진다」. That the two take **the same table mutex** is itself the argument that closes the race with a late insertion after termination.

- ★**The core's deletion at EOF is left as is**★ — `core.finish` erases its own entry with `turn.table.forget(self.id, self.epoch)` (`crates/engram-dashboard-agent/src/output_core.rs:327`, the finalize winner path so exactly once · the other site is the emit recheck of `:251`). **This document neither increases nor moves those two sites.**
- So after EOF the core's answer becomes 「미관측」, and **「미확정」 is the value the path implementation writes last inside itself before it dies.** The two do not mean the same — the core's non-observation is a fail-open that consumers absorb as 「즉시 배달」 (`turn.rs` module header), and the implementation's undetermined is **the name of an observation failure 「이 턴의 결말을 못 봤다」**. ★**And what it does is one log line, nothing more**★ — because there is no next turn in this incarnation that would read that value after EOF and act (ADR-0192 · the EOF section below).
- ★**If a core change becomes truly necessary in implementation, that is not for this document to choose**★ — it is reopening ADR-0127 and `[미확인]`. By present judgment it is **not needed** (the three states in the table above all hold inside the path implementation). One condition that would overturn that judgment = measurement revealing that a consumer invisible outside the core (the mail-parking idle gate, etc.) **must tell** 「미확정」 from 「미관측」. At that time a row is set up in §10.
- ★**The input queue of §4-10 adds nothing to this layer — and does not read it either**★. The owner of the queue-release decision is **each path implementation** and ★**there is no per-backend exception**★ (ADR-0193 · §4-10 discipline 4). ★**The 「claude json 의 해제 조건만 이 계층을 읽는다」 the 5th edition wrote here was wrong**★ — the factual sentence that exception stood on (「claude 는 에코로 **쓰는 순간** 턴 신호를 만든다」) is false, and its refutation is written as lines in §4-10 discipline 4. **The erase call sites remain two.**

### Does that 「미확정」 live across processes — ★it is not carried. And **there is no longer anywhere to carry it either**★

**State living inside the path implementation dies with that implementation.** ★**The 3rd edition opened this section with 「조정 규칙 4·5 가 재기동 후에 그 값을 읽어야 하니 그릇을 찾자」, but those rules are gone**★ (ADR-0192 — the design of re-attaching the same path after an unexpected EOF was itself removed). That is, it is not carried now because **there is no consumer to read it at all**, and the two tables below remain as the **second reason** for 「그때도 나를 수 없었다」 — the decision stands on two legs, so they are kept so the next session does not pull it out again by looking at only one side.

**First, was there a vessel that lives across incarnations at all — enumeration of the session path:**

| Candidate | Lifetime | Does it cross incarnations | Can it hold recovery state |
|---|---|---|---|
| **`ProfileRegistry` + `AgentProfile` entry** | Daemon process / **a disk file**. No `impl Drop` · the trigger for deleting an entry = one explicit delete verb (`profile.rs:479` ← `manager.rs:690-692`) | ★**Yes**★ | ★**Yes — the only place.** But see 「그런데 칸이 없다」 below★ |
| `TurnObservations` (fact table) | Daemon process (`manager.rs:417`). The entry is either unconditionally overwritten by the next `register` (`crates/engram-dashboard-agent/src/turn.rs:125-133`) or erased by `forget` | The table yes, **the entry no** | ★No★ — it has **no serde derive at all**. And that port is 「읽기 전용이 계약」 so it explicitly forbids adding 「지워라/표시해라」 (`crates/engram-dashboard-messaging/src/busy.rs:86`) |
| `SessionTracker` | Daemon process. One polling thread | Yes | No — the learned `resolved_pid` dies with the incarnation, and the only caller of `unwatch` is `kill_agent` (`manager.rs:1778`), so an entry that died naturally **stays for the daemon's lifetime** (the reaper does not know the tracker, `manager.rs:1777`) |
| `BusyPolicy.stale` ledger | Daemon process | Yes | No — it is replaced wholesale on every sweep |
| `AgentSession` · `OutputCore` · **path implementation** · decoder · `intent` cell · control-channel token | **One incarnation** | No | No — `output_core.rs` has no serde derive at all, and the decoder is 「epoch 교체 = 새 transport = 새 decoder 라 리셋이 자동」 by design (`crates/engram-dashboard-agent/src/transport/mod.rs:28-29`) |

★**Conclusion: to carry 「이 턴이 미확정으로 끝났다」 past a restart, the place is `AgentProfile` or nowhere.**★

**But that vessel has no such field — and this explains why the neighboring fields do not exist:**

- The two incarnation-scoped fields are made **unable to reach the disk by serde attributes** — `epoch` is written out with `skip_deserializing` + always `0` (`profile.rs:190-191`), and `last_failure` is `#[serde(skip)]` so it dies with the daemon (`:207-208`). That is, **the disk cannot represent** 「이 관측이 어느 화신 것이냐」 (that asymmetry is intended, and CLAUDE.md 「화신 표식」 limits its scope to `agents.json` disk serde).
- Four fields that are only reserved and ★**have zero production sites that change the value other than initialization and wire mirror**★ = `restart_policy` · `restart_count` · `failed_reason` · `last_start_at` (declaration `profile.rs:213-230` · initialization `:256-261` · wire mirror `crates/engram-dashboard-daemon/src/connection_core.rs:492-498` — measured). ★Do not read those four as 「빈 칸이니 쓰면 된다」★ — they are reserved fields whose removal is explicitly forbidden (`profile.rs:79-84`), and ★**giving them new meaning is both a disk contract change and a wire contract change**★ — it passes through the five layers that comment counts, as is.

★**Decision = 「나르지 않는다」**★ — the first leg is **absence of a consumer** (after ADR-0192 there is no code to read it), and the second leg is **risk on the persistence side**. The values of the second are the three below:

| What would have to change | What it puts at risk |
|---|---|
| Add one field to `AgentProfile` + that field's serde default | `agents.json` is `schema_version: 1` and **a version mismatch falls to an empty list with no backup** (`crates/engram-dashboard-agent/src/persistence/mod.rs:122-129` — only the parse-error path renames to `.corrupt-<ms>`). That is, raising the schema passes through an **unprotected data-loss path** at that moment |
| Write together **which incarnation that observation belongs to** | As above, `epoch` goes to disk only as `0`, so **there is no vocabulary on disk to write incarnation attribution.** Making a new axis collides head-on with ADR-0163's 「읽기를 건너뛰는 것이 의미의 일부」 |
| When to write | Profile saving **synchronously rewrites the whole file inside the mutex** (`profile.rs:395` · `:406`). And ★**a save failure is swallowed as `tracing::error!` and nothing goes to the caller · UI · LLM**★ (`persistence/mod.rs:99-106`, contract = `profile.rs:310-311`). That is, we **cannot confirm** 「미확정을 적었다」 |

★**So 2a does not carry it**★ — undetermined lives only inside the path implementation, and when that implementation dies only one log line remains. **What the outcome is when it is lost is also short now**: that incarnation is over (EOF = session end once + reaping), and the next incarnation **attaches anew with the stored `thread.id`** and does not take over a lost turn marker. ★**That new attach (`thread/resume`) and whether the server reports again the turn that was in progress afterward are both `[미확인]`, and both are questions the resume wiring of Phase 2b carries**★ (§0 · §9-1 · §11) — 2a puts no design on top of it. → §10-12.

### When EOF is observed — ★the same path does not attach again★ (ADR-0192)

★**The 3rd edition put 「조정(reconcile) 규칙 0~5」 here and made its fourth rule 「새 프로세스를 띄우고 `initialize` → `thread/resume`」. We remove that design entirely**★ — because the premise that rule stood on (after an unexpected EOF **the same session survives** and reattaches) is incompatible with this repository's lifetime model. The reason is in "Why it was removed" below.

**So what is actually done at EOF is four, and of those only two (1 and 2) are newly written:**

1. **Wake all waiting RPCs with an error.** Leave not one. ★**The first thing newly written**★ — leave no permanent hang (precedent = the GUI measurement 2026-08-18 where overlapping `request_id` made an old waiter hang permanently, regression net `cargo test -p engram-dashboard --test daemon_client_pending`).
2. **Leave the turn that was in progress in the log as undetermined.** ★**The second thing newly written — and that is all**★. Do not guess the result. ★**It is not a gate**★ — there is no next turn in this incarnation so there is no consumer to read it, and its worth is post-hoc diagnosis alone (the section above).
3. **After that it is today's causality as is** — pump break → `core.finish` → **terminal transition exactly once** (ADR-0005) → the reaper removes the session from the map and the profile is preserved as a corpse (`crates/engram-dashboard-agent/src/reaper.rs:46-71` · `:104-113`). **This document adds not one line to that path.**
4. **A restart is a new incarnation only.** The wiring by which that incarnation calls `thread/resume` with the stored `backend_session_id` is **Phase 2b** (§0), and 2a goes only as far as producing that value.

★**「모르겠으니 새 대화를 파자」 remains forbidden as is**★ — ADR-0082 abolished the fresh fallback and that prohibition is carried by a regression test (`activate_resume_early_exit_ends_failed_no_fresh_fallback` of `crates/engram-dashboard-agent/tests/activation.rs`). This prohibition does not die even if reconnection is gone — because the place it hangs is **the activation of the next incarnation**.

#### ★Why it was removed — it collided head-on with three invariants★

★**It is left here so it will not be pulled out again.** If 「EOF 뒤 같은 통로가 `thread/resume` 한다」 is implemented literally, three break at once:★

- **ADR-0005 (finalize once)** — the pump already emitted `core.finish` at EOF and made the terminal transition once (`crates/engram-dashboard-agent/src/output_core.rs:299-341`). If the path respawns the child after that, that session is alive while **already reported as ended**.
- **ADR-0019 (reaper single consumer)** — `finish` → done_tx → the reaper **erases** that session from the map (`reaper.rs:46-71`). Even if reattachment succeeds, the session to attach to is not in the registry.
- **Job Object boundary** — the new child is left **outside the reaped session's Job Object**. That is, nobody can kill it.

**And that design had no owner either.** The physical form of 「새 프로세스를 띄운다」 is `activate_profile` (`crates/engram-dashboard-agent/src/manager.rs:1113`) and it is not a verb the path can call. The reserved field `restart_policy` has **zero production consumers** (the four reserved fields in the section above that asks whether that undetermined state lives across processes — 「그 「미확정」이 프로세스를 넘겨 사나」), so there was no place there either.

★**The codex-side ground points the same way**★ — #40766 `[문서]`: on Windows MCP OAuth expiry kills the app-server, the rollout is truncated and resume stalls in streaming. **Putting a new turn on a truncated rollout on the spot makes that damage ours.** #33241 `[문서]`: if two processes hold the same rollout **at the same time** the history merges — 「죽은 것 같으니 하나 더 띄운다」 is exactly the shape of that incident. ★**Claude too does not reattach by itself when the process dies — aligning backend defaults with claude is ADR-0192.**★

#### ★「우리 kill 이냐」 must still be told apart — but **the contract is not enlarged**★

Whether to fold EOF into `Killed` or `Exited{code}` is split even today, and the codex path needs the same distinction (so as not to pour error logs on an EOF we killed). ★**But that distinction needs no shared contract — because the asking side and the answering side are the same object.**★

- That bit is **the path's private property** — `shutdown()` sets up `StdioTransport.shutdown: Arc<AtomicBool>` (`crates/engram-dashboard-agent/src/transport/stdio.rs:46`) as `Release` (`:340`) and **that implementation's own pump** reads it as `Acquire` and classifies (`:251` · `:271`). The codex path implementation also **owns its own reading thread** (§5-1) so it uses the same shape as is — it reads its own private field itself.
- ★**So `AgentTransport` stays at six methods as is**★ — the 「공용 계약에 한 줄도 더하지 않는다」 of ADR-0189 is kept, and the place where the 3rd edition noted tension with that sentence is **gone** (the tension itself disappeared).

★**The 「읽기 함수를 하나 더한다」 decision the 3rd edition set up here is withdrawn — the sentence it rested on was false**★:

| What the 3rd edition wrote | Actual |
|---|---|
| 「세 구현체 전부가 **이미 그 비트를 갖고 있다**(`stdio.rs:46` · pty · api)」 | ★**`ApiTransport` has no field at all**★ — `pub struct ApiTransport;` (`crates/engram-dashboard-agent/src/transport/api.rs:14`), `fn shutdown(&self) {}` (`:50`). That implementation **does not hold** that bit, and if a function appears in the contract it would either lie there or have to enlarge `Unsupported` — exactly the shape ADR-0189 rejected |
| 「조정 규칙 4 가 돌 때 물을 수 없으면 죽는 길에 새 프로세스를 띄운다」 | ★**That rule is gone**★ (above) — there is no incident left to block by asking |

★And the rest of the facts the 3rd edition wrote remain true, and now **require nothing**★ — that the classification leaking upward is post-hoc and lossy (`TerminalReason::Killed`/`Exited{code}` → collapsing into the single value `AgentStatus::Killed`, `output_core.rs:306-315`), that `TerminationIntent` has no getter (`crates/engram-dashboard-agent/src/types.rs:96-101` · setter `session.rs:111-113` · sole reader `manager.rs:1284-1288` · `reaper.rs:105-111`). ★**Do not reuse these three as the ground for 「그러니 계약을 넓혀야 한다」**★ — the layer that needs the distinction holds its own field, so there is no reason for a shared contract to carry it. → §10-13.

### The relation of these four to our incarnation marker (epoch) — ★they are not the same axis★

The incarnation marker is **our side's reattach axis** (ADR-0163/0164): a 32-bit random number drawn anew per incarnation, compared only for match/mismatch, the reattach trigger is the authority-registry observation alone, and the subscription effect deps are `[viewId, agentId]` (the marker is not put in). The codex thread id is **the backend side's axis** and lives across processes. ★Do not mix the two★ — a changed marker does not mean the thread changed (continuing the same thread after a restart is our goal), and the thread staying the same does not mean the screen stream continues.

### Login · MCP · subagent recovery

HIGH 7 required all three together, but ★**this document does not design those three**★ — ground: MCP injection itself is out of 2a's scope (§0), the observation of login expiry (#40766) is `[문서]`, and subagents are outside our schema reading range (`ThreadItem` 19 variants unread — §2 `[미확인]`). **Instead all three are absorbed by the one EOF disposition above** — whatever the cause of death, what we do is the same (wake waiting RPCs with an error → log the turn as undetermined → end and reap the session → a restart is a new incarnation). ★**And after ADR-0192 that absorption became stronger**★ — the place where handling could have split by cause (「어느 사유면 다시 붙나」) is gone entirely. ★But that is not 「사유를 구별할 필요가 없다」 but 「지금은 구별할 근거가 없다」★ — if the distinction becomes necessary, `resume_failure_kind` (ADR-0172) is that place. It is left in §11.

## 4. Wire discipline

★**The first nine of the rows below were all required by adversarial review HIGH 7 and 8, and not one is optional**★ — the tenth (§4-10, the input queue) was added after that by **ADR-0190**. ★**「어디에 둘지」 no longer hangs on §5**★ — ADR-0189 closed that answer, and the rows below that touch write, read and correlation are all **inside that path implementation** (§5-1). ★**Do not make another place that counts the items**★ — the number in this line has the section title (`### 4-N`) as its canon.

### 4-1. There is exactly one stdin writer — serialize

One line = one JSON object (S1), but with two writers **a line gets split and interleaved.** What the server receives from that combination is two broken objects.

- `AgentTransport` is `Send + Sync` and `send_input(&self, …)` is an immutable reference, so **it may be called from several threads at once** (`crates/engram-dashboard-agent/src/transport/mod.rs:41-45`). That is, the serialization is carried by **a mutex inside the implementation**.
- That shape already exists today — `StdioTransport { stdin: Mutex<Option<ChildStdin>>, … }` (`transport/stdio.rs:40`).
- ★**The approval response is the actual test of this discipline**★ — approval is the server asking first and us answering (D1), so that write comes **on a different thread from user input**. The two paths must pass through the same mutex.

### 4-2. Reads are always drained

Do not stop reading even if the consumer is slow. Ground = bounded queue + `-32001` (D3) and Windows queue saturation (#22393 `[문서]`) — **if reading stops, the server-side queue fills and an overload response comes back.**

★**This discipline constrains the choice in §5**★ — today the pump thread **exclusively owns** the decoder as `&mut` (`transport/mod.rs:26-29`: 「decoder 는 …가변 상태를 들고, pump 스레드(단일)가 `&mut` 로 배타 소유한다」). If that thread holds the response wait table and waits, **reading stops while it waits** = a violation of this discipline. So the wait table must be **outside the pump**.

★**And that discipline has a second face — the reading thread does not take the stdin lock as blocking**★

There are real moments when the reading thread **must also write**: answering an inbound request (the first row of §5-2 · the unknown-request error response of §6-2 · later the approval response). But every write goes through one stdin mutex (§4-1) and there is no means to put an upper bound on that blocking write (§4-9 — `std::sync::Mutex` has no timed lock and std pipes have no deadline). ★**Multiply the two and it becomes a self-lock**★: with a user-input write blocked holding the mutex under pipe backpressure, if the reading thread waits for the same mutex → **reading stops** → the server queue saturates → ★**EOF never comes so the EOF disposition of §3 never fires**★. The process is alive and there is not a single signal.

- ★**Discipline:** the reading thread does **not take the stdin mutex directly.** The response it must send is also put into the **bounded queue + dedicated writer thread** that §4-9 sets up, and it returns at once★ — then **inside this path** the only thread that takes stdin as blocking is that one writer, and the reading thread never contends with it.
  - ★**Do not write 「워크스페이스에서 유일한 스레드」 — it is false**★. The `StdioTransport::send_input` of the claude json path **still today** runs std `write_all` + `flush` while holding the `stdin` mutex (`crates/engram-dashboard-agent/src/transport/stdio.rs:295-304`). ★That is, this stall shape is not something this path newly brings in but **already exists in the claude json path**★ — §4-9 acknowledges that as is. What this discipline does is not to **eliminate** that shape but to **keep it separate from the read path in the new path**.
- ★**When that queue is full the response is also refused**★. The refusal, as in §4-9 rule 1, **returns at once as `Err` and is logged** — what had been signal-less becomes an observable refusal. ★**But it does not land as session termination**★ — the other side may still stall without getting an answer, and we know that fact only through the log (「알려진 한계」 of §4-9 · §11). ★The 4th-edition sentence that wrote 「거절 = 관측 가능한 종료」 was removed — there is no verb to execute that termination★ (the same section).
- ★**Do not turn this discipline back into 「승인 응답은 급하니 먼저 쓰게 하자」**★ — if priority is to be given, give it inside the queue, and the branch that takes the mutex directly revives the self-lock above.

### 4-3. The downstream queue is bounded

Do not pile what is read into an unbounded buffer. Our canon is already bounded — the replay ring buffer of `OutputCore`. ★Do not make a new unbounded queue★.

### 4-4. ★Separate the inbound / outbound request id spaces★

**What exactly this prevents:** if the request id `0` we issued (e.g. `thread/start`) and the **request id `0` the server issued** (e.g. a command-approval request) share one wait table, the response to the approval request is **delivered to the waiter of our request.** We receive an approval decision in the `ThreadStartResponse` place, and the server never gets an answer so the agent stops.

- **Outbound** = our counter. It goes into our wait table (id → waiter).
- **Inbound** = the server's counter. **It is not put in our table.** The received id is only handed back as is in the response.
- ★**The deciding axis is not the id but 「방향 + 봉투 모양」**★ — in principle the id cannot tell them apart. The id the server issued must be **returned literally** (the line right above), so the two value spaces **cannot help but overlap**, and that is not a defect but a protocol requirement.
  - **If the received line has `method`** it is a server→client **request/notification** → we **do not look up** our wait table. If it is a request, we respond carrying that id as is.
  - **If the received line has `result` or `error`** it is a **response** to our request → only then do we look up our wait table.
  - **The two-counter discipline is unchanged** — the outbound counter is ours and server ids are not mixed into that counter. The inbound id is **not put in the table and is used only for that one response.**
- The decision in one line (rewritten): ★**a structure that does not gate the wait-table lookup on the presence of `method` is itself the defect.**★ The old sentence written as 「id 만 보고 가른다」 was an unsatisfiable acceptance condition — deleted.
- ★**A JSON-RPC 2.0 library does not do this for us**★ — we define the envelope (S1: there is no `jsonrpc` field).

### 4-5. Handling `-32001` (overload)

**It is a target for retry, not a failure** — but the retry is **a resend of that one request** and does not rebuild the process or connection (★no reconnection — ADR-0192 · §3★). The backoff values are implementation constants. ★**Since when it actually appears is `[미확인]`, do not skip the handling on 「안 나올 것이다」**★ — if skipped, that response flows to 「모르는 오류」 and the turn stops silently.

### 4-6. Ignore non-JSON stdout lines, and do not die

Ground = paseo's Windows incident (D6 `[문서]`). ★**Do not treat a parse failure as fatal**★. But **do not silently discard either** — leave it in the log. A masking path already exists (`transport/stdio.rs:24` imports and uses `engram_dashboard_base::logging::mask_secrets`).

★**Do not widen this to 「관용적 파서」**★ — the discipline is one: **let non-JSON lines drain away.** If it is JSON with an unknown name, that is the axis of §4-7, and if it is JSON with a different shape, that is a defect.

### 4-7. There is no protocol version (S8) — what do we do instead

We do three things.

1. **Record the CLI version once at startup.** A precedent already exists — the `record_version_once` of `crates/engram-dashboard-agent/tests/backend_contract.rs` asks for `--version` **with the production argv** and prints it, ★without asserting the value★ (this CLI updates itself, so pinning it would turn red at every update — that file's header writes that decision).
2. **If `deprecationNotice` (D2) is received, leave it in the log.** One notification is the only early signal.
3. ★**An unknown notification name is logged and discarded**★ — once per name, through the masking path, with a counter visible in diagnostics. ★**The first edition wrote that this should be let through the `Structured{kind,json}` escape hatch, but it was removed**★ — that escape hatch **draws the codex method name and the JSON original on screen** in the frontend (§6-2 points to those two lines). The log carries the value of loss prevention, and the screen receives only the neutral vocabulary.

★**Do not leave it as 「깨지면 알 것이다」**★ — if a notification **name** is silently changed (the `newConversation` → `thread_start` of D5 is the precedent), none of the names we know arrive, so **the screen goes empty and that is the only signal**.

**What breaks that silence — three are layered (the first edition hung it on the screen alone):**

1. ★**The translation-table golden**★ (§9-3) — since it asserts 「아는 이름 전부가 중립 이벤트를 낸다」, it turns red when upstream **changes** a name. **It comes earlier than screen observation and runs in CI.**
2. **The log of 3 above** — the actual arrival of an unknown name is left once per name.
3. **The CLI version record of 1 above** — after the fact it tells apart 「언제부터 바뀌었나」.

★**One hole still remains: the case where the name is 「사라지지 않고 새로 생긴」**★ — the golden covers only names we know, so for a newly added notification the log of 2 is the only signal. Not moving that to the screen is the decision of §6-2, and this line is its price.

### 4-8. Teardown — the kill causality is unchanged. ★Not one line is added inside the transport★

There is no shutdown method (S7 `[스키마]`). So we read it as 「정리 = stdin 닫기」 and want to put it **inside** `transport.shutdown()`, but ★**that is the order this repository has named and forbidden.**★ The old draft prescribed exactly that order (「① stdin 을 닫는다 → ② 짧게 기다린다 → ③ kill」), and that sentence was removed.

**The invariant nailed in that place today — still valid and this document does not touch it:**

- ★**「순서 불변 — stdin close 는 kill 보다 절대 먼저 오면 안 된다(데드락, FIX 1)」**★ (`crates/engram-dashboard-agent/src/transport/stdio.rs:330-337`). The causality is written in that comment: `send_input` holds the stdin mutex **throughout the blocking `write_all`**, and if the child does not read stdin (pipe backpressure) that write blocks forever and never releases the lock → if `stdin.lock()` is attempted **before** kill, that lock is never obtained and **it cannot even reach kill** → the pump cannot wake → `core.join_pump` **hangs permanently** (the ADR-0001 causality stops).
- The same comment closed even that temptation in advance — 「※graceful-exit-via-stdin-close 는 필요 없다 — 어차피 여기서 kill 하므로」 (`:337`).
- Today's stdin cleanup is `try_lock` + skip **after** kill (`:356-360`) — if it cannot be obtained it is simply passed over, and the uncleaned `ChildStdin` is reclaimed by the OS on transport drop.
- ★**A regression net already exists**★ — `shutdown_completes_even_if_send_input_blocks_on_full_pipe` (`:457`, `#[cfg(windows)]`). If the order is reversed that test catches it as a timeout.
- ★**§4-1 pulls that trigger more often**★ — since the approval response passes through the **same stdin mutex** as user input (D1), the paths that can block while holding a write grow from one to two. **The codex path is closer to this deadlock than the claude json path.**

**And waiting inside the first verb stretches the 5-second contract — the old draft's accounting was wrong:**

- `AgentSession::kill` is **sequential** code that calls `transport.shutdown();` and then `core.join_pump(timeout);` (`crates/engram-dashboard-agent/src/session.rs:243-246`). So a positive wait inside shutdown does not **fit within** the 5-second budget but **is added in front of it.**
- The contract itself forbids it — 「자원 강제 종료(멱등). pump 종료 대기는 여기서 안 함(core.join_pump 몫)」 (`crates/engram-dashboard-agent/src/transport/mod.rs:53`).
- ★Therefore the old draft's 「②의 값은 사용자 결정이 아니라 구현 상수다 … `join_pump(5s)` 예산 안에 든다」 is **wrong in two places**★ — it does not fit in the budget, and it is not a constant (below).

**So the two verbs are exactly today's shape:**

```
transport.shutdown()                     ← 첫째 동사 (오늘 그대로 — 이 문서가 아무것도 더하지 않는다)
   ① shutdown 플래그 → child.kill + wait                  (stdio.rs:340 · :342-347)
   ② TerminateJobObject — 손자까지                        (:349-354)  ← write 핸들을 닫는 것이 이것
   ③ stdin try_lock + take (best-effort, 못 얻으면 skip)   (:356-360)
core.join_pump(5s)                       ← 둘째 동사 (오늘 그대로)
```

- **EOF → pump break → `core.finish` → done_tx** causality as is. A pipe wakes the read with EOF once the child tree closes all write handles, so unlike a PTY no watcher is needed (`transport/stdio.rs:11-14`).
- **finalize once** (ADR-0005) as is — the terminal transition and notification are the pump's alone and this change does not add consumers to it.

**If we want to shut codex down normally, that place is outside the transport — the session layer, 「앞」 (in front of) the first verb:**

```
(선택) 통로 구현체의 graceful close 시도   ← 유계. 어떤 결말이든 아래로 떨어진다
      ↓
transport.shutdown() → core.join_pump(5s)   ← 위 그림 그대로, 무변경
```

All four conditions must be kept for this arrangement to hold:

1. **Bounded** — past the upper limit it goes down without waiting for the result.
2. **Failure and timeout are no-ops** — it makes no exception and no special path and just falls to the usual kill path. That is, the worst case is **today's behavior**.
3. **It changes not one line of the transport contract** — `shutdown()` is still 「기다리지 않는 강제 종료」.
4. If that attempt writes to stdin, that write also goes through the mutex of §4-1, so ★**no blocking lock here either**★ — the write itself must be bounded (§4-9).

**We write the grades honestly:**

| Claim | Grade |
|---|---|
| The app-server has no shutdown method | `[스키마]` (S7) |
| Closing stdin ends with exit code 0 | `[실측]` (L2) — ★**but that observation had no active turn**★. ★「이 PC 의 app-server 왕복은 `initialize` 하나뿐이다」 that editions 1 and 2 attached here is **stale — deleted**★: the round trips are four (`initialize` · `thread/start` · `turn/start` · `turn/interrupt` — L16). The reason this row is narrow is not the number of round trips but the single fact that **we have never closed stdin mid-turn** |
| **Closing stdin mid-turn also exits soon** | ★`[미확인]`★ — never observed anywhere. **It is only an inference derived from `[실측]` above.** So do not justify a graceful wait value as 「보통 금방 끝난다」 |
| A normal exit flushes the rollout and a hard kill truncates it | `[미확인]` — this fork is exactly what §10-10 asks |

#### ★But that 「유계 graceful 시도」 today **has no verb** — the first edition did not write it★

**The cleanup S7 speaks of = closing stdin**, yet ★**this repository has not a single means to 「죽이지 않고 닫는」 stdin**★. We write it as lines:

- The six verbs of `AgentTransport` have no `close_stdin` (`crates/engram-dashboard-agent/src/transport/mod.rs:41-57`, full-text reading). `shutdown()` is by contract 「자원 **강제** 종료(멱등)」 (`:53`) — 「부드럽게」 is not in that definition.
- The only place where stdin is actually dropped is **step 4** of `StdioTransport::shutdown` and it is ★**after kill**★ and, being `try_lock` best-effort, **it is simply skipped on contention** (`transport/stdio.rs:356-360`).
- ★**`ControlCaps.graceful_shutdown` is `false` in all three implementations and there is not one branch in the workspace that reads that value**★ — `stdio.rs:381` · `pty.rs:355` · `crates/engram-dashboard-agent/src/transport/api.rs:70`. The only non-test consumption is one line that copies it to the wire as is (`crates/engram-dashboard-daemon/src/connection_core.rs:348`). **That is, that field only reports and turns on no behavior** — do not read it as 「이미 그 개념이 계약에 있으니 쓰면 된다」.
- And **issuing a new verb is not cheap.** `close_stdin` doing blocking `stdin.lock()` **revives the deadlock invariant quoted above as is** (`stdio.rs:330-337`) — with the child not reading stdin that lock is never taken, and if that attempt stands **before** kill it cannot even reach kill. So the new verb carries both 「계약 변경 + 명시된 락 순서 위험」 together.

**So we rewrite (가) of §10-10 together with its cost — there are three branches:**

| Branch | Verb | Cost |
|---|---|---|
| **(가-1) Add `close_stdin` to the transport contract** | A new trait method. All three implementations | ★**`try_lock` + it must be a no-op on failure**★ — if blocking, the hang of `stdio.rs:330-337` returns. But if `try_lock` it becomes a graceful close that **silently does nothing on contention**, and the caller cannot tell 「보냈다」 from 「못 보냈다」 (that axis becomes necessary in the return type) |
| **(가-2) The path implementation does not touch stdin and tries only through the protocol** | None — the existing `send_input` | ★**The app-server has no shutdown method** (S7)★. That is, there is **no request** to send. `turn/interrupt` is turn-scoped so it does not take the process down (S6) · `thread/unsubscribe` was left out by §3 as having no caller. **So this branch is not executable with today's schema** |
| **(나) Do not accept — the same hard kill as claude today** | None | Zero change. Price = whether the rollout is flushed is left in codex's hands and that outcome is `[미확인]` |

★**The honest decision: the first edition's framing that wrote (가) as 「유계 대기값 하나만 고르면 되는 일」 did not point to an executable path.**★ (가-2) is impossible because the schema has no verb, and (가-1) is **a contract change + adding a return axis + working next to the deadlock invariant**. So §10-10 asks not 「값을 얼마로 하나」 but ★**「그 문을 낼 값을 낼 것인가」**★. ★Whichever the answer, not one line **inside** `transport.shutdown()` changes★ — the order in it is an explicit invariant and is number 1 of "What is not touched" in §8.

★**So 「유계 graceful 시도를 넣나」 is not an implementation constant but a decision**★ — what the user feels hangs on it (does codex flush its own rollout before dying). Today claude receives a hard kill without that attempt. **§10-10.**

### 4-9. ★There must be a detection means for a write-side stall too★

§4-2 makes reads drain, and the EOF disposition of §3 fires at **EOF**. Between them there is one window nobody watches.

**What exactly happens:** if the server stops reading stdin (queue saturation · hanging on a subprocess · a half-death of the #40766 kind), pipe backpressure makes the `write_all` of `send_input` block holding the mutex. In that state there is **not one signal** — the process is alive, EOF does not come, waiting RPCs do not fail if they have no deadline, and `-32001` does not come either (that is a response the server rejects **after reading**). And because of §4-1 **user input and the approval response are trapped together** behind that mutex — if approval is blocked the agent stops exactly as in the approval row of §6-1.

**Two disciplines — ★both are 「기다리는 쪽을 깨우는 것」, and neither kills the side that stopped★:**

1. ★**The *caller's* wait on an outbound write is bounded**★ — if a bounded queue + a dedicated writer thread is placed in front of `send_input`, **when the queue fills the caller returns at once as `Err`.** This discipline is about leaving no **call** that blocks indefinitely, and ★**it does not eliminate the stall itself**★ (「대가」 below).
2. ★**A waiting RPC has a deadline**★ — if 「응답이 안 온다」 and 「서버가 죽었다」 are told apart by EOF alone, in this window where EOF does not come the waiter remains forever. A precedent for that incident is in this repository (the GUI measurement 2026-08-18 where overlapping `request_id` made an old waiter hang permanently — regression net `cargo test -p engram-dashboard --test daemon_client_pending`). ★**What the deadline wakes is that one waiter only and it does not take the session down**★.

#### ★If that stall lasts long, what releases it — **we do not build a forced-kill watchdog**★ (user decision)

★**The 4th edition wrote 「그 실패가 **연결 = 끊김**으로 올라가 §3 의 EOF 처분과 같은 착지를 탄다」 here. We remove that sentence — it has no subject to execute it.**★ A blocked write is a stall **with the child kept alive**, so it makes no EOF, and so the event to raise as 「연결이 끊겼다」 does not occur at all. To take the session down in that state we would have to newly make a **verb that kills a live agent by timer**, but ★the owner of that verb is nowhere in this document★ — and §3 named and forbade that class (「근거 없는 상태를 기계에 남기면 **구현자가 트리거를 발명한다**」).

**So what actually stands is three:**

- ★**On the mail side the existing 30-minute cap releases it**★ — the messaging kernel already has a `BUSY_MAX_TURN` (30 minutes) fail-open safety valve (`crates/engram-dashboard-messaging/src/busy.rs:44-57`), and the periodic sweep **decides a 「턴 중」 observation past that time is debris and wakes its owner with a doorbell** (`:136-146`). ★**That is the posture this repository takes toward 「너무 오래 멈췄다」 — declare the observation stale, do not kill.**★ That is, even if the stall lengthens, the mail addressed to that recipient is not blocked forever.
- ★**There is no signal on screen — a known limit**★. The process is alive, EOF does not come and the session state does not change. What the user sees is only **an agent that gives no response**, and today there is no surface to tell whether the cause is 「쓰기가 막혔다」 or 「모델이 오래 생각한다」. → §11.
- ★**If we suffer it or measure, we build it then with a value**★ — right now whether this stall actually happens is itself `[미확인]` (§11), and choosing 「몇 분이면 죽인다」 on zero measurement would make that number invented. **Leaving the detection means (the two disciplines above + a log) is all this section decides.**

**We write down the price:**

- ★**We separate what can be prevented from what cannot — the first edition mixed the two**★.
  - **Cannot:** put an upper bound on `write_all` itself. `AgentTransport::send_input` is synchronous (`crates/engram-dashboard-agent/src/transport/mod.rs:45`) and the implementation's write runs std blocking `write_all` + `flush` **holding the `stdin` mutex** (`crates/engram-dashboard-agent/src/transport/stdio.rs:295-304`). There is no means to attach a deadline to a std pipe, and `std::sync::Mutex` has no timed lock.
  - **Can:** put an upper bound on the **caller's wait**. If a bounded queue + a dedicated writer thread is placed **in front of** `send_input`, only that one thread blocks forever and the other callers return **at once as failure** when the queue fills. The stall itself does not vanish but **no-signal turns into an observable refusal** — that is what this section requires.
- ★**And that place is now decided — inside the codex path implementation's own `send_input`**★ (ADR-0189 · §5-1). Editions 1 and 2 were weighing this place by hanging it on the four inside the seam, ★and even then the conclusion was 「네 안 모두에 소유자가 있어 결정이 아니다」★. The contract does not change — standing a queue in front of the blocking `send_input` **needs no new trait method.**
  - ★**Does it touch claude — seen only in this section, ✗**★. The codex path implementation is a **new object** so it touches not one line of `StdioTransport::send_input`. ★**But the input queue of §4-10 is different**★ — that one is **common to json mode** so it changes the write timing of claude json (ADR-0190). **Do not lump the two queues together** (the contrast table of §4-10).
- **When the bounded queue fills, input is refused** — growing it unbounded violates §4-3. The refusal must be a **failure visible to the user** (if silently dropped, 「전송 실패」 and 「모델이 무시했다」 cannot be told apart — the distinction ADR-0088 set up).
  - ★**That refusal must be `Err` — it cannot be expressed as a short `Ok`**★. The two byte fields of `WriteOutcome` are **not independent measurements but values copied from `bytes.len()` by construction** (`crates/engram-dashboard-agent/src/session.rs:178-184`), and the comment of that type pins that explicitly — 「완결성 신호 = Ok-vs-Err 이지 바이트 비교가 아니다 … `bytes_written` 은 독립 계측값이 아니라 `bytes_requested` 를 구성상 그대로 복사한 값이다(short-write 탐지 불가 — 비교하면 항상 같다, 동어반복)」 (`crates/engram-dashboard-agent/src/types.rs:663-671`, the same decision is also in `session.rs:151-154`). ★So do not try to report 「일부만 받았다」 via that field★ — at that moment the distinction ADR-0088 set up **would stand on a tautology.**
  - ★**And that axis is **literally the same** in §4-10 too★ — the two sections do not apply ADR-0088 differently. **The receipt is one and its meaning is one**: `Ok` = 「요청 바이트를 우리가 전량 맡았다」 · `Err` = 「안 맡았다」. ★**The branch that splits 「담겼다」 and 「실제로 썼다」 into two grades to report was rejected**★ (user decision — §4-10 · §10-20).
- The upper-bound **value** is an implementation constant (the same class as the backoff of §4-5). ★But write the ground for that value in a comment — measurement is zero, so a number chosen now is invented.★
- ★**This discipline does not hang on 「app-server 가 실제로 그렇게 멈추나」**★ — there is no evidence that it does not stop (when `-32001` appears and how deep the queue is are `[미확인]`, D3), and since the outcome when it stops is **permanent no-signal** it gets the same decision as §4-5: do not skip it on 「안 나올 것이다」.


### 4-10. ★json-mode input is put in a queue, and when it can be sent it is flushed in order★ (ADR-0190)

★**This discipline is not codex-only — it is common to json mode.**★ So it is placed not beside §5 (the path) but here, alongside the write-axis disciplines: §4-1 (one writer) and §4-9 (bounded write) deal with **the same endpoint** and this section attaches **in front of** it.

★**But do not read the name 「json 모드 공통」 as the *ground* of that policy — what the policy hangs on is not the wire format but the backend**★

The core of the policy this section sets up is **「한 번에 한 턴, 턴 중에는 안 흘린다」** (serial turns). The reason it is true now is that **the two json backends we have today are so** — in claude json one call is one complete user turn (the call contract of `crates/engram-dashboard-agent/src/session.rs:136-141`), and codex left the mid-turn reflect verb (`turn/steer`) out of this scope (rule 5 below). ★**The format JSON does not imply serial turns**★ — if **a third backend that is JSON yet supports concurrent turns or steer** comes, this policy does not fit that backend, and the axis to split on then is not 「wire 가 JSON 이냐」 but ★**「그 백엔드가 턴을 겹쳐 받나」**★. **We do not make that axis now** (no such backend exists and the ground to make it is zero measurement) — instead we leave that fact in §11. ★Do not use this section's name as a ground to force 「JSON = 직렬」 on a third backend★.

**Why it is needed:** the codex app-server **cannot be spoken to right away** even after the process is up — only after the `initialize` round trip (★about 130ms★`[실측]`) and the `thread/start` round trip end do we know `thread.id`, and without it there is **no form at all to build** the `turn/start` request. If input arrives in that interval there is nowhere to send it. ★**And input really does arrive in that interval**★ — a person rarely types in a 130ms window, but the LLM path is not so. This repository already has **T-28** (a freshly spawned terminal receiver does not submit a delivered letter) and its cause is on the same axis — the submit was written **492ms before** the receiver was ready (measured in the daemon debug log).

★**「준비 전 입력」 is not a special case**★ — it is **the same situation as input that arrives while a turn is running** (both 「지금 못 보낸다」) and the only difference is **when to flush**. So the two are merged into one.

**Six disciplines:**

1. ★**Do not make the rule 「준비된 뒤에 쏘라」**★ — if that rule were set, every caller would need to know whether it is ready and the logic would grow complicated. **The caller just sends, and the queue holds it on its own.**
2. ★**Do not drop input**★ — if it exceeds the upper limit or **there is already no way to send at the time of that call**, it is turned back as an error. ★But what failed **after being queued and `Ok` having gone out** cannot be returned to that caller — the limit item of the receipt section below is that★. `send_input` is already `Result` (`crates/engram-dashboard-agent/src/transport/mod.rs:45`). ★The branch that drops silently was rejected — that is the class of incident T-28 recorded★.
3. ★**Make one axis on which each path implementation reports 「지금 보낼 수 있나」**★ — **the decision is made inside each implementation** (codex = a `thread/start` response was received and no turn is running / claude json = no turn is running) and **the axis is shared.** It is not split by backend name.
4. ★**The owner of the release decision is each path implementation — ADR-0193 decided so, and ★there is no per-backend exception★**★. ADR-0190 decision 4 was originally 「턴이 도는가는 **코어가 이미 안다** — 큐는 읽는다」, but ★**ADR-0193 amended that decision and moved the decision inside each implementation**★. ★**This document does not reinterpret that decision — the canon of the reason is that ADR and below only carries over the result**★:
   - ★★**The axis is not 「코어를 읽느냐」 — it is just whether the 「보낼 수 있나」 decision and 「진행 중으로 전이」 happen **inside one lock**★★. `AgentTransport::send_input(&self, …)` is an immutable reference so **concurrent calls are structurally possible** (`crates/engram-dashboard-agent/src/transport/mod.rs:41-45` · §4-1 stands on the same fact), and if the two are split, two calls **both see idle** and each opens a turn — they overlap regardless of which table was read. **Do the check-and-set atomically.** ★That atomicity can be built **only inside the object that holds stdin and the queue together** and that object is the path implementation — that is why the decision lives there, and so it is not a place that can differ per backend★.
   - ★★**The 5th edition wrote a claude json exemption here — that exemption is gone**★★. The 5th edition's sentence was 「claude 는 `input_echo_event` 를 선언해 **쓰는 순간** 턴 신호를 만들어 미관측 창이 없으므로 코어를 읽어도 된다」. ★**That factual sentence is false, and ADR-0193 already stands with that place corrected**★ — we write it as lines:
     - ★**The echo fires *after* `send_input` returns**★ — `write_input_observed` calls `self.transport.send_input(…)?` first (`crates/engram-dashboard-agent/src/session.rs:164`) and **after that** goes `input_echo_event` → `core.emit` (`:175-176`). The comment at that place itself writes 「send_input **성공 후**」 (`:168` · `:174`).
     - ★**So claude json also has an unobserved window**★ — the moment the write goes out and the moment the turn fact arises are apart, and in that window the answer the core gives is idle exactly as with codex (`crates/engram-dashboard-messaging/src/busy.rs:177-180` — if `turn_fact` is `None` then straight to `false`).
     - ★**And removing that window still does not close it**★ — because the concurrent call of the first item above remains. **That is, 「에코가 있느냐」 cannot be the ground of this axis's decision.**
   - ★**No new lock is made**★ — the mutex inside the implementation that §4-1 already requires also carries this transition. ★And **it does not do a blocking write while holding that lock**★ — flushing goes only as far as **putting into** the bounded queue of §4-9 **and releasing the lock at once** (the ADR-0006 lock order: no external call while holding a lock).
   - ★**The codex-side fact stays as is, and what changed is only that claude is not that counterexample**★ — codex does not declare `input_echo_event` so it takes the trait default `None` (`crates/engram-dashboard-agent/src/backend/mod.rs:209-211`) and is unobserved until the first notification arrives. That conclusion (its own turn machine that moves to in-progress **at the very place it sends** — §3) is now **the shape common to both backends**.
   - ★**The queue does not call `AgentManager::turns()`**★ (`crates/engram-dashboard-agent/src/manager.rs:537`) — the 5th edition wrote that the claude json release condition reads that accessor. ★**Since that consumer does not grow, there is nothing to touch in the ADR-0127 accounting either**★ — what that decision fixed is the **two erase call sites** for turn observation, and the reading consumer remains one, the messaging busy gate.
   - ★**§7-4 ④ is not closed by this line**★ — what was closed here is the **release condition of the queue**, and the mail gate **still reads the core.** The unobserved window disappears in the queue and **remains as is in mail** — what closes it is the ①②④ declarations of §7-4.
   - ★**Since nothing is flushed mid-turn, `turn/steer` does not enter this design**★ — the queue flushes **after the turn ends** and the verb then is `turn/start`. If 「턴 중 즉시 반영」 is chosen later, the verb then is `turn/steer` (+ the `expectedTurnId` precondition — S6) and ★not a second `turn/start`★. Rule 5 left that operation out of this scope.
5. ★**All we build this time is the queue**★ — **we do not build operations** such as removing an item · pushing out all waiting items with ESC · reordering. The flushing rule also goes only as far as 「보낼 수 있게 되면 **순서대로**」. Ground = **once there is a queue any operation rule can be added later** (user deferral — 「다른 claude·codex 앱들을 보고 편한 쪽을 판단한다」).
6. **The PTY path is out of scope this time** — its symptom is **T-28**, and that is itself marked as 「수신자 준비됨 신호가 없어 조사부터 시작하는 단독 주제」. Pulling it in would grow 2a.

★**The behavior of claude json mode changes — this is why this discipline is not codex-only and why we got user confirmation**★. Right now claude json pushes input **immediately**. Once a queue exists, **mid-turn input does not go out at once but waits.** ★Do not apply the 「claude 실행 경로는 한 줄도 안 바뀐다」 of §8 to this item★ — that sentence is about ADR-0185's **spawn and restore path**, and this is **write timing**, a different axis.

#### ★The receipt is lumped into one — the meaning of `Ok` is not split★ (user decision · §10-20)

**Adversarial review BLOCKED this place: if `Ok` right after queuing, then even if the writer blocks after the user echo and the delivery success are recorded, the caller cannot hear it. ★We do not resolve that point as 「영수증을 둘로 쪼갠다」★ — it is a user decision, and the reason is 「우편은 보냈고 받는 쪽이 소화한다」.**

- ★**Today is the same bar height — the queue does not lower it**★. The terminal path's `send_input` finishes `write_all` + `flush` **within the call** and the meaning of that `Ok` is 「요청 바이트 **전량 수용**」 (`crates/engram-dashboard-agent/src/session.rs:150-156` · ADR-0088). ★**But whether the receiving CLI read it or acted on it, nobody checks today**★ — that is, **「전달했다, 소화는 상대 몫」 is already this repository's posture**, and the queue does not lower that bar.
- **So the meaning is kept as one** — `Ok` = 「요청 바이트를 **우리가 전량 맡았다**(순서 확정 포함)」 · `Err` = 「안 맡았다」. ★**We do not split 「담겼다」 and 「실제로 썼다」 into two grades to report**★. The mail layer also writes 「전달했다」 as is (the ADR-0088 delivery observation record). ★So the branch of adding an axis to the return type is not even opened — the byte field of `WriteOutcome` is **not an independent measurement but a by-construction copy of `bytes_requested`** so it cannot carry that axis either★ (`crates/engram-dashboard-agent/src/types.rs:663-671`).
- **The three that still return to the original call as `Err` — ★all three diverge *before* answering 「맡겠다」★** (ADR-0190 as is — input is not dropped): ① **queue upper limit exceeded** ② **there is already no way to send at the time of that call** (after this incarnation's connection was already cut and readiness was settled as failed) ③ **the state is ready so it does not go through the queue and the write flushed within that call fails.** ★There is no room to disguise it as `Ok`★ (the **same sentence** as 「짧은 `Ok` 금지」 in §4-9).
  - ★★**So do not read 「준비 실패는 원 호출에 `Err`」 as widened to *after queuing* — the 5th edition wrote that place in two branches**★★. Input that arrived in the initialization window (about 130ms — L1) and **was queued** had already returned as `Ok` at that moment. What ② covers is **only a failure that had already ended at the time of that call**, and a **readiness failure after queuing** goes to the limit item below. ★If the two sentences are stood together this section would say two things★.
- ★★**One thing actually changes — and it is a limit, not a solution**★★. Today the write happens **in the middle of the call** and the failure returns **to that call** as `Err`. Once a queue stands in front, ★**a write that fails after the call has returned has no way back to that caller**★. ★**This document does not make that way — it does not invent a correction channel**★. → the limit row of §11.
  - What remains is **being visible**, not **a way back**: the path implementation holds `core` via `start(core)` so it can put that failure on the output stream as `Error{message}` (an already existing neutral vocabulary — §6), and the frontend draws it as an item and raises `turnDone` to close the waiting indicator (`src/components/slot/structuredAccumulator.ts:101`). ★**But that is something the screen and the LLM see late, and neither the caller that received `Ok` nor the already-written delivery observation record is corrected.**★
  - ★**The 4th-edition sentence that wrote 「그 실패가 연결 = 끊김으로 올라가 세션이 착지한다」 was removed**★ — that landing **has no subject to execute it** (「강제 종료 감시를 만들지 않는다」 of §4-9).
- ★**The echo goes out first — and under this decision that is right**★. The synthetic user echo fires after `send_input` returns as `Ok` (`session.rs:163` → `:175-176`), and since the meaning of that `Ok` is **only 「우리가 맡았다」**, the fact the echo points to is exactly that. ★**So the 「에코를 큐 방출 뒤로 미룬다」 branch is gone**★ — 「`Ok` 가 두 뜻」, the reason to defer, has disappeared. The remaining screen question is the single ★whether 「대기 중」 is shown★, and that is §10-17.

**Is it the same as the bounded writer of §4-9 — we write them apart:**

| | The bounded queue of §4-9 | The input queue of this section |
|---|---|---|
| What it absorbs | A **write itself blocking** (pipe backpressure — the server does not read stdin) | What **has no form to send right now** (before ready · turn in progress) |
| When it releases | When the server starts reading again | **Ready complete** or **turn end** |
| When full | Refuse with `Err` (§4-9) | Refuse with `Err` (2 above) |

★**The two stand in front of the same endpoint — so the implementation may become one lump, but do not lump them into 「같은 문제」**★. If only one exists the other's symptom stays as is: with only the bounded writer, input before ready still has nowhere to go, and with only the input queue, in the 「준비됐다고 신고했는데 쓰기가 영영 안 풀리는」 window **the caller hangs indefinitely.** ★**But even with the bounded writer that stall does not vanish**★ — all that changes is that **the caller returns as `Err`**, and there is still no screen signal (「강제 종료 감시를 만들지 않는다」 of §4-9).

**Four things left open — ★decide at implementation and leave the ground in a code comment★:**

- ★**The queue *length* upper limit and the behavior on excess — the discipline is fixed and only the value is undecided**★. Excess is **`Err`** (① of the three above). ★**There is no tension with ADR-0190 here**★ — because the caller hears **on the spot** when it overflows, and that does not conflict with 「입력을 버리지 않는다」 (dropping = no signal). The value is zero measurement so a number chosen now is invented (the same decision as §4-9).
- ★**The waiting-*time* upper limit — not the same item as above. We separate what the 4th edition tied into one line**★. ★**A time upper limit collides head-on with the 「입력을 버리지 않는다」 of ADR-0190**★: the reason the queue does not release is usually a **legitimately long turn**, and cutting by time **drops an item that was fine and waiting its turn as `Err`** — unlike the length upper limit it punishes not 「넘쳤다」 but 「기다렸다」. And today there is no means to tell 「긴 턴」 from 「영영 안 풀리는 턴」 (the stall of §4-9 is `[미확인]`). ★**So this document's default is 「시간 상한을 두지 않는다」, and to have one the conflict must be resolved first**★ — the connection-cut side is already covered by ② of the three above, so **the remaining case of 「영구히 매달린다」 is only the long turn of a live connection.** → §11.
- ★**The means to tell the screen it is 「대기 중」**★ — **today the frontend has zero of that concept.** The echo appears at once so the input does not look like it vanished, but ★**what is queued and not yet sent cannot be told apart on screen from what has already gone out**★. The scope and shape are a follow-up and this document does not decide them. ★**§10-17 now carries only this one question**★ — the echo-order branch that had been bundled with it was closed by user decision (the section above).
- ★**It overlaps with mail parking in function — and we do not resolve that overlap now**★. Mail parks a letter when the receiver is busy and waits up to the cap (30-minute fail-open). Once the queue exists there are **two waiting places**. **For now we keep the two separate** (user decision — it presumes the mail side will be fixed later). ★**Until that judgment, we go knowing that 「편지가 두 번 대기한다」 can actually exist.**★

## 5. The path — ★the shape for which ADR-0189 fixed the place and ADR-0191 fixed **how to build and hand it over**★

★**This section no longer weighs options.**★ Editions 1 and 2 put four options (가·나·다·라) here and asked 「어느 안이 맞나」, and the recommendations of both editions collapsed **by both assuming a path that does not exist** (§5-8 preserves the shape of those two failures — so the next session does not err the same way). **ADR-0189 closed that fork, and ADR-0191 closed the last hole the 3rd edition left (「그 통로를 누가 만들어 조립점에 꽂나」).** Below are the shapes of the two decisions and what they **do not change**.

### 5-1. The fixed shape — one paragraph

**The codex app-server path is a struct inside `crates/engram-dashboard-agent/src/backend/codex/` and implements `AgentTransport`. The code that builds it is also inside the same folder, and ★the assembly point only receives and uses it and does not know the concrete type by name★** (ADR-0191).

- ★**This decision adds nothing to the shared contract (the six methods of `AgentTransport`)**★ — the session calls only those six exactly as now (`crates/engram-dashboard-agent/src/transport/mod.rs:41-56`). ★The 3rd edition's attempt to add 「읽기 함수 하나」 here was withdrawn★ (§3 — its ground was false and it was not needed).
- **The path-kind axis becomes three** — terminal (`PtyTransport`) · pipe (`StdioTransport`) · **pipe + bidirectional JSON** (this one). ★**Do not tell them apart by backend name**★ — the axis is 「우리 쪽 통로에 무엇을 요구하나」 and not 「누가 쓰나」 (the canon of that decision = the doc of `crates/engram-dashboard-agent/src/backend/mod.rs:113-123`).
- **The PTY codex path of Phase 1 stays alive** — this decision **adds** a path and does not remove the existing one. The same backend comes to have two paths, and the problem that their permission policies diverge is carried by **ADR-0188**. ★But that 「둘」 **diverges starting from the launch argv** — §8 carries that row★. ★★**The input to that fork is now decided — it is the mode field of `AgentCommand::Codex`**★★ (ADR-0194 · the item right below).

#### ★Who builds that path — there is only one switch that tells them apart★ (ADR-0191)

**This repository already has one switch that tells 「어느 backend 냐」 apart** — `backend_for(c)` (`crates/engram-dashboard-agent/src/backend/mod.rs:282`). ★**The path is also decided by that switch, and the assembly point receives its result whole in a single call.**★

- **Today the assembly point goes through that switch again at each phase** — `spawn_agent` draws each of the six, `backend_caps` · `transport_shape` · `input_encoder` · `output_decoder` · `turn_classifier` · `reads_messages` (`crates/engram-dashboard-agent/src/manager.rs:1033-1043`). ★**Those six fold into a single call, and the path rides in that bundle**★. It is the shape in which 「이 백엔드로 세션 하나를 세우는 데 필요한 것」 comes out of one place.
- ★**We do not add a third branch to the central `TransportShape` match of `select_transport` — rejected**★ (`manager.rs:79-99`). Two reasons: ① the place that tells them apart **splits in two** (`backend_for` and that match) ② a function whose own comment writes ★「이 함수는 어느 backend 도 이름으로 모른다(ADR-0004)」★ (`manager.rs:75-76`) **would come to know a backend type by name.** Today the word `codex` appears **0 times** in that file.
- ★★**What disappears is that match and not the enum — the third `TransportShape` variant stands as is**★★ (exactly as ADR-0189 「영향」 wrote). ★**「갈래를 안 더하니 변형도 못 더한다」 was wrong**★ — ADR-0191 removes that shape-keyed creation match **not only for codex but for all backends**, so the match that would become non-exhaustive **no longer exists.** That is, the cost of one variant is **0**.
- ★★**What does that switch look at to tell the paths apart — ADR-0194 fixed that input**★★. **It is a single mode field of `AgentCommand::Codex`** (terminal / JSON). ★That axis is not newly built but **an axis that already exists and is already shared**★ — the values of `crates/engram-dashboard-agent/src/profile.rs:29-37` are already neutral (`Terminal` / `StreamJson`), its comment itself writes 「프로세스 기동 방식(= transport)과 프론트 렌더러를 **함께 가른다**(ADR-0044)」, and ★the gemini backend already borrows that type★ (`crates/engram-dashboard-agent/src/backend/gemini/mod.rs:135` · `:179`). The name that goes outward is also already neutral (`crates/engram-dashboard-agent/bindings/AgentNewArgs.ts:17` = `output_format?: AgentOutputFormat`). ★**It does not conflict with 「백엔드 이름으로 가르지 않는다」 above**★ — what tells them apart is not the backend name but **the mode that session chose**, and the difference of 「같은 JSON 이 claude 에서는 헤드리스 NDJSON, codex 에서는 app-server」 remains inside `backend/<name>/` (ADR-0004 · ADR-0194).
- ★**So after ADR-0191 the shape is not 「생성자를 고르는 스위치」 but a pure declaration axis**★ — a value by which that backend reports 「내 통로는 무엇을 나르나」 in the neutral vocabulary. ★★**But do not write 「그 값에서 caps·렌더 판정이 내려온다」 — that 4th-edition sentence invented a causality**★★: after ADR-0191 **what makes the caps injection value is also the path-creation code of the same backend** (the three sentences of §5-5), and what the frontend's render decision reads is **the single field `output.structured`** and not the shape (`src/components/slot/renderMode.ts:24` — ★the frontend cannot see shape at all★). ★**That is, shape and caps are **two declarations the same backend emits side by side** and not a relation in which the former yields the latter.**★ If the two are declared inconsistent, neither the compiler nor the runtime catches it — ★**that is why the declaration-table tripwire must remain**★, and reading it as 「shape 만 맞추면 caps 는 따라온다」 misses what that net is meant to guard. **Today that axis has exactly two physical consumers** (`rg transport_shape crates/ src-tauri/src/`, non-test) and of those the creation-match side (the `crates/engram-dashboard-agent/src/manager.rs:1235` argument · the `:1241` call) retires with ADR-0191, so ★**the only remaining reader is the declaration-table tripwire**★ (`backend/mod.rs:800-802` — 「transport_shape 불일치 — 위 `expected_codec_axis` 를 따라 **의식적으로 선언할 것**」).
- ★★**So deleting the variant loses that tripwire — that is the place where this edition nearly went wrong once**★★. Without the variant, codex keeps reporting `Pty` and **the declaration table stays green**, and the net that enforced 「이 백엔드의 통로 축을 의식적으로 선언했나」 vanishes. It is **a trade that spares one enum value and sells the regression net** so it does not hold. ★And it would overturn the 「영향」 sentence of ADR-0189 (「`transport_shape` 에 셋째 변형이 생긴다」), so **it is not something the TRD may do on its own**★.
- ★**A precedent already exists — it is not a new shape**★: `backend::output_decoder` (`backend/mod.rs:477`) is the single line `backend_for(c).output_decoder(c)`, and that doc writes the discipline — 「판정도 decoder 실물도 [`AgentBackend::output_decoder`] 가 소유하고 이 함수는 dispatch 뿐이다 … **새 backend 는 자기 폴더에서 그 메서드를 구현하면 되고 이 함수는 손대지 않는다(교체성)**」. The path rides the same shape.
- ★★**The values and order on the claude path are unchanged — zero behavior change is the acceptance condition of this refactor**★★. What folds is **the place that draws**, not the values drawn: injecting `structured: true` while opening the pipe path (`manager.rs:89`), and opening the terminal path, **what was done is done exactly as is** inside each backend's path-creation code.
  - ★★**But do not read it as 「그 match 가 살아남아 이제 백엔드가 그것을 부른다」 — that revives the rejected branch**★★. **The match that picks a constructor by shape (`manager.rs:79-99`) itself retires.** A backend **does not pick its own path by shape** — because it already knows what it opens (that is the meaning of 「가르는 switch 는 `backend_for` 하나」 in the first place). ★If that function is left and the backend calls it passing shape, **the place that tells them apart becomes two again**, and the reason to guard 「이 함수는 어느 backend 도 이름으로 모른다」 (`manager.rs:75-76`) also vanishes★. **What moves over is the *work* those two branches did, not that match.**

**Seven things that struct owns:**

| What it owns | Why here |
|---|---|
| Child process handle + Job Object | It is today's split as is, in which the owner of the process state machine (§3) is the path. `StdioTransport` holds the same two (`crates/engram-dashboard-agent/src/transport/stdio.rs:39` child · `:55` job_handle) |

### 5-2. The inbound branch ends inside that struct — four cases

The reading thread sorts one received line **by shape**. ★The deciding axis is not the id value★ — a server-request id and our request id may overlap in value space (§4-4), and a server response omits even the `jsonrpc` field`[실측]`.

| Received line | What it is | What to do |
|---|---|---|
| `method` **present** and `id` **present** | A server → client **request** | 2a measured **0** (★condition = read-only + `approvalPolicy:"never"` · declared 11 kinds★)`[실측]`. ★**The production value is only half the same as that condition**★ — the value ADR-0192 chose is **write to the working folder + do not ask**, so the approval axis is the same but **the sandbox axis widened** (§10-5). So this row does not lean on 「안 온다」: **if one comes, respond with method-not-found** — ★**if dropped, the other side stops**★. That response **must not pose as success** (it would become auto-approval and bypass the policy — §6-2) |
| **Only** `method` present | notification | **Translate then `core.emit`** — the very work the pump does today |
| **Only** `id` present (accompanied by `result` or `error`) | A **response** to our request | Take it out of the wait map and wake the waiter. ★**It does not go outside**★ |
| JSON parse failure | A non-JSON stdout line | **Only log it and do not die** (§4-6). ★But in this version and this combination there were **0** non-JSON lines on stdout★`[실측]` — even so, not treating it as fatal is the decision of §4-6 |

★**This table makes the 「인바운드를 어느 경로로 보나」 item of editions 1 and 2 vanish entirely**★ — the three that item weighed ((ㄴ) decoder private channel · (ㄷ) `OutputCore::subscribe` sink · (ㄹ) session wait table + a new pump edge) were all costs needed **only when correlation had to be sent outside the implementation.** If correlation ends inside the implementation, **the inter-layer edges are 0.** → §10-14 is closed.

- ★**One placement constraint still remains**★ — **the reading thread does not wait for a response.** That thread is the sole reader (§4-2) so if it waits there, reading stops, and if it stops the server-side bounded queue fills and returns `-32001` (§4-5). So the reading thread **only wakes the waiter** and the one that waits is another thread. This constraint held regardless of the path choice and still holds as is.

### 5-3. The three that were blocked before are gone — and one change that need not be done

The three that editions 1 and 2 wrote as 「막힌 자리」 are **all resolved the moment the path implementation holds state.**

| What was blocked | Why it is gone |
|---|---|
| **Write path** — 「요청 봉투를 누가 만드나」 | The implementation **owns stdin directly**. It passes through neither the session layer nor a static encoder |
| **A place to express 「응답이 안 왔다」** | `send_input` **already returns `Result`** (`transport/mod.rs:45`). No new return axis is needed |
| **Cancel** | `interrupt()` **is already in the shared interface** (`:51`) and this implementation implements it. ★`turn/interrupt` succeeds in a measured 18ms and the same conversation survives as is★`[실측]` — that is, cancel does not require process exit |

★**And the change with the widest ripple becomes entirely unnecessary**★ — 「입력 인코더를 세션마다 상태 갖는 객체로 바꾼다」. The reason that option was needed was that the `turn/start` envelope needs three (**per-session state** · **an outbound id counter** · **an error path**) and today's encoder seam has none of the three:

| Fact | Line |
|---|---|
| What the contract carries is always bytes — `InputEvent` has only one variant (`Raw(Vec<u8>)`) | `crates/engram-dashboard-agent/src/types.rs:73-75` |

### 5-4. ★Why the 2nd-edition review BLOCKED this shape, and the ground on which that decision was overturned★

### 5-5. `transport_shape` third variant — ★now a **declaration** and not a creation switch★

**The third variant stands** (ADR-0189 「영향」). ★**What changed is what that value does**★ — after ADR-0191 removed the shape-keyed creation match, that value **does not pick a constructor** and becomes a **declaration** by which that backend reports 「내 통로는 무엇을 나르나」 in the neutral vocabulary (§5-1). ★**That declaration does not yield the caps or the render decision**★ — caps is also a **separate declaration** the same backend injects side by side and the frontend reads only `output.structured` (that item of §5-1). ★**The sole reader of shape is the declaration-table tripwire**★ — that is, what this value does is the single thing of enforcing 「그 백엔드가 통로 축을 **의식적으로** 선언했나」.

- **The codex backend today declares no path axis at all** — `transport_shape` takes the trait default `Pty` (`backend/mod.rs:126`), and `output_decoder` takes the default `None` (`:219-221`). When the app-server mode stands, **a translator is attached and the path shape diverges** — the two axes move together, and **both must be declared.**
- ★**The declaration-table tripwire enforces it — and half of why the third variant stands is this**★ — the codex row of `expected_codec_axis` is written today as `(InputEncoder::Raw, false, TransportShape::Pty)` (`backend/mod.rs:779`), and the test that checks it is `codec_axis_is_consciously_declared_for_every_backend` (the same file · the shape assertion is `:800-802`, the message is 「**의식적으로 선언할 것**」). ★**If that row is not updated in the same commit, that test turns red**★ — it is not an accident but **intended friction** (so the declaration axis cannot be changed silently). ★If the variant is not set up, codex keeps reporting `Pty` and **this net stays green and catches nothing**★.
- ★★**But that table has one hole, and ADR-0194 made it a *real* hole**★★ — because the mode is carried **not as a separate variant but as a field of `AgentCommand::Codex`**. The table's key is **one variant** of `AgentCommand::Codex { .. }` (`backend/mod.rs:779`) so **two modes fold into the same line, and it is green if only one mode matches.** ★**So filling that hole in the same change is a requirement — if not filled, that test is green and measures nothing**★ (§8 carries that row). ★The precedent is right next door★ — claude's mode is also a field yet the table is split into **two lines per mode** (`:763-774`) and the sample carries both (`:704-722` · its comment `:703` writes 「claude 는 모드가 둘이라 둘 다 싣는다(같은 슬롯 — 중복은 허용)」). ★★**But nothing enforces that second sample**★★ — the coverage array is **per variant** (`BACKEND_VARIANTS = 3` · `variant_slot` `:684`) so carrying only one mode passes the 「슬롯 전부 채움」 assertion, and what the three-gate explanation of the same file (`:672-679`) counts is also a **new variant** and not a new mode.
- **The assembly point does not pick a constructor by shape** — it uses the path the backend built and handed over as is (§5-1 · ADR-0191). ★**And the answer to 「챗 표면에 그리나」 is decided together at the same place**★ — if the codex path-creation code **loads** `output.structured = true` into caps, the frontend picks `rich` from `src/components/slot/renderMode.ts:24`. **It rides onto the chat surface without writing one line of frontend code** (§7-3 · §10-4). ★**But do not read that as 「shape 를 선언했으니 따라온다」**★ — what follows is **because caps was injected** and shape is the line next to it (the item above). #### The axis that honestly reports capability — ★where the lever attaches: ADR-0191 closed it★

The `input`/`output`/`control` of `Capabilities` are **owned by the transport** and the backend cannot fill them (ADR-0030 · `crates/engram-dashboard-agent/src/types.rs:477` `Capabilities::compose`). ★**An explicit prohibition is placed on that one field — the implementation does not hardcode it**★. Two places write it: the path field comment (`transport/stdio.rs:47-49`: 「★조립점 주입(ADR-0044/0030)★ … **하드코딩 금지** — 평문 stdio 엔 false」) and the assembly-point doc (`manager.rs:69-73`: 「파이프 자체는 내용을 모르므로(통로 무정제 불변) StdioTransport 는 structured 를 하드코딩하지 않고 이 지점의 주입값을 받아 caps 로 신고한다」). ★**Since that value flows to both the screen branch (`renderMode.ts:24`) and the mail proxy (`LiveAgent.turn_signal` — `crates/engram-dashboard-daemon/src/messaging_host.rs:104`), it is not a field to handle cheaply.**★

★**The decision (ADR-0191 closed it) — it is three sentences, and the four places of this document all say these sentences**★ (§5-5 = here · §7-2 · §8 · §10):

1. ★**The path implementation does not hardcode caps. It receives them by injection at creation and reports them as is.**★ — it is today's discipline of `StdioTransport` as is, and the new struct is no exception.
2. ★**What makes that injected value is that backend's path-creation code**★ (inside `backend/codex/`). 「이 통로가 구조화 스트림을 나르나 · 키 입력 바이트를 받나 · 인터럽트가 되나」 is **backend/mode knowledge**, and what ADR-0044/0030 forbade is **the pipe deciding it by itself** and not the backend deciding and injecting it (the assembly-point doc itself writes so with 「claude `--output-format`(backend/mode 지식)이 정한다」).
3. ★**The assembly point neither makes that value nor knows the path's concrete type.**★

- ★**The 「레버가 어디 붙나」 the 3rd edition left open as §10-11-a is closed by this**★. The 3rd edition's mismatch was that it was ambiguous whether 「생성자 인자를 넓힌다」 pointed at `StdioTransport::open` or at the new struct's constructor, and after ADR-0191 **neither is the answer** — the lever is **the path-creation code inside the backend folder**, and `StdioTransport::open` is that of the claude json and plain-text paths and **does not change by one character** (a codex session does not pass through that file).
- **So the codex session's report stands like this** — `input{raw:false, message:true}` · `output{structured:true, …}` · `control{interrupt:true}`. ★What the value is is a matter of honesty, and **who makes it** is the three above.★
- ★**「caps 한 칸을 바꾸려고 `TransportShape` 변형을 또 세우지 않는다」 remains valid as is**★ — the third variant stands because **the path kind really differs** (ADR-0189), and what diverges in value on top of that is absorbed by **injection**. ★If the reason to call a fourth is 「caps 한 칸」, it must go to injection★.
- ★**For the first time there is an implementation in which `interrupt()` actually works**★ — today `StdioTransport::interrupt` is `Unsupported` (`transport/stdio.rs:316-321`). ### 5-7. What this decision **does not touch** — invariant check

### 6-2. `Structured{kind,json}` escape hatch — ★not used as the default outlet★

**First one measurement — the first edition's prescription puts codex protocol words on the screen:**

| Fact | Line |
|---|---|
| When the accumulator receives `Structured` it puts `kind` into an item **carrying it as is as `label`** — 「알 수 없는 종류(kind)도 흘려 유실 방지」 | `src/components/slot/structuredAccumulator.ts:125-126` (variant declaration = `:27-28`) |
| The renderer draws every label that is not `thinking` as `GenericItemRow` | `src/components/slot/StructuredTextView.tsx:397-400` |
| That row **prints the label on screen in monospace** and, when expanded, shows the **JSON original as a code block** | Same file `:279-304` (label = `:295` · JSON = `:299`) |

★**So 「모르는 알림 이름을 `Structured` 로 흘린다」 is in effect putting a codex method name such as `item/reasoning/summaryTextDelta` and its payload on the user's screen.**★ That is exactly what this project forbade (`trd.md` §6-1 user decision — 「번역기가 덜 채워져서 원본 JSON 이 화면까지 가는 것」), and the first edition **prescribed** it in 3 of §4-7 and the last two rows of §6-1.

**The corrected discipline — the outlet splits into three:**

| What came | Where to | Does it appear on screen |
|---|---|---|
| A known name · a known shape | The neutral vocabulary of the translation table (§6-1) | ✓ in the neutral vocabulary |
| **An unknown notification name** (= a line with only `method` and no `id`) | ★**Log + discard**★ — `deprecationNotice` also goes here | ✗ |
| ★**An unknown inbound request name** (= a line with both `method` **and** `id`)★ | ★**It must not be dropped — return a bounded error response**★. The item below is the ground | ✗ (there is still no screen vocabulary) |
| A known name but **the shape differs** | Log + discard. ★**This is a defect**★ — tolerating it silently becomes the silence §4-7 warned about. ★**But if that line has `id` the row above wins — a response is emitted before discarding**★ | ✗ |
| `Structured{kind,json}` | ★**Only those whose `kind` we know and have decided to draw on screen**★ | ✓ in the decided shape |

★**Applying 「로그 + 버림」 to notifications and requests alike makes the agent stop — the first edition did not tell these two apart**★

- **A notification may be dropped.** Nobody waits for an answer.
- ★**Dropping a request is a permanent stall.**★ That approval is of that class was already written in the last line of §6-1 and in §5-1 (D1 — if we do not answer the agent stops), but ★that decision hung **only on the five we know**★. If upstream adds a sixth request (D5 shows that precedent — `newConversation` → `thread_start`), it comes in as 「모르는 이름」, rides the 「버림」 of the row above, and **that agent stops right there.** Nothing appears on our screen and only one log line remains.
- **So the discipline:** ★**if the received line has both `method` and `id`, then even when we do not know that name, we return one error response with that `id`.**★ The content can be 「이 메서드를 모른다」 alone — since the envelope is what we define (S1), the error code is also ours to choose. That response must not pose as success (it would become auto-approval and bypass the policy of §10-5).
- ★**This is the same axis as the deciding axis of §4-4**★ — the pair of 「`method` 유무로 대기표 조회를 게이트한다」 is 「`id` 유무로 응답 의무를 게이트한다」. If the two axes are not decided in one place, one of them is sure to go out of line.
- ★**Price:** that error response itself stands on `[미확인]`★ — we have never seen how the app-server accepts an unknown-method error (whether it folds that turn into failure · whether it ignores it). **Even so it is better than 「버림」** — the outcome of dropping is a permanent stall and it gets the same decision as §4-5. It is left in §11.

★**The decision in one line (still valid):** if the screen is right only when the frontend `JSON.parse` what was let flow as `Structured`, then that is not an escape hatch but a deferred translation.★ `Structured.json` is a **string**, so if the frontend parses it **at that moment the frontend comes to know the codex schema.** That is what has already happened with claude today (`extractUserUuid` parses the uuid of a claude replay line — `structuredAccumulator.ts:111`).

**Then what breaks the silence §4-7 worried about — we write the price honestly:**

- The first edition's argument was 「모르는 이름이 화면에 원본으로라도 보이면 침묵이 깨진다」. **Moving that signal from the screen to the log is the price of this change** — the user does not see it, and the one who sees it is the one who opens the log.
- ★**So we do not end with one log line**★: ① an unknown name is left **once per name only** (spam prevention) ② that counter is made visible in diagnostics ③ it goes through the masking path as is (`transport/stdio.rs:24` imports and uses `engram_dashboard_base::logging::mask_secrets`).
- ★**And §9 catches that silence automatically**★ — since the translation-table golden asserts 「아는 이름 전부가 중립 이벤트를 낸다」, if upstream changes a name **the golden turns red.** This comes earlier than screen observation. (That golden covers only names we know, so for **a newly appeared name** the log is still the only signal — we leave that limit.)
- ★**If §10-6 is chosen as 「안 늘린다」, the three axes of §6-1 (reasoning · tool results · interrupted) become 「버림」 under this discipline**★ — that is, the price of that decision changes from 「화면에 원본이 보인다」 to 「화면에 안 보인다」. The §10-6 row carries that fork too.

#### ★And the answer to 「그럼 화면으로 보내면 되지 않나」 — **the frontend has no door that receives the unknown at all.** We traced it down to the pixel★

These three **reinforce** the decision above. 「로그로 보낸다」 reads as giving up the screen, but ★in fact there is no door on the screen side to send to.★

1. ★**An unknown top-level `StructuredEvent.type` simply vanishes — but it takes the spinner with it**★. In the `consume()` switch of the accumulator ★**there is no `default:` arm**★ (`src/components/slot/structuredAccumulator.ts:66-138`). An unmatched `type` puts no item · raises no `nextId` · touches no `turnDone` · and there is no throw, no warn, no counter. **But the caller behaves as if something came** (`src/components/slot/RichSlot.tsx:153-167`): the seq high-water mark advances first (`:156`) · `setItems([...acc.snapshot()])` makes **a new array reference with the same content** and fires a re-render + auto-scroll (`:165` · the scroll effect `:221-224` with deps `[items]`) · ★**`setAwaiting(false)` turns off the 「첫 토큰 대기」 indicator** (`:167`)★. ★**Pixel outcome = 「화면은 이전과 한 픽셀도 다르지 않은데 스피너만 사라졌다」**★. And the release WebView2 has no devtools so `console` cannot be seen either (that is the reason `ConnectionNotice` exists — `src/components/layout/ConnectionNotice.tsx:3-5`). ★**That is, 「우리가 이 이벤트 모양을 모른다」 and 「에이전트가 아무 출력도 안 냈다」 look identical on screen.**★
2. ★**A new frame tag is silently dropped before the client even sees it**★ — `src/api/wsFrame.ts:35` drops everything other than `0`·`1` into `null` (255 takes a separate path) and the two carriers `if (!f) return` (`src/api/tauriTransport.ts:339` · `src/api/wsTransport.ts:294`). There is no log or counter. ★**Until that line is fixed, the `tag=2` stream cannot be told apart from 「한가한 에이전트」.**★ → That is, the branch that reads §10-6 as 「새 태그를 만든다」 **is the work of also fixing one frontend line**, and that line is not in §8 "What is fixed" (it is brought in when §10-6 opens).
3. ★**The only door there is is `Structured.kind`**★ — an unknown `kind` draws **label + JSON original** as `GenericItemRow` (`structuredAccumulator.ts:125-126` → `StructuredTextView.tsx:397-400` → `:279-304`). ★**So the only realization path of 「미지를 화면으로」 is exactly what this section forbade**★ — there is only one door and that door prints the codex method name on the screen. The two cannot be had at the same time.

★**Conclusion: 「로그로 보낸다」 is not a choice that gave up the screen but the only choice that remains because the screen side has no door that safely receives the unknown.**★ To open a door one must newly write the `default:` arm of (1) or the tag pass-through path of (2), and **both are outside this document's scope** (the Phase 3 frontend withdrawal). → That fact is left in §11.

**Vocabulary ownership (as is):** the `kind` string is decided by the backend, and its interpretation declaration is carried by Rust `turn_classifier` (`backend/mod.rs:143`). **We do not make branches per `kind` in the frontend.** The ground is already written by that function's doc — 「공용 층에서 해석하면 한 백엔드의 관례가 전원에게 강제된다」 (`backend/mod.rs:130-137` · ADR-0113).

### 6-3. ★Ordering constraint — a received thread id is persisted before the first turn is allowed★

It is a Phase 2 requirement of ADR-0185 「영향」, and **that ADR stamped it as 「아직 불변식이 아니다 — 성립한 불변식으로 인용하지 말 것」.** The reason design becomes possible here = that **2a is the only stage that owns that response**.

```
thread/start 요청 전송
      ↓
ThreadStartResponse 수령 → thread.id                       [스키마 S3 · 실측 0]
      ↓   ★★★ 이 구간이 위험 창 ★★★  (무엇이 위험한지는 바로 아래 — 「못 잇는다」가 아니다)
ProfileRegistry::observe_session_id(agent_id, thread.id)   profile.rs:629
      ↓   (mutate_if → 변경 즉시 persist — 그 함수 doc :626-628)
여기서부터 turn/start 를 허용한다   ← ★그 게이트는 오늘 없다. 만드는 것이 2a 의 일이다★
```

#### What actually breaks in that window — ★the first edition wrote it wrong★

The first edition wrote 「여기서 죽으면 그 대화를 영영 못 잇는다」. **That is the story for a first conversation, and it missed the worse side.**

★**When a stored sid already exists** (every second and later conversation of that agent) — if it dies inside the window, **the old sid stays as is, and the next activation silently reattaches to the old thread.** The newly made thread becomes an orphan.★ Ground = the two activation entries derive `SpawnMode` **from a single fact, whether a stored sid exists**:

- The local command entry — if `profile.backend_session_id.is_some()` then `Resume` (`crates/engram-dashboard-agent/src/commands.rs:521-526`, `activate_profile` call = `:526`). ★**The sentence that pins down the sameness of the two entries is here**★ — the comment right above that fork: 「★모드 유도 규칙은 WS 경로와 같은 것을 쓴다(ADR-0076)★: 저장된 세션이 있으면 이어받기, 없으면 새로. 여기서 다른 규칙을 쓰면 같은 에이전트가 어느 입구로 깨우느냐에 따라 대화 이력을 잃는다」 (`:519-520`). ★**The first edition attached this citation to the WS line below but it is not in that place — the WS-side comment is a different sentence**★ (right below).
- The WS entry — if `resume || profile.backend_session_id.is_some()` then `Resume` (`crates/engram-dashboard-daemon/src/connection_core.rs:1126-1130`, `activate_profile` call = `:1131`). The comment there is 「★모드 = 세션 존재 여부로 유도(ADR-0076)★ … 저장된 세션이 있으면 wire `resume` 플래그(프론트는 false 로 보낸다)와 무관하게 **항상 Resume** 이다」 (`:1115-1117`), and then it attaches ★「단 '안전하다' 고 읽지 말 것」★ (`:1121-1123`).

★**So the outcome is 「조용한 오답」 and not 「오류」**★ — the user sees that the continuation worked, and only the conversation just held disappears. This is **the surviving half** of survey report BLOCKER B1 and is what ADR-0185 passed on to Phase 2.

#### Where to put the gate — ★the only place that can enforce it★

**We write as lines why there is zero means of enforcement today:**

- The session **gets onto the registry before the pump is launched** — `sessions.insert` comes before `session.start_pump()` (`crates/engram-dashboard-agent/src/manager.rs:1322` → `:1337`, ADR-0019 pinned that order as intended). That is, **from right after spawn it is possible to write to that session.**
- And there is not a single condition on the write path — `AgentSession::write_input_observed` encodes at once and `send_input` at once (`crates/engram-dashboard-agent/src/session.rs:156-165`).
- The name `turn/start` is nowhere in this repository's **code** (`rg "turn/start" crates/ src/ src-tauri/` = 0 lines). ★**Do not write 「코드·문서에 없다」 — it is in the documents**★: ADR-0185 itself and this document use that name (§1 already wrote the same correction — do not write the two places apart). **That there is no means of enforcement is a fact on the code axis.**
- The only production caller of `observe_session_id` is the claude `/clear` watcher (`crates/engram-dashboard-daemon/src/lib.rs:288`). That watcher cannot become codex's receiving path (§1). ★**And that function has no incarnation guard**★ — `observe_session_id(&self, id, new_sid)` does not take a `incarnation` argument (`crates/engram-dashboard-agent/src/profile.rs:629`) and **unconditionally** overwrites if the value differs. `set_last_failure` of the same registry takes `incarnation` (`:575-583`) — ★an asymmetry, and it is the second unclosed gap beside 「그 창에서 죽는 것」 of §9-3★. A late observation from a dead incarnation can overwrite the live incarnation's sid. **2a does not build this guard** (the receiving wiring is Phase 2b — §0) → §11.

★**So the gate is carried by the codex path implementation**★ (ADR-0189 · §5-1) — since that object is **the only place that makes `turn/start`**, it is the only place that can see the condition.

#### ★Can that implementation reach the profile — the writing hand is closed and the reading hand remains★

**Editions 1 and 2 did not look at this door at all.** The value the gate must look at (`backend_session_id`) and the verb the gate must call (`observe_session_id`) both belong to `ProfileRegistry`, but that registry is not in the `backend/` tree. As lines:

- `rg "ProfileRegistry|profiles" crates/engram-dashboard-agent/src/backend/` = ★**0 lines**★ (non-test). What the backend receives is only `&AgentCommand` and the spawn arguments, and the registry is on the opposite side.
- And **it cannot be obtained from outside either** — `AgentManager` hands out `pub fn turns()` (`crates/engram-dashboard-agent/src/manager.rs:537`) and `pub fn presets()` (`:541`) but ★**has no `pub fn profiles()`**★. The doc of that field writes that non-disclosure as intended with 「프로필 단일 소유자」 (`:361-362`).

★**The writing hand = ADR-0189 closed it**★ — it is **a callback the assembly point gave** and the backend does not call the registry directly. A precedent exists as is: `Arc::new(move |agent_id, new_sid| { profiles_cb.observe_session_id(agent_id, new_sid); })` (`crates/engram-dashboard-daemon/src/lib.rs:284-290`). ★**A closure holding only one verb and not the registry itself**★ — so the assembly point does not come to know the backend (§5-6).

★**What remains is the reading hand**★ — since that precedent is **only the one write direction**, there is no verb that asks 「이미 기록됐나」. **Two branches** (the values below, the choice is §10-16):

| Branch | What changes | What it puts at risk |
|---|---|---|
| **(A) Widen the callback to two verbs** — 「읽는다 / 기록한다」 | The closure built at the assembly point goes from one to two. **An extension of the precedent and not a new axis** — it attaches to the line where `spawn_agent` draws and sends down on the spot the six backend-derived facts (`manager.rs:1033-1043`) | ★**The port name must be neutral**★ — if it is 「codex 용」, the assembly point comes to know the backend and ADR-0004 leaks |
| **(B) The implementation remembers only 「자기가 방금 기록했다」** | Nothing — it does not ask the disk | ★**That this is enough is the conclusion of the section below**★ — the honest name of the gate condition is already 「반영 호출이 돌아왔다」 so **there is no need to ask the disk.** But **after a restart** that memory is gone, so a 「이미 있는 sid 로 resume 한다」 path must stand separately |

★**Branches (B) (the session layer notifies only 「준비됐다」) and (C) (put the gate in the session·manager layer) that editions 1 and 2 set up are dead**★ — both held only on top of leaving 「조건을 볼 수 있는 층이 어디냐」 undecided, and ADR-0189 fixed that layer. ★Do not pull them out again★ — (C) is also already closed by the original reason of §6-3, that those layers do not know the backend so they have no vocabulary to ask with.

- **Rule:** the path implementation emits the first `turn/start` **only after** the `observe_session_id` reflection call **has returned.** If user input arrives before that, ★**it is put in the queue of §4-10**★ — **neither refused nor silently passed through** (ADR-0190 closed that fork).
- ★**The gate condition is one — the 3rd edition's second condition is gone**★. The 3rd edition wrote 「조건만 둘(persist 완료 · **미확정 턴 없음**)」, but its second had meaning only on top of the **design where the same path reattaches after a restart.** After ADR-0192 removed it, ★**the path implementation of a new incarnation is born holding no undetermined turn so that condition is always true**★, and putting an always-true condition on a gate makes the next session read it as 「무언가를 막는 것」. **So we delete it.**
- ★**The one condition that remains still carries the 「같은 지점」 discipline**★ — the decision of 「지금 `turn/start` 를 낼 수 있나」 is made **in one place only, the path implementation.** Even if more reasons attach to that decision (「턴이 도는가」 of §4-10 is one) **the place is not increased** — if split between two places one is sure to be bypassed.
- ★**This condition is not put in the session layer**★ — that layer does not know the backend (ADR-0004) so it has no vocabulary to ask 「persist 됐나」 with. ★**But the sentence of editions 1 and 2 that wrote 「transport 에도 두지 않는다」 is deleted**★ — after ADR-0189 **the object that carries that condition is the transport implementation itself.** What that sentence was aiming at was the **general-purpose pipe** (`StdioTransport`), and that side still does not know this condition.
- **We make no new field, new mapping or new file** (ADR-0185 decision 2) — the mapping between our id ↔ backend id is **the profile record itself**.
- ★**`observe_session_id` is atomic only after it is called**★ — ADR-0185 「거부한 대안」 states that explicitly. The gate above **cannot narrow the window** — the window is between 「응답 수령 → 호출」 and the gate stands **after** it. ★What the gate blocks is 「persist 전에 턴이 나가는 것」, and it cannot block 「그 창에서 죽는 것」.★ The recovery of the latter remains as `[미확인]` (§11).
- ★**If the id did not parse as `Uuid` this whole picture would have been blocked — ★that risk is closed★**★: it was measured that the received value is **a UUIDv7 and `thread.id == thread.sessionId`** (§2 L4). It goes as is into the `backend_session_id: Option<Uuid>` (`profile.rs:165`) field — ★**two of the four rows the §9-1 first gate meant to measure got their answers here**★ (id receipt · type). The remaining two = 「id 가 턴마다 재발급되나」 (it was not so — the second turn ran with the same `threadId`) · 「`thread/resume` 이 재기동 뒤에 서나」 (★still `[미확인]`★).

#### ★What that gate can actually assert — it is not 「persist 됐다」★

**The condition name of this gate is 「persist 완료」, but today there is no means to confirm that fact. We write it as lines.**

- `observe_session_id` returns `bool` but the meaning of that value is 「**메모리 맵이 바뀌었다**」 — `mutate_if` returns the closure's decision (`changed`) as is (`crates/engram-dashboard-agent/src/profile.rs:400-409` · `:629-641`). ★**It is not 「디스크에 닿았다」.**★
- In between `store.save(&snapshot)` is called (`:406`) but ★**that function returns `()` and swallows the failure**★ — the contract itself writes so: 「전체 스냅샷을 atomic 하게 저장. **실패는 구현 내부에서 로그만 — 호출자를 막지 않는다**」 (`:310-311`), and the physical form is the single line `tracing::error!` (`crates/engram-dashboard-agent/src/persistence/mod.rs:102-103`). **Nothing goes to the caller · UI · LLM.**
- And today that `bool` is **discarded** — the only production caller does not look at the return value (`crates/engram-dashboard-daemon/src/lib.rs:288`).

★**So the honest name of the gate condition is not 「persist 완료」 but 「수령 → 반영 호출이 돌아왔다」.**★ That is the most this repository can express today, and putting 「디스크에 있다」 on top of it would be **citing a guarantee that does not exist.** To require even disk confirmation, the **return type of `ProfileStore::save` would have to change**, and that overturns the stated contract sentence of that trait (`:310-311`) — ★not 2a's job★. It is left in §11.

★**And do not cite this section as 「첫 턴 전 persist 는 성립한 불변식이다」**★ — ADR-0185 forbade that citation. What is here is **a requirement + the place to hang it**, and a condition becomes an invariant when §9 catches it with an assertion that can fail. ★The section above even decides the **ceiling** of that assertion★ — what §9-3 can measure is 「반영 호출 전에 `turn/start` 가 안 나간다」 and 「그 값이 디스크에 있다」 cannot be measured by any assertion.

## 7. Frontend representation — handling gaps 1·2·3 + readjusting the turn-observation promise

★**The two render paths already exist and already diverge by capability and not by backend name**★ — it is not something 2a will build but something to **keep**.

### 7-1. Gap 1 — a claude convention is embedded in the frontend accumulator

**What exactly breaks (three):**

1. **User echo dedup** — `structuredAccumulator.ts:110-114` pulls a uuid out of the json of `Structured{kind:'user'}` and skips duplicates. If `kind:'user'` is entirely absent from the codex stream, dedup does not run and is **harmless.** But if it is present with a different uuid shape (or in a different place), **the same content appears twice on screen.**
2. ★**The waiting indicator briefly turns off — it is not 「idle 로 보인다」. The first edition got this item wrong in two places**★.
   - ★**Wrong fact ①: 「`:123` 이 turnDone 을 내리는 유일한 지점」**★ — **there are four assignment sites** (all read): `:77` (`TextDelta`) · `:88` (`ToolCall`) · `:123` (`Structured{kind:'user'}`) · `:154` (`reset()`). The places that raise it are two = `:101` (`Error`) · `:136` (`MessageDone`).
   - ★**Wrong fact ②: the symptom**★ — if codex does not emit `kind:'user'`, that frame does not come at all, and the first actual delta lowers it at `:77`. **So 「응답 대기 중 화면이 idle」 is not codex's default symptom.** The actual symptom is the **flicker window** that source comment named.
   - **The mechanism of that window — as lines:** `streaming = awaiting || (!turnDone && items.length > 0)` (`src/components/slot/RichSlot.tsx:270`). On send `setAwaiting(true)` (`:238`), and then ★**when one tag1 frame arrives, whatever it is, `setAwaiting(false)`**★ (`:167`). So **if the first frame does not lower `turnDone`**, at that moment `streaming` falls to false and the waiting indicator (WaitRow) turns off — until the first actual token arrives. The source writes that causality as is: 「합성 user 에코가 awaiting 을 해제하는 순간 … 파생 streaming 이 false 로 떨어져, 첫 assistant 토큰 전까지 대기 인디케이터(WaitRow)가 깜빡 꺼진다(후속 전송 flicker)」 (`src/components/slot/structuredAccumulator.ts:117-122`). ★**`:123` is a patch that closes that window in claude, and it is not 「유일한 지점」.**★
   - ★**So the conditions under which that window reopens in codex are exactly two, and both are already in the §6-1 table**★:
     - **`Usage` comes first** — it is the `thread/tokenUsage/updated` → `Usage` mapping (§6-1), but the `Usage` arm ★**touches `turnDone` not by one line**★ (`structuredAccumulator.ts:90-97`). If that is the first frame of the turn, the spinner turns off.
     - **An unknown top-level `type` arrives** — there is no `default:` arm, so it does nothing (that section of §6-2) and fires only `setAwaiting(false)`.
   - ★**Design consequence (this document's actual product):** the translator must carry as a contract that **the first tag1 frame of a turn must lower `turnDone`** — or it must not emit that frame at all.★ That is one of the assertions that must be pinned when §10-2 (가) says 「테스트로 박는다」, and ★**the first edition's description of (가) did not have this assertion**★ (it wrote only two, 「`MessageDone` 턴마다 1회」 and 「새 턴 시작 신호」).
3. **The turn boundary splits or disappears** — `:129-132` presumes 「decoder(backend claude.rs)가 claude 결과 한 줄·한 턴마다 `MessageDone` 을 정확히 1회 발행한다」 and uses it as ★the only trustworthy turn boundary★ (the same comment wrote a re-litigation guard, saying that changing to `turn_id` is 「현재 always-None 이라 경계가 사라짐」). If the codex translator emits one per `turn/completed` it is correct, and if it emits one per `item/completed` **one turn splits into several boundaries.**

★**And there is no capability field for the frontend to ask**★ — a field reporting this convention is in none of the five areas of `Capabilities` (`crates/engram-dashboard-protocol/src/domain.rs:23-77`). That is, the frontend **has nothing it can do other than assume the claude convention without knowing.**

| Option | What | Price |
|---|---|---|
| **(가)** | **Define the neutral vocabulary's contract strictly and have the backend translator keep it** — pin **three** not in comments but in tests: ① 「`MessageDone` = 턴 경계, 턴마다 정확히 1회」 ② 「새 턴 시작 신호」 ③ ★**「한 턴의 첫 tag1 프레임은 `turnDone` 을 내린다(또는 내지 않는다)」**★ — ③ is the assertion newly found by item 2 above and was not in the first edition | The claude decoder must also be **re-confirmed** against that contract (today that contract exists only in comments). We must draw where it diverges from 「전면 회수」, pushed to Phase 3. ★③ is a **frontend-side assertion** so its place is `src/components/slot/structuredAccumulator.test.ts`, and it **goes in a different lane** from the two above (Rust golden)★ — we add that row to §9-3 |
| **(나)** | **Promote the claude convention to a capability field** that the frontend reads (e.g. a field reporting the turn-boundary axis) | A wire change (§10-6) + ★**it enlarges gap 2**★ — one more field no one reads, or one more branch in the frontend. | **(다)** | Make **the frontend tolerant of both conventions** — make dedup hold even without a uuid, derive the turn boundary from several signals | ★It becomes **code that is exact on no backend**★. ★**Decision = (가) — the user chose it**★ (§10-2). Three grounds: ① the root of the problem is 「번역기가 덜 채워져 원본 JSON 이 화면까지 간다」 and that diagnosis is already written as a user decision (`trd.md` §6-1) ② it does not enlarge gap 2 ③ pinning the contract in tests means **a third backend does not ask the same question again.** ★**And the user pinned one more thing — it is not 「걸러 낸다」**★: the echoed user item is **material for reviving the screen at reattach** so it is not discarded, and **if the translator marks it as 「우리가 보낸 것」 the frontend reads only that mark.** ★On the claude side it is 「이미 참인 것을 적는 것」 and not 「바꾸는 것」, and the full withdrawal is still Phase 3★.
