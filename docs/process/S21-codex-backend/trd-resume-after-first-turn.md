## 1. Problem

**P1 — on a codex resume, the chat slot shows the 「새 에이전트」 first screen for 1.2–2.2 seconds and then it disappears.** Measured 4/4 (GUI). A claude resume does not flicker, and a new codex correctly shows the first screen.

- Timeline (ms from reactivation): registry published 32–183 → Subscribe → `ReplayComplete` at +10 with 0 replay frames → **first screen** → `initialize` 341–587 → `thread/resume` 1393–2243 → first live frame = `Usage` (seq 0) → first screen disappears → `thread/items/list` +20–70 → history renders. The dominant term is codex's own `thread/resume` round trip.
- Causal chain:
  1. `manager.rs:1447` publishes the registry right after `spawn_session` (registration `:1890` → `start_pump` `:1902` → `session.rs:153` `transport.start`).
  2. The frontend re-attaches → the daemon replays the ring synchronously and emits `ReplayComplete` (`connection_core.rs:1773` · `:1821`).
  3. claude seeds the history into the ring **before** publishing (`manager.rs:1375` `resume_transcript_events` → `:1834` `core.seed`). codex puts it in **through the transport, after publishing** — the `transport.rs` `writer_loop` takes the budget (`:1441`) and runs handshake · `thread/resume` (`:810`) → records the id (`:1455`) → history via `thread/items/list` (`:931`, insertion point `:1483`) → gate (`:1493`).
  4. `RichSlot.tsx:190` `replayDone = state==='live'` · `:290` `showEmpty = replayDone && !hasSent && items.length===0` — 「복원 끝 + 0건 = 새 에이전트」 (restore finished + 0 items = new agent).
- ★ADR-0145's premise (「복원 끝 + 0건」 (restore finished + 0 items) tells a new agent apart exactly — `0145:37`) was **silently broken by ADR-0204**★. ADR-0204 does not mention the first screen, `ReplayComplete`, or ADR-0145 (the cost it accepted is other things, at `0204:45-53`). The 2026-09-22 handoff memo's 「ADR-0204 가 알고 수용했다」 (it knew and accepted it) is wrong.

## 2. User decisions (2026-09-23/24 — implement exactly as stated)

- **D1.** The session id is persisted **only after the first conversation** — common to all backends and modes (claude·codex × JSON·terminal). claude keeps the id drawn at spawn **in memory only** and persists it at the first conversation. 「저장된 id 가 있다 ⟺ 이어받을 대화가 있다」 (A stored id exists ⟺ there is a conversation to resume) becomes one rule. Mode selection already splits on whether an id exists (`can_resume_profile` = resume axis ∧ id exists, `backend/mod.rs:704`; entrances = `manager.rs:1942` · `commands.rs:574` · `connection_core.rs:1385`) — that is not changed. No id → Fresh.
- **D2.** The chat slot receives 「이 화신이 대화를 이어받았나」 (did this incarnation resume a conversation) (yes/no — not the id itself) in the **subscribe response**. Not in a broadcast when the id appears. Reason: the subscribe response rides the **same ordered stream** as replay and `ReplayComplete`, and the value is fixed per incarnation at spawn. Keep the name from colliding with the `Resume` of `SubscribeAck.action` (seq resume).
- **D3.** The persistence trigger per backend and mode is delegated to the implementation (pick the best in code and document it). 「저장했는데 백엔드가 대화를 안 만들었다」 (Saved, but the backend did not create a conversation) is absorbed by D4, so it is fine.
- **D4.** When a resume fails in the **「이어받을 대화가 없다」 (no conversation to resume) class** (`NoConversationToResume`), **a new conversation is opened automatically.** Other failures stay exactly as in ADR-0082 (stop and report). No loops. An ADR that amends ADR-0082 for this class only is needed.
- **D5.** While a resumed incarnation waits for its history, the chat slot draws a **new shared 「로딩 패널」** (loading icon + optional text field). For this use, **icon only, no text**. ~~a static icon under e-ink and reduced-motion~~ → changed: it always spins (user decision 2026-09-24 — §3-5). No time-based delay (ADR-0038 · `0145:26`). The wait ends at: arrival of the first history item · user input · incarnation end (today's curtain) · D4 restart (new incarnation → marker false → first screen).

## 3. Design

### 3-1. At a glance

| Decision | What is new | Where |
|---|---|---|
| D1 [A] | A **first-submission latch** (`SessionIdLatch`) per incarnation — persists once, with a **compare-and-swap** verb, at the first moment when both 「id 를 알았다」 (the id is known) and 「첫 턴이 제출되려 한다」 (the first turn is about to be submitted) have happened | new module in the agent crate + new registry verb + two input verbs in `session.rs` + assembly in `manager.rs` (required argument) |
| D2 [A] | Incarnation fact `continues_conversation: bool` → **the subscribe response reads it together with the marker, from the same incarnation as the replay** → `SubscribeAck` field → shell marker flag bit2 → frontend `'live'` notification | agent · daemon · protocol · src-tauri · src/api |
| D3 [A] | Trigger = **the input boundary** (backend-neutral). Table = §3-2-5 | same as above |
| D4 [B] | If a failure matches that class in the three failure arms of `resume_no_fallback` — **while holding the reservation**, reap → a sync in which the reaper answers 「그 화신이 다 거둬졌나」 (has that incarnation been fully reaped) → recheck user kill and shutdown → a new conversation **under the same reservation** | `manager.rs` + `reaper.rs` |
| D5 [A] | `LoadingPanel` shared component + two RichSlot gates + aligning the waiting-tail decision | `src/components/ui/` · `RichSlot.tsx` |

**The contract between the transport and the backend does not change** — the two still know only 「id 를 알게 되면 `SessionIdSink` 를 부른다」 (when the id becomes known, call the sink). What changes is what the assembly point plugs into that spot (today = a sink that persists immediately, afterward = the latch's receiving handle). So the write-order tests in `transport.rs` (`:4123`·`:4150`·`:4169`·`:4763`) and the receiving tests in `codex/mod.rs` (`an_app_server_spawn_hands_the_thread_id_to_the_sink` · `a_recording_failure_ends_the_session`) **remain valid as they are** (§4-2).

### 3-2. D1 — the first-submission latch [A]

#### 3-2-1. Behavior

One latch per incarnation. Two inputs, one output.

- **`offer(id)`** — this incarnation's session id is known.
  - claude (both modes): it is put in **at the very spot where the latch is created, before `open_spawn`** — for Fresh the value drawn in memory, for Resume the stored value that spawn read. The decision axis is not the backend name but the **issuing axis** (`assigns_session_id` — did spawn hold a `sid`), so a single line `if let Some(s) = sid { latch.offer(..) }` is backend-neutral.
    - ★Why it must not be put in later (review finding applied)★: a session can receive input from the moment of registry registration inside `spawn_session` (`manager.rs:1887-1890`), and the registry publish that follows (`:1447`) triggers a flush of parked mail (`messaging_host.rs:450-490`). If the offer comes later than that, the first submission goes out without knowing the id and the commit comes later than the turn.
  - codex app-server: the transport writer puts in the id it received in the handshake response at the existing spot (`record_session_id`, `transport.rs:1455`).
  - codex terminal: the lock-reclaim thread puts it in at the existing spot (`thread_lock` — `codex/mod.rs:1087-1095`).
- **`note_submission()`** — the **first user turn is about to be submitted** to this incarnation (right before it goes out to the other side).
- **`commit(id)`** — the existing recording port (`session_id_sink`, `manager.rs:494` — uuid parsing · logging) stays as it is, and only the verb it calls inside is swapped for a **compare-and-swap**: `ProfileRegistry::commit_session_id(id, epoch, expected, new)` (§3-2-3). Incarnation guard + writes only 「칸이 **이 화신이 시작할 때 본 값**(`expected`)이거나 이미 `new` 일 때만」 (only when the field is the value this incarnation saw when it started, or already the new value) and persists immediately. `expected` = the value spawn saw after release (Fresh = `None` · Resume = the stored value spawn read), and once a commit succeeds the port moves `expected` to that value — ★this is a defensive clause★: by the rule below the port is called at most once per incarnation, so in production the moved value is never used again (the argument for how this relates to ADR-0216 stands on the first offer — note A at the end). It does not create a new recording path — it is a verb swap on the same port.
  - ★Why the overwrite verb (`observe_session_id` — `profile.rs:709-722`) is not used (review finding applied)★: that verb replaces unconditionally, so if another recorder changed the field **before** the first submission, the commit would **rewind** it to the value from spawn. That recorder exists — the ADR-0008 tracker writes with `observe_session_id(id, None, new)` without a comparison (`daemon/src/lib.rs:289`). Example: if a claude resume incarnation changes its id on startup (that drift is why the tracker exists — ADR-0202 rationale section), the tracker writes Y, and the commit(S) of the following first submission reverts to S and pushes Y into history.
  - The case where codex's `thread/resume` returns an id different from the stored value (never observed) has the field == `expected` (S), so it is replaced as today — there is no spot where compare-and-swap changes today's codex behavior.
- **Rule:** one `commit` at the first moment when **both** `offer` and `note_submission` have happened. Order does not matter — if the submission came first, the `offer` that follows does the `commit` on the spot. **If the incarnation ends without a submission, nothing is persisted** — the outcome D1 wants.
  - ★**There is at most one offer per incarnation**★ (review finding applied): this is the recording port's contract (`backend/mod.rs:189` 「호출은 그 id 를 실제로 받은 뒤 정확히 한 번」 (the call is made exactly once, after actually receiving that id)). All four slots keep it — claude = once at latch creation (claude `open_spawn` discards the sink — `claude/mod.rs:408`) · codex app-server = once per writer handshake (`transport.rs:1455`) · codex terminal = calls the sink at `Found` and ends the loop (`thread_lock.rs:444-446`).
  - ★**So there is one rule — 「포트는 화신당 많아야 한 번 불린다. 한 번 부르기 시작했으면(성공·거절·패닉 무엇으로 끝나든) 다시 부르지 않는다」 (the port is called at most once per incarnation. Once the call has started (however it ends — success, rejection, or panic), it is not called again)**★. A second offer outside the contract is dropped whenever it arrives (debug log). Handling after a rejection or a panic is in §3-2-2.
- A resumed incarnation's `offer` value is already equal to the stored value, so `commit` is a no-op (the same-value branch of compare-and-swap — no disk write).

#### 3-2-2. Location

- **New module** `crates/engram-dashboard-agent/src/session_id_latch.rs`. It knows only the `backend::SessionIdSink` type (`backend/mod.rs:203`) and `types::AgentId` for log fields, and does not know backend · transport · profile (uuid parsing and `expected` tracking are inside the commit port — that is the manager side).
  ```rust
  pub(crate) struct SessionIdLatch { agent: AgentId, epoch: u32, commit: SessionIdSink, settled: AtomicBool, state: Mutex<LatchState> }
  struct LatchState { pending: Option<String>, submitted: bool, committed: bool }
  impl SessionIdLatch {
      pub(crate) fn new(agent: AgentId, epoch: u32, commit: SessionIdSink) -> Arc<Self>; // agent·epoch = 로그 필드만
      pub(crate) fn offer_sink(self: &Arc<Self>) -> SessionIdSink; // backend·통로가 받는 것
      pub(crate) fn offer(&self, raw: &str);
      pub(crate) fn note_submission(&self);
  }
  ```
  - ★**The marker for the fast path is 「commit 이 돌아왔다」 (the commit has returned) — not 「제출이 있었다」 (a submission has happened)**★ (review finding applied): `settled` is set only **after** the first commit has **returned** (written with Release, read with Acquire). If the submission marker were the fast path, then when two submitters are on different threads (the mail-flush thread's `submit_input_observed` · the connection's user input), the second would take the fast path **before** the first's commit finishes and call `send_input` — the first turn goes out before it is persisted (claude both modes · codex terminal). Every note before settled takes the mutex and queues behind a commit in progress.
  - While no offer exists yet (during the codex handshake · before the lock reclaim), there is nothing to commit, so settled is not set — the notes in the meantime are one uncontended mutex acquisition each (고름: 「commit 이 영영 없을 화신」 (an incarnation that will never commit) is not decided separately — there is no signal to decide on and the cost is one mutex acquisition).
  - ★**If the id comes before the submission, one info log line**★ (review finding applied): when `offer` comes before a submission, `tracing::info!(agent = %self.agent, epoch = self.epoch, "세션 id 를 받았다 — 첫 제출 전이라 영속을 보류한다")`. Reason: after A, the only line that announces 「id 가 왔다」 (the id arrived) is the commit port's reflect log (`manager.rs:514-518`), so **a 0-turn incarnation leaves nothing** — GUI trial 7 (§4-4) has no event to wait for and field diagnosis also loses that line. The level and shape follow `docs/reference/logging-conventions.md` (normal lifecycle = info · identifiers as fields), and like that existing log it **does not carry the id value**. Since there is one offer per incarnation (§3-2-1), there is at most one line per incarnation. An offer that comes after a submission commits right away, so the port's reflect log is left instead of this line.
  - ★**Even if the commit is rejected, fails, or panics, there is one rule — 「포트는 화신당 많아야 한 번 불린다. 한 번 부르기 시작했으면(성공·거절·패닉 무엇으로 끝나든) 다시 부르지 않는다」 (the port is called at most once per incarnation. Once the call has started (however it ends — success, rejection, or panic), it is not called again) (고름)**★ (review finding applied · that rule from §3-2-1): the latch sets `committed` **before** calling the commit port. Whatever the port ends with, there is no retry. The port has no return value, so the result does not come back to the latch (`SessionIdSink` doc — `backend/mod.rs:199-200`). There are four places that call commit — `WriteStdin` in the WS arrival-order line (`connection_core.rs:1087`) · the mail flush (`spawn_blocking` at `messaging_host.rs:753` → `:135` `submit_stdin_observed`) · the codex writer's `record_session_id` (`transport.rs:1355`) · the codex terminal reclaim thread (`thread_lock.rs:445`). All four end in one of the three below.
    1. **Rejection** (`commit_session_id` returns `false` — marker mismatch · another recorder changed it first · profile absent, or uuid decode failure): the port logs and returns → settled → **the turn goes out as is.** No retry (the same input would get the same answer).
    2. **Disk IO error**: `ProfileStore::save` swallows it (`persistence/mod.rs:102-106` — only an error log). The `bool` is memory-based, so it looks like success to the port → settled as in 1 · the turn goes out. The next save that succeeds (any profile change writes the whole registry) repairs the disk. Same grade as today's `observe_session_id` (§3-6).
    3. **Panic**: the only panic sources under the port are the poison guard's `expect` (the registry map `profile.rs:395`·`:406` · the store write lock `persistence/mod.rs:101`). So it arises **only when someone else's panic poisoned that lock first** (the same analysis on the codex side — `transport.rs:1312-1318`). The latch itself creates no panic source (no indexing, no `unwrap`).
       - ★**This branch does not exist in release**★: the workspace `[profile.release]` is `panic = "abort"` (`Cargo.toml:35`). The first panic ends the daemon on the spot, so no poisoned lock arises. The outcome is the daemon exiting. If the panic came from a note, it is before `send_input`, so that turn did not go out. If it was on the offer side, the codex writer ends together with the turns queued, and the reclaim thread is after the first turn already went out (same grade as the §3-2-4 exception). The disk stays as of the last save, and after a restart it restores only from a persisted id (§3-6 「데몬 재기동」). It is the same grade as the `.expect` that WS-line profile CRUD takes today — not a new kind of risk.
       - ★So the latch gets no `catch_unwind` (고름)★. In release it is dead code that catches nothing (`transport.rs:1319-1322` records its own containment that way). Even on an unwind build (development · tests), the only gain is 「남의 패닉 위에 겹쳐 죽지 않는다」 (not dying stacked on top of someone else's panic).
       - Outcome on an unwind build: the latch mutex is poisoned. The offers and notes that follow recover with `into_inner`. `committed` is already true, so it sets settled and passes through — it does not call the port again (the rule above exactly · test ⑨). The panic itself propagates up through that call — if it arose in a note, **that one input does not go out.** What receives it is the caller side's existing handling: WS = that connection's arrival-order consumer task ends with the panic (what happens to the connection after that was not checked) · mail = the 「언와인딩됐다」 (it was unwound) warning of `DeliveryDone` (`messaging_host.rs:716-719`) · codex writer = `catch_unwind` → brings the connection down · reclaim thread = that thread ends (persistence was already attempted).
- **`InputEncoder::submits_turn(&self, bytes: &[u8]) -> bool`** (`backend/mod.rs`, next to `submit_sequence` `:917`). What counts as a turn submission is backend knowledge, so it goes here (ADR-0004).
  - `ClaudeStreamJson` · `TransportFramed` → always `true` — the contract 「호출 1회 = 완결된 유저 턴 1개」 (1 call = 1 complete user turn) (`session.rs` `write_input` doc FIX 6a · codex `send_input` makes one `Job::Turn` per write, `transport.rs:2490-2512`).
  - `Raw` → `true` if `bytes` contains the submit byte (CR).
  - ★**The CR decision depends on the frontend's key encoding**★ (review finding applied): terminal Enter = CR is the byte xterm sends under its default key encoding. The type definitions of the installed `@xterm/xterm` 6.0.0 have no option to switch encodings such as kitty keyboard or win32-input-mode (checked). If a change turning on such a mode arrives, Enter comes as a non-CR sequence and this decision becomes false **silently** — submissions are not counted and every resume in that mode disappears. A comment goes at that spot and the assumption is put in the test name (`raw_submission_is_cr_under_default_xterm_encoding`). It pairs with `submit_sequence` (`:917`), which stands on the same assumption.
- **`AgentSession`** (`session.rs`): holds the latch, and two input verbs call it **before** `send_input`.
  - `write_input_observed` (`:195`) — if `self.encoder.submits_turn(bytes)`, the `UserKill` check below + `note_submission()`, then `send_input`.
  - `submit_input_observed` (`:251`, mail delivery) — ★**it counts right before the submit CR**★ (review finding applied): inside the `if let Some(submit)` branch, after the wait (`:271`) and right before the submit `send_input` (`:277`), the `UserKill` check below + `note_submission()`. This is because the submit CR goes out directly through `transport.send_input` without passing through `write_input_observed`. `Raw` is always `Some(CR)`, and the two JSON encoders are `None` so that branch does not exist (`backend/mod.rs:917-921`) — there the body is the turn, so it is already counted **before** the body inside `write_input_observed` (`:252`). So 「첫 턴 전에 영속」 (persist before the first turn) holds for `Raw` as well (what opens the turn is the CR).
    - Why the old spot (the very front) was dropped: counting there puts the body write + the body landing confirmation (`confirm_written` — cap `INPUT_FLUSH_BUDGET` 5 s, `session.rs:70`) + `SUBMIT_PACING` 0.5 s in front of the CR, so a kill in that window or a body write or landing confirmation failure leaves a **persistence without a turn** (with A alone, the next activation is P2's failure). Parked mail is flushed right after the registry publish (`manager.rs:1447` → `messaging_host.rs:450-490`), so a kill right after spawn · a `shutdown_all` during boot restore hits exactly that window.
    - Mail whose body itself contains a CR (when the sender loaded in a CR — rare) is counted first, before the body, in the `write_input_observed` decision. It is the same class as the paste line (§3-6).
  - ★**During a user kill, it neither counts nor sends**★ (review finding applied — round 4 added 「보내지도」 (nor sends)): in a session with a latch, the two verbs first look at `termination_intent() == UserKill` (`session.rs:145`) at the note spot. If it is set, they do neither the note nor the `send_input` at that spot, and return `Err(PtyError::WriteFailed(..))` right away — the **turn-producing write** at the counting spot (a key-input fragment containing CR · a JSON turn) does not go out, body and all, and with `Raw` mail the submit CR does not go out. A `Raw` key input without CR is not a counting spot and goes out as is until the input queue closes, even in the kill window (it does not open a turn, so it is harmless). The body of `Raw` mail has already gone out only when it was written before the kill — usually the queue closes within a few µs after `UserKill`, so the body write itself fails first with the same `WriteFailed`. ★The rejection gets its own log line and its own error text that names the user kill★ (the variant `WriteFailed` and the `Err` shape stay as they are): it does not reuse the warn text of the existing 「본문은 썼으나 제출 write 실패」 (body written but submit write failed) branch (`session.rs:277-284`) (「재시도가 그 위에 덧쓴다」 (the retry overwrites on top of it)) — the retry goes to the new incarnation's PTY and there is nothing to overwrite, and since the messaging kernel records the error's Display text as a delivery failure observation (`service.rs:1763` → `:2120`), a generic text would be read as a transport defect. Reason: `kill_agent` sets `UserKill` (`manager.rs:2715`) and then waits up to 5 s for the transport to end and join (`:2722`), and the session stays in the registry until the reaper reaps it (`reaper.rs:51-60`).     - ★The outcome is the same class as today★: a `send_input` after the queue has closed is already `Err(WriteFailed)` (`transport/pty.rs:368-378` → `input_queue.rs:112-113` · stdio uses the same queue · codex `transport.rs:2494-2498`).     - In a default session without a latch (tests · production up to A1) this check is also a no-op — A1's 「동작 불변」 (behavior unchanged) holds as is.

  - The `AgentSession::new` signature is **not changed** — callers outside production number 16 (17 with production `manager.rs:1859` — agent unit and integration tests, daemon tests, the `drain_latency` dev bin). #### 3-2-4. Order and concurrency

- **`note_submission` comes before `send_input`** → 「첫 턴이 상대에게 가기 전에 영속」 (persist before the first turn goes to the other side) holds in **the three slots other than the codex terminal** (the ADR-0185 Phase 2 requirement `0185:32`). In the two claude modes the offer went in at latch creation, so the first note commits on the spot. The codex app-server is one layer firmer: if a submission comes before the handshake, the commit happens inside the writer thread's `record_session_id`, which is before `open_gate` (`:1493`), and a queued turn goes out only after the gate (`take_turn_locked`).
- ★**The codex terminal is an exception**★ (review finding applied): the id in that slot comes only from the lock reclaim — the first sweep is 0.5 s after spawn, and if it comes up empty the wait doubles up to a cap of 15 s, running with no deadline (`thread_lock.rs:242` · `:254` · `:396-450`). The PTY hands a submission straight to the child. So if Enter comes before the reclaim, **the first turn goes out first** and the commit happens at the reclaim moment. If the daemon or the child dies in between, there is a conversation but no handle. ★This is not a regression★ — today too that slot's id appears only at the reclaim moment (ADR-0218). The ADR-0185 Phase 2 requirement does not hold in this slot.
  - ★**It is not 「대개는 offer 가 먼저」**★ (review finding applied — the old sentence was corrected): the lock appears at 0.7–1.9 s (ADR-0218 rationale) but the sweep runs **after waiting** — it starts at **at least** 0.5 · 1.5 · 3.5 · 7.5 s … after spawn (`FIRST_DELAY` `thread_lock.rs:242` · double backoff `:466` · cap `MAX_DELAY` `:254`), and one round opens one Restart Manager session **per candidate lock file** (`:246`). So these figures are a lower bound, and the actual time adds the sweep time to them. The first sweep (0.5 s) is earlier than the measured minimum creation delay (0.735 s), so it comes up empty, and if the reclaim falls within the measured creation delay it happens in the second or third round — **at least 1.5 / 3.5 s + the sweep time**. One GUI measurement was about 6 seconds (at that time there were 10 locks held by other codexes in the folder — `step-log.md:2455`). A 21-second creation case that was not reproduced is also on record (`MAX_DELAY` doc — `thread_lock.rs:252-253`). ★**If there is parked mail, the first turn is always first**★ — the flush is called at the registry publish moment (`manager.rs:1447` → `messaging_host.rs:450-490`), and the submit CR goes out `SUBMIT_PACING` (0.5 s) after the body — within a second (read from the code — not measured). It is the same when a human's first Enter comes before the reclaim. It is still not a regression.
- **The latch mutex is held during the commit call** (고름) — this structurally prevents two commits overlapping and flipping the disk order, and the fast-path race (above). Lock order = `latch → 포트의 expected 칸 → profiles → store write_lock` (latch → the port's expected field → profiles → store write_lock), one direction (review finding applied — the port holds that field while it reads `expected`, calls the compare-and-swap, and moves it, and the port is the only place that takes that field). Every caller that takes the latch holds no other lock: `write_input_observed` (after `get_session` has released the sessions lock — ADR-0006) · `submit_input_observed` (the mail flush thread, same condition) · codex `record_session_id` (called after releasing the state lock — `transport.rs:1344-1355`) · the lock reclaim thread (no locks) · `spawn_agent` (the offer — no locks). The registry is a leaf that calls nothing outside.
- **Fast path:** look at `settled` first as an `AtomicBool` — a key input **after the first commit has returned** does not take the mutex (3-2-2 above).
- **One `agents.json` write is attached to the input path at the first submission** — once per incarnation. The same arrival-order line already runs profile CRUD's synchronous IO (`connection_core.rs:170-176` ㉯) — it is not a new kind of blocking. During that one write, another thread's first submission waits (that is the point).
- **It does not overlap with the warning in ADR-0172 §영향** — what it forbade is taking the profile lock on top of the **turn-end signal** (which comes only from structured output, has no incarnation check, and has the `StatusSink` non-blocking contract). This trigger is the **input command processing thread**, comes out in both modes, and the commit carries the incarnation marker.

#### 3-2-5. D3 — the trigger per backend × mode (고름)

| | Trigger | Grounds |
|---|---|---|
| **claude JSON** | The first `write_input` call (= the first user turn) — before the NDJSON line goes into the queue. The offer already went in at latch creation | The 1 call = 1 turn contract (`session.rs` FIX 6a). claude creates the conversation after the first exchange (ADR-0172 context) |
| **claude terminal** | The first input fragment containing CR, or the mail's submit CR (after the body · §3-2-2) — before it goes into the PTY queue | `Raw` submission = CR (`backend/mod.rs:917-919`) · key-encoding assumption (§3-2-2). Mail writes the CR separately (`session.rs:251-300`) |
| **codex JSON** | The first `write_input` call. **Rejected trigger (the grounds for the 고름):** the orchestrator's original 「codex `writer_loop` `Job::Turn` 팔에서 `turn/start` 직전」 (right before the turn-start request in the codex writer-loop turn-job arm) covers only the codex JSON slot. The transports (stdio · PTY) of the two claude modes and the codex terminal are dumb pipes that do not know turns, so there is no same spot, and in the end one more trigger would have to be set up at the input boundary — that makes two triggers. A single input-boundary trigger covers all four slots with the same code and does not touch the transports.

#### 3-2-6. Relation to claude `/clear` (★decision — user 2026-09-24: §7 Q1 = (a)★)

- The `/clear` tracker (`daemon/src/lib.rs:289` → `observe_session_id(id, None, new)`) is **left as it is** — it persists immediately.
- ★**This is D1's only intended exception**★ — the new id at the `/clear` moment has no conversation yet, but it is persisted right away. Reason (user): `/clear` is the user's explicit act of ending the old conversation. Cost: if the user does `/clear` and shuts down without input, the next activation fails — with A alone it is the same failure as today, and after B it opens as a new conversation.
- There is one place where this decision (Q1 = (a) — user) collides with D1: if the user shuts down right after `/clear` without a word, a new id with no conversation is stored → the next activation fails to resume → **D4 opens it as a new conversation** (if only Phase A has landed, the same failure as today — §6-3). The user's deleted conversation is not revived, so the outcome is right, and the cost is one wasted attempt (about 1 second measured on claude, ADR-0201).
- Order safety **now stands on structure, not on order**: the latch commit is a compare-and-swap, so it cannot overwrite a value the tracker wrote first (§3-2-1). And the first submission (even if it is `/clear` itself) commits the minted value **before sending**, and the tracker's new value is observed only **after** claude has processed `/clear`, so in the normal order the compare-and-swap never has occasion to reject.
- Premise check (before implementation): the tracker emits `Changed` **only when the value differs from the baseline (the minted value)**. The comparison is at `backend/claude/session_file.rs:210` (`current != self.last_seen_sid`), and the baseline is received at `:152` `last_seen_sid: expected_sid` (the passing spot = `session_id_source(..., s)` at `manager.rs:1437`). If the first poll reports the minted value as is, D1 leaks on claude — that spot is pinned by a test (§4-1).

#### 3-2-7. Why this decision does not reopen the rejection in ADR-0172 · ADR-0008

- What ADR-0172 discarded is **「우리 관측을 새 칸에 영속해 활성화 전에 판정한다」** (persist our observation in a new field and decide before activation) — it needs a new field, and old entries have no stamp so it cannot be applied retroactively. D1 has **no new field** — it only changes **when** the already-existing `backend_session_id` is written. Activation still **attempts** a resume when there is an id (`can_resume_profile` unchanged), and failure is still observed at the place where it was attempted (ADR-0172 decision 1). Old entries without a stamp (garbage ids) are received not by a pre-decision but by **D4's reactive handling**.
- There is also no feature extension on the claude file that ADR-0008 forbade — nothing reads the claude file to decide.
- The 「크래시 창」 (crash window) of ADR-0185 (between receiving the response and persisting, `0185:21`) **melts away in the three slots other than the codex terminal** — a thread before the first turn has no rollout, so there is no conversation to lose (backend-capabilities §1), and the first turn goes out **after** persistence. In the codex terminal the window remains when the reclaim is later than the first turn (§3-2-4 — the same grade as ADR-0218).

### 3-3. D2 — the 「이어받는 화신」 marker in the subscribe response [A]

- **Name: `continues_conversation`** (고름) — the word 「resume」 was dropped so it does not collide with `SubscribeAction::Resume` (seq resume, `messages.rs:591`). Meaning = **「이 화신은 저장된 대화를 이어받으려고 떴다(스폰 때 이어받을 손잡이를 실었다)」 (this incarnation came up to resume a stored conversation — it loaded a resume handle at spawn) — not whether the resume succeeded.**
- **Computation (backend-neutral):** `resume_session_id.is_some()` in `spawn_agent_watching_link`. `resume_handle_for` (`manager.rs:487-492`) is already the spot that makes 「손잡이가 있다 ⟺ 이어받기 화신」 (there is a handle ⟺ a resuming incarnation) hold, so it is not a new decision. claude rides the same field (on Resume, `stored_handle` is read in every backend — `:1350-1358`).
- ★**The marker and the replay must come from the same incarnation**★ (review finding applied): today `handle_subscribe` reads the marker with `agent_epoch` (`connection_core.rs:1747`), and `subscribe_from` (`manager.rs:2558-2568`) does `get_session` **again** and replays. If the incarnation changes between the two lookups (D4 creates exactly that replacement), the Ack's marker and the resume marker speak of **a different incarnation than the one replayed**. Today it was a TOCTOU on one marker field (the comment at that spot admits it only for the `Err` branch — `:1778-1781`), but once the resume marker is added, the first-screen/loading decision rides that gap. So they are merged into one lookup:
  - **agent:** in `types.rs`, `pub struct Incarnation { pub epoch: u32, pub continues_conversation: bool }` and `pub struct SubscribeReply { pub outcome: SubscribeOutcome, pub incarnation: Incarnation }`. `AgentSession` carries `continues_conversation: bool` as an incarnation-invariant field (§3-2-2 builder — the marker stays in the existing `epoch` field). `Incarnation` is a response value, not a session field — it is assembled on the spot as `Incarnation { epoch: self.epoch, continues_conversation: self.continues_conversation }`. `AgentSession::subscribe_from` takes `requested_epoch: Option<u32>`, **compares it with its own marker** to compute `epoch_matches` itself, then adds its own `Incarnation` to the core's outcome and passes the same value to **both** `on_ready` and the return. 고름: core does not know the resume marker, so rather than adding a field to `SubscribeOutcome`, it is wrapped at the session layer (ownership split — core is replay/seq, session is epoch). `AgentManager::subscribe_from(agent_id, sink, after_seq, requested_epoch, on_ready)` delegates as is.
  - **daemon:** `handle_subscribe` removes the `agent_epoch` pre-lookup, and fills the Ack's `current_epoch` · `continues_conversation` and `ReplayComplete.epoch` from **that one reply**. ### 3-4. D4 — if 「이어받을 대화가 없다」, then a new conversation [B]

- **Where:** the three failure arms of `resume_no_fallback` — `Terminal` (`manager.rs:2069` — but `Killed` is excluded because it is a user cancel, `:2080`) · `Diagnosed` (`:2107`) · `LinkFailed` (`:2133`). The common decision = the `kind == NoConversationToResume` that the arm already computes.
- ★**Precedent — the same user decision was implemented once and reverted**★ (review finding applied): ADR-0077 implemented 「스폰만 하고 한마디도 안 한 건 그냥 새로 시작」 (an agent that was only spawned and said nothing simply starts anew) as a fresh-fallback and widened it to manual activation. That extension (a4aac1a) **mistook** the 「already running」 `Err` of the double-spawn guard for a resume failure and **killed an agent that was running fine**, and that is the direct cause of ADR-0082 (abolishing fresh-fallback). The grounds on which this design avoids that class **structurally**:
  1. The fallback is started only inside the three decision arms for **the incarnation this call brought up** (`SpawnOutcome::Started(spawned)`). `Moot` (someone else brought it up or is bringing it up — `:2033-2039`) and a spawn `Err` (`:2013-2025`) return before the decision and have no fallback. 「already running」 today is a `Moot`, not an `Err` (`SpawnOutcome` doc — `:83-95`).
  2. The classification is the single `NoConversationToResume` that the backend read from **this incarnation's own evidence** (diagnosis · terminal tail · connection rejection reason) — it does not sort by the shape of an error string.
  3. The reaping is incarnation-guarded — `tear_down_failed_activation` leaves it alone if the marker differs (`:2223-2232`).
  4. Reactivation of a live agent is filtered out earlier than that — the in-flight guard of `activate_profile` (`:1512`) and the 「이미 실행 중」 (already running) branch (`:1522-1532`).
  5. There is no reentrance (「루프 금지」 below — no loops).
- ★**Why it does not violate ADR-0019 decision 2 (「런타임 자동 재시작 없음」 — no runtime auto-restart)**★ (review finding applied): what that decision forbade is **the system reviving an incarnation that had been up, after it dies**. D4 changes **the outcome of the same request** to a new conversation only **inside an activation that a human, an LLM, or boot restore requested**, and only when that activation's resume attempt ended in 「이어받을 대화가 없다」. If an incarnation that once came up later dies, D4 does not get involved (the reaper's handling as is).
- **Procedure (one new helper, 고름):**
  0. **Hold the reservation — do not release it** (review finding applied). A connection-axis backend takes out the reservation of the `LinkWatch` that the decision was holding (`:406-410`) and passes it on (`LinkWatch::into_reservation`). A backend with no connection axis (claude) already had its reservation released together with spawn, so it **takes a new one here** — if it cannot (another request is activating), it does not fall back and gives up as today (record + `Failed`). ★What happens if it is released★: while waiting for the reaping (the reaper's `apply_disposition` writes the whole `agents.json`), another activation can slip in and get the corpse back, or take the reservation and **bring up another Resume with the garbage id that is still stored** — that makes three spawns.
  1. **Hold the failed incarnation's Arc** (when the marker matches) — for the recheck in step 5.
  2. **Reap it** — `tear_down_failed_activation(id, epoch)` (`:2215`, incarnation guard · no-op if already gone) + **`tracker.unwatch(id)`**. `kill_agent` releases tracking (`:2725`) but `tear_down` does not — until now it was used only for codex, to which no tracker attaches, and D4 uses it on claude for the first time. When the new conversation comes up, `watch` replaces the entry (`session_tracker.rs:115`), but if the new conversation fails, an entry watching the old PID remains. The `LinkFailed` arm already reaps. ★The disposition of the `Diagnosed` arm is tied to §7 Q6★ — there the child is still alive running claude's exit hook (diagnosis +2.2 s · exit +6.4 s — `:42-49`), so reaping now kills that hook as well (`TerminateJobObject` ends the whole tree). If it is not reaped, the new spawn sees the old session as 「떠 있다」 (still up) (the lookup in `spawn_agent_watching_link` `:1169`).
  3. **Reaper sync** — add a new `ReaperCmd::Barrier { id, epoch, reply: Sender<bool> }` (`reaper.rs:30`), send it, and wait for the answer. After processing all earlier commands, the reaper answers **on its own thread** 「그 `(id, epoch)` 가 명부에 없나」 (is that incarnation's id-and-epoch pair absent from the registry).
     - ★Why the reaper must answer (review finding applied)★: the reaper is the only one that removes a session from the registry, and `reap_one` **removes it from the map first** and does the revoke · disposition · list notification after that (`reaper.rs:51-60` versus `:77-87`). That one item runs to the end on the reaper thread before it looks at the next command. So a 「없다」 (absent) from the reaper thread means **the reaping of that incarnation is finished, including the list notification**. If the manager waits and then looks at the registry directly, it can see a 「없다」 **in the middle of** the reaping, and that late list notification arrives after the new incarnation's notification and reverts the tree.
     - The cap = **a new constant `REAP_BARRIER_BACKSTOP`** (고름). The value reuses the 5 s `join_pump` cap of the kill path (ADR-0001) as it is — `INPUT_FLUSH_BUDGET` (`session.rs:70`) is a precedent that used the same number for the same reason (「이쯤이면 끝났어야 한다」, it should have been over by now). The reason `LINK_RESOLUTION_BACKSTOP` is not reused: its doc ties the grounds of the value to the handshake, as 「통로의 핸드셰이크 상한보다 커야 한다」 (it must be larger than the transport's handshake cap) (`manager.rs:68-70`) — a different axis.
     - Why it holds: the `session.kill` in `tear_down` waits for `join_pump`, and in all three transports the pump sends its completion signal **after** `core.finish` (including the ReapMsg send — `output_core.rs:442-449`) (`transport/pty.rs:353-358` · `stdio.rs:341-344` · `codex/transport.rs:2473-2474`). If the join was cut off at 5 s, the ReapMsg can come **after** the barrier, but then the answer is 「있다」 (present) and it goes to giving up in step 4.
  4. If the answer is 「있다」 · deadline exceeded · reaper disconnected (`Disconnected`) → **give up unconditionally** — the same as today: record `NoConversationToResume` + `Failed`.
  5. ★**Recheck user kill and shutdown**★ (review finding applied): if the Arc from step 1 has `termination_intent() == UserKill` or `shutting_down` is set, do not fall back — `Failed` with no record, like today's `Killed` arm. Reason: the only place that looks at a user cancel is the decision (`:2080`), so if D4 cannot see a kill **after** the decision (`kill_agent` sets `UserKill` on the old session — `:2715`), it **revives an agent the user shut down** — and because `spawn_session` turns on `auto_restore=true`, it also comes up on the next boot (`:1900`). `shutdown_all` takes the ids only once (`:2763-2766`) and the spawn path does not look at `shutting_down` — if a new conversation comes up during shutdown, nobody kills it.
  6. **A new conversation under the same reservation** — the reservation-handover version of `spawn_fresh_settled` (signature below). Since it is Fresh, D1 pushes the garbage id into history and starts from an empty field (the cleanup of the old profile happens here on its own — it is a history push, so it is not the destruction of ADR-0202).
  7. **Outcome:** success → `(RestoreOutcome::Started, Some(info))`. If the new-conversation branch is `Moot` (the registry has a session even though the reservation was held — the pre-existing window of ADR-0082 open item ③), report it with no record like the `Moot` arm of `resume_no_fallback` (`(RestoreOutcome::Resumed, info)` — `:2033-2039`). Failure → whatever the new-conversation branch recorded under its own discipline, and `Failed`, as is.
- **Signature (the main session pins it first — the contact point that touches the same function as Phase A, §6-5):** `fn spawn_agent_watching_link(&self, profile, mode, reservation: Option<SpawnReservation>)` — `None` = take it here as today. ★This argument is **brought in by B2**★ — with Q5 = (a), A lands first, and A2 does not change this signature. `spawn_fresh_settled(profile)` becomes a thin shell around `spawn_fresh_settled_with(profile, Option<SpawnReservation>)`. The handed-over reservation is carried on by the new conversation's `LinkWatch` and released at that decision.
- ★**Extending the reservation lifetime is safe**★ — what the `SpawnReservation` doc (`:591-608`) warned against is a change that **shortens** the lifetime. If it is lengthened, another activation of the same id in the meantime gets the 「다른 요청이 활성화 중」 `Err` at the in-flight guard (worst case 45 s below).
- **Record (ADR-0172):** when the fallback starts, this attempt's `NoConversationToResume` is **not recorded** — the failure has turned into a normal new creation. It is recorded as today only in the give-up branch. The cause is left in the log (info) — the discarded id also remains in `old_session_ids`.
  - ★**The record left by a previous attempt (ADR-0202)**★ (review finding applied): for claude (no connection axis), `note_spawn_result` of the new-conversation branch erases it. - **No loops = structure:** the fallback calls only `spawn_fresh_settled_with`, and that function does not attempt a resume and fixes the failure classification to `Other` (`manager.rs:1681-1686`). There is no path that re-enters `resume_no_fallback`. A test pins it (at most 2 spawns).
