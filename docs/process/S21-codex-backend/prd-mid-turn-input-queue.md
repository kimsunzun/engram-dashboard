## 1. What / why

**What.** In a structured chat (JSON) slot, a message sent while the agent is running a turn is shown **separately in a list above the input box until the agent actually receives it**, and the moment it is received it moves to **a plain bubble at the end of the conversation**. The message is delivered at **the earliest moment the agent can take it** — usually it is read at **the point where the tool call now running ends**, and if it cannot get into that turn it goes to the next turn. Every item in the list has a ✕ that removes it from the list when pressed — if the agent has already taken the message, it appears as a bubble at the end of the conversation (§3-6).

**Today's symptoms (as the user feels them).**
- **claude (JSON)** — the sent message goes straight to the agent and the agent reads it at the point where a tool call ends, but the screen puts a proper bubble at **the sent position**. So the rest of the earlier answer continues **below** that bubble, and the conversation order looks different from the order in which the agent actually read things. There is no way to withdraw it after sending.
- **codex (JSON)** — a message sent mid-turn reaches **neither the model nor the screen until the turn ends.** You cannot tell whether it was taken, and you cannot correct a running agent midway (a corrective instruction during a long build only arrives at the end of the turn). Even a message sent while idle shows up only when the agent echoes it back — this is the 「보낸 글이 늦게 뜬다」 (the sent message shows up late) the user first pointed out. There is no way to withdraw it either.
- **Common** — the state 「보냈지만 에이전트가 아직 안 받은 글」 (sent, but the agent has not received it yet) exists nowhere on the screen.

**Why this shape (research conclusion).**
- Not blocking sending mid-turn is the current practice of agent tools (Claude Code · Codex · t3code · paseo · Cursor, etc.). — likely
- Waiting items are shown outside the conversation, and the position of the proper bubble is **the delivery time, not the send time** (established by the Codex TUI and t3code source). Orca alone pins it at the sent position. — likely
- There are two options for where to show them outside the conversation (a waiting row at the very bottom of the conversation / a list above the input box), and the user chose the **list above the input box**, the same as the terminal CLIs (Claude Code · Codex TUI).
- Both backends have a means to support this shape — they accept mid-turn input at a tool boundary and report each accepted item one by one. — likely (vendor text and source) · **not measured in our spawn mode** (§8 R1)
- The handover time differs between the two backends — for claude, handing over after the tool has ended misses that boundary (0/10), while for codex, handing over after the tool has ended still lands at the same boundary (10/10). So codex can hold until then, and a ✕ pressed during the hold keeps the message from going to the agent. — Phase 0 measurement · our daemon's reaction time and the stretch without tools are not measured (§8 R8)

## 2. Scope (user decisions)

- **Included:** the **user input** of JSON (structured chat) mode — claude stream-json · codex app-server. Both backends include ✕ cancel of list items (all items · all stretches — §3-6).
- **Excluded — terminal (PTY) mode.** The user: 「터미널 모드는 그런거 필요없잖아」. There the agent's own TUI already queues and shows input during a turn. The behavior of terminal slots and the input bytes do not change at all — agent-to-agent mail in terminal mode also stays as today.
- **Agent-to-agent mail — does not go on the list.** The path stays as today, but in JSON mode user input comes first, so mail can be delayed (§3-9).
- **Excluded — the turn-interrupt operation.** A separate feature, done right after this one (user decision — §7). Fact: today the chat view has no turn-interrupt operation — neither on the screen nor on the command surface (there is a connection-level interrupt request but nothing calls it — code check 2026-09-25). claude JSON does not support interrupting at all yet (TRD §3-1). So within this feature the only thing that actually stops a turn is a turn that ends in an error (§3-10).
- **Excluded — old versions without the vendor prerequisites.** Versions that lack the vendor features this feature relies on (per-item receipt notification, etc.) are not specially supported and stay as today (the user: 「알아서 업데이트」 — §8 R6). However, the mail stop after an abnormally ended turn (§3-9) is our side's business, so it applies to old versions too.

## 3. Behavior spec (user decisions — not reopened)

1. **Hand over at the earliest moment the agent can take it.** The user's principle: deliver as fast as the agent can take it. The agent reads a message received mid-turn at **the point where the tool call now running ends**.
   - The user: 「당연히 도구호출 끝나면 바로 푸쉬」.
   - **claude — hand over as soon as received** (immediately, as today). If we hand it over only after seeing the tool end, we miss that boundary and it is read only when the **next** tool ends (the user checked: 「도구가 끝날 때 넘기면 다음 도구가 끝나야 전달되지 않나」 — right · the Phase 0 measurement agrees). If handed over immediately, the message is in the agent-side inbox from the start and is read at the end of the tool now running.
   - **codex — we hold it only while holding does not delay delivery, and hand it over at once at the earliest moment the agent can take it** (insert into the turn in progress, or a new turn if no turn is running). A ✕ pressed during the hold keeps that message from going to the agent (§3-6). The point where a tool ends landed at the same boundary even when held and then handed over (Phase 0 measurement). **If holding in some stretch would delay delivery, we do not hold in that stretch and hand it over at once** — ✕ is still there, but if the agent has already taken the message when ✕ is pressed, it appears as a bubble (§3-6). Which stretches those are, and the timing basis for that decision, are still being measured and the TRD decides them (§8 R8). The user: this is not later work but part of this feature.
   - **Turn-end boundary:** an item that never got into the running turn (the turn ended with only an answer being written and no tool, or the boundary was missed) goes in **to the next turn, in typed order**, after the turn ends — the user's decision 「도구 경계 없이 턴이 끝나면 남은 항목은 친 순서대로 자동 전송」 (2026-09-25 · TRD body D5). This is not the resend that §3-7 forbids — it is sending in, for the first time, a message that has not yet gone into any turn. **If several items remain, they go into one next turn together, each as its own separate message** (§3-8) — for codex we feed them in that way, and for claude the vendor decides the bundling (not measured — if it differs we raise it again, ADR-0192). A turn that ended in an error follows §3-10, not this rule.
   - ★**Requirement: every sent message goes into a turn in which the agent answers, unless it is discarded under §3-7**★ — there must not be a message left with a bubble in the conversation and no answer. **The three exceptions are below** — the follow-up turn ends abnormally · a turn that ended in an error · a codex item whose receipt arrives late, after the turn has ended.
   - **The same goes for an item that went in but did not get an answer:** if the receipt arrived and the item became a bubble but the turn ended without answering it (codex — a message that went in at the instant the turn was ending), that message must also get a turn that answers it. **But the same message is not handed to the agent twice, and the bubble is not drawn twice.** The method = TRD (M6). **If that follow-up turn ends abnormally (§3-10), it is not reopened again** — the message is already in the conversation record, so the turn the user's next message opens answers it too. Until then mail also waits (§3-9).
   - **Exception — a turn that ended in an error (§3-10):** a message that already became a bubble in that turn but got no answer (including a message sent while idle) is left as it is — no follow-up turn is opened. A codex item left in the list waits until the user sends the next message.
   - ★**Exception — a codex item whose receipt arrives late, after the turn has ended (concession)**★: when the receipt arrives for an acceptance-unknown item (§3-4 — including one closed with ✕, §3-6) after the turn has already ended, the bubble stands at the end of the conversation, but **no turn that answers that message is opened automatically** — the message is in the conversation record, so the turn the user's next message opens answers it too. This is inside a defensive branch that has never been observed, so no extra machinery is provided and we conceded to the simpler side (the user: 「복잡한것보다 약간 양보하면서 단순한 방향으로 하되 나중에 문제되면 기능 추가하면 되지」 — later candidate = §7). **Rare cost:** if mail flows in the meantime, the mail can get its answer before that message.
2. **Until received, keep it in the list above the input box** (terminal style — Claude Code · Codex TUI).
   - One gray line per item, 「…」 if it overflows. For a truncated item, hovering shows the full text (tooltip).
   - The oldest is on top.
   - Beyond 3 items it folds into 「외 N개」 — while folded, **the oldest 3** are visible, and clicking 「외 N개」 expands it. The count and look can be adjusted later (the user: 「나중에 조정」).
   - **No header line (a line of guidance text) above the list** — only gray items (Claude Code style). The user: 「한 줄 낭비」 (§6).
   - Nothing is drawn inside the conversation (neither at the sent position nor at the very bottom of the conversation).
3. **There is one list — every window and the LLM see the same list.** Even when the same agent is viewed in several windows (main · pop-out), the list is the same — an item on which ✕ was pressed disappears at once from every window, whichever window it was pressed in (§3-6). The list stays as it is after closing and reopening a window, and after restarting the dashboard app (as long as the daemon and agent are alive). The LLM also reads the same list through the command surface (`CLAUDE.md 「LLM-우선 제어」` — the screen only draws and does not own the list). Where the list lives is up to the TRD.
4. **An item leaves one by one, only when a 「받음」 (receipt) arrives.**
   - **Receipt = the agent itself reporting, item by item, that 「그 항목을 대화에 넣었다」 (it put that item into the conversation)** (a per-item echo). Our writing the message to the agent, or the agent answering that it accepted the request, is **not a receipt** — until then the item stays in the list.
   - The moment it leaves, it appears as a plain user bubble **at the end of the conversation at that moment** (not at the sent position).
   - The list is not cleared all at once on the grounds that 「도구가 끝났다」 (the tool ended).
   - If the receipt never arrives, the item stays in the list **until the agent ends**, and is then discarded per §3-7. Mail also waits during that time (§3-9).
   - **The same goes when it becomes unknown whether codex accepted that item** — a rare failure: codex did not answer the handover request within the existing 30-second limit, or the answer could not be read, or it answered that it had received it but there was no echo until the turn ended (a branch that should not exist per the source). This is not a rejection (§3-7). An item leaves only when there is a reason — receipt (a late signal that codex has the message → bubble · if the turn has already ended, the answer comes from the user's next turn — §3-1 exception) · ✕ (the user removes it — §3-6) · agent exit. During that time ✕ is always there (pressing it counts as finished at once — §3-6), and mail waits behind it with no upper bound (§3-9 — it is visible in the list, so the reason for being blocked is on screen). **A message typed after it goes over in typed order as usual** — that item is a message already handed to codex, so handing the later message over after it is exactly the typed order (C → D → E). That item stays gray. When the late receipt arrives, its bubble can stand after the bubbles of the messages that went over in the meantime — we accepted this as an on-screen position issue inside a defensive branch that has never been observed (AC2 exception). The user: 「음? 뭔소리야 순서대로 들어가는거잖아. 앞지른다는게 뭔소리? 또 발생되지도 않는걸 가정함?」 (§6). The user: 「갑자기 목록이 사라져서 이상할것같은데 응답이 없으면 유저가 뭘 할 수있다고 스택에서 빼? 목록에서 뺀다는건 이유가 있어야되는거아냐」 (§6).
5. **A message sent to an idle agent goes into the conversation at once** — no flicker through the list. The same for codex (the immediate display of ADR-0198).
   - **Idle = no turn running and the list is empty.** If an item remains in the list — for example, the gap where A and B carried over from the previous turn are waiting for the next turn — a newly sent C does not go into the conversation at once but **stands at the end of the list**. This is because, to keep 「친 순서대로」 (typed order) (§3-1), C must not jump ahead of A and B. While codex is resuming (§3-11) is not idle either. **But while claude is loading a resumed conversation counts as idle** — there is no signal to tell that state from idle (§3-11).
   - **If the backend rejects a bubble drawn that way, the bubble is erased without notification** — the message is discarded (§3-7). The same when the rejection arrives **after** a list item has received its receipt and become a bubble (claude — not measured, §8 R10). The user: 「거절하면 우리쪽 채팅도 지워져야」. Whether such a bubble remains today is unconfirmed (§8 R9).
   - **If it is not a rejection but the agent ended or the turn was interrupted so the message could not be processed, the bubble stays** — nothing is done separately. The user: 「그냥 별도로 뭐 해야되는게 있음? resume 하면 어차피 갱신될텐데」 (§8 R11).
6. **✕ cancel — always present on every item in the list.**
   - **On both backends, in every stretch, every item in the list has a ✕ — pressing it removes that item from the list.** ✕ means 「목록에서 치운다」 (clear it from the list), not a promise to 「에이전트에게서 거둬 온다」 (take it back from the agent). The user: 「x를 건드릴 이유가 있어? 그냥 x누르면 목록에서 기계적으로 빼는거잖아. 구지 비활성 필요 있냐고」 — we also accepted the side effect that a message already handed over later shows up as a bubble (「상관없어」 — §6).
   - **claude item:** since it is a message already handed over, ✕ also sends the agent a request to remove that message.
   - **codex item:** a ✕ pressed while we are holding it (while a tool is running · while resuming (§3-11) · while waiting after an error-ended turn (§3-10)) keeps that message from going to the agent. An item already handed over (including one sent in a stretch where holding would delay delivery and so handed over at once — §3-1) also leaves the list with ✕, but since the vendor has no means to take back a single handed-over message (likely — source), it appears as a bubble at the end of the conversation when the agent receives it ((b) below).
   - **✕ on an item whose acceptance by codex is unknown (§3-4) counts as finished at once (discard)** — it leaves at once from the list that every window and the LLM read and does not stay in 「취소 중」 (it closes immediately). Mail flows unless something else blocks it. If a late receipt arrives, it becomes a bubble at the end of the conversation — we accepted that an outcome recorded as discarded flips into a bubble. If the receipt comes after the turn has already ended, there is no automatic answering turn and the user's next turn answers (§3-1 exception · concession). The user: 「끝난걸로쳐. 유저가 x눌렀을때 우연찮게 들어가는건 그냥 그렇다 치겠지」 (§6).
   - Cancel is a **registered command** — both backends use the same command, and the LLM cancels with the same command. ✕ is a user action that calls that command, not an action of the agent inside the slot.
   - ✕ is reachable with Tab, and the tooltip is 「목록에서 빼기」 — the same wording for every item and both backends, with no warning added. The user: 「계속 몇번을 얘기하는데 x눌러도 없어졌는데 안으로 들어가서 표시하는건 어쩔수 없잖아.」 (§6).
   - No Esc key binding for now (§7).
   - **When ✕ is pressed the item disappears from every window at once and does not reappear** — not only the window where it was pressed. The user: 「x 누르면 바로 빠지는 거잖아. 다른 창도 바로 빠져야 되는 거 아니?」. In the late case where the agent took it first, the message simply appears as a bubble at the end of the conversation in every window, with no separate notification (the user: that is enough).
   - **✕ is a request — the outcome is exactly one of three:** (a) **disappears** — the cancel is confirmed, the message is discarded (§3-7) · (b) **becomes a bubble at the end of the conversation** — the agent took it first · (c) **discarded** — the agent ended before the outcome, or the agent is alive but the backend rejected that item (§3-7). For claude, (a) and (b) are decided only by the agent's notification (§8 R2). A held codex item is in our hands, so it is usually (a) right away, and (b) if it coincides with the instant of handing over. An already handed-over codex item is (b) if the receipt arrives, and (c) if the agent ends without a receipt.
   - **「취소 중」 is a state of the single list that is drawn in no window** (an acceptance-unknown codex item does not go through it — above) — the LLM sees that item as 「취소 중」 in the list it reads through the command surface until the outcome. The outcome is reflected the same way for everyone — in (b) a bubble appears in every window, and in (a) and (c) there is simply nothing. Even after restarting the app a 「취소 중」 item appears in no window, and its outcome is reflected as is.
7. **Withdrawn and unsendable messages are discarded — no notification.**
   - A message cancelled with ✕ is discarded — it is not returned to the input box. The user: 「일단 그냥 다 버리고 나중에 생각하자」.
   - An item that can no longer be delivered because of an interrupt, agent exit, or backend rejection is also discarded (user confirmed night of 2026-09-25).
   - **There is no notification** — an unsent item simply leaves the list (if the rejected message already became a bubble, that bubble leaves — §3-5. An idle-time bubble that could not be processed because of an end or interrupt, not a rejection, stays — §3-5). If needed, it is added later (the user — §7).
   - **Interrupt = the running turn being stopped (by any operation).** A window losing its connection to the daemon is **not** an interrupt — the list stays, and the window re-syncs the list when it reattaches (this follows from §3-3). A turn that ended in an error is also not an interrupt — §3-10 decides it separately.
   - There is no automatic resend — resending an already handed-over message could make the agent receive the same message twice (research §2-4 · TRD §3-1).
8. **Messages stay separate.** Sending several does not concatenate them — one line each, one bubble each. The same applies when several remaining at turn end go into one turn together (§3-1).
9. **User input comes before agent-to-agent mail** (JSON mode).
   - Mail does not go on the list. Mail's 「한가」 (idle) is also the same as for user input — no running turn and the user list empty (§3-5).
   - So if user items are in the list, mail waits until those items go in and that turn ends. Mail can be delayed behind user input — this includes while a user item is waiting after an error-ended turn (§3-10). The user accepted this delay.
   - ★**After an abnormally ended turn, mail is not put in automatically — even if the list is empty**★ (both backends — it is our side that puts mail in, so it has nothing to do with vendor behavior · so it applies even to old codex below the version floor — only that version's list · ✕ · handover stay exactly as today, §2 · R6). During that time mail is not handed to the agent and waits on our side. An abnormally ended turn = a turn that ended with a real error (request limit · overload · context overflow), or a turn that failed at the request stage that opens the turn — whether it is a turn for a user message · a follow-up turn (§3-1) · a mail turn. A user cancel or interrupt and an agent exit do not count (a failure while inserting a message into a running turn also does not count, because the turn continues). **The trigger to flow again = the user's next input turn ends in success** — if that turn also ends abnormally, it keeps waiting. A turn that ended by interrupt or cancel neither sets nor lifts the stop (both backends). It ends together with the agent when the agent ends. The user: 「진짜 에러면 강제로 쑤셔넣으면 안되잖아」 · 「어쨋든 본질은 가능하면 자동으로 되고, 거기에 유저게 우선한다는 얘기지」. **Cost:** during that time the reason mail has stopped is not on the screen — it waits invisibly until the user types a message (the notification is deferred — §7). The LLM reads whether it is stopped through the command surface (AC18).
   - **The delay has no upper bound.** If a user item never gets its receipt and hangs in the list (§3-4), mail also waits that whole time — however long, until the agent ends. The user: 「일단 사용자 글이 막히면 우편도 막혀야 되는거 아냐? 상한이 필요한거? 애초에 글이 막히는것 자체가 이상한건데?」 (§6).
   - Mail in terminal (PTY) mode goes in as today.
10. **A message caught in a turn that ended in an error (request limit · overload · context overflow · request-stage failure).** It is not an interrupt (§3-7). After that, for both backends mail waits until the user's next input turn ends in success (§3-9 — the same for old codex below the version floor).
    - **codex — items left in the list are not sent automatically.** They wait in the list with ✕ (§3-6), and when the user sends the next message, **in one turn** together with that message, the remaining items go in first. Even if the limit is lifted again, they are not sent automatically — the user does not want the session touched. **After an error nothing is put in automatically** — neither list items, nor the follow-up turn for a message that got no answer (§3-1), nor mail (§3-9).
    - **claude — follow what the vendor does.** We do not force a match (the user: 「억지로 구현하지 마」). The list is kept in line with the vendor's actual handling by the per-item notifications — if the vendor discards the item it leaves the list (§3-7), and if it puts it into the conversation it becomes a bubble. **But mail is put in by us, so it does not follow the vendor and waits** (§3-9).
    - **A message that already became a bubble in that turn but got no answer** (including a message sent while idle) is left as it is — no follow-up turn is opened (both backends).
11. **A message sent while resuming (connecting · restoring history · loading a resumed conversation) stands in the list** — it does not count as idle (§3-5). **But claude is an exception** (below).
    - **codex:** we hold it (✕ is there — §3-6) and hand it over at once as soon as ready. When the receipt arrives, the bubble stands **below** the restored history. If the conversation was resumed but only the on-screen history restoration failed or was interrupted, it is handed over as is.
    - **claude — exception, exactly as today:** there is no signal to tell whether it is loading a resumed conversation or idle, so a message sent during that time counts as one sent while idle (§3-5) — it is drawn as a bubble at once and handed over at once, and the vendor processes it after finishing loading (not measured — §8 R5). In that short gap there is neither a list item nor ✕. The restored history is filled in before the agent appears on the list, so the bubble of a message sent after that stands below the history (code reading — TRD §5-4 · before on-screen measurement). The user: 「그냥 내가 채팅 치다가 오면 병합 잘 되는거잖아. 이번에 순서 삐뚤어져도 맞추는거 추가하잖아.」 (§6).
    - If the resume itself fails, the agent ends at the terminal point (ADR-0082 — no automatic switch to a new conversation), so the waiting items are discarded (§3-7).

## 4. Scenarios / edge cases

- **Sent while idle:** a bubble at the end of the conversation at once. The list does not appear.
- **A message sent while idle is rejected by the backend:** the bubble that was drawn disappears without notification, and the message is discarded (§3-5). The same when the rejection arrives after it went through the list and became a bubble (claude — not measured, §8 R10).
- **The agent ends, or the turn is interrupted, before the agent processes a message sent while idle (not a rejection):** the bubble stays — nothing is done separately (§3-5).
- **Corrective instruction during a long tool (build):** a gray line above the input box → when the agent receives it, it leaves the list and becomes a bubble at the end of the conversation at that moment → the agent's next action reflects that instruction. Usually it is received at the point where that build ends, and if it was sent at the instant the build ends, it is received at the next boundary or in the next turn — either way the agent answers (§3-1). For codex, we hold it while the build runs so it can be withdrawn with ✕, and hand it over at once at the point where the build ends.
- **Sent while writing a long answer without tools:** after that answer ends, the agent takes the message and answers → the bubble stands **below** the earlier answer. Whether codex holds or hands over at once in this stretch is decided after measurement — either way ✕ is there, and if it was handed over at once, a message the agent has received appears as a bubble even if ✕ is pressed (§3-1 · §3-6 · §8 R8).
- **Items left in the list when the turn ends:** they go into the next turn, in typed order. The user does not need to send again. If there are several, they go together into one next turn, each as its own separate bubble (for claude the vendor decides the bundling — §3-1).
- **C is sent in the gap where the remaining A and B are waiting for the next turn:** even if no turn is running, it is not idle — C stands at the end of the list, and the bubbles stand in the order A · B · C.
- **codex — right after a message goes into a turn (the bubble is up), that turn ends without answering:** a turn that answers that message follows. The same bubble is not created twice, and the same message does not go to the agent twice (method = TRD, M6). If even that follow-up turn ends in an error, it is not reopened — the turn the user's next message opens answers that message too, and until then mail waits (§3-1 · §3-9).
- **The turn ends in an error (request limit · overload · context overflow) — items remain in the list:** for codex the items wait in the list (✕ possible) → when the user sends the next message, the remaining items go in first, in one turn with that message. Even if the limit is lifted they do not go automatically. For claude the list follows what the vendor does — if the vendor discards, it leaves, and if it puts them into the conversation, they become bubbles. A message that already became a bubble in that turn but got no answer stays as it is (§3-10). For both backends mail does not go in even when the list is empty, and flows once the turn of the user's next message ends in success — if that turn is also an error, it keeps waiting (§3-9).
- **Several in a row:** the oldest on top, from the 4th it folds into 「외 N개」 and the oldest 3 are visible. Clicking 「외 N개」 expands it. They leave one by one as the agent receives them, each becoming its own bubble.
- **A truncated line:** hovering shows the full text.
- **✕ (both backends · every item · every stretch):** the item disappears from every window at once → (a) once the cancel is confirmed it does not reappear and does not go to the model (the next response does not know that message), and the message is discarded · (b) if the agent took it first, the message appears as a bubble at the end of the conversation in every window — no notification.
- **The agent ends or rejects before the ✕ outcome:** the item is discarded (§3-7).
- **A window other than the one where ✕ was pressed, and the LLM:** it is already gone from every window. Only the list the LLM reads shows 「취소 중」 until the outcome. The outcome is reflected the same way for everyone.
- **Sent mid-turn on codex:** we hold it until the agent can take it (a ✕ pressed in the meantime keeps the message from going to the agent) → we hand it over at once at the earliest boundary (usually the end of the tool now running) → when the receipt arrives, a bubble. If it was sent in a stretch where holding would delay delivery, it is handed over at once. ✕ is there even after handover — pressing it removes the item from the list, and when the agent receives it, it appears as a bubble.
- **It becomes unknown whether codex accepted (rare failure — no answer within 30 seconds to the handover request · the answer cannot be read · no echo until the end of the turn after an answer that it was received):** the item stays in the list as it is — ✕ is there, and mail waits with no upper bound. A message typed after it goes over in typed order as usual — if a late receipt arrives, its bubble can stand after the bubbles of the messages that went over in the meantime. If a late receipt arrives it becomes a bubble; otherwise the user removes it with ✕ (counts as finished at once — a bubble if a late receipt arrives) or it leaves when the agent ends (§3-4 · §3-6). If the receipt came after the turn ended, there is no automatically answering turn — the turn the user's next message opens answers that message too (in the meantime mail can get its answer first — §3-1 exception).
- **Input while codex is resuming (connecting · restoring history):** it stands in the list and we hold it (✕ possible) → handed over when ready → when the receipt arrives the bubble stands **below** the restored history. If the conversation was resumed but only the on-screen history restoration failed or was interrupted, it is handed over as is. If the resume itself fails, the agent ends at the terminal point (ADR-0082 — no automatic switch to a new conversation), so the waiting items are discarded (§3-7).
- **Input while claude is loading a resumed conversation:** exactly as today — as when idle, it is drawn as a bubble at once and handed over at once (no list or ✕). The vendor processes it after finishing loading (not measured — §8 R5 · §3-11).
- **The receipt never arrives:** the item stays in the list until the agent ends, and is then discarded. Mail also waits with no upper bound during that time (§3-9).
- **Interrupt / agent exit / rejection:** the remaining items disappear from the list without notification and are discarded. They do not return to the input box and are not resent.
- **A window loses its connection to the daemon and reattaches:** this is not an interrupt — no item disappears because the connection was lost. The reattached window shows the list and bubbles as they actually are: an item the agent received in the meantime as a bubble, an item discarded in the meantime as absent.
- **Two windows (main + pop-out):** the lists of the two windows are the same. Pressing ✕ in one makes it disappear at once from both, and if the agent took it first, it appears as a bubble in both together.
- **Closing and reopening a window:** the list stays as it is.
- **Restarting the dashboard app — daemon and agent alive:** the list appears as it is in the window that comes back up. A 「취소 중」 item appears in no window, and its outcome is reflected as is.
- **Daemon restart:** the list disappears together with the agent (§7 — the same grade as today's input queue).
- **The LLM queries the list · cancels an item:** the list on screen changes the same way — that item leaves every window at once, and only in the list the LLM reads does it stay as 「취소 중」 until the outcome.
- **Sent at the instant the turn ends (claude):** it can flash in the list for a moment and become a bubble at once — a display-only wobble.
- **A slash command (「/compact」, etc.) sent mid-turn:** handed over like any other message with no special treatment. How the agent handles it is not measured (§8 R7).
- **Typing mid-turn in a terminal slot:** no change — only the agent TUI's own waiting display is shown.
- **Agent-to-agent mail arrives (JSON):** it does not go on the list. If a turn is running or the user list has items, it waits and goes in once idle — it can be delayed behind user input. If the previous turn ended abnormally, even when idle it waits until the turn of the user's next message ends in success (§3-9).
- **Agent-to-agent mail arrives (terminal):** the same as today.
- **Old vendor versions (lacking the vendor features this feature relies on):** exactly as today — no list or ✕ of this feature (§2 · §8 R6). However, the mail stop after an abnormally ended turn applies (§3-9).

## 5. Acceptance criteria (visible behavior)

The number = the acceptance criterion id (AC#). The TRD cites these numbers, so they are not changed — new criteria are appended at the end.

1. On both backends, a message sent **while idle** (no running turn + empty list · not resuming — but while claude is loading a resumed conversation counts as idle, §3-5 · §3-11) does not go through the list and shows up at once as a bubble at the end of the conversation — no list flicker.
2. A message sent while items remain in the list stands at the end of the list even if no turn is running, and does not jump ahead of earlier items — the bubble order equals the typed order. **Exception — a codex item whose acceptance is unknown (§3-4):** a message typed after it goes over in typed order as usual, so if a late receipt arrives for that item, its bubble can stand after the bubbles of the later messages.
3. **claude JSON:** a message sent during a long tool shows up at once in the list above the input box (one gray line), usually leaves the list at the moment that tool ends and becomes a bubble **at the end of the conversation at that moment**, and the agent's next response reacts to that message (a message sent at the instant the tool ends goes to the next boundary or the next turn — 5). There is no bubble in the middle of the earlier answer (the sent position).
4. **codex JSON:** a message sent during a long tool reaches the model **at the boundary where that tool ends**, without waiting until the end of the turn — it is not pushed to the next boundary because we were holding it and missed that boundary (a message sent at the instant the tool ends goes to the next boundary or the next turn — 5). The list → bubble transition is the same as in 3.
5. **Every sent message goes into a turn in which the agent answers, unless it is discarded under §3-7.** An item that did not get into the running turn goes into the next turn in typed order after the turn ends, and the user does not need to send again. No bubble without an answer is left in the conversation. **Exception — a turn that ended in an error (§3-10):** a message that already became a bubble in that turn but got no answer (including a message sent while idle) stays as it is (no follow-up turn) · a codex item left in the list waits until the user sends the next message (24) · a claude item left in the list follows the vendor's handling (25). **Exception — when the follow-up turn of 6 ends abnormally (§3-1 · §3-9):** that turn is not reopened, and the message is answered by the turn the user's next message opens. **Exception — a codex item whose receipt arrives late, after the turn has ended (§3-1 · including one closed with ✕ — 13):** the bubble stands but there is no automatically answering turn, and the turn the user's next message opens answers it (in the meantime mail can get its answer first).
6. **An item that already went into a turn but whose turn ended without answering (codex) also gets a turn that answers it** — a bubble of the same message is not created twice, and the same message is not handed to the agent twice. **Exception — if that follow-up turn ends abnormally,** it is not reopened: the message is answered by the turn the user's next message opens, and until then mail waits (29). An item whose receipt arrived late after the turn ended also does not get this follow-up turn (the exception in 5).
7. When several are sent, one line each (「…」 if it overflows · hovering shows the full text), the oldest on top, with 4 or more folded into 「외 N개」, the oldest 3 visible while folded, and clicking 「외 N개」 expands it. When delivered, each becomes its own separate bubble and they are not concatenated.
8. There is no header line (a line of guidance text) above the list — only gray items are shown, whatever state the turn is in. A message typed while codex is resuming (§3-11) stands in the list, and its bubble stands below the restored history.
9. An item leaves one by one only when the agent reports that it received that item — writing the message in is not enough to remove it, and the list does not empty all at once because a tool ended. If the receipt never arrives, it stays in the list until the agent ends.
10. ✕ is always present on every item in the list — both backends, in every stretch (before and after handover · the stretch where it hands over at once · while resuming · while waiting after an error-ended turn). There is no disabled or hidden state. Pressing it removes that item from the list, and the outcome is one of 11–13. ✕ is reachable with Tab and the tooltip is 「목록에서 빼기」 (the same wording for every item · both backends).
11. **✕ — (a) the cancel wins (both backends):** the item disappears from every window at once and does not reappear — no 「취소 중」 item is visible in any window. In the list the LLM reads it stays as 「취소 중」 until the outcome and disappears when the outcome arrives. The model's next response does not know that message, and the message does not return to the input box. **Exception — a codex item whose acceptance is unknown (§3-4):** it leaves at once from the list the LLM reads too and does not stay in 「취소 중」 (it closes immediately — the outcome is recorded as the discard of 13).
12. **✕ — (b) the agent took it first:** the message that had already disappeared from every window appears as a bubble at the end of the conversation in every window (no notification). The agent answers that message.
13. **✕ — (c) the agent ended before the outcome, or the agent is alive but the backend rejected that item:** the item stays gone from every window and does not reappear, leaves the list the LLM reads too, and is discarded (it does not return to the input box). **One ✕ ends in exactly one of 11 · 12 · 13** — it never happens that an item disappeared but went to the model, or became a bubble but the model does not know it. **Exception — a codex item whose acceptance is unknown (§3-4):** it ends as a discard (13) at the moment of ✕, but if a late receipt then arrives it becomes a bubble at the end of the conversation (12) — we accepted this one case in which a discard flips into a bubble (§3-6). If the receipt comes after the turn has already ended, there is no automatically answering turn and the turn the user's next message opens answers (exception to 5 · concession).
14. An item that could not be sent because of an interrupt, agent exit, or rejection disappears from the list without notification, does not return to the input box, and is not resent automatically.
15. When the main window and a pop-out window view the same agent, the list is the same — pressing ✕ in one makes it disappear at once from both, and the outcome is reflected the same way in both (11–13). The list stays as it is after closing and reopening a window.
16. Even when a window loses its connection to the daemon and reattaches, no item disappears **because the connection was lost**. The reattached window shows the list and bubbles as they actually are — an item received in the meantime as a bubble, an item discarded in the meantime as absent — and it matches the other windows.
17. If the dashboard app is restarted with the daemon and agent still alive, the list appears again as it was. An item being cancelled appears in no window, and its outcome (including the bubble of 12) is reflected as is.
18. The LLM reads the same list through the command surface and can cancel any item in the list (both backends) — the same command as the on-screen ✕. Through the same list query it also reads whether the agent is stopped after an abnormally ended turn (one yes/no · both backends — 29). There is no Esc key binding.
19. The gray text of the list is readable in all three themes (dark · light · e-ink).
20. The list does not cover the agent name tag above the input box.
21. **Terminal (PTY) mode stays as it is:** typing mid-turn does not bring up the dashboard list and shows only the agent TUI's own waiting display, and the input bytes are the same as today (the existing terminal regressions are green).
22. Agent-to-agent mail does not go on the list. **In JSON mode mail can be delayed behind user input** — it goes in only when no turn is running and the user list is empty (including while a user item is waiting after an error-ended turn · with no upper bound if a user item is stuck for lack of a receipt — §3-9). **Exception — after an abnormally ended turn it does not go in even if the list is empty (29).** The shape of mail is the same as today. Mail in terminal mode is delivered at the same time and in the same shape as today.
23. Completion is decided by GUI measurement (`/qa full`) — passing tests and the type check alone is not completion.
24. **codex — items left in the list after an error-ended turn** are not sent automatically: they wait in the list with ✕, and when the user sends the next message, the remaining items go in first, **in one turn** together with that message (each as its own bubble). Even if the limit is lifted over time they do not go automatically. Even if a remaining item was typed after an item for which it is unknown whether codex accepted it (§3-4), it goes over as usual (exception to 2).
25. **claude — a list item caught in an error-ended turn** is shown as the vendor handled it — if the vendor discards it, it leaves the list without notification, and if it puts it into the conversation, it becomes a bubble. The list is not left diverging from the vendor's actual handling. Mail does not follow the vendor and waits as in 29.
26. If a message sent while idle is drawn as a bubble and then rejected by the backend — even when the rejection arrives after a list item has become a bubble — that bubble disappears without notification and the message does not return to the input box (both backends). An idle-time bubble that could not be processed because the agent ended or the turn was interrupted, not because of a rejection, stays as it is.
27. **codex — several items left at turn end** go into **one** next turn together, in typed order, each as its own bubble — a separate turn is not run for each item. For claude the vendor decides the bundling, and if it differs from this we report it (ADR-0192).
28. **A message sent while resuming:** for codex it is held in the list with ✕ and handed over when ready, and it is handed over as is even if the conversation was resumed and only the on-screen history restoration failed or was interrupted. claude is an exception — a message sent while loading a resumed conversation does not go through the list, as when idle, but becomes a bubble at once (no ✕), and the vendor answers it after finishing loading. If the resume itself fails, the waiting items are discarded.
29. **Mail after an abnormally ended turn (both backends — including old codex below the version floor, where only that version's list · ✕ · handover stay exactly as today · §2 · R6):** when a turn ends with a real error (request limit · overload · context overflow) or a request-stage failure — whether it is a turn for a user message · a follow-up turn · a mail turn — mail is not put in automatically even if the list is empty, and codex does not reopen the follow-up turn for a message that got no answer either. When the user's next input turn ends in success, mail flows, and if that turn also ends abnormally it keeps waiting. A turn that ended by a user cancel or interrupt neither sets nor lifts the stop (both backends). During that time mail is not handed to the agent and waits on our side.

## 6. Rejected alternatives (the user's reasons — move to the new ADR's 「거부한 대안」)

The symbols in parentheses are names used by the research report and the TRD. They are spelled out so that this document makes sense on its own.

- **Pin a proper bubble at the sent position** (today's claude behavior · the original plan of ADR-0198 · research's B) — mid-turn, the rest of the earlier answer continues below it and the order gets mixed up.
- **Put a gray waiting row at the very bottom of the conversation (below the flowing answer)** (A, which was the research report's recommendation) — the user: 「터미널이 가장 자연스럽다」.
- **Put a header line (a line of guidance text) above the list** — a plan that puts 「도구 호출이 끝나면 전달」 (delivered when the tool call ends) mid-turn while a tool is running, 「준비되면 전달」 (delivered when ready) while codex is connecting or restoring history, and a second wording (for example 「응답이 끝나면 전달」 (delivered when the response ends)) mid-turn when no tool is running. It was once a decision. The user: 「한 줄 낭비」 — like Claude Code, only gray items.
- **We hold it until the turn ends** (today's codex behavior) — the user: 「당연히 도구 호출 끝나면 바로 푸쉬」.
- **codex also hands over as soon as received** (immediate delivery common to both backends — once a decision. The user: 「클로드든 코덱스든 우리가 받고 바로 전달하자. 일단 공용화하고 나중에 세분화」) — replaced by the user's principle 「받을 수 있는 가장 이른 때 전달」 (deliver at the earliest moment it can be taken). codex lands at the same boundary even if held until the end of the tool (Phase 0 measurement), so delivery is not late, and we hold it in the meantime — a ✕ pressed during the hold keeps the message from going to the agent. The user: this is not later work but part of this feature.
- **Hold claude on our side and hand it over after seeing the tool end** (the TRD's S1) — one step late. The agent checks its own inbox as soon as the tool ends, so a message handed over after that misses the boundary and is read only when the next tool ends (user confirmed · Phase 0 measurement 0/10). **For codex this method is the adopted plan** (§3-1) — it landed at the same boundary even when held and then handed over (10/10 · the timing basis for the decision = TRD · §8 R8).
- **Have an agent hook pull our waiting items every time a tool ends** (the TRD's S4) — the user: 「훅마다 매번 뭔가 실행하면 안 된다」.
- **Hold codex and hand over when a tool *starts*, keeping ✕ alive only until then** (the TRD's S5 · the old recommendation in the TRD body) — the original reason was 「공통 동작을 먼저, 세분화는 나중」 (the common behavior first, refinement later). Now the principle of §3-1 (hold while holding does not delay) chooses holding until the tool *ends* — the delivery time is the same and ✕ stays longer.
- **Concatenate the waiting items and send them at once** — each backend needs a workaround, and if we hand over as soon as received there are no waiting items to gather to begin with, so it is meaningless. (Research report §5 adds 「항목별 id 가 하나로 뭉개져 합치기가 깨진다」 (the per-item ids get lumped into one and merging breaks).)
- **Keep the bubble even if a message sent while idle is rejected** (attach a 「전달 안 됨」 (not delivered) mark, or leave it as is) — the user: 「거절하면 우리쪽 채팅도 지워져야」.
- **The first message of a claude resumed incarnation always goes through the list** (a plan that safely puts only the first message in the list, since there is no signal to tell whether it is loading) — a new marker is separately needed to tell this, and even if loading has already finished, the list flashes for an instant (about 1 ms) and leaves, breaking AC1 (no list flicker) on every resume. ## 7. Deferred (non-goals for now — later candidates)

- **The turn-interrupt operation — the feature right after this one** (user decision). An operation in the chat view that stops the running turn. Whether to discard the waiting items when interrupting (as in §3-7) or send them to the next turn (Claude Code's Esc style) is decided in that feature. claude JSON has to bring in interrupt support first (§2).
- **Returning cancelled and unsent messages to the input box** — and the rule for attaching several to the input box (overwrite · concatenate).
- **Notification of discard and failure** — none for now (§3-7). Added later if needed (the user). Shapes that were considered: a line inside the conversation · a place in the list · a toast · showing the full text of the discarded message.
- **Esc key binding** — cancel is already a registered command, so it only needs to be bound.
- **Mail notification** — if in conversation with the user, ask 「우편 왔습니다 — 확인하세요」 and expand, and if not in conversation, just expand (the user's idea 2026-09-26). This resolves the cost that, after an abnormally ended turn, mail looks stopped for no reason (§3-9).
- **Letting it flow again automatically on the limit-lifted signal** — rejected for now (§6 · the user: 「아냐 일단 복잡하게 하지말자」). To bring it up again, we first have to resolve that the signal covers only one kind of usage limit and is a forecast time.
- **「지금 보내기(Send now)」 — interrupt the running turn and send this message at once.** Precedents: Claude Code Ctrl+Enter = interrupt and send now (2.1.275↑) · Esc = interrupt and send the waiting items next · Up = pull the waiting items back into the input box · Cursor also has Ctrl+Enter interrupt and Send now (uncertain — changelog) (research report §2-1 · §2-2). This feature has no path that interrupts and sends. The user raised it only as a question on the night of 2026-09-25 and there is no decision (it sits on top of the turn-interrupt operation above).
- **Automatically opening a turn that answers a codex item whose receipt arrives late after the turn has ended** — conceded for now (§3-1 exception · the user: 「복잡한것보다 약간 양보하면서 단순한 방향으로 하되 나중에 문제되면 기능 추가하면 되지」). To be added if mail getting its answer first in the meantime becomes a real problem (the way of not handing the same message over twice = TRD).
- **Keeping the list across a daemon restart** — the waiting items disappear together with the agent (the same grade as today's input queue).

## 8. Risks · unknowns

- **R1. ★The claude side relies on a vendor-internal surface and has not yet been measured in our spawn mode★.** This applies to both the per-item receipt notification and the cancel request — if they do not work, the claude behavior of §3 (list · ✕) changes. If the measurement result changes what the user feels, it is raised again as a user decision. — likely · not measured. Details = TRD §3-1 · §3-3 (M1–M4).
- **R2. Even if claude answers a ✕ with 「못 뺐다」 (could not remove it), that does not mean 「전달됐다」 (it was delivered)** (it sometimes reserves the cancel and confirms it later) — so the outcome of a claude ✕ is decided only by the notification that follows (§3-6). — likely · not measured (M3). Details = TRD §3-1.
- **R3. A codex item cannot be withdrawn after handover** — there is no means to remove a single item handed over to the vendor. ✕ is there afterwards too and removes the item from the list when pressed (§3-6), but keeping the message from going to the agent is possible only while we hold it — a ✕ pressed after handover returns as a bubble when the agent receives it (the user accepted this). In a stretch where holding would delay delivery (§3-1) it is so from the start, and this feature also has no turn-interrupt operation (§2). In those stretches the felt experience of the two backends (claude even sends a request to remove it with ✕) diverges, and it is a subject of ADR-0192 「못 맞추면 보고」. — likely (source) · the absence of an interrupt operation is certain (code).
- **R4. A message without an answer must not arise (the §3-1 requirement)** — codex has a vendor behavior of only recording, without answering, a message that went in at the instant the turn ends, so whether the design could block this without handing it over twice was a TRD risk (M6). **It stood in Phase 0b** (`docs/research/mid-turn-phase0b-measurements-2026-09-26.md` §0): M9 green — an empty-input turn was accepted and answered exactly that one message that had not got an answer (3/3) · M10 green — the end-of-turn 「기록만」 (record only) branch reproduced in 3 of 4 runs, and the echo of the recorded input came before the turn-complete notification. What remains is a gap of one late receipt that arrives **after** the turn has ended, and that was accepted as the §3-1 exception (concession). — certain (measured).
- **R5. In resume restoration, claude's mid-turn input can be missing** — after resuming, that bubble may be absent from the restored history, and this feature makes that case common. Whether the vendor processes a message handed over while loading a resumed conversation (counted as sent while idle — §3-11) after the loading has also not been measured. If the measurement result changes what the user feels, it is raised again as a user decision. — uncertain (M5 · M14). Details = TRD §3-1.
- **R6. Old versions without the vendor prerequisites (claude's receipt notification · codex's item id echo — codex 0.140.0 or later) are not specially supported** — exactly as today (the user: 「알아서 업데이트」 · §2). How to tell the versions apart is up to the TRD. The mail stop after an abnormally ended turn (§3-9) applies to old versions as an exception.
- **R7. A slash command sent mid-turn (「/compact」, etc.) is not treated specially** — it is handed over like any other message, and whether the agent runs it as a command, defers it to the end of the turn, or emits a receipt notification has not been measured (the Claude Code docs say commands and shell input are held until the end of the turn — whether it is the same in our mode is unknown). **Bad case:** if the vendor holds the command until the end of the turn or does not emit a per-item receipt notification, that item gets no receipt and stays in the list in gray until the agent ends (§3-4). Since the list does not empty in the meantime, the agent is not idle in the sense of §3-5, every message sent afterwards also goes through the list (loss of AC1), and mail also cannot go in, with no upper bound — until the agent ends (§3-9). **Phase 0b M13 green** (`docs/research/mid-turn-phase0b-measurements-2026-09-26.md` §0): `/compact` 3/3 and `/cost` 3/3 sent mid-turn on claude entered the queue and then, instead of being folded in at a tool boundary, were held until the running turn ended and started and finished as a new turn — there was never a rejection, cancel, or discard. So the bad case above does not occur for these two commands (the list item receives its receipt in that new turn and leaves — staying gray until the turn ends is the normal shape of the command). Other commands were not measured. If the measurement result changes what the user feels, it is raised again as a user decision.
- **R8. ★Holding codex (§3-1) stands only if we can hand it over to the boundary in time★** — the point where a tool ends landed at the same boundary even when held and then handed over (Phase 0 — 10/10), but our daemon's reaction time, and whether the same gap exists in the stretch where only an answer is written without tools and then ends, have not yet been measured. The TRD measures and decides the timing basis for the decision. A stretch that cannot keep up hands over at once per §3-1 (✕ is there, but it cannot take the message back — §3-6), and if the measurement shows that even the stretch at the tool end cannot keep up, we ask the user again before coding (holding vs. another path).
- **R9. Whether, today, a bubble remains when a message sent while idle is drawn as a bubble and then rejected by the backend is unconfirmed** — §3-5 decides that it be erased without notification. If it is already erased today there is nothing to do, and if it remains it must newly be erased.
- **R10. The premise that a rejection can come after a list item has received its receipt and become a bubble is not measured** (claude — a rejection notification after the notification that it was received). §3-5 decides that the bubble be erased in that case too. If no such order actually occurs there is nothing to do.
- **R11. When the agent ends or the turn is interrupted before a message sent while idle is processed and the vendor has not recorded it, whether that bubble drops out when resuming and reloading the history is unconfirmed** — §3-5 decided to leave it as is (the user: it gets refreshed anyway when resumed).
