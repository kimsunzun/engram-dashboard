# PRD — S21 턴 도중 보낸 입력: 입력창 위 대기 목록 · 받을 수 있는 가장 이른 때 전달 · 받기 전 취소 (JSON 채팅 모드)

**상태:** 초안 6판(2026-09-26) — TRD 7판 §10-4 사용자 답(N11 · N12 · N13 · ✕ 툴팁)을 반영했다. **6판으로는 아직 리뷰 전이다.** 5판(2026-09-25) = 사용자 Q&A 답(2026-09-25 오전 — §9 Q1–Q9 전부 · TRD 질문 N1·N2·N4·N5·N6 · 같은 날 TRD 질문 N7·N8·N9 · 같은 날 ✕ 상시 표시와 수락 여부를 모르는 codex 항목)을 반영했다. 4판 = `/review prd` 3차 FIX(문장 4건) 반영 · 4차 리뷰 생략(리뷰어 판단 — 메인이 반영만 확인).
**판 이력 — 5판에서 뒤집힌 결정:** ① 4판의 「두 백엔드 공통으로 받자마자 넘긴다 · ✕ 는 claude 항목에만」 → 사용자 원칙 「받을 수 있는 가장 이른 때 전달」: codex 는 붙들어도 늦지 않는 동안 우리가 붙들고 그 동안 ✕ 를 준다(§3-1 · §3-6). ② 목록 머리줄(「도구 호출이 끝나면 전달」 · 「준비되면 전달」)을 없앴다(§3-2). ③ 버림·실패 알림은 두지 않고, 한가할 때 보낸 글이 거절되면 그 말풍선을 지운다(§3-5 · §3-7). ④ 우편이 사용자 입력 뒤로 늦어질 수 있다(§3-9 · AC22). ⑤ 4판의 「✕ 뒤 결말 대기 항목은 모든 창에 「취소 대기」로 보인다」 → ✕ 를 누르면 모든 창에서 곧바로 빠지고, 「취소 중」은 LLM 이 읽는 목록에만 남는다(§3-6). ⑥ 「claude 가 이어받은 대화를 불러오는 중 보낸 글은 목록에 선다」 → 한가와 가려낼 신호가 없으므로 오늘처럼 한가할 때 보낸 글로 친다(§3-11). ⑦ ①의 「codex 는 붙든 동안만 ✕ · 넘긴 뒤와 곧바로 넘기는 구간엔 ✕ 없음」 → ✕ 는 두 백엔드 모든 항목에 어느 구간에서든 늘 있고, 누르면 목록에서 빠진다 — 에이전트가 이미 가져갔으면 말풍선으로 나타난다(§3-6). 뒤집힌 옛 결정은 §6 에 거부한 대안으로 남겼다.
**판 이력 — 6판(2026-09-26)에서 바뀐 것:** ① TRD 질문 N11(빚진 후속 턴이 실패하면)의 답을 원칙으로 넓혔다 — **이상하게 끝난 턴 뒤에는 멈춘다**: 진짜 오류(요청 한도 · 과부하 · 맥락 초과)나 요청 단계 실패로 턴이 끝나면 후속 턴도 우편도 저절로 넣지 않고, 사용자의 다음 입력 턴이 성공으로 끝나야 다시 흐른다 — 우편은 두 백엔드 모두(§3-1 · §3-9 · §3-10 · AC5 · AC6 · AC22 · AC29). 5판의 「오류 턴 뒤 목록이 비면 우편이 곧바로 든다」가 이것으로 바뀌었다. ② N12 — 수락 모름 codex 항목의 ✕ 는 곧바로 끝난 것(버림)으로 친다 — 「취소 중」에 머물지 않는다(곧바로 닫힌다)(§3-4 · §3-6 · AC11 · AC13). ③ N13 — 수락 모름 항목 뒤에 친 글은 평소대로 친 순서대로 넘어간다 — 5판의 「그 항목 뒤에서 기다린다」(사용자 확인 대기)를 걷었다(§3-4 · AC2 · AC24). ④ ✕ 툴팁 = 「목록에서 빼기」 — 5판의 「취소 — 글은 버려짐」을 바꿨다(§3-6 · AC10). 거부한 대안은 §6 에 남겼다. ⑤ 뒤이은 맞춤(같은 날 · TRD 8판 핵심 절에 맞춤): 턴이 끝난 뒤 늦게 받음이 온 codex 항목(✕ 로 닫은 것 포함)은 말풍선만 서고 **저절로 답하는 턴을 열지 않는다** — 답은 사용자의 다음 턴이 한다(양보 · §3-1 · §3-4 · §3-6 · AC5 · AC6 · AC13 · §7) · Phase 0b M9 · M10 · M13 녹(§8 R4 · R7) · 턴 끝 「이것들 받았나」 확인은 TRD 에서 걷혀 수락 모름의 출처에서 뺐다(§3-4). 사용자 방향: 「복잡한것보다 약간 양보하면서 단순한 방향으로 하되 나중에 문제되면 기능 추가하면 되지」. ⑥ TRD 8판 6차 리뷰 맞춤(같은 날): 이상하게 끝난 턴 뒤 우편 멈춤을 **버전 하한 밑 옛 codex 에도 건다** — ⑤ 가 한때 두었던 옛 codex 제외를 걷었다, 우편을 넣는 것은 우리 쪽이고 멈춤은 우리가 보는 턴 끝만 읽기 때문이다(옛 codex 의 목록·✕·넘기기는 그대로 오늘 동작 · §2 · §3-9 · §3-10 · §4 · AC29 · R6) · 멈춤을 푸는 것은 사용자의 다음 입력 턴의 **성공**뿐이고 끊기·취소로 끝난 턴은 멈춤을 걸지도 풀지도 않는다(두 백엔드 · §3-9 · AC29) · TRD 확정과 구현은 사용자가 맡겼다 — 사용자는 최종 보고를 검토한다(§10) · LLM 이 멈춤 여부를 읽는다(§3-9 · AC18).
**작성:** 2026-09-25 — **소급.** 조사 보고서와 TRD 초안이 먼저 나왔고, 그 사이 사용자가 내린 결정을 「무엇·왜」로 박아 두려고 뒤늦게 쓴다. 이 문서는 구현을 적지 않는다 — 「어떻게」는 TRD 몫이다.

## 1. 무엇 / 왜

**무엇.** 구조화 채팅(JSON) 슬롯에서 에이전트가 턴을 도는 도중에 보낸 글을, **에이전트가 실제로 받을 때까지 입력창 위 목록에 따로** 보이고, 받는 순간 **대화 끝에 평범한 말풍선**으로 옮긴다. 글은 **에이전트가 받을 수 있는 가장 이른 때**에 넘긴다 — 보통 **지금 도는 도구 호출이 끝나는 지점**에서 읽히고, 그 턴에 못 들어가면 다음 턴으로 간다. 목록의 모든 항목엔 ✕ 가 있어 누르면 목록에서 빠진다 — 에이전트가 이미 가져간 글이면 대화 끝 말풍선으로 나타난다(§3-6).

**오늘의 증상(사용자 체감).**
- **claude(JSON)** — 보낸 글은 곧바로 에이전트에게 가고 에이전트도 도구 호출이 끝나는 지점에서 읽는데, 화면은 **보낸 자리**에 정식 말풍선을 박는다. 그래서 앞 답의 나머지가 그 말풍선 **아래로** 이어져, 대화 순서가 에이전트가 실제로 읽은 순서와 어긋나 보인다. 보낸 뒤 거둘 방법이 없다.
- **codex(JSON)** — 턴 도중 보낸 글은 **턴이 끝날 때까지 모델에게도 화면에도 가지 않는다.** 글이 먹혔는지 알 수 없고, 도는 에이전트를 도중에 바로잡을 수 없다(긴 빌드 중 교정 지시가 턴 끝에야 닿는다). 한가할 때 보낸 글도 에이전트가 되울려 줄 때에야 뜬다 — 사용자가 처음 짚은 「보낸 글이 늦게 뜬다」가 이것이다. 거둘 방법도 없다.
- **공통** — 「보냈지만 에이전트가 아직 안 받은 글」이라는 상태가 화면 어디에도 없다.

**왜 이 모양인가(조사 결론).**
- 턴 도중 보내기를 막지 않는 것이 현재 에이전트 도구의 관행이다(Claude Code · Codex · t3code · paseo · Cursor 등). — 가능성 높음
- 대기분은 대화 밖에 따로 보이고, 정식 말풍선의 자리는 **보낸 시점이 아니라 전달 시점**이다(Codex TUI · t3code 소스로 선다). 보낸 자리에 정식으로 고정하는 곳은 Orca 하나다. — 가능성 높음
- 대화 밖 표시 위치는 두 갈래(대화 맨 아래 대기 행 / 입력창 위 목록)이고, 사용자는 터미널 CLI(Claude Code · Codex TUI)와 같은 **입력창 위 목록**을 골랐다.
- 두 백엔드 모두 이 모양을 받칠 수단이 있다 — 턴 도중 입력을 도구 경계에서 받아들이고, 받은 항목을 하나씩 알려 준다. — 가능성 높음(벤더 원문·소스) · **우리 스폰 모드에서는 미실측**(§8 R1)
- 넘기는 때가 두 백엔드에서 갈린다 — claude 는 도구가 끝난 뒤에 넘기면 그 경계를 놓치고(0/10), codex 는 도구가 끝난 뒤에 넘겨도 같은 경계에 든다(10/10). 그래서 codex 는 그때까지 붙들 수 있고, 붙든 동안 누른 ✕ 는 글이 에이전트에게 가지 않게 한다. — Phase 0 실측 · 우리 데몬의 반응 시간과 도구 없는 구간은 미측정(§8 R8)

## 2. 범위 (사용자 결정)

- **들어간다:** JSON(구조화 채팅) 모드의 **사용자 입력** — claude stream-json · codex app-server. 두 백엔드 모두 목록 항목의 ✕ 취소를 포함한다(모든 항목 · 모든 구간 — §3-6).
- **빠진다 — 터미널(PTY) 모드.** 사용자: 「터미널 모드는 그런거 필요없잖아」. 거기서는 에이전트 자신의 TUI 가 턴 중 입력을 이미 줄 세워 보인다. 터미널 슬롯의 동작과 입력 바이트는 하나도 안 바뀐다 — 터미널 모드의 에이전트 간 우편도 오늘 그대로다.
- **에이전트 간 우편 — 목록에는 오르지 않는다.** 경로는 오늘 그대로지만, JSON 모드에서는 사용자 입력이 먼저라 우편이 늦어질 수 있다(§3-9).
- **빠진다 — 턴 끊기 조작.** 별도 기능으로, 이 기능 바로 다음에 한다(사용자 결정 — §7). 사실: 오늘 채팅 뷰에는 턴 끊기 조작이 없다 — 화면에도 명령 표면에도 없다(연결 수준의 끊기 요청은 있으나 부르는 곳이 없다 — 2026-09-25 코드 확인). claude JSON 은 끊기 자체가 아직 지원되지 않는다(TRD §3-1). 그래서 이 기능 안에서 턴을 실제로 멈추는 것은 오류로 끝나는 턴뿐이다(§3-10).
- **빠진다 — 벤더 전제가 없는 옛 버전.** 이 기능이 기대는 벤더 기능(항목별 받음 알림 등)이 없는 버전은 따로 받치지 않고 오늘 동작 그대로 둔다(사용자: 「알아서 업데이트」 — §8 R6). 단 이상하게 끝난 턴 뒤 우편 멈춤(§3-9)은 우리 쪽 일이라 옛 버전에도 건다.

## 3. 동작 명세 (사용자 결정 — 다시 열지 않는다)

1. **에이전트가 받을 수 있는 가장 이른 때에 넘긴다.** 사용자 원칙: 에이전트가 받을 수 있는 한 가장 빨리 전달한다. 에이전트는 턴 도중 받은 글을 **지금 돌고 있는 도구 호출이 끝나는 지점**에서 읽는다.
   - 사용자: 「당연히 도구호출 끝나면 바로 푸쉬」.
   - **claude — 받자마자 넘긴다**(오늘처럼 즉시). 도구가 끝나는 것을 보고서야 넘기면 그 경계를 놓쳐 **다음** 도구가 끝날 때에야 읽힌다(사용자 확인: 「도구가 끝날 때 넘기면 다음 도구가 끝나야 전달되지 않나」 — 그렇다 · Phase 0 실측도 같다). 즉시 넘기면 글이 처음부터 에이전트 쪽 대기함에 있어 지금 도는 도구의 끝에서 읽힌다.
   - **codex — 붙들어도 전달이 늦어지지 않는 동안만 우리가 붙들고, 에이전트가 받을 수 있는 가장 이른 때에 곧바로 넘긴다**(진행 중 턴에 끼워 넣기, 도는 턴이 없으면 새 턴). 붙든 동안 ✕ 를 누르면 그 글은 에이전트에게 가지 않는다(§3-6). 도구가 끝나는 지점은 붙들었다 넘겨도 같은 경계에 들었다(Phase 0 실측). **어떤 구간에서 붙들면 전달이 늦어진다면, 그 구간에서는 붙들지 않고 곧바로 넘긴다** — ✕ 는 그대로 있지만, 누른 때 에이전트가 이미 가져갔으면 그 글은 말풍선으로 나타난다(§3-6). 어느 구간이 그런지와 그 판정의 시간 근거는 아직 재는 중이고 TRD 가 정한다(§8 R8). 사용자: 이것은 나중 일이 아니라 이 기능의 일부다.
   - **턴 끝 경계:** 도는 턴에 끝내 못 들어간 항목(도구 없이 답만 쓰다 턴이 끝났거나, 경계를 놓쳤거나)은 턴이 끝난 뒤 **다음 턴으로, 친 순서대로** 들어간다 — 사용자 결정 「도구 경계 없이 턴이 끝나면 남은 항목은 친 순서대로 자동 전송」(2026-09-25 · TRD 본문 D5). 이것은 §3-7 이 막는 재전송이 아니다 — 아직 어느 턴에도 안 들어간 글을 처음 들여보내는 것이다. **남은 항목이 여럿이면 한 다음 턴에 함께, 각자 따로 메시지로 들어간다**(§3-8) — codex 는 우리가 그렇게 들이고, claude 는 벤더가 묶음을 정한다(미측정 — 어긋나면 다시 올린다, ADR-0192). 오류로 끝난 턴은 이 규칙이 아니라 §3-10 을 따른다.
   - ★**요구: 보낸 글은 §3-7 로 버려지지 않는 한 전부 에이전트가 답하는 턴에 들어간다**★ — 대화에 말풍선만 있고 답이 없는 글이 남으면 안 된다. **예외 셋은 아래** — 후속 턴이 이상하게 끝남 · 오류로 끝난 턴 · 턴이 끝난 뒤 늦게 받음이 온 codex 항목.
   - **이미 들어갔는데 답을 못 받은 항목도 같다:** 받음이 와 말풍선이 됐는데 그 턴이 그 글에 답하지 않고 끝나면(codex — 턴이 끝나는 찰나에 들어간 글), 그 글도 답하는 턴을 받아야 한다. **단 같은 글을 에이전트에게 두 번 넘기거나 말풍선을 두 번 그리지 않는다.** 방법 = TRD(M6). **그 후속 턴이 이상하게 끝나면(§3-10) 다시 열지 않는다** — 그 글은 이미 대화 기록에 있으므로 사용자의 다음 글이 여는 턴이 그 글에도 답한다. 그때까지 우편도 기다린다(§3-9).
   - **예외 — 오류로 끝난 턴(§3-10):** 그 턴에서 이미 말풍선이 됐는데 답을 못 받은 글(한가할 때 보낸 글 포함)은 그대로 둔다 — 후속 턴을 열지 않는다. 목록에 남은 codex 항목은 사용자가 다음 글을 보낼 때까지 기다린다.
   - ★**예외 — 턴이 끝난 뒤 늦게 받음이 온 codex 항목(양보)**★: 수락 모름 항목(§3-4 — ✕ 로 닫은 것 포함, §3-6)에 턴이 이미 끝난 뒤 받음이 오면 말풍선은 대화 끝에 서지만, **그 글에 답하는 턴을 저절로 열지 않는다** — 그 글은 대화 기록에 있으므로 사용자의 다음 글이 여는 턴이 그 글에도 답한다. 관측된 적 없는 방어 갈래 안의 일이라 따로 기계장치를 두지 않고 단순한 쪽으로 양보했다(사용자: 「복잡한것보다 약간 양보하면서 단순한 방향으로 하되 나중에 문제되면 기능 추가하면 되지」 — 나중 후보 = §7). **드문 대가:** 그 사이 우편이 흐르면 우편이 그 글보다 먼저 답을 받을 수 있다.
2. **받기 전까지는 입력창 위 목록에 둔다**(터미널식 — Claude Code · Codex TUI).
   - 항목마다 회색 한 줄, 넘치면 「…」. 잘린 항목은 마우스를 올리면 전문이 보인다(툴팁).
   - 오래된 것이 위.
   - 3개를 넘으면 「외 N개」로 접는다 — 접힌 동안은 **가장 오래된 3개**가 보이고, 「외 N개」를 누르면 펼쳐진다. 개수·모양은 나중에 조정할 수 있다(사용자: 「나중에 조정」).
   - **목록 위에 머리줄(안내 문구 줄)을 두지 않는다** — 회색 항목만 둔다(Claude Code 식). 사용자: 「한 줄 낭비」(§6).
   - 대화 안(보낸 자리든 대화 맨 아래든)에는 아무것도 그리지 않는다.
3. **목록은 하나다 — 모든 창과 LLM 이 같은 목록을 본다.** 같은 에이전트를 여러 창(메인·팝아웃)에서 봐도 목록이 같다 — ✕ 를 누른 항목은 어느 창에서 눌렀든 모든 창에서 곧바로 빠진다(§3-6). 창을 닫았다 다시 열어도, 대시보드 앱을 재시작해도(데몬·에이전트가 살아 있는 한) 목록이 그대로다. LLM 도 명령 표면으로 같은 목록을 읽는다(`CLAUDE.md 「LLM-우선 제어」` — 화면은 그리기만 하고 목록을 소유하지 않는다). 목록을 어디에 두는지는 TRD 몫이다.
4. **항목은 「받음」이 올 때만, 하나씩 빠진다.**
   - **받음 = 에이전트 자신이 「그 항목을 대화에 넣었다」고 항목별로 알려 오는 것**(항목별 되울림). 우리가 글을 에이전트에게 써 넣은 것, 에이전트가 요청을 접수했다고 답한 것은 **받음이 아니다** — 그때까지 항목은 목록에 남는다.
   - 빠지는 순간 **그 순간의 대화 끝**에 평범한 사용자 말풍선으로 나타난다(보낸 자리가 아니다).
   - 「도구가 끝났다」를 이유로 목록을 한꺼번에 비우지 않는다.
   - 받음이 끝내 오지 않으면 항목은 **에이전트가 끝날 때까지** 목록에 남고, 그때 §3-7 대로 버린다. 그 동안 우편도 기다린다(§3-9).
   - **codex 가 그 항목을 받아들였는지 모르게 된 경우도 같다** — 드문 실패로, 넘기기 요청에 codex 가 기존 30초 한도 안에 답하지 않았거나, 답을 읽을 수 없었거나, 받았다고 답했는데 턴이 끝날 때까지 되울림이 없는 경우(소스상 없어야 하는 갈래)다. 이것은 거절이 아니다(§3-7). 항목은 이유가 있을 때만 빠진다 — 받음(codex 가 그 글을 가졌다는 늦은 신호 → 말풍선 · 턴이 이미 끝났으면 답은 사용자의 다음 턴 — §3-1 예외) · ✕(사용자가 뺀다 — §3-6) · 에이전트 종료. 그 동안 ✕ 는 늘 있고(누르면 곧바로 끝난 것으로 친다 — §3-6), 우편은 상한 없이 그 뒤를 기다린다(§3-9 — 목록에 보이므로 막힌 이유가 화면에 있다). **그 뒤에 친 글은 평소대로 친 순서대로 넘어간다** — 그 항목은 이미 codex 에 넘긴 글이므로, 뒤 글을 그 뒤에 넘기는 것이 곧 친 순서다(C → D → E). 그 항목은 회색으로 남는다. 늦은 받음이 오면 그 말풍선이 그 사이 넘어간 글들의 말풍선 뒤에 설 수 있다 — 관측된 적 없는 방어 갈래 안의 화면 위치 문제로 받아들였다(AC2 예외). 사용자: 「음? 뭔소리야 순서대로 들어가는거잖아. 앞지른다는게 뭔소리? 또 발생되지도 않는걸 가정함?」(§6). 사용자: 「갑자기 목록이 사라져서 이상할것같은데 응답이 없으면 유저가 뭘 할 수있다고 스택에서 빼? 목록에서 뺀다는건 이유가 있어야되는거아냐」(§6).
5. **한가한 에이전트에 보내면 곧바로 대화에 들어간다** — 목록을 거쳐 깜빡이지 않는다. codex 도 마찬가지다(ADR-0198 의 즉시 표시).
   - **한가 = 도는 턴이 없고 목록도 비어 있음.** 목록에 항목이 남아 있으면 — 예: 앞 턴에서 넘어온 A·B 가 다음 턴을 기다리는 틈 — 새로 보낸 C 는 곧바로 대화에 들어가지 않고 **목록 맨 뒤**에 선다. 「친 순서대로」(§3-1)를 지키려면 C 가 A·B 를 앞지르면 안 되기 때문이다. codex 가 이어받는 중(§3-11)도 한가가 아니다. **단 claude 가 이어받은 대화를 불러오는 중은 한가로 친다** — 그 상태를 한가와 가려낼 신호가 없다(§3-11).
   - **그렇게 그려진 말풍선을 백엔드가 거절하면 말풍선을 알림 없이 지운다** — 글은 버린다(§3-7). 목록 항목이 받음을 받아 말풍선이 된 **뒤에** 거절이 와도 같다(claude — 미측정, §8 R10). 사용자: 「거절하면 우리쪽 채팅도 지워져야」. 오늘 그런 말풍선이 남는지는 미확인이다(§8 R9).
   - **거절이 아니라 에이전트가 끝나거나 턴이 끊겨 그 글을 처리하지 못했으면 말풍선은 그대로 남는다** — 따로 하는 일은 없다. 사용자: 「그냥 별도로 뭐 해야되는게 있음? resume 하면 어차피 갱신될텐데」(§8 R11).
6. **✕ 취소 — 목록의 모든 항목에 늘 있다.**
   - **두 백엔드, 어느 구간에서든 목록의 모든 항목에 ✕ 가 있다 — 누르면 그 항목이 목록에서 빠진다.** ✕ 는 「목록에서 치운다」이지 「에이전트에게서 거둬 온다」는 약속이 아니다. 사용자: 「x를 건드릴 이유가 있어? 그냥 x누르면 목록에서 기계적으로 빼는거잖아. 구지 비활성 필요 있냐고」 — 이미 넘긴 글이 뒤늦게 말풍선으로 나타나는 부작용도 받아들였다(「상관없어」 — §6).
   - **claude 항목:** 이미 넘긴 글이므로 ✕ 는 에이전트에게 그 글을 빼 달라는 요청을 함께 보낸다.
   - **codex 항목:** 우리가 붙들고 있는 동안(도구가 도는 동안 · 이어받기 중(§3-11) · 오류로 끝난 턴 뒤 기다리는 동안(§3-10)) 누른 ✕ 는 그 글이 에이전트에게 가지 않게 한다. 이미 넘긴 항목(붙들면 늦어지는 구간에 보내 곧바로 넘긴 항목 포함 — §3-1)도 ✕ 로 목록에서 빠지지만, 넘긴 글 하나만 거두는 수단이 벤더에 없으므로(가능성 높음 — 소스) 에이전트가 받으면 대화 끝 말풍선으로 나타난다(아래 (나)).
   - **codex 가 받아들였는지 모르는 항목(§3-4)의 ✕ 는 곧바로 끝난 것(버림)으로 친다** — 모든 창과 LLM 이 읽는 목록에서 곧바로 빠지고 「취소 중」에 머물지 않는다(곧바로 닫힌다). 다른 것이 막지 않으면 우편이 흐른다. 늦게 받음이 오면 대화 끝 말풍선이 된다 — 버림으로 적힌 결말이 말풍선으로 뒤집히는 것을 받아들였다. 턴이 이미 끝난 뒤의 받음이면 저절로 답하는 턴은 없고 사용자의 다음 턴이 답한다(§3-1 예외 · 양보). 사용자: 「끝난걸로쳐. 유저가 x눌렀을때 우연찮게 들어가는건 그냥 그렇다 치겠지」(§6).
   - 취소는 **등록된 명령**이다 — 두 백엔드가 같은 명령을 쓰고, LLM 도 같은 명령으로 취소한다. ✕ 는 그 명령을 부르는 사용자 동작이지, 슬롯 안 에이전트의 행동이 아니다.
   - ✕ 는 Tab 으로 닿고, 툴팁은 「목록에서 빼기」다 — 모든 항목 · 두 백엔드 같은 문구, 경고를 덧붙이지 않는다. 사용자: 「계속 몇번을 얘기하는데 x눌러도 없어졌는데 안으로 들어가서 표시하는건 어쩔수 없잖아.」(§6).
   - Esc 키 바인딩은 지금 두지 않는다(§7).
   - **✕ 를 누르면 항목이 모든 창에서 곧바로 사라지고 다시 나타나지 않는다** — 누른 창만이 아니다. 사용자: 「x 누르면 바로 빠지는 거잖아. 다른 창도 바로 빠져야 되는 거 아니?」. 에이전트가 먼저 가져간 늦은 경우에는 그 글이 모든 창에서 대화 끝 말풍선으로 나타날 뿐이고, 따로 알리지 않는다(사용자: 그거면 된다).
   - **✕ 는 요청이다 — 결말은 정확히 셋 중 하나다:** (가) **사라진다** — 취소가 확정됐다, 글은 버린다(§3-7) · (나) **대화 끝 말풍선이 된다** — 에이전트가 먼저 가져갔다 · (다) **버려진다** — 결말 전에 에이전트가 끝났거나, 에이전트가 살아 있어도 백엔드가 그 항목을 거절했다(§3-7). claude 의 (가)·(나)는 에이전트의 알림으로만 정한다(§8 R2). codex 의 붙든 항목은 우리가 쥐고 있으니 대개 곧바로 (가)이고, 넘기는 찰나와 겹치면 (나)다. 이미 넘긴 codex 항목은 받음이 오면 (나), 받음 없이 에이전트가 끝나면 (다)다.
   - **「취소 중」은 하나뿐인 목록의 상태이되 어느 창에도 그리지 않는다**(수락 모름 codex 항목은 거치지 않는다 — 위) — LLM 은 명령 표면으로 읽는 목록에서 결말이 날 때까지 그 항목을 「취소 중」으로 본다. 결말은 모두에게 같게 반영된다 — (나)면 모든 창에 말풍선이 나타나고, (가)·(다)면 그대로 없다. 앱을 재시작해도 「취소 중」 항목은 어느 창에도 나타나지 않고, 그 결말은 그대로 반영된다.
7. **거둔 글·못 보낸 글은 버린다 — 알리지 않는다.**
   - ✕ 로 취소한 글은 버린다 — 입력창으로 되돌리지 않는다. 사용자: 「일단 그냥 다 버리고 나중에 생각하자」.
   - 끊기·에이전트 종료·백엔드 거절로 끝내 전달될 수 없게 된 항목도 버린다(사용자 확인 2026-09-25 밤).
   - **알림은 없다** — 못 보낸 항목은 목록에서 그냥 빠진다(거절된 글이 이미 말풍선이 됐으면 그 말풍선이 빠진다 — §3-5. 거절이 아니라 끝남·끊기로 처리되지 못한 한가 말풍선은 남는다 — §3-5). 필요하면 나중에 더한다(사용자 — §7).
   - **끊기 = 도는 턴이 (어떤 조작으로든) 중단되는 것.** 창이 데몬과의 연결을 잃는 것은 끊기가 **아니다** — 목록은 그대로 남고, 창은 다시 붙을 때 목록을 다시 맞춘다(§3-3 에서 따라 나온다). 오류로 끝난 턴도 끊기가 아니다 — §3-10 이 따로 정한다.
   - 자동 재전송은 없다 — 이미 넘긴 글을 다시 보내면 에이전트가 같은 글을 두 번 받을 수 있다(조사 §2-4 · TRD §3-1).
8. **메시지는 따로 남는다.** 여러 개를 보내도 이어 붙이지 않는다 — 각자 한 줄, 각자 말풍선이다. 턴 끝에 남은 여럿이 한 턴에 함께 들어가도(§3-1) 마찬가지다.
9. **에이전트 간 우편보다 사용자 입력이 먼저다**(JSON 모드).
   - 우편은 목록에 오르지 않는다. 우편의 「한가」도 사용자 입력과 같다 — 도는 턴이 없고 사용자 목록이 비어 있음(§3-5).
   - 그래서 사용자 항목이 목록에 있으면 우편은 그 항목들이 들어가고 그 턴이 끝날 때까지 기다린다. 우편은 사용자 입력 뒤로 늦어질 수 있다 — 오류로 끝난 턴 뒤 사용자 항목이 기다리는 동안(§3-10)도 포함이다. 사용자가 이 지연을 받아들였다.
   - ★**이상하게 끝난 턴 뒤에는 우편을 저절로 넣지 않는다 — 목록이 비어 있어도**★(두 백엔드 — 우편을 넣는 것은 우리 쪽이라 벤더 동작과 무관하다 · 그래서 버전 하한 밑 옛 codex 에도 건다 — 그 버전의 목록·✕·넘기기만 오늘 동작 그대로다, §2 · R6). 그 동안 우편은 에이전트에게 넘기지 않고 우리 쪽에서 기다린다. 이상하게 끝난 턴 = 진짜 오류(요청 한도 · 과부하 · 맥락 초과)로 끝난 턴, 또는 턴을 여는 요청 단계에서 실패한 턴이다 — 사용자 글의 턴 · 후속 턴(§3-1) · 우편 턴 어느 것이든. 사용자 취소·끊기와 에이전트 종료는 아니다(도는 턴에 글을 끼워 넣다 실패한 것도 턴이 이어지므로 아니다). **다시 흐르는 계기 = 사용자의 다음 입력 턴이 성공으로 끝남** — 그 턴도 이상하게 끝나면 계속 기다린다. 끊기·취소로 끝난 턴은 멈춤을 걸지도 풀지도 않는다(두 백엔드). 에이전트가 끝나면 함께 끝난다. 사용자: 「진짜 에러면 강제로 쑤셔넣으면 안되잖아」 · 「어쨋든 본질은 가능하면 자동으로 되고, 거기에 유저게 우선한다는 얘기지」. **대가:** 그 동안 우편이 멈춘 이유가 화면에 없다 — 사용자가 글을 칠 때까지 보이지 않게 기다린다(알림은 미룬다 — §7). LLM 은 명령 표면으로 멈춰 있는지를 읽는다(AC18).
   - **지연에 상한이 없다.** 사용자 항목이 받음을 끝내 못 받아 목록에 걸려 있으면(§3-4) 우편도 그 동안 — 얼마나 길든, 에이전트가 끝날 때까지 — 기다린다. 사용자: 「일단 사용자 글이 막히면 우편도 막혀야 되는거 아냐? 상한이 필요한거? 애초에 글이 막히는것 자체가 이상한건데?」(§6).
   - 터미널(PTY) 모드의 우편은 오늘 그대로 들어간다.
10. **오류로 끝난 턴(요청 한도 · 과부하 · 맥락 초과 · 요청 단계 실패)에 걸린 글.** 끊기가 아니다(§3-7). 그 뒤 우편은 두 백엔드 모두 사용자의 다음 입력 턴이 성공으로 끝날 때까지 기다린다(§3-9 — 버전 하한 밑 옛 codex 도 같다).
    - **codex — 목록에 남은 항목은 저절로 보내지 않는다.** 목록에서 기다리며 ✕ 가 있고(§3-6), 사용자가 다음 글을 보내면 그 글과 함께 **한 턴에**, 남은 항목이 먼저 들어간다. 한도가 다시 풀려도 저절로 보내지 않는다 — 사용자는 세션을 건드리지 않길 원한다. **오류 뒤에는 아무것도 저절로 넣지 않는다** — 목록 항목도, 답 못 받은 글의 후속 턴(§3-1)도, 우편(§3-9)도.
    - **claude — 벤더가 하는 대로 따른다.** 억지로 맞추지 않는다(사용자: 「억지로 구현하지 마」). 목록은 항목마다 오는 알림으로 벤더의 실제 처리와 맞게 유지된다 — 벤더가 그 항목을 버리면 목록에서 빠지고(§3-7), 대화에 넣으면 말풍선이 된다. **단 우편은 우리가 넣는 것이라 벤더를 따르지 않고 기다린다**(§3-9).
    - **그 턴에서 이미 말풍선이 됐는데 답을 못 받은 글**(한가할 때 보낸 글 포함)은 그대로 둔다 — 후속 턴을 열지 않는다(두 백엔드).
11. **이어받기 중(연결·이력 복원 · 이어받은 대화 불러오기) 보낸 글은 목록에 선다** — 한가로 치지 않는다(§3-5). **단 claude 는 예외다**(아래).
    - **codex:** 우리가 붙들고(✕ 가 있다 — §3-6) 준비되는 대로 곧바로 넘긴다. 받음이 오면 말풍선은 복원된 이력 **아래**에 선다. 대화는 이어받았는데 화면의 이력 복원만 실패·중단됐으면 그대로 넘긴다.
    - **claude — 예외, 오늘 동작 그대로:** 이어받은 대화를 불러오는 중인지 한가인지 가려낼 신호가 없어, 그 동안 보낸 글은 한가할 때 보낸 글로 친다(§3-5) — 곧바로 말풍선으로 그려지고 곧바로 넘겨지며, 벤더가 불러오기를 마친 뒤 처리한다(미측정 — §8 R5). 그 짧은 틈에는 목록 항목도 ✕ 도 없다. 복원 이력은 에이전트가 목록에 오르기 전에 먼저 채워지므로 그 뒤에 보낸 글의 말풍선은 이력 아래에 선다(코드 판독 — TRD §5-4 · 화면 실측 전). 사용자: 「그냥 내가 채팅 치다가 오면 병합 잘 되는거잖아. 이번에 순서 삐뚤어져도 맞추는거 추가하잖아.」(§6).
    - 이어받기 자체가 실패하면 에이전트가 종점으로 끝나므로(ADR-0082 — 새 대화로 자동 전환하지 않는다) 대기분은 버려진다(§3-7).

## 4. 시나리오 / 엣지

- **한가할 때 보냄:** 곧바로 대화 끝 말풍선. 목록은 나타나지 않는다.
- **한가할 때 보낸 글을 백엔드가 거절:** 그려졌던 말풍선이 알림 없이 사라지고, 글은 버려진다(§3-5). 목록을 거쳐 말풍선이 된 뒤에 거절이 와도 같다(claude — 미측정, §8 R10).
- **한가할 때 보낸 글을 에이전트가 처리하기 전에 끝나거나 턴이 끊김(거절 아님):** 말풍선은 그대로 남는다 — 따로 하는 일은 없다(§3-5).
- **긴 도구(빌드) 도중 교정 지시:** 입력창 위에 회색 한 줄 → 에이전트가 받으면 목록에서 빠지고 그 순간의 대화 끝 말풍선 → 에이전트의 다음 행동이 그 지시를 반영한다. 보통은 그 빌드가 끝나는 지점에서 받고, 빌드가 끝나는 찰나에 보냈다면 다음 경계나 다음 턴에서 받는다 — 어느 쪽이든 에이전트가 답한다(§3-1). codex 는 빌드가 도는 동안 우리가 붙들고 있어 ✕ 로 거둘 수 있고, 빌드가 끝나는 지점에서 곧바로 넘긴다.
- **도구 없이 긴 답을 쓰는 도중 보냄:** 그 답이 끝난 뒤 에이전트가 그 글을 받아 답한다 → 말풍선은 앞 답 **아래**에 선다. codex 가 이 구간에서 붙들지 곧바로 넘길지는 측정 뒤 정한다 — 어느 쪽이든 ✕ 는 있고, 곧바로 넘겼다면 ✕ 를 눌러도 에이전트가 받은 글은 말풍선으로 나타난다(§3-1 · §3-6 · §8 R8).
- **턴이 끝날 때 목록에 남은 항목:** 다음 턴으로, 친 순서대로 들어간다. 사용자가 다시 보낼 필요가 없다. 여럿이면 한 다음 턴에 함께, 각자 따로 말풍선으로 들어간다(claude 는 벤더가 묶음을 정한다 — §3-1).
- **남은 A·B 가 다음 턴을 기다리는 틈에 C 를 보냄:** 턴이 안 돌아도 한가가 아니다 — C 는 목록 맨 뒤에 서고, 말풍선은 A·B·C 순서로 선다.
- **codex — 글이 턴에 들어가(말풍선이 뜬) 직후 그 턴이 답 없이 끝남:** 그 글에 답하는 턴이 이어진다. 같은 말풍선이 두 번 생기지 않고, 같은 글이 에이전트에게 두 번 가지 않는다(방법 = TRD, M6). 그 후속 턴마저 오류로 끝나면 다시 열지 않는다 — 사용자의 다음 글이 여는 턴이 그 글에도 답하고, 그때까지 우편은 기다린다(§3-1 · §3-9).
- **턴이 오류로 끝남(요청 한도 · 과부하 · 맥락 초과) — 목록에 항목이 남아 있음:** codex 는 항목이 목록에서 기다린다(✕ 가능) → 사용자가 다음 글을 보내면 그 글과 함께 한 턴에, 남은 항목이 먼저 들어간다. 한도가 풀려도 저절로 가지 않는다. claude 는 목록이 벤더가 하는 대로 따라간다 — 벤더가 버리면 빠지고, 대화에 넣으면 말풍선이 된다. 그 턴에서 이미 말풍선이 됐는데 답을 못 받은 글은 그대로 남는다(§3-10). 두 백엔드 모두 목록이 비어 있어도 우편은 들지 않고, 사용자의 다음 글의 턴이 성공으로 끝나면 흐른다 — 그 턴도 오류면 계속 기다린다(§3-9).
- **여러 개 연달아:** 오래된 것이 위, 4개째부터 「외 N개」로 접히고 가장 오래된 3개가 보인다. 「외 N개」를 누르면 펼쳐진다. 에이전트가 받는 대로 하나씩 빠져 각자 따로 말풍선이 된다.
- **잘린 한 줄:** 마우스를 올리면 전문이 보인다.
- **✕(두 백엔드 · 모든 항목 · 모든 구간):** 모든 창에서 항목이 곧바로 사라진다 → (가) 취소가 확정되면 다시 나타나지 않고 모델에 가지 않는다(다음 응답이 그 글을 모른다), 글은 버려진다 · (나) 에이전트가 먼저 가져갔으면 그 글이 모든 창에서 대화 끝 말풍선으로 나타난다 — 알림은 없다.
- **✕ 결말 전에 에이전트가 끝나거나 거절:** 항목은 버려진다(§3-7).
- **✕ 를 누른 창과 다른 창·LLM:** 모든 창에서 이미 없다. LLM 만 읽는 목록에서 결말까지 「취소 중」을 본다. 결말은 모두에게 같게 반영된다.
- **codex 턴 도중 보냄:** 에이전트가 받을 수 있을 때까지 우리가 붙든다(그 동안 누른 ✕ 는 글이 에이전트에게 가지 않게 한다) → 가장 이른 경계(보통 지금 도는 도구의 끝)에서 곧바로 넘긴다 → 받음이 오면 말풍선. 붙들면 늦어지는 구간에 보냈으면 곧바로 넘긴다. ✕ 는 넘긴 뒤에도 있다 — 누르면 목록에서 빠지고, 에이전트가 받으면 말풍선으로 나타난다.
- **codex 가 받아들였는지 모르게 됨(드문 실패 — 넘기기 요청에 30초 안에 답이 없음 · 답을 읽을 수 없음 · 받았다는 답 뒤 턴 끝까지 되울림 없음):** 항목은 목록에 그대로 남는다 — ✕ 는 있고, 우편은 상한 없이 기다린다. 그 뒤에 친 글은 평소대로 친 순서대로 넘어간다 — 늦게 받음이 오면 그 말풍선은 그 사이 넘어간 글들의 말풍선 뒤에 설 수 있다. 늦게 받음이 오면 말풍선이 되고, 아니면 사용자가 ✕ 로 빼거나(곧바로 끝난 것으로 친다 — 늦은 받음이 오면 말풍선) 에이전트가 끝날 때 빠진다(§3-4 · §3-6). 턴이 끝난 뒤 온 받음이면 저절로 답하는 턴은 없다 — 사용자의 다음 글이 여는 턴이 그 글에도 답한다(그 사이 우편이 먼저 답받을 수 있다 — §3-1 예외).
- **codex 이어받기(연결·이력 복원 중) 입력:** 목록에 서고 우리가 붙든다(✕ 가능) → 준비되면 넘긴다 → 받음이 오면 말풍선이 복원된 이력 **아래**에 선다. 대화는 이어받았는데 화면 이력 복원만 실패·중단되면 그대로 넘긴다. 이어받기 자체가 실패하면 에이전트가 종점으로 끝나므로(ADR-0082 — 새 대화로 자동 전환하지 않는다) 대기분은 버려진다(§3-7).
- **claude 가 이어받은 대화를 불러오는 중 입력:** 오늘 그대로 — 한가할 때처럼 곧바로 말풍선으로 그려지고 곧바로 넘겨진다(목록·✕ 없음). 벤더는 불러오기를 마친 뒤 처리한다(미측정 — §8 R5 · §3-11).
- **받음이 끝내 안 옴:** 항목은 에이전트가 끝날 때까지 목록에 남고, 그때 버려진다. 그 동안 우편도 상한 없이 기다린다(§3-9).
- **끊기 / 에이전트 종료 / 거절:** 남은 항목은 알림 없이 목록에서 사라지고 버려진다. 입력창으로 돌아오지 않고 재전송되지도 않는다.
- **창이 데몬과의 연결을 잃었다 다시 붙음:** 끊기가 아니다 — 연결이 끊겼다는 이유로 사라지는 항목은 없다. 다시 붙은 창은 목록과 말풍선을 실제 상태대로 보인다: 그 사이 에이전트가 받은 항목은 말풍선으로, 그 사이 버려진 항목은 없는 채로.
- **창 두 개(메인 + 팝아웃):** 두 창의 목록이 같다. 한쪽에서 ✕ 를 누르면 두 창에서 함께 곧바로 사라지고, 에이전트가 먼저 가져갔으면 두 창에 함께 말풍선으로 나타난다.
- **창을 닫았다 다시 열기:** 목록이 그대로다.
- **대시보드 앱 재시작 — 데몬과 에이전트는 살아 있음:** 다시 뜬 창에 목록이 그대로 나타난다. 「취소 중」 항목은 어느 창에도 나타나지 않고, 그 결말은 그대로 반영된다.
- **데몬 재기동:** 에이전트와 함께 목록도 사라진다(§7 — 오늘 입력 큐와 같은 등급).
- **LLM 이 목록 조회 · 항목 취소:** 화면의 목록이 같게 바뀐다 — 그 항목은 모든 창에서 곧바로 빠지고, LLM 이 읽는 목록에서만 결말까지 「취소 중」으로 남는다.
- **턴이 끝나는 찰나에 보냄(claude):** 목록에 한순간 비쳤다 곧바로 말풍선이 될 수 있다 — 표시만의 흔들림이다.
- **턴 도중 슬래시 명령(「/compact」 등)을 보냄:** 특별 취급 없이 다른 글처럼 넘긴다. 에이전트가 그것을 어떻게 다루는지는 미측정이다(§8 R7).
- **터미널 슬롯에서 턴 중 타이핑:** 변화 없음 — 에이전트 TUI 자신의 대기 표시만 보인다.
- **에이전트 간 우편 도착(JSON):** 목록에 오르지 않는다. 턴이 돌거나 사용자 목록에 항목이 있으면 기다렸다가 한가해지면 들어간다 — 사용자 입력 뒤로 늦어질 수 있다. 앞 턴이 이상하게 끝났으면 한가해도 사용자의 다음 글의 턴이 성공으로 끝날 때까지 기다린다(§3-9).
- **에이전트 간 우편 도착(터미널):** 오늘과 같다.
- **옛 벤더 버전(이 기능이 기대는 벤더 기능이 없음):** 오늘 동작 그대로다 — 이 기능의 목록·✕ 가 없다(§2 · §8 R6). 단 이상하게 끝난 턴 뒤 우편 멈춤은 건다(§3-9).

## 5. 수용 기준 (보이는 동작)

번호 = 수용 기준 id(AC#)다. TRD 가 이 번호를 인용하므로 바꾸지 않는다 — 새 기준은 뒤에 잇는다.

1. 두 백엔드 모두 **한가할 때**(도는 턴 없음 + 목록 빔 · 이어받기 중이 아님 — 단 claude 가 이어받은 대화를 불러오는 중은 한가로 친다, §3-5 · §3-11) 보낸 글은 목록을 거치지 않고 곧바로 대화 끝 말풍선으로 뜬다 — 목록 깜빡임 없음.
2. 목록에 항목이 남아 있는 동안 보낸 글은 턴이 안 돌더라도 목록 맨 뒤에 서고, 앞 항목을 앞지르지 않는다 — 말풍선 순서가 친 순서와 같다. **예외 — codex 가 받아들였는지 모르는 항목(§3-4):** 그 뒤에 친 글은 평소대로 친 순서대로 넘어가므로, 그 항목에 늦게 받음이 오면 그 말풍선이 뒤 글들의 말풍선 뒤에 설 수 있다.
3. **claude JSON:** 긴 도구 도중 보낸 글이 즉시 입력창 위 목록(회색 한 줄)에 뜨고, 보통은 그 도구가 끝나는 시점에 목록에서 빠져 **그 순간의 대화 끝** 말풍선이 되며, 에이전트의 다음 응답이 그 글에 반응한다(도구가 끝나는 찰나에 보낸 글은 다음 경계나 다음 턴 — 5). 앞 답의 중간(보낸 자리)에는 말풍선이 없다.
4. **codex JSON:** 긴 도구 도중 보낸 글이 턴 끝까지 기다리지 않고 **그 도구가 끝나는 경계에서** 모델에 닿는다 — 우리가 붙들고 있었다고 그 경계를 놓쳐 다음 경계로 밀리지 않는다(도구가 끝나는 찰나에 보낸 글은 다음 경계나 다음 턴 — 5). 목록 → 말풍선 전환은 3과 같다.
5. **보낸 글은 §3-7 로 버려지지 않는 한 전부 에이전트가 답하는 턴에 들어간다.** 도는 턴에 못 들어간 항목은 턴이 끝난 뒤 다음 턴으로 친 순서대로 들어가고, 사용자가 다시 보낼 필요가 없다. 대화에 답 없는 말풍선이 남지 않는다. **예외 — 오류로 끝난 턴(§3-10):** 그 턴에서 이미 말풍선이 됐는데 답을 못 받은 글(한가할 때 보낸 글 포함)은 그대로 남는다(후속 턴 없음) · 목록에 남은 codex 항목은 사용자가 다음 글을 보낼 때까지 기다린다(24) · 목록에 남은 claude 항목은 벤더 처리를 따른다(25). **예외 — 6 의 후속 턴이 이상하게 끝나면(§3-1 · §3-9):** 그 턴을 다시 열지 않고, 그 글은 사용자의 다음 글이 여는 턴이 답한다. **예외 — 턴이 끝난 뒤 늦게 받음이 온 codex 항목(§3-1 · ✕ 로 닫은 것 포함 — 13):** 말풍선은 서지만 저절로 답하는 턴은 없고, 사용자의 다음 글이 여는 턴이 답한다(그 사이 우편이 먼저 답받을 수 있다).
6. **이미 턴에 들어갔는데 그 턴이 답하지 않고 끝난 항목(codex)도 답하는 턴을 받는다** — 같은 글의 말풍선이 두 번 생기지 않고, 같은 글이 에이전트에게 두 번 넘어가지 않는다. **예외 — 그 후속 턴이 이상하게 끝나면** 다시 열지 않는다: 그 글은 사용자의 다음 글이 여는 턴이 답하고, 그때까지 우편은 기다린다(29). 턴이 끝난 뒤 늦게 받음이 온 항목도 이 후속 턴을 받지 않는다(5 의 예외).
7. 여러 개를 보내면 각자 한 줄(넘치면 「…」 · 마우스를 올리면 전문), 오래된 것이 위, 4개 이상이면 「외 N개」로 접히고 접힌 동안 가장 오래된 3개가 보이며, 「외 N개」를 누르면 펼쳐진다. 전달되면 각자 따로 말풍선이 되고 이어 붙지 않는다.
8. 목록 위에 머리줄(안내 문구 줄)이 없다 — 턴이 어떤 상태든 회색 항목만 보인다. codex 가 이어받는 중(§3-11) 친 글은 목록에 서고, 그 말풍선은 복원된 이력 아래에 선다.
9. 항목은 에이전트가 그 항목을 받았다고 알려 올 때만 하나씩 빠진다 — 글을 써 넣은 것만으로 빠지지 않고, 도구가 끝났다고 목록이 한꺼번에 비지 않는다. 받음이 끝내 안 오면 에이전트가 끝날 때까지 목록에 남는다.
10. ✕ 는 목록의 모든 항목에 늘 있다 — 두 백엔드, 어느 구간에서든(넘기기 전후 · 곧바로 넘기는 구간 · 이어받기 중 · 오류로 끝난 턴 뒤 기다리는 동안). 비활성이나 숨김 상태가 없다. 누르면 그 항목이 목록에서 빠지고, 결말은 11–13 중 하나다. ✕ 는 Tab 으로 닿고 툴팁은 「목록에서 빼기」다(모든 항목 · 두 백엔드 같은 문구).
11. **✕ — (가) 취소가 이긴 경우(두 백엔드):** 항목이 모든 창에서 곧바로 사라지고 다시 나타나지 않는다 — 어느 창에도 「취소 중」 항목이 보이지 않는다. LLM 이 읽는 목록에는 결말까지 「취소 중」으로 남았다가 결말이 오면 사라진다. 모델의 다음 응답이 그 글을 모르고, 글은 입력창에 돌아오지 않는다. **예외 — codex 가 받아들였는지 모르는 항목(§3-4):** LLM 이 읽는 목록에서도 곧바로 빠지고 「취소 중」에 머물지 않는다(곧바로 닫힌다 — 결말은 13 의 버림으로 적힌다).
12. **✕ — (나) 에이전트가 먼저 가져간 경우:** 모든 창에서 이미 사라졌던 그 글이 모든 창에서 대화 끝 말풍선으로 나타난다(알림 없음). 에이전트가 그 글에 답한다.
13. **✕ — (다) 결말 전에 에이전트가 끝났거나, 에이전트가 살아 있어도 백엔드가 그 항목을 거절한 경우:** 항목은 이미 모든 창에서 사라진 채 다시 나타나지 않고, LLM 이 읽는 목록에서도 빠지며, 버려진다(입력창에 돌아오지 않는다). **한 번의 ✕ 는 11·12·13 셋 중 정확히 하나로 끝난다** — 사라졌는데 모델에 가거나, 말풍선이 됐는데 모델이 모르는 일은 없다. **예외 — codex 가 받아들였는지 모르는 항목(§3-4):** ✕ 순간 버림(13)으로 끝나지만, 뒤이어 늦게 받음이 오면 대화 끝 말풍선이 된다(12) — 버림이 말풍선으로 뒤집히는 이 한 경우를 받아들였다(§3-6). 턴이 이미 끝난 뒤의 받음이면 저절로 답하는 턴은 없고 사용자의 다음 글이 여는 턴이 답한다(5 의 예외 · 양보).
14. 끊기·에이전트 종료·거절로 못 보낸 항목은 알림 없이 목록에서 사라지고, 입력창에 돌아오지 않으며, 자동으로 다시 보내지지 않는다.
15. 메인 창과 팝아웃 창이 같은 에이전트를 보면 목록이 같다 — 한쪽에서 ✕ 를 누르면 두 창에서 함께 곧바로 사라지고, 결말도 두 창에 같게 반영된다(11–13). 창을 닫았다 다시 열어도 목록이 그대로다.
16. 창이 데몬과의 연결을 잃었다 다시 붙어도 **연결이 끊겼다는 이유로** 사라지는 항목은 없다. 다시 붙은 창은 목록과 말풍선을 실제 상태대로 보인다 — 그 사이 받힌 항목은 말풍선으로, 그 사이 버려진 항목은 없는 채로 — 그리고 다른 창과 같다.
17. 데몬과 에이전트가 살아 있는 채로 대시보드 앱을 재시작하면 목록이 그대로 다시 나타난다. 취소 중인 항목은 어느 창에도 나타나지 않고, 그 결말(12 의 말풍선 포함)은 그대로 반영된다.
18. LLM 이 명령 표면으로 같은 목록을 읽고 목록의 어느 항목이든(두 백엔드) 취소할 수 있다 — 화면 ✕ 와 같은 명령이다. 같은 목록 조회로 에이전트가 이상하게 끝난 턴 뒤 멈춰 있는지(예/아니오 하나 · 두 백엔드 — 29)도 읽는다. Esc 키 바인딩은 없다.
19. 목록의 회색 글이 세 테마(dark · light · e-ink) 모두에서 읽힌다.
20. 목록이 입력창 위의 에이전트 이름표를 가리지 않는다.
21. **터미널(PTY) 모드는 그대로다:** 턴 중 타이핑에 대시보드 목록이 뜨지 않고 에이전트 TUI 자신의 대기 표시만 보이며, 입력 바이트가 오늘과 같다(기존 터미널 회귀가 초록).
22. 에이전트 간 우편은 목록에 오르지 않는다. **JSON 모드에서는 우편이 사용자 입력 뒤로 늦어질 수 있다** — 도는 턴이 없고 사용자 목록이 비었을 때에야 들어간다(오류로 끝난 턴 뒤 사용자 항목이 기다리는 동안 포함 · 받음을 못 받아 걸린 사용자 항목이 있으면 상한 없이 — §3-9). **예외 — 이상하게 끝난 턴 뒤에는 목록이 비어 있어도 들어가지 않는다(29).** 우편의 모양은 오늘과 같다. 터미널 모드의 우편은 오늘과 같은 시점·모양으로 전달된다.
23. 완료 판정은 GUI 실측(`/qa full`)으로 한다 — 테스트·타입체크 통과만으로는 완료가 아니다.
24. **codex — 오류로 끝난 턴 뒤 목록에 남은 항목**은 저절로 보내지지 않는다: 목록에서 기다리며 ✕ 가 있고, 사용자가 다음 글을 보내면 그 글과 함께 **한 턴에**, 남은 항목이 먼저 들어간다(각자 따로 말풍선). 시간이 지나 한도가 풀려도 저절로 가지 않는다. 남은 항목이 codex 가 받았는지 모르는 항목(§3-4)보다 뒤에 친 것이어도 평소대로 넘어간다(2 의 예외).
25. **claude — 오류로 끝난 턴에 걸린 목록 항목**은 벤더가 처리한 대로 보인다 — 벤더가 버리면 알림 없이 목록에서 빠지고, 대화에 넣으면 말풍선이 된다. 목록이 벤더의 실제 처리와 어긋난 채 남지 않는다. 우편은 벤더를 따르지 않고 29 대로 기다린다.
26. 한가할 때 보낸 글이 말풍선으로 그려진 뒤 백엔드에 거절되면 — 목록 항목이 말풍선이 된 뒤에 거절이 와도 — 그 말풍선이 알림 없이 사라지고 글은 입력창에 돌아오지 않는다(두 백엔드). 거절이 아니라 에이전트가 끝나거나 턴이 끊겨 처리되지 못한 한가 말풍선은 그대로 남는다.
27. **codex — 턴 끝에 남은 항목 여럿**은 **한** 다음 턴에 함께, 친 순서대로, 각자 따로 말풍선으로 들어간다 — 항목마다 턴을 따로 돌지 않는다. claude 는 벤더가 묶음을 정하며, 이와 다르면 보고한다(ADR-0192).
28. **이어받기 중 보낸 글:** codex 는 목록에 붙들려 ✕ 가 있다가 준비되면 넘겨지고, 대화는 이어받았는데 화면 이력 복원만 실패·중단돼도 그대로 넘겨진다. claude 는 예외다 — 이어받은 대화를 불러오는 중 보낸 글은 한가할 때처럼 목록을 거치지 않고 곧바로 말풍선이 되고(✕ 없음), 벤더가 불러오기를 마친 뒤 그 글에 답한다. 이어받기 자체가 실패하면 대기분은 버려진다.
29. **이상하게 끝난 턴 뒤 우편(두 백엔드 — 버전 하한 밑 옛 codex 포함, 그 버전의 목록·✕·넘기기만 오늘 동작 그대로 · §2 · R6):** 턴이 진짜 오류(요청 한도 · 과부하 · 맥락 초과)나 요청 단계 실패로 끝나면 — 사용자 글의 턴 · 후속 턴 · 우편 턴 어느 것이든 — 목록이 비어 있어도 우편이 저절로 들어가지 않고, codex 는 답 못 받은 글의 후속 턴도 다시 열지 않는다. 사용자의 다음 입력 턴이 성공으로 끝나면 우편이 흐르고, 그 턴도 이상하게 끝나면 계속 기다린다. 사용자 취소·끊기로 끝난 턴은 멈춤을 걸지도 풀지도 않는다(두 백엔드). 그 동안 우편은 에이전트에게 넘기지 않고 우리 쪽에서 기다린다.

## 6. 거부한 대안 (사용자 사유 — 새 ADR 「거부한 대안」으로 옮긴다)

괄호 안 기호는 조사 보고서·TRD 가 쓴 이름이다. 이 문서만 읽어도 뜻이 통하게 풀어 적는다.

- **보낸 자리에 정식 말풍선을 고정한다**(오늘 claude 동작 · ADR-0198 원안 · 조사의 B) — 턴 도중이면 앞 답의 나머지가 그 아래로 이어져 순서가 섞인다.
- **대화 맨 아래(흐르는 답 아래)에 회색 대기 행을 둔다**(조사 보고서의 추천안이었던 A) — 사용자: 「터미널이 가장 자연스럽다」.
- **목록 위에 머리줄(안내 문구 줄)을 둔다** — 도구가 도는 턴 도중 「도구 호출이 끝나면 전달」, codex 연결·이력 복원 중 「준비되면 전달」, 도구가 안 도는 턴 도중엔 둘째 문구(예: 「응답이 끝나면 전달」)를 두는 안. 한때 결정이었다. 사용자: 「한 줄 낭비」 — Claude Code 처럼 회색 항목만 둔다.
- **턴이 끝날 때까지 우리가 붙든다**(오늘 codex 동작) — 사용자: 「당연히 도구 호출 끝나면 바로 푸쉬」.
- **codex 도 받자마자 넘긴다**(두 백엔드 공통 즉시 전달 — 한때 결정이었다. 사용자: 「클로드든 코덱스든 우리가 받고 바로 전달하자. 일단 공용화하고 나중에 세분화」) — 사용자 원칙 「받을 수 있는 가장 이른 때 전달」로 바뀌었다. codex 는 도구 끝까지 붙들어도 같은 경계에 들어(Phase 0 실측) 전달이 늦지 않으므로, 그 동안 붙든다 — 붙든 동안 누른 ✕ 는 글이 에이전트에게 가지 않게 한다. 사용자: 이것은 나중 일이 아니라 이 기능의 일부다.
- **claude 를 우리가 붙들고 있다가 도구가 끝난 것을 보고 넘긴다**(TRD 의 S1) — 한 걸음 늦다. 에이전트는 도구가 끝나자마자 자기 대기함을 확인하므로, 그 뒤에 넘긴 글은 그 경계를 놓치고 다음 도구가 끝나야 읽힌다(사용자 확인 · Phase 0 실측 0/10). **codex 에서는 이 방식이 채택안이다**(§3-1) — 붙들었다 넘겨도 같은 경계에 들었다(10/10 · 판정의 시간 근거 = TRD · §8 R8).
- **에이전트 훅이 도구가 끝날 때마다 우리 대기분을 당겨가게 한다**(TRD 의 S4) — 사용자: 「훅마다 매번 뭔가 실행하면 안 된다」.
- **codex 를 붙들었다가 도구가 *시작될 때* 넘겨, 그 전까지만 ✕ 를 살린다**(TRD 의 S5 · TRD 본문의 옛 권고) — 원래 사유는 「공통 동작을 먼저, 세분화는 나중」이었다. 지금은 §3-1 의 원칙(붙들어도 늦지 않는 동안 붙든다)이 도구가 *끝날* 때까지 붙드는 쪽을 고른다 — 전달 시점은 같고 ✕ 가 더 오래 남는다.
- **대기분을 이어 붙여 한 번에 보낸다** — 백엔드마다 편법이 필요하고, 받자마자 넘기면 모아 둘 대기분이 애초에 없어 의미가 없어진다. (조사 보고서 §5 는 「항목별 id 가 하나로 뭉개져 합치기가 깨진다」를 덧붙인다.)
- **한가할 때 보낸 글이 거절돼도 말풍선을 남긴다**(「전달 안 됨」 표시를 달거나 그대로 두기) — 사용자: 「거절하면 우리쪽 채팅도 지워져야」.
- **claude 이어받은 화신의 첫 글은 무조건 목록을 거친다**(불러오는 중인지 가려낼 신호가 없으니 첫 글만은 안전하게 목록에 세우는 안) — 이를 가릴 새 표식이 따로 필요하고, 불러오기가 이미 끝났어도 목록이 한순간(약 1 ms) 비쳤다 빠져 이어받을 때마다 AC1(목록 깜빡임 없음)을 깬다. 불러오기 자체도 짧다. 사용자: 「그냥 내가 채팅 치다가 오면 병합 잘 되는거잖아. 이번에 순서 삐뚤어져도 맞추는거 추가하잖아.」 · 「애초에 코덱스쪽에서 리스트를 먼저 보내주겠지 시작하자마자」. 오늘 동작 그대로 한가할 때 보낸 글로 친다(§3-11).
- **사용자 글이 30분 넘게 걸려 있으면 우편은 그 뒤를 기다리지 않는다**(턴 관측의 30분 상한과 같은 안전망) — 사용자: 「일단 사용자 글이 막히면 우편도 막혀야 되는거 아냐? 상한이 필요한거? 애초에 글이 막히는것 자체가 이상한건데?」. 우편은 상한 없이 기다린다(§3-9).
- **✕ 를 누른 창에서도 결말까지 항목을 남겨 둔다**(흐리게 + ✕ 비활성) — 사용자는 누른 창에서 곧바로 사라지는 쪽을 골랐다: 에이전트가 먼저 가져간 늦은 경우엔 말풍선으로 나타나면 된다.
- **구간별 ✕ — 넘긴 뒤·곧바로 넘기는 구간에선 ✕ 를 숨긴다**(codex 는 우리가 붙든 동안만 ✕ 를 주는 안 — 한때 결정이었다) — 사용자: 「x를 건드릴 이유가 있어? 그냥 x누르면 목록에서 기계적으로 빼는거잖아. 구지 비활성 필요 있냐고」. 이미 넘긴 글이 뒤늦게 말풍선으로 나타나는 부작용에는 「상관없어」. ✕ 는 모든 항목에 늘 있고 목록에서 빼는 것이다(§3-6).
- **수락 여부를 모르면 목록에서 빼고, 늦게 받음이 오면 말풍선으로**(codex 가 넘기기 요청에 답하지 않거나 · 답을 읽을 수 없거나 · 받았다고 답했는데 턴 끝까지 되울림이 없을 때 — 5판까지는 턴 끝 확인 실패도 여기 들었으나 그 확인은 TRD 에서 걷혔다) — 사용자: 「갑자기 목록이 사라져서 이상할것같은데 응답이 없으면 유저가 뭘 할 수있다고 스택에서 빼? 목록에서 뺀다는건 이유가 있어야되는거아냐」. 항목은 받음 · ✕ · 에이전트 종료 중 하나가 올 때까지 목록에 남는다(§3-4).
- **누른 창만 즉시 감추고 다른 창은 「취소 중」으로 흐리게 보인다** — 사용자: 「x 누르면 바로 빠지는 거잖아. 다른 창도 바로 빠져야 되는 거 아니?」. 모든 창에서 곧바로 빠지고, 「취소 중」은 LLM 이 읽는 목록에만 남는다(§3-6).
- **오류로 끝난 턴 뒤 codex 대기분을 저절로 보낸다**(한도가 풀린 뒤 포함) — 사용자: 세션을 건드리지 않길 원한다. 대기분은 다음 사용자 글과 함께 간다(§3-10).
- **빚진 후속 턴이 실패하면 포기하고 우편을 곧바로 흘린다**(TRD 질문 N11 의 (a)) — 진짜 오류 뒤 자동 투입 금지 원칙과 어긋난다. 사용자: 「진짜 에러면 강제로 쑤셔넣으면 안되잖아」 · 「어쨋든 모종의 이유로 이상하게 종료될때 채팅 입력이 성공하거나 어쨋든 재개 신호가 오면 뿌린다는거잖아」 → 「ㅇㅇ」. 관행도 같은 쪽이다 — codex 가 실패 뒤 대기 입력을 자동 제출하는 동작이 결함으로 신고됐다(openai/codex#24443). 이상하게 끝난 턴 뒤에는 멈추고 사용자의 다음 턴 성공이 다시 흘린다(§3-9).
- **한도 해제 신호(초기화 시각)로 저절로 다시 흘린다** — 사용자: 「아냐 일단 복잡하게 하지말자」. 그 신호는 사용 한도 한 종류뿐이고 해제 알림이 아니라 예고 시각이다 · 「한도가 다시 풀려도 저절로 보내지 않는다」(§3-10)와 같은 방향이다.
- **수락 모름 codex 항목의 ✕ 뒤 받음이나 에이전트 종료까지 「취소 중」으로 둔다**(TRD 질문 N12 의 (b)) — 어느 창에도 안 보이는 항목이 우편을 상한 없이 막고, 그 동안 한가할 때 친 글도 목록을 거친다(AC1 상실). 사용자: 「끝난걸로쳐. 유저가 x눌렀을때 우연찮게 들어가는건 그냥 그렇다 치겠지」(§3-6).
- **수락 모름 codex 항목 뒤에 친 글을 그 항목 뒤에 붙든다**(TRD 질문 N13 의 (a) — 5판의 잠정 문구) — 이미 넘긴 글의 결과를 모른다는 이유로 대화 전체가 사용자의 ✕ 까지 멈춘다. 사용자: 「음? 뭔소리야 순서대로 들어가는거잖아. 앞지른다는게 뭔소리? 또 발생되지도 않는걸 가정함?」 — 넘기는 순서는 친 순서 그대로이고, 그 갈래 자체가 관측된 적 없는 방어 갈래다(§3-4).
- **✕ 툴팁 「취소 — 글은 버려짐」**(5판까지의 문구) — 이미 넘긴 codex 항목엔 틀린 말이다. **「목록에서 빼기 — 이미 넘어간 글은 대화에 나타날 수 있음」** — 늦은 말풍선은 어쩔 수 없는 일이라 경고할 것이 아니다. 사용자: 「계속 몇번을 얘기하는데 x눌러도 없어졌는데 안으로 들어가서 표시하는건 어쩔수 없잖아.」 · (2026-09-25) 「x를 건드릴 이유가 있어? 그냥 x누르면 목록에서 기계적으로 빼는거잖아」. 툴팁은 「목록에서 빼기」다(§3-6).
- **claude 의 오류 턴 처리를 우리 쪽에서 강제로 맞춘다**(예: 남은 항목을 우리가 취소하거나 다음 턴으로 밀어 넣기) — 사용자: 「억지로 구현하지 마」. 벤더를 따른다(§3-10).
- **참고 — 조사 단계의 거부 후보**(사용자 결정이 아니라 조사 보고서 §5 의 판단): 턴 중 보내기 막기(현재 에이전트 도구 관행과 반대이고 claude 경로는 이미 허용 중이라 퇴행) · 글 내용을 비교해 화면 말풍선과 에이전트 쪽 사본을 짝짓기(ADR-0198 이 이미 기각 — 두 백엔드 모두 항목 id 가 있다).

## 7. 미룬 것 (지금은 비목표 — 나중 후보)

- **턴 끊기 조작 — 이 기능 바로 다음 기능이다**(사용자 결정). 채팅 뷰에서 도는 턴을 멈추는 조작이다. 끊을 때 대기분을 버릴지(§3-7 그대로) 다음 턴으로 보낼지(Claude Code 의 Esc 식)는 그 기능에서 정한다. claude JSON 은 끊기 지원부터 들여야 한다(§2).
- **취소·못 보낸 글을 입력창으로 되돌리기** — 그리고 여러 개일 때 입력창에 붙이는 규칙(덮어쓰기 · 이어 붙이기).
- **버림·실패 알림** — 지금은 없다(§3-7). 필요하면 나중에 더한다(사용자). 검토했던 모양: 대화 안 한 줄 · 목록 자리 · 토스트 · 버린 글 전문 보이기.
- **Esc 키 바인딩** — 취소가 이미 등록된 명령이라 묶기만 하면 된다.
- **우편 알림** — 사용자와 대화 중이면 「우편 왔습니다 — 확인하세요」로 묻고 펼치고, 대화 중이 아니면 그냥 펼친다(사용자 구상 2026-09-26). 이상하게 끝난 턴 뒤 우편이 이유 없이 멈춰 보이는 대가(§3-9)를 이것이 푼다.
- **한도 해제 신호로 저절로 다시 흘리기** — 지금은 거부했다(§6 · 사용자: 「아냐 일단 복잡하게 하지말자」). 다시 꺼내려면 신호가 사용 한도 한 종류뿐이고 예고 시각이라는 점부터 풀어야 한다.
- **「지금 보내기(Send now)」 — 도는 턴을 끊고 이 글을 즉시 보낸다.** 선례: Claude Code Ctrl+Enter = 끊고 지금 보냄(2.1.275↑) · Esc = 끊고 대기분을 다음에 보냄 · Up = 대기분을 입력창으로 되가져오기 · Cursor 도 Ctrl+Enter 끊기와 Send now 를 둔다(불확실 — changelog)(조사 보고서 §2-1 · §2-2). 이 기능에는 끊고 보내는 길이 없다. 사용자가 2026-09-25 밤에 질문으로만 올렸고 결정은 없다(위 턴 끊기 조작 위에 선다).
- **턴이 끝난 뒤 늦게 받음이 온 codex 항목에 답하는 턴을 저절로 열기** — 지금은 양보했다(§3-1 예외 · 사용자: 「복잡한것보다 약간 양보하면서 단순한 방향으로 하되 나중에 문제되면 기능 추가하면 되지」). 그 사이 우편이 먼저 답받는 일이 실제로 문제가 되면 더한다(같은 글을 두 번 넘기지 않는 방식 = TRD).
- **데몬 재기동 뒤 목록 보존** — 대기분은 에이전트와 함께 사라진다(오늘 입력 큐와 같은 등급).

## 8. 위험 · 모르는 것

- **R1. ★claude 쪽은 벤더 내부용 표면에 기대고, 우리 스폰 모드에서 아직 안 쟀다★.** 항목별 받음 알림과 취소 요청 둘 다 그렇다 — 안 되면 §3 의 claude 동작(목록 · ✕)이 바뀐다. 측정 결과가 사용자 체감을 바꾸면 사용자 결정으로 다시 올린다. — 가능성 높음 · 미실측. 상세 = TRD §3-1 · §3-3(M1–M4).
- **R2. claude ✕ 에 「못 뺐다」고 답해도 「전달됐다」는 뜻이 아니다**(취소를 예약해 두고 나중에 확정하기도 한다) — 그래서 claude ✕ 의 결말은 뒤이은 알림으로만 정한다(§3-6). — 가능성 높음 · 미실측(M3). 상세 = TRD §3-1.
- **R3. codex 항목은 넘긴 뒤에는 거둘 수 없다** — 벤더에 넘긴 항목 하나를 빼는 수단이 없다. ✕ 는 그 뒤에도 있고 누르면 목록에서 빠지지만(§3-6), 글이 에이전트에게 가지 않게 하는 것은 우리가 붙든 동안뿐이다 — 넘긴 뒤 누른 ✕ 는 에이전트가 받으면 말풍선으로 되돌아온다(사용자가 받아들임). 붙들면 늦어지는 구간(§3-1)에서는 처음부터 그렇고, 턴 끊기 조작도 이 기능엔 없다(§2). 그 구간에서 두 백엔드의 체감(claude 는 ✕ 가 빼 달라는 요청까지 보낸다)이 갈리고, ADR-0192 「못 맞추면 보고」의 대상이다. — 가능성 높음(소스) · 끊기 조작 부재는 확실(코드).
- **R4. 답 없는 글은 생기면 안 된다(§3-1 요구)** — codex 는 턴이 끝나는 찰나에 들어간 글을 답 없이 기록만 하는 벤더 동작이 있어, 설계가 이를 두 번 넘기지 않고 막을 수 있는지는 TRD 위험(M6)이었다. **Phase 0b 에서 섰다**(`docs/research/mid-turn-phase0b-measurements-2026-09-26.md` §0): M9 녹 — 빈 입력 턴이 받혀 답 못 받은 그 메시지 하나에 답했다(3/3) · M10 녹 — 턴 끝 「기록만」 갈래가 4 번 중 3 번 재현됐고, 기록된 입력의 되울림이 턴 완료 알림보다 먼저 왔다. 남은 틈은 턴이 끝난 **뒤** 오는 늦은 받음 하나이고, 그것은 §3-1 예외(양보)로 받아들였다. — 확실(실측).
- **R5. 이어받기 복원에서 claude 의 턴 중 입력이 빠질 수 있다** — 이어받은 뒤 그 말풍선이 복원 이력에 없을 수 있고, 이 기능이 그 경우를 흔하게 만든다. 이어받은 대화를 불러오는 중에 넘긴 글(한가할 때 보낸 글로 친다 — §3-11)을 벤더가 불러오기 뒤에 처리하는지도 안 쟀다. 측정 결과가 사용자 체감을 바꾸면 사용자 결정으로 다시 올린다. — 불확실(M5 · M14). 상세 = TRD §3-1.
- **R6. 벤더 전제(claude 받음 알림 · codex 항목 id 되울림 — codex 0.140.0 이상)가 없는 옛 버전은 따로 받치지 않는다** — 오늘 동작 그대로다(사용자: 「알아서 업데이트」 · §2). 버전을 가려내는 법은 TRD 몫이다. 이상하게 끝난 턴 뒤 우편 멈춤(§3-9)은 예외로 옛 버전에도 건다.
- **R7. 턴 도중 보낸 슬래시 명령(「/compact」 등)은 특별 취급하지 않는다** — 다른 글처럼 넘기며, 에이전트가 그것을 명령으로 실행하는지·턴 끝까지 미루는지·받음 알림을 내는지는 미측정이다(Claude Code 문서는 명령·셸 입력을 턴 끝까지 보류한다고 적는다 — 우리 모드에서 같은지는 모른다). **나쁜 경우:** 벤더가 명령을 턴 끝까지 보류하거나 항목별 받음 알림을 내지 않으면, 그 항목은 받음이 안 와 에이전트가 끝날 때까지 회색으로 목록에 남는다(§3-4). 그 동안 목록이 비지 않으므로 에이전트는 §3-5 의 한가가 아니고, 이후 보낸 글도 전부 목록을 거치며(AC1 상실) 우편도 상한 없이 — 에이전트가 끝날 때까지 — 들어가지 못한다(§3-9). **Phase 0b M13 녹**(`docs/research/mid-turn-phase0b-measurements-2026-09-26.md` §0): claude 턴 도중 보낸 `/compact` 3/3 · `/cost` 3/3 이 대기에 들어간 뒤 도구 경계에서 접히지 않고 달리던 턴이 끝날 때까지 붙들렸다가 새 턴으로 시작해 끝났다 — 거절·취소·버림은 한 번도 없었다. 그래서 위 나쁜 경우는 이 두 명령에서 일어나지 않는다(목록 항목은 그 새 턴에서 받음을 받아 빠진다 — 턴 끝까지 회색으로 남는 것은 명령의 정상 모양이다). 다른 명령은 안 쟀다. 측정 결과가 사용자 체감을 바꾸면 사용자 결정으로 다시 올린다.
- **R8. ★codex 붙들기(§3-1)는 우리가 경계에 제때 넘길 수 있어야 선다★** — 도구가 끝나는 지점은 붙들었다 넘겨도 같은 경계에 들었지만(Phase 0 — 10/10), 우리 데몬의 반응 시간과, 도구 없이 답만 쓰다 끝나는 구간에 같은 틈이 있는지는 아직 안 쟀다. 판정의 시간 근거는 TRD 가 재서 정한다. 못 맞추는 구간은 §3-1 대로 곧바로 넘기되(✕ 는 있으나 글을 거둬 오지는 못한다 — §3-6), 측정이 도구 끝 구간마저 못 맞춘다고 나오면 코드 전에 사용자에게 다시 묻는다(붙들기 대 다른 길).
- **R9. 한가할 때 보낸 글이 말풍선으로 그려진 뒤 백엔드에 거절될 때 오늘 그 말풍선이 남는지는 미확인이다** — §3-5 는 그것을 알림 없이 지우라고 정한다. 오늘 이미 지워진다면 할 일이 없고, 남는다면 새로 지워야 한다.
- **R10. 목록 항목이 받음을 받아 말풍선이 된 뒤에 거절이 올 수 있다는 전제는 미측정이다**(claude — 받았다는 알림 뒤에 거절 알림). §3-5 는 그 경우에도 말풍선을 지우라고 정한다. 그런 순서가 실제로 없으면 할 일이 없다.
- **R11. 한가할 때 보낸 글이 처리되기 전에 에이전트가 끝나거나 턴이 끊겨 벤더가 그 글을 기록하지 않았을 때, 이어받아 이력을 다시 불러오면 그 말풍선이 빠지는지는 미확인이다** — §3-5 는 그대로 두라고 정했다(사용자: 이어받으면 어차피 갱신된다).

## 10. TRD · QA · ADR 로 넘기는 것

- **「어떻게」는 전부 TRD:** 목록을 어느 층이 쥐나 · codex 를 붙들었다 넘기는 방식과 구간별 판정의 시간 근거(R8) · 받음 판정과 창·LLM 이 같은 목록으로 수렴하는 규칙 — 창 쪽에서 사건 순서를 다시 맞춰 기존 순서 불변식을 지킨다(사용자 확인 — TRD N5) · ✕ 를 모든 창에서 곧바로 감추기와 LLM 이 읽는 목록의 「취소 중」 · 명령 이름·인자 · 프로토콜 버전 5 → 6(사용자 승인 — TRD N4) · 창이 다시 붙을 때 목록 맞추기 · 답 못 받은 항목을 두 번 넘기지 않고 답받게 하는 법(M6) · 우편 순서(§3-9) · 벤더 버전 탐지(옛 버전은 오늘 동작 — R6) · 측정(Phase 0 M1–M8 · Phase 0b M9 · M10 · M13 녹 · 남은 것은 TRD §3-3) · 시험 계획.
- **TRD·QA 로 넘기는 게이트:** 새 전역 핸들을 늘리지 않는다(`CLAUDE.md 「LLM-우선 제어」` — 기존 명령 표면에 얹는다) · 터미널 모드 입력 바이트 동일 회귀.
- **TRD 8판이 이 PRD 6판의 답(§9 의 2026-09-26 줄 · §3-1 예외 · 옛 codex 에도 거는 우편 멈춤)을 담는다**(8판 리뷰 중). **TRD 7판이 이 PRD 의 §9 답을 담는다** — 가장 큰 변화는 codex 를 가장 이른 경계까지 붙드는 설계(§3-1 · §3-6)이고, 머리줄 제거 · 알림 없음 · 거절된 말풍선 지우기 · 오류 턴 규칙(§3-10) · 이어받기 중 입력(§3-11) · 우편 순서(§3-9)가 뒤따른다.
- **ADR:** 새 ADR 하나(미채번) — 결정 = §2·§3, 거부한 대안 = §6. 개정 도장 후보 = ADR-0044 · 0045 · 0193 · 0198 · 0226(구체 조항은 TRD §8).
- **순서:** TRD 8판 → `/review trd` → ADR → 구현(TRD §9). TRD 확정과 구현은 사용자가 2026-09-26 맡겼다 — 「나 자러갈테니깐 쭉쭉 진행해. 충분히 얘기한것같으니 구현 너가 알아서하고 후에 최종 보고하는걸로」 · 사용자는 최종 보고를 검토한다. 측정(R8)이 결정과 어긋나면 코드 전에 사용자에게 다시 올린다.
