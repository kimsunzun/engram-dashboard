## 1. 무엇·왜

- **계속 커지는 내부 번호가 사람에게 보인다.** 팝아웃 창 제목 = 「Engram — slot-popup-11」(`src-tauri/src/commands/popout.rs:399`) · 새 창 팝아웃의 탭 이름 = 「Popup 6」(같은 파일 `tab_name` :64). 창 label 은 단조 카운터라 창을 닫아도 번호가 돌아오지 않는다. (코드)
- **메인과 팝아웃이 겉보기로 같다.** 어느 창이 메인인지 모른다 — 사용자 2026-10-20 「나중에 메인창인지 팝아웃인지 구분해주는게 필요해보이긴하는데 똑같으니깐 뭐가 메인인지 모르겠네」(트래킹 T-66 「창 구분」). → R24(메인 = 늘 번호 1) · R10(메인 ✕ = 모든 창 숨기기 · 모양 · 툴팁이 다르다). ★2026-10-23 더함★
- **창 제목이 내용을 말하지 않고, 창 이름은 못 바꾼다.** 메인 제목은 「Engram Dashboard」 고정(`src-tauri/tauri.conf.json`). 탭은 이름을 바꿀 수 있지만(화면 · `tab.rename`) 처음 이름은 대개 「View N」이다(Q6). (코드)
- **OS 제목 표시줄이 탭바 위에 한 줄을 따로 먹는다.** Chrome · Windows 11 탐색기처럼 탭바가 제목 표시줄 자리에 선다. (결정 · 2026-10-17)
- **LLM 이 창을 보이거나 앞으로 낼 길이 없다.** 보이기 · 숨기기는 트레이와 그 Tauri invoke 명령(`show_main_ui` · `hide_main_ui` — `src-tauri/src/commands/tray.rs`)뿐이고 버스 명령이 아니다 · 창 하나를 앞으로 내는 명령은 없다. 단추를 우리가 그리면 이 갭이 사람 · LLM 사이에 그대로 드러난다(R17). (코드)
- 시점 = 슬롯 도킹 9c 직후, 같은 브랜치에서 최종 머지에 포함. 탭바 넘침(슬롯 도킹 R24 — Chrome 규칙)과 같은 줄을 나눠 쓰므로 함께 간다. (결정 · 2026-10-17) ★2026-10-23 — 슬롯 도킹이 먼저 머지됐고(master `c60797a6`) 이 주제는 그 뒤 자기 브랜치 `v0.5.0/feat/window-chrome` · 스텝 S26 으로 이어 간다(사용자 2026-10-20 — 머리 표 「브랜치」). 탭바 넘침과 같은 줄을 나눠 쓰는 것은 그대로다(R13)★

## 3. 요구사항

**창 번호 · 이름**
- **R1** 각 창은 사람에게 보이는 **창 번호**를 갖는다 = 그 창이 생길 때 **살아 있는 창들이 쓰지 않는 가장 작은 번호**. 1 · 2 · 3 에서 2 를 닫으면 다음 새 창 = 2. (결정 · 2026-10-17) 모든 창이 번호를 갖고 메인은 늘 1 이다(결정 · 2026-10-23 — Q3 · D1). 새로 만드는 길 전부가 이 규칙을 탄다 — 적용 서비스(`src-tauri/src/layout/apply.rs`)의 새 창 세 자리: `create_window`(LLM `window.create`) · `move_slot_to_window`(메뉴 「팝업으로 분리」 · LLM `slot.popout`) · `dock_tab` 의 새 창(`DockDest::NewWindow` — 바탕화면 · 슬롯 가운데 놓기 · 출처 dragend — 슬롯 도킹 R6 · R22). 세 자리는 숨긴 예열 창을 먼저 맡고(창 포트 `claim_spare` — ADR-0299) 없을 때만 새로 짓는다 — 어느 쪽이든 이 규칙은 같다. 부팅 복원 · 크래시 사본 수락은 D3(Q8 — 예열 창을 쓰지 않는다 · ADR-0299 결정 5). 「살아 있는 창」 = 모델에 있는 창(`window.list` 에 보이는 창 — 숨은 · 최소화한 창 포함) **+ 모델에서 빠졌지만 OS 창이 아직 없어지지 않은 닫히는 창**. 번호는 창을 모델에 넣는 같은 락 안에서 잡아 동시에 만든 둘이 같은 번호를 받지 않고, **OS 창이 실제로 없어질 때(`Destroyed` — `src-tauri/src/lib.rs:367`) 풀린다** — 모델에서 빼는 길(`window.close` · 팝아웃 닫기 요청(셸이 그때 모델을 먼저 지운다 — 같은 파일 :335–361) · 마지막 탭 닫기 · 0탭 자가닫힘)은 그때까지 번호를 닫히는 창 몫으로 잡아 둔다. (기본값 — 메인 제안 · 거부한 갈래 = D13)
  - ★2026-10-23 — 예열 창(ADR-0299 · 기본값 — 메인 제안 · 사용자는 정하지 않았다)★: 숨은 예열 창은 모델 밖이라 「살아 있는 창」이 아니고 **번호를 쥐지 않는다**. 맡아 쓰는 창은 모델에 드는 순간(위 같은 락) 번호를 받고, 첫 화면(번호 표식 포함)을 그린 뒤 보인다(ADR-0299 결정 3 「창은 내용과 함께 뜬다」) ★2026-10-24 — 단 첫 화면 알림이 시한(1.5 s) 안에 오지 않으면 그리기 전에 보여 번호 표식이 아직 없을 수 있다 — 사용자 결정 2026-10-24 — 따로 처리하지 않음(웹 화면 프로세스가 죽는 드문 경우 · AC2). 0.4판의 「번호 없이 보이는 창이 없다」는 이 결정으로 걷었다★. 모델에 넣지 못해 되물린 예열 창은 번호 없이 숨은 채 돌아간다. 번호는 그 창이 없어질 때(`Destroyed`) 풀린다 — 다른 창과 같다.
  - ★2026-10-23 — 만들기 실패★: 새 창 세 자리는 OS 창(새로 짓거나 맡긴 예열 창)을 먼저 열고 그 뒤 모델에 넣는다(`apply.rs` `create_window` 머리 주석 — 「OS 창을 연 뒤에 모델에 넣는다」 · ADR-0299). 열기가 실패하거나 넣기가 거절돼 연 창을 거두면(예열 창은 되물리고 새로 지은 창은 닫는다) 번호를 잡은 적이 없으므로 풀 것도 없다 — 그 번호는 곧바로 다른 새 창이 쓴다. 0.3판의 「만들기 실패 되돌림은 OS 창이 서지 않았으므로 되돌림에서 곧바로 푼다」와 결과는 같다.
  - **복원 중 같은 번호가 잠깐 두 창에 — 받아들인 위험**(결정 · 2026-10-23 — 「어차피 잠깐 보이는거니 노상관」): 부팅 복원 · 크래시 사본 수락 도중(그사이 닫히는 창과 겹친 새 창 만들기 포함) 같은 보이는 번호가 잠깐 두 창에 설 수 있다. 잠깐이라 받아들인다 — 리뷰 1차 지적 ①(「번호는 `Destroyed` 뒤에만 빈다 · 복원이 기다린다」)의 규칙은 더하지 않는다. 명령은 영향이 없다 — 창을 번호가 아니라 내부 id 로 가리킨다(Q9 · R6). 닫히는 창이 없어진 뒤까지 남는 겹침은 없어야 한다(D3 · AC31 · W12). 보통 닫기의 번호를 그 창이 없어질 때까지 쥐는 0.3판 규칙(위 본문 · D13 · AC20 ②)은 싸고 그 경우를 막으므로 그대로 두되 복원 쪽으로 넓히지 않는다. 사용자가 받아들인 것은 **잠깐 겹침 전반**이다 — 받아들일 때 든 예가 바로 보통 닫기 뒤 새 창이었다. 그래서 TRD 가 그 쥐기를 비싸다고 보면 새 사용자 결정 없이 걷어도 된다(그때 AC20 ② 도 함께 걷는다).
  - ~~**모델에 든 뒤 첫 화면 전 실패**~~ ★2026-10-24 — **걷음**: 사용자 결정 2026-10-24 — 따로 처리하지 않음(웹 화면 프로세스가 죽는 드문 경우). 새 창은 지금처럼 첫 화면 알림이나 시한(1.5 s)에 보이고, 첫 화면 전 · 뒤에 웹뷰가 죽는 경우를 만들기 실패로 다루지 않는다(TRD 0.2 §5-3). 아래는 0.4판 기록(고르지 않은 갈래)★ (0.4판 — 기본값 — 메인 제안 · 2026-10-23 리뷰 반영 · 리뷰 2 반영): 번호를 받고 모델에 든 새 창이 첫 화면을 그리기 전에 그 웹뷰가 죽거나 실패로 판정되면 — ① **그 창을 만든 호출은 실패로 답한다**(이유를 실은 오류 — 성공으로 답하지 않는다 · LLM 명령이든 끌어 놓기 · 메뉴든 · R6) ② **셸이 자기가 만든 OS 창을 거둔다** — 남는 네이티브 창이 없다(맡긴 예열 창이었어도 되물리지 않고 거둔다) ③ 그 창을 모델에서 빼고 번호는 보통 규칙대로 푼다(한 번도 보이지 않았으므로 곧바로 — D13). **탭은 잃지 않는다** — 그 창으로 옮긴 탭(`move_slot_to_window` · 도킹 새 창)은 **출처 창이 모델에 있고 닫히는 중이 아니면** 그 창으로, 아니면 메인으로 돌아간다(`create_window` 의 빈 새 탭은 돌려줄 것이 없다). 그래서 창을 만드는 호출은 첫 화면이나 실패 판정까지 기다려 답한다(꼴 · 시한 = TRD). 무엇을 실패로 보나(웹뷰 끝남 신호 · 시한)도 TRD — 지금 첫 화면 문은 알림이 안 와도 시한에 창을 보일 뿐 실패로 다루지 않는다(`src-tauri/src/first_paint.rs` 머리). 첫 화면 뒤에 웹뷰가 죽는 것은 이 규칙 밖이다(성공 답이 이미 나갔다)(AC33 · ②–③ 과 출처 낱말 = 2026-10-23 리뷰 2 반영).
- **R2** 내부 창 label(`slot-popup-N`)은 지금처럼 **단조**다 — 번호는 label 과 따로 매긴다. capability glob(`slot-popup-*`) · 닫힘 정리 판정은 그대로다. (결정 · 2026-10-17) D12 가 label 에 실행 표식을 더해도 실행 안 단조 · glob 은 그대로다(기본값 — 메인 제안).
- **R3** **창 제목**(작업 표시줄 · Alt+Tab · 작업 보기에 보이는 OS 제목) = **「<활성 탭 이름> - Engram:<n>」**(n = 그 창 번호 — R1 · 결정 · 2026-10-23 — Q3 · 꼴의 선례 = Excel 둘째 창 `Book1.xls:2` — 조사 식별 결론 1). 탭 전환 · 활성 탭 이름 바뀜(사람 · `tab.rename` · R4 의 자동 이름) · 활성 탭 닫기 · 다른 창으로 옮기기 직후 새 활성 탭을 따른다. 활성 탭이 아직 없으면(창을 막 만들어 모델을 받기 전) 「Engram:<n>」 · 번호가 없는 숨은 예열 창(R1)은 「Engram」. 긴 · 유니코드 이름은 OS 제목에 자르지 않고 싣고(작업 표시줄이 자르는 것은 OS 몫), 탭 머리는 말줄임 + 툴팁 전체 이름. 같은 이름 탭이 여러 창에 있어도 그대로 — 창은 번호가 가른다. 우리 제목 표시줄 안에는 제목 글자를 그리지 않는다(Chrome 과 같다) — 창 안에 보이는 것은 번호 표식의 번호뿐이다(R24). (제목 꼴 = 결정 · 2026-10-23 · 따라가기 · 빈 탭 · 예열 창 · 긴 이름 = 기본값 — 메인 제안 · 조사 이름 §2 ③ · §4)
- **R4** **탭 이름 = 자동 이름**(결정 · 2026-10-23 — Q6) — 사람(화면 이름 바꾸기) · LLM(`tab.rename`)이 이름을 정하기 전까지 탭 이름 = 그 탭 **포커스 슬롯의 표시 이름**: 에이전트 슬롯 = 그 에이전트 이름(대개 작업 폴더 이름) · 다른 종류 = 그 종류 이름(에이전트 목록 · 프리셋 팔레트 · 사용량 — `SlotContent` `src-tauri/src/layout/types.rs`) · 빈 슬롯 = 자리표시 이름 「빈 칸」(★낱말 = 결정 · 2026-10-24 — 빈 칸 · 에이전트(이름을 아직 모를 때) · 에이전트 트리 · 프리셋 · 사용량 · 이 판이 모르는 내용을 쥔 슬롯은 웹과 같은 「알 수 없는 내용」(메인 결정 — `SlotContent` 갈래가 아니라 모르는 내용 곁표 · TRD 0.2 §4-2)★). 탭 안 포커스가 옮기거나 에이전트 이름이 바뀌면 따라간다. 이름을 정하면 굳는다. 그래서 시스템이 짓던 「Popup N」 · 「Tab」 · 「View N」은 사람 눈에서 없어진다(사람 · LLM 이 그 글자로 지은 이름은 그대로). 피어 = WezTerm(작업 폴더 이름 · 사람이 바꾸면 그 이름) · Windows Terminal · tmux(손으로 바꾸면 `automatic-rename` 이 꺼진다) — 메인이 결정 때 든 피어이고 조사 문서는 없다. 보이는 글자 · 빈 슬롯 낱말은 i18n 을 따른다(기본값 — 메인 제안 · ★2026-10-24 — 셸이 짓는 이름이라 낱말을 셸 표 한 곳에 둔다 · 로컬라이제이션(T-68)이 웹 i18n 과 합친다 — TRD 0.2 §1-4★). 정한 이름을 자동으로 되돌리는 길 = 이번 범위 밖(아래 「빈 이름」 · §2). 옛 상태 파일 = D16 · 표시 이름 짓는 법 = D17 · 저장 일관성 = R29.

- **W13 접힌 끌기**(★2026-10-24 더함 — 디버그 세션 실측★) — 탭 줄이 테두리 없는 창 맨 위에 붙은 채로 막 보인 팝아웃의 탭을 위로 빠르게 끌면, OS 끌기가 시작되기 전(누름 → dragstart 42–145 ms)에 커서가 창을 벗어나고 OS 끌기가 곧바로(약 6 ms) 끝난다 — 셸이 취소로 읽어 아무 일도 없고 다시 하면 된다. 스파이크 세션에 18 번 · 스파이크 앞 기록에 0 번(스파이크 탓일 가능성 높음 · Win32/Blink 쪽 원인은 모른다). 대응 = 보통 상태 위 여백(R7 · 기본값 — 메인 제안 · 사용자 확인 필요(QA)) · 측정 = 빠른 위쪽 끌기 × 10 을 여백 있음 · 없음 · 보인 뒤 2 초 기다림 · master 기준 빌드로(TRD 0.3 §1-3 S13). 원인을 가르기 전에 시한 · 문턱을 고치지 않는다(`docs/reference/debugging-conventions.md`).
- **W14 웹뷰 밖 자식 창 위 놓기 잃음**(★2026-10-24 더함★) — CSS `app-region` 끌 자리 위 놓기는 받는 쪽 없이 끝난다(실측 — 최상위 창에 tao 의 파일 전용 놓기 등록 · Q5 = Tauri 끌기 영역을 굳힌 근거). 같은 길이 OS 틀을 걷은 창의 위 가장자리 크기 조절 자식 창 · (켤 때) 스냅 오버레이 위에도 있을 수 있다 — 그 몇 px 에 놓은 탭은 아무 일 없이 끝날 수 있다(탭은 잃지 않는다). 측정 뒤 정한다(그 자리를 빼고 받아들임 · 창 수준 놓기 받는 쪽을 둠 — TRD 0.3 §7-9 · S14 · R14 · AC12).
