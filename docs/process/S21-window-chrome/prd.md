## 1. What · why

- **The ever-growing internal number is visible to people.** The popout window title = 「Engram — slot-popup-11」 (`src-tauri/src/commands/popout.rs:399`) · the tab name of a new-window popout = 「Popup 6」 (`tab_name` :64 in the same file). The window label is a monotonic counter, so numbers do not come back even when windows are closed. (code)
- **Main and popouts look the same.** There is no telling which window is main — user 2026-10-20 「나중에 메인창인지 팝아웃인지 구분해주는게 필요해보이긴하는데 똑같으니깐 뭐가 메인인지 모르겠네」 (tracking T-66 「창 구분」). → R24 (main = always number 1) · R10 (the main ✕ = hide all windows · shape · tooltip differ). ★Added 2026-10-23★
- **The window title does not say what is inside, and the window name cannot be changed.** The main title is fixed as 「Engram Dashboard」 (`src-tauri/tauri.conf.json`). A tab can be renamed (screen · `tab.rename`), but the initial name is usually 「View N」 (Q6). (code)
- **The OS title bar takes a separate line above the tab bar.** Like Chrome · the Windows 11 File Explorer, the tab bar stands in the title bar position. (decision · 2026-10-17)
- **There is no way for the LLM to show a window or bring it to the front.** Showing · hiding are only the tray and its Tauri invoke commands (`show_main_ui` · `hide_main_ui` — `src-tauri/src/commands/tray.rs`) and are not bus commands · there is no command that brings one window to the front. If we draw the buttons ourselves, this gap shows up directly between people and the LLM (R17). (code)
- Timing = right after slot docking 9c, on the same branch, included in the final merge. It shares a line with the tab-bar overflow (slot docking R24 — Chrome rule), so they go together. (decision · 2026-10-17) ★2026-10-23 — slot docking was merged first (master `c60797a6`) and this topic continues afterwards on its own branch `v0.5.0/feat/window-chrome` · step S26 (user 2026-10-20 — head table 「브랜치」). Sharing a line with the tab-bar overflow is unchanged (R13)★

## 3. Requirements

**Window number · name**
- **R1** Each window has a **window number** visible to people = **the smallest number that live windows do not use** at the moment the window is created. With 1 · 2 · 3, if 2 is closed the next new window = 2. (decision · 2026-10-17) Every window has a number and main is always 1 (decision · 2026-10-23 — Q3 · D1). Every path that creates a new one follows this rule — the three new-window places of the apply service (`src-tauri/src/layout/apply.rs`): `create_window` (LLM `window.create`) · `move_slot_to_window` (menu 「팝업으로 분리」 · LLM `slot.popout`) · the new window of `dock_tab` (`DockDest::NewWindow` — desktop · dropping onto the center of a slot · origin dragend — slot docking R6 · R22). The three places first claim a hidden prewarmed window (window port `claim_spare` — ADR-0299) and build a new one only when there is none — this rule is the same either way. Boot restore · crash copy acceptance is D3 (Q8 — they do not use a prewarmed window · ADR-0299 decision 5). 「살아 있는 창」 = a window in the model (a window shown in `window.list` — including hidden · minimized windows) **+ a closing window that has left the model but whose OS window has not yet gone away**. The number is taken inside the same lock that puts the window into the model, so two windows created at the same time do not get the same number, and **it is released when the OS window actually goes away (`Destroyed` — `src-tauri/src/lib.rs:367`)** — the paths that remove it from the model (`window.close` · popout close request (the shell erases the model first at that point — same file :335–361) · closing the last tab · zero-tab self-close) hold the number until then as the closing window's share. (default — main proposal · rejected branch = D13)
  - ★2026-10-23 — prewarmed window (ADR-0299 · default — main proposal · the user did not decide)★: a hidden prewarmed window is outside the model, so it is not a 「살아 있는 창」 and **does not hold a number**. A window that is claimed gets a number the moment it enters the model (inside the same lock as above) and is shown after drawing its first screen (including the number marker) (ADR-0299 decision 3 「창은 내용과 함께 뜬다」) ★2026-10-24 — however, if the first-paint notification does not arrive within the deadline (1.5 s), it is shown before drawing and the number marker may not be there yet — user decision 2026-10-24 — not handled separately (the rare case where the web renderer process dies · AC2). The 「번호 없이 보이는 창이 없다」 of edition 0.4 was withdrawn by this decision★. A prewarmed window that could not be put into the model and was returned goes back hidden without a number. The number is released when that window goes away (`Destroyed`) — same as other windows.
  - ★2026-10-23 — creation failure★: the three new-window places first open the OS window (newly built or the claimed prewarmed window) and then put it into the model (head comment of `create_window` in `apply.rs` — 「OS 창을 연 뒤에 모델에 넣는다」 · ADR-0299). If opening fails or putting it in is rejected and the opened window is withdrawn (a prewarmed window is returned and a newly built window is closed), no number was ever taken, so there is nothing to release — that number is used immediately by another new window. The result is the same as 「만들기 실패 되돌림은 OS 창이 서지 않았으므로 되돌림에서 곧바로 푼다」 of edition 0.3.
  - **The same number briefly on two windows during restore — an accepted risk** (decision · 2026-10-23 — 「어차피 잠깐 보이는거니 노상관」): during boot restore · crash copy acceptance (including creating a new window that overlaps with a window closing in the meantime) the same visible number can briefly stand on two windows. It is brief, so it is accepted — the rule of review round 1 finding ① (「번호는 `Destroyed` 뒤에만 빈다 · 복원이 기다린다」) is not added. Commands are not affected — a window is pointed at by internal id, not by number (Q9 · R6). There must be no overlap that remains after the closing window is gone (D3 · AC31 · W12). The edition 0.3 rule of holding the number of a normal close until that window goes away (body above · D13 · AC20 ②) is cheap and prevents that case, so it stays but is not widened toward restore. What the user accepted is **brief overlap in general** — the example given at acceptance was exactly a new window after a normal close. So if the TRD finds that holding too expensive, it may be removed without a new user decision (then AC20 ② is removed with it).
  - ~~**Failure before the first paint after entering the model** (모델에 든 뒤 첫 화면 전 실패)~~ ★2026-10-24 — **withdrawn**: user decision 2026-10-24 — not handled separately (the rare case where the web renderer process dies). A new window is shown, as now, on the first-paint notification or at the deadline (1.5 s), and a webview dying before · after the first paint is not treated as a creation failure (TRD 0.2 §5-3). Below is the edition 0.4 record (a branch not chosen)★ (edition 0.4 — default — main proposal · applied from the 2026-10-23 review · applied from review 2): if the webview of a new window that got a number and entered the model dies or is judged a failure before it draws its first screen — ① **the call that created that window answers with a failure** (an error carrying the reason — it does not answer with success · whether LLM command or drag-drop · menu · R6) ② **the shell withdraws the OS window it created** — no native window is left (even if it was a claimed prewarmed window it is withdrawn, not returned) ③ that window is removed from the model and the number is released by the normal rule (immediately because it was never shown — D13). **The tab is not lost** — the tab moved to that window (`move_slot_to_window` · docking new window) goes back to that window **if the origin window is in the model and not closing**, otherwise to main (an empty new tab of `create_window` has nothing to give back). So the call that creates a window waits and answers until the first paint or the failure decision (form · deadline = TRD). What counts as a failure (webview-ended signal · deadline) is also the TRD's — today the first-paint gate only shows the window at the deadline even if no notification comes and does not treat it as a failure (head of `src-tauri/src/first_paint.rs`). A webview dying after the first paint is outside this rule (a success answer has already gone out) (AC33 · ②–③ and the origin wording = applied from 2026-10-23 review 2).
- **R2** The internal window label (`slot-popup-N`) stays **monotonic** as now — the number is assigned separately from the label. The capability glob (`slot-popup-*`) · the close-cleanup decision are unchanged. (decision · 2026-10-17) Even if D12 adds a run marker to the label, it stays monotonic within a run and the glob is unchanged (default — main proposal).
- **R3** **Window title** (the OS title shown in the taskbar · Alt+Tab · task view) = **「<활성 탭 이름> - Engram:<n>」** (n = that window's number — R1 · decision · 2026-10-23 — Q3 · precedent for the form = Excel's second window `Book1.xls:2` — survey identification conclusion 1). It follows the new active tab right after a tab switch · a change of the active tab name (by a person · `tab.rename` · the automatic name of R4) · closing the active tab · moving to another window. If there is no active tab yet (just created and has not received the model) 「Engram:<n>」 · a hidden prewarmed window with no number (R1) is 「Engram」. Long · Unicode names are put into the OS title without cutting (cutting in the taskbar is the OS's job), and the tab head uses an ellipsis + a tooltip with the full name. - **W6 Window menu** — the Tauri drag region does not bring up a window menu on right-click of the empty space (`drag.js` — looks only at the left button). Whether Alt+Space appears on a borderless window is unverified → Q10.
- **W7 Popout close premise** — the shell erases the model first, presuming 「팝아웃 닫기 요청은 되돌려지지 않는다 · 프론트에 닫기 요청 리스너가 없다」 (`src-tauri/src/lib.rs:335–361` CloseRequested branch). - **W10 Front-window lock** — bring-to-front called by the LLM can be blocked by Windows' restriction on changing the front window when the shell is not the front process, and end as a taskbar flash (for the tray the click grants that permission — the show → unminimize → set_focus order comment in `src-tauri/src/tray/actions.rs`). - **W11 Adding state-file fields** — the screen state gains a number field (Q8 ①) · the tab's 「정한 이름인가」 field (Q6 ④). - **W12 Number briefly overlapping during restore — an accepted risk** (decision · 2026-10-23 — 「어차피 잠깐 보이는거니 노상관」) — during boot restore · crash copy acceptance (including creating an overlapping new window in the meantime) the same visible number briefly stands in the number marker · OS title of two windows. If a person says 「2번 창」 during that moment, it may be ambiguous which window — commands point by persistent id and do not go astray (Q9). The overlap that remains after the closing window is gone is prevented by the rule of D3 and measured by AC31. What was accepted is brief overlap in general (its example = a new window after a normal close) — holding the number of a normal close until `Destroyed` (D13) may be removed by the TRD (R1).
- **W13 Collapsed drag** (★added 2026-10-24 — measured in a debug session★) — when the tab strip sticks to the very top of a borderless window and the tab of a just-shown popout is dragged quickly upward, the cursor leaves the window before the OS drag starts (press → dragstart 42–145 ms) and the OS drag ends right away (about 6 ms) — the shell reads it as a cancel, nothing happens, and one can just do it again. 18 times in the spike session · 0 times in the record before the spike (likely caused by the spike · the Win32/Blink-side cause is not known). Response = top margin in the normal state (R7 · default — main proposal · user confirmation needed (QA)) · measurement = fast upward drag × 10 with margin · without · waiting 2 seconds after showing · on the master baseline build (TRD 0.3 §1-3 S13). Do not fix the deadline · threshold before separating the cause (`docs/reference/debugging-conventions.md`).
- **W14 Drop onto a child window outside the webview is lost** (★added 2026-10-24★) — a drop over a CSS `app-region` draggable spot ends with no receiver (measured — tao's file-only drop registration on the top-level window · the basis for fixing Q5 = Tauri drag region). The same path may also exist over the top-edge resize child window of a window that removed the OS frame · (when turned on) the snap overlay — a tab dropped on those few px may end with nothing happening (the tab is not lost). To be decided after measurement (excluding that spot and accepting · putting a window-level drop receiver — TRD 0.3 §7-9 · S14 · R14 · AC12).
