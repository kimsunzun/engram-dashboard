### 2-2. `DataLayout` — the single source of paths [고름]

- **Location = a new module `layout` in `engram-dashboard-discovery`.** That crate is already the single source of `default_data_dir` (ADR-0024 · `lib.rs:84`) and both the daemon and the shell depend on it. **base rejected** — the folder names are domain knowledge, so it violates the admission condition, and a third resident would call for a re-examination of ADR-0175. **net cannot depend on discovery** (discovery → net), so it takes the paths as arguments.
- Shape: `DataLayout::new(root)` · `resolve()` (= `new(default_data_dir())`) · `root()` · `daemon_state_dir()` · `daemon_run_dir()` · `daemon_file()` · `mcp_config_dir()` · `usage_probe_dir()` · `shell_config_dir()` · `shell_state_dir()` · `shell_run_dir()` · `webview_dir()` · `logs_dir()` · `ensure_daemon_dirs()`. **No function for the old flat paths is kept** (§3-2).
- **Ownership rule:** directories and **files seen by two or more processes** (`daemon.json` — written by the daemon and read by the shell and scripts) are computed by `DataLayout`. **A file name used by only one store is owned by that store** and is appended only inside the directory it receives — `agents.json` (`agent/src/persistence/mod.rs:22`) · `presets.json` (`presets.rs:19`) · ~~`usage_rejects.json` (`reject_store.rs:20`)~~ (dropped by ADR-0284 — 2026-10-08) · `settings.json`·`state.json` (shell storage layer). Pulling the names in as well would make the agent crate depend on discovery.
- Signatures that change: net `instance::acquire(data_dir)` → `acquire(lock_file: &Path)` (now `instance.rs:229` joins inside) · daemon `mcp_config::*(data_dir, …)` → `(mcp_dir, …)` (`mcp_config.rs:48-52,186-187`) · base `logging::init_logging_with_file(data_dir, kind)` → `(logs_dir, kind)` (`logging/mod.rs:87,355`). The discovery public functions (`ensure_daemon`·`daemon_status`·`read_live_daemon`·`daemon_stop`·`send_stop`) **keep taking root as they do** and use `DataLayout` inside — the shell call sites (`commands/discovery.rs` · `daemon_client/mod.rs` · `tray/`) are not touched.
- **Platform-neutral:** the OS split stays only inside `default_data_dir`, as now. `DataLayout` is only `Path::join`. `webview_dir()` is computed on every OS, and the writing side (§4) also passes it along without `#[cfg]` — whether that value is used is up to Tauri's platform implementation (`tauri-2.11.3/src/manager/webview.rs:534-545` — enforced only on Windows and Linux).

## 3. Daemon startup · old data · old shell files

### 3-1. Daemon startup order

The shell does not touch daemon files (an extension of `discovery/src/lib.rs:454-472` 「클라이언트는 daemon.json 을 지우지 않는다」).

The new order of `run()` (now `daemon/src/lib.rs:461-659`):

1. `layout = DataLayout::resolve()` → log (`layout.logs_dir()`).
2. `ensure_data_dir_writable(root)` → `layout.ensure_daemon_dirs()`.
3. **One lock** `acquire(layout.daemon_file())` — the current three branches as they are (`AlreadyRunning` = yield, exit 0 · `FileBusy`/`AccessDenied` = exit 1 · `lib.rs:498-532`). ★**If the earlier-started new daemon has not yet emitted its record (from lock acquisition until emission), the later one exits with `FileBusy`, not `AlreadyRunning`**★ — because the diagnostic read sees an empty file, and the same window exists today. So the `FileBusy` log wording is changed from 「중복 데몬 아님」 to **「다른 프로그램, 또는 아직 발행 전인 다른 데몬이 쥐고 있음」** (`daemon/src/lib.rs:512`).
4. Sweep of the new location (`mcp_config_dir()` · `usage_probe_dir()`) → wiring (`FileProfileStore::new(layout.daemon_state_dir())` etc. — now `:226-235`).

### 3-2. Old data — discarded, not moved (user decision 2026-10-02 · ADR-0264 decisions 5 · 6)

- **New code neither reads, nor moves, nor deletes the old files.** Targets = the flat files of release `<exe>\data\` (`agents.json` · `presets.json` · `usage_rejects.json` · root `daemon.json` · `mcp-config\` · `usage-probe\`) and the whole dev root `.engram-data\`. Rationale = the data is not yet settled (user decision).
- **What does not exist:** first-boot migration · completion marker (`.migrated-v1`) · moving in / preserving (`.legacy-*`) · handling of case variants · exclusion lock on the old root `daemon.json` · cleanup of the old run folder · discovery's two-location read (`pick`) · interpreting a 0-byte old lock · renaming `.engram-data` → `.engram-dev`. The dev root `.engram-dev` starts fresh.
- **There is one lock** (`daemon\run\daemon.json`). discovery and the scripts read only the one new location.
- **Old/new binaries:** they share no state, lock or token file, so they do not interfere with each other — they can even run together on the same root (each with its own registry), and the old data is not visible to the new binary (intended). Downgrading and mixed use are not supported. The only shared place is the top-level `logs\`.

## 4. Webview folder → `<root>\webview` (P4 — ✅ landed `11f8787` · decision = ADR-0283 · landing record = §14-21)

## 5. Settings (`shell\config\settings.json`)

### 5-1. Schema table [고름]

One line of the static table in `src-tauri/src/settings/registry.rs` = one setting:

```rust
SettingDef { key: "theme.default", kind: Kind::Choice(&["dark", "light", "e-ink"]), default: "dark",
             desc: "창별 덮어쓰기가 없는 창의 테마" },
SettingDef { key: "chat.style.fontSize",
             kind: Kind::CssLength { px: (8.0, 48.0), rem: Some((0.5, 3.0)) }, default: "13px",
             desc: "챗 기본 글자 크기" },
```

- **The `CssLength` range is declared separately per unit** — `px: (min, max)` is required, `rem: Option<(min, max)>` only when that key accepts rem·em (em has the same range as rem). A unit that is not declared is `INVALID_ARGUMENT`. If one numeric range is applied regardless of unit, `48rem` passes. Initial table: `fontSize` px 8–48 · rem 0.5–3 / the 8 margin·gap keys px 0–200 · rem 0–12.5 / `railLineOffset` px −200–200 · rem −12.5–12.5 (some keys have rem as the default — `chatStyleStore.ts:37-49` — so rem is not blocked).

- Key = lowercase namespace + dot (`theme.*` · `chat.style.*`). The last segment keeps the existing spelling (`chat.style.fontSize`).
- **12 initial keys:** `theme.default` + 11 of `chat.style.*` (`railRowPt` · `plainRowPt` · `userPy` · `userPx` · `userMy` · `railGutter` · `railLineOffset` · `railDotTop` · `fontSize` · `lineHeight` · `waitStripH` — the defaults are exactly `chatStyleStore.ts:37-49`). Only `lineHeight` is `CssNumber`, and `railLineOffset` allows negatives.
- **The source of truth for the defaults = this table.** The frontend `CHAT_STYLE_DEFAULTS` is dropped. The `--chat-*` fallback of `theme.css` (for the first paint) stays, and the current comment telling the two to be kept in line (`chatStyleStore.ts:35-36` — ADR-0051) is moved next to the table [고름 — U2]. The 3rd edition's 「표를 `settings_registry.json` 으로 내보내 vitest 가 대조」 was dropped — no new test apparatus is added to a temporary namespace.
- ★**`chat.style.*` is a temporary namespace (user decision 2026-10-02 · U2)**★ — the current 11 keys and defaults are carried over **as they are** and implemented lightly. The chat area will be split up and redone later, and in the end the chat layout will be freely composed with plugins, so these keys are due to be replaced. So polishing the chat schema (key names · grouping · range adjustment) is out of scope — the range table above is not touched beyond the generous three groups that the current values pass.
  - **Accepted cost (U2):** because the cross-check test was dropped, nothing verifies (a) that the `theme.css` fallback equals the defaults of the table, or (b) that the table's 11 keys equal the frontend `CSS_VAR_BY_KEY` (`chatStyleStore.ts:52`). If the key sets drift apart, `settings.set chat.style.X` answers `changed:true` while the screen shows no change at all.
  - **The way out is not on the command surface:** once these keys are removed from the table, the values left in the file cannot be erased with a command — the storage layer keeps unknown keys (§5-3), and `reset` of an unknown key is `NOT_FOUND` (§5-2). So the chat rewrite that drops these keys also takes on erasing them from the file.

### 5-2. Wire contract — values are always canonical strings [고름 · F1]

| Kind | Accepted input | Canonical form (the value carried by get · set answers · notifications) | JSON written to the file |
|---|---|---|---|
| `Choice` | An option word, case-insensitive | Exactly the spelling in the table (`e-ink`) | String |
| `CssLength` | Surrounding whitespace allowed · a number + the unit that key declares (case-insensitive) · within that unit's range | Shortest decimal + lowercase unit (`15px` · `0.9rem` · `-1rem`), no `+` | String |
| `CssNumber` | A number without a unit | Shortest decimal (`1.45`) | String |
| `Bool` (future) | `true`/`false`, case-insensitive | `true`/`false` | bool |
| `Int` (future) | Decimal integer | Decimal integer | Number |

- **Errors:** unknown key = `NOT_FOUND` · format or range violation = `INVALID_ARGUMENT` (the expected format goes in the message) · disk write failure = `INTERNAL` (memory · `rev` unchanged · no notification).
- **Whether to write is decided by the disk, `changed` by the effective value** — if the effective value is the same as now, it is `changed:false` · `rev` as is · no notification, but if the file differs from the target (a value fixed outside · an unusable value folded away · a non-canonical spelling), only the file is corrected and written. If the effective value changes but the file already matches the target, nothing is written and only `changed:true` · the notification is emitted. If the file cannot be read (a read IO failure · a file that is unusable as a whole), it writes only when the effective value changes (on a read IO failure that write is `INTERNAL`). Receiving a value equal to the default erases that key from the file (「바꾼 것만」). `reset` uses the same decision — if the file has even one key of the selector, it is erased and rewritten, and only the keys whose effective value changed get a notification.
- **One call = one file.** Today every key is in `settings.json`, so this holds automatically. A `reset` whose prefix spans two files in the future is rejected with `INVALID_ARGUMENT` (no partial-failure semantics is created).
- Why a value is carried as one string: the declaration macro's type alphabet has no arbitrary JSON (`command/src/macros.rs:37-47`).

### 5-3. Storage layer — the only place that knows the file [고름]

- Only `settings/store.rs` knows the file name and location. **No path-branching function is added for now** — all keys go to one file. When another file becomes necessary, the split happens only inside this module, so the call sites need no change.
- The file = a flat dotted-key object + a reserved key: `{"$version":1, "theme.default":"light"}`.
- **Write = read-modify-write (RMW), under the write-serialization lock (`io`).** Each time the file is re-read and only the received key is changed — other keys fixed outside the app and unknown keys are not erased (not reflected while running · read at the next boot). **If the file is missing or unusable as a whole, a new file is rebuilt from all the effective overrides in memory** — otherwise a single write would erase from disk another value still visible on screen.
- **Three locks — order = `io` → notification order (`announce`) → state (`state`).** `io` is held during the RMW and `sync_all`. `state` (memory values · `rev`) is a leaf, and reads (`get` · effective value · theme push) take only this one, so they do not queue behind the disk wait of a write in progress. Commit (issuing `rev`) and notification (`events.changed`) are one unit under `announce`, so notification order = `rev` order, and by then `io` has already been released. The theme push (§5-6) is called without holding any of the settings locks.
- Atomic write = temporary name (`settings.json.tmp<pid>.<n>` — `<n>` is a number that grows by one on each call across the whole process, so temporary names within the same process do not collide · ★what `io` prevents is not a temporary-name collision but a lost update between overlapping RMWs★) → `sync_all` → rename (the same way as the daemon `persistence/mod.rs:57-85` · the old `ui_settings.rs:687` (deleted in P3d — line numbers are based on `git show c93e664:src-tauri/src/ui_settings.rs`) — `write_atomic` was moved to the shell-shared `fsutil.rs` so settings and state write with it together · in P3a the set-aside copy was also moved to `fsutil::copy_aside` — settings and state call the same function, and the caller emits the log, §6-2). If rename fails with access denied · sharing violation · lock violation (Windows 5 · 32 · 33), it retries up to 5 times at 20 ms intervals (when an antivirus or indexer holds it briefly). `ReplaceFileW` is not used (§12 R7). **If the text to write exceeds 64 KiB (the read limit), nothing is written and `INTERNAL`** — writing text over the limit would make the next load fold the whole file as unusable.
- **Tolerance per item:** an unknown key = ignored but left in the file as it is · an unusable value for a known key = folded to the default with a warn, and left as it is in the file until overwritten · read size limit 64 KiB (`read_capped` reused) · a leading UTF-8 BOM is ignored (Notepad · PowerShell add it) · `$version` must be the number 1 (`1.0` is also 1 · if missing it is taken as 1).
- **A file that is unusable as a whole** (not JSON · not an object · over the limit · not UTF-8 · unknown `$version`): memory gets the defaults, **and the load does not touch the file.** The first write on top of it **sets the original aside** under **one fixed name `settings.json.corrupt`** and then atomically swaps that place — there is no moment when the file is missing. If it breaks again later, **that copy is overwritten.** There is no size limit · no duplicate skipping · no time/number names (user decision F21 2026-10-02 — Chromium `Preferences.bad` · Firefox `Invalidprefs.js` practice · ADR-0274). The copy is streamed into a temporary file in the same folder and swapped in by rename after `sync_all` — a half-written copy never overwrites the previous copy (`fsutil::copy_atomic` · if opening the original is also locked, it retries by the same rule as rename). If setting aside fails, that write is `INTERNAL` and both the original and the previous copy stay as they were. Reverses ADR-0166 decision 9 「`.corrupt` 없음」 → ADR-0265 · name · overwrite rule → ADR-0274 (partly discards ADR-0265 decision 4). ★A read IO failure itself is not in this group★ — so as not to overwrite a sound file that was briefly locked, the write fails then (§5-2).
- **Deleting the file while running is not a reset (session default — §10 F20).** If the file is missing, the write rebuilds it from memory, so the next call that writes the file revives it with exactly the values visible on screen. On the other hand, a key deleted by hand from a sound file is not revived — that edit wins at the next boot.
- **Service lifetime:** before the build it is loaded **read-only** and managed (it exists before the webview's first invoke — ADR-0102). The load runs before the logger, so it does not log but collects the logs, and `enable_writes` of `setup` turns writing on and emits those logs once at the level they had at load time. Writing comes only after that (a write before that = `INTERNAL`). The file on first boot does not exist — it is not filled from the old `ui-settings.json` (§3-5).

### 6-3. Window identity · where window properties live

- **Persistent identity = the window id** (`main` · `agent-tree` fixed · pop-out = a UUID drawn when the window is first created, `WindowTabs.window_id`). **The runtime label is an identity only within one boot** — a restored pop-out, whether at boot or at runtime acceptance, gets a **new label** from `PopupCounter` (`popout.rs:47`, based on `f9db35a`). That way a runtime restore does not collide with the label of a pop-out that is up now.
- **Per-window theme and position live in the `WindowTabs.attrs` bundle** (`WindowAttrs` — `theme: Option<UiTheme>` (`None` = follows the global theme) · `bounds: Option<WindowBounds>` (the last normal position · `None` = not seen yet) · `maximized`). They die together with the window entry, and there is one lock, `ViewManager`. The misapplication that ADR-0167 warned about (placing a value outside the window under a label key) disappears structurally. The only way to change them is through a setter (`set_window_theme` · `observe_window_placement` — this is a convention: the field is `pub`, so the compiler does not stop it). The setter raises **`attrs_rev`** **only when the value changed**, not `bump_version` (`manager.rs:565`, based on `f9db35a` — the layout number by which the frontend filters stale notifications) — so the layout number does not jump every time a window is dragged, and the writer watches both (§6-4). ★`attrs_rev` is a private field of `ViewManager` (read = `attrs_rev()`)★ — if `attrs` is edited directly from outside, the number does not rise and the writer misses that change.
- **The tree window (`agent-tree`) is outside the model** (`manager.rs` header 「`agent-tree` 창은 이 모델 밖」). So `TreeAttrs` of `state/tree_attrs.rs` carries it separately — the field uses `WindowAttrs` but ★**carries only theme · position (F9 (a) — session judgment (delegated by the user) 2026-10-03)**★: the maximized marker is always lowered after `set` and the position record (putting maximize on a hidden window makes the window visible — tao's maximize = `SW_MAXIMIZE`), and visibility is not restored (it comes up hidden at every boot). It has its own lock (a leaf — while holding it, no other lock is taken and no OS call is made) and its own change number, and when the field is swapped wholesale (boot fill · runtime acceptance) it also raises the number with `TreeAttrs::set` — it neither reverts nor resets it. `window.setTheme` goes here if it is `agent-tree`, and anything else goes to `WindowTabs` (✅ P3d — the place that splits = `EffectiveThemes::set_window_theme` of `theme.rs` · until then `TreeAttrs::set_theme` had no caller). ★There is no `TreeAttrs` · `state/tree_attrs.rs` · `window.setTheme` rejects `agent-tree` as an unknown window★ (tree window removed by ADR-0225 — 2026-10-08)
- **Position · size recording:** `bounds` is updated from `WindowEvent::Moved/Resized` **only when the window is neither minimized nor maximized** — ★**position = physical outer position (`outer_position` as it is) · size = the logical inner size divided by the window's scale factor**★. If the position were logical, when monitors with different scale factors are mixed (150% to the right of 100% — the logical x 1280..1920 band), one value would point at two monitors and restore onto the other monitor. Writing the position as physical is the same as tauri-plugin-window-state (that plugin writes the size as physical too). Whether to discard is decided in physical space — for each monitor, it checks whether the stored position · the rectangle of logical size × that monitor's scale factor overlaps that monitor. Restore places the position first and the size after (so the size is resolved with the scale factor of the monitor it arrived on — source of truth = `state/placement.rs`). Whether it is maximized is kept separately in `maximized` — restore builds it at the last normal size and then maximizes. **The tree window does not carry maximize** (F9 — theme · position only). ★**A one-entry memo for reverting the read just before maximize (`PlacementMemo` — it lives with the window entry · the tree field and is not persisted)**★: when the user maximizes, tao emits `Moved` before the maximized marker is raised, so the maximized rectangle is written once as the normal position — only **when** the position the previous read wrote as normal is **the same as** the position read now (maximized), that read is reverted (the same idea as tauri-plugin-window-state pushing aside the previous position at every `Moved` · dropping the 「같은 자리」 condition would discard the real normal read before it — source of truth = `WindowAttrs::observe`). **The first position of an opened window** is written once after that window is in the model (`WindowHost::record_placement` — a window that was never dragged is also opened at that position at the next boot). Events for a label not in the model (one arriving late after closing · a new window before it enters the model) are discarded — pop-out labels are not reused, so they are not written to another window by mistake. ★**Window getters (`outer_position` · `inner_size` · `scale_factor` · `is_minimized` · `is_maximized`) are all called before taking the `ViewManager` lock, and inside the lock only values are written**★ — no OS call while holding the layout lock (`layout/apply.rs` head 「락 규율」).
- **Lock order (explicit):** theme gate lock (§5-6) **›** settings state lock (`state`) · `ViewManager` lock · tree-field lock. The gate is outermost and the other three are **not taken overlapping each other** (one at a time, briefly, even under the gate). Even if the day comes when they must overlap, only the `ViewManager` → settings order is allowed, and taking the `ViewManager` lock while holding the settings lock is forbidden. The writer does not touch the disk while holding a lock (it releases after copying). ★There is no tree-field lock — the other two's rules as they are★ (tree window removed by ADR-0225 — 2026-10-08)

### 6-4. Saving — one writing side

- **One writer (`state/saver.rs`) thread** is the **only writer** of `state.json` after the boot phase (§6-5 ①–⑥ — one thread · before the writer) and the **only one that deletes** the copy `state.crash.json` [고름]. Other threads only send requests and wait for the answer. With one writing thread, no write lock or sequence comparison is needed.
- **Periodic save:** every 0.5 seconds it briefly reads `ViewManager.version` (+1 on each layout change · measurement reports do not raise it — `manager.rs:292,565,1101`, based on `f9db35a`) · `attrs_rev` (§6-3) · the tree-field change number, and if anything changed, at **1 second of quiet after the last change or 5 seconds after the first change**, it rewrites the snapshot **as a whole, atomically** (D2) — copy inside the lock → serialize outside the lock → `fsutil` atomic write (temporary `state.json.tmp<pid>.<n>` → `sync_all` → rename · retry on lock — §5-3). The writer starts with the change number at the boot first write (§6-5 ⑤) — what changed after that is carried by the first period.
- **Snapshot source = port `SnapshotSource`** — change number `revision()` · all windows `snapshot() -> Result<Vec<WindowEntry>, String>` (the file header is filled by the writer). **The change number is only checked for equality (magnitude is not compared) — it is neither reverted nor reset** (if it becomes equal to the last seen value again, the changes in between are not seen). **Port failure = a failed write** — log (error) · it comes up again after quiet (the same as a disk error) · the answer to `Resolve` / `Final` being processed at that time is `Failed`. Two things the port must keep (source of truth = the port documentation of `state/saver.rs`):
  - ★**It does not panic**★ — release is `panic = "abort"`, so a panic in the writer thread kills the whole app. A poisoned lock is revived or `Err` is returned.
  - ★**It does not wait for the thread that called `finish` · `resolve`**★ — that thread is standing and waiting for the answer. In particular, a Tauri window getter, when called off the main thread, stands until the main thread answers, and `finish` is called from `RunEvent::Exit` by exactly that main thread — then every normal exit would pass the deadline and be read as an abnormal exit. So position · size are written into the model in `WindowEvent` (§6-3 · P3b3) and **no window getter is called inside `snapshot()`.** The production source = `LiveSource` (`state/boot_plugin.rs` — after reading and releasing the tree field, it briefly takes the layout lock and `to_persisted` · if the layout lock is poisoned, `Err` — writing a half-changed model would make the next boot restore that shape).
- **Limit (I4) — if the codec rejects a write, nothing is written:** `EncodeError::TooLarge` (the serialized result exceeds 4 MiB — the read limit, §6-2) · `EncodeError::Unparsable` (it cannot be read again by the same parser — the cause that is reached is serde_json's nesting limit of 128 levels, and splitting the same slot repeatedly reaches it at 121 nested splits · the byte limit cannot catch this). The log · the request gets `Failed` (the command gets `INTERNAL`). Written as it is, the next boot would fold it as an unusable file. A rejected snapshot is treated as having seen that change number and **waits for the next change** — the same snapshot would be rejected again.
- **Variant that checks just before rename (I8):** `fsutil` gets a variant that takes 「rename 직전에 물어볼 함수」 — it asks **again before the first rename and at every lock retry**, and if it stands, it deletes the temporary file and returns **a separate 「건너뜀」** rather than `Err` (it is not a write failure — not a retry target). `write_atomic` becomes the thin wrapper of that. What it asks = `closed` below.
- **Two requests (channel + answer):** answer = `Written` (it emitted) · `Skipped` (it was after closing so it did not emit — not a failure) · `Failed` (snapshot source failure · codec rejection · disk error).
  - `Resolve { hash }` — attaches the answer (accept · reject) to the disk (I2 · §6-7). ★**The resolve field is raised when the writer takes the request out**★ — it is not raised with the sender's atomic value (I8): only a snapshot taken after taking it out carries the screen after that answer (the commit, if accepted). It writes a snapshot right away (carrying `resolved_crash_copy: hash`), answers with `Written` or `Failed`, and if rename succeeds it deletes the copy — ★**before every delete it re-reads the copy (≤4 MiB) and deletes only when its hash equals the field's hash (N1)**★: if different (a new copy made by a newly started instance) it does not delete and clears the field, and if it is absent it clears the field. This keeps a stale writer from deleting a new copy on a path that proceeded without the lock or in a 2-second-deadline race. If the delete fails, it leaves the field, **deletes again at every later successful write** (carrying the hash all the while), and when it is deleted it clears the field (no longer carrying the hash). Even if the write fails the field stays and the next successful write does the same.
  - `Final` → `clean_exit:true` writes the snapshot (if the resolve field is up, it carries the hash and also tries the delete again — the same hash recheck) and answers, then the thread ends.
  - **Withdrawn (6th edition):** `Flush` (the first write is done directly by the boot phase · the confirming write is `Resolve`) · `DropCrashCopy` (rejection also `Resolve`) · `Final{drop_crash_copy}` (D6 — a normal exit does not delete the copy).
- **Exit (`RunEvent::Exit`) = one deadline (2 seconds — constant `REPLY_DEADLINE` · `Resolve` is the same deadline · it must be shorter than the boot's lock wait of about 3 seconds (§6-5 ①)):** it sends `Final` and waits for the answer **until the same deadline**. If the deadline passes, it raises the `closed` marker (an atomic value) and returns — the writer's rename, where the variant above asks `closed` and it stands, returns 「건너뜀」 (no emission · the copy is not deleted either). The result is that the previous `clean_exit:false` remains and the next boot asks. Even if a trapped writer wakes up later, it cannot emit. When the wait ends, `state.lock` is released (§6-6).
- **Write failure = log only · not handled separately (user decision D8).** The next periodic save rewrites it as a whole. A failure of the run-marker write (§6-5 ⑤) is the same. **Failure logs are folded per branch (snapshot · codec · disk)** — it is left at its own level (snapshot · codec = error · disk = warn) only when the branch is first or changes, a repeat of the same branch is debug (since if disk errors continue it rewrites every second) · after a failure, one info line when it succeeds again. Rationale = [investigation](../../research/crash-session-snapshot-precedents-2026-10-02.md) 「덧붙임」 — Firefox · Chromium · VS Code · Windows Terminal all only log and keep running.

### 6-5. Boot — behind the single-instance gate · before any window

- **Fact ①:** the single-instance plugin ends the second instance with `std::process::exit(0)` in its own plugin setup during `.build()` (`tauri-plugin-single-instance-2.4.2/src/platform_impl/windows.rs:55-108`). Code that changes the disk must come after that.
- **Fact ② (basis of I1):** that plugin releases the mutex in `RunEvent::Exit` (same file `:111-123`). And the plugin's event handling runs **before** our `RunEvent::Exit` callback (`tauri-2.11.3/src/app.rs:1430-1432` → `on_event_loop_event` `:2644-2648`). So while the earlier instance writes `Final` (≤2 seconds), a new instance passes the gate. The basis the 4th edition cited (when the earlier instance's window cannot be found — `!hwnd.is_null()`) was narrow — once the mutex is released it does not even get to the window lookup.
- **Fact ③:** plugin setup runs in registration order inside `build()` (`tauri-2.11.3/src/plugin.rs:880-915` — `register` stacks them in registration order and `initialize_all` runs in that order · caller = `app.rs:2440`). The config windows (main · agent-tree) are created after that in `setup()` of `RunEvent::Ready`, **before** the user setup (`app.rs:2521-2531`). ★From P4 (`11f8787`) the two windows are `"create": false`, so Tauri does not create them and the user setup ⑧ does (§4) — the preceding sentence is the order for the config window that Tauri creates, and the place where this app's windows are first created now is ⑧★.
- **So the file work of boot is done in the setup of a small plugin (the boot phase) registered right after the single-instance plugin** [고름] — after the gate and before any window. `LayoutState` · the restore service is managed empty in the builder as now (ADR-0102 as it is — it exists before the first invoke), and the boot phase fills it before windows exist. ★Why the lock wait is not placed before the build★: that is before the gate, so when the earlier instance is up and healthy (re-running an app that is in the tray), every time it would wait for the lock and the hand-over would be 3 seconds late. ## 9. Phase plan — build·tests green at the end of every phase

### 9-1. Order · merge units

- **Settings (L2) before state (L3):** once state persistence comes in, the premise of the ADR-0167 boot sweep (「부팅 때 팝아웃 0개」) collapses. During L2 the per-window field still runs correctly with the old file + the sweep, and L3 turns off the sweep while changing the home of that field to state (old values are not handled — U1 · §3-5).
- **The webview (L4) goes last** — the 3rd edition's rationale (importing the chat style works only inside the old webview folder) went away with U1. From P2b nobody reads localStorage, so there is no ordering constraint, and the 3rd-edition order is kept as it is [고름].
- ★**Gate before P3 starts — `/review trd` re-review**★: reflects the 5th-edition re-review (designer BLOCK · designer-breaker FIX) and user decisions D4–D8 = **6th edition** (§14-10). The 6th-edition re-review (`/review trd full`) = designer (codex) PASS (plugin order confirmed from Tauri source) · designer-breaker FIX (N1–N8) → reflected → PASS · closing wording L1–L3 reflected — it was judged that no further review is needed (`ae3f6e7` · §14-11). **★Gate passed — P3a landed `41348d9` (§9-2)★**. ★The gate covers all of P3 — P3a's writer · `fsutil` variant are also tied to this design★. ~~The slot view mode (§6-0 ①–⑦ · F19) is also designed in the same place.~~ (P3e was dropped — user decision 2026-10-07 · §14-20) P2 is unrelated to this gate.
  - History: this gate was originally raised to confirm the source of the 4th edition's 「최근 3 개 회전 보관」 (F17) and rewrite the design. That confirmation collapsed the premise and F17 was withdrawn (§14-9).
- **P3 phase cutting (I7 · N8):** it is cut sequentially because of file overlap — state core + `fsutil` (P3a) → `manager.rs` side table (P3b1) → pure boot decision (P3b2) → `lib.rs` wiring (P3b3) → crash copy + a way to answer (P3c1 — Rust) → restore modal · key binding pause · state-file notice (P3c2 — frontend · the two fields of `restore.status` are Rust) → slot two states (P3c3) → per-window theme (P3d) → ~~view mode (P3e)~~ (dropped — user decision 2026-10-07 · §14-20). ★**Making the copy and the way to answer are the same phase (P3c1)**★ — it is satisfied once `restore.answer` stands on the bus (even before P3c2's modal it is answered with `engram restore.answer`). If split, a copy with no way to answer would stick to the dev data. So the abnormal exit of P3b2–P3b3 is 「기본 화면 · 사본 없음」 for a limited time (only inside L3 — it does not stand on master). P3a puts only one `mod state;` line in `lib.rs` (no wiring) — `lib_unit` compiles and runs that test (in P3c1 it became `pub mod state;` — the integration test `src-tauri/tests/layout_commands.rs` builds the restore coordinator). Each phase builds green on its own.
- **Merge units:** a phase is one coder's share and green every phase, but **the master merge is done only at the end of a unit** — L2 = P2a+P2b+P2c (commands and help go out together) · L3 = **P3a–P3d** (recording · restore · crash copy · per-window theme · sweep removal as one piece — ~~P3e view mode~~ was dropped (user decision 2026-10-07 · §14-20) — with P3d landed L3 is finished and is now being merged to master · a state with only recording and no reader, or restore done but the sweep remaining, does not stand on master). **All of L1–L4 go out as one release (v0.3.3).**
- Even inside a phase, **so that the build stands even if stopped midway**: put new modules·types in first without anyone using them and move the call sites one unit at a time. The order of overturning the data structure first and fitting the call sites later is forbidden.

- **Run marker = reuse of the 4th edition's `clean_exit`** (no new marker file) — it is already the same as the Chromium technique. **One thing fixed: the boot first write (`clean_exit:false`) was pulled before pop-out window creation** (§6-5 ③ — the 4th edition had it at the very end).
