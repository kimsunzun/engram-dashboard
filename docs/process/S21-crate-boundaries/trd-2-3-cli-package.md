- **★`mail send --body-stdin` reads stdin after the credentials (C1)★** — today `run` reads all of stdin first (`:419` `materialize_body(m, read_stdin_to_string)` · `read_stdin_to_string` `:1320-1326` = `read_to_end`) and then looks at the credentials (`:428-434`). If stdin stays open and never closes (agent shell · pipe), a call without credentials cannot fail and hangs — it never even reaches the common path. **New order = parsing (form) → credentials → stdin read (body form — empty stdin etc.) → network.** 「본문 오류는 네트워크 전에 끝난다」 (body errors end before the network) (`:418`) stays as it is. ★The error priority changes★ — with no credentials and an empty stdin, today it is `BAD_ARGS` (empty stdin), and after the change it is `NO_TOKEN` (both exit 1). There is no existing test that measures that combination (all stdin tests supply credentials — `engram_cli.rs:322-` · `:349-` · the `materialize_body` unit test is a pure function). Test +1 (`engram_cli.rs` — start `mail send --to bob --body-stdin` without credentials with stdin left open (neither written nor closed), and check that within a time limit (draft: 5 seconds · watched with `try_wait`) it ends with `NO_TOKEN` · exit 1 · if exceeded, kill it and fail).
- **One difference that is explicitly kept:** if the first round trip of a call (the list lookup) fails, after the common failure `note_catalog_failure` (`:1809-1816`) adds one line, 「그 명령은 불리지 않았다」 (that command was not called), to stderr — it is a diagnostic laid on top of the common path rather than a change to it, so it stays (it is attached to the 404 too).
- **★Known limitation — a mail-blocked credential on an old daemon + a new CLI (F5 ②)★:** the old daemon sees `/control/help` as a control path outside the list and folds it into the mail gate (`mail_gated_path` `:178-189` · test `tests/mail_gate.rs:400-427`). A mail-blocked credential (all of today's MCP branches) gets not a 404 but a 200 + `MAIL_NOT_ALLOWED` envelope (「This credential is not allowed to use mail」 — `mail_not_allowed` `:830-838`), and the CLI prints it as the daemon's rejection and exits 1 — the reason looks like the wrong thing. Only an open mail credential gets a 404 → the `PROTOCOL_MISMATCH` of 3 above. We did not choose the option where the CLI rereads it as 「help 에서 온 `MAIL_NOT_ALLOWED` 는 판 어긋남」 (a MAIL_NOT_ALLOWED coming from help is a version mismatch) — that would be the CLI rereading the meaning of a daemon rejection (semantic decisions are the daemon's alone — `engram.rs:103-105`), and that window stands only during development: in a deployment the daemon and the CLI are one folder · one build (ADR-0100). The condition for it to stand = only when engram.exe alone was rebuilt next to a long-running daemon (a running daemon exe is locked and cannot be overwritten). In U1 they are the same package, so `cargo build -p engram-dashboard-daemon` builds both together, and after U2 the launcher · qa build commands build both together (D6).
- **No help-only fallback · no embedded copy:** if the daemon is off, help fails like other commands. Grounds = a user decision — in that state every other command fails, so even if only help survived there is nothing it could do, and the priming already teaches 「`engram` 명령이 계속 실패하면 우회하지 말고 주인에게 알린다」 (if an engram command keeps failing, do not work around it — tell the owner) (1-6). The 「요란하게 죽어도 결과는 같다 — 표면 없이 떠난다」 (even if it dies loudly, the result is the same — it leaves without a surface) in ADR-0212 「거부한 대안」 (rejected alternatives) is the logic from when help could live apart from other commands.
  - **★But this ground is tied to the codex measurement (F4)★** — a codex app-server agent runs its shell in a workspace-write sandbox (`crates/engram-dashboard-agent/src/backend/codex/mod.rs:139` `SandboxMode::WorkspaceWrite`). Whether that sandbox blocks loopback HTTP has no measurement in this repository (`git grep` — 0 records). If it blocks, then for codex agents the CLI's daemon commands already all fail today and only help was alive locally — in that case D10 takes the mail-contract screen (`engram help mail` — the place the two MCP tool descriptions point at · `mcp_server.rs:419` · `:511`) away from codex agents that use mail through MCP. So the U1 QA measures that (§5-1 5), and if blocked, stops before landing and goes to the user.
- **Output channel = today's common envelope (main-session decision · closed during review round 1):** one line `{"status":"error","code","hint"}` on stdout + exit 1. Grounds = ① every command now follows the header contract `:72-78` (「CLI 가 스스로 내는 반려는 항상 stdout 봉투 · 기계 판정은 exit code」 (a rejection the CLI emits by itself is always a stdout envelope · machine decisions go by exit code)) ② tests measure that envelope (`engram_cli.rs:243-259` · `:713-718` · `:1644-1648`) ③ moving it to stderr would change the failure output of every command unrelated to help — outside the scope of this phase. We record in ADR-0284 that this differs from the 「stderr 로 보고」 (report on stderr) in the user's instruction wording — 「한 길 · 0 이 아닌 종료 · help 폴백 없음」 (one path · a nonzero exit · no help fallback) stands as it is. stderr is used, as now, only for diagnostic lines (malformed success · dropped list rows · the note above).
