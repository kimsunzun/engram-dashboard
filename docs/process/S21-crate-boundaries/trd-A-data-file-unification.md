## 0. Conclusion (first)

```
① 데이터 파일 넷(설정 · 상태 · agents · presets)의 읽기 규칙 · 원자 쓰기 · 손상 사본 · 「덮어도 되나」 판정을
     구현 하나로 모은다 — base 새 입주자 `file`. 셸 · agent · 데몬이 같은 함수를 부른다.
     파일 이름 · 자리 · 스키마 · 버전 키 이름은 각 주인이 쥔다.

② 「남이 잠깐 쥐었다」 판정 · 다시 하기 고리 · 폴더 동기화는 platform fs 다 — OS 규칙이라서다.
     base 는 platform 을 못 부르므로 부르는 쪽이 그 둘을 `file` 에 넘긴다(crate 마다 상수 — agent 만 둘).
     → 셸 fsutil.rs 의 cfg!(windows) 가 걷혀 platform 밖 운영 OS 분기가 0 이 된다(ADR-0275 결정 15 를 닫는다).

③ 새 판이 쓴 파일과 읽다 실패한 파일은 덮지도 떠 두지도 않는다 — 네 파일 공통. 판정은 저장 직전마다 다시 한다
     (주인의 모양 검사까지 — 모양이 깨진 파일은 어디서나 손상이다).
     → agent 의 「새 판 agents.json 을 빈 목록으로 덮는다」 결함이 닫힌다(같은 부류인 「읽기 실패 → 덮음」도).
     → agents · presets 가 그 상태면 읽기 전용 모드: 바꾸는 요청이 적용 전에 오류로 돌아오고 agent.list 가 그 상태를 싣는다.
     → 실행 중 바깥 편집은 지원하지 않는다(마지막 작성자가 이긴다 — 지금과 같다). 단 적재 때 없음 · 손상이던 파일이
        쓸 만해져 있으면 첫 저장이 덮기 전에 떠 둔다.

④ 덤으로 공용화 둘 — agent 자식 띄우기 세 벌(codex 의 가드를 셋 모두의 규칙으로 · ~~가드는 자식 트리째 끈다~~ → 가드는 직속 자식 · 후손은 무리 — §3-7 「U7 구현 개정」) ·
     셸 락 오염 복구 12곳과 상태 기록기 시계를 base 로.

⑤ 단위 열(U1~U4 · U5a · U5b · U6~U9) — 어느 단위 뒤에 멈춰도 빌드 · 회귀 초록.
     병렬 = 물결 1 U1 ∥ U8 · 물결 2 U2 ∥ U7 · 물결 4 U4 ∥ U5a ∥ U6.
```

## 3. Design

### 3-1. Home — decision: base new tenant `file` · the OS part is passed in by the caller

> **User decision (2026-10-10 — §1 5).** 「Base에 넣어야지. 나중에 쪼갤려면 base에서 쪼개야지.」 The 2nd edition's A (new crate) is withdrawn. The shape of what is passed in (`OsHooks` — §3-3) is a proposal of this TRD (draft).

There are four things to gather into one — (i) the lock decision, the retry loop, and folder sync (OS rule) · (ii) reading of version-tagged JSON (BOM · cap · version gate · decision — needs `serde_json`) · (iii) atomic write · copy · copy-aside · temp name · sweep (OS-independent machinery, but it calls (i)) · (iv) the 「덮어도 되나」 (may we overwrite) decision (pure rule).

**Chosen:** (i) = platform `fs` (§3-2) · (ii)~(iv) = base `file` (§3-3). Since base cannot call platform (tenancy condition ② — zero workspace dependencies), the IO functions of `file` **take (i) as an argument `OsHooks`** — one retry function, one folder-sync function. The operating value is a constant per crate (one each for the shell and the daemon · two for agent — the long budget for load reads, D7 · §3-4). Dependencies = std · `serde_json` (from U3).

- **Gain:** the whole rule (especially the 「거절」 (refusal) of R2 · R8) stands in one module of one crate — 「구현 하나 · 규칙 하나」 (one implementation · one rule) (1a · 1b) · no new crate · no new gate (workspace members stay at 11 · regression-result line increase 0) · OS rules live only in platform (1d · 1f) · it fits ADR-0269 decision 1 (base is the place that receives general-purpose code · splitting comes later from base) and decision 9 (bottom foundation layer — Chromium `//base` holds files and JSON).
- **Cost:** amends the first item of ADR-0269 decision 6 「지킬 것」 (base does not pull in serde · `file` handles bytes only) (new ADR) · base tenants become eight (gate ③ regex copies at six places · the CLAUDE.md count) · the four operating `OsHooks` (shell 1 · agent 2 · daemon 1) each wire platform in (the remaining cost of 「D 다시 보기」 below).

**Checking against the three base tenancy conditions** (canonical = the `crates/engram-dashboard-base/src/lib.rs` header 「입주 조건 셋」):

1. **It is used in, or copied to, several places now** — three atomic writes (shell fsutil · two in agent) · two shapes of corrupt copy · four read rules (§2-1). Met.
2. **Zero domain knowledge · zero workspace dependencies** — `file` knows nothing of the agent runtime · the wire contract · daemon lifecycle management. What it knows is two name shapes (`<이름>.tmp<pid>.<번호>` · `<이름>.corrupt`) and the version-gate rule (the key name is an argument) — these are rules of file handling, not domain, and the file name · place · schema stay with the owner (the placement canon of ADR-0264 also stays as it is). It does not call platform — this condition is the reason `OsHooks` exists, and gate ① (dependency cap) guards it. ★There is no OS operating code either★ (base header 「OS 에 따라 달라지는 운영 코드는 여기가 아니다」 (OS-dependent operating code does not belong here)) — the runtime OS split for folder sync went to platform `sync_dir` (R10). Met.
3. **No references between tenants** — `file` does not call `time` (ADR-0274 removed the timestamp name — fixed `.corrupt`) · `sync` (no lock — the temp number is an atomic integer) · `writable` (write probe — it stands on its own) · `logging` (it emits no logs) · `text` (fnv1a goes to the shell `codec` — it does not come to base) · `path` · `testing`. No other tenant calls `file` either. **No violation.** Two cautions — ① if `file` is split into submodules, inside them do not call it as `crate::file::…` but as `super::` (gate ③ false-positives that form as a sibling reference — base header 「알려진 한계」 (known limitations)) ② the tests of `file` do not call `crate::testing` either (the current fsutil tests use only std — measured).

**Revisiting D (D 다시 보기) — the two reasons the 2nd edition rejected this shape, and now:**

1. **「base 에 어차피 `serde_json` 이 든다」 (serde_json is in base anyway)** — the 2nd edition counted this as a cost of violating ADR-0269 decision 6 「지킬 것」 (do not bring in heavy dependencies — base does not pull in serde) (the 2nd edition cited it wrongly as 「결정 2」). → The user amends that 「지킬 것」 (§1 5). The weight is also small by measurement — the three that call base as an operating dependency (shell · agent · daemon) already pull in `serde_json` (`cargo tree --locked -i engram-dashboard-base` and each `-p … -e normal`, 2026-10-10), so `Cargo.lock` new packages are 0. What comes in is `serde_json` only (the read decision looks at `Value`), not the `serde` derive · ts-rs — struct ↔ JSON serialization is still done by the owner. The path of ADR-0269 「영향」 — splitting by feature flag if base gets heavy — also stays open.
2. **「부를 때마다 platform 재시도를 들고 와야 하는 이음매는 의존을 피하려고만 생긴다」 (a seam that must bring a platform retry on every call exists only to avoid a dependency)** — both were overreach.
   - It is not 「부를 때마다」 (at every call) — the seam is a single `OsHooks` value and ends as a constant per crate (shell · agent · daemon = three — agent alone gets one more for load reads, D7). The owner only passes that constant.
   - It is not 「의존을 피하려고만」 (only to avoid a dependency) — (a) this repository already has the same shape: the shell `sweep_temps` takes platform's PID liveness decision as an argument (`state/boot.rs:105-110`). (b) That seam is the test seam as it is: the base `file` test measures a path like 「재시도 도중 skip」 (skip in the middle of a retry) with a fake retry (injects locks without sleeping · counts attempts) without a real OS lock — this is what fsutil does today with the `pause` closure (ADR-0012). A fake that holds state is passed not through the public `OsHooks` (fn pointer) but through a private seam inside base (closure argument) (§3-3 · D15).
   - **Remaining cost (honestly):** because the four operating `OsHooks` each wire platform in, it still compiles if a retry that does nothing is passed → one 「운영 `OsHooks` 의 재시도가 잠김 오류를 실제로 다시 한다」 (the operating hooks' retry really retries on a lock error) test per crate (§5-2). Because the retry function is a `fn` pointer, the value type of the attempt must be erased (the value is put in `Option` and taken out — §3-3).
   - So we choose D. The basis on which ADR-0266 decision 8 sent atomic write to platform (one line of OS branching inside the function) also disappears in this shape — that line drops into platform `is_busy` and base only receives its result.

**Rejected alternatives (material for the 「거부한 대안」 of the new ADR):**

- **A — new crate `engram-dashboard-datafile` (the 2nd edition's decision).** Rejected = user decision (2026-10-10 — 「Base에 넣어야지. 나중에 쪼갤려면 base에서 쪼개야지.」). It amounted to doing first, here, the 「목적별 작은 crate 를 지금 나눈다」 (splitting small purpose-specific crates now) that ADR-0269 decision 1 deferred. The cost the 2nd edition counted (workspace members 11 → 12 · four registration gates · result lines +2) also disappears.
- **B — split it across the existing two.** (iii) goes to platform `fs` (widening ADR-0266 decision 8 to that family) · (ii) · (iv) to base `file`. Rejected = **ADR-0266 decision 2 (platform's criterion = whether it depends on the OS)** — (iii) is OS-independent machinery (atomic write · copy · copy-aside · temp name · sweep — the one line of lock decision inside it, the OS part, has already dropped into platform as `is_busy` · §3-2). ★Main decision (delegated) 2026-10-10 · provisional — awaiting user confirmation (review round 2 D12)★: the two reasons the 3rd edition also cited (「`.corrupt` 이름은 도메인 지식이다」 (the .corrupt name is domain knowledge) · 「부르는 쪽이 두 crate 를 각자 잇는다」 (the caller wires the two crates each)) were dropped — they conflicted with the basis for choosing base (condition ②'s 「이름 꼴 둘은 파일 다루기의 규칙이지 도메인이 아니다」 (the two name shapes are rules of file handling, not domain) · the caller passes `OsHooks` in).
- **C — everything in platform + allow `serde_json`.** Rejected = platform's third-party rule (`windows` · `tracing` only — that crate's header 「의존」 (dependency)) breaks and JSON policy enters the OS layer.
- **D′ — pass only the decision function (`is_busy`) and base `file` holds the retry loop and the budget.** Rejected = platform `retry_busy` remains for the part of scratch (U6) · net (transport 3-3), so there would be two loops, and it violates 1d (「잠깐 쥐어졌다」 (briefly held) retry = one platform policy).

### 3-2. platform `fs` — lock decision · retry · folder sync (draft)

```rust
/// 남이 잠깐 쥐어서 난 실패인가 — 지금 fsutil `is_lock_contention` 의 뜻 그대로:
/// ErrorKind::PermissionDenied(모든 OS · Windows 원시 5 포함) · Windows 원시 32(공유 위반) · 33(잠금 위반).
pub fn is_busy(e: &io::Error) -> bool;

/// 첫 시도 + `retries` 번. 값은 부르는 쪽이 정한다(도메인 값은 인자로 — 들이는 규칙 1).
#[derive(Clone, Copy, Debug)]
pub struct Retry { pub retries: u32, pub pause: Duration }

/// `attempt` 를 한 번 하고, `is_busy` 면 `pause` 뒤 `retries` 번까지 다시. 잠김 아닌 오류 · 성공은 바로 돌려준다.
/// 마지막 시도 뒤에는 자지 않는다. 한도를 넘으면 마지막 잠김 오류 그대로. 로그 없음(들이는 규칙 4).
pub fn retry_busy<T>(retry: Retry, attempt: impl FnMut() -> io::Result<T>) -> io::Result<T>;
/// 기다리기를 받는 판 — 부르는 쪽 시험이 실제로 자지 않게(지금 fsutil 시험의 이음매).
pub fn retry_busy_with<T>(retry: Retry, attempt: impl FnMut() -> io::Result<T>, pause: impl FnMut(Duration)) -> io::Result<T>;

/// 폴더 안 이름 바꾸기(rename)를 영속시킨다 — POSIX = 폴더를 열어 `sync_all` · Windows = 명시 무동작(`Ok`).
pub fn sync_dir(dir: &Path) -> io::Result<()>;
```

- The OS split of `sync_dir` is placed inside platform as `#[cfg]` — the 2nd edition's R10 put that split — 「std `File::open` 이 Windows 에서 폴더를 못 연다」 — as a **runtime OS split with no `cfg`**, and that is exactly the shape that the 「한계」 (limitation) of platform header gate ④ noted as meaning 「`cfg` 없이 런타임에 OS 를 가르는 자리는 못 본다 — 그런 규칙의 자리도 이 crate 다」 (review round 1). The Windows no-op is the same as the actual result of agent's best-effort today — behavior does not change and is made explicit.
- net `instance.rs` does not call this in A (follow-up of transport 3-3 — §3-6). Moving it then would not diverge in meaning from net's 「공유 위반만」 (only sharing violation) — net handles access denied (5) separately before putting it into the loop (one clearing of the read-only attribute · if it is an ACL, `AccessDenied` right away). - `ERROR_DIR_NOT_EMPTY` (145) is not included — we do not know with which code a scratch delete actually fails (§8-2 1 · U6 pilot).
- Tests: move to platform the two decision tests of fsutil (`fsutil.rs:392-431` — raw code · `cfg!(windows)` expectation — these two are the test branches that hold fsutil on the 4f list) and the three retry tests (`:358-391` · `:433-447`) · one `sync_dir` test (existing folder = `Ok` · missing folder = `Ok` on Windows / `NotFound` otherwise — a test branch whose expected value splits by OS is inside platform, so unrelated to 4f).

### 3-3. base `file` — data file rules (draft)

- **It emits no logs** — it returns values and the caller prints them with its own wording (same as fsutil · codec today).
- **The only names it knows are two shapes** — temp `<이름>.tmp<pid>.<번호>` · copy `<이름>.corrupt` (same as the current fsutil header). File name · place · schema · the tolerance 「항목 하나가 못 쓸 때」 (when a single item is unusable) · old names (like `agents.json.tmp`) are held by the owner.
- **A lock retry passes only through one path, `os.retry`** — open · read (if it gets locked while reading, open anew — `read_capped_retrying` today) · rename (asks `skip` first on every attempt — `replace_with` today) · opening the copy source. The value type of the attempt is put in `Option` and taken out — if the retry function returned `Ok` but there is no value (the attempt was not called), it is an `ErrorKind::Other` error (it does not panic).
- The reason both `classify` and `load` exist — the shell does IO behind a trait for test fakes (ADR-0012), and agent reads directly by path. The decision rule is one `classify` (today `codec::unusable_read` and the settings' `RawFile` make the same classification twice).
- **Consideration of `#[non_exhaustive]` (review round 3 polish · the decision = main at U3)** — `Parsed` · `Loaded` (and `WritePolicy` · `Refused` in the same position) are matched by three owners outside base (shell · agent · daemon). For branches where leaving a case out overwrites data, like the write decision, the latter is the safe side — U3's brief carries this trade-off.
- **The shape check lives in `Spec` (D1 — main decision (delegated) 2026-10-10 · provisional — awaiting user confirmation)** — the API has no bare decision that looks only at the version gate and answers 「쓸 수 있음」 (usable). Cost = one owner-struct deserialization per decision (within the cap) · at load the owner does it once more to obtain the value (because the check discards the value — the registry now is 1,747 B).
- **Private seam (D15 — main decision (delegated) 2026-10-10 · provisional — awaiting user confirmation)** — the public `OsHooks` stays an fn pointer (the operating value is a `const` per crate). - ★**Why a refusal at load must not clear for the whole run — a trap that re-decision alone cannot stop**★: the in-memory registry did not come from that file. The option of reloading during a run to clear it is not taken, because the registry would change during the run and the consistency with the screen · live sessions would need a separate design (§8-3).

## 4. What the user sees change

1. **Name and behavior of the corrupt copy of agents.json · presets.json** — `<이름>.corrupt-<ms>` (moved at load · accumulates) → `<이름>.corrupt` (copied just before the first save · overwritten). In between, the original stays in place and the same error log appears every time the daemon starts. A second corruption overwrites the first copy (user accepted). **An existing `.corrupt-<ms>` file is not touched** (neither moved nor deleted). Corruption includes a file that is malformed in shape, as it is today (for example, one unknown `kind` in a single entry) — load and the re-decision just before save use the same definition (D1).
2. **A file written by a newer version (common to all four files) is not overwritten**
   - Settings — start with defaults and changing a setting comes back as an error (the same path as today's 「읽기 실패」 — the bus error code is decided in U4; if it is the current path, `INTERNAL` · D13) · file and `.corrupt` untouched. Today the first write copies it aside and overwrites.
   - State — default screen · no state saving this run · new notice (4 below) · file untouched. Today it is copied aside to `state.json.corrupt` and overwritten (this reverses TRD S21-storage §6-5 · §12 R3 — §8-1 2).
   - agents · presets — empty list · ★**read-only**★: creating · deleting · renaming · moving agents and presets and waking an agent come back as errors (both bus and screen — how the screen shows that error is measured in U5b) · `agent.list` carries that state · ★it is released only by restarting the daemon★ (after fixing or removing the file) · file untouched. There is no on-screen notice (§8-3). Today the first save overwrites (a defect).
3. **If reading agents · presets fails (other than "missing"), the same read-only mode applies** — this also covers a file held at boot by something like antivirus and not released within about 1 second per file (R14 — the long budget for load reads · D7). Today it overwrites with an empty list and loses everything.
4. **On-screen notice · bus** — new value `newer` in `state_file` of `restore.status` (the LLM sees it through the same handle — CLAUDE.md 「LLM-우선 제어」 · help · command descriptions · generation 15 → 16) · shell binding · the value list in `src/api/restoreClient.ts` · `StateFileNotice` branch · `src/i18n/ko.ts` draft of the new wording 「화면 상태 파일(state.json)이 이 앱보다 새 버전이 쓴 것이라 기본 화면으로 시작했습니다. 이번 실행에서는 화면 상태를 저장하지 않으며 파일은 그대로 둡니다.」. The 「(손상 · 다른 버전의 형식 등)」 of the two existing messages (`ko.ts:268-273`) becomes 「(손상 · 알 수 없는 형식 등)」 (draft), because the newer version no longer arrives by that path. ★The wording here is a draft — main submits the final text to the user in U4 (§8-3)★.
5. **If a file changes while running, it is re-decided just before save (R16)** — if it becomes a newer version or unreadable while running: settings = same as today (read on every write) · state = that save is skipped (for a newer version, wait until the screen changes again · if unreadable, re-decide at the next debounce — D5) · agents · presets = that change comes back as an error and `agent.list` carries `refusing` (draft — D6) (the next request re-decides · an internal change with no caller stays in memory — 10 below · E1). Today it overwrites.
6. **A file without a version key** — state · agents · presets are also read as version 1 (today it is corrupt).
7. **agents · presets with a BOM are read** (today corrupt).
8. **A size cap on agents · presets** (16 MiB · 4 MiB) — exceeding it is corruption (today there is none). It is about ten thousand times the measured size, so a normal file never reaches it.
9. **Temp file name** — `agents.json.tmp` → `agents.json.tmp<pid>.<번호>` (only while writing · if the process dies, the next daemon start sweeps it, and deletes the old `.tmp` then too). A temp file also appears briefly in the mcp folder while writing.
10. **(Open — §8-3 · if we follow the recommendation)** If the write itself fails for agents · presets (disk full · lock budget exceeded), a change called by a person or the LLM (create · rename · wake and so on) comes back as an error — today it looks like a success and disappears on restart. ★An internal change with no caller is different (D2 · E1)★ — whether the write failed or this write was refused, it stays in memory as it does today, and the disk gets it at the next successful save (if refused, after the refusal is lifted) — if the daemon goes down in between, that change is lost (for example, the session id is not kept and the next activation starts a new conversation — the same ending as a failed save today). In read-only mode (load refused) the registry is empty, so no internal change arises. Boot restore also counts as internal, so it continues launching even when the save fails or is refused (today's operation does not call boot restore — §3-9).
11. **What is not visible** — lock retry on settings · agents · presets reads (worst case +100 ms · for agents · presets only the daemon-start load adds up to +1 second per file in the worst case — D7) · folder sync (explicit no-op on Windows — same result as today) · the state recorder recreates a folder deleted while running (R11) · a child that could not be put into the group fails the spawn instead of living outside the group, and its grandchildren are killed too (g — rare) · agents · presets save reads the file once more (usually negligible · while the file is locked, a registry lookup stalls up to about 0.4 seconds in the worst case — D4) · (h) has no behavior change.
12. **What does not change — editing from outside while running is not supported (C1 — main decision (delegated) 2026-10-10 · provisional — awaiting user confirmation)** — if you edit the four files by hand, or a sync tool changes them, while the daemon · app is running, the next save overwrites them (the last writer wins — same as today). To edit, shut down the daemon · app first. If that edit produces a newer version · an unreadable file · corruption, it goes down the paths of 2 · 5 · 1 above. Settings overlay only the changed keys, as today, so edits to other keys survive.
13. **If a file that was missing · corrupt at load has come back to life while running, the first save copies it aside to `.corrupt` before overwriting (D14 — main decision (delegated) 2026-10-10 · provisional — awaiting user confirmation)** — for example, if the daemon started with an empty registry and a person then put a backup agents.json back, the next change copies it to `agents.json.corrupt` and then writes (the contents are fine, but the name is the fixed `.corrupt` of ADR-0274 — the log tells them apart). To restore it, shut down the daemon and move that copy back into place. Today it overwrites without a copy. State is written by boot right after the decision, so this usually does not apply · settings do not apply (it overlays instead of overwriting).
