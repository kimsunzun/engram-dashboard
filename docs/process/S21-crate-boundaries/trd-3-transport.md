## 1. Context · scope

### 1-1. Why

- transport stands as an independent crate and has finished standalone verification, and it has zero consumers (transport TRD §10 「셸을 이 crate 위로 이사 = 붙이는 순서 ②」). The shell uses a hand-written WS client (`src-tauri/src/daemon_client/connection.rs` 2,073 lines + the synchronous stop client `stop.rs` 370 lines), and the daemon uses net's server layer (`crates/engram-dashboard-net/src/ws.rs` 2,248 lines). The same job (handshake · keepalive · reconnect · pairing) exists in three copies.
- net mixes three things — the daemon-only server layer · the auth frames the client also uses (`net/src/auth.rs:33`) · daemon lifecycle management (`instance.rs` · `portfile.rs`). Only a feature flag (`net/Cargo.toml` `server`) barely keeps the shell from knowing the daemon-side crate (memo §6 fact).
- `protocol` holds four of command's structs (`protocol/src/messages.rs:4`) — ADR-0272 decided to remove this and deferred the start to this stage (decision 7).

### 1-2. In scope

| Step | Content |
|---|---|
| 3-0 | transport reinforcement (D19) — per-peer lossless inboxes (including a byte budget) · lifecycle events · generation stamp · the sent field · drain before close · refusal classification · Debug masking · receiving-side seam · ws accept hardening (with zero consumers) |
| 3-1 | Execute ADR-0272 (four command fields = `Box<RawValue>` · `OwnerToken` disposal · move the pairing functions to the edge) · move `AuthFrame` into protocol · protocol zero-dependency gate · delete the shell's net dependency |
| 3-2 | Shell edge adapter (Wire · handshake · resolving Dialer · event mapping) · connection-info interface · move the stop command client onto transport · N peer places in the shell adapter |
| 3-3 | Daemon edge adapter · moving net's defenses and new defenses · `instance` · `portfile` to the daemon (open retry = platform `retry_busy`) · delete net · daemon identity (there is no daemon-to-daemon skeleton in stage 3 — D5 ③) |

### 1-3. Out of scope — later tracks (the places that §4 「빈 공간」 fills)

Remote Link (rustls key pinning · iroh · user VPN) · pairing · remote address discovery · daemon-to-daemon vocabulary · skeleton (identification · ping · mail relay · list merging — D5 ③ · the multi-daemon PRD decides it right next) · loop-back prevention · the shell screen / LLM choosing a daemon · per-command authorization policy · auth-failure rate limiting · screen sharing. The `daemon.json` ACL was raised to a decision from edition 1's 「연기」, and the edition-6 decision is D22 ② — stage 3 carries only 3-3 U2's `icacls` measurement + a known-limits record, and hardening goes to the multi-daemon · remote security design (D26 ②).

**Three things that break if the stream layer is turned on (certain — code reading):**
1. **The shell is a stateless pass-through router, so it receives the full replay of the same agent again for every window** (`replay_flight.rs:3-7`). If transport's 「`seq <= last` 면 버린다」 (transport TRD §4-3 1) ran in one place in the shell, the replay of a newly opened window would be discarded entirely.
2. **When it sees a gap, transport issues a Subscribe on its own with `resume_request`** (`wire.rs` `resume_request` doc) — this directly violates `replay_flight.rs:36-43` 「추적을 잃은 채 wire 로 나간 Subscribe 를 만드는 진입점을 두지 않는다 — 있으면 gen 펜스 붕괴」.
3. **The contract differs** — after the re-request, transport reports truncation once `resume_timeout` (2 seconds — `policy.rs:208`) has passed and releases what it held · the frontend holds what is behind a gap 「시한 없이」 (CLAUDE.md 「replay→live」).

★「sink 와 셸 중계는 seq 를 건너뛰지 않는다」 (CLAUDE.md 「핵심 불변식」) is the only place that transport's lossy shared queue could newly break★ — edition 2 does not patch it with reattachment but removes the loss itself (R1).

## 3. Seams to fix now (proposal · cost · recommendation — edition 6: all decided, adoption marked)

### 3-0. transport reinforcement — what to fix before attaching (D19 · D11 · D20 · D24 — added in edition 2 · rewritten in edition 3 · edition 4 · edition 5 fixed ① ② ⑤)

Edition 1 judged that the transport surface would be used almost as it is. We confirmed in code the five that the review pointed out (static reading) and none of them can be patched in an adapter — loss and order are already decided inside the crate.

① **Receiving queue — loss, and the daemon's receiving-side structure (A1 · D11 — edition 4 added ②′).**

Fact (loss — as in edition 2): the supervisor `try_send` both messages and events into one shared queue and only counts when it is full (`peer.rs:1224-1256`). The outcome of edition 1's countermeasure (`Dropped` → `reconnect_now`) = the shell replay loop (`ReconnectNow` rewinds the budget to 0 — `machine.rs:272-292`) · starvation among daemons (what `registry.rs:6-9` tried to prevent) · unanswered loss on the daemon side (net `frame_port.rs:195-199` duty 2) · reporting delay (`flush_drop_reports` only when the supervisor wakes).

Fact (the daemon's receiving side): per connection, net has ⓐ an arrival-order lane of 64 entries + 16 MiB ⓑ the **single consumer** `dispatch_task` of that queue (arrival order · no overlap — the real thing behind the upper layer's ordering invariant, `ws.rs:791-829`) ⓒ `bypass_task` that **run overlapped** (cancel family · 8 entries — 「같은 task 의 select 로 합칠 수 없다」 `:829-833`) ⓓ even when the arrival-order lane fills, it does not stop reading and asks the upper layer for the disposal — `Refused` (the reply has already been put in) · `Unanswered` (even the reply could not be put in → the connection ends) · `Bypass` (`frame_port.rs:90-112` · `agent_conn.rs:405-445` · 「차면 읽기가 기다린다」 is the rejected design `ws.rs:62-66`) ⓔ ★that hook runs synchronously inside that connection's read task — it parses one frame up to 16 MiB (`agent_conn.rs:411`)★ ⓕ ★when the priority lane is full, the read **waits** (`ws.rs:782` · basis `CONN_BYPASS_CAP` doc `:98-108`) — that wait stops only that connection's socket read and becomes TCP backpressure★ ⓖ the priority lane is drained at cleanup (`finish_bypass_lane :877`). ADR-0206 decided 「느린 활성화(전형 2.2 s · 상한 15 s)가 다른 명령을 막지 않는다」 with this structure.

Options (D11) — designs the earlier editions rejected: the edition-2 design (merge the per-peer queues into one `Inbound::recv` — `registry.rs:28` 「명부 하나당 하나뿐」 — and transport hook `Wait | Refuse | Bypass`: head blocking between peers · `Bypass` also behind a blocked consumer · hooks before `Connected` · `Wait` stops the supervisor's read so replies cannot get through · false `LinkLost(Idle)` (`peer.rs:826` · `:897-908`) · 16 MiB cannot be measured by count) · awaiting on the shared queue (one peer blocks everyone) · edition 1 (lossy + reattachment).
- ① **(a) per-peer inboxes + a transport hook** (not adopted) — `attach` · `add` return a per-peer inbox + a priority inbox, and the daemon keeps per-connection dispatch · bypass tasks as now. The hook receives a reply handle and returns `Refused | Unanswered | Bypass` · transport also measures the byte budget. Cost: net's semantics (hook · priority lane · budget · cleanup grace period) come into the crate · the 「지금 확정」 surface changes the most (R9).
- ② **(b) a shared delivery task across peers (the edition-3 recommendation — edition 4 recommends rejecting it · not adopted)** — transport only provides a merged lossless queue + backpressure · the daemon's shared delivery task splits what it received into per-connection queues, calls the hook, and never awaits. What breaks: ⓐ the hook runs synchronously in the shared task (16 MiB parse), so a burst of large frames from one peer delays delivery for every peer (weak head blocking) ⓑ when delivery falls behind, that peer's transport queue fills and the socket read stops, and a `Kill` arriving later cannot reach the priority lane ⓒ the bytes in the transport queue are outside net's 16 MiB budget (count only — 512 × 16 MiB ≈ 8 GiB in theory) ⓓ the shared task cannot wait, so net's 「우선 줄 참 → 기다린다」 turns into `Unanswered` → close — if the user presses `Kill` repeatedly during the 5 s kill-join (priority lane of 8 entries), the shell closes.
- **②′ (introduced in edition 4 · recommended · ★adopted — user 2026-10-31★) per-peer inboxes · no hook · net `read_task` per connection as is** — transport returns a lossless inbox for each peer (D24 ② surface · no hook · when full only that peer's socket read stops). The daemon `link/server.rs` moves net's `read_task` per connection **as is** and reads that inbox instead of the socket stream — the per-connection queue · byte budget · hook · `dispatch_task` · `bypass_task` · `finish_bypass_lane` are also unchanged (what is removed is only keepalive refresh `last_recv` · Ping/Pong · the Close branch, which are the transport supervisor's job). The wait of `bypass_tx.send().await` stops only that connection's read as now, and that becomes TCP backpressure through transport's lossless queue — ADR-0206 disposal unchanged · no synchronous hook shared between peers · the surface is narrower than ① (the hook · priority inbox · disposal are outside the crate). ★The transport byte budget is one count (3-0 U1 · edition 5)★ — `read_link` adds when it puts into the read-ahead queue (`frames_rx` — count only · default 512 `policy.rs:169` · `:203`) and the consumer subtracts when it takes out of the inbox. One count covers the three layers: read-ahead queue · ordering area · inbox — if only the inbox is measured as in edition 4, `read_link` keeps reading until the read-ahead queue fills (`peer.rs:595-597` · `:1409-1425`), so even under ②′ it holds 512 × 16 MiB ≈ 8 GiB per connection. The decision is 「더하기 전 물높이」 (net `CONN_RX_MAX_BYTES` rule) — if the count minus the resume window share is at or above the read share, `read_link` does not do the next read (socket backpressure). ★Read share (landed — 3-0 U1c `92096d19`)★ = while no stream piece has been seen, all of B (window cap 0 — the two Wires are `stream_mark = None`, so they are always on this side · ADR-0310 decision 16) · from the first stream piece, read B/2 + a cap of B/2 for the window share held behind a gap (so that a held piece does not block the read of the replay that will fill its own gap · a piece that would exceed the window cap is not held, and that window is closed as truncation) — the two sum to B, so the ceiling below is unchanged (`budget.rs` header). ★The transport-layer cap of one connection = B + M★ (M = the cap of one message, 16 MiB — one piece held just before the fill level or one being assembled) · provisional B = 16 MiB (same for shell and daemon · ★landed 3-0 U1c `92096d19` — the provisional value as is `peer.rs` `BYTE_BUDGET = 16 << 20`★) · the count cap (provisional shell 512 · daemon accepted peer 16) stays for floods of small frames · lifecycle events are 0 bytes · on the daemon, net's layer (arrival-order lane · priority lane · the one being processed — values as now) sits on top of it · the values are internal constants that main decides and reports. Rejected design = `frame_buffer` 1~2 for the accepted peer only (the shell side's read-ahead 512 × M would remain and the count would become two). Cost: one more buffer layer (transport) — its cap is B + M · the number of tasks per connection is the same as net (read · dispatch · bypass).
- **Recommendation history: edition 2 ① → edition 3 ② → edition 4 ②′ → edition 6 adopted ②′ (user 2026-10-31).** Reason: from net's per-connection machine, only the receiving place changes from socket to inbox, so the upper-layer contract (`frame_port.rs`) · disposal · cleanup grace period move over together with the tests (net `ws.rs` 22) (R2 minimum) · the only thing shared among peers is the transport supervisor, and the supervisor only puts into per-peer queues · transport carries only the general repair that the shell also needs (lossless · backpressure · byte budget · per-peer inboxes) · a disposal that knows upper-layer vocabulary does not enter the crate (the spirit of ADR-0177 decision 4).

**The shell's receiving shape (D24 — follows D11 · edition 4 · ★edition 6 adopted = ② — user 2026-10-31★):** ② per-peer inboxes (a consumer task per daemon — it only hands over to the Channel) — the transport surface of D11 ②′ is the per-peer inbox, so one surface fits · if a merged view is needed, the shell adapter merges the inboxes with select (transport surface unchanged) · ★every event of that key (lifecycle · message) is filtered — everything from a Peer that is not the current handle is discarded · an event carrying a generation is discarded if older than the current generation · `ConnectFailed` · `Rejected` · `GaveUp` without a generation pass if they belong to the current handle (the three rules of §3-3) — only the primary daemon's goes out to the frontend · the name ledger (edition 5 had lifecycle only — the edition-6 review widened it to messages · §3-3)★ · D4 ① stands on top of that. ★Landed (3-0 U1d-1 `098dad63`): inbox = `Inbox` — `Registry::add` · `add_with_policy` return `(Peer, Inbox)` and `Registry::new` returns only the registry · the shared `Inbound` was removed · re-raising the same name tag does not carry the queue over (one inbox = one supervisor)★. Not adopted = ① a merged `Inbound` (round-robin over the per-peer lossless queues · one consumer — the pair of D11 ②).

- ② `Registry::new(.., listeners)` — including the accept inside the crate. This is the signature change that transport TRD §12-7 foretold, and the cap · rate would have to enter as crate policy values.
- ③ The daemon runs the Link directly outside the Registry — violates ADR-0179 decision 3 (same registry · same supervisor).
- `Handshake::start(&self)` need not have a context argument — the receiving side builds a new handshake value at every attach, puts `LinkInfo` in it, and writes the `Principal` that `admit` emitted into that value too, **synchronously** (§3-4). The trait does not change.

### 3-2. Peer identity (D3)

- **Fact:** `PeerId` = an opaque string the consumer attaches (`transport/src/event.rs:19-23` — 「나중에 화면에 그대로 뜬다」) · the daemon has no persistent identity (`Hello` = version · capabilities only — `protocol/src/messages.rs:433-438` · `DaemonInfo` = pid · address · token — `protocol/src/discovery.rs`) · the token = a shared secret for anyone who can read the data folder (ADR-0179 impact 4).
- **① A persistent `DaemonId` + an appended field on `Hello` (recommended · adopted)** — create a UUID v4 once in the daemon state folder (daemon `DataLayout` owns the place) · `Hello{.., daemon_id: Option<String>}` (`#[serde(default)]` — compatible with old shells · `PROTOCOL_VERSION` as is · one field in the TS binding) · `PeerId` stays as a name tag (shell = the key of the connection info · a connection the daemon accepted = `conn-<ConnId>`) · the key will later be **bound to the identity** (identity ≠ key). Cost: one file in the data folder · if that file is broken or deleted, a new identity (base `file` rule) — ★the daemon then leaves a loud warning log (C4)★.
  - ★Rule (stage 3 now — D3 ① · ADR-0310 decision 4): `DaemonId` is a claimed · unverified id. Do not build persistent trust keyed on it (an allow list · a remembered daemon, etc.) — until it is bound to a key by pairing★. It stands from the commit in which 3-3 U7 builds `DaemonId` — the shell's `expected_daemon_id` cross-check (below) is only 「다르면 거절」, not 「같으면 더 믿는다」. The trust level of daemon-to-daemon connections (§3-3 「데몬끼리」) has moved to the multi-daemon PRD, but this rule does not move.
- ② Create a key pair now and fingerprint = identity — brings in a crypto dependency not used now, and a key rotation becomes an identity rotation.
- ③ Name tag only — there is no material for a shell to see the same daemon under two addresses or for daemons to point at each other.
- **Cross-check (addition 5):** the shell's `ShellHandshake` compares `Endpoint.expected_daemon_id` with `Hello.daemon_id` in Hello — if the expectation is `None` it does not look · if both exist and differ, `Reject{Terminal}` (「다른 데몬」 — popup text). The local implementation in stage 3 is always `None` (daemon.json is canonical and has no id field) → the cross-check stands only in in-memory tests. The field and the cross-check go into 3-3 U7 together with `Hello.daemon_id` (edition 1 put only the field in 3-2, so it was a dead field until U7).

### 3-3. Do we split the Wire per relationship (D2)

- **Fact:** `Wire` is a generic split into `Out`/`In` and `decode` has no peer argument (`wire.rs:20-60`) · `Registry<W>` is a single Wire · ★the shell↔daemon link is already bidirectional requests★ — to the daemon→shell `AgentEvent::CommandRequest{envelope}` (`messages.rs:608`) the shell answers with `AgentCommand::CommandOutcome{reply}` (`:333`), and that pair is carried by the daemon `command_delivery` with a deadline · place table (it is not the transport pending).
- **① Separate Wire · Registry · Listener per relationship (recommended · adopted)** — shell↔daemon = `ShellWire`/`DaemonWire` (current vocabulary) · daemon↔daemon = later `PeerWire` (new vocabulary — ★not built in stage 3: D5 ③ · the multi-daemon PRD decides the shape★). Each Wire is bidirectional within its own relationship. Cost: one registry per relationship · the real daemon-to-daemon Listener (second port · `daemon.json` field) is not in stage 3 (D5 ③ — one port). The day that relationship is added, shell↔daemon is not touched — this is the place D5 ③ leaves. For remote, bind addresses and TLS tend to differ per relationship, so splitting is the natural side.
- ② One union Wire + a role field in `AuthFrame` — if packet namespaces overlap, `decode` cannot tell them apart · the shell knows the daemon-to-daemon vocabulary as types.
- ③ One port + peeking at the first frame after accept to pick the Registry — needs a Link wrapper that puts the frame back so the handshake reads it again.

**DaemonWire shape (DaemonWire 모양) (B1 · B2 — main may decide, outside the D list):**
- Edition 1 made In = `AgentCommand` so that the Wire decodes. Then ① the upper-layer contract (`on_text(&str)` · `on_inbound_saturated(&str)` · `Frame::Text(String)` · `broadcast_text` — `net/src/frame_port.rs:79` · `:170` · `:203`) and 「위층 무변경」 contradict and ② the default decode-failure policy (`DropFrame`) silently drops three current behaviors — an Error reply to a broken command + keeping the connection (`agent_conn.rs:351-372` · `ws_e2e` case21 `:1447`) · 「already authenticated」 on a second Auth · Error + close on binary (`:384-389`) ③ the `AgentCommand` vocabulary comes into `link/` and the axis of net gate 4 disappears.
- **Proposal:** raw-text pass-through — In = `RawIn{Text(String) | Binary(Vec<u8>)}` (zero decode failures · carry the byte length together to continue `CONN_RX_MAX_BYTES` accounting) · decoding stays as now in `agent_conn` · `link/` receives the vocabulary only as a factory callback (net `handshake_error_frame` form — `frame_port.rs:241`) → edge vocabulary gate ② (§2-4).
- ★`DaemonWire::request_tag` · `reply_tag` is `None` for every input★ — if even one `reply_tag` is `Some` (e.g. the shell's `CommandOutcome`), `route()` cannot find it in the waiting table and swallows it as `UnmatchedReply` (`peer.rs:929-950`). With raw pass-through it holds by structure.
- ★Order change on the shell side (B2)★ — a reply whose `ShellWire::reply_tag` is `Some` skips the receiving queue and wakes the waiter directly (`peer.rs:938-942`). The shell's read loop now emits events and resolves replies in frame order — after attaching, an event that came just before a reply (e.g. a list update) may be seen by the upper layer later than the reply. Put a test in 3-2 U2 that measures that order, and find and write down the callers that depend on that order (not verified — not found even through edition 3). ★Landed (3-2 U2 C, 2026-11-04): the order is pinned by a test and the caller survey found no caller that breaks — §6-2 U2 C note★
- ★Hello first · fan-out registration (edition 3 · rewritten in edition 4)★ — the daemon handshake cannot end with Hello (after `Send` comes always `Await` — `peer.rs:1364-1375`) → Hello is put in by `on_connect` after Live. Edition 3's 「어댑터가 Hello 를 넣은 뒤 등록」 does not stand — `link/` does not know Hello (edge vocabulary gate ② — vocabulary only through the factory callback). In net, registration (`ws.rs:437`) comes before `on_connect` (`:447`), so fan-out can overtake Hello (the contract doc admits it). Spec (edition 4): wrap the `FrameSink` handed to `on_connect` and put the ConnId on the fan-out list **right after that connection's first frame enters the queue** (`agent_conn.rs:291-302` — first frame = Hello · next = the list snapshot) · if `on_connect` returns without putting anything in, put it on then · ★rule: registration is before dispatch starts★. If it were deferred until after `on_connect` returns, the state · input lease (`InputLeaseChanged`) broadcasts between the snapshot and the registration would be lost — after a reconnect the frontend re-pulls only the list · usage · profiles (`eventBus.ts:54-67`). Test (3-3 U4): the first frame of a shell that attached during a fan-out burst = Hello · the state broadcast right after the snapshot reaches that shell. Rejected designs = a 「보내고 끝」 step in `HandshakeStep` (「지금 확정」 trait change) · the adapter peeking at frames (violates vocabulary gate ②).
- ★The shell's receiving right (edition 3 · D4 ①)★ — if the shell registry has several daemons, a daemon→shell `CommandRequest` is applied **only if it came from the primary daemon (`primary()`)**. Another daemon's is not applied, and that daemon is answered with a refusal `CommandOutcome` (provisional text 「not the primary daemon」). ★Event · output routing also looks at the sending daemon (edition 4 · N4)★ — adapter state (agent table · subscriptions · output routing) is keyed by `(DaemonKey, AgentId)`, and the events · outputs of a `AgentId` that is not in the sending daemon's list are discarded and only logged — so that one daemon cannot shake the screen by citing another's agent id. ★Every event of that key comes only from the current handle (edition 5 lifecycle · the edition-6 review widened it to messages · D24 ②)★ — a per-peer inbox is a consumer task per peer, so the order splits on re-raising the same key (`connect` · `ensure` re-entry of a new drive — the current places `daemon_client/mod.rs:482` · `:555` · 3-2 U3 · the F4 re-raise after a stop — 3-2 U5): the old supervisor runs a little longer (`registry.rs:111-128` — 「겹침이 0 이 되지는 않는다」) · if the old inbox tail's `Disconnected` · `Closed` is processed after the new peer's `Connected`, `on_disconnect` (`replay_flight.rs:372-377` — clears the flight of every agent) erases the new Subscribe flight and the view stops · ★not only lifecycle (edition-6 review)★ — if a stale `AgentListUpdated` in the old tail is processed after the new peer's list snapshot, it overwrites the frontend list and the name ledger with the old list · the disconnect of a non-primary daemon also clears the same table (D4 ①). Spec: put a generation on `Closed` (`Disconnected` already carries it · for messages `Arrival.generation` carries it — `transport/src/event.rs:84`) and the adapter filters that key's events with three rules (edition-6 review — applied to **every event** of that key (list · state · output · command request · lifecycle) · what is discarded is only logged) — ① **the handle filter applies to every event** — an event from a Peer that is not that key's current handle (the current Peer) in the registry is discarded ② **the generation filter applies only to events that carry a generation** — messages (`Arrival.generation`) · `Connected` · `Disconnected` · `Closed` are discarded if older than the current generation of the current handle ③ **a lifecycle event without a generation always passes if it is from the current handle** — `ConnectFailed` · `Rejected` · `GaveUp` carry no generation (`transport/src/event.rs:163-177`). ★If ③ is dropped and read as 「마지막 `Connected` 세대와 비교」, the D20 ① · ADR-0180 decision 5 path (reconnect → `current()` version mismatch → `GaveUp(Rejected)` → 4001 fixed popup — §3-0 ⑤ · §6-4 ③) and the `ConnectFailed` · `GaveUp` · `Closed` of a Peer that never attached even once (it has no last generation) are discarded★ · one `replay_flight` per `DaemonKey`.
- ★What goes out to the frontend is only the primary daemon's (edition-6 review · D4 ① — the same rule as §6-4 ⑥ 「primary 만 화면에 · 둘째는 로그로」)★ — in stage 3 there is no screen for choosing a daemon, so frontend broadcasts from a daemon that is not primary are suppressed **entirely**: agent list · state · output · screen connection state · replay re-request · name ledger (`AgentNamesSink` — `AgentId` is the only key · master recheck A2). **Between daemons (데몬끼리) (with D5 — C4 · addition 6 · ★edition 6: D5 ③ — not built in stage 3. Below are premises handed to the very next multi-daemon PRD — but 「`DaemonId` 를 키로 한 영속 신뢰 금지」 is a present rule that is not handed over (§3-2 · ADR-0310 decision 4)★):**
- **Trust (premise):** the `PeerDaemon(DaemonId)` of a daemon-to-daemon connection is a **claimed · unverified** id and its trust level is the same as `LocalClient`. Credential = the receiving daemon's `daemon.json` token (being able to read the same PC's data folder = the same belief as the shell now). ★Do not build persistent trust (allow list, etc.) keyed on `DaemonId` — until it is bound to a key by pairing · this one line is not a premise but a rule that stands from stage 3 (§3-2)★. Each Listener refuses the auth frame of the other relationship (shell `Auth` ↔ `PeerAuth`). ★A relationship is not an authority boundary (edition 3)★ — one token of the receiving daemon opens both relationships. - **Dialing direction (premise):** without automatic discovery, configuration decides 「누가 누구에게 건다」 and only one side dials. If both sides dial at the same time, the side whose `DaemonId` is smaller keeps the connection it dialed (provisional · symmetry breaking — the multi-daemon PRD confirms).
- **Loop-back:** in stage 3 there is no daemon-to-daemon vocabulary, so a loop cannot form — it is placed in §4 as a premise for the day a relay vocabulary comes in.

### 3-5. Link replacement place — TLS · iroh (not a stage-3 decision)

- **Fact:** transport · time are dyn (`link.rs:99-155`) · `Registry` receives one Dialer (`registry.rs:80`) · `WsDialer` uses tungstenite's default features, so `wss://` fails at dial (`ws.rs:33-34`) · TLS must be placed **below** the byte stream and iroh must build message boundaries separately on top of the QUIC stream (security research §3-2 · §5 D).
- Direction (provisional): a composite Dialer that splits by address scheme + a Listener per relationship — `ws://` (stage 3) · later `wss://` (stream layer inside the ws adapter — tokio-rustls · key pinning) · `iroh://` (new implementation). The peer key goes up to the handshake · `admit` through the `LinkInfo` field. Alternatives = a per-peer Dialer (`Registry::add` signature change) · encryption over frames (a hand-rolled Noise — close to the taboo of rolling your own crypto in security research §5 E).
- ★Why there is no D number (addition 3)★ — stage 3 builds only one `ws://` and the shell's logical-address resolving Dialer (§3-6). Choosing among the three is the remote-track TRD's job, and what stage 3 fixes in advance is one peer-key field of `LinkInfo` (§4) — whichever is chosen, that field is the same.
- **The Origin · Host check is visible only in the WS upgrade (HTTP)** — so it lives in the ws adapter's accept settings (D8 ① · the values are given by the consumer · the values themselves are D21 ①). ★Edition 3: lower `transport::ws::split_link` (`ws.rs:237` public — used in only three places inside the crate `:183` · `:226` · `:536`) to `pub(crate)`★ — if left public, anyone can build a Link with their own accept and bypass every accept check. Edition 2's D8 ② (the daemon's own accept + `split_link`) was deleted for that reason · the daemon `ws_e2e` runs on the release accept-policy values (D21 ① — reject upgrades that carry an Origin).

### 3-6. Connection-info interface (3-2 scope — main may decide, outside the D list)

- **Fact:** `DaemonDiscovery` (`daemon_client/mod.rs:131-141`) = `ensure_spawn` (may launch) · `read_live` (does not launch — ADR-0021) → `DaemonInfo` (includes the token) · on every reconnect it rereads daemon.json and follows the moved port (`connection.rs:818-855`) · transport fixes the address and the handshake at `add` and calls the same `dialer.dial(&addr)` → `handshake.start()` on every attempt **one after another in one task** (`peer.rs:540` · `:1324` · `:1342`).
- **Proposal:** `EndpointSource` — `ensure() -> Result<Endpoint>` · `current()` (a live connection info or the branches of why it cannot be used — D25 below) · `Endpoint{key, address, credential: Secret}` (`Secret` = `Debug` · `Display` masking · `serde(transparent)` — the same type as `AuthFrame` · `DaemonInfo`, §5 5) · 3-3 U7 adds `expected_daemon_id: Option<DaemonId>` (§3-2) · production implementation = the local data folder. `Address` = a logical address (provisional `engram-local:<data_dir>` — keeping the contract that transport does not interpret addresses). The shell `LocalDaemonDialer` resolves the real address with `current()` at every dial, and puts the credential it resolved in **a field shared with the handshake of the same peer** — after `Reject{Retryable}` (§3-0 ⑤), the next dial fills that field anew. Only the first connection calls `ensure()` (may launch) **outside** `Registry::add` — a reconnect is only `current()` inside the dialer, so ADR-0021 stands by structure.
- **Old-address fallback (D25 — introduced in edition 3 · narrowed in edition 4 · narrowed again in edition 5 · edition 6 adopted ①):** today, if `read_live` is `None`, it dials the last known address **regardless of the reason** (`connection.rs:846-850` 「일시적 daemon.json 부재일 수 있어」). But that `None` is almost always 「산 데몬이 없다」 — ⓐ daemon.json is not deleted (net `portfile.rs` header · the client does not delete it either `discovery/mod.rs:227`) and while the daemon lives it only gives `FILE_SHARE_READ` and holds it (`platform/src/fs.rs:31-42` — no delete sharing) → **absent** = no live daemon ⓑ empty · broken content is seen only between the new daemon's `set_len(0)` + write (`portfile.rs:44-55`) — the new daemon took the lock, so the daemon at the old address is already gone, and if it dies while writing it stays empty ⓒ the recorded pid is dead · version mismatch (`check_acceptable :215`) goes without saying. Anyone on the same PC who took that old port first can receive the shell's Auth (the dead daemon's token — the daemon draws a new one at every start `daemon/src/lib.rs:556`) and the input after it, and can push `CommandRequest` — `Hello` has no proof and the local `expected_daemon_id` is always `None` (§3-2). ★D25 ① (edition 4 · narrowed again in edition 5): dialing the old address is **only for a sharing violation** (someone else blocked sharing and held it briefly — antivirus · indexer · platform `fs::is_sharing_violation`)★ — then the file exists and someone else merely held it briefly, so the old owner is likely alive and holding that port (likely — the pid cannot be seen at that moment · the remaining window = the daemon died exactly while someone else held it). ★It is not edition 4's `fs::is_busy` (edition 5)★ — that one hits `PermissionDenied` (`platform/src/fs.rs:63-82`): it opens the fallback even for refusals that do not clear, such as ACLs · read-only attributes · pending delete, and on POSIX access denied is that function's only branch. The existing function is enough (no new predicate needed) — a lock violation (33) is not hit by that function, but since it is a byte-range lock it is rare for this file and missing it costs one `Unusable`. On POSIX the fallback does not stand (there is no sharing mode). Absent · empty · broken · dead pid · access denied · other I/O errors = one failure (budget) · reread on the next attempt without dialing · ★version mismatch = `Terminal` (does not use the budget · popup — §3-0 ⑤ · edition 5 correction)★. So `current()` returns branches, not `Option` (provisional `Live(Endpoint) · Busy · Absent · Unusable · VersionMismatch{daemon}`) — today `FileReader` turns the error into text (`:603`) and loses the kind, so `EndpointSource` splits it in `io::Error`. ★Anyone who can **write** daemon.json turns the shell toward their own address★ — that axis is a known limit through D26 ② · D22 ② (§4 — multi-daemon · remote security design). Edition 3's D25 ② (HMAC proof of `Hello`) was deleted — it is a proof made from the token the shell already sent, so the interceptor can make it too. 「토큰을 보내기 전 · 그 연결에 묶인 증명」 is an empty space of the remote track (§4).
- **Rejected designs:** widen transport so that `Dialer` returns the context and `Handshake::start(ctx)` receives it — 「지금 확정」 trait change · swap `Registry::add` by watching daemon.json — the generation · budget break.
- **Remote preparation:** another implementation of the same trait (pairing store · remote address) comes in — the real thing of memo §4 「나중: 데몬 주소와 토큰을 어디서 얻나를 인터페이스로」.

## 8. Risks · unknowns · user decision list

### 8-1. Risks

1. **A hole in the seq stream (R1 · the largest)** — the 1st edition tried to fill transport shared-queue loss (`transport/src/lib.rs:128-131`) by attaching again, and that measure created loops · budget rewinds · starvation (§3-0 ①). The 2nd edition removes the loss itself (3-0 U1). The remaining risk = backpressure fills the daemon outgoing queue, so D13 disconnects → full replays become frequent (when shell consumption is slow) — 3-0 U1 · 3-2 U3 measure whether one replay has zero loss · zero disconnects. The mistake of turning on the stream layer has the same outcome (D10).
2. **Loss of meaning on the daemon receiving side (R2 · 3rd edition · rewritten in the 4th)** — net's per-connection receiving queue · single consumer · overlapping priority lane · saturation disposition (`Refused` reply obligation · `Unanswered` close · `Bypass` cancel first · priority lane full = wait) are the actual form of ADR-0206. If a peer-shared consumer (2nd edition) or a shared delivery task (3rd edition ②) is introduced, one connection's slow handling · large frame slows other peers and turns a priority-lane wait into a close (§3-0 ①). D11 ②′ (adopted) moves net's read task as is and changes only the receiving place, so its risk is smallest (① was as large as rebuilding it as a crate). The remaining difference (5th edition) = the end cause is split into read · write so net's drain · abort are rebuilt, but a new cap (draft 30 s) enters the read-end drain · on the path where the daemon ends first the socket does not close by itself, so the adapter calls `close_after_flush` (§3-0 ① 「연결 수명 순서」) — if that is missed, the link stays Live. The regression net = 3-3 U4's test move + the four between peers.
3. **Size of the replacement (R3)** — the shell's 2,073-line loop + 6,329 lines of tests · the daemon's 2,248-line server layer · the 2nd edition added 3-0 (seven transport units). The measures are splitting (3-0 U1 · 3-2 U3/U4 · 3-3 U1/U4/U5) · the test fate table · the clock (`ManualClock`).
4. **Replay flood (R4)** — if the daemon peer policy is left at the default (512), every replay causes a disconnect · re-replay loop (D16).
5. **Request deadline (R5)** — at 30 s, handlers that had no cap until now start failing at 30 s · at 8 s, a slow spawn may be misjudged (real time not measured).
6. **Origin value · Host check (R6)** — the four Origin values are unmeasured and the release value is likely not in the list (D21) · the Host check may block a legitimate client (`[::1]` etc.) — all that was confirmed is that our client dials with `127.0.0.1` (`connection.rs:438`).
7. **New daemon write deadline of 5 s (R7)** — if shell reading stalls for 5 s, disconnect and full replay. The 2nd-edition backpressure (R1) raises that possibility — if the shell queue fills and socket reading stops, the daemon write reaches the deadline (unchecked). ★3rd edition: in-memory cannot imitate the TCP buffer and so cannot measure this — moved to the real-socket test of 3-2 U4★. ★Mirror (5th edition)★ — the shell also newly gets the transport write deadline of 5 s (§7). Under D11 ②′ the daemon read task can stand on the priority lane for up to 8 × 5 s, and meanwhile the daemon transport layer takes in up to B + M and then stops socket reading → if a larger paste · input arrives in between, the shell write reaches the deadline and disconnects, then a full replay (low likelihood — a large paste during `Kill` mashing). The same real-socket test of 3-2 U4 measures it.
8. **Overlapping-number behavior change (R8)** — transport fails both (M1). `daemon_client_pending` is rewritten — it is the user decision of 2026-09-06 as is, so it is not a new decision.
9. **Reopening the 「지금 확정」 surface (R9)** — per-peer inbox (D24 ②) · byte budget · `Listener` · `Registry::attach` · `RequestError` field · `Reject` kind · `close_after_flush` · `PeerCmd` generation · `AcceptPolicy` · `notify_in` · `request_in` · `close_all` · one close-code entry · `Closed{generation, cause}` · ★5th edition: the rejection kind of `Dialer::dial` (`DialFailure` draft) · the read · write distinction of `DisconnectCause::LinkError` · where the byte count sits (from the read-ahead queue to the consumer) · detecting at once when the inbox is dropped★ · `split_link` taken down. With zero consumers nothing breaks — 3-0 is the last cheap time to fix that surface.
10. **Reply order change (R10 · new)** — a reply skips the receiving queue and overtakes earlier events (§3-3 B2). It is not known whether any shell caller relies on that order — 3-2 U2 test + caller survey. ★Closed by 3-2 U2 C (2026-11-04): no caller breaks; at most a short-lived default tab name or slot placeholder — §6-2 U2 C note★
11. **Local DoS (R11)** — the accept caps (§5 14) can be filled by another OS user on the same PC. That failure is 「못 붙음」, so once the D14 budget (5) is spent it hardens into `GaveUp`, and while there is no 「다시 연결」 button it lasts until the app is started again. ★D26 decides the scope (4th edition) — 6th-edition adoption ②★: accept it as a known limit and write this outcome into the `docs/tracking.md` item (revisit with the multi-daemon · remote track · when the button lands). ★2026-11-06 (ADR-0347): with the 15 s auth window the net daemon (no pre-auth cap) can also be driven out of memory by another OS user on the same PC — each pre-auth connection can pin up to 16 MiB for the window — accepted as part of this limit until 3-3 U4's caps; size those caps for 15 s.★
12. **Another user on the same PC · WebView scripts (R12 · 3rd edition · fixed in the 4th)** — port hijacking (D25) · reading · writing the data folder · a planted daemon.json (D22 · §5 28) · filling the accept permits (R11) are faces of one threat model (another OS user on the same PC — scope = D26). Blocking only one of the three leaves the others giving the same thing — so they were deferred together (6th edition D26 ② · D22 ② — multi-daemon · remote work is where the security design is redone).
