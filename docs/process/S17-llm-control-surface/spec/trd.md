# TRD — LLM control surface (engram-ctl)

> Status: **in progress.** PRD (requirements, passed `/review prd` 2026-07-14) → this document (how, interface settled). Major decisions are recorded in ADRs; the PRD open items are exhausted here.
> Anchors: PRD `./prd.md` · ADR-0080 (control-surface architecture) · ADR-0014 (CLI-via-Bash) · ADR-0035 (ViewManager = UI authority).

## Current terrain (measured — what already exists and what is net-new)

**Already exists (reuse — not a new design):**
- **request_id correlation** — every side-effect `AgentCommand` carries a `RequestId(Uuid)`, the daemon echoes it with `Ack`/`Error`/a dedicated reply (`Spawned`, `AgentList`, `Snapshot`, etc.), and the app's `DaemonClient` matches with `PendingMap[request_id]→oneshot`. (`crates/engram-dashboard-protocol/src/messages.rs`) → engram-ctl reuses it as is.
- **The whole set of backend commands** — spawn/kill/interrupt/write/resize/list + lease + profile/preset CRUD + snapshot are all already wire+dispatch (`connection_core.rs`). engram-ctl **only sends** these.
- **portfile discovery + WS + Auth** — proven by the spike `scripts/engram.mjs` (daemon.json → WS → Auth → request_id matching). Only a Rust rewrite.

**Net-new (this TRD designs):**
- **UI relay** — today there is no cross-client routing (every connection is a symmetric peer, broadcast only). The path `CLI → 데몬 → 앱 → ViewManager → 결과 → CLI` is created wholesale.
- **App role registration** — the daemon cannot tell "which connection is the UI app" (a connection has no role). The app must announce its identity for the relay target to be designated.
- **App inbound UI-command handler** — the app currently only consumes events + sends outbound commands. There is no path where the daemon→app command is received and applied to the ViewManager.
- **dedup store** — there is a request_id but no at-most-once dedup store (the R6 idempotency requirement).

## Component design

### 1. engram-ctl (Rust CLI) — formalizing the spike
- portfile discovery (reuses the discovery crate path) → WS connect → Auth frame → send command → match reply by request_id → stdout JSON envelope (`{v,ok,requestId,result}`/`{error}`) → exit code.
- Backend commands = send the existing AgentCommand directly. UI commands = relay envelope (§3).
- CLI grammar = **noun-verb group style** (`agent`/`view`/`obs` + `list-commands`) — decided 2026-07-14. Avoids verb collision and ambiguity as the catalog grows.

### 2. Backend command path — as is + dedup
- Reuses the existing AgentCommand. Addition = the **dedup store** (§5): a retry with the same requestId is at-most-once.

### 3. UI relay (net-new core — ADR target)
- **App role registration:** a new `RegisterRole { UiApp }` (sent only by the app right after auth). The daemon marks that ConnId as "the UI app connection". (Single app instance premise = PRD scope → no target addressing needed.)
  - ★**Resend on reconnect (F)**★: the app resends `RegisterRole{UiApp}` **on every reconnect, not only on the first auth** (put it on the reconnect handshake). Otherwise after a reconnect the daemon has no UI-app target and every UI relay wrongly fails with `APP_OFFLINE`. A duplicate UiApp registration is **last-registration-wins** (the new ConnId replaces the stale one — the old ConnId mark is discarded).
- **Relay envelope (opaque, single request_id):** `CLI → 데몬`: `RelayUi { request_id, payload(opaque JSON value) }`. `데몬 → 앱`: `UiCommand { request_id, payload }`. `앱 → 데몬`: `UiResult { request_id, result }`. `데몬 → CLI`: the result is returned with the same request_id. ★**The request_id the CLI supplied flows end-to-end unchanged** (no separate `relay_id` namespace — the daemon stores only `request_id → 원 ConnId`).★ The daemon **does not parse the payload** and keeps only a routing table (opaque bridging). The payload is an **opaque JSON value** inside the envelope (avoids a JSON-in-JSON string where the wire allows a raw value).
- **★Non-blocking relay dispatch (B)★:** the daemon `RelayUi` handler **does not await** the app round trip inside `dispatch` — `ws.rs` reads and dispatches commands one at a time per connection (read/dispatch are sequential), so awaiting would head-of-line block that CLI connection's command stream. Instead: (1) register an entry in the routing table + (2) enqueue `UiCommand` to the app connection + (3) **return `DispatchFlow` immediately**. The correlation completes asynchronously later, when `UiResult` arrives through the app connection's read path.
- **★Relay routing table + lifetime boundary (D)★:** entry = `{ request_id → 원 ConnId, deadline }`. Evict triggers = (1) `UiResult` received, (2) **connection cleanup of either endpoint** (the daemon's connection-cleanup path sweeps the relay entries keyed by that ConnId — **both** the origin-CLI side and the app side), (3) timeout. A `UiResult` with an unknown/duplicate request_id → drop (mirrors the existing "ignore unknown request_id" defense).
- **App apply path = (A) shared `ViewCommand` apply service + async correlation** (decided 2026-07-14, refined by /review trd) — the app applies the UI command it received by relay to the ViewManager through **a transport-neutral `ViewCommand` apply service shared with the human Tauri path** (a single path — consistent with §5 "a human click uses the same handle"). ★However, that shared path is **not a way of re-invoking the Tauri command entry on top of the actor**★: the relay inbound handler runs the apply **outside the `daemon_client` actor task (in a spawned task)** and returns the result to the actor as `request_id → oneshot` → the actor keeps servicing the socket and avoids a re-entrancy deadlock. (B) Calling the ViewManager directly is rejected = the risk of syncing 2 paths and lock-ordering (violates §5).
- **★Opaque coupling guard (H)★:** the relay envelope of the `protocol` crate carries **only an opaque payload**. The UI command enum + the payload→`ViewCommand` dispatch map live **only in `src-tauri`**. `engram-ctl`, the daemon relay and `core` **do not import the UI command enum** (core stays tauri-free, ADR-0003). The isolation gate reminder `rg "use tauri"` → 0 lines is **extended to engram-ctl as well** (engram-ctl is ignorant of UI semantics — an opaque envelope only).
- **ADR target:** "the app = a WS peer that receives commands from the daemon" is a new capability → a new ADR (or an extension of ADR-0080). Rejected alternatives = broadcast + app filter / an app-owned separate endpoint (already rejected in ADR-0080).

### 4. Observation primitives — on top of the existing Subscribe/epoch/seq/replay
- `wait --until` · `output tail --until message-done` (turn-boundary contract = PRD) · `events poll --cursor` · `list_commands`.
- **events poll cursor = a §5 decision** (a daemon monotonic event cursor + a bounded in-memory ring journal + RESET when pushed out → `agent list` full reconciliation).

### 5. Exhausting the PRD open items — decisions (grounded in measurement 2026-07-14)

- **Token injection + discoverability = spawn env overlay (infrastructure exists).** `CommandSpec.env: Vec<(String,String)>` already flows `profile.env → build_spec → transport pty cmd.env(k,v)` (`manager.rs:254-260` · `backend/claude.rs` · `transport/pty.rs:74`). The injection seam = `manager.rs` right before spawn (before build_command_spec). **A non-persistent overlay** (not put into profile.env — storing in plaintext in agents.json is forbidden, CLAUDE.md). Injected items:
  - **Control token** = an env var (e.g. `ENGRAM_CONTROL_TOKEN`) = the current master token (MVP; per-child = R7 deferred/T-11).
  - **engram-ctl discoverability = PATH prepend** (not a dedicated env var) — the LLM Bash resolves `engram-ctl` by name naturally, no separate CLI awareness needed (with an env var an explicit `$ENGRAM_CTL` call is needed = inferior UX). The bundle dir goes at the front of PATH.
  - **Own identity (source of the sender marker — slice 1 decision 2026-07-14)** = additionally inject `ENGRAM_AGENT_ID` (+`ENGRAM_AGENT_NAME`) — read by the automatic `[from: …]` marker of `agent write` (§6). The name is a snapshot at spawn time (a stale name after rename is accepted — the marker is informational, not an address).
- **write(stdin) ⟂ lease = automatic per-call acquisition (decision (a), 2026-07-14).** When the lease is **empty**, engram-ctl `write` **acquires it automatically for the scope of that single call** (within one call: acquire→write→release). If a human (or another holder) holds it → `LEASE_DENIED` (an honest failure). ★This design is decoupled from the per-connection lease evaporating★: engram-ctl opens a new WS connection on every call, so a per-connection lease disappears between calls — so the LLM `write` path **does not depend on holding a lease across calls**. (A standalone `input acquire`/`release` for explicit human-style holding may still exist, but the LLM write does not depend on it.)
- **dedup store = a daemon-global map (request_id → cached result), lifetime = bounded (the scale of the retry window — not the session/daemon lifetime).** ★Key point: engram-ctl is spawned per call (a new WS connection each call), so per-connection dedup is impossible → it **must be daemon-global**.★
  - **Unify correlation + dedup in a single request_id (C):** at-most-once holds only if **the caller supplies a stable key** (a new engram-ctl call = a new uuid → no dedup). engram-ctl exposes a **reusable `--request-id <k>`** (option) to run **correlation and dedup as one identity** (replaces the earlier separate `--idempotency-key`). If present, the daemon dedups on that request_id (at-most-once, cached result, `ALREADY_APPLIED`); if absent, engram-ctl generates a fresh uuid → at-least-once (a retry may be applied twice). Consistent with the PRD R6 stance.
  - **Lifetime = bounded (D — not "unbounded accumulation over the daemon lifetime"):** a **TTL** over the retry window (seconds to minutes in scale — not the session) or **an LRU cap of explicit size**. The reset on restart (PRD) is kept, but it is not the upper bound.
  - **Commit timing (D — critical):** a relay UI command commits its dedup entry **only on a successful `UiResult` (after applying)** — **no pre-caching before the relay** (pre-caching = a false "success" cached on timeout → violates PRD "UI success is confirmed only after the ViewManager applies it"). An in-flight duplicate (the same request_id arrives again while the first relay is in progress) → **coalesce onto the same pending result** (no double apply).
- **Ordering = the app-side shared `ViewCommand` apply service + async correlation (no new queue needed, avoids re-entrancy deadlock).** ★The earlier claim ("the ViewManager Mutex alone is enough for order, no new queue needed, no re-entrancy") is **false for compound commands → discarded**★: a composite UI command such as `spawn_into` (`commands/layout.rs`) calls `client.send_command(...).await` inside itself, and that reply is resolved **only inside the stream loop of the same `daemon_client` actor**. If the relay inbound handler is run **inline** on that actor and awaits such a Tauri command → self-deadlock (the actor cannot pull out its own reply). Instead: the human Tauri path and the relay **share a transport-neutral `ViewCommand` apply service** (keeping the §5 single path — not a re-invoke of the Tauri command entry), and the relay runs that apply **outside the actor (a spawned task)** and correlates by `request_id → oneshot`, leaving the actor free to service the socket. The single ViewManager Mutex still serializes the apply order (the RMW critical section), but **re-entrancy safety** comes from this async correlation design. `LayoutState(Arc<Mutex<ViewManager>>)` (`layout/mod.rs:29`) and the PRD read-your-writes remain valid.
- **stale-ref error codes (initial closed set) + certainty encoding (G):** `STALE_REF` (the addressed ID vanished/closed) · `APP_OFFLINE`, `APP_DISCONNECTED`, `TIMEOUT` (routing, PRD) · `LEASE_DENIED` (write lease not held) · `UNSUPPORTED` (outside the capability gate) · `ALREADY_APPLIED` (dedup hit).
  - ★**Certainty encoding**★: `APP_OFFLINE` = **confirmed not applied** (certain-not-applied — no target app). `APP_DISCONNECTED`/`TIMEOUT` = **unknown** (it may have been applied → the LLM reconciles by read). The retryable flag **must not imply that re-running an unknown state is safe** (only certain-not-applied is safe to retry).
  - **Addressing selector typing (R5 2-mode):** distinguish `byId` (stable id) from live-relative (spatial/direction etc. real-time relative) selectors by type — the exact enum, message and retryable flag = implementation.
- **mixed-version:** engram-ctl↔daemon is covered by the existing `PROTOCOL_VERSION` handshake (Auth mismatch rejected). The relay payload (the UI command JSON the app parses) is versioned by the envelope `v` field, and if the app does not support the `v` it returns an honest error. The MVP is a single v, reserved as a field.
- **Atomicity of partial application (multi-command intent) = open (hard).** Atomicity on a mid-way failure when one logical intent is split into several engram-ctl calls — the MVP gives each command its own honest result + the LLM reconciles by read (no transaction introduced). Batch/transaction is later.

## 6. Interface detail table — slice 1: the message path (2026-07-14, implementation session)

> **Slice split (user decision 2026-07-14, tracking.md T-13):** the message-sending path (`agent list`/`agent write`/`list-commands` = backend direct) is implemented and measured first as **slice 1**. The tables for observation (`obs tail/poll/wait`) and UI relay (`view *`) are **carried over to slice 2** — the design (§3~§5) stays locked, only the tables come later. Reason: the only unimplemented piece of the sending path is engram-ctl (JSON `write_input` already wraps plain text into a stream-json user turn + a synthetic echo — the `session.rs:106` contract and the `:338` test), and the UI relay machinery (§3) is not needed for backend-direct commands.

### 6-0. Common contract (all subcommands — /review trd FIX applied v2, 2026-07-14)
- **Connection lifetime = per-call:** portfile (`daemon.json`) discovery → WS connect → Auth (`ENGRAM_CONTROL_TOKEN`) → send 1 command → match reply (request_id) → stdout output → exit. (§1)
- **stdout = a one-line JSON envelope:** success `{v:1, ok:true, requestId, result}` · failure `{v:1, ok:false, requestId, error:{code, message, retryMode}}`. **exit code = 0 (success)/1 (failure)** — the finer breakdown of failure is the source of truth in `error.code` (do not branch on the exit code, the LLM reads the JSON).
- **v1 result mapping (caller insulation — blind review HIGH):** the wire commands and replies are sent directly and reused as they are (variant and field name source of truth = `messages.rs`), but **the stdout `result` is mapped to each subcommand's v1 CLI schema** — exposing the internal wire types as they are would let a backend refactor break CLI callers.
- **Error code synthesis (the real thing — doc-aware review measurement):** the daemon currently responds to failures only with a free-string `Error{message}` (no typed variant, the `connection_core.rs` reply). engram-ctl **synthesizes `error.code` best-effort** by message pattern matching, and no match = `INTERNAL`. A string contract is fragile → pin the matching patterns with a golden test of the daemon's real strings; promoting to typed error variants is later (outside slice 1).
- **Common error codes:** `INVALID_ARGUMENT` (argument/body convention violated — decided locally in ctl) · `AUTH_FAILED` · `PROTOCOL_MISMATCH` (PROTOCOL_VERSION mismatch) · `DAEMON_UNREACHABLE` (no portfile/WS failure) · `REQUEST_ID_CONFLICT` (below) · `OUTCOME_UNKNOWN` (below) · `INTERNAL` (unclassified).
- **`retryMode` (required on every error — replaces the bool retryable, the machine-readable form of the §5 certainty encoding):** `never` | `same-request-id` | `after-condition`. Full mapping: INVALID_ARGUMENT, STALE_REF, REQUEST_ID_CONFLICT, ALREADY_APPLIED (already applied = effectively success), INTERNAL = `never` / AUTH_FAILED (fix the token), PROTOCOL_MISMATCH (align versions), DAEMON_UNREACHABLE (start the daemon), LEASE_DENIED (release the hold) = `after-condition` (the condition is stated in message) / OUTCOME_UNKNOWN = `same-request-id` (only a retry with the same id is safe).
- **`--request-id <uuid>` (option) + retry contract (blocks duplicate injection — blind review BLOCK resolved):** the correlation+dedup unified key (§5). **The backend-command dedup store (the locked design of §2·§5) is included in the slice 1 implementation scope.** A same request-id arriving again: a completed one = **replay the cached original result envelope** (idempotent replay) · in-flight = coalesce onto the same pending result · **the same id + a different command/payload** (fingerprint mismatch) = `REQUEST_ID_CONFLICT` · a boundary where the cache cannot be replayed = `ALREADY_APPLIED` (confirms only the fact of application). **Retry window = `retryWindowMs` (the dedup TTL, default 300000 = 5 minutes — an implementation constant, making it config is later):** after the window passes the same id = treated as new (duplicate injection possible) → **retry immediately within the window**. The error of an `OUTCOME_UNKNOWN` response carries `retryWindowMs` so the caller knows the safe window. **`--timeout <ms>` (default 10000):** a reply that does not arrive within the deadline / a lost connection = `OUTCOME_UNKNOWN` (whether it was applied is unknown) — **a retry must be with the same request-id** (a retry with a new id = at-least-once = the risk that the same user turn is injected twice). No request-id specified = fresh uuid = at-least-once (the documented default).

### 6-1. `agent list`
- **Arguments:** none (MVP — filter/format options later).
- **Result (v1 fixed — including types and nullability):** `{agents:[{id: string(UUID)·비null, name: string·비null, status: string(enum), cwd: string·비null, structured: bool, epoch: number(u32 — 재활성화마다 증가, 신선도 판별용)}]}` — **`structured` is derived from the wire `capabilities.output`** (the wire `AgentInfo` has no `mode` field — doc-aware review measurement `domain.rs`, no-redefinition principle kept). **The `status` enum = a v1 snapshot of the wire `AgentStatus` variant strings** — list the values at implementation time by cross-checking `messages.rs`, and pin them with a golden test (no fabrication here); an unknown new value passes through as the string (forward-compat, the caller must tolerate unknown values). **Addressing source**: the LLM resolves name→id here.
- **Errors:** common codes only (§6-0).

### 6-2. `agent write <agent-id>`
- **Arguments:** `<agent-id>` = **UUID byId fixed** (name addressing unsupported — a display name has no uniqueness guarantee, ADR-0070). **Body source = exactly one:** `--text <msg>` XOR a stdin pipe. Convention violations = `INVALID_ARGUMENT`: both specified · both absent · stdin is a TTY and not a pipe (**fail immediately without waiting** — blocks the LLM from waiting forever) · empty body · non-UTF-8 · over the limit (1 MiB). Newlines preserved.
- **Action chain:** attach the sender marker (§6-4) → send the existing `WriteStdin` directly → ack. JSON-mode wrap + synthetic echo = the backend's existing path as is (**1 write = 1 complete user turn**, `session.rs:106`).
- **lease (corrected to the real thing — doc-aware review measurement `connection_core.rs`):** there is **no** separate acquire/release round trip — **with an empty lease `WriteStdin` just passes through** (`check_input` Allow), and **if another connection (a human viewer, etc.) holds it, `LEASE_DENIED`**. The real implementation of §5 "automatic per-call acquisition" = this empty-lease pass-through. ★Implementing 3 commands acquire→write→release is forbidden★ — on a crash in the middle it creates a new window of an orphaned lease (human input locked).
- **busy behavior = inherited from existing (not a new decision):** even when the target is mid-turn, it is the same path as a human's mid-turn intervention (the `RichSlot.tsx:138` allowance precedent) — stdin queuing/steering, no separate waiting or rejection.
- **Terminal-mode target = raw delivery, no automatic submit:** ctl does not append `\r` — if the caller wants submission too it includes a newline in the body. The ack ("written") means **the session stdin has taken it**, not a guarantee of submission or the turn firing (behavior stated per mode). The MVP's main target = JSON agents.
- **Errors:** common (§6-0) + `STALE_REF` (nonexistent/exited id) · `LEASE_DENIED` (held by a human or another holder) · `ALREADY_APPLIED` (dedup boundary, §6-0).
- **Result (v1 fixed):** `{agentId, status:"written"}` — `written` = the session has taken it, **not a guarantee that the target LLM consumed or answered** (that is observation = slice 2's responsibility).

### 6-3. `list-commands`
- **Result (v1 fixed):** `{commands:[{name: string, args:[{name, required: bool, type: string, summary}], result: string(shape 한 줄 서술 또는 §6 참조), errors:[string(코드)], summary: string}]}` — self-discovery at a level where one can "read and use it right away" (blind review applied). MVP = a static catalog at build time.

### 6-4. Sender marker — automatic marker (FORK-3, user decision 2026-07-14)
- `agent write` **automatically attaches** `[from: <발신자 이름> (<풀 UUID>)] ` in front of the message. Source = `ENGRAM_AGENT_ID`/`ENGRAM_AGENT_NAME` of the spawn env overlay (§5). **The id is the full UUID** (changed from id8 — determinism of the reply target, blind review applied). **The name gets a forced one-line escape** (newline and `]` removed, 64-char cap — prevents breaking the header).
- **No own identity in env (a human calling directly from a shell) = no marker** — a human's message is not disguised as agent-originated.
- **The marker is not forgery prevention (advisory):** it cannot stop forgery where a fake `[from:]` is planted in the body — an accepted risk of the local MVP, which has no trust model (an authenticated marker belongs to the R7/T-11 branch). "Preventing mistaking it for a human instruction" is a conventional hint, not a guarantee.
- **The marker is informational, not an address:** a stale name (rename) is accepted, the reply address is re-resolved by `agent list`.
- **Rejected alternatives:** manual `--from` (if the LLM omits it the receiving side mistakes it for a human instruction — unsuitable as an orchestration basic) · no marker, pure delivery (loses the origin, depends on a prompt convention = lowest reliability) · a structured-metadata marker (a blind review proposal — claude stream-json input has no metadata slot that reaches the model, so in-band is the only way to reach it).
- **QA measurement item:** round trip of a Korean display name through env (UTF-8, Windows·portable-pty) — doc-aware review flag.
