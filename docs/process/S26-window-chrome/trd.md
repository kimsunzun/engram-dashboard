## 0. Summary of conclusions

- **The layout model holds the number.** The window entry (`WindowTabs`) of `ViewManager` gets a `number` field · a table of numbers (`closing`) for windows that left the model but whose OS window still exists · a pure-function module `layout/numbering.rs` (smallest free number · fixing saved numbers). The number is taken inside the same lock that puts the window into the model and is released at `Destroyed` (D13 stays — M2). **A window whose OS window is already gone** (a restored pop-out that could not be opened · a window that vanished before it could be swapped) is released at once, without going through `closing` (`drop_window_gone` — review Claude ⑥).
- **The shell builds the tab name.** `View.name: String` becomes `TabName { Auto, Named(String) }`, so that 「정한 이름인가」 is carried by the type. Effective name = the set name, otherwise the display name of the focus slot — one `match` without a wildcard over `SlotContent` in `layout/tab_name.rs` (D17). Wording = T2 (one shell table). The agent name comes from a ledger inside the model fed by the daemon's `AgentListUpdated`, and when the effective name changes it raises the layout `version` (so that the web's version guard does not discard it — review Claude ③).
- **The shell puts the OS title on.** The window-tabs notification payload (`WindowTabsPayload`) carries the number · persistent id · the title 「<활성 탭 이름> - Engram:<n>」, and the Tauri adapter of that notification calls `set_title` **on the main thread only when the version is newer than the last version number of that window** (an old version that arrives late is discarded — review codex ⑤). Invariant = 「창 제목이 바뀌는 쓰기는 그 창의 탭 목록을 새 판 번호로 알린다」.
- **Window state is a bus command.** New: `window.minimize` · `window.maximize` · `window.unmaximize` · `window.raise` · `window.hideAll` · `window.showAll`; `window.close` becomes main = hide all windows · `if_empty` (re-check of the 0-tab self-close — decided in the same lock before the common resolver · review codex ②); `window.list` keeps the old `windows` field and adds a `details` field. The LLM's raise · show **does not steal focus** — it goes through the existing `first_paint::raise_and_show` sequence (raise z while hidden → Tauri `show` · `unminimize` → `set_focus` only when the foreground is ours · no Alt synthesis · ADR-0299 · review Claude ⑤ · edition 0.3 re-review ①) and shares one path with the tray show (`Activation::{TrayClick, NoSteal}`). The front-window decision is platform's foreground-window comparison (Tauri `is_focused` is not used on Windows · review Claude ④). One window-state action runs as **one main-thread job** (read · decide · defer · OS call), so it does not interleave with the first-paint show, and the LLM show skips the first-paint wait window (precedent of the deferred maximize — review codex ⑥ · edition 0.3 re-review ② ③).
- **Window argument = persistent id · label alias within the same run · numbers rejected.** One resolver (`layout/window_arg.rs`) is shared by the bus and the invoke shells. The pop-out label becomes `slot-popup-<실행 표식 8 hex>-<n>`, so that labels from a previous run do not match (D12).
- **The answer for the three places that make a new window = `{ window, window_id, number }`** (the same three for invoke · bus · web registry — R6). The first paint is not waited for (T1).
- **The title row (web) only draws.** `TitleRow` = tab bar (tabs · `+`) · empty draggable area (minimum 42 — Chromium `FrameGrabHandle`) · number marker (a draggable area · `pointer-events: none`) · three window buttons. The buttons call registry commands and do not call the Tauri window API. **The tab bar zone for the tab-drop decision is widened to the title row (including the top margin) only vertically, and horizontally it is from the first tab to the right end of `+`** (user decision 2026-10-26 · T-66 — 「탭이 있는 곳만 탭바 구역」 · a drop over the empty space · marker · buttons = a new window · even a window's own tab is detached if it goes past `+` · R14 · AC12 · §7-9). Window facts (maximized · front window · chrome shape) are received **by adding fields to the existing `window:frame` path** (no new channel — review codex ⑧). Draggable area = Tauri `data-tauri-drag-region` (Q5 — in the spike a tab dragged over it could be dropped) · Alt+Space · right-click window menu are accepted as that technique gives them (Q10 — QA records them).
- **The OS frame is withdrawn in one place, `WebviewEnv::finish`** (`decorations(false)` · `shadow(true)`). 「단추를 우리가 그리나 · 왼쪽 비울 폭」 is answered in one place, platform `window::caption_style()` (R16 · D10). The web measures the minimum window width per window and reports it, and the shell applies it as the OS minimum size (normal state only · pulling wider only at open time — pure decision `chrome::ChromeBook` · review Claude ⑩ · codex ⑩).
- **Implementation units = U0 (withdraw the spike code) · U1–U7 (shell · model · commands) · U8a · U8b (web title row → withdraw the OS frame) · U9 (snap overlay behind the off feature) · U10 (docs).** After each unit the build and regression are green and the app is in a usable state.

### 2-4 Boundary invariants (what this TRD adds)

1. **The number is computed only inside `ViewManager` methods** — every path that inserts a window entry (`create_window` · `attach_view_as_new_window` · the new window of `dock` · `from_restored` · `adopt_restored`) and every path that removes one (the pop-out emptying of `pull_tab` · `close_window` · `drop_window_gone` · `adopt_restored`) goes through two private methods (`insert_window_entry` · `retire_window_entry(label, Os::{Alive, Gone})`). No new code is written that directly `insert`s or `remove`s the `windows` field (that field is `pub` only for tests · the read of the persistence conversion — writes are blocked by this rule and a test checks it — §10-1).
2. **A write that changes the window title announces that window's tab list with a new version number** — if any of the active tab · tab effective name · number changes, `version` is raised and that window's `WindowTabsPayload` is emitted (`announce`). Of the writes that today emit no tab notification, the ones that change the title = `create_window` (new window) · agent name change (which does not even raise `version`) · boot — all three are fixed (§4-3 · §4-4). Slot writes (`split_slot` · `close_slot` · `focus_slot` · `assign_agent` · `set_slot_content` …) already carry `owner_tabs` and raise `version` (code — those functions in `layout::apply` · the full cross-check is U4's part — 미검).
3. **The web does not call the Tauri window API for minimize · maximize · close · show · raise** (R17 · AC10) — type-check test §10-4.
4. **`slot_label` has no wildcard · grouped-name branch** (D17) — `#[deny(clippy::wildcard_enum_match_arm)]` on the function + an rg gate on that file (§10-4 — because CI does not run clippy).
5. **The only things that reveal a first-paint wait window (a window put on the first-paint gate) are the first-paint gate and the human's tray show** — window state commands and the LLM's show (`window.showAll` · `window.raise` of a hidden window · invoke `show_main_ui`) skip that window. The tray-click show withdraws that wait and shows, as it does now (code — `cancel_hold` → `show()` in `tray::actions::show_main_ui` · it is a show pressed by a human — edition 0.3 re-review ③ · §5-2).

### 3-1 In-memory model (`src-tauri/src/layout/`)


- **`View.name: String` → `TabName`** (main decision M4′) — the type carries whether the name was set. The places that read the old `name` directly (building `ViewMeta` in `list_tabs` · `convert::tab_entry` etc.) stop compiling and are all moved to the effective-name calculation. The branch of keeping `String` and bolting a 「정한 이름인가」 field onto it was rejected — if anyone reads the stale string of an auto tab (「View 1」) directly, AC3 breaks.
- **The default-name construction is withdrawn** — `make_view(name)` → `make_view()` (`TabName::Auto`) · `create_tab(label, name)` takes `Some` = `Named` · `None` = `Auto` · `refill_main` · the empty main of `from_restored` · `create_window` · the name argument of `prepare_detached_view` · the `"Tab"` of `apply::move_slot_to_window` · `LabelSource::tab_name` (「Popup N」 — `commands::popout::PopupCounter`) are all withdrawn (code — those places now hold 「View N」 · 「View 1」 · 「Tab」 · 「Popup N」).
- **`rename_tab` rejects an empty name · a whitespace-only name** (defense on the model side — `LayoutError::EmptyName`). Now, because 「정규화는 경계 몫」, it uses the received string as is (the comment on `ViewManager::rename_tab`). The bus (`commands::text`) and the screen (`TabBar.tsx` `commitEdit` · registry `tab.rename`) already filter, so the result is the same, and even if a new boundary appears later, a 「정한 이름」 does not harden into an empty string (AC36).
- **`rename_tab` hardens into `Named` even when the text equals the current effective name** — if a human "renames" (「바꾸면」) an auto-named 「myproj」 tab to 「myproj」, that is setting the name (it no longer follows later agent name changes). The web `TabBar.tsx` `commitEdit` now sends only when `trimmed !== tab.name` (code) — fix it so that, if `tab.named` is false, it sends the same text too (U3a · review codex ⑨). The same text is sent only on Enter (a deliberate confirmation), and focus loss · pressing a covered neighbor send only changed text — main decision (U3a review · 2026-10-25).
- **`WindowTabs::new` takes `number` as an argument** — every new window entry goes through that constructor (code — the comment on that function), so no entry without a number can arise.

### 3-3 Persistence (`shell\state\state.json` — `state/schema.rs` · `codec.rs` · `convert.rs`)

- **`WindowEntry.number: Option<u32>`** — writes always carry a value (main also writes 1 — reads do not look at main's value · D3). The read (`codec::WindowHead`) takes `#[serde(default)] number: serde_json::Value` and decodes **leniently**: only an integer in `1..=MAX_SAVED_NUMBER` becomes `Some`. Field missing · `null` = `None` without a warning · any other unusable value (0 · negative · float · string · bool · over the upper bound) = `None` + warning `DecodeWarning::NumberDropped` (the original is kept up to the first 64 characters) · main's value is neither looked at nor warned about. The fact that numbers were reassigned is reported by the restore warning `NumberReassigned`. ★Do not skip the window★ — a window's tabs must not be lost because its number looks odd (AC25 · AC38).
- **`TabEntry.named: Option<bool>`** — writes always carry a value. The read is `#[serde(default, deserialize_with = "lenient_bool")]` — field missing · `null` · a non-bool value = `None`. `None` · `Some(false)` = auto (D16 — no migration rule), `Some(true)` = `TabName::Named(name)`. Do not skip the whole tab over a non-bool value.
- **`TabEntry.name`** — writes = the **effective name** at that moment. An agent name change also raises `version` (§4-3), so the recorder rewrites and the name in the file is always the current value. If an old build reads this file, it shows that name as it is (downgrade is not supported, but this looks better — storage TRD §12 R3). This edition does not use the `name` of a tab with `named != Some(true)` as a name — it is used only to seed the agent-name ledger (§4-3).
- **The 「같은 JSON」 rule** — the head of `state/schema.rs` says `TabEntry` and `layout::View` are the same JSON, and a test (`view_shapes`) checks them against each other. Because the name field now diverges, fix that head and test to 「이름 칸만 `convert` 가 풀어 옮긴다」 (U3a). The other fields are still checked against each other.
- **`STATE_VERSION` stays 1** — both are optional fields that are readable when absent. If an old build saves again, both fields disappear = at the next boot of this edition the numbers are reassigned from main in saved order (the 「옛 파일」 rule of AC25) and set names go back to auto. Accepted (storage TRD §12 R3).

### 3-4 Fixing saved numbers (D3 — `numbering::resolve_saved`)

Input = the pop-out numbers in saved order (`Option<u32>` — after the lenient read above) · the set of numbers already held `held` (always including main's 1). Output = numbers of the same length.

1. A pop-out that wrote 1 = none (it is main's).
2. If two or more wrote the same number, only the earlier window in saved order keeps it and the rest become none.
3. A number in `held` (held by another window that is not then closing) = none — **the window that already holds it keeps it** (D2 · D3).
4. After all valid numbers are set, the windows that are none receive, in saved order, the smallest free number.

`MAX_SAVED_NUMBER = 999` (main decision M3) — AC38 measures the shape shown up to three digits. A new window during a run does not look at the upper bound. The warning `RestoreWarning::NumberReassigned { window_id, saved, given }` is left in the log.

### 3-5 Snapshot consistency (R29 · AC37)

The number · 「정한 이름인가」 · name · persistent id sit in the same window entry · tab entry of the same `StateFile` — they are not separated. The recorder rewrites the whole file when the layout `version` changes (storage TRD §6-4). The number changes only in writes that insert or remove a window entry, the 「정한 이름」 only in `rename_tab` · `create_tab`, and those writes already raise `version`. The auto name changes by only two paths: focus writes (which already raise it) and agent name changes (which §4-3 makes raise it) — so the `name` in the file is always the effective name of that version, with no contradiction with the value the boot seed (§4-3) reads (the 「한 박자 낡을 수 있다」 of §3-5 in edition 0.1 was withdrawn — review finding).

## 4. Number · name · title rules

### 4-1 Number lifetime (R1 · D1 · D2 · D13)

| Event | What the model does | Place |
|---|---|---|
| Boot default · boot restore | main = 1 · pop-outs = `resolve_saved(저장값, {1})` | `ViewManager::new` · `from_restored` · `convert::Restorer` |
| Insert a new window entry (three places · whether a prewarmed window or a newly built window) | `number = smallest_free(살아 있는 번호 ∪ closing 번호)` — inside the very lock that inserts | `insert_window_entry` |
| Remove a pop-out entry — the OS window is alive (close of the last tab · emptied by docking · `window.close` · close request) | move that number into `closing[label] = { window_id, number }` | `retire_window_entry(label, Os::Alive)` |
| OS window `Destroyed` | `closing.remove(label)` — no-op if absent (prewarmed window · already released window). If the window was still in the model then, remove it as `Os::Gone` and release at once | `release_closing` · `drop_window_in_model(label, DropCause::Destroyed)` inside the same lock |
| **Remove a pop-out entry — the OS window is already gone** (a boot-restore pop-out could not be opened — `state::placement::open_restored_popouts` · it vanished after the copy was accepted and before the swap — `forget_vanished` in `state::restore`) | removed at once without going through `closing` — that window's `Destroyed` has already passed or will not come (review Claude ⑥ — in edition 0.1 those two called `close_window`, so the number stayed held until the end of the run) | `drop_window_gone` (= `retire_window_entry(label, Os::Gone)`) |
| Accept the copy | release the numbers of all old pop-outs (the live ones · all of `closing`) and set the copy's numbers with `resolve_saved(사본값, 지금 쥔 번호)` — `held` = main's 1 (note below) | `adopt_restored` |
| Before a prewarmed window is handed over · when returned | outside the model — no number | — |
| Open failure · insert rejected (the opened window is withdrawn) | the number was never taken — nothing to release (PRD R1 「만들기 실패」) | — |

- **D13 stays** (main decision M2) — its value = one table inside the model (`closing`) + two private insert/remove methods + one line of `Destroyed` cleanup. If it were removed, after a normal close a new window would briefly show the same number as the closing window, and AC20 ② would have to be withdrawn.
- **If `Destroyed` never arrives**, that number stays held until the end of the run (W7 — accepted). `closing` is not persisted.
- **The cause of `drop_window_in_model`** — a close request and `Destroyed` both call that function (code — `commands::popout`). Add the argument `cause: DropCause { CloseRequested, Destroyed }` so that the removal from the model becomes `CloseRequested` = `Os::Alive` · `Destroyed` = `Os::Gone`, and for `Destroyed` it also does `release_closing` at the end (inside the same lock — that function already does the tombstone · subscription cleanup inside the lock). The path where `output_router::cleanup_window_core` calls `close_window` inside it is fixed to receive the cause.
- **The branch that cannot call the `Destroyed` cleanup also releases the number** (a small fix of the edition 0.3 re-review · U2 review corrected the place) — the `Destroyed` branch of `lib.rs` calls `cleanup_popup_window` only when all four of `LayoutState` · router · channel registry · daemon client exist (code — 「하나라도 없으면 조용히 스킵」). When all four exist, the number is released by `drop_window_in_model(Destroyed)` inside it in one lock — the removal · tombstone · subscription cleanup stay in the same lock and the deleted-tab-count log keeps its meaning (if the number release were put in front separately, the model window would drop out in the earlier lock without a tombstone and that log would always be 0). If even one is missing, the `else` branch of that conditional calls `layout::release_window_number(&state, label)` with `LayoutState` alone (= lock → `release_closing` → if still in the model, remove as `Os::Gone`) — if it did not call this, the number would stay held until the end of the run.
- **`held` of the copy acceptance** — `adopt_restored` clears every window entry other than main inside the same lock (code). So at the commit moment the only 「닫히는 중이 아닌 다른 창」 is main, and the D3 branch 「이미 쥔 창이 지킨다」 does not occur in this sequence. It is written as a general rule (the input takes `held`) and measured by a pure test — the PRD edition 0.5 AC31 records this fact (§13).
- **Boot restore** — the model is built by the plugin initialization (`state::boot_plugin`) before setup (likely — that the bus connection comes after it is 미검). Then a `window.create` during boot is always inserted after the restored windows and gets a free number (AC31 ①).

- **U1 builds on its own** (review codex ⑦) — `slot_label` · `window_title` · `word` know only `SlotContent`. `effective_tab_name` and the empty-name ledger (`agent_names`) were moved to U3a, where the `TabName` · `ViewManager` fields exist.

### 4-3 Agent name ledger

- **Source = `AgentInfo.name` of the daemon's `AgentListUpdated`** (protocol — canonical display name = `display_name ?? basename(cwd)` · including name uniquification — the daemon `AgentManager` builds it · ADR-0101 · ADR-0120). - **Notification after a daemon rename** — before U3b, a successful `RenameProfile` emitted only `ProfileListUpdated` → now, on `Renamed`, it also emits `AgentListUpdated` (reusing `agent_list_event` · the U3b test confirms that `AgentInfo.name` changes for a live agent). Rejected branch = the shell recomputes the name from `ProfileListUpdated` (it would miss the uniquification suffix). **Bus · CLI `agent.rename`** does not pass through this WS arm and notifies through the roster notification port (`RosterFanout::roster_changed`), so that port also **always** emits `AgentListUpdated` after `ProfileListUpdated` (main decision · U3b review 2026-10-25). The port does not know which verb called it — for the lists that spawn · create · move · unchanged rename add on, if the name is unchanged the shell's name ledger passes them with neither a version bump nor a notification (the web's agent list replacement · roster observation still run one more time as before).
- **Ledger = `ViewManager.agent_names`** (main decision M5) — the name calculation finishes inside one layout lock (no new lock · no new order). The path that changes it = `apply::agent_names_updated(state, events, &[(id, name)])`: lock → take the effective names of the auto-named tabs before the change → overwrite the ledger (not erase — a dead agent's slot also uses its last name) → if at least one tab's effective name actually changed, **raise `version`** and copy those tabs' window payloads → release the lock and `announce` (including the title — invariant 2). If it did not raise it, the web would discard a tab notification with the same version number (code — the version guard in `viewStore.ts`) and the title application would also see it as an old version (review Claude ③ · codex ⑤). If nothing changed, nothing is emitted.
- **Connecting path** — `emit_broadcast` of the connection task (`daemon_client/connection.rs`) calls the new port `AgentNamesSink::agents(&[AgentInfo])` after the existing `events.agent_list_updated` in the `AgentListUpdated` arm. The real one is the shell assembly calling `apply::agent_names_updated` with `LayoutState` · `TauriEvents`. The emit port `DaemonEvents` is not widened (the head of that file, 「넓히기 금지」 · the same split as the sibling port `refusal`). The place that calls `emit_broadcast` (one place, the Text arm of `main_loop`) holds no other lock (confirmed in U3b).
- **Boot seed** (main decision M16) — `from_persisted` fills `agent_names[agent_id]` with the saved `name` of a tab that has `named == Some(false)` and whose focus slot is `Agent`. An old file (no `named` field) is not seeded — its `name` may be an old default like 「View 3」. This keeps the OS title from flickering once as 「에이전트 - Engram:1」 even if the daemon attaches late. Copy acceptance adds the seed to the live ledger **only for empty entries** (the live value is newer).
- **When there is no daemon** — an agent not in the ledger = 「에이전트」 (T2). It changes when the daemon attaches and the list arrives.

### 4-4 Window title (R3 · AC3 · AC21)

- **Shape** = `window_title(활성 탭 유효 이름, 번호)`: both present → 「<이름> - Engram:<n>」 · no tab → 「Engram:<n>」 · no number (hidden prewarmed window · a window outside the model) → 「Engram」. Not truncated (truncation in the taskbar is the OS's part).
- **Place · order of applying** (main decision M6 · review codex ⑤) — `commands::layout::TauriEvents::window_tabs_updated` hands the `title` · `version` of `WindowTabsPayload` to `app.run_on_main_thread` right after the emit. On the main thread, `chrome::ChromeBook::accept_title(label, version)` returns true only when it is greater than the last version applied to that window, and if true, `set_title` (failure = warn). Notifications are emitted outside the lock by several threads, so their order can be swapped (`layout::apply` 「락 규율」), but the one main-thread line + the version comparison discards the old version. If the title is the same, the OS call is skipped. The ledger entry is forgotten at that window's `Destroyed` (`ChromeBook::forget`). **U4 implementation**: there are three decisions — `Stale` (same or old version · discarded) · `Same` (new version · same text · only the version recorded) · `Set` (applied) — and if `set_title` fails, `title_failed` erases only the text so that the next new version applies even with the same text (`chrome::book::apply_title`). Tauri 2.11.3 facts (confirmed from source by the U4 review): a `run_on_main_thread` called from the main thread runs on the spot (`send_user_message` of `tauri-runtime-wry`) — the title job holds only the ledger leaf lock · Tauri internals, so whatever lock the caller holds there is no deadlock path · at `Destroyed` Tauri deletes the window before the user `on_window_event` (`manager.on_window_close`) — the job after that does not create an entry because `get_webview_window` is None.
- **A title job arriving after forgetting does not revive the entry** (small fix of the edition 0.3 re-review) — when the handed-over job runs on the main thread, it first checks with `app.get_webview_window(label)` whether the window exists, and if not it finishes without touching the ledger. The `Destroyed` handler is also on the main thread, so `forget` cannot slip in between 「창 있음 확인 → 장부 적기」 within one job. So a late job that arrives after `forget` does not recreate that label's entry (a label is not reused within a run, so no tombstone is kept). Test = a step that gives `ChromeBook` 「창 없음」 (no window) (§10-1).
- **Where to add notifications** — ① `apply::create_window`: `announce` that new window's payload after inserting (now the window pulls at mount, so there is no notification — the head comment of the code) ② `apply::agent_names_updated` (§4-3) ③ boot: after the windows are built (setup ⑧ · ⑨), apply the title once from all window payloads (`apply::sync_titles(state, events)` — the frontend emit is harmless because no window is listening yet) ④ copy acceptance already `announce`s all window tabs (code — `commit` · `after_commit` in `state::restore`).
- **Title at build time** — change the `.title(format!("Engram — {label}"))` of the pop-out · prewarmed window builders (code — `commands::popout::build_window`) to 「Engram」. main's configured title 「Engram Dashboard」 (`tauri.conf.json`) also becomes 「Engram」 — the first title is soon overwritten by boot ③.

## 5. Concurrency · order

### 5-1 Locks · ports

| Lock | Kind | What it does while held | Order |
|---|---|---|---|
| Layout `LayoutState(Mutex<ViewManager>)` — including numbers · `closing` · the name ledger | existing | only model mutation · payload copy · `SubscriptionSync::resync` | outer |
| Prewarmed window pool `SpareState` | existing | — | layout → pool |
| First-paint gate `FirstPaintGate.held` | existing | — (adds one `is_held` read) | layout → pool → first-paint gate (leaf) |
| Window facts `tab_drop::FrameBook` | existing | field comparison · recording | leaf |
| Chrome `chrome::ChromeBook` (the adapter's `Mutex`) | new | decisions only — no OS call · emit · other lock while held | leaf |
| Deferred maximize `state::placement::DeferredMaximize` | existing | — | leaf (code — the type's doc 「락은 잎이다」) |

- **All new OS calls (title · minimize · maximize · minimum size · state read · front-window read) are outside the layout lock** (「락 규율」). State reads follow the same order as `WindowPlacement` — read outside the lock and pair them with the model rows (a query answer is a momentary value).
- **Applying the title is one main-thread line** (§4-4) — the version comparison of `ChromeBook` and `set_title` run in turn inside the same main-thread job (no OS call is made while holding the lock — the lock is released after the comparison and then the call is made. The two jobs of the same window cannot interleave because the main thread is a single line).
- **The name ledger is a field inside the layout lock**, so there is no new order.

### 5-2 Windows not yet visible · window state commands = one main-thread job (review codex ⑥ · edition 0.3 re-review ② ③ — main decisions M23 · M29 · M30)

A new window · restored window is 「올려져」 (put) on the first-paint gate while hidden until the first-paint notification or the deadline (`first_paint` — that gate owns showing), and a window after hide-all is revealed by tray show · `window.showAll` · `window.raise`. tao's maximize · minimize · restore reveal a hidden window (code comment — `state::placement::DeferredMaximize`, 「숨은 창을 최대화하면 tao 가 `SW_MAXIMIZE`(창을 보이고 활성화한다)를 낸 뒤에야 `SW_HIDE` 로 되숨긴다」). So for a window that is not visible, do this:

| Window | `minimize` | `maximize` | `unmaximize` | `raise` | `close` |
|---|---|---|---|---|---|
| Visible | do it | do it | do it | §6-2 | §5-4 |
| Awaiting first paint (has an entry on the first-paint gate — `first_paint::is_held`) | `CONFLICT`「아직 첫 화면 전인 창」 | record the desired maximized state `true` (`DeferredMaximize` — a bool per label · it overwrites what was recorded earlier · model `attrs.maximized = true`) — applied when shown · answer `{ deferred: true }`. If already maximized (not minimized), only withdraw the recorded desire · `{ deferred: false }` | record the desired state `false` (model `attrs.maximized = false`) — applied as the original size when shown · answer `{ deferred: true }`. If already normal size (not maximized · not minimized), only withdraw the desire · `{ deferred: false }`. Does not reject | do nothing — the first-paint gate will show it soon · answer `{ shown_all: false, focused: false, pending: true }` | do it (closing is unrelated to showing) |
| Hidden (hide-all · `--hidden`) | `CONFLICT`「숨은 창 — 먼저 window.raise 또는 window.showAll」 | same as above (the next show applies it — code `tray::actions::show_main_ui` · `window_ctl::show_one_no_steal`) | same as above | LLM show (`NoSteal` — §6-2) → bring that window to the front | do it |

- **A minimized window's `is_maximized` is false (최소화된 창의 is_maximized)** (tao 0.35.3 `platform_impl/windows/event_loop.rs` — the `WM_SIZE` of minimizing lowers the maximize flag · source reading) — a window that was maximized and then minimized reads as `min = true, max = false`, so on restore we cannot know which size it returns to. So `maximize` · `unmaximize` of a non-visible minimized window always records a desire (show → restore → apply-desire order — §6-2 ⓑ), and `unmaximize` of a visible minimized window is a no-op (do `window.raise` first).
- **If already that size, the desire is withdrawn** — if not withdrawn, an opposite desire recorded earlier (`maximize` after `unmaximize` of a hidden maximized window etc.) is applied when shown and the later action is reversed. The same holds for a visible window — `maximize` · `unmaximize` withdraw the desire after the OS call, and the no-op branch that is already that size (not minimized) also withdraws the desire and sets the model `attrs.maximized` to that value (`Settle` of `window_ctl::plan`). If applying the desire at show time fails, the desire stays on the visible window (`apply_deferred` leaves it if it could not apply), and the leftover desire is applied at the next hide · show and reverses the action in between. `unmaximize` (no-op) of a visible minimized window does not touch the desire.
- **A hidden window is OS-maximized only when hide-all was done while maximized** — boot · runtime restore also defers main's maximize (records it as a desire and applies it when shown). So a main that came up with `--hidden` is not OS-maximized while hidden even if the saved state is maximized (`is_maximized` false · desire `true`) — `maximize` of that window is a desire overwrite, not `Settle`, and `unmaximize` only withdraws the desire.

- **Read · decide · apply run as one main-thread job** (edition 0.3 re-review ② — M29) — the first-paint show runs on the main thread (code — `release_on_main_thread` → `show_as` → `show_placed` of `first_paint` reads the deferred-maximize table at that time). If, as in edition 0.2, `is_held` were read on the bus thread and the deferral recorded on the main thread, a show could pass in that gap and leave the deferral alone — then `state::placement::record` would stop position recording and the `window:frame` push by an early return while the deferral stands (code — `is_pending` in `record`). So the real port (`WindowControl::apply`) does the state read (`is_held` · visible · maximized · minimized) → table decision (`window_ctl::plan` — pure) → recording/withdrawing the deferral · the OS call inside **one `app.run_on_main_thread` job** and waits for its answer. The main thread is a single line, so that job and the first-paint show cannot interleave. The caller is not the main thread, and while waiting it does not hold an async worker either. The `blocking_handler` body of the shell table runs not on a blocking pool but on an async worker of the daemon-client runtime (code — the doc of `offloaded_handler` in `layout/commands.rs`). So the new verbs `window.minimize` · `window.maximize` · `window.unmaximize` · `window.raise` · `window.showAll` · `window.hideAll` and `window.list`, which reads OS state, are plugged in as `offloaded_handler` (they run behind `spawn_blocking`). The invoke `window_control` is an async command. ★Calling from the main thread is not a deadlock either★ — `send_user_message` of tauri-runtime-wry 2.11.3 runs a job handed over from the main thread on the spot (source reading). There are two dangers: ① if it is called while holding the layout lock, that job takes the same lock again (a non-reentrant mutex) ② if the answer channel has capacity 0, the send of a job that runs on the spot stands forever in front of a receive that has not yet come — the real one receives with `mpsc::channel()` (or `sync_channel(1)`) and waits with `recv_timeout` (if the main thread stalls, it becomes an error value without holding a pool thread).
- **The LLM show skips a first-paint wait window · the tray click stays as it is** (edition 0.3 re-review ③ — M30) — the tray show now does `cancel_hold` → `show()` on every window that is not a prewarmed window (code — `tray::actions::show_main_ui`) — it reveals even a first-paint wait window before it has drawn. It is a show pressed by a human, so that behavior stays. The LLM path (`NoSteal` — `window.showAll` · `window.raise` of a hidden window · invoke `show_main_ui`) skips windows with `is_held` inside the same job — that window will be shown soon by the first-paint gate (invariant 5).
- **Every show branch applies the deferred maximize** — now, among the first-paint shows only the 「지어서 올린 창 · 복원 창」 branch (`state::placement::show_placed`) and the tray show apply it, and the branch where the window port built a window without focus · the branch that hands over a prewarmed window (`raise_and_show` · `show_adopted` of `first_paint`) do not (code — the head of `first_paint`, 「보이는 법은 셋이다」). U7a attaches desire-applying (`apply_deferred_maximize` — the desire becomes a bool, and `false` applies the original size) to those two as well (a no-op if nothing was recorded).
- **Tests** (edition 0.3 re-review ②) — put in `lib_unit` a 「메인 스레드 줄」 (main-thread line) imitation (a queue that runs jobs one at a time in the order they were put in), and for the same window put the 「첫 화면 보이기 일」 (first-paint show job) and the 「`maximize` 일」 (maximize job) in two orders: (a) show first → `maximize` is decided as a shown window and applied on the spot, and the deferral table is empty (b) `maximize` first → it is recorded in the deferral and the later show applies it and withdraws it. In both orders the deferral table is empty at the end (= `record` does not stop). `unmaximize` · hidden windows · the wait-window skip of LLM `showAll` are also measured with the same imitation. The pure decision function `plan` is measured separately by table tests.

### 5-3 Three places that make a new window — the answer (R6 · AC2)

Open (outside the lock — as is) → insert (lock — takes the number · copies the payload) → announce (outside the lock — applies the title) → confirm (outside the lock — `settle_new_window` as is) → answer `{ window, window_id, number }`. The first paint is not waited for (decision · 2026-10-24 — T1). A new window is shown, as now, on the first-paint notification or at the 1.5 s deadline (`first_paint::FALLBACK_REVEAL` as is) — a window shown first at the deadline is before its first draw, so the number marker may not be there yet (accepted — PRD edition 0.5 AC2). A webview dying after the first paint · a window shown at the deadline without having drawn is not handled separately (T1).

### 5-4 Joining the closing paths (R10 · R23 · AC8 · AC24)

### 5-5 0-tab self-close re-check (R23 · W9 · AC24 · AC32)

- **Put into model terms** — a pop-out entry drops out of the model in the very operation in which its tabs reach 0 (code — `PopoutRemoved` of `ViewManager::pull_tab`). So 「아직 탭 0 개」 (still 0 tabs) = **there is no entry for that label in the model**, 「그사이 탭이 들어왔다」 (a tab came in meanwhile) = **there is an entry in the model** (if there is an entry, it has at least one tab — invariant). There is no entry with 0 tabs.
- **Command** — the web (the 0-tab effect of `WindowLayout.tsx`) calls, instead of `getCurrentWindow().close()`, the registry-routed invoke `window_control{ Close, if_empty: true }` with its own **persistent id** (payload `window_id` — the value it received while it had tabs).
- **Decision (`window_ctl::close_if_empty(state, host, window_id)` — before the resolver · one lock)** — inside the lock, in order: ① if an entry with that id is in the model, `Kept` (no-op · not an error) ② if not, and `closing` has that id, pick that label ③ if neither, `Kept`. Outside the lock: if the OS window of the label from ② is open, `host.close` → `Closed`. ①–③ are inside one lock, so there is no gap for a tab to come in meanwhile (if one comes in, it is ①).
- **AC32 「새 창(다른 영속 id)은 닫히지 않는다」** — it looks up by persistent id, so it does not touch other windows (a label is not reused within a run either).
- **How to measure** — that state (not in the model and the OS window exists) does not arise in production in the normal flow (the backend does the close directly — code, the 0-tab effect comment of `WindowLayout.tsx`). Make it with the unit harness (a plain close where the fake `WindowHost::close` does nothing) and measure (§2-3 「시험 몫 도우미」 · PRD edition 0.5 AC24 · AC32).

### 5-6 Restore · copy acceptance (D3 · W12 · AC25 · AC31)

- Boot = §4-1. Copy acceptance = the current order as is (② build hidden new pop-outs → ③ commit (`adopt_restored`) → ④ show · withdraw old windows — code `state::restore`). Numbers are set at ③ (§4-1 table). Because the withdrawal of old windows at ④ is after the copy windows are shown, the same number can briefly stand on two windows — **an accepted risk** (W12). The order is not changed (PRD D3 「지금 코드 차례여도 된다」).
- **No overlap remains** (AC31) — the old pop-out numbers are all released at ③ (including `closing`), and the `Destroyed` of an old window finds by label alone through `release_closing(label)` and does not touch the copy windows' numbers. `forget_vanished` at ④ (a copy window that vanished before the swap) is released at once by `drop_window_gone` (§4-1). A new window inserted after ③ receives the smallest free number.

### 5-7 Accepted brief overlaps (what is not blocked again)

During restore · copy acceptance (W12) · the number gap in `window.list` while waiting for `Destroyed` (the price of D13 — written in the help). Commands point by persistent id, so they do not go astray (Q9).

Two things accepted in the name ledger (§4-3) (main decision · U3b review 2026-10-25):

- **The rename of a sleeping · dead agent is not reflected in that slot's tab until that agent comes alive again** — `list_agents` carries only live sessions and the shell does not rebuild the name.
- **There is no order among the parties that emit `AgentListUpdated`** — an old list emitted by a concurrent spawn · stop revives old names until the next list, and revives a finished agent in the web roster, so the tree looks alive and that view can go through a subscription rejection and settle as `error` (the list arrives only on spawn · stop · roster verbs · reconnect, so if quiet it can last long · U3b increased the number of emitters). It is a pre-existing class of race, and the real fix is a list version number in the protocol (out of scope).

### 7-7 Minimum window width · saved size (R20 · D14 · D15 · AC22 · AC27 · AC34)

- **Calculation (web · per window — `minWindowSize` in `titleRow/metrics.ts`)** = left margin of the tab strip + `TAB_MIN_ACTIVE_W` (52) + the `+` cell (now 4 + 22 — `TAB_ADD_GAP` · `TAB_BUTTON_SIZE` in `tabStrip/layout.ts`) + `GRAB_MIN_W` + the current width of the number marker (the measured value · not counted below `MARKER_MIN_W`) + buttons 3 × 46 (only when drawn). With a one-digit number = 286 + left margin (calculated — on-screen measurement 미검). Screens before the number is received (prewarmed window wait · loading · boot failure) do not send it (see 「보고」 below). Minimum height = normal-state row height (34) + cell minimum (`min_pane_px` — that value of ADR-0227 · the web `MIN_PANE_PX` 30 in `splitPreview.ts`) = 64 — the same value is sent for maximized too. Rounded up to an integer.
- **Report (보고)** — new invoke `report_window_min_width { width, height, seq, epoch }` (web → shell · `titleRow/minSizeReport.ts` · the window label is taken by the shell from the Tauri window · same shape as `report_window_canvas` — the arguments are only numbers, so there is no generated binding · outside the range 1~4096 = `Err`). ★Send only after the window number has been received★ (U8b review fix · main decision 2026-10-26) — for a prewarmed window the wait-time report and the after-taking-in report are the same page, so they cannot be told apart by the report sequence number below, and if a wait-time report in flight (width 120) first withdraws the open marker recorded at take-in time, the taken-in window is not widened and pulled. Widening by the width of a loading · boot-failure screen (no marker) is the same mismatch, so it was left out together (that screen has no OS minimum size — accepted). Other branches = let the shell withdraw only a page newer than the `epoch` at the time it recorded the marker (it cannot block, since it is the same page) · add a 「대기」 (wait) flag to the report (grows the wire). Sent after the number is received · when the marker · buttons · left margin change · when the marker width changes (observation) — the same value is not sent again and only one is in flight at a time. The answer deadline of one attempt = `MIN_SIZE_ATTEMPT_TIMEOUT_MS` 1 s — an attempt past it is treated as unknown whether it reached the shell and moves on to the next turn (same-value retry · a newer value) (so that one unanswered invoke does not block all later reports · the order is decided by the report sequence number below). **Sent before the first-paint notification** — so that widening finishes before the first-paint show (the order in the web `WindowLayout` — `reportFirstPaint` after the report `await`. The wait upper bound = `MIN_SIZE_WAIT_CAP_MS` 300 ms — even if there is no answer or it is rejected it does not block the first paint. A window shown first by the 1.5 s deadline · that upper bound may be widened after being shown — accepted under T1). The U8a shell only recorded the report in the ledger (`ChromeBook`), and from U8b it applies it as decided below inside the same synchronous command (main thread) — so while the first-paint notification waits for the report answer, the shell finishes widening-and-pulling the hidden window and applying the OS minimum size (the answer goes after that).
- **Report sequence number (보고 순번)** (main decision · U8a review 2026-10-25) — an attempt put down at the deadline can reach the shell later than a newer attempt, so the order is decided in the shell. `seq` = a sequence number (from 1) that goes up by one each time a send is made within one web page (retries included) · `epoch` = the wall-clock ms at which the page was read, `Math.floor(performance.timeOrigin)` (u64 — the later it is re-read the larger · had it been random, a late report of the page before the re-read would have overwritten the new page's value · two pages read in the same ms get mixed as one page — not handled). The shell `ChromeBook::record_min` compares `(epoch, seq)` lexicographically — if it is an old `epoch`, or in the same `epoch` not newer than the accepted sequence number, it is not recorded and returns `Ok` (debug log) · a larger `epoch` restarts the sequence count · `forget` erases it together — regardless of arrival order, the value last sent by the newest page remains. The web records as 「셸의 지금 값」 (the shell's current value) only the success answer of the largest sequence number (an answer for an older sequence number is discarded even if it came after the deadline) · and at the moment it sends a new sequence number it returns that value to unknown — the same-value skip compares only with that value.
  - **A re-read after the wall clock went backwards** (accepted limit · not handled — the same as two pages in the same ms · code reading 2026-10-26) — if the web page was re-read while the window stayed the same (same label · no `Destroyed`) and in between the wall clock went backwards so that the new page's `epoch` is smaller than the previous page's `epoch` recorded in the ledger (if equal, it is the 「같은 ms」 branch above), all of the new page's reports are `Stale` regardless of sequence number — not recorded · the open marker not withdrawn · nothing applied, yet the answer is `Ok`, so the web records it as reached and does not send the same value again (the `epoch` is fixed per page, so it is not released during that page). Meanwhile that window's OS minimum size follows the last value of the previous page remaining in the ledger (`on_frame` also applies that value again) — released when = that window disappears and `forget` erases the entry · or the re-read page's `epoch` exceeds the previous page's value. main does not disappear during a run (close = hide all windows — ADR-0302) and the ledger is only in memory, so it lasts until the app is started again.
- **Decision (pure — `chrome::ChromeBook`, review Claude ⑩)** — the shape U8b built (2026-10-26):
  - `mark_opening(label, state) -> MinPlan` — written by the shell when a window is **opened** (six places): the fresh build of the window port's `open` · `open_at` (the `Fresh` branch of `commands::popout::open_new_window`) · `committed` of a handed-over prewarmed window (`commands::spare::commit` — confirmation · **before** the `spare:adopted` notification) · building the boot-restore windows (`open_static` (main) · `open_popout` of `state::placement`) · building the hidden pop-outs of copy acceptance (`TauriRestoreWindows::open_hidden`) · **applying main's position at copy acceptance** (`TauriRestoreWindows::place_main` — U8b review fix · PRD AC34 「사본 수락」 does not exclude main). All are called **after** the window is built (for main, after the position is applied). The adapter (`chrome::mark_opening`) hands the recording over as a main-thread job and creates the entry only after seeing in that job that the window exists (the invariant at the head of the ledger — if called from the main thread, it runs on the spot). It runs before that window's first report — the main thread is a single line and the report arrives on the same line after the page is read (for a taken-in prewarmed window it is recorded before the take-in notification). **The decision is made once, after that window's minimum size is received** — if not yet received (new window · taken-in prewarmed window — no report during the wait), a marker is set and the next accepted report decides; if already received (main — it is not rebuilt, so that page does not report again unless the value changes), that job decides at once from `state` (read after the position is applied) — if `Normal`, widen-and-pull and ★always re-apply the received value to the OS★ (even if it equals the value recorded as applied — even if the ledger and the OS have diverged, it is fixed at open time · U8b review 2 fix · before that = only when different from the applied value).
  - `lift_min(label, state) -> bool` — **before** applying a new normal position to a window that is not rebuilt (now only copy acceptance's main — adapter `chrome::lift_min`). It sets the open marker, and if `Normal` and the OS minimum size has been applied, it forgets the applied value and withdraws it (`set_min_size(None)` — not withdrawn if maximized · minimized · reason above). If not withdrawn, the OS grows a narrow copy position to the minimum tracking size keeping the left end, and `fit_min_width` has nothing to do (the width is already the minimum). It does not create an entry (if there is none there is nothing to withdraw). ★Reading the size state · recording in the ledger · OS withdrawal = one main-thread job★ (body `chrome::book::lift` — U8b review 2 fix) — restore acceptance runs outside the main thread (`spawn_blocking`), and a Tauri setter called outside the main thread stands in the main-thread line. Before that, the record was made on the caller's thread and only the withdrawing setter was put in the line, so a report (value Y) of that window that ran in between withdrew the marker, recorded Y as applied, applied it, and the withdrawal queued afterwards erased the OS minimum size — a later size change · open marker looked at the ledger's 「Y 를 입혔다」 (Y was applied) and skipped, so there was no OS minimum size until a different value came. Now the withdraw job · the position setter · the open-marker job stand in the same line in the order they were handed over (tauri-runtime-wry 2.11.3 `send_user_message` → `proxy.send_event` — source reading), and a report runs only before or after the withdraw job. If a report is interposed between the withdrawal and the open marker, that report withdraws the marker and applies, and if the later position setter is caught by that minimum size and grows a narrow position keeping the left end, the open marker re-applies the received value but does not pull (`mark_opening` above — it always re-applies the received value · the width is already the minimum so `fit_min_width` does not move it — it may be left overflowing to the right of the work area · rare · accepted).
  - `on_min_report(label, order, min, state) -> MinReport { verdict, plan: MinPlan { widen: Option<MinSize>, set_min: Option<MinSize> } }` — `state` = the size state of that window (`Normal` · `Other` = maximized · minimized · unreadable — read inside the same main-thread job). **The OS minimum size is applied only when `Normal` (only when different from the applied value) and is neither applied nor withdrawn while maximized · minimized** — the minimum-size setter of tao 0.35.3 (`set_min_inner_size`) re-applies the current size (`set_inner_size`), lowers the maximize flag, and returns the window to its original size with `SW_RESTORE` · if the window is hidden it is shown and activated (source reading — `platform_impl/windows/window.rs` · `apply_diff` in `window_state.rs`). So the 「최대화면 걷는다」 of edition 0.3 could not be built and was withdrawn — maximized rectangle = work area is kept by tao's borderless-window `WM_NCCALCSIZE` (cut to rcWork so it does not cover the taskbar · source reading), and the web's minimum size (several hundred px) is smaller than the work area, so there is nothing to interfere (a screen whose work area is narrower than that = S8). `widen` happens only when that window has an open marker and is `Normal`, and an accepted report (not `Stale`) always withdraws the marker — **widening-and-pulling is once, at open time only** (while a human drags the window to a narrow monitor only the OS minimum size applies — review codex ⑩ · PRD edition 0.5 R20 · AC34). A window that was (OS-)maximized at open is not widened — the maximize of a restored window is deferred until it is shown, and at report time it is normal size, so it does not enter this branch (§5-2).
  - `on_frame(label, state) -> MinPlan` — called by `WindowEvent::Resized` in `lib.rs` (including prewarmed windows — `chrome::on_resized`). If it became `Normal` and the recorded minimum size has not yet been applied to the OS, apply it (a report that arrived during maximized · minimized · a value that failed to apply). If the open marker is standing, it does not apply — so that the size change produced by the withdrawal · position applying of `lift_min` does not apply again at once (the decision that withdraws the marker applies after widening-and-pulling). It does not create an entry. It does nothing when changing to maximized (reason above). The 「창 사실 밀기 길(§6-5)에서 부른다」 of edition 0.3 was moved to `Resized` — a maximize change is always a size change, and the window-fact push stops during a deferred maximize (`state::placement::record`).
  - `min_failed(label)` — the OS minimum size could not be applied → forget the applied value so that the next report · size change applies again. `forget(label)` — `Destroyed` (open marker · applied value · report sequence number all).
  - **Remaining gap (남은 갭) — maximizing on a screen whose work area is narrower than the minimum size** (U8b · 미검 · user-report part) — PRD R20 · AC34 demands 「최대화한 창은 작업 영역이 최소 폭보다 좁아도 작업 영역과 같다」, but since the minimum size cannot be withdrawn while maximized (above), the OS minimum size remains on such a screen. Whether Windows' `DefWindowProc` grows the maximize size to the minimum tracking size too at `WM_WINDOWPOSCHANGING` (Wine grows everything except minimize — inference · likely · tao touches that event only in full screen), and, even if it grows, whether tao's `WM_NCCALCSIZE` cuts the inside to the work area so what is seen stays in the work area, is unknown → S8 measures with a narrow-work-area setup (e.g. 800×600 · 300 % = logical width about 266). If it overflows, the paths to choose from = ① accept it ② reduce the applied minimum size to the work area of that window's monitor (loses the normal-state 「최소 폭이 이긴다」 (R20) on that screen) ③ a `WM_GETMINMAXINFO` subclass in platform (withdraws the minimum tracking size while maximized — large).
  - **Applying order** (`chrome::book::apply_min` — outside the ledger lock · seam `MinWindow` = one window's `widen_to` · `apply_min_size`) — ★widening-and-pulling first★ (if the OS minimum size were applied first, the OS would widen to the right keeping the left end and push out of the work area before pulling) → OS minimum size (Tauri `set_min_size`). ★The value passed to the setter = the reported inner size + the invisible border (outer − inner · the value resolved to logical by the scale)★ (U8b review fix · `chrome::book::os_min_size`) — `WM_GETMINMAXINFO` of tao 0.35.3 (`platform_impl/windows/event_loop.rs`) computes the minimum tracking size with `util::adjust_size`, which for a frameless window removes `WS_CAPTION` · `WS_SIZEBOX` and calls `AdjustWindowRectEx` so it does not add the border, while `WM_NCCALCSIZE` shrinks the inside by the left · right · bottom resize borders · top one or two px (Windows 11 — `calculate_insets_for_dpi`) — passed as is, the inside was dragged narrower than the reported value by about 16 px in width · about 9 px in height at 100 % (source reading). Since it is applied only to a normal-size window, the measured difference is that window's border. The border is proportional to the scale and the logical value is nearly the same even when moving between monitors (a 1 px inside mismatch from rounding of the top border is accepted). Even if widening fails, the minimum size is applied (warn).
- **Widen-and-pull (D14)** — with `widen`, when that window's normal size is narrower than the minimum it is widened to the minimum width, and if the ★visible right edge★ of the widened window goes past the right of the work area, the position is pulled into the work area · if the work area itself is narrower than the window, ★visible left edge★ = the left end of the work area (R20). Visible edge = inside the outer edge by one side of the invisible border (`frame` / 2 — tao puts the same thickness on left and right) — if the outer edge were aligned, the visible window would stand away from the work-area edge by that much (about 8 px at 100 %) (U8b review fix). The range of outer x = `[ceil(왼쪽 − frame/2), floor(오른쪽 − frame/2 − 최소 폭 × 배율)]` · if the two cross, the left wins. If there is nothing to widen, a position that straddles off-screen is not moved. Calculation = the pure function `fit_min_width(bounds, min_w, work, frame) -> bounds` of `state::placement` (the same layer as `resolve_place` of that module · `bounds` = physical outer position · logical inner size · `work` = the work area (physical) of the monitor the window sits on + that window's scale · `frame` = outer width − inner width (physical) — even a window with the OS frame withdrawn has an invisible border for resizing around it from tao (`calculate_insets_for_dpi` · about 8 px each on left and right at 100 % — source reading) · `frame` is added to the three arguments of edition 0.3). Applying = `placement::move_steps` (position only when it changes · size — adapter · outside the lock · main thread).
- **Inner size of old files** (W5 · D14) — the saved size = the inner size (code — the head of `state/placement.rs`), so when the OS frame is gone the first boot window becomes shorter by the frame height. Accepted (PRD D14 — once only).
- **Tabs visible at the minimum width — AC22** (main decision 2026-10-26 · follows user decision Q22 · M35) — the calculation above includes the room for **one** active minimum-width tab, but which tab stands in that room is decided by the tab bar overflow rule (slot docking PRD R24 — Chrome rule · tabs hide whole from the end). So an active tab that is not the first can hide at the minimum width (measured 2026-10-26 — narrow a window whose active tab is not the first down to the minimum width and only the first tab is visible). It is seen as the same branch as the limit accepted by slot docking PRD edition 4.7 R24 (there is no device that pulls a hidden active tab into a visible place — the same limit as Chrome · decision 2026-10-17 — Q22) and is not fixed. The rest of AC22 (`+` · empty draggable area · number marker · three buttons) is measured as is.

### 7-9 Tab drop decision — tab bar zone = first tab ~ `+` × title row (R14 · D9 · AC12 — review codex ① · user decision 2026-10-26)

- **Now (code)** — the base rectangle of the tab bar zone for the drop decision = horizontally from the left of the first tab to the right end of `+` (the place of `+` = the right end of the last visible head — that value at which the tab bar draws `+` · cut at the right end of the tab-bar row) × vertically, if there is a title row, from above to below the title row (including the top margin), otherwise the tab strip (`stripZoneArea` in `tabStrip/measure.ts` — called by `geometryOf` in `tabStrip/useTabDragSource.ts` · option `UseTabDragSourceOptions.titleRow` — passed by `WindowLayout`). `stripZone` in `dock/bands.ts` widens that rectangle up and down by `STRIP_ZONE_PX`. Outside it is a band (canvas) or 「다른 곳」 (somewhere else), and a drop makes a new window (`to ??= { type: 'new_window' … }` in `deliver` of `dock/windowDrop.ts`) — a drop over the empty space right of `+` · the empty draggable area · the number marker · the window buttons is also a new window, and if it is the source window's own tab it is seen as having left the zone (remaining tab — slot docking R15) and a drop detaches it. If there are no tabs, the zone = `+` only · if there is no `+` either, there is no zone.
- **User decision 2026-10-26 (T-66)** — 「탭이 있는 곳(첫 탭 ~ `+`)만 탭바 구역」 (the user decided it after seeing Chrome's drop over tabs — it does not mean the detach boundary of one's own tab is the same as Chrome's: research `slot-docking-chrome-desktop-drag-2026-10-18.md` A5 reads Chrome's detach boundary as outside the horizontal extent of the tab-bar drag area). It replaces the horizontal 「탭 줄 왼끝 ~ 제목 줄 오른끝」 that U8a put in (main decision M26 — a drop over empty space · marker · buttons = end of the tab bar). The vertical extent (the title row — including the top margin `TOP_GAP`) and `stripZone` widening it up and down by `STRIP_ZONE_PX` (15 px on the canvas side) are unchanged — the shell `strip_zone` takes the base as is, so the shell · golden do not change. The insertion-place calculation is also unchanged: another window = `dropIndex` gives the end number at an x past the center of all heads (over `+`) (code — `dropIndex` in `reorderGeometry.ts`) · own tab bar = `draggedLeft` is clipped by `reorderAreaWidth` and stays at the end position (code — `stripAt` in `judge.ts`). Band removal (`zone` of `windowBands`) also sees the same zone.
  - **D-a Horizontal overflow of one's own tab** (decision · 2026-10-26) — a tab dragged from one's own tab bar is also outside the zone when the cursor goes past the right end of `+`: reordering stops and it returns to its place and shows the remaining tab (slot docking R15), and releasing there detaches it into a new window — the current code as is. Rejected alternative = keep one's own tab attached up to the end of `dragAreaWidth` (the measured `available`) — up to the empty space right of `+` (user — if one has to go that far to detach, it is hard to handle).
  - **D-b Top end of the canvas below and right of `+`** (decision · 2026-10-26) — the top 0..15 px of the canvas below and right of `+`, which became outside the zone, belongs to the outer top strip (a drop splits over the whole layout · a preview shows before the drop) — since that above is no longer the tab bar, the strip below treats it as the top end of the content (accepted by the user).
- **Buttons do not block a drop** — a drop over a window button (outside the zone = new window) does not press the button either — an HTML5 drop does not emit `click` (likely · AC12 measures it). The drop is received by the root `dragover` · `drop` (ADR-0296).
- **A drop over a child window outside the webview can be lost** (W14 · edition 0.3) — the same path as ② above may also exist in the **top-edge resize child window** of a window with the OS frame withdrawn (Tauri core `undecorated_resizing` — a `SM_CYFRAME` height at the top end) and in the snap overlay `STATIC` child window (only when the feature is turned on — §8-4) (미검 — inference). Then a tab dropped on the top few px of the drop zone (including the top margin `TOP_GAP`) · the place of the maximize button (which would be a new window because it is outside the zone) ends with no receiver (the source is 「우리 창 위 = 아무 일 없음」 — slot docking Q38 — so the tab is not lost). **Decide after measuring with S14** (main proposal · M33): ① remove that place from the drop zone and accept it ② put a top-level-window-level drop receiver (`IDropTarget` — accepts only our drag data format and passes it to the webview) in platform — ② is large because it replaces tao's file-drop registration.
- **Collapsed drag and the source decision** (edition 0.3 · record) — the web's `tabStrip/dragSource.ts` treats a dragend in the same task as dragstart as a 「엔진이 접은 끌기」 (a drag the engine collapsed) and does not send it to the shell (code — `Flight.sameTask`). The collapsed drag of W13 has its dragend arrive in the **next task** (about 6 ms later) and passes that decision and goes to the shell — the shell reads an end with the button still pressed as a cancel and does nothing, so there is no harm now. Widening that decision comes after the cause of W13 is separated.

### 7-12 Notice strip · restore modal and the title row (user decision 2026-10-26 · T-66 — U8b)

With the OS frame withdrawn, the title row is the only place to move and close the window. Two things used to cover it — the notice strip (`NoticeOverlay` · state file · connection failure) and the restore modal (`RestoreModal` — main only · after an abnormal exit).

- **The notice strip is below the title row** (decision · 2026-10-26) — up to edition 0.3 the notice layer was attached to the very top (`top: 0` · z 40) of the wrapping cell of `AppLayout` · `PopoutPage` and covered the title row (tab bar · draggable area · window buttons) (ADR-0276 decision 2 「TabBar 를 가려도 된다」). Now the caller passes that layer to `WindowLayout` as `notices`, and `WindowLayout` attaches it at the front of the canvas cell (positioned) right below the title row — there is no need to count the title row height separately (normal 34 · maximized 28). The covering shape (out of flow · as much as its lines · z 40 · max height 33vh) is unchanged and covers the upper part of the canvas. ★The loading · boot-failure screens use the same frame★ (U8b review fix) — title row (draggable area · window buttons · the number marker is not there yet · the tab bar's place is filled with a draggable area) → cell (front = notice layer) → screen content. Since there is no OS frame, those screens also need a place to move and close the window (the window buttons reach it even if that window is not in the model — §6-2 「모델 밖 창」 · M34), and the notice layer must be in the same place in the tree on every screen so that React does not remount it, so that the memory of closing with ✕ (`ConnectionNotice` · `StateFileNotice` — what ADR-0277 said not to withdraw) survives in loading → tab screen · boot failure → revival (test = 「화면이 바뀌어도 알림의 닫힘 기억이 남는다」 in `WindowLayout.test.tsx`). That screen's cell does not report the canvas size (only while drawing tabs — ADR-0227). The 「TabBar 를 덮는다」 of ADR-0276 decision 2 · ADR-0277 is changed by this decision — the record is U10 (§12-4).
- **During the restore modal the title row stays blocked as it is** (decision · 2026-10-26 — 「작은 변경일 때만 살린다」 · the size was measured and it was not done). Now `AppLayout` locks the whole layout (including the title row) with `inert`, and the modal's overlay covers the whole window (`fixed inset-0` · z-50). To keep only the title row's window buttons · draggable area alive, one would have to (1) take `inert` off the wrapping cell and hang it separately on the canvas cell inside `WindowLayout` and on the tab bar (the `TabBar` root — a child of the title row) (`inert` cannot be released from a descendant) (2) make the modal overlay start below the title row (move it into the canvas cell or count the row height by the maximized window fact) (3) put a separate overlay on the loading · boot-failure screens and (4) decide that a press on a locked tab slips, like `pointer-events`, to the parent title row (draggable area) and becomes a window drag — four components (`AppLayout` · `WindowLayout` · `TabBar` · `RestoreModal`) · about 60–100 lines + tests, so it was not done. Ways to move or hide the window while the question is being asked = keyboard (Alt+Space · Win+arrows — QA records the result · AC23) · tray hide · taskbar. If a human closes the window meanwhile (Alt+F4 · tray), main only hides (ADR-0229) and the question remains `awaiting` and the modal is as it was when shown again — even if the app is ended, an unanswered copy remains and is asked again at the next boot (code — `state::boot_plugin` test `an_unanswered_copy_survives_a_clean_exit_and_is_asked_again`).

If a grouped branch takes a new variant, it is caught regardless of syntax. If the range is cut, that variant is missing only when the cut place is earlier than that variant's branch, so it fails on the closed side — a grouped branch hidden after the cut, cut after all variant branches, is not seen now and ① catches it when the next variant is added. ② Branch shape — the `match` line indentation + 4 is the branch position, and the line at that position holds at most one `=>` (FAIL if a second branch is written on one line), except for `}` · `},` · `} => …` (the end of a multi-line structural pattern), what precedes `=>` must not be empty, and after stripping a leading `|`, every branch obtained by splitting what precedes `=>` by `|` must start with `SlotContent::`. A `=>` at any other place (a nested `match` · a guard that rustfmt moved to the next line etc.) is FAIL. Pair = exactly one column-0 `pub fn slot_label` and the `#[deny(clippy::wildcard_enum_match_arm)]` before it (`#[…]` · `//` lines allowed in between) · no `allow` · `expect` · `warn` that turns off this lint in that file · no rustfmt skip (`rustfmt::skip` · `rustfmt_skip`) anywhere in that file (it turns off the rustfmt shape that ② relies on — U1 review 3) · a `match` outside comments · the helper's own tests (a branch-shape violation · samples that are not violations and a fake enum/body missing one variant — counts fixed). **The intent is as in edition 0.3 — a new variant cannot pass before it is given a name, and no wildcard · grouped-name branch is placed** (main decision · U1 review 2 · 2026-10-24 — the negative gate that enumerated violation shapes with regexes (the one line of edition 0.3 · the four branches of review 1) kept leaking on `Other =>` · `other | other =>` · `other @ &_ =>` · a column-0 `}` in a raw string cutting the range so later branches are missing · comment-text false positives. A positive check that passes only the allowed shape does not need that enumeration). So `slot_label` is kept as a column-0 function whose body holds one `match` only, and its branches use only `SlotContent::<변형>` path patterns (a guard's `||` · a `crate::…` path · a nested `match` are caught on the closed side — written at the head of the file). CI has no clippy, so the function attribute alone does not enforce it (main decision M15). What it relies on = rustfmt (`cargo fmt --check`) places the branches on separate lines at 4-space indentation. Remaining holes = multi-line block comments · branches built by a macro · `SlotContent::<변형>` inside a body string (it fools ① — even then ② and the compiler's exhaustiveness check remain). **The three deliberately-deceiving shapes are accepted** (user acceptance · U1 review — U1 commit `4cefce48`: the limit of a text-check gate · the purpose is preventing mistakes. Argued in U1 review 3 — a raw string holding a fake `match` · a `SlotContent::<새 변형>` inside a string that fills ① · leaving the exhaustive `match` unreachable and returning early before it with a helper that has a grouped branch — code review sees them · ADR-0301 invariant 4).
- **AC10 (the web does not call window-control APIs)** — the one rg line of edition 0.1 is bypassed by line breaks · aliases (`const w = getCurrentWindow(); w.close()`) (review Claude ⑦). Instead one vitest test (`src/__tests__/noWindowControl.test.ts`) type-checks `src/**/*.{ts,tsx}` (test files excluded) with the project `tsconfig` through the TypeScript compiler API, and fails if it finds a **property access whose receiver type is `Window` · `WebviewWindow` of `@tauri-apps/api`** named `close` · `destroy` · `minimize` · `maximize` · `unmaximize` · `toggleMaximize` · `show` · `hide` · `setFocus` · `unminimize` (main decision M25 — `typescript` is already a dev dependency · `npx tsc --noEmit` uses it). Aliases · line breaks · destructuring (`const { close } = getCurrentWindow()` — that shape is also seen via the source type of the binding element) are caught by type. The places that use `getCurrentWindow` now (label · `listen` part — code) are not caught.
