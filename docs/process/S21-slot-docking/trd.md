## 0. Summary of conclusions

- **Drag = WebView2's HTML5 drag and drop** (VS Code style · image = tab name label). **While dragging, the drag does not sync its own decisions · state with the shell — the drag command is sent on drop** (ADR-0297 decision 1). Shell calls unrelated to the drag (terminal size fitting · window frame lookup · canvas size report · the LLM's tab · window operations) flow as usual while dragging — neither blocked nor deferred (§2-2 · §4-7). Per drag, the shell commands after it ends are `tab_drop` **at most two** (one from the source dragend + one from the receiving window) + restoring the original selection `switch_tab_if` 0–1 times (§2-2 · §4-6), and the drop write (`dock_tab`) happens **at most once**.
- **Our window's webview receives our tab drag anywhere** (`preventDefault` at the root) — when released over our webview, drop always arrives at that window. That window picks with the pure decision `judge`: tab-bar zone → `TabBar` · valid band → `Seam` · anywhere else (cell center etc.) → `NewWindow{by: Drop}`. The shell applies it once through the same `apply::dock_tab` as LLM commands — it re-finds the target the drop pointed to by id, applies against the current state if it exists, and does nothing if it does not (ADR-0297 decision 2 · §3-3).
- **The source sends `NewWindow{by: DragEnd{effect}}` on every dragend** (both `none` · `move`) (`effect` = its own `dropEffect` · neither a drop at the same place in the same window nor a drag the engine aborted is sent — §2-4 ④). **After the drag ends**, the shell first reads the cursor · primary button · Esc · **the topmost window under the cursor (z order)** and tells them apart: `none` and button · Esc pressed = cancel · topmost window is our window = ignore (when `move`, ignore even if the topmost window cannot be read — wait for the receiving window's `Drop`) (if our webview received it, that window's `by: Drop` wins · over the title bar · border nothing happens — user decision Q38) · anywhere else = a new window at the cursor position (even if another app received it — user decision Q39 · if it is a pop-out with only one tab, move that window — restore first if it was maximized). That is, a drag released outside our webview is 「우리 창 위면 아무 일 없음 · 그 밖은 전부 새 창」 (exception — §9-2 · §9-5: the LLM moves the dragged tab to another window or closes it while dragging). The shell notifies the result only to the source window for each handling (`tab_drop:done` — it does not notify duplicates, nor `DragEnd` that held `Drop` of the same drag before the new window was rejected · §3-2 ④), and on cancel · ignore the source restores the original selection (not if its own dragend is `move` — §4-6).
- **Visible behavior** — own tab bar = Chrome-style reorder (transform only) · other window's tab bar = 2 px vertical line · cell = 10% band · outer 20 px band (a band that would give a zero-area cell in the result is neither painted nor picked — R8) · attach size preview · the source window shows the remaining tab once it leaves the tab-bar zone (R15 · web display only).
- **The source of truth for decision geometry = the shell (Rust)** — the pure functions of the old `dock/{geometry,sizing,strip}` are moved to `layout/` and kept (the T-65 LLM command uses them), and the web keeps a mirror (`bands.ts` · `dockedTree.ts` · `dragSize.ts`) to use on every dragover. The two are tied by one golden JSON that both sides' tests consume (precedent `queued_input_golden.json`). **Constants (band 10% · tab-bar zone 15 px · attach share cap 0.5 etc.) are set in one place in Rust, and TS reads one `src-tauri/bindings/DockConstants.ts` made through the binding generation path** (§4-5). The original size · new-window size are computed by the source webview at dragstart and carried — materials = the window facts the shell pushes only on change (`window:frame`) + `screen.avail*`.
- **New window = adopting the hidden prewarmed window** (ADR-0299 · §3-9) — when the app starts, build one hidden window, and a new window puts the tab in that window, paints the first screen, then shows it (the window is shown together with its content — user decision 2026-10-19). Build the next one right after use · if there is none, build new as now. The window port (`layout::apply::WindowHost`) hands it out, so the application service does not know Tauri. **Which new windows use it = every new window opened with a new label** (§9-3 prewarm F1 (b) — user decision 2026-10-21). The gain figure is a hypothesis (M14).
- **Removed ≈ 15,000 lines** (§5-5 — the spare-window share that is kept is not yet subtracted). **Migration** = U0 ((B) split commits) → U1 shell commands → U2 geometry move · web pure module · golden → U3 switch → user measurement → U4a′ · U4b′ · U4c′-1 removal of the old engine (spare window kept) → U4c′-2 spare window move · rename → U4d′ prewarmed window adoption → U5 platform → U6 model slimming → U7 docs — it is green after any unit where it stops.

## 1. Premises · relations · accepted costs

- **ADR-0296** — OS drag · the model moves once on drop (`layout::apply`) · the preview is on the target webview · outside the window the shell reads the cursor · **zero shell calls during a drag is the invariant** — **ADR-0297 narrowed the scope**: while dragging, the drag does not sync its own decisions · state with the shell — the drag command is sent on drop. Shell calls unrelated to the drag are not blocked. The `tab_drop` after dragend · the input reading inside it · restoring the original selection happen after the drag has ended, so they do not break this invariant.
- **ADR-0297** (amendment of ADR-0296) — nothing is blocked while dragging (§2-2 · §4-7) · on drop the shell re-finds the target by id and applies against the current state if it exists · no-op if not (§2-4 · §3-3).
- **ADR-0299** (amendment of ADR-0296 decision 5) — instead of removing the spare window, keep one hidden prewarmed window for new windows to use · build the next right after use · if there is none, build new (§3-9). The rest of decision 5 (move loop · hook · shell drag session · geometry report) and the guide window removal stay. The user decisions it relies on = the window is shown together with its content (2026-10-19 — `src-tauri/src/first_paint.rs:2-3`) · no off-screen waiting place (2026-10-19 — the only record is one code comment (U4c′-2 moves it — `src-tauri/src/commands/spare.rs:74`) and it is not in the docs, so ADR-0299 decision 3 becomes the docs record).

## 2. Who owns what · flow

### 2-1 Ownership

| Subject | Owns | Does not own |
|---|---|---|
| **Source webview** (the dragged tab's window) | starting the drag (carrying · original size · new-window size · dragged tab shape · image) · its own tab-bar reorder look · showing the remaining tab on leaving the zone · the dragend command (none for drop in place · a drag the engine aborted — §2-4 ④) · releasing the swap-render by `done` (and the safety-net triggers) · restoring the original selection after cancel · ignore (conditional `switch_tab_if` — §4-6) | model writes (restoring is also a shell command) |
| **Target webview** (the window under the cursor — including the source itself) | receiving at the root dragover · `judge` (tab-bar zone · valid band · anywhere else) · preview · vertical line · the drop command | model writes · communication with other windows |
| **Shell `tab_drop`** | validating one command · input state if `DragEnd` · topmost-window reading and distinguishing · ledger (duplicates · Drop wins) · new-window position computing · `dock_tab` once · focus of the window that holds the moved tab (§3-2 ⑤) · result notification · one log line | state while dragging |
| **Shell geometry** (`layout/bands.rs` · `layout/drag_size.rs`) | the source of truth for bands · picking · attach share · preview · validity · new-window size — used by the LLM command (T-65) and tied to the web mirror by the golden | is not called while dragging |
| **Layout** (`apply::dock_tab` · `ViewManager::dock`) | model writes · decisions (no target — re-find by id on drop (ADR-0297 · §3-3) · zero area · share range) · notification · output subscription resync | does not know about dragging |
| **Shell prewarmed-window pool** (ADR-0299 · §3-9 — from U4c′-2 `spare/` · before that = `dock/{mod,parked}.rs` · `commands/dock.rs`) | building one hidden prewarmed window · rebuilding · handover (`claim_spare`) · taking back · adoption commit (`committed`) · that window's role answer (`window_role`) · the out-of-model window predicate (tray · `--hidden` · position record) · re-feeding canvas · measures on commit (inside the layout lock — §3-9) | model writes (inserting the window entry is the application service's — the commit is heard after it · what the pool writes to the model is only canvas · measures on commit, two things) · taking the layout lock while holding the pool lock (the pool lock is a leaf — order = layout → pool) · dragging |

### 2-2 What crosses the boundary — invariant

| When | Direction | What |
|---|---|---|
| Normal (outside a drag) | shell → web | `window:frame` (that window's restore size · maximized · frame inset — **only when the value changes**) · at mount pull `window_frame` (§3-8) |
| Press (pointerdown) | web → shell | the existing `switch_tab` (R2 activate at the moment of press — before the drag starts · same path as a click) |
| dragstart ~ drop · dragend | web ↔ shell · web ↔ web | **nothing drag-related** — the drag does not send its own decisions · state to the shell (ADR-0297 decision 1). Calls unrelated to the drag (terminal `resizePty` · `window_frame` · canvas size report · LLM command) flow as usual (§4-7). There is no communication between windows either — all the target knows is the type string of the drag data (§4-2) |
| drop on our webview | web → shell | `tab_drop` once — zero times if same window, same place |
| source dragend (both `none` · `move`) | web → shell | `tab_drop{NewWindow{by: DragEnd{effect}}}` once — **zero times for a drop at the same place in the same window · a drag the engine aborted** (user decision 2026-10-20 「드래그 스타트 안보내는거면 엔드도 보내지마」 · §2-4 ④) |
| After handling | shell → web | if applied, the existing notifications `window:tabs-updated` · `layout:updated` → then **`tab_drop:done{drag, outcome}`** (only to the source window (`from`) · at most once per handling · duplicates and rejections that gave way to a held `Drop` are not emitted — §3-2 ④) |
| `done` is cancel · ignore | web → shell | the source's `switch_tab_if(initial, expect = 끄는 탭)` 0–1 times (§4-6) |

- Other communication while dragging (agent output · terminal size fitting · window frame lookup · canvas size report · LLM command and so on) is outside this invariant and is neither blocked nor deferred (ADR-0297 decision 1). The drag does not move the window — if the window size changes while dragging, the receiving window recomputes the band geometry (ADR-0297 「영향」 · §4-5).
- **Terminal size fitting caused by the drag is not blocked either** (ADR-0297 decision 1 — the deferral of the old edition is removed · §4-7) — even if the R15 remaining-tab showing · the `switch_tab` of the press changes the `display:none` of a keep-alive tab and `TerminalSlot` sends `resizePty` while dragging, it is left as is. Because it is not a decision · state of the drag. Test = C7 (counts only drag commands · §8-4).
- **One drag = `tab_drop` at most two · drop write (`dock_tab`) at most once.** The source sends one `DragEnd` on every dragend (§4-2 · a drop at the same place in the same window · a drag the engine aborted both send 0 — §2-4 ④), and if our webview received it, that window sends one more `Drop`. The two usually arrive together, and in whatever order they arrive the shell ledger makes `Drop` win (§3-4). Anything else = the same event delivered twice.
- `window:frame` · `tab_drop:done` are ordinary shell → web events on the existing event surface — not a new global handle (CLAUDE.md 「LLM-우선 제어」). The listening side owns its own disposer (`dock/windowFrame.ts` · `dock/tabDrop.ts` — the subscription lifetime distinction rule). **The web listens to both with `listen(…, { target: getCurrentWindow().label })`** — even if the shell emits to that window only with `emit_to`, a plain `listen()` (target `Any`) also receives events addressed to another window (the `match_any_or_filter` of Tauri 2.11.3 `event/listener.rs`). The `WindowFrame` body has no label, so the receiver cannot tell either. Same shape = `src/api/restoreClient.ts:244-247`.

### 2-3 Flow

1. **Press** — pointerdown on the tab head makes that tab active right away (R2 · `switch_tab`). The web records two things: that window's model-active tab before the press `initial` · the pressed point (ratio inside the head · y). Releasing without moving is a click (S14 5/5). Pressing twice is rename (2/2).
2. **dragstart** (Chromium threshold) — the source webview attaches the carried data · original size · new-window size · dragged tab shape · image (§4-2). Put `effectAllowed = 'move'`, and cut the events with `stopPropagation` (§4-2 react-dnd).
3. **dragover** — every window of ours receives at the root (`preventDefault` · `dropEffect = 'move'` · cut) and `judge` (§4-3).
   - **Source tab-bar zone** = Chrome-style reorder look (R23 · transform).
   - **Other window's tab-bar zone** = 2 px vertical line (W13).
   - **Cell** = valid band · preview (R3 · R4 · R8). If it is not a band, nothing is painted (R6).
   - **The source window shows the remaining tab when outside the tab-bar zone** (R2 · R15 — when it returns to the zone, the dragged tab is shown again).
   - The OS gives no events to places that are not our window · covered places · minimized windows (R15).
4. **The end of the drag** — the source sends one `NewWindow{by: DragEnd{effect}}` on every dragend (whether `dropEffect` is `none` or `move`) (§4-2 · neither a drop at the same place in the same window nor a drag the engine aborted is sent — §2-4 ④). The shell tells them apart (§3-5): `none` and button · Esc pressed = cancel · topmost window under the cursor is our window = ignore · `move` but the topmost window cannot be read = ignore · anywhere else = new window. On top of that, the two split by where the end was.
   - **a. drop on our webview** — the first sentence of the handler is `preventDefault`, so the source dragend is `move`. The receiving window sends one more `tab_drop` with the last `judge` result. The target is `TabBar` · `Seam` · `NewWindow{by: Drop}` (cell center · anywhere else — R6 · R22), and if same window, same place it is not sent (the source dragend is not sent either — §2-4 ④). `DragEnd{move}` of the same drag splits to ignore because the topmost window is our window (or unreadable), and in whatever order the two arrive `Drop` wins (§3-4 — except the case where the topmost window was misread as `Foreign` · §9-1 M13). The source does not restore because of that ignore (§4-6).
   - **b. outside our webview** (another app · desktop · our window's title bar · border) · Esc · abnormal end — a single `DragEnd`. Title bar · border = nothing happens (user decision Q38 — 「별도의 처리를 안하는 방향으로.」) · even if another app received it (dragend `move`) a new window (user decision Q39 — 「새창.」 · if the topmost window cannot be read (`Unknown`), ignore — §3-5 ⑤ · §9-2). That is 「우리 창 위면 아무 일 없음 · 그 밖은 전부 새 창」 (exception — §9-2 · §9-5: the LLM moves the dragged tab to another window or closes it while dragging).
   - The old 「c. 다른 앱이 받음(`copy` · `link` · `move`) = 보내지 않음 · 탭 제자리」 was removed — `effectAllowed = 'move'` so `copy` · `link` was a dead path that never arrives, and `move` became a new window by Q39 (re-review 2026-10-20).
5. **After handling** — the shell emits `tab_drop:done`. Each window store has already been updated by the earlier model notifications, and the source releases the swap-render with `done` (dropping in place in the same webview was already released at dragend — §2-4 ④), and on cancel · ignore restores the original selection (except for an ignore · cancel whose own dragend is `move` — §2-4 · §4-6).

### 2-4 Order · races

- **Releasing the source's swap-render (showing the remaining tab)** — the pure reducer `dock/dragOverride.ts`. **There is no deadline** — there are four release triggers (widened by re-review 2026-10-20 B5 · ④ = re-review round 3).
  - **① `tab_drop:done` of that drag** (right away if its own invoke errors). If `done` is `Applied`, release after 「그 창 스토어의 탭 목록이 dragstart 때와 다름」 has arrived too (moving out · reorder · same-window seam — all three change the list · a pop-out with only one tab has no swap-render). Because the shell emits `done` after the model notification on the same thread, in practice it is the same tick. The model active after the drop (`successor` — §3-3) is the same as the tab that was being swap-rendered, so the screen does not change on release (test §8-3). If its own dragend is `move` and `done{Ignored}` · `done{Canceled}`, it does not release by that (wait for the result of the following `Drop` — the end state is set by the winning `Drop`, and if that `Drop` is lost or that `Drop` is ignored (`no-cursor`), ② · ③ release it · §4-6).
  - **② When, after dragend, that window's `window:tabs-updated` does not leave the dragged tab active** (removed from the list · another tab active — including the LLM's `switch_tab`). So a late swap-render does not cover the tab the LLM picked. It does not release on a notification where the dragged tab is active (such as the `switch_tab` of a late press) — releasing would show the dragged tab before `Drop` is applied (§8-3 ②). A notification where the dragged tab **drops out** of that window's tab list releases it even before dragend (§9-3 U2 ⑥ — left as is by user decision 2026-10-20 「극 예외는 실 발생될때 처리」).
  - **③ That window's next pointerdown · dragstart.**
  - **④ Dropping in place in the same webview — straight from the source dragend.** If the receiving webview is the source itself and drop sent nothing (same window, same place, tab bar — §4-3), that webview records that drag id at drop, and the following source dragend reads it, **sends no `DragEnd` either**, releases the swap-render and withdraws the transform to 0 (user decision 2026-10-20 「드래그 스타트 안보내는거면 엔드도 보내지마」 — same for a drag the engine aborted · §9-3 U2 ⑨). This drag makes zero shell calls, so there is no `done`. The model stays as is, so the dragged tab is visible in that place (same as a click).
  - Since the source sends `DragEnd` on every dragend, `done` usually always arrives, and ④ releases a drop in place that sent nothing · a drag the engine aborted. ② · ③ are only a safety net for when an invoke or an event is lost.
- **Own tab-bar reorder look** — while dragging only transform is used. The DOM order · React key is not changed, and the dragged head node is not detached (detaching it makes the drag source disappear). After the drop, the transform is withdrawn to 0 in the very frame the model notification arrives — so the order does not jump in between. A drop in place that sent nothing has no model notification, so it is withdrawn straight from the source dragend (④).
- **Clearing the target preview · vertical line** (VS Code style) — drop · leaving the window (root `dragleave` · no related target) · **no dragover for 300 ms** · 300 ms after `mousemove` over the overlay (meaning the drag has ended). Even with a stopped cursor dragover arrives about every 63 ms (S1), and a drag that ended in another window gives that window no dragend, so the deadline clears it. `mousemove` over the overlay looks only at the primary button being released (`buttons === 0`) — synthesis while dragging · delayed moves (such as hover recomputation caused by swap-render) are filtered because the button is still pressed (`dock/windowDrop.ts`). ★「HTML5 끌기 동안 출처 · 대상은 버튼 눌린 마우스 사건만 받는다(`buttons ≠ 0`)」 is a premise that has not been measured★ — if wrong, the preview is cleared after 300 ms while dragging and does not come back until a new dragenter (the drop decides at that point — §4-3 · M11 measures it · the net (b) of the old §4-7 relied on the same premise).
- **If the drop reaches the shell before the model notification** (changed in transit — R4 · R13c · the LLM moved the same tab · D9) — the command does not carry the state at decision time, and the shell re-finds the target by id on drop, applies against the current state if it exists · no-op if not (the rule source of truth = §3-3 「놓을 때 다시 찾기」 · ADR-0297 decision 2). It does not reject merely because it differs from the state the drop saw — a slightly off result is not fatal and one can drag again (user decision 2026-10-20 「크리티컬한게 아니고 어차피 유저가 다시 하면 되는거라서」).
- **If the `switch_tab` round trip of the press is slower than the drop** — the active is not cross-checked on drop, so it is not rejected (the `active` precondition of the old edition is removed · ADR-0297).

### 3-1 Shape

- The wire value of `DockSide` is the variant name as it is (`layout/dock.rs` head — no rename). Right now there is no `TS` derive, so **U1 attaches it to `layout/dock.rs:21`** (binding `DockSide.ts`). The rest of the serde tag shape is matched to the neighboring wire types. The decision-time state fields (`TabBar.expect` · `Seam.rev` · `Seam.active`) that U1 had carried are removed by ADR-0297 decision 2 — the shell re-finds the target on drop (§3-3).
- `PointCss` — during U1 ~ U4b′ use the one in `layout/chrome.rs`. When U4c′-1 deletes that file, it moves together with `RectCss` to `layout/bands.rs` (§4-5) in exactly the same shape. If two types with the same name are set up, ts-rs overwrites one binding file with the other — do not set up two. `SizeCss` is set up new. For the frame inset, use the already existing `layout::geometry::Insets` (t · r · b · l · CSS px — binding `Insets.ts`) (only the meaning note is widened).

### 3-2 Shell handling order

1. **Read the input first** — before the lock · ledger. `DragEnd` = platform `input::cursor_pos` · `primary_button_down` · `escape_down`, then `window::top_level_at(cursor)` → if that window is a webview window of ours (compared with `NativeWindow::of`) `TopAt::Ours(label)` · otherwise `Foreign` · if the cursor · window cannot be read, `Unknown`. `Drop` reads only the cursor — the drop event itself is the proof of the drop. Reading 0–0.1 ms after dragend equals the drop point (S14 · S1 — measured only inside our window). **It is a call after the drag has ended** — it reads inside the command the source dragend sent, so 「끄는 동안 끌기 명령 0」 (ADR-0296 · ADR-0297) stays as it is.
2. **`tab_drop::plan(&drop, caller, &InputNow, &SourceFrame)`** (pure · Tauri 0) → `Plan::Dock(DockRequest) | Plan::Cancel | Plan::Ignore(why)`. `SourceFrame` = the source window's frame inset · scale (Tauri getter — read **after** reading the input · §3-5).
3. **Ledger** — if `DropBook::admit` (§3-4) does not accept it, it is `Duplicate` (debug log · no notification). A `Drop` that arrives while a new window of the same drag's `DragEnd` is in progress (including while its rejection notification is being emitted) is also answered with `Duplicate`, but the ledger holds it (④ · §3-4).
4. `Dock` → `apply::dock_tab(&layout, &RouterSubs{..}, &TauriEvents{..}, &TauriWindowHost{..}, &**counter, req)` — the same adapter as pop-out · T-65 (from U4d′ the window of `NewWindow` may be a prewarmed window that adapter handed over — §3-9 · prewarm F1). **Call it from an async command** — calling `NewWindow` from the main thread · a sync command deadlocks window creation (`dock_tab` documentation). **For the new window of `by: DragEnd`**, `DropBook::settle(drag, outcome)` writes the result after `dock_tab` returns (§3-4 · leaf lock · after releasing the layout lock). If applied, discard the `Drop` it was holding in the meantime (one debug line · no notification). **If rejected and there is a held `Drop`, this handling does not emit its own `done`** (the info line of ⑦ stays and `superseded = true` is attached) — since that `Drop` is continued through the same path as a normal `Drop` (④ ~ ⑦), the `done` the source receives for that drag is that `Drop`'s alone. If the rejection `done` goes first, the source releases the swap-render (§2-4 ①) and the dragged tab flashes. **If nothing is held**, set the record to 「거절 알림 중」 (`Rejecting`), and **after** emitting `done{Rejected}` call `DropBook::close(drag)` — it lowers the record to 「거절된 `DragEnd`」, and if a `Drop` was held in the meantime it hands it back and continues through the same path (that `done` comes after the rejection — the order is guaranteed · the flash in that gap is accepted · §9-2). The old edition lowered the record before the notification, so if a `Drop` that arrived in that gap was applied on another thread, that `done{Applied}` could go before the rejection (re-review 2026-10-20 · main's decision).
5. On success and `TabBar` · `Seam`, call Tauri `set_focus()` on the window that holds the moved tab (usually the calling window — if the seam target tab has moved to another window in the meantime, that window · same as the response `Applied.window` · §3-3) (R11b). The 「`set_focus` 금지」 of 6.3 (F7 — the drag key watcher read the Alt synthesized by tao as a drop) is resolved because that watcher is gone. A new window is opened with `open_at(activate = Reveal)` — how it is shown · activation is §3-9 「보이는 차례」 (for a prewarmed window, after the adoption commit it is raised in z and shown on the first paint, and `set_focus` only on the condition of I5 — an active-open handover ∧ the foreground is ours · the fallback new window is the same condition — I30).
6. Response: `DockError` → `Rejected{kind, reason}` · success → `Applied{window, reused}` · `Cancel` → `Canceled` · `Ignore` → `Ignored{why}`. On cancel · ignore the shell does not write the model — the selection the press changed is restored by the source after the end (§4-6).
7. **Notification · log** — after releasing all locks, emit `tab_drop:done{drag, outcome}` only to the source window (`from`) (if that window is closed, skip with one debug line · if applied, after the model notification of `dock_tab` — continue on the same thread · not emitted for a rejection that gave way to a held `Drop` — ④). Log (`docs/reference/logging-conventions.md` — normal lifecycle event = info · identifiers · numbers as fields) = one info line per handling: `drag` · `by` (and `effect` if `DragEnd`) · `view` · `from` · `to` (branch) · `decision` · `cursor` · `button` · `esc` · `top` (`ours=<label>` · `foreign` + that window's class name · `unknown` — the class is used by M13 to tell the drag image window apart) · result (`kind` if rejected · `why` if ignored · `superseded = true` if a rejection that gave way to a held `Drop`) · for a new window `via = spare | fresh | reuse` (U4d′ — computed from `DockOutcome.prewarmed` and `reused` · the prewarm meaning is not layered onto `reused` (the `Reuse` plan of a pop-out with only one tab) · §3-9). `Duplicate` is one debug line.

### 3-3 Mapping table — `DropTo` → `DockRequest`

| `DropTo` | `DockDest` | `focus` | `mv.successor` |
|---|---|---|---|
| `TabBar{index}` | `TabBar{window: 부른 창, index: Some(index)}` (if past the end of the current list, the end position) | `Reveal` | `initial` (when ≠ `view` and the dragged tab is in `from` at apply time — `successor_window = from`) |
| `Seam{target, anchor, side, share}` | `Seam{target, anchor: Slot(id) \| Outer, side, share}` | `Reveal` | 〃 |
| `NewWindow` → drop | `NewWindow{at: WindowPlace{pos: Some(new_window_origin(..)), size}}` | `Reveal` | 〃 |

- **`DockRequest` = `view` · `to` · `focus` · `mv`, four** (after U6 `617cc54a` — `src-tauri/src/layout/apply.rs` `DockRequest`). Two fields of the old table are removed — `DockGuard` (the cross-check container · for a drop it only looked at `DockGuard::NONE` = target existence) goes whole with the marker · the old cross-check · `on_emptied` (a drop is always `Close`) goes by folding `OnEmptied` — a source pop-out emptied and deleted is always closed (§3-7). The rule that only looks at target existence stays (「놓을 때 다시 찾기」 below).
- There is no drag marker (lease) — U6 removed the marker machinery whole (§3-7).
- **`NewWindow` can use the prewarmed window** (ADR-0299 · U4d′ · §3-9) — the label of `DockTo::NewWindow{label}` may be a prewarmed window the window port handed over (if there is none, `LabelSource::next_label` as is). This table stays as it is — in the model it is the same `DockTo::NewWindow` as a new window (U6 removes `seed` · `measures` and carries only one label), and the canvas · measure of the prewarmed window are fed again by the report function at adoption commit (I6). The `DockDest::AdoptWindow` of the old engine was removed by U6 — do not revive it (§3-7).
- **`successor`** — `initial` if `initial ≠ view`, otherwise shell `succession` (right neighbor → left). This is the 「Chrome 규칙이 고른 남은 탭」 of R2 · R15, and it is the same as the tab the source swap-renders while dragging (§4-2). **`initial` is used only when the dragged tab is also in `from` at drop time** (`DockMove.successor_window = from` — `successor` is used only when the moved tab is in that window at apply time) — otherwise the shell `succession` is applied to the window the tab lives in now (「다른 창으로 옮겨졌으면」 below).
- **`size: None`** (a pop-out with only one tab) — the existing `plan_new_window` moves that window to `at.pos` with `Reuse` and keeps the size (Q34). If the tab count grew in the meantime through a race, `Create` opens it at the source's normal size.
- If a pop-out with only one tab is dropped on another window's tab bar or a cell, the source becomes empty and the application service closes that window (Q34 · R10 — always closed · so there is no field to report 「닫았다」 separately — after U6 `DockOutcome.closed_window`, which was always the same as `emptied`, was folded into `emptied` by `d2a67026` (2026-10-23) · `apply.rs` `DockOutcome` documentation).
- **Re-find on drop (놓을 때 다시 찾기)** (ADR-0297 decision 2 · user decision 2026-10-20 — replaces the old 「사전조건을 왜 싣나」) — the decision was made with the web store, and that store may lag behind the model (§2-4). The shell re-finds the target the drop pointed to by id — the dragged tab · target tab (`Seam.target`) · target cell (`anchor = Slot(id)`). **If it exists, apply against the current state** — if the `TabBar` position exceeds the current list length, clamp to the end position · `Seam` attaches to the anchor cell if it still exists (even if it was split in the meantime). **If any one of the dragged tab · target tab · target cell is missing, it is a no-op** (rejection = model unchanged · §3-4). It does not reject merely because the state differs from what the drop saw (tab list · target view edition number · that window's active · source window) — the same as the mainstream of practice (VS Code · dockview · FlexLayout · Zed · Lumino dock — only dockview throws instead of no-op) (research `docs/research/drag-external-events-practice-2026-10-20.md`). The shell carries no state to cross-check on a drop — `TargetExpect::Tabs` · `SeamAt{window, rev, active, or_initial}` · `expect_window` of the old edition were removed (`SeamAt` · `expect_window` = U3 · the remaining old cross-check and its container `DockGuard` = U6 — §3-7). Do not revive (ADR-0297 「영향」).
  - **If the target has moved to another window in the meantime** (main's decision 2026-10-20 — application of ADR-0297 「있으면 지금 상태에 맞춰」) — the dragged tab is taken out of **the window it lives in now**. The tab to remain in that window is picked by the shell's usual rule (`succession` — same as when closing a tab), and `initial` is used only when that window is `from` (`successor_window` — `successor` above). Even if the `Seam` target tab has gone to another window, if that tab and the anchor cell remain, attach **in the window that tab lives in now** and give focus to that window too (§3-2 ⑤ · response `Applied.window`).
  - **Accepted — losing the old `SeamAt.window` cross-check** (ADR-0297 「있으면 지금 상태에 맞춰」) — even if a web defect sends a tab of another window as the seam target, the shell does not reject and silently attaches it to the window that tab lives in. On the normal path this does not occur because the target tab is a visible tab of the calling window.

### 3-4 Rejection · ledger · no change

- **Rejection** — returns `DockError` as `Rejected{kind, reason}` (`kind` = the word inside the parentheses of the error text). Model unchanged · the web does not change the screen and only writes a debug log. Cases = no target (the no-op of ADR-0297 decision 2 · §3-3 — dragged tab · seam target tab = `TabNotFound` · tab-bar window = `WindowNotFound` · target cell = `SlotNotFound` · if that cell went to another tab, `SlotNotInTab`) · `ZeroArea` (when the web mirror missed it — §4-5) · `WindowOpen` · only by a web defect `InvalidShare` · `SelfTarget`. There are no cross-check rejections (`SourceChanged` · `TargetChanged`) and no marker rejections (`Dragging` · `StaleLease`) — `expect_window` · `SeamAt`, which were the drop's share, were removed by U3 (ADR-0297), and those variants, the old engine cross-check that emitted them (`expect_source` · `TargetExpect::{Seam, Tabs}`), the marker and `DockGuard` were removed by U6 (§3-7).
- **Ledger `DropBook`** — the latest 64 drag ids and the branch of each drag: `Drop` (handled) · `Quiet` (`DragEnd` that did not write the model) · `Placing` (new window in progress) · `Rejecting` (new window rejected and its notification being emitted) · `Placed` (new window created). `Placing` · `Rejecting` hold the first `Drop` that arrived in the meantime. `admit(Handling) -> Admit` (`Handling` = command · calling window · input · topmost window class · decision — it holds together what handling uses so that it can be held · `Admit` = `Run(Handling) | Parked | Duplicate`) decides and writes inside one lock. `settle` · `close` are the same lock (a leaf lock — held only inside these three, and while held there is no layout lock · emit · window call). On overflow, forget the oldest of the finished records first — those in progress (`Placing` · `Rejecting`) are not forgotten so that the held `Drop` is not lost (if all 64 are in progress — in practice never — grow it and emit warn once per ledger).
  - First-seen id → accept.
  - **`Drop` but the earlier record is a cancel · ignore of `DragEnd` · a rejected new window (after its rejection notification · `close`) → accept (Drop wins · change the record to `Drop`).** The earlier `DragEnd` did not write the model — if the cursor is over our window (§3-5 ③) · if `move` but the topmost window could not be read (§3-5 ⑤), it does not create a new window — and the definite drop came later.
  - **The new window of `DragEnd` is written as `Placing` at `admit` time, and `settle` writes its result** (§3-2 ④ · re-review 2026-10-20 F6). A `Drop` that arrives while in progress is not handled on the spot (so that the two do not write the model together) and **the ledger holds it** (only the first · the answer to that call is `Duplicate`). When the new window is up, write `Placed` and discard the held `Drop` (no notification). If rejected — if there is a held one, `settle` writes the record as `Drop` and returns it (that `DragEnd` handling continues it without `done` — the source's `done` is that `Drop`'s alone). If there is none, leave it as `Rejecting` so that a `Drop` arriving while the rejection notification is emitted is also held, and after the notification `close` lowers the record to 「거절된 `DragEnd`」 (`Quiet`) — if something was held in the meantime, write `Drop` and hand it back to continue, and a `Drop` that arrives after that wins by the second line above (re-review 2026-10-20 · main's decision). The old edition wrote 「새 창을 만든 `DragEnd`」 before seeing the application result, and discarded the `Drop` after the rejection as `Duplicate`.
  - Anything else (two `Drop` of the same id · `DragEnd` after `Drop` · `Drop` after `DragEnd` that created a new window · the second `Drop` when something is already held) → `Duplicate`.
  - The case that can occur = **a drag our webview received always comes as two** — the receiving window's `Drop` and the source's `DragEnd` (§2-3 4a · the source sends on every dragend · dropping on the same window at the same place is zero for both — §2-4 ④). The order is not fixed. Anything else = the same event delivered twice. If `DragEnd` comes first, that dragend is `move` (§4-3), so if the topmost window is our window or unreadable it is written as ignore and `Drop` wins by the second line above. **If the topmost window is misread as `Foreign`** (drag image · another app's overlay · notification window and so on — M13), it is written as new window in progress and when that new window is up, the later `Drop` is `Duplicate` — a drop our webview received becomes a new window (§9-1 M13 · §9-2). If that new window is rejected, the held `Drop` is continued. If `Drop` comes first, the later `DragEnd` is `Duplicate`.
- **No change** — if same window, same place, the web does not send (the source dragend does not send either and releases the swap-render by itself — §2-4 ④). Even if sent, `dock_tab` is a no-change `Ok`.
- **No retry** — on an IPC error the web only leaves a log. If it is the source's own invoke error, release the swap-render right away, and the source does not know about the receiving window's invoke error (its own dragend is `move`, so it does not release by the ignore of `DragEnd` — §4-6) — the safety-net triggers (§2-4 ② · ③) release it.

### 3-5 New window — decision · position (`tab_drop/plan.rs` · pure)

```rust
pub enum TopAt { Ours(WindowLabel), Foreign, Unknown }
pub struct InputNow { pub cursor: Option<PhysPoint>, pub primary_down: bool, pub escape_down: bool, pub top: TopAt,
                      pub scale: f64 /* 커서 밑 모니터 */ }
pub fn decide(by: &NewWindowBy, i: &InputNow) -> Decision;   // Cancel | Ignore(why) | Place(cursor)
pub fn new_window_origin(cursor: PhysPoint, scale: f64, inset_dip: (f64, f64), grab: PointCss) -> (i32, i32);
//   = cursor − round((inset_dip + grab) × scale)   · round = .5 는 0 에서 멀리
```

**`decide` — the order is the contract**

| # | Condition | Result | Basis |
|---|---|---|---|
| ① | `Drop` | `Place` | The drop event is the proof of the drop. If there is no cursor, `Ignore("no-cursor")` |
| ② | `DragEnd{None}` + (Esc pressed ∨ primary button pressed ∨ no cursor) | `Cancel` | R12 · R13b. At Esc end = button · Esc pressed 4/4 · at drop = both released 5/5 (real input inside our window — desktop = not tested · M1). The button is the firmest discriminator (even if Esc is tapped briefly, the button is still held). `DragEnd{Move}` skips this row — somewhere received the drop, so it is not a cancelled drag |
| ③ | `DragEnd` + `top = Ours(_)` | `Ignore` — `None` = `"lost-drop"` · `Move` = `"accepted-ours"` | If released over our webview, the root always receives it (§4-3), so that window's `by: Drop` comes separately — in whatever order they arrive `Drop` wins (§3-4). If `Move`, that is the usual path. If `None` and there is no drop, it is a lost drop (4.6 defect · AC27 · AC28 · R13b) — no new window is created. The frame outside the webview (title bar · border) is also our window, so ignore = **nothing happens** (user decision 2026-10-20 Q38 — 「별도의 처리를 안하는 방향으로.」). Since the z order is looked at, these are told apart: overlapping windows of ours · a lost drop over another window's tab bar · another app's window covering a maximized source (→ `Foreign`) (R22 · AC8) |
| ④ | `DragEnd` + `Foreign` (both `None` · `Move`) · `DragEnd{None}` + `Unknown` | `Place` | R22. `Foreign` is the same even if it is `Move` (another app received the drop) — **new window** (user decision 2026-10-20 Q39 — 「새창.」 · accepted limit = §9-2). If the topmost window is misread as `Foreign`, a drop our webview received also comes here (§3-4 · §9-1 M13). `Unknown` + `None` = outside Windows · read failure — falls toward a new window (§9-2) |
| ⑤ | `DragEnd{Move}` + `Unknown` | `Ignore("accepted-unknown")` | The receiver is unknown — if it is our webview, wait for that window's `Drop` (same as ③), and if it is another app, there is no new window (§9-2). So even outside Windows (`top` always `Unknown`) our webview's drop does not race with `DragEnd` |

- **Removed** (edition 7 draft · review 2026-10-20) — the web ↔ web 「아직 받는 창이 있나」 (VS Code `isWindowDraggedOver` · `BroadcastChannel`) · the 48 px edge (`EDGE_PX`) refinement · 「커서가 출처 창 바깥 사각형 안이면 무시」. The tally is wrong with overlapping windows (even dragging A over an overlapping B and releasing on the desktop outside B, 「받는 중」) · the tab-bar zone is inside the edge band, so a lost drop over another window's tab bar was read as 「떠남」 and a new window was created (AC27 recurrence) · the rectangle rule did not know z, so dropping on another app's window over a maximized source created no new window (R22 · AC8 violation).
- **`top_level_at`** — keep a thin one from platform (ADR-0296 decision 5 left to the TRD whether to keep it · §5-1 · this TRD is written as its source of truth in the ADR-0296 related line). Walk from the top of the z order and skip invisible · minimized · DWM-cloaked · see-through windows (windows that let clicks pass · transparent layered windows of other apps — B2 `hit_accepts`) — even if a screen-capture tool's overlay covers our window, it is read as our window (M8). **The drag image window is not of our process** — the drag source · image is inside the WebView2 browser process (ADR-0296 「거부한 대안」 third), so it shows up in `hit_accepts` as `ours = false`. If that window remains at dragend and is read as the topmost (M13), skip it by **window class**, not by process (§9-1).

**Position · size**

- **`scale`** = the scale of the monitor under the cursor (Tauri `monitor_from_point` · if none, the source window scale).
- **`inset_dip`** = the source window's (inner origin − outer origin) ÷ source scale — computed with **the same single shell function** as the frame inset of `window:frame` (§3-8). The premise is that the window frames of pop-out and main are the same. If T-66 removes the title bar, it approaches 0.
- **`grab`** (computed by the source webview at dragstart) = (tab-bar left + r × W1, pressed y) — r = the width ratio of the pressed point inside the head · W1 = the head width of one tab in the new window's tab bar (computed from the new window width with `layout.ts` — usually 160). PRD R22 「커서 − 끌기 오프셋 — 누른 점의 탭 안 상대 위치를 지킨다」 (Chrome `GetTabOffsetForDetachedWindow`). VS Code's 「커서 − (폭/2, 30 + 높이/2)」 is not followed, because the PRD decided otherwise.
- **A pop-out with only one tab** — that tab is already the first tab and W1 = the current head width, so `grab` is the pressed point. So `Reuse` moves the window **by the amount it was dragged** (Q34 · exact at the same scale · M2 if scales are mixed).
- **Dropping a maximized pop-out with only one tab outside the window** (user decision 2026-10-20 「1. 맞고」 — PRD Q37) — restore it, then move to 「커서 − 끌기 오프셋」 (same formula). `WindowHost::move_window` already releases the maximization of a maximized window and shows it at normal size (`apply.rs` documentation). The W1 of `grab` is computed with the restored window width.
- **`size` (new window size · R22)** = computed by the source webview at dragstart and carried (§4-2). The shell only checks that it is finite · positive, and if not, replaces it with `None` (the existing `plan_new_window` size). A new window is not made maximized.

### 3-8 Pushing window facts — `window:frame` (materials for R7 · R22)

- **The web does not have it now** — `WindowTabsPayload` has only tabs · active · version. The model `WindowAttrs` has `bounds` (restore — physical outer position + logical inner size) and `maximized`.

### 4-2 Drag source — `useTabDragSource`

- **`draggable` condition** — not while editing the name · not `+` and not an empty tab-bar spot · **not if main has only one tab** (Q35).
- **dragstart**
  - **`e.stopPropagation()` — for our drag only, also cut the root's dragenter · dragover · drop.** The HTML5 backend of the agent tree (react-arborist → react-dnd), with a `window` bubbling-phase listener, `preventDefault` a dragstart that no registered source received and kills the drag (`handleTopDragStart` 「If by this time no drag source reacted, tell browser not to drag」) and overwrites the `dropEffect` of a dragover that is not its own with `none` (`handleTopDragOver`) — `react-dnd-html5-backend` 14.1.0 `dist/esm/HTML5BackendImpl.js` code confirmed · the spike window had no tree cell. A drag that is not ours (file · tree row) is not cut (the same reason as the `fileDropGuard` head).
  - **Carrying** — type string = `application/x-engram-tab;app=<identifier>;drag=<uuid>;w=<정수>;h=<정수>;shape=<모양>` · value = JSON `{v:1, drag, view, from, initial, size, grab}`.
    - **Why a type string** — during dragover `getData` is blocked and all the target can see is `types`, but the original size is needed then for the preview (R4) and the dragged tab shape for band validity (R8). **Rejected** = going through the shell (invariant violation) · web ↔ web `BroadcastChannel` (delivery is async so it races with dragenter and sets up one more communication between windows). If the type-string field cannot cross OLE between windows (M3), §9-1.
    - **`shape`** = only the shape of the dragged tab's layout (slot id · no content) — preorder `l` (cell) · `h<비율>_` · `v<비율>_` (left-right · top-bottom split, followed by two children). Ratio = JS `String(n)` (f64 round-trip exact · lowercase · no `;` `=`). One cell = `l`. With this the target decides the zero area of the result of inserting that tab (§4-5 · slot ids are made up in preorder). Length ≈ number of splits × 20 characters — the upper bound is untested (M3).
    - `app` = Tauri `getIdentifier()` (once at mount · failure is a bounded retry `retryAsync` — ADR-0102 · a drag started before the answer is not read as ours · `tabStrip/appIdentifier.ts`) — does not receive drags of other builds (dev · release · spike). Chromium lowercases the type, so carry and compare in lowercase.
  - **Size** (`dragSize.ts` · materials = `window:frame` (restore size · maximized · frame inset — computed by the shell) · `screen.availWidth/Height` (work area · DIP) · viewport − canvas (chrome))
    - **A window with two or more tabs** — new window inner size `size` = Chrome `dragged_size` carried to the inner size (PRD R22 · 6.3 §5-5 C5 order): s = restore size (if none, the current one) → a side that exceeds the work area (− frame) becomes work area − 20 → if maximized each side ≥ maximized inner size ÷ 2 (it wins because it is last). Original size (R7 — `w` · `h`) = `size` − chrome.
    - **A pop-out with only one tab** — `size = null` (move that window) · original size = (restore size if maximized · otherwise the current size) − chrome.
    - If the size field is absent or broken, the target treats the original length = cell half (cap).
  - **Image** (R29 · VS Code `applyDragImage` · research F) — tab name label · inner padding 1 px 7 px · rounding 10 px · text 12 px · max width 120 px · ellipsis · color = theme token. Attached off screen and erased on the next tick after `setDragImage(el, −10, −10)`.
- **Source window while dragging** (R2 · R15 · R23) — if the cursor is **inside its own tab-bar zone** it is the Chrome-style reorder (the dragged head follows the cursor horizontally and neighbors step aside with 200 ms EASE_OUT · `reorderGeometry` as is · transform only). Outside the zone · outside the window, withdraw the move look (200 ms back) and **show the remaining tab** — `initial ≠ view ? initial : succession(tabs, view)` · if there is only one tab, the dragged tab as it is. The remaining tab is a web display that does not change the model and is the same as the `successor` the shell picks on drop — the only path that attaches to another tab of the same window as a seam (S12). On returning to the zone the dragged tab is shown again and the move continues.
- **dragend** — **regardless of `dropEffect` (both `none` · `move`)** send `tab_drop{NewWindow{by: DragEnd{effect}, size, grab}}` (§3-5) (re-review 2026-10-20 · user decision Q39 — even if another app receives, a new window). **But a drop in place in the same webview · a drag the engine aborted (a dragend in the same task as dragstart — §9-3 U2 ⑨) is not sent** (user decision 2026-10-20 「드래그 스타트 안보내는거면 엔드도 보내지마」 · below · §2-4 ④). `effect` = `move` if its own `dropEffect` is `move` · otherwise `none` (re-review round 3 — the shell looks at `move` and tells our window · unreadable as ignore · §3-5 ③ · ⑤). For the response only a log is left and the result is received by `done` (if the invoke errors, release the swap-render right away). Its own `dropEffect` is recorded — used when reading `done{Ignored|Canceled}` (§4-6). If the same webview's drop sent nothing (same window, same place — §4-3), it does not send `DragEnd`, releases the swap-render and withdraws the transform right away (§2-4 ④).
  - **The old `copy` · `link` branch was removed** — because of `effectAllowed = 'move'`, even if someone else receives it the dragend is only `move`, so it was a dead path. A `move` received by another app has the shell choose a new window by the topmost window under the cursor (`Foreign`) (the fact of `move` is now sent along to the shell — what tells it apart from a `move` received by our webview is only the topmost window).
  - **Cost** — a drag our webview received also issues one more `DragEnd` invoke after it ends (two together with the receiving window's `Drop` · a drop in place on the same window is zero for both · the drop write (`dock_tab`) is at most once — ledger §3-4). It is a call after the drag has ended, so the invariant stays.

### 4-3 Decision — `judge` (root dragover of every window of ours)

- **Receiving** — if it is our drag (`app` matches), always receive (`preventDefault` · `dropEffect = 'move'` · `stopPropagation`). So when released over our webview, drop always comes. If there is no receiver, OLE gives DragLeave instead of Drop and it cannot be told apart from 「창을 떠남」 (likely · MS `DoDragDrop` · HTML end handling) — this is avoided (lost drop — §9-2).
- **Tab-bar zone** (R2) = the horizontal range of the tab-bar decision area (`src/components/layout/tabStrip/measure.ts` `stripZoneArea` — called by `useTabDragSource.ts` `geometryOf` · from the left of the first tab to the right end of `+`) × 15 px above and below the tab bar (if the tab bar is inside the title row, above and below the title row — S26 §7-9). To its right (empty spot · draggable empty area · number mark · window buttons) is not the zone — dropping there is a new window and a tab of the source window itself is detached. ☞ The old 「`+` 앞」 was never implemented (the same note in §「그대로인 것」) — user decision 2026-10-26 (T-66 — 「탭이 있는 곳(첫 탭 ~ `+`)만 탭바 구역」) decided the horizontal range — its own tab is also outside the zone if it goes past the right end of `+` (D-a) and the top edge of the canvas below the right of `+` is the outer top band (D-b · S26 §7-9).
  - **Source window** — `insertionIndex(B, d, draggedLeft(..))` · `moveDue` for the reorder look (R23).
  - **Other window** — 2 px vertical line (W13 · VS Code). `dropIndex(B, x, null)` = the number of visible heads whose center < `x` (strict `<` — if `x` equals some head's center, the spot to the left of that head) · does not go past the spot after the last visible head (R24 — 6.3 `insertionIndex` ⑤) · empty spot = end. Line = right end of the left head at that spot + left end of the right head (VS Code `::after` · `::before` shape · `--accent`).
- **Canvas** — pick a **valid** band with `bands` (§4-5) · if there is a band, preview · if none, do not paint (R6 · R8).
- **Anywhere else** (cell center · our UI outside the canvas) → `Elsewhere` (`NewWindow{by: Drop}` on drop — R6 · R22).
- **drop** — **the first sentence of the handler = `e.preventDefault()`** (next is `stopPropagation`) — so that the source dragend is `move`. The source also sends `DragEnd` for that drag (§4-2), but looks at `move` and neither releases nor restores by that `DragEnd`'s ignore (§4-6 — the result is decided by this window's `Drop` · ledger §3-4). After that it sends to **the target the last decision (preview) pointed to** — it does not decide again from the coordinates at the moment of the drop (user decision 2026-10-20 「유저는 미리보기로 판단하는거잖아」). **The only fallback** = a drop that arrives when there is no open preview round (300 ms of silence · the mousemove deadline closed it — §2-4) is decided at that drop point (it is not discarded). Branches: tab bar → `TabBar{index}` (if same window, same place it is not sent and that drag id is recorded in that webview — the following source dragend reads it, does not send `DragEnd` either, and releases right away · §2-4 ④) · band → `Seam{target: 보이는 탭, anchor, side, share}` · `Elsewhere` → `NewWindow{by: Drop, size, grab}` (value = the carried JSON). The decision-time state (tab list · edition number · active) is not carried — the shell re-finds the target on drop (ADR-0297 decision 2 · §3-3). **The response only leaves a log** — the result is received by the source through `done` (§4-6). `Duplicate` does not mean the drop was lost — if the new window of the same drag's `DragEnd` is in progress, this `Drop` that the ledger holds may be applied later (§3-4).
- **A canvas where the dragged tab itself is visible** (a source window with only one tab) — there is no band (`SelfTarget` · VS Code 「출처 칸이 비게 되면 덮개 없음」 shape). Releasing over it moves that window by the amount dragged through `Elsewhere` → `Reuse` (R6 · Q34).
- **What stays** — tab width · hiding · overflowing tab bar (R24) · close mode (R26 — unconnected TODO U7c as is) · no tab-bar scroll. There is no hover-to-open · window raising (Q36).

The canvas is measured again only at dragenter and at **a size change during a round** (one ResizeObserver per round — `watchCanvas` of `useWindowDrop`) — if it changes, measure again and **decide again right away from the last decision point**, so the preview follows the new size without waiting for dragover (because a window size change while dragging is not blocked — ADR-0297 「영향」).

### 4-6 After the end — result notification · restoring the original selection (source)

- The source looks only at the ones with its own drag id among `tab_drop:done` (from that drag's dragstart to the next dragstart). The results of every branch come through this single path — the source also learns the result of a drop sent by the receiving window through this. Since the source sends `DragEnd` on every dragend (§4-2), `done` usually always comes — a drop in place on the same window · a drag the engine aborted does not send `DragEnd` so there is no `done` (§2-4 ④).
- **Releasing the swap-render** — §2-4.
- **Its own dragend is `move` but `done{Ignored}` or `done{Canceled}`** — there was a receiver and the topmost window is our window or unreadable (§3-5 ③ · ⑤) = usually our webview received it. That window's `Drop` result follows (`Drop` wins — §3-4 · a drop in place on the same window does not send the source dragend either so this `done` does not exist — §2-4 ④). **It neither releases nor restores by that `done`** — if it releases, the dragged tab shows for a frame or two before `Drop` is applied (§8-3 ②), and if it restores, a drop in place that sent nothing shows `initial` instead of the pressed tab (different from a click — now that drop does not send `DragEnd` either so this `done` does not come). The following `done` or a safety-net trigger (§2-4) releases it — the end state is decided by the winning `Drop`, and if that `Drop` is lost or that `Drop` is ignored (`no-cursor`) the §2-4 ② · ③ net releases it. `Canceled` does not come out for `move` under the current `decide` (`move` skips the cancel row — §3-5 ②) but if it comes it is the same as `Ignored` (re-review round 3). If `Unknown` but another app received it, `Drop` does not come — the pressed tab stays active (the same as a click) and the net releases it (§9-2). (Added while addressing F3 of the re-review 2026-10-20)
- **Restoring the original selection** (R12 · R15 · AC19 · AC25) — if `outcome` is `Canceled` · `Ignored` (outside the `move` branch above — that is, its own dragend is `none`), the source sends `switch_tab_if(initial, expect = 끄는 탭)` once. Because the press already changed the model active with `switch_tab` (R2). Skip = no `initial` · `initial = view` · `initial` is not a tab of that window · **that window's store active is already not `view`** (the user · LLM changed it in the meantime — it is not overwritten). **The store may lag behind the model so the shell looks once more** (review 2026-10-20) — `switch_tab_if` changes it inside the layout lock only if that window's active is still `expect` (the notification is the same as `switch_tab`), and otherwise changes nothing and notifies nothing and it is `false`. So after issuing the restore, before it arrives, it does not overwrite the tab the user click · the LLM `tab.switch` picked. **But if what was pressed in between is the dragged tab itself,** the store active is already that tab so an ordinary click does not issue `switch_tab`, and a restore that arrives later overwrites that click — so if that tab is pressed while the restore is in flight, the source sends an explicit `switch_tab` (`DragSource.forceSwitch`). Tauri sync commands run in order on the main thread, so it is applied after the restore and the click wins. It is not a bus command (§3-6). It is a call after the drag has ended so it does not break the invariant. `Rejected` is not restored — the drop was made and the tab is in place so the pressed tab stays active (the same as a click).
- **Restore error** — `switch_tab_if` can return an error (the `initial` to restore closed in the meantime and so on — a normal race). The caller catches it and only leaves a log (the overlay falls back to the model active).
- If one drag has two `done` (`DragEnd` ignore → `Drop` apply — §3-4), the later one wins. If its own dragend is `move`, it does not restore by the earlier ignore, so usually the restore does not come before `Drop`. Even in the earlier case (dragend is `none` but `Drop` comes — the same event delivered twice and so on) **the end model is the same** — for a target in another window the `successor` of `Drop` apply is `initial` (§3-3), and for the same-window seam · tab bar the active is not cross-checked on drop, so even if the restore arrives first it is not rejected (ADR-0297 decision 2 · §3-3 — the old edition received this separately at the seam with `SeamAt.or_initial` · the moved tab is active with `Reveal`).

### 9-2 Risks

- **Missing a fast Esc** — it is a property of the OS drag loop (S14 1/5). If missed, the release after that becomes a drop. Our code cannot fix it (accepted by M1 · PRD R12).
- **Lost drop** (the revival of PRD R13b · AC27 · AC28) — two devices reduce it = always receiving at the root (§4-3) · the z decision after dragend (§3-5 ③ — if the topmost window is our window, ignore). The remaining gap = the topmost-window decision is wrong (the drag image window remains · another app's see-through window · notification window — B2 `hit_accepts` · M8 · M13). That misjudgment (`Foreign`), if `DragEnd` arrives first, **also turns a successful drop our webview received into a new window** — even if `move` it cannot be told apart from one another app received, and the real `Drop` after it is `Duplicate` (§3-4). A read failure (`Unknown`) is ignore if `move` (§3-5 ⑤) so this gap does not exist there, and if `none` it is a new window as now. The key · button state of a drag ended by the lock screen · UAC is untested so it may be read as a new window (PRD R13b).
- **A `Drop` that arrives at a new window in progress · the rejection of that new window** (re-review round 3 · review 2026-10-20 U1 — blocked · re-review 2026-10-20 · main's decision) — a `Drop` that arrives while the new window of `DragEnd` is in progress (including during its rejection notification) is not discarded and the ledger holds it (§3-4). If that new window is rejected, the held `Drop` is continued, so the drop is not lost. If one was already held at the rejection decision, that `DragEnd` does not emit `done` so the source receives only that `Drop`'s `done` — the swap-render is never released by the rejection and set again (§3-2 ④). **The accepted gap** = when that `Drop` arrives after the rejection notification was emitted and before `close` — the source first receives `done{Rejected}` and releases the swap-render (§2-4 ①) and right after receives that `Drop`'s `done`. The order is guaranteed but the dragged tab may be visible for a frame or so in between. What reaches this path is only the case where the topmost window of a drag our webview received (`move`) was misread as `Foreign` (anything else = an abnormal delivery where dragend is `none` but `Drop` comes — §4-6) — `Unknown` is dropped because it is ignore if `move` (§3-5 ⑤). Since the ledger does not forget in-progress records even on overflow (§3-4), there is no path that forgets and loses a held `Drop`.
- **Restore ABA** (re-review 2026-10-20 · main's decision — an accepted gap) — if the active changes twice as B→C→B within the few ms before the restore command reaches the shell, the condition (active == dragged tab) passes and it overwrites with `initial`. It is accepted because it is two switches within one IPC round trip.
- **While dragging the LLM moves the dragged tab to another window or closes it — the source dragend of that drag does not come** (main's judgment — application of the ADR-0297 principle (minimal exceptions) · accepted by user delegation (2026-10-21) · §9-5) — since nothing is blocked while dragging (ADR-0297 decision 1 · §3-6) that command succeeds. The source tab bar draws heads from the model list (the `order` of `src/components/layout/TabBar.tsx` is from `ids`), so the dragged head is detached and the source dragend of that drag does not come (the head comment `:12-13` of the same file records this fact). So there is no `DragEnd` — releasing outside our webview (desktop · another app) does nothing (no new window) · releasing on our webview has `Drop` handled as usual (§3-3 「놓을 때 다시 찾기」 — if moved, take it out of the current window · if closed, no-op) · the source's swap-render is released by the `window:tabs-updated` that removes that tab (§2-4 ②). If it is a pop-out with only one tab, the source window itself closes while dragging — what happens in a WebView2 OLE drag is untested.
- **Release over our window's title bar · border** — it is outside the webview so there is no drop and the z decision sees our window, so it is not a new window but nothing happens (user decision 2026-10-20 Q38 · written in PRD R22 · AC8).
- **A drop another app received — someone else reads the drag data** (the accepted limit of user decision 2026-10-20 Q39 「새창.」 · not hidden) — the web page that receives the drop (another browser and so on) can read at drop the value of our MIME (JSON `{v, drag, view, from, initial, size, grab}` — tab · window identifier · window label · size) and the type string (`app` identifier · size · drag id · dragged tab shape). Agent content · output is not carried (§4-2). The result on our side is a new window (§3-5 ④ — if the topmost window cannot be read (`Unknown`) it is ignore so there is no new window and the pressed tab stays active · §3-5 ⑤). The value must be read by our target webview at drop (§4-3), so it cannot be taken out of the carried data.
- **When the cancel distinction is wrong** — if Esc is tapped very briefly and the button is released right after, both are read as released and it becomes a drop. If pressed again during the snap-back it is read as cancel. If the command arrives late (the shell is busy) this gap widens — so the reading is done first (§3-2). Key · button · cursor reading was measured only inside our window — over the desktop · another app is untested (M1 · M2).
- **Swap-render remains** — since the source sends `DragEnd` on every dragend, `done` usually always comes. The remaining gaps = our webview received it (its own dragend `move` → does not release by `done{Ignored|Canceled}` — §4-6) but the receiving window's invoke does not reach the shell · an event is lost · the topmost window could not be read but another app received it (§3-5 ⑤ — `Drop` does not come) · the receiving window's `Drop` cannot read the cursor (`Ignore("no-cursor")` — `move` so it does not release by that `done{Ignored}` · the path where a held `Drop` stood in for the rejection is the same). The `done{Ignored}` of the same drag's `DragEnd{move}` ignore (`accepted-ours`) may arrive later than the `done{Applied}` of `Drop` (the two handlings are on different threads — a gap that existed before this edition) — `move` + `Ignored` neither releases nor restores (§2-4 ①) so there is no screen effect. A drop in place in the same webview that sent nothing is released at dragend (§2-4 ④) so it is not a gap. In those cases the source's swap-render remains until the safety-net triggers (§2-4 ② that window's next `window:tabs-updated` in which the dragged tab is not active · ③ next press) (the remaining tab is visible and the model active is the pressed tab) — the price of not setting a deadline.
- **Moving the dragged source element** (W13) — there is no measurement that moving the dragged tab by transform does not cut the OS drag (M12). The precedent is one old Chromium WebUI tab bar.
- **The web mirror diverges from Rust** — only the samples the golden holds are guarded. If they diverge, preview ≠ result (R4) and the shell only re-checks the share range · zero area on drop.
- **The length of the `shape` field** — for a tab with a great many splits the type-string cap is untested (M3). If it cannot be carried, it is treated as one cell and a blocked band may be painted, and on drop it is a `ZeroArea` rejection · the tab stays in place.
- **A new window with mixed scales** — `open_at` receives a physical position + logical size. When opening on a monitor with a different scale, tao's `WM_DPICHANGED` handling may fix the size once more (a phenomenon 6.3 E3 saw — this time no two-step drop is done). The web's `screen.avail*` is based on the source window's screen (Chrome is the screen near the cursor). M2 measures. → 2026-10-23 M2: a drop at the middle of the screen (1.5 → 1.75) is normal · a drop right next to the edge = untested (§8-5 M2 row).
- **The new-window cursor position (`dragGrab`)** — it is assumed that the left and vertical position of the new window's tab bar are the same as the source tab bar ([untested]). The new window is a pop-out but main's chrome to the left of and above the tab bar may differ from the pop-out's, so a new window dragged out of main comes up shifted from the cursor by that difference. `headRoom` (new-window tab-bar width) is computed by U3 from the new-window size. M2 measures the cursor drift from main → new window.
- **The 「복원 크기」 of a source window that was Snapped** — whether it is the pre-Snap size is untested (PRD R7).
- **macOS (WKWebView) · WebKitGTK** — HTML5 drag between windows · the type-string field · dragend `dropEffect` are untested (ADR-0296). `escape_down` · `top_level_at` are false outside Windows · `None` so `top` is always `Unknown`. If dragend is `move` it is ignore (§3-5 ⑤) so a drop our webview received is decided by `Drop` and does not race with `DragEnd` — instead there is no new window for a drop another app received (differs from Q39). If `none`, the cancel distinction shrinks to the button alone and a lost drop falls to a new window (`Unknown` + `none` → `Place`). At porting, add that OS's key state · topmost-window reading to platform.
- **Limits of the CDP test** — the source dragend differs from real input (§8-4) and it does not pass through OLE. Delivery between windows · type-string passing · image · lost drop · z decision are measured only by the M items.
- **Prewarmed window** (ADR-0299 · §3-9 · design draft)
  - **First showing of a window hidden for a long time** [untested] — it is the first time showing a WebView2 window whose DOM changed while it was hidden. A newly built window is also built hidden and shown at its first paint (it works — research §1) but only for a few seconds. If Chromium sees a page hidden for a long time as throttled or occluded (`visibilityState` hidden → no rAF → notification before raster), the first frame shown may be a stale standby frame or an empty surface. M15 decides · if it flickers it is a stop condition (§9-1).
  - **Scale when passing a hidden window across monitors** [untested] — `placement.rs:502-504` already points at it. It may be shown at a wrong size and then jump (I9 · M16).
  - **z order · focus when shown** (user decision 2026-10-21 「ㅇㅇ 그래 포커스 뺏지말고, 순서만 위로올려.」) — a window hidden for a long time, if simply shown, stands at its old z position. A handed-over window has only its z raised to the top before it is shown (platform `place_window` · `ZOrder::Top` · without activation — I29) and is shown without activation · activation (`set_focus`) is only for an actively opened handover and only when the foreground is ours (I5) — a window the LLM opened when our app is not in the foreground · the window of T-65 (`Keep`) does not steal focus (no fake Alt `force_window_active` is used). **Raising alone does not stand above another app's foreground window — measured 30/30 (2026-10-21 · M22)**: the new window stands without focus just below the window in use now · above the other windows (the raise call succeeds · Windows keeps the foreground window above — the cause is a guess). The user accepted this behavior (§9-3 「정해짐」 2026-10-21) — no workaround is invented.
  - **Stall of rebuilding** — the main thread is occupied ≈ 160 ms right after the new window is shown (prewarm F2) [size unmeasured — M17]. Sync commands (such as a tab click) wait during that time.
  - **Memory** — one hidden WebView2 always lives (+ the share of that page's store holding all `layout:updated`) [unmeasured — M18].
  - **Dead prewarmed renderer** — if the renderer process dies while hidden, the adoption shows a dead page (after the 1.5 s deadline). There is no crash signal wired up today · rare · only written down.
  - **A handed-over prewarmed window disappears before `open_at`** → that drop is rejected (`WindowOpen`) instead of falling back (at that time the label is decided and a tombstone stands on that label so it cannot be built fresh — §3-9 「실패 계약」). Rare · warn log.
  - **A late `window_role` answer overwrites `adopted`** — the one-direction mode (I7) closes it · guarded by tests (§8-2).
  - **Tray show between commit and first paint** — shows the window early (a newly built window has the same gap today). The hide · show between handover and first paint is handled by the raise set at handover (§3-9 「숨어 있기」 · I17) — a tray show where the commit slipped in after being skipped by the predicate (`Adopted`) shows that window right away and becomes the same 「일찍 보임」.
  - **The destination of the view-command bridge** — it can be a prewarmed page (it is so now too because a boot spare window exists — not new). Check that `Registered::repick` picks main.
  - **macOS (WKWebView) · WebKitGTK** — drawing of a hidden webview and the same-scale query are unknown (the port is OS-neutral · behavior untested).
