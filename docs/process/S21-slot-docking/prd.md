## 1. What and why

- Today the only way to move a slot to another window is pop-out, and even that only puts it into a **new tab** of the target window (`slot.popout{to_window}`). There is no way to insert it at the position you want (which side of which slot).
- This feature was there from the first concept — 「Visual Studio 스타일 도킹 — 플로팅끼리 합치기, 메인 재도킹」 (`docs/process/S0-view-phase/requirements.md:98-104`). Moving tabs between windows is also left as 「후속」 in ADR-0057.
- User flow: to move one slot, **make a separate window with pop-out, then drag that window's tab and attach it at the position you want in the window you want**. (decision)

## 3. Requirements

**The two handles of a drag**
- **R1** Dragging a window's **title bar** moves only the window (OS default move). The docking guide does not appear. Moving the window is the default and docking is the option — the convention of Unreal · Unity · VS Code. (decision) The empty tab bar after the title bar is removed behaves the same (R25 — T-66).
- **R2** The moment you press a window's **tab**, that tab becomes active — not on drop (survey A4). Moving past the **OS drag threshold** while pressed starts a drag — the threshold is a value set by WebView2 (Chromium) and cannot be changed (measured = 4 physical px · 3.2 CSS px at 125% · OS-drag spike S14 real input 5/5 · `dragstart` cannot be delayed, only cancelled). From then on the **drag image** (tab name label — R29) follows the cursor. At first it is a **reorder within that window's tab bar** (R23). While dragging, the tab **stays in the original window** — it is not detached, no new window is created, and it does not attach to another window. When the drag leaves the original window's **tab-bar zone** (the horizontal extent of the **tab-bar hit-test area** × **15 px** above and below the tab bar — Chrome `kVerticalDetachMagnetism`, survey A5 · D19), the original window's canvas shows the remaining tab that Chrome's rules pick (only inside that window's webview — R15). When the cursor is over one of our windows, that window's webview draws the guide inside itself — in a tab-bar zone the insertion vertical line (R21 · 2 px · the R23 reorder if it is the original window), over a cell the docking band (R3). On drop the result at that position happens **at once** (「배치를 바꾸는 때」 below) — on a band it attaches to that cell (R7), on a tab bar it goes into that position (R21), and elsewhere (slot center · outside our windows) **a new window holding only that tab is created at the drop position (cursor)** (R22). Esc reverts the drag (R12). The tab of a **single-tab pop-out** follows this rule as-is — except that if it is dropped on no window, instead of a new window **that pop-out is moved to the drop position** (same size · decision · 2026-10-20 — Q34 · R22). **The main window's last tab does not start a drag** — pressing · renaming work as before (decision · 2026-10-20 — Q35 · R14).
