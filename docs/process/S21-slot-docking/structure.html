탭을 끌어, 원하는 창의 원하는 자리에 붙인다

메인 · 팝아웃 창의 탭을 끌어 다른 창(또는 같은 창)의 슬롯 옆 · 탭바 · 빈 곳에 놓는 기능입니다. 이 페이지는 무엇이 어느 층에 있나를 그림으로 먼저 보이고(1절), 사용자가 보는 동작과 5.7 · 5.8 판에서 새로 들어온 규칙을 차례로 그립니다.

TRD 5판 이후 바뀐 것 — ① 자기 탭바 안에서는 끌기가 순서 이동이고, 탭바 구역을 벗어나야 떼어집니다(Q20 · 5.7 — 3절). ② 어느 창도 보고하지 못한 채 끝난 끌기는 셸이 뗀 순간 커서로 판정해 적용하고(Q21), 엔진이 곧바로 접은 끌기(15ms 안)는 무변경입니다(5.7 — 5절). ③ 탭바는 스크롤하지 않고 Chrome 규칙대로 폭을 줄이다 꼬리 탭을 숨깁니다(Q22 · 5.8 — 4절). ④ 사용자 확인 대상은 전부 닫혔습니다(8절).

1–6c 가 「놓으면 붙는다」의 셸 쪽 전부이고, 7 이 웹뷰를 붙여 마우스 도킹이 처음으로 끝까지 됐습니다. 그 뒤 실 마우스 실측에서 나온 결함 셋과 사용자 결정 Q20 · Q21 · Q22 가 5.7 · 5.8 판이 되어 9a(순수 규칙) → 9b(장부 · 실행기) → 9c(웹뷰) 순으로 들어가는 중입니다. 각 단계는 새 것을 더하기만 하고 부르는 쪽까지 같은 커밋에서 닫아, 어디서 멈춰도 빌드가 섭니다.

01층마다 무엇을 쥐나

웹뷰는 그리고 알리기만, 셸 장부는 판정만, 배치를 바꾸는 문은 하나

그림 읽기

  1. 엔진 — 끌기 자체는 우리 코드가 아니다. 커서 추적 · 커서 밑 맨 위 창 · 끌기 그림 · 버튼 · Esc 는 WebView2 브라우저 프로세스(msedgewebview2.exe)의 OS 끌기 루프가 돌립니다. 웹뷰에는 DOM 사건(dragstart · dragover · drop · dragend)으로만 닿습니다. 셸 프로세스의 메인 스레드는 이 루프에 들어가지 않아(실측 지연 최대 4.1ms), 끄는 동안에도 데몬에서 오는 에이전트 출력을 웹뷰로 계속 흘려보냅니다.
  2. 웹뷰 — 그리기와 사건 전달만. 창마다 하나입니다. 탭바(TabBar.tsx)가 끌기를 시작하고 끝을 알리며, dockDrag.ts 가 dragover 마다 셸이 미리 보낸 영역 위에서 점을 판정하고(판정 거울 dockPick.ts) 출처 창이면 모드를 정한 뒤 가이드(DockOverlay.tsx)를 그립니다. 탭 폭 · 숨김을 계산하는 순수 함수(tabStripLayout.ts)도 여기 있습니다. 배치를 바꾸는 코드는 웹뷰에 없습니다.
  3. invoke — 웹뷰에서 셸로 가는 길은 일곱뿐. 시작은 dragstart 안에서 잰 탭바(strip)를, 놓기 · 출처 끝은 그 창이 마지막으로 그린 판정을 그대로 싣습니다. 보인 것 보고(dock_drag_over)는 바뀔 때만 내므로 dragover 60/s 가 셸로 넘어가지 않습니다.
  4. 실행기 (commands/dock.rs) — invoke 껍데기. 도착 시각(now)을 먼저 찍고 커서 · 창 사각형 · 배율을 락 밖에서 읽어 장부에 먹인 뒤, 장부가 돌려준 할 일을 실행합니다: emit · 탭 하나 팝아웃 숨기기 · 보이기(메인 스레드 줄에서 장부의 지금 값으로 맞춤) · 시한 · 적용 호출(늘 async).
  5. dock — 끌기 장부와 판정. book.rs 는 사건을 받아 할 일만 내는 순수 상태 하나입니다(잎 락 하나 · 스레드 · 틱 없음). regions.rs 가 창마다 놓을 영역을 미리 계산하고 놓을 때 같은 점을 다시 고르며, hit.rs 가 그 규칙(이음새 · 탭바 자리 · 순서 이동 구역)을 순수 함수로 갖습니다. snap.rs 는 레이아웃 락 안에서 모델을 장부 재료로 뜹니다.
  6. 적용 서비스 apply::dock_tab — 배치를 바꾸는 유일한 문. 마우스 놓기(이음새 · 탭바 · 새 창)와 자기 탭바 안 순서 이동(TabBar{같은 창, index})이 모두 여기를 한 번 지납니다. 잠금 한 번 안에서 모델(manager.rs)과 트리 연산(layout/dock.rs)을 부르고, 메인이 비면 그 안에서 빈 탭을 채웁니다.
  7. 결과 알림 — 새 사건이 없다. 도킹 결과는 기존 layout:updated · window:tabs-updated 로만 웹뷰에 돌아가고, 웹뷰는 받은 배치를 그릴 뿐입니다.
  8. 골든 — 판정 규칙 두 벌을 묶는 파일 하나. 규칙은 Rust(hit.rs · regions::pick)와 TS(dockPick.ts)에 두 벌 있고, 같은 pick_golden.json 을 Rust 시험과 vitest 가 함께 먹습니다.
  9. LLM 명령 — 점선 상자는 이번에 만들지 않는 것. 다음 작업이 같은 문(⑥) 위에 얹습니다.
  10. platform — 새 함수 없음. 셸이 직접 읽는 OS 값은 Tauri API 셋뿐입니다.

왜 이렇게 놓았나

dock 을 layout 밑에 두지 않은 까닭. 장부는 레이아웃의 권위가 아니라 그 권위를 부르는 손님입니다 — 놓기도 적용 서비스를 부를 뿐입니다. 둘을 한 모듈에 섞으면 「레이아웃 변경은 적용 서비스 하나」라는 경계가 흐려집니다(TRD §1-1). 그래서 장부 락(잎 락)을 쥔 채로는 레이아웃 락 · emit · 창 호출 · 적용 서비스 · 커서 읽기를 하지 않습니다(TRD §1-3).

배치를 바꾸는 길은 하나. 마우스 놓기 · 순서 이동 · 앞으로의 LLM 명령이 모두 apply::dock_tab 을 지납니다. 다음 작업의 명령은 그 위에 껍데기만 얹고 두 번째 변경 경로를 짓지 않습니다(TRD §3 · ADR-0081 결정 3). 출처에서 빼기 · 대상에 넣기 · 빈 팝아웃 지우기 · 메인 빈 탭 채우기 · 출력 경로 다시 계산이 이 문 안의 잠금 한 번에 일어나므로, 저장 파일에는 도킹 전 아니면 도킹 뒤만 실립니다(TRD §5).

판정 규칙이 두 벌인 까닭 — 의도된 중복. 가이드는 커서를 60Hz 로 따라가야 하는데, 움직일 때마다 셸에 물으면 invoke 왕복(실측 p99 약 16ms · 최대 약 50ms)만큼 가이드가 늦습니다(TRD §7 #3). 그래서 셸이 창마다 영역을 미리 보내고, 웹뷰는 같은 규칙의 TS 판으로 점만 고릅니다. 놓을 때는 셸이 Rust 판으로 같은 점을 다시 고르고 보인 것과 같을 때만 적용하므로, 두 판이 갈라져도 결과는 엉뚱한 도킹이 아니라 「무변경」입니다(TRD §11-2 #4). 갈라짐은 골든 하나(src-tauri/src/dock/pick_golden.json — 영역 13 · 사례 132)를 Rust 시험과 vitest 가 함께 먹어 막고, 규칙을 고치면 Rust · 골든 · TS 를 같은 변경에서 고칩니다. 판정 순서와 f64 연산 순서까지 같게 짭니다(TRD §2-4).

LLM 명령이 없는 것은 의식적 예외. 이번 도킹은 LLM 명령(tab.dock 류 · layout.get)도, 탭 순서를 바꾸는 명령도 만들지 않습니다. CLAUDE.md 「LLM-우선 제어」(새 UI 기능엔 LLM 호출 경로를 함께)의 의식적 예외이고 사용자 결정입니다(PRD Q10 · 순서 이동은 D22). 남기는 것은 그 명령이 얹힐 자리 — apply::dock_tab · 타입드 DockError · FocusPolicy::Keep — 이고, 도킹 바로 다음 작업이 그 위에 명령을 얹어 갭을 닫습니다. 그 사이의 갭은 8단계에서 CLAUDE.md 「남은 갭」에 한 줄로 적습니다. 끌기 invoke(dock_*)는 사람 손의 입력과 그 측정이라 명령 버스에 싣지 않습니다.

OS 층에 새 함수가 없는 까닭과 대가. 커서 추적 · 맨 위 창 · 끌기 그림 · 버튼 · Esc 를 엔진이 맡아, 셸은 Tauri API 셋만 락 밖에서 읽습니다. 그래서 platform 과 OS 경계 게이트 명단이 하나도 바뀌지 않습니다(TRD §1-6). 대가로 셸은 「커서 밑 맨 위 창」을 모르므로, 보고 없는 끝의 커서 판정은 그 끌기를 본 창과 원래 창으로만 좁혔습니다(PRD D21 — 5절). 셸 쪽 준비는 하나 — 창을 만드는 모든 코드가 지나는 한 곳(WebviewEnv::finish)에서 wry 의 드롭 처리기를 끕니다. 켜 두면 wry 의 드롭 대상이 HTML5 끌어 놓기를 막습니다.

02사용자가 보는 동작

떼고, 들고, 셋 중 한 곳에 놓는다

가장 흔한 경우입니다 — 팝아웃의 탭 「리뷰」를 끌어 메인 창 슬롯 B 의 오른쪽 띠에 놓습니다. 끄는 동안 바뀌는 것은 화면뿐이고(가이드 · 떼어진 모습 · 숨긴 팝아웃), 실제 배치는 놓는 순간 적용 서비스에서 한 번 바뀝니다. 탭이 하나뿐인 팝아웃은 커서가 그 창 탭바 구역을 벗어나 다른 창에 닿을 때 창째 숨고(3절), 붙으면 비어서 닫힙니다.

놓는 곳은 셋뿐입니다. ① 이음새 — 슬롯 상하좌우 띠(슬롯의 1/3)와 창 바깥 변의 32px 띠이고, 빗금 띠 하나가 곧 「놓으면 새것이 차지할 사각형」입니다. ② 다른 창의 탭바 — 탭 사이 세로 막대 자리에 끼웁니다(원래 창 탭바 안은 놓는 곳이 아니라 순서 이동입니다 — 3절). ③ 그 밖 — 슬롯 가운데 · 창 밖 · 다른 앱 위는 그 탭만 든 새 창입니다. 결과에서 면적이 0 이 되는 슬롯이 생기는 띠는 칠하지 않습니다.

규칙 넷입니다. 제목줄 끌기는 OS 기본 창 이동이라 이 기능이 끼어들지 않습니다. Esc 와 비정상 끝은 「원래대로 되돌리기」가 아니라 그 자리에 놓기입니다. 메인의 마지막 탭도 끌 수 있고, 떠나면 같은 연산 안에서 메인에 빈 탭이 생깁니다. 다른 창 탭 머리 위에 0.5초 머물면 그 탭으로 바뀝니다 — 원래 창 탭바의 머묾 전환은 순서 이동(Q20)과 함께 없어졌습니다(받아들임 · TRD §11-1b ②).

자세히 — 띠 규칙 · 고를 수 있는 곳 · 새 창 · 비목표
  • 띠가 겹치면 창 바깥 띠가 슬롯 띠보다 이기고, 슬롯 모서리에서는 커서에서 가장 가까운 변(띠 두께로 나눈 거리)이 이깁니다. 경계선 위는 늘 같은 답입니다(src-tauri/src/dock/hit.rs).
  • 바깥 띠 두께 = 32 CSS px — 탭바 높이(28px)보다 조금 두꺼워 노리기 쉽고, 배율과 무관하게 같은 눈 크기입니다. 출처 창에서는 캔버스 맨 위 15px 이 순서 이동 구역에 들어가 바깥 위 띠의 남은 몫이 17px 입니다(TRD §2-5).
  • 고를 수 있는 곳 = 커서 밑 맨 위가 우리 창일 때, 그 창의 지금 보이는 탭과 탭바. 다른 앱 창에 가려진 자리 · 최소화된 창은 대상이 아닙니다. 같은 창의 다른 탭에 붙이려면 그 탭을 먼저 띄워 둔 채 다른 탭을 끌어 캔버스로 내립니다.
  • 새 창 — 크기 = 떼어 온 창의 크기(최대화였으면 보통 크기 · 메인에서 뗐으면 팝아웃 기본 720×500), 자리 = 커서에서 끌기 그림 안 커서 자리를 뺀 곳. 탭이 하나뿐인 팝아웃이면 새 창을 만들지 않고 숨겨 둔 그 창을 놓은 자리로 옮깁니다(다시 확인 · 되돌리기 없음 — Q19).
  • 파일 끌어 놓기(탐색기 파일 등)는 모든 창에서 늘 막습니다 — 드롭 처리기를 끈 웹뷰가 그 파일로 이동하지 않게.
  • 놓은 뒤 대상 창이 앞으로 오고 붙은 첫 슬롯에 포커스가 갑니다. 에이전트 출력은 끊기지 않습니다 — 배치를 바꾸는 같은 잠금 안에서 출력 경로를 다시 계산합니다(팝아웃과 같은 길).
  • 비목표: 슬롯 하나 직접 끌기 · 슬롯 가운데 칸 · Ctrl 끌기 · 직전 도킹 되돌리기 · 크기 기억 · 웹뷰 안 화면 상태(입력 초안 · 스크롤) 옮기기.
03탭바 안 순서 이동 · Q20 · TRD 5.7

자기 탭바 안에서는 순서만 바꾸고, 벗어나야 떼어진다

그림 읽기

  1. 구역. 출처 창의 탭바 상자(+ 와 그 오른쪽 빈 곳까지 든 줄)를 위아래로 15 CSS px 넓힌 사각형입니다(REORDER_SLACK_PX — Chrome 탭 스트립의 떼기 문턱 kVerticalDetachMagnetism = 15 와 같은 값). 지금 탭바가 뷰포트 맨 위라 위쪽 여유에는 닿지 않습니다. 들어올 때와 나갈 때 경계가 같습니다(이력 없음 — PRD D19).
  2. 순서 이동 모드 (왼쪽). 끄는 머리가 커서를 따라 가로로만, 머리들이 차지한 범위 안에서 움직입니다. 끄는 머리 가장자리가 이웃 머리의 가운데를 넘으면 그 이웃이 머리 폭만큼 150ms 에 비켜납니다(Lumino 규칙). 그림에서는 C 의 왼쪽 끝이 B 의 가운데를 넘어 B 가 오른쪽으로 비켰고, 놓으면 A · C · B · D 입니다. 떼어진 모습 · 가이드 · 머묾 전환은 없고, 끌기 그림(Windows 기본)은 그대로 따라옵니다.
  3. 도킹 모드 (오른쪽). 구역을 벗어나는 순간부터 5.6 판 그대로입니다 — 끄는 머리가 접히고 캔버스는 승계 탭(오른쪽 이웃 우선)을 보이며, 다른 창은 가이드를 그립니다. 같은 끌기에서 구역으로 돌아오면 다시 순서 이동입니다(PRD D15).
  4. 누가 정하고 누가 적용하나 (아래 줄). 모드는 출처 웹뷰가 자기 dragover 마다 자기 판정 결과로 정하고 셸에 묻지 않습니다(왕복 없이 60Hz). 놓을 때는 셸 장부가 dragstart 때 잰 탭바(strip — 세션 내내 얼림)로 같은 점을 다시 판정해, 웹뷰가 그린 것과 같은 index 일 때만 적용합니다(놓기 판정 4c). 규칙은 셸 hit.rs 하나이고 웹뷰는 그 거울이라, 보이는 자리가 곧 적용하는 자리입니다.

설계상 붙은 것 · 받아들인 것

왜 시작 측정을 얼리나. 도킹 모드에서 머리가 접히면 크롬 보고에서 끄는 머리가 빠져 그 폭을 잃고, 비켜나는 모습(transform)이 걸린 머리를 재면 판정이 자기 그림을 따라 흔들리며, 셸의 크롬 보고는 100ms 디바운스라 늦을 수 있습니다(TRD §2-4). 그래서 출처 창의 구역 · 자리는 dragstart 안에서 한 번 잰 값으로만 판정하고, 순서 이동 모습이 서 있는 동안 출처 창은 크롬 보고를 건너뜁니다. 그 한 번도 앞 끌기의 미끄러짐(transform)이 아직 남았으면 그만큼 빼고 재며, 잡은 자리(grab_x)도 같은 배치에서 잽니다 — 모습 · 놓기 · 보고 없는 끝의 커서 판정이 같은 자리를 내도록(TRD §1-4).

첫 dragover 전은 순서 이동. OS 끌기 루프는 다음 마우스 메시지 전에는 대상 창에 DragEnter 를 내지 않아 그 틈엔 판정할 점이 없습니다. 그래서 첫 판정 전은 dragstart 점(구성상 구역 안)으로 정합니다. 대가 — 문턱 직후 구역 밖으로 빠르게 빼고 멈추면 다음 움직임까지 모습이 순서 이동 그대로입니다. 결과는 커서 자리 그대로이고 모습만 늦습니다(받아들임 · S7 ⑫ 가 잼 · TRD §11-2 #35). 창 밖으로 나간 떠남도 100ms(LEAVE_GRACE_MS) 뒤에야 도킹 모습으로 바꿉니다 — 구역 안 Esc 가 떠남을 먼저 내기 때문입니다.

탭 하나 팝아웃은 숨기기를 미룬다. 탭바 안에 머무는 동안은 그 창이 보여야 머무는 것이 보입니다. 그래서 시작 때 숨기지 않고, 「출처 창이 그린 보고가 순서 이동이 아님」 · 「출처 창을 떠난 뒤 100ms 동안 끝도 돌아옴도 없음」 · 「다른 창의 보고」 중 처음 것이 서면 그때 숨깁니다(TRD §1-3 「도킹 모드 증거」). 숨기기 · 보이기는 메인 스레드에서 장부의 지금 값으로 맞춰, 끝의 보이기가 늦은 숨기기에 덮이지 않게 합니다.

받아들인 것. 원래 창 탭바의 머묾 탭 전환이 없어집니다(Q20 에서 따라 나옴 — 커서 밑이 대개 끄는 머리라 성립하지 않음 · 예외 둘 = 탭바 끝에 닿아 머리가 멈춘 때 · 앞 끌기의 미끄러짐이나 놓음 모습이 남은 채 누른 머리 · TRD §11-1b ②). 그때도 머묾은 걸리지 않습니다. 그 둘째 경우 끄는 머리는 그 끌기 내내 남아 있던 이동만큼 커서와 어긋나 따라갑니다(탭바 끝에 닿기 전까지 · TRD §1-4 「탭바 재기 strip」). 순서 이동도 이번 LLM 명령 예외에 듭니다(PRD D22) — 같은 apply::dock_tab 을 쓰므로 다음 작업의 명령이 그 위에 얹으면 됩니다.

04탭바 넘침 · Q22 · TRD 5.8

탭바는 스크롤하지 않는다 — 폭은 Chrome 규칙, 남는 탭은 통째로 숨긴다

그림 읽기

  1. 넉넉하면 모든 머리가 같은 표준 폭 S 160 입니다. 이름이 짧아도 같은 폭이고(PRD D23), 긴 이름은 머리 안에서 말줄임입니다.
  2. 모자라면(단계 A) 모든 머리가 같은 폭으로 활성 최소 폭 A 42 까지 고르게 줄어듭니다. 나눠 떨어지지 않는 px 는 왼쪽 머리부터 1 px 씩 받습니다.
  3. 더 모자라면(단계 B) 활성은 A 42 에 서고 비활성만 비활성 최소 폭 I 32 쪽으로 줄어듭니다. 닫기 버튼(×)은 폭이 A 이상인 머리에만 보이므로 활성은 늘 닫을 수 있고, 좁아진 비활성의 버튼은 CSS 로 감춥니다(DOM 에는 남습니다).
  4. 그래도 안 들어가면 끝의 머리부터 통째로 숨깁니다 — 일부만 잘려 보이는 머리가 없고, 탭 목록 · 넘침 메뉴도 없습니다. + 는 고정 크기라 짓눌리지 않고 보이는 마지막 머리 바로 뒤에 늘 보이며, 누르면 지금처럼 맨 끝에 더해 활성으로 만듭니다.
  5. 알려진 한계. 넘친 탭바에서 다른 창에서 끝에 끼운 탭과 + 로 더한 탭은 활성인데 끝 너머라 보이지 않고, 끝 너머의 활성 탭을 보이는 자리로 당기는 장치는 없습니다. Chrome 도 같습니다(사용자 지시 「안되는건 안되는걸로 넘어가고」 · TRD §11-2 #40).

어느 층에 놓였나

계산은 웹뷰의 순수 함수 하나다. 폭 · 숨김은 tabStripLayout(available, n, activeIndex)(src/components/layout/tabStripLayout.ts — 9c 신설)가 냅니다. 상수는 S 160 · A 42 · I 32 CSS px 이고(TRD §1-3 상수 표 — 값은 우리 척도로 옮긴 메인 판단, 규칙은 Chromium 소스 그대로), 우리가 따로 고안한 규칙은 없습니다. 탭바 줄은 스크롤 상자가 아니라 머리들 → + → 빈 곳 순으로 놓입니다.

셸의 도킹 동작은 바뀌지 않는다(9c 의 Rust 는 주석만). 크롬 보고와 strip 은 숨긴 머리까지 DOM 순서대로 재고, 숨긴 머리는 보이는 마지막 머리의 오른 끝 c 에 선 폭 0 입니다. 그래서 9a 가 커밋한 탭바 · 순서 이동 규칙(hit.rs)과 골든이 그대로 서고, 끼울 자리 막대와 끄는 머리는 보이는 끝 안에 머뭅니다. 5.7 리뷰가 들였던 넘친 탭바 스크롤 설계(엔진 자동 스크롤 · 끝 띠 · 스크롤 사건마다 다시 판정)는 탭바가 밀리지 않으므로 걷었고, wire 의 scroll 칸과 「내용 x = 뷰포트 x + scrollLeft」 식만 늘 0 인 채 남았습니다 — 커밋된 셸 코드 · 골든을 다시 만지지 않으려는 것이고 동작 차이는 없습니다(TRD §7 #64).

검증은 화면에서. jsdom 에는 레이아웃이 없어 배치는 vitest 로 단언할 수 없습니다. 폭 함수는 vitest 로, 실제 폭 · 숨김 · + · 닫기 버튼은 화면 QA(AC29 — A 42 가 닫기 버튼 실폭과 맞는지 포함)로 봅니다.

05끝 신호 · 커서 판정

끄는 동안 셸은 바꾸지 않고, 끝에서 한 번 다시 고른다

끝 신호는 셋입니다 — 우리 창 위에서 뗀 drop, 창 밖 · Esc · 멈춘 채 뗀 dragend(none), 신호를 잃었을 때의 끝 뒤 pointermove. 5.7 판이 여기에 엔진이 곧바로 접은 끌기와 보고 없이 끝난 끌기를 따로 다룹니다.

그림 읽기

  1. ① 시작. 엔진이 dragstart 를 내면 출처 탭바가 우리 MIME · 끌기 그림을 싣고 탭바를 잽니다(strip — 읽기만; 여기서 DOM 을 바꾸면 Chromium 이 끌기를 끝냅니다). 셸 세션은 그 사건 처리가 끝난 뒤(setTimeout 0) 시작이 취소되지 않았을 때만 엽니다 — 에이전트 트리(react-arborist)가 window 에 단 끌기 리스너가 시작을 취소할 수 있어서입니다. 셸은 표식을 세우고 창마다 영역을 보냅니다.
  2. ② 끄는 중. 대상 창마다 dragover 를 받아 영역 위에서 판정하고 가이드를 그립니다. 셸에는 보인 것이 바뀔 때만 알리고, 셸은 이때 배치를 바꾸지 않습니다(예외 하나 — 다른 창 탭 머리 위 0.5초 머묾 = 사람 클릭과 같은 탭 전환).
  3. ③ 끝 — 네 줄. A: 우리 창 위에서 떼면 그 창의 drop 이 그린 판정을 싣고 오고, 셸이 같은 규칙으로 다시 고릅니다. B: 창 밖 · Esc · 멈춘 채 뗀 끝은 출처의 dragend(none) 하나로 오고 셸이 「마지막 점에 놓기」를 돕니다(다음 그림). C: 엔진이 곧바로 접은 끌기는 canceled 로 와 무변경입니다. D: 끝 신호를 잃으면 끝 뒤 첫 pointermove 가 알리고, 300ms 안에 끝 신호가 안 오면 마지막 보고로 판정합니다.
  4. ④ 마무리. 적용 알림(window:tabs-updated) 뒤에 Ended 를 내고, 숨긴 출처를 되보이고 대상 창에 포커스를 주며 표식을 내립니다. 웹뷰는 Ended 에서 가이드 · 머묾 · 떼어진 표시를 무조건 지웁니다.

그림 읽기

  1. 먼저 거르는 셋. 엔진이 접은 끌기(canceled)와 끄는 중 출처 배치가 바뀐 끌기(blocked)는 판정 없이 무변경입니다. 출처는 끝 전에 떠났다고 말하는데 다른 창의 Over 가 아직 오는 중이면 최대 50ms(OVER_WAIT_MS) 붙든 뒤 계속합니다 — 두 웹뷰의 invoke 는 도착 순서가 보장되지 않아, 사용자가 본 다른 창 가이드를 놓치지 않으려는 것입니다.
  2. W 고르기. W 는 마지막으로 Over 를 보낸 우리 창입니다. W 가 출처이고 출처 끝이 last(마지막으로 그린 판정)를 실었으면, 셸이 받은 마지막 Over 대신 그것을 씁니다(아래 오른쪽 그림).
  3. 네 갈래. 커서가 W 안이면 W 의 보고로 놓기 판정을 하고, W 의 사각형이 사라졌으면 가이드를 보였던 경우만 무변경입니다. 어느 창도 보고하지 않았는데 커서가 출처 창 안이면 커서 판정, 그 밖은 커서 자리에 새 창입니다.
  4. 커서 판정 (Q21). 끝 순간 커서를 그 창의 뷰포트 점으로 옮겨 그 창의 지금 영역으로 판정하고, 그 결과를 그대로 적용합니다 — 구역 안이면 순서 이동, 이음새 · 끼울 자리면 그 자리, 가이드 없음이면 새 창. 사용자가 준 근거는 「창 안으로 옮겨 온 것 자체가 마우스 움직임이라 뗀 순간 커서가 있는 곳이 목적지」입니다. 단 그린 보고가 있는데 판정이 다르면 여전히 무변경입니다(R13c — 범위는 보고 없는 끝 · 빈 보고뿐).

왜 보고 없는 끝이 생기나. OS 끌기 루프는 다음 마우스 메시지 전에는 대상 창에 DragEnter 를 내지 않습니다(해석 — 실측에서 추정). 그래서 문턱만 넘고 멈춘 채 떼면 어느 창도 보고하지 못합니다. 7 단계 뒤 실측에서 같은 창 12/12 · 짧은 톡 4–9/10 이 그렇게 새 창이 됐고, 영역 전에 낸 보고(rev 0)로 판정돼 무변경이 된 끌기도 있었습니다(이웃 창 6/20). 둘을 「빈 보고」로 묶어 이 판정이 닫습니다. 캔버스 거름은 그 창이 보이던 탭이 영역의 탭과 다르면 이음새를 가이드 없음으로 치는 것으로, 화면에 한 번도 안 보인 탭의 칸에 붙지 않게 합니다.

출처 창이 부서짐 · 출처 탭이 사라짐Destroyed · 스냅숏그냥 끝 (변경 없음)
  • Esc 와 떼기를 키 상태로 가르지 않습니다. 우리 창 위에서 버튼으로 떼면 그 창의 drop 이 처리하므로, none 끝이 우리 창 위를 가리키면 그것은 Esc(또는 시스템 취소)입니다. Esc 와 떼기는 같은 「그 자리에 놓기」라 가를 것이 없고, 남는 질문 「지금 커서가 어느 우리 창의 보인 가이드 위인가」를 마지막 보고 + 셸 커서의 창 사각형 검사가 답합니다.
  • 끄는 동안 웹뷰에는 포인터 사건이 오지 않습니다(끌기가 대신함). 그래서 세션 중 어느 창이든 pointermove 를 보면 끌기는 이미 끝난 것이고, 이것이 유실 대비 신호입니다.
  • 끄는 탭은 커스텀 형식 application/x-engram-tab 하나만 싣습니다 — 다른 앱이 받지 않아 그 앱에 아무것도 들어가지 않습니다. Esc 키는 세션 동안 + 200ms 삼켜 터미널 · 입력창에 들어가지 않게 합니다.
06안전장치

어긋남을 막는 네 장치 — 둘은 웹뷰와 장부 사이, 둘은 layout 모델에

끌기 · 창 닫기 · 출력이 동시에 일어날 수 있는 경로입니다. 넷이 「탭이 두 곳에 있거나 어디에도 없는」 상태, 「사용자가 못 본 결과」, 「끝나지 않는 끌기」를 막습니다. ① ② 는 웹뷰와 셸 장부 사이의 약속이고, ③ ④ 는 layout 모델 쪽 — 레이아웃 락 한 번 안 — 에 있습니다.

그림 읽기 — ① 웹뷰는 셸이 보낸 영역(번호 rev 가 달림)으로 가이드를 그리기만 하고, 놓은 점과 보인 것을 셸에 돌려보냅니다. 셸은 같은 규칙으로 다시 골라 보인 것과 같고 영역이 최신일 때만 적용합니다. ② 끝나는 길이 몇 갈래든 모두 「그 점에 놓기」로 모이고, 출처가 사라진 경우만 그냥 끝납니다. ③ 팝아웃 X 를 누르는 순간 모델에서 그 창을 빼고 묘비를 달아, 그 뒤 그 창으로의 확정은 「창 없음」으로 무변경입니다. ④ 메인의 마지막 탭이 떠나면 같은 연산 안에서 빈 탭이 생겨, 아무도 빈 메인을 보지 않습니다.

자세히 — 각 장치의 근거와 한계
  • 한 세션에 적용은 많아야 한 번 — 판정과 「적용 중」 표시가 장부 잠금 한 번 안이라, 그 뒤 오는 놓기 · 끝 신호는 늦은 신호로 버립니다. 모르는 세션 id 의 신호도 버립니다.
  • 표식(lease_tab)은 끌기 시작 때 서고, 놓기는 그 표식을 싣고 갑니다. 지난 끌기의 늦은 놓기는 StaleLease 로 무변경입니다.
  • 닫히는 창 장치의 전제 = 「팝아웃 닫기는 막을 수 없다」. 누가 프론트에 닫기 요청 리스너를 달면 이 전제가 무너지므로, 점검 명령 두 줄을 QA 게이트로 매번 돌립니다(rg -i "close.?requested" src/ → 0줄 · rg "prevent[_]close" src-tauri/src/ → 1줄).
  • 드롭 처리기 점검(6단계부터) — rg "disable_drag_drop_handler" src-tauri/src/ → 1줄(webview_env.rs) · 끈 처리기의 사건을 기대하는 코드 0줄.
  • 저장: 기록기는 같은 잠금 안에서 배치를 통째로 복사해 쓰므로 저장 파일에는 도킹 전 아니면 도킹 뒤만 실립니다 — 다시 켜도 탭은 정확히 한 곳에 있습니다. 끄는 동안 저장되는 것은 0.5초 머물러 바꾼 탭 전환 하나뿐입니다.
07왜 바꿨나 · TRD 5판 (2026-10-16)

셸이 끌기를 몰던 설계에서, 브라우저에 맡기는 설계로

끌기를 셸이 직접 몰려면 커서 폴링 · 맨 위 창 판정 · 딱지 창 · OS 함수를 모두 우리가 짜야 했습니다. 브라우저 내장 끌어 놓기는 그 일을 엔진이 하고, 셸 메인 스레드도 막지 않는다는 것을 스파이크로 확인해 바꿨습니다(사용자 결정 2026-10-16).

  • 사라지는 것
    • 셸의 8ms 커서 폴링 루프
    • 커서 밑 맨 위 창 판정
    • 딱지 창(별도 창)
    • OS 함수 대부분 → macOS 이식 때 다시 짤 것이 준다
  • 받아들인 것
    • 끌기 그림은 Windows 기본 모양 — 불투명하게 못 만들고, 가장자리가 흐려진다
    • 다른 앱 창 위에서는 끌기 그림이 사라진다
  • 버린 대안 — crabnebula 끌기 플러그인
    • 끌기 루프를 셸 메인 스레드에서 돌려, 끄는 동안 위치 사건이 막혔다가 놓은 뒤 몰려온다 → 실시간 가이드 불가
    • Esc = 취소로 고정 · 끄는 동안 위치 없음
    • 실은 것이 실제 임시 파일(탐색기에 놓으면 복사됨)
    • 끝나지 않아 앱이 멈추는 열린 버그
자세히 — 피어 · 근거 문서
  • VS Code(Electron)가 편집기 탭을 다른 창 · 새 창으로 떼는 방식이 HTML5 끌어 놓기입니다. 창 밖에 놓았는지는 「어느 창도 마지막에 dragover 를 보지 못했다」로 가르고, 호스트에 커서 위치를 물어 새 창을 엽니다(소스 확인).
  • dockview 의 Tauri 데모도 같은 방식이고 모든 창에서 Tauri 드롭 핸들러를 끕니다(리눅스에서만 실측된 데모).
  • 근거 문서: docs/research/slot-docking-drag-mechanism-2026-10-16.md (적대 리뷰 대신 실측으로 판정 — 확신도 라벨은 그 문서에).
