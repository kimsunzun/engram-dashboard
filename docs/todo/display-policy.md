# Display policy is scattered across surfaces

> **Status:** Waiting for trigger · **Canonical index:** [`../todo.md`](../todo.md)

- **Display policy as one set of data** — scrollbar · font · color · margin · scrollback length · line wrapping are hard-coded separately on each surface (terminal / structured / DOM), so "only the terminal looks different" keeps recurring. If the policy is held as data and each renderer applies it by its own means, that class of problem shrinks in principle, and it also fits the LLM-control stance. **Why not now:** the design step of separating what is policy from what is implementation discretion comes first.
- **Scrollbar — the branch is settled as (B); starting is deferred to the frontend refactor** (user decision 2026-08-21). What is wanted: **zero space taken · appears only when scrolling or when near the scrollbar area · can be grabbed and dragged · thickness the same as the structured surface** (the thickness is already reflected). ★Note — this is not "making the terminal match the chat"★: **appearing on proximity does not exist on the chat side either** (the chat reacts only to scrolling, with no reaction to hover). So two of the four items have to be newly built on both sides. The terminal's space occupation (14px) is reserved not by CSS but by an **xterm option**, and reducing it **changes the column count** (FitAddon reads the reserved width from a JS constant — measured).
  - **Can be shared:** policy values (thickness · margin · shape · color · hide delay · proximity distance) and the **"should it be visible now" decision** (it holds by looking only at the pointer position and scroll events).
  - **Cannot be shared:** thumb position · length calculation (the chat is DOM overflow, the terminal is **internal buffer state** — only xterm knows) · drag conversion (pixel→scroll position vs pixel→**buffer line number**) · DOM structure.
  - **Branch (A) style each separately + share the policy** — cheap, but the implementation stays in two copies forever, and the terminal side has to override xterm's own rules with CSS and so **breaks on version upgrades** (this is the lineage of the dead code that appeared this time).
  - **★Branch (B) = adopted (user judgment 2026-08-21)★** — **turn off** the xterm scrollbar by setting its **width to 0** (a public option) and lay our own thumb on top. The adapter does only two things, reading and writing the scroll position, and we confirmed that all the xterm APIs it needs are public: visible start line · baseline · total line count (thumb geometry) · scroll event (updates · "is scrolling" decision) · scroll to a given line / relative scroll (dragging). So the parts that rely on xterm internal classes or inline styles are **0**, and it does not break on version upgrades. ★Going with (B) discards the thickness CSS added today.★
  - **Volume — it can be split. Phase 1 alone satisfies all four spec items.**
    - **Phase 1 = terminal only (small).** thumb geometry calculation (pure calculation → easy to test) · drag · appear decision (scroll + proximity) · hide timer · turning off the xterm scrollbar + **confirming the dimension renegotiation for the resulting column-count change**. The implementation still remains in two copies. ★**Start condition = the frontend refactor**★ — do not start before it (user decision 2026-08-21).
    - **Phase 2 = global unification (large).** ★This is the heart of the volume★ — that scroll-area component is not chat-only but an **app-wide seam** (everything passes through it: tree · presets · popup lists · DOM observer), and swapping it affects the whole app. Moreover, "that component is the seam" **reverses the ADR-0053 decision**, so a new decision record is needed.
    - **If calculation and drag are written surface-neutral from the start in phase 1, phase 2 ends with adding an adapter** — without this condition, phase 2 would have to rewrite them.
- **The terminal scrollbar appears on hover alone — not fixed yet.** The cause is not our CSS but **xterm itself** (the scroll component reveals it on mouseover of the whole terminal). The visibility rule that the 2026-08-21 commit (788051b) described as unified **targeted the native scrollbar, but what is visible on screen is a DOM element xterm creates**, so it did not reach it (after forcing a fluorescent color, a color search of the full capture → 0 pixels). The branch was settled as (B), and the fix waits for starting its phase 1 (deferred to the frontend refactor).
- **The `::-webkit-scrollbar` block in `index.css` is currently dead code** — we left it in place (two existing tests assert that form, and it becomes the fallback if a scrollbar implementation comes back). Its deletion goes together with starting (B) phase 1 above (deferred to the frontend refactor).
- **Slider color and shape differ from the structured surface** — the color is xterm's default, the shape is square (the structured surface is a pill). It is a visible decision, so a separate matter.
- **How to open the failure reason — by clicking a symbol, not row hover** (user preference 2026-08-23, deferred as a separate matter). Currently the browser's default tooltip is attached to the **entire tree row**, so ⓐ it appears when hovering anywhere on the row, not on the symbol, ⓑ it appears only **after a delay of about 1 second**, and ⓒ it pushes out the working-folder path that was in that spot. In the user's own words: 「아이콘 클릭했을때 툴팁 뜨는게 맞다고 생각」 (I think a tooltip appearing when the icon is clicked is right). **Why not now:** ADR-0165 sets 「원인은 로그가 소유하고 화면은 아이콘만」 (the log owns the cause and the screen shows only the icon) as its policy (provisionally approved), so leaving the tree hover is itself at the boundary of that policy — while touching how it opens, it is right to settle that boundary together.
- **Open the terminal cursor as a user setting** — currently it is only the default blinking bar (`cursorStyle:'bar'` · `cursorBlink:true` · `cursorInactiveStyle:'bar'` — `src/components/slot/TerminalSlot.tsx:84-86`, `fa1690d`). User decision (2026-09-25): 「나중에 옵션으로 뺀다」 (pull it out as an option later). **Trigger = when the terminal settings are built.** For it to become a setting, an LLM control path must exist with it (`CLAUDE.md` 「LLM-우선 제어」). The existing surfaces that carry such settings are the shell `settings.json` and the four generic commands (`settings.get` · `set` · `reset` · `schema`), and one setting = one line of the schema table (`src-tauri/src/settings/registry.rs` — ADR-0265). The old `ui-settings.json` (a single theme field) was retired in P3d. **Why not now:** the user deferred it.
