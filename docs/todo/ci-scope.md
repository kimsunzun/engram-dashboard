# CI 실행 범위를 좁힐지 — 경로 필터 조사

> **상태:** 착수 가능 · **정본 색인:** [`../todo.md`](../todo.md)

- **문제(사용자 제기 2026-08-26):** 문서만 바꿔도 검증 3잡이 통째로 돈다. 러너 비용은 0이지만(public repo) **기다림이 거슬린다.**
- ★**먼저 재 볼 것 — 아픔의 원인이 CI 가 아닐 수 있다**★. 2026-08-26 에 문서 작업으로 CI 가 다섯 번 돌았는데, 그중 넷은 **커밋을 하나씩 따로 밀어서** 생긴 것이다(밀 때마다 `concurrency` 가 앞 실행을 죽이고 새로 돈다). 모아서 한 번에 밀면 한 번이다. **이 습관 교정은 비용 0·위험 0 이고, 그것만으로 충분한지부터 보는 게 순서다.**
- **지금 왜 넓은가 — 의도된 것이다.** 워크플로 주석이 근거를 갖고 있다(`.github/workflows/ci.yml` 의 `on.push.branches`): *"좁히면 그 브랜치 작업에는 게이트가 아예 없어진다. 로컬을 quick 으로 낮춘 분담과 맞물리면 무게이트 구간이 생긴다."* ★단 그 근거는 **브랜치 축**에 대한 것이고 **경로 축**은 다루지 않는다★ — 이 항목이 여는 것은 그 빈자리다.

## ★착수 전 반드시 풀 것 — 태그 경로★

**모른다. 추측으로 메우지 말 것.** GitHub Actions 의 경로 필터가 **태그 push 에도 적용되는지**가 이 결정의 안전성을 가른다.

- 이 워크플로는 `v*` 태그 push 에서 검증 3잡을 **일부러** 돌리고, 릴리스 잡이 `needs: [backend, gates, frontend]` 로 그 결과에 매달려 있다.
- 주석이 그 이유를 박아 뒀다 — 태그는 아무 커밋에나 달 수 있어 "이 커밋은 master 에서 이미 초록이었다"를 전제할 수 없다.
- ★따라서 경로 필터가 태그에도 걸린다면, 문서만 바뀐 커밋에 태그를 달았을 때 **릴리스가 막히거나 검증 없이 나갈 수 있다**★. 릴리스는 되돌리기 어렵고 재시도도 안 되는 경로다.

## 조사할 축 둘

1. **필터로 잡 자체를 건너뛴다**(`on.push.paths` / `paths-ignore`) — 단순하지만 위 태그 문제와, 필수 체크로 쓸 때 「체크가 영영 안 붙는」 알려진 함정이 있다고 들었다(미확인).
2. **잡은 항상 돌되 안에서 변경을 감지해 무거운 단계만 건너뛴다** — 체크 자체는 계속 보고되므로 `needs:` 의존이 안 깨진다. 대가는 러너를 어쨌든 띄우는 것.

**성숙 프로젝트가 어느 쪽을 왜 고르는지**가 조사의 중심이다.

## 절차

★**CI 는 게이트라 이 저장소에서 굵은 변경이다**★ — `/research`(참조 구현 조사) → 선택지 → **사용자 결정** → 필요하면 ADR. 임의로 워크플로를 고치지 않는다. 고칠 땐 `ADR-0131`(러너 단일화·검증 전용 범위·빌드/발행 잡 분리의 근거)을 먼저 읽는다.
