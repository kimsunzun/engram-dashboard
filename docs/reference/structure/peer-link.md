# Peer link (daemon ↔ daemon)

> Live reference doc — edit in place when the code moves. Anchors are file and symbol names only.
> Decisions and their reasons: ADR-0389 (identity per OS account and machine, sealing, list MAC, duplicate detection, local identity lock; its form is ADR-0401) · ADR-0401 (the local identity lock is a private namespace bounded by the account SID) · ADR-0291 (data file rules) · ADR-0395 (the OS account is the local trust boundary) · ADR-0266 (OS code lives in platform) · ADR-0388 (the iroh link adapter: one QUIC connection per link, liveness from QUIC, tie-break) · ADR-0390 (mail only, the accept gate, removal before the save) · ADR-0310 (D2: its own Wire · Registry · Listener).

**Whole picture** = `docs/reference/architecture.md` · **Transport crate** = `docs/reference/structure/transport.md` · **Shell link** = `docs/reference/structure/daemon-link.md`

## What it is

`crates/engram-dashboard-daemon/src/link/peer/` is the daemon's link to the daemons of the same user on other PCs, beside the shell link in `link/`. It holds this PC's identity and its trusted list (a per-account-and-machine identity key sealed for the current OS account, the PC ID derived from it, the trusted list with its network settings and MAC, one state object `PeerStore`), the PeerWire vocabulary, and the running link (`PeerLink`): the trust operations over `PeerStore`, the link endpoint on transport's `iroh` adapter, the accept gate, one transport registry of PeerWire links, and the state `peer.list` and the app read. The daemon starts it at boot and stops it first at shutdown. Not built yet: approvals and the ask-the-user seam, the `peer.*` commands, mail over the link and the agent directory — they call `PeerLink` and fill in the PeerWire messages the link hands on unread.

## Modules

- `link/peer/mod.rs` — module root; link adapter types never enter here.
- `link/peer/id.rs` — `PeerId`: the 32-byte public key, its canonical text (64 lowercase hex), the grouped full-ID display (`grouped`) and parsing (`parse` also takes the grouped and uppercase forms; stored IDs must be canonical).
- `link/peer/identity.rs` — `Secret` (zeroed on drop, never printed; `id` derives the PC ID through transport's `iroh::public_key`), `PeerFiles` (the per-account-and-machine names in the state folder, and this account's key files under other machine ids), `load_key` → `KeyLoad` (loaded / missing / unreadable / transient / unavailable; the unsealed plaintext is wiped), `create_key` (never replaces), `replace_key` (backup copy, then atomic swap), `sweep_temps` (leftover temp files of the key and list — `PeerLink::start` runs it through `PeerStore::sweep_temps`).
- `link/peer/mac.rs` — `sign` / `verify`: HMAC-SHA256 over the stored body bytes with an HKDF-SHA256 key from the identity secret (`ring`); pinned by a known-answer test.
- `link/peer/trusted.rs` — `TrustedList` / `TrustedPeer` / `Permission` / `NetworkSettings` / `Helper`, the entry rules (`check_entries`, `check_name`), the default listen ports (`RELEASE_DEFAULT_PORT`, `DEV_DEFAULT_PORT`), the file `SPEC` for base `file`, `read_list` → `ListFile`, `write_list`.
- `link/peer/os.rs` — `PeerOs`: the OS seam (seal, unseal, identity lock, wall clock); `OsPeer` = platform `secret` and `account_lock` (lock name `engram-peer-identity.<ID>`).
- `link/peer/store.rs` — `PeerStore` (the state object), `PeerStatus`, `PeerError`, `PeerEdit`, `Removal`, `Regenerated`; `store/tests.rs` runs it over real temp folders with a fake `PeerOs`.
- `link/peer/wire.rs` — `PeerWire` (transport `Wire`: JSON text frames tagged by `type`; `Mail` is the only request, paired by its id with `MailVerdict`), `PeerMsg` (`Hello` · `Mail` · `MailVerdict` · `ReplyOverdue` · `DirSnapshot` · `DirDelta` · `DirResync` · `Probe` · `ProbeAck` · `Duplicate`), `Instance` (the run id in `Hello`), `PEER_WIRE_VERSION`, `ALPN` (`engram/peer/1`), `MAX_FRAME_BYTES` (512 KiB), `encoded_len` (the sender's size check).
- `link/peer/handshake.rs` — `PeerHandshake` (dialer: its `Hello` first; acceptor: the dialer's `Hello` → done, its own `Hello` follows as the first frame), the version and duplicate-run checks, `HandshakeNotes` (the run each finished handshake saw, and why a refusal happened — the transport reports only the close code).
- `link/peer/book.rs` — `LinkBook`, pure: per listed PC the live links, the chosen one, the dialing handle's state, the duplicate evidence; answers with `Action`s (close · send · add a dialing handle · redial). `Online`, `Warning`, `Refusal`, the timing constants. `book/tests.rs` drives it with synthetic instants.
- `link/peer/gate.rs` — `Knocks`: PCs refused at the accept gate (bounded list for `peer.list`, throttled refusal log).
- `link/peer/runtime.rs` — `PeerLink` (`start`, `stop`, `snapshot`, `changes`, the trust operations), `LinkSettings`, `PeerSnapshot` / `PeerRow` / `EndpointView` / `EndpointError`; inside: the actor that owns the endpoint, registry and handles, `PeerDialer` (a listed PC's logical address resolved at each dial), the accept loop and one drain task per handle. `runtime/tests.rs` runs PCs in one process over real loopback endpoints with helpers off.
- Platform (`crates/engram-dashboard-platform/src/`): `secret.rs` (`seal` / `unseal`, DPAPI CurrentUser), `account.rs` (`current_account_id`, `machine_id`), `account_lock.rs` (`acquire` — a private object namespace bounded by the account's SID; nothing on disk), `fs.rs` (`rename_no_replace`). Base `file.rs`: `write_atomic_new` / `copy_atomic_new` (temp → sync → rename that never replaces).

## Files (daemon state folder, `DataLayout::daemon_state_dir`)

- `peer-key.<account>.<machine>` — the sealed secret blob, nothing else. `<account>` = OS account id (Windows SID), `<machine>` = machine id (Windows `MachineGuid`); both are checked to be letters, digits and `-` before they become names.
- `peer-key.<account>.<machine>.bak-<UTC time>[-n]` — copies of the keys a regenerate replaced; never overwritten, never read back.
- All writes are base `file` atomic writes (temp names `<name>.tmp<pid>.<n>`); the key and the backups are created with a rename that never replaces.
- `peers.<account>.<machine>.json` — `{version, mac, body}`: `body` is the list serialized as a JSON string and `mac` covers its exact bytes. Under base `file` rules (`SPEC`): a newer version or a failed read refuses writes; a corrupt file (including a body that does not parse or breaks an entry rule) puts an empty list with default settings in memory, but once a key is loaded the feature stays off (`ListCorrupt`) until `accept_list`, whose write copies the corrupt file to `.corrupt` first; a missing file is just an empty list; the overwrite decision is made again right before every write.
- Files of any other name are never touched. Two accounts sharing the folder never see each other's files.

## Flow and promises

- Load (`PeerStore::load` / `open`): name the files → read the list file → read and unseal the key → decide the key state (no key file: `KeyUnreadable(MissingUnderList)` if the list names PCs, else `AdoptOrFresh` if this account has keys under other machine ids, else `NoIdentityYet`) → check the list MAC under the key (no key: not checked) → take the identity lock when a key is loaded. Loading creates nothing.
- `PeerStatus` is the one answer to "may the peer feature run" — only `Ready` does. Priority: unavailable → key transient / unreadable / adopt-or-fresh → no key yet (list refused, else no identity) → identity in use → list refused → list changed outside / list corrupt → ready.
- A key is written only by `ensure_identity` (from `NoIdentityYet`; `add` and `set_network` call it first, the other list writes need `Ready`), `regenerate`, `start_fresh` and `adopt`. A list file that must not be written over (newer version, failed read) wins over the adopt-or-fresh question, so none of them runs then. Regenerate keeps a backup and does not re-sign the list, so the list reads as changed outside until `accept_list`; a restart in between gives the same state. Regenerate is refused while the key is transient or the adopt-or-fresh question is open.
- `adopt` copies the other machine's key (create, never replace) and list, then reloads — a key this account cannot open lands in `KeyUnreadable`. A list file already here is handled by base `file`'s write policy first: refused (newer, failed read) → nothing is written; otherwise it is set aside as `.corrupt` before the other list is copied over it. The other machine's files stay.
- List writes apply to a copy, sign it, write it, and keep it only on success; `remove` revokes in memory first and reports a refused save in `Removal::saved`. A file refusal answers `PeerError::Conflict`.
- Identity lock: platform `account_lock` — a private object namespace named `engram-peer-identity.<ID>` whose boundary holds only this account's SID; the process that creates it holds the lock, and it goes when that process closes it or ends. Nothing is written to disk. Other accounts cannot create it (Win32: the creator must be within the boundary — measured: a boundary SID the caller lacks is refused), and a boundary without a session number spans sessions. Held for as long as a key is loaded and moved on a regenerate. Held elsewhere → `IdentityInUse`, and `retry` tries again (the other copy may have ended); an OS failure → the copy runs without it (`lock_note`). ADR-0401 replaced ADR-0389 decision 9's `Global\` named mutex, which another account could pre-create.
- `PeerStore` does no gating (human vs agent, approvals), no retry timing (`retry` reloads from a transient key or a failed list read and retakes a lock held elsewhere; the caller decides when) and no logging.
- Not defended (ADR-0395): a process of the same account can unseal the key and recompute the MAC; an older correctly signed list or a key backup put back by anyone who can write the folder is accepted.

## Links (the running peer link)

- Start (`lib.rs` `run`, after `daemon.json` is published, on its own task so the accept loop never waits on it; the started link lands in `peer_slot`): `PeerLink::start(daemon_state_dir, LinkSettings::daemon())` — loads `PeerStore` on the blocking pool (which takes the identity lock when the key loads), sweeps the key and list temp files, draws this run's `Instance`, spawns the actor. A failure to start logs and leaves the daemon running without peer links. Stop (`run` step 12, first): a start still loading is aborted; `PeerLink::stop` closes every link with a short flush, then the endpoint — within `STOP_DEADLINE` (3 s), past which the actor is aborted; dropping its state (`Running`'s `Drop`) still aborts the accept and drain tasks, cuts every handle and closes the endpoint, so nothing networks on after a stop.
- Endpoint lifecycle: the endpoint runs only while `PeerStatus::Ready` (key loaded, identity not held by another copy, list verified) and at least one PC is listed — none at boot with an empty list, up on the first applied add, down after the last removal or when the status leaves ready (regenerate, an unaccepted list, a key that cannot be read, the identity in use by another copy). The build runs `NetworkSettings::check_for_endpoint` first: a stored helper URL the adapter refuses is `EndpointError::HelperRefused` (never n0's servers instead; it stays until the settings change), a bind failure is `EndpointError::Bind`, retried every `BIND_RETRY` — except right after a restart, when it is first retried every 250 ms for about 3 s (the closed endpoint may hold the fixed port a moment longer) without showing an error. A change of the identity or the network settings restarts the endpoint: a new registry, and the link book starts its links and dialing over (`LinkBook::restart`) but keeps the duplicate evidence for the daemon run. While the status is key-transient, identity-in-use or list-unreadable, `PeerStore::retry` runs on the blocking pool with a 5 s → 5 min backoff.
- Settings: `LinkSettings::daemon()` takes the dev default port in debug builds (`DEV_DEFAULT_PORT` — the builds that run on `.engram-dev`), release's otherwise; `loopback_only` binds 127.0.0.1 for tests. The registry's policy: no supervisor ping or silence cut (QUIC liveness, ADR-0388 d6), reconnect without end with a 2 → 60 s backoff and a 20 s connect timeout, `Mail` deadline 120 s.
- Accept: the adapter calls the gate (`accept_if`) with the dialer's key before any stream — a listed PC with permission `mail` while the status is ready passes; anyone else is refused (`HANDSHAKE_REJECTED`, terminal for the dialer), recorded in `Knocks` and logged under one budget for all refusals — the first per minute, the rest folded into the next line with their count and number of PCs (the change signal ticks on the same budget, plus once at the end of a window that folded anything). Accepted links are attached as `acc-<key>` with the acceptor handshake.
- Dial: every listed PC gets one dialing handle (label `dial-<ID>`, logical address `peer:<ID>`); `PeerDialer` resolves the ID and the PC's current direct address at each dial, so an address edit is used from the next attempt (a handle waiting out its backoff is nudged to dial at once). A terminal refusal stops the handle until a re-arm: any applied add, a link of that PC ending, daemon start, and every 10 min for "not paired".
- The link book decides (`book.rs` head): tie-break, closing the dialing handle while an accepted link is the chosen one (at once when it is between attempts — backing off, idle, gave up, as the runtime reads from the handle; a handle mid-attempt is left to the tie-break and closed if it fails), re-arms, duplicate detection (probe the older run's link; a replaced or refused run coming back is refused in the handshake; flap rule — same-direction replacements only) and the per-PC `Online` state. The runtime shows `EndpointError` for every PC while the endpoint is in error.
- Per frame: each drain task checks the sending PC against the current published trust before handling a frame; a PC no longer trusted has its frame dropped and its handles closed. `Probe` is answered on the same connection; only the first `ProbeAck` with the nonce of the probe waiting on that link reaches the actor; a `Duplicate` is recorded in the book on the drain task and logged only when it changes the PC's warning; `Hello` after the handshake is ignored; `Mail`, `MailVerdict` (a reply the transport pairs), `ReplyOverdue` and the directory frames are dropped with a debug line until their units handle them.
- Trust operations (`PeerLink::add` · `edit` · `remove` · `set_network` · `regenerate` · `accept_list` · `adopt` · `start_fresh` · `ensure_identity`) run the `PeerStore` operation under the store lock, then re-publish the state and wake the actor — they finish without waiting for links. ★Blocking (disk, DPAPI) — call them on the blocking pool★. `remove` revokes first: the PC leaves the published trust (the gate and the per-frame check see it at once) and its links are cut as refused at once (transport `Peer::abort` — no flush and no wait for the PC to acknowledge what was written, so a PC that stopped reading or answering cannot hold them), then the list is saved; a refused save is in `Removal::saved` and the revocation stays. `add` re-arms every refused dialing handle and drops the PC from the knock list.
- State for `peer.list` and the app: `PeerLink::snapshot` (status, ID, lock note, network settings, `EndpointView`, per PC `Online` + duplicate `Warning`, refused knocks) and `PeerLink::changes` (a watch that ticks on every change of it; refused knocks fold into one tick per refusal-log window, so a new knock shows at most one window late). Neither takes the store lock.

## Promises (links)

- Lock order: the store lock, then the published state (`Core::publish` · `revoke`). The link book, the knock list and the endpoint view are each taken alone and briefly; the handshake (on transport tasks) and the gate (on the adapter's gate tasks) take theirs there. Nothing async takes the store lock; only the trust operations and the start-up load (blocking pool) do.
- The actor alone touches the endpoint, the registry and the handles; it awaits only the endpoint bind, `close_all` and the endpoint close, never a request. Drain tasks read their inbox to `None` and never await a request (transport receiver invariants). Messages carry an endpoint epoch, so a closed endpoint's late events are ignored.
- The secret leaves `PeerStore` only as a copy in the published state for the endpoint build (zeroed when the last copy goes); it is never logged.
- Duplicate warnings stay for the rest of the daemon run, across endpoint restarts (nothing clears them yet).
- Not shown by the tests here (two real PCs): NAT traversal, relay and lookup servers, mDNS, the firewall prompt, the 30 s QUIC idle-out of a frozen peer.
