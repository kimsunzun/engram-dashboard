## What it is

`crates/engram-dashboard-daemon/src/link/peer/` is the daemon's link to the daemons of the same user on other PCs, beside the shell link in `link/`. It holds this PC's identity and its trusted list (a per-account-and-machine identity key sealed for the current OS account, the PC ID derived from it, the trusted list with its network settings and MAC, one state object `PeerStore`), the PeerWire vocabulary, and the running link (`PeerLink`): the trust operations over `PeerStore`, the link endpoint on transport's `iroh` adapter, the accept gate, one transport registry of PeerWire links, and the state `peer.list` and the app read. The daemon starts it at boot and stops it first at shutdown. On top of it: the `peer.*` commands (the daemon's own command table) with their approval gate, and the approvals — pending requests from agents and the questions the peer state raises — which a human answers in the app or in the OS dialog the daemon's shared "ask the user" seam (`src/ask_user.rs`) shows. Mail rides on the link (`Mail` / `MailVerdict` / `ReplyOverdue`) and so does the agent directory (`DirSnapshot` / `DirDelta` / `DirResync`): the link carries them in PeerWire terms only, and the daemon's mail host behind `mail::MailInbox` (`messaging_host.rs` `PeerMail`) is what they mean to the agents — `link/` names no agent or mail-kernel type (CI daemon gate 1).

## Files (daemon state folder, `DataLayout::daemon_state_dir`)

- `peer-key.<account>.<machine>` — the sealed secret blob, nothing else. `<account>` = OS account id (Windows SID), `<machine>` = machine id (Windows `MachineGuid`); both are checked to be letters, digits and `-` before they become names.
- `peer-key.<account>.<machine>.bak-<UTC time>[-n]` — copies of the keys a regenerate replaced; never overwritten, never read back.
- All writes are base `file` atomic writes (temp names `<name>.tmp<pid>.<n>`); the key and the backups are created with a rename that never replaces.
- `peers.<account>.<machine>.json` — `{version, mac, body}`: `body` is the list serialized as a JSON string and `mac` covers its exact bytes. Under base `file` rules (`SPEC`): a newer version or a failed read refuses writes; a corrupt file (including a body that does not parse or breaks an entry rule) puts an empty list with default settings in memory, but once a key is loaded the feature stays off (`ListCorrupt`) until `accept_list`, whose write copies the corrupt file to `.corrupt` first; a missing file is just an empty list; the overwrite decision is made again right before every write.
- Files of any other name are never touched. Two accounts sharing the folder never see each other's files.

## Flow and promises

- Load (`PeerStore::load` / `open`): name the files → read the list file → read and unseal the key → decide the key state (no key file: `KeyUnreadable(MissingUnderList)` if the list names PCs, else `AdoptOrFresh` if this account has keys under other machine ids, else `NoIdentityYet`) → check the list MAC under the key (no key: not checked) → take the identity lock when a key is loaded. Loading creates nothing.
- `PeerStatus` is the one answer to "may the peer feature run" — only `Ready` does. Priority: unavailable → key transient / unreadable / adopt-or-fresh → no key yet (list refused, else no identity) → identity in use → list refused → list changed outside / list corrupt → ready.
- A key is written only by `ensure_identity` (from `NoIdentityYet`; `add` and `set_network` call it first, the other list writes need `Ready`), `regenerate`, `start_fresh` and `adopt`. A list file that must not be written over (newer version, failed read) wins over the adopt-or-fresh question, so none of them runs then. Regenerate keeps a backup and does not re-sign the list, so the list reads as changed outside until `accept_list`; a restart in between gives the same state. Regenerate is refused while the key is transient or the adopt-or-fresh question is open.
- `adopt` copies the other machine's key (create, never replace) and list, then reloads — a key this account cannot open lands in `KeyUnreadable`. A list file already here is handled by base `file`'s write policy first: refused (newer, failed read) → nothing is written; otherwise it is set aside as `.corrupt` before the other list is copied over it. The other machine's files stay.
- List writes apply to a copy, sign it, write it, and keep it only on success; `remove` revokes in memory first and reports a refused save in `Removal::saved`. A file refusal answers `PeerError::Conflict`.
- Identity lock: platform `account_lock` — a private object namespace named `engram-peer-identity.<ID>` whose boundary holds only this account's SID; the process that creates it holds the lock, and it goes when that process closes it or ends. Nothing is written to disk. Other accounts cannot create it (Win32: the creator must be within the boundary — measured: a boundary SID the caller lacks is refused), and a boundary without a session number spans sessions. Held for as long as a key is loaded and moved on a regenerate. Held elsewhere → `IdentityInUse`, and `retry` tries again (the other copy may have ended); an OS failure → the copy runs without it (`lock_note`). ADR-0401 replaced ADR-0389 decision 9's `Global\` named mutex, which another account could pre-create.
- `PeerStore` does no gating (human vs agent, approvals), no retry timing (`retry` reloads from a transient key or a failed list read and retakes a lock held elsewhere; the caller decides when) and no logging.
- Not defended (ADR-0395): a process of the same account can unseal the key and recompute the MAC; an older correctly signed list or a key backup put back by anyone who can write the folder is accepted; and any process of the same account can press Approve in the native dialog (`TDM_CLICK_BUTTON`, UI Automation) — the dialog is not a boundary against same-account code.

## Links (the running peer link)

- Start (`lib.rs` `run`, after `daemon.json` is published, on its own task so the accept loop never waits on it; the started link lands in `peer_slot`): `PeerLink::start(daemon_state_dir, LinkSettings::daemon(), Some(Host { mail, bell }))` — loads `PeerStore` on the blocking pool (which takes the identity lock when the key loads), sweeps the key and list temp files, draws this run's `Instance`, spawns the actor. A failure to start logs and leaves the daemon running without peer links. Stop (`run` step 12, first): a start still loading is aborted (with it the `follow` task); the approvals stop their dialog thread; `PeerLink::stop` refuses every trust operation from its first moment, then closes every link with a short flush, then the endpoint — within `STOP_DEADLINE` (3 s), past which the actor is aborted; dropping its state (`Running`'s `Drop`) still aborts the accept and drain tasks, cuts every handle and closes the endpoint, so nothing networks on after a stop.
- Endpoint lifecycle: the endpoint runs only while `PeerStatus::Ready` (key loaded, identity not held by another copy, list verified) and at least one PC is listed — none at boot with an empty list, up on the first applied add, down after the last removal or when the status leaves ready (regenerate, an unaccepted list, a key that cannot be read, the identity in use by another copy). The build runs `NetworkSettings::check_for_endpoint` first: a stored helper URL the adapter refuses is `EndpointError::HelperRefused` (never n0's servers instead; it stays until the settings change), a bind failure is `EndpointError::Bind`, retried every `BIND_RETRY` — except right after a restart, when it is first retried every 250 ms for about 3 s (the closed endpoint may hold the fixed port a moment longer) without showing an error. A change of the identity or the network settings restarts the endpoint: a new registry, and the link book starts its links and dialing over (`LinkBook::restart`) but keeps the duplicate evidence for the daemon run. While the status is key-transient, identity-in-use or list-unreadable, `PeerStore::retry` runs on the blocking pool with a 5 s → 5 min backoff.
- Settings: `LinkSettings::daemon()` takes the dev default port in debug builds (`DEV_DEFAULT_PORT` — the builds that run on `.engram-dev`), release's otherwise; `loopback_only` binds 127.0.0.1 for tests. The registry's policy: no supervisor ping or silence cut (QUIC liveness, ADR-0388 d6), reconnect without end with a 2 → 60 s backoff and a 20 s connect timeout, `Mail` deadline 120 s.
- Accept: the adapter calls the gate (`accept_if`) with the dialer's key before any stream — a listed PC with permission `mail` while the status is ready passes; anyone else is refused (`HANDSHAKE_REJECTED`, terminal for the dialer), recorded in `Knocks` and logged under one budget for all refusals — the first per minute, the rest folded into the next line with their count and number of PCs (the change signal ticks on the same budget, plus once at the end of a window that folded anything). Accepted links are attached as `acc-<key>` with the acceptor handshake.
- Dial: every listed PC gets one dialing handle (label `dial-<ID>`, logical address `peer:<ID>`); `PeerDialer` resolves the ID and the PC's current direct address at each dial, so an address edit is used from the next attempt (a handle waiting out its backoff is nudged to dial at once). A terminal refusal stops the handle until a re-arm: any applied add, a link of that PC ending, daemon start, and every 10 min for "not paired".
- The link book decides (`book.rs` head): tie-break, closing the dialing handle while an accepted link is the chosen one (at once when it is between attempts — backing off, idle, gave up, as the runtime reads from the handle; a handle mid-attempt is left to the tie-break and closed if it fails), re-arms, duplicate detection (probe the older run's link; a replaced or refused run coming back is refused in the handshake; flap rule — same-direction replacements only) and the per-PC `Online` state. The runtime shows `EndpointError` for every PC while the endpoint is in error.
- Per frame: each drain task checks the sending PC against the current published trust before handling a frame; a PC no longer trusted has its frame dropped and its handles closed. `Probe` is answered on the same connection; only the first `ProbeAck` with the nonce of the probe waiting on that link reaches the actor; a `Duplicate` is recorded in the book on the drain task and logged only when it changes the PC's warning; `Hello` after the handshake is ignored; `Mail` goes to that PC's receive queue, `ReplyOverdue` to the host (blocking pool), `DirSnapshot` / `DirDelta` to that PC's copy and `DirResync` is answered with this PC's snapshot on the same connection; a `MailVerdict` that reaches the inbox answers no waiting request (past its deadline — the transport pairs the others) and is dropped.
- Trust operations (`PeerLink::add` · `edit` · `remove` · `set_network` · `regenerate` · `accept_list` · `adopt` · `start_fresh` · `ensure_identity`) run the `PeerStore` operation under the store lock, then re-publish the state and wake the actor — they finish without waiting for links. ★Blocking (disk, DPAPI) — call them on the blocking pool★. `remove` revokes first: the PC leaves the published trust (the gate and the per-frame check see it at once) and its links are cut as refused at once (transport `Peer::abort` — no flush and no wait for the PC to acknowledge what was written, so a PC that stopped reading or answering cannot hold them), then the list is saved; a refused save is in `Removal::saved` and the revocation stays. `add` re-arms every refused dialing handle and drops the PC from the knock list.
- State for `peer.list` and the app: `PeerLink::snapshot` (status, ID, lock note, network settings, `EndpointView`, per PC `Online` + duplicate `Warning` + directory copy, refused knocks) and `PeerLink::changes` (a watch that ticks on every change of it; refused knocks fold into one tick per refusal-log window, so a new knock shows at most one window late). Neither takes the store lock.

## Mail over the link

- Sending (`PeerLink::send_mail`, non-blocking, callable from any thread): the encoded `Mail` over `MAX_FRAME_BYTES` → `MailEnd::TooLarge` (nothing sent, the link stays); no chosen link or the PC no longer trusted → `Offline`; `IN_FLIGHT_CAP` (256) requests to that PC already waiting → `Limit`; else a PeerWire request on the PC's chosen link under the registry's 120 s deadline (`mail::MAIL_DEADLINE` — ADR-0388 d8), on a spawned task. ★One `MailEnd` per mail★, given to the caller's callback on the blocking pool: the verdict; `Disconnected { sent: false }` → `Offline`; a full outbound queue → `Limit`; the deadline, `Disconnected { sent: true }` or anything else → `Unconfirmed`. A verdict is paired inside the transport, past the drain task's per-frame trust check, so the runtime checks again that the PC is still trusted and still the run the mail went to (`Core::still_trusted` — trust + `LinkBook::last_run`) on the blocking thread that hands the end on, right before the callback — a removal while the answer waited for that thread still stops it; otherwise it is `Unconfirmed` (ADR-0390 d4). From that check until the callback returns (the kernel has applied the verdict) the thread holds the read side of the verdict gate (`Core::verdict_gate`); `Core::revoke` takes the write side before it withdraws trust, so once `peer.remove` returns no verdict of that PC is applied. The kernel's verdict entry only parks a late notice and rings the flush doorbell (in the daemon's assembly), so the gate is never held across an injection.
- Receiving: a `Mail` frame with more than `MAX_MAIL_ROWS` (64, the kernel's `MAX_REMOTE_ROWS`) rows, or whose text fields sum to more than `MAX_MAIL_BYTES` (512 KiB, `mail::mail_bytes`), is refused before it is queued (`REMOTE_REFUSED`); the others go to their PC's `Inbound` queue — never run on the drain task, because the kernel injects inline. A frame waits only for earlier frames of that PC sharing a recipient token; at most 4 run at once, at most 64 wait or run (a frame arriving at a full queue is answered at once with every row refused `REMOTE_LIMIT`, "receiver busy"); one past 120 s since it arrived here is dropped — when the queue would start it and again when its blocking job starts (ADR-0404 d5). A runnable frame runs `MailInbox::mail` on the blocking pool (`run_job`) with this PC's name for the sender's PC and the arrival instant, and its verdict goes back on the connection the frame came on (`notify_in` — after a reconnect it is not sent and the sender reports it unconfirmed). Its slot and tokens go back to the queue it started from on every exit, a panic included (`Finished`, by the queue's generation — a PC removed and added again has a new queue). A whole-frame refusal answers every row `refused` with its code and reason, at most 64 rows; a verdict over the frame cap leaves rows out until it fits (the sender settles them unconfirmed), so an answer never ends this PC's own link. Without a mail host, mail is refused `REMOTE_REFUSED`.
- `PeerLink::send_reply_overdue` — best-effort `ReplyOverdue` on the PC's chosen link (lost when it has none or the PC was just removed); an inbound one is dropped unless its request id passes `MailInbox::mail_id_ok` (the kernel's `remote_msg_id_ok`); the others wait in that PC's queue (each id once, at most `MAX_OVERDUE_WAITING` = 256 — past it a report is dropped with a warning) and go to `MailInbox::reply_overdue` on the blocking pool, at most `MAX_OVERDUE_RUNNING` (4) at once. The other PC's sweep sends one report per overdue request back to back and never again, so a burst is kept. `peer.remove` drops that PC's queue (`Core::revoke`) and `PeerLink::stop` drops every queue; each report checks trust and the stop again as its job starts, so nothing waiting reaches the host after either (a report already being handed on finishes).
- The daemon's side (`messaging_host.rs` `PeerMail`, assembled with the kernel by `messaging_with_peers` in `run` step 6.5 and handed to the link as its mail host at 8.5): the kernel's `RemoteDeliveryPort` (one `Mail` per (send, PC) → `send_mail`; `MailEnd` → one final `handle_remote_verdict` per mail with every tag; no peer link yet → `PEER_OFFLINE`; the kernel already fails the rows past the first 64 to one PC per send, `REMOTE_LIMIT` with "split the send") and `MailInbox` (this PC's ingress contract checks — `control::ingress::validate_contract`, `contract_unsupported_by_envelope` — then the kernel's remote entrance; each delivered or held recipient is noted with `Approvals::note_mail_from`). The control entrances wait for remote rows until their request's arrival + `CommandDeliveries::DEFAULT_DEADLINE` (`ingress::handle_send_at` → `await_remote_answer`).

## Agent directory

- What is published (`MailInbox::directory` — `PeerMail` reads the local layers of `addressing_sources`, `ManagerDeliveryPort::local_sources`, without the other PCs): live agents that read mail (`live`) and every dormant profile (`sleeping`), as id, name and state only — nothing else about an agent and nothing about this PC (no addresses). A name another PC would refuse (`remote_name_ok`) is left out with a warning.
- Publisher (`publish_loop`): the daemon rings `DirectoryBell` on every profile-list save (`lib.rs` `DirectoryRingingStore` — the one point create, delete and rename pass, from the command path and the shell's profile messages alike) and on every session status and list change (`MessagingFlushSink`, live ↔ asleep). The task waits `COALESCE` (250 ms) after a ring, recomputes on the blocking pool, and sends nothing when nothing changed; a change is one `DirDelta` (`rev` + 1) on every chosen link, or a `DirSnapshot` when the delta would exceed the frame cap. ★A snapshot is always one frame★ (ADR-0411 — QUIC splits and reassembles it; PeerWire never splits): a directory over `MAX_FRAME_BYTES` goes with the rows that fit in id order and the rest left out, with one warning per change (the snapshot is built once per `rev` and every link gets the same frame) — the link is never closed for it. Directory frames are sent only under the publisher's lock, so they go in the publisher's order. When the directory read changed the host's local ids (`MailInbox::local_ids_version`), the same blocking call re-checks the copies (`Core::recheck_copies`); otherwise it does not. No timer, no periodic re-send.
- Chosen links: the actor re-reads each PC's chosen link after every event (`Actor::refresh_routes`), skipping a PC no longer trusted (a removal is published before the actor carries it out); a newly chosen link (new key, endpoint or run) first gets this PC's snapshot (cut to the frame cap when the directory exceeds it — ADR-0411), and asks the other PC for its snapshot (`DirResync` — what came on that link before it was chosen here was dropped). Directory frames carry no node: a frame changes the copy of the link's PC only, and only when it came on that PC's chosen link — the actor records each PC's chosen link in the copies (`Copies::set_chosen`, in `refresh_routes`) and the frame's link is checked there, under the copies' lock alone, so applying a frame never holds the link book; a frame before any link is chosen is dropped too (the resync on choosing brings it again). The publisher and `send_reply_overdue` check trust before each send too. A `DirResync` is answered off the drain task by one worker per link at a time, at most once per `RESYNC_INTERVAL` (1 s): requests arriving before the worker takes its target fold into it and the answer goes to the connection of the latest one (a dialing handle reconnects under the same key); a request arriving while the worker sends gets one more answer, scheduled by that worker as it ends, an interval later. The resync state of an endpoint's links goes with them at its teardown, and the teardown retires the endpoint's epoch with it, so a request its drains still read is not answered.
- Copies (`Copies`): a snapshot replaces the copy on arrival; a delta applies only on the copy's run at `rev` + 1, else the holder sends `DirResync` on that connection; an older snapshot of the same run is ignored, another run's replaces the copy. Agent ids are rewritten to one spelling (`Uuid` canonical text) on arrival. Arriving rows are checked by the host before the copies' lock is taken (`MailInbox::row_problems`, once per frame and once more under the copies' lock when the local ids moved meanwhile, not blocking — `PeerMail` answers from the local agent ids it read at assembly, before the link starts, and at every directory read on the blocking pool: not an agent id, a local agent's id, a name breaking the remote name rule — dropped; a dropped upsert also removes that id's old row). After a directory read that changed those ids the runtime re-checks every copy's rows against them and drops those that now name an agent of this PC (`Core::recheck_copies`, scanning and dropping under the copies' lock); a frame whose rows were checked before the ids changed checks them again under the copies' lock when the version moved meanwhile, so such a row cannot be committed past the re-check. Trust is checked again under the copies' lock, so a removal racing a frame does not bring the copy back. An id two PCs list is kept in both. Dropped rows and shared ids are counted per frame (`directory::Report`) and logged at most once per `DIR_WARN_WINDOW` (60 s) per PC, with the frames folded since. A copy follows the PC, not a link: kept when the last link ends (shown `disconnected`; its names resolve to `PEER_OFFLINE`), kept across endpoint restarts and renames, dropped with `peer.remove` (`Core::revoke`) or when the PC leaves the list otherwise. Memory only — after a restart a PC is `unknown` until it links.
- For mail addressing: `PeerLink::rows` → `ManagerDeliveryPort::addressing_sources` (`remote_pcs`: node, name, `PcLink` from `Online`, the copy or `None` = unknown this run), read under the peer link's own locks, never under the messaging lock. For `peer.list`: per PC `directory` (connected | disconnected | unknown) and `agents` (name, id, state, sorted by name; `--agents false` leaves them out).

## Commands and approvals

- Entrance: `peer.*` reach the daemon only through `control::commands::call_daemon_command` — from the socket bus (the app; caller `Caller::Shell` = a live shell connection = a human), `/control/call` (`engram peer.list …`; caller `Caller::Agent` = the agent token's identity) and nothing else (`/control/agent` takes `agent.<verb>` only; MCP `/mcp` has no command tool; a relay through `CommandBus::invoke` is delivered as the asking agent — `deliver_as` — and refuses the daemon's own names anyway). Order: the declaration's argument check → `PeerCommands::call`: this PC's identity is made if it has none yet (`ensure_identity`, any caller — ADR-0389 d3, its own key widens no trust) → the approval gate → the handler, driven to its first poll. The table is private to `PeerCommands`. It is joined by `DaemonTable::with_peer` in `lib.rs` `run` only; assemblies without the peer link (the test server, smoke bins) do not hold `peer.*`.
- Who may call what (`agent_policy`, ADR-0394 d1 — one rule per declared name; a name without one is refused for agents, and a test checks every declaration has one): agents run `peer.list`, `peer.remove` and an address-only `peer.edit`; an agent's `peer.add`, `peer.setNetwork`, `peer.regenerateKey` and `peer.edit --new_name` become a pending request answered at once (`outcome: requested`, the request id, in the command's declared answer shape); `peer.approve` / `peer.deny` from an agent are refused (`CONFLICT`). A human (the shell connection) runs everything at once. Human vs agent is the typed caller only — never an argument or the entrance label.
- Before the peer link has started (`peer_slot` empty) every change answers `CONFLICT` and `peer.list` says `not_started`.
- Arguments: a PC is named by `--name` (any case) or `--id` (canonical, grouped or uppercase hex), exactly one; `--address ip:port` (`peer.edit --address none` clears it); `peer.setNetwork` names only the fields to change (`--port <n>|default`, `--relay` / `--address_lookup` `default|none|URL`, `--mdns`) and is checked against the link adapter on the current settings before it is applied or recorded. `peer.add` checks what it can before recording or applying (ID form, own ID, already trusted, name rules and uniqueness, address form); the store checks again when it applies. `peer.approve --start_fresh true` answers the adopt request with a fresh identity (refused on any other request, which stays).
- Answers: gated commands `{outcome: applied|requested, request?, message}` (`peer.regenerateKey` also `id`, the new ID, and says every other PC must re-pair); `peer.remove` `{id, name, saved, message}` — a refused save is reported (`saved: false`) and the removal holds for the run (ADR-0390 d4).
- `peer.list` (one query for the area; `--name` narrows `pcs` to one trusted PC, `--id` narrows `pcs` and `knocks` to one PC, trusted or knocking): `state` (word) + `reason`, `id`, `addresses` (`interfaces::my_addresses` — each usable interface address with the listen port; the interface read is reused for 30 s, as it can take seconds), `network`, `endpoint` (`off|up|error`) + `endpoint_error`, `pcs` (`online` word, duplicate `warning`, `directory`, `agents`), `knocks`, `requests` (id, kind, summary, agent id and name, origin, ask time, time left), `actions` (every state that needs a human and the command or answer that resolves it: key unreadable → `peer.regenerateKey`; adopt-or-fresh → the adopt request (approve or start fresh) or, while the user put it off, that it comes back; list changed outside / damaged → the accept request or that it was put off; identity in use; list refused; helper URL refused → `peer.setNetwork`; bind failure; a duplicate warning → look for a second copy, then `peer.regenerateKey`; knocks → a human pairs one only after its owner confirms the ID another way; agent requests waiting).
- Pending requests (`Approvals`, ADR-0394 d4): kind + change + agent + time + origin (`note_mail_from` — called by the mail host for each agent a remote mail reached). Memory only; at most 8 agent requests (`MAX_PENDING`, the 9th refused with a hint to ask the user); an identical change already pending returns that request (`existing`); expiry 24 h (`REQUEST_TTL` — checked on every read and answer and every minute by `follow`). Every answer consumes the request under the lock before the change is applied outside it, so a second or late answer finds nothing (`NOT_FOUND`). A deny refuses the same (agent, kind) for 10 min (`DENY_COOLDOWN`); deny-and-stop (`peer.deny --stop_asking true`, or the dialog's third button) refuses that agent's gated calls until the daemon restarts and drops its other requests. An approved change that the store refuses consumes the request and reports the refusal. A network change names only its fields (`trusted::NetworkPatch`) and is merged, checked against the adapter and saved in one store step under the store lock (`PeerStore::patch_network`), so a concurrent change to another field is kept; a named field that changed after the request was made is overwritten with the requested value (what the human approved) and reported (`Applied::NetworkMoved`) — in the `peer.approve` answer on the app path (its `moved` field names the fields; the PC list slot says so), only in the daemon log when the approval came from the OS dialog. A network request is refused (`CONFLICT`) while the current settings are not known (the list file could not be read), so the question always shows a true "from".
- System questions (`Approvals::sync_state`, run by `follow` on every peer-state change and every minute): `ListChangedOutside` / `ListCorrupt` → one accept-list request (approve = `accept_list`); `AdoptOrFresh` → one adopt request — the first machine id by name, counting the others (approve = `adopt`; the third answer, "Start fresh" in the dialog or `peer.approve --start_fresh true`, = `start_fresh`; deny = "not this run" for the question as a whole, asked again at the next start). They have no expiry and are withdrawn when the state no longer needs them. On the accept question deny = "not now" (asked again after 10 min) and the third answer = "not this run". `peer.regenerateKey` while the adopt question is open also starts fresh. Key unreadable has no question — `peer.regenerateKey` is the human action.
- Question text (`approvals/text.rs`, in English and Korean — ADR-0372; the dialog picks the user's `ui.language` when it shows, English until the shell has said): what is asked and what approving allows, built from the state at request time — an add marks a PC that knocked uninvited and a name another ID held earlier this run; a rename shows `"<current>" → "<new>"` and which `name@<current>` addresses stop working; a network change lists every field it names from → to, also one equal to the current value; a regenerate during the adopt question says it abandons the saved identity and its pairings; the accept question shows the count and the first 5 PCs, then "N more — review in the app or with peer.list". An agent's request starts with the system-written agent id, then its own name. Every string from outside (agent and PC names, addresses, URLs) goes through `text::visible`: one line, `"` and `\` escaped, every whitespace other than a space, control character and invisible format character (`trusted::is_invisible` — bidi overrides, zero-width) shown as U+FFFD, quote look-alikes escaped like `"`, at most two stacking combining marks and at most eight code points per user-perceived character (`unicode-segmentation`, `MAX_MARKS` · `MAX_CLUSTER_CHARS`; whatever either bound drops is shown as one U+FFFD after that character), capped; a helper URL shows its host and port whole (DNS limits: 253 characters, 63 per label — `trusted::authority_ok`) and caps only the path. The other PC's ID is the full grouped ID (`PeerId::grouped`), never a short fingerprint. The expiry is computed from `REQUEST_TTL`. Buttons: Approve / Deny / Deny and stop asking this agent; accept-list: Accept the list / Not now / Not this run; adopt: Adopt / Not this run / Start fresh; deny is the default and enabled at once, and the platform dialog enables Approve and the third choice only a second after it appears (a click meant for the window beneath cannot act). The dialog shows the request id but no expiry (`peer.list` gives the time left).
- The ask-the-user seam (`AskUser`, ADR-0394 d5 as amended by ADR-0410): questions go to the app while it is attached with a PC list slot open, on screen or not (`AppRoute::takes_questions`, read under the seam's lock; the app answers with `peer.approve` / `peer.deny`, which withdraw the question) — however long one waits there, since a question buried behind other windows is the user's to find — else to the native dialog on the seam's own thread — one at a time, oldest first, at most one new dialog per question kind per minute (`DIALOG_RATE`), the body counting how many others wait, the answer applying to the question shown only; closing without a choice is a deny. While the app takes the questions no new dialog opens (an open one stays); when it stops — the last slot closed or the last connection dropped (`route_changed`, which goes through the seam's lock so its wake-up cannot be lost), open questions go to the dialog. A withdrawn question's dialog is dismissed, or left stale with its answer ignored where the platform cannot close it. A dialog that fails to show is retried each minute and warned about once until one shows. No desktop → no dialog is tried again this run and questions wait for the app or their expiry. Shutdown (`lib.rs` step 12, before the peer link stops): `Approvals::stop` lets nothing new through, waits at most 3 s for an answer being applied (every answer holds the read side of a stop gate from its consume through its apply; past the bound that apply finishes on its own), then drops every request — an answer after it finds nothing, a request is refused — and ends the dialog thread (an open dialog dismissed, no later click handed on, a bounded wait); then `PeerLink::stop` refuses every trust operation from its first moment, so nothing changes the files of a stopping daemon.
- UI language: the shell sends `AgentCommand::SetUiLanguage { language }` on every connection it opens and on each `ui.language` change (`daemon_client::connection` `set_ui_language`); the daemon keeps it in `ControlRegistry` (`set_ui_language`, English for a word it does not know). The daemon never reads the shell's settings file. An open dialog keeps its language until the next one (Task Dialog buttons cannot be relabelled). An agent can switch the dialog language through `settings.set --key ui.language` (a shell command open to agents — accepted under ADR-0055 / ADR-0372: the switch is visible app-wide, and the request id, the grouped full IDs, the URLs and the default Deny are the same in both languages).
- For the app: the adopt question's third choice is `peer.approve --start_fresh true` — not `peer.deny --stop_asking`, which on that question means "not this run" like its plain deny.
- The app (S37 U4): the daemon-root module `src/peer_state.rs` (`PeerStateHub`) keeps, per shell connection, the flag of `AgentCommand::PeerSubscribe` — `subscribed`: the app has a PC list slot open in some tab of some window, active or not (the shell's `daemon_client::peer_watch` reads the layout and sends each change at once — the layout model never passes through a state without the slot while one moves, so there is nothing to debounce). Subscribed connections get `AgentEvent::PeerStateUpdated` — the protocol `PeerState`, field for field `peer.list --agents false` (`commands.rs` `AppPeerState` / `app_state` — each PC's `directory` word without its agent rows, which the slot does not show and which could grow one push past the shell's 16 MiB message cap) — when they subscribe and on every tick of `PeerLink::changes` and `Approvals::changes` (`peer_state::forward`); one task builds it on the blocking pool and sends it (`PeerStateHub::run`), so one connection's copies go in order. The hub is the seam's app route (ADR-0410): any connection subscribed → the app; every change of that answer (a subscribe, a connection dropping) calls `Approvals::route_changed`. The connection layer attaches and detaches each connection (`agent_conn.rs`); `lib.rs` `run` binds the approvals after step 6 and aborts the hub's tasks at shutdown. The broadcast does not make the identity; the slot's own `peer.list` read on mount does (the first-call rule above). The hub is nudged once more when the peer link has started (`lib.rs` 8.5), so a shell that subscribed while it was loading gets the started state. Each request row (`peer.list` and the broadcast alike) carries the question exactly as the dialog shows it, in the language the shell told the daemon — `title`, `heading`, `lines` from `PendingRow::text` (the `Question` kept with each request) — so the slot shows every value, the grouped IDs, the flags and what approving allows; `agent_name` and `origin` leave the daemon quoted as the dialog quotes them (`text::quote` — escaped, one line, capped); `summary` groups IDs. A language switch (`SetUiLanguage`) nudges the hub, so the cards are re-worded at once. In the slot (`PeersSlot.tsx` head): the requests come first in a section that is always there; an answered card keeps its place 3 s as a placeholder with the outcome; the buttons that say yes and the two-step buttons are held 1 s after anything that can move them — the cards shown, the UI language, the size of the slot, a section, a card or the scroll content (a row added or removed), a scroll of the slot, the window resized, coming to the front or becoming visible, or this slot's own rectangle in the layout snapshot changing (a move without a resize) — the look is derived during render (counted per change, so a return to an earlier state is held again), and the press itself is checked at click time against a move stamp those changes set synchronously, so a click that lands before React re-renders is refused too; an answered placeholder says what was answered by the request's translated heading; the answer buttons have one width in every language; Start fresh, regenerate and remove take a second click no sooner than 1 s after the first.
- The app's actions (S37 U4): the PC list slot calls `peer.*` through `ProtocolClient.peerCommand` — an `AgentCommand::Command` on the shell's own connection, so the daemon types it as the human. Every slot action that writes is a `humanOnly` command of `src/commands/peerCommands.ts` without `help`, run from the slot's buttons through `runAsHuman`; the shell command table declares no `peer` name (`layout/commands.rs` test) — so neither `window.__engramCmd.run`, the bus bridge nor `/control/call` can relay one into a human call.

## Promises (links)

- Lock order: the store lock, then the published state and the copies (`Core::publish` · `revoke`); the publisher before the routes; the link book before the copies (`Core::rows`). The knock list, the endpoint view, the in-flight counts, the receive and overdue queues and the resync state are each taken alone and briefly; the handshake (on transport tasks) and the gate (on the adapter's gate tasks) take theirs there. Nothing async takes the store lock; only the trust operations and the start-up load (blocking pool) do.
- The actor alone touches the endpoint, the registry and the handles; it awaits only the endpoint bind, `close_all` and the endpoint close, never a request. Drain tasks read their inbox to `None` and never await a request (transport receiver invariants). Messages carry an endpoint epoch, so a closed endpoint's late events are ignored.
- The secret leaves `PeerStore` only as a copy in the published state for the endpoint build (zeroed when the last copy goes); it is never logged.
- Duplicate warnings stay for the rest of the daemon run, across endpoint restarts (ADR-0403 d3 — no command clears them).
- Not shown by the tests here (two real PCs): NAT traversal, relay and lookup servers, mDNS, the firewall prompt, the 30 s QUIC idle-out of a frozen peer, the 120 s `Mail` deadline end to end (the mapping of `TimedOut` is unit-tested; the deadline is the registry's `request_timeout`).
