## What it is

`engram-dashboard-messaging` is the mail kernel between agents: address resolution, per-recipient decision, parking, injection order, the idle gate, TTL, the reply contract (request / `reply_by` / overdue notice) and the ledger. It depends on no workspace crate; the daemon plugs real objects into port traits the kernel owns. `MessagingService::handle_send` is the one send entry point — single, multi-recipient and `@` group sends share it. Each send takes one decision-source snapshot (`DeliveryPort::addressing_sources`), resolves every token once from it, enqueues each accepted recipient at its queue tail, then drains live recipients' queues in the same call outside the lock. Agents reach it through two daemon entrances — MCP tool `eg_send` and HTTP `/control/send` (CLI `engram mail send`) — both funnelled into `control::ingress::handle_send`. Everything is in memory; nothing is persisted.

Mail to agents on the user's other PCs (S37) goes through the same pipeline: the snapshot also carries the listed PCs and their directory copies, a row resolved to another PC is recorded `RemotePending` and handed to `RemoteDeliveryPort` (one mail per PC), and its outcome comes back through the verdict entry. Inbound mail from another PC enters through the remote entrance and resolves on local agents only. The link, the PeerWire vocabulary and the directory sync are the daemon's; the kernel sees a PC only as an opaque `NodeRef`.

## Modules

Kernel (`crates/engram-dashboard-messaging/src/`):

- `lib.rs` — `PeerId` (= `uuid::Uuid`; the host `AgentId` passes unconverted), `SenderIdentity` (`node: Option<NodeRef>` = the sender's PC, `None` = this PC) and `NodeRef` (32 raw node-key bytes, `Copy`).
- `service.rs` — `MessagingService`: the send pipeline (resolution, per-recipient decision, park, drain), async flushes, the maintenance sweep, profile-deletion cleanup and lookups; the ports `DeliveryPort` · `ControlPlanePort` · `FlushTrigger` · `RemoteDeliveryPort` and the snapshot type `AddressingSources` (`pcs`: `RemotePc` with `PcLink` and `directory: Option<Vec<DirectoryEntry>>`); the remote surface `await_remote_answer` · `handle_remote_verdict` · `handle_remote_mail` · `handle_reply_overdue`, `ResolveScope`, `RemoteLimits`, `remote_name_ok`.
- `mailbox.rs` — `Mailbox`: per-recipient FIFO parking keyed by recipient id; two independent lanes (`ParkKind::Message` capped by `MAILBOX_CAP`, `ParkKind::Notice` capped by `NOTICE_CAP`); expiry by `PARK_TTL`; in-flight accounting.
- `ledger.rs` — `Ledger`: history ring (`HISTORY_CAPACITY` delivery records), request tracking (`MAX_OPEN_REQUESTS`, strict `in_reply_to` matching, due timeouts), contract reservations; remote rows — a `RemoteRef` mark on the history row (display only) and a bounded remote store (`RemoteEntry`: `record_remote` with `RemoteSend`, states `RemotePending` / `RemoteHeld`, the verdict-only verb `settle_remote`, `seal_remote_answer`, `mark_remote_replied`, `accept_reply_overdue`, `prune_remote`) — and the contract's `sender_node` and reply holds (`hold_reply` / `release_reply`).
- `groups.rs` — `GroupSource` / `BuiltinGroups`: expands `@here` (live pool) and `@all` (live + dormant pools). Expansion only.
- `busy.rs` — `BusyGate`, `BusyPolicy` (facts + `BUSY_MAX_TURN` cap, `sweep_stale_busy`), `TurnFacts`, `IdleNotifier`, `BusyReason`.
- `envelope.rs` — the single wrap point `wrap_message` / `wrap_notice`, `EnvelopeFormat`, `Entrance` (`Mcp` · `Cli` · `Daemon` · `Remote`), `new_msg_id`, delivery observation types.

Daemon host (`crates/engram-dashboard-daemon/src/`):

- `messaging_host.rs` — the adapters (its header is the seam ledger): `ManagerDeliveryPort` (`DeliveryPort` over `AgentManager`), `ManagerTurnFacts` (`TurnFacts`), `ControlPlanePort for ControlRegistry`, `messaging_for_manager_gated` / `busy_gate_for_manager`, `ChannelIdleNotifier` (`IdleNotifier` + `FlushTrigger` → flush channel) with `IdleCoalescer`, `MessagingFlushSink` (status-sink decorator; `RosterDiff` → `FlushMsg::Appear`, `turn_ended` / `inputs_drained` → `FlushMsg::Idle`), `spawn_flush_worker` / `run_flush_worker` / `run_flush_lane` (delivery lanes on `spawn_blocking`).
- `control/ingress.rs` — `ControlCommand`, `validate_contract` (request / `reply_by` / `reply_to` rules), `handle_send` (argument checks, `MAX_BODY_BYTES`, sender display name, one id-collision retry, then the kernel), `handle_messages` (`eg_messages` lookups), result JSON.
- `control/mcp_server.rs` — `eg_send` / `eg_messages` tools and `control_send_handler` (`/control/send`; `cli_recipient_tokens` splits commas for this route only), all calling `ingress::handle_send` on `spawn_blocking`; `MessagingSlot` (late-injected `Arc<MessagingService>`); `ControlRoute::is_mail`.
- `control/registry.rs` — `ControlRegistry` (Bearer token → `BoundIdentity`); `From<BoundIdentity> for SenderIdentity`.
- `connection_core.rs` — the only caller of `MessagingService::handle_profile_deleted` (WS `DeleteProfile`).
- `lib.rs` `run` — assembly steps 6.4–6.7: busy gate, `MessagingService`, the 60 s sweep task (`sweep` + `sweep_stale_busy`), the flush worker.

## Wiring and flow

- Send: agent → MCP `eg_send` or `/control/send` (Bearer) → `BoundIdentity` from the token, never the payload → `ControlCommand` → `ingress::handle_send`: contract validation, envelope-format support, recipient trim, single-recipient rule for `reply_to`, body cap → `MessagingService::handle_send(msg_id, SenderIdentity::from(bound), sender_name, to, body, entrance, meta)`. On `SendReject::IdCollision` ingress retries once with a new id; a second collision answers `INTERNAL_ID_COLLISION`.
- Resolution (`resolve_token`, pure, same rule as agent `resolve_in`): a UUID-shaped token is looked up as live id, then dormant id; otherwise exact case-sensitive name — live layer first, dormant layer only when no live match; two or more in a layer → `Resolution::Ambiguous` for that layer; none → `NotFound`. `@` tokens expand through `GroupSource` (sender removed by id) and expanded members resolve by id (`resolve_id`). Rows are deduplicated by resolved id, or by notation if unresolved.
- Per-row outcome: live → enqueue, then the same-call drain gives `Delivered` or `Pending`; dormant → park and return `Pending` with no drain (delivered by the appearance flush); not found → `RECIPIENT_NOT_FOUND`; ambiguous → `RECIPIENT_AMBIGUOUS` (`ambiguous_hint`: count + layer, "tell the user"); full lane → `MAILBOX_FULL`; contract table full → `REQUEST_CAPACITY`. Whole-send bounces from the kernel: `GROUP_NOT_FOUND`, `GROUP_EMPTY`, id collision; from ingress: `INVALID_SEND_ARGS`, `BODY_TOO_LARGE`. `RECIPIENT_DELETED` appears only later in lookups. Codes = `FailCode` / `SendReject`.
- Later delivery: core status sink → `MessagingFlushSink` → unbounded flush channel (`FlushMsg::Appear` from `RosterDiff` on appearance / incarnation change; `FlushMsg::Idle` on turn end or emptied input list, coalesced) → flush worker → delivery lane (`spawn_blocking`) → `flush_for` / `flush_for_agent` → `drain_queue`. The kernel's doorbell (`FlushTrigger::request_flush`) and the cap sweep (`IdleNotifier::notify_idle`) use the same channel.
- Idle gate: `LiveAgent::turn_signal == false` → inject without asking; else `BusyGate::busy_reason` (`BusyPolicy` over `ManagerTurnFacts`): busy = user inputs pending, or halted after an error, or mid-turn within `BUSY_MAX_TURN`. Unobserved = idle. Checked once per drain.
- Reply contract: `SendMeta.request` opens a contract per accepted recipient keyed `(msg_id, recipient id)` (dormant uses the profile id) before enqueue. `reply_to` closes only the replier's own contract by strict match. Overruns are found by `Ledger::due_timeouts` in `sweep`; `deliver_notice` parks a `<notice>` (`ParkKind::Notice`, `Entrance::Daemon`) to the requester's id and rings the doorbell. Missing the deadline does not close the contract.
- Lookups: `eg_messages` / `/control/messages` → `ingress::handle_messages` → `message_state` or `open_items_for` (by caller id).
- Remote resolution (`resolve_token`, `ResolveScope::All` only): `name@pc` first (the text after the last `@` names a listed PC, ignoring case — that PC, its copy not consulted, even over a local agent literally named the whole token); then the local rule above (a local agent always wins); then a UUID-shaped token listed by a copy; then a bare name counted per PC over the known copies (connected or not). Two or more PCs → `RECIPIENT_AMBIGUOUS` with sorted `name@pc` candidates; a PC whose directory is unknown this run (`directory: None`) is not counted and is named in the not-found hint. `@all` / `@here` stay local. Rows naming one PC and stripped token fold into one.
- Remote send: a chosen PC whose `PcLink` is not `Connected` → `PEER_OFFLINE` at once (hint per cause); a sender name breaking `remote_name_ok` → `NAME_TOO_LONG`; a token over `REMOTE_NAME_MAX_BYTES` → `RECIPIENT_NOT_FOUND`, contract fields the receiver would refuse → `REMOTE_REFUSED`, and a row past the first `MAX_REMOTE_ROWS` to one PC in this send → `REMOTE_LIMIT` ("split the send"), per row (the receiver would refuse the whole mail to that PC); else the row is recorded `RemotePending` with `tag` = its row index (no contract on this side; a reply takes one hold on its contract — `hold_reply`), and after the lock one `OutboundMail` per PC goes to `RemoteDeliveryPort::enqueue`. `handle_send` returns such a row `pending` with an "awaiting" hint; the entrance then calls `await_remote_answer(msg_id, rows, deadline)`, which waits on `remote_settled` until every remote row has a verdict or the deadline, seals the answer under the lock (`seal_remote_answer`) and writes the outcome or "unconfirmed" into the rows by tag.
- Verdict entry (`handle_remote_verdict`): per row by (mail id, tag, node) → `Delivered` / `RemoteHeld` / `Failed` (peer codes mapped by `FailCode::from_remote_code`, reason capped by `clip_reason`) or unconfirmed (stays `RemotePending`). A reply's contract closes here by ADR-0116 decision 2's rule. Rows already in the sealed answer get one `<notice>` (outcome and code only, never the peer's reason). One final call per mail (mail id, node): tags it leaves unsettled are settled unconfirmed by the kernel.
- Remote entrance (`handle_remote_mail`): validation (`REMOTE_REFUSED`, `validate_inbound`: mail id per `remote_msg_id_ok` — 1–64 bytes of `[A-Za-z0-9_-]`, row count and tags, token size and `@`, sender name and id, and the pure contract rules on `meta` re-checked — reply_by ≤ 30 days, reply_to a mail id, no `to_attr`), a sender id that is local per `RemoteDeliveryPort::is_local_agent_id` (`REMOTE_REFUSED`, copied data folder), body cap and per-PC mails per minute (`REMOTE_LIMIT`, `RemoteLimits`, window per node in `MessagingState.backstop`), then the pipeline with `ResolveScope::LocalOnly`, `Entrance::Remote`, sender `"<name>@<pc>"` and `SenderIdentity.node` from the link; per-row `RemoteRowResult` by tag. An accepted reply to one of this PC's requests (delivered, parked, or requester gone — the rule the replier's PC closes by) marks that request's rows to that node for the replier as answered (`mark_remote_replied`); a refused one does not. The host drops an inbound mail past its transport deadline (`REMOTE_TRANSPORT_DEADLINE`) instead of running it late. The host still runs its own entrance checks (reply_by notation, envelope support); the kernel's are defence in depth.
- Overdue across PCs: a contract opened for a remote requester carries `sender_node`; `sweep` sends `RemoteDeliveryPort::send_reply_overdue` to it instead of a local notice, not while a reply hold is live (holds count each reply in flight and lapse after `REPLY_HOLD_MAX`). The requester's daemon renders its own notice in `handle_reply_overdue`, only after the deadline on its own clock, covering that request's rows to that node that are not failed, not answered by a reply and not reported yet — one row names that agent, several name the PC and list them; each row is reported once.

## Promises no single file shows

- Phases of one send (`handle_send`): the snapshot is taken before the lock; acceptance, contract open, parking, ledger rows and the closure of an accepted reply's contract (`ReplyClosing::close_in_lock`) happen in one lock span; drains run after the lock is released.
- Reply disposition (`reply_disposition`): if any row is accepted (delivered or pending) the replier's contract closes as replied; if every row failed and one is `RECIPIENT_NOT_FOUND` it closes as `reply_failed` (`fail_reply_contract`); any other failure (`MAILBOX_FULL`, `RECIPIENT_AMBIGUOUS`) leaves it open. A new `FailCode` must be classified there.
- One snapshot per send: `addressing_sources` is called exactly once per `handle_send`; `ManagerDeliveryPort::addressing_sources` builds `roster` and `dormant` from one `manager.roster()` read — `roster` with the same predicate as `live_agents` (live + `reads_messages`, so shells are excluded), `dormant` = profiles with no live session, duplicates kept. In the daemon's assembly (`messaging_with_peers`) it also fills `pcs` from the peer link in the same call (`remote_pcs` — `PeerLink::rows`, read under the peer link's own locks); before the link has started, and in assemblies without it, `pcs` is empty and every address resolves locally. The host side of `RemoteDeliveryPort` and of the remote entrance is `messaging_host` `PeerMail` (`docs/reference/structure/peer-link.md`, "Mail over the link").
- Lock discipline: one `Mutex<MessagingState>` (mailbox + ledger). Never call `DeliveryPort`, `ControlPlanePort`, `FlushTrigger` or `RemoteDeliveryPort` while holding it; injection may take the session locks. `BusyGate::busy_reason` *is* called under it (`drain_queue` → `gate_busy_reason`), so a `BusyGate` implementation must not block and must not take the messaging lock (the `busy.rs` trait doc saying the call sites are outside is stale).
- Non-blocking notification paths, all into the unbounded flush channel: agent output pump threads call the status sink (`MessagingFlushSink::turn_ended` / `inputs_drained` → `ChannelIdleNotifier::enqueue`); the 60 s sweep task calls `IdleNotifier::notify_idle` (from `BusyPolicy::sweep_stale_busy`) and `FlushTrigger::request_flush` (from `deliver_notice`); request threads and flush-lane blocking threads call `request_flush` from drains. `RosterDiff` enqueues while holding its own lock (snapshot order = channel order).
- Order: a recipient sees enqueue order. Drains for one recipient never overlap (queue-axis in-flight + `in_flight_targets`). A drain that finds one in progress only records itself as a waiter (`deferred_flush` / `deferred_by_target`) and returns; the drain holding the in-flight receipt rings `request_flush` for each waiter when it settles.
- Keys: mailbox queue key, contract key and ledger record key all use the agent id (`PeerId`), never the name. `msg_id` is unique per daemon only (`new_msg_id`, collision-checked against this daemon's ledger). Names exist only at the edge (tokens, envelope `from` / `to`, response `to`).
- Mailbox lanes are independent: message backlog never blocks notices; the notice lane reclaims its oldest notice on overflow and never bounces.
- `Entrance` is a log / observation label only; the pipeline does not branch on it.
- Remote rows move only through the verdict entry (`DeliveryStatus::can_settle_remote`); no sweep, flush or cleanup touches `RemotePending` / `RemoteHeld`. Each remote row is reported once — in the sealed answer or in one later notice. `RemoteDeliveryPort` is called outside the messaging lock and must not block; each mail it is handed gets exactly one final verdict call — tags that call leaves out are settled unconfirmed, and a mail with no call stays unconfirmed until its remote entry ages out (`REMOTE_VERDICT_HORIZON`). Remote rows are not listed among a sender's outstanding items (`open_items_for` lists local `Pending` only) and show as plain "pending" in an id lookup.
- Remote correlation lives in the ledger's remote store, not the history ring, so history eviction loses no verdict, answer or overdue report. An entry lives while a verdict or the answer is due (at most `REMOTE_VERDICT_HORIZON`, 10 min) or, for a deadline-bearing request row, until it is reported, answered, failed or past its deadline + `REMOTE_OVERDUE_GRACE` (10 min = transport deadline 120 s + `REPLY_HOLD_MAX` 180 s + the receiver's sweep 60 s + 4 min margin); at most `MAX_REMOTE_ENTRIES` (4096, oldest dropped, logged). A reply entry dropped before its verdict releases its contract hold. A remote row's peer-reported recipient id stays in the store; the history row's `to_id` stays `None`, and `transition` / `fail_pending` never pick a remote row.
- The kernel trusts `SendMeta` as validated: for local mail ingress is the only validator (`handle_send` has debug asserts only); mail from another PC is re-checked by `validate_inbound` (contract rules, id, row tokens) before the pipeline.
- Who fills what: the daemon fills `AddressingSources` and `LiveAgent::turn_signal`, the envelope format (`ControlRegistry`), turn facts (`ManagerTurnFacts`) and the sender display name (`ingress::sender_display_name`, byte-equal to the roster name). The kernel fills results, hints, ledger rows and notices.
- Roster-change notice is not a messaging input: the composition notice `RosterChanged` (agent crate port, `crates/engram-dashboard-agent/src/commands.rs`) → `control::commands::LateRosterBroadcast` → `control::agent::RosterBroadcast` → `connection_core::RosterFanout` goes to the shells only, and only for command-table verbs; WS-originated profile changes broadcast directly from `connection_core` (`broadcast_profile_list`). Messaging learns about agents only from its per-send snapshot and from `MessagingFlushSink::agent_list_updated` (appearance / incarnation diff by id).
- The control entrance and mail resolve targets by the same rule; `crates/engram-dashboard-daemon/tests/control_agent.rs` (`resolver_alignment`) guards it.
