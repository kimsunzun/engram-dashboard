# Asset library structure

> **Live reference, edited in place.** The picture and the cross-file contracts of `engram-dashboard-asset-library`; the code holds the details. Anchors are file and symbol names only. The crate's `lib.rs` header is the canonical short form of its boundary and gates.

**Whole picture** = `docs/reference/architecture.md` · **Launch argv per backend** = `agent-backend.md` (this folder)

---

## What it is

The preset library: instruction, skill, settings and preset files in the folders of its mounts (one virtual root whose top holds named mounts — ADR-0396), plus three built-ins in the reserved read-only mount `engram` (`engram/default` · `engram/priming` · `engram/settings/default` — ADR-0400 decision 20) shipped in the install's `builtin\` folder. The crate reads and checks those files, keeps a catalog of them, resolves what an agent actually receives from its attached presets, and makes that agent's launch materials. `LibraryService` is the daemon's real `LaunchKitSource`; the only other implementation is agent `NoopLaunchKits`.

**Boundary** (ADR-0311): its workspace dependencies are exactly agent · platform · command · base. agent defines the ports and does not know this crate. There is no daemon call, no network client, no process runner (ADR-0359), no OS `cfg`, and no test feature. CI `asset-library gate 1`–`4` in `.github/workflows/ci.yml` hold the test line, the dependency set, the messaging-isolation name and no `use tauri`; OS `cfg` is held by `platform gate 4` and `6`; the network, process-runner and test-feature rules are stated in the crate's `Cargo.toml` only, with no gate.

**Backend extensibility** (ADR-0367): backend tags and raw-field names are strings, checked only through `backends::Backends`. Every per-backend choice is a `SettingsCheck` answer, so adding a backend to agent changes nothing here.

## Wiring

- **The daemon only wires.** `build_library_service` in daemon `src/lib.rs` is the one builder, shared by production and the `roundtrip_smoke` bin. It plugs in `AgentBackends`, `FsStore`, `BoundedIo` over `StdFolderOps` + `ThreadSpawn` and the shared `ProfileRegistry`; the builtin folder, the launch root, the `LibraryHost` and the `LibraryStart` are its caller's arguments (production: `data_dir::find_builtin_dir`, `DataLayout::launch_dir`, `LibraryHost::process`; `roundtrip_smoke`: `--builtin-dir`, a temp launch folder, and a hermetic host in its tests).
- **What the daemon passes for the root.** `LibraryStart` carries `config::load` over `DataLayout::daemon_state_dir` (read before the service is built — `LibraryService::new` does no disk work beyond the built-ins), `DataLayout::default_library_root`, the daemon identity from daemon `identity::load_or_create` (`identity.json`, the daemon's file) and the root generation base from daemon `root_generation_base` (drawn at random each run — the crate holds no random source and reads no clock). `roundtrip_smoke` passes a temp state folder with no file, so its root stays unset.
- **First start, then the boot scan.** `build_daemon_wiring` calls `LibraryService::first_start` once, after the service is built and before `run()` sets the command table, and right after it — on every start, whatever the first start answered — `LibraryService::start_boot_scan`, which runs the first scan on a background job and returns at once. Nothing on the boot path before `daemon.json` walks the library or waits for that walk (ADR-0382). The test server builds no service and so runs neither.
- **The service goes into the manager as its launch-kit source.** `build_daemon_wiring_with_store` passes it via `AgentManager::with_launch_ports(LaunchPorts { kits, … })` and keeps the same service as `DaemonWiring.library` for the library commands. The test server passes no `LaunchInputs` and keeps the Noop kits.
- **The service also answers the manager's folder stat.** `agent.setWorkspace` stats its folder through `LaunchKitSource::stat_folder` before taking any lock; the service answers it with `BoundedIo` on a fresh read budget (`IO_LIMIT`, ADR-0360 decision 4), so a dead share answers `timeout`. The Noop kits answer one std stat. No library lock is taken (ADR-0386).
- **The manager goes into the service as its profile-edit port.** Right after it wraps the manager, `build_daemon_wiring_with_store` plugs it in with `LibraryService::plug_profile_edit` — before `run()` sets the command table. The cell is set once and holds the manager weakly, so the pair makes no cycle; an empty or dead cell answers `profile-edit-unavailable` (ADR-0380). The test server builds no service.
- **The service answers the library commands.** `run()` and the test server build the command table with `DaemonWiring::library_commands` — the kept service, or the daemon `NoLibrary` port when there is none (the test server; `saturation_pilot` passes `NoLibrary` too), which answers `library-unavailable` and an empty-scan refresh report and judges `agent.new {presets}` by the attach rule (a library preset refused, built-ins judged). `roundtrip_smoke` passes its own service and plugs its manager as that service's profile-edit port before it builds the table (the ADR-0380 order). Every handler is a `blocking_handler` (ADR-0386).
- **Boot sweep order.** `build_daemon_wiring` runs `launch::sweep_launch_dir` after the instance lock and before the service is plugged in.

**The setting is a mount list; every path the service holds is virtual** (ADR-0375 · ADR-0396 · ADR-0400). `library.json` is schema 2, `{"schema_version": 2, "mounts": [{"name", "path"}]}` in the order shown; a `path` is the word `default` or an absolute path, and `default` resolves every start to that run's `default_root` (`DataLayout::default_library_root`, a folder named `default_library` — beside the data folder for a release, inside it otherwise, by the rule that found the data folder, never by a name), so the library moves with the data folder. A schema-1 file (one `root`, never shipped) has no reader and is corrupt (ADR-0398). Catalog paths, references and answers are virtual (`<mount>/…`); `mounts.rs` joins one to its mount's folder only at the disk boundary, and a first name that names no mount reads as absent. A scan walks every mount (a folder refresh only its own mount) and applies them in one write lock; with no mount registered the virtual root holds only the built-in mount. The built-in mount `engram` is always present and read-only: `list` / `folders` / `read` answer it from `builtin.rs` (`list engram` → `default`, `priming` and the virtual folder `settings`; `read engram/default` → its real file), never from the catalog or a walk; a write into it refuses `mount-read-only`; a `refresh` of it walks nothing and answers that it is not scanned; `library.list` has no `builtins` flag (ADR-0400 decision 20). Its name is matched ASCII case-insensitively on every OS (`mounts::builtin_rest`, the one place), and what follows it — an id, the folder `settings` — exactly, by `list` and `read` alike. With no built-in folder, or one none of whose built-in files could be read at start (`Builtins::folder_unreadable`), the run's `engram` row (`list`, `folders`) is `unreadable` and a whole-tree read names it in `unavailable`; `read engram/…` refuses `library-unavailable` with `mount`, and its item rows stay as stand-ins; a launch still goes on with `builtin-unavailable` notices. A `query` in a built-in folder answers strictly below it, as in a library mount. The reference counts of a built-in cover only the Default slot (`engram/default`; 0 for the others). The old spelling `engram:/…` is refused `item-path-invalid` with the new spelling in its `why` — never rewritten (ADR-0398). Before it draws its ticket a scan stats every mount it would walk in one bounded batch (`BoundedIo`, share probe included, holding no lock); a mount whose stat is not `Ok`, or whose whole walk fails, is not walked and becomes that mount's last known state (`gate::MountSeen` in `State`) and an error row naming the mount — the scan still applies the others and raises the first scan (ADR-0400 decision 17). The mount commands change the list (ADR-0400 decisions 7–16): `add_mount` (a name by the mount name rules, an absolute folder, `create` to make it) and `relocate_mount` (the same name at another folder) judge the folder's overlap with every other mount and stat it on one read budget — only mounts are judged, so a mount may lie anywhere else, the daemon's own folders included; canonical paths and identities asked in one batch each, refusing `mount-overlaps`, and refusing `library-root-unusable` when an ask about either side gives no answer (fail closed; a mount whose canonical path the OS refuses is judged on its spelling, logged); with `create` the folder is judged first, by its nearest ancestor with a canonical path, and made only after the judgement passed, so a refused judgement leaves nothing on disk — then walk that one mount and publish it under a `Root` ticket, dropping only its range (`Gate::change_mount`); `remove_mount` drops the mount and its range and touches no file. Each raises the one root generation and the change number, and every save writes each published mount, one at the default place as `default`. A save that fails leaves the change live (`config: unsaved`), and repeating the same call saves it: an add of the same name at the same folder or a relocate to the folder already live only saves, and a remove of a name not registered while `unsaved` whose last saved list still names it answers `saved_only` — otherwise `mount-not-found` (ADR-0400 decision 14). The built-in `engram` is refused `mount-read-only` by remove and relocate. Once per run, before any mount is stat'ed, the registered mounts are judged against each other (`LibraryService::judge_at_load` over `mounts::overlapping` — nothing fails closed there: a canonical path that cannot be had falls back to the spelling, an identity that gives no answer is left unknown): whoever first needs a mount stat'ed or changed — the boot scan's job, a reader's scan, a read entrance, a launch, `status`, a mount command — runs it and the others wait for it, so no mount is walked or read before it was judged and no mount command changes the list between the judgement and its holds. It costs no caller more than its own budget (ADR-0360): the one that runs it spends on it at most what is left of its own required budget (at most one limit), one that finds it running waits at most that much, and either is charged the time (`LaunchIo::charge_required`), so its own stats get only the rest; a caller whose budget runs out first takes no mount as `Ok` (`not checked`), and a mount command refuses `library-unavailable`. A scan is the exception (ADR-0402 decision 5): it runs or waits for the judgement on a read budget of its own and then stats its mounts on a fresh one the judgement charged nothing to, so a mount it merely ran out of time for is never recorded; when its wait for the judgement runs out first it states no mount (`gate::Stat` answers `None` — not stated), records and walks nothing, does not raise the first scan, and its waiters go round to a fresh scan — each such round waits a whole budget on a judgement begun before it, and the rounds end once the judgement does. A mount that gave no answer to its own ask within that fresh budget is recorded unreadable as before. A mount overlapping an earlier one is held — registered, never walked, `unreadable` naming the other in every stat the service takes of it (`stat_mount_list` for read entrances, launches and `status`; `scan_stats` for scans, where the hold wins even over a stat whose worker could not be started) — until it is relocated or removed (ADR-0400 decision 10). A read computation keeps each mount's stat by its name and folder (`mount_key`), so two mounts on one folder keep their own answers. Only a missing `library.json` makes the first start due: it creates the default place, stats it as a new mount is stat'ed (`stat_new_mount`), publishes it as the mount `default_library` without a walk and only then writes it with `default`; the boot scan walks it (ADR-0382). A failed create or stat leaves no mount and no file, and the next start retries; a failed write leaves the mount live for the run (`config: unsaved`) and the next start follows the file that is left (with none left, the first start runs again). A first walk that fails after the publish leaves the file written and the mount not walked: reads inside it answer `library-unavailable` with `mount` until a walk of it succeeds, and `status` answers its folder's fresh stat. A configured mount folder that vanished stays `missing` and is never re-created. A corrupt, newer or unreadable `library.json` registers no mount and leaves the mounts unknown for the run; newer or unreadable also makes every mount command refuse `library-config-read-only` for the run (ADR-0376 · ADR-0400 decision 15). With no mount registered — a valid empty list or unknown mounts — catalog reads answer the virtual root with only the built-in mount, never `library-unavailable`; `agent.attachPreset` and `agent.new {presets}` naming a library preset refuse the whole call `library-unavailable` while the mounts are unknown — also while a missing `library.json`'s first start has not published the default mount (not run yet, or failed) — and with `mount` when that preset's mount cannot be read (ADR-0386 decision 5 per mount); with a valid empty list they skip it as `not-found`. A mount not walked this run, or not `Ok` when last seen, cannot be read — one rule for every reader. A read inside it (`list` of a folder in it, `read`, `preset.get` of a preset in it) first stats it fresh: one that does not stat `Ok` takes that state under a brief write lock without a ticket (so it does not queue behind a slow walk), one that does is walked again; if it still cannot be read, the read refuses `library-unavailable` with `mount`. A write into it (a preset edit, `newFolder` / `newFile`, a relink's `to`) refuses the same way before any change, and is judged again from the recorded state inside the change before any disk IO (a scan queued ahead of it may have found the mount gone), so its disk is never touched under the write lock; a relink skips the files of such mounts (`skipped`, `library-unavailable` with `mount`), and a mount never walked this run is one skipped row at its top with no pair reported fixed — what in it refers to the old paths is unknown. `preset.check` refuses like `preset.get`. Accepted: a mount last seen `Ok` and walked that has died since still gets a write's disk IO under the write lock, as `read` reads its stale rows and as the one root did before mounts. A read entrance (`agent.presets`, `preset.get`, an agent-preset edit) stats the mount of each library preset it names and of every library reference those presets reach in the catalog by the resolution's tag rule (`reached_mounts` · `resolve::TagRule` — a reference only another backend's tag lists is not followed), walks again one that stats `Ok` but cannot be read, and judges one still not readable by its last known state: missing is absent (skipped), otherwise unreadable (④). A mount it did not stat — one reached only through the Default slot's built-in preset or a `preset.check` draft's own entries — is judged by its last known state (`read_states`). The mount states are judged in the read lock that resolves, over that lock's mounts. A `preset.get` row in a mount that cannot be used is not looked up: an unreadable mount's row answers `library-unavailable` `{mount, message}`, an absent one's `not-found`, and neither is link-probed. Whole-tree reads never walk again: the virtual root's `list` rows and `folders`' mount nodes carry each mount's last known state (no fresh stat), and `list {query}` without a folder and `folders` answer from the readable mounts and name the others in `unavailable` (ADR-0400 decisions 4, 6 and 17). A launch judges each mount it reaches by its own stat (ADR-0387 · ADR-0400 decision 19), following references by the same tag rule as its resolution, so a mount only another backend's entries reach is neither stat'ed nor read: it leaves out the items of a mount that is not registered or absent (missing or not a folder) — one `library-unavailable-skipped` notice per mount, with `mount` — and is blocked with that mount's ④ row only when it exists but cannot be read or did not answer; the other mounts' items load. An agent whose backend has a `SettingsCheck` and no library preset still gets a real plan: `engram/default` (with its priming and default settings) when the profile's `default_preset` is set, otherwise an empty one.

## Main flow

1. **Read**: the scan stats each mount it would walk (before its ticket), the store walks each one that stats `Ok`; `ScanResult::build` reads and parses outside every lock; the gate applies the results per item into the `Catalog` and records each mount's last known state. The first walk starts in the background at daemon start (`start_boot_scan`, which logs a `warn` per mount it could not walk); readers (`list`, `resolve_*`) pass `first_scan_join` first, which joins that walk or starts one.
2. **Check**: `check_settings` and `check_skill` ask the backend port; there is no value or schema check (ADR-0359).
3. **Resolve**: `resolve::resolve` expands `engram/default`, then the attached presets in order, nested presets depth-first. It takes common items, then the agent's backend's tagged items, and yields the materials plus problem rows and notices. A library item is looked up only when its mount is usable (`MountStates`); the items of a mount that cannot be used stand as one ④ row naming it (an absent mount's: skipped).
4. **Launch materials**: `launch_check` stats each mount it reaches once (the attached presets' mounts in one batch, then each wave their references reach) and reads the presets an agent reaches fresh in the mounts that stat `Ok` (the overlay), resolves over them, runs the required folder phase and then the advisory phase, and judges the command line. The rows it skips (`Resolution::skipped`) become `missing-item-skipped` / `library-unavailable-skipped` notices and a launch note, the last part of the merged instructions: the named form, else the count form, else none when the command line cannot carry it (`Skips`). A backend whose instructions replace the user's own (`SettingsCheck::instructions_append` false — codex) gets no note when the merged text without it is `trim()`-empty. It returns a `LaunchPlan` with a stamp, or `LaunchBlocked` with only the rows it refuses on. `prepare_in` re-reads the stamped sources and writes the merged instructions, the note included, into `<launch_root>\<id>-<epoch>\`. `release` removes that folder.
5. **Preset edits**: an edit body (`edit.rs`) passes the first-scan entrance, stats the folders an `add` names outside every lock, then runs one `LibraryService::change_at`: link admission, the store read of the file's current bytes, the parse, the operation over `format::PresetLists`, `format::rewrite_lists`, `LibraryStore::write_atomic`, and the item made from the written bytes applied per item. It answers the `preset.get` view of the preset as committed, built inside the same change (its folder stats and link probes run after it, outside every lock); `LibraryService::preset_get` builds the same view from the catalog under a read lock.
6. **Agent-preset edits**: an edit body (`agent_edit.rs`) takes the live port from the cell, passes the first-scan entrance (only an `attach` naming a library preset refuses when no first scan was applied or the mounts are unknown), stats in one batch, outside every lock, the mounts its attachments and the request name (as `agent.presets` does), then runs one `LibraryService::change_at`: the registry read, the judgement against the catalog (`attach`), the `baseRev` check (`reorder`), and `ProfileEditPort::set_attachments` with the whole new attachments. It answers the `agent.presets` view of the attachments as committed, built inside the same change; `LibraryService::agent_presets` builds the same view through `resolve_*`.
7. **Relink**: `LibraryService::relink` passes the first-scan entrance, then runs one `LibraryService::change_at`: the checks of `to` (in the catalog, link admission, the kind the referencing lists need), the registry read, the pairs to fix (the picked one, and — when the catalog lacks `from` — the other missing targets of its old folder found by name in `to`'s folder), each preset file listing an old path rewritten through `LibraryService::rewrite_in` (the edits' per-file pipeline, without the answer view), and then `ProfileEditPort::rewrite_preset_paths` once. It answers the pairs fixed, the files written and skipped, and where it stopped.
8. **Create**: `LibraryService::new_file` and `LibraryService::new_folder` check the name, pass the first-scan entrance, then run one `LibraryService::change_at`: the parent's link admission, the existence check, the create through the store (`LibraryStore::create_new` · `create_dir`, which refuse a taken name), and the new item (made from the bytes written, as a scan makes it) or folder (`Catalog::insert_folder`, after dropping what the catalog still held at or below it) entered into the catalog.

## Contracts not visible from one file

- **Lock order.** One `RwLock<State>` (catalog + mounts), then the turn mutex as a leaf, never the reverse. Walking, reading and parsing run outside the lock; the write lock is taken only to apply. Canonical: `gate.rs` header (ADR-0324). Above both sits the service's mount-change mutex (the mount commands and `first_start`); under it they take the gate's locks, the leaf mutexes (the config's state in `config.rs`, the held overlaps, the load judgement's state — each held for no IO), the registry's read lock under the library read lock (reference counts), and do bounded folder IO. The load-time judgement (`judge_at_load`) runs before the mount-change mutex (under it, a mount command's final status finds it done) and never under a library lock or a ticket; its state mutex is a leaf held for no IO, and `first_start` does not run it (it runs before the daemon answers, ADR-0382 decision 1).
- **Lock order across crates.** The library lock comes before the manager's and the profile registry's locks, never the reverse. The manager calls `check_in` holding none of its locks (agent `manager/prelaunch.rs` header), and the profile-edit port impl never calls back into the library (agent `profile_edit.rs`).
- **Generations.** `Numbers` holds the gate's generations, each raised inside the write lock. A scan whose walk saw `change` move walks again. A late merge applies only if neither `change` nor `root` moved since the caller noted them before its disk read, and it never removes (ADR-0324 · ADR-0366). A mount change raises `root` (one generation for the whole tree) and `change`; a change refused inside its body that applied no catalog item raises nothing (ADR-0400 decision 16). `root` starts each run at the base the daemon passes (`LibraryValues::root_generation_base`), not 0, and every generation is compared only for equality (ADR-0381).
- **Tickets.** Tickets are served FIFO. A mount change (`Gate::change_mount`) is a `Root` ticket, exclusive from its ticket to its publish, and never a pending first scan: it walks one mount, and the first scan stays a whole scan. A refresh joins only a covering scan that is queued and not yet walking (ADR-0366). A scan reads the mounts from the gate's view under the turn mutex — no library lock, so a change that holds the write lock across its body cannot overtake a scan drawn before it (ADR-0324 decision 4) — and stats them before it draws its ticket, so a mount that does not answer never holds the line; a mount that answers its stat but walks slowly still does, for its walk, as one root did (ADR-0400 decision 17). No stat is taken under a ticket: a mount registered or moved after a scan's stats is not walked by it (a whole scan that left one out does not raise the first scan; the reader prepares again). Each mount's state is stamped with the sequence number drawn before its stat, and an older observation never replaces a newer one. A stat whose worker could not be started says nothing about the mount: the scan walks it, as the first reader did before stats were taken (ADR-0382 decision 4). A folder refresh in a mount not walked yet walks the whole mount (decision 6 per mount). The first start's publish without a walk is a root ticket too, but it lowers the first scan (so the new mount's first scan is a real walk) and is not a pending first scan, so the first scan of that root is a real walk (ADR-0382).
- **The boot scan is an ordinary first scan.** `start_boot_scan` passes the first-scan entrance on a job from the service's spawner (the `BoundedIo` one), so it joins a first scan a reader already started and readers arriving during its walk wait for it; before that entrance it runs the load-time overlap judgement unless a request already ran it (ADR-0400 decision 10); it holds no lock across the boot and not the mount-change mutex. No published mount: no job. A job that cannot be started is logged and the first reader starts the scan. Launch checks skip the entrance and never wait for it (ADR-0382).
- **Mount changes are serialized and saved only after success.** The mount commands and `first_start` take one mount-change mutex across their publish (`Gate::change_mount`; the first start: the stat and `Gate::publish_mount_unwalked`) and the `library.json` write that follows it. The file is written only after the change was published, and nothing is ever undone (ADR-0381): a refused change writes nothing; a write that fails leaves the change live, the file as it was and `status` `config: unsaved` (it wins over `corrupt`, and clears at the next successful write), and the next start follows the file that is left; repeating the call saves it (ADR-0400 decision 14). `library.json` writes are judged again right before each write (base `file` rules). A change refused inside its body that applied no catalog item moves no number (`ChangeAnswer`).
- **Agent attachments change only through the port, inside one change.** This crate never writes `ProfileRegistry`: an agent-preset edit reads the agent and writes its whole attachments with `ProfileEditPort::set_attachments` inside one `change_at` write lock, and a relink calls `ProfileEditPort::rewrite_preset_paths` inside its own. The port is last-write-wins with no comparison, correct only because every writer of an existing agent's attachments queues under that lock (agent `profile_edit.rs`). A `reorder` `baseRev` is compared with the one computed from the registry read inside the change (ADR-0378). A port store error is passed through unchanged (ADR-0379). Canonical: `agent_edit.rs` header.
- **The root generation is checked inside the edit.** An edit that carries the root generation `status` answered goes through `LibraryService::change_at`, which compares it inside the change's own write-lock take, so an edit queued behind a mount change is refused `root-generation-stale`, nothing applied (ADR-0377).
- **Refusals are a class plus a reason.** Bodies refuse with `LibraryRefusal`: a `RefusalClass` and an agent `launch::Reason`, or the profile store's error passed through unchanged. `host.rs` converts it 1:1 into agent's `PortRefusal` and agent `library_commands::refusal_error` maps the class onto the bus code, and a refusal that applied nothing maps onto a code that does not keep the request id, except the two `INTERNAL` cases of ADR-0379 decision 5 (`profile-edit-unavailable` and a profile-store write failure); `library-config-write-failed` applied the mount change and still maps onto such a code, so a retry saves again (ADR-0381 · ADR-0400 decision 14). The codes are consts beside the code that refuses.
- **A preset edit is one change and does not re-create a file missing at its read.** Everything from the link admission to the per-item apply runs inside one `change_at` write lock; a file or parent missing at the read answers `not-found` before anything is written; an edit whose lists come out unchanged writes nothing; a `reorder` or `save` `baseRev` is compared with the `rev` of the bytes just read; and bytes read that differ from the catalog item are applied also when the edit refuses (ADR-0378). Folder stats run before the change, never under the lock. Canonical: `edit.rs` header.
- **`rev` is a catalog value.** A preset item's `rev` is the SHA-256 of the exact bytes it was made from (`catalog::yaml_item`), on every path that makes one — scan, late merge, launch overlay, edit, relink, create — so `preset.get` does no disk read of the preset and `rev` is the same after a restart (ADR-0378).
- **Catalog writes are per item.** There is no whole-catalog swap: per key the later `read_seq` wins, and a removal needs an absence observed after the read. `Catalog::drop_range` is for a mount change (`Gate::change_mount`) only. Folders change only by a scan's apply and by `Catalog::insert_folder` (`newFolder`).
- **Relink is presets first, then agents, with no journal.** Inside one change each preset file listing an old path is rewritten through the edits' per-file pipeline (origins kept; in a list it changed, only the first place of each target stays — ADR-0339; folder entries untouched), then the agents once (ADR-0335). Part (b) runs only when the catalog holds neither an item nor a folder at `from` (ADR-0330); each pair re-points only in the list its new target goes into, and a file the rewrite would make reach itself is skipped `preset-cycle`. A refusal that would repeat on a retry skips that file; a read or write failure stops the walk and the agents are not rewritten; a stop before any file was written answers that failure's refusal. Once the failure is cleared, running the same relink again recovers the rest. Canonical: `relink.rs` header.
- **A create never overwrites and never makes a parent.** The create itself refuses a taken name (`LibraryStore::create_new` · `create_dir`; the existence check before it is only a fast path), so an existing name answers `name-exists` and a missing parent `not-found` with nothing created or replaced; settings and preset templates carry `version: 1`, so they read. Canonical: `create.rs` header.
- **Links.** Only a mount's folder itself may be a link. A path at or below a link inside the library is never read; a reference to it becomes `path-through-link` (ADR-0365). `LibraryStore` read and write follow links themselves, so the admission is the caller's: every new way into the catalog (edits, moves, deletes, relink, create) passes `admits` and `LibraryStore::first_link` before any read, write or merge — `LibraryService::admit` (for a create, on the parent folder).
- **Problem rows are the launch's rows; absent is skipped, unreadable blocks.** Resolution problems are agent `launch::BlockReason` rows; the problem list, the tree ⛔ and the launch block come from one list. A launch leaves out every ① `Missing` row and the ④ row of an absent mount (`Resolution::skipped`) and refuses on the rest (`Resolution::blocked`, ordered ② `Broken` → ③ `Conflict` → ④ `LibraryUnavailable`); the two parts are exactly the problems. A folder entry or a mount folder is absent only when its stat says missing or not a folder and, on a network share, the share root stats as a folder (`BoundedIo::stat_all` share probe over platform `fs::share_root`; a share root that answers anything else — access denied included — makes the path `share not reachable`); one that exists but cannot be read or did not answer is ② `folder-unreadable` (a folder entry) or ④ (a mount). A mount name no mount is registered under is absent (`not registered`). A link probe that fails is ② `library-read-failed`, a path under a file is absent (`link_verdict`) (ADR-0387).
- **④ stands per mount.** At the read entrances the items reached in a mount that cannot be used are one ④ row naming it (`args` = `{mount, message}`) — none of them looked up, as that mount's part of the catalog cannot be trusted — and every other mount and the built-ins expand normally (ADR-0361 · ADR-0400 decision 19). A launch that reaches a mount that exists but cannot be read is refused with the rows found so far — no folder IO, no advisory step, no command-line check. An absent or unregistered mount's items are skipped `not-found` rows instead, never read or link-probed, and one `library-unavailable-skipped` notice per mount names them (ADR-0387).
- **Built-ins never block.** An unreadable built-in becomes an empty stand-in and adds one `builtin-unavailable` notice (ADR-0361). The priming reaches an agent only through a real plan's `include_priming`; Noop launches carry none (ADR-0370).
- **The priming is an English pointer, bounded by the codex command line.** `builtin\instructions\priming.md` points at the help screens with one `engram help <word>` line each (`library` among them) and carries the whole-file-rewrite sentence and the description rule; the file formats and the commands live in the `## library` section of `prompts/engram-help.md` (ADR-0386). It goes onto every codex terminal launch line, so its length and its characters (no `'` · `"` · `%` · `\`) are bounded by agent `backend/codex/cmdline.rs` — `builtin.rs` `the_shipped_priming_fits_the_codex_terminal_command_line` pins it. Daemon `control/help.rs` pins that every `engram help <word>` line names a screen that renders; the CLI pins only that each such line parses as a help request.
- **One launch, one scope.** The manager opens `begin_launch` once per launch and passes that `LaunchScope` to every `check_in`, `prepare_in` and `working_folder`. The scope holds one `LaunchIo` (one budget, one answer set) and the working folder the last check decided, so the spawn runs where the check looked.
- **The check waits only briefly on the library.** `launch_check` skips the first-scan entrance and takes two brief read-lock takes, so it waits behind a held write lock — keep write-lock holds short. It reads its files fresh and hands the merge off (`hand_off_merge`). `hand_off_merge` must be called holding no library guard: if its job cannot start, it merges in place and takes the write lock. `prepare_in` takes no library lock; a stamped source that changed or vanished is `PrepareError::Stale`.
- **Folder IO is bounded.** Every stat, list, canonicalize, file identity or read on a folder entry, a native skill root, the working folder (a launch's, and the folder `agent.setWorkspace` asks about), the library root or a mount folder and its ancestors (the overlap check) goes through `BoundedIo` and never runs under the library lock. The built-ins (`Builtins::new`), the launch folder (`prepare_in`, sweep, release), `library.json` and the folder a mount command's `create` or the first start creates use std `fs`. A launch has a required budget and a separate advisory allowance (agent `LAUNCH_REQUIRED_FOLDER_WAIT_SECS` · `LAUNCH_ADVISORY_FOLDER_WAIT_SECS`); a read outside a launch gets `IO_LIMIT` (ADR-0360).
- **Class B rule.** Required and advisory asks never share a batch or a wait; required runs first and alone. Advisory work runs only when nothing blocks, and a missing advisory answer is never substituted. Canonical: `folder.rs` header.
- **Removal is best effort.** `release` and the boot sweep never follow a link; they detach it. They never wait, retry, lock or panic, and anything they cannot remove stays for the next boot sweep.
