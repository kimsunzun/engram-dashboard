# Test Strategy

> This document is a **living operating map** — "what verifies each layer, how far, and how, and where the blanks are". The *rationale (why)* of the decisions is in **ADR-0012** (test strategy — isolation harness + TDD), and this document tracks the actual inventory, division of roles and gaps on top of it. The progress flow is in git log (`S<n>:` commit titles) + each work folder's `README.md`.
>
> When adding a new module or feature, write the test that fits the "role per layer" of this document **together** (TDD, ADR-0012). If the way of testing changes, update this document.

## 0. Core principle — test pyramid + separation of roles per layer

Split into three layers, and **catch as much as possible in the cheap, fast lower layers.** The upper layer (real app/visual) takes only what the lower layers cannot see.

| Layer | What it verifies | Tool | Speed | Security software |
|---|---|---|---|---|
| **① Logic unit** | pure logic (decode/dedup/state transition/conversion) | Rust `#[test]` · (frontend) vitest | fast | not relevant |
| **② Isolated integration** | causality across module boundaries (external dependencies cut at a seam) | examples/smoke bin · `tests/` integration · in-process WS E2E | medium | not relevant |
| **③ Real app/visual** | a real process · real rendering · the real OS | real process (#[ignore]) · CDP (`scripts/cdp.mjs`) | slow | **CDP is a detection target of security software** |

**Role separation rules (important):**
- **Logic goes in ①.** "Does it process the data correctly" is a unit test. No browser or real process needed.
- **CDP/Chrome is ③ only** — screenshots · layout · the final smoke of "does the real app actually come up and connect". **Do not use CDP eval to verify logic** (overuse = slow, friction with security software, bugs caught late).
- Rationale: the reconnect resume bug (2026-06-15) was a logic bug that should have been in ①, but there was no frontend unit test, so it was caught only by reaching ③ (CDP). It would have been caught at once without a browser by a mock socket unit test.

### 0-a. Unified placement — fix the folder by purpose (not by period)

In the past the same "module isolation verification" was split into `examples/` (run it and eyeball the log) at first and `tests/` (assertions) in S12. This is only a difference of period, and **a verification harness outside `cargo test` (in examples) becomes a hole that falls out of the automatic regression gate**. It is unified as below:

| Category | Rust placement | Frontend placement | `cargo test`/`npm test` gate |
|---|---|---|---|
| ① Unit (pure logic) | `#[cfg(test)] mod tests` inside `src/` | `*.test.ts` colocation (vitest) | ✅ |
| ② Integration (module boundary causality, assertions) | `crates/<crate>/tests/*.rs` | vitest (mock transport) | ✅ |
| ③ Real/visual (real process · rendering) | `tests/*.rs` + `#[ignore]` | CDP (`scripts/cdp.mjs`, shot/layout) | manual/CI |
| Demo · spike | `examples/` | — | ❌ (not a gate) |

**The rule in one line: `examples/` is only for demos · spikes (usage examples · throwaway). Every verification harness goes in `tests/` (assertion based).** Only then does `cargo test --workspace` become the single source of truth for regression across all layers (this command is also not run directly from the shell but goes through `scripts/run-detached.ps1` — rule = qa binding 「모듈별 명령」, rationale · measurements · usage = qa binding 「분리 실행」).

## 4. Security software caution — CDP

`scripts/cdp.mjs` opens a debug port on WebView2 (Edge based) with `--remote-debugging-port` and an external `node` attaches and controls it. The security software of a development PC detects this pattern as **"browser process memory access"** (the signature is identical to an attacker's credential theft technique). It was actually detected on 2026-06-15.
- **Principle**: verify logic in ① (vitest) to minimize CDP dependence. Use CDP only when visual/layout confirmation is really necessary.
- **If formal use becomes frequent**: the combination that is detected is target = `msedgewebview2.exe` + debug flag / subject = `node` `scripts/cdp.mjs` / loopback `127.0.0.1` — in an environment where this combination keeps being detected, do not increase CDP use.

## 5. Checks when adding new code (TDD, ADR-0012)
- If it is pure logic → ① a unit test **first/together** (Rust `#[test]` or frontend vitest).
- If it is a module boundary · causality → ② an isolation harness (example/smoke bin or `tests/`).
- Cut external dependencies with a seam (trait/sink) so it can run alone (making it impossible to isolate by direct calls violates ADR-0012).
- Use ③ (CDP/real process) only for the parts where real app/visual confirmation is truly needed. Code passing ≠ done, but **do not grow the ③ dependence; push it down to ①② as far as possible.**
