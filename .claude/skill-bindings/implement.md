# implement 바인딩 — engram-dashboard

## 작업 문서 폴더

- 주제 하나 = `docs/process/S<n>-<슬러그>/` 폴더 하나. `S<n>` 은 CLAUDE.md 「브랜치·커밋」이 정하는 그 주제의 번호다.
- 폴더 안 = `README.md` · `prd.md` · `trd.md`. 한 주제에 PRD · TRD 가 여럿이면 `prd-<부제>.md` · `trd-<부제>.md`.
- `README.md` = 무엇인지 한 문단 · 관련 ADR · tracking 번호 · 타임라인(`docs/process/step-log.md` 의 `## S<n>`) 링크.

## PRD — 무엇 · 왜

절:
1. 무엇 · 왜
2. 범위 / 비목표
3. 요구사항 — 번호를 단다(`R1` …).
4. 수용 기준 — 실측(화면 · CLI)으로 확인할 문장. 번호를 단다(`AC1` …).
5. 미결 결정 — 사용자 결정 대상(선택지마다 트레이드오프 · 놓친 대안) · 메인 기본값.
6. 위험

## TRD — 어떻게

- 머리에 「상태」 줄 = 판 · 날짜 · 정본 ADR.
- 절은 그 과업에 필요한 것만 쓴다 — 범위와 PRD 관계 · 모듈 경계 · 자료 모양(wire · 영속) · 동시성 · 시험 계획 · 구현 단위 · 결정 · 위험 · 리뷰 기록.
- 시험 계획 = 무엇을 무엇으로 확인하나 — qa 바인딩 표의 행 · 로컬 레인 · GUI 장면을 짚는다.
- 구현 단위 = 파일이 겹치는 단위는 순차로 둔다. 단위 끝마다 빌드 · 시험이 초록이어야 한다.
- PRD+TRD 리뷰 통과는 「리뷰 기록」 절에 한 줄 — 날짜 · 강도 · 판정 · 커밋.

## 사용자용 HTML — 멀티데몬 주제부터

- PRD · TRD 마다 사용자가 읽는 한국어 HTML 을 따로 만든다 — `/engram-explain` 으로 쓰고 자리는 explain 바인딩을 따른다. md(영어)는 리뷰어 · 코더가 읽는 정본으로 그대로 둔다. md 가 바뀌면 HTML 도 같이 고친다.
- PRD HTML = 무엇을 왜 만드나 · 화면에서 어떻게 보이나. 사용자 승인을 받아야 TRD 로 간다.
- TRD HTML = 위에서 아래로 — 전체 구조 → 프로세스 · 연결 관계 → 각 부분의 역할 → 세부. 사용자가 읽으며 배우는 글이다. 사용자가 수긍해야 리뷰 · 코딩으로 간다. 막힌 자리는 설명을 보강해 다시 보인다.
- 사용자: 「멀티데몬 만들때 prd trd 각각 html 양식으로 진행해야될듯. trd는 탑다운 식으로 내가 학습하는 식으로 보고 … 내가 어느정도 수긍하면 진행하는 스탭으로」 (2026-11-10).

## 결정 대장

- 코더 지시서 재료를 추릴 때 결정을 읽는 곳 = ADR(`docs/decisions/`) · PRD 「미결 결정」 · TRD 「결정」 · `docs/tracking.md`(보류 항목).
