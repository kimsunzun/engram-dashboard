# ADR-NNNN (S25-A): 라이브러리는 따로 된 얇은 crate `engram-dashboard-asset-library` 다 — 데몬은 배선만

- 상태: 제안 (2026-10-31, 근거: 사용자 결정 G16(2026-10-20 「라이브러리를 별도 create로 확정하는건 맞는데」) · G24(2026-10-29 「asset 으로해」) + 메인 결정 M1 · M17 · M18 · M25(보고) · 판정표 `docs/research/crate-split-checklist-2026-10-20.md`)
- 관련: 옛 메모 96(데몬 안 모듈 — 사용자 2026-10-14)을 대신한다 · ADR-0151(crate 분리 판정 기준) · ADR-0155 결정 1(어휘는 생산자 옆 — `library.*` 는 agent 블록) · ADR-0251(동기 포트 + `blocking_handler` 선례) · ADR-0175 · ADR-0269(base 입주 조건) · CLAUDE.md 「백엔드 확장」 · S25-I · TRD §1-1 거부한 대안 · §1-4 · §7 30

## 맥락
라이브러리(지침 · 스킬 · 설정 · 프리셋 파일의 훑기 · 읽기 · 쓰기 · 해석 · 다시 연결)를 어디 둘지. 메모 96(2026-10-14)은 데몬 crate 안 전용 모듈로 정했다 — trait seam 은 처음부터 두고, base 는 입주 조건(도메인 지식 · 소비자 하나)에 걸려 배제했으며, 따로 된 crate 는 「다른 crate 가 필요하거나 프리셋 로직이 커지거나 격리 시험이 필요할 때」로 미뤘다. TRD 의 옛 기각 사유는 「소비자가 하나다」였다.

## 결정
1. 라이브러리는 신설 crate `crates/engram-dashboard-asset-library/`(Rust `engram_dashboard_asset_library`)다. 이름 = 담는 것이 에이전트에 싣는 에셋이라 asset(TRD 어휘 `AssetRef` 와 맞춤). 버스 명령 `library.*` 와 화면 이름 「라이브러리」 는 그대로다.
2. 의존 = 정확히 agent · platform · command · base. 데몬이 이 crate 를 의존하고 **배선만** 한다(만들기 · 포트 꽂기 · 값 넘기기). agent 는 이 crate 를 모르고 포트만 정의한다.
3. 바깥 접점은 포트다. `LaunchKitSource` · `LibraryCommandHost`(명령마다 타입 있는 메서드)를 이 crate 의 서비스가 직접 구현한다. 백엔드마다 다른 설정 지식은 agent `backend` 의 설정 검사 포트(S25-I). 명부 변경은 manager 의 프로필 편집 포트로 — 명부 변경과 스폰 예약이 한 락 순서를 쓴다(M18).
4. 네트워크 클라이언트를 갖지 않는다 — 스키마 받기는 데몬이 꽂는 fetch 포트(trait 은 이 crate 가 정의 — M25). 시험 기능(`test-support`)이 없다 — 데몬 쪽 시험은 실 `FsStore` + 임시 폴더(M17).
5. 데몬 내부(`connection_core` · `command_delivery` · `control`)를 부르지 않는다. 데몬은 값(`DataLayout` 이 낸 자리 · `daemon_id`)으로 넘긴다.
6. 게이트 넷(M17): 시험 줄 · 의존 상한 = 이름 **집합** {agent · asset-library · base · command · platform}(줄 수 아님) · 메시징 격리 정규식에 `asset_library` · `use tauri` 0줄. async 반입 게이트는 스키마 받기가 들어올 때 정한다.

## 거부한 대안
- **데몬 안 모듈**(메모 96 — 사용자 2026-10-14 「애매하긴 하지만 그렇게 해」) — 사용자가 2026-10-20 따로 된 crate 로 확정했다(G16 — 「분리할수 있으면 분리 … 데몬안에 있는 조건이 데몬에 있는걸 너무 많이 연관시켜야되고 상호참조가 필요해서 어쩔수 없을때」). 옛 기각 사유 「소비자가 하나다」 는 ADR-0151 결정 1 이 폐기한 기준이다(판정표 결론 · TRD §1-1).
- **base 에 두기** — 도메인 지식이 있고 소비자가 하나라 입주 조건에 걸린다(메모 96).
- **crate 이름 `engram-dashboard-library`**(메모의 예) — 사용자가 asset 을 골랐다(G24 — 담는 것이 에셋 · `AssetRef` 어휘).

## 근거
- 판정표: 「분리할 수 있나」 다섯 물음이 다 「예」 — 단 백엔드 검사 지식을 backend 포트로 옮긴 뒤(M2). 대가는 고정분(매니페스트 · 게이트 등록 · 공개 표면)뿐이고, 들어오는 간선이 없는 신설 때가 가장 싸다(TRD §1-1). 판정표의 확신도 = 중간.
- 옮길 타입이 없다(판정표 C6 = 0) · 시험 기능이 필요 없다(C5 = 0)(TRD §1-4).

## 영향 / 불변식
- 이 crate 가 데몬 내부를 부르게 되면 crate 판정이 뒤집힌다(TRD §1-4 · 판정표 §3 「뒤집는 것」).
- 데몬 조립 순서(TRD §1-4): 명부 → 라이브러리 서비스(프로필 편집 포트 = 늦게 채우는 빈 칸 · 채운 뒤 약한 참조) → manager → 빈 칸 채움 → 스키마 갱신 스레드 → 수락 루프. 빈 칸에 닿으면 오류로 답한다 — Noop 으로 접지 않는다.
- CLAUDE.md 「백엔드 모듈 맵」 · 「빌드·검증 명령」 의 새 줄은 구현 때 사용자 확인을 받아 더한다(M1 · M17).
- 메모 96 에 대체 표시(TRD §5 0c).

# ADR-NNNN (S25-B): 라이브러리 루트는 하나다 — 바깥 내용은 루트 안으로 들인다

- 상태: 제안 (2026-10-31, 근거: 사용자 결정 G36(2026-10-31 「ㅇㅇ 루트를 하나로」) · G37(「외부에 두지말고 engram 안으로」) · G37-NOTE(「라이브러리 폴더 바꾸기는 그대로 놔둬」) · G35(「최초 디폴트 등록해둬」) · G31 + 메인 M22 · M24-2(보고) · PRD R7)
- 관련: 옛 메모 127(2026-10-15 「그냥 한 개 폴더로 하자」 — 되살림) · G25 · G25-RESOLVED · G26 · G27 · G30 · M23 · M19/M21 의 여러 루트 부분(되돌림) · S25-H · S25-W · TRD §1-1 · §1-2 `LibPath` · §1-4 「루트 · 기본 경로」 · §7 31 · 조사(배경) `docs/research/multi-root-asset-library-practice-2026-10-30.md` · `docs/research/cross-root-move-practice-2026-10-30.md`

## 맥락
메모 127(2026-10-15)은 라이브러리 폴더 하나로 정했다. 2026-10-29 사용자가 여러 루트를 요청했고(G25), 그 뒤 루트를 넘는 참조 허용(G25-RESOLVED) · 루트 이름 접두 `<이름>:/`(G26) · 루트 사이는 복사만(G27) · 루트 이름을 바꾸면 참조 고침(G30) · 참조된 루트 지우기에 `yes`(M23)가 줄줄이 붙었다. 2026-10-31 사용자가 하나로 되돌렸다.

## 결정
1. 라이브러리 루트는 하나다(R7 되살림). 프리셋도 그 안의 파일이다.
2. 루트 안이면 어디로든 옮기고 이름을 바꾼다(탐색기 규칙 — P5). 드라이브가 하나라 볼륨을 넘는 이동이 없다.
3. 바깥 내용(예 `~/.claude/skills`)은 제자리에서 쓰지 않는다 — 루트 안으로 복제 · 복사해 들인다(G37).
4. 나눠 줄 때 = 필요한 파일을 루트 기준 경로로 내보내 같은 경로로 들인다. 내보내기 · 들이기(의존 닫힘)는 S25 밖이다(G37 · T-73). S25 는 참조 걷기를 다시 쓰는 함수 하나로 둬 나중에 꽂히게 한다(G37). 일부만 손으로 옮기면 빈 참조는 「찾을 수 없음 · 다시 연결」(R19).
5. 첫 시작에 루트가 없으면 빈 `<배포판>\library` 를 만들어 루트로 적는다(개발 · 시험 = `DataLayout` 규칙 · `ENGRAM_DATA_DIR` 격리 — G35). 만들기에 실패하면 미설정 상태로 물러난다(M24-2). 「라이브러리 폴더 바꾸기」(R9)는 그대로다(G37-NOTE).
6. 나중에 루트를 늘리면 새 루트에만 이름 접두를 붙이고, 접두 없는 경로는 지금 루트를 뜻한다(G36).
7. 그대로 두는 것: 휴지통 `<루트>\.trash\`(G31 · S25-W) · 루트가 git 작업 트리면 `.git/info/exclude`(M22) · 기본 제공 `engram:/`.

## 거부한 대안

# ADR-NNNN (S25-C): 지침 · 스킬의 백엔드 꼬리표는 프리셋 항목에 단다 — 에셋 파일은 손대지 않는다

- 상태: 제안 (2026-10-31, 근거: 사용자 결정 G29(2026-10-30 「프리셋에 하는게 맞지 싶은데」) + 메인 M20 · M24-4 · M25 · M26(보고) · 조사 `docs/research/per-agent-instructions-practice-2026-10-30.md`)
- 관련: PRD R54 · P12(안 실리는 줄 흐림) · S25-F(「기본」 의 백엔드별 프라이밍) · S25-K(codex 터미널 알림) · TRD §1-2 · §1-3 1 · 5 · 6 · §7 32

## 맥락
에이전트마다 공통 지침에 더해 claude · codex 전용 지침 · 스킬을 실을 길이 필요했다(G29 — 새 기능 · PRD 수준 추가). 꼬리표를 어디에 다느냐.

## 결정
1. 지침 · 스킬 항목은 경로 문자열(= 공통) 또는 `{path, backend: claude|codex}` 다. 꼬리표는 **프리셋에** 있고 에셋 파일에는 없다.
2. `presets` · `settings` 항목은 경로 문자열 그대로다 — 설정은 파일 안 `claude:` · `codex:` 칸이 이미 백엔드를 가른다.
3. 실리는 순서 = 펼친 전체에서 공통 항목 전부(펼친 순서) → 그 백엔드 항목 전부(펼친 순서). **전역 순서다**(M24-4 — 프리셋마다 번갈아가 아니다). 덧붙임이지 덮어쓰기가 아니다.
4. 충돌 검사는 그 에이전트에 실제로 실리는 항목끼리 한다.
5. codex 터미널은 여전히 지침 · 스킬을 싣지 않고 codex 꼬리표 줄도 알림에 넣는다(M20 · S25-K). 기본 제공 「기본」 은 꼬리표로 백엔드마다 다른 프라이밍을 실을 수 있다.
6. 명령 = `preset.add` 의 선택 `backend` + 꼬리표 바꾸기 `preset.setBackend {path, items, backend?}`(M26). 에이전트 슬롯은 그 에이전트 백엔드에 안 실리는 줄을 흐리게 보인다(P12 와 같음). 화면 꼴(공통 / claude만 / codex만 세 묶음 · 끌기나 우클릭으로 꼬리표 바꾸기)은 클라이언트 단계에서 다시 보인다(M20).

## 거부한 대안
- **에셋 파일 앞머리에 꼬리표**(rulesync 꼴 — 조사의 (나)) — 받은 파일을 고쳐야 하고 · 같은 파일을 프리셋마다 달리 못 쓰며 · 실을 때 앞머리를 벗겨야 한다(G29 · 조사 「우리에게」 표 · 사용자가 (가) 를 골랐다).
- **프리셋마다 공통 → 전용을 번갈아 싣기**(M20 의 첫 읽기 — 프리셋 단위 순서) — 메인 세션이 전역 순서로 정했다(M24-4 · M25 OVERRIDDEN). 거부 근거: **사용자에게 받을 것**(§7 32 — `/adr` 때 사용자 확인).
- **전용 먼저 → 공통 나중**(Roo Code 가 문서로 적은 순서 — 조사 결론 3 · 우리 안과 반대) — 거부 근거: **사용자에게 받을 것**.

## 근거
- 조사(2026-10-30): 「공통 기본 + 에이전트별 예외」 는 있는 꼴이다(rulesync `targets` — 규칙 · 스킬 둘 다) · 묶음 쪽에 표시를 다는 선례는 못 찾았다 · 합치기는 거의 전부 덮어쓰기가 아니라 이어 붙이기다.
- 사용자 결정 G29.

## 영향 / 불변식
- 에셋 파일 형식에 백엔드 칸을 더하지 않는다 — 받은 파일을 고치지 않는다는 성질이 이 결정의 이유다.
- 순서 규칙(전역 · 공통 먼저)을 바꾸면 결정 3 과 「기본」 의 프라이밍 자리가 함께 움직인다.

# ADR-NNNN (S25-F): 프라이밍의 원천은 배포판 `builtin\` 하나 — 기본 제공 프리셋 「기본」 의 지침 파일

- 상태: 제안 (2026-10-31, 근거: 메인 세션 결정 G1(2026-10-20 · 보고) · M7(2026-10-21 · 보고 · TRD 리뷰 #4 · #8) · M18(보고))
- 관련: **Amends ADR-0092 결정 1**(아래 「바뀌는 조항」) · ADR-0099 · ADR-0100 · ADR-0211 · ADR-0215(같은 경로나 배달을 가리킨다 — 「영향」 의 확인 항목) · S25-C · S25-K · S25-V · TRD §1-1 · §1-2 · §2-4 1 · 2 · §5 17 · §7 35

## 맥락
지금 프라이밍은 고정 경로의 공용 마크다운(`prompts/agent-priming.md` · 덮개 `ENGRAM_PRIMING_FILE`)을 스폰 때 로더가 읽어 시스템 프롬프트에 주입한다 — 전원 무조건(ADR-0092 결정 1). S25 는 기본 제공 에셋(프리셋 「기본」 과 그 지침 · 설정)을 라이브러리와 같은 꼴의 파일로 두고 가짜 경로 `engram:/…` 로 가리킨다(Δ1). 원천이 「코드 + 배포판 `prompts\agent-priming.md`」 로 나뉘어 있던 것을 하나로 모은다(G1).

## 결정
1. 기본 제공 에셋은 배포판 `builtin\` 폴더 하나에 라이브러리와 같은 꼴로 둔다(프리셋 `.yaml` · 지침 `.md` · 설정 `.yaml`). `engram:/…` 가 그 파일에 대응한다(G1). 파일 이름 · 대응의 꼴은 구현 판단.
2. 프라이밍의 원천은 그 안의 지침 파일(`engram:/priming` — 지금 프라이밍 글 그대로) 하나다. 「기본」 프리셋이 그것을 지침으로 싣는다(M7).
3. 해석은 asset-library 가 스스로 한다 — `LaunchKitSource::prepare` 에 priming 인자가 없다(M18).
4. `builtin\` 이 없으면 프라이밍 없이 뜬다 — 막지 않는다(M7).
5. 배포 zip 에 싣는다(§5 17). 개발 · 시험 · `ENGRAM_DATA_DIR` 에서 찾는 법과, 옛 길(지금 `NoopLaunchKits` 만 쓰는 `priming_file`)을 걷는 때는 미결이다(TRD §2-4 1 · 2 · M25 LEFT OPEN).

## 바뀌는 조항 (ADR-0092)
- **결정 1 만 바뀐다 — 부분 개정이다.** TRD §7 35 · §5 0c 의 「폐기」 는 넓다. 결정 2(1:1 선행 · 다중수신 추상) · 3(형식 판정축 수용>토큰) · 4(happy-path-first)는 프라이밍 원천과 무관해 그대로다.
- 결정 1 에서 바뀌는 것: ① 경로 — repo 의 `prompts/agent-priming.md` → 배포판 `builtin\` 의 지침 파일 ② 로더 seam → 실행 재료 포트 `LaunchKitSource`(ADR-0092 가 「미래 구현체 = 에이전트별 프롬프트 인젝션/스킬등록 시스템(로더 교체로 흡수)」 이라 예고한 자리) ③ 「임시판은 전원 무조건 주입」 → 「기본」 이 붙은 에이전트에만(만들 때 붙고, 떼기는 `yes` 확인 — M21).
- 결정 1 에서 그대로인 것: 하드코딩 금지(여전히 외부 파일) · 데몬이 읽어 시스템 프롬프트 쪽으로 넘긴다(에이전트가 스스로 파일을 읽지 않는다). ADR-0092 「영향」 첫 줄(프라이밍 내용 하드코딩 금지 · 로더는 seam)은 계속 지켜진다.
- 이 초안의 결정 4(없으면 막지 않음)를 TRD 는 「ADR-0092 와 같은 너그러움」 이라 적지만 ADR-0092 본문에 그 조항은 없다 — 지금 코드의 동작인지는 확인하지 않았다.

## 거부한 대안
- **사용자에게 받을 것** — 메인 결정이라 적힌 사용자 거부가 없다(TRD §7 35).
- (참고 · 거부 아님) 대신한 것 = 「코드 + 배포판 `prompts\agent-priming.md`」 나눔(G1). 프라이밍 자체를 사용자 라이브러리 에셋으로 두는 것은 비목표 · 나중 생각이다(PRD R52 · 결정 기록 ROUND 2 「LATER IDEA」).

## 근거
G1 · M7 · M18(메인 — 보고). M7 이 가리키는 TRD 리뷰 #4 · #8.

## 영향 / 불변식
- 프라이밍 글을 고치는 자리는 `builtin\` 의 지침 파일 하나다 — 코드에 다시 두지 않는다.
- 「기본」 을 떼면 프라이밍과 Engram 통로 설정(`allowedMcpServers` — S25-V)이 함께 빠진다 — 떼기 확인 문구가 그것을 말한다(R32 · `DetachDefaultConfirm`).
- 옛 길(`NoopLaunchKits` 의 `priming_file`)은 걷는 때가 정해질 때까지 남는다 — Noop 회귀 골든(argv 바이트 같음)이 그것에 기댄다(§2-4 2).
- **확인 필요(`/adr link` 때)**: ADR-0099(결정 4 — 이미 ADR-0211 이 부분 폐기) · ADR-0100(배포판 조립) · ADR-0211 · ADR-0215 가 `prompts/agent-priming.md` 경로나 프라이밍 배달을 가리킨다. 이 초안이 그 조항까지 바꾸는지 판정하지 않았다.

# ADR-NNNN (S25-G): 프리셋 · 라이브러리는 데몬이 소유하는 에셋이고 클라이언트가 요청해 읽는다

- 상태: 제안 (2026-10-31, 근거: 사용자 결정 메모 53 · 74 · 76 · 99(2026-10-14) · R7 / G36 · G22-RESOLVED · G32)
- 관련: **ADR-0061 폐기**(남은 조항 — 이미 ADR-0291 이 부분 폐기) · **ADR-0070 부분 폐기**(프리셋 이름 `Preset.name` 부분) · S25-A(crate 자리) · S25-B(루트 하나) · S25-D · ADR-0029(데몬이 유저 데이터 단일 소유) · ADR-0264(옛 데이터는 버린다) · ADR-0291 · 메모 58(기계 쪽 = 데몬 · 보는 쪽 = 클라이언트) · TRD §1-1 · §1-12 · §7 1

## 맥락
옛 「프리셋」 은 작업 폴더 책갈피였다(ADR-0061 — 데몬 `presets.json` · `Preset{id, cwd}` · CRUD 뒤 전 연결 방송 / ADR-0070 — `Preset.name` 표시명). S25 의 프리셋은 지침 · 스킬 · 설정 · 다른 프리셋을 묶는 에셋이라 이름이 겹친다(메모 43).

## 결정
1. 프리셋은 라이브러리 폴더 안의 YAML 파일이다 — 스킬 · 지침과 같은 자리의 에셋(메모 74 · 76). 라이브러리 폴더는 하나다(S25-B).
2. 데몬 프로세스 안 asset-library 가 단독으로 읽고 쓴다(자리 = S25-A). 클라이언트는 디스크를 읽지 않는다.
3. 요청형: 클라이언트가 자기 동작(슬롯 열기 · 포커스 · 새로 고침 · 폴더 바꿈)에 요청하고, 데몬은 훑어 그 클라이언트에만 답한다 · 에이전트 실행 전 다시 확인한다. 감시(notify) · 구독 · 방송 · 보이는 동안 주기 폴링이 없다(메모 99).
4. 데몬 쪽 기능(명령 · CLI)은 늘 켜져 있다(G22-RESOLVED · S25-D).
5. 옛 `presets.json` · 옛 프리셋 wire · 프리셋 팔레트 슬롯은 걷는다 — 옛 데이터는 묻지 않고 버린다(G32 · M26 · ADR-0264).

## 거부한 대안
- **셸이 라이브러리를 훑는다** — 클라이언트 디스크 읽기 금지(PRD 불변 제약)이고, 원격 데몬(나중)에서 성립하지 않는다(TRD §1-1).
- **notify 감시 + 방송** — 사용자 「화면 보고 있는 동안 바로 보여줄 필요 없음」(메모 99 · 조사 `docs/research/library-folder-change-sync-survey-2026-10-14.md`). 요청형은 원격 · 모바일 클라이언트에도 선다 — 모든 계기가 클라이언트 동작이다(메모 99). 나중 감시는 덧붙일 수 있다(TRD §1-12).
- **프리셋을 내부 목록으로**(옛 `presets.json` 꼴) — 다른 사람에게 나눠 줄 때 폴더를 건네므로 프리셋이 함께 가야 한다(메모 53 · 74).

## 근거
사용자 결정 메모 53 · 74 · 99(2026-10-14) · 메모 58 의 나눔 규칙 · TRD §1-1.

## 영향 / 불변식
- ADR-0061 의 남은 조항(데몬 `FilePresetStore` · `PresetRegistry` · 프리셋 wire · 방송 · `Preset{id, cwd}`)과 ADR-0070 의 `Preset.name` 부분이 폐기된다. ADR-0070 의 `AgentProfile.display_name` 부분은 이 초안이 다루지 않는다(§7 1 은 프리셋 이름 부분만 꼽는다).
- **확인 필요**: ADR-0291 의 `presets.json` 조항(R6 상한 · R9 손상 사본 · R12 임시 이름 · R17 읽기 전용 모드)이 사문화된다 — `/adr link` 때 판정.
- 라이브러리 목록 변화를 클라이언트에 밀어 보내는 길을 만들지 않는다.

# ADR-NNNN (S25-H): 참조 = 라이브러리 루트부터의 `/` 경로 한 꼴 + 기본 제공 `engram:/`

- 상태: 제안 (2026-10-31, 근거: 사용자 결정 메모 101–103(2026-10-15 「ㅇㅇ 지정한 폴더로 확정」) · PRD R3 · Δ1)
- 관련: S25-B · S25-M(자리 = 정체) · TRD §1-2 `LibPath` · §7 2 · 조사 `docs/research/preset-asset-reference-base-survey-2026-10-14.md`(+ 2026-10-15 덧붙임)

## 맥락
프리셋 안의 참조(스킬 · 지침 · 설정 · 다른 프리셋)를 어떤 꼴로 적나.

## 결정
1. 참조 = 라이브러리 맨 위부터의 `/` 경로 한 꼴(예 `스킬/리뷰/review`) · 범위 제한 없음(R3).
2. `LibPath` 규칙: UTF-8 · 구분자는 `/` 만 · 앞뒤 `/` 없음 · 빈 칸 · `.` · `..` · `\` · `:` · 제어 문자 없음. 루트가 하나라 루트 접두가 없다(S25-B).
3. 기본 제공 에셋 = 라이브러리 밖의 고정 가짜 경로 `engram:/…`(Δ1). `LibPath` 가 `:` 를 받지 않아 둘이 섞이지 않는다.

## 거부한 대안
- **프리셋 파일 기준 상대**(`./` — Claude Code 플러그인 · Compose · Cargo 꼴) — 파일이 묶음 안에 사는 경우에 맞고, 여러 프리셋이 나눠 쓰는 공유 라이브러리엔 안 맞는다(메모 103 (a) · PRD R3).
- **이름 참조**(Claude Code 플러그인 의존 · Continue `owner/name`) — 범위가 분명한 네임스페이스 안에서만 선다. 폴더 브라우저에선 다른 폴더의 같은 이름이 흔하다(메모 103 (b) · PRD R3).
- **고정 ID 파일**(Unity · Godot) — 무거운 엔진 모델이고 바깥 이동에 깨진다(메모 103 (c)).
- **URI 꼴**(`lib://업무/...`) — URL 호스트 정규화가 비 ASCII 라이브러리 이름을 망가뜨린다(메모 126 — 세션이 기각 · 사용자 확인 기록 없음).

## 근거
사용자 이유(메모 102): 스킬은 여러 프리셋이 나눠 쓴다(다대다) — 한 프리셋 옆에 두면 다른 프리셋이 둘 자리가 없다 · 프리셋이 프리셋을 품는다 · Engram 은 폴더 브라우저라 항목의 정체는 자리다. 브라우저 꼴 피어 확인(Obsidian 볼트 루트 경로 등 — 조사 덧붙임 2).

## 영향 / 불변식
- 검증 · 디스크 경로 바꾸기 · 이동 때 접두 바꾸기는 `LibPath` 타입 하나가 맡는다(`relative-path` 감쌈 — TRD §1-2).
- 여러 루트를 다시 열면 새 루트에만 접두를 붙인다(S25-B 결정 6).

# ADR-NNNN (S25-I): 실행 재료는 포트로 넘긴다 — 해석은 asset-library, 플래그 번역 · 백엔드 설정 지식은 backend

- 상태: 제안 (2026-10-31, 근거: 메인 결정 M2 · M16 · M18(보고 — 사용자 이의 가능) · TRD 리뷰 #2 · #3 · CLAUDE.md 「백엔드 확장」)
- 관련: ADR-0004(백엔드 지식 격리) · S25-A · S25-F · S25-J · S25-K · TRD §1-4 포트 표 · §1-5 · §7 3

## 맥락
에이전트를 띄울 때 붙은 프리셋을 펼쳐 지침 · 스킬 · 설정을 CLI 플래그로 바꿔 싣는다. 펼치기 · 플래그 · 백엔드마다 다른 설정 형식을 누가 아나.

## 결정
1. 실행 재료 포트 `LaunchKitSource`(`check` · `prepare` · `release`)는 agent 가 정의하고 asset-library 서비스가 직접 구현한다. manager 가 부른다.
2. 플래그 번역은 backend `materialize`(`backend/claude/launch.rs` · `backend/codex/launch.rs` — 플래그 지식은 이 둘뿐).
3. 백엔드마다 다른 설정 지식(스키마 출처 · CLI 판 확인 · 원문 → JSON · claude 합침 · 모르는 키 처리 · codex 스킬 형식 · 명령줄 가드)은 agent `backend` 의 설정 검사 포트 하나에 모은다(M18). 내려받기는 데몬이 꽂는 fetch 포트로.
4. `check` 에 실행 출처 인자가 없다(M16 — 다음 주제가 더한다) · `prepare` 에 priming 인자가 없다(S25-F).

## 거부한 대안
- **manager 가 프리셋을 해석** — 사유: **사용자에게 받을 것**(§7 3 에 거부로만 적혀 있다).
- **backend 가 라이브러리를 읽음** — 사유: **사용자에게 받을 것**(같음).
- **`ControlEndpoint` 에 칸 덧붙이기** — 사유: **사용자에게 받을 것**(같음).
- **설정 검사 지식을 라이브러리(`validate.rs`)에** — TRD 리뷰 #2 · #3 이 걷어 backend 포트로 옮겼다(M2). 그대로면 crate 분리 판정의 조건이 서지 않는다(판정표 결론 — S25-A).

## 근거
CLAUDE.md 「백엔드 확장」(백엔드 전용 코드는 한 곳 `backend` 에 모은다) · M18.

## 영향 / 불변식
- 플래그 · 백엔드 설정 형식 지식이 asset-library 나 manager 로 새면 위반이다. 새 백엔드는 `materialize` 와 설정 검사 포트 구현을 늘린다.

# ADR-NNNN (S25-J): claude 실행 재료 = 합친 지침 파일 + `--system-prompt-snapshot off` + `--plugin-dir` 정션 + 합친 `--settings` 하나

- 상태: 제안 (2026-10-31, 근거: TRD 결정 T7(확정 2026-10-18 — 추천 그대로) · T10(사용자 2026-10-18) · R35 · 실측(TRD §1-5 표 · §6-1))
- 관련: S25-I · S25-F · S25-V · ADR-0109 결정 9 · TRD §1-5 「backend 번역」 · §7 4

## 맥락
claude 두 모드(JSON · 터미널)에 프리셋 재료를 어떤 플래그로 싣나.

## 결정
1. 지침: 실리는 순서로 합친 파일 하나 → `--append-system-prompt-file`(지금 프라이밍 자리를 대신). 실 재료일 때만 `--system-prompt-snapshot off`(이어받기에도 새 글).
2. 스킬: 휘발 폴더 `engram\skills\<이름>` = 라이브러리 스킬 폴더로 가는 디렉터리 정션 → `--plugin-dir <휘발>\engram` → 이름 `engram:<스킬>`.
3. 설정: 붙인 순서로 합친 claude 원문 → 휘발 `settings.json` 하나 → `--settings` 하나(S25-V).
4. 모델은 따로 싣지 않는다 — 원문의 `model` 키가 `--settings` 로 간다(R35).

## 거부한 대안
- **스킬을 `--add-dir` 로** — 접두가 없어 네이티브 스킬과 이름이 겹치면 승자를 모른다(T7). 고른 쪽은 사용자 `~/.claude/skills` 와 안 섞이고 적재가 실측됐다(T7).
- **`--settings` 여럿** — 두 번째 `--settings` 의 동작이 문서에 없고 재지 않았다(§7 19).

## 근거
- claude 2.1.284 `--help`: `--plugin-dir`(반복 가능) · `--settings <file-or-json>`(한 번 꼴) · `--system-prompt-snapshot <on|off>` 있음(TRD §6-1 — 확실).
- 플러그인 폴더 적재 = 실측 확실 · 정션 따라가기 = 미측 · snapshot off 로 이어받기에도 새 글 = 실측 확실 · 같은 글이면 캐시 손해 없음 = 실측(TRD §1-5 표).

## 영향 / 불변식
- 정션 따라가기는 미측이다 — 해당 단계에서 잰다. Noop 재료는 지금 argv 를 바이트 그대로 낸다(S25-V).

# ADR-NNNN (S25-K): codex 실행 재료 — JSON 은 developerInstructions · extraRoots, 터미널은 「기본」 프라이밍과 설정 `-c` 만

- 상태: 제안 (2026-10-31, 근거: 사용자 결정 P4-FINAL(2026-10-20 「프리셋은 베이스때문에 무조건 들어가야겠네. 그럼 안에 스킬이나 그런 지시서가 있을때 경고 띄우면 될듯」) · P7AC · G28 + 메인 M8 · M13 · M19 · M20(보고))

codex 는 JSON(app-server)과 터미널 모드의 지침 · 스킬 채널이 다르다. 터미널은 프로세스마다 스킬 폴더를 줄 길이 없다(PRD R37 · 조사).

## 결정
1. **JSON**: 새 대화 = `thread/start.developerInstructions` · 스킬 = 같은 정션 폴더를 `skills/extraRoots/set`(프로세스마다 · 안에 든 프리셋 속 스킬까지 — M13) · 이어받기 = 지침 해시가 지난 적용값과 다를 때만 첫 턴 `additionalContext`(실험 API — T6) · codex 가 못 싣는 스킬 형식 = 「오류」 막힘(새 범주 없음 — P7AC).
2. **터미널**: 「기본」 의 프라이밍(지금 길 `-c developer_instructions=`) + 프리셋 설정 codex 칸 `-c` 줄만 싣는다. 프리셋 지침 · 스킬(공통 · codex 꼬리표 모두)은 싣지 않는다.
3. 터미널에서 빠진 지침 · 스킬은 실행 성공 답의 알림 목록 `notices` 에 이름을 싣는다 — 호출자(CLI 출력 · 화면)에게만, 띄운 에이전트에는 아무것도 보내지 않는다. 문구는 사실만 · 의도된 동작이라 적고 해결책을 권하지 않는다(G28 — 마지막 문구는 구현 때 사용자에게 보인다).
4. 작업 폴더 · `~/.codex` 에 아무것도 쓰지 않는다.
5. 설정 `-c` 줄 = 패스스루 뒤 · 우리 덮어쓰기 앞 · 명령줄 가드 · 길이 예산에 걸리면 막힘(M8).

## 거부한 대안
- **터미널 작업 폴더에 늘 생성 지침 파일 + `.agents\skills` 정션**(2026-10-18 결정) — 같은 폴더 codex 끼리의 경합 · 복제본 막힘 · 정리 없음(리뷰 #1 · P4 로 걷음).
- **에이전트별 프로필 `-p` 로 지침만**(P4) — 「codex 가 지원하면 나중」 의 조사로 남겼다(`codex-instruction-channels-2026-10-20.md`).
- **터미널엔 프리셋을 아예 안 싣기**(P4-REVISED) — 「기본」 때문에 들어가야 한다(P4-FINAL 사용자 말).
- **못 싣는 스킬에 고치기 단추 · 「고치고 실행」 모달**(P7A) — 사용자 「너무 요란한데?」 · 기존 막힘 길로(P7AC).
- **알림 문구에 해결책(「JSON 모드를 쓰세요」)을 넣기**(P4-FINAL 의 첫 문구) — 나쁜 문구가 LLM 이 그 파일을 스스로 읽어 넣게 만들 수 있다는 사용자 걱정으로 사실만 남겼다(G28).
- **`CODEX_HOME` 바꾸기 · 로컬 플러그인 설치** — 사유: **사용자에게 받을 것**(§7 5 에 거부로만).
- **사용자 폴더면 만들지 묻고 기억**(옛 R37 대답) — 2026-10-18 사용자 결정으로 걷었다. 사유: **사용자에게 받을 것**.

## 근거
- 실측: `developerInstructions` = 확실 · `extraRoots` = 가능성 높음 · `additionalContext` = 실험 API(TRD §1-5 표).
- 사용자 결정 P4-FINAL · P7AC · G28.

## 영향 / 불변식
- 알림은 경고 범주가 아니다(S25-Y). codex 터미널 알림은 P4-FINAL 의 사용자 예외다.
- 터미널에 지침 · 스킬을 싣는 길은 codex 가 프로세스마다의 지침 채널을 지원할 때 그 조사에서 다시 연다.

# ADR-NNNN (S25-L): 편집 = 데몬이 최신 파일에 적용하는 연산 — 판 확인은 순서 바꾸기만

- 상태: 제안 (2026-10-31, 근거: 메모 41 · 118(바로 저장 · 저장 단추 없음) + 메인 M21 · M24-8 · M25(보고))
- 관련: S25-I · TRD §1-4 `edit.rs` · §1-7 · §7 6

## 맥락
프리셋 편집(붙이기 · 빼기 · 순서 · 꼬리표)을 누가 어떤 순서로 적용하나 — 클라이언트가 여럿일 수 있고 파일은 바깥에서도 바뀐다.

## 결정
1. 프리셋 편집(`add` · `remove` · `reorder` · `preset.setBackend`)은 데몬이 「최신 파일 읽기 → 연산 → 원자적 쓰기」 로 적용한다. 클라이언트엔 초안 · 저장 단추가 없다(바로 저장 — 메모 41 · 118).
2. 판 확인은 `reorder` 만 — `baseRev` 가 다르면 `CONFLICT`. 판 = 안정된 내용 해시(M21 — 데몬 재시작 뒤 첫 순서 바꾸기의 헛 `CONFLICT` 를 고침).
3. `add` · `remove` 는 낡은 판이어도 멱등이다 — 낡은 화면이 보낸 「빼기」 도 지금 파일에서 그 경로를 뺀다(알려진 동작 · 받아들임 — M24-8).
4. 에이전트 프리셋 붙이기 · 떼기 · 순서는 검증 뒤 프로필 편집 포트로 간다(M18). 에이전트 `baseRev` = `default_preset` + `presets` 순서의 안정 해시(M25).

## 거부한 대안
- **클라이언트 초안 + 저장 단추** — 사유: **사용자에게 받을 것**(메모 41 · 118 은 바로 저장을 결정으로만 적는다).
- **전부 판 확인** — 사유: **사용자에게 받을 것**(M24-8 은 판 확인 없음을 받아들인다고만 적는다).

## 근거
M21 · M24-8(PRD 리뷰 #23 뒤 절반) · M25.

## 영향 / 불변식
- 편집은 늘 데몬이 그 순간의 파일에 적용한다 — 클라이언트가 파일 전체를 다시 써 보내는 길을 만들지 않는다.

# ADR-NNNN (S25-M): 파일 조작 = 계획 → 실행 → 참조 고침, 진행 기록 없이 순서만 (Obsidian 꼴)

- 상태: 제안 (2026-10-31, 근거: 사용자 결정 G38(2026-10-31 「일단 이건 이대로 두고 나중에 생각하자」) · P3 · P5 · G36 + 메인 M4 · 조사 `docs/research/multi-file-rename-crash-safety-practice-2026-10-31.md`)
- 관련: S25-B · S25-H · S25-N · S25-W · PRD R17 · R19 · TRD §1-4 흐름 ④ · `store.rs` · §7 7 · T-74

## 맥락
앱 안 이동 · 이름 바꾸기는 파일 하나와 그것을 가리키는 여러 프리셋 · 에이전트를 함께 고친다. 중간에 끊기면 어떻게 되나.

## 결정
1. 이동 · 이름 바꾸기 · 다시 연결 = 계획 → 실행 → 참조 고침. 순서 = 파일 이름 바꾸기 → 참조하는 프리셋을 하나씩 고침 → 에이전트. 파일 쓰기는 하나하나 원자적(임시 + 바꿔 넣기).
2. 진행 기록(일지)이 없다. 중간에 끊기면 일부 참조가 옛 경로를 가리켜 「찾을 수 없음」 이 되고, 다시 연결 한 번이 그 옛 경로의 참조를 전부 고친다(R19 · S25-N). 부팅 때는 남은 임시 파일만 쓸어 낸다 — 정리이지 일지가 아니다.
3. 탐색기 규칙 — 덮어쓴 파일만 `.trash` 로(P5). 루트 안 이동은 어디로든(S25-B).
4. 삭제는 참조를 고치지 않는다 — 자리 = 정체(P3 · M4). 삭제 = 루트 안 `.trash`(S25-W).

## 거부한 대안
- **의도를 적어 두는 조작 기록 + 부팅 때 마저 끝내기**(옛 `library-ops\` 일지 롤포워드) — 사용자 「일단 이건 이대로 두고 나중에 생각하자」(G38) · 그런 피어를 못 찾았다(조사 2026-10-31).
- **삭제 때 참조를 휴지통 경로로 고치기**(리뷰 #5) — 사용자 「따로 처리를 해야됨?」(2026-10-20 · P3). 되살리면 경로로 풀린다(P3 · M4).
- **파일마다 고정 정체(사이드카 `.meta` · 파일 안 id · NTFS 파일 id)를 다시 연결 후보로** — 사용자 「나중에 생각하자」(G38 · T-74). 하면 R19 「후보 제안 없음」 을 다시 연다(G38).
- **영구 삭제** — S25-W 의 같은 대안 사유(「영구 삭제 + 센 확인 — 에이전트 호출엔 답할 사람이 없다」)를 본다.
- **바깥 정리 + 이름 다시 연결만**(메모 68 — 앱 안 이동 · 이름 없음) — 사유: **사용자에게 받을 것**(§7 7 에 거부로만 · P1 이 앱 안 이동 · 이름 · 삭제를 2판에 넣었다).

## 근거
사용자 결정 G38 · P3 · P5 · 조사(2026-10-31).

## 영향 / 불변식
- 일지를 되살리려면 G38 을 다시 연다. 끊긴 조작의 회복 길은 다시 연결 하나다.
- 공통 뼈대(계획 → 실행 → 참조 고침)는 이동 · 이름 바꾸기 · 다시 연결만 쓴다.

# ADR-NNNN (S25-N): 다시 연결 = 하나를 고르면 나머지를 이름으로 잇는다 — 훑기는 후보를 제안하지 않는다

- 상태: 제안 (2026-10-31, 근거: 사용자 결정 B11(2026-10-19 「ㅇㅇ 그게 더 자연스러운것같네」 — D10 해결) · 관행 조사 2026-10-18 · P1 · 메인 M14)
- 관련: PRD R19 · S25-M · 조사 `docs/research/relink-and-error-popup-practice-2026-10-18.md` · §7 8

## 맥락
가리키던 파일이 사라진 참조(바깥에서 옮겼거나 조작이 끊겨서)를 어떻게 다시 잇나.

## 결정
1. 가리키던 것이 없는 줄 = 「찾을 수 없음 · [다시 연결] ×」. [다시 연결] = 같은 종류로 거른 검색 팝오버 · 옛 이름 미리 채움(우리 편의 · 피어 근거 없음) · 열 때 옛 상위 폴더를 다시 읽는다(M14).
2. 사용자 · LLM 이 파일 하나를 고르면 묻지 않고 나머지를 잇는다 — (a) 같은 옛 경로를 가리키는 모든 참조 (b) 옛 폴더가 같았던 다른 찾을 수 없음 항목 중 새 파일의 폴더에 같은 이름이 있는 것(같은 종류만 — M14). 「N개 더 찾아 연결함」 으로 알린다.
3. 훑기 때 후보를 제안하지 않는다 · 고르기 전엔 아무것도 잇지 않는다. 1판부터(P1).

## 거부한 대안
- **이름만 보고 저절로 적용**(메모 68) — 사용자가 찾기를 시작하기 전에 이름으로 다시 연결하는 피어가 없다(§7 8).
- **훑기 때 같은 이름 후보 하나를 제안하고 확인 전까지 막힘 「다시 연결 확인 대기」**(2026-10-18 D10 꼴) — 사용자 「ㅇㅇ 그게 더 자연스러운것같네」(2026-10-19) · 피어는 첫 하나를 손으로 찾게 한다.
- **항목마다 하나씩 고르기** — 관행 = 「N개 더 찾음」(§7 8).
- **리다이렉터 파일** — 사유: **사용자에게 받을 것**(메모 68 은 「No redirector files」 를 결정으로만 적는다).
- **루트를 넘는 다시 연결** — 사유: **사용자에게 받을 것**(§7 8 에 거부로만).

## 근거
관행 조사(Premiere 「미디어 연결」 · After Effects · Resolve · Blender — 첫 하나는 사용자가 손으로 찾는다) · 사용자 결정 B11.

## 영향 / 불변식
- 다시 연결은 끊긴 파일 조작의 회복 길이다(S25-M). 훑기 후보 제안을 더하는 것은 G38 의 「파일마다 고정 정체」 재론과 함께 연다.

# ADR-NNNN (S25-O): 백엔드는 에이전트 값 — 설정은 백엔드별 원문 칸만, 모델 충돌 검사 없음, 기본 제공은 「기본」 하나

- 상태: 제안 (2026-10-31, 근거: 사용자 결정 메모 199 · 201(2026-10-18 「그건 에이전트가 골라야지」 · 「그냥 고정해. 백엔드는.」 · 「어 고정해.」))
- 관련: S25-J · S25-K · PRD R35 · D4 · D5 · §7 11

## 맥락
옛 메모 7(2026-10-10~12)은 에이전트를 빈 껍데기로 두고 설정 에셋이 백엔드 · 모델을 고르게 했다(둘이면 오류 · 없으면 실행 안 함 · 바꾸면 새 대화).

## 결정
1. 백엔드는 만들 때 고정되는 에이전트 값이다 — 바꾸려면 새 에이전트(메모 199). 모드(JSON · 터미널)도 같다(메모 201 · D5).
2. 설정 파일 = `description` + 백엔드별 원문 칸(`claude:` · `codex:`)만. 정식 `backend` · `model` 칸이 없다 — 모델도 원문 안이다. 원문은 에이전트 백엔드와 맞을 때만 실린다.
3. 모델 충돌 검사가 없다 — Engram 은 원문을 해석하지 않는다.
4. 기본 제공 프리셋은 「기본」 하나다.

## 거부한 대안
- **설정이 백엔드 · 모델을 정함**(메모 7) — 사용자 「그건 에이전트가 골라야지」 · 「설정을 claude codex 둘다 입력되게 해놓은건 특정 모델의 에이전트 설정되면 설정을 스위칭 하라고 해놓은거잖아. 근데 model을 왜 에이전트가 골라」(메모 199).
- **기본 제공 백엔드 프리셋**(풀 때 양보 · 바꾸기 — 옛 후보 「사용자 백엔드가 있으면 사용할 수 없음」) — 백엔드가 에이전트 값이라 필요가 없다(PRD D4 「백엔드가 에이전트 값이라 백엔드 프리셋이 필요 없다」).
- **`model` 둘 = 충돌** — 검사하려면 CLI 마다 대조표를 갱신 때마다 고쳐야 한다(메모 199 · 사용자 「대조표? 매번 업데이트 받아서 비교된다는거잖아. 그게 아니라 이번에 적용하고 나중에 또 대응해야되면 빼는게 맞고」).

## 근거
사용자 결정 메모 199 · 201(2026-10-18).

## 영향 / 불변식
- 프리셋 편집은 에이전트 백엔드를 바꾸지 않는다 — 그래서 편집 답에 영향받는 에이전트 목록을 싣지 않는다(TRD §1-7).
- 같은 백엔드 칸에 모델이 둘 들면 CLI 가 하는 대로 둔다.

# ADR-NNNN (S25-P): 보는 쪽 상태(번호별 보기 · 접고 펴기)는 셸이 갖고, 키에 데몬 신원을 넣는다

- 상태: 제안 (2026-10-31, 근거: 메모 58 나눔 규칙(사용자가 기록에 동의) · TRD §1-1 · §7 12)
- 관련: S25-X · S25-E(슬롯 안 보기 상태 저장 가름 — G23-NOTE) · ADR-0035 · ADR-0057 · CLAUDE.md 「LLM-우선 제어」 · TRD §5-4

## 맥락
라이브러리 1~4 의 번호별 보기 상태(마지막 폴더 · 칸 폭 · 트리 펼침 · 「기본 제공 보기」)와 접고 펴기 상태를 어디 둘지.

## 결정
1. 보는 쪽 상태는 셸이 권위로 갖는다(`state.json`). 키에 데몬 신원을 넣는다.
2. 컬렉션(즐겨찾기)은 이번 판에 없다(G34). 슬롯 안 보기 상태를 패키지 저장소로 옮길지는 클라이언트 단계에서 정한다(G23-NOTE · S25-E).

## 거부한 대안
- **데몬에** — 보는 쪽 상태다. 클라이언트가 여럿이면 주인이 없다(메모 58 「레이아웃을 데몬에 두지 않는다」 와 같은 이유 — TRD §1-1).
- **웹뷰 `localStorage` 에** — 창(웹뷰)마다 갈려 팝아웃 창의 라이브러리 슬롯과 메인 창 편집 칸이 원천을 나누지 못하고, LLM 이 셸 명령으로 닿지 못한다(TRD §1-1).

## 근거
메모 58: 에이전트가 도는 기계에 묶인 것 = 데몬 · 보는 사람에 묶인 것 = 클라이언트.

## 영향 / 불변식
- 클라이언트 단계가 §1-9~§1-11 을 다시 확정한다(§5-4) — 이 초안의 번호는 그 뒤로 미뤄도 된다.

- 상태: 제안 (2026-10-31, 근거: 메인 M21(보고) · CLAUDE.md 「LLM-우선 제어」 · TRD §3 · §7 13)

# ADR-NNNN (S25-V): 숨은 settings 조각을 없앤다 — claude 원문은 붙인 순서로 `--settings` 파일 하나에 합친다

- 상태: 제안 (2026-10-31, 근거: 사용자 결정 T10(2026-10-18 「프리셋으로 해줘. 사실 감추는 설정이 있으면 안되지.」 · 「이어붙이기 진행」))
- 관련: **Amends ADR-0109 결정 9**(조각 부분 — 아래) · ADR-0099(mcp-config 수명주기) · S25-F · S25-J · PRD R32 · TRD §1-2 · §1-5 표 · §3 합침 규칙 · §7 19

## 맥락
지금 제어 채널은 스폰마다 `{"allowedMcpServers":[{"serverName":"engram"}]}` 단일 키 조각 파일을 `--settings` 로 싣는다(ADR-0109 결정 9 · `control/mcp_config.rs`). S25 는 프리셋의 claude 원문 설정도 `--settings` 로 싣는다.

## 결정
1. 숨은 settings 조각이 없다. `allowedMcpServers:[{serverName:"engram"}]` 와 `DISABLE_AUTOUPDATER` 는 기본 제공 「기본」 의 claude 원문(`engram:/settings/default`)에 보이게 든다.
2. 붙은 프리셋(「기본」 포함)의 claude 원문을 붙인 순서로 휘발 폴더 `settings.json` 하나에 합쳐 `--settings` 하나로 싣는다. 합침 = 값은 나중 것 · 객체는 재귀 · 목록은 이어 붙이고 같은 값은 하나 · 키마다 다른 규칙 없음 · Engram 우선 규칙 없음. 합치는 쪽은 backend 설정 검사 포트(S25-I).
3. 실 재료면 제어 채널 조각(`ControlEndpoint.settings_file`)을 싣지 않는다. `NoopLaunchKits` 는 지금 그대로 싣는다(argv 바이트 같음).
4. `--mcp-config` 는 범위 밖이다(실행 인자 그대로 · 프리셋 아님).

## 바뀌는 조항 (ADR-0109 결정 9)
- 바뀜: 「조각은 `allowedMcpServers` 단일 키 유지(잡동사니화 금지 — 회귀 테스트로 고정)」 → 조각이 없고 그 키는 「기본」 원문으로 옮긴다. 「mcp-config 디렉토리 · 스윕 · revoke 수명주기에 동승」 → 합친 파일은 실행 재료 휘발 폴더(`daemon\run\launch\` — TRD §1-4)에 산다.
- 그대로: 「`--settings` = 파일 경로 주입(인라인 JSON 아님)」 과 그 사유(`cmd /c` 따옴표 붕괴).
- **원천에 없음(확인 필요)**: 「쓰기 실패는 warn+계속」 이 새 판에서 어떻게 되는지.
- Noop 길은 걷힐 때까지 결정 9 그대로 돈다.

## 거부한 대안
- **숨겨 주입하는 조각** — 사용자 「사실 감추는 설정이 있으면 안되지」(T10).
- **`allowedMcpServers` 는 Engram 값이 권위**(옛 추천 — 프리셋의 그 키는 버리고 경고) — 사용자가 숨은 설정 없음을 골랐다(T10).
- **목록 갈아 끼우기** — 사용자 「이어붙이기 진행」. 귀결: 뒤 프리셋이 `engram` 을 못 뺀다 — 받아들였다.
- **두 번째 `--settings`** — 동작이 문서에 없고 재지 않았다.
- **원문을 안 싣기** — 사유: **사용자에게 받을 것**(§7 19 에 거부로만).

## 근거
사용자 결정 T10(2026-10-18) · TRD §2-2 T10.

## 영향 / 불변식
- 「기본」 을 떼면 Engram 메시지 · 제어 통로가 빠질 수 있다(사용자 전역 설정이 `allowedMcpServers: []` 로 막을 때) — 떼기 확인 문구가 그것을 말한다(R32 · `DetachDefaultConfirm`).
- 합친 claude settings 도 검사한다 — 오류는 그것을 들인 나중 에셋 줄에 붙는다(M14).
- ADR-0109 의 앵커 `mcp_config.rs`(settings 조각)는 Noop 길에만 남는다.

# ADR-NNNN (S25-W): 삭제 = 라이브러리 루트 안 우리 숨은 `.trash` 로 옮긴다

- 상태: 제안 (2026-10-31, 근거: 사용자 결정 B8 / F9-confirmed(2026-10-19 「ㅇㅇ 우리 trash 폴더로해」) · G31(2026-10-30 「휴지통 경로 … 시스템에서 알아서 보내는게 맞는것같은데 고정경로로하고 나중에 변경경로로」) + 메인 M22(보고) · 조사 `docs/research/trash-unavailable-delete-practice-2026-10-19.md`)
- 관련: S25-B · S25-M · S25-AE · PRD R18 · TRD §1-1 · §1-4 `store.rs` · §6-5 1 · §7 20

## 맥락
라이브러리 항목을 지울 때 어디로 보내나. 사람 · LLM · CLI 가 다 지운다.

## 결정
1. 삭제 = 라이브러리 루트 안 숨은 `.trash` 로 옮긴다. 자리 = 시스템이 정한 고정 `<루트>\.trash\` — 바꿀 수 있는 자리는 필요가 생기면 나중(G31).
2. 같은 루트 안 rename 이다. 트리 · 목록 · 검색에서 숨긴다. 루트 자체는 못 지운다. LLM · CLI 삭제도 같은 곳으로 간다.
3. 루트가 git 작업 트리면 그 저장소의 `.git/info/exclude` 에 `.trash/` 를 더한다(로컬 · 커밋 안 함 — M22).
4. 비우기 · 영구 삭제 = S25-AE.

## 거부한 대안
- **삭제를 OS 휴지통으로**(platform 의 전용 STA 작업 스레드가 부르는 `IFileOperation` — 2026-10-18 까지의 후보) — 휴지통 대신 말없이 영구 삭제할 수 있고(Microsoft 문서 `FOF_WANTNUKEWARNING` — UI 없이 부르면 그 경고가 묻힌다 · 네트워크 드라이브 · 휴지통 없는 볼륨 · 용량 초과) · 비우기를 사람만으로 묶을 수 없다(탐색기 · 다른 도구가 비운다)(§7 20).
- **`trash` crate** — 같은 OS 휴지통 길에 셋째 `windows` 사본 · `CoInitialize` 실패 패닉(§7 20).
- **OS 휴지통을 못 쓰면 거절**(옛 F8(b)) — `.trash` 가 같은 볼륨 rename 이라 물음 자체가 사라졌다(결정 기록 F9-confirmed).
- **영구 삭제 + 센 확인**(VS Code 꼴) — 에이전트 호출엔 답할 사람이 없다(§7 20).
- **중앙 휴지통 한 곳** — 드라이브를 넘는 복사가 필요하다(G31 — 같은 볼륨 rename 이 빠르고 반쯤 옮긴 상태가 없다). ★이 사유는 여러 루트 시절(G25)에 든 것이다★ — 루트 하나(S25-B)에서도 그대로 서는지는 다시 보지 않았다.
- **바꿀 수 있는 휴지통 자리** — 필요가 생기면 나중(G31 「고정경로로하고 나중에 변경경로로」).

## 근거
사용자 결정 B8 · G31 · 조사(2026-10-19 — 앱 전용 `.trash` 선례 = Obsidian).

## 영향 / 불변식
- 그 밖의 `library.*` 는 `.trash` 아래를 가리키지 못한다(뒷문 막기 — S25-AE).
- 에이전트 자신의 `rm` · 파일 도구는 `.trash` 를 우회한다 — 받아들였다(P13).

# ADR-NNNN (S25-X): 번호별 보기 상태 = 셸 권위 + `libraryView.*` 셸 명령 — `Library{n}` 유일성은 레이아웃 관리자가 지킨다

- 상태: 제안 (2026-10-31, 근거: TRD §1-7 · §1-9 · §7 21 · CLAUDE.md 「LLM-우선 제어」)
- 관련: S25-P · ADR-0035 · ADR-0057(레이아웃 · 창 · 탭 · 슬롯은 백엔드 소유) · ADR-0055 · ADR-0064(`__engramCmd`) · TRD §5-4

## 맥락
라이브러리 1~4 의 보기 상태를 사람 몸짓과 LLM 이 같은 핸들로 바꾸게 하고, 같은 번호의 슬롯이 둘 생기지 않게 해야 한다.

## 결정
1. 번호별 보기 상태는 셸이 권위로 갖고 `libraryView.*` 셸 명령으로 바꾼다. 셸이 상태를 바꾸고 그 번호의 슬롯을 가진 창에만 `library-view:updated {number, state}` 를 쏜다. 화면은 사람 몸짓도 같은 명령으로 보내고 받은 상태를 그리기만 한다.
2. `Library{n}` 유일성은 레이아웃 관리자가 슬롯 내용을 쓰는 단일 길(`write_slot_content` — `set_slot_content` · 버스 `layout.setSlotContent` 가 지난다)에서 지킨다 — 같은 번호가 어느 창에든 있으면 `CONFLICT` · 복원은 같은 번호의 둘째부터 빈 슬롯 + 복원 경고 · 슬롯 옮기기는 통과. `slot.openUnique` 는 그 위의 편의(있으면 포커스)다.
3. 새 전역 핸들 · 웹뷰 레지스트리 명령을 만들지 않는다.

## 거부한 대안
- **웹뷰 레지스트리 명령** — 사유: **사용자에게 받을 것**(§7 21 에 거부로만).
- **열기 명령에서만 유일성** — 사유: **사용자에게 받을 것**(같음).

## 근거
CLAUDE.md 「LLM-우선 제어」 — 레이아웃 · 창 · 탭 · 슬롯은 백엔드 소유 · 기존 표면에 얹고 새 전역 핸들을 늘리지 않는다.

## 영향 / 불변식
- 슬롯 내용을 쓰는 길을 둘째로 만들면 유일성이 샌다.
- 클라이언트 단계 재확정 대상(§5-4).

# ADR-NNNN (S25-Y): 편집 칸 · 실행이 알리는 것은 충돌뿐이다 — 경고 범주가 없다

- 상태: 제안 (2026-10-31, 근거: 사용자 결정 2026-10-18 · B3(2026-10-19) + 메인 M19 · G28 · TRD §7 22)
- 관련: S25-K(codex 터미널 알림 — 사용자 예외) · S25-Z · S25-AA · PRD R22 · R51

## 맥락
편집 칸과 실행이 사용자 · LLM 에게 무엇을 알리나.

## 결정
1. 알리는 것은 충돌뿐이다 — 경고 범주가 없다. 충돌 줄 = 걸린 항목 전부 + 각자 온 길 · 실행 막힘 사유와 같은 줄.
2. 편집 칸 위 문제 목록(B3)은 그 줄들과 줄 상태(찾을 수 없음 · 오류)를 위에 모아 보일 뿐이고 경고 범주를 되살리지 않는다.
3. 막지 않는 알림 목록 `notices`(codex 터미널이 싣지 않은 것 · 이 백엔드에 안 실리는 흐린 줄 · 스키마 흐림 — M19 · G28)는 사실 알림이지 경고 범주가 아니다. codex 터미널 알림은 P4-FINAL 의 사용자 예외다.

## 거부한 대안
- **노랑 경고 줄**(「다음 실행은 새 대화」 · codex 크기 한도 올림 · 문맥 차지 비율 · 자동 다시 연결) — 어떤 편집이 새 대화를 부르는지 같은 규칙은 바뀔 수 있어 화면이 그것을 따라 계산하게 되고, 옛 대화는 옛 목록에 남아 잃지 않는다(사용자 이유 · 2026-10-18).

## 근거
사용자 결정 2026-10-18.

## 영향 / 불변식
- 새 경고 범주를 더하지 않는다. ★원천 어긋남 확인★ — codex 모르는 키는 ⚠ 이고 CLI 가 「경고 — <경로> · <키> · <이유>」 줄을 낸다(TRD §1-4 `validate.rs` · §1-7 — S25-Z). 이 결정과 어떻게 맞는지 원천이 말하지 않는다.

# ADR-NNNN (S25-Z): 설정 검사 = 프로세스 안에서 가볍게 — 문법 + 스키마, 읽을 때마다

- 상태: 제안 (2026-10-31, 근거: 사용자 결정 2026-10-18 · P10 · P10-ADD + 메인 M2 · M18 · TRD §7 23)
- 관련: S25-I · S25-Y · S25-AF · TRD §1-4 `validate.rs` · 실측 `docs/research/settings-asset-validation-spike-2026-10-17.md`

## 맥락
설정 에셋(claude 원문 JSON · codex `-c` 줄)을 언제 · 얼마나 검사하나.

## 결정
1. 프로세스 안에서 가볍게 — 문법(YAML) + 스키마, Engram 이 읽을 때마다.
2. 스키마가 아는 키의 타입 · 범위 오류 = 실행을 막는다.
3. 모르는 키 = claude 는 알리지 않는다 · codex 는 ⚠ 만(막지 않음). 가진 스키마가 설치된 CLI 보다 낡았으면 모르는 키는 흐림 「이 판 스키마로는 확인 못 함」(P10-ADD).
4. 스키마 = 배포판 한 벌 + 데몬이 뒤에서 갱신(캐시 = S25-AF). 실패하면 가진 것을 쓴다 · 스키마가 없어서 막는 일은 없다(P10).
5. 백엔드마다 다른 것(스키마 출처 · 판 읽기 · 원문 → JSON · 모르는 키 처리)은 backend 설정 검사 포트가 낸다(S25-I).

## 거부한 대안
- **실행 직전 CLI 검사**(`claude --settings … doctor` · `codex debug models`) — 사용자 「가볍게하는걸로하고 나중에 문제되면 차후에 고려하자」.
- **「모두 검사」 메뉴 · `library.validate`** — 새로 고침이 덮는다(§7 23).
- **편집기 포커스 때 다시 읽기** — 사용자 「너무 복잡하게 할 필요는 없는것같아」.

## 근거
사용자 결정 2026-10-18 · P10 · 실측 스파이크(2026-10-17).

## 영향 / 불변식
- 검사는 실행을 기다리게 하지 않는다 — 스키마 받기는 락 밖 뒤에서 한다(P10).
- 원천 어긋남 확인: S25-Y 영향 참조(codex ⚠ 와 「경고 범주 없음」).

# ADR-NNNN (S25-AA): 실행 막힘 = 한 범주 · 요청 한 번 · 구조 있는 오류 답 — 사람이 낸 실행만 막힘 창을 띄운다

- 상태: 제안 (2026-10-31, 근거: 사용자 결정 2026-10-18 · G13(2026-10-20 「저거 띄우면 되는거 아니냐」 · 「단독 슬롯으로되야함. 왜냐하면 창 크기에 막히면 안되니깐」) · G13-AMEND · G15 · P4-FINAL · P11 + 메인 M15 · M19 · M21)
- 관련: S25-Y · S25-K · CLAUDE.md 「LLM-우선 제어」 · ADR-0283(창 만들기는 `WebviewEnv::finish`) · TRD §1-3 8 · §1-5 (가) · §1-9 · §1-10 · §7 24 · 조사 `docs/research/launch-blocked-popup-navigation-practice-2026-10-20.md`

## 맥락
붙은 프리셋에 문제가 있으면 실행을 막는다. 누가 실행하든 같은가, 어떻게 알리나.

## 결정
1. 실행 막힘 = 사유 넷의 한 범주(2026-10-19 「다시 연결 확인 대기」 · 2026-10-20 「codex 파일 사전 검사 실패」 를 걷음 — P4-FINAL). 누가 실행하든 막는다.
2. 실행 = 요청 한 번. 막힘 = 구조 있는 오류 답(`CommandError` 인자 칸 · 넓힌 wire 활성화 답 · CLI 는 0 아닌 종료 — G15 · M19).
3. 사람이 낸 실행(더블클릭 · 메뉴)이 막히면 그 에이전트의 프리셋 편집 칸을 에이전트 트리 줄 옆 따로 된 떠 있는 OS 창(막힘 창)으로 띄운다 — 주인 = main 창(전역 늘 위 아님 — M15) · × · Esc 로만 닫힌다 · 고치기는 그 안에서 · 라이브러리는 사용자가 파일로 갈 때만(G13-AMEND) · 슬롯 배지 · ⛔ 줄이 남는 기록.
4. LLM · CLI 실행은 창 없이 트리 ⛔ + 코드 + 인자.
5. 막힘 창의 그 밖 수명(여럿 · 다시 열기 · 트레이 등)은 다음 주제(P11).

## 거부한 대안
- **화면 실행만 막고 버스 · CLI 는 기본값으로 진행**(옛 Δg 갈래) — 사유: **사용자에게 받을 것**(§7 24 에 거부로만).
- **모달** — 관행상 모달은 심각한 · 앱 전체 오류에만 쓴다 · 사용자 「모달에 아니라 그냥 뜨는 팝업」.
- **에이전트 곁 비모달 카드에 막힌 항목 이유 + 링크 → 라이브러리**(2026-10-18 꼴) — 사용자 「저거 띄우면 되는거 아니냐」(2026-10-20)로 편집 칸 자체를 띄운다.
- **main 창 안에 띄우기** — 사용자 「단독 슬롯으로되야함. 왜냐하면 창 크기에 막히면 안되니깐」.
- **바깥 누름에 닫기** — 거기서 라이브러리를 열면 창이 사라진다(G13-AMEND · 관행 = 남는 패널 Unreal Compiler Results).
- **실행 앞 점검 명령 `agent.launchCheck` + 실행(요청 두 번)** — 앞 점검과 실 점검의 경합(G15) · 사용자 「패킷을 왜 두번보냄? 한번 보내고 실패하면 팝업 띄우는거고 아니면 실행하는거 아님?」 · M21 이 명령째 걷었다.

## 근거
사용자 결정 2026-10-18 · 2026-10-20(G13 · G15) · 관행 조사(2026-10-20).

## 영향 / 불변식
- `CommandError` 에 인자 칸이 생긴다(command crate 변경 — M19).
- 막힘 창이 서는지(테두리 없는 · 주인 main · 줄 옆 · 다중 모니터 · DPI)는 재지 않았다 — 해당 단계 앞에 재고 안 되면 멈추고 사용자에게 돌아간다(TRD §6-2).
- 막힘 창 부분은 클라이언트 단계 재확정 대상(§5-4).

# ADR-NNNN (S25-AB): 작업 폴더는 에이전트 값 — 대화 뒤 · 떠 있는 동안 잠근다

- 상태: 제안 (2026-10-31, 근거: 사용자 결정 2026-10-18 · D3 · P2-REVISED · 「ssi 박히잖아. 그게 있으면 못바꾸게」 · 「대화 뒤 잠금은 있어야지」)
- 관련: ADR-0226(첫 제출 래치 — 영속된 세션 id) · TRD §1-5 「작업 폴더 `cwd`」 · §8 · §7 25

## 맥락
에이전트의 작업 폴더를 어디서 정하고 언제 바꿀 수 있나.

## 결정
1. 작업 폴더 = 에이전트 값. 에이전트 슬롯 「작업 폴더」 칸 + `agent.setWorkspace {agent, cwd}` 로 바꾼다. 만들 때 폴더 선택(`cwd` 필수)은 지금 그대로.
2. 영속된 backend 세션 id 가 있거나(대화 뒤 — ADR-0226) 떠 있으면 바꿀 수 없다. 잠긴 까닭 문구는 둘(실행 중 · 대화함 — P2-REVISED).
3. 대화 전에만 바뀌므로 놓을 세션이 없다 — 세션 놓기 로직을 짓지 않는다.

## 거부한 대안
- **대화 뒤에도 바꾸고 다음 실행을 새 대화로 맞추기**(`launched_workspace` · `release_session_id` — §8 에 옮겨 둔 옛 설계) — 사용자 「대화 뒤 잠금은 있어야지」.
- **작업 폴더를 프리셋 부품으로** — 라이브러리 종류를 늘리지 않는다(D3 추천).

## 근거
사용자 결정 2026-10-18 · D3.

## 영향 / 불변식
- 경로 없는 생성 · 자동 경로 · 묶는 폴더 = 다음 주제(§8). 대화 뒤에도 바꾸는 길을 열면 거부한 대안 1 의 옛 설계를 다시 꺼낸다.

# ADR-NNNN (S25-AC): 상세 카드는 잘리지 않는다 — flip → shift → clamp

- 상태: 제안 (2026-10-31, 근거: D11 · 관행 조사 2026-10-18 · PRD R29)

## 맥락
부품 줄을 누르면 뜨는 상세 카드가 슬롯 · 창 가장자리에서 잘린다.

## 결정
1. 상세 카드는 어느 경우에도 잘리지 않는다 — flip → shift → clamp.
2. 에이전트 슬롯 = 슬롯 오른쪽 바깥(옆 슬롯 위로 겹침) → 왼쪽 바깥 → 창 안으로 당김. 라이브러리 1~4 = 오른쪽 칸 왼쪽 가장자리에 그 줄 높이로.

## 거부한 대안
- **창 끝에서 잘린 채 둠 · 뒤집기 없음**(메모 137) — 관행에 맞춰 뒤집는다(§7 26 · PRD R29).
- **기준 요소를 먼저 덮기** — 마지막 수단이다(관행 — Floating UI `flip()` 다음 `shift()` · Radix · MUI · NSPopover 같은 순서 — PRD R29).

## 근거
관행 조사(2026-10-18 — Floating UI 확인함 · Radix · MUI · NSPopover).

# ADR-NNNN (S25-AE): 휴지통 비우기 · 영구 삭제는 사람만 — 셸 전용 버스 명령, 원칙에 예외 목록을 더하지 않는다

- 상태: 제안 (2026-10-31, 근거: 사용자 결정 F9 / B8(2026-10-19 「휴지통으로 가되 휴지통 비우기를 llm으로 쏘지 못하게 막자는거지」) · G9 · G11 · G12(2026-10-20) · G21(2026-10-29) · P13 + 메인 M6 · M24-7 · M26)
- 관련: S25-W · S25-Q · CLAUDE.md 「LLM-우선 제어」 · PRD R18 · TRD §1-4 `store.rs` · 흐름 ④ · §6-5 2 · §7 28

## 맥락
삭제는 `.trash` 로 가서 되살릴 수 있다(S25-W). 비우기 · 영구 삭제는 되돌릴 수 없다 — 에이전트가 잘못 부르면 잃는다.

## 결정
1. 휴지통 비우기 · 영구 삭제는 사람만 한다 — 셸 전용 버스 명령 `library.emptyTrash {items?}`. 데몬은 제어 라우트로 온 것을 거절한다. 에이전트 명령 표 · 프라이밍 · `engram help` 에 없다. 새 wire 변형이 없다(M6 · M26).
2. 원칙 「LLM-우선 제어」 에 예외 목록 · 장치를 더하지 않는다. LLM 이 바깥 도구(WS · `rm`)로 우회하는 것은 받아들인다(G21 · P13).
3. 삭제(→ `.trash`) · 휴지통 보기 · 되살리기(`library.restore`)는 LLM · CLI 도 한다(G11). 그 밖의 `library.*` 는 `.trash` 아래를 가리키지 못한다.
4. 비우기 = 데몬 PC 의 OS 휴지통으로 보내고, 안 되면 바로 지운다. 확인 모달이 그것을 미리 말한다(G12). OS 휴지통 호출은 platform 함수 하나(G12 · 「플랫폼 중립」) · 라이브러리 고름은 §5 0a 조사.
5. 저절로 비우지 않는다(G11). 사람 화면 = 왼쪽 칸 맨 아래 「🗑 휴지통」 → 휴지통 보기(G9).

## 거부한 대안
- **비우기를 에이전트 명령 표(`engram`)에** — LLM 이 영구 삭제할 수 있다(§7 28).
- **사람만 가드에 장치 · 예외 목록을 더하기** — 사용자 2026-10-29(G21 — LLM 은 바깥 도구로 늘 우회할 수 있다).
- **CLAUDE.md 원칙의 「의도된 예외」 로 적기**(옛 F9 · R18 틀) — G21 · M24-7 이 걷었다.
- **삭제 자체를 사람만** — LLM · CLI 삭제는 `.trash` 로 가서 되살릴 수 있으므로 막을 까닭이 없다(사용자 — F9).
- **30일 같은 자동 비우기**(관행 — Notion · Apple 사진) — 사용자 「일단 유저가 비우게 나중에 필요하면 추가하고」(G11 — 나중 생각).
- **휴지통 입구를 「…」 메뉴 안에** — 메뉴 안에만 둔 피어를 못 찾았다(G9).
- **되살리기를 버스에 열지 않기**(2026-10-19 메인 제안) — 해가 없어 연다(G11).

## 근거
- 이유 = 에이전트가 잘못 지워도 되살릴 수 있게 남긴다(F9 · 사용자 2026-10-19).
- G12 「휴지통 비우면 윈도우 휴지통으로 보내고 안되면 그냥 삭제되게」 · G11 「일단 유저가 비우게 나중에 필요하면 추가하고. 윈도우 휴지통 생각하면됨」.

## 영향 / 불변식
- Windows 는 말없이 영구 삭제로 물러날 수 있어 무엇이 일어났는지 늘 알 수는 없다 — 그래서 뒤가 아니라 앞에 말한다(G12).
- 비우기를 LLM 표면(명령 표 · 프라이밍 · help)에 올리는 변경은 이 결정을 다시 연다.

# ADR-NNNN (S25-AF): `daemon\cache\` = 다시 만들 수 있는 데이터만 — 언제 지워도 된다

- 상태: 제안 (2026-10-31, 근거: 사용자 결정 B14(2026-10-19 「cache로 하자. 그래야 유저가 인지하고 삭제하지」) · P10)
- 관련: **Amends ADR-0264**(데이터 루트의 `state\` · `run\` 가름에 셋째 칸을 더한다 — 덧붙임) · S25-Z · TRD §1-1 · §1-4 `validate.rs` · §7 29

## 맥락
데몬이 내려받은 설정 스키마를 어디 두나. 지금 데이터 루트는 지키는 `state\` 와 실행 중 휘발 `run\` 으로 갈린다(ADR-0264).

## 결정
1. `daemon\cache\` 는 다시 만들 수 있는 데이터만 둔다 — 언제 지워도 된다. `state\`(지키는 것) · `run\`(실행 중 휘발 · 부팅 때 쓸어 냄)과 가른다.
2. 첫 입주자 = 내려받은 설정 스키마 `daemon\cache\schemas\…`. 앞으로 다시 만들 수 있는 데이터도 여기 둔다.
3. 스키마는 배포판 한 벌이 늘 있고 여기는 갱신본만이다(P10).

## 거부한 대안
- **스키마를 `state\` 나 데이터 폴더 어딘가에** — 지워도 되는지 이름으로 알 수 없다(사용자 이유 — B14).

## 근거
사용자 결정 B14 · P10.

## 영향 / 불변식
- `cache\` 아래가 지워져도 동작이 서야 한다 — 지워져 있으면 다음 판 확인 때 다시 받는다(TRD §1-4).
- 지켜야 하는 데이터를 여기 두지 않는다. 자리는 데몬 `DataLayout` 이 낸다.
