- 관련: 옛 메모 96(데몬 안 모듈 — 사용자 2026-10-14)을 대신한다 · ADR-0151(crate 분리 판정 기준) · ADR-0155 결정 1(어휘는 생산자 옆 — `library.*` 는 agent 블록) · ADR-0251(동기 포트 + `blocking_handler` 선례) · ADR-0175 · ADR-0269(base 입주 조건) · CLAUDE.md 「백엔드 확장」 · S25-I · TRD §1-1 거부한 대안 · §1-4 · §7 30

## 맥락
라이브러리(지침 · 스킬 · 설정 · 프리셋 파일의 훑기 · 읽기 · 쓰기 · 해석 · 다시 연결)를 어디 둘지. 메모 96(2026-10-14)은 데몬 crate 안 전용 모듈로 정했다 — trait seam 은 처음부터 두고, base 는 입주 조건(도메인 지식 · 소비자 하나)에 걸려 배제했으며, 따로 된 crate 는 「다른 crate 가 필요하거나 프리셋 로직이 커지거나 격리 시험이 필요할 때」로 미뤘다. TRD 의 옛 기각 사유는 「소비자가 하나다」였다.

## 결정
1. 라이브러리는 신설 crate `crates/engram-dashboard-asset-library/`(Rust `engram_dashboard_asset_library`)다. 이름 = 담는 것이 에이전트에 싣는 에셋이라 asset(TRD 어휘 `AssetRef` 와 맞춤). 버스 명령 `library.*` 와 화면 이름 「라이브러리」 는 그대로다.
2. 의존 = 정확히 agent · platform · command · base. 데몬이 이 crate 를 의존하고 **배선만** 한다(만들기 · 포트 꽂기 · 값 넘기기). agent 는 이 crate 를 모르고 포트만 정의한다.
3. 바깥 접점은 포트다. `LaunchKitSource` · `LibraryCommandHost`(명령마다 타입 있는 메서드)를 이 crate 의 서비스가 직접 구현한다. 백엔드마다 다른 설정 지식은 agent `backend` 의 설정 검사 포트(S25-I). 명부 변경은 manager 의 프로필 편집 포트로 — 명부 변경과 스폰 예약이 한 락 순서를 쓴다(M18).
4. 네트워크 클라이언트를 갖지 않는다 — 스키마 받기는 데몬이 꽂는 fetch 포트(trait 은 이 crate 가 정의 — M25). 시험 기능(`test-support`)이 없다 — 데몬 쪽 시험은 실 `FsStore` + 임시 폴더(M17).
5. 데몬 내부(`connection_core` · `command_delivery` · `control`)를 부르지 않는다. 데몬은 값(`DataLayout` 이 낸 자리 · `daemon_id`)으로 넘긴다.
6. 게이트 넷(M17): 시험 줄 · 의존 상한 = 이름 **집합** {agent · asset-library · base · command · platform}(줄 수 아님) · 메시징 격리 정규식에 `asset_library` · `use tauri` 0줄. async 반입 게이트는 스키마 받기가 들어올 때 정한다.

## 거부한 대안
- **데몬 안 모듈**(메모 96 — 사용자 2026-10-14 「애매하긴 하지만 그렇게 해」) — 사용자가 2026-10-20 따로 된 crate 로 확정했다(G16 — 「분리할수 있으면 분리 … 데몬안에 있는 조건이 데몬에 있는걸 너무 많이 연관시켜야되고 상호참조가 필요해서 어쩔수 없을때」). 옛 기각 사유 「소비자가 하나다」 는 ADR-0151 결정 1 이 폐기한 기준이다(판정표 결론 · TRD §1-1).
- **base 에 두기** — 도메인 지식이 있고 소비자가 하나라 입주 조건에 걸린다(메모 96).
- **crate 이름 `engram-dashboard-library`**(메모의 예) — 사용자가 asset 을 골랐다(G24 — 담는 것이 에셋 · `AssetRef` 어휘).

## 근거
- 판정표: 「분리할 수 있나」 다섯 물음이 다 「예」 — 단 백엔드 검사 지식을 backend 포트로 옮긴 뒤(M2). 대가는 고정분(매니페스트 · 게이트 등록 · 공개 표면)뿐이고, 들어오는 간선이 없는 신설 때가 가장 싸다(TRD §1-1). 판정표의 확신도 = 중간.
- 옮길 타입이 없다(판정표 C6 = 0) · 시험 기능이 필요 없다(C5 = 0)(TRD §1-4).

## 영향 / 불변식
- 이 crate 가 데몬 내부를 부르게 되면 crate 판정이 뒤집힌다(TRD §1-4 · 판정표 §3 「뒤집는 것」).
- 데몬 조립 순서(TRD §1-4): 명부 → 라이브러리 서비스(프로필 편집 포트 = 늦게 채우는 빈 칸 · 채운 뒤 약한 참조) → manager → 빈 칸 채움 → 스키마 갱신 스레드. 빈 칸 채우기는 명령 표 슬롯 `command_table_slot.set` **앞**이다 — 제어 라우트(MCP 서버)는 데몬 배선보다 먼저 뜨므로 빈 칸을 지키는 것은 그 표 슬롯이고(표가 서기 전 라우트 = 503) 수락 루프는 그 뒤에 연다(M31 — 옛 「채운 다음에 수락 루프 · 제어 라우트를 연다」 는 코드와 어긋났다). 빈 칸에 닿으면 오류로 답한다 — Noop 으로 접지 않는다.
- 데몬 `DataLayout` 은 `daemon\state\` 폴더를 넘기고 그 안 `library.json` 이름은 asset-library 가 소유한다(ADR-0264 결정 4 · M30).
- CLAUDE.md 「백엔드 모듈 맵」 · 「빌드·검증 명령」 의 새 줄은 구현 때 사용자 확인을 받아 더한다(M1 · M17).
- 메모 96 에 대체 표시(TRD §5 0c).

# ADR-NNNN (S25-B): 라이브러리 루트는 하나다 — 바깥 내용은 루트 안으로 들인다

- 상태: 제안 (2026-10-31, 근거: 사용자 결정 G36(2026-10-31 「ㅇㅇ 루트를 하나로」) · G37(「외부에 두지말고 engram 안으로」) · G37-NOTE(「라이브러리 폴더 바꾸기는 그대로 놔둬」) · G35(「최초 디폴트 등록해둬」) · G31 · G39 + 메인 M22 · M24-2(보고) · PRD R7)
- 관련: 옛 메모 127(2026-10-15 「그냥 한 개 폴더로 하자」 — 되살림) · G25 · G25-RESOLVED · G26 · G27 · G30 · M23 · M19/M21 의 여러 루트 부분(되돌림) · S25-H · S25-W · TRD §1-1 · §1-2 `LibPath` · §1-4 「루트 · 기본 경로」 · §7 31 · 조사(배경) `docs/research/multi-root-asset-library-practice-2026-10-30.md` · `docs/research/cross-root-move-practice-2026-10-30.md`

## 맥락
메모 127(2026-10-15)은 라이브러리 폴더 하나로 정했다. 2026-10-29 사용자가 여러 루트를 요청했고(G25), 그 뒤 루트를 넘는 참조 허용(G25-RESOLVED) · 루트 이름 접두 `<이름>:/`(G26) · 루트 사이는 복사만(G27) · 루트 이름을 바꾸면 참조 고침(G30) · 참조된 루트 지우기에 `yes`(M23)가 줄줄이 붙었다. 2026-10-31 사용자가 하나로 되돌렸다.

## 결정
1. 라이브러리 루트는 하나다(R7 되살림). 프리셋도 그 안의 파일이다.
2. 루트 안이면 어디로든 옮기고 이름을 바꾼다(탐색기 규칙 — P5). 드라이브가 하나라 볼륨을 넘는 이동이 없다.
3. 바깥 내용(예 `~/.claude/skills`)은 제자리에서 쓰지 않는다 — 루트 안으로 복제 · 복사해 들인다(G37).
4. 나눠 줄 때 = 필요한 파일을 루트 기준 경로로 내보내 같은 경로로 들인다. 내보내기 · 들이기(의존 닫힘)는 S25 밖이다(G37 · T-73). S25 는 참조 걷기를 다시 쓰는 함수 하나로 둬 나중에 꽂히게 한다(G37). 일부만 손으로 옮기면 빈 참조는 「찾을 수 없음 · 다시 연결」(R19).
5. 첫 시작에 루트가 없으면 빈 `<배포판>\library` 를 만들어 루트로 적는다(개발 · 시험 = `DataLayout` 규칙 · `ENGRAM_DATA_DIR` 격리 — G35). 만들기에 실패하면 미설정 상태로 물러난다(M24-2). 「라이브러리 폴더 바꾸기」(R9)는 그대로다(G37-NOTE).
6. 나중에 루트를 늘리면 새 루트에만 이름 접두를 붙이고, 접두 없는 경로는 지금 루트를 뜻한다(G36).
7. 그대로 두는 것: 휴지통 `<루트>\.trash\`(G31 · S25-W) · 루트가 git 작업 트리면 `.git/info/exclude`(M22) · 기본 제공 `engram:/`.

## 거부한 대안
- **루트 여럿**(G25 · G25-RESOLVED · G26 · G27 · G30 · M23 — 2026-10-29~30) — 사용자가 되돌렸다(G36). 사용자 이유: 나눠 주기는 루트 기준 경로로 내보내고 같은 경로로 들이는 것으로 한다(언리얼 「Migrate」 · 유니티 「Export Package + dependencies」 꼴 — 메인 지식 · 조사 안 함). 원래 이유(메모 127): 여러 라이브러리의 문제(라이브러리를 넘는 프리셋 참조 · 루트를 넘는 순환)는 프리셋이 라이브러리 안에 살기 때문에 생긴다.
- **프리셋 폴더 따로 + 부품 라이브러리 여럿** — 보였으나 고르지 않았다(메모 127 · PRD R7 「루트를 넘는 참조 · 순환 문제」).
- **바깥 폴더를 제자리에서 쓰기**(예 `~/.claude/skills`) — 사용자 「외부에 두지말고 engram 안으로」(G37).

## 근거
- 사용자 결정 G36 · G37 · G37-NOTE · G35(2026-10-31).
- 조사(배경 — 여러 루트를 검토할 때 쓴 것): multi-root-asset-library · cross-root-move(2026-10-30).

## 영향 / 불변식
- `LibPath` 에 루트 접두가 없다 — `:` 를 받지 않아 `engram:/` 와 섞이지 않는다(TRD §1-2).
- 루트 관리 명령은 `library.status` + `setRoot` 둘이다(M21 의 addRoot · removeRoot · renameRoot 를 되돌림 — G36).
- 여러 루트를 다시 열 때는 결정 6 의 확장 길에서 출발하고, G25 갈래(루트를 넘는 참조 · 이름 바꾸면 참조 고침 · 복사만)는 다시 따진다.
- 참조 걷기 함수는 내보내기 · 들이기가 다시 쓸 수 있게 둔다(G37) — 그 기능이 올 때 따로 걷기를 짓지 않는다.
- 기본 루트 `<배포판>\library` 는 배포판 폴더 안이라 `scripts/build-release.ps1` 이 배포판을 다시 지을 때 함께 지워진다 — 의도다(`data\` 와 같음). 쓰는 라이브러리는 「라이브러리 폴더 바꾸기」(R9)로 배포판 밖에 둔다(G39 · 사용자 「빌드용이 뭔가 저장될 필요가 있음? 내가 사용할건 밖으로 뺄건데」). 스크립트는 바꾸지 않는다.

# ADR-NNNN (S25-C): 지침 · 스킬의 백엔드 꼬리표는 프리셋 항목에 단다 — 에셋 파일은 손대지 않는다

- 상태: 제안 (2026-10-31, 근거: 사용자 결정 G29(2026-10-30 「프리셋에 하는게 맞지 싶은데」) · G51 · G51-PURPOSE(2026-10-31 — 순서 · 쓰임) + 메인 M20 · M25 · M26(보고) · 조사 `docs/research/per-agent-instructions-practice-2026-10-30.md`)
- 관련: PRD R54 · P12(안 실리는 줄 흐림) · S25-F(「기본」 의 백엔드별 프라이밍) · S25-K(codex 터미널 알림) · TRD §1-2 · §1-3 1 · 5 · 6 · §7 32 · M24-4(전역 순서 — G51 이 뒤집음)

## 맥락
에이전트마다 공통 지침에 더해 claude · codex 전용 지침 · 스킬을 실을 길이 필요했다(G29 — 새 기능 · PRD 수준 추가). 꼬리표를 어디에 다느냐. 꼬리표의 쓰임(G51-PURPOSE — 사용자 「프리셋이 메인세션 프리셋인데 로컬모델이 구져서 제대로 안들으면 클로드랑 다르게 덧붙이는 느낌으로 해야되는거 아니면 각각 쓰거나」): 한 프리셋을 잘 따르지 못하는 백엔드(예 약한 모델)에 그 프리셋의 공통 항목이 못 덮는 줄을 덧붙이는 패치다. 백엔드마다 내용이 크게 다르면 프리셋을 따로 쓴다.

## 결정
1. 지침 · 스킬 항목은 경로 문자열(= 공통) 또는 `{path, backend: claude|codex}` 다. 꼬리표는 **프리셋에** 있고 에셋 파일에는 없다.
2. `presets` · `settings` 항목은 경로 문자열 그대로다 — 설정은 파일 안 `claude:` · `codex:` 칸이 이미 백엔드를 가른다.
3. 실리는 순서 = **프리셋마다** — 펼친 순서대로 각 프리셋의 공통 항목 → 그 프리셋의 그 백엔드 꼬리표 항목(G51 — 예 [A, B] 가 붙고 A = [공통 a · codex a'] · B = [공통 b · codex b'] 면 codex 에이전트가 받는 순서 = a → a' → b → b'). 안에 든 프리셋은 자기 항목보다 먼저 펼친다(D1 — 그대로). 덧붙임이지 덮어쓰기가 아니다. 같은 경로는 펼친 순서의 처음 자리 한 번이다(M14 — 그대로).
4. 충돌 검사는 그 에이전트에 실제로 실리는 항목끼리 한다.
5. codex 터미널은 여전히 지침 · 스킬을 싣지 않고 codex 꼬리표 줄도 알림에 넣는다(M20 · S25-K). 기본 제공 「기본」 은 꼬리표로 백엔드마다 다른 프라이밍을 실을 수 있다.
6. 명령 = `preset.add` 의 선택 `backend` + 꼬리표 바꾸기 `preset.setBackend {path, items, backend?}`(M26). 에이전트 슬롯은 그 에이전트 백엔드에 안 실리는 줄을 흐리게 보인다(P12 와 같음). 화면 꼴(공통 / claude만 / codex만 세 묶음 · 끌기나 우클릭으로 꼬리표 바꾸기)은 클라이언트 단계에서 다시 보인다(M20).

## 거부한 대안
- **에셋 파일 앞머리에 꼬리표**(rulesync 꼴 — 조사의 (나)) — 받은 파일을 고쳐야 하고 · 같은 파일을 프리셋마다 달리 못 쓰며 · 실을 때 앞머리를 벗겨야 한다(G29 · 조사 「우리에게」 표 · 사용자가 (가) 를 골랐다).
- **펼친 전체에서 공통 항목 전부 → 그 백엔드 항목 전부(전역 순서)**(M24-4 · M25 OVERRIDDEN — 메인 세션이 정했던 꼴 · 이 초안의 옛 결정 3) — 사용자가 뒤집었다: 「공용 전용이 그렇게 쓰이는게 아니라 공용으로 안되는걸 덧붙이는 느김이라 aa bb 가 맞을듯?」(G51 — 백엔드 항목은 그 프리셋의 공통 항목이 못 덮는 것을 덧붙이는 것이라 그 바로 뒤에 선다).

# ADR-NNNN (S25-D): 구현은 서버 먼저 — 데몬 라이브러리 기능은 늘 켜져 있고 화면만 끄고 켠다

## 맥락
G18(2026-10-21)은 화면만 먼저 짓는 시제품 + 사용성 시험을 백엔드 앞에 뒀고, G18-REVISED 는 데몬 · 셸 없이 실 슬롯에 가짜 데이터로 짓는 꼴을 정했다. G22 는 라이브러리 화면을 켜고 끄는 「플러그인 같은」 기능으로 두되, 끄면 무엇이 꺼지는지(화면만 · 데몬 명령까지)를 열어 뒀다.

## 결정
1. 서버 먼저: asset-library + 데몬 명령 + `engram library.*` CLI 를 짓고 CLI 로 검증한 뒤 클라이언트(G20). 명령 · 답 꼴은 TRD 가 먼저 박는다.

## 거부한 대안
- **화면만 먼저 짓는 가짜 시제품 + 사용성 시험 뒤 백엔드**(G18 · G18-REVISED) — 사용자가 순서를 뒤집었다(G20 「일단 서버 먼저가 맞고」 · 결정 기록의 덧말 = LLM 길이 바탕).
- **끄면 데몬 명령까지 끄기**(G22 의 열린 갈래) — 사용자 「데몬은 디폴트로 제공하는거고」(G22-RESOLVED).

## 근거
- 사용자 결정 G20 · G22-RESOLVED.
- CLAUDE.md 「LLM-우선 제어」 — LLM 이 메인 조작 주체 · 프론트는 렌더링만 소유한다. 결정 기록 G28 이 같은 읽기(「LLM-first + UI optional (G20/G22)」)로 codex 터미널 알림을 화면이 아니라 데몬 답에 싣는다.

## 영향 / 불변식
- 화면만 아는 동작을 만들지 않는다 — 화면이 하는 조작은 전부 버스 명령이다(M21 — 예외 = 휴지통 비우기(셸 전용) · 로컬 OS 도우미).

# ADR-NNNN (S25-F): 프라이밍의 원천은 배포판 `builtin\` 하나 — 기본 제공 프리셋 「기본」 의 지침 파일

- 상태: 제안 (2026-10-31, 근거: 메인 세션 결정 G1(2026-10-20 · 보고) · M7(2026-10-21 · 보고 · TRD 리뷰 #4 · #8) · M18(보고) · G46(2026-10-31 — 메인 결정 · 사용자 위임: 폐기가 아니라 부분 개정))
- 관련: **Amends ADR-0092 결정 1**(아래 「바뀌는 조항」) · ADR-0099 · ADR-0100 · ADR-0211 · ADR-0215(같은 경로나 배달을 가리킨다 — 「영향」 의 확인 항목) · S25-C · S25-K · S25-V · TRD §1-1 · §1-2 · §2-4 1 · 2 · §5 17 · §7 35

## 맥락
지금 프라이밍은 고정 경로의 공용 마크다운(`prompts/agent-priming.md` · 덮개 `ENGRAM_PRIMING_FILE`)을 스폰 때 로더가 읽어 시스템 프롬프트에 주입한다 — 전원 무조건(ADR-0092 결정 1). S25 는 기본 제공 에셋(프리셋 「기본」 과 그 지침 · 설정)을 라이브러리와 같은 꼴의 파일로 두고 가짜 경로 `engram:/…` 로 가리킨다(Δ1). 원천이 「코드 + 배포판 `prompts\agent-priming.md`」 로 나뉘어 있던 것을 하나로 모은다(G1).

## 결정
1. 기본 제공 에셋은 배포판 `builtin\` 폴더 하나에 라이브러리와 같은 꼴로 둔다(프리셋 `.yaml` · 지침 `.md` · 설정 `.yaml`). `engram:/…` 가 그 파일에 대응한다(G1). 파일 이름 · 대응의 꼴은 구현 판단.
2. 프라이밍의 원천은 그 안의 지침 파일(`engram:/priming` — 지금 프라이밍 글 그대로) 하나다. 「기본」 프리셋이 그것을 지침으로 싣는다(M7).
3. 해석은 asset-library 가 스스로 한다 — `LaunchKitSource::prepare` 에 priming 인자가 없다(M18).
4. `builtin\` 이 없으면 프라이밍 없이 뜬다 — 막지 않는다(M7).
5. 배포 zip 에 싣는다(§5 17). 개발 · 시험 · `ENGRAM_DATA_DIR` 에서 찾는 법과, 옛 길(지금 `NoopLaunchKits` 만 쓰는 `priming_file`)을 걷는 때는 미결이다(TRD §2-4 1 · 2 · M25 LEFT OPEN).

## 바뀌는 조항 (ADR-0092)
- **결정 1 만 바뀐다 — 부분 개정이다**(G46 — 메인 결정 · 사용자 위임 · TRD §7 35 도 「폐기가 아니라 개정」 으로 고쳤다). 결정 2(1:1 선행 · 다중수신 추상) · 3(형식 판정축 수용>토큰) · 4(happy-path-first)는 프라이밍 원천과 무관해 그대로다.
- 결정 1 에서 바뀌는 것: ① 경로 — repo 의 `prompts/agent-priming.md` → 배포판 `builtin\` 의 지침 파일 ② 로더 seam → 실행 재료 포트 `LaunchKitSource`(ADR-0092 가 「미래 구현체 = 에이전트별 프롬프트 인젝션/스킬등록 시스템(로더 교체로 흡수)」 이라 예고한 자리) ③ 「임시판은 전원 무조건 주입」 → 「기본」 이 붙은 에이전트에만(만들 때 붙고, 떼기는 `yes` 확인 — M21).
- 결정 1 에서 그대로인 것: 하드코딩 금지(여전히 외부 파일) · 데몬이 읽어 시스템 프롬프트 쪽으로 넘긴다(에이전트가 스스로 파일을 읽지 않는다). ADR-0092 「영향」 첫 줄(프라이밍 내용 하드코딩 금지 · 로더는 seam)은 계속 지켜진다.
- 이 초안의 결정 4(없으면 막지 않음)를 TRD 는 「ADR-0092 와 같은 너그러움」 이라 적지만 ADR-0092 본문에 그 조항은 없다 — 지금 코드의 동작인지는 확인하지 않았다.

## 거부한 대안
- **「코드 + 배포판 `prompts\agent-priming.md`」 나눔**(G1 이 대신한 꼴 — 내장 프리셋 · 설정 정의는 코드의 내용 표(`builtin.rs`) · 프라이밍 글만 배포판 파일 · 2026-10-15 TRD 첫 판 §1-1) — 근거(메인 2026-10-31 — 보고): ① 기본 제공 에셋은 라이브러리 화면에서 읽기 전용 뿌리로 둘러보고(프리셋 → 안의 지침 · 설정 · 상세 칸) 라이브러리로 복사해 나가는 대상이다(R43 · G2-REVISED · P6 · M14 — 사용자 결정) — 라이브러리와 같은 꼴의 파일이어야 같은 훑기 · 해석 · 상세가 그대로 돌고, 코드의 내용 표는 그 길마다 기본 제공 몫의 둘째 길을 요구한다. ② 「기본」 의 설정(`allowedMcpServers` · `DISABLE_AUTOUPDATER`)은 보여야 한다(T10 — 사용자 「사실 감추는 설정이 있으면 안되지」) — 파일이면 같은 화면에 그대로 보인다. ③ ADR-0092 가 프라이밍을 코드에 박지 않은 이유(「내용 수정마다 재빌드」 · 교체 불가 — 그 ADR 의 거부한 대안)가 「기본」 의 프리셋 · 설정 정의에도 같다.
- **ADR-0092 통째 폐기(supersede)**(TRD §7 35 · §5 0c 의 옛 문구) — 바뀌는 것은 결정 1 의 고정 경로뿐이고 결정 2~4 는 프라이밍 원천과 무관해 그대로 선다(G46 — 메인 결정 · 사용자 위임).
- (참고 · 거부 아님) 프라이밍 자체를 사용자 라이브러리 에셋으로 두는 것은 비목표 · 나중 생각이다(PRD R52 · 결정 기록 ROUND 2 「LATER IDEA」).

G1 · M7 · M18(메인 — 보고). M7 이 가리키는 TRD 리뷰 #4 · #8. 거부한 대안의 근거 = 위(메인 2026-10-31 — R43 · G2-REVISED · P6 · T10 · ADR-0092).

- 프라이밍 글을 고치는 자리는 `builtin\` 의 지침 파일 하나다 — 코드에 다시 두지 않는다.

- **확인 필요(`/adr link` 때)**: ADR-0099(결정 4 — 이미 ADR-0211 이 부분 폐기) · ADR-0100(배포판 조립) · ADR-0211 · ADR-0215 가 `prompts/agent-priming.md` 경로나 프라이밍 배달을 가리킨다. 이 초안이 그 조항까지 바꾸는지 판정하지 않았다.

# ADR-NNNN (S25-G): 프리셋 · 라이브러리는 데몬이 소유하는 에셋이고 클라이언트가 요청해 읽는다

- 상태: 제안 (2026-10-31, 근거: 사용자 결정 메모 53 · 74 · 76 · 99(2026-10-14) · R7 / G36 · G22-RESOLVED · G32 · G43(2026-10-31 「engram이 할때는 갱신하고, 바깥은 실행할때 막히거나 새로고침으로 … 라이브러리도 동등한 룰」) + 메인 M25 · M30 · M58(보고) · 조사 `docs/research/broken-reference-check-timing-practice-2026-10-31.md` · `docs/research/derived-vs-stored-broken-marker-practice-2026-10-31.md`)
- 관련: **ADR-0061 폐기**(남은 조항 — 이미 ADR-0291 이 부분 폐기) · **ADR-0070 부분 폐기**(프리셋 이름 `Preset.name` 부분) · S25-A(crate 자리) · S25-B(루트 하나) · S25-D · ADR-0029(데몬이 유저 데이터 단일 소유) · ADR-0264(옛 데이터는 버린다) · ADR-0291 · 메모 58(기계 쪽 = 데몬 · 보는 쪽 = 클라이언트) · TRD §1-1 · §1-12 · §7 1

## 맥락
옛 「프리셋」 은 작업 폴더 책갈피였다(ADR-0061 — 데몬 `presets.json` · `Preset{id, cwd}` · CRUD 뒤 전 연결 방송 / ADR-0070 — `Preset.name` 표시명). S25 의 프리셋은 지침 · 스킬 · 설정 · 다른 프리셋을 묶는 에셋이라 이름이 겹친다(메모 43).

## 결정
1. 프리셋은 라이브러리 폴더 안의 YAML 파일이다 — 스킬 · 지침과 같은 자리의 에셋(메모 74 · 76). 라이브러리 폴더는 하나다(S25-B).
2. 데몬 프로세스 안 asset-library 가 단독으로 읽고 쓴다(자리 = S25-A). 클라이언트는 디스크를 읽지 않는다.
3. 요청형: 클라이언트가 자기 동작(슬롯 열기 · 포커스 · 새로 고침 · 폴더 바꿈)에 요청하고, 데몬은 훑어 그 클라이언트에만 답한다 · 에이전트 실행 전 다시 확인한다. 감시(notify) · 구독 · 방송 · 보이는 동안 주기 폴링이 없다(메모 99).
4. 데몬 쪽 기능(명령 · CLI)은 늘 켜져 있다(G22-RESOLVED · S25-D).
5. 옛 `presets.json` · 옛 프리셋 wire · 프리셋 팔레트 슬롯은 걷는다 — 옛 데이터는 묻지 않고 버린다(G32 · M26 · ADR-0264). 새 판의 프로필은 새 파일 이름이라 옛 `agents.json` 은 읽지도 지우지도 않는다(M25).
6. **트리 ⛔ 도 라이브러리 목록과 같은 규칙이다**(G43): Engram 을 거친 변경(파일 조작 · 편집 · 다시 연결)은 메모리 `Catalog` 에 곧바로 들고, 화면은 라이브러리 목록과 같은 계기(칸 열기 · 포커스)에 더해 에이전트 목록 갱신 때 다시 받는다(M58). 바깥 변경은 새로 고침(F5 · `library.refresh`) · 실행 때 막힘에서만 보인다. 새 방송을 만들지 않는다 — 「감시 · 방송 없음」 그대로.
7. **「찾을 수 없음」(가리키는 것이 없음)은 저장하지 않고 볼 때 `Catalog` 에서 파생한다. 파일 자체의 파싱 · 스키마 오류는 그 파일을 읽을 때 계산해 항목과 함께 저장한다**(G43).

## 거부한 대안
- **셸이 라이브러리를 훑는다** — 클라이언트 디스크 읽기 금지(PRD 불변 제약)이고, 원격 데몬(나중)에서 성립하지 않는다(TRD §1-1).
- **notify 감시 + 방송** — 사용자 「화면 보고 있는 동안 바로 보여줄 필요 없음」(메모 99 · 조사 `docs/research/library-folder-change-sync-survey-2026-10-14.md`). 요청형은 원격 · 모바일 클라이언트에도 선다 — 모든 계기가 클라이언트 동작이다(메모 99). 나중 감시는 덧붙일 수 있다(TRD §1-12).
- **프리셋을 내부 목록으로**(옛 `presets.json` 꼴) — 다른 사람에게 나눠 줄 때 폴더를 건네므로 프리셋이 함께 가야 한다(메모 53 · 74).
- **트리 ⛔ 만 바깥 변경까지 곧바로**(PRD 수용 문구의 옛 「곧바로 사라진다」) — 사용자 「바깥은 실행할때 막히거나 새로고침으로 … 라이브러리도 동등한 룰」(G43). 문구를 그에 맞춰 고쳤다.
- **「찾을 수 없음」 을 항목마다 저장**(바뀔 때 계산) — 메모리 색인에서 볼 때 찾으면 충분한 곳에선 이 꼴이 안 보인다 · 항목마다 저장은 판정에 디스크 I/O 가 드는 곳(Nautilus)에서 보인다(조사 derived-vs-stored — 사용자 물음 「폴더를 이리저리 옮기는데 매번 저 검사를 한다고?」 에 답한 것 · G43).

## 근거
- 사용자 결정 메모 53 · 74 · 99(2026-10-14) · 메모 58 의 나눔 규칙 · TRD §1-1 · G43.
- 조사 broken-reference-check-timing(light · 근거 얇음): 「새로 고침이나 쓸 때만」 은 파일 기반 도구에 흔한 꼴이다(Blender 「Report Missing Files」 = 확실 · Premiere · Ableton · Lightroom = 가능성 높음) · 바깥 변경 감시자는 표본에서 확인하지 못했다.
- 조사 derived-vs-stored(light): 나눈 꼴이 흔하다 — 파일 사이 관계 색인은 저장하고 증분으로 고치고, 항목 옆 표시는 볼 때 계산한다(Foam = 확실 — `graph.ts` · `document-decorator.ts` 원문 확인). S25 설계(첫 훑기에 관계 표 · Engram 변경 때 증분 · 보이는 것만 찾아 표시)가 Foam 과 같은 꼴이다.

## 영향 / 불변식
- ADR-0061 의 남은 조항(데몬 `FilePresetStore` · `PresetRegistry` · 프리셋 wire · 방송 · `Preset{id, cwd}`)과 ADR-0070 의 `Preset.name` 부분이 폐기된다. ADR-0070 의 `AgentProfile.display_name` 부분은 이 초안이 다루지 않는다(§7 1 은 프리셋 이름 부분만 꼽는다).
- **확인 필요**: ADR-0291 의 `presets.json` 조항(R6 상한 · R9 손상 사본 · R12 임시 이름 · R17 읽기 전용 모드)이 사문화된다 — `/adr link` 때 판정.
- 라이브러리 목록 변화를 클라이언트에 밀어 보내는 길을 만들지 않는다. 트리 ⛔ 를 위해서도 만들지 않는다(G43 · TRD §1-11a 발견 18 닫힘).
- 파생 「찾을 수 없음」 이 맞으려면 `Catalog` 이 비어 있으면 안 된다 — 재시작 뒤 `Catalog` 을 읽는 메서드는 전부 첫 훑기를 지난다(S25-AG 결정 6).
- 새 프로필 파일 이름은 `.gitignore` 의 `**/data/daemon/state/agents.json*` 을 비켜 가고 프로필에는 평문 `env` 가 든다 — 그 파일을 들이는 구현 단계가 새 이름 + `*` 꼬리 줄을 `.gitignore` 에 더한다(M30 · ADR-0136 결정 3 · ADR-0264 결정 7).

# ADR-NNNN (S25-H): 참조 = 라이브러리 루트부터의 `/` 경로 한 꼴 + 기본 제공 `engram:/`

- 상태: 제안 (2026-10-31, 근거: 사용자 결정 메모 101–103(2026-10-15 「ㅇㅇ 지정한 폴더로 확정」) · PRD R3 · Δ1)
- 관련: S25-B · S25-M(자리 = 정체) · TRD §1-2 `LibPath` · §7 2 · 조사 `docs/research/preset-asset-reference-base-survey-2026-10-14.md`(+ 2026-10-15 덧붙임)

## 맥락
프리셋 안의 참조(스킬 · 지침 · 설정 · 다른 프리셋)를 어떤 꼴로 적나.

## 결정
1. 참조 = 라이브러리 맨 위부터의 `/` 경로 한 꼴(예 `스킬/리뷰/review`) · 범위 제한 없음(R3).
2. `LibPath` 규칙: UTF-8 · 구분자는 `/` 만 · 앞뒤 `/` 없음 · 빈 칸 · `.` · `..` · `\` · `:` · 제어 문자 없음. 루트가 하나라 루트 접두가 없다(S25-B).
3. 기본 제공 에셋 = 라이브러리 밖의 고정 가짜 경로 `engram:/…`(Δ1). `LibPath` 가 `:` 를 받지 않아 둘이 섞이지 않는다.

## 거부한 대안
- **프리셋 파일 기준 상대**(`./` — Claude Code 플러그인 · Compose · Cargo 꼴) — 파일이 묶음 안에 사는 경우에 맞고, 여러 프리셋이 나눠 쓰는 공유 라이브러리엔 안 맞는다(메모 103 (a) · PRD R3).
- **이름 참조**(Claude Code 플러그인 의존 · Continue `owner/name`) — 범위가 분명한 네임스페이스 안에서만 선다. 폴더 브라우저에선 다른 폴더의 같은 이름이 흔하다(메모 103 (b) · PRD R3).
- **고정 ID 파일**(Unity · Godot) — 무거운 엔진 모델이고 바깥 이동에 깨진다(메모 103 (c)).
- **URI 꼴**(`lib://업무/...`) — URL 호스트 정규화가 비 ASCII 라이브러리 이름을 망가뜨린다(메모 126 — 세션이 기각 · 사용자 확인 기록 없음).

## 근거
사용자 이유(메모 102): 스킬은 여러 프리셋이 나눠 쓴다(다대다) — 한 프리셋 옆에 두면 다른 프리셋이 둘 자리가 없다 · 프리셋이 프리셋을 품는다 · Engram 은 폴더 브라우저라 항목의 정체는 자리다. 브라우저 꼴 피어 확인(Obsidian 볼트 루트 경로 등 — 조사 덧붙임 2).

## 영향 / 불변식
- 검증 · 디스크 경로 바꾸기 · 이동 때 접두 바꾸기는 `LibPath` 타입 하나가 맡는다(`relative-path` 감쌈 — TRD §1-2).
- 여러 루트를 다시 열면 새 루트에만 접두를 붙인다(S25-B 결정 6).
- 경로로 찾는 표(`Catalog`)의 열쇠와 대소문자 비교는 platform `path_key` · `same_path` 가 맡는다(S25-AI) — `LibPath` 문자열 그대로 견주지 않는다.

# ADR-NNNN (S25-I): 실행 재료는 포트로 넘긴다 — 해석은 asset-library, 플래그 번역 · 백엔드 설정 지식은 backend

- 상태: 제안 (2026-10-31, 근거: 메인 결정 M2 · M16 · M18(보고 — 사용자 이의 가능) · TRD 리뷰 #2 · #3 · CLAUDE.md 「백엔드 확장」)
- 관련: ADR-0004(백엔드 지식 격리) · S25-A · S25-F · S25-J · S25-K · TRD §1-4 포트 표 · §1-5 · §7 3

## 맥락
에이전트를 띄울 때 붙은 프리셋을 펼쳐 지침 · 스킬 · 설정을 CLI 플래그로 바꿔 싣는다. 펼치기 · 플래그 · 백엔드마다 다른 설정 형식을 누가 아나.

## 결정
1. 실행 재료 포트 `LaunchKitSource`(`check` · `prepare` · `release`)는 agent 가 정의하고 asset-library 서비스가 직접 구현한다. manager 가 부른다.
2. 플래그 번역은 backend `materialize`(`backend/claude/launch.rs` · `backend/codex/launch.rs` — 플래그 지식은 이 둘뿐).
3. 백엔드마다 다른 설정 지식(스키마 출처 · CLI 판 확인 · 원문 → JSON · claude 합침 · 모르는 키 처리 · codex 스킬 형식 · 명령줄 가드)은 agent `backend` 의 설정 검사 포트 하나에 모은다(M18). 내려받기는 데몬이 꽂는 fetch 포트로.
4. `check` 에 실행 출처 인자가 없다(M16 — 다음 주제가 더한다) · `prepare` 에 priming 인자가 없다(S25-F).

## 거부한 대안
- **manager 가 프리셋을 해석** — 근거(메인 2026-10-31 — 보고): 편집 칸의 충돌 줄 · 문제 목록 · 트리 ⛔ · 실행 막힘 사유 · 실행 재료를 asset-library 의 해석 함수 하나가 모두 만든다 — 화면과 실행이 다른 규칙으로 갈리지 않게(TRD §1-3 「같은 함수가 … 모두를 만든다」 문단). manager 가 실행 몫을 따로 해석하면 해석이 둘이 된다. 또 agent 는 asset-library 를 모르고 포트만 정의한다(S25-A 결정 2 — 사용자 G16 의 crate 분리) — manager 가 프리셋 형식을 알면 그 지식이 agent 로 새어 crate 판정의 조건이 무너진다(판정표 — S25-A).
- **backend 가 라이브러리를 읽음** — 근거(메인 2026-10-31 — 보고): 라이브러리를 읽고 쓰는 것은 데몬 안 asset-library 하나다(S25-G 결정 2 · TRD §7 1) · backend 는 agent crate 안이라 asset-library 를 모른다(S25-A 결정 2). CLAUDE.md 「백엔드 확장」 이 backend 에 모으는 것은 백엔드마다 다른 지식이고 라이브러리 읽기는 백엔드와 무관하다 — backend 에 두면 같은 읽기가 claude · codex 에 둘로 선다.
- **`ControlEndpoint` 에 칸 덧붙이기** — 근거(메인 2026-10-31 — 보고): `ControlEndpoint` 는 제어 채널과 함께만 실리는 것의 descriptor 다 — `Option<ControlEndpoint>` 가 「제어 채널이 있나」 를 타입으로 답하고(ADR-0099 · `crates/engram-dashboard-agent/src/types.rs` 의 그 구조체 주석) 엔드포인트가 없으면 거기 실린 것도 실리지 않는다(ADR-0217 결정 5). 실행 재료는 제어 채널 유무와 무관하게 실리고 수명도 따로다 — `LaunchKitGuard` 는 `ProvisionGuard` 와 독립이고 재료 descriptor 는 `ControlEndpoint` 와 같은 방식의 따로 된 인자다(TRD §1-5 (나) 5 · 7).
- **설정 검사 지식을 라이브러리(`validate.rs`)에** — TRD 리뷰 #2 · #3 이 걷어 backend 포트로 옮겼다(M2). 그대로면 crate 분리 판정의 조건이 서지 않는다(판정표 결론 — S25-A).

## 근거
CLAUDE.md 「백엔드 확장」(백엔드 전용 코드는 한 곳 `backend` 에 모은다) · M18. 거부한 대안 셋의 근거 = 위(메인 2026-10-31 — TRD §1-3 · S25-A 결정 2 · S25-G 결정 2 · ADR-0099 · ADR-0217 결정 5).

## 영향 / 불변식
- 플래그 · 백엔드 설정 형식 지식이 asset-library 나 manager 로 새면 위반이다. 새 백엔드는 `materialize` 와 설정 검사 포트 구현을 늘린다.

# ADR-NNNN (S25-J): claude 실행 재료 = 합친 지침 파일 + `--system-prompt-snapshot off` + `--plugin-dir` 정션 + 합친 `--settings` 하나

- 상태: 제안 (2026-10-31, 근거: TRD 결정 T7(확정 2026-10-18 — 추천 그대로) · T10(사용자 2026-10-18) · R35 · G42(2026-10-31) · 실측(TRD §1-5 표 · §6-1))
- 관련: S25-I · S25-F · S25-V · ADR-0109 결정 9 · TRD §1-5 「backend 번역」 · §7 4

## 맥락
claude 두 모드(JSON · 터미널)에 프리셋 재료를 어떤 플래그로 싣나.

## 결정
1. 지침: 실리는 순서로 합친 파일 하나 → `--append-system-prompt-file`(지금 프라이밍 자리를 대신). 실 재료일 때만 `--system-prompt-snapshot off`(이어받기에도 새 글).
2. 스킬: 휘발 폴더 `engram\skills\<이름>` = 라이브러리 스킬 폴더로 가는 디렉터리 정션 → `--plugin-dir <휘발>\engram` → 이름 `engram:<스킬>`.
3. 설정: 붙인 순서로 합친 claude 원문 → 휘발 `settings.json` 하나 → `--settings` 하나(S25-V).
4. 모델은 따로 싣지 않는다 — 원문의 `model` 키가 `--settings` 로 간다(R35).

## 거부한 대안
- **스킬을 `--add-dir` 로** — 접두가 없어 네이티브 스킬과 이름이 겹치면 승자를 모른다(T7). 고른 쪽은 사용자 `~/.claude/skills` 와 안 섞이고 적재가 실측됐다(T7).
- **`--settings` 여럿** — 두 번째 `--settings` 의 동작이 문서에 없고 재지 않았다(§7 19).

## 근거
- claude 2.1.284 `--help`: `--plugin-dir`(반복 가능) · `--settings <file-or-json>`(한 번 꼴) · `--system-prompt-snapshot <on|off>` 있음(TRD §6-1 — 확실).
- 플러그인 폴더 적재 = 실측 확실 · 정션 따라가기 = 미측 · snapshot off 로 이어받기에도 새 글 = 실측 확실 · 같은 글이면 캐시 손해 없음 = 실측(TRD §1-5 표).

## 영향 / 불변식
- 정션 따라가기는 미측이다 — 해당 단계에서 잰다. Noop 재료는 지금 argv 를 바이트 그대로 낸다(S25-V).
- 떠 있는 에이전트는 정션 너머 라이브러리 스킬 폴더를 본다 — 세션 도중 그 폴더를 옮기거나 이름을 바꾸거나 지우면 그 세션이 깨지거나 「파일 열림」 으로 실패한다. 지금 CLI 스킬 폴더와 같은 동작이고 따로 다루지 않는다(G42 · 사용자 「그건 기존에도 똑같은거 아냐?」 · TRD §1-11a 발견 14 닫힘).
- 정션 만들기 · 끄기의 부품 = S25-AH(`junction` 2.1.0 `create` · 끄기 = 링크임을 먼저 확인한 뒤 `std::fs::remove_dir`).

## 결정
*초안*
1. 화면 편집 칸은 초안을 고친다 — 「+ 담기」 팝오버 체크도 초안에 든다 · 저장 안 한 상태는 표시한다 · [저장] 으로 데몬에 보낸다(G52).
2. **초안의 자리 = 셸 쪽 따로 된 초안 파일**(사용자 G54 — VS Code 핫 엑싯 꼴 · 메인 M82 의 셸 메모리 초안과 M77 의 「재시작 · 크래시에 잃음」 을 대체) — Engram 데이터 폴더의 셸 쪽(예 `shell\state\drafts\` — 파일 이름 · 꼴 = 클라이언트 단계)에 쓰고 라이브러리 폴더에는 두지 않는다 · 데몬 · 버스엔 초안이 없다(G52). 초안 파일의 열쇠 = **(라이브러리 번호 · 프리셋 경로) 짝**(M89-REVISED — 이름 · 치우기(예 그사이 지워진 프리셋의 초안)는 클라이언트 단계에서 다시 본다) — Library n 에서 A 를 B 로 바꿔도(LLM · 묻지 않음) A 의 초안 파일은 남고 그 번호에서 A 로 돌아오면 ● 와 함께 되살린다 · 같은 프리셋을 연 두 슬롯 = 초안 둘 · 마지막 저장이 이긴다(G53). 그 번호를 다시 열면(재시작 · 크래시 뒤도) 보기 상태가 마지막에 보이던 프리셋을 그 짝의 초안 · ● 와 함께 보인다 · [저장] 이 성공해 저장 안 됨 표시가 지워지거나(초안이 아직 r — 결정 7) 「저장 안 함」 · [되돌리기](결정 10)를 고르면 지운다 · r 을 보낸 뒤 더 고쳤으면 초안 파일은 남아 그 뒤 고침을 지닌다(M88). 탭 옮기기 · 붙이기 · 떼기(사람 끌기 · 버스 `tab.move` · `tab.dock` · `tab.detach`)와 LLM 의 닫기 · 고르기 바꾸기는 초안을 지킨다 — 파일에 있으니 문 · `CONFLICT` 가 없다(G54). 되살린 초안의 원본이 그사이 바뀌었으면 [저장] 은 마지막 저장이 이긴다(G53 · 세부 = 클라이언트 단계). 셸 → agent 의존 없음은 그대로다(ADR-0270).
3. **초안 검사 = 데몬 읽기 `preset.check {path, instructions, skills, settings, presets}`** — 준 목록을 그 프리셋 자리에 넣어 실행과 같은 해석 함수로 돌리고 `preset.get` 과 같은 충돌 · 문제 꼴을 낸다 · 쓰지 않는다 · 클라이언트는 해석을 다시 짜지 않는다(M80 · TRD §1-3 「같은 함수」). 편집 칸 자기 검사(충돌 줄 · 문제 목록 · 팝오버 「이미 추가됨」 · 순환 흐림)는 초안 위에서 바로 · 라이브러리 전체 상태(트리 ⛔ · 실행 막힘 · 다른 칸)는 저장된 파일만 따른다(M75 — 편집기가 저장 안 한 버퍼에 진단을 보이는 꼴).

*저장*
4. **저장 = 버스 명령 `preset.save {path, instructions, skills, settings, presets, baseRev?}`** — 프리셋의 네 목록을 초안의 것으로 통째로 바꾼다 · 초안 연산을 합치지 않는다 · 화면은 `baseRev` 를 보내지 않는다 — 그사이 디스크가 바뀌었어도(다른 칸 · LLM · 손 고침) 덮는다 = **마지막 저장이 이긴다**(메모장 규칙 — G53). `baseRev` 는 선택이다 — LLM · CLI 가 읽은 뒤 주면 어긋날 때 `CONFLICT` · help 는 LLM 에게 `baseRev` 를 주거나 `add` · `remove` · `reorder` 를 쓰라고 이끈다(M84).
5. **저장 검사 = 전부 아니면 무** — 순환 · 틀린 종류 · `presets` · `settings` 항목의 꼬리표 · 꼴이 틀린 `AssetRef`(`LibPath` 나 `engram:/`) · 목록 안 겹친 항목이 하나라도 있으면 저장 전체를 거절한다 — 안정 코드 + 어긋난 항목 인자 · 아무것도 쓰지 않는다(M78 · M78-REVISED · M85). **없는 경로는 어긋남이 아니다** — 「찾을 수 없음」 줄은 정당한 내용이다(M78-REVISED). 보통은 편집 칸이 초안에서 이미 보이므로(결정 3) 어긋난 것이 저장까지 오지 않는다.
6. 쓰기 = 디스크의 지금 파일에서 그 목록으로 가는 고침을 계산해 `yaml-edit` 로 쓴다 — 주석 · 모양은 S25-AD 대로(G53 — 메인 내부) · 쓰기 문이 거절하면 저장도 같은 코드로 거절된다(S25-AD 결정 4). 그사이 그 프리셋이 옮겨지거나 이름이 바뀌거나 지워졌으면 `NOT_FOUND` — 옛 경로에 파일을 다시 만들지 않는다(부모 · 대상이 있는지 먼저 본다 · `write_atomic` 이 되살리지 않는다 — M76-REVISED-2 · M65).
7. **저장 상태 기계**(M81): 초안은 제 판 번호를 지닌다 · [저장] 은 판 r 을 보낸다 · 성공하면 초안이 아직 r 일 때만 저장 안 됨 표시를 지운다(그 뒤 편집은 저장 안 됨으로 남는다) · 거절(저장 검사 · 쓰기 문 · 루트 세대 · `NOT_FOUND` 등)이면 초안을 지키고 까닭을 보인다 · 성공해도 초안이 r 이 아니면 초안 파일은 남는다(M88 — 결정 2) · 「저장」 을 부른 닫기 · 바꾸기는 저장이 성공하고 **초안이 아직 보낸 판 r 일 때만** 이어 가고, 아니면(그사이 다시 연결 답 등이 초안을 고침) 그 자리에 남아 다시 묻는다(M81-AMEND · 프런트 시험에 그 끼어듦을 넣는다).

*다른 조작과의 관계*
8. **다시 연결 · 옮기기 · 이름 바꾸기와 초안**(M76 · M76-REVISED · M76-REVISED-2): [다시 연결] 은 바로 적용하는 라이브러리 전체 명령(`library.relink` — S25-N)으로 남는다. 그 명령과 `library.move` · `library.rename` 을 낸 **같은 창**이 받은 답의 옛 → 새 대응을 그 창의 열린 초안 줄에도 적용한다(초안 파일 포함 — 그 창이 연 초안 · 클라이언트 몫 — 그래야 뒤의 [저장] 이 그 고침을 되돌리지 않는다). 다른 창의 초안 · 어느 창도 열지 않은 초안 파일(예 LLM 이 탭을 닫은 뒤 — M88) · LLM 이 낸 명령은 초안에 들지 않는다 — 그런 초안을 나중에 저장하면 옛 경로를 되써 그 줄이 다시 「찾을 수 없음」 이 된다(다시 연결로 고친다 · G53 아래 받아들임). 새 방송을 만들지 않는다(「감시 · 방송 없음」 그대로).
9. LLM 의 `preset.add` · `remove` · `reorder` · `setBackend` 는 바로 적용하는 버스 · CLI 명령으로 남는다(버스엔 초안이 없다 — G52). 데몬이 「최신 파일 읽기 → 연산 → 원자적 쓰기」 로 적용 · 판 확인은 `reorder` 만(`baseRev` = 안정 내용 해시 — M21) · `add` · `remove` 는 낡은 판에도 경로로 멱등(M24-8). 명령 하나가 곧 저장 하나다 · 되돌리기 기록은 없다 — 잘못된 에이전트 편집은 다시 고친다(라이브러리가 git 저장소면 git 으로 · G54-ADD).
10. **닫기 · 바꾸기**(메인 — 관행 · G53 · 사용자 G54 · G54-ADD): 사람이 저장 안 된 그 탭 · 슬롯을 닫거나 · 그런 탭이 든 팝아웃 창 하나를 닫거나(= 그 탭들을 닫는 것 — M87) · 그 편집 칸에서 프리셋을 바꾸면 「변경 내용을 저장할까요?」 [저장] [저장 안 함] [취소] 를 묻는다(저장 규칙 = 결정 7). 대시보드 전체를 닫을 때는 묻지 않는다 — 초안 파일이 남아 다음 시작에 ● 로 되살린다(G54 · M87 — 관행: VS Code 는 저장 안 한 편집기가 든 마지막이 아닌 창을 닫을 때 묻고, 핫 엑싯은 앱 끝내기만 덮는다). 버스 · LLM 의 닫기 · 고르기 바꾸기는 묻지도 거절하지도 않는다 — 초안은 파일에 남는다(G54 — 옛 M82 의 `CONFLICT` · `--yes` 문과 OS 닫기 · 앱 끝내기 물음을 걷음). **[되돌리기]** = 초안 파일을 버리고 원본을 다시 읽어 ● 를 지운다(VS Code 「Revert File」 꼴 — G54-ADD · 자리(단추 · 메뉴 · 단축키) = 클라이언트 단계).
11. 에이전트 슬롯의 프리셋 붙이기 · 떼기 · 순서는 초안 없이 바로 적용한다(메인 — 관행 · 사용자 위임 G53) — 검증 뒤 프로필 편집 포트로 간다(M18) · 에이전트 `baseRev` = `default_preset` + `presets` 순서의 안정 해시(M25).

*화면*
12. 화면 꼴(표시 · [저장] · [되돌리기] 자리 · 모달)과 초안 파일(이름 · 꼴 · 되살리기 세부)은 클라이언트 단계에서 정한다(§5-4 · M77 · G54 · G54-ADD). 서버 단계 몫 = `preset.save` · `preset.check` · 버스 연산(데몬엔 초안이 없다 — G52).

## 거부한 대안
- **바로 적용 — 칸마다의 초안 · 저장 단추 없음**(메모 41 · 메모 83 「+ 담기」 팝오버 바로 적용 · 이 초안의 옛 결정 1) — 사용자가 뒤집었다: 「다 수정하고 저장 눌러야되는거 아님? 물론 저장안된건 마킹되있는게 맞고??」(G52).
- **저장 때 초안 연산을 지금 파일에 합치기 · 화면 저장에 「파일이 바뀌었습니다」 묻기(판 확인)** — 사용자 「A가 보는대상하고 B가 보는대상이 다르잖아. 노트패드 룰로 해야될듯? … 그냥 마지막으로 덮으면 되는거 아님?」(G53). LLM · CLI 의 선택 `baseRev` 는 이것과 다르다 — 주는 쪽이 고른다(M84).
- **저장 검사의 부분 적용**(맞는 줄만 쓰기 — `preset.add` 의 Δ7 · G41 꼴) — 저장은 통째 바꾸기라 사용자 초안의 줄을 말없이 버린다(M78).
- **없는 경로도 저장 거절** — 「찾을 수 없음」 줄은 정당한 내용이다(삭제는 되살리기 · 다시 연결까지 그 줄을 남긴다 — P3 · M4) · 막으면 그런 프리셋을 저장할 수 없다(M78-REVISED).
- **클라이언트가 해석을 다시 짜 초안을 검사** — 화면과 실행이 다른 규칙으로 갈린다(M80 · TRD §1-3 「같은 함수」).
- **초안을 셸 메모리에만 두기**(라이브러리 번호마다 `LibraryViewState` 곁 · `state.json` 에 쓰지 않음 — 메인 M82 · M77 · 이 초안의 옛 결정 2 · 10) — 재시작 · 크래시에 초안을 잃고, 버스 · LLM 의 닫기 · 고르기 바꾸기마다 `CONFLICT` · `--yes` 문이 들어야 했다(재리뷰 r10 NF1–NF5). 사용자가 따로 된 초안 파일을 골랐다 — 「ㅇㅇ ㅇㅋㅇㅋ … 클리쪽이라서 나중에 펼치면 되고」(G54 · VS Code 핫 엑싯 꼴).
- **번호만 열쇠로 하는 초안 파일**(Library1–4 — 번호별 보기 상태와 같은 꼴 · 메인 M89 의 첫 꼴) — 그 번호에서 LLM 이 프리셋을 바꾸면(묻지 않는다 — 결정 10) 앞 프리셋의 초안을 덮는다(메인 2026-10-31 M89-REVISED).
- **프리셋마다 초안 하나**(VS Code 의 공유 버퍼 꼴 — 같은 프리셋을 연 칸들이 한 초안을 함께 본다) — 웹뷰 사이 실시간 동기가 든다 · 단순함을 골랐다(메인 2026-10-31 M89 · M89-REVISED — 두 초안의 마지막 저장이 이김은 이미 받아들였다 · G53).
- **초안을 그 슬롯 웹뷰의 클라이언트 상태에만 두기**(TRD 첫 반영 꼴 · 재리뷰 r10 뒤 갈래 B) — 탭이 다른 창으로 옮겨지거나 LLM 이 닫기 · 바꾸기를 하면 초안을 잃는다(G54 가 따로 된 초안 파일로 정했다).
- **다른 창 초안 · LLM 이 낸 다시 연결까지 초안에 반영** — 방송이 없어 닿지 않는다 · 「감시 · 방송 없음」 을 지키고 G53 아래 받아들였다(M76-REVISED).
- (물음 사라짐) 옛 「전부 판 확인」 갈래 — 그 물음을 부른 낡은 화면의 「빼기」(PRD 리뷰 #23 뒤 절반)는 화면이 `add` · `remove` 를 보내지 않게 되어(결정 1 · 4) 없어졌다. 버스(LLM) 연산엔 결정 9 의 멱등 규칙이 그대로다(M24-8).

## 맥락
앱 안 이동 · 이름 바꾸기는 파일 하나와 그것을 가리키는 여러 프리셋 · 에이전트를 함께 고친다. 중간에 끊기면 어떻게 되나.

## 결정
1. 이동 · 이름 바꾸기 · 다시 연결 = 계획 → 실행 → 참조 고침. 순서 = 파일 이름 바꾸기 → 참조하는 프리셋을 하나씩 고침 → 에이전트. 파일 쓰기는 하나하나 원자적이고 **이미 있는 `base::file::write_atomic` 을 그대로 쓴다**(임시 `<이름>.tmp<pid>.<번호>` → sync → 바꿔 넣기 — ADR-0265 결정 4 · ADR-0291 · M56).
2. 진행 기록(일지)이 없다. 중간에 끊기면 일부 참조가 옛 경로를 가리켜 「찾을 수 없음」 이 되고, 다시 연결 한 번이 그 옛 경로의 참조를 전부 고친다(R19 · S25-N).
3. **남은 임시 파일을 저절로 치우지 않는다 — 부팅 때도 훑기 때도**(G40). 라이브러리는 `base::file::sweep_temps` 를 부르지 않는다(M56). 훑기는 base 임시 이름 꼴을 건너뛴다 — 목록에 안 나오고 문제도 아니다(G40 · M56).
4. 탐색기 규칙 — 덮어쓴 파일만 `.trash` 로(P5). 루트 안 이동은 어디로든(S25-B). 이름이 부딪는데 `onConflict` 를 안 주면 그 항목만 실패하고 아무것도 덮어쓰지 않는다 — 호출자가 고른다(M26 · 되살리기의 이름 부딪힘도 같은 꼴).
5. 삭제는 참조를 고치지 않는다 — 자리 = 정체(P3 · M4). 삭제 = 루트 안 `.trash`(S25-W).
6. 에이전트 쪽 참조 고침 = 옛 → 새 대응표만 프로필 편집 포트에 넘기고, manager 가 **지금** 명부 전체에서 맞는 붙임을 명부 락 한 번 보유로 고쳐 바꾼 에이전트를 돌려준다. 계획은 에이전트 목록을 미리 뽑지 않는다(계획의 명부 읽기는 `yes` 판정만). `agent.duplicate` 도 원본 읽기 + 넣기를 한 보유 안에서 해 둘이 줄 선다 — 복제가 먼저면 사본이 고쳐지고, 고침이 먼저면 사본이 새 경로를 싣는다(M36 · 재리뷰 B3).

## 거부한 대안
- **의도를 적어 두는 조작 기록 + 부팅 때 마저 끝내기**(옛 `library-ops\` 일지 롤포워드) — 사용자 「일단 이건 이대로 두고 나중에 생각하자」(G38) · 그런 피어를 못 찾았다(조사 2026-10-31).
- **삭제 때 참조를 휴지통 경로로 고치기**(리뷰 #5) — 사용자 「따로 처리를 해야됨?」(2026-10-20 · P3). 되살리면 경로로 풀린다(P3 · M4).
- **파일마다 고정 정체(사이드카 `.meta` · 파일 안 id · NTFS 파일 id)를 다시 연결 후보로** — 사용자 「나중에 생각하자」(G38 · T-74). 하면 R19 「후보 제안 없음」 을 다시 연다(G38).
- **영구 삭제** — S25-W 의 같은 대안 사유(「영구 삭제 + 센 확인 — 에이전트 호출엔 답할 사람이 없다」)를 본다.
- **바깥 정리 + 이름 다시 연결만**(메모 68 — 앱 안 이동 · 이름 없음 · 사용자 2026-10-14) — 사용자가 2026-10-15 뒤집었다(메모 106 · 107 「이왕 하는 김에 다 해버려」 — 앱 안 옮기기 · 이름 바꾸기 · 삭제를 넣음). 기록된 이유(메모 108): 참조가 라이브러리 루트부터의 경로라 옮기거나 이름을 바꾸는 순간 참조를 고치고 지울 때 알릴 수 있는 것은 Engram 뿐이다 — 앱 안 이동이 없으면 모든 재정리가 이름 다시 연결에 기댄다. 자리 = 2판(P1 — 메인 · 사용자 위임 「알아서 해 순서적인 부분은」).
- **부팅 때 남은 임시 파일 쓸기**(G38 의 세부 「Stray temp files swept at boot」) — 사용자 2026-10-17 「데몬이 켜질 때 미리 훑지 않는다」 와 어긋났고(TRD §1-11a 발견 15) 사용자가 「남기고 알아서 치우라그래」 로 정리 자체를 뺐다(G40). 표본에서 앱 기동 때 훑어 치우는 곳은 없다(조사 atomic-write-temp-cleanup).
- **훑기 때 오래된 임시 파일 치우기**(조사의 둘째 갈래 — Syncthing 24시간 · git `tmp_obj_*` 꼴) — 같은 사용자 결정으로 훑기 때도 치우지 않는다(G40 「not at boot, not at scan」).
- **고정 이름 `<파일>.engram-tmp`**(G40 의 첫 꼴 — 같은 파일의 다음 쓰기가 덮는다 · VS Code `.vsctmp` 와 같은 모델) — 이미 있는 `base::file::write_atomic` 곁의 둘째 규칙이 된다(M56 · 조사 junction-recycle-bin). 대가: 남은 찌꺼기는 다음 쓰기가 덮지 않는다(pid 가 다르다) — 쓰는 도중 죽는 일은 드물어 받아들였다(M56).
- **계획 때 에이전트 목록을 뽑아 그 목록만 고치기** — 그 사이 `agent.duplicate` 가 만든 사본이 옛 경로를 지닌 채 남는다(M36 · 재리뷰 B3).

## 근거
- 사용자 결정 G38 · G40 · P3 · P5 · 조사(2026-10-31).
- 조사 atomic-write-temp-cleanup(light · 리뷰 없음): 흔한 두 갈래 = 안 치움(고정 이름이라 다음 쓰기가 덮는다 — VS Code · git `index.lock` · Rust crate) · 훑기 때 게으르게(알아볼 접두 + 나이 문턱). 공통 = 같은 폴더 · 이름에 앱 표식 · 훑는 쪽이 그 이름을 건너뜀. Windows 에서 이름 있는 임시 파일은 피할 수 없다(`O_TMPFILE` 은 리눅스뿐).
- 조사 junction-recycle-bin(medium · codex 리뷰): `write_atomic` = 확실(`file.rs:348`) · 셸 설정 저장이 이미 쓴다.

## 영향 / 불변식
- 일지를 되살리려면 G38 을 다시 연다. 끊긴 조작의 회복 길은 다시 연결 하나다.
- 공통 뼈대(계획 → 실행 → 참조 고침)는 이동 · 이름 바꾸기 · 다시 연결만 쓴다.
- 찌꺼기 `<이름>.tmp<pid>.<번호>` 가 라이브러리 폴더에 남을 수 있다 — 목록에 안 보이고 지우는 것은 사용자 몫이다(G40). 「훑기가 base 임시 이름 꼴을 건너뛴다」 는 구현 전제다(조사 파일럿 항목).
- 내구성은 임시 파일 sync + 같은 볼륨 rename 까지로만 쓴다 — Windows 의 디렉터리 sync 는 무동작이다(조사 junction-recycle-bin).
- 라이브러리가 `sweep_temps` 를 부르게 바꾸면 G40 을 다시 연다.

# ADR-NNNN (S25-N): 다시 연결 = 하나를 고르면 나머지를 이름으로 잇는다 — 훑기는 후보를 제안하지 않는다

- 상태: 제안 (2026-10-31, 근거: 사용자 결정 B11(2026-10-19 「ㅇㅇ 그게 더 자연스러운것같네」 — D10 해결) · 관행 조사 2026-10-18 · P1 · 메인 M14)
- 관련: PRD R19 · S25-M · 조사 `docs/research/relink-and-error-popup-practice-2026-10-18.md` · §7 8

## 맥락
가리키던 파일이 사라진 참조(바깥에서 옮겼거나 조작이 끊겨서)를 어떻게 다시 잇나.

## 결정
1. 가리키던 것이 없는 줄 = 「찾을 수 없음 · [다시 연결] ×」. [다시 연결] = 같은 종류로 거른 검색 팝오버 · 옛 이름 미리 채움(우리 편의 · 피어 근거 없음) · 열 때 옛 상위 폴더를 다시 읽는다(M14).
2. 사용자 · LLM 이 파일 하나를 고르면 묻지 않고 나머지를 잇는다 — (a) 같은 옛 경로를 가리키는 모든 참조 (b) 옛 폴더가 같았던 다른 찾을 수 없음 항목 중 새 파일의 폴더에 같은 이름이 있는 것(같은 종류만 — M14). 「N개 더 찾아 연결함」 으로 알린다.
3. 훑기 때 후보를 제안하지 않는다 · 고르기 전엔 아무것도 잇지 않는다. 1판부터(P1).

## 거부한 대안
- **이름만 보고 저절로 적용**(메모 68) — 사용자가 찾기를 시작하기 전에 이름으로 다시 연결하는 피어가 없다(§7 8).
- **훑기 때 같은 이름 후보 하나를 제안하고 확인 전까지 막힘 「다시 연결 확인 대기」**(2026-10-18 D10 꼴) — 사용자 「ㅇㅇ 그게 더 자연스러운것같네」(2026-10-19) · 피어는 첫 하나를 손으로 찾게 한다.
- **항목마다 하나씩 고르기** — 관행 = 「N개 더 찾음」(§7 8).
- **리다이렉터 파일**(옛 자리에 새 자리를 가리키는 파일을 남기기) — 결정은 사용자다(메모 68 「No redirector files」 — 이유는 기록에 없다). 근거(메인 2026-10-31 — 보고): 리다이렉터가 할 일이 남지 않는다 — Engram 안 옮기기 · 이름 바꾸기는 그 자리에서 참조를 고치고(S25-M 결정 1 · 메모 106 — 사용자 결정), 바깥 이동은 Engram 이 보지 못해(감시 없음 — 메모 99 · G43) 남길 수가 없다. 그 회복 길이 이 결정의 다시 연결이다.
- (물음 사라짐) **루트를 넘는 다시 연결** — 루트가 하나라(S25-B · G36) 넘을 루트가 없다. §7 8 의 거부 목록에서 걷어도 된다(문서 정리).

## 근거
관행 조사(Premiere 「미디어 연결」 · After Effects · Resolve · Blender — 첫 하나는 사용자가 손으로 찾는다) · 사용자 결정 B11.

## 영향 / 불변식
- 다시 연결은 끊긴 파일 조작의 회복 길이다(S25-M). 훑기 후보 제안을 더하는 것은 G38 의 「파일마다 고정 정체」 재론과 함께 연다.

# ADR-NNNN (S25-O): 백엔드는 에이전트 값 — 설정은 백엔드별 원문 칸만, 모델 충돌 검사 없음, 기본 제공은 「기본」 하나

- 상태: 제안 (2026-10-31, 근거: 사용자 결정 메모 199 · 201(2026-10-18 「그건 에이전트가 골라야지」 · 「그냥 고정해. 백엔드는.」 · 「어 고정해.」))
- 관련: S25-J · S25-K · PRD R35 · D4 · D5 · §7 11

## 맥락
옛 메모 7(2026-10-10~12)은 에이전트를 빈 껍데기로 두고 설정 에셋이 백엔드 · 모델을 고르게 했다(둘이면 오류 · 없으면 실행 안 함 · 바꾸면 새 대화).

## 결정
1. 백엔드는 만들 때 고정되는 에이전트 값이다 — 바꾸려면 새 에이전트(메모 199). 모드(JSON · 터미널)도 같다(메모 201 · D5).
2. 설정 파일 = `description` + 백엔드별 원문 칸(`claude:` · `codex:`)만. 정식 `backend` · `model` 칸이 없다 — 모델도 원문 안이다. 원문은 에이전트 백엔드와 맞을 때만 실린다.
3. 모델 충돌 검사가 없다 — Engram 은 원문을 해석하지 않는다.
4. 기본 제공 프리셋은 「기본」 하나다.

## 거부한 대안
- **설정이 백엔드 · 모델을 정함**(메모 7) — 사용자 「그건 에이전트가 골라야지」 · 「설정을 claude codex 둘다 입력되게 해놓은건 특정 모델의 에이전트 설정되면 설정을 스위칭 하라고 해놓은거잖아. 근데 model을 왜 에이전트가 골라」(메모 199).
- **기본 제공 백엔드 프리셋**(풀 때 양보 · 바꾸기 — 옛 후보 「사용자 백엔드가 있으면 사용할 수 없음」) — 백엔드가 에이전트 값이라 필요가 없다(PRD D4 「백엔드가 에이전트 값이라 백엔드 프리셋이 필요 없다」).
- **`model` 둘 = 충돌** — 검사하려면 CLI 마다 대조표를 갱신 때마다 고쳐야 한다(메모 199 · 사용자 「대조표? 매번 업데이트 받아서 비교된다는거잖아. 그게 아니라 이번에 적용하고 나중에 또 대응해야되면 빼는게 맞고」).

## 근거
사용자 결정 메모 199 · 201(2026-10-18).

## 영향 / 불변식
- 프리셋 편집은 에이전트 백엔드를 바꾸지 않는다 — 그래서 편집 답에 영향받는 에이전트 목록을 싣지 않는다(TRD §1-7).
- 같은 백엔드 칸에 모델이 둘 들면 CLI 가 하는 대로 둔다.

# ADR-NNNN (S25-P): 보는 쪽 상태(번호별 보기 · 접고 펴기)는 셸이 갖고, 키에 데몬 신원을 넣는다

- 상태: 제안 (2026-10-31, 근거: 메모 58 나눔 규칙(사용자가 기록에 동의) · TRD §1-1 · §7 12)
- 관련: S25-X · S25-E(슬롯 안 보기 상태 저장 가름 — G23-NOTE) · ADR-0035 · ADR-0057 · CLAUDE.md 「LLM-우선 제어」 · TRD §5-4

## 맥락
라이브러리 1~4 의 번호별 보기 상태(마지막 폴더 · 칸 폭 · 트리 펼침 · 「기본 제공 보기」)와 접고 펴기 상태를 어디 둘지.

## 결정
1. 보는 쪽 상태는 셸이 권위로 갖는다(`state.json`). 키에 데몬 신원을 넣는다.
2. 컬렉션(즐겨찾기)은 이번 판에 없다(G34). 슬롯 안 보기 상태를 패키지 저장소로 옮길지는 클라이언트 단계에서 정한다(G23-NOTE · S25-E).

## 거부한 대안
- **데몬에** — 보는 쪽 상태다. 클라이언트가 여럿이면 주인이 없다(메모 58 「레이아웃을 데몬에 두지 않는다」 와 같은 이유 — TRD §1-1).
- **웹뷰 `localStorage` 에** — 창(웹뷰)마다 갈려 팝아웃 창의 라이브러리 슬롯과 메인 창 편집 칸이 원천을 나누지 못하고, LLM 이 셸 명령으로 닿지 못한다(TRD §1-1).

## 근거
메모 58: 에이전트가 도는 기계에 묶인 것 = 데몬 · 보는 사람에 묶인 것 = 클라이언트.

## 영향 / 불변식
- 클라이언트 단계가 §1-9~§1-11 을 다시 확정한다(§5-4) — 이 초안의 번호는 그 뒤로 미뤄도 된다.

# ADR-NNNN (S25-Q): 웹뷰 → 데몬 버스 왕복을 완성해 쓴다 — 화면과 LLM 이 같은 명령을 부른다

- 상태: 제안 (2026-10-31, 근거: 메인 M21(보고) · CLAUDE.md 「LLM-우선 제어」 · TRD §3 · §7 13)
- 관련: S25-D · S25-AE · TRD §1-7 · §1-8 · §5 단계 11

## 맥락
라이브러리 · 프리셋 화면이 데몬에 조작을 보내는 길.

## 결정
1. 라이브러리 · 프리셋 · 에이전트 프리셋 조작은 전부 버스 명령이고, 화면과 CLI(LLM)가 같은 명령을 쓴다(M21).
2. 웹뷰 → 데몬 버스 왕복을 완성해 쓴다(`CommandReply` 갈래 · `callCommand` · 넓힌 실행 답 — §5 단계 11). 라이브러리용 wire 메시지를 따로 만들지 않는다(TRD §3).
3. 예외 = 휴지통 비우기(셸 전용 버스 명령 — S25-AE) · 로컬 OS 도우미(폴더 선택 · 열기 · 보이기 — 화면 전용 · 명령 아님)(M21).

## 거부한 대안
- **기능마다 타입 있는 wire 메시지** — 사유: **사용자에게 받을 것**(§7 13 에 거부로만).

## 근거
CLAUDE.md 「LLM-우선 제어」 — LLM 과 사람이 같은 핸들을 흔든다 · 프론트는 렌더링만 소유한다.

## 영향 / 불변식
- 화면 전용 조작 경로를 새로 만들지 않는다(예외는 결정 3 둘뿐).

# ADR-NNNN (S25-R): 서드파티는 목적 포트 · 부품 경계로 감싼다

- 상태: 제안 (2026-10-31, 근거: 조사 `docs/research/third-party-wrapping-criteria-survey-2026-10-14.md` · TRD §1-4 `store.rs` · §7 14)
- 관련: S25-A · TRD §1-12

## 맥락
walkdir · serde-saphyr · 트리 · 표 · 끌기 · 쿼리 같은 서드파티를 어떻게 감싸나.

## 결정
1. 감싸는 단위는 목적이다 — walkdir · std::fs → 「라이브러리 저장소」 포트 하나(`LibraryStore`) · serde-saphyr → 형식 / 트리 · 목록 · 끌기 · 쿼리 → 우리 부품 한 곳씩.
2. 감싸지 않을 것 = 언어 표준 · 어디에나 쓰이는 기반(serde · tokio · React) · 한 곳에서만 쓰는 순수 도우미(조사 결론 3).

## 거부한 대안
- **라이브러리마다 1:1 래퍼** — 감싸는 단위는 라이브러리가 아니라 목적이다(Cockburn 헥사고날 — 조사 결론 2 · 확실) · 얇은 1:1 투과 래퍼는 아래 세부가 그대로 새서 이득이 없다(조사 결론 3 · 가능성 높음 — 통설).

## 근거
조사 결론 1~4(Fowler Gateway · Cockburn 헥사고날 · Spolsky · Rust API Guidelines C-STABLE).

## 영향 / 불변식
- crate 경계를 넘는 공개 API 에 남의 crate 타입을 내보내지 않는다(C-STABLE — 조사 결론 4).
- 무엇을 감싸는지(부품 고름)는 S25-AH 이고 이 초안은 감싸는 단위만 정한다.
- (클라이언트 몫 메모 — 2026-10-31 프론트 조사 · 잠정) 트리 react-arborist 는 자기 끌기(react-dnd)에 묶여 있고 「트리 · 목록 · 폴더 줄이 react-dnd 관리자 하나를 나눈다」 는 주장은 조사가 거뒀다 — 옮길 id 를 자기 트리 상태에서 가져오므로 목록 → 트리 · 트리 → 트리 이동엔 우리 쪽 놓기 어댑터가 필요하다(`docs/research/frontend-tree-dnd-virtualization-2026-10-31.md`). 「끌기 → 우리 부품 한 곳」 이 그 어댑터 자리다. 메모 113 의 `@dnd-kit/core` 는 arborist 를 못 몬다 — 클라이언트 단계에서 다시 정한다.

# ADR-NNNN (S25-U): 실행 전처리는 예약 · 떠 있음 확인 뒤, 세션 파생 앞 — 명부 변경은 mutate 한 번

4. 무인 기본값 채움은 다음 주제(M16). 작업 폴더 맞추기 · Engram 폴더 몫은 §8.

- **예약 앞** — 같은 에이전트의 두 실행이 겹친다(§7 17).

## 근거
TRD `/review trd` 2회차 두 리뷰어 FIX 반영 — 전처리를 예약 · 떠 있음 확인 바로 뒤로 + 명부 변경 mutate 한 번(비교-교체)(TRD 머리 이력).

# ADR-NNNN (S25-V): 숨은 settings 조각을 없앤다 — claude 원문은 붙인 순서로 `--settings` 파일 하나에 합친다

- 상태: 제안 (2026-10-31, 근거: 사용자 결정 T10(2026-10-18 「프리셋으로 해줘. 사실 감추는 설정이 있으면 안되지.」 · 「이어붙이기 진행」))
- 관련: **Amends ADR-0109 결정 9**(조각 부분 — 아래) · ADR-0099(mcp-config 수명주기) · S25-F · S25-J · PRD R32 · TRD §1-2 · §1-5 표 · §3 합침 규칙 · §7 19

## 맥락
지금 제어 채널은 스폰마다 `{"allowedMcpServers":[{"serverName":"engram"}]}` 단일 키 조각 파일을 `--settings` 로 싣는다(ADR-0109 결정 9 · `control/mcp_config.rs`). S25 는 프리셋의 claude 원문 설정도 `--settings` 로 싣는다.

## 결정
1. 숨은 settings 조각이 없다. `allowedMcpServers:[{serverName:"engram"}]` 와 `DISABLE_AUTOUPDATER` 는 기본 제공 「기본」 의 claude 원문(`engram:/settings/default`)에 보이게 든다.
2. 붙은 프리셋(「기본」 포함)의 claude 원문을 붙인 순서로 휘발 폴더 `settings.json` 하나에 합쳐 `--settings` 하나로 싣는다. 합침 = 값은 나중 것 · 객체는 재귀 · 목록은 이어 붙이고 같은 값은 하나 · 키마다 다른 규칙 없음 · Engram 우선 규칙 없음. 합치는 쪽은 backend 설정 검사 포트(S25-I).
3. 실 재료면 제어 채널 조각(`ControlEndpoint.settings_file`)을 싣지 않는다. `NoopLaunchKits` 는 지금 그대로 싣는다(argv 바이트 같음).
4. `--mcp-config` 는 범위 밖이다(실행 인자 그대로 · 프리셋 아님).

## 바뀌는 조항 (ADR-0109 결정 9)
- 바뀜: 「조각은 `allowedMcpServers` 단일 키 유지(잡동사니화 금지 — 회귀 테스트로 고정)」 → 조각이 없고 그 키는 「기본」 원문으로 옮긴다. 「mcp-config 디렉토리 · 스윕 · revoke 수명주기에 동승」 → 합친 파일은 실행 재료 휘발 폴더(`daemon\run\launch\` — TRD §1-4)에 산다.
- 그대로: 「`--settings` = 파일 경로 주입(인라인 JSON 아님)」 과 그 사유(`cmd /c` 따옴표 붕괴).
- **원천에 없음(확인 필요)**: 「쓰기 실패는 warn+계속」 이 새 판에서 어떻게 되는지.
- Noop 길은 걷힐 때까지 결정 9 그대로 돈다.

## 거부한 대안
- **숨겨 주입하는 조각** — 사용자 「사실 감추는 설정이 있으면 안되지」(T10).
- **`allowedMcpServers` 는 Engram 값이 권위**(옛 추천 — 프리셋의 그 키는 버리고 경고) — 사용자가 숨은 설정 없음을 골랐다(T10).
- **목록 갈아 끼우기** — 사용자 「이어붙이기 진행」. 귀결: 뒤 프리셋이 `engram` 을 못 뺀다 — 받아들였다.
- **두 번째 `--settings`** — 동작이 문서에 없고 재지 않았다.
- **원문을 안 싣기**(프리셋의 claude 원문을 싣지 않기 — 2026-10-15 TRD 첫 판부터 이름만 적힌 갈래) — 근거(메인 2026-10-31 — 보고): 설정 에셋은 백엔드별 원문 칸이고 claude 칸은 `--settings` 로 넘긴다(PRD R5 — 사용자 2026-10-18) — 싣지 않으면 claude 에이전트에겐 설정 에셋이 하는 일이 없다. 또 T10 이 Engram 통로 키를 「기본」 의 claude 원문으로 옮겼으므로 원문을 안 실으면 그 키가 빠지거나 숨은 조각으로 돌아가야 한다(T10 — 사용자 「사실 감추는 설정이 있으면 안되지」).

## 근거
사용자 결정 T10(2026-10-18) · TRD §2-2 T10.

## 영향 / 불변식
- 「기본」 을 떼면 Engram 메시지 · 제어 통로가 빠질 수 있다(사용자 전역 설정이 `allowedMcpServers: []` 로 막을 때) — 떼기 확인 문구가 그것을 말한다(R32 · `DetachDefaultConfirm`).
- 합친 claude settings 도 검사한다 — 오류는 그것을 들인 나중 에셋 줄에 붙는다(M14).
- ADR-0109 의 앵커 `mcp_config.rs`(settings 조각)는 Noop 길에만 남는다.

# ADR-NNNN (S25-W): 삭제 = 라이브러리 루트 안 우리 숨은 `.trash` 의 묶음 폴더로 옮긴다

- 상태: 제안 (2026-10-31, 근거: 사용자 결정 B8 / F9-confirmed(2026-10-19 「ㅇㅇ 우리 trash 폴더로해」) · G31(2026-10-30 「휴지통 경로 … 시스템에서 알아서 보내는게 맞는것같은데 고정경로로하고 나중에 변경경로로」) · G44(2026-10-31) + 메인 M22 · M46 · M52 · M53(보고) · 조사 `docs/research/trash-unavailable-delete-practice-2026-10-19.md`)
- 관련: S25-B · S25-M · S25-AE · S25-AG(휴지통 잠금) · PRD R18 · TRD §1-1 · §1-4 `store.rs` · §6-5 1 · §7 20

## 맥락
라이브러리 항목을 지울 때 어디로 보내나. 사람 · LLM · CLI 가 다 지운다.

## 결정
1. 삭제 = 라이브러리 루트 안 숨은 `.trash` 로 옮긴다. 자리 = 시스템이 정한 고정 `<루트>\.trash\` — 바꿀 수 있는 자리는 필요가 생기면 나중(G31).
2. 같은 루트 안 rename 이다. 트리 · 목록 · 검색에서 숨긴다. 루트 자체는 못 지운다. LLM · CLI 삭제도 같은 곳으로 간다.
3. 루트가 git 작업 트리면 그 저장소의 `.git/info/exclude` 에 `.trash/` 를 더한다(로컬 · 커밋 안 함 — M22).
4. **조작 하나 = 묶음 하나** — `.trash\<UTC>-<id>\` 폴더 안에 원래 경로대로 둔다. 삭제 · 덮어쓰기로 밀려난 파일(P5) 모두 이 길로 가고, 두 파일을 밀어낸 이동도 묶음 하나다(M46 · M52 · M53). 비우기는 이 묶음 폴더를 통째로 OS 휴지통에 보낸다(G44 · S25-AE).
5. `.trash` 로 옮기기 · 되살리기는 휴지통 잠금으로 비우기와 줄 선다(S25-AG 결정 9).
6. 비우기 · 영구 삭제 = S25-AE.

## 거부한 대안
- **삭제를 OS 휴지통으로**(platform 의 전용 STA 작업 스레드가 부르는 `IFileOperation` — 2026-10-18 까지의 후보) — 휴지통 대신 말없이 영구 삭제할 수 있고(Microsoft 문서 `FOF_WANTNUKEWARNING` — UI 없이 부르면 그 경고가 묻힌다 · 네트워크 드라이브 · 휴지통 없는 볼륨 · 용량 초과) · 비우기를 사람만으로 묶을 수 없다(탐색기 · 다른 도구가 비운다)(§7 20).
- **`trash` crate** — 같은 OS 휴지통 길에 셋째 `windows` 사본 · `CoInitialize` 실패 패닉(§7 20). 비우기 길에서도 걷었다 — 항목마다 보고가 없다(S25-AE · M57).
- **OS 휴지통을 못 쓰면 거절**(옛 F8(b)) — `.trash` 가 같은 볼륨 rename 이라 물음 자체가 사라졌다(결정 기록 F9-confirmed).
- **영구 삭제 + 센 확인**(VS Code 꼴) — 에이전트 호출엔 답할 사람이 없다(§7 20).
- **중앙 휴지통 한 곳** — 드라이브를 넘는 복사가 필요하다(G31 — 같은 볼륨 rename 이 빠르고 반쯤 옮긴 상태가 없다). ★이 사유는 여러 루트 시절(G25)에 든 것이다★ — 루트 하나(S25-B)에서도 그대로 서는지는 다시 보지 않았다.
- **바꿀 수 있는 휴지통 자리** — 필요가 생기면 나중(G31 「고정경로로하고 나중에 변경경로로」).

## 근거
사용자 결정 B8 · G31 · 조사(2026-10-19 — 앱 전용 `.trash` 선례 = Obsidian).

## 영향 / 불변식
- 그 밖의 `library.*` 는 `.trash` 아래를 가리키지 못한다(뒷문 막기 — S25-AE).
- 에이전트 자신의 `rm` · 파일 도구는 `.trash` 를 우회한다 — 받아들였다(P13).

# ADR-NNNN (S25-X): 번호별 보기 상태 = 셸 권위 + `libraryView.*` 셸 명령 — `Library{n}` 유일성은 레이아웃 관리자가 지킨다

- 상태: 제안 (2026-10-31, 근거: TRD §1-7 · §1-9 · §7 21 · CLAUDE.md 「LLM-우선 제어」)
- 관련: S25-P · ADR-0035 · ADR-0057(레이아웃 · 창 · 탭 · 슬롯은 백엔드 소유) · ADR-0055 · ADR-0064(`__engramCmd`) · TRD §5-4

## 맥락
라이브러리 1~4 의 보기 상태를 사람 몸짓과 LLM 이 같은 핸들로 바꾸게 하고, 같은 번호의 슬롯이 둘 생기지 않게 해야 한다.

## 결정
1. 번호별 보기 상태는 셸이 권위로 갖고 `libraryView.*` 셸 명령으로 바꾼다. 셸이 상태를 바꾸고 그 번호의 슬롯을 가진 창에만 `library-view:updated {number, state}` 를 쏜다. 화면은 사람 몸짓도 같은 명령으로 보내고 받은 상태를 그리기만 한다.
2. `Library{n}` 유일성은 레이아웃 관리자가 슬롯 내용을 쓰는 단일 길(`write_slot_content` — `set_slot_content` · 버스 `layout.setSlotContent` 가 지난다)에서 지킨다 — 같은 번호가 어느 창에든 있으면 `CONFLICT` · 복원은 같은 번호의 둘째부터 빈 슬롯 + 복원 경고 · 슬롯 옮기기는 통과. `slot.openUnique` 는 그 위의 편의(있으면 포커스)다.
3. 새 전역 핸들 · 웹뷰 레지스트리 명령을 만들지 않는다.

## 거부한 대안
- **웹뷰 레지스트리 명령** — 사유: **사용자에게 받을 것**(§7 21 에 거부로만).
- **열기 명령에서만 유일성** — 사유: **사용자에게 받을 것**(같음).

## 근거
CLAUDE.md 「LLM-우선 제어」 — 레이아웃 · 창 · 탭 · 슬롯은 백엔드 소유 · 기존 표면에 얹고 새 전역 핸들을 늘리지 않는다.

## 영향 / 불변식
- 슬롯 내용을 쓰는 길을 둘째로 만들면 유일성이 샌다.
- 클라이언트 단계 재확정 대상(§5-4).

# ADR-NNNN (S25-Y): 편집 칸 · 실행이 알리는 것은 충돌뿐이다 — 경고 범주가 없다

- 상태: 제안 (2026-10-31, 근거: 사용자 결정 2026-10-18 · B3(2026-10-19) + 메인 M19 · G28 · TRD §7 22)
- 관련: S25-K(codex 터미널 알림 — 사용자 예외) · S25-Z · S25-AA · PRD R22 · R51

## 맥락
편집 칸과 실행이 사용자 · LLM 에게 무엇을 알리나.

## 결정
1. 알리는 것은 충돌뿐이다 — 경고 범주가 없다. 충돌 줄 = 걸린 항목 전부 + 각자 온 길 · 실행 막힘 사유와 같은 줄.
2. 편집 칸 위 문제 목록(B3)은 그 줄들과 줄 상태(찾을 수 없음 · 오류)를 위에 모아 보일 뿐이고 경고 범주를 되살리지 않는다.
3. 막지 않는 알림 목록 `notices`(codex 터미널이 싣지 않은 것 · 이 백엔드에 안 실리는 흐린 줄 · 스키마 흐림 — M19 · G28)는 사실 알림이지 경고 범주가 아니다. codex 터미널 알림은 P4-FINAL 의 사용자 예외다.

## 거부한 대안
- **노랑 경고 줄**(「다음 실행은 새 대화」 · codex 크기 한도 올림 · 문맥 차지 비율 · 자동 다시 연결) — 어떤 편집이 새 대화를 부르는지 같은 규칙은 바뀔 수 있어 화면이 그것을 따라 계산하게 되고, 옛 대화는 옛 목록에 남아 잃지 않는다(사용자 이유 · 2026-10-18).

## 근거
사용자 결정 2026-10-18.

## 영향 / 불변식
- 새 경고 범주를 더하지 않는다. ★원천 어긋남 확인★ — codex 모르는 키는 ⚠ 이고 CLI 가 「경고 — <경로> · <키> · <이유>」 줄을 낸다(TRD §1-4 `validate.rs` · §1-7 — S25-Z). 이 결정과 어떻게 맞는지 원천이 말하지 않는다.

# ADR-NNNN (S25-Z): 설정 검사 = 프로세스 안에서 가볍게 — 문법 + 스키마, 읽을 때마다

- 상태: 제안 (2026-10-31, 근거: 사용자 결정 2026-10-18 · P10 · P10-ADD + 메인 M2 · M18 · M45 · M49 · TRD §7 23)
- 관련: S25-I · S25-Y · S25-AF · S25-AG · S25-AH · TRD §1-4 `validate.rs` · 실측 `docs/research/settings-asset-validation-spike-2026-10-17.md` · 조사 `docs/research/yaml-schema-https-crates-2026-10-31.md`

## 맥락
설정 에셋(claude 원문 JSON · codex `-c` 줄)을 언제 · 얼마나 검사하나.

## 결정
1. 프로세스 안에서 가볍게 — 문법(YAML) + 스키마, Engram 이 읽을 때마다.
2. 스키마가 아는 키의 타입 · 범위 오류 = 실행을 막는다.
3. 모르는 키 = claude 는 알리지 않는다 · codex 는 ⚠ 만(막지 않음). 가진 스키마가 설치된 CLI 보다 낡았으면 모르는 키는 흐림 「이 판 스키마로는 확인 못 함」(P10-ADD).
4. 스키마 = 배포판 한 벌 + 데몬이 뒤에서 갱신(캐시 = S25-AF). 실패하면 가진 것을 쓴다 · 스키마가 없어서 막는 일은 없다(P10).
5. 백엔드마다 다른 것(스키마 출처 · 판 읽기 · 원문 → JSON · 모르는 키 처리)은 backend 설정 검사 포트가 낸다(S25-I).

## 거부한 대안
- **실행 직전 CLI 검사**(`claude --settings … doctor` · `codex debug models`) — 사용자 「가볍게하는걸로하고 나중에 문제되면 차후에 고려하자」.
- **「모두 검사」 메뉴 · `library.validate`** — 새로 고침이 덮는다(§7 23).
- **편집기 포커스 때 다시 읽기** — 사용자 「너무 복잡하게 할 필요는 없는것같아」.

## 근거
사용자 결정 2026-10-18 · P10 · 실측 스파이크(2026-10-17).

## 영향 / 불변식
- 검사는 실행을 기다리게 하지 않는다 — 스키마 받기는 락 밖 뒤에서 한다(P10).
- 원천 어긋남 확인: S25-Y 영향 참조(codex ⚠ 와 「경고 범주 없음」).
- **새 스키마가 오면 다시 검사도 `Catalog` 변경이다** — 번호표 · 변경 세대를 지고 파싱 캐시의 검사 결과까지 고친다(S25-AG 결정 8 · M45 · M49). 남는 것(받아들임): 첫 훑기의 바꿔 끼우기와 다시 검사 사이에 답한 읽기는 옛 스키마 결과를 보일 수 있다 — 다음 질의가 맞다(M45 · TRD §1-11a 시나리오 8).
- 부품(2026-10-31 조사): 검사기 = `jsonschema` 0.60.2(TRD 의 0.59.0 에서 올림) · 받기 = `ureq` — S25-AH. 두 대상 스키마가 draft-07 이라 포맷 검증 정책을 코드에 밝힌다(조사 yaml-schema-https).

# ADR-NNNN (S25-AA): 실행 막힘 = 한 범주 · 요청 한 번 · 구조 있는 오류 답 — 사람이 낸 실행만 막힘 창을 띄운다

- 상태: 제안 (2026-10-31, 근거: 사용자 결정 2026-10-18 · G13(2026-10-20 「저거 띄우면 되는거 아니냐」 · 「단독 슬롯으로되야함. 왜냐하면 창 크기에 막히면 안되니깐」) · G13-AMEND · G15 · P4-FINAL · P11 · G41(2026-10-31 「ㅇㅇ」 — 추천대로) + 메인 M15 · M19 · M21 · M27 · M42(보고 — 재리뷰 A1 · R2 C4))
- 관련: S25-Y · S25-K · CLAUDE.md 「LLM-우선 제어」 · ADR-0283(창 만들기는 `WebviewEnv::finish`) · TRD §1-3 8 · §1-5 (가) · §1-9 · §1-10 · §7 24 · 조사 `docs/research/launch-blocked-popup-navigation-practice-2026-10-20.md`

## 맥락
붙은 프리셋에 문제가 있으면 실행을 막는다. 누가 실행하든 같은가, 어떻게 알리나.

## 결정
1. 실행 막힘 = 사유 넷의 한 범주(2026-10-19 「다시 연결 확인 대기」 · 2026-10-20 「codex 파일 사전 검사 실패」 를 걷음 — P4-FINAL). 누가 실행하든 막는다.
2. 실행 = 요청 한 번. 막힘 = 구조 있는 오류 답(`CommandError` 인자 칸 · 넓힌 wire 활성화 답 · CLI 는 0 아닌 종료 — G15 · M19).
3. 사람이 낸 실행(더블클릭 · 메뉴)이 막히면 그 에이전트의 프리셋 편집 칸을 에이전트 트리 줄 옆 따로 된 떠 있는 OS 창(막힘 창)으로 띄운다 — 주인 = main 창(전역 늘 위 아님 — M15) · × · Esc 로만 닫힌다 · 고치기는 그 안에서 · 라이브러리는 사용자가 파일로 갈 때만(G13-AMEND) · 슬롯 배지 · ⛔ 줄이 남는 기록.
4. LLM · CLI 실행은 창 없이 트리 ⛔ + 코드 + 인자.
5. 막힘 창의 그 밖 수명(여럿 · 다시 열기 · 트레이 등)은 다음 주제(P11).
6. **막힘 답의 바깥 오류 코드**(M27 · M42): 있는 에이전트 깨우기 = `CONFLICT` + 사유 인자. 에이전트를 **만드는** 동사(`agent.spawn --cwd` · `agent.new {presets}`)는 만들기 전에 만들 프로필(명부 밖)로 점검하고, 거기서 막히면 `CONFLICT` · 아무것도 만들지 않는다. 만든 **뒤** 난 막힘(다시 점검 · 비교-교체 실패 · 경합 — `agent.spawn --cwd` 가 활성화 전에 명부에 올린 틈에 `agent.setWorkspace` 가 예약을 가져간 경우 포함)은 번호를 붙드는 `INTERNAL`(ADR-0122) + 만든 에이전트 id + 사유 인자다.
7. **`agent.new {presets}` 의 안 맞는 프리셋 = 부분 적용**(G41 · Δ7 — `agent.attachPreset` 과 같은 규칙): 안 맞는 것은 건너뛰고 맞는 것만 단 채 만들며 건너뛴 것을 답에 싣는다(답 꼴 = 붙이기의 부분 적용 결과와 같음).

## 거부한 대안
- **화면 실행만 막고 버스 · CLI 는 기본값으로 진행**(옛 Δg 갈래) — 사용자가 2026-10-18 「누가 실행하든 막는다」 로 정하며 「화면 실행만 막힘」 범주를 걷었다(메모 205 「막는게 좋을듯」 — 기록된 까닭 = 명시로 붙인 부품은 필수라 없으면 막는 관행 · `docs/research/launch-missing-component-practice-2026-10-18.md`). 근거(메인 2026-10-31 — 보고): CLAUDE.md 「LLM-우선 제어」 — LLM 이 메인 조작 주체이고 사람과 같은 핸들을 흔든다. 버스 · CLI 만 기본값으로 넘기면 같은 실행이 부른 쪽에 따라 다르게 돈다 · LLM 은 같은 막힘 사유를 코드 + 인자로 받는다(결정 4 · P7AC).
- **모달** — 관행상 모달은 심각한 · 앱 전체 오류에만 쓴다 · 사용자 「모달에 아니라 그냥 뜨는 팝업」.
- **에이전트 곁 비모달 카드에 막힌 항목 이유 + 링크 → 라이브러리**(2026-10-18 꼴) — 사용자 「저거 띄우면 되는거 아니냐」(2026-10-20)로 편집 칸 자체를 띄운다.
- **main 창 안에 띄우기** — 사용자 「단독 슬롯으로되야함. 왜냐하면 창 크기에 막히면 안되니깐」.
- **바깥 누름에 닫기** — 거기서 라이브러리를 열면 창이 사라진다(G13-AMEND · 관행 = 남는 패널 Unreal Compiler Results).
- **실행 앞 점검 명령 `agent.launchCheck` + 실행(요청 두 번)** — 앞 점검과 실 점검의 경합(G15) · 사용자 「패킷을 왜 두번보냄? 한번 보내고 실패하면 팝업 띄우는거고 아니면 실행하는거 아님?」 · M21 이 명령째 걷었다.
- **막힘을 `INTERNAL` 로 답하기**(바깥 코드 없음) — 번호를 붙드는 규칙(`retains_the_id`)이 고친 뒤 같은 번호로 다시 보낸 실행을 `ALREADY_APPLIED` 로 삼킨다(TRD §1-11a 발견 2 · M27).
- **만든 뒤 난 막힘도 번호를 놓고 `CONFLICT`** — 재시도가 에이전트를 하나 더 만든다(ADR-0122 · 발견 2 · M27).
- **`agent.setWorkspace` 와의 틈에 진 `agent.spawn --cwd` 를 `CONFLICT` 로** — 그때는 이미 명부에 올라 알려진 뒤라 만든 뒤 막힘이다(M42 · 재리뷰 R2 C4).
- **`agent.new` 의 안 맞는 프리셋 = 통째로 거절 — 아무것도 안 만들고 `CONFLICT`**(발견 7 의 옛 갈래) — 사용자가 부분 적용을 골랐다(G41 · 붙이기와 같은 규칙).

## 근거
사용자 결정 2026-10-18 · 2026-10-20(G13 · G15) · G41(2026-10-31) · 관행 조사(2026-10-20) · 재리뷰(2026-10-31 — M27 · M42).

## 영향 / 불변식
- `CommandError` 에 인자 칸이 생긴다(command crate 변경 — M19).
- 막힘 창이 서는지(테두리 없는 · 주인 main · 줄 옆 · 다중 모니터 · DPI)는 재지 않았다 — 해당 단계 앞에 재고 안 되면 멈추고 사용자에게 돌아간다(TRD §6-2).
- 막힘 창 부분(결정 3 · 5)은 클라이언트 단계 재확정 대상(§5-4) — 그 부분의 번호는 클라이언트 단계로 미뤄도 된다. (2026-10-31 프론트 조사 메모 · 잠정) 따로 된 Tauri 창(`parent` · `WebviewEnv::finish` 를 지남)을 그대로 둔다 — 창 안 모달은 작은 main 창을 벗어나지 못한다 · 그 창의 Tauri capability 는 미확인(`docs/research/frontend-popover-query-modal-markdown-2026-10-31.md`).

# ADR-NNNN (S25-AB): 작업 폴더는 에이전트 값 — 대화 뒤 · 떠 있는 동안 잠근다

- 상태: 제안 (2026-10-31, 근거: 사용자 결정 2026-10-18 · D3 · P2-REVISED · 「ssi 박히잖아. 그게 있으면 못바꾸게」 · 「대화 뒤 잠금은 있어야지」 + 메인 M28 · M32 · M42(보고 — 재리뷰 A2 · A6 · R2 C4))
- 관련: ADR-0226(첫 제출 래치 — 영속된 세션 id) · ADR-0006(락 순서) · ADR-0122 · S25-AA(만든 뒤 막힘) · TRD §1-5 「작업 폴더 `cwd`」 · 「`display_name` 고정」 · §8 · §7 25

## 맥락
에이전트의 작업 폴더를 어디서 정하고 언제 바꿀 수 있나.

## 결정
1. 작업 폴더 = 에이전트 값. 에이전트 슬롯 「작업 폴더」 칸 + `agent.setWorkspace {agent, cwd}` 로 바꾼다. 만들 때 폴더 선택(`cwd` 필수)은 지금 그대로.
2. 영속된 backend 세션 id 가 있거나(대화 뒤 — ADR-0226) 떠 있으면 바꿀 수 없다. 잠긴 까닭 문구는 둘(실행 중 · 대화함 — P2-REVISED).
3. 대화 전에만 바뀌므로 놓을 세션이 없다 — 세션 놓기 로직을 짓지 않는다.
4. **`agent.setWorkspace` 는 그 에이전트의 스폰 예약(RAII)을 쥔 채** 잠금 확인 · `cwd` 바꾸기를 한다 — `spawning` 잎 락을 쥔 채 프로필을 쓰지 않는다(ADR-0006). 예약을 setWorkspace 에 진 스폰 = `CONFLICT`(작업 폴더 바꾸는 중) · setWorkspace 가 스폰의 예약을 만남 = `CONFLICT`(실행 준비 중). 예약 표는 쥔 쪽의 종류를 가른다(꼴은 구현 판단 — M28). 예외 = `agent.spawn --cwd` 가 활성화 전에 명부에 올린 틈 — 그 스폰은 만든 뒤 막힘 길(`INTERNAL` + 만든 id — S25-AA 결정 6 · M42).
5. **이름이 `cwd` basename 에서 파생 중이면(`display_name` 없음) setWorkspace 가 `cwd` 를 바꾸기 전에 같은 예약 안에서 지금 이름을 `display_name` 으로 고정한다** — 작업 폴더 바꾸기가 말없이 이름(우편 주소 · 트리 이름)을 바꾸지 않게(M32).

## 거부한 대안
- **대화 뒤에도 바꾸고 다음 실행을 새 대화로 맞추기**(`launched_workspace` · `release_session_id` — §8 에 옮겨 둔 옛 설계) — 사용자 「대화 뒤 잠금은 있어야지」.
- **작업 폴더를 프리셋 부품으로** — 라이브러리 종류를 늘리지 않는다(D3 추천).
- **`spawning` 잎 락을 쥔 채 잠금 확인 · 프로필 쓰기** — 잎 락을 쥔 채 밖을 부르는 락 순서 위반이다(ADR-0006 · M28 · 재리뷰 A2).
- **예약을 진 스폰을 `Moot(None)` 으로** — 말없이 안 뜬다 · M28 이 사유를 실은 `CONFLICT` 로 바꿨다.

## 근거
사용자 결정 2026-10-18 · D3 · 재리뷰(2026-10-31 — M28 · M32 · M42).

## 영향 / 불변식
- 경로 없는 생성 · 자동 경로 · 묶는 폴더 = 다음 주제(§8). 대화 뒤에도 바꾸는 길을 열면 거부한 대안 1 의 옛 설계를 다시 꺼낸다.

## 결정

# ADR-NNNN (S25-AD): 프리셋 YAML 편집은 손 주석 · 모양을 보존한다 — `yaml-edit =0.3.5` + 조건 셋

- 상태: 제안 (2026-10-31, 근거: TRD 결정 T2(2026-10-18 관행) · 사용자 「없으면 관행대로 처리해」 · G48(2026-10-31 「보통 메모 지킴은 맞는데 그걸 위해 별도로 노력할 필요는 없음 … 어쨋든 그 라이브러리에 맞게 하면 될것같음」) + 메인 M61(0b 스파이크) · M68(2차 측정) · M73(보고) · 스파이크 `docs/research/yaml-comment-preserving-edit-spike-2026-10-31.md`)
- 관련: S25-L · S25-R · S25-AH(읽기 = serde-saphyr) · TRD §1-4 `format.rs` · §1-12 · §5 0b · §7 27 · 앞선 관행 조사 `docs/research/yaml-comment-preserving-edit-2026-10-18.md`

## 맥락
데몬이 프리셋 파일을 고칠 때(붙이기 · 빼기 · 순서 · 꼬리표) 사람이 쓴 주석 · 모양이 남느냐. 0b 스파이크가 손 주석 14개 · 목록 넷인 실제 꼴 프리셋으로 두 편집기를 재었다(연산마다 새 사본 · `diff` · serde-saphyr 로 다시 읽어 값 대조 · CRLF/LF 셈).

## 결정
1. 읽기 = serde-saphyr · 쓰기 = `yaml-edit` **`=0.3.5` 로 판을 박는다**(M61) — 패치 판마다 동작이 바뀐다(0.3.2 → 0.3.5 사이 다섯 연산의 결과가 달라졌다 · 0.3.3~0.3.5 가 이틀에 셋 나왔다).
2. 조건 셋(M61):
   ① **순서 바꾸기 = 빼기 + 뺀 노드 글을 그 노드의 원래 내용 칸(CST 오프셋)만큼 내어 쓰고 다시 읽어 넣기**(주석 · 빈 줄은 건너뛴다 — M73 · 옛 고정 칸은 들여쓰기 없는 꼴 · 4칸 꼴에서 틀렸고(M68) 「둘째 줄부터 공통 들여쓰기」 도 M73 이 대신했다) — 이동 API 가 없고, 0.3.5 에서 뺀 노드를 그대로 다시 넣으면 맵 항목이 다시 못 읽는 YAML 이 된다(0.3.2 에서 되던 것의 회귀). 우회는 실측으로 통했다(줄 끝 주석도 따라감). 새 값으로 다시 만들어 넣으면 값은 맞지만 그 항목 줄 끝 주석을 잃는다.
   ② **소스가 빈 흐름 목록 `[]` 이면 첫 항목 때 새 블록 `Sequence` 로 바꿔 끼운다** — 그대로 넣으면 흐름 꼴 `[x]` 로 남는다.
   ③ **골든 시험 + `format.rs` 의 문** — 쓰기 전에 출력을 serde-saphyr 로 다시 읽어 의도한 값과 견주고, 어긋나면 쓰지 않고 거절한다(결정 4 — 안정된 코드 + 걸린 앵커 이름 · serde 다시 쓰기로 물러나지 않는다 · G48). 스파이크에서 본 깨진 출력을 이 문이 다 잡았다.
3. TRD 0b 의 물러날 자리(serde 로 다시 쓰고 손 주석 잃음)는 쓰지 않는다.
4. **쓰기 문이 거절하면 거절한다** — 안정된 코드 + 걸린 앵커 이름을 인자로 답하고 serde 다시 쓰기로 물러나지 않는다(G48 · U3 (a) — 「별도로 노력할 필요는 없음」 을 메인이 이렇게 옮겨 보고). 2차 측정에서 문이 거절한 것은 앵커 · 별칭으로 나눠 쓰는 값의 고침뿐이다(2/220 · 앵커가 없으면 0/200 — M68).
5. **주석 보존을 위해 더 하지 않는다**(G48) — 조건 셋까지가 전부다(값을 견주는 쓰기 문은 주석이 아니라 값의 정확성을 지키므로 남는다). 알려진 틈(받아들임 — G48): ① 뺀 항목 **위** 주석 줄은 제자리에 남아 다음 항목의 주석처럼 읽힌다 · 중간 넣기도 새 항목이 다음 항목 윗줄 주석 아래로 든다(M61) ② 흐름 목록 안 순서 바꾸기는 옮긴 항목의 줄 끝 주석을 잃을 수 있다 ③ 제자리 값 고침은 따옴표 꼴을 잃을 수 있다(U4 · M68 · M74).

## 닫힌 물음(G48)
- 항목을 빼면 그 **위** 주석 줄이 제자리에 남아 다음 항목의 주석처럼 읽히는 것(두 편집기 공통 · 줄 끝 주석은 함께 간다 — M61) — 받아들였다(결정 5 ①). 윗줄 주석을 함께 지우는 길(`yaml-edit` 의 주석 노드 API)은 재지 않았고 짓지 않는다(G48 「별도로 노력할 필요는 없음」).

## 거부한 대안

# ADR-NNNN (S25-AE): 휴지통 비우기 · 영구 삭제는 사람만 — 셸 전용 버스 명령 · OS 휴지통엔 묶음째 · 영구 삭제는 휴지통이 없다고 확정될 때만

> **채번됨 = ADR-0322**(정본 = `docs/decisions/` — 이 절은 채번 전 사본). 제목 · 결정 5 · 6 을 G47 · G50 이 뒤집었고 결정 7 의 전부 비우기 대상을 M83 이 바꿨다 → 개정 초안 = **S25-AJ**(이 파일 끝).

- 상태: 제안 (2026-10-31, 근거: 사용자 결정 F9 / B8(2026-10-19 「휴지통으로 가되 휴지통 비우기를 llm으로 쏘지 못하게 막자는거지」) · G9 · G11 · G12(2026-10-20) · G21(2026-10-29) · P13 · G44(2026-10-31 「괜찮은데」) · G45(2026-10-31 「열려있음 지우지 않고, 휴지통이 없으면 영구 삭제」) + 메인 M6 · M24-7 · M26 · M46 · M47 · M50 · M52 · M53 · M55 · M57 · M59(보고) · 조사 `docs/research/junction-recycle-bin-atomic-write-2026-10-31.md`)
- 관련: S25-W · S25-Q · S25-AG(휴지통 잠금 · 넘겨주기) · CLAUDE.md 「LLM-우선 제어」 · 「플랫폼 중립」 · PRD R18 · TRD §1-4 `store.rs` · 흐름 ④ · §1-6 OS 휴지통 행 · §1-7 `library.emptyTrash` · §1-11a 시나리오 10 · 발견 17 · §6-2 · §6-5 2 · 5 · §7 28

## 맥락
삭제는 `.trash` 묶음으로 가서 되살릴 수 있다(S25-W). 비우기 · 영구 삭제는 되돌릴 수 없다 — 에이전트가 잘못 부르면 잃는다. 또 Windows 휴지통 보내기는 볼륨 · 파일 상태에 따라 휴지통 대신 지우거나 실패한다.

## 결정
1. 휴지통 비우기 · 영구 삭제는 사람만 한다 — 셸 전용 버스 명령 `library.emptyTrash {items?}`. 데몬은 제어 라우트로 온 것을 거절한다. 에이전트 명령 표 · 프라이밍 · `engram help` 에 없다. 새 wire 변형이 없다(M6 · M26).
2. 원칙 「LLM-우선 제어」 에 예외 목록 · 장치를 더하지 않는다. LLM 이 바깥 도구(WS · `rm`)로 우회하는 것은 받아들인다(G21 · P13).
3. 삭제(→ `.trash`) · 휴지통 보기 · 되살리기(`library.restore`)는 LLM · CLI 도 한다(G11). 그 밖의 `library.*` 는 `.trash` 아래를 가리키지 못한다.
4. **비우기 = 데몬 PC 의 OS 휴지통으로 보낸다.** 전부 비우기 = 묶음 폴더 `<UTC>-<id>` 를 통째로 보낸다 — OS 휴지통엔 묶음마다 한 항목(원래 경로를 품은 폴더)이 들고 결과도 묶음마다다(G44 · M52). `items` = 그 묶음의 준 항목만. 묶음 통째 보내기가 실패하면 그 묶음에 **남은 것**을 항목마다 다시 보내 열린 · 잠긴 파일 하나가 저만 걸리게 하고, 그 묶음 결과는 항목마다 싣는다(M55).
5. **보내기 실패의 가름**(G45 · M59): 영구 삭제는 「이 볼륨엔 휴지통이 없다 · 꺼져 있다」 로 **확정되는 코드에서만** 한다. 쓰는 중 · 접근 거부 · 너무 큼 · **알 수 없는 코드는 전부 지우지 않고 `.trash` 에 남기고** 항목마다 원 HRESULT 를 알린다. 확인 모달이 미리 말하는 것도 이 가름이다(G12 의 「안 되면 지움」 = 휴지통이 없을 때만).
6. **OS 휴지통 호출 = platform 이 `IFileOperation` 을 직접 부른다**(M57) — `FOFX_RECYCLEONDELETE` + 진행 sink(`PreDeleteItem` · `PostDeleteItem` 으로 항목마다 결과). `PreDeleteItem` 에서 「가능하면 휴지통」 표식(`TSF_DELETE_RECYCLE_IF_POSSIBLE`)이 없으면 취소하는 가드를 둔다 — Electron · Qt 와 같은 가드이나 **미검**이라 파일럿에서 잰다(M59). OS 갈림은 platform 함수 하나 안(「플랫폼 중립」).
7. **비우기는 라이브러리 락도 번호표도 잡지 않는다** — `.trash` 는 `Catalog` 밖이다. 묶음 목록은 휴지통 잠금 아래 한 번 떠 두고(그 뒤 생긴 묶음은 건드리지 않는다 · 차례 전에 되살려 나간 항목은 전부 비우기면 그냥 없고 `items` 면 그 항목 `NOT_FOUND` · 그 사이 `setRoot` 가 끼어도 떠 둔 루트의 경로로 계속), 휴지통 잠금을 묶음마다 잡고 놓으며 기다리는 옮기기 · 되살리기에 넘겨준다 — 꼴 = S25-AG 결정 9(M46 · M47 · M50 · M52 · M53).
8. 저절로 비우지 않는다(G11). 사람 화면 = 왼쪽 칸 맨 아래 「🗑 휴지통」 → 휴지통 보기(G9).

## 거부한 대안
- **비우기를 에이전트 명령 표(`engram`)에** — LLM 이 영구 삭제할 수 있다(§7 28).
- **사람만 가드에 장치 · 예외 목록을 더하기** — 사용자 2026-10-29(G21 — LLM 은 바깥 도구로 늘 우회할 수 있다).
- **CLAUDE.md 원칙의 「의도된 예외」 로 적기**(옛 F9 · R18 틀) — G21 · M24-7 이 걷었다.
- **삭제 자체를 사람만** — LLM · CLI 삭제는 `.trash` 로 가서 되살릴 수 있으므로 막을 까닭이 없다(사용자 — F9).
- **30일 같은 자동 비우기**(관행 — Notion · Apple 사진) — 사용자 「일단 유저가 비우게 나중에 필요하면 추가하고」(G11 — 나중 생각).
- **휴지통 입구를 「…」 메뉴 안에** — 메뉴 안에만 둔 피어를 못 찾았다(G9).
- **되살리기를 버스에 열지 않기**(2026-10-19 메인 제안) — 해가 없어 연다(G11).
- **보내기가 안 되면 무엇이든 영구 삭제**(G12 의 처음 읽기 — 쓰는 중 · 권한 실패도 지움) — 사용자 「열려있음 지우지 않고, 휴지통이 없으면 영구 삭제」(G45 · TRD §6-5 미결 5 닫힘).
- **세 HRESULT(휴지통 없음 `0x8027003A` · 쓰는 중 `0x80070020` · 거부 `0x80070005`)로 갈라 「없음」 이면 영구 삭제**(M57 의 첫 꼴) — 코드가 깨끗이 갈리지 않는다: `0x8027003A` 는 「휴지통을 찾지 못했거나 쓸 수 없음」 이고 재활용이 꺼진 볼륨 · 너무 큰 항목 · 공유 위반은 각자 다른 코드 변종이 있다 → 확정된 코드만 영구 삭제 · 나머지는 남김으로 좁혔다(M59 · 조사 — codex 리뷰).
- **보내기 전에 「휴지통을 쓸 수 있나」 미리 확인** — 믿을 수단이 없다(`SHQueryRecycleBinW` 는 내용만 본다 · `GetDriveType` 은 거르기용일 뿐 — USB 가 고정 디스크로 보이고 리디렉션 네트워크 폴더에도 휴지통이 있을 수 있다)(M59 · 조사).
- **`trash` crate 5.2.9**(MIT) — 항목마다 보고가 없다(`DeleteItem` 을 묶어 `PerformOperations` 한 번) · `FOFX_RECYCLEONDELETE` · `FOFX_EARLYFAILURE` 가 없다(일부 지운 채 실패해도 한 덩어리 보고) · 무창 데몬에서 `FOF_WANTNUKEWARNING` + `FOF_NO_UI` 동작 불명 · 스레드마다 STA `CoInitializeEx` 가 `RPC_E_CHANGED_MODE` 에서 패닉 · 셋째 `windows` 사본(0.62)(M57 · 조사). ★M57 의 「실패가 전부 `Error::Unknown`」 은 조사 리뷰가 고쳤다 — 실패는 `Error::Os{code}` 이고 「성공했는데 취소됨」 만 Unknown 이다★ — 거부의 남은 근거는 항목마다 보고가 없다는 것이다.
- **비우기가 라이브러리 쓰기 잠금 · 휴지통 잠금을 내내 쥠 · 넘겨주기 없이 묶음마다 다시 잡기** — 잠금 쪽 거부 = S25-AG(M46 · M47 · M50).

## 근거

# ADR-NNNN (S25-AF): `daemon\cache\` = 다시 만들 수 있는 데이터만 — 언제 지워도 된다

- 상태: 제안 (2026-10-31, 근거: 사용자 결정 B14(2026-10-19 「cache로 하자. 그래야 유저가 인지하고 삭제하지」) · P10)
- 관련: **Amends ADR-0264**(데이터 루트의 `state\` · `run\` 가름에 셋째 칸을 더한다 — 덧붙임) · S25-Z · TRD §1-1 · §1-4 `validate.rs` · §7 29

## 맥락
데몬이 내려받은 설정 스키마를 어디 두나. 지금 데이터 루트는 지키는 `state\` 와 실행 중 휘발 `run\` 으로 갈린다(ADR-0264).

## 결정
1. `daemon\cache\` 는 다시 만들 수 있는 데이터만 둔다 — 언제 지워도 된다. `state\`(지키는 것) · `run\`(실행 중 휘발 · 부팅 때 쓸어 냄)과 가른다.
2. 첫 입주자 = 내려받은 설정 스키마 `daemon\cache\schemas\…`. 앞으로 다시 만들 수 있는 데이터도 여기 둔다.
3. 스키마는 배포판 한 벌이 늘 있고 여기는 갱신본만이다(P10).

## 거부한 대안
- **스키마를 `state\` 나 데이터 폴더 어딘가에** — 지워도 되는지 이름으로 알 수 없다(사용자 이유 — B14).

## 근거
사용자 결정 B14 · P10.

## 영향 / 불변식
- `cache\` 아래가 지워져도 동작이 서야 한다 — 지워져 있으면 다음 판 확인 때 다시 받는다(TRD §1-4).
- 지켜야 하는 데이터를 여기 두지 않는다. 자리는 데몬 `DataLayout` 이 낸다.

# ADR-NNNN (S25-AG): 라이브러리 잠금 규약 — `RwLock` 하나 + 훑기 세대 번호표(FIFO) + 조건부 늦은 합치기 · 휴지통 잠금은 따로 된 잎에 넘겨주기

- 상태: 제안 (2026-10-31, 근거: TRD `/review trd` 재리뷰 R1~R6 반영 — 메인 M34 · M35 · M37 · M39 · M40 · M41 · M43 · M44 · M45 · M46 · M47 · M48 · M50 · M51 · M52 · M53 · M54(보고) · 흐름 점검 G17 · 조사 `docs/research/markdown-frontmatter-hash-sync-crates-2026-10-31.md`(잠금 부품))
- 관련: S25-A · S25-G(요청형 · 첫 훑기) · S25-M · S25-W · S25-Z(새 스키마 다시 검사) · S25-AE · ADR-0006(락 순서) · CLAUDE.md 「핵심 불변식」 의 락 순서 · TRD §1-4 흐름 ① 「잠금」 ①~⑤ · 「Engram 안의 변경」 · §3 잠금 · §1-11a 시나리오 1 · 5 · 6 · 8 · 10 · 발견 9 · 17 · §4 「메모리 목록 · 훑기」 · 「파일 조작 · 휴지통」 행

## 맥락
asset-library 는 메모리 `Catalog`(항목 · 프리셋 쪽 참조 역색인)을 들고, 동기 포트라 여러 스레드가 함께 부른다 — 실행 점검(마감 7초 · 「실행은 전체 훑기를 기다리지 않는다」), 목록 · 상세 읽기, 훑기(첫 훑기 · `library.refresh` · `setRoot`), Engram 변경(파일 조작 · 프리셋 편집 · 다시 연결), 새 스키마 다시 검사, 휴지통 비우기. 재리뷰 여섯 회차가 경합 결함(유령 항목 · 제 스스로 막힘 · 끝없는 앞지르기 · 거짓 「찾을 수 없음」 · 7초를 넘는 멈춤)을 차례로 잡았고, 그 고침이 한 규칙으로 모였다.

## 결정
1. **`Catalog` 락 = `std::sync::RwLock` 하나**(포트가 동기라 tokio 락이 아니다). 걷기 · 파싱은 락 밖이고, 쓰기 잠금은 `Catalog` 을 바꿔 끼우는 순간만 잡는다. 그 락을 쥔 채 바깥으로 가는 간선은 프로필 편집 포트 · `ProfileRegistry` 읽기 둘뿐이고, manager 는 `LaunchKitSource` 를 부를 때 명부 · 예약 락을 쥐지 않는다 — asset-library → manager 한 방향.
2. **읽기 잠금을 쥔 채 쓰기 잠금을 잡지 않는다**(M35). 실행 점검은 붙은 파일을 락 밖에서 읽고, `resolve` · `validate` 는 읽기 잠금 아래 돌린 뒤 놓으며, 새로 읽은 바이트는 따로 된 짧은 쓰기 잠금으로 합친다(결정 5). `library.list` 의 「목록에 없는 경로 하나 확인해 넣기」 도 같다.
3. **훑기 ↔ Engram 변경 = 훑기 세대 `Mutex` + `Condvar`**(라이브러리 락이 아니다 — M35). 그 `Mutex` 가 진행 중 훑기 · 진행 중 변경 수 · 변경 세대 · 루트 세대 · 바꿔 끼우기 수 · 번호표 줄을 든다(루트 세대의 자리는 여기 하나 — M43). 잎이다 — 쥔 채 다른 락을 잡지 않고, 그 `Condvar` 를 기다리는 동안 라이브러리 락을 쥐지 않는다.
4. **차례 = 번호표 한 줄(FIFO — M41)**: 훑기는 앞 번호가 다 끝났을 때, 변경은 앞 번호가 다 들어갔고 진행 중 훑기가 없을 때 들어간다(이어 뽑은 변경끼리는 함께 들어간다). 세대 올리기 — 변경은 쓰기 잠금을 놓기 **전에** 변경 세대를(M39), `setRoot` 는 루트 세대를, 훑기의 바꿔 끼우기는 바꿔 끼우기 수를(M43) 올린다. 바꿔 끼우기는 훑기 시작 뒤 변경 세대가 움직였으면 결과를 버리고 다시 훑으며(M35), 훑기 범위 밖 항목은 게시된 그대로 둔다(M34).
5. **늦은 합치기 = 조건부**(M39 · M43): 실행 점검의 새 바이트 · 목록 안전장치의 넣기는 락 밖 디스크 읽기 **전에** 변경 세대 · 루트 세대 · 바꿔 끼우기 수를 함께 적어 두고, 합치는 쓰기 잠금 안에서 다시 견준다 — 세대가 움직였으면 통째로 버리고, 바꿔 끼우기만 끼었으면 `Catalog` 에 없는 경로를 넣는 것만 버린다(목록 안전장치의 넣기는 늘 없던 경로라 그때 버린다). 셋 다 그대로면 훑기 중이어도 바로 들어가고(M34), 훑기 범위 안에서 같은 항목을 함께 읽었으면 늦게 읽은 쪽이 남는다(차례 = 파일을 열기 전에 뽑는 단조 번호 · 훑기가 범위 안에서 못 찾은 항목은 그 폴더를 나열하기 전 번호로 「없음」 을 읽은 것으로 친다 — M43).
6. **첫 훑기 입구**(M37 · M40 · M48 · M51): `Catalog` 을 읽는 `LibraryCommandHost` 메서드는 전부(`library.*` 읽기 · `preset.get` · `agent.presets` · 트리 ⛔ · 답에 문제 목록 · 참조 수를 싣거나 계획 · 검증이 `Catalog` 을 읽는 편집) 첫 훑기를 시작하거나 기다린다 — 편집은 **메서드 입구에서**, 번호표 · 진행 중 셈 · 라이브러리 락보다 앞. 「첫 훑기가 끝났다」 = **전체** 훑기 하나가 게시됨(폴더 범위 게시로는 안 바뀐다). 첫 훑기 전의 `library.refresh {folder}` 도 전체 첫 훑기를 지나고(답은 그 폴더 몫), 기다린 첫 훑기가 게시되지 못했으면 번호표 대신 입구를 다시 지난다(거기서도 실패하면 그 실패가 답). 실행 점검(`LaunchKitSource::check`)은 이 입구 밖이다.
7. **요청 합치기**(M9 · M44): 첫 훑기를 기다리는 `Catalog` 읽기(편집 입구 포함)는 이미 걷는 훑기에도 붙는다 — 새것이 아니라 `Catalog` 이 있기만 하면 된다. `library.refresh` 는 아직 걷기 전인 덮는 세대에만 붙고, 덮는 훑기가 이미 걷고 있으면 자기 번호표를 뽑는다(「밖에서 바꾼 뒤 refresh 를 부른다」 계약 — PRD R41). 몰려온 refresh 는 걷기 전 세대 하나로 접힌다.
8. **새 스키마의 설정 다시 검사도 변경이다**(M45): 새 스키마를 검사기에 꽂은 **뒤** 번호표를 뽑고, 진행 중으로 세고, 쓰기 잠금 안에서 변경 세대를 올리며, 파싱 캐시에 붙은 검사 결과도 고친다(M49). 첫 훑기 입구를 지나지 않고 첫 훑기를 일으키지 않는다 — 훑기가 한 번도 없었으면 빈 `Catalog` 이라 할 것이 없다.
9. **휴지통 잠금 = 따로 된 잎**(M46 · M47 · M50 · M52 · M53 · M54): `.trash` 를 만지는 조작끼리만 줄 세운다. 옮기기(삭제 · 덮어쓰기로 밀려난 파일) · 되살리기는 라이브러리 쓰기 잠금을 쥔 채 이것을 잡는다(순서 = 라이브러리 락 → 휴지통 잠금). `library.emptyTrash` 는 라이브러리 락도 번호표도 잡지 않는다 — 루트를 읽기 잠금으로 잠깐 한 번 읽고 놓은 뒤, 휴지통 잠금을 잠깐 잡아 묶음 목록을 떠 두고, **묶음마다** 잡고 보내고 놓는다. **넘겨주기**: 옮기는 쪽은 기다리기 전에 기다리는 수를 올리고 그 조작의 `.trash` 옮기기를 **전부** 마친 뒤 내린다(조작 하나 = 휴지통 단계 하나 = 묶음 하나 — M53). 비우기는 목록을 뜨기 전과 묶음을 잡기 전마다 그 수가 0 이 될 때까지 아무 락도 쥐지 않고 기다린다. 기다리는 수는 묶음을 보내는 도중에도 올릴 수 있어야 하고(보내는 동안 쥔 락 뒤에 두면 놓는 순간 비우기가 0 을 읽는다), 상태가 바뀌면 모두 깨우며, 실패 · 조기 반환 길에서도 내린다(가드 — M54). 모양 예 = `Mutex<휴지통 상태>` + `Condvar`(상태 = 잡힘 · 기다리는 수) — 정확한 꼴은 구현 판단.
10. 부품 = std `Mutex` + `Condvar` + 손으로 짠 번호표 — 서드파티 락을 들이지 않는다(조사).

## 거부한 대안
- **걷는 동안 쓰기 잠금을 쥐는 훑기** — 실행 점검이 전체 훑기를 기다린다(갱신 규칙 「실행은 기다리지 않는다」 위반 — TRD 흐름 ① 「잠금」 ① · 발견 9).
- **읽기 잠금에서 쓰기 잠금으로 올리기** — `std` `RwLock` 은 올림이 없어 제 스스로 막힌다(M35 · 재리뷰 B2).
- **훑기 중엔 실행 점검의 합치기를 건너뛰고 바꿔 끼우기가 들이게**(옛 규칙) — 폴더 A 훑기의 바꿔 끼우기가 그 사이 실행이 고친 폴더 B 항목을 되돌려 문제 목록 · ⛔ 가 낡았다(M34 · 재리뷰 B1).
- **조건 없는 늦은 합치기** — 그 읽기와 합치기 사이에 끝난 이름 바꾸기 · 삭제 · 프리셋 편집의 옛 경로 · 옛 바이트를 되살렸다(유령 항목 · M11 깨짐 — M39 · R2 C1). 세대만 견주면 바깥 삭제 뒤 덮는 훑기가 뺀 경로를 다시 넣었다(M43 · R3 E1).
- **편집이 번호표를 뽑거나 진행 중으로 센 뒤 첫 훑기에 합류** — 진행 중 변경이 그 훑기의 시작을 막거나, 이미 돈 훑기의 바꿔 끼우기가 그 변경의 쓰기 잠금을 기다려 제 스스로 막힌다(M40 · R2 C2).
- **공정성 없는 차례**(먼저 잡는 쪽이 들어감) — 새로 오는 훑기가 기다리는 변경을 끝없이 앞지르거나, 겹친 변경이 첫 훑기를 끝없이 미룬다(M41 · R2 C3).
- **`library.refresh` 가 이미 걷는 훑기에 붙음** — 호출자가 그 전에 바깥에서 바꾼 바이트를 놓친 결과를 돌려준다(PRD R41 깨짐 — M44 · R3 E2).
- **첫 훑기 전 폴더 refresh 는 그 폴더만 훑음** — 부분 `Catalog` 이 올라가 폴더 밖 참조가 거짓 「찾을 수 없음」 이 되고, LLM 이 그것을 보고 사용자 데이터를 「고칠」 수 있다(M48 · R4 H2). 기다린 첫 훑기가 실패한 뒤 번호표로 폴더만 훑기도 같은 결함이다(M51 · R5 J2).
- **스키마 다시 검사가 번호표 · 세대 밖에서 `Catalog` 을 고침** — 걷고 있던 첫 훑기가 옛 스키마 결과를 게시해 재시작까지 틀린 ⛔ · 문제가 남았다(M45 · R3 E3).
- **비우기가 라이브러리 쓰기 잠금을 내내 쥠** — `.trash` 는 `Catalog` 밖인데 7초 마감을 넘기고 실행의 읽기 잠금을 세웠다(M46 · R3 E4).
- **비우기가 휴지통 잠금을 내내 쥠** — 비우는 도중 온 삭제 · 되살리기가 쓰기 잠금을 쥔 채 비우기 전체를 기다려 모든 읽기 잠금이 7초를 넘겨 섰고, `setRoot` 도 비우는 도중에 끼었다(M47 · R4 H1).
- **묶음마다 놓고 바로 다시 잡기만**(넘겨주기 없음) — `std` `Mutex` 는 공정하지 않아 비우기가 곧바로 다시 잡고, 쓰기 잠금을 쥔 채 기다리는 삭제가 비우기 내내 질 수 있다(M50 · R5 J1 · Windows 의 std `Mutex` 는 넘겨주기가 없다 — 조사).
- **잠금 밖에서 묶음 목록 뜨기** — 옮기는 도중 반쯤 찬 묶음을 잡는다(M52 · R5 J3).
- **항목마다 기다리는 수를 올리고 내림** — 여러 항목 되살리기 · 두 덮어쓰기 사이에 비우기가 다음 묶음(또는 목록)을 잡는다(M53 · R6 K1).
- **`parking_lot`** — 데몬 그래프에 새로 들어오고(0.12.5 만 tauri 를 거쳐 잠금에 있다) 0.13.0 에서 자동 최종 공정성을 걷고 MSRV 1.95 로 올랐다 · 「훑기는 배타 · 편집은 동시」 같은 섞인 조건은 락 공정성으로 표현되지 않는다(조사). **`spin::TicketMutex`** — 스핀한다. **`ticket_lock` crate** — crates.io 에 없다(같은 조사).

## 영향 / 불변식
- **락 순서**: 라이브러리 `RwLock` → 휴지통 잠금. 훑기 세대 `Mutex` · 휴지통 잠금은 잎. 프로필 편집 포트 · 명부 읽기는 라이브러리 락 아래에서 부를 수 있고 그 반대는 없다. CLAUDE.md 「핵심 불변식」 의 락 순서 줄에 더할 후보(구현 때 사용자 확인).
- **`Catalog` 을 바꾸는 새 길**(새 변경 종류)을 더하면 번호표 · 진행 중 셈 · 쓰기 잠금 안 세대 올리기를 함께 진다 — 빠지면 늦은 합치기가 옛 상태를 되살린다. 새 읽기 메서드는 첫 훑기 입구를 지난다.
- **남은 것(받아들임)**: 첫 훑기의 바꿔 끼우기와 스키마 다시 검사 사이에 답한 읽기는 옛 스키마 결과를 보일 수 있다 — 다음 질의가 맞다(M45 · 시나리오 8). 비우는 도중 온 삭제 · 되살리기는 묶음 하나 보내는 동안 쓰기 잠금을 쥔 채 기다리고 그동안 실행의 읽기 잠금도 선다(M47) — 묶음 하나도 길면 다음 걸음 = 떠 둔 묶음을 `.trash` 안 숨은 폴더로 옮긴 뒤 락 없이 보내기(실측이 부를 때만 — 발견 17).
- FIFO · 넘겨주기 · 조건부 합치기는 §4 시험이 결정적으로 고정한다(경합이 아니라 관문에서 단언 — M50 · M53 · 실패 주입 = M51).

# ADR-NNNN (S25-AI): 경로 열쇠 = OS 대문자 표의 UTF-16 단위 접기 · 파일 신원 = 128비트 우선 — 둘 다 platform `fs`

- 상태: 제안 (2026-10-31, 근거: 메인 M38(재리뷰 B5 · F11) · M60(0a codex 리뷰 BLOCK 유지 · 보고) · 조사 `docs/research/library-scan-file-identity-path-key-crates-2026-10-31.md`)
- 관련: S25-H · S25-AG · S25-AH(walkdir) · CLAUDE.md 「플랫폼 중립」 · ADR-0266(운영 OS 분기는 platform 안) · TRD §1-6 · §1-4 `catalog.rs` · 흐름 ① 훑기 꼬리표 · 흐름 ② 「찾을 수 없음」 · §5-2 2 단계 · T-74

## 맥락
Windows 는 대소문자를 가리지 않는다. `Catalog` 의 `items` · `used_by` 는 경로로 찾는 표인데, 짝 비교 `same_path(a,b)` 로는 표의 열쇠를 만들 수 없어 대소문자만 다른 참조가 Windows 에서 「찾을 수 없음」 으로 보였다(M38). 훑기는 바뀐 파일만 다시 파싱하려고 경로 · 수정 시각 · 크기 · 파일 신원을 꼬리표로 견준다(TRD 흐름 ①).

## 결정
1. platform `fs` 에 `path_key(path)` 를 더한다 — **`same_path(a,b)` == 열쇠가 같음**. `Catalog` 의 `items` · `used_by` 는 이 열쇠로 찾고, 경로를 견주는 자리(에이전트 쪽 역조회 · 경로 고침의 맞는 붙임)는 `same_path` 로 견준다(M38).
2. Windows 열쇠 = **UTF-16 코드 단위마다 · BMP 단위만(서로게이트는 그대로) · OS 대문자 매핑**(`RtlUpcaseUnicodeChar` 또는 `LCMapStringEx` invariant UPPERCASE — 파일럿에서 고른다). 그 밖 OS = 그대로(M60).
3. 폴더마다 대소문자를 가리는 폴더(WSL `setCaseSensitiveInfo`)는 지원 밖이라 적는다(M60).
4. 파일 신원(훑기 꼬리표) = **128비트 `FileIdInfo` 우선 · 안 되는 볼륨은 64비트(볼륨 일련번호 + 파일 인덱스)로 물러난다**(M60 — 64비트는 ReFS 에서 유일하지 않을 수 있다). 얻는 길(platform 직접 호출 · `file-id` · `winapi-util`)은 파일럿에서 고른다(조사).
5. 파일 신원은 훑기 꼬리표에만 쓴다 — 다시 연결 후보가 아니다(G38 · T-74 — 그건 R19 「후보 제안 없음」 을 다시 연다).

## 거부한 대안
- **Rust `char::to_uppercase`**(수집자 안 — 한 글자 매핑일 때만) — 보충 평면 이름을 합친다(U+10428 → U+10400 · NTFS 의 `$UpCase` 표는 BMP 만이라 둘을 가른다)(M60 · codex 리뷰 BLOCK 유지).
- **짝 비교 `same_path` 만** — 표의 열쇠를 만들 수 없다(M38).
- **`unicase`** — 완전 접기(`ß` → `ss`)라 NTFS 와 다르다 · **`icu_casemap`** — 무겁다 · **git `strcasecmp` 꼴** — ASCII 만 · **`CompareStringOrdinal`** — 비교 함수지 열쇠가 아니다(조사).
- **std Windows `MetadataExt` 의 `volume_serial_number` · `file_index`** — 불안정(rust-lang/rust#63010 · 1.95 에서도 nightly) · **`same-file`** — 저장할 신원 값이 없다(비교만)(조사).

## 근거
- 조사 library-scan(medium · codex 리뷰 BLOCK → M60 으로 정정): 열쇠 방향 = 결정 · NTFS 와의 일치 = 미측 · 정확한 API = 불확실. MS `BY_HANDLE_FILE_INFORMATION` 문서 — 64비트 인덱스는 ReFS 에서 유일하지 않을 수 있다.

## 영향 / 불변식
- 열쇠 규칙을 바꾸면 `same_path` 와 함께 바꾼다 — 둘이 같다는 것이 불변식이다.
- **파일럿 실측**: `RtlUpcaseUnicodeChar` · `LCMapStringEx` 가 NTFS `$UpCase` 와 어디서 갈리나(보충 평면 · 서로게이트 · `ß` · `ı`) · ReFS 에서 128비트 신원이 실제로 얻어지나 · 안 되는 볼륨에서 물러나기가 도나.
- macOS APFS 는 접기 + NFC/NFD 정규화가 필요한데 `unicode-normalization` 이 잠금에 없다 — 문서로 남긴 갭이다(조사 · 「플랫폼 중립」).
- `winapi-util` 을 고르면 platform 게이트 5(OS crate 손 명단)에 더한다(조사).

# ADR-NNNN (S25-AJ): 휴지통 비우기 · 영구 삭제 = OS 휴지통에 넘기고 OS 가 정한다 — ADR-0322 결정 5 · 6 · 7 개정

- 상태: 제안 (2026-10-31, 근거: 사용자 결정 G47(2026-10-31 「음? 일단 이미 삭제해서 간거라서 삭제하는거에 대해서 디테일하게 챙길 필요있음?」 → 「그냥 휴지통으로 보내고 삭제되던지 말던지는 다 os에서 알아서 하라고그래」) · G50(2026-10-31 「그냥 휴지통말고 삭제하시겠습니까해」) · G12(2026-10-20 — 되돌아간 원래 규칙) + 메인 M64 · M69(스레드 — 그대로) · M79 · M83 · M85(재리뷰 r9 · 보고) · M86(재리뷰 r10 · 보고))
- 관련: **Amends ADR-0322 제목 · 결정 5 · 6 · 7**(+ 결정 4 의 결과 말 · 거부한 대안 · 영향 — 아래 「바뀌는 조항」) · ADR-0320 · ADR-0324 · ADR-0292 · ADR-0293 · CLAUDE.md 「플랫폼 중립」 · PRD R18 · TRD §1-6 OS 휴지통 행 · 「결과 가름」 · §6-2 · §6-5 8 · 9(U1 · U2) · §7 20 · §7 28

## 맥락
ADR-0322 는 OS 휴지통 보내기의 실패를 우리가 갈랐다 — 「휴지통 없음 · 꺼짐」 으로 확정된 코드에서만 영구 삭제하고 쓰는 중 · 거부 · 너무 큼 · 모르는 코드는 `.trash` 에 남기며(결정 5 · G45 · M59), 엔진이 지우지 않게 `PreDeleteItem` 가드를 둔다(결정 6 · M59 — TRD 는 M70 으로 「엔진은 `no_bin_confirmed` 만 돌려주고 platform 영구 삭제 함수가 지운다」 까지 좁혔다). 그러자 휴지통 없는 볼륨의 `.trash` 를 Engram 에서 비울 수 없게 되는 것(U1)과 너무 큼 · 모르는 코드도 남길지(U2)가 사용자 물음으로 남았다. 사용자는 비우기 대상이 이미 지워 `.trash` 로 간 것이라 지우는 방식을 따로 챙길 까닭이 없다고 보고 G12(2026-10-20)의 원래 규칙으로 되돌렸다.

## 결정
1. 휴지통 비우기 · 휴지통 보기의 영구 삭제 = 항목을 데몬 PC 의 OS 휴지통에 넘기고 **OS 가 정한다** — 휴지통에 넣든, 넣지 못해 그대로 지우든 Windows 의 동작 그대로다(G47 · G12).
2. 가드가 없다 — `PreDeleteItem` 의 `TSF_DELETE_RECYCLE_IF_POSSIBLE` 검사 · 휴지통 없음 판정 · 따로 된 platform 영구 삭제 단계를 두지 않는다(G47).
3. 항목 결과 = **사라짐 · 남음** 둘 + 원 네이티브 코드(진단으로만). OS 가 거절한 것(열린 파일 · 거부 등)은 `.trash` 에 남기고 항목마다 알린다. 가름 = 앞뒤 — 부르기 **전에** 이미 없던 경로는 `NOT_FOUND` · 부른 **뒤** 없어진 것은 사라짐(M85). 있는지 먼저 보기는 스레드 · COM 초기화 **앞**에서 돈다 — 초기화가 실패해도 부르기 전에 없던 항목은 `NOT_FOUND` 다(M86). 항목 하나마다 제 `PerformOperations` 를 부르므로(M66) `FOFX_EARLYFAILURE` 로 건너뛰는 항목이 없다 — not_attempted 칸을 두지 않는다(M85 · G47 이 남겨 둔 칸을 걷음). M62 · M71 의 결과 칸을 이 꼴로 접는다.
4. 확인 모달 = 휴지통을 말하지 않는 삭제 물음 — 예 제목 「영구 삭제」 · 본문 「항목 12개를 삭제하시겠습니까?」 · [취소] [삭제](G50 — G47 이 남겨 둔 초안 「Windows 휴지통으로 보냅니다 — 휴지통이 없는 드라이브면 바로 지웁니다」 를 대신한다 · 동작은 결정 1 그대로). N = 휴지통 보기가 보이는 항목(줄) 수 — 묶음 폴더 수가 아니다 · 전부 비우기도 같다(M79).
5. 부르는 수단(`IFileOperation` 직접 · `trash` crate)은 구현 때 다시 잰다 — 항목마다 실패 보고는 여전히 필요하고 셋째 `windows` 사본 걱정은 그대로다(G47).
6. **전부 비우기 = 휴지통 보기가 보인 묶음 id 만** — 화면은 목록에 보인 묶음 id 를 보내고 데몬은 그 묶음만 비운다 · 목록 뒤에 지운 항목은 `.trash` 에 남는다(M83 · 모달의 N 도 보인 줄 — M79). `items` 도 묶음 id 도 없는 `library.emptyTrash` 는 거절한다 — 누가 부르든 M83 의 보장을 지킨다(M86).
7. 그대로인 것: 사람만 · 셸 전용 버스 명령(ADR-0322 결정 1~3) · 묶음째 보내고 실패한 묶음은 남은 것을 항목마다 다시 보낸다(결정 4) · 잠금 · 넘겨주기(결정 7 의 나머지 · ADR-0324) · 저절로 비우지 않음(결정 8) · 스레드 = 호출마다 `std::thread::Builder::spawn` 새 STA 스레드 · 실패는 값으로 · 새 가둠 자리 없음(M64 · M69 · ADR-0292 · ADR-0293) · OS 갈림은 platform 함수 하나 안(「플랫폼 중립」).

## 바뀌는 조항 (ADR-0322)
- 제목 「… 영구 삭제는 휴지통이 없다고 확정될 때만」 → 「… OS 가 정한다」.
- **결정 5**(보내기 실패의 가름) — 통째로 바뀐다 → 이 ADR 결정 1 · 3. 그 안 「확인 모달이 미리 말하는 것도 이 가름이다」 → 결정 4.
- **결정 6** — 가드를 걷는다(결정 2). 「platform 이 `IFileOperation` 을 직접 부른다(M57)」 는 확정이 아니라 구현 때 다시 잰다(결정 5). 「OS 갈림은 platform 함수 하나 안」 은 그대로.
- 결정 4 — 「그 묶음 결과는 항목마다 싣는다」 의 결과 = 결정 3 의 두 값. 다시 보내는 꼴은 그대로.
- **결정 7** — 전부 비우기가 비울 묶음 = 휴지통 보기가 보인 묶음 id(이 ADR 결정 6 · M83) · `items` 도 묶음 id 도 없으면 거절(M86). 「그 뒤 생긴 묶음은 건드리지 않는다」 · 잠금 · 넘겨주기 · `setRoot` 가 끼어도 떠 둔 루트로 계속은 그대로.
- 거부한 대안 — 「세 HRESULT 로 갈라 「없음」 이면 영구 삭제」 · 「보내기 전에 미리 확인」 은 물음이 사라진다(우리가 가르지 않는다). 「`trash` crate」 거부는 다시 연다(결정 5). 「보내기가 안 되면 무엇이든 영구 삭제」 거부는 우리 쪽 지우기 단계가 없어 그대로 선다 — OS 가 거절한 쓰는 중 · 거부는 남는다(결정 3).
- 영향 — 첫 줄 「그래서 뒤가 아니라 앞에 말한다(G12)」 → 모달은 삭제로 묻는다(결정 4). 파일럿 실측 목록 → 아래 「영향」 의 줄인 목록. 마지막 줄 「영구 삭제의 가름을 넓히면 G45 를 다시 연다」 → 아래 「영향」.

## 거부한 대안
- **우리가 코드로 갈라 지울지 정하기** — 「휴지통 없음 · 꺼짐」 확정 코드에서만 영구 삭제 · 너무 큼 · 모르는 코드는 남김(M59 — ADR-0322 결정 5 · G45 의 이유 가름을 좁힌 꼴) — 사용자 「음? 일단 이미 삭제해서 간거라서 삭제하는거에 대해서 디테일하게 챙길 필요있음?」 → 「그냥 휴지통으로 보내고 삭제되던지 말던지는 다 os에서 알아서 하라고그래」(G47).
- **`PreDeleteItem` 가드 + `no_bin_confirmed` 뒤 platform 영구 삭제 함수**(M59 · M70 — ADR-0322 결정 6 · TRD §1-6) — 같은 사용자 말(G47).
- **(U1) 가드에 걸려 못 비운 항목에 사람만 쓰는 「그래도 영구 삭제」 확인 · (U2) 너무 큼 · 모르는 코드 남김 승인** — 물음이 사라졌다(G47 — 가드가 없어 OS 가 정한다).
- **확인 모달에 휴지통을 말하기**(G12 의 메인 채움 · G47 이 남겨 둔 초안 「Windows 휴지통으로 보냅니다 — 휴지통이 없는 드라이브면 바로 지웁니다」) — 사용자 「그냥 휴지통말고 삭제하시겠습니까해」(G50).
- **전부 비우기 = 그 순간 `.trash` 에 있는 전부**(ADR-0322 결정 7 의 「휴지통 잠금 아래 떠 둔 목록」) — 근거(메인 2026-10-31 — 보고): 사람은 모달에서 본 N개(보인 줄 — M79)를 확인했다 · 목록 뒤에 지운 것까지 비우면 확인하지 않은 것을 되돌릴 수 없게 지운다(M83).
- **not_attempted 칸**(G47 이 남겨 둔 것 — M66 · M71) — 항목마다 따로 부르므로 건너뛸 항목이 없다(M85).

## 근거
- 사용자 결정 G47 · G50(2026-10-31) · G12(2026-10-20 「휴지통 비우면 윈도우 휴지통으로 보내고 안되면 그냥 삭제되게」 — 되돌아간 규칙). M79 · M83 · M85 = 메인(재리뷰 r9 — 보고) · M86 = 메인(재리뷰 r10 — 보고).
- 사용자 이유(G47): 비우기 대상은 이미 지워 `.trash` 로 간 것이다 — 지우는 방식을 따로 챙길 까닭이 없다.
- ADR-0322 「근거」 의 이유(에이전트가 잘못 지워도 되살리게 남긴다 — F9)는 그대로다 — 비우기가 사람만인 것(ADR-0322 결정 1 — 그대로)으로 지켜진다.

## 영향 / 불변식
- Windows 가 휴지통 대신 지워도 받아들인 동작이다 — 결과의 「사라짐」 은 휴지통에 들었는지를 말하지 않는다.
- 파일럿(9b)이 줄어든다: 데몬 아래 OS 호출이 도는가(스레드 — M64 · M69) · 열린 파일이 남는가 · 어떤 UI 대화상자든 뜨면 실패(G47).
- 부르는 수단을 고르면(결정 5) ADR-0322 「영향」 의 비용 줄(`Win32_UI_Shell` · COM 구현 · STA 스레드)이 그에 맞춰 바뀐다.
- 우리 쪽 가름 · 가드 · 지우기 단계를 다시 들이면 G47 을 다시 연다. 비우기를 LLM 표면에 올리는 변경은 여전히 ADR-0322 를 다시 연다.
- 따라 고칠 자리(다른 작업자 몫 — 확인): TRD §1-6 OS 휴지통 행 · 「결과 가름」 표 · §6-2 9b · §6-5 8 · 9(U1 · U2) · §7 20 의 M70 문장 · §7 28 · PRD R18 문구.
