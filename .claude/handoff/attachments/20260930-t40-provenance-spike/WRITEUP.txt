B. Provenance — hook chain vs Bash-tool chain
Claude-direct children seen in main (analyze-main.txt aggregate): HOOK launcher 291, taskkill.exe 202, git.exe 18,
reg.exe 12, rg 18 (image = claude.exe, argv0 "rg"), where.exe 6, cmd.exe 6 (REG QUERY MachineGuid), BASH_TOOL 6,
first-Bash-use helpers 9 (bash -c env / bash -lc "echo $PATH" / snapshot maker, 3 each).
Exact command-line shapes (claude 2.1.284, Git for Windows at C:\Program Files\Git):
  (1) hook launcher (depth 2):   "C:\Program Files\Git\bin\bash.exe" -c "<hooks.json command>"
        e.g. -c "bash ${CLAUDE_PLUGIN_ROOT}/hooks/wiki-preconsult.sh"
             -c "C:/Users/<user>/.orca/agent-hooks/claude-hook.cmd || echo {}"
             -c "node \"${CLAUDE_PLUGIN_ROOT}/scripts/stop-review-gate-hook.mjs\""
             -c "python -c \"import sys,json,re; …\""
      depth 3: "C:\Program Files\Git\bin\..\usr\bin\bash.exe" -c "<same string>" (+ conhost 0xffffffff -ForceV1)
      depth 4 (.sh): "C:\Program Files\Git\usr\bin\bash.exe" C:/Users/<user>/.claude/plugins/cache/…/hooks/<x>.sh
      depth 5+: forks with the SAME cmdline as depth 4, plus exec'd tools (cat, jq, grep, awk, tr, git, …).
  (2) Bash tool, foreground AND run_in_background — identical shape (depth 2):
      "C:\Program Files\Git\bin\bash.exe" -c "source /c/Users/<user>/.claude/shell-snapshots/snapshot-bash-<ms>-<rand>.sh
       2>/dev/null || true && export TEMP='…' TMP='…' && export <plugin env, e.g. CODEX_COMPANION_SESSION_ID=…,
       CLAUDE_PLUGIN_DATA=…> … && eval '<the command>' < /dev/null && pwd -P >| '<TMP>/claude-<4 hex>-cwd'"
      depth 3/4 forks: "…\usr\bin\bash.exe" -c "<same string>"; exec'd leaves: "C:\Program Files\Git\usr\bin\sleep.exe" 5 / 2
  (3) first Bash use only: "…\bin\bash.exe" -c env; "…\bin\bash.exe" -lc "echo \"$PATH\"";
      "…\bin\bash.exe" -c -l "SNAPSHOT_FILE='C:\Users\<user>\.claude\shell-snapshots\snapshot-bash-….sh' …"
  (4) interrupt: "C:\WINDOWS\System32\taskkill.exe /PID <hook launcher pid> /T /F", one per running hook launcher,
      two rounds (~1–15 ms and ~1.5 s after the interrupt; the 2nd round hits already-dead pids: 105/200).
Verdict:
- At the claude-direct-child layer the two are separable by command line: 291 hook launchers vs 6 Bash-tool
  launchers, 0 ambiguous (shape (1) never starts with `source …shell-snapshots…`; shape (2) always does).
  Confidence high for this version/install; it rests on undocumented claude internals (the `bash ` prefix, the
  snapshot wrapper, Git-bash launcher) -> re-verify per claude version.
- Below the launcher, only MSYS FORK children carry the marker (cmdline copied from the parent): bash.exe under
  hook launchers 1820/1820 carried the hook command / script path; bash.exe under Bash-tool launchers 43/43 carried
  the shell-snapshots line. Exec'd programs carry only their own argv: no marker for sleep/cat/jq/grep/git/conhost
  (node/cmd show the hook script path only because it is their argument).
- All observed stall holders (5 today + 3 on 09-29 + 2 bg-trial hangs) are bash.exe whose own cmdline is
  `usr\bin\bash.exe <…/hooks/<name>.sh>` — self-identifying as hook even with every ancestor dead.
- "Parent is dead" is NOT a separator: exec'd children normally outlive their Windows parent under MSYS
  (bg-loop sleep.exe 31/31, hook-tree cat/tr/grep ~all; analyze-main.txt last block).
- foreground vs background Bash: not separable by process; only by stream events (below). A background loop
  survives interrupts (claude never taskkilled a Bash-tool launcher on interrupt; it did so on stdin EOF, 2/3) and
  keeps creating post-Esc children, so the TRD §3-4 selector picked a bg-loop sleep.exe in 3/3 bg trials (+pilot).
- Caveats: a Bash-tool command that itself launches a script (e.g. `bash foo/hooks/x.sh`) produces exec'd bash
  descendants WITHOUT the snapshot marker (not measured, follows from the fork/exec rule); hook commands that are not
  bash (node/cmd/python) produce descendants with no marker; the Store-alias python of the PreToolUse hook never
  appeared as a job record (0 in 12 runs, although the hook answered) — where it ran was not measured.
Stream-event correlation:
- hook_started carries only type/subtype, hook_id, hook_name (e.g. "UserPromptSubmit", "PreToolUse:Bash"),
  hook_event, uuid, session_id. hook_response adds output, stdout, stderr, exit_code, outcome
  (success/cancelled). No pid, no command, no script path in either.
- Timing (corr.txt): UserPromptSubmit/PreToolUse/PostToolUse/Stop launchers spawn 0.9–124 ms (median 6.9 ms, n=264)
  after the hook_started line is received; a batch's hook_started lines are ~0.1 ms apart, so timing identifies the
  batch, not the member. Spawn order = hook_started order = config order in 143/144 unambiguous cases (ordinal
  heuristic only). SessionStart hook_started lines arrive ~0.4 s AFTER their launchers spawned (6/6 processes).
- hook_response arrives ~2.6 ms (median; 1.5 ms min) after the hook's process tree releases its pipe — normally the
  launcher's exit, but in a stall only after the orphan dies (max 9775 ms). So "hook_started without hook_response
  N s after Esc" names the stalled hook_id/hook_name, but no event maps it to a pid.
- Bash tool: assistant tool_use {name:"Bash", input:{command, description, run_in_background:true}} (key absent in
  fg); tool_use -> launcher spawn = 2.26–2.34 s fg (first use: PreToolUse hooks + env/PATH probe + snapshot maker)
  and 0.33–0.36 s bg. system/task_started {task_id, tool_use_id, description, is_backgrounded, task_type:"local_bash"}
  arrives 3–4 ms after the bg launcher spawn (is_backgrounded:true) but 3.0 s after the fg spawn (is_backgrounded:
  false; 3/3 + pilot — apparently emitted only once a fg command runs ~3 s). fg ends with task_notification
  {status:"completed"} ~5 ms after launcher exit. bg tool_result: "Command running in background with ID:
  <task_id>. Output is being written to: …\tasks\<task_id>.output …". No pid anywhere (b-timeline-p1.txt:20/39/40/47,
  :79/92/93/98).
- The only process-level link claude itself exposes is the taskkill /PID <launcher> command line at interrupt; the
  holder is by construction NOT in that tree when taskkill enumerates it (it is born during the kill, Esc+263…454 ms,
  while the first-round taskkills run ~250–420 ms), so linking it needs ancestry recorded before its parents die
  (our port + held handles did that; a snapshot-only walk after Esc cannot — its ppid points at a dead process).

C. How the UserPromptSubmit hooks are run
- Via `bash <path>`, not via the shebang. hooks.json has the bare path (`${CLAUDE_PLUGIN_ROOT}/hooks/
  wiki-preconsult.sh`; the scripts start with `#!/usr/bin/env bash`), but claude 2.1.284 spawns
  `"C:\Program Files\Git\bin\bash.exe" -c "bash ${CLAUDE_PLUGIN_ROOT}/hooks/wiki-preconsult.sh"` (same for
  handoff-trigger, plugin-notice, plugin-autoupdate, pre-build-check), and the script runs as
  `"C:\Program Files\Git\usr\bin\bash.exe" C:/Users/<user>/.claude/plugins/cache/…/hooks/wiki-preconsult.sh`.
  No env.exe appears in any of the 291 hook-launcher subtrees (env.exe only under claude's own `bash -c env`).
  Non-.sh commands are passed verbatim (orca `….cmd || echo {}` -> cmd.exe /c …; `node "…mjs"`; `python -c …`).
