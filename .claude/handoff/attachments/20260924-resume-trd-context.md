P2. An agent killed before any conversation cannot be reactivated: resume fails "이어받을 대화가 없습니다" (`ko.ts:91-92`, `failureKinds.ts:33` retryable false), every retry fails. The user decided 2026-09-21 to fix resume failure in a "just start a new session" direction (`step-log.md:2442`).

## User decisions (2026-09-23/24) — the TRD must implement exactly these
D1. The session id is persisted only after the FIRST CONVERSATION, uniformly for all backends (claude + codex, JSON + terminal). For claude, keep the id we mint at spawn only in memory ("임시 캐싱") and persist it when the first conversation happens. Rationale (user): an id stored before any conversation is garbage; "has stored id" ⇔ "has a conversation to resume" becomes one clean rule. Mode selection already keys off id presence (`can_resume_profile` = can-resume && id present, `backend/mod.rs:704-706`; callers `restore_one` manager.rs:1942, `wake_existing` commands.rs:574, WS `SpawnProfile` connection_core.rs:1385) — no change needed there: no id → Fresh.
D2. The chat slot learns "this incarnation resumed a conversation" (yes/no — NOT the id itself) from the SUBSCRIBE response, not from a broadcast when the id is created. Reason: the subscribe reply travels in the same ordered stream as replay + ReplayComplete (race-free); the value is fixed per incarnation at spawn. No broadcast on id creation is needed for this (the frontend reportedly has no other reader of the id — verify). Avoid the name clash: `SubscribeAck.action` already has `Resume` meaning replay-from-seq.
D3. The exact persistence trigger per backend/mode is delegated to the implementation (choose the best code-wise; document). Orchestrator's current lean: JSON mode = when Engram sends the first user message (codex: just before the first `turn/start` write in `writer_loop` `Job::Turn` arm, `transport.rs:1686-1700` — rollout exists from turn start per `docs/reference/backend-capabilities.md:47-49` and `.claude/handoff/attachments/codex-measurements-2026-09-09.md:66-67`; claude JSON: when the first user message is written — verify path); terminal mode = first Enter/submitted input line reaching the PTY (verify the input path; mail-injected turns count too). The user accepted that "saved but backend never created the conversation" is fine because of D4.
D4. When a resume fails specifically because there is no conversation to resume (`NoConversationToResume` class), start a FRESH session automatically. Other resume failures keep ADR-0082 behaviour (stop and report). Justification: nothing is lost when no conversation existed; ADR-0082's reason for forbidding fallback is not to silently lose a real conversation. This also cleans up existing profiles that already hold a garbage id, and claude/codex terminal. Must not loop (fresh spawn of a failed fresh must not retrigger). Needs an ADR amending ADR-0082 for this class.
D5. While a resumed incarnation waits for its history, the chat slot shows a NEW shared "loading panel" component (loading icon + optional text slot for other uses); for this use: icon only, NO text (flashing text looks like a bug). No existing spinner/loader in `src/` (grep of Loader2|Spinner|animate-spin = 0). Stack: Tailwind v4 + shadcn/ui + lucide-react; theme via CSS vars; `data-theme` dark/light/e-ink — on e-ink (and prefers-reduced-motion) show a static icon (orchestrator decision). No timer-based delay (ADR-0038 / ADR-0145:26 rejected timers). The waiting state ends when: first history item arrives, user sends input, the incarnation ends (veil as today), or D4 restarts fresh (new incarnation → flag false → splash).
