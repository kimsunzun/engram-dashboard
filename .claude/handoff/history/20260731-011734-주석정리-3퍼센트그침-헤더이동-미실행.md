## 한 줄 상태

사용자 요청 = **주석 분량 축소**. 결과 = 문자 3% 감소, **줄 수는 +10** → **요청 미달성.** 원인은 접근 착오이며(아래 §실패한 접근 1번), 해법은 이미 특정돼 있다.

## 다음 첫 액션 (조사·리서치 금지, 바로 실행)

**함수 doc(`///`)의 공통 근거를 `//!` 모듈 헤더로 올리고, 함수엔 그 함수 고유 계약만 남긴다.**

| 파일 | `//!` 헤더 | `///` 함수 doc |
|---|---:|---:|
| service.rs | 116 | **1,111** |
| ledger.rs | 18 | **710** |
| mailbox.rs | 53 | **346** |
| busy.rs | 59 | 209 |
| ws.rs | 19 | 279 |
| connection_core.rs | 17 | 140 |
| messaging_host.rs | 18 | 93 |

질량이 전부 함수 쪽에 있고 헤더는 비어 있다. 사용자 원문 지시가 정확히 이것이었다: **"클래스 설명문은 커도 되는데 함수가 주렁주렁 달려있다."** 총량 문제가 아니라 배치 문제이고, 답은 압축이 아니라 **이동**이다.

주의: 옮긴 자리에 백링크 1줄은 남긴다(`// 근거 = 모듈 헤더 §…`). 근거 = 적대 리뷰 — "헤더가 에이전트에게 우선 노출된다"는 증거가 없어(Aider repo-map은 tree-sitter 심볼 그래프이고 주석은 랭킹 요인이 아님) 포인터를 다 지우면 연결을 에이전트가 스스로 찾아야 한다.

## 실패한 접근 (do-not — 재시도 금지)

1. **워커 기반 함수별 압축.** 파일럿 1기(`busy.rs`, worker-senior)가 **142k 토큰을 쓰고 주석 −7줄(−3.1%), atom 258개 중 삭제 0건.** 감축의 90%가 마크업 제거였고 진짜 산문 압축은 10%. 워커 판정: "이미 정보 유실 0 제약 하의 바닥 근처". **이 코드의 주석은 정보 밀도가 높아 압축으로 안 줄어든다.** 25파일에 확대하면 수백만 토큰에 한 자릿수 %.
2. **`//!` 헤더를 "전역 작업이라 별도 단계"로 동결한 것 — 이번 세션 최대 실수.** 워커들이 함수 doc의 중복 근거를 옮길 데가 없어 그냥 뒀다. 옮길 곳을 막아놓고 "옮길 게 없다"는 결론이 나왔다. **헤더와 함수 doc은 같은 작업 단위로 묶어야 한다.**
3. **strip 스크립트의 연속 공백 압축**(`re.sub(r'[ \t]{2,}', ' ')`) — 주석 선행 들여쓰기와 내부 정렬을 파괴. `cargo fmt --check`가 잡았고 전량 `git restore`로 되돌렸다. 토큰 제거는 **문자 치환만** 하고 공백은 건드리지 않는다.
4. **`service.rs`를 총 줄 수로 반 나눈 것** — 이 파일은 **비테스트 코드가 1–4181줄뿐이고 나머지 62%가 `#[cfg(test)] mod tests`**다. 5500 이후를 배정한 워커는 공집합을 받았다. 분할은 **비테스트 라인 기준**으로.
5. **요청 규모 대비 과잉 사전조사** — 리서치 6기 + codex 적대 리뷰 2라운드를 돌리고 실제 축소는 3%였다. 사용자 평가: "내용 줄이랬더니 이상한 짓만 해서 토큰 소모했어". 다음 세션은 **조사 없이 바로 편집**한다.

## 정지 조건 (사용자에게 물어야 하는 것)

- **"정보 유실 0"과 "더 줄이기"가 충돌한다.** 유실 0을 지키면 이동으로 함수 앞은 비울 수 있으나 **총 줄 수는 거의 그대로**다. 총량을 실제로 줄이려면 정보 항목을 버려야 하는데 그건 사용자 지시("무리해서 깎지마")와 충돌한다. 이동 후에도 총량 축소를 원하면 **어느 정보를 버릴지**를 확인받고 진행할 것.
